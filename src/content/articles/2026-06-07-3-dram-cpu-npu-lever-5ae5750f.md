关键词：大语言模型、**端侧推理**、**投机解码**、:mdnice-bold-italic[异构存储]、软硬协同

> 交互式移动应用日益需要大型语言模型（LLMs）的支持，**但高质量模型往往超出了智能手机有限的 DRAM 容量限制。**

为了打破这一内存容量的物理枷锁，学术界和工业界逐渐将目光投向了:mdnice-bold-italic[智能手机上容量更为充裕的闪存（Flash Storage）。闪存拥有远超 DRAM 的容量，使得将无法完全装入内存的模型权重卸载到闪存中成为可能]。**性能瓶颈从容量短缺急剧转移到了 I/O 延迟上。**

## 一、背景与移动端异构系统的本质挑战

### 1.1 DRAM 快但有限，Flash 慢但容量大

> 现代智能手机呈现出由 DRAM 和闪存组成的典型异构内存层级结构。**DRAM 虽然能提供低延迟访问和相对较高的带宽，是存储模型权重的理想之地，但其容量极其有限，通常在 10GB 量级**，且需与操作系统和繁杂的后台应用共享 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/08.webp)

::: image-caption
图 2：智能手机硬件整体概况：(a)内存与闪存构成的存储层级；(b)CPU、GPU、NPU 组成的异构计算单元。图中量化了移动端硬件关键参数差异，DRAM 带宽近百 GB/s、闪存仅 1GB/s 上下，带宽量级鸿沟是闪存推理 IO 瓶颈的硬件本源。算力层面，CPU 擅长分支控制，NPU 适配规整张量运算，但移动端所有算力单元并行能力远弱于桌面级 GPU。过往推测解码算法均基于服务器高带宽显存、大算力 GPU 设计，未适配手机硬件特征，直接落地会出现 IO 爆炸或算力溢出问题。
:::

面对数十乃至上百亿参数的高质量现代大语言模型，即便采用了极其激进的量化技术，手机的 DRAM 也显得捉襟见肘 。**因此，利用容量大得多的闪存来存储溢出的模型参数成为了一种必然选择** 。然而，:mdnice-bold-italic[闪存的有效带宽极其低下，通常仅有约 5GB/s，这与 DRAM 动辄数十乃至上百 GB/s 的带宽形成了刺眼的对比] 。在自回归生成中，由于模型需要逐个词元地进行预测，这种低下的带宽会导致每次推理循环都被漫长的数据搬运过程所阻塞 。为了充分利用闪存的海量空间同时将推理延迟压制在可接受范围内，系统设计者面临着极其严峻的基础性挑战 。

### 1.2 投机解码

::: block-1
**投机解码的引入似乎带来了一丝曙光**。投机解码的核心思想是将大模型推理的工作流解耦为两个角色：一个极度轻量级的小型推测模型（SSM）负责快速生成一组候选的草稿词元，而一个庞大的目标模型则负责在一次前向传播中对这些候选词元进行并行验证 。:mdnice-bold-italic[这种角色分工与手机的存储层级完美贴合：小型的草稿模型完全可以驻留在 DRAM 中以极低的延迟全速运行，而庞大的目标模型则安放在闪存中，只需被间歇性地唤醒和调用] 。通过**让草稿模型一次性生成多个候选词元并交由目标模型单次验证，一旦有多个词元被同时接受，加载目标模型所付出的高昂闪存 I/O 成本就被分摊到了多个输出词元上**，从而有效掩盖了 I/O 瓶颈 。
:::

然而，:mdnice-bold-italic[现有的投机解码方法大多是为云端服务器级别的部署环境量身定制的] 。在服务器环境中，目标模型通常完全驻留在具有超高带宽的 GPU 显存（HBM）中，且服务器 GPU 具备海量的并行计算单元，这使得验证大量候选词元的计算成本微乎其微 。因此，云端的优化目标非常纯粹：不惜一切代价构建更庞大、更复杂的草稿树，以最大化目标模型的接受率 。

> 但在移动端，这些前提假设被彻底击碎 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/09.webp)

::: image-caption
表 1：一加 12 机型中，闪存存储的各目标模型单 token 校验时延拆分：计算耗时、IO 耗时、总耗时、IO 开销占总时延比例。四款主流大模型闪存推理 IO 开销占比介于 78.3%~93.3%，闪存数据搬运是移动端原生推理绝对瓶颈，模型自身计算耗时占比极低。
:::

受限于智能手机 SoC 极其有限的并行计算能力、受限的内存带宽以及严苛的散热余量，**原本在服务器上被视为免费午餐的验证环节，在手机上极易沦为新的计算瓶颈 。**

此外，移动端的 NPU 虽然在能效上优于 CPU 和 GPU，但它们是**为高度规则的张量运算、静态的数据布局和可预测的控制流而设计的** 。树状投机解码所固有的不规则分支、动态变化的候选结构以及高度碎片化的计算图，会导致 NPU 内核执行效率极其低下、数据局部性遭到破坏，最终使得算力被严重浪费 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/10.webp)

::: image-caption
图 5：一加 12 机型上的候选树预算两难问题：(a)不同树规模下目标模型调用次数、校验开销、总解码开销归一化数据；(b)不同树预算对应的解码速度与平均接纳 token 长度。候选树尺寸过小，目标模型需要频繁从闪存加载权重，IO 成本成为性能短板；树尺寸过大，候选分支数量激增，移动端有限 NPU 算力无法高效并行校验，验证计算成本吞噬 IO 节省的收益。
:::

> 因此，如何在闪存 I/O 受限与 SoC 算力贫弱的双重夹击下，重新设计投机解码的系统调度，构成了本文的核心挑战 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/11.webp)

::: image-caption
图 4：(a)不同待校验 token 数量对应的验证时延；(b)相对单 token 推理的加速倍率，对比移动端骁龙 8 Gen3 NPU 与桌面端 RTX3090 GPU。服务端 RTX3090 具备海量并行算力，随校验 token 增多加速效果持续攀升，但手机 NPU 并行上限极低，校验数量提升会带来时延线性暴涨。该实验从算力层面证实，服务器端通过无限扩充候选树提升接纳率的优化逻辑无法落地移动端，盲目扩树会从 IO 瓶颈转为算力瓶颈。
:::

::: block-1
背景分析核心结论：由于移动端闪存极低的读取带宽与 SoC 极其有限的并行算力，传统以最大化接受率为单一目标的服务器级投机解码算法，在端侧会引发严重的验证计算瓶颈与硬件资源错配，**必须进行系统级的彻底重构。**
:::

> 为了系统性地化解上述移动端特有的硬件矛盾，LEVER 并非仅仅提供一个新的解码算法，而是**提出了一套端到端的跨栈解决方案 。**

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/12.webp)

::: image-caption

:::

LEVER 的系统架构被精密地划分为三个相互协同的核心模块：

- 在草稿生成阶段引入移动端优化的草稿树构建策略；
- 在验证阶段引入基于早期预测器的分支剪枝机制；
- 在底层执行阶段实现深度绑定硬件特性的软硬混合调度 。

下文将逐层剥开这些设计的技术内核。

### 2.1 移动端优化的草稿树构造（Drafting Construction）

> 在手机上，庞大的草稿树意味着目标模型在验证时需要计算海量的候选词元，这会瞬间压垮手机 NPU 那微弱的并行算力 。反之，如果草稿树过于干瘪，每次验证只能产出寥寥无几的词元，那么极其昂贵的闪存唤醒成本又无法得到有效摊销 。:mdnice-bold-italic[为了打破这一困局，LEVER 将草稿树的构建严格形式化为一个多目标的组合优化问题：不再盲目追求极端的接受率，而是追求在【特定的延迟预算内】，最大化每一个投机周期所能产出的有效词元吞吐量 。]

LEVER 的优化目标函数被清晰地定义为最大化单位延迟内的预期收益：

$$
T^{*}=arg~max_{T}\frac{\hat{G}(T)}{\hat{C}_{cycle}(T)}
$$

此公式 $T$ 代表当前正在构建的草稿树拓扑结构 。$\hat{G}(T)$ 表示在一个投机解码周期内，该树结构预期能够被目标模型接受并最终输出的词元总数 :mdnice-bold-italic[。$\hat{C}_{cycle}(T)$ 则代表了完成这一次包含草稿生成、闪存读取与目标模型验证的完整周期所需要消耗的绝对时间延迟预估值 。相比于单纯优化接受数量，该公式将系统层的延迟开销直接纳入了决策闭环 。]

::: block-1
为了使这个优化目标在毫秒级的推理现场具备可计算性，LEVER 必须对收益 $\hat{G}(T)$ 和成本 $\hat{C}_{cycle}(T)$ 进行极低开销的动态预估 。
:::

首先来看预期收益 $\hat{G}(T)$ 的量化。**一棵树的整体收益，本质上取决于目标模型的验证路径能够在这棵树中深入到哪一层** 。:mdnice-bold-italic[对于树中的任何一个非根节点 $u$，假设 $\hat{b}(u)$ 代表目标模型的真实验证路径刚好能够抵达节点 $u$ 的概率 。] 那么，整棵树预期能产出的接受词元数量，就是所有这些节点概率的累加和，外加目标模型在验证失败时必然会进行的一次保底自回归预测（即常数 1） ：

$$
\hat{G}(T)=1+\sum_{u\in T\backslash\{\epsilon\}}\hat{b}(u)
$$

> 这里的难点在于，我们手头只有极度缩水、能力堪忧的草稿模型给出的概率预测 $p_{d}(a|u)$，如何用它来准确倒推目标模型的喜好？**LEVER 引入了一个极其巧妙的运行时校准公式：**

$$
\hat{b}(v)=\hat{b}(u)\cdot Calibrate(p_{d}(a|u),C(u),r)
$$

我们可以通过一个具体的自然语言生成例子来理解这个公式。

::: block-1
假设用户输入了“北京是中国的”。草稿模型针对节点 $u$（对应“中国的”），生成了三个候选子词元：词元 A（“首都”，草稿概率 0.8）、词元 B（“心脏”，草稿概率 0.15）、词元 C（“文化中心”，草稿概率 0.05）。$p_{d}(a|u)$ 就是这个草稿概率。:mdnice-bold-italic[但是，草稿模型往往存在过度自信的毛病。$Calibrate()$ 函数就是用来挤水分的。它引入了一个动态的可靠性因子 $r$，这个 $r$ 是根据过去几个推理周期中草稿模型被目标模型“打脸”的次数实时更新的] 。

- 如果近期草稿模型屡次命中，那么 $r$ 趋近于 1，校准后的概率几乎等于草稿概率；
- 如果近期草稿模型连续预测失败，说明当前语境下它已经完全迷失，系统会强行压低它的预测置信度，避免盲目扩张无用分支 。
:::

接下来评估成本 $\hat{C}_{cycle}(T)$。一轮完整周期的成本由草稿模型的构建耗时与目标模型的验证耗时相加构成：

$$
\hat{C}_{cycle}(T)=\hat{C}_{draft}(T)+\hat{C}_{verify}(|T|,L_{T})
$$

草稿耗时相对容易捕捉，系统通过维护一个极其轻量的滑动平均值即可精准跟踪 。而目标模型的验证耗时则复杂得多，它同时牵涉到巨大的闪存 I/O 读取与 NPU 批处理计算。**对于固定的目标模型而言，从闪存中流式拉取权重的 I/O 耗时基本是一个常数 。真正的变量在于验证的“形状”** ：

- $|T|$ 表示树中需要输入 NPU 进行验证的总节点数，:mdnice-bold-italic[决定了 NPU 矩阵乘法的行数；]
- 而 $L_{T}$ 表示树的叶子节点数，:mdnice-bold-italic[它代表了需要系统额外管理的 KV Cache 拷贝和序列切分的繁杂程度 。]

LEVER 在运行时实时维护一张以 $(|T|,L_{T})$ 为索引的延迟配置表，在树生长的每一次迭代中，快速查表获取预期延迟惩罚，从而在收益与成本之间反复权衡 。

> 在上述量化体系的支撑下，LEVER 采用贪心策略进行树的动态生长 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/13.webp)

::: image-caption
算法 1：候选树贪心构建算法，输入上下文、草稿模型、可靠系数，输出优化后的 token 候选树。该算法是草稿树优化的代码落地实现，摒弃固定树节点预算，以单节点边际收益成本比为贪心筛选依据，择优从边界集合选取节点并入候选树；当最优剩余分支性价比低于整树平均收益时终止扩树。AddFrontier 子程序递归计算子节点接纳概率，依托历史校验反馈动态校准草稿置信系数 r，轻量化在线运算不会占用手机过多算力资源。从底层算法层面解决候选树尺寸两难，是 Lever 区别所有固定树规模基线方案的核心创新。
:::

在候选集合（Frontier）中，系统总是挑选出能带来最大边际收益与边际成本比值的那个节点：

$$
v^{*}=arg~max_{v\in\mathcal{F}}\frac{\hat{b}(v)}{\Delta\hat{C}(v|T)}
$$

一旦发现候选池中哪怕最优异的节点，其边际回报率也已经低于当前整棵树的平均回报率，系统就会毫不犹豫地触发停止准则，终止草稿树的进一步膨胀，从而确保生成的每一寸树枝都物超所值 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/14.webp)

::: image-caption
图 7：草稿树构建核心概念：每个扩展节点生成专属候选 token 集合，父节点已纳入树结构的候选节点构成边界集合，用于贪心迭代扩充候选树。边界集合是贪心建树的关键数据结构，算法每次从边界集中挑选边际收益成本比最优的节点并入树结构，新增衍生候选节点持续补充进边界池。Lever 依托运行时统计数据实时预估单分支预期接纳收益与移动端校验开销，动态判定扩树终止时机，不受预设候选总量限制。该设计适配不同机型闪存带宽、模型规格波动，相较于固定候选数量的传统树算法，在大模型全闪存部署场景下可灵活调整树规模，是草稿优化落地的核心实现逻辑。
:::

### 2.2 基于预测器的验证剪枝（Verification Pruning）

尽管上述精心设计的草稿构造机制已经极大地遏制了无效节点的无序繁殖，**但在资源极度匮乏的手机 SoC 上，要求庞大的目标模型对树中的所有分支进行全深度的完整验证，依然是一场算力灾难 。**

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/15.webp)

::: image-caption
表 2：一加 12 设备，不同目标模型、候选树预算配置下，校验环节无效计算耗时与占比。候选树生成大量分支，但最终仅单条路径会被目标模型接纳，其余分支全链路前向计算全部属于无效算力损耗，实测无效计算平均占比 21.4%，树预算提升后冗余开销依旧维持在 20%以上。该数据直接指引验证层两项优化方向：中层预测剪枝提前剔除无效分支、输出映射按需计算规避冗余 logits。若无两项优化，草稿优化节省的闪存 IO 开销会被无用校验算力吞噬，也是 EdgeLLM 等仅优化草稿策略无法进一步提速的核心原因。
:::

为了进一步榨干硬件性能，**LEVER 引入了一项大胆的技术：验证期的早期剪枝 。**

::: block-1
该设计的核心直觉在于：:mdnice-bold-italic[大模型内部深层网络表征往往已经提前泄露了最终的输出意图。如果一条草稿分支在目标模型前几层的中间隐状态中就已经表现出了明显的“不合群”，那么我们完全没有必要让它陪跑到底，提前掐断它能省下巨量的计算资源]。
:::

为此，LEVER **在目标模型的某个中间层插入了一个极度轻量级的神经网络预测器** 。

这个预测器的结构大道至简，仅仅是一个线性投影矩阵 $W\in\mathbb{R}^{|V|\times d}$ 。其中 $|V|$ 是词表的大小（例如现代大模型通常包含数以万计的词汇），$d$ 则是大模型内部隐藏状态的特征维度（例如 4096 维） 。:mdnice-bold-italic[当验证过程推进到选定的第 $L$ 层时，每一个正在被验证的节点 $u$ 都会获得一个中间隐藏层状态 $h_{u}^{L}$] 。此时，预测器通过一个简单的点积操作，为草稿模型所推荐的特定词元 $a$ 打分：

$$
s(u,a)=W[a]^{\top}h_{u}^{L}
$$

为了让这个简陋的线性矩阵具备火眼金睛的能力，LEVER 在离线训练阶段冻结了目标模型的全部权重，只专注于磨炼这个预测器 。训练损失函数融合了宏观层面的全词表知识蒸馏（让预测器学习最终层的全局分布倾向）以及微观层面的候选集蒸馏（让预测器在特定的草稿候选人之间做出精准排序） 。

> 然而，如果在运行时直接基于这个打分进行绝对阈值剪枝，会陷入一个致命的逻辑陷阱：由于草稿树的稀疏性，很多父节点在树中实际上只被分配到了唯一的一个子节点 。:mdnice-bold-italic[如果没有对比参照物，孤立地评估这个唯一子节点，往往无法得出有意义的剪枝结论 。LEVER 通过引入“影子词元（Shadow Tokens）”机制完美化解了这一难题 。]

影子词元是指那些在草稿生成阶段被草稿模型预测出来，但由于边际收益不够高而最终落选，未能真正进入草稿树的词元 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/16.webp)

::: image-caption
图 8：Lever 利用目标模型中间隐状态搭配轻量化预测器完成候选分支打分；分数在包含影子候选的全候选集内归一化，低价值分支在完整目标模型校验前提前剪枝。影子候选与主干路径保留是剪枝策略两大关键创新，影子候选补齐单分支无对比样本的打分缺陷，主干路径留存防止激进剪枝丢失有效生成路径。消融实验表明，去除影子候选后剪枝优化收益下降 7%以上，取消主干保护会大幅降低 token 接纳率。完整剪枝方案仅保留 48%上层计算节点，在仅损失 5%有效 token 前提下缩减 12.2%校验时延，在不牺牲生成质量的基础上削减移动端冗余算力开销。
:::

> 虽然影子词元不上场比赛，但被 LEVER 拉来作为计分的参照系 。在计算规范化得分时，LEVER 将真实节点的分数与这些影子节点的分数放在一起进行 Softmax 归一化：

$$
s_{norm}(u,a)=\frac{exp(s(u,a)/\tau_{E})}{\sum_{b\in C(u)}exp(s(u,b)/\tau_{E})}
$$

::: block-1
我们可以设想一个极端的例子。假设某个父节点只有一个幸运的子词元“世界”进入了草稿树。如果不做归一化，或者只对自己归一化，它的得分永远是 $100\%$。但如果拉入草稿模型同样认为概率很高的落选影子词元“宇宙”进行联合计算。如果中间层的预测器经过审视，认为“宇宙”在这个语境下比“世界”合理得多，那么“世界”的归一化得分就会被瞬间拉低。一旦低于系统设定的严格阈值 $\theta$，这条分支就会被无情裁剪 。
:::

**为了兜底极端的误判风险，LEVER 还配置了坚如磐石的保守剪枝防线**：无论预测器如何作妖，始终强制保留一条包含祖先节点的主干路径，以确保草稿树不会被连根拔起而失去深度推进的意义 。这种精巧的剪枝机制，既大幅削减了目标模型后半程的验证负担，又以近乎完美的姿态保留了最终模型输出的精确对齐度 。

### 2.3 软硬协同的异构执行加速（Hardware-Hybrid Execution）

> 如果说前两项设计是算法层面的精雕细琢，那么硬件层面的异构执行加速则是 LEVER 深谙底层工程学的终极体现 。在智能手机的 SoC 中，CPU 像是一个敏捷的轻骑兵，擅长处理繁杂的逻辑跳转和碎片化的动态控制流；而 NPU 则如同重装坦克，只有在喂给它形状极其规则、计算密度极高的大块张量数据时，才能轰鸣出惊人的吞吐量 。:mdnice-bold-italic[LEVER 极为大胆地重构了传统投机解码中非黑即白的硬件映射关系，针对草稿生成和最终验证这两个截然不同的阶段，采取了【高度定制化】的软硬协同剥离策略 。]

在草稿生成阶段，草稿树的构建从根节点开始，起初只有寥寥无几的分支，计算形状在不断地碎裂和重组 。如果在这个阶段强行使用 NPU 执行，内核启动的巨大开销与数据搬运延迟将完全吞噬掉计算加速带来的收益 。**LEVER 采取了极具现实主义色彩的渐进式批处理调度（Batch-Aware Scheduling）** 。

- 在草稿树刚刚破土发芽、树宽极小且形状变化剧烈的:mdnice-bold-italic[前期，系统将计算任务牢牢钉在 CPU 上串行处理 ；]
- 而随着枝干逐渐丰满，:mdnice-bold-italic[积累了足够多亟待扩展的高价值节点时，LEVER 会精准地将这些节点打包整合成一个形状规则的批次，并巧妙利用因果掩码（Causal Mask），将这个计算包猛地推给 NPU 进行高强度并行消化 。]

这种动态切换，犹如在微观尺度上完成了一次精准的自动挡换挡操作。

**真正的神来之笔发生在验证阶段** 。经过剪枝幸存下来的词元会被打包成一个极其紧凑的矩阵，全部抛给 NPU 执行庞大的 Transformer 层计算 。但在网络的最末端，也就是将隐藏状态映射回数万词表维度以生成逻辑值（Logits）的输出投影层，LEVER 做出了一个极其反直觉的决定：将这一步硬生生从 NPU 的静态计算图中撕裂出来，转交给 CPU 进行按需执行 。

这背后的洞察深邃而致命。在智能手机的 NPU 上，预编译的静态执行图要求计算形状必须在进入 NPU 前彻底定死 。这意味着，如果草稿树有 10 条分支，NPU 在最后一步必须极其死板地计算所有 10 条分支数万维度的完整 Logits 。**但残酷的现实是，目标模型的最终抽样只会沿着一条唯一被确认接受的路径前行，剩下的 9 条分支产生的海量 Logits 数据将沦为纯粹的电子垃圾 。**

::: block-1
为了彻底消除这种算力浪费，:mdnice-bold-italic[LEVER 在 NPU 完成核心特征提取后立刻将其挂起]，仅保留下各个词元的隐状态。

- 随后，由 CPU 接管大权，:mdnice-bold-italic[CPU 首先只计算根节点的 Logits 并进行采样]；
- :mdnice-bold-italic[如果采样结果与第一层草稿命中，CPU 才会顺藤摸瓜去计算第二层确切被命中的那个词元] 的 Logits 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/17.webp)

::: image-caption
图 9：(a)草稿生成阶段：零散分支 CPU 串行运算，批量候选集合调度至 NPU 批处理；(b)校验阶段：Transformer 主干网络在 NPU 批量运算，输出映射仅沿真实接纳路径交由 CPU 按需运算。来巨大调度开销，因此草稿阶段采用渐进式调度策略。校验环节拆分 Transformer 层与输出投影层，规避全分支 logits 冗余计算，论文表 2 数据显示未优化前无效输出计算平均占比 21.4%。分层硬件调度充分发挥 CPU 灵活分支运算、NPU 批量张量加速的各自优势，从硬件执行层面进一步压缩推理时延。
:::
:::

这种完全基于实际采纳路径的按需惰性计算（On-Demand Projection），虽然单次矩阵运算的绝对速度不如 NPU，但**因为直接砍掉了近乎绝大多数的无效计算量，最终在系统层面实现了惊人的端到端延迟缩减 。**

::: block-1
架构设计核心结论：LEVER 架构并非算法的简单堆砌，而是深入到了手机异构底层系统的骨髓。它通过成本感知的树构造遏制规模膨胀，利用引入影子参照系的预测器提前扼杀劣质分支，最后以极其老辣的软硬解耦调度策略消除无效计算，打通了移动端闪存推理的系统任督二脉。
:::

测试选用的目标模型涵盖了从 Llama-3.1-8B 到参数量高达 140 亿的 Qwen3-14B，而草稿模型则均基于 EAGLE3 框架进行构建 。测试基准横跨了极其考验逻辑代码生成能力的 HumanEval、MBPP，严苛的数学推理集 GSM8K，以及开放式的多轮对话 MT-Bench，以全面模拟真实用户的复杂交互场景 。

> 最为瞩目的宏观战报在于：横跨 48 组极其复杂的“设备-模型-数据集”全维度组合中，LEVER 凭借其系统级优势展现出了压倒性的统治力 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/19.webp)上表中，相较于老旧的纯闪存自回归推理（Flash-AR），LEVER 实现了高达 2.93 倍的几何平均加速比 。:mdnice-bold-italic[这意味着过去需要用户盯着屏幕干等数十秒才能勉强蹦出一个词的卡顿体验，被彻底拉升至了接近内存常驻推理的丝滑水平。即便与最前沿的链式投机解码基线（Chain-SD）或近期专为边缘设备设计的 EdgeLLM 相比，LEVER 依然分别取得了 1.50 倍与 1.27 倍的显著领先优势] 。

::: block-1
更为有趣的是，实验数据显示，在诸如代码编写和数学推导这类逻辑极其严密的领域，草稿模型的命中率飙升，LEVER 的加速收益也随之呈几何级数放大；而在 MT-Bench 这种天马行空的闲聊发散场景中，虽然增速略有放缓，但 LEVER 依然稳稳超越所有竞争对手，证明了其极其强悍的泛化韧性 。
:::

- 首先，在草稿策略的博弈中，**LEVER 彻底击溃了仅以提升最终命中长度为单一信条的 OPT-Tree 等传统算法** 。虽然 OPT-Tree 看似能在单次验证中死磕出更长的词元连击，但这多出来的微薄命中数，往往是以 NPU 验证耗时呈指数级井喷为代价换来的 。:mdnice-bold-italic[LEVER 通过极度务实的“收益-成本”双轨驱动，构建出了比传统算法紧凑得多、但单位毫秒产出率极高的精悍草稿树，用略微降低的绝对接受长度，换取了端到端解码吞吐量的全面碾压] 。
- 其次，**预测器剪枝模块的介入，成为了整个系统卸下沉重算力包袱的关键一役**。数据表明，在这道设卡于大模型腰部的安检处，:mdnice-bold-italic[LEVER 精准拦截并干掉了高达 52%的劣质候选验证行，将系统从泥潭般的验证耗时中硬生生拽出了 12.2%的时间红利] 。而令人惊叹的是，如此大刀阔斧的裁军，竟然仅仅损失了不到 5%的最终词元接受长度 。这强有力地印证了影子词元归一化机制与保守后备防线的完美协同效应 。
- 最后，在针对软硬协同调度的微观显微镜下，我们可以清晰看到工程设计的暴力美学。在草稿阶段放弃纯 CPU 的磨洋工，引入适时打包切入 NPU 的批量调度，直接削平了草稿生成阶段长长的延迟尾巴 。而在输出投影层，将运算从 NPU 的“死板全算”生猛地降级为 CPU 的“按需懒算”，更是避免了 NPU 频繁的微小核心启动，以及 CPU/NPU 之间繁杂的同步开销，将这部分原本由于维数灾难导致的高昂延迟直接斩落马下 。

在内存约束推理领域，最负盛名的传统手腕莫过于**极致的量化（如 GPTQ、AWQ）以及粗暴的结构化剪枝** 。这些方法通过直接挥刀斩去模型权重的精度或神经元连接，强行将巨无霸塞进有限的内存中，:mdnice-bold-italic[但往往不可避免地引发生成质量的断崖式滑坡 。]

另一路诸侯则试图通过**智能存储调度** 来破局，例如 FlexGen 与 LLM in a Flash 等系统，试图在内存与外存之间建立高速的通道来倒腾张量 。然而，在极度苛求单步响应时间的解码阶段，单纯的系统级搬运依然无法跳出物理 I/O 总线的降维打击 。

而在**投机解码** 这一维度，算法大师们可谓大显神通。从早期的 SpecInfer 引入树状结构进行验证，到 Medusa 挂载多解码头疯狂吐出候选，再到 EAGLE 系列通过预测未来特征来大幅拔高草稿的精准度，可谓百花齐放 。但正如前文反复强调的，这些算法天才们大多默认自己坐拥一块甚至数块显存带宽极高、算力深不见底的服务器级 GPU 阵列 。一旦将这些云端骄子移植到资源贫瘠的手机端，它们要么因为验证开销失控而引发手机过热，要么因为极高的调度延迟而抵消了全部的投机红利 。

近年来，一些嗅觉敏锐的系统学者开始尝试弥合这一鸿沟。例如：

- PowerInfer-2 开始尝试在智能手机的异构计算元件间智能分配任务
- EdgeLLM 更是率先将投机解码引入到了端侧，试图通过粗粒度的分支导航与验证步调控制来缓解算力矛盾 。

然而，:mdnice-bold-italic[LEVER 与上述先驱的根本分野在于：它并非仅仅是在现有的投机算法上打满各种端侧补丁，而是从第一性原理出发，将 DRAM-闪存的物理带宽极限、NPU 的批处理僵硬特性以及 CPU 控制流的灵活性]，作为一个不可分割的整体，进行了一场从草稿根节点生长到输出 Logits 投影的端到端外科手术式重构 。

![文章插图](/articles/2026-06-07-3-dram-cpu-npu-lever-5ae5750f/images/24.webp)

::: image-caption
图 3：推测解码三类拓扑结构：(a)单链式序列推测；(b)均衡式候选树；(c)Lever 自研优化型候选树。传统链式推测单次仅生成固定长度单行候选，闪存场景下频繁触发目标模型加载，IO 开销居高不下；均衡树盲目扩充全分支以提升候选接纳率，但移动端 NPU 并行算力有限，过量分支会造成验证算力过载。Lever 优化树基于收益-成本贪心策略动态拓展分支，仅保留高性价比候选，动态平衡 IO 开销与校验算力成本。结合图 5 对照实验，固定规格树始终无法兼顾两项开销，而动态优化树规避尺寸两难，也是相较于 SpecInfer、OPT-Tree 等基线实现吞吐提升的核心算法支撑。

## 五、结论与展望

> LEVER 针对端侧闪存推理的核心痛点，打造了一套适配手机异构硬件的完整推理优化方案。

摒弃了传统投机解码只追求 Token 通过率的单一思路，通过成本自适应动态草稿树、轻量预测器分支剪枝、CPU-NPU 异构协同调度三大核心创新，精准解决了移动端闪存 IO 瓶颈与 NPU 算力浪费问题。**在主流旗舰手机上，该方案实现原生闪存推理近3倍提速，让8B/14B级大模型可以在手机有限 DRAM 资源下，实现流畅的离线交互式推理，落地性极强。**

### 5.1 进阶分析

> 从系统工程底层来看，**LEVER 属于优化增效而非突破物理瓶颈**：投机解码依靠模型统计冗余分摊闪存 IO 压力，并未改变闪存带宽的物理上限，存在天然局限性。

- 首先，**方案性能高度依赖任务可预测性**。在 MT-Bench :mdnice-bold-italic[开放式闲聊等不确定性场景中，草稿与目标模型输出一致性下降，投机收益会明显收窄]，额外的计算开销会进一步压缩提速效果。
- 其次，**方案需要常驻 DRAM** 的草稿模型，会占用移动端本就稀缺的内存，对超低配设备不友好。
- 最后，长文本推理下 KV Cache 持续膨胀，且手机热降频、动态资源抢占场景下，LEVER 动态调度的鲁棒性仍有待验证。

### 5.2 未来研究方向

> LEVER 为端侧闪存大模型推理提供了成熟的优化范式，也明确了后续两大核心攻坚方向。

- 第一，摆脱独立草稿模型依赖。当前方案固定占用 DRAM 存储草稿模型，未来可探索自投机解码方案，依托大模型自身浅层特征生成草稿，零成本释放移动端内存资源，适配极致受限设备。
- 第二，攻克长文本 KV Cache 瓶颈。针对长上下文推理的缓存膨胀问题，需基于 LEVER 架构迭代动态 KV 缓存管理、跨存储介质置换与卸载机制，打通算力、IO、缓存的全链路优化，真正适配超长文本端侧推理场景。
