## 1. 复杂语言模型程序的高效执行与优化技术

> ❝
>
> 最近大型语言模型（LLMs）能力的提升扩展了它们的用途，使它们能够处理更广泛的通用任务并充当自主智能体（autonomous agent）。在这些应用中，LLMs 会进行多轮规划、推理，并与外部环境交互。这通过工具使用、多种输入模态和广泛的提示技术实现，例如少样本学习、自一致性、思维骨架和思维树。**所有这些新用例都需要多次**、通常是**相互依赖的 LLM 生成调用**，显示出使用多调用结构完成复杂任务的趋势。

这种模式的出现标志着我们**与 LLMs 交互方式的转变，从简单的聊天转向更复杂的 LLM 编程式使用**，这意味着**使用程序来调度和控制 LLM 的生成过程**。我们将这些程序称为“语言模型程序”（LM Programs）。上述高级提示技术和智能体工作流都属于 LM 程序的范畴。**LM 程序有两个共同特性**：

1. LM 程序通常**包含多个 LLM 调用**，并且这些调用之间**夹杂着控制流**。这需要完成复杂任务并提高整体质量。
2. **LM 程序接收结构化输入** 并**产生结构化输出**。这使得 LM 程序能够组合使用，并集成到现有的软件系统中。

尽管 LM 程序得到了广泛应用，但表达和执行它们的系统仍然效率低下。我们识别出与 LM 程序高效使用相关的两个主要挑战：

1. 首先，由于 **LLM 的非确定性特性，编程 LM 程序既繁琐又困难**。开发 LM 程序通常需要大量的字符串操作、**实验性提示调整**、脆弱的输出解析、**多种输入模态的处理以及并行机制的实现**。这种复杂性显著降低了即使是简单程序的可读性（第 2 节）。
2. 其次，执行 **LM 程序的效率低下是由于冗余计算和内存使用**。现有的推理引擎（例如 vLLM、TGI 和 TensorRTLLM ）在没有直接了解工作负载的情况下进行了优化，以减少延迟并提高吞吐量。这使得这些系统通用且稳健，但也导致了**针对特定工作负载的显著低效**。

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/06.webp)

> ❝
>
> 为了解决这些挑战，我们提出了 **SGLang（a Structured Generation Language for LLMs），这是一种用于 LLM 的结构化生成语言**。核心思想是**系统地利用 LM 程序中的多调用结构以实现高效执行**。

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/07.webp)

如图 1 所示，它包含两个部分：**一个前端语言和一个后端运行时**。

- 前端简化了 LM 程序的编程。
- 而后端加速了它们的执行。

这两部分可以协同工作以提高性能，也可以独立运行。

### 语言前端和解释器

我们以嵌入在 Python 中的领域特定语言（domain-specific language，即专门针对某一特定领域设计的编程语言）的形式引入 SGLang。它提供了用于生成（例如 extend、gen、select）和并行控制（例如 fork、join）的原语。

**SGLang 与 Python 的控制流和库兼容**，因此用户可以**使用原生的 Python 语法轻松开发高级提示工作流**。我们为 SGLang 提供了**解释器和编译器**。解释器将**提示状态管理为一个流，并将原语操作提交给该流以异步执行，确保对同步和程序内并行的正确控制**。此外，SGLang 程序**可以被跟踪和编译** 以实现更多优化。

### 运行时

在运行时方面，我们提出了几种新颖的优化技术来加速 SGLang 程序的执行。

- 第一种技术是 RadixAttention，它能够**自动复用多个生成调用中的 KV 缓存**。在现有的推理引擎中，请求的 KV 缓存在处理完成后会被丢弃，这阻止了不同调用之间的 KV 缓存复用，显著减慢了执行速度。相反，我们的系统**在基数树** （radix tree，一种高效的数据结构，用于存储和匹配前缀）**中维护所有请求的 KV 缓存的 LRU** （Least Recently Used，最近最少使用）**缓存**。这种方法**将 KV 缓存作为传统缓存来管理，并使用基数树进行高效匹配、插入和驱逐**。它允许运行时通过缓存感知调度策略高效地处理各种复用模式。
- 第二种技术是压缩有限状态机，它能够**更快** 地进行**结构化输出的约束解码**。现有系统仅遵循下一个 token 的约束，通过屏蔽不允许的 token 的概率来实现，这使得它们每次只能解码一个 token。相反，我们的系统分析约束并构建压缩有限状态机来表示约束。这种方法尽可能将多 token 路径压缩为单步路径，从而允许一次性解码多个 token，以实现更快的解码速度。最后，SGLang 还支持仅通过 API 提供的模型（如 OpenAI 的 GPT-4）。
- 我们引入了第三种技术，即 API 投机执行（API speculative execution），以优化多调用程序对仅 API 模型的调用。

使用 SGLang，我们实现了各种 LLM 应用，包括智能体控制、逻辑推理、少样本学习基准测试、JSON 解码、检索增强生成管道、多轮对话和多模态处理。我们在 NVIDIA A10G 和 A100 GPU 上测试了包括 Llama7B/70B 、Mistral-8x7B 、LLaVA-v1.5-7B（图像）] 和 LLaVA-NeXT-34B（视频）在内的模型。实验结果表明，与现有的编程和推理系统（包括 Guidance 、vLLM 和 LMQL ）相比，**SGLang 在各种工作负载、模型和硬件设置上实现了高达 6.4 倍的吞吐量提升**。

### SGLang 架构概览

下图中展示了 SGLang 的整体架构，分为客户端（Client）和服务器端（Server）两部分。

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/09.webp)

下面先单独介绍图中的客户端和服务端。

#### 1. 客户端（Client）

客户端是用户与 SGLang 交互的入口，负责将用户的请求发送到服务器端并接收结果。客户端包含以下模块：

1. 原生生成 API（Native generation API）：提供直接与模型交互的接口，支持本地模型的生成调用。
2. OpenAI 兼容 API：支持与 OpenAI 提供的模型（如 GPT-4）进行交互，允许用户使用 OpenAI 的 API 进行生成任务。
3. 结构化语言前端（Structured language frontend）：**这是 SGLang 的核心前端部分**，提供了一种嵌入在 Python 中的领域特定语言（DSL），简化了复杂语言模型程序的编程。用户可以**通过 SGLang 的语法（如 gen、select、fork 等原语）编写程序，控制模型的生成和并行执行**。

#### 2. 服务器端（Server）

服务器端负责处理客户端的请求并执行模型推理。服务器端包含以下模块：

1. API 服务器分词器（API server Tokenizer）：接收客户端的请求，将输入文本转换为模型可以处理的 token，这是模型生成的基础。初步处理后，将请求转发到调度器和模型工作者。它还负责将结果返回给客户端。
2. 解码器（Detokenizer）：将模型生成的 token 转换回可读的文本，以便客户端能够理解结果。
3. 调度器与模型工作者（Scheduler & Model Worker）:这是**服务器端的核心** 部分，**负责模型的执行和优化**。

调度器与模型工作者包含下面组件：

- KV 缓存内存池（KV Cache memory pool）：用于存储生成过程中产生的中间张量（KV 缓存）。每个页面的大小为 1 个 token，以支持高效的缓存管理。
- **基数树缓存** （Radix tree cache）：一种基于**基数树的数据结构**，用于**高效地匹配和复用具有相同前缀的请求的 KV 缓存**。这是 **SGLang 的核心优化技术之一**，能够显著**减少冗余计算和内存使用**。
- 有限状态机分析器（Finite state machine analyzer）：用于结构化输出的约束解码。它将正则表达式转换为有限状态机，并通过压缩有限状态机加速解码过程。
- 注意力后端（Attention backend）：使用 FlashInfer 和 Triton 等优化工具加速注意力计算。这些工具通过高效的内存管理和并行计算显著提高了模型的推理速度。

#### 3. 工作流程

整体工作流程为:

1. 客户端发送请求：用户通过 SGLang 的前端编写程序，并通过 API 或 OpenAI 兼容接口将请求发送到服务器端。
2. 服务器处理请求：API 服务器接收请求并将其转发到调度器和模型工作者。调度器根据缓存感知策略选择合适的缓存数据，模型工作者执行生成任务。
3. KV 缓存复用：基数树缓存管理 KV 缓存，复用具有相同前缀的请求的缓存数据，减少冗余计算。
4. 结构化输出解码：有限状态机分析器根据约束条件生成结构化输出，压缩有限状态机加速解码过程。
5. 结果返回：解码后的结果通过解码器转换为可读文本，并返回给客户端。

通过这种架构设计，SGLang 能够高效地执行复杂的语言模型程序，同时支持多种模型和 API，为用户提供了灵活且高效的开发和执行环境。

### 2.1 运行示例

SGLang 是一种嵌入在 Python 中的领域特定语言（DSL），使用分支-解决-合并提示技术（branch-solve-merge prompt）。

> ❝
>
> ## 知识补充：分支-解决-合并提示（branch-solve-merge prompt）
>
> Branch-Solve-Merge（BSM）是一种用于提升大型语言模型（LLM）在多方面语言任务中的表现的方法。它通过将复杂任务分解为多个并行子任务、独立解决这些子任务，并将它们的解决方案融合，从而提高模型的性能和一致性。

> ❝
>
> 下面这幅图通过一个具体的例子说明了 BSM 的三个模块（分支、解决、合并）是如何协同工作的。先将问题分解成多个子任务（分支），然后分别解决每个子任务（解决），最后将结果整合起来（合并），从而得出一个全面且可靠的判断。这种方法能够提高 LLM 评估的准确性和一致性，同时减少偏见。[图片]常见的应用场景比方受限制文本，如某些特定要求场景下的故事生成。一个具体的例子，如在评估一篇作文时，分支模块可以将任务分解为多个维度（如清晰度、原创性和证据）。求解时，每个维度的评估也可以单独进行，生成每个维度的评分和反馈。最终，将每个维度的评分和反馈整合为一个综合的评估结果。

图 2 展示了一个使用分支-解决-合并（branch-solve-merge）提示技术评估一篇关于图片的作文的程序。

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/10.webp)

函数 `multi_dimensional_judge` 接受三个参数：`s`、`path` 和 `essay`。`s` 管理提示状态，`path` 是图片文件路径，`essay` 是作文文本。使用 `+=` 操作符可以将新的字符串和 SGLang 原语追加到状态 `s` 中以供执行。

首先，函数将图片和作文添加到提示中。然后使用 `select` 检查作文是否与图片相关，并将结果存储在 `s["related"]` 中。如果相关，则使用 `fork` 将提示状态分成三个副本，用于从不同维度并行评估。使用 `gen` 存储结果在 `f["judgment"]` 中。接下来，合并评估结果，生成总结和评分，并以 JSON 格式返回结果。SGLang 大幅简化了这个程序，因为使用类似 OpenAI API 的接口编写的等效程序需要多 2.1 倍的代码行数，因为需要手动进行字符串操作和并行控制。

### 2.2 语言原语

SGLang 提供了用于控制提示状态、生成和并行控制的原语。它们可以与 Python 语法和库一起使用。以下是原语：

- `gen`：调用模型生成文本，并将结果存储在指定变量中。它支持通过正则表达式约束输出以遵循语法（例如 JSON 模式）。
- `select`：调用模型从列表中选择概率最高的选项。
- `+=` 或 `extend`：将字符串追加到提示中。
- `[variable_name]`：获取生成结果。
- `fork`：创建提示状态的并行副本。
- `join`：合并提示状态。
- `image` 和 `video`：处理图像和视频输入。

### 2.3 执行模式

执行 SGLang 程序最简单的方法是通过**解释器** 实现，**将提示视为异步流**。像 `extend`、`gen` 和 `select` 这样的原语被提交到流中以异步执行。这些非阻塞调用允许 Python 代码在等待生成完成之前继续运行。这类似于异步启动 CUDA 内核。每个提示由后台线程中的流执行器管理，启用程序内并行。但是，**获取生成结果前会被一直阻塞，直到结果准备好**，确保正确的同步。

或者，SGLang 程序可以被编译为计算图并通过**图执行器** 执行，**允许更多的优化**。本文默认使用解释器模式。SGLang 支持其自己的 SGLang 运行时（SRT）的开放权重模型，以及 OpenAI 和 Anthropic 模型等 API 模型。

- 低级系统通常不修改提示，但允许直接操作提示和原语。

## 3. 使用 RadixAttention 高效复用 KV 缓存

> ❝
>
> SGLang 程序通常会链式调用多个生成操作，并使用 fork 原语创建并行副本（在 SGLang 中，fork 操作用于创建提示状态的并行副本。这些副本可以独立处理不同的子任务）。因此，**不同的程序实例** 通常会**共享一些公共部分** （例如系统提示）。这些场景在执行过程中会**生成许多共享的提示前缀**，从而**提供了许多复用 KV 缓存的机会**。在 LLM 推理过程中，KV 缓存存储了前向传递中的中间张量，这些张量用于解码未来的 token。**KV 缓存的计算仅依赖于前缀 token**，因此具有**相同提示前缀的请求可以复用 KV 缓存，从而减少冗余计算和内存使用**。

鉴于 KV 缓存复用的机会，优化 SGLang 程序的一个关键挑战是**在多个调用和实例之间复用 KV 缓存**。虽然一些系统探索了某些 KV 缓存复用场景，但它们**通常需要手动配置**，并**且无法处理所有复用模式** （例如动态树结构）。因此，**大多数最先进的推理系统对每个请求重新计算 KV 缓存**。我们将在第 7 节相关工作（Related Work）中讨论它们的局限性以及我们的不同之处。

### 3.1 技术原理

为了优化 SGLang 程序中的 KV 缓存复用，我们提出了 **RadixAttention**，这是一种在**运行时自动且系统地复用 KV 缓存的技术**。

**与现有系统在生成请求完成后丢弃 KV 缓存不同**，我们的系统将所有请求的 KV 缓存——提示和生成结果，都保留在一个**基数树（radix tree）** 中，从而实现高效的前缀搜索、复用、插入和驱逐。我们实现了：

1. 基于最近最少使用（LRU）策略的缓存驱逐。
2. 并设计了缓存感知调度策略以提高缓存命中率。

RadixAttention 与连续批处理（continuous batching）、分页注意力（paged attention）和张量并行（tensor parallelism）等技术兼容。此外，当没有缓存命中时，它只会引入可以忽略不计的内存和时间开销。

#### 3.1.1 RadixAttention（基数树）

RadixAttention（基数树）是一种数据结构，作为经典前缀树（trie）的空间效率替代方案。与典型树不同，**基数树的边不仅可以 token 单个元素，还可以 token 不同长度的元素序列**，显著提高了效率。在我们的系统中，我们使**用基数树来管理 token 序列及其对应的 KV 缓存张量之间的映射**。这些 KV 缓存张量以非连续的分页布局存储，每页大小相当于一个 token。

由于 GPU 内存很快会被 KV 缓存填满，我们引入了简单的 LRU 驱逐策略，优先驱逐最近最少使用的叶子节点。通过首先驱逐叶子节点，我们使得它们的公共祖先可以被复用，直到这些祖先也成为叶子节点并被驱逐。

在连续批处理设置中，我们不能驱逐当前正在运行的批处理所使用的节点。因此，**每个节点维护一个引用计数器，表示有多少正在运行的请求正在使用它**。如果**节点的引用计数器为零，则可以驱逐该节点**。请注意，我们没有预分配固定大小的内存池作为缓存。相反，我们让缓存的 token 和当前正在运行的请求共享同一个内存池。因此，系统动态地为缓存和正在运行的请求分配内存。**当有足够的等待请求运行时，系统将驱逐所有缓存的 token 以支持更大的批处理大小**。

> ❝
>
> 想象你有一个文件夹系统，文件夹代表缓存数据。当有新的请求（如聊天消息或查询）时，系统会检查是否有相关的文件夹（缓存数据）。如果有，它会复用这些文件夹；如果没有，它会创建新的文件夹。为了节省空间，系统会定期删除最近最少使用的文件夹。

通过这种方式，RadixAttention 动态管理缓存数据，确保高效利用内存并提高缓存命中率。

#### 3.1.2 缓存感知调度

我们定义缓存命中率公式为：`缓存命中率 = 缓存的提示 token 数量 / 提示 token 总数量`。当等待队列中有请求时，它们的执行顺序会显著影响缓存命中率。例如，如果请求调度程序频繁在不同的、不相关的请求之间切换，可能会导致缓存抖动和低命中率。

我们**设计了一种缓存感知调度算法来提高缓存命中率**。在批处理设置中，我们根据匹配的前缀长度对请求进行排序，并优先处理匹配前缀较长的请求，而不是采用先到先服务的调度方式。

算法 1展示了具有连续批处理的缓存感知调度的伪代码。看着很长，这里简单**对流程描述** 一下，更容易看明白：

- 获取请求：先从等待队列中获取所有待处理的请求
- 前缀匹配：对每个请求，使用基数树进行前缀匹配，找到最长的匹配前缀
- 排序：根据匹配的前缀长度对请求进行排序，优先处理匹配前缀较长的请求
- 选择新批次请求：计算可用内存大小，选择可以放入当前批次的请求
- 更新：将选中的请求合并到当前运行批次中
- 内存分配和驱逐：分配内存以处理新批次的请求。如果内存不足，根据 LRU 策略驱逐缓存数据
- 处理完成的请求：处理完成的请求，更新缓存状态，并将结果返回
- 循环处理：循环重复上述步骤，直到所有请求处理完成

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/15.webp)

该算法采用最长共享前缀优先的顺序。在更敏感于延迟的设置中，可能仍然可以容忍有限的批处理重排序以提高缓存复用率。此外，我们证明了以下定理 3.1，涉及离线情况下的最优调度。

#### 定理 3.1

> ❝
>
> 对于一批请求，我们可以通过按**深度优先搜索顺序遍历请求的基数树** 来**实现最优的缓存命中率**，**前提** 是`缓存大小 ≥ 最大请求长度`。最长共享前缀优先顺序等同于深度优先搜索顺序。

更具体的证明过程在附录的第 A.3 节（本文我就不理了出来了）。在在线情况下，深度优先搜索顺序可能会被打乱，但我们的调度仍然近似于在完整基数树的扩展部分上的深度优先搜索行为，如第 A.3 节所述。**虽然贪婪的缓存感知调度可以实现高吞吐量**，但它**可能导致** 某些请求长期得不到处理（**饥饿问题**）。我们将其与其他公平调度方法的集成留作**未来的工作**。

#### 3.1.3 分布式环境下的数据并行 RadixAttention

> ❝
>
> RadixAttention 可以扩展到多个 GPU。对于张量并行，每个 GPU 维护一个分片的 KV 缓存。由于树操作相同，因此不需要额外的同步。

为了将 RadixAttention 适应于具有多个副本工作进程的分布式环境（即数据并行），我们开发了一种机制，其中**每个工作进程维护自己的子树**，而**路由器监督一棵元树**。这**棵元树作为一棵前缀树，用于跟踪所有子树及其相关的设备**。

当路由器接收到一批新请求时，会在元树上执行前缀匹配。我们根据每个请求的亲和力（通过与特定工作进程和其他同组请求共享的前缀长度来衡量）实现了各种策略，以做出高效的调度决策，从而最小化冗余计算。

每次处理新请求时，路由器和工作进程都会独立更新各自的树。如果某个工作节点发生缓存驱逐，它会将此驱逐操作提交到一个队列中，路由器在低活动期间处理此队列以更新元树。我们使用四个工作进程和 MMLU 数据集对这种分布式配置进行了基准测试，观察到**其性能实现了线性扩展**，并且在这种**弱一致性分布式缓存设计中** 实现了**最优的缓存命中率，同时开销极小**。在**最大化数据局部性和并行处理效率之间存在权衡**。探索先进的调度策略以优化这种权衡被指定为未来研究的一个领域。此外，基于 SGLang 的早期版本的 Preble 的并发工作，也做了有关数据并行调度的研究。

### 3.2 具体实现

实现包括如下模块：

1. 基数树缓存：使用基数树（一种空间效率高的数据结构）管理提示序列与对应的 KV 缓存张量之间的映射。这些 KV 缓存张量以非连续的分页布局存储，每页大小相当于一个 token。
2. LRU 缓存驱逐：由于 GPU 内存很快会被 KV 缓存填满，我们引入了简单的 LRU 驱逐策略，优先驱逐最近最少使用的叶子节点。
3. 缓存感知调度：我们设计了一种缓存感知调度算法，以提高缓存命中率。在批处理设置中，我们根据匹配的前缀长度对请求进行排序，并优先处理具有较长匹配前缀的请求。

### 3.3 应用场景

- 多轮对话：共享对话历史的缓存数据。
- 少样本学习：共享示例的缓存数据。
- 智能体控制：共享智能体模板的缓存数据。

RadixAttention 是一种高效的 KV 缓存复用技术，通过基数树缓存和缓存感知调度，显著减少了冗余计算和内存使用，提高了复杂语言模型程序的执行效率。

## 4. 使用压缩有限状态机实现高效的约束解码

> ❝
>
> 在语言模型程序（LM 程序）中，**用户通常希望模型的输出遵循特定的格式，例如 JSON 模式**，这可以提高模型输出的可控性和鲁棒性，并**使输出更易于解析**。

**SGLang 提供了一个 regex 参数**，用于通**过正则表达式** 强制**执行这样的约束**，这在许多实际场景中足够表达需求。现有的系统通过将正则表达式转换为有限状态机（FSM）来支持这一点。

在解码过程中，它们维护当前 FSM 状态，检索下一个状态允许的 token，并将不允许的 token 的概率设置为零，逐个 token 进行解码。然而，这种方法在有机会一次性解码多个 token 时效率低下。

> ## 知识补充：有限状态机、压缩有限状态机
>
> ### 什么是有限状态机（FSM）？
>
> 有限状态机是一种数学模型，用来描述对象的行为。它由一系列状态和状态之间的> 转换规则组成。想象一个简单的交通信号灯：
>
> - 状态：红灯、黄灯、绿灯。
> - 转换规则：红灯变绿灯，绿灯变黄灯，黄灯变红灯。
>
> ### 什么是压缩有限状态机？
>
> 压缩有限状态机是对普通有限状态机的**优化**。它的目标是**减少冗余状态，使状态机更紧凑、更高效**。例如，如果有**一系列连续的单一步骤** （如红灯直接变绿灯，而不需要经过黄灯），**可以** 将这些步骤**合并为一个步骤**。

> ### 来个例子：越简单越好
>
> 想象你需要生成一个符合以下格式的文本：`{"name": "John", "age": 30}`。
>
> - 普通有限状态机：每一步都检查一个字符，确保格式正确。第一步：检查 `{`第二步：检查 `"`第三步：检查 `n`第四步：检查 `a`第五步：检查 `m`第六步：检查 `e`第七步：检查 `"`依此类推。
> - 压缩有限状态机：将连续的检查步骤合并。例如，直接检查 `{"name":`，减少步骤数量。
>
> 压缩有限状态机通过减少冗余状态，使后续约束解码更高效。在确保生成的文本符合特定格式下，同时提高了生成速度。

例如，图 2 中的常量序列 `{"summary": "` 在正常解码过程中会跨越多个 token，如图 4（c）所示，需要多个解码阶段，即使在解码过程中只有一个有效的下一个 token。

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/16.webp)

因此，整个序列可以一次性解码（即一次前向传递）。然而，由于现有系统中的 FSM 和模型运行器之间缺乏集成，只能逐个 token 进行处理，导致解码速度缓慢。

**SGLang 通过创建一个快速约束解码运行时来克服这一限制**，该运行时使用压缩有限状态机。该运行时**分析 FSM 并压缩 FSM 中的相邻单转移边**，如图 4（b）所示，使其能够识别何时可以一次性解码多个 token。在图 4（d）中，压缩转移边上的多个 token 可以一次性在一个前向传递中解码，这大大加速了解码过程。它还具有通用性，适用于所有正则表达式。更多关于背景和实现的细节，请参阅附录 B（我这里就不列出来了）。

## 5.使用 API 投机执行实现高效的端点调用

> ❝
>
> 在多调用程序中，API 调用的延迟和成本是一个重要的瓶颈。为了优化这些调用，SGLang 引入了一种称为 **API 投机执行（API Speculative Execution）** 的技术。这种技术通过在**第一次 API 调用中** 继续**生成额外的 tokens**，从而**减少后续 API 调用的延迟和输入成本**。

通俗来说，想象你正在编写一个程序，该程序需要从一个 API 获取多个字段的信息（如名称、工作等）。通常，每次获取一个字段都需要一次 API 调用，这会增加延迟和成本。API 投机执行允许在第一次调用中生成多个字段的信息，从而减少后续调用的次数和成本。

例如，一个程序可能要求模型按照多调用模式生成一个角色的描述：

```
s += context + "name:" + gen("name", stop="\n") + "job:" + gen("job", stop="\n")
```

简单来说，这两个 `gen` 原语通常对应两次 API 调用，这意味着用户需要为上下文的输入 token 支付两次费用。 在 SGLang 中，我们可以在第一次调用时启用投机执行，忽略停止条件，继续生成几个额外的 token。

**解释器会保存这些额外生成的输出**，**并在后续的原语调用中匹配和复用它们**。在某些情况下，通过精心设计的提示（prompt engineering，即优化输入提示以引导模型生成预期输出），模型可以**以高精度正确匹配模板**，从而**节省了一次 API 调用的延迟和输入成本**。

### 应用场景

- 多字段提取：从文本中提取多个字段（如名称、工作、地址等）。
- 多步骤生成：需要多个步骤生成复杂输出的任务。
- 高成本 API：对于每次调用成本较高的 API，投机执行可以显著节省成本。

API 投机执行是一种优化技术，用于减少多调用程序对仅 API 模型的调用次数和成本。通过在第一次调用中生成额外的 token 并复用这些 token，可以显著提高程序的执行效率和响应速度。

我们大多数实验都在配备 **NVIDIA A10G GPU（24GB）的 AWS EC2 G5 实例** 上运行。我们在单个 A10G GPU 上运行 7B 模型，并在多个 A10G GPU 上使用张量并行运行更大的模型。我们还在 A100G（80GB）GPU 上运行了一些额外的实验。

#### 实验基线

我们将 SGLang 与以下系统进行了比较：

- Guidance：一种用于控制 LLM 的语言。我们使用 Guidance v0.1.8 并以 llama.cpp 作为后端。
- vLLM：一种高吞吐量的推理引擎。我们使用 vLLM v0.2.5 及其默认的 API 服务器。RadixAttention 已被部分集成到最新版本的 vLLM 中，作为可选的实验性功能，这里比较的是较早的 vLLM 版本。
- LMQL：一种查询语言。我们使用 LMQL v0.7.3 并以 Hugging Face Transformers 作为后端。

除非另有说明，我们没有启用会改变计算结果的优化，以确保所有系统计算相同的结果。

#### 工作负载

我们测试了以下内容：

- 5-shot MMLU 和 20-shot HellaSwag 基准测试。对于 MMLU，我们解码一个 token；对于 HellaSwag，我们使用 select 原语选择概率最高的答案。
- ReAct 智能体和生成智能体：我们从原始论文中提取跟踪并重放它们。
- 思维树：用于 GSM-8K 问题。
- 思维骨架：用于提示生成。
- LLM 评估器：使用分支-求解-合并技术。
- JSON 解码：使用正则表达式指定模式。
- 多轮对话：4 轮，每轮的输入随机采样为 256-512 个 token。多轮对话（短）表示短输出（4-8 个 token），多轮对话（长）表示长输出（256-512 个 token）。
- DSPy 检索增强生成（RAG）管道：使用其官方示例。

#### 性能指标

- **吞吐量**：运行足够大的程序实例批次以计算最大吞吐量，比较每秒执行的程序实例数量（programs per second, p/s）。
- **延迟**：单次执行程序而不进行批处理，并报告多个实例的平均延迟。

### 6.2 端到端性能

#### 开放权重模型的结果

> ❝
>
> 延迟和吞吐量结果如图 5 和图 6 所示。SGLang 将吞吐量提高了多达 6.4 倍，将延迟减少了多达 3.7 倍。这些改进源于 KV 缓存复用、单个程序内的并行性利用以及更快的约束解码。接下来，我们解释每个基准测试中速度提升的原因。

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/17.webp)

![文章插图](/articles/2025-05-02-sglang-llm-54db4ea5/images/18.webp)

在 MMLU 上，SGLang 可以通过 RadixAttention 复用 5 个示例的 KV 缓存。**RadixAttention 对吞吐量和延迟都有好处**。RadixAttention 通过共享 KV 缓存减少总内存使用，从而**允许更大的批处理大小以提高最大吞吐量**。RadixAttention 还**减少了预填充的计算**，从而降低了首个 token 的延迟。在 HellaSwag 上，SGLang 复用了少样本示例和多选题的公共问题前缀的 KV 缓存，实现了两级共享。对于 ReAct 和生成智能体，SGLang 复用了智能体模板和之前调用的 KV 缓存。在思维树和思维骨架上，SGLang 在单个程序内并行化生成调用，并尽可能复用 KV 缓存。

在 JSON 解码上，SGLang 通过压缩有限状态机一次性解码多个 token，加速了解码过程。在多轮对话中，SGLang 复用了对话历史的 KV 缓存。对于短输出，速度提升更为明显，因为 KV 缓存复用主要有助于减少前缀时间。对于长输出，由于不同对话会话之间的共享较少且解码时间占主导地位，几乎没有速度提升。在 DSPy RAG 管道中，SGLang 复用了公共上下文示例的 KV 缓存。

#### RadixAttention 的有效性

我们在几个具有代表性的基准测试中测试了 RadixAttention 及其组件的有效性。如图 8(c) 所示，“No Cache” 表示不使用任何缓存，“No Tree-Structure” 表示使用简单的基于表的缓存而不是树结构缓存，“FCFS Schedule” 表示使用先到先服务的策略而不是我们的缓存感知调度，“Random Schedule” 表示使用随机顺序调度请求，“No Frontend Parallelism” 表示禁用解释器中的并行性，“No Frontend Hint” 表示禁用从解释器发送的 fork 提示，“Full optimizations” 表示我们启用了所有优化。

实验结果表明，**每个组件对于实现最佳性能都是必需的**。禁用解释器中的并行性和提示也会导致运行时性能不佳，突出了**前端语言和运行时协同设计的重要性**。

#### RadixAttention 的开销

我们在一个没有任何 KV 缓存复用机会的基准测试中测试了 RadixAttention 的开销。该基准测试在 ShareGPT 数据集上测量吞吐量。运行 100 个请求需要 74.3 秒；然而，管理 RadixAttention 数据结构所用的时间仅为 0.2 秒，占总时间的不到 0.3%，开销可以忽略不计。这是由于树操作的复杂度是线性的且较小。因此，我们可以默认启用 RadixAttention，也证明其有效性。

#### 压缩有限状态机的有效性

我们在 JSON 解码基准测试中测试了压缩有限状态机及其组件的有效性。实验结果表明，**压缩有限状态机将吞吐量提高了 1.6 倍**，因为它可以**一次性解码多个 token**。此外，我们需要对状态机进行预处理，并将其复用到一批请求中。否则，每个请求都重新进行预处理会使吞吐量降低 2.4 倍。

## 7. 相关工作

### KV 缓存复用

许多工作已经探索了 KV 缓存的复用，其中一些与我们的工作同时进行。我们提出的 RadixAttention **首次将 KV 缓存视为基于树的 LRU 缓存**。它支持**多级共享、缓存感知调度、前端-运行时协同调度以及分布式场景**。

vLLM 和 ChunkedAttention 探索了一些简单的复用场景（例如系统提示共享），但没有涵盖多级树结构共享或 LRU 缓存。PromptCache 提出了超出前缀的模块化 KV 缓存复用，但可能会导致高达 43% 的准确性下降。HydraGen、FlashInfer 和 ChunkedAttention 专注于 CUDA 内核优化，并不包括 LRU 缓存的概念。API Serve 和 LLM-SQL 研究了 KV 缓存复用在特定应用中的使用，例如与外部 API 调用和关系数据库的交互，但它们没有我们的基数树或缓存感知调度。

### LLM 编程和智能体框架

存在多种 LLM 编程和智能体框架，例如 Guidance、LMQL、DSPy、LangChain、AutoGen 和 LLM Compiler。Guidance 和 LMQL 与 SGLang 最为相似，我们已在第 2 节进行了比较。

**我们的创新在于** 为提出的**编程模型引入** 了**新的运行时优化**。SGLang **其他框架兼容**，可以加速它们（例如我们在评估中展示的 DSPy 示例）。此外，SGLang 还**兼容许多其他常见的推理优化**。

## 8. 未来方向及总结

### 8.1 未来方向

尽管 SGLang 取得了进展，但仍然存在一些限制，这些限制揭示了未来研究的有前景方向。这些方向包括：

- **扩展 SGLang 以支持更多输出模态**：目前 SGLang 主要支持文本和简单的多模态输入（如图像和视频）。未来可以扩展其功能，支持更多种类的输出模态，例如音频和 3D 模型。
- **将 RadixAttention 适应多级存储层次结构**：当前的 RadixAttention 主要关注内存中的缓存复用。未来可以将其扩展到多级存储（如 DRAM 和磁盘），以支持更大规模的应用。
- **在 RadixAttention 中引入模糊语义匹配**：目前的 RadixAttention 依赖精确的前缀匹配。引入模糊语义匹配可以提高缓存复用率，尤其是在处理语义相似但文本不同的请求时。
- **在 SGLang 上提供更高层次的原语**：当前的 SGLang 提供了低层次的编程原语。未来可以引入更高层次的抽象，简化复杂任务的编程。 - **解决缓存感知调度中的饥饿问题**：缓存感知调度可能会导致某些请求长时间得不到处理（饥饿问题）。未来可以研究更公平的调度算法，确保所有请求都能及时得到处理。
- **增强 SGLang 编译器以执行更高级的静态优化**：例如调度和内存规划，以进一步提高性能。
