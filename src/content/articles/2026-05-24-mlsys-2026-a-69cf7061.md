## 二、问题本质：在两级存储的"夹缝"里调度计算图

> 要理解这套求解器为何"如此设计"，必须先看清问题的物理底色。

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/04.webp)

::: image-caption
慢速内存、快速内存与子图引擎交互架构图。该架构直观呈现 GPU 异构存储的核心约束，慢速内存容量大但带宽低，负责数据持久化；快速内存带宽高但容量有限，支撑实时计算。两层内存间数据传输会引入显著延迟，常驻张量机制可减少重复加载开销。此架构明确了调度优化的硬件边界，凸显 “内存受限下最小化延迟” 的核心矛盾，为后续束搜索调度提供场景前提与优化方向。
:::

研究场景下存在两类特性矛盾的存储介质：

- **慢速内存（Slow memory）容量大但带宽受限**，数据读写效率低；
- **快速内存（Fast memory）读写速度快但容量极其有限**，却是计算执行的核心载体。

在子图执行过程中，算子融合还会派生出额外的临时中间张量（ephemeral internal tensors），进一步挤压快内存空间。每个子图须被赋予 `[w, h, k]` 的粒度参数——空间方向上的 `w/h` 决定输出 tile 尺寸，归约方向上的 `k` 决定 MatMul 的内层切分——它直接决定了内存分配与调度效率。数据需在慢/快内存间通过 load/store 交互，而"常驻张量"（resident tensors）则可跨子图边界直接在快内存中供下一个引擎调用。

> 求解的核心目标只有一句话：**在确保每个执行步骤均适配快内存容量限制的前提下，最小化计算图的总执行延迟。**

作者的破题思路是将子图调度转化为一个**显式的状态空间搜索问题**。搜索状态被设计为三元组 `(covered ops, stored tensors, resident tensors)`：

- 初始时无任何算子被覆盖，所有图输入存于慢内存，快内存为空；
- 目标状态则要求所有算子均被覆盖、所有图输出落地于慢内存。

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/05.webp)

::: image-caption
DAG 计算图搜索模型状态转移示意图。该图刻画搜索模型的初始状态、状态转移逻辑与目标状态，搜索状态由已覆盖算子、存储张量、常驻张量三元组定义。该图将子图调度转化为可迭代的搜索问题，初始状态所有输入存于慢速内存、无算子覆盖；每次转移选择可行子图更新状态；目标状态覆盖全部算子且输出存储完成。三元组状态精准量化计算与内存状态，避免调度信息模糊。该模型把复杂调度决策拆解为状态搜索，为束搜索落地提供理论框架，保障调度过程可追踪、可优化，适配 DAG 计算图的依赖特性。
:::

状态转移即"选择一个可行的子图执行方案"，必须同时满足两条硬约束：

1. 所有所需输入要么已在快内存中常驻，要么可从慢内存加载；
2. 整个执行过程严格遵守快内存容量上限。

## 三、架构总览与设计哲学

> 整套求解器的源码只散落在 `source/`[7] 下不到 20 个文件中，层次极其干净：

```
main.cpp           ──► 命令行入口problem_io.*       ──► JSON 读/写solver.*           ──► 顶层 Solver，做超参自适应state_search.*     ──► 束搜索主循环 (BeamSearchScheduler)candidate_generator.* ─► 生成结构候选 (单算子/链/锥)cost_model.*       ──► Evaluator：候选 → 子图 + 延迟retention_policy.* ──► 跨子图边界的张量保留策略tile_simulator.*   ──► 真正干"算延迟+查内存"的tile级模拟器graph_utils.*      ──► DAG 拓扑、前驱/后继、几何工具mlsys.h            ──► Problem/Solution 等核心数据结构
```

### 3.1 一道题被切成三层抽象

> 作者把这道复合优化题非常干净地切成了三层抽象，每一层只对上层暴露最少的信息：

1. **结构层（`CandidateGenerator`）**：只看 DAG 拓扑，提名"哪些算子可以放进同一个子图"——单算子、线性链、反向锥、带重计算的反向锥；
2. **几何层（`Evaluator`）**：在一个候选已经确定的前提下，枚举 tile 粒度 `(w, h, k)`、保留集合与遍历顺序；
3. **物理层（`TileSimulator`）**：基于具体粒度**逐 tile** 地模拟实际访存与计算，产出严格的 `latency` 与 `peak_fast_memory`。

这种分层让每个组件都能被独立、严肃地实现——尤其是最底层的 tile 模拟器，其正确性直接决定整个方案是否会被官方校验脚本判错。

### 3.2 顶层入口：一个会"看图下菜"的 Solver

> `Solver::solve` 本身只有 20 行，却做了一件极其务实的事情——**根据图规模动态降级搜索预算**，这是冠军方案能在大图上不超时的关键：

```
// 来源：source/solver.cppmlsys::Solution Solver::solve(const mlsys::Problem &problem) const {    SearchConfig cfg = config_;    // 大图调整：把搜索"控制住" >> 用更宽的束。    if (problem.ops.size() > 80) {        cfg.beam_width = 5;        cfg.max_candidate_ops = 5;        cfg.max_recompute_depth = 1;        cfg.max_retained_outputs = 1;    } elseif (problem.ops.size() > 50) {        cfg.beam_width = 4;        cfg.max_candidate_ops = 5;    }    GraphInfo graph(problem);    BeamSearchScheduler scheduler(graph, cfg);    return scheduler.build_solution();}
```

注释里那句 *"keeping the search bounded >> using a wider beam"* 直接道破核心哲学：**与其拓宽，不如收紧** ——超过 80 个算子时，束宽从 8 砍到 5，候选锥大小、重计算深度、保留张量数都一起降级。:mdnice-bold-italic[这正是工程派胜过盲目搜索派的关键判断。]

## 四、束搜索骨架：状态、候选、剪枝

> 为什么是束搜索（Beam Search）而非纯贪心？因为单步贪心几乎一定会陷入"前一步省了访存、后一步却被迫多算一倍"的局部最优陷阱。束搜索同时维护多个优质的部分调度方案，让早期的"次优选择"也有机会被晚期的"全局回报"翻盘。

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/06.webp)

::: image-caption
这张图展示了基于束搜索的算子调度优化流程，共五步：扩展束状态、模拟器评估候选、追加子图生成新状态、等价状态去重、按预估总延迟保留最优状态；下方的优先级函数以当前状态延迟为主项，辅以未覆盖算子的基础成本加权和，平衡局部性能与全局剩余开销，引导搜索优先选择低延迟、剩余工作量小的路径，是典型的带启发式的束搜索优化框架。
:::

整个循环每步只做四件事：**扩展候选 → 模拟评估 → 等价去重 → 估值排序剪枝**。

### 4.1 三比特位串构成的搜索状态

> 状态（State）被刻意压扁成三组 `vector<bool>`，让"是否访问过同一状态"成为可哈希的字符串比较：

```
// 来源：source/search_types.hstruct ScheduleState {    std::vector<bool> covered_ops;       // 已被覆盖的算子    std::vector<bool> stored_tensors;    // 已落到慢内存的张量    std::vector<bool> resident_tensors;  // 仅"跨一次子图边界"驻留在快内存的张量    int covered_count = 0;    double total_latency = 0.0;    std::vector<mlsys::Subgraph> schedule;  // 已接受的子图序列};
```

这里最值得玩味的是 `resident_tensors` 的语义——它**只允许跨越恰好一次子图边界**。这条看似严苛的约束，把"快内存驻留"这一可能爆炸的状态空间一刀压回有限维度，同时与官方输出格式中"`tensors_to_retain` 只针对当前子图输出"的规则完全对齐。

### 4.2 主循环：扩展—评估—去重—剪枝

> 主循环如下所示，代码中增加的注释会描述循环过程

```
// 来源：source/state_search.cppfor (int step = 0; step < config_.max_search_steps; step++) {    // (1) 终止判定：若束中已有"覆盖全图 + 所有图输出落地"的完整状态，直接返回    for (constauto &state : beam) {        if (state.covered_count == (int)graph_.problem().ops.size()            && is_all_outputs_stored(state)) {            if (!best_complete.has_value() ||                state.total_latency < best_complete->total_latency) {                best_complete = state;            }        }    }    if (best_complete.has_value()) return mlsys::Solution{best_complete->schedule};    // (2) 扩展：每个状态生成结构候选 → 排序 → 截断    std::vector<ScheduleState> expanded_beam;    for (constauto &state : beam) {        auto candidates = generator_.generate(state);        std::sort(candidates.begin(), candidates.end(),                  [&](const Candidate &a, const Candidate &b "&") {                      if (a.ops.size() != b.ops.size())   // 大候选优先（融合更多算子）                          return a.ops.size() > b.ops.size();                      if (a.uses_recompute != b.uses_recompute)  // 不重计算优先                          return !a.uses_recompute;                      return a.tip_op < b.tip_op;          // 稳定性                  });        if (candidates.size() > config_.max_candidate_num)            candidates.resize(config_.max_candidate_num);        // (3) 评估：每个候选丢给 Evaluator，得到带 latency 的具体子图        for (constauto &candidate : candidates) {            if (!consumes_required_residents(graph_, state, candidate)) continue;            Evaluator evaluator(graph_, config_, state, candidate);            auto eval = evaluator.evaluate_candidate();            if (!eval.has_value()) continue;            /* ...更新 covered_ops / stored_tensors / resident_tensors... */            expanded_beam.push_back(std::move(next_state));        }    }    // (4) 同状态去重 + 启发式排序 + 截断到 beam_width    /* ... best_beam_map 按 state_key 留 latency 最小者 ... */    /* ... 按 estimated_total_latency 升序排序、resize 到 beam_width ... */}
```

### 4.3 一条被反复"挽救"的关键约束

> 下面 `consumes_required_residents`**这个看起来不起眼的判断守住了"保留=承诺立刻消费"的契约**：任何还驻留在快内存、又不在慢内存里的张量，其全部未完成的消费者必须落进本次候选——否则上一轮辛苦保留下来的数据就会在边界处"凭空消失"，让方案变得不合法。

```
// 来源：source/state_search.cppstatic bool consumes_required_residents(const GraphInfo &graph,                                        const ScheduleState &state,                                        const Candidate &candidate) {    std::unordered_set<size_t> candidate_ops(candidate.ops.begin(),                                             candidate.ops.end());    for (size_t t = 0; t < state.resident_tensors.size(); ++t) {        if (!state.resident_tensors.at(t) || state.stored_tensors.at(t)) continue;        for (size_t consumer : graph.consumers_of_tensor().at(t)) {            if (state.covered_ops.at(consumer)) continue;            if (!candidate_ops.count(consumer)) return false; // 消费者不在，拒绝        }    }    return true;}
```

### 4.4 启发式 A* 风格节点择优搜索思路

> 搜索框架并非纯贪心，它使用一个轻量却有效的估值函数，把"剩余未覆盖算子的 10% 基础代价"作为未来代价的下界估计，合在已发生延迟之上做束剪枝。对应到本节开头中的优先级公式：

$$
priority(State)=latency(State)+0.1 \times \sum_{uncovered\ ops} base\_cost
$$

```
// 来源：source/state_search.cppdouble BeamSearchScheduler::estimated_total_latency(    const ScheduleState &state) const {    double remaining = 0.0;    for (size_t op_id = 0; op_id < graph_.problem().ops.size(); ++op_id) {        if (!state.covered_ops.at(op_id)) {            remaining += 0.10 * static_cast<double>(                                     graph_.problem().ops[op_id].base_cost);        }    }    return state.total_latency + remaining;}
```

`0.10` 这个系数不是拍脑袋——作者的意图是**让估值"乐观但不离谱"：乐观才能避免误剪掉真正优秀的路径，不离谱才能拉开不同状态之间的差距**。这是束搜索调参的经典艺术，也是 A* 启发式可采纳性（admissibility）思想的工程版本。

## 五、候选生成：用结构判断代替蛮力

> 如果说束搜索是骨架**，`CandidateGenerator` 就是它的血肉**。作者在这里采用了一条工程黄金法则**："先生成少量高价值子图模板，再由评估器剔除非法或高代价方案"，** 而不是盲目枚举所有子集——后者在算子数稍多时就会指数爆炸。

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/07.webp)

::: image-caption
候选子图模板示意图（线性链与后向锥），上图右侧上为线性逐元素链结构，上图右侧下为逐元素后向锥结构，是候选子图生成的两类核心模板。两种模板匹配 DAG 计算图高频依赖模式，线性链适配算子串行依赖场景，结构简单、易验证；后向锥适配多算子汇聚依赖场景，覆盖复杂依赖关系。模板化生成可过滤大量无效候选，大幅压缩搜索空间，兼顾候选多样性与搜索效率。二者互补覆盖主流子图结构，贴合 GPU 计算图特性，是束搜索高效运行的关键，为候选评估提供高质量输入，平衡调度效率与解质量。
:::

### 5.1 三种候选，覆盖典型计算模式

> 候选只有三类（外加一类预留），在 `search_types.h` 中以枚举形式直白列出：

```
// 来源：source/search_types.henum class CandidateType {    SingleOp,             // 单算子（包括单个 MatMul）    LinearChain,          // 线性 pointwise 链    MatMulPointwiseChain, // 预留：MatMul + pointwise 链（当前实现已注释）    BackwardCone,         // 反向锥：沿入边反向扩展，所有节点 pointwise    RecomputeCone,        // 允许"一次"重计算的反向锥};
```

它们分别对应实际计算图中最常见的三种"可融合"形态：

- 单个就绪算子作为兜底；
- 线性 pointwise 链对应类似 `Add → Relu → Cast` 的流水；
- 反向锥则刻画了"多个 pointwise 算子共同收敛到一个输出"的扇形结构——这种形态在 LayerNorm、Softmax、注意力分数归一化等场景里随处可见。

### 5.2 反向锥：一次只允许一次重计算

> 反向锥的递归扩展算法 `expand_backward_cone` 是整篇代码最优雅的部分之一。它对每个未覆盖的 pointwise 算子作"尖端"，沿着入边反向递归，**预算 `budget` 控制锥的最大尺寸，`max_recompute_depth` 控制递归深度**；一旦遇到已经被覆盖的生产者，在 `allow_recompute=true` 模式下会消费"一次"重计算许可，把这个生产者再"算一遍"塞进锥内：

```
// 来源：source/candidate_generator.cpp（节选并简化）bool CandidateGenerator::expand_backward_cone(    const ScheduleState &state, size_t op_id, int *budget, int depth,    bool allow_recompute, std::vector<bool> *in_candidate,    bool *used_recompute) const {    if (in_candidate->at(op_id)) returntrue;    if (graph_.is_matmul(op_id)) returnfalse;   // 锥内不允许 MatMul    if (*budget <= 0) returnfalse;    in_candidate->at(op_id) = true;    (*budget)--;    for (size_t t : graph_.problem().ops.at(op_id).inputs) {        constint p = graph_.producer_of_tensor().at(t);        if (p == -1) continue;  // 图输入        if (!state.covered_ops.at((size_t)p)) {            // 生产者未覆盖：递归把它拉进锥            if (!expand_backward_cone(state, p, budget, depth + 1,                                      allow_recompute, in_candidate,                                      used_recompute)) returnfalse;            continue;        }        // 生产者已覆盖，但允许重计算且深度未超 → 把它"再算一遍"        if (allow_recompute && depth < config_.max_recompute_depth) {            *used_recompute = true;            if (!expand_backward_cone(state, p, budget, depth + 1,                                      /*allow_recompute=*/false,  // 仅允许一次                                      in_candidate, used_recompute)) returnfalse;            continue;        }        if (!tensor_available(state, t) && !graph_.is_graph_input().at(t))            returnfalse;    }    returntrue;}
```

请注意第二次递归把 `allow_recompute` 强制传 `false`**——"重计算"只允许在锥里发生一次。** 这是一个典型的"剪枝以保住搜索可控性"的取舍，背后是一个朴素观察：实际 ML 计算图里，大多数显著收益的重计算场景（LayerNorm 后的激活、Softmax 中间值等）都只需要一次。

### 5.3 候选排序：大优先 + 不重计算优先

候选生成完后，束搜索循环里那段排序值得回看一遍："**算子数多优先，不重计算优先，tip 算子 id 升序保稳定"**——这背后是一个有偏的搜索策略：** 优先尝试一次性吃掉更多算子的"大"子图**，因为它们更有可能受益于片上数据复用。

## 六、Evaluator 与 TileSimulator：把候选"算"成延迟

> 候选只是结构上的"提名"，**真正决定它优劣的是延迟** ——这一刻 `Evaluator` 上场。它的任务是在一个候选确定的前提下，枚举**tile 粒度 (w, h, k)、保留集合、遍历顺序** 这三类自由度，把每一种组合丢给 `TileSimulator` 跑一遍，选出最小延迟的那一份。

该流程描述了子图从候选方案到最终可行方案的完整筛选过程，分为粒度、驻留、tile 模拟三个核心阶段。首先枚举空间维度w、h的选择，并选取最大可用的split-k值，确定计算粒度；接着对边界输出的驻留集合进行枚举，规划高速内存中需保留的数据；随后通过 tile 模拟验证各组合，剔除存在内存溢出（OOM）风险的方案；最终从所有可行子图中，返回延迟最低的方案，确保在内存安全的前提下，实现最优的调度性能。

### 6.1 分类派发：同样是候选，算法却不同

```
// 来源：source/cost_model.cpp（节选）std::optional<CandidateEvaluation> Evaluator::evaluate_candidate() {    constauto &tip = graph_.problem().tensors.at(summary_.tip_output_tensor);    constauto w_choices = make_dim_choices(tip.width,                                            graph_.problem().native_granularity.width);    constauto h_choices = make_dim_choices(tip.height,                                            graph_.problem().native_granularity.height);    constauto spatial_choices = make_spatial_choices(w_choices, h_choices);    if (summary_.single_matmul)           return evaluate_single_matmul_candidate(spatial_choices);    if (summary_.matmul_pointwise_chain)  return evaluate_matmul_pointwise_chain_candidate(spatial_choices);    if (summary_.all_pointwise)           return evaluate_pointwise_candidate(spatial_choices);    // 混合/复杂候选：粒度全枚举    /* ... */}
```

对整套优化哲学可精炼为：

> 1. 单个 MatMul：枚举空间 (w, h)，**为该空间形状选最大可行的 native-bounded k**，使用蛇形遍历；
> 2. pointwise 链/锥：`k=1`，合法性由分块工作集裁决；
> 3. 保留（retain）选择由同一模拟器评估，**绝不为了省访存而接受 OOM**。

对应到 PPT 描述：MatMul 候选无需穷举所有 `k`，而是从大到小尝试、选取**首个可行值** ——因为同一空间 tile 下，最大可行 `k` 通常对应最低计算成本（拆分 `k` 的计算时间与 `k / k_native` 成正比）。纯 pointwise 候选则因无归约维直接固定 `k=1`，仅评估空间 tile。

### 6.2 维度选择：对半折叠的等比序列

`make_dim_choices` 给出的不是任意整数，而是 `{native, native/2, native/4, ..., 1}` 这样以 2 为公比的有限集合。这一步看似简单，**却把组合爆炸瞬间压回 `O(log²)` 级别**：

```
// 来源：source/cost_model.cppstd::vector<int64_t> Evaluator::make_dim_choices(int64_t dim, int64_t native_dim) {    std::vector<int64_t> choices;    if (dim <= 0 || native_dim <= 0) return choices;    int64_t x = std::min<int64_t>(dim, native_dim);    while (x >= 1) {        choices.push_back(x);        if (x == 1) break;        x = std::max<int64_t>(1, x / 2);    }    std::sort(choices.rbegin(), choices.rend()); // 大优先    return choices;}
```

随后 `make_spatial_choices` 把 (w, h) 笛卡尔积**按面积降序排序** ——这与 `evaluate_pointwise_candidate` 里"一旦在某一面积找到可行解就早停"的策略形成完美配合：更大的面积通常意味着更少的 tile 数和更高的访存复用，先试为敬。

### 6.3 TileSimulator：逐 tile 的"硬核账本"

> 如果说前面所有模块都在"想"，那 `TileSimulator` 就是在"算"。**所有候选子图均通过模拟方式被验证，而非依赖启发式估算** ——这是冠军方案敢于声称"绝不接受 OOM"的底气。

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/09.webp)

::: image-caption
TileSimulator 这一模块提出了保障内存正确性的容量规则，核心是通过张量矩形追踪与并集计算，确保不发生内存溢出（OOM）。实现上，首先从子图的末端张量回溯，追踪所有必要的张量矩形；同时持续跟踪外部输入、边界输出、驻留张量与累加器的内存占用，并通过计算张量矩形的并集面积避免重复统计。校验阶段会对每个空间分块（tile）与split-k步骤进行验证，最终通过 `|R_resident ∪ R_retain ∪ R_input ∪ R_output ∪ R_accumulator| ≤ C_fast` 的容量规则，确保所有常驻内存的张量总和不超过高速内存上限，从而保障调度方案的内存安全与正确性。
:::

> 它的 `simulate(spatial_order)` 函数在一次调用里做完三件事：

1. **沿 `spatial_order` 遍历每一个 (tile_row, tile_col)** 输出 tile；
2. 对每个 tile**递归回溯到外部输入**，精确算出需要哪些张量的哪些矩形区域（`Rect`）、哪些归约范围（`Range`），由 `build_step_requirements` 汇总成 `StepRequirements`；
3. 把这些区域的**新增面积** （`incremental_area`）乘以 `slow_memory_bandwidth` 换算成访存延迟，叠加 `compute_latency`；同时实时检查**快内存峰值** 是否超出 `fast_memory_capacity`——一旦越线，模拟器直接返回 `std::nullopt`，该粒度被判出局。

`tile_simulator.h` 里这几个内嵌结构体，把这套"账本"刻画得极其清晰：

```
// 来源：source/tile_simulator.h（节选）struct Rect {int64_t row_begin, row_end, col_begin, col_end; };struct Range {int64_t begin, size; };enumclass SliceKind { Spatial, ReductionOnRows, ReductionOnCols, };struct StepRequirements {    std::unordered_map<size_t, std::vector<Rect>> external_inputs;    std::unordered_map<size_t, std::vector<Rect>> boundary_outputs;    std::unordered_map<size_t, std::vector<Rect>> accumulators;    double compute_latency = 0.0;};struct TileSimulationResult {    double latency = 0.0;    int64_t peak_fast_memory = 0;};
```

这套结构有两个亮点值得指出：

- **`SliceKind` 三态** 让模拟器同时支持 pointwise（纯空间切分）与 MatMul（沿 K 维归约切分）两类语义，避免了为每类候选写一份独立模拟器。
- **`accumulators` 单独建账** ——MatMul 的 split-K 累加器需要常驻在快内存里跨多个 tile，只有把它和 `external_inputs/boundary_outputs` 分开，才能正确算出峰值占用。

合到一起，模拟器在每个 tile 步骤上严格执行这条容量约束：

$$
|R_{resident} \cup R_{retain} \cup R_{input} \cup R_{output} \cup R_{accumulator}| \leq C
$$

其中 $C$ 即 `fast_memory_capacity`。**只有所有 tile 步骤都不越线，候选才被判定为可行**，这彻底杜绝了求解器"假装合法"的可能。完整实现见 `source/tile_simulator.cpp`[8]。

### 6.4 遍历顺序：光栅 vs 蛇形

> 对于含 MatMul 的候选，作者特意选择了**蛇形（snake）遍历** 而非朴素的光栅（raster）：

```
// 来源：source/cost_model.cppstd::vector<int64_t> Evaluator::build_snake_order(int64_t rows, int64_t cols) {    std::vector<int64_t> order;    for (int64_t r = 0; r < rows; ++r) {        if ((r % 2) == 0) for (int64_t c = 0; c < cols; ++c) order.push_back(r*cols + c);        else              for (int64_t c = cols-1; c >= 0; --c) order.push_back(r*cols + c);    }    return order;}
```

为什么？因为 MatMul 中 RHS 矩阵的某些列 tile 在相邻输出 tile 之间是**可复用** 的——光栅顺序每行结束后会"突然跳回最左"，上一行末尾辛苦加载的 RHS 列直接作废；蛇形顺序则让相邻输出 tile 始终在物理上相邻，**最大化片上 RHS 的复用率**。这是一条来自经典 GPU 编程的成熟经验，被严肃地搬进了本竞赛代码。

## 七、保留策略：跨子图边界的微观博弈

最后一块拼图是 `retention_policy.cpp`——它决定**每个子图哪些输出张量"留"在快内存、哪些"刷"回慢内存**。算子融合并非总能带来收益（甚至可能不可行），因此**张量保留策略是减少慢内存读写流量、避免冗余传输的另一条独立优化路径**。

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/10.webp)

::: image-caption
子图调度中的 Retention（驻留）机制，本质是子图间数据的 “持久化” 管理：只有被选中的边界输出，才会保留在高速内存中供下一轮调度使用。驻留候选对象是那些存在后续使用节点的边界输出；未被选中的边界输出则会被写回低速内存，释放高速内存空间。驻留张量必须在下一个紧邻的调度步骤中被消费，以此保障数据依赖链的连续性，同时平衡高速内存的占用与计算效率，避免不必要的数据搬运开销。
:::

### 7.1 一条铁律和一个分数

代码用注释直白写出了铁律：

> A retained output is **not also** stored to slow memory.

一旦保留，就**不能再"为了保险"同时写回慢内存** ——这是问题约束本身决定的。基于此，作者只允许两种张量被保留：**恰好剩 1 个未完成消费者、且该消费者能立刻从当前状态被调度起来**。这把保留语义收得很紧，但也保证了**每一次保留都是有意义的**：

```
// 来源：source/retention_policy.cppdouble retention_score(const GraphInfo &graph, const ScheduleState &state,                       size_t tensor_id) {    if (graph.is_graph_output().at(tensor_id)) return-1.0;    int remaining_consumers = 0, ready_consumers = 0;    int nearest_consumer_distance = 1 << 20;    constint producer = graph.producer_of_tensor().at(tensor_id);    for (size_t c : graph.consumers_of_tensor().at(tensor_id)) {        if (state.covered_ops.at(c)) continue;        ++remaining_consumers;        if (!consumer_ready_with_fresh_tensor(graph, state, tensor_id, c)) continue;        ++ready_consumers;        if (producer != -1)            nearest_consumer_distance = std::min(nearest_consumer_distance,                                                 std::max(1, (int)c - producer));    }    if (remaining_consumers != 1 || ready_consumers != 1) return-1.0;    constdouble transfer = graph.transfer_time(graph.tensor_elements(tensor_id));    constdouble immediacy = 1.0 / std::max(1, nearest_consumer_distance);    return transfer * 2.0 * immediacy;  // 节省"两次"传输 × 紧迫度}
```

分数公式 `transfer * 2.0 * immediacy` 凝缩了一个朴素的成本/收益分析：**保留省下的就是"写一次慢内存 + 读一次慢内存" = 两次传输**，再用 `1 / 距离` 作为"如果留不上代价更高"的紧迫度权重。`enumerate_retention_choices` 最终取得分最高的前 6 个候选，加上"全空集"和"两两组合（在内存预算内）"，一共最多十几个保留集合送给 `Evaluator` 逐一试算。

### 7.2 谁来兜底？让模拟器说话

这里最值得品味的工程纪律是：**保留候选可以"提名得很激进"，但最终是否合法，完全由 `TileSimulator` 在该粒度下重新跑一遍仿真说了算**。换言之，启发式只负责"出主意"，正确性永远握在最底层的硬核账本里。这也是为什么作者敢在注释里写下 "OOM is never accepted just to save memory traffic"——因为他真的把这条约束写进了模拟器。

与此同时，第四章提到的 `consumes_required_residents` 在搜索侧再筑一道防线：常驻张量必须在紧随其后的步骤中被消费，否则状态扩展直接被拒。保留策略与搜索约束**在物理状态语义不变的前提下双向闭环**，从根本上杜绝了"留下来却用不上"的尴尬。

## 结语：为什么"工程派"赢了？

![文章插图](/articles/2026-05-24-mlsys-2026-a-69cf7061/images/12.webp)

::: image-caption
该调度方案通过多维度设计实现了性能与资源的平衡：采用Beam Search避免单步贪心决策，结合候选模板将搜索空间控制在可管理范围；通过Tile Simulation实现了稳健的内存溢出（OOM）预判与规避；Retention机制则在保留物理状态语义的同时，大幅降低了低速内存的读写开销。此外，方案也明确了未来的优化方向，包括扩充矩阵乘法链的候选模板、引入内存感知的启发式策略，以及强化驻留策略的评分机制，以进一步提升调度效率与资源利用率。
:::

> 通读这份冠军代码，会发现它**几乎不依赖任何"花哨"技术**：没有强化学习、没有 ILP solver、没有大模型，甚至没有多线程。它能赢，靠的是四件极朴素却被做得极扎实的事情：

1. **正确分层** ——结构候选 / 几何枚举 / 物理模拟，三层只暴露最少接口，使得每一层都能被独立加固；
2. **诚实的代价模型** ——`TileSimulator` 逐 tile、按矩形并集去重地算访存，绝不在合法性上偷懒；
3. **有偏但克制的搜索** ——大候选优先、不重计算优先、按面积早停、按图规模降级束宽，所有的"偏置"都来自对 ML 计算图的常识性观察，而非随机调参；
4. **保守而非激进的语义选择** ——只在融合规则明确时优化，对混合场景宁可放弃融合也不接受非法解，让"正确性"始终优先于"激进度"。

::: block-1
作者本人也在报告里给出了三条未来改进方向，恰好对应当前的三条主动留白：**丰富 MatMul 链候选类型** （当前 `MatMulPointwiseChain` 在代码里仍被注释保留）、**设计更强的内存感知启发式**、**优化留存评分以提升数据复用精准度**。
:::
