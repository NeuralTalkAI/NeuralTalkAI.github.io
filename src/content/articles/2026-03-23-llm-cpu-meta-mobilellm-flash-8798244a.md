关键词： **端侧大模型**、延迟感知、**硬件在环**、架构搜索、:mdnice-bold-italic[混合注意力]

> 当你对着手机上的 AI 助手问了一个问题，然后等待……1 秒、2 秒、3 秒……直到第 10 秒，才看到第一个字蹦出来。根据尼尔森定律，这种超过 4 秒的延迟，已经足以让用户感到焦躁，甚至放弃使用。这就是当前端侧大模型（On-Device Large Language Model, OD-LLM）在追求“智能”时，常常忽略的“人性化”痛点。

业界普遍认为，模型的“快”等同于参数少、计算量低。于是，我们看到了大量“小而美”的模型，它们在 FLOPs 和参数量上表现优异，但一部署到真实的手机上，却依旧步履蹒跚。

## 一、引言：端侧大模型的“紧箍咒”—— 真实延迟

> 在构建 AI 应用时，我们通常关注两个指标：质量和效率。但对于部署在手机、智能眼镜等资源受限设备上的端侧大模型，效率的定义远非“参数量”或“FLOPs”那么简单。真正的紧箍咒，是延迟，特别是首字延迟（Time-to-First-Token, TTFT）。

论文中明确指出了这一点，并将其与用户体验直接挂钩：“While a 4s TTFT can still yield a reasonable user experience, a 10s TTFT does not (Nielsen 1994; Kim et al. 2026).” 这就意味着，:mdnice-bold-italic[在设计模型时，我们必须在保证质量的前提下，强制性地将 TTFT 压入一个严格的“时间窗口”。作者发现，对于端侧模型而言，处理约 2000 个 token 的预填充（Prefill）阶段，是一个能兼顾任务能力和延迟的“甜蜜点”。]

然而，传统的优化方法常常与这个目标背道而驰：

### 1.1 以 FLOPs/参数量为替代指标：这是最普遍的误区

> 下面表 2 揭示了残酷的现实：参数量与预填充延迟的 Kendall tau 相关系数仅为 0.40，FLOPs 与预填充延迟的相关系数也仅有 0.46。

*注：Kendall tau 相关系数：一种统计量，衡量两个排序序列之间的一致性。值越接近 1 表示排序越相关，作者用于证明参数量/FLOPs与真实延迟排序关联较弱。*

这意味着，**一个 FLOPs 更低的模型，在手机上跑起来未必更快！ 这背后的原因很复杂，比如内存访问模式、算子优化、硬件调度等**。依赖这些替代指标，无异于“盲人摸象”。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/04.webp)

::: image-caption
表 2：实际测量的预填/解码速度与参数量/FLOPs。该表通过 Kendall tau 相关系数揭示了理论指标与实际延迟之间的微弱关联。无论是参数量还是 FLOPs，其与预填、解码延迟的相关系数均在 0.4 至 0.55 之间，属于中度相关，远未达到强相关（>0.8）。这意味着，在移动端 CPU 上，单纯通过压缩参数量或降低计算量，并不能可靠地预期延迟的线性下降。实际延迟受内存带宽、算子实现、缓存命中率等多种硬件因素影响。这一发现是本文的核心洞察之一，强烈建议研究者放弃以 FLOPs 为替代的优化，转而采用硬件在环的直接延迟测量。
:::

### 1.2 依赖专用内核

> 许多优秀的模型设计，如 Mamba2、Gated DeltaNet 等，虽然从算法上大幅降低了计算复杂度，但它们依赖于高度优化的、非标准的 CUDA 内核。

这在服务器端可能不是问题，但**在跨平台（Android、iOS）的移动端运行时如 ExecuTorch上，这些内核的缺失或性能不佳，会成为部署的“最后一公里”障碍。**

::: block-1
MobileLLM-Flash 的设计哲学，正是要破除这两个障碍。它的核心思想是：在真实硬件上测量延迟，并用这个真实的延迟来指导整个设计流程。
:::

## 二、核心方法：让硬件说话——两阶段延迟感知设计

> MobileLLM-Flash 的方法论可以概括为一个由“硬件-软件协同”驱动的两阶段搜索框架，如图 2 所示。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/05.webp)

::: image-caption
图 2 我们两阶段端侧大语言模型设计概览。我们通过使用基于 Ax 平台的贝叶斯优化（BO）对预训练模型 $a_0$ 进行剪枝，来联合搜索架构与注意力模式。在第一阶段，我们对剪枝后的架构进行采样，并在手机上测量其延迟，以低成本学习一个延迟模型。在第二阶段，利用该延迟模型，我们高效地搜索空间，生成精度-延迟的帕累托前沿。其核心在于将“延迟”这一实际部署中的关键指标引入搜索循环。第一阶段通过低成本的真实设备测量构建延迟代理模型，避免了对每个候选架构进行昂贵的训练；第二阶段则利用该替代模型引导贝叶斯优化，聚焦于高潜力区域进行精度评估。这种硬件在环的设计使得搜索过程能够直接反映真实硬件瓶颈（如内存访问、算子调度），而非依赖 FLOPs 等理论指标。该流程不仅提高了搜索效率，也确保了最终产出的模型能够直接满足工业级部署的严苛延迟要求。
:::

*注：Ax 平台 是 Meta 开源的贝叶斯优化平台，用于自动化搜索超参数或架构，高效探索大规模设计空间以优化多目标（如延迟与精度）。*

### 2.1 结构化剪枝：高效的架构“继承者”

> 从头训练每个候选模型是不现实的，成本太高。:mdnice-bold-italic[MobileLLM-Flash 巧妙地采用了结构化剪枝的方法。他们从一个预先训练好的、相对较大的“主干模型”（Base Model）出发，通过剪枝其维度（$d_{model}, d_{ffn}$）、层数（$d_L$）和注意力模式，来生成新的、更小的候选架构。]

这种方法的关键在于“继承”：

- 效率：剪枝后的模型直接继承了原始模型的权重，因此只需极少的“持续预训练”（Continued Pretraining, CPT）即可达到较高的质量。
- 快速排名：作者发现，训练仅 2.6B token 后，不同架构的质量排名，就已经与训练 500B token 后的最终排名高度一致（Kendall tau 相关系数为 0.74）。这极大地加速了搜索过程。
- 基于能量的剪枝标准：剪枝不是随机的。他们使用激活能量指标来决定哪些部分可以剪掉。

这为架构搜索提供了一个高效、数据驱动的起点。

### 2.2 受限的搜索空间：拥抱“开箱即用”的算子

> 为了确保模型能在生产环境中无缝部署，MobileLLM-Flash 严格限制其搜索空间，只包含那些被主流移动端运行时（如 ExecuTorch）原生支持的算子。这大大降低了部署门槛。

他们将搜索空间 S 定义为：

$$
S = { d_L, d_{ffn}, d_{model}, P_{attn} }
$$

其中，最关键的是注意力模式 $P_{attn}$。他们只考虑了三种类型：

1. 全局注意力（Global Attention）：标准的全注意力机制。
2. 滑动窗口注意力（Sliding Window Attention, SWA）：限制每个 token 只关注其附近一定窗口内的 token。
3. 跳跃注意力（Skip Attention）：完全跳过某个 Transformer 层的注意力计算，相当于该层只由前馈网络（FFN）构成。

这种务实的限制，使得最终搜索出的模型可以“即插即用”，无需任何自定义内核。

### 2.3 两阶段贝叶斯优化：延迟与质量的双重奏

> 有了搜索空间和候选生成方法，如何高效地找到最优解？MobileLLM-Flash 采用了贝叶斯优化，并巧妙地将其分为两个阶段，以解决“测量延迟快、训练质量慢”的矛盾。

#### 第一阶段：学习延迟模型

在这个阶段，他们**从搜索空间中大量采样候选架构（通常远多于最终要训练的候选数），在真实的手机上快速测量它们的预填充延迟**。这些数据点被用来训练一个高斯过程（Gaussian Process）替代模型，这个模型可以非常准确地预测任何新架构在手机上的延迟。

#### 第二阶段：帕累托前沿搜索

有了延迟预测模型后，搜索就从“真实硬件测量”转变为“模型预测”，速度得到极大提升。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/06.webp)

::: image-caption
图 3 一个延迟-精度帕累托前沿。在端侧模型设计中，延迟与精度往往是一对矛盾的目标，无法同时达到最优。帕累托前沿上的每一个点都代表一种最优的权衡：在不牺牲精度的情况下无法进一步降低延迟，反之亦然。本文通过贝叶斯优化在搜索空间中探寻这一前沿，使得产品团队可以根据具体应用场景（如对实时性要求极高的智能眼镜交互）灵活选择合适的工作点。这种设计哲学为端侧模型的定制化部署提供了理论依据，避免了单一指标优化带来的偏颇。
:::

现在，他们只需要关注“质量”这一昂贵的评估目标。贝叶斯优化算法（使用 NEHVI 采集函数）在搜索空间中，根据延迟替代模型和质量评估（通过在 2.6B token 上训练后的损失）结果，寻找能最大化超体积改进（Hypervolume Improvement） 的架构，即探索延迟-质量帕累托前沿。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/07.webp)

::: image-caption
图 4 剪枝模型的损失演变。图中展示了不同候选架构在持续预训练（CPT）过程中损失的下降曲线。关键发现是，在训练约 10k 步（约 2.6B 个 token）时，各模型的损失排名已经与训练 120k 步后的最终排名高度一致。这表明，无需将每个候选模型训练至收敛，即可通过早期损失值可靠地筛选出最优架构。这大大降低了搜索成本，使得在有限计算资源下探索数百个候选架构成为可能。该实验证实了“稳定排序”现象的客观存在，是本文搜索方法高效性的关键支撑。
:::

::: block-1
这个两阶段方法的核心优势在于，:mdnice-bold-italic[它将最昂贵、最耗时的模型训练（质量评估）精确地聚焦在最有希望的区域，而将相对廉价的延迟测量作为预处理步骤，从而在总搜索预算内找到了更优的解。]
:::

## 三、创新成果：MobileLLM-Flash 家族的设计原则与性能

通过上述方法，作者提炼出了两个关键的设计原则，并最终构建了 MobileLLM-Flash 模型家族。

### 3.1 效率原则一：浅而宽 > 深而薄

> 传统的设计直觉是，更深的模型通常表达能力更强。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/08.webp)

::: image-caption
图 5 不同模型深度的帕累托曲线。揭示了深度与延迟-精度权衡的复杂关系。图中黄色点（深层模型）位于曲线的左上角，意味着在达到最低损失（最高精度）的同时，付出了最高的预填延迟。而深蓝色点（浅层模型）则位于曲线的右下部分，提供了更快的响应速度，尽管精度略有下降。有趣的是，在极低延迟区域，继续增加深度反而无法获得精度收益，此时浅而宽的模型成为最优选择。这一观察提炼为“效率原则1”，指导端侧模型设计者在固定参数量下，优先考虑浅层结构以更好地平衡延迟与精度。
:::

但 MobileLLM-Flash 的帕累托分析如图 5，给出了一个有趣的发现：**在相同的参数和延迟预算下，浅而宽（fewer layers, wider dimensions）的模型，其延迟-质量平衡优于深而薄（more layers, narrower dimensions）的模型。**

为什么？ 推理延迟主要由内存访问和计算模式决定。

::: block-1
更深的模型意味着更多的层间依赖，增加了内存加载和存储的次数，无法充分利用移动端 CPU 的并行性。**而浅而宽的模型，每一层都能处理更大的矩阵，更好地利用了指令集和数据并行，从而在达到相同或更高质量的同时，获得更快的速度。**

这一发现:mdnice-bold-italic[与 NVIDIA Nemotron-Flash 等近期工作（Fu et al., 2025）的观察一致。]
:::

### 3.2 效率原则二：跳跃注意力 > 滑动窗口注意力，并需要合理布局

> 滑动窗口注意力（SWA）被认为是降低长上下文计算量的有效手段。然而，在移动端的现实约束下，SWA 反而可能成为累赘。

而在搜索过程中，作者发现，在同等延迟下，采用跳跃注意力（跳过整个注意力层）的模型，其质量普遍优于使用 SWA 的模型。

> 所以作者进一步分析了滑动窗口注意力（SWA）低效性，在移动端运行时（如 ExecuTorch），SWA 的实现存在两个问题：

1. 块大小的限制：预填充阶段会分成 1024 token 的块（chunk），SWA 的窗口大小必须大于等于这个块大小。因此，在处理 2k token 时，:mdnice-bold-italic[只有第二个块（从 1025 到 2048）才能真正利用到滑动窗口带来的稀疏性，收益被稀释。]
2. 实现方式：SWA 的环形缓冲实现，可能要求计算整个注意力矩阵，而不是像标准注意力那样只计算下三角部分，这反而增加了计算开销。

**因此，跳过注意力层（即只保留 FFN）成为一种更高效的、直接省去注意力计算的策略。**

::: block-1
但是，过度跳过也会带来问题。下表 4 表明，连续跳过 3 个以上的注意力层会严重损害模型在复杂生成任务上的性能。**因此，最优的注意力模式是在全局注意力和跳跃注意力之间进行合理“交错”（interleaving），以平衡长程建模能力和延迟。**
:::

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/13.webp)

::: image-caption
表 4：具有相同延迟/相同架构和跳过注意力数量的候选模型，由于连续注意力模式的不同，其性能可能存在差异。该表通过对比实验揭示了注意力模式中“连续性”的重要性。尽管两组模型在总跳过注意力数量上可能相同，但那些连续跳过超过3层的模型，在 TQA、ANLI 等复杂生成任务上的性能出现了断崖式下降（例如 TQA 从 33.2% 降至 8.8%）。这说明，过长的连续注意力缺失会严重损害模型的长程依赖建模能力和推理能力。基于此发现，作者在最终搜索中增加了约束：避免出现三个或更多连续的跳过注意力或 SWA 层。这一原则确保了在追求低延迟的同时，模型仍能保持足够的表达能力和任务性能。
:::

### 3.3 MobileLLM-Flash 的性能表现

> 基于上述原则，作者推出了 MobileLLM-Flash 系列模型，包括 350M、650M 和 1.4B 三个版本。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/14.webp)

::: image-caption
图 1 MobileLLM-Flash 与最先进的端侧大语言模型（OD-LLM）的比较。在移动端 CPU 上，MobileLLM-Flash 的预填和解码速度分别提升至 1.8 倍和 1.6 倍，同时精度优于 LFM2（Amini 等人，2025）。这一对比直接回应了引言中提出的实时性需求，即端侧模型必须在有限硬件资源下实现低延迟响应。该图不仅验证了作者所提方法的有效性，也强调了以实际延迟而非参数数量或理论计算量为优化目标的必要性，为后续的 Pareto 前沿分析奠定了直观基础。
:::

与同量级的最先进模型（如 LFM2）相比，其性能优势显著如图 1：

- 速度优势：在移动端 CPU 上，MobileLLM-Flash 实现了 1.8 倍的预填充（Prefill）加速和 1.6 倍的解码（Decode）加速。
- 质量优势：在加速的同时，它在多项基准测试（如常识推理、阅读理解）上的表现不仅没有下降，反而超越了 LFM2，实现了真正的“又快又好”。

这充分证明了，以真实延迟为导向的硬件在环设计，能够挖掘出在计算与通信效率上更优的模型结构。

## 四、相关工作对比：MobileLLM-Flash 的独特定位

> 为了让读者更清晰地理解这项工作的创新性，我们将它与当前最相关的几类研究进行对比如下表 1。

![文章插图](/articles/2026-03-23-llm-cpu-meta-mobilellm-flash-8798244a/images/15.webp)

::: image-caption
表 1：方法论比较。该表清晰地划定了 MobileLLM-Flash 与现有工作在方法论上的核心差异。相较于 LFM2，本文引入了统一的架构与注意力模式联合搜索，并通过基于剪枝的继承策略大幅提升了搜索效率。而与 Jet-Nemotron 等专注于服务器端 GPU 优化的模型相比，本文直接以移动端 CPU 延迟为优化目标，并确保模型无需定制内核即可部署于 Executorch 等通用运行时。这种设计使得 MobileLLM-Flash 在保持高兼容性的同时，能够更精准地匹配真实工业部署场景的需求，体现了从研究到生产的工程化考量。
:::

从上表可以看出：

- **LFM2：虽然也针对边缘设备优化，并采用了基于 conv1d 的注意力，但它的搜索范围是有限的**，并没有像 MobileLLM-Flash 一样，将架构形状（层数、维度）和注意力模式进行统一的、自动化的联合搜索。:mdnice-bold-italic[更重要的是，其 conv1d 算子在移动端小 batch、短序列场景下可能存在性能瓶颈。]
- **Jet-Nemotron/Nemotron-Flash：这一类工作更侧重于服务器端 GPU 优化，其搜索目标通常是 FLOPs 或参数效率，而不是真实的移动端延迟**。它们依赖的某些算子可能缺乏移动端运行时支持，导致其成果难以直接迁移到手机端。

::: block-1
因此，MobileLLM-Flash 的独特定位在于，它将“在真实硬件上实现最低延迟”这一目标贯穿于模型设计的全流程，从搜索空间定义、候选生成到优化算法，都围绕着移动端的实际约束展开，从而产出了真正面向工业级部署的、开箱即用的高质量模型。
:::

## 结论与展望

> MobileLLM-Flash 不仅仅是一个模型系列，它更是一种范式的转变。它有力地证明了：

1. 延迟是第一原则：**在端侧，真实的、硬件可测量的延迟，是比 FLOPs 或参数量更重要的优化目标**。用“硬件在环”的方法，让模型去适应硬件，而不是反过来，是设计出高效模型的关键。
2. 搜索是强大的工具：**通过结构化的剪枝和两阶段贝叶斯优化，我们可以在巨大的设计空间中，高效地探索出符合真实约束的最优解**。这避免了以往依赖直觉和经验的手动设计可能带来的偏差。
3. 简单的算子也能成就大事：:mdnice-bold-italic[不一定非要追求复杂新颖的注意力机制。利用好标准算子如全局注意力、跳跃注意力，并精心布局它们的组合方式，在移动端就能达到出人意料的加速效果。]

::: block-1
对于 AI Infra 从业者而言，提供了极其宝贵的启示：:mdnice-bold-italic[在构建下一代端侧 AI 应用时，我们需要将“模型设计”与“运行时系统”更紧密地结合起来。]

这意味着，一个优秀的 AI Infra 工程师**不仅要懂模型架构，还要懂硬件、懂操作系统、懂编译器**。只有这样，我们才能真正让 AI 模型从论文的象牙塔中走出来，跑进每个人的口袋。
:::

未来的挑战依然存在。随着模型能力的增强和上下文长度的进一步增加，如何持续优化内存带宽和计算效率，如何处理更复杂的多模态数据，都将是我们需要继续探索的课题。但 MobileLLM-Flash 无疑为我们指明了一个正确的方向：让硬件说话，让应用落地，这是端侧 AI 走向规模化的唯一路径。
