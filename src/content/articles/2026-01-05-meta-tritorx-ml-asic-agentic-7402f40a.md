## 一、引言

> 机器学习（ML）和人工智能（AI）硬件的快速普及，预计将导致到 2028 年美国数据中心功耗占总电力消耗的比例达到 6.7%至 12.0%[Shehabi et al., 2024]，这凸显了开发高效加速器硬件以支持大规模模型推理和训练的迫切需求。

对此，行业正大力投入构建异构数据中心集群，其中整合了多种加速器解决方案，包括为特定工作负载和需求定制的硅基 ASIC（专用集成电路，一种为特定用途设计的集成电路，区别于通用 CPU/GPU）[Silvano et al., 2025]。例如，**Meta 训练与推理加速器（MTIA）目前正为 Facebook、Instagram 和 Threads 平台上数十亿用户提供推荐模型（DLRM）支持** [Naumov et al., 2019]，同时:mdnice-bold-italic[相比 GPU 将总拥有成本（TCO，指设备全生命周期内的总成本，包括采购、运维等）降低了 44%] [Coburn et al., 2025]。

然而，尽管自研加速器具有显著优势，但每一个新平台都需要大量工程投入来构建与现有工具（如 PyTorch[Paszke et al., 2019]）兼容的软件生态系统，这源于对大量张量算子的需求[Kahn et al., 2022]。其中一个关键问题是**算子覆盖率**，:mdnice-bold-italic[即 PyTorch 张量库 ATen[Paszke et al., 2017]中，能够在特定加速器上原生执行内核的算子所占比例]。建立并维持全面的算子覆盖率是一项艰巨的任务，无论是运行新模型的推理任务，还是为训练任务原型化新模型架构，都离不开这一基础。换言之，新的加速器平台不仅需要具备有竞争力的单位成本性能，还需提供友好的开发者体验，配备完善的内核后端。

> 为应对这一挑战，我们提出了一种智能体驱动的 AI 系统——TritorX，它能够大规模生成功能正确的 Triton ATen 内核以适配 MTIA。该工具融合了开源大型语言模型（LLM）与自定义代码检查器（linter）、即时编译以及基于 PyTorch OpInfo 的测试框架。TritorX 不仅兼容已部署的 Meta 训练与推理加速器（MTIA）硬件，还支持下一代设备的硬件仿真环境。

与以往优先优化少量高使用率算子性能的内核生成方法不同，TritorX 以**覆盖率** 为核心目标：

- **系统注重在整个算子集中确保正确性和通用性，涵盖不同的数据类型、张量形状和参数模式。**
- 在实验中，TritorX 成功生成了 481 个独特的 ATen 算子及其包装器（wrapper），且所有算子均通过了对应的 PyTorch OpInfo 测试（总计超过 20,000 项测试）。
- TritorX 为新加速器平台“overnight（隔夜式）”生成完整的 PyTorch ATen 后端奠定了基础。

::: block-1
需要说明的是，:mdnice-bold-italic[TritorX 与其他内核生成方案存在本质区别：我们的框架严格以整个后端的正确性和通用性为优化目标，而非仅针对一小部分关键路径算子提升性能] [Lange et al., 2025a]。

例如，TritorX 生成的内核-包装器对可兼容多种量化数据类型、张量形状或 PyTorch 参数输入。在某些情况下，TritorX 会为单个算子生成多个内核实现，并在包装器函数中实现对应的调度逻辑。通过名为“Triton MTIA”的方言（dialect，指针对特定硬件定制的 Triton 语言变体），标准模型可生成可运行的内核，并借助执行反馈识别 MTIA 特有的语义或内部函数（intrinsic，硬件原生支持的底层函数）。
:::

::: image-caption
图 1：TritorX 系统概述。(A) 选择待生成的 OpInfo 算子及其 PyTorch 文档字符串/签名；(B) TritorX 通过有限状态机（FSM）反馈循环对每个算子进行迭代处理，利用大型语言模型（LLM）生成内核-包装器对，生产环境基础设施支持大规模并行生成与测试；(C) 若算子通过所有对应的 OpInfo 测试，则生成任务成功

重要的是，**TritorX 仅需输入 ATen 算子的文档字符串（docstring），即可生成对应的实现代码**。图 1 展示了加速器启用流程的端到端工作流。

TritorX 通过迭代式上下文内学习（in-context learning，指 LLM 通过上下文示例学习任务模式的能力），基于编译器等工具直接提供的反馈，提炼硬件需求及其对应的 Triton 语义。以往研究表明，类似 TritorX 的流水线常存在“作弊”行为：在算子包装器中调度到主机（host，指控制加速器的 CPU）或调用其他未定义的 PyTorch 函数[Lange et al., 2025b]。**为避免这一问题，我们集成了自定义代码检查器（linter），可捕获此类未授权的函数或工具调用，并通过反馈强制修正。**

> TritorX 的核心在于整合多种测试框架，以确保在不同数据类型、张量形状或输入参数下的正确性。我们采用 PyTorch 原生测试框架 OpInfo，并结合自定义测试框架——该框架**从生产环境的模型中提取测试数据**。

综上，本文的贡献如下：

- **系统层面**：:mdnice-bold-italic[提出一种基于开源 LLM 的有限状态机（FSM），可端到端生成、编译并验证数百个 Triton MTIA 内核]。
- **覆盖率目标**：设计以功能正确性和后端覆盖率为优化目标的方案，通过生成包装器实现对多种数据类型、形状及分支调度逻辑的支持。
- **实验结果**：在大规模测试中，TritorX 生成了 481 个 ATen 内核（MTIA 兼容 OpInfo :mdnice-bold-italic[覆盖率达 84.7%:mdnice-bold-italic[），] 所有内核均通过对应的 OpInfo 测试] （总计超 20,000 项）。此外，TritorX 在 MTIA 上实现了多种模型的端到端启用能力，可在:mdnice-bold-italic[数小时内完成对整个 OpInfo 算子集的迭代]，支持快速的后端开发与迭代。
- **测试框架**：整合 PyTorch OpInfo 与生产环境输入数据测试，确保在部署场景下的正确性。

## 二、背景知识

> 本节将介绍 MTIA 架构、Triton MTIA 方言，以及 TritorX 如何实现大规模内核生成。

MTIA 架构采用 8×8 的处理单元（PE，加速器中的基本计算单元）网格，负责执行核心内核工作负载[Coburn et al., 2025]。每个 PE 包含一个标量 RISC-V 核心、一个向量 RISC-V 核心，以及多个固定功能单元（FFU，用于执行特定专用计算，如 DMA 和点积运算）。图 2 展示了 MTIA 的架构概览。

![文章插图](/articles/2026-01-05-meta-tritorx-ml-asic-agentic-7402f40a/images/05.webp)

::: image-caption
图 2：MTIA 架构概述。核心内核计算由处理单元（PE）网格执行，每个 PE 包含标量核心、向量核心和专用功能单元
:::

::: block-1
具体而言，**MTIA 具有独特的内存层级结构**：

- 通过一系列:mdnice-bold-italic[交叉开关] （XBAR，用于连接不同组件的高速数据传输链路），所有 PE 可访问大量本地静态随机存取存储器（SRAM）。
- :mdnice-bold-italic[PE 专用的 FFU 支持循环缓冲区] （circular buffer）抽象，能够高效地:mdnice-bold-italic[对计算与通信进行流水线处理]，从而抵消数据移动带来的整体延迟。
:::

这种设计带来的计算效率提升，使得 **MTIA 可采用成本更低的 LPDDR5 内存**，而非高带宽内存（HBM）。重要的是，:mdnice-bold-italic[MTIA 在下降主机侧内核或任务调度开销方面做了大量优化，从而支持即时模式工作流] （eager-mode，PyTorch 中一种逐操作执行的计算模式）。

要在 MTIA 上执行内核，开发者可通过 C++ API 编写工作负载（该 API 通过 LLVM 后端编译），或使用为 MTIA 定制的 Triton 方言。Triton 是一个开源 Python 库，提供领域特定语言（DSL），用于编写高效的自定义 GPU 内核[Tillet et al., 2019b]。它通过直观的块级抽象（block-based abstraction）让开发者表达复杂的并行计算，同时自动处理内存访问模式、同步等底层细节，使开发者无需深入了解 GPU 架构即可实现与手写 CUDA 代码相当的性能。

> 尽管 Triton 最初是为表达 GPU 计算语义而设计的，但其中多个现有语义可直接映射到 MTIA 的硬件特性。

例如，无需将 Triton 块（block）映射到 GPU 线程，而是可将其**映射到 MTIA 的 PE 网格，并通过加载/存储操作中的掩码（masking）确保符合张量边界**。此外，加载/存储操作可利用 MTIA 的 DMA 引擎实现结构化内存访问。当内部函数（intrinsic）无法完全匹配时，我们可通过扩展底层 Triton 功能集（如引入用于非线性激活的 FFU 设备库）来适配。Triton MTIA 是一种专用方言，旨在实现上述映射，并通过编译器后端提供多种性能优化。

尽管 Triton MTIA 尽可能保留了现有 Triton 语义，但 **MTIA 的某些硬件需求导致了显著的语义差异**。

::: block-1
- 例如，MTIA 要求 32 字节对齐的内存访问模式，若不满足此要求，加载/存储操作将失败。表面上看，这可能会给使用现成模型生成内核带来困难；
- 但 Triton MTIA **提供了详细的断言（assert）信息和错误处理机制，可为模型提供必要反馈，使其能够将标准 Triton 代码适配到 MTIA**。
:::

事实上，:mdnice-bold-italic[构建一个能提供描述性反馈的编译器工具链，是利用自动化方法生成代码的关键环节。]

> 当前的挑战在于：实现与现有生产环境基础设施兼容的执行流水线。

MTIA（及所有未来硬件版本）部署在生产级 Linux 容器生态系统中[Tang et al., 2020]。典型的生产工作流需要**端到端的工作负载** （例如，为特定服务大规模部署或训练模型），这还需要**与 PyTorch 生态兼容** 的复杂内核注册栈。然而，:mdnice-bold-italic[Triton 即时编译（JIT）支持在这些生产容器中实时生成、编译和测试内核，从而实现大量并行实验。]

## 三、系统设计

本节将介绍 TritorX 的系统架构，以及用于验证生成结果的测试框架。

### 3.1 Triton MTIA 语义的上下文内提炼

> 生成 Triton MTIA 代码的朴素方法（naive approach）是：在 LLM 的初始提示中加入硬件需求和对应 Triton 语义差异的完整说明，然后检查生成的代码是否通过相关测试。**但在实际场景中，完整的加速器文档往往滞后于其他栈组件** （stack component，指软件生态中的各个层级模块）。**早期尝试通过简单的提示工程** （prompt engineering，通过设计优化输入提示来提升 LLM 性能的技术）:mdnice-bold-italic[为 MTIA 生成 Triton 代码，不仅需要大量人工干预，且无法实现规模化。] 这里可以参考 GEAK 的零样本（zero-shot）结果

相比之下，TritorX 通过与代码检查器（linter）、编译器和调试器的交互获取反馈，以迭代方式实现上下文内学习，从而提炼硬件需求及其对应的 Triton 语义。

::: block-1
我们将 TritorX 实现为有限状态机（FSM），并配备专用工具和流程，包括代码检查（linting）、编译、测试、调试和 LLM 调用。
:::

尽管近年来的内核生成框架常依赖具有预设工具调用能力的专用推理智能体[Lange et al., 2025b; Wang et al., 2025; Chen et al., 2025b; Andrews and Witteveen, 2025; Li et al., 2025a,b]，但我们发现，:mdnice-bold-italic[在生产环境基础设施中集成 FSM 架构更易于实现规模化。FSM 为执行和处理的内容提供了明确的约束，且便于对系统关键组件进行调试——这对于生产级系统而言是重要需求]。此外，FSM 的后端支持在已部署的 MTIA 机器和下一代 MTIA 的 QEMU 模拟器（一种用于模拟硬件的工具）上同时进行编译和测试。

1. 与文档字符串中指定的 PyTorch 算子签名匹配的 Python 包装器；

我们选择 exp、argmax 和 diag 算子作为示例，因其涵盖了多种内核类型（如逐元素算子、归约算子）。通常，ATen 文档字符串会引用其他算子的文档字符串（例如，argmax 引用 max），因此我们构建了所有文档字符串的有向无环图（DAG），以确保包含“嵌套”文档字符串，保证信息完整性。提示中还包含下游解析器所需的输出格式说明。

**推理 LLM 根据提示生成初始候选包装器/内核对**，随后将其发送至自定义 Triton MTIA **代码检查器** （linter）。该代码检查器负责以下三项任务：

::: block-1
1. 确保输出的包装器和内核代码与 Triton JIT 框架兼容；
2. 防止“作弊”行为——即检查实现是否调用了尚未实现的其他算子；
3. 确保代码使用有效的 Triton MTIA 语法和库（上游 Triton 的部分功能在 MTIA 上不可用）。
:::

**代码检查器轻量且可配置** （详见下面 Triton MTIA Linter）。若检测到代码检查违规，将生成结构化报告，并作为反馈发送给模型以进行修正（部分见下面 State Transition Prompts 状态转换提示词）。此过程重复进行，直到无代码检查错误或达到 LLM 调用次数上限。

- 若结果在指定误差范围内，则继续下一个测试用例；
- 一旦运行器遇到编译失败、运行时错误或精度错误，流程将中断并进入“反馈”状态，以确定后续操作。

**反馈状态分析测试运行器的执行结果**，:mdnice-bold-italic[判断是否需要为下一次 LLM 迭代生成反馈提示，或是否需要进一步调试]。例如：

::: block-1
- 若最近一次运行因运行时崩溃产生崩溃转储（crash dump），则通过基于 LLDB（LLVM 调试器）的调试器加载该转储，提取调用栈（backtrace）、解码寄存器和其他帧信息，作为修正提示的上下文（如内存访问违规细节）；
- 若发生编译失败，根据超参数配置，可选择通过次要 LLM 实例（同样可预先配置）总结编译日志（Triton MTIA 编译日志可能包含数千个 token，提炼关键错误信息可避免主 LLM 会话的上下文窗口溢出）；
- 若检测到精度错误，则在反馈提示中包含 MTIA 输出张量和 CPU 输出张量的摘要——即使对于大型输出张量，张量值的精简摘要通常也足以让模型推理潜在的精度问题。

> 生成适当的反馈提示后，流程重复进行，直到满足以下任一条件：

1. 所有测试通过，流程成功退出；
2. 达到预设的 LLM 调用次数上限，流程退出；
3. LLM 上下文窗口饱和，以最新生成的包装器/内核作为初始候选，启动新的 LLM 对话会话；
4. 意外错误导致主进程崩溃（TritorX 全程实现了全面的异常处理，包括在必要时启动容器化子进程，以尽可能避免主进程崩溃）。

**为实现大规模算子生成，上述流程可针对每个指定算子并行执行，甚至可对失败的算子重复执行**。大规模运行的配置参数包括：目标算子、期望数据类型、LLM 参数（如模型、上下文长度、温度参数）、运行参数（如最大 LLM 调用次数、最大对话会话数）以及测试复杂度。

重要的是，**算子的编译和执行在生产级 MTIA 机器上进行**；LLM 调用则通过集中式推理平台服务处理，以支持大规模运行所需的高并发请求。

### 3.3 ATen 算子与 OpInfo 测试

> 为评估我们方法的规模化可行性，我们针对 PyTorch OpInfo 测试套件中定义的算子生成内核。重要的是，OpInfo 通过为所有支持的数据类型、张量形状和输入参数提供“样本”，实现对算子覆盖率的严格测试。例如，OpInfo 包含数百项针对 linalg.vector_norm 算子的测试，可全面验证不同输入/输出张量形状及输入参数配置的正确性。

**将 OpInfo 作为主要测试框架，构建了端到端生成流水线，其测试数量较当前最先进方案（state-of-the-art）高出一个数量级** [Ouyang et al., 2025]。通过在生成过程中覆盖更广泛的输入空间，我们期望最终实现的算子能在任意原型开发和生产环境中更可靠地工作。

尽管如此，我们认识到:mdnice-bold-italic[覆盖整个输入空间的完美测试是不可能的。因此，我们引入了针对生产模型的二次测试框架，该框架使用生产环境输入数据]。此额外测试套件可用于评估算子通过 OpInfo 测试后的泛化能力：若在生成阶段发现覆盖缺口（如生产数据测试失败），TritorX 可进一步修复该缺口。

MTIA 硬件存在某些限制，导致部分算子和测试与目标工作负载不兼容或不相关。例如：

- MTIA 不支持复数，因此我们从生成列表中移除了对应的算子（如 FFT 算子）；
- 由于设备与主机的随机数生成算法存在差异，验证随机数算子的输出正确性极具挑战性，因此也将其排除；
- 受分布式测试基础设施限制，我们仅覆盖 OpInfo 测试数量少于 900 项的算子。

::: block-1
最终筛选后的算子列表包含 568 个独特算子（从原始 629 个中筛选），且仅测试以下数据类型：bfloat16、float16、float32、int32 和 int64。:mdnice-bold-italic[所有算子的测试总数超过 20,000 项，且仅当算子通过所有对应测试时，才将其归类为“成功生成”。]
:::

## 四、实验与结果

> 本节将介绍用于验证我们方法的实验。

- 首先，我们呈现涵盖所有与 MTIA 兼容的 OpInfo 算子、跨多次大规模运行的聚合结果。从这组生成的算子中，我们将各类第一方和第三方模型进行“产品化”（即使其达到可投入实际生产环境的状态）。
- 此外，我们还扩展了这些算子的测试套件，纳入基于生产数据的额外正确性测试，以识别 OpInfo 最初未覆盖到的漏洞。
- 最后，我们对 TritorX 的多种配置进行消融实验，明确流水线中各组件的重要性及其作用原因。

本实验的基准设置为：在所有 568 个与 MTIA 兼容的 OpInfo 算子上运行 TritorX，具体配置如下：

- 每个算子最多允许 3 次 TritorX 尝试（即对话会话），以生成通过所有测试的内核并判定为“成功”；
- 每次尝试最多允许 15 次大语言模型（LLM）调用，换言之，在判定该尝试“失败”前，最多可完整迭代 15 次有限状态机。
- **内核生成所使用的大语言模型（LLM）为 Code World Model（CWM，参见[Copet et al., 2025]）或 GPT-OSS 120B（OpenAI, 2025）**。
- 反馈总结模型采用 Llama-4-Maverick，其生成参数与 CWM 保持一致。

::: block-1
**我们将生成任务分发到 200 台生产环境中的 MTIA 设备上，这些设备可在 2 小时内完成 95%的运行任务**。:mdnice-bold-italic[剩余 5%的长尾任务（通常由不佳的推理路径等因素导致）则需额外 6-8 小时才能完成]。新的运行任务可并发分发。**依托这一基础设施，我们执行了多次运行，后续运行重点针对前序运行中失败的算子。**

### 4.1 端到端应用

> 基于基准 OpInfo 算子集，我们利用 TritorX 在 MTIA 上实现了多种第一方和第三方模型的支持。尽管 OpInfo 测试套件具有较强的鲁棒性，但我们意识到，**生产环境的工作流中可能包含 OpInfo 测试分布之外的算子及算子参数** （如张量形状、标量值等）。

:mdnice-bold-italic[为解决这一问题，我们将多个目标模型拆解为独立算子，提取训练过程中观察到的所有算子输入，并用这些输入替代 OpInfo 生成的输入，纳入 TritorX 的验证循环。]

::: block-1
具体而言，我们**通过`__torch_dispatch__`机制（PyTorch 中的一种算子拦截接口）对多个代表性模型的前向和反向传播过程进行插桩**，这些模型包括 NanoGPT（[Karpathy, 2023]）、DLRM（[Naumov et al., 2019]）以及两个内部推荐模型（记为 MM1 和 MM2），以**拦截并记录传递给每个算子的张量和标量数据。**

所有四个模型均采用固定批次大小（batch size）1024 进行评估，并训练一个迭代轮次；其中后三个模型（DLRM、MM1、MM2）使用真实生产数据而非随机输入执行。
:::

此外，我们为 TritorX 新增了一个步骤：首先将给定算子与预生成的 OpInfo 算子（若存在）进行匹配，然后立即使用从完整端到端运行中收集的输入（记为 MIS，Model Input Shapes）对其进行测试。若该内核无法直接通过所有测试，则以其为起点，由 TritorX 进一步优化（见表 2 中 B 列“MIS”）。

## 五、相关工作

### 5.1 定制 ASIC、MTIA 与深度学习编译器

> 自 Triton 推出面向高性能 GPU 内核的 Python 优先 DSL（领域特定语言，参见[Tillet et al., 2019a]），并被 PyTorch Inductor（[Ansel et al., 2024]）广泛用于生成融合算子以来，**多个生态系统已推出 Python 级别的内核 DSL。**

- **NVIDIA 的 Warp** （[Macklin, 2022]）是一款用于编写 CUDA 内核的 Python DSL，提供了可选的基于分块（tile-based）的编程模型，用于张量核心（tensor-core）GEMM（通用矩阵乘法，深度学习中的核心计算操作）。
- 在 **JAX 框架中，谷歌的 Pallas** （[Bradbury et al., 2018]）允许用户用 Python 编写自定义内核：其通过 Triton 面向 GPU，通过 Mosaic（[Bansal et al., 2023]）面向 TPU（张量处理单元，谷歌专为机器学习优化的硬件加速器，参见[Jouppi et al., 2017]），从而支持在 JAX 生态系统中实现细粒度的融合操作。Meta 也将 Triton 应用于 MTIA，以提升 PyTorch 开发的效率。

### 5.2 内核研究

近年来，针对特定设备的定制内核优化一直是研究热点：[Lavin and Gray, 2016; Dao et al., 2022; Dao, 2023; Shah et al., 2024]。这种关注既受前沿模型训练与推理计算需求快速增长的推动，也为其提供了支持：[Cottier and Rahman, 2024; Hooker, 2021]。

### 5.3 基准测试

> 为衡量大语言模型生成内核的功能正确性与性能，研究社区已发布多个基准测试套件。

- KernelBench（[Ouyang et al., 2025]）和 TritonBench（[Li et al., 2025a]）用于评估模型能否为代表性算子套件生成正确且高效的 GPU 内核；
- 而 NPUEval（[Kalade et al., 2025]）则针对 AMD NPU（神经网络处理单元，专为 AI 任务设计的硬件加速器）。
- 此外，AlgoTune（[Press et al., 2025]）重点关注大语言模型能否通过自然语言描述加速科学计算问题的求解。
- 自动生成的内核容易利用测试套件的漏洞（即未覆盖的测试场景），针对这一问题的研究已取得显著进展：[Lange et al., 2025b; METR, 2025]。
- 值得注意的是，与我们的工作类似，BackendBench（[Saroufim et al., 2025]）也采用 PyTorch 的 OpInfo 作为全面测试套件，以确保内核的正确性与完整性。

### 5.4 基于大语言模型的内核生成

大多数基于大语言模型的内核生成方法依赖提示工程（prompting techniques），并结合测试时计算作为搜索手段。

> 近期的系统通过训练或提示大语言模型来合成内核，或通过搜索优化内核。

- KernelLLM（[Fisches et al., 2025]）为从 PyTorch 模块生成 Triton 内核提供了有监督基准。
- AutoTriton（[Li et al., 2025b]）则引入了基于可验证奖励的强化学习（reinforcement learning）。
- 此外，[Baronio et al., 2025]还探索了用于 CUDA 内核生成的多轮强化学习方法。

> 另一方面，已有多种方法通过现有大语言模型扩展推理计算，涵盖提示工程、智能体（agentic）技术、进化算法等多种技术，并结合单元测试进行验证：

- [Lange et al., 2025b; METR, 2025; Chen et al., 2025a; Wei et al., 2025; Wang et al., 2025]。

尽管已有多种针对 CUDA 和 GPU 的方法，但我们认为目前仅有 NPU-Eval（[Kalade et al., 2025]）采用 C++面向非 GPU 设备（如 NPU）。

## 六、讨论与未来工作

> TritorX 的有限状态机（FSM）框架为生成功能正确的 Triton MTIA 内核提供了稳健的测试套件。凭借其灵活性，我们确定了多个可进一步提升覆盖率与性能的方向，并反思了对成功至关重要的关键因素。

### 6.1 自洽算子生成

为防止“作弊”，检查器限制智能体在封装器（wrapper，用于将 PyTorch 算子接口转换为 Triton 内核接口的代码）中使用其他 ATen 算子（张量分配相关算子除外）。:mdnice-bold-italic[一种更高效且可能更优的方法是：允许封装器调用其他算子，但需满足两个条件——这些算子也在新后端中实现，且算子间不存在循环依赖] （cyclic dependencies，指算子 A 依赖算子 B，而算子 B 又依赖算子 A 的情况，会导致代码无法编译或运行死锁）。这需要一种自洽的生成方案，使智能体能够感知整个后端的状态，因此不再是“易并行”（embarrassingly parallel，指可轻松拆分为独立子任务并行执行的问题）的生成模式。

### 6.2 优化提示工程

如前所述，我们发现不含专用 MTIA 文档的简单提示效果最佳，但提示优化仍有提升空间。此外，我们可通过定位（localization，即引入相关算子作为上下文）等策略改进示例内核-封装器对的质量，甚至可通过多轮运行实现流程的自举（bootstrapping，指利用前期生成的正确结果优化后续生成过程）。

### 6.3 全智能体流水线

在更高层面，我们讨论了将整个有限状态机（FSM）改造为智能体驱动模式——将当前大多数状态转换为大语言模型可调用的工具，并新增与调试相关的工具（如为大语言模型提供代码执行沙盒）。

### 6.4 专用模型微调

本研究中使用的两个模型均为开源的现成模型（off-the-shelf），所有 MTIA 相关的上下文信息均通过与检查器、编译器和调试器的交互获取。另一个正交的研究方向是：针对 Triton MTIA 内核生成任务对大语言模型进行微调（post-training），并将其结果与文献中针对普通 Triton 的结果进行对比。

### 6.5 规模的重要性

由于底层语言模型具有随机性，在非零温度参数（temperature>0，控制生成结果的随机性）下重复运行基准测试会得到不同的通过率。因此，**通过多次运行聚合通过的算子即“测试时扩展”（test-time scaling）技术可显著提升算子覆盖率。**

例如，仅通过两次 CWM 基准测试的聚合，覆盖率就从 55%提升至 64%。我们推测，进一步扩展这一技术，并探索更复杂的策略如进化扩展（evolutionary scaling，参见[Lange et al., 2025b]）将大幅提升覆盖率。此外，支持更多代硬件、更多 DSL 以及更多算子定义，需要一个灵活且可扩展的算子集生成流水线。

### 6.6 构建后端维护环境

随着 AI 驱动的内核生成技术发展，AI 生成的内核数量终将超过人类可审核的范围——尤其是在硬件多样性增加、多代硬件共存于生产集群的场景下。**构建无需人工审核、完全自动化的稳健框架**，对 AI 生成内核的成功应用至关重要。这一需求在每次模型更新都需全面刷新内核库以优化性能时，将变得更加迫切。

## 七、结论

> 本文介绍了 TritorX——一款可扩展、以覆盖率为优先目标的系统，用于自动化定制 ML ASIC（机器学习专用集成电路）的 PyTorch 后端搭建，并在 Meta 的 MTIA 硬件上进行了验证。**TritorX 将现有大语言模型（LLM）与有限状态工作流、生产级兼容工具相结合，可在已部署的硬件以及面向下一代设备的基于 QEMU 的模拟器上执行**。该系统生成了 481 个 ATen 算子，这些算子均通过了对应的所有 OpInfo 测试（总计超过 20000 项测试），整体通过率达 84.7%。基于这些算子，我们成功在 MTIA 上部署了 80%以上的多类第一方和第三方大规模模型。

通过对模型和系统因素的消融实验，我们明确了影响覆盖率的关键组件，**使后端搭建从“手工技艺”（artisanal effort）转变为可量化的工程流程。**

除 MTIA 外，:mdnice-bold-italic[TritorX 的设计还可应用于其他加速器，并自然扩展到相邻任务（如跨代内核迁移、通过仿真为硬件/编译器提供早期反馈）]。尽管性能调优不在本研究范围内，但 TritorX 为自动调优、调度搜索（schedule search）和基于学习的代码优化提供了基础框架。

::: block-1
未来的研究方向包括：扩展算子类别（如归约算子、稀疏/量化算子）、增强安全性/隔离性、为代码生成添加形式化检查（formal checks）、与编译器 IR 更紧密集成，以及构建性能优化的自动化路径。
:::

综上所述，这些结果为工具链创建的普及化提供了切实可行的蓝图，并为内核工程师提供了“倍增器”（force multiplier）——将专家精力从基础工作中解放出来，专注于真正性能关键的路径，同时**将整个后端的搭建时间从数月缩短至数小时。**
