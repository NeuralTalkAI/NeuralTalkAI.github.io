## 一、被忽视的鸿沟：企业级 Agent 的“静态诅咒”与自进化的系统瓶颈

> LLM 智能体的落地已经从实验室演示走向生产部署，部署的对象也从单纯的“输入 token 输出 token”的语言模型，逐渐变成嵌入复杂业务环境的长周期智能体策略。

这些智能体可以读取文件、调用工具、检索文档、触发 API、更新记忆、请求人工审批，完成复杂的分析类工作，**但能力提升的方式却还停留在完全依赖人工的传统软件迭代模式。**

### 1.1 从模型部署到智能体部署：范式转变带来的错配

> 传统 LLM 服务的部署逻辑非常清晰：模型训练完成后打包上线，通过推理接口对外提供服务，:mdnice-bold-italic[后续的能力迭代大多依赖周期性的离线微调，部署后的模型本身基本保持静态。这种模式适配单轮对话、文本生成等简单场景，但完全跟不上智能体时代的需求。]

智能体是多步交互、工具增强的长流程系统，部署后每天会产生成千上万甚至百万级的工具交互轨迹，这些轨迹中蕴含了大量可以用来提升能力的经验信号。**但在当前的主流模式中，这些轨迹仅仅被用来做调试、运维和合规审计，没有被转化为学习素材。智能体的能力提升仍然依赖人工循环**：运维人员抽检日志、定义新的评测基准、人工修改提示词、补充工具描述、离线微调模型、调整智能体编排逻辑、重新部署上线。

::: block-1
整个闭环完全由人工驱动，不仅成本高、周期长，还会出现训练数据与生产场景的分布偏差——离线训练用的是人工构造或筛选的数据，和真实生产环境中的复杂交互存在天然差异，导致微调后的模型上线后效果往往达不到预期。
:::

### 1.2 个人自进化 Agent 的兴起与企业级的落地壁垒

近两年自进化智能体已经不再是概念，个人级产品已经验证了这条路径的可行性。比如 OpenClaw 这类个人智能体，可以作为用户专属的持久化助手，跨邮箱、日历、出行、社交等应用完成任务，同时能从和用户的每一次交互中持续学习，更新记忆、补充技能、优化提示词，实现能力的自我迭代。

> **但个人级的自进化方案，完全无法直接迁移到企业级场景**，二者面临的问题有本质区别。

- 个人智能体只服务单一用户，数据所有权清晰，不需要考虑多团队权限隔离、合规审计、数据脱敏等问题；
- 而企业级智能体需要服务多个业务线、多个租户、大量终端用户，必须严格遵守数据权限、许可边界、隐私合规、审计追溯等要求。

| 场景 | 核心约束与要求 |
| --- | --- |
| 企业编码智能体 | 跨产品团队问题解决轨迹学习；禁止泄露各团队私有代码与业务逻辑。 |
| 客服智能体 | 从海量工单与用户交互中持续学习；严格保护用户隐私，符合数据安全法规（如GDPR、《个人信息保护法》）。 |
| 科研智能体 | 基于实验轨迹与文献检索流程优化能力；必须保留完整数据溯源链路，确保实验可复现。 |

**这些都是个人自进化方案从未解决的核心问题，也是企业级自进化落地的核心障碍。**

### 1.3 真正的瓶颈：不是 RL 算法，是系统底座

> 当前行业的研究重心大多集中在算法层面：更强大的基座模型、更有效的提示工程、更丰富的工具集成、更先进的强化学习算法。但很少有人关注，**企业级自进化的核心瓶颈根本不在算法层面。**

强化学习算法本身已经非常成熟：从 PPO 到 DPO，从 RLHF 到 RLAIF，再到以 DeepSeek-R1 为代表的推理类强化学习，算法层面已经有了大量成熟的可选方案，能够适配不同的优化目标。:mdnice-bold-italic[真正阻碍企业级自进化落地的，是一整套系统层面的缺失：没有标准化的方式把生产环境的交互轨迹转化为可用于 RL 训练的数据，没有合规的机制跨异构系统采集学习素材，没有自动化的流程决定什么时候用什么方式升级智能体，没有安全的管控体系保证进化过程的可控可审计。]

这也是这篇论文最核心的洞察：**企业级自进化智能体的落地，本质上是一个系统工程问题，而不是算法问题**。要让自进化从个人 demo 走向企业规模化部署，首先要搭建一套完整的系统底座，打通从生产交互到学习进化的完整闭环。

::: block-1
企业级智能体的自进化瓶颈，根源不在于模型能力不足或强化学习算法不成熟，而在于**缺少一套能将生产交互轨迹转化为受管控学习素材、并自动触发安全进化的系统底座**。:mdnice-highlight[智能体部署范式的转变，要求 AI 基础设施从面向静态模型的后训练系统，升级为面向动态智能体的在线进化系统。]
:::

## 二、第一根支柱：ATDP 智能体轨迹数据协议，让“不可学习”的日志变成“可归因”的训练素材

> 要实现自进化，第一个要解决的根本问题是数据抽象：我们到底需要采集什么样的数据，才能支撑强化学习训练？现有的智能体日志只能用来排查问题，远远达不到 RL 训练的要求。

论文提出的智能体轨迹数据协议（Agent Trajectory Data Protocol，简称 ATDP），就是为了解决这个底层问题，它把异构的智能体执行过程，统一转化为标准化的、可审计、可重放、可归因的事件序列。

### 2.1 为什么现有 Agent 日志撑不起在线 RL？

当前绝大多数智能体系统的日志，都是为运维调试设计的，通常只记录提示词内容、生成结果、工具调用记录、接口延迟、错误信息、token 用量这些基础字段。:mdnice-bold-italic[这些信息用来排查接口故障、统计用量、做合规审计足够，但用来做强化学习训练存在本质的缺失。]

**强化学习的核心是信用分配：要明确知道轨迹中的每一步决策，对最终的成功或失败有多大贡献，才能针对性地优化策略**。这就需要步级的完整决策过程信息：Agent 在做决策时看到了什么观测、当时的内部状态是什么、选择了什么动作、动作执行后得到了什么结果、后续获得了什么奖励信号，以及对应的模型版本、工具版本、租户信息、合规状态等元数据。

缺少这些信息，轨迹就只是一堆不透明的日志，无法做因果分析，无法做信用分配，自然也就无法支撑有效的强化学习。**ATDP 协议的核心目标，就是定义一套标准化的数据格式，把这些 RL 训练必需的信息完整、规范地记录下来。**

### 2.2 ATDP 的核心定义：六元组的步级事件模型

> ATDP 定义的一条完整轨迹 $\tau$，是一个有类型的事件序列，包含轨迹中的所有决策步骤：

$$
\tau=\left(e_{1}, e_{2}, ..., e_{T}\right)
$$

其中 $T$ 是轨迹的总步数，每一个中间步骤 $e_t$ 都是一个六元组，完整记录单步决策的所有关键信息：

$$
e_{t}=\left< o_{t},h_{t},a_{t},y_{t},r_{t},m_{t}\right>
$$

六个字段的具体含义如下：

- $o_t$ 是观测状态，也就是 Agent 在这一步能感知到的所有外部信息，比如工具返回的结果、检索到的文档片段、用户的输入消息、环境的当前状态等，相当于 Agent 做决策时的“输入信息”。
- $h_t$ 是隐藏内部状态，也就是 Agent 的内部思考上下文，比如当前遵循的执行计划、草稿板内容、置信度评估、推理总结等，相当于 Agent 做决策时的“内部背景”。
- $a_t$ 是选择的动作，也就是 Agent 在这一步做出的具体决策，比如带参数的工具调用、生成的回复文本、代码修改操作、记忆更新操作等，相当于 Agent 的“行为输出”。
- $y_t$ 是动作的结果，也就是动作执行后的直接反馈，比如工具的返回值、用户的接受/修改/重试操作、程序的退出码等，相当于动作的“即时反馈”。
- $r_t$ 是奖励信号，也就是这一步对应的学习奖惩信号，可以是二元的成功失败标记、标量分数、自然语言批评，或者从动作结果中提取的隐含信号，相当于 RL 训练中的“优化目标信号”。
- $m_t$ 是相关元数据，包括接口延迟、token 用量、调用成本、租户 ID、会话 ID、上下文框架指纹、模型 ID 等附属信息，相当于这一步的“溯源标签”。

::: block-1
**可以用一个企业客服 Agent 的场景做理解**：用户发起退款请求的某一步中，观测 $o_t$ 是用户的退款诉求加上之前的完整对话历史；内部状态 $h_t$ 是 Agent 当前的执行规划：先查订单、再校验退款条件、最后执行退款操作；动作 $a_t$ 是调用“查询订单”工具，参数为用户手机号；动作结果 $y_t$ 是工具返回的用户近 30 天的订单列表；奖励 $r_t$ 初始为空，需要等后续用户确认订单、退款完成、给出满意度评价后再补充；元数据 $m_t$ 则记录了本次调用的模型版本、所属业务线、工具版本、调用耗时等信息。
:::

如果把内部状态 $h_t$ 和元数据 $m_t$ 去掉，这个六元组就退化成标准的部分可观测马尔可夫决策过程抽象，但 ATDP 的丰富性足以支撑 LLM 智能体特有的所有元素：推理轨迹、检索片段、工具 schema、人工纠错、自然语言批评等，适配各类异构的智能体范式。

### 2.3 ATDP 的六大设计原则

> 为了适配企业级场景的复杂需求，ATDP 协议遵循六大核心设计原则：

| 特性 | 描述 | 补充说明 |
| --- | --- | --- |
| 决策相关的有限披露 | ATDP 只记录支撑行为优化的必要信息，不暴露全部 token 或完整思考链；聚焦信用分配、因果诊断与轨迹重放 | 零散推理碎片缺乏可审计性，且带来数据安全与隐私风险 |
| 跨框架跨任务统一 | 将学习基本单元从“提示词-回复对”或不透明日志，升级为有类型、可审计、可归因的事件记录 | 兼容不同框架（如 LangChain、AutoGen）与任务（编码、客服等），格式统一 |
| 可归因性 | 每条轨迹需明确回答“哪个观测/提示片段/检索结果/工具调用/记忆项/护栏决策”导致成败 | 工具调用需记录版本、参数 schema、权限、延迟、错误类型、返回对象及后续信任状态（被忽略、纠正、推翻等） |
| 延迟绑定的学习信号 | 奖励与批评信号（如用户纠错、测试结果、人工标注、远程评分）可异步补充至事件的 reward 字段 | 原始决策记录不可修改，保障因果链完整性；适用于企业中规则驱动、采样生成的判断信号 |
| 带版本的可重放性 | 每个事件关联模型 ID 及完整执行环境：框架 schema、工具版本、检索索引快照、护栏配置、策略模型检查点 | 缺失版本信息则经验仅具统计意义，无法支持反事实测试与精确复现 |
| 受管控的可观测性 | 交互数据生成时即嵌入隐私、安全、血缘字段；支持脱敏标记、分类标签、租户 ID、留存策略、合规依据、审核状态、训练合格性标记 | 分级可见：调试人员仅见脱敏轨迹；训练任务需策略审批后访问加密字段 |

::: block-1
ATDP 轨迹协议是自进化智能体的数据基石，它将智能体的交互经验从“调试用日志”重构为“RL 级训练素材”。通过步级六元组事件模型与六大设计原则，ATDP 解决了异构智能体数据的统一表示、信用分配、延迟奖励、可重放性与合规性问题，为后续的学习与进化提供了标准化的数据底座。
:::

## 三、第二根支柱：企业级智能体数据代理，把生产流量转化为受管控的学习语料

> ATDP 定义了学习用的轨迹应该包含什么内容，而企业级智能体数据代理解决的是，在异构的生产环境中，如何无侵入地采集这些轨迹。

数据代理不是简单的 API 网关、追踪导出器或者日志服务，它是把生产工作负载转化为受管控学习素材的核心机制，也是自进化 RL 闭环的第一道安全边界。

### 3.1 数据代理的定位：不是日志网关，是 RL 闭环的第一道安全边界

**企业内部的智能体技术栈几乎不可能统一**：有的团队用 LangChain 或 LangGraph 搭建，有的用 CrewAI 编排，有的用 OpenAI 或 Claude 的官方 Agent SDK，还有大量团队使用自研的定制化编排逻辑。:mdnice-bold-italic[要求所有团队统一框架、改造代码来适配自进化系统，显然是不现实的。]

::: block-1
:mdnice-highlight[数据代理的核心设计思路就是无侵入拦截：不需要修改上层 Agent 的业务代码，只需要在稳定的执行边界做流量拦截，就能采集到所有需要的 ATDP 轨迹数据]。这些稳定的执行边界包括：LLM API 调用、工具调用、检索调用、记忆读写操作、文件或浏览器操作、人工审批事件、最终用户反馈。**只要在这些边界点完成拦截，无论底层用什么框架，都能统一采集到标准化的轨迹数据。**
:::

和传统的日志网关不同，数据代理从设计之初就是为学习服务的，它不仅要导出轨迹，还要完成脱敏、权限管控、奖励采集、重放支持等一系列处理，保证进入学习队列的数据都是合规、可信、可用的。因此**它是自进化 RL 闭环的第一道安全边界，直接决定了后续学习的安全性和有效性。**

### 3.2 六大核心设计原则

> 企业级智能体数据代理遵循六大核心设计原则，覆盖从采集到治理的全流程：

| 特性 | 描述 | 补充说明 |
| --- | --- | --- |
| 兼容现有框架的无侵入拦截 | 数据代理在稳定执行边界（覆盖智能体全链路关键节点）进行拦截，无需业务方重构代码，保障轨迹完整采集并降低接入成本 | 执行边界即智能体运行中天然稳定的切面，如 LLM 调用入口、工具执行前后、记忆读写点等 |
| 无损的 ATDP 输出 | 将拦截调用转为标准 ATDP 事件流，按序列学习需求持久化存储 
LLM 调用保留：提示词模板指纹、系统提示词版本、工具列表、解码参数、采样输出、token ID、对数概率、模型版本 
工具调用保留：输入、输出、schema、版本、权限范围、错误类型、下游使用情况 | 无损 = 保留所有合规且学习必需字段，非冗余字段可裁剪 |
| 可重放能力 | 支持输入输出、环境状态、可授权 LLM 版本、文件/数据库快照、外部副作用边界等采集 
区分三类重放：确定性重放、近似重放、不可重放事件 | 目标是回答“换提示词/模型/记忆/检索/工具 schema 后是否成功”，而非仅记录失败事实 |
| 跨租户聚合与隔离 | 支持租户隔离存储、策略驱动聚合、联邦/拆分训练、租户感知评估 | 需适配不同团队的仓库权限、数据分类、法律限制，保障学习有效性与合规性 |
| 奖励自动采集 | 全量捕获弱/延迟奖励信号：用户回复、工单重开、测试失败、编译错误、人工纠错、退款撤销、审批延迟、下游修改、用户放弃等 
扩展 OpenClaw-RL 观察，将所有操作状态变化视为候选信号 | 采集先行，控制平面后续决定哪些信号用于奖励建模 |
| 学习前的数据完整性校验 | 在轨迹入队前强制执行脱敏、访问控制、留存策略、训练合格性检查 | 作为 RL 闭环第一道安全闸门，杜绝“先日志后治理”，从源头防控合规风险 |

::: block-1
企业级数据代理是连接生产环境与学习系统的桥梁，它通过无侵入拦截、无损 ATDP 转换、可重放采集、租户隔离、奖励采集与前置治理，将异构的生产智能体流量转化为合规、可信、可用于强化学习的训练素材，是自进化闭环中不可或缺的数据流转枢纽。
:::

## 四、第三根支柱：智能体进化控制平面，决定“何时进化、怎么进化”的智能大脑

> 有了标准化的轨迹数据，有了采集数据的代理层，接下来要解决的核心问题是：什么时候触发进化，用什么方式进化？

**自进化不等于盲目更新模型权重，一个部署的智能体是一个复合策略系统，不同的故障模式需要匹配不同的干预方式**，控制平面就是负责做出这些决策的核心大脑。

### 4.1 打破误区：自进化不等于盲目更新模型权重

很多人对自进化智能体存在误解，认为自进化就是自动微调模型权重。但实际上，一个部署的自进化智能体是一个多组件的复合系统，模型权重只是其中的一部分。完整的智能体由五个核心部分组成：底座策略 LLM、上下文线束、记忆系统、工具集、安全护栏。

::: block-1
其中**上下文线束** 是很多读者陌生的概念，**它指的是包裹在底座模型外面的所有配置和逻辑**，包括系统提示词、开发者指令、智能体提示模板、工具描述、路由规则、记忆检索策略、规划模板、子智能体定义、技能库等等。:mdnice-highlight[不需要修改模型权重，只需要调整上下文线束，就能显著改变智能体的行为表现。]
:::

不同的故障模式，对应成本和风险完全不同的干预方案：

- 反复出现的事实类缺失，比如经常记错某个业务规则，最优解决方案是插入对应记忆，成本最低、风险最小。
- 工具路由失败、检索格式错误、护栏措辞问题、开发者消息结构问题，最优解决方案是修改上下文线束，不需要动模型。
- 可复用的流程性错误，比如某类任务的执行步骤总是出错，最优解决方案是补充对应的技能补丁。
- 只有当同一类错误在多个租户、多个任务、多个工具配置下都反复出现时，才说明问题不是记忆或线束的局部问题，需要用强化学习、过程奖励学习、知识蒸馏等方式更新模型权重。

因此自进化是一个多维度的治理决策问题，不是只有更新模型一种选择，**控制平面的核心职责，就是根据轨迹数据，选择最优的进化方式。**

### 4.2 控制平面的形式化定义

> 论文给出了控制平面的形式化定义。在时刻 $t$ 的部署自进化智能体 $\mathcal{A}_t$，是一个五元组的复合系统：

$$
\mathcal{A}_{t}=\left<\pi_{\theta_{t}}, \mathcal{H}_{\psi_{t}}, \mathcal{M}_{t}, \mathcal{T}_{t}, \mathcal{G}_{t}\right>
$$

五个组成部分分别是：

- $\pi_{\theta_{t}}$：由 $\theta$ 参数化的策略 LLM，也就是智能体的底座大模型。
- $\mathcal{H}_{\psi_{t}}$：由 $\psi$ 参数化的上下文线束，包括提示词、路由规则、模板等所有外层配置。
- $\mathcal{M}_{t}$：记忆系统，包括长期记忆、短期记忆、技能库等。
- $\mathcal{T}_{t}$：工具集和工具 schema，也就是 Agent 能调用的所有工具和它们的描述定义。
- $\mathcal{G}_{t}$：安全治理和护栏配置，包括内容审核、权限控制、合规规则等。

> 在自进化过程中，控制平面观测一个时间窗口内的 ATDP 轨迹集合 $D_t$，然后从所有可选进化动作中选择收益最大的最优动作 $u^*$：

$$
u^{*}=arg max _{u \in \mathcal{U}}\left[\mathcal{J}_{\mathcal{A}}\left(u | \mathcal{A}_{t}, \mathcal{D}_{t}\right)\right]
$$

其中 $\mathcal{J}_{\mathcal{A}}$ 是衡量进化动作对智能体提升效果的目标函数，$\mathcal{U}$ 是所有可选的进化动作集合，包括六类动作：

1. 更新策略 LLM 的权重，比如有监督微调、直接偏好优化、在线强化学习等。
2. 更新上下文线束，比如补充技能补丁、修改提示词、调整路由规则等。
3. 更新记忆系统，比如优化检索策略、插入新的记忆条目等。
4. 更新工具集和工具 schema，比如修改工具描述、调整工具参数定义等。
5. 回滚到之前的稳定版本。
6. 不做任何操作。

::: block-1
所有进化动作的执行，都必须在安全治理规则 $\mathcal{G}_t$ 的约束下进行。:mdnice-bold-italic[通俗来说，控制平面就像智能体的“运维总监”，定期查看一段时间内的智能体运行数据，评估各维度的表现，然后决定是给智能体补充知识、修改操作手册、升级核心能力，还是保持现状，或是出现问题时立即回滚。]
:::

### 4.3 控制平面的六大落地要点

> 企业级的进化控制平面，需要满足六大核心落地要求：

| 能力维度 | 描述 | 关键要点 |
| --- | --- | --- |
| 多维度适配能力 | 控制平面需按故障模式匹配干预类别，遵循“局部问题局部解决”原则 | 窄范围偶发问题用记忆或线束解决；全局普遍性问题才启动模型更新；兼顾进化效率与系统风险 |
| 基于轨迹统计的自动触发 | 进化决策依赖量化指标自动触发，而非人工抽检 | 指标包括：评估器分数、用户纠错率、过程奖励估计、工具失败聚类、金丝雀版本指标变化、单位任务成本、工作负载分布漂移 |
| 统一触发接口下的算法多元性 | 后端支持多种学习与适配范式，由控制平面统一调度 | 模型更新：在线/近在线 RL、过程奖励学习、反馈蒸馏；线束适配：提示词优化、上下文进化、代码搜索、轨迹文本编辑；记忆/技能更新：轨迹蒸馏为工作流或推理对象 |
| 安全审计的分阶段部署 | 自进化需全流程管控与审计，不可跳过审核直接上线 | 升级路径：影子评估 → 回溯重放检查 → 离线回归测试 → 金丝雀发布 → 回滚机制 → 差异化监控 |
| 重放优先的评估机制 | 所有更新须在历史轨迹及反事实变体上完成评估后方可触达用户 | 线束修改：测试失败与成功历史案例；工具 schema 修改：重放历史调用轨迹；模型更新：留出轨迹、安全测试集、租户评测集、分布漂移探测集 |
| 带版本的溯源与回滚能力 | 所有进化产物须唯一版本化，回滚为一等公民 | 版本对象包括：LLM 检查点、提示词、工具 schema、记忆条目、检索策略、护栏、技能文件、路由器、数据集；需清晰记录“改了什么、为什么改、何时改” |

::: block-1
:mdnice-highlight[进化控制平面是自进化智能体的决策大脑，它将自进化从单一的模型更新问题，转化为多干预维度的治理决策问题]。通过自动触发、多维度适配、算法多元性、分阶段部署、重放评估与版本回滚，控制平面保证了企业级自进化的自动化、安全性与可控性，是规模化落地的核心保障。
:::

## 五、AREAL2.0 原型验证：把离线 RL 系统改造成在线自进化服务底座

> 前面的三大支柱是完整的企业级自进化系统蓝图，而论文提出的 AREAL2.0，是这个蓝图的一个定向原型验证。

AREAL2.0 没有试图实现完整的自进化底座，而是聚焦在其中一条最具代表性的进化路径：基于部署智能体轨迹的在线策略 LLM 权重更新，验证现有 RL 基础设施改造为在线自进化系统的可行性。

### 5.1 核心设计思路：把 RL 训练单元变成可插拔的推理后端

> 原始的 AREAL 是一个离线的强化学习后训练系统，和生产部署的 Agent 完全解耦：离线收集整理数据、离线完成训练、人工评估后再重新部署上线，整个流程和传统的模型迭代没有区别。

**AREAL2.0 的核心设计思路，是彻底改变 RL 基础设施的定位**：不再把 RL 系统当成和在线服务脱节的离线后训练流水线，而是:mdnice-bold-italic[把用于 rollout 采样和策略训练的计算单元，包装成可以插入任何现有在线智能体部署的微服务组件。]

::: block-1
简单来说，:mdnice-highlight[就是把 RL 系统里的推理和训练算力，封装成一个可以直接替换现有 LLM 推理后端的标准服务]。企业现有的 Agent 不需要修改任何业务逻辑，不需要更换开发框架，只要把原来调用 vLLM、SGLang 的接口地址，换成 AREAL2.0 的网关地址，就能接入在线 RL 闭环，自动采集交互轨迹，自动完成策略更新。
:::

### 5.2 四大核心组件

> **AREAL2.0 原型系统由四个核心组件构成：网关、路由器、数据代理、智能体计算节点**。四个组件解耦了公共服务协议、会话调度、轨迹管理、模型推理与训练计算，形成了完整的在线 RL 服务架构。

![文章插图](/articles/2026-07-15-agent-rl-d6727cd5/images/04.webp)

::: image-caption
图 1：AREAL2.0在线RL工作流示意图：现有Agent服务保留原有规划、工具执行、沙箱与记忆模块，仅需将LLM API调用重定向至网关，由路由器通过数据代理将请求分发至智能体计算节点，记录部署轨迹并打通推理服务与在线RL训练链路，实现策略模型权重更新。该架构最核心的优势是极低的集成成本：企业无需重构现有Agent的业务代码，仅替换推理后端即可接入自进化闭环，大幅降低了生产落地的工程门槛。同时，计算资源可以根据推理流量和训练需求动态调度，显著提升了GPU资源的利用率。
:::

四个核心组件的具体功能如下：

| 组件 | 功能描述 | 关键特性 |
| --- | --- | --- |
| 网关 | 在线 RL 系统中智能体服务栈的公共入口，将 AREAL2.0 包装为标准推理后端替代品，使上层应用仅需替换推理端点即可将 LLM 调用重定向至支持在线 RL 的运行时 | 请求标准化、权限认证、请求转发，显著降低业务集成成本 |
| 路由器 | 为多个在线 RL 训练任务提供轻量级会话亲和性管理。针对智能体 RL 天然有状态的特性（如多轮对话、工具调用、中间观测、延迟奖励），将每个会话固定分配给一个数据代理，并全程保持该绑定关系 | 保障会话状态一致性，支持高并发智能体 RL 工作负载 |
| 数据代理 | 负责智能体数据流量与存储的控制面管理，在外部服务请求与计算节点间中转，完整记录智能体数据轨迹，为下游训练准备结构化轨迹数据 | 将部署流量转化为在线 RL 可用的学习经验，实现响应服务与训练数据采集的双重目标 |
| 智能体计算节点 | 连接部署智能体服务与 AREAL2.0 中 rollout、训练后端的执行抽象，统一封装 SGLang/vLLM（推理 rollout）和 Megatron/FSDP（训练 worker）等引擎 | 支持计算资源按轨迹流与训练需求动态调度，在统一服务架构中同步完成在线请求服务、轨迹采集与策略更新 |

### 5.3 落地案例：Hermes Agent 的在线 RL 改造

> 论文用 Hermes Agent 作为代表性案例，验证了架构的可行性。在传统部署模式中，:mdnice-bold-italic[Hermes 在执行任务时会调用独立的推理后端获取模型响应。接入 AREAL2.0 后，只需要把推理后端替换成由网关暴露的 AREAL2.0 管理的智能体计算节点即可。]

**整个 Agent 服务的其他模块几乎不需要修改**：Agent 还是像以前一样发起 LLM 推理请求，AREAL2.0 在后端自动拦截交互流、记录轨迹、把轨迹接入在线 RL 训练循环。:mdnice-bold-italic[这个案例最能体现 AREAL2.0 的设计价值：不需要单独搭建一个模仿生产行为的 RL 环境]，直接复用原有 Agent 服务产生的真实生产数据，Agent 原生的多轮交互、工具使用工作流，自然成为 ATDP 轨迹的来源。

这种模式大幅缩小了离线后训练数据和部署智能体行为之间的分布差距，解决了传统离线训练“训练数据和生产数据脱节”的核心痛点，为智能体从自身服务流量中持续提升能力提供了可行的落地路径。

### 5.4 原型的边界与完整蓝图的差距

> 需要明确的是，AREAL2.0 只是一个定向的可行性验证原型，远不是完整的自进化智能体底座。它只覆盖了更广泛的控制平面动作空间中的“模型权重更新”这一个分支，距离三大支柱的完整蓝图还有很多工作要做。

完整的自进化智能体系统，还需要一系列超出当前原型的能力：完整的 ATDP 协议实现，包含步级决策上下文和全量治理元数据；全面的数据代理，能采集工具、检索、记忆、文件、浏览器、人工反馈、延迟奖励等全链路事件；完整的重放和反事实评估支持；感知租户的隐私和训练合格性管控；能自动选择记忆更新、技能补丁、线束编辑、工具 schema 修改、策略更新、回滚、无操作的全功能进化控制平面。

因此 AREAL2.0 是整个蓝图中的第一步，验证了策略更新这条路径的工程可行性，而完整的多维度、受管控、可重放、自动触发的自进化闭环，仍然是未来更大的研究和系统工程方向。

::: block-1
AREAL2.0 原型验证了将现有离线 RL 基础设施改造为在线自进化服务的可行性，通过“可插拔推理后端”的设计思路，以极低的集成成本打通了智能体部署、轨迹采集、推理服务与 RL 训练的闭环。它是三大支柱蓝图的第一个落地实例，为后续完整自进化系统的研发提供了工程参考。
:::

## 六、行业影响与未来展望：自进化 Agent 的系统时代正在到来

本文核心价值，不在于提出新强化学习算法，也不在于刷新榜单分数，而在于首次系统定义了企业级自进化智能体的架构范式——**将“自进化”从算法构想推向可工程化、可规模化落地的系统层级，为 AI 基础设施演进锚定了新方向。**

### 6.1 重构智能体生命周期：从静态部署到持续进化

> 当前企业智能体普遍沿用“开发-部署-人工维护”模式，能力迭代严重依赖人工，响应慢、成本高。自进化系统底座将智能体转变为“活系统”：

- 客服智能体自动从工单中提炼新问题并优化应答逻辑；
- 编码智能体实时沉淀解决路径，动态更新代码策略。

运营成本显著下降，迭代周期从周/月级压缩至小时级，真正释放智能体的复利价值。

### 6.2 催生新一代AI基础设施

**现有 AI Infra 围绕静态模型构建，难以支撑持续进化需求**。新赛道正在浮现：标准化智能体轨迹协议（ATDP）、企业级智能体数据代理、进化控制平面，乃至面向自进化智能体的操作系统。:mdnice-bold-italic[RL 训练系统亦将重构——训练与推理深度融合，如AREAL2.0所示，GPU资源可按需动态切换服务与训练任务，资源利用率跃升。]

### 6.3 关键挑战与演进路径

合规与隐私平衡（需融合联邦学习、差分隐私）、多模态轨迹协议扩展（视觉/语音/物理交互）、多智能体协同进化机制、以及算法与系统协同设计（应对延迟奖励、分布漂移等生产约束），仍是待突破的系统性难题。

> 自进化不是可选升级，而是智能体发展的必经阶段；系统底座，已成为行业竞争的新分水岭。
