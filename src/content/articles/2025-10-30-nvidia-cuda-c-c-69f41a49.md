关键词：CUDA、**共享内存**、:mdnice-bold-italic[bank 冲突]、**动态共享内存**、多设备兼容、:mdnice-bold-italic[线程同步]

::: block-1
- 共享内存（Shared Memory）是 CUDA 中的一种高速片上内存，按线程块（Thread Block）分配，可用于实现全局内存合并访问（Global Memory Coalescing，即让多个线程对全局内存的分散访问合并成单次内存事务，提升访问效率），并支持线程间协作。
- 为避免线程间共享数据时出现竞态条件（Race Condition，指多个线程同时访问同一数据，且至少有一个线程在修改该数据，导致最终结果不确定的问题），CUDA 提供了屏障同步原语 `__syncthreads()`，该函数可确保线程块内所有线程都执行到某一节点后，才继续执行后续操作。
- 在 CUDA C/C++ 设备代码中，共享内存可通过静态或动态方式声明：动态分配时需额外指定一个执行配置参数，用于定义共享内存的分配大小。
:::

对于新版本的 CUDA 硬件，非对齐的数据访问已不再是大问题。

::: block-1
早期 CUDA 硬件（如计算能力 1.x，:mdnice-bold-italic[计算能力 Compute Capacity 定义了每种 NVIDIA GPU 架构的硬件特性和支持的指令]，查询不同型号 GPU 的计算能力见 developer.nvidia.com/cuda-legacy-gpus[1]）对非对齐敏感，未按照硬件要求对齐如 32 字节、64 字节，就会拆分内存事务、降低效率；

但新版本硬件（2.x 及以上）通过硬件优化（如地址重映射，硬件面对非对齐数据动态调整地址映射，使其映射到连续的内存事务），已能高效处理非对齐访问。
:::

但**无论何种代际的 CUDA 硬件，“按步幅访问全局内存”始终是个难题**，且在许多场景下似乎无法避免。这里“按步幅访问”，是指线程块内的线程访问全局内存时，地址间隔（步幅）大于 1（如线程 0 访问地址 0、线程 1 访问地址 4、线程 2 访问地址 8…… 步幅为 4）。

典型场景是 多维数组跨维度访问第二维度及更高维度访问元素时，就会出现这样的情况，如 2D 数组`a[row][col]`，按col方向（即第二维度）访问时，相邻线程访问的地址间隔为 “数组行宽”，步幅远大于 1。

## 为何 “按步幅访问” 是跨代难题？

> 全局内存的高效访问依赖 “合并访问”（多个线程的分散请求合并为 1 次内存事务），而 “按步幅访问” 会直接破坏合并条件：

- 无论硬件代际，**全局内存的 “合并规则”** 核心是 “**线程访问的地址需连续或按固定小间隔排列** ”；
- 按步幅访问时，线程请求的地址分散（如步幅为 1024 字节时，线程 0-31 访问的地址每个间隔达 1024 字节，线程 0 到线程 31 横跨 $31 × 1024 + 4 ≈ 32KB$ 的内存空间），硬件无法合并请求，只能拆分为数十次独立事务 —— 导致带宽利用率骤降，且这种**地址分散的本质** 是 “**数据存储布局与访问模式不匹配** ”，:mdnice-bold-italic[硬件无法通过自身优化解决，因此成为 “跨代难题”。]

## 共享内存如何解决这个问题？

> 不过，若使用共享内存，我们完全可以在这类场景下实现全局内存的合并访问。

因为共享内存是 GPU **片上** 高速内存，可通过 “数据重排” 将 “按步幅的全局内存访问” 转化为 “合并的全局内存访问 + 无冲突的共享内存访问”，核心逻辑分两步：

1. 合并加载：让线程按 “连续地址”（步幅 1）从全局内存读取数据，存入共享内存（此时全局内存访问是合并的，效率高）。例如访问 2D 数组第二维度时，先让线程按 “行优先” 连续读取 1 行数据到共享内存数组。
2. 协作访问：线程块内线程通过共享内存交换数据，按目标维度（如第二维度）从共享内存读取所需数据 —— **共享内存访问无 “步幅” 限制，且只要规避 bank 冲突，就能以近硬件极限的速度完成访问。**

::: block-1
简言之：共享内存相当于 “中间缓存 + 数据重排枢纽”，用 “高效的全局内存合并加载” 规避步幅问题，再用 “高速片上访问” 满足跨维度数据需求。
:::

## 一、共享内存

> 共享内存位于 GPU 芯片内部，因此其访问速度远快于本地内存（Local Memory，每个线程独有的内存）和全局内存（Global Memory，所有线程可访问的显存）。

事实上，在无 bank 冲突（Bank Conflict，下文将详细说明）的情况下，**共享内存的延迟约为未缓存全局内存延迟的 1/100。**

- 共享内存按线程块分配，因此同一线程块内的所有线程均可访问同一块共享内存。
- 线程还能访问由同一线程块内其他线程从全局内存加载到共享内存中的数据。

::: block-1
后者这种能力，当结合线程同步会有多种用途，例如：实现用户管理的数据缓存、构建高性能协作式并行算法（如并行归约算法），以及在原本无法实现全局内存合并访问的场景下，为该访问模式提供支持。
:::

### 1.1 线程同步

**当线程间共享数据时，需特别注意避免竞态条件**。竞态条件指的是当多个线程同时访问（包括读取和修改）同一块共享数据时，:mdnice-bold-italic[虽在逻辑上并行，但受限于 GPU 硬件的执行机制（如 warp 调度方式）]，线程在物理层面并非完全同步执行，导致最终数据结果不确定或错误的问题。

::: block-1
举个例子：线程 A 和线程 B 分别从全局内存加载一个数据元素并存储到共享内存中，之后线程 A 要从共享内存中读取线程 B 存储的元素，线程 B 也要读取线程 A 存储的元素。
:::

假设 A 和 B 属于不同的 warp（线程束，指 GPU 中一组同时执行的线程，通常包含 32 个线程），**若线程 A 尝试读取数据时，线程 B 尚未完成数据写入**，就会产生**竞态条件**，进而导致未定义行为和错误结果。

> 要**确保并行线程协作** 时得到正确结果，必须对线程进行同步。

CUDA 提供了一个简单的屏障同步原语（Barrier Synchronization Primitive）——`__syncthreads()`。线程执行到 `__syncthreads()` 时，必须等待其所在线程块内的所有线程都执行完该函数后，才能继续执行后续代码。

::: block-1
因此，对于上述竞态条件，我们只需在“将数据存储到共享内存”之后、“任何线程从共享内存加载数据”之前调用 `__syncthreads()`，即可避免问题。
:::

需注意的是：在分支发散代码（Divergent Code，指线程块内部分线程执行某一分支、另一部分线程执行其他分支的代码）中调用 `__syncthreads()` 属于未定义行为，可能导致死锁——线程块内的所有线程必须在同一节点处调用 `__syncthreads()`。

### 1.2 共享内存示例

> 在 CUDA C/C++ 设备代码中，需使用 `__shared__` 变量声明符来声明共享内存。:mdnice-bold-italic[根据内存大小在编译时是否已知，在核函数（Kernel，GPU 上执行的并行函数）内部声明共享内存的方式有多种]。

以下完整代码（可在 GitHub 上获取[2]）展示了使用共享内存的多种方法，**如果你觉得这部分比较冗长可以跳过，后面会拆分讲解**：

```
#include <stdio.h>__global__ void staticReverse(int *d, int n){  __shared__ int s[64];  // 静态声明共享内存数组，大小为64个intint t = threadIdx.x;   // 获取当前线程在线程块内的x方向索引int tr = n - t - 1;    // 计算当前线程对应数组反转后的索引  s[t] = d[t];           // 将全局内存中的数据d[t]加载到共享内存s[t]  __syncthreads();       // 等待线程块内所有线程完成共享内存写入  d[t] = s[tr];          // 将共享内存中反转后的数据写入全局内存}__global__ void dynamicReverse(int *d, int n){extern __shared__ int s[];  // 动态声明共享内存数组，不指定大小int t = threadIdx.x;int tr = n - t - 1;  s[t] = d[t];  __syncthreads();  d[t] = s[tr];}int main(void){constint n = 64;int a[n], r[n], d[n];// 初始化主机端数组：a为原始数组，r为预期反转数组，d为存储设备端结果的数组for (int i = 0; i < n; i++) {    a[i] = i;    r[i] = n - i - 1;    d[i] = 0;  }int *d_d;  cudaMalloc(&d_d, n * sizeof(int));  // 在设备端分配全局内存// 运行使用静态共享内存的版本  cudaMemcpy(d_d, a, n * sizeof(int), cudaMemcpyHostToDevice);  // 主机到设备的数据拷贝  staticReverse<<<1, n>>>(d_d, n);  // 启动核函数：1个线程块，每个线程块n个线程  cudaMemcpy(d, d_d, n * sizeof(int), cudaMemcpyDeviceToHost);  // 设备到主机的数据拷贝// 验证结果是否正确for (int i = 0; i < n; i++)    if (d[i] != r[i]) printf("错误：d[%d] != r[%d]（实际值：%d，预期值：%d）\n", i, i, d[i], r[i]);// 运行使用动态共享内存的版本  cudaMemcpy(d_d, a, n * sizeof(int), cudaMemcpyHostToDevice);// 启动核函数：第三个参数指定每个线程块的共享内存大小（n个int的字节数）  dynamicReverse<<<1, n, n * sizeof(int)>>>(d_d, n);  cudaMemcpy(d, d_d, n * sizeof(int), cudaMemcpyDeviceToHost);// 验证结果是否正确for (int i = 0; i < n; i++)    if (d[i] != r[i]) printf("错误：d[%d] != r[%d]（实际值：%d，预期值：%d）\n", i, i, d[i], r[i]);}
```

该代码使用共享内存对一个包含 64 个元素的数组进行反转。两个核函数非常相似，差异仅在于共享内存数组的声明方式以及核函数的启动方式。

### 1.3 静态共享内存

若共享内存数组的大小在编译时已知（如 `staticReverse` 核函数），则可直接显式声明该大小的数组，就像声明数组 `s` 那样。

```
__global__ void staticReverse(int *d, int n){  __shared__ int s[64];  // 静态声明：大小固定为64个int  int t = threadIdx.x;  int tr = n - t - 1;  s[t] = d[t];           // 从全局内存加载数据到共享内存  __syncthreads();       // 线程同步，确保所有线程完成数据写入  d[t] = s[tr];          // 从共享内存读取反转数据，写入全局内存}
```

在该核函数中，`t` 和 `tr` 分别代表数组原始顺序和反转顺序的索引。线程通过语句 `s[t] = d[t]` 将数据从全局内存拷贝到共享内存，再通过两行后的语句 `d[t] = s[tr]` 完成数组反转。

::: block-1
但需注意：在执行最后一行代码（每个线程访问由其他线程写入共享内存的数据）之前，必须调用 `__syncthreads()`，确保所有线程都已完成共享内存的加载操作。
:::

**本示例中使用共享内存的原因，是为了在较旧的 CUDA 设备（计算能力 1.1 及以下）上实现全局内存合并访问**。通过使用线性对齐索引 `t` 访问全局内存，可实现读写操作的最优内存合并。而反转索引 `tr` 仅用于访问共享内存——:mdnice-bold-italic[共享内存不存在“为实现最优性能而需按顺序访问”的限制]。

**共享内存唯一可能影响性能的问题是 bank 冲突，下文将对此展开讨论**。

注：对于计算能力 1.2 及以上的设备，内存系统即使使用反转索引写入全局内存，也能实现完全的内存合并。

### 1.4 动态共享内存

> 示例中的其他核函数（此处指 `dynamicReverse`）使用**动态分配** 的共享内存——**当共享内存大小在编译时未知时，可采用这种方式**。

此时，必须通过一个可选的第三个执行配置参数，指定每个线程块的共享内存分配大小（以字节为单位），如下列代码片段所示：

```
dynamicReverse<<<1, n, n * sizeof(int)>>>(d_d, n);
```

动态共享内存核函数 `dynamicReverse()` 使用“未指定大小的外部数组”语法声明共享内存数组，即 `extern __shared__ int s[]`（注意空括号和 `extern` 说明符的使用）。

::: block-1
- 空括号 `[]` 明确告知编译器：该共享内存数组的大小在编译阶段无法确定，需留空占位，等待运行时通过核函数启动参数动态指定。
- `extern` 用于表示所声明的共享内存数组是 “外部定义的、大小未在编译时确定” 的变量。
:::

数组大小由核函数启动时的第三个执行配置参数隐式确定。核函数的其余代码与 `staticReverse()` 完全相同。

**若需在单个核函数中使用多个动态大小的数组，该如何操作？** 此时仍需像之前那样声明一个 `extern` 未指定大小的数组，然后通过指针将其划分为多个子数组，如下列代码片段所示：

```
extern __shared__ int s[];                  // 全局动态共享内存数组int *integerData = s;                        // 第一个子数组：存储nI个intfloat *floatData = (float*)&integerData[nI]; // 第二个子数组：存储nF个float（紧跟在int数组之后）char *charData = (char*)&floatData[nF];      // 第三个子数组：存储nC个char（紧跟在float数组之后）
```

在核函数启动时，需指定所需的共享内存总大小，如下所示：

```
myKernel<<<gridSize, blockSize, nI*sizeof(int) + nF*sizeof(float) + nC*sizeof(char)>>>(...);
```

## 二、共享内存 bank 冲突

> **为实现并发访问的高内存带宽，共享内存被划分为多个大小相等的内存模块** （即“bank”，也有中文翻译为“存储体”），这些模块可同时被访问。

因此，若对 `n` 个地址的内存加载或存储操作涉及 `b` 个不同的内存 bank，则这些操作可同时被处理，从而使有效带宽达到单个 bank 带宽的 `b` 倍。

然而，若多个线程请求的地址映射到同一个内存 bank，这些访问操作将被串行化处理。硬件会将存在冲突的内存请求拆分为多个无冲突的请求（拆分次数等于冲突请求的数量），这会导致有效带宽降低——**降低倍数等于冲突内存请求的数量**。

::: block-1
有一种例外情况：**若一个 warp 内的所有线程都访问同一个共享内存地址，则会触发广播（Broadcast）机制** ——:mdnice-bold-italic[此时数据会被同时发送给该 warp 内的所有线程]。

计算能力 2.0 及以上的设备还支持共享内存访问的多播（Multicast）功能，即:mdnice-bold-italic[一个 warp 内任意数量的线程访问同一地址时，【均可同时】获得数据。]
:::

要最大限度减少 bank 冲突，需先理解内存地址如何映射到内存 bank。共享内存 bank 的组织规则为：连续的 32 位字（Word）被分配到连续的 bank 中，且每个 bank 每时钟周期的带宽为 32 位。

- **对于计算能力 1.x 的设备：warp 大小为 32 个线程，bank 数量为 16 个**。一个 warp 的共享内存请求会被拆分为两部分：一部分对应 warp 的前半部分线程，另一部分对应 warp 的后半部分线程。需注意：若一个半 warp（Half-Warp，即 16 个线程）的线程仅访问每个 bank 的一个内存地址，则不会发生 bank 冲突。
- **对于计算能力 2.0 的设备：warp 大小为 32 个线程，bank 数量也为 32 个**。与计算能力 1.x 的设备不同，该设备不会拆分 warp 的共享内存请求——这意味着，一个 warp 前半部分线程与后半部分线程之间可能发生 bank 冲突。
- **对于计算能力 3.x 的设备：bank 大小可配置** ——通过 `cudaDeviceSetSharedMemConfig()` 函数，可将 bank 大小设置为 4 字节（`cudaSharedMemBankSizeFourByte`，默认值）或 8 字节（`cudaSharedMemBankSizeEightByte`）。:mdnice-bold-italic[将 bank 大小设置为 8 字节，有助于在访问双精度（Double Precision）数据时避免共享内存 bank 冲突。]

## 总结

> 共享内存是编写高性能 CUDA 代码的强大工具。

由于共享内存位于芯片内部，其访问速度远快于全局内存。同时，共享内存由线程块内的线程共享，这为线程间协作提供了机制。**利用这种线程协作能力使用共享内存的方式之一，就是实现全局内存合并访问** ——本文中的数组反转示例已对此进行了演示。

通过共享内存实现数组反转，所有全局内存的读写操作均可按单位步幅（Unit Stride，即线程访问连续的内存地址）执行，从而在任何 CUDA GPU 上实现完全的内存合并。
