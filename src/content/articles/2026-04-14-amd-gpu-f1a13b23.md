## 一、架构总览与设计哲学

### 1.1 五大子库的分工协作

> ROCm device-libs 并非一个单一的巨型数学库，而是一个精心分层的库族。打开 `amd/device-libs/CMakeLists.txt`，可以清晰看到其构建骨架：

```
add_subdirectory(oclc)add_subdirectory(ocml)add_subdirectory(ockl)add_subdirectory(opencl)add_subdirectory(hip)add_subdirectory(asanrtl)
```

这六个子目录对应着功能清晰的分层体系。值得注意的是，除了这六个核心子库之外，仓库中还可以看到 `irif`（IR Intrinsic Functions，提供底层 LLVM IR 内建函数封装）、`cuda2gcn`（CUDA 到 GCN 的兼容层）、`doc`（OCML 和 OCKL 的文档）、`test`（编译测试套件）以及 `utils`（辅助构建工具如 `prepare-builtins`，用于处理 bitcode 中的内建函数符号）。这些辅助模块共同构成了完整的生态系统：

| 子库（全称） | 职责 | 依赖关系 |
| --- | --- | --- |
| **oclc** Open Compute Library Controls | 编译期控制变量（ISA 版本、浮点行为开关、ABI 版本、wavefront 大小等） | 无 |
| **ocml** Open Compute Math Library | 核心数学函数（sin, exp, log, pow, erf, bessel 等） | oclc* |
| **ockl** Open Compute Kernel Library | 内核基础设施（workitem/workgroup 查询、设备端内存分配、wave 操作、printf 支持） | oclc* |
| **opencl** OpenCL Built-in Library | OpenCL 标准内建函数的封装层 | ocml, ockl, oclc* |
| **hip** HIP Built-in Library | HIP 标准内建函数的封装层 | ocml, ockl, oclc* |
| **asanrtl** AddressSanitizer Runtime | GPU 端地址消毒运行时，用于检测越界访问和 use-after-free 等内存错误 | — |

这种分层的核心思想是**关注点分离**：

- `oclc` 负责"知道"当前硬件是什么、用户想要什么精度策略——它是整个库族的"神经系统"；
- `ocml` 负责"做"数学运算但不关心调用者是 OpenCL 还是 HIP——纯粹的算法实现层；
- `ockl` 则提供与硬件对话的底层原语——GPU 线程索引、内存栅栏、原子操作等。

::: block-1
上层的 `opencl` 和 `hip` 库只是"薄封装"，将标准 API 签名映射到 `ocml`/`ockl` 的内部符号。这意味着一个 `sin` 的优化只需在 `ocml` 中修改一次，OpenCL 和 HIP 两个生态就同时受益——避免了代码重复，也保证了数值一致性。
:::

### 1.2 bitcode 编译流水线

> 所有 `.cl` 源文件并不生成传统的 `.o` 目标文件，而是被 Clang 编译为 **LLVM bitcode** （`.bc`）。编译标志定义在 `cmake/OCL.cmake` 中：

```
set(CLANG_OCL_FLAGS -fcolor-diagnostics -Werror -Wno-error=atomic-alignment -x cl -Xclang  -cl-std=CL2.0 -target "${AMDGPU_TARGET_TRIPLE}" -fvisibility=hidden -fomit-frame-pointer  -Xclang -finclude-default-header -nostdlibinc -Xclang -fexperimental-strict-floating-point  -Xclang -fdenormal-fp-math=dynamic  -nogpulib -cl-no-stdinc "${CLANG_OPTIONS_APPEND}")
```

这段配置揭示了几个关键设计选择：

- **目标三元组 `amdgcn-amd-amdhsa`：** 生成的 bitcode 直接面向 AMDGCN ISA，而非中间表示。这个三元组在 `CMakeLists.txt` 第 53-55 行中默认设置，确保了生成的 IR 携带正确的数据布局（data layout）和目标特征（target features）信息。
- **`-fdenormal-fp-math=dynamic`：** 反规格化数（denormal）的处理方式由运行时决定，而非编译期写死——这是一个优雅的延迟绑定策略。不同的 GPU 硬件对 denormal 的性能惩罚不同（某些旧架构 flush-to-zero 更快），这个选项让同一份 bitcode 能适配所有情况。实际上，`opts.h` 中的 `DAZ_OPT()` 宏会在运行期通过 `__builtin_isfpclass(__builtin_canonicalizef(0x1p-149f), __FPCLASS_POSZERO)` 动态检测当前模式是否为 flush-to-zero。
- **`-fexperimental-strict-floating-point`：** 确保浮点运算语义在 IR 层面的严格性，防止编译器进行可能改变数值结果的优化（例如将 `a + b + c` 重排为 `a + c + b`）。对于数学库这种精度敏感的代码来说，这是不可或缺的。
- **`-nogpulib`：** 编译库本身不链接 GPU 库——因为它自己就是那个库，避免循环依赖。
- **`-Werror` 和 `-fvisibility=hidden`：** 编译警告即错误保证代码质量；隐藏可见性确保内部辅助函数不会污染用户的符号命名空间。
- **`-Xclang -mcode-object-version=none`：** 禁止在 bitcode 模块中嵌入 code object version 标记，避免与用户内核的版本标记冲突。

::: block-1
最终生成的 `.bc` 文件被安装到 `amdgcn/bitcode/` 目录下（由 `INSTALL_ROOT_SUFFIX` 变量控制），等待用户内核编译时被 Clang 驱动自动链接。用户也可以通过 `--rocm-path` 参数指定自定义的 bitcode 路径，或者使用 `-Xclang -mlink-bitcode-file` 手动链接单个库文件。
:::

## 二、OCLC——编译期的"基因开关"

### 2.1 控制变量的实现机制

> `oclc` 是整套库中最"小"却最"重要"的部分。它不包含任何数学运算逻辑，只定义了一组 `__constant bool` 或 `__constant int` 全局变量。以 `finite_only` 控制为例：

```
#include "oclc.h"const __constant bool __oclc_finite_only_opt = 0;
```

对应地，还有一个 `finite_only_on.cl` 将其设为 `1`。编译时，链接器根据用户的编译选项选择链入 `oclc_finite_only_off.bc` 或 `oclc_finite_only_on.bc`。

控制变量的完整声明列表定义在 `oclc/inc/oclc.h` 中：

```
extern const __constant bool __oclc_finite_only_opt;extern const __constant bool __oclc_unsafe_math_opt;extern const __constant bool __oclc_wavefrontsize64;extern const __constant uint __oclc_wavefrontsize_log2;extern const __constant int __oclc_ISA_version;extern const __constant int __oclc_ABI_version;#define OCLC_WAVEFRONT_SIZE (1u << __oclc_wavefrontsize_log2)
```

头文件中的注释清楚地解释了每个变量的语义：`__oclc_finite_only_opt` 表示应用只传递有限参数且只期望有限结果；`__oclc_unsafe_math_opt` 表示应用接受降低精度的优化；`__oclc_wavefrontsize64` 标记当前目标的 wavefront 宽度；`__oclc_ISA_version` 指定目标 GPU 的 ISA 版本号；`__oclc_ABI_version` 指定编译的 ABI 版本（当前支持 400、500、600 三个版本）。

这些看似简单的布尔/整数变量，实际上驱动着 `ocml` 中数百个数学函数的行为分支。在 `opts.h` 中，它们被封装为宏：

```
#include "oclc.h"#define HAVE_FAST_FMA32() (__oclc_ISA_version == 7001 || __oclc_ISA_version == 8001 || __oclc_ISA_version >= 9000)#define FINITE_ONLY_OPT() __oclc_finite_only_opt#define UNSAFE_MATH_OPT() __oclc_unsafe_math_opt#define DAZ_OPT() __builtin_isfpclass(__builtin_canonicalizef(0x1p-149f), __FPCLASS_POSZERO)
```

妙处在于：由于 `__oclc_finite_only_opt` 是 `__constant` 限定的全局变量，LLVM 的常量传播（Constant Propagation）和死代码消除（DCE）会在链接期优化（LTO）中将未选择的分支**完全擦除**。头文件注释也明确期望实现提供 `const bool int __oclc_... = 0;` 这样的定义，"*allowing them and any control flow associated with them to be optimized away* "——:mdnice-bold-italic[这意味着"如果用户声明只处理有限值，那么所有 NaN/Inf 检查代码将从最终的机器码中消失"——零运行时开销的条件编译。]

而 `DAZ_OPT()` 的实现更为巧妙：它不依赖任何控制变量，而是通过实际执行一次对最小正规格化数（`0x1p-149f`，即 `FLT_TRUE_MIN`）的规范化操作，然后检查结果是否被 flush 到零。这使得 denormal 行为检测在 `-fdenormal-fp-math=dynamic` 模式下也能正确工作——如果硬件或运行时配置了 FTZ（flush-to-zero），`canonicalize(0x1p-149f)` 会返回 `+0.0`，`DAZ_OPT()` 返回 `true`，相关的 denormal 保护代码就可以被跳过。

### 2.2 ISA 版本与跨代兼容

> `oclc` 的另一个重要职责是告知数学库当前运行在哪一代 GPU 上。从 `oclc/CMakeLists.txt` 中可以看到覆盖范围之广：

```
set(OCLC_ISA_TARGETS  # GFX6  "600|6000"    # Southern Islands (HD 7000 series, 2012)  "601|6001"  "602|6002"  # GFX7  "700|7000"    # Sea Islands  "701|7001"    # Hawaii - 注意这是少数 GFX7 中支持快速 FMA32 的型号  "702|7002"  ...  # GFX9  "900|9000"    # Vega 10  "906|9006"    # Vega 20 (MI50/MI60)  "908|9008"    # Arcturus (MI100)  "90a|9010"    # Aldebaran (MI200 series)  "942|9402"    # Aqua Vanjaram (MI300 series)  "950|9500"    # 下一代计算 GPU  "9-generic|9000"    # GFX9 通用目标  "9-4-generic|9402"  # GFX9.4 通用目标（MI300 系列）  # GFX10  "1030|10300"  # RDNA2 (RX 6000 series)  ...  # GFX11  "1100|11000"  # RDNA3 (RX 7000 series)  "1150|11500"  # RDNA3.5  ...  # GFX12  "1200|12000"  # RDNA4 (RX 9000 series, 2024-2025)  "1201|12001"  "1250|12500"  # 最新的 RDNA4 变体  "1251|12501"  "12-generic|12000")
```

从 GFX6（Southern Islands 系列，2012 年）到 GFX12（RDNA4，2024-2025 年），跨越了十多年的 GPU 微架构，总计超过 **50 个具体的 ISA 版本目标**。每个目标都通过 CMake 的 `configure_file` 机制从模板文件 `isa_version.cl.in` 生成具体的源文件：

```
#include "oclc.h"const __constant int __oclc_ISA_version = @ISA_VERSION@;
```

`@ISA_VERSION@` 在配置阶段被替换为具体的数值（如 `9402`），每个版本号都经过精心编码——高位代表主版本（generation），低位代表子版本（stepping/variant）。

此外，oclc 还为 ABI 版本生成单独的 bitcode（当前支持 400、500、600 三个版本），同样通过模板机制实现。ABI 版本的变化主要体现在内核参数传递方式和隐式参数（implicit kernarg）布局上——这直接影响 `ockl` 中 workitem 查询函数的实现路径。

`HAVE_FAST_FMA32()` 宏正是利用 ISA 版本号来判断硬件是否原生支持单精度 FMA 指令——只有 GFX701（Hawaii）、GFX801（Carrizo）和所有 GFX9 及以上架构（包括 Vega、CDNA、RDNA2+）支持此特性。这直接影响 `ocml` 中扩展精度算法的实现路径：在没有硬件 FMA 的老架构上，需要使用更慢但等价的 Dekker 分裂技术来获取乘法误差项。

## 三、OCML——数学运算的核心引擎

### 3.1 源文件的命名规范与类型覆盖

> 进入 `ocml/src` 目录，你会看到一个壮观的景象：数百个 `.cl` 文件按照**严格的命名约定** 排列。以 `sin` 为例：

- `sinD.cl` — `double` 精度实现（后缀 D = Double）
- `sinF.cl` — `float` 精度实现（后缀 F = Float）
- `sinH.cl` — `half` 精度实现（后缀 H = Half）

这种"一个函数 × 三种精度=三个文件"的模式几乎覆盖了所有标准数学函数：三角函数（sin, cos, tan 及其反函数、双曲变体）、指数对数（exp, exp2, exp10, log, log2, log10）、幂函数（pow, pown, powr, rootn）、特殊函数（erf, erfc, erfcx, erfinv, erfcinv, lgamma, tgamma, bessel j0/j1/y0/y1, 修正 bessel i0/i1）、复数运算（cabs, cacos, cacosh, casin, casinh, catan, catanh, ccos, ccosh, cexp, clog, csin, csinh, csqrt, ctan, ctanh, cdiv...）、向量长度（len3, len4, rlen3, rlen4, hypot, rhypot）、正态分布（ncdf, ncdfinv）等等。

> 除了 D/F/H 三种精度的实现文件，还有大量的辅助文件承载着关键的子算法：

- **trigredF.cl / trigredD.cl / trigredH.cl** — 三角函数参数规约（argument reduction）
- **trigredsmallF.cl / trigredlargeF.cl** — 分离小参数和大参数的规约路径
- **sincosredF.cl / sincosred2F.cl** — 规约后区间上的 sin/cos 核心多项式逼近
- **expD_base.h / powD_base.h / logD_base.h** — 用宏实现的共享算法框架
- **ep.h** — 扩展精度（extra-precision）运算的泛型头文件
- **builtins.h** （超过 13KB）— 所有硬件内建函数的 `#define` 封装
- **tables.cl / tables.h** — 预计算的查找表（如 log2 的分段逼近表）
- **besselD_table.h / besselF_table.h** — Bessel 函数的系数表

仅 `ocml/src` 下就有超过 **250 个源文件** （实际查看目录内容后确认远超此数——仅前 100 个文件就已覆盖从 acos 到 y1 的大量函数），每一个都是针对特定精度类型手工优化的实现。

### 3.2 sinF.cl 的解剖：一个三角函数的完整旅程

> 让我们以 `sinF.cl` 为例，看看一个"简单"的 `sin(float x)` 在 GPU 上如何被计算：

```
#include "mathF.h"#include "trigredF.h"floatMATH_MANGLE(sin)(float x){    if (!FINITE_ONLY_OPT())        x = BUILTIN_ISINF_F32(x) ? QNAN_F32 : x;    float ax = BUILTIN_ABS_F32(x);    struct redret r = MATH_PRIVATE(trigred)(ax);#if defined EXTRA_PRECISION    struct scret sc = MATH_PRIVATE(sincosred2)(r.hi, r.lo);#else    struct scret sc = MATH_PRIVATE(sincosred)(r.hi);#endif    float s = (r.i & 1) != 0 ? sc.c : sc.s;    s = AS_FLOAT(AS_INT(s) ^ (r.i > 1 ? SIGNBIT_SP32 : 0) ^                 (AS_INT(x) ^ AS_INT(ax)));    return s;}
```

这段核心不到 20 行的代码蕴含着经典的三角函数计算流水线：

1. **特殊值处理** （第 7-8 行）：如果未开启 `FINITE_ONLY_OPT()`，需要检测 ±∞ 并返回 NaN（IEEE 754 规定 sin(±∞) = NaN）。:mdnice-bold-italic[注意这里用的是硬件内建函数 `BUILTIN_ISINF_F32`，直接映射为 GPU 的 V_CMP 指令，几乎零开销。] `QNAN_F32` 在 `mathF.h` 中定义为 `__builtin_nanf("")`，生成标准的 quiet NaN 位模式 `0x7fc00000`。而 `MATH_MANGLE(sin)` 展开为 `OCML_MANGLE_F32(sin)`，这是统一的符号名修饰宏，确保生成的符号在不同精度之间不会冲突。
2. **参数规约** （第 12 行）：`trigred()` 将任意范围的输入 `x` 规约到 `[-π/4, π/4]` 的小区间内，同时返回象限信息 `r.i`。这是三角函数实现中最关键也最精巧的步骤。查看 `trigredF.cl` 的实现，可以看到它根据输入的大小分派到两条不同路径：CONSTATTR struct redretMATH_PRIVATE(trigred)(float x){if (x >= SMALL_BOUND)return MATH_PRIVATE(trigredlarge)(x);elsereturn MATH_PRIVATE(trigredsmall)(x);}`SMALL_BOUND` 在 `trigredF.h` 中定义为 `0x1.0p+17f`（即 131072），小于此值的参数走快速路径（`trigredsmall`，使用 Cody-Waite 规约），大参数则走 `trigredlarge`，使用高精度的 `2/π` 常数表（存储在 `trigredlargeF.cl` 的 4519 字节实现中）进行 Payne-Hanek 规约——避免灾难性消去（catastrophic cancellation）。结果结构 `redret` 根据是否启用 `EXTRA_PRECISION` 宏包含不同的字段：高精度模式额外携带一个 `lo` 余项。
3. **核心逼近** （第 14-18 行）：在小区间内用多项式（minimax 逼近）计算 sin 和 cos 的值。`sincosred` 是标准精度版本，查看 `sincosredF.cl` 的实现可以看到使用了 Horner 形式的多项式评估：CONSTATTR struct scretMATH_PRIVATE(sincosred)(float x){float t = x * x;float s = MATH_MAD(x, t*MATH_MAD(t, MATH_MAD(t, -0x1.983304p-13f, 0x1.110388p-7f), -0x1.55553ap-3f), x);float c = MATH_MAD(t, MATH_MAD(t, MATH_MAD(t, MATH_MAD(t,0x1.aea668p-16f, -0x1.6c9e76p-10f), 0x1.5557eep-5f), -0x1.000008p-1f), 1.0f);structscretret; ret.c = c; ret.s = s;return ret;}sin 使用 3 阶奇多项式 `x + x³(c₃ + c₅t + c₇t²)`，cos 使用 4 阶偶多项式 `1 + t(c₂ + c₄t + c₆t² + c₈t³)`。这些十六进制浮点常数（如 `-0x1.55553ap-3f` ≈ -1/6 ≈ -sin 泰勒系数的 minimax 修正值）是通过 Remez 算法或类似的最佳逼近方法预计算得到的，使得在 `[-π/4, π/4]` 区间上的最大误差最小化。`sincosred2` 是高精度版本，额外利用规约余项 `r.lo` 来修正——在 `sincosred2F.cl`（1207 字节）中有更复杂的实现。
4. **象限翻折与符号修正** （第 20-22 行）：根据象限信息选择 sin 或 cos 值，并通过位运算快速修正符号位——`AS_FLOAT`/`AS_INT` 的位级转换避免了分支指令，这在 GPU 的 SIMT 架构上至关重要。`SIGNBIT_SP32` 在 `mathF.h` 中定义为 `(int)0x80000000`。这个异或技巧的本质是：sin 在第 2、3 象限取负，而 `r.i > 1` 恰好覆盖这两个象限。

**跨精度对比**：`sinD.cl` 的 double 版本结构完全一致，但始终使用 `sincosred2`（因为 double 精度需要更高的内部精度），并且位操作使用 `AS_DOUBLE`/`AS_LONG` 和 `SIGNBIT_DP64`。`sinH.cl` 的 half 版本则用 `AS_HALF`/`AS_SHORT` 和 `SIGNBIT_HP16`，并额外包含 `UGEN(sin)` 宏调用来生成 `half2` 的向量版本（利用 GPU 的 packed half 运算能力将吞吐量翻倍）。

### 3.3 expD_base.h：用宏实现的"编译期多态"

> 指数函数 `exp`、`exp2`、`exp10` 共享了大量算法框架，只是常数和规约方式不同。ROCm device-libs 用一种巧妙的宏方案实现了代码复用：

```
CONSTATTR double#if defined COMPILING_EXP2MATH_MANGLE(exp2)(double x)#elif defined COMPILING_EXP10MATH_MANGLE(exp10)(double x)#elseMATH_MANGLE(exp)(double x)#endif{#if defined(COMPILING_EXP2)    double dn = BUILTIN_RINT_F64(x);    double f = x - dn;    double t = MATH_MAD(f, 0x1.62e42fefa39efp-1, f * 0x1.abc9e3b39803fp-56);#elif defined(COMPILING_EXP10)    double dn = BUILTIN_RINT_F64(x * 0x1.a934f0979a371p+1);    double f = MATH_MAD(-dn, -0x1.9dc1da994fd21p-59, MATH_MAD(-dn, 0x1.34413509f79ffp-2, x));    double t = MATH_MAD(f, 0x1.26bb1bbb55516p+1, f * -0x1.f48ad494ea3e9p-53);#else    double dn = BUILTIN_RINT_F64(x * 0x1.71547652b82fep+0);    double t = MATH_MAD(-dn, 0x1.abc9e3b39803fp-56, MATH_MAD(-dn, 0x1.62e42fefa39efp-1, x));#endif    double p = MATH_MAD(t, MATH_MAD(t, MATH_MAD(t, MATH_MAD(t,               MATH_MAD(t, MATH_MAD(t, MATH_MAD(t, MATH_MAD(t,               MATH_MAD(t, MATH_MAD(t, MATH_MAD(t,                   0x1.ade156a5dcb37p-26, 0x1.28af3fca7ab0cp-22), 0x1.71dee623fde64p-19), 0x1.a01997c89e6b0p-16),                   0x1.a01a014761f6ep-13), 0x1.6c16c1852b7b0p-10), 0x1.1111111122322p-7), 0x1.55555555502a1p-5),                   0x1.5555555555511p-3), 0x1.000000000000bp-1), 1.0), 1.0);    double z = BUILTIN_FLDEXP_F64(p, (int)dn);    if (!FINITE_ONLY_OPT()) {        z = x > 1024.0 ? PINF_F64 : z;    }    z = x < -1075.0 ? 0.0 : z;    return z;}
```

核心步骤清晰可见：

1. **范围规约**：将 `x` 分解为整数部分 `dn`（最近的整数，使用硬件的 `BUILTIN_RINT_F64` 指令）和小数部分。对于 `exp(x)` = `2^(x/ln2)`，乘数 `0x1.71547652b82fep+0` 正是 `1/ln(2)` ≈ 1.4426950408...；对于 `exp10(x)` = `2^(x*log2(10))`，乘数 `0x1.a934f0979a371p+1` 是 `log2(10)` ≈ 3.3219280948...。减去 `dn * ln(2)` 时使用双段常数技巧——`0x1.62e42fefa39efp-1` 是 `ln(2)` 的高 53 位，`0x1.abc9e3b39803fp-56` 是低位补偿——避免规约中的精度损失。
2. **多项式逼近**：用 **11 阶 Horner 形式** 的多项式逼近 `2^t - 1`（最后两个 `+ 1.0` 加回了常数项）。这些系数近似于 `2^t` 的泰勒展开系数 `1/n!`（例如 `0x1.55555555502a1p-5` ≈ 1/30 ≈ 1/5!...），但经过 minimax 优化使得在 `[-0.5, 0.5]` 区间上的最大误差最小化。11 阶多项式足以达到 double 精度（~15.9 位十进制有效数字）的精度要求。
3. **缩放**：`BUILTIN_FLDEXP_F64(p, (int)dn)` 即 `ldexp(p, dn)` = `p × 2^dn`，通过直接操作浮点指数位来完成，是一条单周期指令。
4. **溢出/下溢处理**：如果未开启 `FINITE_ONLY_OPT()`，大于 1024 的输入返回正无穷（`exp(1024) > DBL_MAX`）。小于 -1075 的输入总是返回 0（因为 `2^(-1075) < DBL_TRUE_MIN`，下溢为零）。

调用者（如 `expD.cl`）只需 `#define COMPILING_EXP` 然后 `#include "expD_base.h"` 即可。这种"在头文件中实现函数体 + 宏控制变体"的模式，是 C 语言中实现代码复用的经典技巧——虽然不如 C++ 模板优雅，但在 OpenCL C 的语言约束下已是最佳选择。同样的模式还用于 `powD_base.h`（3762 字节，pow/pown/powr 共享）、`logD_base.h`（log/log2/log10 共享）、`remainderD_base.h` 等。

### 3.4 扩展精度算术：ep.h 的泛型设计

> 处理超越函数时常需要"比原生精度更高一点"的中间结果。`ep.h` 用预处理器构建了一套泛型的扩展精度 (extra-precision) 运算框架：

```
#define ATTR __attribute__((const, overloadable))#if defined FLOAT_SPECIALIZATION#define T float#define T2 float2#define FMA BUILTIN_FMA_F32#define RCP MATH_FAST_RCP#define DIV(X,Y) MATH_FAST_DIV(X,Y)#define LDEXP BUILTIN_FLDEXP_F32#define SQRT MATH_FAST_SQRT#define ISINF(X) BUILTIN_ISINF_F32(X)#define USE_FMA HAVE_FAST_FMA32()#define HIGH(X) AS_FLOAT(AS_UINT(X) & 0xfffff000U)#elif defined DOUBLE_SPECIALIZATION#define T double#define T2 double2#define FMA BUILTIN_FMA_F64...#define USE_FMA true#define HIGH(X) AS_DOUBLE(AS_ULONG(X) & 0xfffffffff8000000UL)#elif defined HALF_SPECIALIZATION#define T half#define T2 half2#define FMA BUILTIN_FMA_F16...#define USE_FMA true#define HIGH(X) AS_HALF(AS_USHORT(X) & (ushort)0xffc0U)#endif
```

`HIGH(X)` 宏通过位掩码截断浮点数的低位尾数，得到一个"高位部分"。具体来说：

- **float**：`& 0xfffff000U` 保留高 12 位尾数（共 23 位），截断低 11 位
- **double**：`& 0xfffffffff8000000UL` 保留高 26 位尾数（共 52 位），截断低 26 位
- **half**：`& 0xffc0U` 保留高 4 位尾数（共 10 位），截断低 6 位

::: block-1
这是经典的 **Dekker 分裂** （Dekker's splitting）技术的入口——将一个浮点数拆为 `hi + lo` 两部分，使得 `hi` 的有效位数不超过原精度的一半，因此 `hi * hi` 可以精确计算（不会丢失尾部位），从而实现"用两个 float 模拟一个 double"（double-float）、"用两个 double 模拟一个 quad"（double-double）的效果。
:::

`USE_FMA` 的判断尤其精妙：

- 对于 **double** 和 **half**，`USE_FMA` 固定为 `true`——因为所有 AMD GPU 都支持 double FMA（`v_fma_f64`）和 half FMA（`v_fma_f16`）。
- 对于 **float**，`USE_FMA` 等于 `HAVE_FAST_FMA32()`——只有 GFX701、GFX801 和 GFX9+ 才有硬件单精度 FMA。

如果硬件支持 FMA，Dekker 分裂可以完全避免，因为 `FMA(a, b, -a*b)` 能精确得到乘法误差项（这是 FMA 的数学性质——一次运算中同时完成乘法和加法，中间结果不舍入）。`ep.h` 中的扩展精度乘法、加法、除法、平方根等运算都会根据 `USE_FMA` 选择不同的代码路径——这一切都发生在编译期，因为 `HAVE_FAST_FMA32()` 最终依赖于 `__oclc_ISA_version` 这个编译期常量。

`ep.h` 的整体大小达到 7744 字节，包含了完整的扩展精度加/减/乘/除/平方根/倒数运算——这些基础设施被 `eplnD.cl`（扩展精度 ln）、`epexpepD.cl`（扩展精度 exp）、`epcsqrtepD.cl`（扩展精度复数平方根）等多个高精度函数复用。

## 四、OCKL——内核基础设施层

### 4.1 WorkItem 查询与 ABI 兼容

> `ockl` 提供了 GPU 内核运行时最基础的能力。以工作项查询为例，`workitem.cl` 展示了如何在不同 ABI 版本间保持兼容：

```
#include "device_amd_hsa.h"#include "oclc.h"#include <amdhsa_abi.h>#define ATTR __attribute__((const))#define OLD_ABI __oclc_ABI_version < 500#define IMPLICITARG(T) ((__constant T *)__builtin_amdgcn_implicitarg_ptr())static __constant amdhsa_implicit_kernarg_v5 *get_v5_implicitarg_ptr(){    return (__constant amdhsa_implicit_kernarg_v5 *)__builtin_amdgcn_implicitarg_ptr();}ATTR static size_tget_global_size_x(void){    if (OLD_ABI) {        __constant hsa_kernel_dispatch_packet_t *p = __builtin_amdgcn_dispatch_ptr();        return p->grid_size_x;    } else {        __constant amdhsa_implicit_kernarg_v5 *args = get_v5_implicitarg_ptr();        return args->block_count[0] * (uint)args->group_size[0] + (uint)args->remainder[0];    }}
```

- 旧版 ABI（< 500）直接从 HSA dispatch packet 读取 grid size——这个 packet 是 HSA 运行时在内核启动时填充的硬件数据结构，包含网格维度、工作组大小等信息；
- 新版 ABI（v5，即版本 500+）则从**隐式内核参数区** （implicit kernarg）解码——后者通过 `block_count × group_size + remainder` 的方式计算总大小，支持**更大的网格维度** （旧 ABI 中 `grid_size_x` 只是 `uint32_t`，新方式可以表达更大的值），并且参数布局更紧凑。`__builtin_amdgcn_implicitarg_ptr()` 和 `__builtin_amdgcn_dispatch_ptr()` 是 Clang 的 AMDGCN target 内建函数，分别返回指向隐式参数区和 dispatch packet 的 `__constant` 指针。

类似地，`get_global_id_x()` 函数通过 `__builtin_amdgcn_workitem_id_x()` 和 `__builtin_amdgcn_workgroup_id_x()` 获取线程级和工作组级索引——这些内建函数直接映射到 AMDGCN 的硬件寄存器（`v0` 用于 workitem ID，`s6`/`s7`/`s8` 用于 workgroup ID），是零开销的。工作组大小同样根据 ABI 版本从不同来源获取：旧 ABI 用 `__builtin_amdgcn_workgroup_size_x()`（从 dispatch packet 读取），新 ABI 从 `args->group_size[0]` 读取。

同样地，由于 `__oclc_ABI_version` 是编译期常量，`OLD_ABI` 分支在 LTO 中会被完全消除——最终的机器码中只保留与目标 ABI 版本匹配的那条路径。这是 oclc 控制变量"零开销分支"设计哲学的又一个精彩体现。

### 4.2 设备端动态内存分配器

> `ockl/src/dm.cl` 是整套库中最"重量级"的单个文件（超过 37KB），它实现了一个**完整的设备端 malloc/free**。其设计借鉴了 slab 分配器的思想：

```
// The number of kinds of blocks.  Do not change.#define NUM_KINDS 16// The size where we switch the large & slow mechanism.  Do not change.#define ALLOC_THRESHOLD 3072// This controls the size of the heap, and also how often// we need to expand the capacity of the array that tracks// the allocations that have been made.//// With the definition below, 256, one level can hold 256// slabs (512 MiB), and two levels can hold (256+1)*256 = 65792// slabs (131585 MiB)#define SDATA_SHIFT 8#define NUM_SDATA (1 << SDATA_SHIFT)#define SDATA_MASK (NUM_SDATA - 1)#define MAX_RECORDABLE_SLABS ((NUM_SDATA + 1) * NUM_SDATA)
```

设计要点：

- **16 种规格（kinds）的 slab 分配**：小于 3072 字节的分配请求按大小分类到 16 个桶中，每个桶管理固定大小的内存块。分配操作通过**原子位掩码操作** （使用 `gmask_t` 即 `ulong` 作为 64 位位图）快速找到空闲块——一个 slab 可以包含最多 64 个同种大小的块，使用一个 64 位整数的每一位来跟踪空闲状态。
- **两级 slab 索引**：一级可以追踪 256 个 slab（总计 512 MiB），两级可以追踪 65792 个 slab（总计约 128 GiB）——对于 MI300X 等拥有大显存的 GPU 来说是必要的。
- **大分配直接向主机端请求**：通过 `extern ulong __ockl_devmem_request(ulong addr, ulong size)` 函数（在 `dm.cl` 第 18 行声明）与主机端运行时通信，处理超过 3072 字节的分配。
- **非 slab 分配追踪**：`NON_SLAB_TRACKING`（默认启用）允许查询当前有多少"大"分配正在使用中，便于调试和内存分析。

这个设计在 GPU 上尤为困难——数万个线程可能同时调用 `malloc`，需要极度精细的无锁（lock-free）原子操作协调。文件中大量使用了 `cl_khr_int64_base_atomics` 和 `cl_khr_int64_extended_atomics` 扩展提供的 64 位原子操作。

## 五、构建系统的工程巧思

### 5.1 opencl_bc_lib 宏——bitcode 的工厂

> 整套构建系统的核心是 `cmake/OCL.cmake` 中定义的 `opencl_bc_lib` 宏，它接受库名（`NAME`）、源文件列表（`SOURCES`）和可选的内部链接库（`INTERNAL_LINK_LIBS`），为每个 `.cl` 文件生成对应的 `.bc`，然后链接、剥离（strip）、安装。

生成的文件遵循明确的命名约定：`{name}.lib.bc`（链接后）→ `{name}.strip.bc`（剥离调试信息后）→ `{name}.bc`（最终安装文件）。

::: block-1
这种"源文件 → 单独编译 → 链接为整体 bitcode"的流程，使得每个数学函数都是独立的编译单元——链接器可以只拉取用户实际调用的函数，实现**链接期的死代码消除** （Link-Time Dead Code Elimination）。如果你的内核只用了 `sin` 和 `exp`，那么 `cos`、`log`、`pow` 等数百个未使用函数的代码不会出现在最终的 code object 中。
:::

构建系统还支持跨平台细节：Windows 上额外添加 `-fshort-wchar` 以兼容 MSVC 头文件，并且通过 `EXE_SUFFIX` 变量处理 `.exe` 后缀差异。对于 LLVM 树内构建（非独立构建），还支持将 bitcode 安装到 Clang 资源目录（`lib/clang/{version}/lib/amdgcn/bitcode`），使得 `clang` 驱动能自动发现这些库。

### 5.2 每个 GPU 型号一份 oclc bitcode

> oclc 的构建方式尤其值得关注：它为**每一种 GPU 型号** 都生成一份独立的 `oclc_isa_version_XXX.bc`。构建流程如下：

1. CMake 遍历 `OCLC_ISA_TARGETS` 列表中的 50+ 个条目
2. 对每个条目，解析 `TARGET_NAME|ISA_VERSION` 对（如 `"942|9402"`）
3. 用 `configure_file` 将 `isa_version.cl.in` 中的 `@ISA_VERSION@` 替换为具体数值
4. 调用 `opencl_bc_lib` 编译生成 `oclc_isa_version_942.bc`

::: block-1
这意味着当你为 MI300（gfx942）编译内核时，Clang 驱动会自动选择 `oclc_isa_version_942.bc`，其中 `__oclc_ISA_version` 被硬编码为 `9402`。这个值传播到 `HAVE_FAST_FMA32()` 后返回 `true`（因为 `9402 >= 9000`），于是所有扩展精度路径都走 FMA 快速分支——**硬件能力信息在编译期就被"烙印"进了最终代码**。同样，ABI 版本（400/500/600）、wavefront 大小（32 或 64）、finite-only 和 unsafe-math 标志也各自生成独立的 bitcode 文件，由链接器根据用户选项组合选择。
:::

README 中给出了手动链接的完整示例，可以看到一个典型的内核编译需要链接约 8 个 bitcode 文件：`opencl.bc` + `ocml.bc` + `ockl.bc` + `oclc_finite_only_off.bc` + `oclc_unsafe_math_off.bc` + `oclc_wavefrontsize64_on.bc` + `oclc_isa_version_900.bc`——每个文件都是精确切面的控制参数。

## 总结与启示

> ROCm device-libs 的设计展现了一种在**约束极端严格的硬件** 上构建高质量数学库的范式：

1. **分层解耦**：控制层（oclc）、数学层（ocml）、内核层（ockl）、标准封装层（opencl/hip）各司其职，修改精度策略不需要改动数学实现。:mdnice-bold-italic[一个新的 GPU 架构只需在 oclc 中添加一行 ISA 条目即可获得完整的数学库支持。]
2. **编译期常量传播**：通过 `__constant` 变量 + LTO 的组合拳，将运行时分支转化为编译期决策，实现"零开销抽象"。六种控制变量（ISA 版本、ABI 版本、wavefront 大小、finite-only、unsafe-math、DAZ 模式）的全排列，在理论上可以产生数百种行为变体——但最终编译出的代码只包含用户实际需要的那一条路径。
3. **精度 × 类型的全覆盖**：每个超越函数都有 half/float/double 三种手工优化版本（half 版本还额外支持 `half2` packed 运算），拒绝"强制类型提升"带来的性能损失。仅 `ocml/src` 目录就包含 250+ 个精心优化的源文件和头文件。
4. **硬件感知的算法选择**：ISA 版本号驱动 FMA 可用性判断，ABI 版本号驱动 workitem 查询路径，wavefront 大小驱动 wave 操作行为——同一段源码在不同 GPU 上编译出不同的指令序列，无需维护多份代码。
5. **经典数值方法的工程化**：Cody-Waite 和 Payne-Hanek 参数规约、Remez/minimax 多项式逼近、Dekker 分裂和 double-float/double-double 扩展精度、Horner 形式的多项式评估——这些教科书级的数值计算技术在 GPU 的约束下得到了极致的工程化实践。
