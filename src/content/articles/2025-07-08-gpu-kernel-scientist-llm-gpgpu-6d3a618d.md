> 为实现高性能而优化 GPU 内核是一项复杂的任务，通常需要深入的架构知识、广泛的性能分析以及反复的实验。当目标是更新或文档较少的 GPU 架构时，这一挑战更为艰巨，因为传统的开发辅助工具稀缺。

本文介绍了一种由大语言模型驱动的 “GPU 内核科学家”，这是:mdnice-bold-italic[一种用于迭代优化加速器内核的自动化方法。]

::: block-1
我们的方法在一个多阶段的 GPU Kernel 代码演进过程中运用大语言模型：

1. 策略性地选择有前景的先前代码版本，作为新迭代的基础；
2. 根据现有代码以及从通用 GPU 文献中吸收的知识，生成优化实验的假设；
3. 通过代码修改自主实施这些实验，随后将其提交到外部评估系统，仅使用观察到的时间数据作为性能反馈。

我们详细阐述了**这种方法如何应对 AMD MI300 目标架构的挑战**，并利:mdnice-bold-italic[用大语言模型来弥补特定领域人类专业知识的不足]。
:::

## 一、引言

GPU 内核优化是一项重大挑战，传统上需要专业知识。**在处理文档有限的新型/小众硬件时，这一挑战变得更加艰巨**，而在使用**功能薄弱的分析工具时，难度更是加倍**。我们针对这个问题提出的解决方案是“GPU 内核科学家”，这是:mdnice-bold-italic[一个自动化的迭代框架，仅通过端到端计时结果，就能针对非 CUDA 硬件优化内核。]

> 核心思想是利用前沿的大语言模型，仅基于在线测试/基准平台的有限反馈，创建一个代码选择、实验构思以及代码生成/修改的循环。

这篇短文的主要贡献如下：

::: block-1
- **新型框架本身** 的展示；
- 展示其在**信息/工具严重受限** 的情况下对 HIP 内核优化的应用；
- 突出**大语言模型** 如何在这些场景中**弥合知识差距并推动优化**。

我们将首先讨论相关工作，然后详细介绍我们的方法以及早期实验结果。
:::

## 二、相关工作

长期以来，计算机代码一直是进化方法的目标（Koza, 1992），其中函数直接编码为树结构，使用类似于遗传算法（Holland, 1975）的交叉和变异操作来创建新的子代。

> 然而，近年来，大语言模型为从父代代码创建新的个体程序提供了新方法（Novikov 等人，2025；Romera-Paredes 等人，2024）。在这里，大语言模型同时充当交叉和变异算子，甚至可能在过程中调整自身指令（如 Fernando 等人，2024）。

我们的方法侧重于大语言模型的交叉过程，:mdnice-bold-italic[强调其在代码创建和搜索过程中的主动作用]。因此，我们提出的是“GPU 内核科学家”，而非“GPU 内核进化器”。

事实上，这项工作也可以被视为拟议的 AI 科学家（Lu 等人，2024；Yamada 等人，2025）和有趣的 **AI CUDA 工程师（Lange 等人，2025）** 之间的融合。*尽管我们的“科学”范围比前者有限得多*，但分析深度:mdnice-bold-italic[似乎] （🤣）比后者更深。

通过 **KernelBench（Ouyang 等人，2025）** 提供的挑战数量使其成为优秀的基准，而我们的系统尝试的内核数量非常有限，因为我们的重点是 AMD 开发者挑战赛 2025（AMD，2025a）所需的内核。此外，例如用于大语言模型推理的内核多样性可能随着时间的推移而减少，而硬件的多样性却在增加：这些因素影响了我们为 GPU 内核科学家做出的设计选择。

像 **OpenTuner（Ansel 等人，2014）和 KernelTuner（van Werkhoven，2019）** 这样的工作，其运行方式可能类似于超参数调优。相比之下，:mdnice-bold-italic[我们工作中对代码的修改范围可能更广泛——有可能测试针对内核优化问题的根本不同方法]。因此，这些调优框架似乎也可以（通过大语言模型自动）应用于我们系统生成的内核，形成互补。

OpenAI Triton（Tillet 等人，2019）、TileLang（Wang 等人，2025）和 ThunderKittens（Spector 等人，2024）等框架旨在减少实现高级内核模式所需的详细工作。然而，尽管这些框架可能成为未来工作的目标，但竞赛环境仅支持 Triton，且 AMD 低精度算子的适用程度尚不明确。因此，我们决定在工作中**直接优化 AMD HIP 内核**。

## 三、方法

> 我们的 GPU 内核科学家涉及 3 个 LLM 处理阶段的编排，这些阶段迭代更新不断增长的内核列表，如图 1 所示。

![文章插图](/articles/2025-07-08-gpu-kernel-scientist-llm-gpgpu-6d3a618d/images/04.webp)

::: block-1
这个过程:mdnice-bold-italic[从几个“种子”内核开始]，包括：

- （提供的）基本 PyTorch 实现；
- 第一个内核直接翻译为 HIP 的版本——其速度约比 PyTorch 慢 6 倍；
- 将问题翻译为使用矩阵核心（类似 Nvidia 的张量核心）的 HIP 内核。
:::

尽管后者看似给 **LLM** 的“馈赠”，但**缺乏在该特定硬件上使用低精度操作的代码示例**，使得**人类/AI 共同创建** 一个工作（验证为正确结果）的**内核极具挑战性**。这个深入探索随后被 LLM 总结为“发现”文档，以便未来迭代可以简洁地利用硬件的特性。

:mdnice-bold-italic[与在线可用的大量 CUDA 资源（Nickolls 等人，2008）相比，AMD 的文档非常有限]。

- 我们利用了 AMD rocWMMA 库（AMD，2025c）、AMD HIP 参考（AMD，2024）和 AMD 矩阵指令计算器（AMD，2025b），主要通过*让 LLM 总结这些与内核规格相关的来源*。
- 我们还*让 LLM 参考 CUDA 资源*，如 Boehm（2022）和 Armbruster（2024），其中详细介绍了如何使用 Nvidia 的张量核心。

LLM 自身在 Nvidia 和 AMD 平台之间进行“翻译”。

### 3.1. LLM 进化选择器

GPU 内核科学家流程的**第一阶段是从不同内核的种群中选择两个个体**。种群中的成员由 ID 标识，每个成员的“父代”ID 也会给出，以及 6 个指定 MxKxN 输入配置的基准测试结果。

::: block-1
LLM 被指示：

- 选择其中一个个体作为下一个实验的“基础”（Base）
- 另一个（“参考”，Reference）则因其有助于分析实验的能力而被选择。
:::

因此，我们:mdnice-bold-italic[依赖 LLM 从多目标优化场景中判断合理选择，而非使用复杂的选择机制] （或其他多样性增强想法，如 Mouret & Clune（2015）中的方法）。

### 3.2. LLM 实验设计器

该流程的**第二阶段是设计后续需要执行的有用实验**。为此，我们关注从前一步传入的个体的现有“基础”代码，并使用外部知识（例如博客文章或手册片段的摘要，如上述）增强此代码。

::: block-1
关键指令有两部分：

- 首先，生成 10 个可能考虑的实验“方向”——这个列表故意长于所需，但已发现这会增加第二部分可用选项的多样性；
- 其次，生成 5 个实验计划，包括整体实验描述和多行规则。此外，LLM 被要求估计实验可能产生的性能提升范围，以及实验的“创新性”程度。
:::

### 3.3. LLM 内核编写器

> **此阶段** 是 GPU 内核科学家**流程的核心**：如果无法生成语法正确的内核代码，同时遵循实验规则中的指令，整个流程显然会失败。幸运的是，使用的 Gemini 2.5 Pro 模型出奇地能够生成有效代码，即使被要求进行重大结构更改。

向 LLM 提供了广泛的上下文：

- 竞赛组织者提供的任务描述，以及任务的 PyTorch 基本实现；
- 与 LLM 合作生成的“发现”文档，其中包含高性能内核的伪代码；
- 两个代码清单：一个用于“参考”代码，另一个用于“基础”代码。基础代码将是生成输出 HIP 代码的“差异”基础，而参考代码（由第一阶段的 LLM 进化选择器建议）因其可能有助于对比或支持代码更改而被提供。
- LLM 输出要求：LLM 必须生成新的 HIP 内核（带有调用代码，准备好 PyTorch 集成），以及关于它用于实现实验规则的技术的简短报告（为了完整，这部分也被添加到上述单步实验分析中，因为偶尔观察到 LLM 决定不实际遵循整个实验规则）。

#### 关键特性分解

LLM 生成的 HIP 内核针对 AMD GPU 优化的通用矩阵乘法（GEMM）实现及其关键特性。此内核通过 rocWMMA 库集成 AMD 矩阵核心，采用 32×32×16 的 MFMA 变体，支持 FP8 输入、float 累加和 BF16 输出的混合精度计算。

- **内存优化方面**，利用共享内存（LDS）实现乒乓双缓冲流水线，重叠数据加载与计算，并动态重排 LDS 缓存缩放因子以提升利用率。线程块配置为 128 或 256 线程，通过多波执行分布式加载全局内存，仅由特定波执行最终写入以避免冲突。
- **数据布局** 上，输入矩阵采用列主序，输出为行主序，配合向量化加载优化带宽。
- 此外，内核通过逐元素缩放实现**动态范围量化**，
- **数据重排** 由 rocWMMA 库隐式处理，整体展现了对硬件特性与内存层次的深度整合优化。

### 3.4. 内核测试与评估

内核测试和评估机制由 2025 年 AMD 开发者挑战赛平台决定。幸运的是，**命令行工具可用**，因此**整个过程可以在闭环中自动化**。

然而，请注意，竞赛接口对我们的 GPU 内核科学家施加的约束也意味着系统必须比没有这些约束时更有能力。最显著的限制是缺乏任何用于分析内核的工具（除了每个基准下不同规模如 MxKxN 配置的端到端运行时间）。

此外，遵守一些比较的规则限制，提交代码请求只能顺序进行（而非并行），这限制了可以处理拿到运行时间的的内核个数。

## 四、发现

如上所述，GPU 内核科学家系统必须应对几个约束，这些约束在以下子部分中讨论。

### 4.1. 有限的目标特定文档

CUDA 生态系统的支持比此处针对内核开发的 AMD 服务器级 MI300 GPU 好得多。因此，GPU 内核科学家系统需要:mdnice-bold-italic[能够自行探索 GPU 的能力，并应用基本的 GPU 优化原则，而非特定硬件的预训练知识。]

同样重要的是观察到 LLM **从相关架构中泛化的能力** （例如，如果在提示中提供 CUDA 文档，则推断 HIP 最佳实践），然后通过执行精心选择的实验来验证其理解。

### 4.2. 补偿缺乏性能分析工具

由于竞赛提交的基准计时是唯一可用的评估工具，当前系统别无选择，只能将其用作主要性能信号。因此，LLM 必须将代码更改与这些黑盒计时结果相关联（隐式地，或通过显示前后基准）。

因此，尽管拥有更好的分析工具显然会是一个优势，但我们的 GPU 内核科学家已被证明能够在苛刻的约束下优化代码。

### 4.3. 增强有限的人类专业知识

构建系统的一个明确**目标是开发者不必成为 GPU 专家的情况下具有竞争力**。因此，有意识地决定要求**引导系统** 过程中的所有“聪明”步骤都源自 LLM 本身。这包括由 LLM 驱动的 lengthy **初始硬件探测阶段** （此调试通过检查竞赛测试接口的返回值完成），以便它可以生成**自己的“发现”文档**。

一旦初始引导阶段结束，:mdnice-bold-italic[关于更改哪些代码以及如何更改的所有决策都留给 LLM 系统]。如果发现可能合适的新文档（例如博客文章），它们会被提供给 LLM，以消化成与当前任务更相关的形式——这种消化后的形式会提供给 LLM 实验设计器。

通过这种方式，LLM 成为“知识伙伴”，提出作者不知道的技术。此外，GPU 内核科学家系统通过提出自己迭代执行的明智实验，消除了人类开发人员的任何试错负担。

### 4.4. 作为发现过程的迭代改进

为 GPU 内核科学家创建的循环允许系统作为一个整体通过实验学习目标架构，无需明确指导。

从阅读 LLM 实验设计过程的输出以及 LLM 内核编写器选择实现的技术可以清楚地看出，系统可以:mdnice-bold-italic[通过实验循环实现自洽的定向行动]。因此，该系统具有显然超越组成它的单个 LLM 的属性。

## 5. 讨论与未来工作

由于竞赛仍在进行中（截至提交日期），以下讨论是初步的。

很明显，Gemini 2.5 Pro 模型可以有效地生成语法正确且新颖的 HIP 代码。令人惊讶的是，以前常见的挑战（如“幻觉”、生成无法编译的代码或处理高度复杂逻辑的困难）似乎不是主要因素。这可能是由于 LLM 上下文被仔细控制，并且按构造始终存在已知工作的代码。

### 5.1. 更广泛的影响与局限性

GPU 内核科学家系统显示出:mdnice-bold-italic[普及高性能 GPU 编程的潜力]。这可用于:mdnice-bold-italic[加速内核开发周期，尤其是对于新硬件的探索性工作]，这是当前依赖单一 GPU 硬件供应商的行业中的一个重要因素。

如前所述，系统当前对外部评估的依赖意味着它不并行运行，导致整体优化进展缓慢。此外，作者认为，访问来自分析器的细粒度反馈将显著提升 GPU 内核科学家系统的能力。

### 5.2. 未来工作

GPU 内核科学家的整体结构使其适合适应其他目标硬件、框架和工具。应用可能包括来自当前安装基数有限的供应商的硬件，或:mdnice-bold-italic[希望在不扩展人力资源的情况下构建更广泛能力的供应商] （🐎！？）。

为了促进我们的系统适应新框架（可能几乎没有最新文档），我们计划**构建自动工具来动态扩展它可以访问的知识库**。

总之，我们的 GPU 内核科学家展示了 *LLM 驱动的进化过程在导航和征服复杂优化挑战方面的深远潜力*，即使在有限的先验知识或工具的情况下，也展示了性能工程的强大新范式。
