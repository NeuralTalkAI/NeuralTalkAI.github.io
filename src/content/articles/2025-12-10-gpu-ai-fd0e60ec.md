## 关键问题

### 问题 1：PVA/VIC 未被利用的核心瓶颈：硬件接口限制与建模双重缺失

> 论文明确指出 PVA/VIC 加速器在卷积、图像预处理等任务中具备显著性能优势（如 PVA 卷积速度接近 CPU、VIC 图像缩放效率是 CPU 的 7.5 倍），但现有调度器几乎未利用这两类硬件，且 NVIDIA 官方框架（TensorRT、DeepStream）限制了 PVA 对 DNN 卷积层的支持——**这一矛盾是否反映了边缘设备硬件设计与调度算法的协同断层？** 其核心瓶颈是硬件接口的底层限制，还是调度器对多加速器兼容性的建模不足？

该矛盾本质上**反映了边缘设备硬件设计与调度算法的协同断层**，且【核心瓶颈】来自**硬件接口底层限制** 与**调度器兼容性建模不足** 的双重制约，二者相互交织导致 PVA/VIC 的性能潜力未被释放。

- **从硬件接口限制来看，NVIDIA 官方框架（TensorRT、DeepStream）存在明确的功能封锁：**这种:mdnice-bold-italic[框架层面的底层限制，使得调度算法即便想将 DNN 层分配给 PVA/VIC，也缺乏软件接口支撑]，形成“:mdnice-bold-italic[硬件有能力但软件不允许] ”的断层。
- **从调度器建模不足来看，现有调度器普遍【未】将 PVA/VIC 纳入硬件资源池进行系统性建模**。论文指出，仅有[22]一文尝试建模 CPU、GPU 与 PVA 的能量消耗和内存竞争，而绝大多数调度器（如 Jedi、CP-CNN、AxoNN 等）的硬件适配范围仅局限于 CPU、GPU、DLA，完全忽略了 PVA/VIC 的存在。即便已知 PVA 卷积速度接近 CPU（1920×1080 INT8 数据卷积仅需 0.27ms，CPU 需 0.297ms）、VIC 图像缩放效率是 CPU 的 7.5 倍（640×480 缩放至 1920×1080 仅需 0.893ms，CPU 需 6.75ms），:mdnice-bold-italic[调度器也因缺乏对其层兼容性、内存访问特性、过渡成本的建模]，无法设计合理的任务分配策略，进一步加剧了协同断层。

### 问题 2：静态调度的性能天花板与动态调度未主流的关键原因

> 现有调度器中【仅】 D-HaX-CoNN 为动态调度，且**多数方案依赖“DLA→GPU”单过渡点设计**，而 LLM 等复杂模型的动态推理需求、边缘场景中多 DNN 突发并发的负载特性，对静态调度的预定义优化策略构成挑战——**静态调度是否在复杂模型和动态负载下存在不可突破的性能天花板？动态调度未能成为主流的核心原因**，是边缘设备有限算力无法承载实时优化开销，还是缺乏兼顾延迟、能耗与兼容性的统一动态调度评估体系？

静态调度在复杂模型（如 LLM）和动态负载（多 DNN 突发并发）场景下存在**不可突破的性能天花板**，而动态调度未能成为主流的核心原因并非边缘设备算力限制，而是**缺乏兼顾多目标的统一动态调度评估体系**。

**从静态调度的性能天花板来看，静态调度依赖预定义的任务分配策略（如“DLA→GPU”单过渡点），其优化逻辑基于固定的模型结构和负载特征**。

::: block-1
- 但 LLM 等复杂模型存在动态推理需求（如层维度动态变化），边缘场景中多 DNN 突发并发（如自动驾驶中突然出现的多目标检测需求）会导致负载特征实时波动，预定义策略无法灵活调整资源分配，必然出现 latency 激增或资源闲置。
- 论文中提到，【仅】 D-HaX-CoNN 这一款动态调度器能通过 runtime 优化适配负载变化，而其他静态调度器（如 Jedi、CP-CNN）在多 DNN 并发场景下，需通过固定分区点分配资源，面对突发负载时无法动态调整，验证了静态调度的灵活性局限。
:::

**从动态调度未成为主流的原因来看，算力限制并非关键**：论文中 D-HaX-CoNN 的实验表明，其 Z3 求解器在 CPU 上运行的开销仅占系统总开销的 2%，远低于边缘设备的算力冗余阈值。核心症结在于**缺乏统一的动态调度评估体系**：

::: block-1
- 动态调度的优化目标需根据应用场景灵活切换（如自动驾驶优先低延迟，工业监测优先能耗），但目前行业尚未形成涵盖 latency、吞吐量、能耗、资源利用率的统一评估标准，不同调度器的性能指标缺乏可比性。
- 此外，动态调度的优化策略高度依赖场景适配（如多 DNN 并发与单 DNN 实时处理的策略差异），缺乏通用化的设计框架，导致其难以在不同应用中规模化推广，最终未能替代静态调度成为主流。
:::

## 一、引言

> 随着人工智能片上系统在各类嵌入式设备中日益普及和广泛应用，以高效方式分配任务变得至关重要——既要保证高性能，又要实现低功耗运行，在边缘设备中尤其如此[1]。**NVIDIA Jetson 系列** 就是这类功能强大的边缘设备之一，其搭载的硬件加速器在人工智能和图形处理应用中应用广泛。**该系列设备包含多个硬件引擎，这些引擎分别适用于不同的并行计算模型**，并与高速、低功耗的同步动态随机存取存储器相连。

然而，在大多数情况下，这些设备需要处理繁重的工作负载，包括多个深度神经网络，这可能会降低其性能。已有部分研究致力于优化 DNN 在 GPU中的执行效率，例如文献[2]的研究，但这些研究:mdnice-bold-italic[往往忽略了其他加速器，导致系统性能未能达到最优。将任务合理调度并分配到各个硬件引擎中，能够显著提升系统效率]，从而充分发挥边缘计算的潜力。

随着 Jetson 设备需求的增长，**开发一套能够保证其高效能运行的框架变得至关重要**。例如，Jetson 系列已被应用于自动驾驶领域：

::: block-1
- 文献[3]评估了 Jetson Xavier 和 Jetson Orin 设备在基于 MM-Net 模型的行人检测任务中的性能；
- 另一应用案例是配送机器人，该机器人采用 Jetson Xavier 设备实现导航与目的地抵达功能，其中使用了改进版的单发多框检测器进行目标检测[4]。
:::

除机器人领域外，Jetson 系列还被用于监测场景，尤其在海洋学领域。与传统的人工实地测量数据方法相比，使用这类设备能够让研究人员以更安全、更经济的方式实现数据采集自动化，同时还能获取实时数据与洞察[5]。此外，Jetson 设备还被应用于工业检测，用于识别产品缺陷[6]。

> 在上述每一个应用场景中，部署任务调度器都能让系统运行更高效、资源利用更充分。**理想情况下，调度器应实现吞吐量最大化、延迟最小化以及功耗最小化**。然而，要同时实现这些目标并非易事，因此**大多数调度算法往往只优化其中部分目标，而将其余目标维持在一个阈值之上。**

选择合适调度器的另一个关键因素是同时运行的 DNN 实例数量。

- 以配送机器人[4]为例，部署“**异构感知的并发深度神经网络执行调度器** （HaX-CoNN，一种能够感知硬件异构特性、支持多个 DNN 同时运行的调度器）”，可:mdnice-bold-italic[让多个专注于不同任务的 DNN 并发执行]。例如，SSD 模型经过训练用于识别人群，而另一个 DNN 模型则可用于检测其他障碍物。通过为不同 DNN 分配特定任务，相比使用单个更通用的模型，系统性能能够得到提升。此外，:mdnice-bold-italic[与仅使用 GPU 执行相比，使用 HaX-CoNN 调度器可将延迟降低 20%，从而提高系统效率] [7]。
- 另一种可选用的调度器是“**卷积神经网络计算并行化调度器** （CP-CNN，一种专门针对卷积神经网络（CNN）设计、支持并行处理帧数据的调度器）”，该调度器可:mdnice-bold-italic[支持对单个 DNN 模型的帧数据（指视频处理中连续的图像帧）进行并发处理]。对于 SSD 模型，CP-CNN 调度器可将其速度和效率分别提升 75.6%和 75.9%[8]。

随着 AI 模型复杂度的提升，**在评估其性能时，必须优先考虑能耗和延迟**。事实上，随着大型语言模型应用的增多，人们对这类模型在边缘设备上的高能效执行重新产生了兴趣[9]。

> 迄今为止，尚未有综述论文对适用于最新 NVIDIA Jetson 边缘加速器的各类调度器进行全面比较。

- 文献[10]对早期 Jetson 型号（即 Jetson TK1、TX1 和 TX2）的硬件与算法优化进行了综述，但这些**早期型号中并不包含深度学习加速器（DLA）**。该综述中提到的算法优化:mdnice-bold-italic[【仅限于】调整 DNN 的特性，包括减小 DNN 规模、降低图像分辨率、减少帧数量以及调整深度图层级]。此外，该综述还探讨了部分利用 Jetson 设备中 CPU 和 GPU 来提升 DNN 模型性能的研究，涉及与本文类似的问题（如内存竞争）。
- 另一篇涉及调度的综述论文是文献[11]，该论文**研究了 GPU 数据中心中训练和推理工作负载的调度问题**。:mdnice-bold-italic[GPU 数据中心与边缘计算在加速器异构性方面具有相似性——两者均包含 CPU 和 GPU 资源]。此外，在深度学习模型训练的:mdnice-bold-italic[调度方法上，两者也存在相似之处]，例如线性规划和性能建模在训练任务调度中均被广泛应用。

## 二、背景知识

### 2.1 性能指标

> **调度器的性能通过三个关键指标进行评估**：吞吐量（$T$）、延迟（$L$）和资源利用率（$U$）。

- 吞吐量指 DNN 模型在特定时间内可处理的数据量；
- 延迟指处理单个输入所需的时间；
- 资源利用率则用于评估可用加速器的计算能力被利用的程度。

在调度器的问题建模中，还会用到以下各类变量（其定义如下，:mdnice-bold-italic[这段比较晦涩可以跳过，后面遇到时候，查询回来再看]）：

::: block-1
- $a_{i}$：表示来自集合 $A$ 的单个任务，其中集合 $A$ 包含百度 Apollo 自动驾驶软件[12]中的 3 个深度神经网络（DNN）任务和 3 个循环神经网络（RNN，一种具有记忆功能的神经网络，擅长处理序列数据如时间序列、文本等）任务。
- $ce_{j}$：表示来自集合 $CE$ 的一个处理单元（指具备计算能力的硬件组件，如 CPU 核心、GPU 核心等），集合 $CE$ 包含所有可能的处理单元，具体包括：
- $L[a_{i}, ce_{j}]$：表示任务 $a_{i}$ 在处理单元 $ce_{j}$ 上执行时的延迟。
- $B[a_{i}, ce_{j}]$：表示二进制决策变量（取值仅为 0 或 1），用于指示任务 $a_{i}$ 是否在处理单元 $ce_{j}$ 上执行（1 表示执行，0 表示不执行）。
- $N$：表示一个深度神经网络（DNN）模型。
- $N_{n}$：表示 DNN 模型 $N$ 中的第 $n$ 层（DNN 模型通常由多层网络结构组成，如卷积层、全连接层等，每层负责特定的计算任务）。
- $s(N_{n})$：表示执行 DNN 第 $n$ 层（$N_{n}$）的硬件处理单元（如 GPU、DLA 等）。
- $L(N_{n}, s(N_{n}))$：表示 DNN 第 $n$ 层（$N_{n}$）在处理单元 $s(N_{n})$ 上执行时的延迟。
- $TR_{n}$：表示二进制决策变量，用于指示在 DNN 第 $n$ 层（$N_{n}$）处是否发生处理单元切换（即从一个处理单元切换到另一个处理单元执行下一层，1 表示切换，0 表示不切换）。
- $\tau(N_{n}, s(N_{n}), \text{OUT})$ 和 $\tau(N_{n+1}, s(N_{n+1}), \text{IN})$：分别表示 DNN 第 $n$ 层（$N_{n}$）从处理单元 $s(N_{n})$ 中退出时的过渡开销（时间），以及 DNN 第 $n+1$ 层（$N_{n+1}$）进入处理单元 $s(N_{n+1})$ 时的过渡开销（时间）。过渡开销指数据在不同处理单元之间传输或处理单元切换时产生的额外时间消耗。
- $\text{pipeline}(N_{n}, s(N_{n}))$：表示当执行 DNN 第 $n$ 层（$N_{n}$）的子单元（指处理单元内部的细分功能模块）与执行第 $n+1$ 层（$N_{n+1}$）的子单元不同时，所产生的额外开销（通常为时间开销）。
- $e(N_{n}, s(N_{n}))$：表示 DNN 第 $n$ 层（$N_{n}$）在处理单元 $s(N_{n})$ 上执行时消耗的能量。同理，$e(N_{n}, s(N_{n}), \text{OUT})$ 和 $e(N_{n+1}, s(N_{n+1}), \text{IN})$ 分别表示 DNN 第 $n$ 层（$N_{n}$）从处理单元 $s(N_{n})$ 中退出时消耗的能量，以及 DNN 第 $n+1$ 层（$N_{n+1}$）进入处理单元 $s(N_{n+1})$ 时消耗的能量。
- $ECT$：表示用户设定的能耗目标（即用户期望系统运行时不超过的最大能耗值）。
- $LT$：表示用户设定的延迟目标（即用户期望系统处理单个输入时不超过的最大延迟值）。
- $C_{N_{n}, s(N_{n})}$：表示在多层并发执行（指多个 DNN 层同时在不同处理单元上执行）过程中，由于资源竞争导致 DNN 第 $n$ 层（$N_{n}$）产生的性能下降系数（即慢 down 系数，值越大表示性能下降越严重）。
- $P$：表示用户设定的性能目标（如吞吐量达到某一数值、延迟低于某一数值等）。
- $\text{size}(F, I)$：表示存储每个推理阶段（指 DNN 模型执行推理时的各个步骤）的即时特征（指推理过程中每层输出的中间数据，如卷积层输出的特征图）和指示矩阵（$I$，用于标记这些即时特征是否在后续阶段中需要被使用）所需的内存大小。
- $M$：表示处理单元可使用的共享内存（指多个处理单元或线程可共同访问的内存区域）的最大容量。
:::

### 2.2 Jetson AGX 系列设备的硬件架构

> 在人工智能和深度学习应用中，NVIDIA Jetson AGX Orin 的算力（以 TOPS，即每秒万亿次操作计）几乎是 Jetson Xavier 的 8 倍。例如，在运行 PeopleNet 模型（一种用于人员检测的预训练 DNN 模型）时，Orin 设备每秒可完成 536 次推理，而 Xavier 在相同时间内仅能完成 196 次推理[13]。NVIDIA Jetson AGX 系列设备包含以下核心模块：

![文章插图](/articles/2025-12-10-gpu-ai-fd0e60ec/images/05.webp)

::: image-caption
图 1：NVIDIA Jetson AGX Orin 的硬件架构[13]
:::

1. **CPU（中央处理器，计算机的核心计算单元，负责执行通用计算任务）**：Orin 设备包含 3 组 4 核的 Cortex-A78 架构芯片[13]，而 Xavier 设备则搭载的是 Carmel 架构 CPU[14]。除了三级缓存（L1/L2/L3）外，Orin 系统还包含一个 4MB 的系统缓存（用于整个系统共享的高速缓存）。:mdnice-bold-italic[其 CPU 最大工作频率为 2.2GHz[13]，并通过系统一致性架构（用于确保多个硬件组件访问内存时数据一致性的硬件架构）与内存进行数据通信] [15]。
2. **GPU（图形处理器，擅长并行计算，广泛用于深度学习任务）**：Orin 设备采用 Ampere 架构 GPU[13]（而 Xavier 设备采用的是 Volta 架构 GPU[14]），最大工作频率为 1.3GHz。该 GPU 包含 16 个流式多处理器和两级缓存[13]，并通过内存子系统接口与内存相连[15]。:mdnice-bold-italic[仅该 GPU 模块一项，就能提供高达 170 Sparse TOPS 的算力，用于运行 AI 模型[16]。]
3. **深度学习加速器（DLA，专门用于加速深度学习推理任务的硬件模块，能耗通常低于 GPU）**：DLA 本质上是一种固定功能加速器（指仅能执行特定类型计算任务的加速器，而非通用计算组件），:mdnice-bold-italic[其计算能力虽无法与 GPU/CUDA（CUDA 是 NVIDIA 推出的用于 GPU 编程的并行计算平台）相比，但具有显著更高的能效]。DLA 专用的 SDRAM 内存容量为 2MB[17]。:mdnice-bold-italic[Orin 设备搭载的 DLA 版本比 Xavier 设备更新，其性能提升了 9 倍] ——这一提升得益于其架构改进：新增了本地缓冲区，并降低了对 SDRAM 带宽的依赖[13]。这一性能差异可从图 2 中清晰看出。

![文章插图](/articles/2025-12-10-gpu-ai-fd0e60ec/images/06.webp)

::: image-caption
图 2：DLA 的架构框图
:::

1. **可编程视觉加速器（PVA，专门用于处理视觉相关任务的硬件模块，如特征检测、目标跟踪等）**：在 Xavier 和 Orin 设备中，:mdnice-bold-italic[PVA 均由一个 Cortex-R5 架构芯片（一种低功耗、实时性强的处理器核心）、2 个 DMA 引擎，以及 2 个超长指令字向量处理单元组成]。此外，Orin 设备的 PVA 模块中还包含一个 1MB 的二级缓存（L2）[13]。:mdnice-bold-italic[该模块足以处理相对轻量化的后处理任务]，如特征检测、立体视差、视觉感知、特征跟踪以及目标跟踪[14]。
2. **视频图像合成器（VIC，专门用于处理视频和图像预处理任务的硬件模块）**：该:mdnice-bold-italic[加速器负责执行预处理技术]，如镜头畸变校正（指修正因相机镜头光学特性导致的图像变形）、时间噪声 reduction（指减少视频序列中因传感器噪声导致的帧间波动）以及像素处理（指对图像像素进行的各类操作，如色彩空间转换等）[19]。:mdnice-bold-italic[Orin 平台的 VIC 最大工作频率限制为 729.6MHz[20]，而 Xavier 设备的 VIC 最大工作频率可达 1036.8MHz[21]。]

> 据我们所知，目前尚无研究在任务调度中利用 PVA 和 VIC 模块。

::: block-1
仅有文献[22]对 CPU、GPU 和 PVA 之间的能耗与内存竞争关系进行了建模。该研究成果可进一步扩展，为调度算法提供支持，以生成最优的执行流水线。

例如，PVA 可用于执行卷积层的计算任务，而 VIC 可用于执行预处理步骤（如镜头畸变校正、像素处理等）。
:::

### 2.3 软件开发工具包（SDK）与库

> NVIDIA 提供了多种工具资源，帮助用户访问 Jetson 设备中的不同模块，并在目标模块上执行任务。

其中，CUDA[23]和 cuBLAS[24] 库对于在多核系统中实现更复杂的并行计算仍然必不可少。

::: block-1
- **TensorRT**：该工具允许用户在 NVIDIA Jetson 设备上部署训练好的 DNN 模型，其核心功能是构建一个优化后的推理引擎。用户可通过 TensorRT 调整执行过程中的技术参数，例如混合精度，还可选择执行模型的硬件设备（GPU 或 DLA）。此外，TensorRT 还提供层间优化和层内优化技术，以确保推理引擎达到最佳性能[25]。
- **DeepStream**：该工具基于 TensorRT 等其他库构建，主要用于辅助开发 AI 应用。在计算机视觉应用中，DeepStream 可搭建从数据输入到结果输出的完整流程[26]。
- **视觉编程接口（VPI）：这是一个支持图像和视频处理算法的库，用户可通过 VPI 访问 PVA 和 VIC 模块**。VPI 支持的算法示例包括图像格式转换、滤波、镜头畸变校正以及特征跟踪等。:mdnice-bold-italic[VPI 是 DeepStream SDK 的一部分] [27]。
:::

- 当执行的任务与某一加速器不兼容时，上述工具会将任务重定向到 GPU 上执行。
- 若 GPU 已在执行其他任务，这种重定向会导致任务执行中断。

此外，TensorRT 不允许将 DNN 的卷积层分配给 PVA 执行，这限制了 PVA 的应用场景——仅能用于滤波和其他预处理任务。

### 2.4 构建调度器面临的挑战

::: block-1
在构建调度器的过程中，需要解决以下几方面的挑战：
:::

#### 1. 内存竞争

> **内存竞争** 不仅发生在 SDRAM 和辅助内存中，还会**发生在缓存内部以及不同加速器之间**。

![文章插图](/articles/2025-12-10-gpu-ai-fd0e60ec/images/05.webp)

::: image-caption
图 1：NVIDIA Jetson AGX Orin 的硬件架构[13]
:::

如图 1 所示，Orin 设备的 GPU 和专用加速器（包括 DLA、VIC 和 PVA）均通过一条共享的内存控制器架构（memory controller fabric）连接到外部的低功耗双倍数据速率 5 型（LPDDR5，一种高性能、低功耗的移动内存标准）SDRAM 内存。这类系统需要精细的内存管理，以**避免多个加速器同时访问内存时产生冲突** [7,28]。

**边缘张量处理单元（TPU）中也存在类似的“单内存总线”问题** （文献[29]对此进行了研究）。在边缘 TPU 中，若参数未被缓存，处理单元就必须等待参数从主内存中加载，这会导致内存流量增加，进而增加能耗。:mdnice-bold-italic[研究表明，在执行 AI 模型时，近 50.3%的能耗用于片外数据传输[29]。因此，有效的调度器必须考虑这些潜在的性能瓶颈，以优化系统整体性能。]

#### 2. 过渡开销

在将 DNN 的不同层分配到合适的加速器时，还需考虑一个问题——若连续的两层被分配到不同设备上执行，会产生额外的延迟。这是因为前一个加速器内存中的数据必须传输到共享内存中，后一个加速器才能访问这些数据，这一过程会引入延迟，影响系统整体性能[7]。因此，在 DNN 的某些执行阶段，将连续层分配到同一设备上执行，可能更有利于避免延迟增加。

由此可见，**调度器需要在“总过渡时间”（所有层切换设备产生的延迟总和）和“过渡次数”（层切换设备的次数）之间进行权衡** ——:mdnice-bold-italic[既要避免过渡次数过多导致总延迟过大，又要确保不会因过度减少过渡次数而影响加速器资源的充分利用，最终避免损害 DNN 模型的执行性能。]

#### 3. 加速器特性限制

每种加速器在可处理的任务或层类型、可支持的输入/输出格式方面都存在特定限制。例如，:mdnice-bold-italic[根据功能不同，PVA 和 VIC 【仅】支持特定的数据格式：]

::: block-1
- PVA 可对无符号 8 位整数和 16 位整数格式的数据执行卷积和滤波操作；
- 而 VIC 可对相同格式的数据执行图像转换和其他处理操作，且通常【仅】处理亮度通道数据。
:::

**在卷积操作性能方面，PVA 接近甚至超过 CPU**。例如：

- 对于尺寸为 1920×1080 的无符号 8 位整数数据和 3×3 大小的卷积核，PVA 执行卷积操作仅需 0.27 毫秒，而 CPU 则需要 0.297 毫秒[27]。
- 在图像缩放和部分重映射任务中，VIC 的性能也优于 CPU：将 640×480 尺寸的图像缩放至 1920×1080 尺寸时，VIC 仅需约 0.893 毫秒，而 CPU 则需要约 6.75 毫秒[30]。

:mdnice-bold-italic[具体到 DLA，根据文献[31]的研究，其限制包括但不限于以下几点：]

::: block-1
- 仅支持半精度浮点数和 8 位整数；**但对于某些特定层，【仅】支持其中一种格式**。例如：
- 反卷积层的填充必须为 0。
- 卷积核大小必须在 1 至 32 之间。
:::

> 在大多数情况下，为确保 DLA 能够执行 DNN 模型的某一部分，**多数调度器[8,32,33]会将 DNN 模型的前几层分配给 DLA 执行** ——因为这些层通常与 DLA 的兼容性最高，而模型后几层的兼容性较低。

因此，在将每一层分配给硬件设备时，必须仔细考虑层的规格（如卷积核大小、是否为反卷积层等）、输入格式、输出格式以及硬件限制，以确保兼容性并最大化处理效率。

#### 4. 静态调度器与动态调度器

> 根据并行化技术和调度方法的不同，调度器可分为**静态调度器** 和**动态调度器** 两类。

- 静态调度器遵循预先设定的执行计划（:mdnice-bold-italic[在任务执行前就确定好每一层的分配方案]）；
- 而动态调度器则会在运行时:mdnice-bold-italic[（任务执行过程中）根据性能指标（如实时延迟、吞吐量）或算法设定的特定目标（如最小化延迟、最大化吞吐量、降低能耗）动态调整执行策略]。

::: block-1
静态调度器的实现相对简单，但在执行流程中出现**突发变化（如某一加速器突然故障、任务负载突然增加）时缺乏灵活性；此时，动态调度器更为适用。**
:::

在本文参考的所有调度器中，除“动态异构感知的并发深度神经网络执行调度器（D-HaX-CoNN）”[7]外，几乎所有调度器均为静态调度器。

#### 5. 横向调度器与纵向调度器

在多数情况下，**调度器会将 DNN 模型的层划分为多个子组，每个子组在指定的加速器上执行** ——:mdnice-bold-italic[这种方式被称为“纵向流水线（vertical pipelining）”]。该方式适用于视频帧的并行处理（指同时处理多个连续的视频帧）和多 DNN 执行场景。

另一方面，少数调度器会基于“宽度维度”（指 DNN 模型中同一层的并行计算维度，如同一卷积层中不同卷积核的并行计算）划分 DNN 模型，使:mdnice-bold-italic[每个加速器能够独立执行 DNN 模型的一个子集——这种执行方式更适用于仅运行单个 DNN 模型的场景。]

## 三、调度器

> 为 NVIDIA 边缘设备开发的调度器，**可根据其寻找最优执行流水线** （:mdnice-bold-italic[pipeline，指将任务分解为多个连续阶段并在不同硬件上并行执行的方式]）所采用的方法进行分类。它们**要么采用优化技术，要么采用启发式方法** 来获得解决方案。

大多数调度器是为 Xavier 设备开发的。由于 Xavier 和 Orin 设备在架构上相似，因此这些调度器的功能预计也会相似。

### 3.1 基于启发式的调度技术

大多数基于启发式的调度器通过一种算法来找到最优的分割方案，该算法会使用一组指标（包括延迟、吞吐量和能耗）。

#### 3.1.1 Jedi 调度器

在 Jetson 感知嵌入式深度学习推理（Jedi，Jetson-aware embedded deep learning inference）调度器[33]中，当算法在保持令人满意的利用率的同时达到最高吞吐量时，解决方案即确定。

::: block-1
这一过程**首先通过启发式全局搜索实现**：先通过一组样本分割点（cut-point，指将 DNN 模型的层划分为不同部分，分配给不同加速器执行的分界点）让算法确定一个估计分割点，然后通过启发式局部搜索来确定分割点的精确位置。
:::

通过 DLA 的部署和并发处理，CP-CNN 下这组帧的延迟得以降低。**由于 DLA 的延迟与 GPU 的延迟相等，因此 DLA 和 GPU 在任何时刻都不会处于空闲状态。**

CP-CNN 算法会迭代地将“从第一层到当前层的操作数与所有层总操作数的比值（操作比）”和“DLA 计算能力与总计算能力的比值（计算能力比）”进行比较。如果操作比小于或等于计算能力比，则将当前层设为分割点。同时，该算法还会比较执行这些层所需的总时间（包括在 DLA 上的操作时间和数据传输时间）。如果运行到分割点的延迟大于运行到“分割点+1 层”的延迟，则将分割点向后移动一层[8]。

#### 3.1.3 Herald 调度器与 H2H 调度器

> 与 CP-CNN 和 Jedi 算法类似，Herald 调度器[34]也考虑 DNN 的并发执行，但它会对层进行划分并将其分配给处理元素。该调度器先执行一个设计空间探索（design-space exploration，指遍历不同的硬件映射和参数组合，寻找最优方案）算法，根据数据流分配层，然后进行后处理以消除空闲时间。

**异构模型到异构系统映射（H2H，Heterogeneous Model to Heterogeneous System Mapping）调度器[35]在 Herald 的基础上进行了改进**，将转换成本（transition cost，指数据在不同加速器间传输或任务切换时产生的时间或能耗开销）纳入层分配过程。

在性能建模后，该映射算法通过四个步骤完成调度任务：

::: block-1
- 首先，基于层级计算评估生成初始映射，暂不考虑其他因素；
- 其次，使用背包算法（knapsack algorithm，一种经典的组合优化算法，用于在给定容量约束下选择物品以最大化价值）将权重缓冲到设备的本地 SDRAM 内存中；
- 再次，合并相邻层，以进一步减少输入/输出特征图（feature map，指 DNN 中层与层之间传递的数据，包含图像的特征信息）数据传输所带来的延迟；
- 最后，调度器会在转换成本和计算成本之间进行权衡，形成一种更能感知转换成本的方案。
:::

H2H 调度器的**动态版本则使用了改进的背包算法** [35]。

### 3.2 基于优化的调度技术

#### 3.2.1 LP 调度器

> 与列出的大多数方法[1,7,8,32,33]不同，**线性规划方法[36]会将整个 DNN 实例映射到一个处理元素上——该处理元素既可以是子单元，也可以是完整的加速器** （CPU、GPU 或 DLA）。由于 DNN 整体在处理元素上执行，因此无需考虑层之间的转换点。

在多核 CPU 模块中，通过 OpenMP 库[37]可使用 2、4 或 6 个内核。在 GPU 模块中，通过 CUDA 和 cuBLAS 库[23,24]可使用 4 或 8 个流式多处理器。通过 TensorRT[25]，可使用 1 或 2 个 DLA 单元。

**LP 调度器是为百度 Apollo 自动驾驶软件[12]设计的**，该软件包含以下模块：

::: block-1
- 感知（Perception）模块：用于定位目标物体
- 语音识别（Speech Recognition）模块：DNN5
- 规划（Planning）模块：用于规划行驶轨迹
- 定位（Localization）模块：用于从传感器获取位置信息
- 地图（Map）模块：用于提供道路信息
- 预测（Prediction）模块：用于预测未来轨迹
- 控制（Control）模块：用于生成加速、制动、转向等操作指令
- 控制器局域网（CAN，Controller Area Network，一种用于汽车内部电子设备间通信的总线协议）总线：用于指令执行和信息传输
:::

::: image-caption
图 6：Apollo 软件中 DNN 和 RNN 的时序图[36]
:::

上述 DNN 和 RNN 均需纳入调度，且已通过评估确认其与加速器的兼容性——结果表明，**RNN 无法在 DLA 上执行，部分 DNN 无法在 CPU 上执行**。图 6 展示了这些 DNN 和 RNN 如何在 Xavier 设备上同时执行。不同的神经网络实例会根据设定的帧率（frame rate，指每秒处理的图像帧数）循环执行，因此该调度器属于静态调度器。

**LP 调度器的目标函数聚焦于最小化系统的累积延迟** （公式 1）。每个任务的延迟是通过在各设备上进行性能分析得到的[36]。该调度器将内存竞争视为一个预设条件，在分析得到的延迟中加入了一个时间因子，但未考虑系统的能耗。

约束条件包括：

- 确保一个任务 $a_i$ 只能映射到一个处理元素 $c e_j$；
- 且当选择某个处理元素 $c e_j$ 后，处理元素集合 $C E$ 中的部分其他元素将不再可用。

例如，如果单个 DNN 实例使用了两个 DLA 单元，那么剩余任务 $a_i$（来自任务集合 $A$）将无法再选择单个 DLA 单元作为处理元素。同理，对于 GPU，如果某个模型使用了全部 8 个 SM，那么剩余模型将无法再选择 4 个 SM 的选项[36]。

#### 3.2.3 GA 调度器

> 文献[1]中探索的另一种方法是使用遗传算法（GA，Genetic Algorithm，一种模拟生物进化过程的优化算法，通过选择、交叉、变异等操作寻找最优解）进行任务调度，**调度依据是来自不同加速器的性能分析数据**。

与 AxoNN 和 HaX-CoNN 类似，GA 调度器会先对转换时间和执行时间进行性能分析，再将数据输入遗传算法。随后，遗传算法会生成 DNN 的理想分割点。

**该算法的机制与自然界的进化过程相似**：只有“最适应”的染色体（chromosome，此处指一个层数组，数组索引代表处理元素）会保留下来。该方法最初在三星 Galaxy S9 等智能手机上进行测试，后来在文献[33]中在 Xavier 设备上进行了测试。

::: block-1
- 当处理单个 DNN 时，GA 调度器的目标是最大化吞吐量并最小化能耗；
- 当处理多个 DNN 时，其目标是最小化延迟和能耗。
:::

GA 方法会将 DNN 的层分配给处理元素，从而能够利用处理单元内部和处理单元之间的并行性。

#### 3.2.5 Map-and-Conquer 调度器

> Map-and-Conquer 调度器[39]采用了与上述所有调度器不同的独特方法：

- 首先，**它沿水平方向实现并行化，将模型划分为多个独立的推理阶段，这些阶段可同时运行——这与垂直流水线（按层划分）形成对比**。文献[40]认为，将层跨加速器划分并非利用加速器的最有效方式。诸如卷积和多头自注意力等操作可进行并行化，使得同一层的多个操作能在不同设备上并发执行，从而最大化效率。
- 其次，**该调度器是少数同时考虑 Transformer 模型（而非仅 DNN 模型）的调度器之一**，因此在模型架构兼容性方面更具通用性。与 GA 调度器类似，Map-and-Conquer 使用进化算法来确定理想调度方案，算法输入包括来自 TensorRT 的性能分析数据，以及由 XGBoost[41] 预测器提供的“各设备上每层的延迟和能耗估计值”。该预测器是必需的，因为它需要同时考虑计算成本和通信成本（与 HaX-CoNN 中的 PCCS 模型类似）。

以 VGG-19 模型为例：仅使用 GPU 执行时能耗为 630 毫焦（mJ），而 Map-and-Conquer 可提供一种能耗仅为 136 毫焦的方案（降低 4.62 倍），同时延迟基本保持不变（25 毫秒）。Map-and-Conquer 的目标函数如公式 7 所示。

该调度器允许用户设定能耗阈值（与 AxoNN 类似）、延迟阈值和性能目标，因此在流水线创建方面**具有更高的灵活性** [39]。

#### 3.2.6 MaGNAS 调度器

> 映射感知图神经网络架构搜索（MaGNAS，Mapping-Aware Graph Neural Architecture Search）调度器同样使用进化算法，但专为视觉图神经网络（设计。

**在 Xavier 设备上，与仅使用 GPU 执行相比，MaGNAS 可将延迟降低 1.57 倍，将效率提高 3.38 倍。**

MaGNAS 采用两步进化算法：第一步优化 GNN 的架构，第二步基于性能建模进行层映射。

::: block-1
- 在架构优化阶段，会根据“考虑准确率、延迟和能耗的适应度函数（fitness function，用于评估个体（此处指 GNN 架构）优劣的函数）”对不同代的架构进行评估；
- 评估后，淘汰部分架构，剩余架构通过变异（mutation，指对架构或映射方案进行随机修改以产生新方案）和交叉（crossover，指将两个方案的部分结构结合以产生新方案）操作生成新一代架构。这一过程会持续到达到搜索预算（search budget，指用于架构搜索的计算资源或时间限制）为止。
:::

层映射的理想硬件分割也采用相同的过程。与 Map-and-Conquer 类似，MaGNAS 允许用户设定能耗阈值和延迟阈值[42]。但该调度器未将内存竞争纳入适应度函数考虑范围。

## 四、对比分析与讨论

> Jedi 与 CP-CNN 的区别在于 DLA 和 GPU 之间的空闲时间。

::: image-caption
图5：模型的时序图（a）在仅GPU执行情况下（b）在CP-CNN方案下，表明该方案降低了整体延迟[8]

- Jedi 中存在 DLA 或 GPU 处于未使用状态的情况；
- 而 CP-CNN 中不存在这种空闲时间，因为其目标函数旨在平衡 DLA 和 GPU 的延迟。

因此，**同一模型的分割点会有所不同**：在 Jedi 中，YOLOv3 模型在第 57 层处被划分为 DLA 和 GPU 两部分执行；而在 CP-CNN 中，分割点位于第 16 层。
:::

另一方面，Jedi 使用了两个 DLA 单元，而 CP-CNN 将 DLA 视为一个整体单元。此外，与 CP-CNN 相比，Jedi 能探索更多的并行实例（包括加速器间并行和加速器内并行）。在大多数情况下，使用 Jedi 时，预处理的流数范围为 1 至 6，后处理的流数范围为 1 至 3。流水线在大多数情况下会联合使用 DLA 和 GPU，并通过部分网络复制（PND）技术使用两个 DLA 单元。对于较小的模型（如 8 位整数格式的 YOLOv3-tiny），仅使用 GPU 即可完成推理。在加速器内部，DLA 采用 4 个流，而 GPU 采用 2 个流[8,33]。

**AxoNN 在考虑延迟的同时还会考虑能耗，并设定了能耗阈值**。尽管 CP-CNN 将计算能力作为目标参数，但它使用的是“计算能力比”而非“计算能力值本身”来确定分割点，因此无法确保最优流水线的能耗最低。此外，两者的另一个**区别在于数据处理场景**：:mdnice-bold-italic[CP-CNN 允许对视频流中的连续帧进行并发处理，而 AxoNN 仅考虑无法并发处理的静态图像。]

AxoNN 和 CP-CNN 均探索了“实现多次转换”的可能性：

::: block-1
- 但 AxoNN 通常选择单次转换——因为有限带宽下的瓶颈会导致转换时间增加。
- 而在 CP-CNN 中，对于包含多个 GPU 的设备，会考虑多次转换[8,32]。
:::

> 表 3 总结了本文所综述的所有调度器。**大多数研究旨在平衡执行速度和能效**。

通常，这些调度器仅实现一次从 DLA 到 GPU 的数据传输——因为设备间的频繁切换会导致效率降低，而**这种“单次传输”已被证明是比“DLA 与 GPU 间持续切换”更高效的方法之一**。仅在极少数情况下（如 Jedi 中的 CSPNet 模型），才会优先考虑多次转换。

此外，大多数调度器将两个 DLA 单元视为一个整体，且减少设备间转换有助于优化速度。但在 Jedi 调度器中，通过引入部分网络复制（PND）技术，可使同一网络的两个实例并发运行。

设**备操作的典型顺序是“先 DLA、后 GPU”，这由任务特性决定**：DLA 非常适合特征提取等早期阶段任务，而 GPU 更适合目标检测或图像识别等后期阶段的专项任务。

**调度器的设计也反映了 DLA 的层兼容性问题**：Jedi 和 CP-CNN 通过将转换点设置在 YOLO 模型的早期部分（这些部分在其他情况下可能与 DLA 不完全兼容），从而规避了兼容性问题。对于 LP、AxoNN 和 HaX-CoNN 调度器，性能分析阶段会确保将不兼容的层永久分配给 GPU。

调度器通常会采用循环结构（looped structure），根据特定方法组织层的执行，不同调度器用于决策的参数存在差异。

::: block-1
- Jedi 的特点在于其多策略（multi-policy）方法。
- 而其他调度器则会单独或成组评估每层，以寻找转换点。
- 相比之下，LP 方法则将任务视为一个整体，通过将不同 DNN 分配给不同设备来利用设备异构性。
:::

最后值得注意的是，2021 年后开发的调度器（包括 H2H、AxoNN、CP-CNN 和 HaX-CoNN）均将转换成本纳入了考虑范围。

## 五、结论与未来展望

> 本文系统地对比了为最新的 NVIDIA Jetson 边缘设备（这些设备的硬件中包含 DLA）开发的各类调度器。

总体而言，:mdnice-bold-italic[当前的发展趋势是开发“采用优化技术且在 DLA 与 GPU 间仅设置单个转换点”的调度器]。许多调度器通过延迟来确定理想调度方案，部分调度器还将能耗纳入了考虑范围。**由于众多应用需要多个 DNN 协同执行，因此开发“能够处理多个 DNN 实例”的调度器已成为研究重点**。在各类调度器中，:mdnice-bold-italic[HaX-CoNN 的通用性极强，能够适应多种调度场景；而 Map-and-Conquer 在模型架构兼容性方面更具优势] （可支持 Transformer 模型）。

随着 DNN 模型复杂度的不断提高，模型早期阶段的层可能不再总是与 DLA 兼容。例如，许多基于 CNN 的生成对抗网络（GAN）中存在的转置卷积层（de-convolution layer）填充，就可能导致 DLA 不兼容。因此，:mdnice-bold-italic[设计一种能够解决此类问题的系统具有重要意义——例如，在部署前用类似操作替换不兼容的层。]

当前的框架（如 DeepStream 和 TensorRT）采取了“防御性策略”：它们不会主动解决这些兼容性问题，而是将 CNN 模型直接卸载到 GPU 上执行，这会导致流水线中断。因此，在边缘设备上部署模型前，需要对 DNN 的模型架构进行研究。此外，还需尽可能将任务或层卸载到未被充分利用的 PVA 和 VIC 上。在现有文献中，几乎没有提及这些设备的应用。:mdnice-bold-italic[有一篇文献[22]探索了 CPU、GPU 和 PVA 之间的能耗与内存竞争关系——这一研究成果可用于调度器设计，以实现 PVA 的高效利用。一种可能的流水线设计是：]

- 将 VIC 用于图像缩放、格式转换等预处理任务
- 将 PVA 用于初始卷积层或滤波操作（filter operation，一种用于提取图像特征的计算操作）。

然而，NVIDIA 的框架（DeepStream 和 VPI）限制了 PVA 的使用场景——仅允许将其用于跟踪、滤波和其他预处理任务。通过 TensorRT，DNN 模型的层只能分配给 DLA 或 GPU[25,43]。

另一个**值得探索的方向是“利用 AI 进行调度”**。例如，SCHED²[44]是一种用于 GPU 数据中心的强化学习调度技术，可确定资源的最佳使用方式。该方法同样可应用于边缘设备，从而实现更具动态性的调度——能够预测并适应未来的信息变化[11]。

最终，调度器的选择必须与应用场景相匹配：

::: block-1
- 对于多 DNN 场景，HaX-CoNN 是更优选择；
- 对于执行实时处理的单 DNN 场景，CP-CNN 和 Jedi 是理想选择；
- 如果关注能耗，AxoNN 和 Map-and-Conquer 则更合适。
:::
