> 本文围绕 2-单纯形注意力（2-Simplicial Attention）的硬件高效内核设计展开，旨在解决大型语言模型中注意力机制的 token 效率提升与计算成本优化问题。

2-单纯形注意力通过三线性函数建模 token 三元组间的复杂交互，虽能提升 token 效率（尤其在数学、逻辑推理任务中），但完整计算呈 $O(N^3)$ 复杂度且无法直接适配 GPU 张量核心，存在实用性瓶颈。

::: block-1
为突破这一限制，研究团队采用硬件对齐协同设计思路：

- 首先通过二维滑动窗口（由 W1、W2 定义）将计算复杂度降至可处理范围，同时保留注意力表达能力；
- 其次针对张量核心适配难题，将三线性运算分解为二元组件（如预计算 Q⊙K1、V1⊙V2），实现张量核心友好型设计；
- 此外，通过非对称滑动窗口（W1=32、W2=512）提升张量核心利用率、头的组拼接（Pack GQA）将计算浪费率从 73.2%降至 1.35%、V1 瓦片（tile）优化消除冗余存储操作，进一步优化内核性能。
:::

**为解决原 Triton 内核（张量核心利用率仅 34%）的性能短板，团队基于 TLX（Triton 低级扩展）重写内核，开发了三种版本（含 Warp 特化、计算流水线、乒乓调度等现代 GPU 技术）**。

在 NVIDIA H100 GPU 上，前向传播实现高达 588 Tensor Core BF16 TFLOPs 的性能，张量核心利用率约 60%，较原 Triton 内核（337 TFLOPs）提速 1.74 倍，且达到 FlashAttention3（750 TFLOPs）性能的 78.4%，其中 Kernel-1（前向+Warp 特化）表现最优，Kernel-2 因寄存器溢出存在性能回退，Kernel-3 性能提升不显著。

最后，本文指出未来研究方向，包括支持计算流水线、开发反向传播与解码场景的快速内核、实现持久调度，以及沿 N 维度划分消费组以支持小 GQA 比率，为注意力机制的硬件对齐设计提供了可借鉴的优化思路与实践方案。代码仓库已开源：https://github.com/pytorch/FBGEMM/tree/main/fbgemm_gpu/experimental/simplicial_attention。

## 关键问题（Beyond Paper）

### 问题 1：小序列长度场景下的效率矛盾与调和方案

> 【具体问题】Meta 指出 2-Simplicial Attention 通过非对称滑动窗口（如 W1=32、W2=512）适配 Tensor Core 并降低 SMEM 占用，但同时提到小序列长度（N<W2）会因大量 token 需掩码计算导致性能下降，且这种场景下计算密度显著降低。那么在小序列长度占比高的实际 LLM 场景（如短文本生成、对话交互）中，当前基于 TLX 的硬件对齐设计是否存在“为适配长序列优化而牺牲短序列效率”的固有矛盾？该矛盾是否有可行的调和方案，且不破坏现有 Tensor Core 利用率优势？

根据博客内容，当前基于 TLX 的 2-Simplicial Attention 设计确实存在“为适配长序列优化而牺牲短序列效率”的矛盾，但博客未明确提出完整调和方案，**仅提供了部分可参考的优化思路以缓解该问题。**

从矛盾本质来看，作者指出非对称滑动窗口（如 W1=32、W2=512）的核心优势是“提升 Tensor Core/CUDA Core 比例”和“将小 W1 对应的 K1/V1 tile 高效存入 SMEM”（仅占 H100 SMEM 的 7%），但当序列长度 N<W2 时，大量 token 需通过掩码计算确保因果性（j≤i），这会增加 CUDA Core 开销并降低计算密度，导致小序列占比高的场景（如短文本交互）性能显著下降。

关于**调和方向，博客虽未直接给出解决方案**，但可结合现有硬件对齐设计推断：

::: block-1
- 一方面，可复用“头维度分块”思路（如将 Q token 与 Q 头打包以满足 WGMMA 的 64 尺寸要求），通过动态调整 W1/W2 窗口大小适配短序列（如小序列时缩小 W2 以减少掩码范围），但需平衡 Tensor Core 利用率；
- 另一方面，可延续“SMEM 高效利用”策略，针对小序列优化 K2/V2 的加载逻辑（如减少冗余 SMEM→RMEM→SMEM 的数据迁移，参考 V1 Tile 优化思路），但作者未验证此类调整的有效性。
:::

### 问题 2：性能天花板与核心突破点

> 【具体问题】Meta 显示 TLX 优化的 2-Simplicial Attention 前向峰值达 588 TFLOPs，仅为 FlashAttention3 750 TFLOPs 的 78.4%，而 2-Simplicial 的核心价值是通过三元组 token 交互提升 token 效率。那么在保持“三元组建模能力”这一核心特性不变的前提下，当前硬件优化（预计算 Q×K1/V1×V2、乒乓调度等）是否已触及性能天花板？若要进一步缩小与 FA3 的性能差距，核心突破点应聚焦于 TLX 层面的硬件控制优化，还是需修改 2-Simplicial Attention 的数学模型以降低计算复杂度？

博客信息显示，:mdnice-bold-italic[当前 2-Simplicial Attention 的硬件优化未触及性能天花板]，:mdnice-bold-italic[进一步缩小与 FlashAttention3（FA3）性能差距的核心突破点应聚焦于 TLX 层面的硬件控制优化]，而非修改 2-Simplicial Attention 的数学模型。

::: block-1
首先，从性能上限来看，博客指出当前优化（预计算 Q×K1/V1×V2、乒乓调度、Warp 专业化）已实现 588 Tensor Core BF16 TFLOPs（60%利用率），达到 FA3 性能的 78.4%，但:mdnice-bold-italic[未来方向中明确提及“支持计算流水线”“实现持久调度”“沿 N 维度划分消费组以支持小 GQA 比”，这些未落地的优化均指向 TLX 层面的硬件控制升级] （如更精细的 warp 同步、更高效的 SMEM 分块），说明仍有性能提升空间。

其次，数学模型层面无需修改：作者强调当前通过“将 2-Simplicial 滑动窗口注意力重构为 Tensor Core 友好设计”，已在保持“三元组 token 交互”核心特性的同时实现数学等价性，若修改模型则可能削弱 token 效率优势（这是 2-Simplicial 区别于 FA3 的核心价值），因此模型本身并非性能瓶颈。
:::

### 问题 3：反向传播效率与训练整体速度问题

> 【具体问题】Meta 明确将“开发反向传播和解码形状的快速内核”列为未来方向，当前仅重点优化了前向传播，且提到算法 2 的 CUDA Core 计算未成为前向瓶颈。但 LLM 训练需前向与反向协同，推理需高效解码，而反向传播涉及梯度计算的复杂内存访问模式（与前向的单向计算不同）、解码涉及动态序列长度。那么当前仅优化前向的 2-Simplicial 内核，在实际 LLM 训练中是否会因反向传播效率低下导致“前向快但整体训练速度无提升”的问题？反向传播的硬件优化相比前向会面临哪些独特挑战（如梯度存储的 SMEM 冲突、多轮迭代的依赖关系）？

Meta 明确**当前【仅】优化了 2-Simplicial Attention 的前向传播，反向传播和解码内核尚未开发**，因此在实际 LLM 训练中存在“前向快但整体训练速度无提升”的潜在风险，且反向传播的硬件优化面临比前向更复杂的内存访问与依赖关系挑战。

从训练效率来看，LLM 训练需前向与反向传播协同，博客虽指出前向中 CUDA Core 并非瓶颈（附录 5 验证），但反向传播涉及梯度计算的双向依赖（与前向单向计算不同），且需处理大量中间梯度的存储与复用——博客中前向优化的“SMEM 高效利用”“预计算”等策略，在反向中可能因梯度数据量更大、访问模式更随机而失效，导致反向成为训练瓶颈，进而抵消前向性能提升。

关于反向优化的独特挑战，可结合前向硬件瓶颈推断：

::: block-1
- 一是梯度存储的 SMEM 冲突，反向需同时存储 query、key、value 的梯度，可能超出当前 SMEM 容量规划（如前向仅需存储 K1/V1 tile）；
- 二是多轮迭代的依赖关系，反向计算需等待前向中间结果，难以复用前向的“乒乓调度”（该调度依赖前向的单向数据流）；
- 三是 CUDA Core 开销增加，反向的梯度掩码计算比前向更复杂，可能打破“Tensor Core/CUDA Core 比例平衡”（前向中 Tensor Core TFLOPs 是 CUDA Core 的 410 倍，反向可能缩小这一比例）。
:::

## 一、2-单纯形注意力机制回顾（Recap of 2-Simplicial Attention）

> 随着大型语言模型规模不断扩大，获取足够数量的高质量训练 tokens 变得愈发困难。提升注意力机制的 token 效率对于解决这一问题至关重要。

![文章插图](/articles/2025-09-06-fa3-78-4-triton-2-cbb0ff18/images/05.webp)

其中一项极具前景的技术进展便是 2-单纯形注意力机制（见下面的算法 1，2-Simplicial Attention），它利用三线性函数（trilinear functions）建模查询与两组键（keys，简称 K，分别记为 K1、K2，用于与查询匹配的向量）和两组值（values，简称 V，分别记为 V1、V2，用于生成输出的向量）之间的交互关系，进而建模 token 三元组（triples of tokens）之间的复杂交互，**而非** 标准点积注意力机制中**仅** 建模 token 对之间的交互。

![文章插图](/articles/2025-09-06-fa3-78-4-triton-2-cbb0ff18/images/06.webp)

正如《Logic and the 2-Simplicial Transformer》[3]一文首次提出的那样，2-单纯形注意力机制在基本保持原模型规模的同时，提升了注意力机制的每秒万亿次浮点运算数量。**根据缩放定律实验结果，2-单纯形注意力机制在 token 效率方面表现出显著提升**，尤其在数学、逻辑问题求解等推理任务中效果突出。

## 二、TLX 简介——Triton 底层扩展

> TLX（Triton 底层扩展，Triton Low-Level Extensions，https://github.com/facebookexperimental/triton/tree/tlx）是 Triton 领域特定语言的一种语言扩展，它兼具高性能与开发者易用性。

**TLX 可与 Triton 的高层 Python API无缝集成，同时通过丰富的内部函数** （intrinsics，编译器或硬件提供的底层函数，可直接访问硬件特性），提供对 GPU 核函数执行过程的:mdnice-bold-italic[线程束感知] （warp-aware，线程束是 GPU 的基本并行执行单元，通常包含 32 个同步执行的线程）、:mdnice-bold-italic[近硬件级（hardware-close）控制。]

:mdnice-bold-italic[TLX 原生支持 NVIDIA 的 Hopper 和 Blackwell 系列 GPU 架构，并采用可扩展设计以适配未来架构（包括潜在的 AMD GPU）]，从而支持下面特性：

::: block-1
- 共享内存分块（shared memory tiling，将数据分割为小块存储在 GPU 共享内存中，降低对延迟较高的全局内存的访问频率）
- 寄存器支持的累加器（register-backed accumulators，利用 GPU 高速寄存器存储累加运算结果，避免频繁访问内存）
- 线程束专用化（warp specialization，为不同线程束分配特定子任务，优化并行执行效率）
- 流水线执行（pipelined execution，将计算流程拆分为多个阶段并重叠执行，提升整体吞吐量）
- 细粒度线程束级同步（fine-grained warp-level synchronization，在线程束内部实现高精度的执行步调协调，保证数据处理的正确性）
:::

## 三、快速 2-单纯形注意力机制——硬件对齐设计

> 为使核函数真正实现高效运行并达到最先进性能，我们在模型（算法层面）与核函数（硬件执行层面）之间进行了**大量硬件对齐的协同设计（hardware-aligned co-design）**。

所提出的核函数设计具备以下关键特性。

### 3.1 适配张量核心

由于点积（dot product）本质上是两个张量之间的二元运算仅涉及两个操作数，而 2-单纯形注意力机制（代码太长了，详见附录[3]）中存在三个张量参与的三线性乘积（trilinear_product）运算。

> 这带来了一个根本性挑战：该计算**无法** 直接利用张量核心（Tensor Cores，GPU 中专门用于加速矩阵乘法、张量乘积等密集型运算的硬件单元，计算效率远高于普通 CUDA 核心）。

为解决这一局限，我们通过战略性预计算（pre-computation，在核心计算流程前提前完成部分运算，以简化后续硬件执行步骤），**提出了一种适配张量核心的方法**。我们的方案将**三元** 运算分解为**二元** 组件：

![文章插图](/articles/2025-09-06-fa3-78-4-triton-2-cbb0ff18/images/10.webp)

::: image-caption
注：$\odot$ 表示按元素乘法（element-wise multiplication，即两个张量对应位置元素逐一相乘）。
:::

::: block-1
- 首先，我们预计算 Q[i]与 K1[s]的按元素乘积（式(c)第 10 行），从而使后续与 K2[t]的乘法运算（式(c)第 11 行）能够利用张量核心进行计算；
- 类似地，我们预计算 V1[s]与 V2[t]的按元素乘积（式(c)第 13 行），使得 P 与合并后的 V12[s][t]进行的运算（式(c)第 14 行）能够高效利用张量核心。
:::

这种重构（如式(c)所示）将 2-单纯形滑动窗口注意力机制转化为**适配张量核心** 的设计，同时保持了数学等价性。

我们:mdnice-bold-italic[考虑了两种将适配张量核心的公式实现为 GPU 核函数的方案]：

::: block-1
1. **分离式核函数（Separate kernels）**：在一个核函数中实现预计算，:mdnice-bold-italic[将结果（预计算的 QK1 和预计算的 V1V2）写入全局内存] （GMEM，Global Memory，GPU 的主内存，容量大但访问延迟高，可被所有线程访问），再通过一个自定义点积注意力核函数进行后续计算；
2. **融合式核函数（Fused kernel）**：将式(c)的完整计算流程（从预计算到最终输出）整合到一个单一的注意力核函数中。
:::

**经过仔细分析，第一种方案存在一个显著缺陷**：:mdnice-bold-italic[峰值内存占用大幅增加]。具体而言：

- 预计算的 QK1 所需内存是 Q 的 W1 倍
- 预计算的 V1V2 所需内存是 V 的 $(W1 + W2)$ 倍

当取典型值（如 W1=32、W2=512）且序列长度 N 随模型上下文窗口增大时，这种内存开销对于集成了 2-单纯形注意力机制的训练模型而言变得难以承受。

因此，我们采用了第二种方案，为 2-单纯形滑动窗口注意力机制实现了一个端到端融合核函数。

### 3.2 非对称滑动窗口（Asymmetric Sliding Window）

> **非对称滑动窗口** （$W1 \neq W2$）与**对称滑动窗口** （$W1 = W2$）：实验结果[1]表明，当 $W1 \times W2$ 乘积保持不变时，非对称配置通常能带来更优的模型效果。

为实现硬件对齐，我们采用小 W1、大 W2 的参数设置（本实现中 W1=32、W2=512），原因如下：

::: block-1
1. **适配张量核心**：更大的 W2 值会提高张量核心与 CUDA 核心的运算占比，从而提升张量核心的计算效率；
2. **将所有 K1 和 V1 分块驻留在共享内存中**：根据算法 2，每个 K1/V1 分块（tile）的形状为 $[1, D]$，且需要加载 W1 次。当 W1 较小时，我们可以在循环外部，为每个线程块（CTA，Cooperative Thread Array，GPU 中可共享共享内存的线程集合，是 GPU 并行计算的基本单位）将所有 W1 个 K1/V1 分块以 $[W1, D]$ 的形状加载到共享内存中，随后在 W1 循环过程中，从共享内存将单个 $[1, D]$ 分块重新加载到寄存器。当 W1=32、D=128 且采用 BFloat16 精度时，K1 和 V1 分块的总大小为 16KB，约占 NVIDIA H100 GPU 共享内存容量的 7%。
:::

### 3.3 注意力头的分组分块——打包 GQA（Group Tiling of Heads – Pack GQA）

> 在滑动窗口注意力机制中，每个查询（Q）token 会选择不同的键（K）token 集合。当沿序列维度（sequence dimension，张量中对应 token 序列长度的维度，如长度为 N 的序列对应序列维度大小为 N）进行分块时，我们必须屏蔽某些 Q-K 对，这会导致计算浪费。

这种低效问题在二维滑动窗口注意力机制中更为严重。例如，当 BLOCK_M=64、BLOCK_KV=128、N=8192、W1=32 且 W2=512 时，根据下面二维滑动窗口注意力（2D SWA）计算浪费率的计算，约有**73.2%** 的计算量被浪费。

```
------------------------------参数（Parameters）：M=64，KV=128，N=8192，W1=32，W2=512，D=128沿序列维度分块（Tiling Sequence）：效率（Efficiency）：26.80%浪费率（Waste）：73.20%沿注意力头维度分块（Tiling Heads）：效率（Efficiency）：98.65%浪费率（Waste）：1.35%
```

受原生稀疏注意力机制[5]核函数设计的启发，我们将同一 GQA（分组查询注意力，Grouped Query Attention）键值头组（KV head group）下的所有查询头（query heads，注意力机制中并行处理查询的分支，多头注意力通过多个头捕捉不同类型的 token 交互模式）打包到一个分块中，而非沿序列维度分块。**这种方法消除了大部分二维滑动窗口的屏蔽计算。**

在我们的最终实现中，仅在最初几个线程块（CTA）的最后一次 W2 循环迭代中需要进行滑动窗口屏蔽，将计算浪费率从**73.2% 降至1.35%**

```
------------------------------参数（Parameters）：M=64，KV=128，N=8192，W1=32，W2=512，D=128沿序列维度分块（Tiling Sequence）：效率（Efficiency）：26.80%浪费率（Waste）：73.20%沿注意力头维度分块（Tiling Heads）：效率（Efficiency）：98.65%浪费率（Waste）：1.35%
```

#### 权衡考量（Trade-off considerations）

沿注意力头维度分块（head-dimension tiling）的缺点是查询头数量配置的灵活性降低。WGMMA（warp 级矩阵乘法累加指令，Warp-Level Matrix Multiply-Accumulate，GPU 中用于激活张量核心的线程束级矩阵运算指令）[6]要求最小 M 值为 64，若配置的 M 值低于 64，同样会造成计算浪费。

**为平衡屏蔽效率与模型灵活性，我们可将连续的 Q token 与 Q 头打包到一个分块中，以满足 64 的大小要求** （类似 FlashAttention3 解码核函数中的 PACK_GQA 机制）。尽管原论文采用的 GQA 比例（查询头数量与键值头数量的比值）为 64，但:mdnice-bold-italic[在我们的实现中，为使峰值 TFLOPs 基准测试能在不同 Q 分块间实现两个消费者线程束组分区] （consumer warp-group partitions，负责消耗数据进行计算的线程束组的划分方式），我们**将 GQA 比例设置为 128。**

### 3.4 V1 分块优化（V1 Tile Optimization）

考虑矩阵运算 $C = A @ B$（$@$ 表示矩阵乘法，即通用矩阵乘法 GEMM）。:mdnice-bold-italic[WGMMA 指令 允许矩阵 A 存储在寄存器内存或共享内存（SMEM）中，而矩阵 B 必须驻留在（reside in）共享内存中]。

输出分块 C 则存储在寄存器内存中。在注意力机制的 PV12 矩阵乘法（GEMM）中，P（QK12 矩阵乘法的输出）驻留在寄存器内存中，V2（通过 TMA 加载）驻留在共享内存中。**然而，式(c)中 V1 与 V2 的广播乘法运算，要求两个操作数均位于寄存器内存中**。这使得我们必须将 V2 从共享内存加载到寄存器内存，执行按元素计算生成 V12，再将 V12 写回共享内存——:mdnice-bold-italic[这是一个低效的过程。]

我们观察到，PV 矩阵乘法的输出驻留在寄存器内存中，且由于 V1 会沿 PV12 点积维度进行广播，因此在数学上，将 V1 应用于 V2 的操作（即 V1 与 V2 的运算融合）在与 P 进行点积之前或之后执行是等价的。

![文章插图](/articles/2025-09-06-fa3-78-4-triton-2-cbb0ff18/images/11.webp)

因此，我们对算法进行了优化：:mdnice-bold-italic[将 V1 分块直接应用于 PV 矩阵乘法的输出，从而消除了共享内存（SMEM）与寄存器内存（RMEM）之间冗余的加载/存储操作。]

> **注**：为何计算 $Q \odot K1$ 而非 $K1 \odot K2$，原因如下：

::: block-1
1. $K1 \odot K2$ 无法在 w1 循环中预计算。预计算所有 $K1$ 与 $K2$ 的组合（combinations）需要在共享内存中存储大小为 $w1 \times w2 \times D$ 的数据，而该数据量过大，共享内存无法容纳；
2. $K1 \odot K2$ 的运算结果会驻留在寄存器内存中，这会导致与 $V1 \odot V2$ 运算相同的低效问题（即需要在共享内存与寄存器内存间频繁传输数据）。
:::

## 四、采用基于 TLX 的现代 GPU 技术

> 尽管我们已实现上述所有优化，但 Triton 核函数的性能仍远未达到领域最先进（SOTA）水平。**我们最优的前向注意力核函数仅能实现 34%的张量核心利用率，而 FlashAttention3[4]的利用率却高达 75%。**

对生成的 PTX 代码（PTX，Parallel Thread Execution，NVIDIA GPU 的中间汇编语言，是连接高级语言与 GPU 硬件指令的桥梁）分析后发现，:mdnice-bold-italic[该核函数的软件流水线与自动线程束专用化（automatic warp specialization，为不同线程束分配特定子任务以优化并行效率的技术）功能均无法正常工作]：**软件流水线编译器后端无法完成必要的模式匹配，因此跳过了优化步骤**；而线程束专用化则触发了 2-单纯形注意力实现特有的编译错误。

**为在 Hopper 架构上快速集成现代注意力优化技术**，如 FlashAttention3[4]中的线程束专用化、线程束组间重叠（inter-warpgroup overlapping，即乒乓调度，pingpong scheduling）与线程束组内重叠（intra-warpgroup overlapping，即计算流水线，computation pipelining），:mdnice-bold-italic[我们使用 TLX 重写了核函数，开发了三个不同版本的核函数]：

## 五、基准测试（Benchmarks）

> 根据附录[5]的分析，张量核心的 TFLOPs 显著高于 CUDA 核心的 TFLOPs。因此，为简化计算，我们仅将张量核心 TFLOPs 作为衡量核函数性能的主要指标。

请注意二维滑动窗口注意力机制的以下行为（假设 $W1 \leq W2$）：

::: block-1
- 当总序列长度 $N < W1$ 时：该机制在 W1 和 W2 两个维度上均表现为二维因果注意力（2D causal attention，因果注意力指当前 token 仅能关注其之前的 token，无法关注后续 token，常见于语言模型的自回归任务）；
- 当 $W1 \leq N < W2$ 时：该机制在 W1 维度上表现为一维滑动窗口（1D sliding window），在 W2 维度上表现为一维因果注意力（1D causal attention）；
- 当 $N \geq W2$ 时：该机制完全表现为二维滑动窗口（full 2D sliding window）。
:::

具体而言，当 token 的索引 $i < W2$ 时，需对最后一个分块应用因果屏蔽（causal mask）以确保 $j \leq i$（即当前 token 仅关注之前的 token）。**这不仅降低了这些 token 对应最后分块的计算密度（computational density，单位内存访问对应的计算量，密度越低，硬件利用率越低），还增加了 CUDA 核心用于屏蔽计算的额外开销（overhead）**。相反，当 $i \geq W2$ 且 $W2$ 能被 BLOCK_KV（KV 维度的分块大小）整除（$W2 \% BLOCK_KV = 0$）时，我们可直接遍历 $K2_j$ 从 $i-W2+1$ 到 $i$ 的范围，无需屏蔽——因为所有分块均为完整分块（full tiles）。由于短序列中 $i < W2$ 的 token 占比更高，因此整体性能会受影响。

我们将 FlashAttention3（FA3）作为点积注意力机制的参考实现。为确保点积注意力与 2-单纯形注意力中每个查询 token 的计算量一致（即与相同数量的不同 KV token 交互），我们将 FA3 的 KV 序列长度设置为 $W1 \times W2$，且不启用因果屏蔽。:mdnice-bold-italic[基准测试结果显示，FA3 的峰值性能可达 750 TFLOPs，这意味着我们最优的 2-单纯形注意力实现达到了 FA3 峰值性能的约78.4%。]

| --- | --- | --- | --- |
| 峰值TFLOPs | 590 | 680 | 717 |

我们的快速 2-单纯形 TLX-WS 核函数（核函数 1）的峰值 TFLOPs 与 FA TLX-WS 核函数几乎持平。:mdnice-bold-italic[剩余的性能差距主要源于 2-单纯形注意力核函数尚未完全启用计算流水线与乒乓调度优化] ——这些将是我们未来工作（future work）的重点方向。

## 六、结论

> 本文全面阐述了 :mdnice-bold-italic[2-单纯形注意力机制的硬件对齐核函数设计方法，通过系统性优化（systematic optimizations）实现了优异性能]。

我们提出了一种简洁的融合式 2-单纯形注意力核函数实现算法，并借鉴了 Hopper 架构的部分特性（如适用于标准点积注意力的 FlashAttention 2.X 技术）。

::: block-1
**未来仍有多个方向可进一步优化**：启用计算流水线、开发反向传播与解码形状（decoding shapes，自回归生成任务中模型输出 token 的过程）的快速核函数、实现持久调度（persistent scheduling，一种让核函数长期驻留 GPU 以减少启动开销的调度方式），以及沿 N 维度划分消费者组以支持小 GQA 比例。
:::

```
def dot_product(A, B):    """    标准点积（矩阵乘法）    输入（Input）：A的形状为[M, K]，B的形状为[N, K]    输出（Output）：C的形状为[M, N]    等价于矩阵运算 A @ B.T（A乘以B的转置）    """    M, K = A.shape    N, K2 = B.shape    assert K == K2, "内维度必须匹配（Inner dimensions must match）"# 矩阵乘法要求前矩阵列数等于后矩阵行数    C = np.zeros((M, N))    for i in range(M):        for j in range(N):            C[i][j] = sum(A[i][inner_k] * B[j][inner_k] for inner_k in range(K))    return Cdef trilinear_product_2D_to_3D(A, B1, B2):    """    用于计算3D注意力对数（logits）的三线性乘积    输入（Input）：A的形状为[M, K]，B1的形状为[N, K]，B2的形状为[N, K]    输出（Output）：C的形状为[M, N, N]    每个元素C[i,j,k]是A[i,:]、B1[j,:]与B2[k,:]沿K维度的按元素乘积之和    """    M, K = A.shape    N, K1 = B1.shape    N2, K2 = B2.shape    assert K == K1 == K2, "所有K维度必须匹配（All K dimensions must match）"    assert N == N2, "N维度必须匹配（N dimensions must match）"    C = np.zeros((M, N, N))    for i in range(M):        for j in range(N):            for k in range(N):                C[i][j][k] = sum(A[i][inner_k] * B1[j][inner_k] * B2[k][inner_k]                                for inner_k in range(K))    return Cdef trilinear_product_3D_to_2D(A, B1, B2):    """    用于通过3D注意力权重（weights）聚合信息的三线性乘积    输入（Input）：A的形状为[M, N, N]，B1的形状为[N, K]，B2的形状为[N, K]    输出（Output）：C的形状为[M, K]    利用3D注意力权重A聚合来自B1和B2的信息    """    M, N, N2 = A.shape    assert N == N2, "A的最后两个维度必须为正方形（A must be square in last two dimensions）"# 注意力权重矩阵通常为方阵    N3, K = B1.shape    N4, K2 = B2.shape    assert N == N3 == N4, "N维度必须匹配（N dimensions must match）"    assert K == K2, "K维度必须匹配（K dimensions must match）"    C = np.zeros((M, K))    for i in range(M):        for k in range(K):            C[i][k] = sum(A[i][a][b] * B1[a][k] * B2[b][k]                         for a in range(N) for b in range(N))    return C
```

### [5] CUDA 核心计算量的理论分析（Theoretical Analysis of CUDA Core Computation）

为简化分析，本文省略了批量维度（batch dimension，记为 B，指一次训练或推理中处理的数据样本数量），并采用以下符号（notation）：

::: block-1
- Hq：查询头数量（Number of query heads）
- N：序列长度（Sequence length）
- D：头维度（Head dimension，每个注意力头的特征维度）
- Hkv：键值头数量（Number of key-value heads），此处设为 1（= 1），分析中同样省略
- BLOCK_M：查询头维度的分块大小（Tile size for query heads），此处等于 Hq（= Hq）
- BLOCK_KV：KV 序列维度的分块大小（Tile size for the sequence length dimension of KV）
:::

张量核心 TFLOPs 计算：

$$
N \times Hq \times D \times W1 \times W2 \times 2 \times 2 = 4 \times N \times Hq \times D \times W1 \times W2
$$

公式中“2×2”的含义：矩阵乘法中每个元素计算需一次乘法和一次加法，对应 2 次浮点运算；2-单纯形注意力的三线性乘积分解后引入额外 2 倍运算量，故总系数为 4。

CUDA 核心 TFLOPs 计算（仅统计 2-单纯形注意力引入的 CUDA 核心运算量）：

QK1 计算（Q 与 K1 的按元素乘积）：

::: block-1
- 每个线程块（CTA）的运算量：$W1 \times BLOCK_M \times D$
- 线程块数量（Number of CTAs）：$N$
- 总运算量：$N \times W1 \times BLOCK_M \times D$
:::

PV2V1 计算（P 与 V2、V1 的融合运算）：

::: block-1
- 每个线程块的运算量：$W1 \times (W2 / BLOCK_KV) \times BLOCK_M \times D$
- 线程块数量：$N$
- 总运算量：$N \times W1 \times (W2 / BLOCK_KV) \times BLOCK_M \times D$
:::

合并后的 CUDA 核心 TFLOPs：

$$
N \times W1 \times BLOCK_M \times D + N \times W1 \times (W2 / BLOCK_KV) \times BLOCK_M \times D = N \times W1 \times BLOCK_M \times D \times (1 + W2 / BLOCK_KV)
$$

比例分析（Ratio Analysis）：

$$
\text{张量核心TFLOPs / CUDA核心TFLOPs} = \frac{4 \times W2 \times BLOCK_KV}{BLOCK_KV + W2}
$$

例如，当 BLOCK_KV=128、W2=512 时，张量核心 TFLOPs 约为 CUDA 核心 TFLOPs 的 410 倍；且根据[7]，张量核心的硬件运算速度约为 CUDA 核心的 7.38 倍。因此，CUDA 核心计算**不会** 成为 2-单纯形注意力核函数的性能瓶颈。
