## 一、问题的根源：成本悬崖与工作负载的“马太效应”

要理解 FleetOpt 为何有效，首先要搞清楚钱到底浪费在了哪里。答案就藏在两个词里：**KV-Cache 和 工作负载分布。**

### 1.1 KV-Cache 的“内存税”

> 在 LLM 的推理过程中，为了加速生成，模型会将所有历史 Token 的 Key 和 Value 向量缓存下来，这就是 KV-Cache。

对于一个像 Llama-3-70B 这样的模型，在 fp16 精度下，每个 Token 的 KV-Cache 大小约为 320KB——80 层 x 2 矩阵 x 2 字节。

- 如果为单条请求预留一个 64K Token 的上下文，那么它占用的 KV-Cache 就是：`64,000 * 320KB ≈ 20.5GB`。
- 而如果只预留 8K Token，则只需 `8,000 * 320KB ≈ 2.5GB`。

::: block-1
**这意味着，在同样的 GPU 显存下，配置为 8K 上下文的 GPU 可以容纳的并发请求数 $n_{max}$ 是 64K 配置的 8 倍**。这种吞吐能力的差异，就是“成本悬崖”的底层物理基础。
:::

### 1.2 “成本悬崖”：一个 Token 的代价

> 假设我们设定一个短池边界 $B_{short}$ = 8,192 Token。那么：

- 一个请求正好 8,192 Token，进入短池，占用一个 2.5GB 的“小”插槽。
- 一个请求 8,193 Token，**只多了一个 Token，就必须进入长池，占用一个 20.5GB 的“大”插槽。**

:mdnice-bold-italic[这意味着，这“一个 Token”的代价，是让 GPU 的并发能力（吞吐量）从 128 个插槽（短池）骤降到 16 个插槽（长池）]。这就是论文中定义的成本悬崖，其悬崖比 $\rho = n_{max}(s) / n_{max}(l) = 128 / 16 = 8$ 倍。如果短池边界设得更低，比如$B_{short}$ = 1,536 Token，这个悬崖比甚至可以达到惊人的 42 倍！

下表清晰地展示了当请求长度仅超出短池边界一个 Token 时，其消耗的 GPU 成本是如何跃升的。

### 1.3 工作负载的“马太效应”与“边界带”

> 任何规划都必须基于数据。FleetOpt 的基石是对工作负载的深入理解。作者分析了三种典型的负载类型：

1. **I 型：集中-短** （Concentrated-below）：大部分请求集中在短池边界之下（如 LMSYS 多轮对话）。:mdnice-bold-italic[位于边界带 $(B_{short}, \gamma B_{short}]$ 的请求虽然占总请求的比例不高（~4.6-7.8%），但在超过边界的请求中却占了大多数（51-76%）。 这意味着，只要能把边界带的请求处理好，长池的规模就能大幅缩减。]
2. **II 型：分散型** （Dispersed）：请求长度分布在多个数量级，如 RAG + 工具调用混合负载。:mdnice-bold-italic[边界带请求占比较高（~7-12%），且分布较为分散。]
3. **III 型：集中-长** （Concentrated-above）：大部分请求位于短池边界之上，如代码生成任务。此时，压缩的意义有限，主要杠杆是提高 $B_{short}$。

## 二、核心创新一：从第一性原理出发的数学模型

FleetOpt 的第一个核心创新，在于它不是拍脑袋决定配置，而是构建了一个严格的数学框架，推导出最优集群应该是什么样子的。

### 2.1 将每个池建模为 M/G/c 队列

> 作者将每个池，即短池和长池，建模为一个 M/G/c 队列。这里：

- **M 队列：表示请求到达过程是泊松过程（Poisson Process）**，这是一个在系统建模中常用且合理的假设。
- **G 队列：表示服务时间，即请求的推理时间**，其服从一般分布（General Distribution）。这是关键，因为 LLM 的请求长度和输出长度差异巨大，服务时间不可能是指数分布。
- **c 队列：表示服务器的数量**。在 FleetOpt 的模型中，每个 KV-Cache 插槽就是一个“服务器”。每个 GPU 能同时处理的插槽数 $n_{\text{max}}$ 取决于其配置的上下文长度。例如，长池若配置为 64K 上下文，则 $n_{\text{max}}^{(l)} = 16$；短池若配置为 8K 上下文，则 $n_{\text{max}}^{(s)} = 128$。因此，对于有 $n$ 个 GPU 的池，其总服务器数 $c = n \cdot n_{\text{max}}$。

服务时间模型则基于连续批处理（Continuous Batching）的特性推导。每次迭代（Iteration）的延迟 $t_{\text{iter}} = W + H \cdot n_{\text{slots}}$，其中 $W$ 是基础计算时间（如 8ms），$H$ 是每个插槽带来的内存带宽开销（如 0.65ms/插槽），$n_{\text{slots}}$ 是当前活跃的插槽数。

> 最终，一个请求的服务时间 $S$ 由其输入长度 $L_{\text{in}}$ 与输出长度 $L_{\text{out}}$ 共同决定：

$$
\mathbb{E}[S] = \left( \lceil L_{\text{in}} / C_{\text{chunk}} \rceil + L_{\text{out}} \right) \cdot t_{\text{iter}}
$$

其中 $C_{\text{chunk}} = 512$ 为分块大小。由于不同请求的 $L_{\text{in}}$ 和 $L_{\text{out}}$ 差异巨大，$S$ 的分布具有一般性，这正是采用 $G$ 分布（General Distribution）的原因。

### 2.2 利用 Erlang-C 公式和 Kimura 近似进行精确规划

> 有了这个模型，FleetOpt 就能利用队列论的经典工具进行精确的容量规划。

令 $\lambda_p$ 为池的请求到达速率，每插槽服务率为 $\mu = 1 / \mathbb{E}[S]$，则总插槽数为 $c$，系统负载为 $\rho = \lambda_p / (c \mu)$。

- **Erlang-C 公式**：用于计算一个新到达的请求需要等待一个空闲插槽的概率 $C(c, \rho)$。
- **Kimura 近似**：用于在 M/G/c 场景下，结合服务时间的方差，来近似计算 P99 排队等待时间 $W_{99}$。定义服务时间的平方变异系数 $C_s^2 = \text{Var}[S] / (\mathbb{E}[S])^2$，则：

$$
W_{99}(c, \mu, C_s^2) = \frac{\ln(C(c, \rho) / 0.01) \cdot (1 + C_s^2)}{2(c\mu - \lambda_p)}
$$

TTFT（Time to First Token）被分解为三部分：

$$
TTFT = W_{\text{queue}} + T_{\text{prefill}} + T_{\text{first-decode}}
$$

其中，预填充时间 $T_{\text{prefill}}$ 是确定的，$T_{\text{first-decode}} = t_{\text{iter}}$ 为单次解码步骤。因此，规划的 SLO 约束就变成了：

$$
W_{99}(c,\mu ,C_s^2)\leq T_{\mathrm{slo}} - T_{\mathrm{prefill}}^{(99)} - t_{\mathrm{iter}}
$$

这里 $T_{\mathrm{prefill}}^{(99)}$ 是池中请求的 P99 预填充时间，由请求长度分布与 $t_{\text{iter}}$ 共同决定。

::: block-1
**通过这个约束，我们可以为给定的请求速率和长度分布，反推出所需的最小插槽数 $c$，进而得到最小 GPU 数 $n$。** 这是一个从 SLO 倒推配置的精妙过程。
:::

### 2.3 推导出最优边界：等边际 GPU 成本条件

> FleetOpt 最优雅的贡献之一，就是它从理论上推导出了最优双池边界的条件。

设路由后的请求到达率分别为 $\lambda_s = \alpha' \lambda$（短池）和 $\lambda_l = (1 - \alpha')\lambda$（长池），其中 $\alpha'$ 是经过压缩后实际进入短池的请求比例。$n_s^*$、$n_l^*$ 是在给定到达率下满足 SLO 所需的最小 GPU 数。总成本函数为 $\mathcal{C} = c_s n_s^* + c_l n_l^*$。

作者对总成本函数 $\mathcal{C}(B_{\text{short}})$ 关于边界 $B_{\text{short}}$ 求导，并令导数为零，得到了一个一阶条件，即最优边界的**等边际成本条件**：

$$
c_{s}\frac{\partial n_{s}^{*}}{\partial\lambda_{s}} = c_{l}\frac{\partial n_{l}^{*}}{\partial\lambda_{l}}
$$

其中 $\partial n^* / \partial \lambda$ 表示**每增加单位请求速率所需额外增加的 GPU 数**。这一等边际条件意味着：:mdnice-bold-italic[在最优边界 $B_{\text{short}}^$ 处，将额外一个请求路由到短池带来的边际 GPU 成本，【必须等于】从长池移除一个请求带来的边际 GPU 节省。]

::: block-1
这个条件告诉我们，**最优集群的配置不是任意设定的，而是由工作负载特性和硬件成本共同决定的一个精确平衡点**。这个“等边际条件”就像一个指南针，指引我们找到成本最低的舰队配置。
:::

## 三、核心创新二：压缩即路由——跨越悬崖的桥梁

> 数学上的最优解是完美的，但现实的硬件却存在一个无法逾越的障碍：成本悬崖。如果你直接按照理论最优的 $B_{short}^*$ 来划分，那么所有边界带的请求都将被无情地推向昂贵的长池，这不仅浪费了长池的容量，也让你无法真正享受到理论上的最优。

FleetOpt 的**第二个核心创新，就是用压缩即路由来架起这座桥梁**。它不是一个事后补救的工具，而是实现理论最优边界的实施机制。

### 3.1 虚拟池：改变硬边界的本质

> C&R 的核心思想是：在请求进入引擎之前，在网关层进行干预。

对于落在边界带 $(B_{short}, \gamma B_{short}]$ 的请求，我们并不直接将其丢入长池，而是先将其压缩到 $B_{short}$ Token 以内。

这样，**从 LLM 引擎的角度来看，短池的“有效容量”被提升了**。虽然短池的硬件 KV-Cache 大小是 $B_{short}$，但通过 C&R，它可以处理长度达 $\gamma B_{short}$ 的请求。这就形成了一个虚拟池。C&R 将硬件上的硬边界，变成了一个软件上可读、可调的参数 $\gamma$。

由于原文没有直接提供图示，下面给出虚拟池概念图，公式字符用 tex 表示：

```
[原始请求] --> [Gateway]                  |                  +-- 长度 <= B_{short}? --> [短池 (B_{short})]                  |                  +-- B_{short} < 长度 <= \gammaB_{short}? --> [压缩] --> [短池 (B_{short})]                  |                  +-- 长度 > \gammaB_{short}? --> [长池 (\gammaB_{short})]
```

*注：压缩组件在网关层将原本会进入长池的边界请求“拽回”短池，从而改变了实际路由到长池的流量分布。*

### 3.2 轻量级提取式压缩：快、准、狠

> 压缩器本身也是经过精心设计的。它不是为了追求极致的压缩率，而是为了在毫秒级延迟内完成压缩，并保证硬性的 OOM 保障。

- 算法：这是一个:mdnice-bold-italic[纯经典的 NLP 提取式流水线，结合了 TextRank、位置、TF-IDF 和新颖性得分，为句子打分，然后贪婪地选择得分最高的句子，同时保留关键的“首 3 句”和“尾 2 句”。整个流程不依赖任何 LLM 推理，因此非常快。]
- 硬性 OOM 保障：压缩器收到的目标预算 $T_c = B_{short} - L_{out}$。这意味着，**压缩后的 Token 数 $T_c$ 加上请求的输出 Token 数 $L_{out}$，恰好等于 $B_{short}$** 。:mdnice-bold-italic[因此，任何被压缩后的请求，其总 Token 数都不会超过短池的 KV-Cache 容量，从根本上杜绝了内存溢出的风险。]
- 安全门：并非所有内容都适合压缩。代码（Code）被排除在外。路由器会使用 EMA 估计为每个请求打上内容类别标签，**只有 RAG 和散文等结构可提取的内容才进入压缩流程，确保语义无损。**
- 延迟：在 Intel Xeon Platinum 8568Y+上，端到端压缩时间在 2-7 毫秒之间。即使是最坏的情况（Agent-heavy 负载），平均每个请求的压缩开销也仅为 0.39 毫秒，相对于 500 毫秒的 TTFT SLO 完全可以忽略。

### 3.3 协同设计的价值：为什么 1+1 > 2

> FleetOpt 将 C&R 与集群规划协同进行，而不是简单地将 C&R“改造”到一个已有的集群上。

Theorem 2 (Co-design is never worse than retrofit) 指出：**协同设计的集群成本总是低于或等于事后改造的集群成本。**

这个证明很简单：**协同设计的集群在规划阶段就已经知道，未来有一部分请求会被压缩并进入短池，因此它可以放心地缩减长池的规模**。而事后改造的集群，在规划时并未考虑压缩，其长池规模是为原始流量设计的，即使后来加入了压缩，也无法回收为长池多买的那部分 GPU。:mdnice-bold-italic[这个“协同设计”的优势，在流量分布呈现出“集中-短”特征（如 Azure 和 LMSYS）时，表现得尤为突出。]

## 四、FleetOpt 离线规划器：1 毫秒内的最优解

> 将前面的所有理论、模型和机制统一起来的，是 FleetOpt 的离线规划器。这个规划器就像一个“最优集群计算器”，:mdnice-bold-italic[它输入工作负载的 CDF、SLO 要求、GPU 硬件信息和成本，在不到 1 毫秒的时间内，输出最优的$(n_s^, n_l^, B_{short}^, \gamma^)$。]

**规划器的核心逻辑是枚举和优化**。它有两个关键步骤：

1. 枚举边界 B 和带宽 $\gamma$：$B_{short}$ 受硬件约束，必须是使 $n_{max}(s)$ 为整数的值，因此候选集有限。$\gamma$ 则从 1.0 到 2.0 进行扫描。
2. 重新校准长池服务率：这是整个规划器中最容易被忽略但至关重要的一步。当我们通过压缩将部分请求“挪”到短池后，剩下进入长池的请求 $L_{total} > \gamma B_{short}$ 的平均长度会变长，服务率 $\mu_l$ 会降低。如果忽略了这一点，规划器就会错误地认为长池的服务能力更强，从而低估所需的 GPU 数量，导致集群过载。

![文章插图](/articles/2026-04-01-82-gpu-fleetopt-llm-2bf08e59/images/07.webp)

::: image-caption
算法 1：FleetOpt 离线规划器。规划器的核心是枚举所有可能的短池边界 B 和压缩带宽 $\gamma$，并对每种组合进行完整的 M/G/c 建模。第 6 步“重新校准长池服务率”至关重要，因为它考虑了压缩后长池请求分布变“硬”的事实，避免了高估收益。

## 六、相关工作的对比与定位

> 在 FleetOpt 之前，已经有很多工作试图解决 LLM 推理的成本问题，但 FleetOpt 的独特之处在于其全局优化和从第一性原理出发的视角。

### 6.1 池化路由与长度感知调度

- 代表工作：Chen et al. [2026b], Yuan et al. [2025], She et al. [2026]
- 核心思想：**将请求根据其长度路由到不同的、针对特定长度优化的池中**。FleetOpt 借鉴了这一思想，并将其作为最优解的基本架构。
- 区别：这些工作通常将池化路由视为一个独立的技术。而 FleetOpt 将其置于一个更大的优化框架中，并指出了“成本悬崖”是阻碍其达到理论最优的根本障碍，需要引入其他机制来解决。

### 6.2 压缩作为路由杠杆

- 代表工作：Chen et al. [2026a]
- 核心思想：**首次将提示压缩作为一个操作性的路由杠杆，在现有集群上“改造”应用。**
- 区别：FleetOpt 将压缩视为实现理论最优边界的实施机制，而不是一个可选的“外挂”。它从规划阶段就考虑了压缩，实现了协同设计，而不仅仅是事后补偿。

### 6.3. LLM 容量规划

- 代表工作：Romero et al. [2021], Gujarati et al. [2020]
- 核心思想：**专注于模型变体选择、预测性扩展等。**
- 区别：FleetOpt 是首个联合考虑池边界、GPU 数量和压缩率，并直接从工作负载 CDF 推导出最优集群配置的系统。它回答了“在给定流量下，我的集群应该长什么样”这个核心问题。

### 4. 推理模拟与建模

- 代表工作：Vidur [Agrawal et al., 2024b], inference-fleet-sim [Chen et al., 2026c]
- 核心思想：**模拟单个引擎或集群的行为。**
- 区别：FleetOpt 利用这些模拟器，如`inference-fleet-sim`来验证其分析模型，但它的核心价值在于其快速的分析求解能力，可以在 1 毫秒内给出最优解，而模拟器则用于验证和精细化调优。

## 总结

> FleetOpt 为我们展现了一幅全新的 LLM 推理集群规划图景。它的启示是多方面的：

1. **成本优化应从“第一性原理”出发：不要盲目堆卡，而是要从数学上推导出最优解**。M/G/c 队列模型为我们提供了一个强大的工具，将复杂的系统行为转化为可求解的数学问题。
2. **硬件边界需要软件机制来“软化”**：成本悬崖是硬件设计的必然结果，但我们可以通过软件手段（如 C&R）来改变其影响。:mdnice-bold-italic[C&R 的本质，就是将物理上的内存容量限制，转化为一个可动态调整的软件参数，从而在更大范围内实现硬件效率的提升。]
3. “协同设计”是未来 AI Infra 的方向：将压缩、路由、调度、规划等模块视为一个整体，而不是孤立的组件，才能释放出最大的优化潜力。**FleetOpt 证明了，在规划阶段就考虑到未来的压缩行为，可以带来额外的、甚至是巨大的成本节省。**
4. 数据的价值：**FleetOpt 的有效性，高度依赖于对工作负载 CDF 的准确刻画**。没有数据，任何优化都是空中楼阁。未来，随着 AI 应用的多样化，我们需要更精细、更动态地理解我们的负载，并将其反馈给规划器，实现真正的“数据驱动”的 AI 基础设施运营。

::: block-1
最终，FleetOpt 不仅仅是一个技术方案，它更是一种思维方式的转变：**从“应对”最坏情况，转变为“设计”最经济系统**。对于任何希望将 LLM 推理成本控制在合理范围的团队而言，这无疑是一份值得深入研究和实践的宝贵财富。
:::
