## 一、MoE 规模化的核心瓶颈：专家负载失衡

> 混合专家模型已经成为当前大语言模型规模化扩张的主流技术范式，**专家并行则是支撑数百亿乃至数千亿参数 MoE 模型高效训练与推理的核心并行策略。**

随着专家并行度从 8 路、16 路逐步提升到生产环境常用的 32 路、64 路，原本就存在的**专家负载失衡问题被成倍放大，逐渐从次要矛盾演变为制约 MoE 模型性能释放的核心瓶颈。**

### 1.1 专家并行的基本逻辑

::: block-1
混合专家架构的核心思路，是将 Transformer 模型中占算力大头的前馈网络拆分为多个独立的专家模块，每个输入 token 只会被路由到少数几个专家进行计算，用稀疏激活的方式在不显著增加计算量的前提下，大幅提升模型的总参数量与表达能力。从早期的 GShard、Switch Transformer，到当前主流的 DeepSeek-V3、Qwen3、Llama-4，MoE 已经成为大模型规模化的核心路线。
:::

为了承载越来越多的专家，专家并行技术被广泛应用。

简单来说，专家并行就是将所有专家均匀拆分到不同的 GPU 上，每个 GPU 只持有一部分专家的权重。计算流程分为几个步骤：

- 首先每个 GPU 本地计算门控结果，确定本地 token 分别要送往哪些专家；
- 然后通过全局的路由信息交换，统计每个 GPU 要发送和接收的 token 数量与位置；
- 接着通过 all-to-all 全交换通信，把 token 送到对应专家所在的 GPU；
- 之后每个 GPU 对收到的 token 按专家分组，执行批量矩阵乘法完成专家计算；

![文章插图](/articles/2026-07-22-moe-94-ultraep-db148ef5/images/05.jpg)

::: image-caption
图 3 专家并行前向计算流程示例（4 个专家、2 路 EP、top-2 路由配置）
:::

- 最后再通过一次反向的全交换，把计算完成的 token 送回原 GPU。

在实际部署中，专家并行通常和张量并行、流水线并行、数据并行组合使用，作为专家维度的主要扩展方式。相比其他并行策略，专家并行的扩展效率更高，既能提供充足的并行度，又能保持较高的计算密度，因此成为大规模 MoE 部署的核心支柱。

### 1.2 负载失衡的三大表现

> 由于输入内容的多样性、路由算法的动态性，token 在不同专家之间的分布天然是不均匀的，总会有部分专家更热门、承接更多 token，部分专家则相对空闲。在专家并行模式下，这种专家层面的不均衡会直接转化为 GPU 层面的负载差异，带来三方面的性能损耗。

| 问题类型 | 描述 |
| --- | --- |
| 计算掉队问题 | MoE 层总计算时长由负载最高的 GPU 决定，空闲 GPU 需等待最忙 GPU 完成；负载差距越大，资源浪费越严重；且随专家并行度提升，实际性能与理想性能的差距会进一步放大。 |
| token 全交换通信瓶颈 | all-to-all 通信总时长由收发量最大的 GPU 决定；负载不均衡导致部分 GPU 通信量远超均值，拉长通信阶段耗时；通信可能从可重叠的次要开销升级为关键路径上的主要瓶颈。 |
| 激活内存尖峰 | 接收 token 更多的 GPU 需存储更多中间激活值，形成内存峰值；训练中多层激活累积易触发显存溢出；迫使降低批量大小或启用更重的激活检查点，进而降低训练吞吐量。 |

### 1.3 现有均衡方案的本质缺陷

> 针对专家负载失衡问题，行业内已经有不少成熟的解决方案，其中应用**最广泛的是 DeepSeek 提出的 EPLB 专家并行负载均衡器**。这类方案的核心逻辑属于:mdnice-bold-italic[预测式均衡：基于过去一段时间的路由历史统计，周期性地调整专家在 GPU 上的分布，或者给热门专家创建冗余副本，以此平衡各 GPU 的负载]。由于均衡操作是周期性执行的，规划和专家迁移的开销可以摊销到多个批次中，不会占用单步的关键路径。

但这类方案的**有效性，高度依赖负载模式的平稳性**。如果热门专家的分布相对稳定，历史统计就能准确预测未来的负载，均衡效果就好。:mdnice-bold-italic[但当前前沿的 MoE 模型普遍向细粒度方向演进，专家数量从十几个增长到几百个，单个专家的体量更小、专业性更强，负载的动态性也随之大幅提升。]

> 从实验数据可以看到，无论是推理预填充还是训练过程，专家的热度分布都是高度非平稳的。

- 推理场景下，不同语义域的请求会激活完全不同的专家集，同一域内不同批次的热门专家也在持续漂移；

- 训练场景下，辅助损失的负反馈会不断调整专家利用率，加上采样随机性带来的微批次抖动，负载始终处于动态变化中。

在这种场景下，基于历史统计的周期性均衡就会出现严重的滞后性。当实际负载和用于规划的历史数据出现偏差时，均衡效果就会大打折扣，甚至可能因为错误的副本创建反而加剧负载倾斜，形成新的掉队者。

:::

## 二、从周期预测到实时精确：UltraEP 的设计范式转变

> 机架级节点的出现，从硬件层面打破了传统集群的带宽限制，为专家负载均衡的范式转变提供了物理基础。

![文章插图](/articles/2026-07-22-moe-94-ultraep-db148ef5/images/09.jpg)

::: image-caption
图 1 UltraEP 在负载保真度、决策时机以及均衡频率方面不同于现有方案。
:::

UltraEP 没有延续过去“预测-调整”的思路，而是**转向了基于精确负载的实时均衡**，直接在每个微批次、每一层的计算关键路径上完成均衡操作。

### 2.1 机架级节点：新的硬件底座

> 在传统的 RDMA 集群中，高速互联的范围被限制在单台服务器内部，通常是 4 张或 8 张 GPU 通过 NVLink 等 scale-up 链路连接，单卡带宽可以达到数百 GB/s；而服务器之间则通过 RDMA 网络连接，属于 scale-out 链路，单网卡带宽通常只有几十 GB/s，延迟也更高。

在这种架构下，大规模专家并行组必然跨越多台服务器，专家状态的跨节点传输成本极高，完全不可能在单步的关键路径上完成专家复制或迁移，因此只能走周期性离线均衡的路线。

**机架级节点的出现彻底改变了这个限制**。机架级节点将 scale-up 高速域从单台服务器扩展到了整个机架，一个机架内的几十张 GPU（通常 64 张以上）全部通过机架级的高速互联网络直接连接，依然能提供接近单机内的高带宽与内存加载语义。:mdnice-bold-italic[这样一来，整个 32 路或 64 路的专家并行组就可以完全放在同一个机架的高速域内，跨 GPU 传输专家权重的成本大幅降低，让热路径上的实时均衡具备了物理可行性。]

![文章插图](/articles/2026-07-22-moe-94-ultraep-db148ef5/images/10.jpg)

::: image-caption
图 2. 机架级节点内扩展纵向扩展域示意图，与标准RDMA集群对比。
:::

### 2.2 实时精确均衡的核心挑战

> 机架级节点只是提供了硬件可能性，要真正落地实时精确均衡，还需要解决两个层面的核心挑战。

- **第一个是控制面的决策窗口极小**。精确的负载数据只有在门控计算完成之后才能拿到，而拿到负载数据到 token 派发之间的时间窗口非常短，:mdnice-bold-italic[均衡规划算法必须在亚毫秒级别给出高质量的决策，否则规划本身的开销就会抵消均衡带来的收益]。同时，大规模专家并行下，专家数量多、副本组合空间大，联合优化复制与路由的决策复杂度很高，对算法效率提出了严苛要求。
- **第二个是数据面的带宽利用率问题**。实时均衡带来的专家复制流量，是:mdnice-bold-italic[动态、不规则的稀疏传输模式，每个批次、每层需要传输的专家和目标都不一样]。传统的通信库都是针对静态、规则的集合通信优化的，适配这种动态不规则流量的效率很低，很容易出现控制开销占比过高、跑不满机架高速带宽的情况。此外，特别热门的专家需要复制到很多 GPU 上，源 GPU 的发送端口会形成扇出瓶颈，进一步拉低通信效率。

::: block-1
如果这两个问题没有解决好，实时均衡的开销反而会超过收益，得不偿失。**UltraEP 的核心创新，就是针对控制面和数据面分别做了深度的定制优化**，最终把关键路径上的总开销控制在了 0.3 毫秒左右，完全可以被均衡带来的性能增益覆盖。
:::

### 2.3 UltraEP 的整体架构与流水线

> UltraEP 采用**仅复制的均衡策略，永远不调整主专家的位置，只通过创建热门专家的副本来分摊负载**。这种设计的:mdnice-bold-italic[原因在于，大规模专家并行下每个 GPU 持有的主专家数量很少，通常只有 2 到 4 个，重新排列主专家的边际收益很低，反而会带来大量状态迁移和控制复杂度]，破坏数据局部性。而针对瓶颈专家的定向复制，成本更低、收益更直接。

在内存布局上，每个 GPU 都预留固定数量的主专家槽和冗余副本槽。

- 主专家槽持久化存储专家的完整权重、梯度与优化器状态；
- 冗余副本槽则跨所有网络层共享缓冲区，不存储优化器状态，仅在当前层计算时临时存放副本的权重与梯度。

**前向传播的流水线** 分为几个阶段：首先复用现有的 token 全交换通知机制，收集全局的路由负载信息，得到精确的负载矩阵；然后所有 GPU 独立计算出完全一致的复制与重路由计划，不需要额外同步；接着并行执行 token 重路由映射和专家权重分发，权重分发完成后启动正式的 token 全交换与专家计算。整个规划和权重分发都在前向的关键路径上，因此对延迟极其敏感。

## 三、配额驱动规划：联合复制与重路由的控制面创新

> 控制面的核心任务，是在极短时间内同时决定哪些专家需要复制、复制到哪里，以及 token 如何在多个副本之间分配。

传统方案是先决定复制哪些专家，再用轮询之类的启发式方法分配 token，两步分离，很难达到最优均衡效果。**UltraEP 提出的配额驱动规划，把复制和重路由联合优化，直接求解最终的负载分配目标。**

### 3.1 问题的形式化定义

> 整个优化的核心目标，是最小化前向与反向的总延迟。前向的总延迟公式为：

$$
T_{solve\_rep}^{fwd} + max\left(T_{reroute}^{fwd}, T_{w\_distr}^{fwd}\right) + T_{tok\_a2a}^{fwd} + T_{moe}^{fwd}
$$

其中，$T_{solve\_rep}^{fwd}$ 是均衡方案求解的延迟，$T_{reroute}^{fwd}$ 是 token 重路由的计算延迟，$T_{w\_distr}^{fwd}$ 是专家权重分发的通信延迟，$T_{tok\_a2a}^{fwd}$ 是 token 全交换的通信延迟，$T_{moe}^{fwd}$ 是专家计算的延迟。重路由和权重分发可以并行执行，因此取两者的最大值计入总时长。

反向传播的总延迟公式为：

$$
T_{tok\_a2a}^{bwd} + T_{moe}^{bwd}
$$

由于反向复用前向的均衡计划，副本相关的通信可以和计算重叠，不会暴露在关键路径上，因此只剩下 token 全交换和专家计算两项延迟。

MoE 计算的延迟由负载最高的 GPU 决定，和该 GPU 上的总 token 数成正比：

$$
T_{moe}^{fwd/bwd} \propto \max_{r \in \mathcal{R}} \sum_{e \in \mathcal{E}} u_{e,r}
$$

其中 $u_{e,r}$ 就是专家 e 在 GPU r 上的副本承接的 token 配额，$\max_{r \in \mathcal{R}} \sum_{e \in \mathcal{E}} u_{e,r}$ 就是所有 GPU 中总负载的最大值。**这个公式的直观含义就是木桶效应，最忙的 GPU 决定了整层计算的时长。**

token 全交换的延迟同样由最忙的发送或接收 GPU 决定：

$$
T_{tok\_a2a}^{fwd/bwd} \propto \max_{r \in \mathcal{R}} max\left(\sum_{e \in \mathcal{E}} \lambda_{r,e}, \sum_{e \in \mathcal{E}} u_{e,r}\right)
$$

其中 $\lambda_{r,e}$ 是 GPU r 发往专家 e 的原始 token 数，代表发送侧的负载；$\sum_{e \in \mathcal{E}} u_{e,r}$ 是 GPU r 接收的总 token 数，代表接收侧的负载。两者的最大值决定了通信的总时长。

权重分发的延迟由拥有最热主专家的 GPU 决定，和该 GPU 上专家的副本总数正相关：

$$
T_{w\_distr}^{fwd} \propto \max_{r \in \mathcal{R}} \sum_{e \in \mathcal{E}_r} (|\mathcal{H}(e)| - 1)
$$

其中 $\mathcal{E}_r$ 是 GPU r 上的主专家集合，$|\mathcal{H}(e)|$ 是专家 e 的副本总数，减 1 就是需要对外分发的副本数。

整个优化的约束包括：主专家的位置固定不变；每个 GPU 的冗余槽位有数量上限；同一个专家不能在同一个 GPU 上出现多次；反向的副本通信必须完全隐藏；每个新创建的副本至少承接 $u_{min}$ 个 token，避免创建没有实际收益的无效副本。

### 3.2 基于阈值二分搜索的复制策略

> 配额驱动规划的核心思路，是寻找一个最小的负载阈值 $\tau$，使得通过专家复制就可以让所有 GPU 的最终负载都不超过这个阈值。阈值越小，代表均衡后的负载越平均，效果越好。

求解这个最小阈值采用的是二分搜索法。阈值的下限是平均负载乘以目标均衡系数 $\beta$，**论文中 $\beta$ 设为 1.01，也就是目标是让最大负载不超过平均负载的 1.01 倍**；阈值的上限是初始状态下最大的 GPU 负载。

对于每一个候选阈值，都会运行一个贪心可行性验证器，判断这个阈值是否可以通过有限的副本实现。验证的步骤是：

1. 计算每个 GPU 的超额负载（当前负载超过阈值的部分）和空闲容量（低于阈值的部分）。
2. 按照超额负载从高到低遍历超载的 GPU，对每个 GPU 上的主专家按照总负载从高到低排序。
3. 从最热的专家开始，把尽可能多的负载转移到当前空闲容量最大的可用 GPU 上，每次转移的量不能小于最小配额 $u_{min}$。每成功转移一部分负载，就在目标 GPU 上创建该专家的一个副本，并更新对应的配额、超额负载和空闲容量。
4. 如果所有 GPU 的超额负载都能被完全消化，说明这个阈值是可行的，可以继续尝试更小的阈值；如果副本槽位用完还没消化完超额负载，说明阈值不可行，需要尝试更大的阈值。

**这种方法的优势在于，它把副本创建和负载分配直接绑定，每个副本创建的时候就明确了要承接多少负载**，不会出现“创建了副本但没分到多少 token”的无效情况，资源利用效率非常高。

### 3.3 带局部性优先的重路由策略

> 当所有专家的配额分配确定之后，下一步就是把各个 GPU 产生的 token 分配到对应的专家副本上，也就是重路由阶段。**这个阶段不再调整总负载配额，只做 token 的来源拆分，目标是尽量减少跨 GPU 的 token 流量。**

UltraEP 采用局部性优先的拆分策略：对于每个专家，优先让同一个 GPU 产生的 token，消耗该 GPU 上该专家副本的配额。比如 GPU 0 上有专家 A 的主副本，那么 GPU 0 本地产生的要送往专家 A 的 token，优先在本地计算，不用发到其他副本上。:mdnice-bold-italic[这种策略只会改变不同来源 token 的分配，不会改变每个副本的总配额，因此不会破坏已经达成的负载均衡，却能直接减少跨卡传输的 token 总量，降低 all-to-all 通信的压力。]

本地配额消耗完之后，剩余的 token 需求会按照各个副本剩余配额的比例进行分配，采用确定性舍入算法保证总数量精确匹配，不会出现配额超用或者没用完的情况。

最终，每个 GPU 会把拆分结果存储为按副本排序的累积配额表，token 派发的时候只需要做一次简单的上限查找就能确定目标 GPU，开销极低，完全可以在 GPU 端快速完成。

### 3.4 GPU 原生求解实现

> 为了避免主机侧的同步与数据搬运开销，整个配额规划算法完全在 GPU 端实现，不需要 CPU 参与。算法本身不是简单的数据并行扫描，**每个二分搜索步骤都会修改全局状态，存在顺序依赖，因此 UltraEP 采用了单 SM 协作线程块的实现方式**：

- 用一个线程块运行在单个流多处理器上，把负载矩阵和规划状态都存在共享内存里，访问延迟极低。
- 多个 warp 并行评估不同的阈值探针，通过 warp 级别的归约操作快速查找符合条件的空闲容量最大的目标 GPU。
- 同一个内核同时输出最终的槽位映射、配额表和累积重路由元数据，一次性完成所有规划工作。

这种实现把整个规划求解的延迟压缩到了 0.1 毫秒级别，完全满足热路径的延迟要求。和同样使用精确负载的 EPLB+相比，UltraEP 的求解速度快 27.4%，消耗的冗余槽位少 57.9%，同时最终的不平衡度更低，充分体现了配额驱动联合规划的优势。

## 四、RSN 原生通信：适配动态流量的数据面优化

> 有了均衡计划，还要高效地完成专家权重和梯度的传输，才能把均衡的收益真正落地。

UltraEP 的均衡流量是动态的、不规则的稀疏传输图，和传统静态集合通信的模式完全不同，普通通信库很难跑满 RSN 的高速带宽，因此需要专门定制通信栈。

### 4.1 持久化 tile 流传输机制

UltraEP 把每个专家的权重、梯度都切分成固定大小的 tile ，把整个传输任务编译成设备端的 tile 级任务流。通信由持久化内核执行，内核的线程块会不断从全局任务流里取下一个 tile 任务执行，不用每次传输都重新启动内核，大幅降低了调度开销。

对于权重分发场景，源端的 tile 会被一次性加载到共享内存中，然后直接写入所有远程副本的对应内存位置，一次加载多次写入，提升内存访问效率。对于梯度规约场景，内核会从远程副本的缓冲区加载梯度 tile ，累加到本地主专家的梯度缓冲区中，然后清空远程副本的缓冲区，为下一层计算复用。

**内核采用双缓冲流水线设计**：当第 i 个 tile 正在执行写入或规约操作的时候，线程块已经预取了第 i+1 个 tile 的索引，并启动了数据加载。这样一来，任务查找、地址转换、同步等控制开销都被隐藏在数据传输的流水线里，不会作为单独的步骤暴露出来，有效提升了带宽利用率。

同时，内核的资源占用是可配置的。在前向传播的关键路径上，会启动足够多的线程块，提升在途 tile 数量，尽量跑满机架高速带宽；在反向传播和计算重叠的阶段，会显式限制线程块的 SM 占用率，避免和计算内核争抢资源，保证整体的流水线效率。

### 4.2 分块流中继解决热点扇出瓶颈

> 当一个热门专家需要复制到很多个 GPU 上时，源 GPU 的发送端口会成为瓶颈。**单个 GPU 的发送带宽是有限的，要复制的副本越多，总传输时间就越长，形成扇出瓶颈**。传统的交换机组播功能需要预先定义通信组，无法适配 UltraEP 这种每批次都变化的动态副本模式。

为了解决这个问题，**UltraEP 提出了分块流中继机制：当一个专家的副本数量超过阈值（论文中设为 4）时，就构建两级中继树进行传输**。源 GPU 先把数据传给少数几个中继 GPU，再由中继 GPU 转发给剩下的叶子副本。:mdnice-bold-italic[中继节点的数量大概是副本数的平方根，这样可以平衡两级传输的工作量，把源端的扇出压力分摊出去。]

和传统的整文件两级中继不同，**UltraEP 的中继是按 tile 块粒度执行的流水线传输**。源端发完一个 tile 块，中继 GPU 收到完整的块之后，不需要等整个专家传输完成，就立刻向下游的叶子节点转发。

![文章插图](/articles/2026-07-22-moe-94-ultraep-db148ef5/images/16.jpg)

::: block-1
中继节点的选择也有对应的负载感知策略：内核会跟踪每个 GPU 当前分配的发送数据量，优先选择发送量最小的副本作为第一级中继；剩下的叶子节点也会优先分配给加入后总发送量最小的中继节点。

通过这种方式，所有 GPU 的发送负载被尽量拉平，避免出现新的发送瓶颈。
:::

### 4.3 通信性能收益

> 实验数据显示，在相同的均衡计划下，**UltraEP 的定制通信栈相比 PyTorch 分布式批量收发、DeepEP 通信库，速度提升了 3.1 到 5.5 倍**。

在高不平衡度、大扇出的场景下，开启中继机制能额外带来 1.3 到 1.8 倍的性能提升。

**实验结果显示，三个模型上 UltraEP 都能把平均 GPU 级不平衡度控制在 1.01 到 1.03，接近完美均衡**。:mdnice-highlight[吞吐量方面，UltraEP 相比基础版 Megatron-LM 平均提升 42%，达到强制平衡理想吞吐量的 94.6%。] 对比其他均衡方案，EPLB 平均提升 20%，LPLB 平均提升 12%，使用精确负载的 EPLB+平均提升 29%，均显著低于 UltraEP。
:::

尤其值得注意的是 DeepSeek-V3 模型的测试结果。该模型采用细粒度专家设计与路由补偿机制，整体平均不平衡度更低，但短期的负载波动更大。在这种场景下，EPLB 和 LPLB 的性能甚至和无均衡的 Megatron-LM 相当，部分迭代更差，因为周期性的预测完全跟不上快速变化的负载。而 UltraEP 依然能保持 96%以上的理想吞吐量，性能非常稳定。

从延迟拆解来看，以 Qwen3-235B 模型为例，相比理想强制均衡，UltraEP 在前向仅带来 0.33 毫秒的额外延迟，占总延迟的 1.8%，反向的额外开销几乎可以忽略，充分证明了热路径开销控制的有效性。

:::

MoE 计算部分的延迟已经非常接近理想值，说明负载不均衡带来的计算浪费基本被消除；token 全交换部分还有少量差距，来源于真实路由的不规则性，并非均衡方案的问题。

### 5.2 推理预填充场景性能

> 推理场景的优化目标是预填充阶段，也就是处理用户输入 prompt 的阶段。因为解码阶段是内存绑定的，计算不均衡的影响被内存访问延迟掩盖，优化收益有限；而预填充是计算绑定的，负载均衡的收益非常显著，直接影响首 token 延迟与系统吞吐量。

推理测试在 Qwen3-235B 与 GLM4.7-358B 两个模型上开展，覆盖 STEM 与混合域两种负载，测试不同请求速率下的平均首 token 延迟。

结果显示，UltraEP :mdnice-bold-italic[相比基础 SGLang 推理框架，预填充吞吐量提升 1.56 倍；相比 EPLB 方案提升 1.29 倍，平均达到理想吞吐量的 93.9%，均衡后的不平衡度稳定在 1.01 到 1.04。]

![文章插图](/articles/2026-07-22-moe-94-ultraep-db148ef5/images/21.jpg)

::: image-caption
图 12 端到端预填充性能：两类数据域与两款模型下，每秒请求数—平均首token时延的权衡关系。
:::

由于推理预填充的负载波动比训练更大——请求的语义域、prompt 长度、批量组成都在动态变化，因此 **UltraEP 的相对收益也比训练场景更明显。即使是搭配了精确负载的 EPLB+方案，UltraEP 依然有 5%到 24%的性能优势**，进一步验证了配额驱动联合规划的优越性。

### 5.3 内存优化与生产验证

> 除了吞吐提升，UltraEP 还大幅降低了激活内存的峰值。没有均衡的时候，**过载 GPU 的激活内存会形成很高的尖峰，训练场景下 MoE 激活峰值是理想状态的 2 倍，推理场景更是达到 11 倍。**

在真实生产环境中，团队用 UltraEP 训练了 288B 参数的 RefMoE 模型，跨多个机架部署。长期运行数据显示，UltraEP 能稳定保持 92%以上的理想吞吐量，平均比无均衡方案提升 9.6%，且性能波动更小。

## 总结

> UltraEP 并非仅是 MoE 负载均衡的迭代，更是**面向机架级 AI 架构的系统级优化范式**。主要体现在三方面：

- 训练中提升 GPU 利用率（三款模型平均吞吐提升 42%），降低内存峰值，支持更大 batch 与更少检查点，加速模型迭代；
- 推理中提升预填充吞吐、降低首 token 延迟，尤其利好长 prompt 与复杂任务，直接降本增效；
- 以独立运行时库形式实现，与训练/推理框架解耦，仅需不到 1000 行代码即可集成至 Megatron-LM 与 SGLang。

论文在结论中明确指出的扩展方向是：由于 UltraEP 同时覆盖训练与推理预填充，**同一套均衡抽象可自然延伸至交替执行这两种流程的强化学习（RL）流水线，实现训推协同**。需要注意的是，论文分析表明解码阶段为内存绑定、计算不均衡的影响被内存访问延迟掩盖，并非实际的均衡优化目标。

::: block-1
最后，也不得不承认这项工作的扎实。:mdnice-highlight[以实时热路径均衡替代粗粒度周期预测，算法与通信协同设计，开销极低；实测平均达 94.3% 理想吞吐、不平衡度降至 1.01–1.04，逼近理论极限]。它标志着 MoE 优化正从模型层下沉至系统层——当机架成为 AI 基础单元，UltraEP 提供了一种可复用、可扩展、可落地的架构级答案。
:::
