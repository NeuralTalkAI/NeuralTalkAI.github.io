## 一、分布式张量编程的底层困境

> 大模型参数规模的指数级增长，正在让分布式系统的通信短板愈发凸显。**当 H100、H800 这类旗舰 GPU 的单卡算力已经达到数百 TFLOPS，跨卡、跨节点的数据传输带宽却停留在几十到几百 GB/s，两者的差距越拉越大。**

论文给出的统计数据显示，:mdnice-bold-italic[通信开销在大模型训练和推理的总运行时间中占比高达 20%到 80%。这意味着大部分时间里，GPU 都处于闲置等待状态，算力利用率被严重拉低。]

### 1.1 硬件层级的天然割裂

> 现代分布式 GPU 集群的内存与计算层级天然是非均匀的，从底层计算单元到跨节点网络，一共可以划分为三个截然不同的域，每个域的带宽和延迟都有数量级的差异。

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/07.webp)

::: image-caption
图 1：GPU 分布式内存层级与集群总览。该图完整呈现了从单卡内部的寄存器、L2 缓存、HBM，到节点内 NVLink 互联、再到节点间以太网 / InfiniBand 的完整内存层级结构，不同层级的带宽差异可达上百倍。分布式编程的核心挑战，正是单个操作往往需要同时跨越这三个域，传统单一粒度的编程模型无法同时适配所有层级的特性。
:::

- **第一个域是核内域，也就是单 GPU 内部**。数据在 HBM、L2 缓存和寄存器之间移动，带宽可以达到数 TB 每秒，:mdnice-bold-italic[优化的核心是最大化 SRAM 中的数据复用，利用 Tensor Core 等专用计算单元。]
- **第二个域是节点内域，也就是同一台服务器内的多块 GPU 之间**。它们:mdnice-bold-italic[通过 NVLink、xGMI 这类高速互联技术连接，带宽可以达到几百 GB 每秒]，支持统一内存访问，但远程访问的延迟已经不可忽略，:mdnice-bold-italic[还具备 NVLink Sharp 这类在网络内做归约计算的硬件特性。]
- **第三个域是节点间域，也就是不同服务器之间的通信**。数据通过以太网或者 InfiniBand 网卡传输，带宽通常只有几十 GB 每秒，延迟也更高，数据传输需要 DMA 引擎和网卡的显式协调，属于严格的 NUMA 架构。

### 1.2 现有方案的能力边界

> 面对这样的多层级硬件结构，现有软件栈始终无法提供一个统一的抽象来兼顾性能与灵活性，主要分为两大技术路线。

**第一条路线是手工调优的函数库**。比如 FLUX、COMET 这类工作，:mdnice-bold-italic[把通信原语直接集成到 CUTLASS 内核里，实现计算与通信的重叠。但这类方案的编程接口晦涩难用，开发者需要深入了解汇编指令或者复杂的 C++模板元编程]，新的模型架构适配起来非常困难，开发周期往往长达数月。

**第二条路线是分布式编译器与** DSL。比如 CoCoNet、DistEinsum 这类工作，:mdnice-bold-italic[提供算子级别的分布式编程接口；Pallas、TileLink 等框架则尝试把分块的概念扩展到分布式场景。但它们大多难以应对多层级硬件的复杂性]，比如 TileLink 主要聚焦节点内的抽象，没有提供高效跨节点通信所需的控制能力，在大规模集群上表现受限。

整体而言，现有方案要么牺牲灵活性换性能，要么牺牲性能换易用性，始终没有找到一个理想的平衡点。

### 2.1 三大设计原则

> DITRON 的整体设计遵循三条核心原则，这也是它能够同时兼顾灵活性、可扩展性与可移植性的根本原因。

- 第一，**提供与主流张量编译器对齐的灵活编程接口**。DITRON :mdnice-bold-italic[直接采用 Triton 的分块编程模型，在此基础上做分布式扩展]，存量的单卡 Triton 内核只需要少量代码修改就能适配分布式场景，大幅降低迁移成本。
- 第二，**采用可适配任意集群规模与问题形状的可扩展编程范式**。DITRON :mdnice-bold-italic[支持多层分块，细粒度的分块对应高速连接，粗粒度的分块对应低速链路]，可以无缝适配从 NVLink 到 PCIe 再到以太网的各类异构互联架构。
- 第三，**提供一套跨硬件后端可移植的统一原语**。不同硬件平台的拓扑和底层技术差异巨大，:mdnice-bold-italic[DITRON 通过硬件无关的抽象原语屏蔽这些差异，适配新的硬件后端只需要实例化这些原语并实现对应的翻译规则即可。]

### 2.2 核内层级：兼容 Triton 的细粒度分块

> **核内层级是最细的粒度，继承了 Triton 的分块语义，用来管理单个 GPU 内部的计算**。这一层操作的是静态形状的 tile，比如 128×128 的数据块，可以最大化 Tensor Core、TMA 等专用硬件加速单元的利用率。

通过保持与标准 Triton 语法的兼容性，用户可以无缝复用已有的优化内核来实现计算逻辑。论文中给出的 AllGather+GEMM、GEMM+ReduceScatter 等融合内核，计算部分只需要修改几行代码就能适配分布式系统。

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/09.webp)

::: image-caption
All-Gather GEMM 融合内核完整代码示例。代码分为主机侧调度逻辑、通信生产者内核、计算消费者内核三部分。可以看到核心的 GEMM 计算逻辑完全沿用标准 Triton 写法，仅新增了信号等待、分块重排等少量分布式语义，存量 Triton 内核迁移成本极低。
:::

核内层级的接口主要包含三类功能：信号控制（wait、notify）、交换计算（multimem）、分块重排（swizzle），这些原语为后续的中端优化提供了编程基础。

### 2.3 设备层级：DMA 驱动的粗粒度块传输

> **设备层级是 DITRON 区别于单卡编译器的核心层级，专门用来管理分布式内存层级中的数据移动**。这一层操作的是 chunk，也就是由多个细粒度 tile 组成的粗粒度数据块。

设备层级的抽象有两个关键特性。

- **其一，采用以 DMA 为中心的语义**。和核内层级的 load/store 指令不同，:mdnice-bold-italic[设备级原语直接映射到异步 DMA 引擎和网卡，绕过 GPU 的 SM 流多处理器]，节省宝贵的计算资源。
- **其二，支持动态形状**。:mdnice-bold-italic[对于混合专家模型（MoE）这类动态架构，数据块的大小、输入输出的尺寸都可以在运行时动态计算]。比如在 AllToAll 操作中，rank 之间传输的块大小可以根据 token 路由的结果动态确定，这是静态分块方案无法做到的。

### 2.4 任务层级：全图融合的巨型内核调度

> 任务层级是最高层的抽象，把整个分布式负载看作一个由任务组成的有向无环图。**这一层的核心能力是把通信内核和计算内核融合成一个完整的巨型内核（MegaKernel）。**

通过全局管理任务依赖关系和调度，DITRON 可以消除重复内核启动的开销，让内核常驻在硬件上，保证通信链路和计算单元持续处于忙碌状态。:mdnice-bold-italic[和以往需要用 CUDA 或者 C++编程的巨型内核工作不同，DITRON 允许用户注册原生的 Triton 内核作为任务，编译器通过软件维护的记分板在编译时自动调度这些内核，最终生成融合后的巨型内核。]

::: block-1
:mdnice-highlight[总之，三级分块抽象从细到粗依次匹配单卡计算、节点内传输、跨节点调度三个硬件层级，既保留了 Triton 生态的编程便利性，又通过分层抽象解决了分布式场景下复杂的内存层级适配问题]。这是 DITRON 能够同时实现易用性与高性能的核心根基
:::

## 三、中端核心优化：分布式 Swizzling 与计算通信重叠

> 分布式场景下，访问远端内存的延迟比本地 HBM 高出几个数量级。如果按照默认的顺序执行计算，GPU 大部分时间都在等待数据传输，算力被大量浪费。

DITRON **中端最核心的优化就是分布式 Swizzling，通过重排分块的执行顺序，让计算和通信自动重叠**，把通信延迟隐藏在计算过程中。

### 3.1 Swizzling 的核心原理

Swizzling 本质上是一种分块执行顺序的重排。

::: block-1
我们可以用 GEMM+ReduceScatter 的场景来理解它的作用：在没有优化的朴素调度中，所有 rank 都从索引 0 的分块开始依次处理，而分块 0 的数据通常只在 rank 0 上，其他所有 rank 都需要等待数据传输完成才能开始计算，这段时间计算单元完全闲置。
:::

:mdnice-bold-italic[DITRON 的做法是给每个 rank 的执行顺序加上一个感知 rank 的偏移，让每个 rank 优先处理本地已经有数据、或者数据正在传输途中的分块。这样每个 rank 都可以立刻启动计算，不需要等待远端数据全部到位]，计算过程和数据传输过程就可以并行起来。

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/11.webp)

::: image-caption
图 3：简化的 GEMM+ReduceScatter 代码示例与分布式分块重排示意图。没有重排时所有 rank 从 rank 0 的分块开始处理，其他 rank 都会出现依赖阻塞；重排后每个 rank 从自己本地数据对应的分块开始执行，无需等待即可启动计算，有效将 GEMM 计算与 ReduceScatter 通信过程重叠。
:::

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/12.webp)

::: image-caption
图 10：无重排策略下 rank 与数据分块的全局视图。每一行对应一个 rank，每一列对应一个数据分块。可以看到所有 rank 都从最左侧的分块开始执行，大部分 rank 在初始阶段都处于数据等待状态，计算单元大量空闲。
:::

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/13.webp)

::: image-caption
图 11：加入 Swizzling 重排后 rank 与数据分块的全局视图。每个 rank 的起始分块都做了 rank 感知的偏移，优先执行本地数据就绪的分块，计算与数据传输并行推进，整体执行的空窗期大幅减少，通信延迟被计算过程有效隐藏。
:::

### 3.2 两种适配模式

> DITRON 的 **Swizzling 逻辑分为两种模式，分别对应不同的通信场景。**

- **第一种是 Gather 模式，适用于计算依赖远端数据的场景**，比如 AllGather+GEMM。:mdnice-bold-italic[编译器会尽可能早地发起远端数据的拉取请求，把本地 HBM 当作远端内存的缓存，数据一到就立刻投入计算。]
- **第二种是 Scatter 模式，适用于计算结果需要发送出去的场景**，比如 GEMM+ReduceScatter。:mdnice-bold-italic[编译器会优先计算需要发送给最远节点的分块，数据一旦计算完成，立刻发起长距离通信，充分利用网络带宽。]

Swizzling 逻辑在编译器中被封装为一个无状态、兼容 JIT 即时编译的工具，可以作为可插拔原语灵活注入到任意内核中。

### 3.3 非完美形状的适配

> 在实际的模型负载中，**张量的形状往往不是分块大小的整数倍，会出现跨多个 rank 的分块，这种情况被称为非完美形状。** 如果处理不当，这些跨 rank 的分块会成为新的阻塞点。

:mdnice-bold-italic[DITRON 的 Swizzling 算法专门针对非完美形状做了优化，会把这些需要被多个 rank 使用的分块排到执行顺序的前面，提前计算完成并传输给需要的 rank。]

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/14.webp)

::: image-caption
图 12：单节点场景下非完美分块的 Swizzling 重排全局视图。对于不能被分块大小整除的张量形状，跨 rank 的分块会被调整到执行顺序的前端，优先计算并分发，避免成为整体性能的瓶颈。
:::

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/15.webp)

::: image-caption
图 13：双节点场景下非完美分块的 Swizzling 重排全局视图。算法同时考虑了节点内高速互联与节点间低速网络的差异，节点间传输的分块优先级更高，充分利用长距离通信的时间重叠更多计算。
:::

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/16.webp)

整体看下来，分布式 Swizzling 是一种通用且轻量的优化手段。对于大输入形状的场景，:mdnice-highlight[最多可以隐藏 87.5%的通信延迟]，这也是 DITRON 相对传统非重叠方案性能大幅领先的核心原因。
:::

## 四、后端可移植性：硬件无关原语与多平台适配

> 可移植性一直是分布式编译器的一大痛点。不同硬件厂商的通信接口、内存模型差异巨大，每适配一个新平台都要重写大量底层代码，成本极高。

DITRON 通过一套符合 OpenSHMEM 标准的硬件无关原语，把后端通信功能统一抽象出来，**适配新硬件只需要实现对应的翻译规则，大幅降低了移植成本。**

### 4.1 三类统一原语

> **DITRON 把所有底层操作抽象为三大类原语，所有原语都具备硬件无关的语义**，不同后端只需要提供对应的实现即可。

![文章插图](/articles/2026-09-05-ditron-kernel-30-325729b3/images/17.webp)

::: image-caption
表 19：DITRON 统一原语列表。该表完整列出了 DITRON 的硬件无关原语体系，分为分布式原语、SIMT 原语、SHMEM 设备原语三大类。所有原语都具备统一的语义定义，适配新硬件平台只需为每个原语实现对应的代码生成规则，无需修改上层编译逻辑。
:::

- **第一类是分布式原语，用于生成分布式信号控制的底层代码**，包括等待信号、消费令牌、获取 rank 编号、获取总 rank 数、对称内存指针映射、发送通知等功能。
- **第二类是 SIMT 原语，用于线程间的协作与同步**，包括线程 ID 获取、线程块内同步、原子比较交换、原子加法、带内存语义的读写等操作。
- **第三类是 SHMEM 设备原语，用于远端数据传输和信号交换**，包括获取处理单元 ID、远端指针解析、全局屏障、内存栅栏、阻塞/非阻塞的远端内存读写等功能。

### 4.2 代码生成流程

> DITRON 的编译器栈由大约 5.9 万行 Python 代码和 7000 行 C++代码组成，代码生成的整体流程清晰分层。

- 用户使用**三层分块接口编写类 Triton 程序，这些程序会首先转化为分布式中间表示（Distributed IR）。其中标准的单卡语义会降级为标准的 Triton IR，而分布式语义则保留在分布式 IR 中。**
- 接下来，:mdnice-bold-italic[带有 OpenSHMEM 语义的分布式 IR 会进一步降级为 LLVM IR，通过 LLVM 的外部调用能力链接到厂商特定的底层通信库]，比如 NVIDIA 的 NVSHMEM 和 AMD 的 rocSHMEM。如果需要支持其他硬件，也可以对接厂商提供的自定义 SHMEM 库。

目前 DITRON 已经支持超过五种不同类型的 GPU，以及 NVLink、xGMI、PCIe、InfiniBand 等不同的通信架构。

### 4.3 底层针对性优化

> 为了在不同硬件上都达到最优性能，**DITRON 还针对分布式系统的特定硬件约束和延迟瓶颈，做了三项关键的底层优化。**

- **第一项是低延迟协议集成**。标准通信协议通常优先保证带宽，但同步延迟较高。:mdnice-bold-italic[DITRON 参考 NCCL 的设计，实现了专门的低延迟协议，绕过了开销高昂的同步握手过程。]
- **第二项是设备到设备拷贝融合**。离散的驱动 API 调用往往会带来启动抖动和不确定的 SM 占用，产生掉队节点抵消重叠优化的收益。:mdnice-bold-italic[DITRON 把这些数据移动操作直接融合到生成的通信或计算内核中，消除了驱动开销，保证了资源调度的确定性。]
- **第三项是 PCIe 感知的同步与拓扑**。普通 PCIe 互联没有原子内存序的硬件保证，:mdnice-bold-italic[DITRON 通过易失性读写指令实现软件屏障，在不依赖硬件原子操作的前提下保证了内存一致性]，让 PCIe 显卡也能高效运行分布式内核。

::: block-1
回顾一下，硬件无关原语体系让 DITRON 摆脱了单一硬件平台的绑定。:mdnice-highlight[目前不仅在 NVIDIA 平台上实现了超越专家库的性能，在 AMD 平台上也能带来 1%~38%的提速，在 PCIe 显卡上平均提速更是达到 8.33 倍]，展现了极强的跨平台适配能力。
:::

## 六、工业化落地：从实验室到生产级的规模应用

DITRON 已经在字节跳动内部实现了企业级部署，同时覆盖训练和推理两大场景，带来了实实在在的成本节约。对于工业界而言，编译器的价值最终要体现在算力成本的降低和业务效率的提升上。

### 6.1 训练场景落地成效

> 在训练场景，DITRON 已经应用于**从几十亿到上千亿参数的各类模型，不同网络层都得到了不同程度的加速。**

- **注意力模块采用序列并行注意力方案，将 GEMM 计算和 AllToAll 通信重叠**。:mdnice-bold-italic[和原生 Megatron 实现相比，注意力投影部分的提速超过 20%。]
- **MoE 模块实现了 Dispatch、分组 GEMM 和 Combine 操作的重叠**。:mdnice-bold-italic[和原生 Megatron 实现相比，端到端收益达到 10%；即使和高度优化的手写 CUDA 重叠实现 FLUX 相比，也能达到相当的性能，同时代码量减少超过一个数量级]，开发周期从数月缩短到数天。
- **优化器部分支持 Muon 优化器的优化，优化步骤的提速超过 20%。** 流水线并行方面，实现了高效的 PP 通信内核，:mdnice-bold-italic[节点内只需要 8 个 SM 就可以打满带宽，跨节点只需要 1 个 SM]，同时支持和其他层的灵活重叠。

整体来看，DITRON 让训练任务的 MFU（模型浮点运算利用率）提升超过 10%，每月可以节省约 50 万 GPU 小时的训练成本，经济效益十分显著。所有适配的内核都和原生实现逐位一致，完全保证了训练的数值精度和稳定性。

### 6.2 推理场景规模化应用

> 在推理场景，DITRON 同样实现了规模化的落地应用，覆盖云端和边缘两大类场景。

- **云端推理服务方面，部署了高性能的张量并行推理服务**，:mdnice-bold-italic[通过重叠和融合 AllReduce 与 GEMM 操作，同时支持 PCIe 和 NVLink 架构的 GPU，端到端性能提升约 20%，] 有效降低了推理服务的单位成本。
- :mdnice-bold-italic[边缘推理方面，针对机器人这类边缘设备的算力受限场景，提供了高性能的张量并行注意力和张量并行 GEMM 实现，端到端提速超过 30%，] 让大模型在边缘端的部署成为可能。

## 总结与展望

> DITRON 用三级分块抽象打通了从核内到集群的完整内存层级，用分布式 Swizzling 最大化计算通信重叠，用统一原语实现了跨硬件平台的可移植性。

这项工作的意义在于它探索出了一条分布式张量编程的新路径：**基于成熟的单卡分块编程模型向上扩展，而不是从零开始设计全新的分布式语言。**

- :mdnice-bold-italic[对于工程团队而言，DITRON 可以大幅降低分布式优化的人力成本和时间成本]，同时提升硬件资源的利用率，直接降低算力成本。
