## 一、GPU 内核优化的痛点：追踪保真度的双重困境

> 随着大模型训练与推理的算力成本持续攀升，GPU 内核的性能榨取已经进入精细化阶段。融合内核将计算、访存、通信打包进单次启动，软件流水线的重叠效率直接决定了硬件利用率，而细粒度的时序数据是优化的核心前提。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/07.jpg)

::: image-caption
图 3：使用 CuTeDSL IKET 为 FA-3 内核插入探针，追踪 SoftMax 和 P-convert 两个阶段的示例。图中标记了插入的探针代码，通过在阶段首尾调用 range_start 和 range_end 记录时间戳，最终生成对应阶段的运行时追踪结果。这是当前主流内核内追踪的典型用法，本质是在内核执行流中埋点，捕获细粒度的阶段耗时。
:::

传统 GPU 性能工具依赖硬件计数器输出宏观指标，比如总指令数、平均访存带宽、计算单元利用率，**这些数据只能反映内核的整体表现，无法拆解内部各个阶段的耗时与依赖关系。**

::: block-1
对于 FlashAttention 这类深度融合、依赖软件流水线的内核来说，:mdnice-highlight[想要定位流水线气泡、指令重叠不足等细粒度瓶颈，必须依靠内核内追踪技术。内核内追踪通过在内核代码中插入探针，记录精确的时间戳与运行状态，相当于给内核执行做了纳秒级分辨率的 X 光扫描。]
:::

### 1.1 编译期干扰：探针改写了内核的优化结果

> 高保真追踪的第一要求，是追踪的内核和生产环境运行的内核是同一个二进制。**但现有工具几乎都在编译前插入探针**，无论是源码级还是 IR 级插桩，都会让编译器将探针代码与原内核放在一起优化，最终生成的二进制与原版差异巨大。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/08.jpg)

::: image-caption
图 1：Neutrino与IKET在三个代表性内核上的两类追踪保真度损失。左图为二进制相似度，数值越高越好；右图为追踪开销，数值越低越好。从图中可以直观看到，现有工具的二进制相似度最高仅48%，最低只有8%，意味着追踪的内核和实际运行的内核差异极大；而开销最高达到75.6%，严重扭曲原有的执行时序。
:::

论文用二进制相似度来量化这种扭曲，定义为追踪后二进制中与原版完全一致的指令占比。如图 1 所示，在 FlashAttention-3、FlashMLA、FlashAttention-4 三个生产级内核上，**Neutrino 的二进制相似度仅 8-20%，IKET 也只有 13-48%。也就是说，超过一半甚至九成的指令都被改写了，追踪观测到的本质上是另一个内核的执行行为。**

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/09.jpg)

::: image-caption
图 4：现有追踪工具在 H100 上改变 FA-3 内核的实际执行。左图为编译后的指令序列，①②③标记了插桩后丢失的三项编译器优化；右图为运行时追踪结果，Ⅰ-Ⅳ放大了四个被追踪区域。优化丢失直接导致 SoftMax 耗时、V-tile 等待时间被严重高估，开发者基于此得到的是完全失真的性能画像。
:::

这种改写会直接掩盖编译器的关键优化，导致性能分析完全偏离真相。以 FlashAttention-3 的消费者 warp 为例，原版内核中编译器会做三个关键优化：交错展开两次 SoftMax 迭代、将 P 格式转换与 SoftMax 重叠执行、提前 V tile 的释放指令到 SoftMax 区域内。**插入探针后，这三个优化全部失效，两次 SoftMax 变成串行执行，P 转换独立成阶段，V tile 释放被推迟到 SoftMax 之后。最终工具统计出的 SoftMax 耗时、V tile 等待时间都被严重放大**，开发者根据错误数据做优化，自然无法得到预期效果。

### 1.2 运行时扰动：开销扭曲了真实的执行时序

> 高保真追踪的第二要求，是探针本身的开销足够小，不会打乱原有的流水线时序。现有工具的探针需要占用寄存器存放 profiling 数据，与原内核竞争寄存器资源，还会引入额外的数据依赖和同步开销，显著拉长内核执行时间。

**论文定义追踪开销为插桩后内核执行时间相对原版的增幅。如图 1 所示，Neutrino 的开销达到 11.8-75.6%，IKET 也有 3.8-28.4%。** 对于原本只有几百纳秒的流水线阶段来说，几十纳秒的额外开销就会完全改变阶段间的重叠关系，最终得到的时序画像完全失真。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/10.jpg)

::: image-caption
图 5：Neutrino探针周围的等待分布。左图为生产者warp的探针，右图为消费者warp的探针。可以看到探针引入了大量额外的等待，包括WAR寄存器依赖、记分板等待、warp同步等待，这些等待在原版内核中完全不存在。
:::

> 进一步拆解探针周围的等待类型，可以看到三类额外开销：

- 一是 **WAR 写后读依赖**，探针的存储指令写完寄存器后，后续探针指令覆盖同一寄存器，需要等待存储完成；
- 二是**记分板等待**，探针的访存操作会阻塞原内核的后续指令；
- 三是 **warp 同步**，虽然只有一个线程写追踪记录，但整个 warp 都要在重汇聚点等待。

在 Hopper 架构上，:mdnice-bold-italic[一次全局内存访问就要 270-380 纳秒，和被追踪的阶段本身时长相当]，这种级别的扰动足以彻底改变软件流水线的运行节奏。

::: block-1
总之，:mdnice-highlight[现有内核内追踪工具的核心矛盾在于探针本身改变了被观测对象的执行行为]。编译期插桩破坏了编译器的优化决策，运行时资源竞争打乱了原有的流水线时序，最终得到的是一个被扭曲的执行画像，无法指导精准的性能优化。
:::

## 二、现有方案的局限：从源码到二进制的插桩路线对比

> GPU 内核内追踪的本质是在执行流中插入记录指令，捕获时间戳、寄存器值等运行时状态。根据插桩所处的编译栈层级，现有工具可以分为四大类，不同层级的插桩对编译和运行的干扰程度截然不同。

GPU 内核的编译流程通常是源码经过前端编译器生成 IR，再经过后端编译器生成最终二进制。插桩位置越靠前，越容易实现，但对编译的干扰越大；插桩位置越靠后，越接近真实执行，但实现难度越高。

### 2.1 四类插桩路线的分层对比

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/12.jpg)

::: image-caption
图 2：现有 IR 级、预留式、非内联二进制级三类插桩机制与 Xtrace 的二进制指令拼接机制对比。FE 和 BE 分别代表前端与后端编译器。四类方案按插桩时机从早到晚排列，越靠后对编译干扰越小，但实现难度越高；Xtrace 是唯一实现内联式二进制插桩的方案，既不干扰编译，又避免了函数调用的高额开销。
:::

| 类别 | 代表工具与描述 | 优缺点 |
| --- | --- | --- |
| 源码级与 IR 级插桩 | 包括 nano-trace、FlashInfer、Neutrino 等；直接在源码或 LLVM IR、PTX 等中间表示中插入探针代码，由编译器统一编译优化。 | 优点：实现简单、可编程性强；缺点：对编译干扰最大，保真度最低；探针改变指令调度、寄存器分配、循环展开等，导致生成的二进制与原版差异巨大。 |
| 预留式插桩 | 以 NVIDIA 官方 IKET 为代表；在源码中插入占位符，编译时预留寄存器与指令槽位，运行时动态替换为真实探针指令。 | 优点：相比 IR 级插桩对指令调度干扰略小；缺点：预留资源本身影响寄存器分配与优化决策，仍存在显著编译期干扰；且仅支持 CuTeDSL 编写的内核，通用性差。 |
| 非内联二进制级插桩 | 包括 SASSI、NVBit 等；在已编译的二进制中插入函数调用，探针以独立函数形式运行，不侵入原内核指令流。 | 优点：完全不干扰编译过程；缺点：函数调用需保存与恢复全部寄存器上下文，开销极高，不适用于细粒度性能追踪。 |

### 2.2 现有路线的固有矛盾

> **三类路线各有取舍，但始终跳不出“保真度”和“开销”的两难。** 源码和 IR 级路线牺牲编译保真度，换取相对可控的运行开销，但追踪到的是被改写的内核；非内联二进制路线保留了编译结果，但运行开销大到无法用于性能分析。没有任何方案能同时做到高编译保真度和低运行开销。

**造成这一矛盾的核心原因，是现有方案都将探针视为内核的额外组成部分**，要么让编译器一起处理，要么作为独立函数调用。:mdnice-bold-italic[如果能直接将探针指令嵌入原有的二进制指令流，既不重新编译内核，又不引入函数调用的上下文开销，就有可能打破这个两难。这正是 Xtrace 选择的路径：二进制级指令拼接。]

::: block-1
回顾一下，:mdnice-highlight[现有插桩路线始终在编译干扰和运行开销之间摇摆。源码/IR 级路线牺牲编译保真度换低开销，非内联二进制路线保留编译结果但开销爆炸]，始终没有方案能同时做到近乎无损的二进制保留和可接受的运行时开销。
:::

## 三、Xtrace 核心设计：指令拼接技术的三大挑战与解法

> Xtrace 的核心思路是**在编译完成的 GPU 二进制指令流中，直接插入探针指令**，整个过程不重新编译内核，因此完全不会干扰编译器的优化决策。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/13.jpg)

::: image-caption
图 6：Xtrace 系统架构，由探针库、二进制拼接器、运行时追踪驱动三部分组成。工作流程为：开发者在源码中放置追踪标记→内核按正常流程编译生成二进制→拼接器通过调试信息定位标记位置，静态完成指令拼接→运行时驱动劫持内核启动，分配追踪缓冲区并收集结果。整个流程不需要修改编译器，也不需要重新编译内核。
:::

> 要实现这一点，必须解决三个核心问题：寄存器复用的正确性、指令冒险的兼容性、运行开销的可控性。

指令拼接不是简单地在指令序列里塞几条新指令。GPU 的指令执行有严格的调度规则，寄存器的使用有明确的生命周期，随意插入指令要么覆盖活值导致内核计算错误，要么触发未处理的冒险导致执行异常，还可能引入大量额外等待大幅增加开销。

Xtrace 通过三项核心技术分别解决这三个问题。

### 3.1 挑战一：死寄存器复用的正确性保障

> 插入探针指令首先需要寄存器存放时间戳、缓冲区地址等数据。如果随便占用寄存器，很可能覆盖掉原内核后续还要使用的值，导致计算结果错误。Xtrace 的解法是通过反向数据流分析，计算每个插入点处的寄存器活性，只使用那些已经死亡、后续不会再被读取的寄存器。

寄存器活性分析的逻辑并不复杂：从内核的结尾往回遍历，遇到寄存器读取就标记为活跃，遇到寄存器写入就标记为死亡，最终得到每个程序点处每个寄存器的生死状态。但 GPU 内核有两个复杂场景需要特殊处理：

- 一是 warp 专业化内核，不同角色的 warp 会在运行时重新分配寄存器预算，比如生产者 warp 只用少量寄存器，消费者 warp 用大量寄存器。Xtrace 会从寄存器重分配指令中提取每个角色的预算上限，分角色做活性分析。
- 二是异步操作，比如 Tensor Core 指令，它会异步持有寄存器中的累加器，指令发射后很久才会完成读写。如果只看指令顺序，很容易误判寄存器已经死亡，实际还在被异步操作占用。Xtrace 会将这类异步操作持有的寄存器全程标记为活跃，确保不会被探针复用。

> 如果插入点的死寄存器不够用，Xtrace 还有两个兜底方案。

- 第一个是修改二进制中的寄存器数量配置，小幅提高每线程的寄存器上限，新增的寄存器全部给探针使用，原内核的寄存器分配完全不变。
- 第二个是降级为 warp 级追踪，使用 warp 级的统一寄存器，这类寄存器数量固定，不受内核的寄存器压力影响，现代高性能内核的很多操作本身就是 warp 粒度的，降级后依然有足够的追踪精度。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/14.jpg)

::: image-caption
图 9：FlashAttention-3内核的寄存器活性示意图。图中展示了通用寄存器、谓词寄存器、统一寄存器等不同类型的活性分布，以及三个探针插入点复用的死寄存器。可以看到即使是寄存器压力很高的消费者warp，也有大量处于死亡状态的寄存器可以复用。
:::

### 3.2 挑战二：指令冒险的兼容性处理

> 现代 GPU 采用顺序发射的指令调度，编译器会在编译时解决所有指令间的冒险，并将对应的调度信息编码进每条指令的控制位中，包括停顿计数和记分板标记。插入新指令会改变指令间的间距，还会在探针和原内核之间引入新的冒险，如果不做处理，会导致执行错误。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/15.jpg)

::: image-caption
图 7：现代 GPU 的指令调度原理。编译器读取结构冒险表与数据冒险表，将调度结果以控制位的形式固化到二进制指令中；硬件端通过每 warp 的停顿计数器和记分板，按预设计划发射指令。其中结构冒险和静态数据冒险用停顿解决，动态数据冒险用记分板解决，这是 Xtrace 冒险处理的底层依据。
:::

GPU 的指令冒险分为三类： 第一类是结构冒险，两条指令共用同一个硬件流水线，必须间隔足够的周期发射。编译器通过插入停顿周期解决。 第二类是静态数据冒险，生产者指令的延迟是固定的，消费者必须等待足够周期后再发射。编译器也通过停顿周期解决。 第三类是动态数据冒险，生产者指令的延迟不固定，比如内存加载，编译器会给它分配一个记分板，消费者发射前等待记分板就绪。

Xtrace 使用和编译器完全相同的冒险表，精确计算探针指令之间、探针与原内核指令之间的所有冒险，生成对应的停顿和记分板配置。**它精确计算每个冒险需要的间隔周期，同时利用探针与原内核之间的其他指令掩盖部分停顿，只补充剩余需要的周期，尽可能减少额外开销。**

如果插入点处没有空闲的记分板可用，Xtrace 会选择提前等待前面的某个操作完成，主动腾出一个记分板。这种提前等待是安全的，它只会让数据更早就绪，不会暴露未就绪的数据给后续指令，只是牺牲一点原内核的指令重叠度，换取记分板资源。

### 3.3 挑战三：运行时开销的最小化调度

> 即使保证了正确性，探针指令本身也会带来额外的执行延迟，还会和原内核产生依赖关系，阻塞原指令的发射。**Xtrace 的目标是在所有合法的插桩方案中，找到运行开销最低的那一个，** 尽可能将探针的影响融入原有的调度空隙中。

开销的核心来源是数据依赖导致的等待。Xtrace 通过三个维度的优化来压低等待：一是优化指令顺序，让长延迟的操作尽早发射，和其他操作重叠；二是优化寄存器分配，尽量减少探针与原内核之间的依赖，避免引入额外的 WAR、WAW 冒险；三是优化控制位配置，用最少的停顿和记分板操作解决所有冒险。

**这三个维度的决策是相互影响的**，比如指令顺序变了，最优的寄存器分配也会变；寄存器分配变了，冒险的数量和类型也会变。**Xtrace 将这三个决策联合起来做全局搜索，在极小的决策空间内找到最优解**，这也是它能将开销压到远低于现有工具的关键。

::: block-1
整体看下来，指令拼接的本质是在不改变原内核指令的前提下，在二进制的指令缝隙里“塞”进探针代码。:mdnice-highlight[通过活性分析复用空闲寄存器、通过冒险表保证执行正确、通过调度优化压低运行开销，最终实现对原内核的最小扰动。]
:::

## 四、拼接算法详解：如何在二进制空间里做最优插桩

> 确定了三大挑战的解法后，Xtrace 将指令拼接建模为一个带约束的组合优化问题，在插入点处枚举所有可行的寄存器分配、指令顺序和控制位组合，选出运行开销最低的方案。由于探针指令数量很少，枚举空间完全可控。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/16.jpg)

::: image-caption
图 8：将一个 7 指令的内存访问追踪探针拼接到内核指令流中的示例。探针包含读时间戳、计算追踪缓冲区地址、存储追踪结果三个步骤；拼接问题的输入是插入点与原有指令，决策变量包括寄存器分配、指令顺序、控制位配置三类。Xtrace 会在所有合法组合中选出运行开销最低的方案。
:::

编译器做指令调度和寄存器分配时，因为内核指令成千上万、寄存器数量众多，联合优化的空间太大，只能分阶段用启发式算法求解。但探针通常只有几条到十几条指令，死寄存器的数量也有限，完全可以做全空间的最优搜索，得到比编译器启发式调度更好的结果。

### 4.1 问题建模与三大决策变量

> 拼接问题的输入包括内核二进制、插入地址、探针指令集合以及探针内部的 RAW 数据依赖关系。输出是最优的插桩方案，包含三个决策变量：

- 寄存器分配：给探针的每个值分配一个插入点处的死寄存器。
- 指令顺序：排列探针指令的发射顺序，必须满足内部的数据依赖。
- 控制位：给每条探针指令设置停顿计数和记分板，解决所有结构和数据冒险。

插桩方案的开销定义为插入探针后，原插入点位置指令的发射时间延迟，也就是原指令被推迟了多少个周期。对于动态数据冒险，因为延迟不固定，还需要加上实测的保守延迟值做修正，得到更贴近实际的开销估计：

$$
o'=t'\left[i^{(p)}\right]-t_{0}\left[i^{(p)}\right]
$$

其中 $o'$ 是修正后的总开销，$t'[i^{(p)}]$ 是插桩后原插入点指令的发射时间，$t_0[i^{(p)}]$ 是原版内核中该指令的发射时间。

每条指令的发射时间由它的所有前驱指令决定，取前驱发射时间加上对应延迟的最大值：

$$
t^{\prime }[i^{(k)}]=\operatorname* {max}_{i^{(j)}\to i^{(k)}}\left( t^{\prime }[i^{(j)}]+\delta [i^{(j)}\to i^{(k)}]\right)
$$

其中 $i^{(j)}\to i^{(k)}$ 表示从指令 j 到指令 k 的依赖，$\delta$ 是该依赖对应的总延迟，包含静态停顿和动态延迟修正。

### 4.2 最优拼接算法的执行流程

> Xtrace 通过分层枚举的方式搜索最优方案，完整流程如下：

- 第一步，预处理内核二进制，分析插入点周围的寄存器活性和原有控制位信息，得到可用的死寄存器和空闲记分板列表。
- 第二步，枚举所有满足数据依赖的探针指令拓扑顺序。**探针内部有 RAW 依赖，不是所有排列都合法，必须保证生产者指令在消费者之前发射。** 虽然全排列的数量是指令数的阶乘，但数据依赖会大幅压缩空间，比如 7 条指令的探针，全排列有 5040 种，合法拓扑序只有 22 种。
- 第三步，对每个指令顺序，枚举所有合法的寄存器分配方案。生存期重叠的值不能共用寄存器，这本质上是干涉图的着色问题。Xtrace 不需要遍历所有死寄存器的组合，只需要对值做分区，相同分区的值共用寄存器，分区数量远小于寄存器数量，通常只有个位数。
- 第四步，对每个寄存器分配方案，枚举所有冒险表允许的控制位配置，验证方案的正确性，计算对应的静态开销，再加上动态延迟修正得到总开销。
- 第五步，遍历所有合法方案，保留总开销最小的那个作为最终结果。

> 整个决策空间的理论上界可以用公式表示：

$$
\underbrace{|I| !}_{指令顺序} \cdot \underbrace{\left|\mathcal{R}_{d}\right|^{|V|}}_{寄存器分配} \cdot \underbrace{2^{\left|E_{static }\right|}\left(|I|\left|\mathcal{S}_{f}\right|\right)^{\left|E_{dynamic }\right|}}_{控制位配置}
$$

其中 $|I|$ 是探针指令数，$\mathcal{R}_d$ 是死寄存器集合，$|V|$ 是探针的值数量，$E_{static}$ 是静态依赖数量，$\mathcal{S}_f$ 是空闲记分板集合，$E_{dynamic}$ 是动态依赖数量。实际由于各种约束的裁剪，真实搜索空间远小于这个上界，通常只有几百到几千种方案，几毫秒就能完成搜索。

### 4.3 贪心加速：大场景下的快速调度

> 对于极少数指令较多的探针，如果最优搜索的空间还是偏大，Xtrace 提供了贪心调度的加速版本。贪心策略基于依赖链长度排序，优先发射位于长依赖链起点的指令，让长延迟操作尽早开始，和其他指令重叠执行。

每个指令的优先级用价格表示，等于从该指令出发的最长依赖链总延迟：

$$
p\left[i^{(k)}\right]=max _{i^{(k)} \to i^{(l)} \in E_{RAW}}\left(\delta\left[i^{(k)} \to i^{(l)}\right]+p\left[i^{(l)}\right]\right)
$$

每次从所有前驱都已发射的指令中，选择价格最高的那一条发射。这种方法不需要枚举所有拓扑序，一次遍历就能得到指令顺序，速度更快。**实验结果显示，贪心调度的最终开销和最优搜索几乎没有差别，完全可以满足绝大多数场景的需求。**

::: block-1
总之，Xtrace 的拼接算法没有采用编译器的分阶段启发式策略，而是针对探针规模小的特点，做了**全空间的最优搜索**。:mdnice-highlight[在极小的搜索空间里做穷举，反而比通用编译器的启发式调度得到更优的插桩效果，这也是 Xtrace 能把开销压到极低的核心原因之一。]
:::

## 五、跨架构实现：NVIDIA 与 AMD 的差异化适配

> Xtrace 的设计并非只针对单一厂商架构，而是抽象了通用的 GPU 执行模型，再针对 NVIDIA 和 AMD 的架构特点做差异化实现，目前已经支持 19 款不同的 GPU 架构，覆盖从 Volta 到 Blackwell 的 NVIDIA 全线，以及 AMD 的 CDNA 和 RDNA 两大产品线。

不同厂商的 GPU 在指令调度机制上差异很大，NVIDIA 采用全静态调度，所有冒险都由编译器解决；AMD 采用硬件辅助调度，大部分冒险由硬件自动消解。**Xtrace 的核心拼接逻辑是通用的，但冒险处理、寄存器模型、时间戳实现都需要针对架构适配。**

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/17.jpg)

::: image-caption
表 2：Xtrace支持的GPU架构列表，以及对应反汇编器支持的指令数量。NVIDIA侧覆盖从Volta到Blackwell共10款架构，AMD侧覆盖CDNA和RDNA共9款架构，是目前支持架构最广的内核内追踪工具。
:::

### 5.1 NVIDIA 架构：全量执行模型的精确复刻

> NVIDIA GPU 采用顺序发射、全静态调度的设计，硬件本身不做任何冒险消解，所有结构冒险、数据冒险都由编译器提前计算好，编码进指令的控制位中。因此 **Xtrace 在 NVIDIA 架构上实现了完整的执行模型，完全复刻编译器的冒险计算逻辑，精确生成每一条探针指令的控制位。**

在时间戳实现上，Xtrace 做了一个关键优化：不使用 GPU 全局时钟，改用每个 SM 的本地时钟。全局时钟的优点是跨 SM 直接对齐，但读取延迟高达几百纳秒，而且需要 64 位宽度，占用两个寄存器；SM 本地时钟读取只需要几十纳秒，32 位宽度就足够，一个寄存器就能放下，而且精度更高。

**为了解决跨 SM 时钟不对齐的问题，Xtrace 在每个线程块的开始和结束位置，同时读取全局时钟和本地时钟，得到校准映射关系，事后再将所有本地时间戳统一转换为全局纳秒时间线。** 通过这个优化，每个记录探针都省去了昂贵的全局时钟读取延迟，大幅降低了运行开销。

### 5.2 AMD 架构：精简执行模型的轻量适配

> **AMD GPU 的调度机制和 NVIDIA 完全不同，大部分寄存器依赖由硬件自动互锁，指令中没有停顿计数和记分板字段，编译器只需要对少数未被硬件覆盖的冒险插入等待指令**，比如 s_waitcnt 系列计数器等待。因此 Xtrace 在 AMD 架构上使用精简执行模型，只需要按照编译器的规则，给探针补充必要的等待指令即可。

AMD 的寄存器分为三类：每线程的向量寄存器 VGPR、每 wave 的标量寄存器 SGPR、CDNA 架构特有的累加寄存器 AGPR。Xtrace 的活性分析会覆盖这三类寄存器，同时特殊处理矩阵指令对 AGPR 的异步持有，和 NVIDIA 的 Tensor Core 处理逻辑一致。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/18.jpg)

::: image-caption
表 5：AMD 各架构每 wave 跟踪的异步操作计数器类型及位宽。CDNA、RDNA3、RDNA4 三代架构的计数器命名和位宽各有差异，分别对应向量内存、本地内存、标量内存等不同类型的异步操作。这些计数器是 AMD 硬件自动调度的核心，探针插入的访存操作会被自动计数，不需要修改原内核的等待指令。
:::

AMD 用硬件计数器代替记分板跟踪异步操作，比如 vmcnt 跟踪向量内存操作，lgkmcnt 跟踪本地内存和标量内存操作。探针插入的访存指令会自动增加对应计数器的值，原内核后续的等待指令会自动等待这些操作完成，不需要修改原内核的任何等待指令，天然保证正确性。:mdnice-bold-italic[唯一的代价是等待时间会变长，也就是运行开销，Xtrace 会在开销评估中精确计算这部分影响。]

::: block-1
回顾一下，Xtrace 通过抽象通用的拼接框架，针对不同厂商的硬件调度机制做差异化适配，用一套算法覆盖了两大阵营的 19 款架构。:mdnice-highlight[跨架构的二进制级追踪能力，让它可以在统一的框架下对比不同厂商的内核执行行为，这是现有厂商专属工具完全做不到的。]
:::

## 六、实验评估：保真度与开销的全面碾压

> 研究团队在 NVIDIA H100、B300 和 AMD MI300X 三款旗舰 GPU 上，:mdnice-bold-italic[用生产级的 LLM 内核做了全面测试，对比对象是当前最先进的 Neutrino 和 IKET，从二进制相似度、运行开销、寄存器复用、拼接耗时多个维度验证了 Xtrace 的高保真特性。]

实验选用的内核都是当前大模型中最核心的生产级内核，包括 FlashAttention-3、FlashAttention-4、FlashMLA、HSTU，以及 AMD 平台的 FMHA 和 FusedMoE。追踪类型分为从轻到重三档：trace-sche 只在 warp 入口出口记录，trace-pp 在每个流水线阶段边界记录，trace-mem 在每次内存访问时记录。

### 6.1 二进制相似度：98%指令零改动

> 实验用两个指标衡量编译保真度：保留的基本块比例，以及保留的原指令比例。基本块不变意味着内核的控制流完全没有被改变，指令不变意味着原内核的计算逻辑和调度完全保留。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/19.jpg)

::: image-caption
图 12：不同工具下的二进制保留情况。左图为保留的基本块比例，右图为保留的原指令比例，数值越高越好。可以看到Xtrace在所有场景下基本块100%保留，指令保留率达到94-98%，远超现有工具的8-48%。
:::

**结果显示，Xtrace 在所有追踪场景下，基本块保留率都是 100%，** 没有任何一个基本块被修改、拆分或合并。**指令保留率达到 94-98%，** :mdnice-bold-italic[仅有的改动来自分支指令的目标地址偏移——插入指令后指令地址整体后移，分支目标需要做对应调整，这是插入操作带来的必然变化]，不影响指令本身的逻辑和调度。

作为对比，Neutrino 的指令保留率最低只有 8%，超过 90%的指令都被重写；IKET 稍好，但最低也只有 13%。即使是最轻量的 trace-sche 追踪，它们也会改写 78%以上的基本块，说明哪怕只插几个探针，也会影响编译器对整个内核的优化决策。

::: block-1
以 FlashAttention-3 的 trace-pp 场景为例，Neutrino 只保留了 21%的基本块，IKET 保留了 46%，而 Xtrace 完整保留了全部 85 个基本块。整个内核原本有 2432 条指令，Xtrace 只新增了 117 条探针指令，修改了 85 条分支指令的目标地址，其余 2347 条原指令完全没有变化。
:::

> 运行时开销是衡量追踪保真度的第二个核心指标，越低的开销对原执行的扰动越小，追踪结果越接近真实情况。实验从端到端执行时间和探针依赖等待占比两个维度进行衡量。

## 七、实战价值：从内核优化到闭源逆向的能力拓展

> 高保真追踪的最终价值是落地到实际的内核优化中。Xtrace 不仅能提升开源内核的优化效率，**还能追踪闭源的厂商内核**，为开发者提供对标官方优化的参考，这是现有所有工具都做不到的能力。

过去的内核优化很大程度上依赖开发者的经验和直觉，或者靠反复试错调整代码。低质量的追踪数据会误导优化方向，浪费大量迭代时间。**Xtrace 的高保真追踪可以精准定位真实瓶颈，大幅缩短优化周期；而闭源内核追踪能力更是打破了厂商黑盒，让开发者可以直接学习官方优化的实现细节。**

### 7.1 开源内核优化：迭代效率提升 3.9 倍

> 第一个实验是用 AI 编码 Agent 优化 FlashAttention-3，分别用硬件计数器、Neutrino 追踪、IKET 追踪、Xtrace 追踪作为优化依据，对比达到相同峰值性能所需的迭代次数。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/25.jpg)

::: image-caption
图 11：不同追踪工具指导下的FlashAttention-3优化过程。左图为不同迭代轮次的TFLOPS表现，右图为第一轮追踪得到的流水线耗时分布。Xtrace精准定位了真实瓶颈，而其他工具给出了被扭曲的耗时分布。
:::

结果显示，Xtrace 精准定位了真正的性能瓶颈：生产者 warp 有 90%的时间在等待消费者释放 K tile 缓冲区。而 Neutrino 和 IKET 因为探针推迟了 V tile 的释放，错误地将大部分等待归因于 V tile，给 Agent 提供了错误的优化方向。

**最终四组实验都达到了相近的峰值性能 566 TFLOPS，但迭代次数差异巨大：没有追踪指导需要 85 轮，IKET 指导需要 71 轮，Neutrino 指导需要 54 轮，而 Xtrace 指导仅需 14 轮**。Xtrace 比最快的基线工具还要少 3.9 倍迭代，大幅提升了内核优化的效率。

### 7.2 闭源内核对标：反向优化提升 FA-4 吞吐量

> 第二个实验更能体现二进制级追踪的独特价值：追踪闭源的 cuDNN SDPA 内核，对比它和开源 FlashAttention-4 的执行差异，指导 Agent 优化 FA-4。现有工具都需要源码才能插桩，完全无法分析闭源的厂商内核，而 Xtrace 只需要二进制就能工作。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/26.jpg)

::: image-caption
图 10：基于cuDNN追踪的FlashAttention-4优化对比。从左到右分别是cuDNN SDPA、原版FA-4、优化后FA-4的执行 timeline，以及最终的吞吐量对比。通过对标闭源内核的优化思路，FA-4的吞吐量得到显著提升。
:::

> 通过对比两者的追踪结果，Agent 找到了四个核心优化点：

- 第一，持久化网格调度。原版 FA-4 每个计算块对应一个 CTA，分多波次执行，SM 在波次边界空闲；cuDNN 让每个 SM 常驻一个 CTA，自动取下一个计算块，消除了波次间隙。通过集群启动控制实现持久化网格，吞吐量提升 9.4%。
- 第二，全局负载均衡。持久化后，原版按组排序的计算块会导致重负载块集中，负载不均。改为全局排序，将重负载块分散到不同 CTA，吞吐量再提升 2.0%。
- 第三，长短块配对。因果掩码下块长度随索引递增，cuDNN 将长块和短块配对到同一个 CTA，平衡负载；原版是长长配对、短短配对。改为静态长短配对后，吞吐量提升 11.1%。
- 第四，末尾块去冗余等待。最后一个计算块写完后，不需要等待写入完成再释放缓冲区，原版保留了这个不必要的等待。去掉后吞吐量再提升 1.2%。

四项优化叠加后，FlashAttention-4 在 B300 上的吞吐量提升了 5.2-13.3%，四个测试形状中有三个追平了闭源 cuDNN 的性能，还有一个超出了 5.2%。

除了 cuDNN 之外，Xtrace 还可以追踪 cuBLAS、TensorRT-LLM 等闭源库的内核，追踪开销普遍在 2.1-8.3%，二进制相似度 95-98%，完全可以用于分析和对标厂商级优化。

![文章插图](/articles/2026-11-02-gpu-neutrino-iket-xtrace-19-e7c776ce/images/27.jpg)
