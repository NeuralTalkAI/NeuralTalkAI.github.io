> 尽管 CUDA 已成为通用 GPU（GPGPU）计算的主流并行计算平台和编程模型，但 :mdnice-bold-italic[CUDA 引发的 bug 模式尚未得到充分探索]。

在本文中，我们开展了首次实证研究，基于从 GitHub 上 **5 个流行 CUDA 项目中识别出的 319 个 bug，揭示了 CUDA 程序 bug 的重要类别**。

::: block-1
我们的研究结果表明，CUDA 的特定特性**可能导致诸如同步 bug 等难以检测的问题**。

为了**高效检测此类同步 bug**，我们:mdnice-bold-italic[构建了首个轻量级通用 CUDA bug 检测框架 Simulee]，该框架通过**解释相应的 LLVM 字节码** （一种低级中间代码）来**模拟 CUDA 程序执行**，并收集内存访问信息，从而:mdnice-bold-italic[自动检测 CUDA 同步 bug]。
:::

为评估 Simulee 的有效性和效率，我们开展了一系列实验，结果表明，Simulee 能够检测出 27 个研究的同步 bug 中的 20 个（覆盖率 20 / 27 ≈ 74%），此外，发现了 **26 个此前未知的同步 bug，其中 10 个已被开发者确认**。

## 关键问题

### Q1：CUDA 程序中最具挑战性的 bug 类型是什么？其本质特征和影响为何？

解答：CUDA 程序中:mdnice-bold-italic[最具挑战性的是同步 bug] （占内核函数执行阶段 bug 的 12.4%），包括:mdnice-bold-italic[数据竞争、屏障发散和冗余屏障函数]。其本质特征为：

- **数据竞争**：多线程对同一内存地址进行“读-写”或“写-写”操作，且访问顺序未被同步机制保证；
- **屏障发散**：同一线程块中部分线程到达屏障函数，而其他线程未到达，导致未定义行为；
- **冗余屏障函数**：移除后无数据竞争，但会降低性能的多余同步操作。

::: block-1
其核心影响在于：

- 难复现且修复耗时（中位数 144 天，平均 180 天）；
- 与 CUDA 架构特性深度绑定，传统 CPU-based 检测方法失效；
- 可能污染计算结果或掩盖其他 bug，增加调试难度。
:::

解答：Simulee 的:mdnice-bold-italic[核心机制基于“自动输入生成+内存模型构建+同步 bug 判定”的流水线]，实现高效全自动检测：

3. **同步 bug 判定**：
:::

其**高效性源于仅模拟运行时内存访问信息，无额外搜索开销**；全自动性体现在输入生成、模型构建及 bug 判定均**无需人工干预**。

### Q3：与现有工具相比，Simulee 在检测 CUDA 同步 bug 时的核心优势是什么？

解答：与 GKLEE 等现有工具相比，Simulee 的核心优势体现在三方面：

1. **检测范围更广**：可同时检测数据竞争、屏障发散、冗余屏障三类同步 bug，而 GKLEE 仅支持数据竞争检测；
2. **效率更高**：通过轻量模拟而非静态/动态分析，避免路径爆炸问题，复杂程序检测耗时在秒级（如某内核函数 Simulee 耗时 6253ms，GKLEE 超时）；
3. **实用性更强**：在 9 个项目中检测出 26 个未知同步 bug，其中 10 个被开发者确认，而 GKLEE 仅能检测自身测试样本中的 bug，对真实项目失效。

这些优势源于其针对同步 bug 的定向输入生成策略和基于内存模型的精准判定机制，更贴合 CUDA 并行计算的特性。

## 一、引言

CUDA[2]是一种主流的并行计算平台和编程模型，允许软件开发人员利用通用 GPU（GPGPU）计算[3]。**CUDA 的优势在于简化内存的 I/O 流以及将计算划分为子计算，因为它通过网格（grid）和块（block）的形式实现程序并行化**。此外，CUDA 支持更灵活的缓存管理，从而加速 CPU 的浮点计算。因此，CUDA 被认为在加速深度学习相关应用方面极具潜力，因为这类应用中的矩阵计算能够被高效加载。

### CPU bug 检测方法为什么不能应用于 GPU

由于 GPU 与 CPU 存在本质差异，适用于 CPU 的传统 bug 检测方法无法直接应用于 GPU。具体而言：

1. **由于 GPU 程序使用屏障（barrier）而非锁（lock）进行同步，且仅支持简单的 happens-before 关系** （描述事件执行顺序的关系，用于检测并发错误），因此传统基于锁集（lockset，通过跟踪线程持有锁的集合来检测数据竞争的方法）[15,43]和 happens-before[20,39]的 **CPU bug 检测方法，在检测 GPU 并行计算相关 bug 时已不再适用**。
2. 有观点认为，开发者缺乏 GPU 并行编程经验以及对第三方内核函数隐含假设的不了解，是导致 GPU 并行计算相关 bug 的主要原因。例如，开发者可能在未意识到一个块中最优的最大线程数仅为 256 的情况下[47]，用 512 个线程启动内核函数。然而，尽管 CUDA 编程在主流深度学习相关应用中占据主导地位，但对其并行计算相关 bug 模式的研究仍十分有限[45]。

### CUDA 程序 bug 阶段和根本原因

> 因此，全面梳理 CUDA 的 bug 模式有助于开发者理解这些模式以提高编程效率，并为研究人员提供未来研究的方向。

在本文中，我们**基于从 5 个流行 CUDA 项目中收集的 319 个 bug（这些项目总计有 15314 次提交和 110 万行代码，截至 2019 年 1 月），对真实世界中的 CUDA bug 模式开展了全面的实证研究**，选择这些项目的依据是一套强调其重要性和影响力的标准。通过这项研究，我们:mdnice-bold-italic[对 CUDA 程序的 bug 模式有了更深入的理解]。具体而言，:mdnice-bold-italic[我们从两个维度描述这些收集到的 CUDA 程序 bug：运行时阶段和根本原因]。

::: block-1
在研究中，我们识别出三个运行时阶段和五个根本原因，并得出以下发现：

1. **大多数内核函数 bug 并非特定于单指令多数据** （SIMD，一种并行处理方式，单条指令同时操作多个数据），也可能出现在其他平台上，因此可通过传统的基于 CPU 的方法检测；
2. 大**多数内存相关 bug 也可通过传统方法解决**；
3. **同步 bug 的检测** 具有重要性和**挑战性**，且超出了传统方法的适用范围。
:::

受这些发现的启发，我们进一步开发了一个:mdnice-bold-italic[系统性的轻量级 bug 检测框架 Simulee[6]，用于检测 CUDA 内核函数的同步 bug]。尽管已有一些技术（如 GKLEE[32]、CURD[40]）被开发用于检测 CUDA 程序 bug，但它们大多基于昂贵的静态/动态分析，导致不可忽视的开销，或者无法生成有效的测试用例来检测不同类型的同步 bug。

> Simulee 则会生成一个内存模型，该模型描述线程级的内存访问信息，包括线程 ID、访问顺序和操作（读/写）。

- 基于此内存模型，Simulee 会构建一个虚拟机，该虚拟机接收 CUDA 内核函数的 LLVM 字节码，用于初始化运行环境设置（包括参数、维度，必要时还包括全局内存）。
- 接下来，Simulee 应用进化编程（Evolutionary Programming，一种模拟自然进化过程的优化算法）[24]来生成诱发错误的输入，以执行 CUDA 程序的 LLVM 字节码，并收集相应的内存访问信息。
- 最后，结合 CUDA 的特性，对收集到的信息进行分析，判断是否存在同步 bug。

与其他 CUDA 同步 bug 检测方法不同（这些方法大多未实现完全自动化[40,5,23]，或仅能检测特定类型的 bug，如数据竞争[47,48]），**Simulee 能够全自动检测多种 bug 类型，包括数据竞争、冗余屏障函数和屏障发散**。此外，Simulee 的:mdnice-bold-italic[优势在于仅模拟 CUDA 程序的运行时]，无需承担额外处理（如搜索）的开销，因此:mdnice-bold-italic[比基于静态/动态分析的方法[32,42]更高效] ——后者通常需要处理庞大的搜索空间。

为评估 Simulee 在检测同步 bug 方面的有效性和效率，我们基于共 9 个项目开展了一系列实验，包括用于实证研究的 5 个项目以及另外 4 个项目（总计 2113 次提交和 12.2 万行代码）。实验结果表明，Simulee 能够成功检测出从实证研究中提取的 27 个同步 bug 中的 20 个。它还在所有 9 个项目中检测出 26 个此前未知的 bug，其中 10 个已被相应的开发者确认。此外，实验结果还显示，在:mdnice-bold-italic[检测同步 bug 方面，Simulee 比最先进的 GKLEE 更有效] ——例如，10 个已确认的 bug 中，**没有一个能被 GKLEE 检测到**。

::: block-1
总之，本文的贡献如下：

- 据我们所知，我们首次对 CUDA 程序的整体 bug 开展了广泛研究。我们的发现有助于理解 CUDA bug 的特性，并为未来的相关研究提供指导。
- 据我们所知，我们开发了首个轻量级、全自动且通用的 CUDA 同步 bug 检测框架 Simulee，它能够自动检测 CUDA 程序中多种难以手动捕捉的同步 bug。
- 我们在多种实验设置下对 Simulee 进行了评估。结果表明，Simulee 能够检测出研究项目中的大多数同步 bug。
:::

## 二、研究背景

在本节中，我们将概述 CUDA、CUDA 并行计算机制以及典型的 CUDA 同步 bug。

### CUDA 概述

CUDA 是一种并行计算平台和编程模型，它使开发者能够使用 GPU 硬件进行通用计算。CUDA 由一个运行时库和 C/C++的扩展版本组成。具体来说，CUDA 程序在 GPU 核心（即“设备端”）上执行，但在执行前需要在 CPU（即“主机端”）上分配资源。因此，开发者需要在 CUDA 程序执行后回收已分配的资源（如全局内存）。

> 综上，一个完整的 CUDA 程序包含 3 个运行时阶段：主机端资源准备、内核函数执行、主机端资源回收。

### CUDA 并行计算机制

内核函数是指在设备端运行的 CUDA 程序部分。具体来说，线程是内核函数的基本执行单元。

::: block-1
- 在物理层面，32 个线程组成一个线程束（thread warp，指一组同时执行的线程，**同一线程束内的线程通常执行相同指令**），其中所有线程在:mdnice-bold-italic[任意时刻都执行相同的语句，除非发生分支发散] （branch divergence，指线程束中不同线程因条件判断执行不同分支，导致性能下降）；
- 在逻辑层面，一个或多个线程组成一个块（block），一个或多个块组成一个网格（grid）。
:::

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/07.webp)

开发者通过设置网格和块的维度作为输入来执行内核函数。具体来说，他们将计算划分为子计算，并根据网格和块的维度将每个子计算分配给不同的线程。最终，子计算的结果可以通过归约（reduction，一种将数组元素逐步合并为单一结果的并行算法）等算法合并为整体计算的最终结果。**CUDA 内核函数并行计算机制的层次结构如图 1 所示。**

为了同步线程，CUDA 使用屏障（barrier）机制——同一线程块中的所有线程必须在屏障处等待，之后才能继续执行。在 CUDA 内核函数中，屏障函数为 `__syncthreads()`，用于同步同一线程块中的线程。当一个线程到达屏障时，只有当该线程块中的所有线程都到达同一个屏障时，它才能继续执行下一条语句。否则，程序将出现未定义行为。

### CUDA 同步 bug

> 根据我们在后续章节中的研究发现，CUDA 内核函数中主要有三类同步 bug：数据竞争（data race）、屏障发散（barrier divergence）[17]和冗余屏障函数（redundant barrier function）。

具体来说，数据竞争指的是在访问全局内存或共享内存时，CUDA 无法保证两个或多个线程的“读&写”操作或“写&写”操作的访问顺序。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/08.webp)

例如，图 2 展示了项目“thundersvm”[44]（GitHub 上一个评分较高的项目）中文件“smo-kernel.cu”的 bug 修复提交（Revision no. “febf515a82”）。从图 2 中可以看出，“if”语句向“f_val2reduce”的内存地址写入数据，而设备端的“get_block_min”函数也向同一内存地址写入数据。这个“写&写”bug 通过添加`__syncthreads`（用于同步线程间操作）得以修复。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/09.webp)

当从源代码中删除某个屏障函数后不存在数据竞争时，该屏障函数被认为是冗余的。冗余屏障函数会在时间和内存使用方面降低程序性能。例如，图 3 展示了项目“arrayfire”[8]中文件“kernel/homography.hpp”的 bug 修复提交（Revision no. “31761d27f01”）。可以看出，块维度为 1，因为从第 1 行可知，“tid”的值仅由“threadIdx.x”赋值。这意味着同一线程块中不同线程的“tid”是相同的。因此，“s_median[tid]”和“s_idx[tid]”只能被一个线程访问，导致第 4 行的屏障函数是冗余的——因为删除它后，“s_median”或“s_idx”中不会出现竞争。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/10.webp)

当一个线程块中的部分线程完成任务并离开屏障，而其他线程尚未到达屏障时，就会发生屏障发散。图 4 展示了项目“arrayfire”中文件“nearest neighbour.hpp”因屏障发散导致的 bug 修复提交（Revision no. “0ed6cccc5ff”）。可以看出，开发者通过将`__syncthreads()`语句移到给定分支外部，确保同一线程块中的所有线程在每次内核函数执行时都到达同一个屏障。否则，他们将不得不处理未定义行为。

## 三、实证研究

为了研究 CUDA 的 bug 模式，我们:mdnice-bold-italic[首先从开源 CUDA 项目中构建了一个大规模的真实世界 bug 数据集]，然后**实证分析** 了所收集的 CUDA 程序 bug 的**运行时阶段** 和**根本原因**。

### 3.1 数据收集与筛选

为了收集足够的 CUDA bug 用于研究，我们首先制定了选择开源 CUDA 项目的标准。在本文中，我们旨在选择重要且有影响力的项目，尽可能覆盖多种项目类型。我们首先通过搜索关键词“CUDA”初始化收集工作，从 GitHub 上得到了超过 12,000 个项目。接下来，我们根据星标数量和提交次数对这些项目进行排序。具体来说，**所选项目分为两组：较活跃项目（定义为提交次数超过 1000 次）和较不活跃项目（定义为提交次数在 500 到 1000 次之间）**。在每组中，我们**收集星标数量最多的一个库类型项目和一个应用类型项目**。然而，这些选定项目中没有一个将 CUDA 标记为其主要语言。因此，我们额外收集了一个将 CUDA 标记为主要语言且星标数量最多的项目。

> 最终，我们收集了“kaldi”[29]（较活跃的应用）、“arrayfire”[8]（较活跃的库）、“thundersvm”[44]（较不活跃的应用）、“mshadow”[21]（较不活跃的库）和“cuda-convnet2”[7]（主要语言为 CUDA），如表 1 所示。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/11.webp)

收集项目后，我们根据提交消息和“git diff”（用于查看代码提交前后差异的命令）结果提取 bug。具体操作如下：我们首先筛选提交，只保留提交消息中至少包含集合{“fix”，“error”，“mem”}中一个关键词的提交，这遵循了之前对其他类型 bug 的研究[46]。通过这种方式，所选提交的先前版本更有可能包含 bug。

然而，仅包含这些关键词的提交消息可能与 CUDA bug 无关。因此，在筛选后的提交消息中，我们根据其与父节点的“git diff”结果进一步筛选：如果结果中至少包含集合`{global，device}`中的一个关键词，或匹配集合`{“cuda\w+\s*[(]”，“[^<]<<<[^<]”}`中的至少一个正则表达式，则保留该提交。例如，`global`是内核函数的修饰符，`device`是可由内核函数调用的设备函数的修饰符。“cuda\w+\s*[(]”是根据主机端在执行内核函数前后准备/释放资源的信息设计的，例如“cudaMalloc((void **) &host, sizeof(int) *100)”会在执行前为内核函数分配 400 字节的全局内存；“cudaFree(&host)”会在执行后释放为内核函数分配的内存。“[^<]<<<[^<]”是根据为内核函数设置环境的场景设计的，例如“函数名<<<网格大小, 块大小>>>(参数)”。**所有这些正则表达式共同覆盖了内核函数执行的完整生命周期，从而可以覆盖整个生命周期中的所有 bug。**

我们进一步手动审查了两轮筛选后剩余的所有提交，以去除任何潜在的误报。由于手动检查繁琐且耗时，我们对所有选定的 CUDA 项目仅分析了最近的 1000 次提交（如果提交次数少于 1000 次，则分析所有提交）。:mdnice-bold-italic[最终，我们收集了总共 319 个真实世界的 CUDA bug]。

> 请注意，由于 CUDA 程序以数值计算为导向，正如以下章节所述，它们的 :mdnice-bold-italic[bug 模式呈现出收敛性]。据我们所知，这是迄今为止对 CUDA 程序 bug 最广泛的研究。

### 3.2 Bug 分类

为了理解 CUDA 程序 bug 的特征，我们从以下维度研究 CUDA 程序 bug：

#### 3.2.1 运行时阶段

运行时阶段指的是 CUDA 程序运行的生命周期阶段，包括第 2 节中提到的主机端资源准备、内核函数执行和主机端资源回收。具体来说，:mdnice-bold-italic[“内核函数执行”阶段比其他运行时阶段更容易出现 bug] ——在 **319 个 bug 中涉及 217 个（217/319=68%）**，而“主机端资源回收”占 11%（34 个 bug），“主机端资源准备”占 21%（68 个 bug）。在本文中，我们重点研究“内核函数执行”阶段，因为该阶段的程序是 GPU 特有的。

#### 3.2.2 Bug 根本原因

CUDA 程序 bug 的根本原因可分为以下五类。根本原因及其相应的 bug 症状的详细统计数据见表 2。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/12.webp)

##### a. 资源管理不当

这种根本原因指的是由于:mdnice-bold-italic[不当使用和管理内存及 GPU 而引发的 bug]。这种根本原因广泛存在于 CUDA 程序的生命周期中，除了不稳定测试（flaky test，指测试结果非确定性的测试）外，与所有 bug 症状相关。具体来说，它包括错误的设备资源分配、内存泄漏、设备调用过早重置、未授权内存访问等 bug 场景。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/12.webp)

从表 2 可以看出，**资源管理不当在所有根本原因中占 14%（31/217）**。我们还可以注意到，:mdnice-bold-italic[资源管理不当是导致崩溃（crash）的主要根本原因] （即 73%），因为资源管理不当引发的内存问题可能导致致命错误，使程序崩溃。

##### b. 非最优实现

这种根本原因指的是虽然满足功能需求但性能受损的实现。它通常与测试失败和性能低下相关，原因多种多样，例如数据类型不当、库函数过时、内核函数中的分支发散等。**非最优实现在所有根本原因中占 8%（17/217）**。

##### c. 通用错误

这种根本原因指的是在任何平台或任何编程语言中都可能出现的错误，例如范围检查错误、异常处理不当、作用域错误以及其他无法完成给定功能需求的实现。这种根本原因也广泛存在于内核函数的整个生命周期中。可以看出，**通用错误是测试失败（94%）和所有 bug（63%）的主要根本原因**。

##### d. 同步不当

这种根本原因基于三类 CUDA 特有的同步问题：数据竞争、屏障发散和冗余屏障函数。数据竞争指的是当多个线程对同一内存地址进行“读&写”或“写&写”操作时，即使在相同的环境设置下，内核函数多次执行可能返回不同的结果。屏障发散指的是同一线程块中的线程无法到达同一个屏障函数，从而导致未定义行为。冗余屏障函数指的是移除屏障函数后不存在数据竞争的情况。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/13.webp)

相关示例可参考图 2、图 3 和图 4。请注意，其他问题（如由实现不当导致的同步问题）也包含在此类中。总体而言，**同步不当在所有根本原因中占 12%（27/217）**。由于这类 bug 的性质，性能低下和不稳定测试是主要的 bug 症状，而这两者都难以诊断。

##### e. 可移植性差

这种根本原因指的是与特定平台（如操作系统、硬件）相关的问题。例如，在 vs2013 上，编译“mshadow”[21]需要在调用“half2float”之前执行一个额外步骤，否则编译会失败（“mshadow”项目的提交编号“51a8a7e3e5”）。可移植性差是所有 CUDA bug 中最罕见的根本原因（3%）。

### 3.3 Bug 影响和检测难度

我们的研究得出了关于 bug 影响和检测难度的以下发现：

#### 3.3.1 大多数内核函数 bug

并非 CUDA 特有或仅特定于单指令多数据（SIMD）架构，且可能出现在其他平台上，可通过传统方法检测。如前所述，通用错误是所有 bug 的主要类型。具体来说，对于这些并非 CUDA 特有的通用错误，设计类似于通用软件程序的测试用例是常规操作。因此，可以推断，检测这些 bug 可以使用适用于其他程序类型的传统方法，无需设计新方法[26,28]。

#### 3.3.2 大多数内存相关 bug

**可通过基于 CPU 的传统方法解决**。在本文中，与内存相关的 bug 主要指崩溃 bug 和其他由资源管理不当引发的 bug。在涉及全局内存和共享内存的 36 个 bug 中，内存泄漏（13 个）和未授权内存访问（20 个）是主要类型。

大多数 CUDA 程序依靠注入的网格或块维度来确定线程级的内存访问范围。如果存在计算错误或不当的内存访问范围，很可能会越界，导致错误的程序输出甚至程序崩溃。**为了检测此类 bug，在内核函数启动时，可以根据某条语句的线程级内存访问范围是否重叠或违反预设的合法全局内存访问范围，来判断该语句是否存在越界访问**，例如“kaldi”项目的提交编号“97cca6c0ff6”和“arrayfire”项目的提交编号“ba19743bb6”。一些基于 CPU 的方法（如[25]）可用于解决此类问题。

#### 3.3.3 同步 bug 的检测具有重要性且耗时

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/12.webp)

我们认为:mdnice-bold-italic[同步 bug 对 CUDA 程序有显著影响]，原因如下：

::: block-1
1. 同步 bug 的**发生率不可忽视** （27/217=12.4%）；
2. 这类 bug **难以复现**，会增加测试和调试的难度（如表 2 所示，这类 bug 通常:mdnice-bold-italic[导致性能问题和不稳定测试]，而这两者都**难以诊断**）；
3. 同步 bug :mdnice-bold-italic[与 CUDA 的特性紧密相关]，现有基于 CPU 的方法难以检测，而其他大多数 bug（如通用错误）可通过传统方法检测；
4. 一些同步 bug（如数据竞争）**容易污染计算结果**，甚至**掩盖其他类型的 bug**，使其更难被发现。
:::

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/14.webp)

在本文中，同步 bug 的影响通过时间成本（定义为引入 bug 的代码提交与修复 bug 的代码提交之间的时间窗口）来衡量。从图 5 可以看出，:mdnice-bold-italic[许多“不稳定测试”同步 bug 在程序中存在了很长时间（中位数为 144 天，平均为 180 天，17 个中有 11 个超过 100 天）]。因此，可以得出结论，**同步 bug 难以检测和修复**。

在所有与 CUDA 内核函数相关的根本原因中，同步不当的检测具有挑战性且耗时，需要新的检测方法。

### 3.4 Bug 检测的动机和可能性

从之前的研究可以推断，同步 bug 对 CUDA 内核函数的执行有显著影响。近年来，一些基于编译器的方法被提出用于检测 CUDA 同步 bug，如 CURD[41]、BARRACUDA[23]。通**常，这些方法在编译阶段将检测器与应用程序链接，并在运行时检查 bug**。然而，它们的局限性在于：

::: block-1
1. 并非“完全自动化”——用户必须手动提供诱发错误的输入。
2. 另一方面，如果输入不佳，同步 bug 可能不会被触发和检测到。
3. 此外，这种运行时检测需要编译过程和 GPU 计算环境，因此成本较高。
:::

其他自动同步 bug 检测方法（如 GKLEE[32]）采用静态/动态分析，在真实项目中可能导致较差的运行时性能。此外，**它们中的大多数** [33,5]**仅针对特定类型的 bug** （如数据竞争）设计，而在检测其他类型的 bug（如屏障发散和冗余屏障函数）方面**存在局限**。

> 因此，开发一种能够高效检测多种同步 bug 的新方法至关重要。

从我们的研究可以看出，传统测试用例能够捕捉除 CUDA 同步 bug 之外的各种 bug 类型。另一方面，可以推断，使用理想的测试用例，同步 bug 有望被轻松捕捉。这类测试用例应不同于仅提供运行时程序输出的传统测试用例，而应提供有助于捕捉同步事件的信息，例如确定性的线程级内存访问顺序。

**为此，考虑到直接运行 CUDA 程序难以捕捉此类信息**，一个可能的思路是:mdnice-bold-italic[设计一个虚拟机，将运行时的 GPU 编程卸载到离线的 CPU 编程中，以便更好地观察内核函数中的运行时信息，并设置机制来收集和分析这些信息]。因此，可以以完全自动化的方式生成基于上下文的诱发错误的网格和块，以检测同步 bug。

::: block-1
这一思路的可行性基于以下原因：

1. CUDA 复杂的并行计算模型允许收集各种运行时信息，而不会显著降低运行时性能；
2. 整个过程本质上是模拟运行时的 CUDA 程序并收集运行时信息，其效率有望接近直接运行原始程序。
:::

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/15.webp)

图 6 是“kaldi”项目最新版本提交中的一个示例。对于这个 bug，开发者通常很难判断这段代码是否存在同步 bug，因为常规测试用例在多次运行中可能都能通过。我们设计针对同步 bug 的特定测试用例的思路可能在这种情况下检测到同步 bug：通过为“_copy_from_mat”设置初始环境。如果将网格维度设置为 1，块维度设置为（3,2），“d_in.stride”设置为 1，“d_out.stride”设置为 1，“d_out.rows”设置为 5，“d_out.cols”设置为 5，那么线程（0,1,0）和线程（1,0,0）将在第 10 行报告“写&写”数据竞争，这表明当“d_out.stride”小于“d_out.cols”时，内核函数应立即抛出“stride 应大于 cols”的异常，而不是长时间执行所有代码。最终，:mdnice-bold-italic[自动检测此类同步 bug 的问题可以转化为自动生成诱发错误的网格和块维度的问题]。

> 只要能够**自动生成测试用例** （例如诱发错误的网格和块维度），以**收集和分析相应的内存访问信息**，就有可能:mdnice-bold-italic[设计出一个通用的自动化框架] 来检测 CUDA 同步 bug。

## 四、SIMULEE 框架

在本节中，我们介绍 Simulee——一个用于检测真实世界 CUDA 同步 bug 的自动化工具。Simulee 通常:mdnice-bold-italic[接收从 CUDA 内核函数程序转换而来的 LLVM 字节码] （一种低级中间代码），**自动生成相关的诱发错误的输入，并生成内存模型以检测同步 bug**。

> 具体来说，Simulee 由“自动输入生成”和“基于内存模型的 bug 检测”两部分组成。

- “自动输入生成”通过输入内核函数的 LLVM 字节码初始化，然后对内存访问语句（如读写语句）进行切片，并将其输入进化编程（Evolutionary Programming，一种模拟自然进化的优化算法）[24]。随后，进化编程通过迭代变异和排序维度及参数，生成诱发错误的环境设置，并将可接受的最优解传入“基于内存模型的 bug 检测”。
- 最后，“基于内存模型的 bug 检测”通过构建内存模型来检测结果。详情可参考图 7。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/04.webp)

### 4.1 自动输入生成

**生成诱发错误的输入** 【本质上等同于】:mdnice-bold-italic[生成能导致线程间内存访问冲突的输入，以提高 CUDA 同步 bug 的出现概率]。然而，如何自动生成此类诱发错误的输入仍具挑战性。一些直观的解决方案（如随机生成或面向覆盖率的生成）在有效性和效率上可能存在局限，因为它们并非专为触发内存访问冲突设计。

> 在本节中，我们将介绍 Simulee 如何以高效且有效的方式自动生成用于检测 CUDA 同步 bug 的诱发错误的输入。

#### 4.1.1 基本思路

一种高效且有效的自动生成诱发错误输入以触发 CUDA 同步 bug 的方法，意味着**在短时间内生成尽可能多的内存访问冲突**。给定第 i 个内存地址和内核函数输入（即网格、块维度及参数），f(i)定义为访问第 i 个内存地址的线程数，而 g(i)是一个函数——当第 i 个内存地址被任何线程访问时返回 1，否则返回 0。[start, end]表示内存访问范围。一个直观的目标函数 F（维度，参数）如公式（1）所示，它:mdnice-bold-italic[表示被访问的内存地址总数与内存访问线程总数的比值]：

$$
F(维度, 参数)=\frac{\sum_{i= start }^{end } g(i)}{\sum_{i= start }^{end } f(i)} \quad (1)
$$

可以得出：

- F（维度，参数）的最大值为 1，这表示任意线程对之间均无内存访问冲突；
- 反之，**F（维度，参数）越小，内存访问冲突的概率越高**。

因此，:mdnice-bold-italic[F（维度，参数）可用于优化以获取触发 CUDA 同步 bug 的诱发错误输入]。请注意，由于 F（维度，参数）是离散的，我们选择进化编程[24]作为优化方法。

#### 4.1.2 框架

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/16.webp)

“自动输入生成”的框架如算法 1 所示。首先，Simulee 随机初始化参数和维度，创建并排序用于进化的个体解（第 3 至 7 行）。在每一代中，每个解都会变异生成两个子解，并加入整个种群集合（第 8 至 14 行）。接下来，种群中的优胜者将存活至下一轮迭代（第 15 至 16 行）。一旦找到可接受的解，迭代将终止；否则，迭代完成后返回当前的最优解。

- **初始解**：随机生成初始维度和参数，并将其作为初始解传入适应度函数，用于后续进化。请注意，维度可从内核函数中提取。例如，如果一个内核函数包含“threadIdx.x”和“threadIdx.y”，则表示块是二维的。
- **适应度函数**：公式（1）被选为进化编程的主要适应度函数。具体来说，F（维度，参数）的输出是进化编程中维度和参数解的适应度得分。然而，仅通过优化 F（维度，参数）难以得出维度和参数的最优解。特别是当梯度不存在时，F（维度，参数）不可微，**因此很难从一组较差的解（例如所有 F（维度，参数）均为“1”的解）中找到最优解**。:mdnice-bold-italic[为解决这一问题，我们设计了次要适应度函数，使解按其成为最优解的可能性排序]：R（start，end）= end - start。具体而言，内存访问范围越小，内存访问冲突的可能性越高。因此，我们将主要适应度函数的输出称为主要得分，次要适应度函数的输出称为次要得分。在种群评估中，首先按主要得分排序；仅当排名靠前的主要得分均为 1 时，才按次要得分排序，以确定哪个解更可能收敛到 F（维度，参数）的最小值。
- **变异**：在 Simulee 中，解通过变异生成，每个解在一代中生成两个子解。具体来说，参数和维度在变异过程中相互独立，各自采用不同的变异策略。维度的变异策略很简单：Simulee 首先根据维度大小随机生成一个范围在-1 到 1 之间的整数向量；然后，子解的维度通过父解的维度与生成的整数向量相加得到。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/17.webp)

参数的变异策略细节如算法 2 所示。由于与内存访问相关的参数是数值，Simulee 将其视为浮点数，并在执行 f(i)时转换回实际类型。因此，每一代生成两个子解：

- 一个子解在父解参数的基础上加上一个由标准正态分布（Normal Distribution）[4]生成的随机数（$N(x)=\frac{1}{\sqrt{2 \pi}} e^{-x^{2} / 2}$）
- 另一个子解则加上一个由标准柯西分布（Cauchy Distribution）[1]生成的随机数（$C(x)=\frac{1}{\pi(1+x^{2})}$）。

我们将参数的搜索步长定义为从上述两种分布中生成的数的绝对值，其期望值如公式（2）和（3）所示。

$$
E_{正态}(x)=\int_{0}^{\infty} x \frac{1}{\sqrt{2 \pi}} e^{-x^{2} / 2} d x=0.399
$$

$$
E_{柯西}(x)=\int_{0}^{\infty} x \frac{1}{\pi\left(1+x^{2}\right)} d x=+\infty
$$

我们:mdnice-bold-italic[接下来解释为何采用上述两种分布]。从公式（2）和（3）可以看出，标准正态分布生成的步长期望值较小，这意味着：

::: block-1
- 如果最优解在附近，生成的子解很可能接近它；
- 相反，标准柯西分布生成的步长期望值较大，这意味着如果附近的解较差，生成的子解很可能跳出该区域。
:::

### 4.2 基于内存的同步 bug 检测

利用自动生成的诱发错误输入，**Simulee 的同步 bug 检测建立在构建内存模型的基础上** ——该模型描述线程级的内存访问实例。

> 基于此内存模型，Simulee 制定了一系列标准来检测数据竞争、冗余屏障函数和屏障发散三类同步 bug。

#### 4.2.1 内存模型

内核函数访问的内存模型被定义为由一组内存单元（Memory Unit）组成，每个内存单元对应一个内存地址，并由一组单元元组（Unit Tuple）构成。**单元元组被定义为三维向量空间<访问顺序，线程 ID，操作>，** 其中：

- “访问顺序”表示不同线程对关联内存地址的访问顺序
- “线程 ID”表示这些线程的索引
- “操作”指这些线程的读或写行为。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/18.webp)

图 8 展示了一个内存单元的示例，包含四个单元元组：<0, (1,0,0), 读>、<0, (2,0,0), 读>、<0, (3,0,0), 读>和<1, (3,0,0), 读>。其中，线程(1,0,0)、(2,0,0)和(3,0,0)在相同的访问顺序下读取同一内存地址，因为它们在读取前均未到达任何屏障函数。假设所有线程随后到达一个屏障函数，且线程(3,0,0)再次读取，则该线程的访问顺序将从 0 递增到 1，其他线程后续的访问顺序也会相应递增。

#### 4.2.2 内存模型构建

由于内存模型仅与屏障函数和内存访问语句相关，因此:mdnice-bold-italic[无需执行完整的 CUDA 程序，只需获取这些语句并提取/分析内存访问信息，即可检测同步 bug——即模拟 CUDA 内核函数程序的执行]。这一模拟过程通过输入自动生成的块、网格维度及传入内核函数的参数启动，然后为每个内存地址构建内存单元。

- 具体来说，该算法首先初始化块和网格维度，以及每个线程的全局内存和共享内存（第 2 至 5 行）。
- 接下来，对于每个块，初始化共享内存（第 7 行）以及全局内存和共享内存的线程级访问顺序（第 8 至 9 行）。如果仍有未终止的线程，则为所有线程基于收集的参数（如全局内存和全局访问顺序）生成相应的内存单元（第 10 至 14 行）。当没有运行的线程时，共享内存和全局内存的线程级内存单元构建完成（第 15 至 16 行）。

#### 4.2.3 基于内存模型的检测机制

内存模型的设计可用于 Simulee 检测 CUDA 同步 bug，即数据竞争、冗余屏障函数和屏障发散。

- **数据竞争**：在一般并行计算程序中，当多个线程访问同一内存地址且访问顺序相同，且至少有一个线程执行写操作时，可能发生数据竞争。在 CUDA 内核函数中，除上述一般情况外，数据竞争还发生在：

**定理 4.1**：:mdnice-bold-italic[给定同一内存单元中的两个单元元组 ψi 和 ψj，若满足以下条件，则它们之间存在数据竞争]：

- ψi[访问顺序] = ψj[访问顺序]
- ψi[线程 ID] ≠ ψj[线程 ID]
- 当 ψi 和 ψj 的线程（1）来自不同线程束，或（2）在同一线程束中对同一条语句执行“写”操作，或（3）在当前“写”操作前发生分支发散时，ψi[操作] = “写”或 ψj[操作] = “写”。

- **冗余屏障函数**：当移除某个屏障函数后未检测到数据竞争时，该屏障函数被视为冗余。在 CUDA 内核函数中，当至少有一个线程到达屏障函数时，某个单元元组的访问顺序会递增。换句话说，**一个内存单元中访问顺序相邻的两个单元元组表明存在一个屏障函数** （如图 8 所示）。因此，:mdnice-bold-italic[要检测一个屏障函数是否冗余，需收集所有相关的单元元组，并分析它们是否会导致数据竞争]。若这些单元元组之间未检测到数据竞争，则该屏障函数被判定为冗余。

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/18.webp)

**算法 5：基于内存模型的检测**输入：内存模型，访问顺序变化次数输出：数据竞争，冗余屏障

![文章插图](/articles/2025-07-20-cuda-simulee-llm-d834c677/images/21.webp)

算法 5 展示了基于内存模型检测数据竞争和冗余屏障函数的细节。对于每个内存单元，为检测数据竞争，Simulee 首先将相同访问顺序的单元元组分组；对于每组中的所有单元元组，Simulee 根据定理 4.1 检查是否有任何单元元组与其他元组存在数据竞争（第 4 至 16 行）。**为检测一个内存单元中的冗余屏障函数，Simulee 提取其访问顺序，并将访问顺序相邻的所有单元元组分组，以判断是否可能发生数据竞争** （第 18 至 22 行）。:mdnice-bold-italic[若未检测到数据竞争，则 Simulee 识别相关的屏障函数，并将其记录器加 1] （第 23 至 24 行）。最后，检查记录器总数是否与该屏障函数导致的访问顺序变化次数（构建内存模型后可获取）匹配——若两者相等，则该屏障函数为冗余（第 25 至 28 行）。

- **屏障发散**：如 4.2.2 节所述，在构建内存模型的过程中，当当前执行终止后仍存在停滞线程时，可检测到屏障发散——这表明**至少有一个线程未到达屏障函数，而其他线程已离开**。

> 综上，Simulee 方案的流程是：

::: block-1
- Simulee 首先应用进化编程生成诱发错误的网格、块维度及参数；
- 然后将这些维度和参数输入以构建内存模型，该模型提供线程级的内存访问信息；
- 最后，结合 CUDA 同步 bug 检测机制，判断是否存在 CUDA 同步 bug。
:::

## 六、有效性威胁

**外部有效性威胁主要存在于研究对象和缺陷中**。尽管所研究的项目可能无法代表所有项目的分布，但我们选择这些项目时已尽可能最大化其覆盖的 CUDA 项目特征。另一方面，通过分析提交消息提取研究 bug 的方式可能会导致一些误报。为减少这一威胁，我们**收集了大量真实 bug（319 个），远多于相关研究** （如[46]中的 175 个和[37]中的 70 个）。据我们所知，这是迄今为止规模最大的 CUDA bug 研究。

构造有效性和内部有效性威胁可能源于对 bug 症状定义的不同理解。:mdnice-bold-italic[由于立场不同，有些人可能不认为某些症状是问题]。例如，一些开发者可能对性能低下问题持容忍态度，并忽视 Simulee 在检测这些问题时的有效性。为减少这一威胁，我们**设计了两轮筛选，尽可能确保提取的 bug 确实反映了程序存在的错误**。接下来，我们手动检查描述和源代码以明确理解原因。最后，我们:mdnice-bold-italic[将提取的症状与相应的提交消息进行对比，确保每个 bug 都归入正确类别]。此外，开发者对我们提交的 bug 报告的反馈也支持了我们对 bug 的理解。

- Yang 等人[45]对 CUDA 程序的性能 bug 特征进行了实证研究；
- Burtscher 等人[12]研究了控制流不规则性和内存访问不规则性，发现这两种不规则性相互依赖且存在于大多数内核中；
- Che 等人[14]验证了 CUDA 在表达不同性能特征集方面的有效性。

一些研究者热衷于 CUDA 与 OpenCL 的对比，例如：

- Demidov 等人[19]对比了在 CUDA 和 OpenCL 上运行的一些 C++程序，发现它们在处理大规模问题时表现相当；
- 而 Du 等人[22]则研究了 OpenCL 和 CUDA 编译器优化中的差异对相关 GPU 计算性能的影响。

### CUDA bug 检测

已有多种**基于静态/动态分析的方法用于检测 CUDA bug** [32,42,23,36,31,10,16,9]。尽管这些方法可能**有效**，但它们也被认为**耗时** [40]。:mdnice-bold-italic[许多研究专注于检测特定的数据竞争 bug]。除上述工作外：

- LDetector[34]通过内存快照差异对编译器进行插桩以检测竞争；
- Boyer 等人[11]在 GPU 模拟器（而非真实 GPU 硬件）上检测数据竞争。
- 已有许多工具用于检查 CUDA 程序，例如 GKLEE[32]采用基于符号执行的验证和测试用例简化启发式方法进行 CUDA 程序检测，并通过参数化流技术[35]实现了扩展。

:mdnice-bold-italic[与 Simulee 密切相关的一项工作是基于测试放大的 bug 检测方法] [30]，该方法**通过将单次运行测试的结果与静态分析相结合，验证所有输入和交织情况**。

::: block-1
尽管将测试思想注入 CUDA 程序的思路与 Simulee 相似，但 Simulee 的优势在于：

1. 它是一个通用、全自动的 bug 检测框架，可检测多种同步类型，而[30]仅处理数据竞争且需要手动输入；
2. Simulee 只需运行与内核函数执行相关的代码，而[30]需要运行整个程序生命周期，导致开销大得多；
3. [30]存在同步输入不正确和有效性损失的问题，而 Simulee 无这些局限。
:::

## 八、结论

> 在本文中，我们对 CUDA 程序 bug 开展了广泛研究。

研究结果表明，**bug 主要出现在内核函数** 中，其中**跨平台的通用错误是主要 bug 症状**。还可观察到，:mdnice-bold-italic[同步 bug 极难处理]。

因此，我们开发了一种:mdnice-bold-italic[全自动方法 Simulee]，它**基于自动生成的运行环境**，能高效检测同步 bug。

具体而言，**Simulee 能检测出研究项目中的大多数同步 bug**，甚至成功发现了 26 个此前从未被报告/检测到的未知 bug。此外，Simulee 在有效性和效率上均优于 GKLEE。
