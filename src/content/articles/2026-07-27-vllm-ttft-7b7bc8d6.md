## 一、被忽视的一环：推理引擎配置为何重要

> 大模型**推理消耗了其全生命周期 90%以上的算力**。当每天数以百万计的请求涌向推理服务，推理阶段省下的每一度电、每一毫秒延迟，都会被请求规模放大成可观的成本与碳排放。

过去几年，优化大模型推理的主流叙事集中在两条路线。

- 一条向上卷模型本身：量化、蒸馏、剪枝轮番登场；
- 一条向下卷硬件：从 A100 到 H100，再到各类专用推理芯片。

后者是夹在模型与硬件之间的推理引擎，也就是 vLLM、Hugging Face Transformers、Ollama、llama.cpp 这类负责 token 化、KV 缓存管理、请求调度与批处理的系统软件，:mdnice-bold-italic[却长期被当作"装上去就能跑"的中性管道。其中 vLLM 凭借 PagedAttention 显存管理技术，已成为业界部署最广的推理与服务引擎，但它同时向外暴露了数十个配置项，从温度、top-p、top-k 这类采样参数，到注意力内核、前缀缓存、分块预填充这类系统级开关。]

> 问题在于，**这数十项开关该怎么拧**，业界一直没有系统答案。论文作者点出了三个现实障碍。

- 其一，**配置项之间可能相互冲突**，比如 :mdnice-bold-italic[KV 缓存与超长注意力窗口的组合就可能打架]。
- 其二，**配置效果高度依赖项目与上下文**，:mdnice-bold-italic[对话式 Agent 和代码生成需要的解码策略完全不同。]
- 其三，**不同配置会导致截然不同的运行时行为**，:mdnice-bold-italic[能耗与精度都可能大幅波动。]

而已有研究大多孤立地评估某一项优化，或者在受限场景下做小规模对比，三个关键疑问始终悬而未决：配置项之间如何交互？效应如何随任务类型变化？配置是否会影响模型输出本身？

## 二、实验设计：9000 次运行、93600 个数据点如何炼成

> 这项受控实验包含：三个配置因子、五个模型、五类任务，每个组合重复 30 次以捕捉测量波动，最终构成 60 种配置乘以 5 类任务再乘以 30 次重复，即 9000 次独立运行、93600 个测量数据点。

### 2.1 三个配置因子：恰好卡住推理流水线三段

vLLM 暴露的配置项多达数十个，全部穷举在算力上不可行。

作者定下三条筛选标准：配置项对实践者直接暴露、修改时无需触碰模型权重；作用于可能影响能耗、延迟或基准分数的运行时机制；与具体模型解耦，不直接左右模型的选择。

最终入选的三个选项，恰好分别卡住推理流水线的三个不同阶段。

| 阶段 | 说明 | 特点 |
| --- | --- | --- |
| 注意力内核 | 注意力机制在 GPU 上的底层实现。注意力计算是 Transformer 中最消耗显存带宽的环节，每个 token 需与所有历史 token 两两交互，显存与计算单元间的数据搬运次数直接影响耗时与功耗。 | FlashAttention-2 是应用最广的基线；FlashAttention-3 针对 H100 等新架构深度调优；FlashInfer 是可定制的注意力引擎，专为推理服务场景设计。 |
| 前缀缓存 | 开关型功能。多请求常共享相同提示词前缀（如系统提示词、多轮对话历史），该模块将已计算好的公共前缀 KV 缓存保留，供后续请求直接复用。 | 省去重复预填充计算，缩短预填充阶段，降低 TTFT（首 token 延迟）。 |
| 分块预填充 | 开关型功能。长提示词一次性预填充会占用大量算力，影响其他请求解码。该模块将长提示词切分为小块，分批处理，实现预填充与解码交错执行。 | vLLM 默认仅在提示词长度超过 max_num_batched_tokens（默认 8192 token）时触发分块，该阈值是理解后续“反常结果”的关键。 |

作者从 Hugging Face 按下载量筛选文本生成模型，要求参数规模在 3B 到 40B 之间以保证单卡可跑且排除微型模型，必须是开放权重、稠密架构（排除注意力内核实现不同的 MoE 模型）、指令微调版本，再从每个主流家族中选取一大一小两个代表。最终阵容覆盖 Qwen、Mistral、Llama 三大当红开源家族，参数从 3B 跨到 32B。

### 2.3 能耗、性能与精度怎么测

> 能耗测量采用经典的功率积分思路，公式为：

$$
E = W \times T
$$

其中 $E$ 是能耗，单位焦耳；$W$ 是系统运行期间的平均功率，单位瓦特，CPU 侧用 perf 采样、GPU 侧用 nvidia-smi 采样，采样率均为 1Hz；$T$ 是实验运行的时长，单位秒。

::: block-1
例如，如果一次推理任务期间 GPU 与 CPU 合计平均功率为 350 W，跑了 100 秒，那么这次任务的能耗就是 350 乘 100 等于 35000 J，即 35 kJ。**论文报告的所有能耗都只覆盖生成阶段，模型加载与预热被明确排除在外。**
:::

- 性能侧采用两个互补指标。一个是 **TTFT**，指从发出请求到收到第一个生成 token 的延迟，它决定用户感知的"响应快不快"；另一个是**请求推理时间**，即从提交到完成的端到端时长，它决定服务的整体吞吐成本。
- 精度侧，EvoEval 代码生成任务使用 pass@k 指标，其无偏估计公式为：

$$
pass@k = 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}}
$$

其中 $n$ 是为每道题生成的样本总数，$c$ 是其中通过全部测试用例的样本数，$k$ 是实际抽取用于评估的样本数，$\binom{n}{k}$ 表示从 $n$ 个样本中取出 $k$ 个的组合数。

这个公式的直觉很朴素：$\frac{\binom{n-c}{k}}{\binom{n}{k}}$ 是"抽 $k$ 个样本全军覆没"的概率，用 1 减去它，就是"至少抽中一个正确解"的概率。以作者设定为例，每道题生成 $n=5$ 个解，若其中有 $c=2$ 个正确，取 $k=1$ 时，$pass@1 = 1 - \frac{\binom{3}{1}}{\binom{5}{1}} = 1 - \frac{3}{5} = 0.4$。LongBench-v2 则采用逐题精确匹配计分，答对得 1 分、答错得 0 分、无法抽取答案时补偿 0.25 分。

统计方法上，由于大多数指标分布不满足正态假设，作者采用 ART ANOVA（对齐秩变换方差分析）这种非参数因子方差分析来检验主效应与交互效应，用 Holm-Bonferroni 方法校正多重比较的假阳性，用 Cliff's Delta 度量效应量大小。:mdnice-bold-italic[实验控制的细节也堪称严苛：所有运行以随机顺序分布在 4 台相同节点上，避免同一配置的重复扎堆在同一天同一台机器；每次评估前先做预热与 30 秒空闲功耗校准；不同数据集之间显式清空 KV 缓存与前缀缓存，保证前缀缓存配置每次从冷缓存起步]。硬件环境为 4 台配备 AMD EPYC 7513 处理器、512 GiB 内存、4 块 Nvidia A100-SXM4-40GB GPU 的节点，软件栈为 vLLM 0.10.2、FlashInfer 0.4.1、CUDA 12.2。测量稳定性数据令人安心：空闲功耗的变异系数仅 0.024，相同配置重复能耗测量的变异系数仅 0.043。

> 第一个研究问题直击要害：:mdnice-bold-italic[给定模型和任务，vLLM 配置项及其交互到底如何影响能耗、性能与精度？数据探索阶段的第一张图就透露了答案的轮廓。]

![文章插图](/articles/2026-07-27-vllm-ttft-7b7bc8d6/images/05.jpg)

::: image-caption
图 1：按模型、任务与vLLM配置分组的总能耗（kJ），散点为各次运行，黑点为中位数；配置ID中f2、f3、fi分别代表FlashAttention-2、FlashAttention-3与FlashInfer，p与c代表前缀缓存与分块预填充的开关（0关1开）。横向对比五行任务可以一眼看出，LongBench与WildChat是能耗大户，而每一列内部配置间的纵向离散程度，就是"配置杠杆"的直观长度。Qwen-4B一列尤其醒目：同一任务下不同配置的能耗带几乎不重叠，调错配置的代价清晰可见。

最直观的感受是，**模型规模决定了能耗的基本盘**，Qwen-32B 在 LongBench 上的单批能耗从 220 kJ 一路跨到 388 kJ 以上，而 Llama-3B 只在 28 kJ 到 42 kJ 之间窄幅波动。

- **但更有意思的现象藏在分布形态里**：:mdnice-bold-italic[对某些模型-任务组合，不同配置的能耗分布泾渭分明，说明配置选择影响巨大]；对另一些组合，分布大面积重叠，配置几乎无所谓。
- **配置敏感性并不随模型规模简单放大**，Qwen-32B 跨配置的最大波动约 30%，体量最小的 Llama-3B 反而达到约 39%。

::: block-1
把这些分布差异换算成中位数变化，三个指标的敏感程度依次拉开档次：能耗最高相差 38.8%，端到端延迟最高相差 80.6%，TTFT 最高相差 324.0%。:mdnice-highlight[TTFT 对配置的极端敏感，对做交互式产品的团队是一个明确信号：首 token 延迟这种直接影响用户体验的指标，恰恰是配置调优回报最高的地方。]
:::

> 综合表 3 与表 4，三条主效应结论浮出水面。

- 第一，**FlashInfer 在能耗上总体占优**，尤其在 Qwen-4B 和 Llama-8B 上效应量大而稳定。
- 第二，:mdnice-bold-italic[FlashAttention-3 往往比 FlashAttention-2 更耗电，论文在讨论部分点出了一个可能的硬件根源：FlashAttention-3 是针对 H100 架构调优的]，而本实验跑在 A100 上，新内核在新架构上的红利无法兑现。
- 第三，**前缀缓存几乎在一切场景下省电，连没有重复前缀的任务也受益**，这个反直觉现象留到第四章细说。

**延迟与 TTFT 的大方向与能耗一致，但有一个微妙的解耦**：:mdnice-bold-italic[能耗最低的 FlashInfer 并不总是最快的]，FlashAttention-3 在不少场景下延迟与 TTFT 反而更低。**省电与省时是两本账，优化目标不同，最优配置就不同**，只报单一指标的效率结论都靠不住。

::: block-1
重复下本章核心结论👀：三个配置项中，:mdnice-highlight[注意力内核与前缀缓存是真正的能耗与性能杠杆，FlashInfer 省电、FlashAttention-3 省时、前缀缓存压 TTFT 最狠]；分块预填充在默认配置与本实验负载下影响可以忽略。
:::

## 四、交互效应：配置项不能孤立评估

> 如果说主效应回答的是"哪个开关有用"，第二个研究问题回答的就是"**开关之间、开关与任务之间如何互相牵扯"。** 论文用 15 比 0 的悬殊比分给出了答案。

针对每个模型，作者分别检验三个配置因子与任务类型的交互。结果干净利落：

- **注意力内核与任务的交互、前缀缓存与任务的交互，在全部 15 项检验中全部显著**，15 比 15；
- 而**分块预填充与任务的交互是 0 比 15**，连长上下文任务 LongBench 算进去也无一例外。

### 4.1 配置与配置的联动

> **配置项之间的交互同样实打实**。注意力内核与前缀缓存的二阶交互在 25 项延迟检验中显著 10 次、在 25 项 TTFT 检验中显著 11 次。

图 2 给出了两个代表性样例：Llama-3B 跑 AssistantTraces、Qwen-4B 跑 LongBench 时，只有搭配 FlashAttention-3，开启前缀缓存才能明显降低延迟，换用其他内核后缓存的收益大幅缩水甚至变形。

![文章插图](/articles/2026-07-27-vllm-ttft-7b7bc8d6/images/08.jpg)

::: image-caption
图 2：端到端请求延迟上代表性的两因子交互效应，(a)为Llama-3B-Instruct在AssistantTraces上，(b)为Qwen-4B在LongBench上。两幅子图的折线都不平行，这正是交互效应的几何含义：前缀缓存的收益大小取决于使用哪种注意力内核。这直接否定了一种常见的调优姿势——逐个参数独立试一遍再拼起来，因为孤立评估得到的"最优"组合可能恰恰是次优的。
:::

交互的系统性证据更充分：以 FlashAttention-3 为后端时，前缀缓存在 50 个模型-任务组合中的 37 个降低延迟、38 个降低 TTFT、40 个降低能耗。这个效应并非 FlashAttention-3 独有，**用 FlashAttention-2 和 FlashInfer 时前缀缓存同样多数情况下有益，只是与 FlashAttention-3 搭配时收益最稳定**。:mdnice-bold-italic[一句话，前缀缓存的"成色"要在具体内核下检验。]

### 4.2 配置与任务的联动

> 图 3 展示了任务与注意力内核在能耗上的交互。每一幅子图代表一个模型，五条彩色折线代表五类任务。

最醒目的特征是**任务间的能耗差距远大于内核间的差距，任务才是能耗的第一决定因素**；但细看折线形状，不同任务上内核的排序并不一致，有些任务上三条线几乎贴合，内核选择无关痛痒，有些任务上则明显张开。

![文章插图](/articles/2026-07-27-vllm-ttft-7b7bc8d6/images/09.jpg)

::: image-caption
图 3：任务类型与注意力内核在总能耗（kJ）上的交互，每幅子图对应一个模型。注意EvoEval（绿色线）在多个模型上呈现FlashAttention-2偏高、FlashInfer收敛的形态，而LongBench（橙色线）的内核间差距随模型规模放大。这印证了一个实践原则：不存在脱离任务的"最佳内核"，基准测试必须覆盖自己真实的负载类型。
:::

> 前缀缓存与任务的交互则通过下面图 4 的热力图一目了然。

*图中每个格子是开启前缀缓存相对关闭的中位能耗变化量，负值代表省电*。绝大多数格子是浅绿色的负值，但幅度差异巨大，**还埋着两处"反常"。**

![文章插图](/articles/2026-07-27-vllm-ttft-7b7bc8d6/images/10.jpg)

::: image-caption
图 4：各模型与任务上开启前缀缓存相对关闭的总能耗差值（kJ），负值为省电。两处深绿色格外扎眼：Qwen-32B在LongBench上省电39.67 kJ，在WildChat上省电15.71 kJ；而Llama-3B在AssistantTraces上反而多耗3.56 kJ，是整张图中唯一明显"开缓存更耗电"的案例。
:::

- 反常1：Qwen-32B 在 LongBench 上的那个格子值得单独拆解。

LongBench 的提示词彼此没有重复前缀，缓存命中无从谈起，按理说前缀缓存开了也白开，可实测能耗大降，效应量高达 0.93。论文给出的解释颇具启发性：:mdnice-bold-italic[开启前缀缓存会改变 vLLM 的 KV 缓存块分配与显存管理路径，即便没有任何缓存命中，GPU 的显存访问模式也随之改变，进而影响能耗。这提醒我们，系统级开关的作用从来不局限于它的"名义功能"，底层资源管理策略的连锁反应可能才是主角。]

- 反常2：至于分块预填充为何全场"隐身"，答案藏在默认值里。

vLLM 默认的 max_num_batched_tokens 预算是 8192 个 token，提示词不超过这个预算，分块机制根本不会触发。五类任务里有四类的平均提示词长度远低于 8192，唯一超长的 LongBench 也只出现少数显著且效应量可忽略的案例。而 8192 又恰好是 vLLM 官方文档推荐的吞吐优化值，所以"**分块预填充无用"的结论严格来说只适用于推荐设置，不能推广到所有分块预算。**

::: block-1
总得来说，:mdnice-highlight[注意力内核、前缀缓存与任务类型之间存在全面而显著的交互（15/15），配置项之间的交互也不容忽视（延迟 10/25、TTFT 11/25）]；配置评估必须采用覆盖交互的因子化设计，并落在自己的真实负载上，孤立调参会得到次优结论。
:::

## 五、帕累托前沿：模型定大局，配置做微调

> 第三个研究问题把视角拉高：**固定任务类型，在能耗、延迟、精度三个目标之间，哪些"模型加配置"的组合是帕累托最优的？** 答案先说结论：:mdnice-bold-italic[模型选择决定大局，配置只在前沿上做微调。]

先交代一下帕累托最优的含义。一个配置如果找不到另一个配置在能耗、延迟上同时更低、精度上同时更高，它就站在帕累托前沿上，属于"谁也无法全面碾压"的非支配解。**作者在能耗与延迟上取中位数、精度上取均值，把同一配置的 30 次重复聚成一个点，再筛选非支配解。**

> 图 5 是 EvoEval 任务上能耗与精度二维投影下的帕累托前沿，紫色圆点连成前沿线，灰色点是被支配的次优解。

![文章插图](/articles/2026-07-27-vllm-ttft-7b7bc8d6/images/11.jpg)

::: image-caption
图 5：EvoEval帕累托前沿在能耗（kJ）与精度上的二维投影，覆盖各配置与所选模型；前沿在能耗、延迟、精度三目标上计算，延迟见表 5。前沿的形状几乎完全由模型排布决定：左下角是Llama-3B，中间是Qwen-4B与Llama-8B，右上角是Qwen-4B之外的精度担当Qwen-32B。同一模型内部的配置差异，只让点沿着前沿小幅滑动，改变不了所处的"段位"。

表 5 列出了各任务完整的帕累托最优配置，数字把"模型定大局"量化得清清楚楚。在 EvoEval 上，

- Llama-3B 占据低成本端，能耗 11.0 到 12.2 kJ、延迟 1.61 到 1.71 秒、精度 0.48 到 0.49；
- Qwen-4B 把精度拉高到 0.62，相对 Llama-3B 提升 27%，代价是能耗增加 33%到 47%、延迟增加 63%到 73%；
- Qwen-32B 精度最高（0.65 到 0.66），但能耗比 Qwen-4B 暴涨 223%到 232%。

从 3B 模型换到 32B 模型带来的精度跃迁，是任何配置调优都给不了的；反过来，**同一模型内部，配置只能带来几个百分点的改善**，例如 :mdnice-highlight[Qwen-32B 从 FlashAttention-3 换到 FlashInfer 省电约 3%且精度无损，Llama-8B 换 FlashInfer 省电约 7%但延迟增加 5%到 6%。]
:::

流程是：**先按任务的精度门槛选定模型段位，进入对应的帕累托区间；再按成本结构在前沿上挑点**，电费敏感就选 FlashInfer 侧的点，体验敏感就选 FlashAttention-3 侧的点，多数情况下把前缀缓存打开。

::: block-1
本章核心结论：:mdnice-highlight[没有任何配置在所有任务上占优；模型选择划定了能耗、延迟、精度权衡的主格局，vLLM 配置调优只是格局之内的局部精修，收益随任务而变，选对模型是第一决策，调配置是第二决策。]
:::

## 六、最意外的发现：推理配置竟能改变模型精度

> **整篇论文最颠覆认知的发现，藏在一组本该为零的数字里**。注意力内核与前缀缓存是纯计算层面的优化，:mdnice-bold-italic[理论上既不改变模型权重，也不改变其所近似的数学运算，基准精度理应对它们免疫。 实测却非如此。]

最清晰的案例是 Qwen-4B 在 LongBench 上的表现：

- 用 FlashInfer 时，准确率落在 0.37 到 0.43 区间；
- 换用两种 FlashAttention 内核，准确率掉到 0.20 到 0.35，组间差异达到大效应量，而两种 FlashAttention 之间差别很小。

同一模式在 EvoEval 上更弱地复现：**FlashInfer 对所有模型的精度都显著优于 FlashAttention-2**，对 Magistral-24B 之外的所有模型优于 FlashAttention-3。例外同样存在，Llama-3B 在 LongBench 上是 FlashAttention-2 拖后腿，其余两个内核难分伯仲。

前缀缓存的影响方向更加飘忽。开启缓存显著改变了六个模型-基准组合的精度：Magistral-24B 在 EvoEval 上精度下降且效应量大，Llama-8B 也小幅下降；而 Qwen-32B、Qwen-4B、Llama-3B 在 EvoEval 上精度反而上升，Llama-3B 的升幅最大。**同一个开关，在不同模型上有推有拉，毫无规律可循。**

> 一个号称"输出中性"的系统优化，为什么会改变模型输出？论文给出两种候选解释。

- 一种是统计噪声，评测集毕竟有限。
- 另一种更耐人寻味，也更有可能是真相：不同的注意力内核与缓存代码路径会重排浮点归约的顺序，而浮点加法不满足结合律。用白话说，先加 a 加 b 再加 c，和先加 b 加 c 再加 a，在浮点世界里结果会有微小差别。这些数值上不同、数学上等价的结果一路传播，就可能让采样出的 token 在某个分叉口走向另一边，一个 token 变了，后面的生成就全盘改写。

要彻底区分这两种解释，需要固定随机种子反复运行并逐 token 比对 logits，作者把这项验证留给了后续工作。

> **这个发现的分量在于，配置导致的精度漂移幅度已经堪比不同规模模型之间的精度差距**。由此推出两个对行业影响深远的结论。

- 其一，已发表的基准分数在不报告完整推理配置时不可完全复现，换一套推理栈重跑，同一模型的分数可能显著不同，从业者不能假设官方榜单成绩会原样迁移到自己的部署环境。
- 其二，**凡是以精度为评估对象的实证研究，都应把完整的推理引擎配置写进实验协议**，这也与软件工程领域既有的基准报告规范相呼应。

::: block-1
重复下本章核心结论👀：推理配置不是输出中立的——注意力内核与前缀缓存能在部分模型-基准组合上造成统计显著、幅度可观的精度漂移，浮点归约顺序差异是最可能的机理；:mdnice-highlight[推理栈应当被当作一等实验变量来对待]。
:::

## 七、实践指南、局限与结语

> 把 93600 个数据点蒸馏成**可执行的决策**，论文在讨论部分给出了一份面向部署者的行动清单，同时也坦承了结论的边界。

先看行动清单，五条建议按优先级排列：

| 行动建议 | 说明 |
| --- | --- |
| 节能优先就把 FlashInfer 设为默认内核，压延迟优先就选 FlashAttention-3；两个目标都要，就在帕累托前沿上挑折中点，而不是按单一指标拍脑袋。 | 节能与低延迟目标存在权衡，需基于帕累托前沿选择综合最优配置，避免单一指标决策。 |
| 前缀缓存值得默认开启，它能压 TTFT、多数情况下同时省电省延迟，但务必在自己的任务类型上验证，Llama-3B 跑 AssistantTraces 这种反例真实存在。 | 前缀缓存通常有益于 TTFT、功耗与延迟，但存在任务依赖性，需在具体场景（如特定模型与 trace）中实测验证。 |
| 分块预填充在默认 8192 token 预算下可以放心保持默认，本实验未观察到有意义的影响；但如果你的负载以超长提示词为主且调低了批处理预算，结论需要重新检验。 | 在标准预算（8192 token）下分块预填充影响可忽略；超长提示或降低批处理预算时，其效果需重新评估。 |
| 配置要联合评估，注意力内核与前缀缓存的交互在延迟和 TTFT 上大面积显著，逐个孤立调参再拼装的做法已被实验证伪；未来的基准评测也应采用因子化设计。 | 注意力内核与前缀缓存存在强交互效应，需联合调优；孤立调参不可靠，基准评测应采用因子化实验设计。 |
| 发布或引用任何精度数据时，连同模型版本一起报告完整的推理栈配置，否则数字无法复现。 | 精度数据必须附带完整推理栈配置（含模型版本、内核、缓存策略等），确保结果可复现与可比。 |

> 再看结论的**适用边界**，作者的态度相当克制。

- 硬件上，**全部实验跑在 A100-40GB 上，而 FlashAttention-3 为 H100 调优，换平台后内核排序可能重排**。接口上，实验使用 vLLM 离线批处理接口，HTTP 服务模式下的异步请求、调度与缓存行为可能不同。
- 测量上，**nvidia-smi 在 A100 上只能对约 25%的运行时间采样、其余靠插值，极端尖峰负载下能耗误差可达 65%，** 所以论文中的能耗值应理解为估计值，好在 30 次重复与 0.043 的变异系数保证了相对比较的稳健。
- 覆盖面上，精度:mdnice-bold-italic[只评测了 EvoEval 与 LongBench-v2 两个有标准答案的数据集，MoE 架构、多卡部署、更多 vLLM 参数都留给了未来工作。]

即便如此，这项研究的方法论价值已经立住了。

::: block-1
它把"推理引擎配置"从部署文档里的附录，提升为与模型选择、任务类型并列的一等变量，并用 9000 次运行证明：:mdnice-bold-italic[能耗、延迟、精度三个目标彼此纠缠，配置项之间彼此纠缠，配置与任务之间也彼此纠缠。面对这样一个三重纠缠的系统，唯一可靠的导航方式就是论文示范的这套打法——受控的全因子实验、多目标的帕累托分析、以及对默认配置永不轻信的态度]。
:::
