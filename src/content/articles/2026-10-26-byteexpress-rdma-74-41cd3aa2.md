## 一、为什么 RDMA 落地不是“换个协议”这么简单

> 在很多技术认知中，RDMA 的优势来自硬件卸载，只要把 TCP 换成 RDMA，就能自动获得低延迟、高吞吐、低 CPU 占用的收益。但真实生产环境的复杂度，远非点对点带宽测试所能覆盖。

字节跳动的在线推荐、搜索与广告业务，全部基于参数服务器架构构建，这也是当前工业界大规模分布式推理与训练最主流的部署范式。

### 1.1 参数服务器架构的通信特征

> 参数服务器架构将系统分为两类核心角色：工作节点与参数服务器节点。模型参数被切分为多个分片，通过哈希等方式分散存储在不同的参数服务器上。

- 推理场景下，排序节点需要从多个参数服务器拉取所需的模型参数，完成计算后返回排序结果；
- 训练场景下，训练节点除了拉取参数，还需要将计算得到的参数更新推送回参数服务器。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/05.jpg)

::: image-caption
图 1：参数服务器架构示意图。图中展示了排序/训练节点与多台参数服务器的交互关系，排序/训练节点通过拉取/推送操作与存储不同参数分片的参数服务器进行通信。这种架构天然带有扇出与扇入的流量特征：一个用户请求会拆分为多个并发子请求发往多台参数服务器，多个节点的响应又会汇聚到同一台工作节点，形成典型的incast流量模式。
:::

> 这种架构带来了三个鲜明的通信特征，也是 RDMA 落地必须面对的核心约束：

- 消息尺寸高度可变。请求与响应的大小随用户属性、模型结构变化，范围从几千字节到几兆字节不等，不存在固定的消息模板。
- 并发连接数量庞大。每个工作节点需要与大量参数服务器建立逻辑连接，同时处理多个用户请求的异步 IO，逻辑连接数远超物理节点数量。
- 尾延迟直接决定业务体验。一次推理请求或一轮训练迭代的完成时间，取决于最慢的那个子请求，单点的延迟抖动会被放大到整个业务链路。

### 1.2 硬件 RDMA 的能力边界

> RDMA 通过专用网卡实现传输层硬件卸载，支持用户态直接操作硬件，绕过内核网络栈，理论上可以消除拷贝开销与调度延迟。**但硬件卸载的能力存在明确边界，很多生产环境的问题无法通过硬件本身解决，具体体现在三个方面。**

| 能力边界维度 | 具体说明 |
| --- | --- |
| 传输可靠与业务语义可靠 | RC 传输模式可以保证消息按序、无丢失地送达对端，但对端节点宕机、服务进程挂死或业务副本不可用时，硬件层面的重传机制完全无效，只会无意义地消耗重试次数，最终触发传输层错误。 |
| 拥塞控制与突发 incast | DCQCN 等硬件拥塞控制算法基于网络拥塞反馈调整发送速率，但面对大量并发流同时涌向一个节点的极端 incast 场景，硬件的反应速度不足以避免交换机缓存耗尽，进而触发 PFC 暂停，甚至引发 PFC 风暴扩散。 |
| 硬件资源容量 | RNIC 的 QP 上下文缓存、内存区域缓存都有容量上限，当活跃连接数或注册内存区域超过缓存容量时，网卡需要通过 DMA 从主机内存拉取上下文，反而会引入额外开销，抵消硬件卸载的收益。 |

### 1.3 生产级落地的三大核心命题

> 面对这些约束，字节跳动的 RDMA 落地需要同时解决三个核心命题：

- 如何支持可变尺寸消息的零拷贝传输，同时兼容应用层灵活的 buffer 生命周期管理，不能为了 RDMA 强制改造业务的内存模型。
- 如何在海量并发连接下保障 RDMA 资源的高效利用，既不触发硬件缓存溢出，也不产生驱动层的锁竞争，同时应对突发 incast 流量。
- 如何在硬件传输可靠的基础上，构建完整的服务可用性体系，在节点故障、链路异常时快速恢复，不影响业务的正常运行。

::: block-1
总之，RDMA 的硬件能力只是基础，真正的落地挑战在软件层。:mdnice-bold-italic[简单替换传输协议非但无法兑现全部收益，还可能引入可扩展性与可用性的新风险。ByteExpress 的核心设计思路，就是在保留 RDMA 硬件卸载优势的前提下，通过软件层的跨层协同设计，补齐硬件能力的短板。]
:::

## 二、ByteExpress 整体架构：RPC 与硬件 RDMA 之间的中间层

> 大规模生产系统的技术升级，必须兼顾兼容性与收益。如果为了引入 RDMA 就要彻底重构上层业务的通信接口，落地成本与风险都会指数级上升。**ByteExpress 的设计选择，是作为中间层嵌入现有通信栈，对上保留原有的 RPC 接口，对下对接硬件 RDMA。**

ByteExpress 没有让业务直接操作 RDMA 原语，而是在现有 Archon RPC 框架与硬件 RNIC 之间，构建了一层完整的软件通信抽象。上层应用继续通过 Archon 发起 RPC 调用，Archon 将消息传递给 ByteExpress，再由 ByteExpress 转化为 RDMA 操作下发给硬件。

### 2.1 分层通信栈的职责划分

> 整个通信栈从上到下分为三层，各层职责边界清晰，避免了跨层的逻辑耦合，其完整结构如图 2 所示。

| 分层 | 职责 |
| --- | --- |
| Archon RPC 层（最上层） | 负责业务级的通信语义，包括请求封装、超时重试、副本选择、负载均衡等；完全保留 TCP 时代的设计，业务代码无需任何修改，即可透明切换到 RDMA 传输。 |
| ByteExpress 核心层（中间层） | 向上提供类 socket 的端点抽象，向下管理 RDMA 硬件资源，负责内存分配、消息分片、连接调度、流控与拥塞控制等功能。 |
| 硬件 RNIC 层（最底层） | 提供 RC 传输模式的硬件卸载，包括传输可靠性保障、DCQCN 拥塞控制等硬件原生能力。 |

### 2.2 核心抽象：Socket 与 Engine

> ByteExpress 设计了两个核心抽象，用来解耦逻辑连接与物理传输资源，业务视角的通信端点与硬件视角的传输资源被明确分开。

- Socket：代表一条逻辑连接，对应 Archon 的一条 RPC 通道，和 TCP Socket 类似，是业务视角的通信端点，每条 RPC 通道对应一个 Socket 实例。
- Engine：每个 Engine 对应一个 RC QP，以及配套的传输状态、工作请求链与接收资源；发往同一个远端地址的多个 Socket 可以共享同一个 Engine，由调度器协调它们的传输顺序。

**这种设计的核心价值是 QP 复用。** 在 TCP 模式下，每个逻辑 Socket 对应一条独立的 TCP 连接；**而在 ByteExpress 中，发往同一目标的所有逻辑 Socket 共享同一个物理 QP，大幅减少了 QP 的总数量，降低了 RNIC 的连接状态压力。**

当然，共享 QP 会带来队头阻塞的问题：一个 Socket 的大消息会阻塞同 Engine 上其他 Socket 的小消息。**ByteExpress 通过消息分片机制解决这个问题，将大消息拆分为多个小分片，调度器在不同 Socket 之间轮询发送分片，从而实现逻辑连接之间的调度公平性。**

::: block-1
回顾一下，:mdnice-highlight[ByteExpress 的架构本质是逻辑连接与物理传输解耦。上层业务保持原有的并发通信模型不变，底层通过复用物理 RDMA 资源降低硬件开销]，中间通过软件调度平衡共享带来的公平性问题。这种设计既控制了落地改造成本，又充分发挥了 RDMA 的硬件优势。
:::

## 三、高性能通信引擎：零拷贝的核心是内存所有权跨层协同

> 零拷贝是 RDMA 最广为人知的优势，但很多人对零拷贝的理解停留在数据不经过内核拷贝的层面。实际上，要实现真正端到端的零拷贝，核心是解决应用层与通信层之间的内存所有权问题，而不仅仅是绕过内核。

如果应用层的 buffer 没有注册 RDMA 权限，通信层就必须把数据拷贝到注册好的 buffer 里再发送，接收端同理，这就会产生用户态内部的拷贝，抵消 RDMA 的收益。ByteExpress 通过自研的 bemalloc 内存分配器，实现了应用层与通信层的注册内存共享，配合消息传输机制的优化，达成了真正的端到端零拷贝。

### 3.1 传输协议选型：为什么选择 RC 而非 UD

在具体讲解内存管理之前，首先需要明确底层传输协议的选型。RDMA 有三种主流传输模式：RC、UC、UD，不同模式的特性差异很大。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/06.jpg)

::: image-caption
表 1：RDMA传输模式对比。该表对比了RC、UC、UD三种传输模式的SEND/RECV支持、内存读写与原子操作支持、面向连接特性、可靠性与最大消息尺寸。其中RC是面向连接的可靠传输，最大支持2GB单消息；UD是无连接的数据报，单消息最大仅支持MTU大小。
:::

业界很多 RDMA RPC 框架选择 UD 模式，因为它无需维护连接状态，适合小消息高并发场景。但字节的推理训练负载包含大量大于 MTU 的消息，如果使用 UD，就需要在软件层实现分片、重组、重传等逻辑，相当于把硬件卸载的工作又拿回软件做，得不偿失。

ByteExpress 通过实测验证了这个判断。在不同链路速率与 MTU 配置下，RC 与 UD 的吞吐量表现存在明显差异：

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/07.jpg)

::: image-caption
表 2：不同链路速率与MTU下RC与UD的吞吐量对比。测试使用ib_send_bw工具，结果显示在25Gbps链路、1024字节MTU下，两者吞吐量接近；但在100Gbps链路、1024字节MTU下，RC可达92.26Gbps，UD仅为48.29Gbps；即使提升MTU到4096字节，200Gbps链路下RC仍能达到191.36Gbps，UD仅为114.70Gbps。
:::

**从测试结果可以看出，随着链路速率提升，UD 的包处理速率会成为吞吐量瓶颈。** 对于字节的大消息为主的负载，RC 的硬件级大消息支持与可靠性保障，综合收益远高于 UD 的无连接优势。:mdnice-bold-italic[最终 ByteExpress 选择 RC 作为底层传输模式，将连接管理的复杂度放在软件层解决。]

### 3.2 bemalloc：RDMA 感知的动态内存分配器

> 要实现零拷贝，首先要解决的问题是：应用层可以方便地分配 RDMA 注册内存，不需要关心注册、注销的细节，同时分配性能接近通用内存分配器。

业界常见的做法是预先分配一块固定的 RDMA 内存池，应用从池子里申请内存。:mdnice-bold-italic[但这种方式的问题是，固定池的大小难以适配动态的业务负载，而且内存的生命周期管理很不灵活]。**ByteExpress 的思路是，在通用内存分配器的基础上，增加 RDMA 内存注册能力，让 RDMA 内存的使用和普通内存一样简单。**

bemalloc 基于 rpmalloc 构建，后者是一个轻量高性能的通用分配器，代码量约 3000 行，支持线程本地缓存与跨线程释放。bemalloc 在 rpmalloc 的块分配与块释放回调中，分别插入内存注册与注销的逻辑：当分配器从操作系统申请大块内存时，自动调用 ibv_reg_mr 完成 RDMA 注册；当大块内存被释放回操作系统时，自动注销对应的内存区域。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/08.jpg)

::: image-caption
图 3：bemalloc接口示例。代码展示了bemalloc的核心接口：初始化设备上下文、分配注册内存、O(1)获取内存区域元数据、释放内存。整个接口和普通malloc完全一致，应用层无需感知RDMA注册的细节。
:::

> 这种设计带来了三个核心优势：

- 第一，接口兼容通用分配器，应用层改造成本极低，只需要把对应网络数据的内存分配替换为 bemalloc 即可。
- 第二，注册开销被摊销。每次注册的是 4MB 左右的大块内存，块内的多次小分配共享一次注册成本，稳态下内存池稳定后，不再有注册注销操作。
- 第三，支持灵活的内存生命周期。应用可以持有接收得到的 buffer，传递给其他线程处理，处理完成后再释放，不需要和接收环的生命周期绑定。

### 3.3 零拷贝消息传输机制

> 有了 bemalloc 的内存基础，ByteExpress 实现了收发双向的零拷贝传输。

- 接收路径上，RNIC 直接将数据写入按需分配的注册 buffer 中，通信层将 buffer 的所有权直接移交给应用线程，应用处理完成后自行释放。整个过程没有任何数据拷贝，buffer 的生命周期完全由应用控制，不需要和固定接收环绑定。
- 发送路径上，应用层直接用 bemalloc 分配待发送的 payload，这些内存天然具备 RDMA 权限，RNIC 可以直接读取发送，不需要通信层再做一次拷贝。

对于大消息，ByteExpress 采用单边 WRITE 操作进行传输，流程分为三步：

1. 发送方通过 SEND/RECV 交互，向接收方请求目标 buffer 的地址与远程内存密钥。
2. 接收方用 bemalloc 分配目标 buffer，将地址与 rkey 返回给发送方。
3. 发送方将消息拆分为分片，通过 RDMA WRITE 依次写入接收方的目标地址，最后一个分片使用 WRITE_WITH_IMM 通知接收方消息完成。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/11.jpg)

::: image-caption
图 6：大消息传输流程示意图。发送方先发送写请求携带长度，接收方分配buffer后返回地址与rkey，发送方分多个分片执行WRITE操作，最后一个分片用WRITE_WITH_IMM通知接收方。
:::

::: block-1
**这种设计的一个关键细节是，使用 WRITE_WITH_IMM 的完成事件来通知接收方**，而不是通过在 payload 里写标志位轮询。:mdnice-highlight[原因在于，RDMA 内存区域通常使用松弛内存序，写入的顺序没有保障，单独轮询标志位无法确认前面的 payload 数据已经全部可见。] 而完成事件的语义可以保证，之前的所有写入都已经对主机可见，避免了内存序带来的一致性问题。
:::

### 3.4 接收信用流控

> RDMA 的双边操作（SEND、RECV）需要接收方预先发布接收请求，如果接收请求耗尽，发送方会触发 RNR（接收方未就绪）错误，导致重传甚至连接断开。WRITE_WITH_IMM 同样会消耗接收请求。

为了避免 RNR，ByteExpress 设计了接收信用流控机制，灵感来自接收方驱动的传输协议。每个发送方维护对端的可用接收请求信用数，建立连接时双方交换初始信用值。发送一个 SEND 或 WRITE_WITH_IMM 消耗 1 个信用，普通 WRITE 操作不消耗信用。信用不足时，发送方等待，不再继续发送。

接收方批量补充接收请求。每消耗 k 个接收请求，就批量补充 k 个，同时给对端发送信用更新消息。k 的取值为接收队列深度的一半，这样在信用更新消息传输的过程中，还有一半的接收容量可以使用，避免出现空档。

::: block-1
整体看下来，零拷贝并非单一的技术点，而是一整套从内存分配到传输流程的协同设计。:mdnice-highlight[bemalloc 解决了注册内存的动态分配与所有权转移问题，大消息 WRITE 机制避免了中间拷贝，接收信用流控保障了传输的稳定运行]。三者结合，才实现了真正高效、灵活的端到端零拷贝通信。
:::

## 四、规模化扩展：连接、接收容量与突发流量的分层管控

> 单点性能优秀不代表大规模部署依然高效。当节点规模从几十台扩展到几万台，并发连接数、多线程竞争、突发 incast 流量都会成为新的瓶颈。**ByteExpress 的可扩展性设计，核心是分层管控不同维度的资源，让每一层的控制机制都有明确的保护目标。**

RDMA 的规模化扩展需要解决三类问题：一是连接状态过多导致的硬件缓存压力，二是多线程 IO 导致的驱动层锁竞争，三是突发 incast 导致的网络拥塞与 PFC 触发。ByteExpress 分别用 QP 复用、线程域资源隔离、软件发送窗口三种机制对应解决，形成了分层的资源管控体系。

### 4.1 QP 复用与消息分片：平衡连接开销与调度公平性

> RNIC 的 QP 上下文缓存容量有限，当活跃 QP 数量超过缓存大小时，网卡需要频繁从主机内存 DMA 拉取上下文，性能会急剧下降。ByteExpress 通过 Socket 共享 Engine 的方式，将发往同一目标的所有逻辑连接复用到同一个 QP 上，大幅降低了 QP 总数量。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/12.jpg)

::: image-caption
图7：RDMA引擎：一个QP、接收资源，以及一条工作请求链，该链划分为进行中、待处理和空闲表项。
:::

QP 复用带来的队头阻塞问题，通过消息分片来缓解。大消息被拆分为固定大小的分片，调度器在活跃 Socket 之间轮询，每次最多发送一个分片。这样一来，小消息不会被单个大消息长时间阻塞，调度的公平性得到保障。

分片大小是一个需要权衡的参数：分片越小，调度粒度越细，公平性越好，但每个分片的开销占比越高，吞吐量越低；分片越大，吞吐量越高，但队头阻塞越严重。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/13.jpg)

::: image-caption
图 10：吞吐量与分片大小的关系。25G网卡下，约2KB的分片就可以打满链路；100G网卡下，需要8KB以上的分片才能接近线速。
:::

ByteExpress 根据不同的链路速率选择合适的分片大小，在吞吐量与调度公平性之间取得平衡。在轮询调度下，若有 n 个活跃 Socket，最大分片大小为 S，则一个 Socket 两次调度之间，最多会有 $(n-1)S$ 字节的其他 Socket 数据被发送，这是调度引入的延迟上界。

论文通过测试验证了分片的效果：当一个 Engine 上同时存在小流与大流时，4KB 分片可以让小流的延迟远低于不分片的情况，有效缓解了队头阻塞。

### 4.2 线程感知的资源管理：消除驱动层锁竞争

> 在多线程 IO 场景下，仅仅做到应用层数据结构无锁是不够的。ByteExpress 最初将每个 Engine 绑定到一个 IO 线程，应用层的数据结构没有锁竞争，但实测发现，当 QP 数量超过 64 后，512 字节消息的速率急剧下降。

经过性能分析定位，瓶颈出现在 ibv_post_send 内部的自旋锁上。不同线程的 QP 共享了驱动内部的全局结构，即使应用层做了线程隔离，驱动层依然存在锁竞争。

为了解决这个问题，ByteExpress 引入了线程域（Thread Domain，TD）。每个 IO 线程分配一个独立的线程域，该线程管理的所有 QP、CQ 等资源都关联到对应的线程域上。线程域可以让驱动层知道这些资源只会被单个线程访问，从而优化内部实现，去掉不必要的全局锁。

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/14.jpg)

::: image-caption
表 3：ByteExpress的RDMA资源分配表。其中QP每个远端地址一个，接收队列默认每个QP一个，共享接收队列模式下每个线程一个，完成队列与线程域每个线程一个，内存区域每个注册块一个，保护域全局一个。
:::

除此之外，每个 IO 线程还共享一个完成队列，所有该线程管理的 QP 的完成事件都上报到同一个 CQ，线程批量拉取完成事件，再根据 QP 编号分发给对应的 Engine。这种设计减少了 CQ 的总数量，同时提升了批量处理的效率。

对于接收队列，ByteExpress 还支持共享接收队列（SRQ）模式，同一个 IO 线程下的所有 QP 共享一个接收缓冲池。这种模式可以提升缓冲区的利用率，但无法再使用精确的对端信用流控，需要通过更大的队列深度、RNR 超时重试来缓解接收耗尽的问题。两种模式各有优劣，对应不同的业务场景。

### 4.3 软件发送窗口：应用级的 incast 流量管控

> incast 是分布式训练场景最棘手的网络问题之一。大量训练节点同时向同一台参数服务器推送参数，或者一台训练节点同时从多台服务器拉取参数，聚合流量很容易超过交换机的缓存容量，触发 PFC 暂停，严重时甚至引发 PFC 风暴，导致整个集群网络瘫痪。

硬件层面的 DCQCN 拥塞控制，基于 ECN 标记反馈调整发送速率，但它的反应速度跟不上突发极强的 incast 场景。字节的生产训练集群中，仅靠硬件 DCQCN 无法避免持续的 PFC 暂停，尾延迟表现甚至不如 TCP。

::: block-1
ByteExpress 的解决方案是在应用层增加一个软件发送窗口，限制每个 Engine 的在途字节总数。这个窗口和 TCP 的拥塞窗口不同，它并非自适应算法，而是根据业务负载配置的固定上限，和消息分片机制配合，控制注入网络的数据总量。
:::

这里需要明确几个机制的不同职责：

- 软件发送窗口：限制单个 Engine 的在途字节数，从源头控制突发流量
- DCQCN：硬件级的速率控制，根据网络拥塞反馈调整发送速率
- PFC：链路级的背压机制，作为最后防线避免丢包

三者是互补关系，而非替代关系。软件窗口在最上层做流量整形，DCQCN 在硬件层做速率调整，PFC 在链路层做兜底保护。

> 论文通过合成 incast 场景测试了软件窗口的效果：

![文章插图](/articles/2026-10-26-byteexpress-rdma-74-41cd3aa2/images/15.jpg)

::: image-caption
表 4：不同软件窗口大小下，触发PFC前的服务器数量。无软件控制时，63台服务器就会触发PFC；16KB窗口时提升到273台；8KB窗口时567台；4KB窗口时可以支持1218台服务器而不触发PFC。

**测试结果清晰地表明，通过软件层限制在途数据量，可以大幅提升 incast 场景的规模上限，从根源上减少 PFC 的触发。** 当然，固定窗口的大小需要根据业务的消息尺寸、incast 规模来配置，适合流量模式相对稳定的训练负载。

::: block-1
总之，*:mdnice-highlight[规模化扩展的核心是分层管控，各负其责。QP 复用解决连接状态开销，线程域解决驱动层锁竞争，软件发送窗口解决 incast 突发拥塞]。三个机制分别对应不同维度的资源瓶颈，共同支撑了万级节点规模的稳定运行。
:::

## 五、服务可用性：传输可靠不等于服务不中断

> 很多人对 RDMA 的可靠性存在误解，认为 RC 是可靠传输，所以系统就是可靠的。实际上，传输可靠只是最基础的一层，节点故障、链路异常、服务副本不可用，这些真实生产环境的故障，都不是硬件传输层能够解决的。

**ByteExpress 的可用性设计，遵循一个核心原则：传输层只负责传输的可靠性，服务级的恢复交给上层 RPC 框架**。ByteExpress 向 Archon 提供连接状态、故障检测等信号，由 Archon 基于业务语义做出恢复决策，包括重试、切换副本、回退 TCP 等。

### 5.1 传输可靠与服务恢复的边界

> RC 传输模式可以保证：只要连接正常，消息就会按序、无重复、无丢失地到达对端。但如果出现以下情况，传输层本身是无能为力的：

- 远端节点宕机、断电或者内核崩溃
- 远端服务进程异常退出，没有正常关闭连接
- 网络路径出现持续性故障，重传次数耗尽
- 业务副本下线维护，服务不可用

这些场景下，硬件层面的重传只会白白消耗时间，最终触发连接错误，而无法自动切换到其他可用的服务副本。因为 RNIC 根本不知道业务有多个副本，也不知道该切换到哪里。

::: block-1
所以，:mdnice-highlight[ByteExpress 没有试图在传输层实现完整的故障恢复，而是保留了 Archon 原有的 RPC 级可用性机制，同时补充 RDMA 特有的连接监控与故障检测能力]，让上层可以更快地感知故障、做出决策。
:::

### 5.2 多层级的故障恢复机制

> 整个可用性体系分为三层，从底层到上层依次是连接监控、RPC 级恢复、TCP 回退。

**第一层是连接监控**。ByteExpress 通过两种方式检测连接故障：

- 一是通过完成队列的错误事件感知传输层错误；
- 二是发送保活消息，每个 Engine 周期性地向对端发送递增的序列号，如果对端的序列号在超时时间内没有更新，就判定连接故障，进入错误状态，通知上层。

保活机制可以检测到远端宕机、进程挂死等静默故障，避免连接长时间挂死，拖累业务请求。保活的间隔与超时时间需要根据集群的网络延迟与调度延迟来配置，避免误判。

**第二层是 RPC 辅助恢复**。Archon 本身就有独立的连接超时与请求超时机制，比如连接超时 10ms，请求超时 40ms。请求超时后，会根据策略进行概率重试，容忍瞬时故障。

当检测到连接故障后，Archon 会按照优先级尝试不同的恢复手段：

1. 尝试通过网卡的端口亲和性切换连接路径，绕开故障路径
2. 如果重连失败，选择其他 mini-pod 里的就近副本
3. 如果 RDMA 通信全部不可用，自动回退到 TCP 传输

**第三层是 TCP 回退**。这是最终的兜底机制，当 RDMA 网络出现大面积异常时，业务可以无缝切换到 TCP 栈，保障服务不中断。根据论文中的部署经验，TCP 回退可以在一分钟内恢复高吞吐量。

除此之外，Archon 还有故障节点隔离机制。如果一个节点在 5 分钟内出现超过 30 次连接故障或者 50 次请求故障，就会被加入排除列表，暂时不再向它发送请求，由其他副本承接流量，工程师可以离线排查问题。

### 5.3 部署层面的容灾保障

> 除了软件层面的机制，部署层面也做了对应的容灾设计。

排序节点与参数服务器都跨多个数据中心部署，同一个数据中心内，参数服务器的副本分布在不同的 mini-pod 中，每个副本都包含完整的参数分片。mini-pod 之间的网络支持无损 RDMA 配置，单个 mini-pod 的网络故障不会影响其他副本。

在部署前，还会用 Collie 工具对 RDMA 机器进行性能测试，识别性能异常的节点，避免带病上线。同时部署了基于看门狗的 PFC 风暴遏制机制，防止局部故障扩散为集群级事故。

::: block-1
回顾一下，:mdnice-highlight[高可用的核心是边界清晰，多层兜底。传输层只做传输该做的事，服务恢复交给理解业务语义的 RPC 层，再加上部署层面的副本容灾与 TCP 兜底]，共同构建了完整的可用性体系，这也是 RDMA 能够支撑核心在线业务的关键前提。
:::

## 六、生产环境实测：推理与训练的双重性能收益

> 所有的设计最终都要靠生产数据说话。ByteExpress 已经在字节跳动的生产环境部署超过两年，覆盖数十个数据中心集群，支撑头条、抖音、西瓜视频等核心业务的推理与训练。

论文分别从在线推理与离线训练两个场景，给出了与 TCP 基线的对比数据，所有数据都来自真实生产负载，具备很高的参考价值。

### 6.1 在线推理场景：延迟与 CPU 双重收益

> 推理场景的测试集群包含 300 台参数服务器与 124 台排序节点，每台机器配备 25Gbps Mellanox ConnectX-5 网卡，对比的基线是生产环境在用的 Linux 内核 TCP/IP 栈。

> 训练场景的测试集群包含 124 台参数服务器与 346 台训练节点，同样配备 25Gbps ConnectX-5 网卡。训练节点反复执行参数拉取与推送操作，形成持续的 incast 流量。

这里对比了三组配置：TCP 基线、仅硬件拥塞控制的 RDMA、硬件拥塞控制加软件发送窗口的 RDMA，核心指标如表 7 所示。

整体看下来，ByteExpress 的生产收益是全面且扎实的。:mdnice-bold-italic[推理场景实现了延迟与 CPU 的双降，训练场景实现了尾延迟的大幅优化与 PFC 的消除。这些数据充分证明，经过合理的软件层设计，RDMA 完全可以在大规模生产环境中兑现其性能承诺。]
:::

## 七、落地经验总结与行业启示

> 这篇论文最大的价值，不在于提出了某个突破性的算法，而在于分享了字节跳动两年多的 RDMA 规模化生产落地经验。这些从真实业务中踩坑总结出来的经验，对于所有想要落地 RDMA 的团队都有很强的参考意义。

论文总结了四条核心落地经验，每一条都直击 RDMA 落地的痛点。

### 7.1 四大核心落地经验

**第一条，跨层整合 RDMA 缓冲区所有权。** 零拷贝的本质是内存所有权的契约。bemalloc 的真正价值，是让应用层与通信层遵循统一的内存生命周期模型，让注册内存可以像普通内存一样灵活分配、传递、释放。:mdnice-bold-italic[只有把内存管理的契约做通，零拷贝才能从实验室走向真实业务。]

**第二条，分开管控接收容量与在途流量。接收信用保护接收队列容量，软件发送窗口限制在途数据量，两者保护的是完全不同的资源。** 很多团队容易把这两个问题混为一谈，要么只做流控不做接收容量保护，导致频繁 RNR；要么只做接收保护，不控制突发流量，导致网络拥塞。:mdnice-bold-italic[分层管控、各负其责，才是正确的思路。]

**第三条，RDMA 资源共享要与 IO 线程所有权对齐。** 应用层做了线程隔离，不代表驱动层就没有竞争。很多 RDMA 项目做到一定规模都会遇到驱动层锁的瓶颈，线程域是解决这个问题的有效手段。:mdnice-bold-italic[资源的共享边界要和线程的所有权边界对齐，才能充分发挥硬件的性能。]

**第四条，RDMA 传输可靠性要与服务策略紧密配合。** 不要试图在传输层解决所有可靠性问题，传输层只负责传输的可靠，服务级的故障恢复交给理解业务语义的上层。:mdnice-bold-italic[保留原有的 RPC 级超时、重试、副本选择、TCP 回退机制，再补充 RDMA 特有的连接监控，才是风险最低、收益最高的落地方式。]

### 7.2 多多少少带来的启发

> 当前 AI 算力的瓶颈正在**从计算侧逐渐转向通信侧，无论是大模型训练还是推荐推理，通信都越来越成为系统的关键瓶颈。** RDMA 作为高性能通信的核心技术，正在从 HPC 场景走向更广泛的互联网业务场景。

但很多团队对 RDMA 的认知还停留在换个协议就能提速的层面，落地过程中很容易踩坑。ByteExpress 的实践告诉我们，**RDMA 的落地是一个系统工程，需要从内存管理、资源调度、拥塞控制、可用性保障多个维度进行跨层协同设计，只关注硬件本身是远远不够的。**

::: block-1
对于想要落地 RDMA 的团队，可以参考字节的思路：:mdnice-highlight[先保留上层业务接口不变，在中间层封装 RDMA 的复杂度；从内存管理入手实现真正的零拷贝；通过资源复用与分层管控解决扩展性问题；最后用多层兜底机制保障服务可用性。] 循序渐进，从单点验证到规模落地，逐步释放 RDMA 的性能红利。
:::

随着 AI 模型规模的持续增长，通信的重要性还会不断提升。RDMA 技术本身也在不断演进，从 100G 到 200G 再到 400G，从 RoCE 到 InfiniBand，硬件能力在不断提升。**但无论硬件如何发展，软件层的跨层协同设计，永远是兑现硬件收益的关键。**
