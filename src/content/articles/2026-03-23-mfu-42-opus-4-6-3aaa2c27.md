## AutoResearch

> 前些天卡帕西的 autoresearch 项目:https://github.com/karpathy/autoresearch 在推上火了，身边好多人都不约而同向我进行了推荐，所以决定周末试试。

其中 autoresearch 的核心思想是**构建一个可准确评估，自我迭代的最小集合，每次可以基于现状完成一次最小迭代**，然后剩下的事情就全交给大模型了，尽量减少人的干预。具体的画风如下:

![文章插图](/articles/2026-03-23-mfu-42-opus-4-6-3aaa2c27/images/05.webp)

模型通过读取 program.md 来知道自己想要干啥，为了保证它的专注和避免对系统的影响，然后只允许它修改指定的文件 train.py，整体非常简单，其中 program.md 的内容也很简单，主要就是规定了一下 ① 怎么起环境 ② 怎么做实验 ③ 对齐模型的输入输出，结果如下，模型真的开始自己吭哧吭哧干活了，按照卡帕西的话说（5min 一轮，一个小时可以做 12 次实验），在这种高强度搜索下，validation loss 确实也在愉快的下降。

![文章插图](/articles/2026-03-23-mfu-42-opus-4-6-3aaa2c27/images/06.webp)

很好，模型看上去真的在干活，那么神奇的 program.md 在干嘛呢，详细的内容可以看 program.md，简短的总结是卡帕西用大白话告诉模型：① 如何准备实验 ② 实验的目标和衡量标准 ③ 如何跑实验 ④ 如何记录结果和决策 ⑤ 自主运行 ⑥ 故障处理。

很简单是吧，我一开始对这个结果并不是很在意，一是模型太小了，本身有些 toy 的性质，二是觉得类似于之前 automl 的搜索工作。真正对这种工作模式的观点转变来自于周末自己上手做的一个 gpu 算子优化实验。在花巨资充了 claude code 的账号后，我终于准备尝试一下传说中的 opus 4.6 到底有多强，然后就果不其然的被结果震惊了。

## Flash attention with mask

> 既然准备复现，那我们需要一个目标任务，我选择了 GPU 算子编程，因为这个任务 1.很确定，写的对不对快不快一测就知道 2.写好也需要花很多精力，属于上限高。

目标算子我选择了 flash attention with custom mask 的算子，具体的考量包括：① 这个算子在业务中确实被高频使用，优化有实际意义 ② 大模型领域面向 random 的 custom mask 的解决方案网上相对比较少，大模型应该没有背过(存疑)。在实际实现中，我还添加了(context length < 1k)的短序列限制，这个场景在很多大模型场景是不会遇到的。

算子本身的解决方案跟常规的 flash attention 算子解法很类似，大家可以参考 triton 的解决方案，本来还想考察模型对 mask 稀疏性的利用，后来觉得这个跟业务数据强绑定，就没弄。

仓库的地址：https://github.com/xgbj/sparse-mask-attention/tree/main

![文章插图](/articles/2026-03-23-mfu-42-opus-4-6-3aaa2c27/images/07.webp)

::: image-caption
在完成一个类似于 autoresearch 的仓库后，经过模型 2 天总共 23 轮的迭代，取得如下效果，在保证正确性的前提下，模型自己写计划，自己测试，自己跑 ncu profile，最终在 gtx3080 的 gpu 上跑出来了 25.17TFLOPS (MFU 42%左右)的性能，相比于 Pytorch naive 实现加速 4x，超过了 cuDNN、FlashInfer 和 triton 的结果。
:::

> 其中模型的成果可以总结为以下几点：

1. **效果好** ：相比于业内主流的 cudnn、大模型推理后端常用的 Flashinfer、Flash attention 以及 openai 的 triton，大模型的方案性能呈现明显的领先（也有可能是开源库没有针对特定算子的特定场景进行专门优化）。
2. **思路清晰** ：大模型在整个优化过程中主要采用了 ①mask 压缩加速 io 访问 ② 寄存器和 smem 的精细化操作 ③ wmma TC 指令全覆盖 ④ io offset 解决 bank conflic 等主要优化手段，也尝试了例如 ① 稀疏块 skip ② double buffer 等其它手段，整个过程除了类似算法人员的主动思考外，模型也采用了 Profile->PTX 指令分析->优化的自闭环逻辑，再连续多次没有加速的情况下也会主动上网搜索优化方案，表现上很接近工程师的思维。
3. **速度快** ：从开始写代码到超越开源库，大模型只花了两天总共 8h（受限于每天的配额限制），对比早期的迭代模式（工程师需要一周时间熟悉论文和 triton 语法，一周写代码调试），大模型快了 10 倍以上（这还不包括例如底层 PTX 指令分析和 wmma 等 TC 指令的学习）。

### 启动准备

在让模型自己左脚踩右脚自我提升前，我们还需要搭建好整个迭代环境，包括：① 研发环境准备，比如 python，torch，cuda 这些 ② 各种开源库的安装，比如 flash attention，flash infer 等等 ③ 评测脚本，这个可以让 ai 写，但是我们得保证它是对的。后面就不能让 ai 去修改 run.py 了（在切换到某大模型之后，它自作主张把评测 case 改了，导致纸面性能提升）。

### 运行

咒语没有什么特殊的要求，主要是让大模型阅读一下 optimization_rules.md，然后开始干活，具体类似于“麻烦看一下@notes/optimization_rules.md，然后开始你的新一轮迭代吧”。

(claude code 在启动的时候可以开启 claude --dangerously-skip-permission，这样就不需要每次 approve 了)

## 使用中的思考

1. 模型最关键，目前 claude code 的 opus 4.6 可以较好的胜任整个迭代工作，其它模型效率会降低很多。
2. 模型需要指引，模型的迭代优化本身很像训练本身，也会有陷入局部最小值的情况，如果没有比较强的冲量或者输入，容易陷在一些细节中。
3. auto research 的迭代模式本身是正确使用大模型所提炼出来的经验：① 可准确的评估和自我迭代，意味着明确的优化目标和实时反馈机制，可以减少问题的模糊度 ② 每次完成一次小的更新可以保证低成本的 resume，大模型在上下文过长的时候性能会明显下降，此刻 clear 上下文，重新 resume 就很有必要。
4. auto research 的迭代本身就很像强化学习，目前看合适的引导就能发挥大模型很大的潜力，并不需要专门做强化学习也可以，联想到最近看的一篇论文 Neural Thickets: Diverse Task Experts Are Dense Around Pretrained Weights：www.alphaxiv.org/abs/2603.12228
