## 关键问题

### 问题 1：论文提到 EAGLE-based 投机解码在大 batch 尺寸下实现了 1.4× 到 2.0× 的加速，但此前研究（如 vLLM、SGLang）显示投机解码的加速比会随 batch 增大而下降（甚至低于 1×）。那么，当前优化方案（如树注意力拆分、PyTorch-2 编译、分布式推理重构）在本质上解决了投机解码在计算密集型场景（大 batch 下从内存带宽受限转为计算受限）中的效率矛盾吗？其加速效果的上限受哪些硬件或算法因素制约？

本文的优化方案通过针对性解决计算密集型场景的核心瓶颈，在一定程度上缓解了投机解码在大 batch 尺寸下的效率矛盾，但加速效果仍受硬件与算法因素制约：

::: block-1
- **本质改进**：通过树注意力拆分（将注意力分为无掩码的前缀计算和带掩码的后缀计算，减少掩码开销）、PyTorch-2 编译（减少 CPU 嵌套循环开销，支持动态 batch 维度避免重编译）、分布式推理重构（移除不必要的 CPU-GPU 同步点、重叠 CPU 与 GPU 任务）等优化，有效提升了计算密集型场景（大 batch）的资源利用率。例如，树注意力的两阶段计算使验证阶段的并行效率提升，而分布式推理重构将 GPU 利用率提高至 94%，缓解了计算资源浪费问题。
- **加速上限制约**：硬件层面受 GPU 计算能力（如 H100 的 FLOPs）、内存带宽（KV 缓存访问速度）限制；算法层面受树结构复杂度（过大的树会增加计算开销）、draft 模型 TPC 上限（TPC 决定验证阶段的效率）制约。例如，flash decoding kernel 在树尺寸 ≤4、batch≤64 时最优，而更大规模需依赖 Flash Attention v3，硬件支持程度直接影响性能。
:::

### 问题 2.：训练优化中，3 层密集型 draft 模型相比 MoE 结构在参数更少的情况下实现了相当的 TPC，但 Llama4 系列采用 MoE 架构，而其 draft 模型仍用密集结构。这种“主模型 MoE+draft 模型密集”的搭配是否会导致 draft 模型与主模型的特征对齐效率下降？对于 MoE 主模型，是否存在更适配的 draft 模型架构设计（如稀疏激活），当前方案是否为权衡工程复杂度后的妥协？

“主模型 MoE+draft 模型密集”的搭配未显著影响特征对齐，当前方案是算法效果与工程复杂度权衡的结果：

::: block-1
- **特征对齐保障**：通过在线蒸馏（最小化主模型与 draft 模型的隐藏状态 L1 损失和 logits 交叉熵损失），即使 draft 模型为密集结构，仍能与 MoE 主模型保持特征对齐。例如，Llama4 Scout（MoE 主模型）的 3 层密集 draft 模型在 MT-Bench 上实现 2.87 的 TPC，与同规模 MoE draft 模型相当。
- **架构选择原因**：密集型 draft 模型参数更少（如 Llama4 Maverick 的密集 draft 模型参数比 MoE 少 10×），计算与存储开销更低，工程实现更简单（无需处理 MoE 的稀疏激活调度）。论文未提及针对 MoE 主模型的稀疏 draft 架构，但明确指出密集结构在 TPC 与效率间的平衡更优，是当前阶段的合理选择。
:::

### 问题 3：推理优化中，树调度器依赖预计算的静态树结构适配不同 batch 尺寸，但生产环境中请求的输入长度、输出分布差异极大（如长对话与短问答混合）。静态树结构在动态负载下的适配性如何？动态调整树深度/分支因子的 overhead 能否被收益覆盖？论文未提及的动态树生成策略是否存在潜在优化空间？

静态树结构在动态负载下通过树调度器实现一定适配性，但动态调整仍存在优化空间：

::: block-1
- **静态树的动态适配**：树调度器基于预计算的静态树（如不同深度和分支因子的树），根据当前 batch 尺寸选择最优结构（如小 batch 用大尺寸树，大 batch 用链状 draft），在实验中实现了 TPC 与计算成本的平衡。例如，Llama3.3 70B 和 Llama4 Scout 分别选择 N8 和 N12 的树结构，在不同 batch 下保持高效。
- **动态调整的权衡**：论文中未提及动态生成树结构的策略，但指出静态树已能覆盖多数场景。动态调整的 overhead（如实时计算最优树结构）可能抵消收益，尤其是在高负载时。不过，对于输入长度差异极大的场景，作者承认静态树存在适配局限性，动态树生成可能是潜在优化方向，但当前未验证其收益。
:::

## 一、引言

Vaswani 等人[Vaswani et al. (2017)]提出的基于注意力机制的 Transformer 模型，在机器学习和人工智能的多个领域得到广泛应用，包括自然语言处理、计算机视觉和语音处理。具体而言：

::: block-1
- 基于 Transformer 的大型语言模型（LLMs）已扩展到数十亿参数，并在数万亿 token 上进行训练，以生成高质量模型（例如，Achiam 等人[Achiam et al., 2023]；
- Grattafiori 等人[Grattafiori et al., 2024]；Meta[Meta, 2025]；团队等人[Team et al., 2023]）。
:::

> 由于其自回归特性（即模型逐 token 生成输出，每一步都依赖上一步的结果）和庞大的规模，这些模型的解码速度非常慢，这在需要处理大量具有不同输入和输出长度的请求的生产环境中，带来了重大挑战。

已有多种方法被提出用于提高 Transformer 模型的训练和推理速度，包括 FlashAttention（Dao 等人[Dao et al., 2022]；Dao[Dao, 2024]）、内存高效注意力（Rabe 和 Staats[Rabe and Staats, 2021]）、全分片数据并行（Baines 等人[Baines et al., 2021]）以及分布式推理（Zhong 等人[Zhong et al., 2024]；Qin 等人[Qin et al., 2024]）。

作为这些方法的补充，**投机解码** （Leviathan 等人[Leviathan et al., 2023]；Chen 等人[Chen et al., 2023]）已成为**加速 LLMs 推理** 速度的一种有前景的技术。

> 简而言之，投机解码:mdnice-bold-italic[通过一个更小的模型（即草稿模型，用于提前预测多个可能的 token）自回归地预测多个 token，然后由大型语言模型在单步内对这些 token 进行验证]。这**减少了对自回归大型语言模型的调用次数**，从而提高了解码速度。

然而，与非投机解码相比，**这种方法需要显著更多的浮点运算次数** （FLOPs），因为大型语言模型需要验证多个 token，而非投机解码设置中只需解码单个 token。已有多种投机解码方法被提出（例如，Cai 等人[Cai et al., 2024]；Miao 等人[Miao et al., 2024]；Li 等人[Li et al., 2024]）。然而，这些方法大多在小规模设置（例如，批处理大小为 1）下进行基准测试，以证明其相对于非投机解码方法的速度提升，这可能是因为**将这些方法扩展到需要高效处理大量动态请求的生产环境中，存在显著的工程挑战**。

例如，当批处理大小从 2 增加到 48 时，基于 EAGLE 的投机解码（使用 vLLM 测量）**相对于非投机解码的加速比从 1.3 倍下降到 0.7 倍** （参见 Li 等人[Li et al., 2025]的 v3 版本中的表 5）。在 SGLang（SGLang[2023]）中也观察到了类似的现象（参见 Li 等人[Li et al., 2025]的表 5）。

> 在本文中，我们详细介绍了为实现基于 EAGLE 的投机解码在 Llama 模型上的生产级规模化应用而实施的训练（参见第 2 节）和推理（参见第 3 节）优化技术，以解决这些模型在实际应用部署中面临的挑战。

## 二、训练优化

> 我们为基于 EAGLE 的推测解码引入了三项改进：（a）在线蒸馏（见 2.1 节）、（b）更长时间的训练（见 2.2 节）以及（c）多层稠密 draft 模型（见 2.3 节）。

通过这些改进，我们为四个不同的 Llama 模型训练了 draft 模型，这些模型在多个方面（包括架构和模型大小）存在差异。相关结果将在 2.4 节中呈现。

### 2.1 在线蒸馏

> 图 2 展示了我们所实现的 EAGLE 推测解码的概述。具体来说，它使用了一个基础模型 B 和一个 draft 模型 D，两者都是自回归的（自回归指模型会根据之前生成的 token 来生成下一个 token，逐 token 生成输出）。

基础模型由 N 个连续的 Transformer 层组成，而草稿模型是轻量级的，具有 M 层，其中 $M << N$ （即 M 远小于 N ）。

在训练过程中，基础模型 B 接收 $n$ 个 token $t=\{t_{1}, t_{2}, \cdots, t_{n}\}$ 作为输入。它会生成隐藏状态（hidden states，模型中间层输出的、包含输入特征信息的向量）$h^{b}=\{h_{1}^{b}, h_{2}^{b}, \cdots, h_{n}^{b}\}$（即语言模型头（LM head，模型中用于输出预测结果的部分）之前的归一化层的输出）和对数几率（logits，模型输出的未经过 softmax 激活的原始分数）$l^{b}=\{l_{1}^{b}, l_{2}^{b}, \cdots, l_{n}^{b}\}$（即语言模型头输出的、经过 softmax 激活之前的结果）。

对于草稿模型，输入 token 向右偏移一位，得到 $\hat{t}=\{t_{2}, t_{3}, \cdots, t_{n}\}$。这些 token 被输入到嵌入层（embedding layer，将离散的 token 转换为连续的向量表示，方便模型处理）。**与基础模型不同，草稿模型在嵌入层和第一个 Transformer 层之间包含一个全连接层** （fully-connected layer，一种神经网络层，其中每个神经元都与上一层的所有神经元相连）。该层接收 $\hat{t}$ 的 token 嵌入和来自基础模型的隐藏状态 h 作为输入，其输出被送入草稿模型的其余部分，以生成隐藏状态 $h^{d}=\{h_{2}^{d}, h_{3}^{d}, \cdots, h_{n}^{b}\}$ 和对数几率 $l^{d}=\{l_{2}^{d}, l_{3}^{b}, \cdots, l_{n}^{b}\}$¹。

为了训练草稿模型，我们最小化基础模型 B 和草稿模型 D 在（a）隐藏状态和（b）对数几率之间的损失。具体来说，我们**计算基础模型向右偏移后的隐藏状态与草稿模型的隐藏状态之间的平滑 L1 损失** （smooth L1 loss，一种对异常值更稳健的损失函数，结合了 L1 损失和 L2 损失的优点），即 $L_{L1}=l1\_loss(h_{2:n}^{b}, h_{2:n}^{d})$。类似地，我们计算基础模型偏移后的对数几率与草稿模型的对数几率之间的交叉熵损失（cross entropy loss，用于衡量两个概率分布之间差异的损失函数，常用于分类任务），即 $L_{CE}=ce\_loss(l_{2:n}^{b}, l_{2:n}^{d})$。

最终损失是 $L_{L1}$ 和 $L_{CE}$ 的加权和，如下所示：

$$
\mathcal{L}=\lambda_{CE} \cdot \mathcal{L}_{CE}+\lambda_{L1} \cdot \mathcal{L}_{L1}
$$

其中 $\lambda_{CE}$ 和 $\lambda_{L1}$ 是分别控制交叉熵损失和 L1 损失贡献的系数。在我们的实验中，我们使用 $\lambda_{CE}=0.1$ 和 $\lambda_{L1}=1.0$。

### 2.2 更长时间的训练

> 我们为属于 Llama3（Grattafiori 等人，2024）和 Llama4（Meta，2025）系列的以下**四个基础模型训练了 draft 模型**：（1）Llama3.1 8B、（2）Llama3.1 70B、（3）Llama4 Scout（总参数和活跃参数分别约为 1090 亿和 170 亿）以及（4）Llama4 Maverick（总参数和活跃参数分别约为 4000 亿和 170 亿）。

::: block-1
- Llama3 系列的模型使用稠密前馈网络（FFN，一种每个输入都会经过所有神经元的前馈网络）层，
- 而 Llama4 模型使用混合专家（MoE；Shazeer 等人，2017）层（一种包含多个“专家”子网络的结构，由门控网络决定每个输入使用哪些专家）。
:::

我们使用与训练基础模型相同的有监督微调（SFT，使用标注数据对预训练模型进行微调以适应特定任务）数据集，共进行 48k 次迭代，每次迭代处理 200 万个 token。使用 Adam 优化器（Kingma，2014）来优化 draft 模型，学习率（控制模型参数更新步长）设为 0.0002 且权重衰减（一种正则化方法，通过在损失函数中加入参数的 L2 范数来防止过拟合）设为 0.1。

为了**评估 draft 模型的质量**，我们**在两个基准测试集上测量了每个 draft-验证阶段的接受 token 数量** （即每次调用的 token 数，TPC）：

::: block-1
1. MT-Bench（Zheng 等人，2023），一个广泛用于衡量推测解码性能的公开基准测试集；
2. 一个私有内部基准测试集，包含多样化、多语言且更难的样本。
:::

我们在 TPC 评估中使用批量大小（每次处理的样本数量）为 1、链式 draft 且推测长度（draft 模型一次生成的 token 数量）为 3。更高的 TPC 值更为理想。

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/06.webp)

图 3a 展示了使用 Llama4 Scout 进行更长时间 draft 训练的效果。我们可以看到，**更长时间的训练有助于提高两个基准测试集上每个 draft 步骤的平均接受 token 数** （即每次调用的接受 token 数，TPC）。需要注意的是，我们:mdnice-bold-italic[在其他模型中也观察到了类似的趋势。]

### 2.3 多层稠密 draft 模型

## 三、推理优化

我们的 EAGLE 投机解码推理过程如图 4 所示，分为以下阶段：

::: block-1
1. 预填充（Prefilling）：该阶段包括对输入提示词 token 执行基础模型预填充，然后基于输入 token 和基础模型产生的隐藏状态执行草稿模型预填充。
2. 树调度器（Tree Dispatcher）：在该阶段，为当前批次选择最优的静态树结构。
3. 草稿生成（Drafting）：EAGLE 草稿生成器接收来自基础模型的上一个 token 及其隐藏状态，通过草稿模型自回归运行来构建草稿 token 树。
4. 验证（Validation）：在这里，草稿 token 通过基础模型进行验证。基于树注意力的推理支持对整个草稿 token 树进行高效的一次性验证。
5. 采样（Sampling）：该阶段决定是否接受部分或全部提议的 token 。遵循 EAGLE 的方法，我们使用多轮投机采样，这能保留原始大语言模型的输出概率分布。
6. 记录（Bookkeeping）：EAGLE 投机解码需要缓存隐藏状态以用于下一轮草稿生成。因此，在记录阶段，键值缓存（KV cache，用于存储注意力计算中的键和值，加速后续推理）和隐藏状态会根据接受的长度回滚到适当的位置。
:::

### 3.1 树注意力

> 树注意力[Miao et al., 2024]是 EAGLE 投机解码中的一项重要技术，在草稿生成和验证阶段均有使用。

在每个解码轮次中，树中的一条路径会基于接受准则被部分接受，该准则利用目标模型在每个节点生成的验证对数概率（logits，模型输出层未经过 softmax 的原始输出，可反映 token 的预测概率）。计算这些对数概率的一种朴素方法是展开所有可能的路径，并执行预填充计算，其有效批次大小等于批次大小与路径数量的乘积。

然而，**一种更高效的方法是将所有草稿 token 平化为单个序列**。这种方法在计算注意力时带来了一个挑战：平化后的树 token 并非自然的顺序，难以应用标准的因果注意力掩码（causal attention mask，确保模型在预测时只能关注之前的 token ，不能关注未来的 token ）。

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/09.webp)

可以通过提供显式的掩码张量来应用自定义的树掩码。但是，带有显式掩码的树注意力速度较慢，因为掩码的形状很大，会随查询和上下文（键/值）的长度而扩展。因此，我们**将注意力计算分为两部分**：:mdnice-bold-italic[（a）查询与上下文之间的注意力（前缀），（b）查询自身内部的注意力（后缀）]，如图 5 所示。**前者计算量大但无需掩码，而后者需要树掩码但规模相对较小**。

这种两阶段方法使我们能够有效地准备和提取用于后缀计算的推测 token 的查询/键/值，且没有任何性能开销。这两种注意力计算随后通过`merge_attentions`进行聚合，这是一种基于在两个不相交的键值上下文块上计算的部分注意力输出，来计算完整注意力的简单方法[Juravsky et al., 2024]。

我们已使用这种方法在 xFormers[Lefaudeux et al., 2022]中实现了高效的树注意力。值得一提的是，我们**在 xFormers 中优化的树注意力代码可以与其他基于树的投机解码方法** （如 SpecInfer[Miao et al., 2024]和 Medusa[Cai et al., 2024]）:mdnice-bold-italic[无缝结合，以进一步提高它们的推理效率。]

### 3.2 多轮投机采样

EAGLE 中的多轮投机采样（MSS）扩展了 Leviathan 等人[2023]、Chen 等人[2023]的标准投机采样方法，专门**针对树形草稿进行了适配**。多轮投机采样的:mdnice-bold-italic[朴素实现会在生产解码环境中带来显著开销，因为涉及到对树深度的嵌套循环以及需要启动大量小型核函数] （kernel，GPU 上的计算单元）。

> 为解决这一问题，我们实施了下面三点优化：

#### 优化点1：PyTorch 2 编译

这是一种通过编译代码提升执行效率的技术。虽然多轮投机采样中的大多数操作本身计算强度不高，但对树深度和每个节点的子节点的嵌套循环可能导致显著的 CPU 开销，尤其是在大规模生产环境中。

为缓解这一问题，我们使用 PyTorch 2 对代码进行编译，实现了 1.5 倍的加速。**一个关键考虑是处理可变输入流量的动态批次维度**。朴素地应用`torch.compile`可能会导致针对每个批次大小进行重新编译，这可能在生产中造成延迟峰值。

为解决这一问题，我们将每个输入张量的批次维度指定为动态的。通过这一改变，重新编译仅限于两种情况：批次大小为 1 和批次大小大于 1。此外，如果服务在启动时接收预热流量，且两种情况都被覆盖，那么`torch.compile`会在预热阶段填充编译器缓存。该缓存随后在实际流量中被重用，有助于避免延迟峰值。

#### 优化点2：跨张量并行进程

即用于分布式计算中拆分模型张量的进程的并行化。尽管实现了 GPU 高效的优化和 PyTorch 2 编译，但在**大批次大小时，采样仍是解码性能的一个显著瓶颈**。

一个主要原因是 top-p 掩码（或核采样，nucleus sampling[Holtzman et al., 2020]）的应用，这涉及到固有的“串行”操作，难以在 GPU 上加速。我们观察到：（a）采样在批次维度上是极易并行的；（b）所有张量并行进程应获得相同的采样结果。

因此，我们**通过将批次大小填充为 GPU 总数（即世界大小，world size）的倍数，来跨张量并行进程对采样进行并行化**。然而，对于这种简单的解决方案，必须特别注意跨进程同步随机数生成器。

实际上，在采样过程中，每个进程生成的随机张量大小与批次大小成比例。如果不同的进程处理不同的本地批次大小（例如，最后一个进程处理全局批次大小除以世界大小的余数），随机数生成器可能会发散，这可能导致后续迭代中的系统挂起。为防止这种情况，我们**在每个进程上生成一个完整大小的随机张量，并让每个进程获取该张量的不同切片。**

#### 优化点3：贪心草稿解码

对于树形草稿，存在多种采样草稿 token 的方法，包括多项式采样（有放回和无放回）和贪心采样[Miao et al., 2024; Jeon et al., 2024]。具体而言，对于贪心解码，我们考虑一个具有 k 个子节点的节点，并将 k 个概率最高的 token 放入这些子节点中。

在我们的实验中，**观察到贪心采样比其他方法的 token 接受数（TPC）略高**。此外，**对于贪心解码的草稿概率，计算成本高昂的 top-p 掩码是无效操作**，这使我们能够在草稿生成阶段跳过 top-p 掩码（同时仍在验证阶段将其应用于目标对数概率）。这减少了草稿生成的计算开销，进一步提高了推理效率。

### 3.3 大批次大小下的分布式推理

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/10.webp)

在生产环境中，我们采用分布式方法，预填充和解码操作在单独的主机上执行（见图 6）。在这种设置中，客户端与解码主机通信，解码主机将第一轮请求重定向到预填充主机，并自行处理其余轮次。

由于这种分布式架构，投机解码必须适应大批次大小和可变流量，这具有挑战性，因为它使高效的计算资源管理变得复杂。此外，更大批次大小对浮点运算（FLOPs）的需求增加，需要谨慎分配硬件资源，以确保系统能够处理峰值负载而不出现瓶颈（包括内存不足错误）。

> 为了在投机解码中处理大批次大小，我们实施了以下优化，将执行效率和 GPU 利用率提高到 94%：

我们**收集了硬件轨迹** 以:mdnice-bold-italic[识别不必要的 CPU-GPU 同步点，并将其移除]。这**使 CPU 能够跑在 GPU 前面，确保 GPU 的工作队列中有足够的任务**。这有助于减少 GPU 空闲时间并改善延迟。

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/11.webp)

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/12.webp)

图 7 显示了一个示例轨迹。在图 7a 中蓝色框突出显示的同步点处，CPU 等待 GPU 执行完成，由于 CPU 核函数启动开销和 GPU 空闲，导致后续操作的效率低下和速度减慢，如 7a 中的红色框所示。移除该同步点后，如图 7b 所示，CPU 核函数在 GPU 执行之前就已启动。这种优化消除了 GPU 空闲时间，并将每个 token 的解码时间（TTIT）改善了 0.4 毫秒。**平均而言，我们发现移除所有可能的 CPU-GPU 同步点后，每个 token 的解码时间改善了 8-12%。**

我们通过将 CPU 操作与 GPU 核函数执行重叠来重构解码周期，以进一步改善延迟。具体而言，我们将任务（如记录）分解为不同的 GPU 和 CPU 组件。这使我们能够在 GPU 核函数运行时并发执行 CPU 后处理任务，有效地将 CPU 操作隐藏在 GPU 处理之后，提高了整体系统效率。如图 6 所示，在记录、预填充处理和草稿生成之间存在间隙，如 6a 中的红色箭头所示。通过重构，我们能够减少 GPU 空闲时间（见图 6b 中的红色箭头），这帮助每个 token 的解码时间平均改善了约 10%。为了优化首个 token 的生成时间（TTFT），我们在预填充阶段结束时添加了一个采样步骤（如图 6b 中的蓝色框所示）。这使我们能够在解码器收到第一个 token 的输出（隐藏状态和下一个预测 token ）后立即使用它们，而不必等待整个解码周期完成。通过这种方式，我们减少了延迟，平均改善了响应时间约 8-30%（取决于流量大小）。

我们通过将预填充响应处理移到记录之前来重新排序处理序列，使其能够隐藏在长时间运行的验证核函数之后。此外，我们更早启动下一轮草稿生成和验证核函数，有效地掩盖了向客户端传输结果的延迟。

### 3.4 其他性能优化

#### 预计算静态树

在我们的生产环境中，批次大小变化很大，范围从 1 到 100 以上。这种可变性带来了一个挑战，因为没有单一的树结构在整个范围内都是最优的。

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/13.webp)

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/14.webp)

:mdnice-bold-italic[图 8 显示，更大的树结构（在小批次大小时有效）能产生更高的 token 接受数，但速度较慢]。此外，**在更大的批次大小时，计算成本超过了 token 接受数增加带来的好处**。为了选择最优的树配置，我们开发了树调度器。基于预计算的静态树结构，它决定为当前批次大小使用哪种树配置。例如，对于一个通常在小批次大小下运行的模型，我们可以决定在批次大小为 1 时使用静态树，在批次大小大于 1 时使用 3 个 token 的链式草稿。这样，我们平衡了计算成本和 token 接受数之间的权衡，并确保在所有流量条件下的最优性能。

#### 草稿键值缓存对齐

在每个草稿生成阶段开始时，EAGLE 方法通过使用上一轮新接受的 token 和隐藏状态执行前向传播，来覆盖草稿模型的键值缓存。在此阶段同步键值缓存确保草稿模型整合来自上一轮验证的相关上下文信息，从而产生更准确和连贯的草稿。然而，这种方法会带来不可忽视的额外计算成本。我们:mdnice-bold-italic[发现，仅使用上一轮的最后一个输出 token 及其相应的隐藏状态，就足以使草稿模型的键值缓存与基础模型对齐，同时提高推理效率。]

#### CUDA 图

在推理过程中，特别是在大批次大小时，由于模型执行，草稿生成和验证阶段的计算需求最高。我们**扩展了 Meta 内部推理引擎中 CUDA 图的使用，以优化草稿生成和验证**。这有效地:mdnice-bold-italic[消除了核函数启动开销，并简化了 GPU 操作]。值得注意的是，为了获得最佳性能，我们选择在 CUDA 图中捕获整个模型执行。这种方法与一些开源推理库（如 vLLM-v1[Kwon et al., 2023]）形成对比，后者将注意力计算与 CUDA 图捕获分开，以提供更大的灵活性。

#### 注意力核函数

大语言模型**解码过程中使用的注意力受限于从 GPU 高带宽内存（HBM）中的缓存加载键和值的需求**。因此，:mdnice-bold-italic[运行时间随上下文长度线性增长]。已有多项工作致力于在特定硬件上高效实现注意力（例如 Dao 等人[2023, 2022]; Dao[2024]）。

为了在生产环境中实现更快的解码，我们使用特定于硬件的注意力核函数。在我们的环境中，有三种选择：

::: block-1
1. Flash 解码（或 Triton Split-k 核函数）
2. Flash Attention v2 和 v3
3. AMD 上的可组合核函数（ROCm[2023]）
:::

**基于批次大小、树大小和 GPU 类型，我们使用一种基于启发式的方法来选择这些注意力选项**，这主要源于这些方法中的键值拆分策略。例如，当树大小 ≤4 且批次大小 ≤64 时，Flash 解码核函数在延迟方面优于其他核函数。当硬件支持时，Flash Attention v3 在更大的树和批次大小下提供最佳延迟。

#### 支持树注意力的分页键值缓存

分页键值缓存将键值缓存划分为块，并根据需要分配块[Kwon et al., 2023]。我们使用分页键值缓存来优化内存使用，并为基础模型和草稿模型维护单独的缓存。然而，**分页键值缓存与树注意力不兼容。为了使其兼容，我们实施了两项更改**：

::: block-1
1. 树注意力中的后缀部分相对较小。为了最小化查找分页块的开销，我们仅将分页应用于前缀注意力，并写回中间键和值，而不是从缓存中检索它们；
2. 在为草稿生成和验证阶段分配块时，我们添加额外的树填充，以防止推测 token 超出块边界。
:::

#### 持久键值缓存

我们的系统利用持久键值缓存来提高跨请求性能。在处理请求时，分页键值缓存中最近最少使用（LRU）的块被驱逐到持久键值缓存中，以容纳新的键值对。然后，在预填充期间，这些缓存的键值对被重用于匹配的提示前缀，从而减少首个 token 的生成时间。

我们为基础模型和草稿模型维护单独的持久键值缓存，确保两者都能从这种优化中受益。此外，我们的系统强制要求对于任何给定的 token 序列，两种模型都表现出相似的缓存命中和块驱逐行为。这主要是为了简化实现并提高可维护性。为了实现这种统一行为，我们进行了以下调整：

::: block-1
- 我们使用整个提示 token 序列预填充基础模型和草稿模型的键值缓存。然而，对于草稿生成，EAGLE 需要来自基础模型的上一个 token 的隐藏状态，而第一个提示 token 没有这个状态。与 EAGLE 在草稿预填充期间跳过第一个提示 token 不同，我们将第一个 token 与其从基础模型预填充输出的自身隐藏状态融合。**根据经验，我们观察到这种方法导致 token 接受数略有增加。**
- :mdnice-bold-italic[为了维持草稿模型和基础模型之间的同步，我们将草稿模型的键值缓存大小相对于基础模型的键值缓存大小按（$\frac{草稿层数}{基础模型层数}$）的比例进行缩放]。这确保了两种模型的分页缓存和持久缓存都具有相同的块集，从而实现同步的块驱逐时间。
:::

#### 量化草稿模型

**投机解码的“无损性”意味着草稿模型的质量不会影响最终输出，只会影响速度**。因此，我们:mdnice-bold-italic[可以采用与基础模型不同的方式压缩草稿模型]。表 2 显示，INT4 前馈网络（FFN）量化在 token 接受数和解码速度之间提供了良好的权衡。

#### 引导解码

> **引导解码有助于生成结构化输出，在生产环境中至关重要** [Willard and Louf, 2023]。为了支持引导解码请求的投机解码，我们实施了两项更改：

::: block-1
1. 我们将引导解码逻辑集成到投机解码工作流的所有阶段，包括草稿生成、采样和记录。
2. 我们通过在 GPU 上优化与引导解码相关的操作来提高性能。
:::

具体而言，我们高效地初始化了引导解码有限状态机（FSM）状态，并通过将与 CPU 相关的操作移至 GPU 来加速对数概率掩码的关键步骤。这避免了同步开销，并且我们观察到，**与非投机解码基线相比，使用带有投机解码的引导解码时，速度提升了 2.6 倍**。需要注意的是，本文中呈现的结果不包含引导解码。

Llama4 的 iRoPE：Llama4 引入了交错旋转位置编码（iRoPE），这是一种局部注意力变体，其中序列被拆分为固定长度的子序列，查询只能关注同一子序列内的值。这有效地修改了注意力掩码，使块对角掩码中的块更小。回想一下，树注意力（见 3.1 节）也会修改注意力掩码。因此，**对于 Llama4 推理，正确组合这两种修改至关重要。**

解码的 iRoPE 注意力掩码是使用 XFormers 的间隙注意力偏置（gappy attention biases）实现的。我们调整了树注意力，使其在前缀注意力中使用 XFormers 的间隙注意力偏置，并通过验证路径集成 iRoPE 逻辑。我们:mdnice-bold-italic[遇到的一个特例情况是，草稿字符串跨越两个子序列的边界]。虽然从理论上讲，可以实施复杂的逻辑来在两个子序列之间拆分树掩码，但**我们选择了一种更简单的解决方案：将草稿截断以完全适合一个子序列**。由于这种情况极为罕见，对接受率的影响可以忽略不计。

### 3.5 基准测试

:mdnice-bold-italic[许多先前的工作假设投机解码的加速比随着批次大小的增加而降低] [Su et al., 2023; Miao et al., 2024; Liu et al., 2024]。这**可能是因为投机解码方法【可能未充分利用】 GPU 计算资源**，即由于解码受 GPU 内存带宽而非计算限制，运行草稿生成和验证所增加的浮点运算成本可以忽略不计。**然而，在大批次大小时，解码受计算限制，导致加速比下降。**

![文章插图](/articles/2025-08-13-94-gpu-llama-10-2-3511ec60/images/17.webp)

**在大上下文长度下，即使对于大批次大小，注意力也主导计算**，因此:mdnice-bold-italic[工作负载仍受内存限制] [Sadhukhan et al., 2025]。我们在图 9 中的结果部分证实了这些观察结果。

总体而言，:mdnice-bold-italic[我们观察到端到端投机解码加速比与批次大小之间的关系 因模型大小及其性能特征而异]。例如，Llama3.1 8B 模型在大批次大小下比在小批次大小下表现出更大的投机解码加速比。相比之下，具有约 4000 亿参数的 Llama4 Maverick 的加速比随着批次大小的增加而降低。
