## 一、megakernel 的性能迷雾：持久化本身还是调度策略？

> 在大模型 batch=1 推理场景下，:mdnice-bold-italic[GPU 的利用率瓶颈往往不在计算本身，而在内核启动、资源切换与权重加载的调度开销。megakernel 方案的出现，曾被认为是通过“单内核常驻”从根本上消除了这些开销。]

长久以来，行业内普遍将 megakernel 的性能优势归因于“减少内核数量”和“常驻执行”，认为只要内核拆分就必然带来显著的性能损失。:mdnice-bold-italic[但这项研究的核心洞察在于，megakernel 真正的高效之处可能是其内部的指令级调度能力——在前一个算子还未完成时，下一个算子的权重加载就已经开始，资源可以在算子边界无缝复用。如果能在普通内核之间复现这种重叠调度，那么无需常驻解释器也能拿到大部分性能收益。]

### 1.1 megakernel 的原始设计逻辑

> Hazy Research 的原始 megakernel 方案，针对 Llama-1B 这类小模型的 batch-1 解码场景，设计了常驻流式执行架构。每个流式多处理器（SM）上常驻一个协作线程阵列（CTA），整个模型被编码为一条指令流，由片上调度器依次派发。CTA 是 GPU 上的基本执行单元，对应一组运行在同一个 SM 上的线程，共享片上寄存器与共享内存资源。

这种架构下，权重加载器和计算消费者线程组可以跨算子边界保持存活，共享内存缓冲区由片上分配器循环复用。:mdnice-bold-italic[最重要的是，第 $i+1$ 条指令的权重加载，可以在第 $i$ 条指令还在计算时就提前启动，加载过程通过张量内存加速器（TMA）异步执行，与计算完全并行。这种算子间的流水线重叠，是 megakernel 低延迟的核心来源之一。]

### 1.2 研究的核心问题与验证思路

> 研究团队没有直接否定 megakernel 的价值，而是:mdnice-bold-italic[选择了拆解验证的思路：保留原始的算子实现、模型结构与计算逻辑，只移除常驻解释器、片上共享内存分配器、运行时指令派发等持久化机制，将每个算子变成独立的 CUDA 内核节点，通过 CUDA Graph 组织成完整的执行链。]

实验的核心变量只有内核间的依赖调度方式：默认 CUDA Graph 依赖是等前一个内核完全结束再启动下一个；而 PDL 依赖可以让下一个内核提前启动，只在真正的数据依赖点等待。通过对比两种调度下的性能，就可以量化出“调度优化”能追回多少 megakernel 的性能，剩下的才是“持久化本身”带来的收益。

## 二、基准对照：81 内核拆分后的性能全景

> 实验基于 Llama-3.2-1B 模型，在单张 H100 SXM5 GPU 上运行，采用 BF16 精度，设置 32token 提示词、生成 128token 的真实工作负载。完整的推理链路包含嵌入、Transformer 层计算、LM 头、argmax 和 token 输出全流程。

原始 megakernel 在 16 层 Transformer 中，每层包含 5 个有效操作指令，加上最终的 LM 头，总共 81 个计算节点。

```
# 持久化程序中单层 Transformer 的 5 条活跃计算指令序列1  RMSNorm + QKV projection + RoPE/KV append        2  attention        4  output projection        5  RMSNorm + up/gate projection + SiLU        6  down projection           -> next layer's opcode 1
```

拆分后，每个节点对应一个独立的 CUDA 内核，通过 CUDA Graph 组织成完整的执行链，所有内核复用完全相同的计算逻辑与访存模式。

### 2.1 测试环境与对比说明

> 所有测试都在同一台服务器上完成，配备两颗 Intel Xeon Platinum 8558 CPU，单颗 48 物理核，开启超线程后共 192 逻辑核。GPU 使用单张 NVIDIA H100 SXM5 80GB HBM3，不使用张量并行。驱动版本为 590.48.01，GPU 功耗限制 700W，没有强制锁频。

软件环境分为两套：

- 持久化版本、默认依赖版本和 PDL 版本使用同一套 megakernel 虚拟环境，基于 PyTorch 2.7.0+cu128 和 CUDA Runtime 12.8 构建。
- SGLang 参考使用单独的虚拟环境，版本为 v0.5.15.post1，基于 PyTorch 2.11.0+cu130 和 CUDA 13.1 构建。

需要特别说明的是，SGLang 的计时范围是服务器请求端到端，包含了 CPU 侧的全部开销，和其他三者的进程内解码步计时范围不同，不能直接作为严格的横向对比，仅作为系统级参考。

### 2.2 实验的变量控制

> 为了保证对比的公平性，研究团队做了严格的变量控制：:mdnice-bold-italic[默认依赖基线和 PDL 链使用完全相同的二进制文件和内核入口，唯一的区别就是 CUDA Graph 的边语义——基线保留捕获期间创建的默认依赖，而 PDL 链将这些边重写为程序依赖。]

所有延迟测量都关闭了时间线、分析器和设备端计时记录，避免额外开销。计算结果经过了严格的正确性校验，确定性单步 token 检查全部通过，位置相关的中间张量也在轨迹的开始、中间和结尾做了校验，没有精度损失。

## 三、内核边界如何制造 190 微秒的性能空洞

> 很多人会把多内核的性能损失归因为 CPU 侧的内核启动开销，但在 CUDA Graph 的加持下，整个执行链一次性提交，CPU 开销已经被基本消除。那 190 微秒的差距到底来自哪里？

![文章插图](/articles/2026-08-31-megakernel-cuda-pdl-97-4-aa5c9945/images/05.jpg)

::: image-caption
表 2 默认 CUDA 图依赖与 PDL 两种调度模式下，拆分内核主体延迟、配对持久化主体延迟及二者性能差值对比。
:::

实验数据显示，在去掉 LM 头的纯 Transformer 主体部分，持久化方案耗时 776.942 微秒，而默认依赖的拆分内核耗时 967.162 微秒，两者相差 190.220 微秒。这 190 微秒的差距，完全来自内核边界带来的硬件层面开销，和 CPU 无关。

### 3.1 内核边界的四类开销

> 具体来说，每一个内核边界都会带来四方面的开销，这些开销在 80 个内部边界上累积，最终形成了 190 微秒的性能空洞。

| 项目 | 描述 |
| --- | --- |
| 网格准入与排空开销 | 每个内核启动时，CTA 需要逐个调度到 SM 上，结束时需要等待所有 CTA 都退出，该过程存在固定的硬件延迟。 |
| CTA 与屏障初始化开销 | 每个内核启动时，都需要重新初始化 CTA 的资源、同步屏障和共享内存配置，这些操作无法跨内核复用。 |
| 常驻状态丢失 | 持久化方案中，加载器线程组、共享内存缓冲区等是跨算子复用的；而拆分内核中，每个内核结束后所有资源均被释放，下一个内核需重新申请。 |
| 跨算子权重加载重叠消失 | 持久化方案可在前一个算子计算时即加载下一个算子的权重；而默认依赖要求前一个内核完全结束后，才能启动下一个内核的权重加载，导致原本可隐藏的访存延迟完全暴露在关键路径上。 |

这四类开销叠加起来，其中**占比最大的就是跨算子权重加载的重叠机会丢失，这也是 PDL 优化最核心的切入点。**

### 3.2 PDL 的核心价值：重建重叠调度

> NVIDIA 的程序依赖启动（Programmatic Dependent Launch，PDL）机制[2]，提供了打破默认依赖限制的能力。它允许后继网格在前驱网格还未完成时就提前启动，后继可以先做自己的初始化和权重加载，只在真正需要读取前驱输出数据的地方等待。

简单来说，**默认依赖是“前一个内核全做完，后一个才能开始”，而 PDL 是“前一个内核发出数据后，后一个就可以开始做准备，等数据真的要用了再等一下”**。这样就可以把权重加载的开销隐藏在前驱内核的计算时间里，重建持久化方案里的重叠效果。

::: block-1
整体看下来，190 微秒的性能缺口本质上是:mdnice-highlight[默认调度机制强制内核串行执行带来的流水线断裂]。PDL 的核心作用就是修复这条流水线，让权重加载等独立操作可以跨内核边界重叠执行，从而追回大部分损失。
:::

## 四、PDL 调度：两行代码追回 158 微秒的技术细节

> PDL 的 API 接口非常简洁，每条内核依赖边只需要两个函数调用。**但真正的性能优化精髓，在于触发时机的选择——早一点或晚一点触发，都会带来显著的性能差异。**

最终的 PDL 实现，在每条依赖边上只增加了两行核心代码，就追回了 158 微秒的性能，将 190 微秒的缺口缩小到 32.5 微秒，找回了 82.8%的性能损失。**优化的核心在于对触发时机的极致打磨**。

### 4.1 两条核心原语的作用机制

每条 PDL 依赖边包含两个关键操作，分别由生产者和消费者内核调用，共同完成细粒度的依赖控制。

- **第一个操作由生产者内核调用**：`cudaTriggerProgrammaticLaunchCompletion()`。这个函数的作用是通知硬件，生产者已经完成了数据生产的前置工作，消费者内核可以开始启动了。:mdnice-bold-italic[注意，这个调用不需要等生产者内核完全结束，只需要等生产者发出了自己的权重加载请求之后就可以调用。]
- **第二个操作由消费者内核调用**：`cudaGridDependencySynchronize()`。这个函数的作用是等待生产者的数据真正准备好，只有执行到这里，消费者才会真正停下来等待。:mdnice-bold-italic[在这之前，消费者可以自由地做自己的初始化、权重加载等独立工作。]

通过这两个操作，内核间的依赖从“整个内核完成”细化到了“数据真正可用”的时间点，中间的准备时间就可以完全重叠在前驱的计算过程中。

### 4.2 触发时机的极致优化

> 研究团队发现，触发时机的选择对性能影响巨大。最初他们把触发点放在生产者的最终权重 TMA 到达之后，后来前移到 TMA 刚刚发出的时候，仅此一项调整就追回了 34.032 微秒。

背后的逻辑是：**触发点越早，消费者就能越早启动，也就有更多时间隐藏自己的权重加载延迟**。但触发也不能太早，必须保证生产者的数据输出不会出现依赖问题。:mdnice-bold-italic[最优的触发点，就是生产者发出自己的独立访存请求之后，立刻释放后继启动权限，既不浪费一点时间，也不会破坏依赖正确性。]

![文章插图](/articles/2026-08-31-megakernel-cuda-pdl-97-4-aa5c9945/images/06.jpg)

::: image-caption
表 3 单独启用每一类 PDL 连接边缘时，相对于默认依赖对照组的延迟节省量，以及全部 79 条边缘均启用时的总收益。该表通过消融实验拆解了 Transformer 不同阶段间 PDL 调度的收益分布，验证了 QKV 到注意力、MLP 内部、跨层连接等各类边缘均有正向贡献；同时体现总收益低于单边缘收益的简单相加，说明各边缘调度会相互影响流量与启动环境，存在边际递减效应，PDL 的性能提升是全链路协同优化的结果。

回顾一下，PDL 的优化本质不是创造了新的计算能力，而是:mdnice-highlight[将内核间的依赖粒度从整个内核细化到了数据依赖点]，把原本串行的准备工作并行化。两行代码就能带来巨大收益，背后是对 GPU 执行流水线的精准把控。

## 五、滚动尾波效应：PDL 性能收益的底层运行机制

> 这里存在一个看似矛盾的问题：H100 的每个 SM 最多只能容纳一个完整的 CTA，两个 CTA 无法同时驻留在同一个 SM 上。那 PDL 的提前启动，到底是怎么实现重叠的？

答案在于，一个内核的所有 CTA 不是同时结束的，而是像波浪一样逐个 SM 陆续退出。PDL 利用的就是这种陆续退出的时间差，让后继内核的 CTA 逐个填补空出来的 SM，形成滚动的尾波效应。

### 5.1 滚动尾波的执行过程

> 研究团队通过在 CTA 入口、加载发起、触发、依赖等待、CTA 出口等位置插入计时探针，完整观测到了 PDL 调度下的内核交接过程：

- 前驱内核的 CTA 按照启动顺序，在不同的 SM 上陆续完成计算并退出；
- 每当有一个 SM 空闲出来，后继内核的 CTA 就可以立刻进驻，开始自己的权重加载；
- 后继内核的 CTA 加载完权重后，会在依赖同步点等待前驱对应的数据准备好；
- 等前驱的数据就绪，后继立刻开始计算。

```
# PDL 滚动尾波调度时序示意图predecessor:  [full grid work.............][straggling CTAs]        free SMs:                                ^   ^   ^   ^        successor:                              [admit][load][wait]...[compute]
```

整个过程就像波浪一样，前驱的尾波和后继的首波在 SM 层面上交替前进，没有任何 SM 出现空闲。权重加载的时间完全隐藏在前驱 CTA 陆续退出的时间差里，不会占用额外的关键路径时间。

### 5.2 关键观测结论

> 通过观测，研究团队得到了几个关键结论，彻底澄清了 PDL 的工作机制。

- 第一，所有 240 个观测到的内核边界，都至少有一个后继 CTA 在前驱网格的最后一个 CTA 退出之前就已经准入。
- 第二，同一个 SM 上，后继 CTA 一定会等前驱 CTA 完全退出后才会进入，不会出现两个 CTA 共存的情况，完全符合硬件资源限制。
- 第三，同一 SM 上，前驱退出到后继准入的最短延迟只有 0.256 微秒，几乎是无缝衔接。
- 第四，每个运行中，63 到 75 个边界都会在前驱网格结束前就发起至少一个后继的权重或 KV 加载。

这些观测证明，PDL 没有打破 SM 的硬件资源限制，反而**利用了网格层面的执行时间差，通过滚动调度实现了流水线重叠。**

::: block-1
总之，PDL 的性能收益不是来自 SM 资源的超用，而是:mdnice-highlight[通过滚动尾波调度消除了 SM 的空闲间隙]。它把原本集中的内核启动开销打散到了前驱内核的执行末尾，让整个 GPU 的计算流水线保持连续。
:::

## 六、三个失效的优化思路与背后的技术陷阱

> 追回 82.8%的性能后，剩下的 17.2%差距还有没有办法弥补？研究团队尝试了三个看似非常合理的优化方向，结果全部失效，甚至带来了反效果。

这三个尝试不仅解释了为什么剩下的差距难以弥合，也揭示了 GPU 架构下很多看似正确的优化其实是陷阱，对工程实践有很强的指导意义。

### 6.1 尝试一：让两个相邻内核共驻同一个 SM

> 第一个思路很直接：既然 SM 是逐个空闲的，那能不能让两个 CTA 同时驻留在一个 SM 上，进一步提高重叠度？

为了验证这个思路，研究团队做了一个机制性对照实验：:mdnice-bold-italic[通过调整共享内存大小，控制是否允许两个 CTA 共驻。结果发现，在默认依赖下，允许共驻几乎没有性能变化；在 PDL 调度下，允许共驻能带来 51 微秒的收益。]

![文章插图](/articles/2026-08-31-megakernel-cuda-pdl-97-4-aa5c9945/images/07.jpg)

::: image-caption
表 4 默认依赖与全边缘 PDL 两种模式下，允许单 SM 共存两个 CTA、强制单 SM 仅一个 CTA 时的延迟，以及阻塞共存带来的性能损失比例。该表通过控制共享内存配额的对照实验，验证了同 SM 多 CTA 共存对 PDL 调度的性能贡献，同时明确该收益仅存在于简化诊断场景；真实模型内核因寄存器与共享内存占用更高，无法实现同 SM 共存，这也解释了真实场景下 PDL 与持久化方案仍存在剩余性能差距的原因。
:::

但这只是诊断实验的结果，真实的算子无法实现共驻。因为原始的 ThunderKittens 算子每个 CTA 需要 208KB 共享内存和大量寄存器，H100 的单个 SM 根本放不下两个完整的 CTA。如果为了共驻而缩小算子的共享内存和寄存器使用，就会改变算子本身的流水线，导致单算子性能下降。

后续的微块化（micro-tiled）优化也验证了这一点：把输出投影算子的寄存器从 88 个压缩到 37 个，确实实现了双 CTA 共驻，但单算子性能下降了 3.42%，再加上共驻带来的资源竞争，最终整体性能反而比单 CTA 版本更差。

### 6.2 尝试二：用虚拟张量并行细化依赖粒度

> 第二个思路来自 megakernel 内部的细粒度调度：megakernel 可以在算子内部的分块（tile）级别做同步，不需要等整个张量计算完就启动下一个算子的部分计算。这种模式被称为虚拟张量并行（VTP）。

```
# 虚拟张量并行（VTP）的分片结构与同步逻辑示意图up/gate output:   [ shard 0 ][ shard 1 ][ shard 2 ][ shard 3 ]                                 |          |          |          |        ready counter:         signal 0   signal 1   signal 2   signal 3                                 |          |          |          |        down projection:      split-K 0  split-K 1  split-K 2  split-K 3
```

研究团队在 MLP 层做了验证：把 up/gate 的输出分成 4 个分片，每个分片计算完就发出信号，对应的 down 投影分片可以提前开始，不需要等整个 up/gate 层做完。

![文章插图](/articles/2026-08-31-megakernel-cuda-pdl-97-4-aa5c9945/images/08.jpg)

::: image-caption
表 6 相同生产者配置下，采用全网格 PDL 等待与按分片信号等待两种模式的主体延迟，以及相对于持久化主体的性能差距。 适。该表验证了虚拟张量并行（VTP）细粒度依赖调度的实际效果，证明在当前 PDL 的网格级调度粒度下，更细粒度的算子内分片同步会引入额外的轮询与通信开销，反而导致性能退化，说明调度粒度并非越细越好，需要平衡同步开销与重叠收益。
:::

结果出乎意料，更细粒度的依赖反而让性能下降了 4.886 微秒。**原因在于，PDL 已经让整个 down 投影网格提前启动，权重加载已经完全隐藏了**。而细粒度的分片同步需要额外的轮询开销，反而增加了等待时间，得不偿失。

### 6.3 尝试三：缩小内核资源占用实现共驻

> 第三个思路是缩小内核的资源占用，让两个内核可以同时放在一个 SM 里。研究团队对输出投影算子做了微块化（micro-tiled）优化，将每个线程的寄存器使用从 88 个降到 37 个，从硬件上满足了双 CTA 共驻的条件。

![文章插图](/articles/2026-08-31-megakernel-cuda-pdl-97-4-aa5c9945/images/09.jpg)

::: image-caption
表 5 16 层权重的输出投影（Opcode-4）算子链，在原始单 CTA/SM、微块化允许双 CTA/SM、微块化阻塞共存三种配置下，分别采用默认边缘与 PDL 边缘调度的延迟数据。 该表验证了 “缩小内核资源占用以实现同 SM 共存” 思路的实际效果，证明即使通过微块化满足了硬件共驻条件，计算流水线破坏带来的单算子性能下降，加上双 CTA 的资源竞争开销，最终会抵消调度收益，整体性能反而低于原始单 CTA 的 PDL 版本，佐证了 “共驻优化得不偿失” 的结论。
:::

但最终的结果是，共驻版本的性能反而比单 CTA 版本差。

- 一方面，微块化（micro-tiled）本身带来了 3.42%的单算子性能损失；
- 另一方面，两个 CTA 共驻会带来资源竞争，进一步拖慢执行速度。

最终两者叠加，反而不如单 CTA 的 PDL 版本快。

::: block-1
回顾一下这三个失败的尝试，可以得到一个重要结论：:mdnice-highlight[所有能让内核共驻的优化，都会改变算子本身的计算流水线，带来单算子性能损失]。最终的收益无法抵消损失，这也是剩下的性能差距难以通过纯软件优化弥合的核心原因。
:::

## 七、剩余 2.7%差距的本质与未来方向

> 最终 PDL 版本和持久化版本还有 26.584 微秒的差距，对应 2.7%的性能损失。**这部分差距不是调度优化可以解决的**，它触及了当前 CUDA 编程模型的底层边界。

这部分差距本质上是持久化状态的复用价值，是当前普通内核模型无法复刻的部分。具体来说，包含四个层面的差异，也指向了未来编程模型和硬件架构的演进方向。

### 7.1 剩余差距的四个来源

| 差异点 | 说明 |
| --- | --- |
| 资源生命周期的差异 | 持久化方案里，寄存器、共享内存、屏障、加载器角色都是跨算子复用的，每个内核边界都会销毁和重建这些资源，带来固定开销。 |
| 资源持有粒度的差异 | 持久化方案可以在算子内部就释放不用的资源，比如加载完权重就释放加载器的资源；而普通内核必须等整个 CTA 结束才能释放所有资源，资源释放的粒度太粗。 |
| CTA 准入和初始化开销 | 每个内核都需要重新做 CTA 调度和初始化，这部分开销是网格级别的，无法通过 PDL 消除。 |
| 调度上下文的差异 | 持久化方案有常驻的片上调度器，可以直接派发下一条指令；而普通内核必须通过网格级的程序端口启动，调度粒度更粗。 |

### 7.2 缺失的硬件原语：阶段作用域的资源生命周期

研究团队指出，**当前 CUDA 编程模型缺少一个关键原语：阶段作用域的资源生命周期**。也就是说，:mdnice-bold-italic[当加载器用完共享内存或寄存器后，应该可以在算子内部就释放这些资源，不需要等整个内核结束。]

::: block-1
如果有了这个原语，后继内核的加载器就可以提前进驻 SM，利用前驱内核释放的资源继续工作，不需要等整个 CTA 退出。这样就可以在不改变算子计算流水线的前提下，进一步缩小和持久化方案的差距。
:::

### 7.3 演进方向的启示

> 这项研究最大的启示在于，**重新定义了 megakernel 的价值边界。对于大多数场景，我们不需要完整的常驻解释器，只需要利用好 PDL 这样的调度原语，就可以拿到绝大多数的性能收益**，同时保留普通内核的可维护性、可组合性和通用性。

而剩下的性能差距，也指明了未来 GPU 架构和编程模型的演进方向：**更细粒度的资源管理、更灵活的内核启动机制、更丰富的调度原语。**

::: block-1
整体看下来，这项研究用扎实的实验量化了 megakernel 的性能本质，证明:mdnice-highlight[绝大多数性能收益来自调度优化而非持久化本身]。81 个普通内核通过 PDL 调度就能达到 97.4%的持久化性能，这一结论为 GPU 推理延迟优化提供了全新的思路，也让我们对 megakernel 技术的价值有了更清醒的认知。
:::
