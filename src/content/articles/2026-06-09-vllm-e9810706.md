## 一、为什么 vLLM 冷启动是行业痛点？

> 在 Serverless LLM 服务成为主流的今天，冷启动延迟已经成为影响用户体验和服务成本的最关键因素之一。当流量出现突发峰值时，云厂商需要快速启动新的容器实例来处理请求，但一个冷启动的 vLLM 实例往往需要几十秒才能准备就绪，这会直接导致**首字延迟（TTFT）飙升**，甚至出现请求超时。

vLLM 作为当前业界事实上的标准推理引擎，凭借 PagedAttention、连续批处理等技术极大地提升了推理吞吐量，:mdnice-bold-italic[但它的启动过程却一直缺乏系统性的理解。社区中大量关于启动慢的 issue 和讨论，大多是基于经验的零散优化，没有从根本上解决问题]。更令人惊讶的是，不同版本的 vLLM 启动时间差异巨大：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/04.webp)

::: image-caption
图1 | 在H100显卡上运行OPT6.7B模型时，不同vLLM版本的启动耗时（数值越低代表启动性能越好）。该图表统计了1.5年内9个主流vLLM版本的启动耗时，数据显示版本间最大耗时差距达4倍，v0.9至v0.10版本更是实现启动耗时减半。这反映出vLLM高速迭代过程中，V1接口、torch.compile等新架构、新功能会大幅改变冷启动性能。版本性能的剧烈波动，也直接论证了对vLLM启动流程做系统性拆解分析的必要性。同时该组数据可作为版本迭代的性能基线，帮助开发者评估新功能对冷启动的负面影响，指导版本优化方向。
:::

从图中可以看到，过去 1.5 年里 vLLM 的启动时间从 v0.3.1 的 35.77 秒降到了 v0.10.0 的 7.8 秒，有超过**4 倍的波动**，v0.9 到 v0.10 版本更是直接减半。:mdnice-bold-italic[这说明 vLLM 的冷启动优化空间巨大，但也反映出之前对启动过程的理解非常有限。]

## 二、vLLM 启动过程的六大步骤全拆解

> 论文的核心贡献之一，是**第一次将 vLLM 的启动过程清晰地分解为 6 个独立的、可量化的步骤，并明确了每个步骤的资源瓶颈**。整个启动过程定义为从引擎初始化开始，到打印"Application startup complete"为止的总时长。

我们以 Llama3.2-3B 模型在 H100 GPU 上的启动为例，来看完整的延迟分解：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/05.webp)

::: image-caption
图2 | 基于Llama3.2-3B模型的vLLM启动耗时拆解图。该图将vLLM完整启动流程划分为六大核心步骤，整体启动总时长为20.32秒，并标注每个环节的资源占用类型。实验证实，仅KV缓存探测、CUDA图捕获两个环节由GPU主导，其余全部步骤均为CPU瓶颈，这是本文核心结论之一。各子步骤的耗时占比清晰展现：框架初始化、Torch编译等CPU侧流程是冷启动的主要耗时来源。这套步骤拆解框架成为后续所有环境变量测试的基础，也为开发者针对性优化冷启动指明了具体发力环节。
:::

这张图直接推翻了很多人的直觉：**前 4 个步骤全部是 CPU-bound，只有最后 2 个步骤是 GPU-bound**。也就是说，:mdnice-bold-italic[即使你把 GPU 从 L40S 升级到 H100，大部分启动步骤的速度也不会有任何提升]。

> 下面我们逐个深入讲解每个步骤的工作原理、瓶颈和缩放规律。

### 2.1 vLLM 框架引导（Framework Bootstrapping）

这是启动的第一个步骤，负责配置运行环境，包括 4 个子步骤：

1. **平台检测**：探测可用的硬件后端（如 CUDA），确定执行环境
2. **依赖导入**：加载 PyTorch、Transformers 等核心依赖库
3. **获取模型信息**：从本地或 HuggingFace 下载模型配置和 tokenizer 元数据
4. **Worker 初始化**：通过 Ray 或 Python 多进程启动主 Worker，设置 IPC 和 GPU 上下文

::: block-1
**关键发现**：这个步骤的延迟与模型大小、架构完全无关，只由 vLLM 的内部实现决定。值得注意的是，v0.11 版本引入的**ModelClass 缓存** 功能，将"获取模型信息"子步骤从原来的 4.47 秒大幅降低到了 0.12 秒，这是一个非常显著的优化。
:::

### 2.2 Tokenizer 初始化

> Tokenizer 负责将原始文本转换为模型可以处理的数字 ID。启动过程中只需要加载 tokenizer 的词汇表文件和配置，构建内部的分词逻辑。

![文章插图](/articles/2026-06-09-vllm-e9810706/images/06.webp)

::: image-caption
图3 | 分词器大小（括号内为对应数值）与分词器初始化时间之间的强线性关系图。该图结合柱状图与拟合曲线，得出二者皮尔逊相关系数高达0.99，线性关联极强。实验验证SentencePiece、BPE等不同分词算法对初始化耗时几乎无影响，分词文件体积才是决定性因素。通义千问全系模型分词器大小一致，初始化耗时也完全相同，进一步佐证该规律。对于推理服务而言，精简词表、压缩分词文件是优化该环节的简单有效手段，该结论也可迁移到所有搭载外置分词的大模型推理框架中。
:::

#### 核心结论

- Tokenizer 初始化时间与**tokenizer 文件大小** 呈完美线性关系，皮尔逊相关系数（PCC）=0.99
- 词汇表大小是决定 tokenizer 大小的最主要因素，tokenizer 类型（如 SentencePiece vs BPE）几乎没有影响
- 例如，Llama3 系列使用 128K 词汇表，tokenizer 大小为 8.7MB，初始化时间约 0.29 秒；而 Llama2 系列使用 32K 词汇表，初始化时间仅 0.08 秒

#### 皮尔逊相关系数公式解释

$$
r = \frac{\sum_{i=1}^{n}(x_i - \bar{x})(y_i - \bar{y})}{\sqrt{\sum_{i=1}^{n}(x_i - \bar{x})^2}\sqrt{\sum_{i=1}^{n}(y_i - \bar{y})^2}}
$$

其中 $x_i$ 和 $y_i$ 是第 i 个样本的两个变量值，$\bar{x}$ 和 $\bar{y}$ 是它们的平均值。PCC 取值范围为[-1, 1]，绝对值越接近 1 表示线性关系越强。

### 2.3 模型加载

> 模型加载分为两个子步骤：初始化模型结构和加载预训练权重。

- **模型结构初始化**：在内存中创建模型的层、注意力块和激活函数，这个步骤与模型参数大小无关，所有模型都稳定在 0.1±0.05 秒
- **权重加载**：将预训练参数从检查点文件传输到 GPU 内存，这是模型加载步骤的主要瓶颈

![文章插图](/articles/2026-06-09-vllm-e9810706/images/07.webp)

::: image-caption
图4 | 模型参数量大小与权重加载时间之间的强线性关系图。本组实验基于预热内存缓存环境，排除磁盘I/O干扰，最终得出二者皮尔逊相关系数为1，呈现完全线性关系。在FP16精度下，模型参数量每增长十亿，权重加载耗时同步稳定增加。模型架构、注意力机制不会影响该环节速度，仅数值精度、量化方案会改变数据体积进而影响耗时。该规律可实现权重加载耗时的精准预估，也为集群内存带宽规划、大模型部署方案设计提供了可量化的参考依据。
:::

#### 核心结论

- 权重加载时间与**模型参数大小** 呈完美线性关系（PCC=1.00）
- 数值精度会直接影响加载时间：例如，使用 4 位量化可以将模型大小减少 75%，加载时间也会相应减少
- 图中的数据是在 Linux 缓冲区缓存预热后的结果（即模型文件已经在 DRAM 中），如果直接从 SSD 加载，这个步骤会变慢约 50%

### 2.4 Torch 编译（torch.compile）

> 这是 v0.7 版本引入的重大优化，它将 Python 级别的执行转换为优化的低级内核，大幅提升了推理吞吐量，但也带来了巨大的启动开销。这个步骤分为两个子步骤：

1. **Dynamo 字节码转换**：捕获 Python 字节码并转换为中间表示（IR）
2. **加载/存储编译图**：将 IR 编译为 GPU 内核，并缓存到文件系统中

![文章插图](/articles/2026-06-09-vllm-e9810706/images/08.webp)

::: image-caption
图5 | 编译图大小（括号内单位为KB）与Dynamo转换时间之间的强线性关系图。该图针对torch.compile中的Dynamo字节码转换环节展开分析，皮尔逊相关系数为0.96。编译图总大小可以直观表征模型层数与单网络层复杂度，同架构模型层数越多，编译图体积越大，转换耗时越长。Llama2-7B与Llama2-13B的对比也验证了网络层数是核心变量。该环节属于纯CPU运算，也是vLLM引入torch.compile后新增的主要耗时点，而开启编译图缓存可直接规避该开销，这也是热启动速度远快于冷启动的关键原因。
:::

![文章插图](/articles/2026-06-09-vllm-e9810706/images/09.webp)

::: image-caption
图6 | 编译图大小与编译图加载时间之间的强线性关系图。该环节皮尔逊相关系数为0.95，加载耗时与编译图体积严格线性相关。实验发现模型参数量不会影响加载速度，模型架构、网络层数决定编译图大小，因此同架构、不同参数量的模型，编译图加载耗时基本持平。该步骤在编译图缓存命中时开销极低，是vLLM热启动性能优异的重要保障。基于该规律，对编译图进行分片存储、文件精简，能够进一步降低该环节的加载延迟，适配大规模集群部署场景。
:::

核心结论：

- 两个子步骤的时间都与**编译图总大小** 呈强线性关系（PCC 分别为 0.96 和 0.95）
- 编译图大小主要由模型的层数和每层的复杂度决定，与模型参数大小没有直接关系
- 例如，Llama2-13B 比 Llama2-7B 层数更多（40 vs 32），所以编译时间更长（5.97 秒 vs 4.86 秒）

缓存的重要性：如果关闭编译缓存，强制每次启动都重新编译，这个步骤的时间会从 3-6 秒飙升到 11-21 秒，几乎占总启动时间的一半以上。

### 2.5 KVCache 性能分析

> KVCache 用于存储注意力机制生成的过去键值张量，避免重复计算。启动过程中，vLLM 会执行一个**dummy 前向传播** 来测量峰值内存使用量，从而确定可以分配给 KVCache 的最大 GPU 内存。

为了准确测量这个步骤的固有延迟，论文特意关闭了 torch.compile，排除了编译开销的干扰：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/10.webp)

::: image-caption
图7 | 不同模型的KV缓存探测耗时图。内嵌子图为关闭torch.compile后，仅针对非混合专家（MoE）模型拟合的线性回归曲线（图中黄色、橄榄色点位分别为通义千问、深度求索MoE模型，未参与拟合）。关闭编译开销后，常规Transformer模型的KV缓存探测耗时与参数量线性相关，皮尔逊相关系数为0.92。但MoE模型因存在动态专家激活、负载均衡机制，额外增加运算量，脱离该线性规律。KV缓存探测依靠模拟前向传播测算显存上限，是防止推理显存溢出的必要步骤。MoE模型的特殊性使其冷启动优化难度更高，也意味着针对这类模型需要单独设计探测逻辑与优化策略。
:::

核心结论：

- 对于普通 Transformer 模型，KVCache 分析时间与**模型参数大小** 呈线性关系（PCC=0.92）
- MoE 模型会偏离这个趋势，因为它们的动态专家激活和负载均衡机制增加了 dummy 运行的复杂度
- 这个步骤是第一个 GPU-bound 的步骤，但占总启动时间的比例很小（约 5-8%）

### 2.6 CUDA 图捕获

> 这是启动的最后一个步骤，vLLM 会执行另一个 dummy 前向传播，将推理内核的执行序列（包括内存分配、注意力计算等）记录为一个 CUDA 图。之后的推理请求可以直接重放这个图，避免了重复的内核启动开销和 CPU-GPU 同步。

![文章插图](/articles/2026-06-09-vllm-e9810706/images/11.webp)

::: image-caption
图8 | 模型参数量大小与CUDA图捕获时间之间的强线性关系图。二者皮尔逊相关系数达到0.99，线性特征十分显著。CUDA图需要完整录制推理阶段的所有GPU指令，模型参数量越大，运算节点越多，录制耗时就越长。该环节是少数由GPU主导的启动步骤，虽然GPU算力会小幅影响速度，但模型规模仍是第一影响因素。CUDA图仅在冷启动阶段录制，热启动会直接复用，因此该步骤仅影响冷启动延迟，不会干扰线上常态推理的性能与吞吐。
:::

![文章插图](/articles/2026-06-09-vllm-e9810706/images/12.webp)

::: image-caption
图9 | 基于Llama2-7B模型，不同批大小数量对应的CUDA图捕获耗时图（Touvron等人，2023）。CUDA要求为每一种独立批大小单独录制CUDA图，因此批大小的种类越多，整体捕获耗时越高，二者皮尔逊相关系数为1。线上推理服务通常需要兼容多批次请求，这会明显拉高冷启动耗时。结合该结论，生产环境可根据业务主流批大小定向录制CUDA图，舍弃低频批次，以此在冷启动延迟与推理灵活性之间取得平衡，是兼顾性能与业务需求的实用部署策略。
:::

核心结论：

- CUDA 图捕获时间与**模型大小** 和**需要捕获的 batch size 数量** 都呈完美线性关系（PCC 分别为 0.99 和 1.00）
- 每个唯一的 batch size 都需要单独捕获一次 CUDA 图，因此在生产环境中应该只捕获实际需要的 batch size，避免不必要的开销

## 四、环境因素对启动时间的影响

论文全面评估了 GPU、CPU、存储和权重加载方式对启动时间的影响，得出了很多反常识的结论。

### 4.1 GPU 真的不重要吗？

> 论文对比了 H100 和 L40S 两种 GPU 在相同 CPU 配置下的启动时间：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/15.webp)

::: image-caption
图10 | H100（节点n1）与L40S（节点n2）显卡下各启动步骤性能对比，所有数值均以H100为基准做归一化处理。归一化数据显示，绝大多数启动步骤在两款GPU下性能几乎无差异，仅CUDA图捕获环节H100实现1.2倍加速。这直接证实vLLM冷启动整体为CPU瓶颈，即便H100的理论浮点算力远超L40S，也无法提升整体启动速度。GPU仅在CUDA捕获、KV探测这类纯运算环节发挥作用，其余CPU密集步骤不受GPU型号影响。该结论为硬件选型提供关键指导：优化冷启动应优先选用高性能CPU，而非高端GPU。
:::

::: block-1
**惊人发现**：除了 CUDA 图捕获步骤有 1.2 倍的提升外，其他所有步骤在 H100 和 L40S 上的表现几乎没有差异！这说明**GPU 的计算能力对 vLLM 启动时间的影响微乎其微**，因为大部分工作都是 CPU 在做。
:::

### 4.2 CPU 才是真正的瓶颈

> 相比 GPU，CPU 的影响要大得多。论文对比了 AMD EPYC 9354 和 Intel Xeon Platinum 8568Y+两种 CPU 搭配 H100 GPU 的表现：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/16.webp)

::: image-caption
图11 | 搭配H100显卡时，AMD EPYC 9354（节点n1）与Intel Xeon Platinum 8568Y+（节点n3）两款CPU的性能对比图。更换CPU带来的性能波动远大于更换GPU，再次验证CPU是vLLM冷启动的核心瓶颈。两款CPU各有所长：AMD在分词器、模型初始化环节速度更快，英特尔则在Dynamo转换、CUDA图捕获阶段表现更优。这种差异源于两款CPU的微架构、指令集与系统调度机制不同。整体总耗时差距明显，说明CPU选型、架构针对性调优是降低冷启动的核心方向，后续版本优化也需要针对不同CPU做适配。
:::

可以看到，不同的 CPU 在不同步骤上表现各异：

- AMD 在 Tokenizer 初始化和模型初始化上更快
- 而 Intel 在 Dynamo 转换和 CUDA 图捕获上更快

总体来看，**CPU 的单核性能是决定 vLLM 启动时间的关键因素**，因为大部分启动操作都是单线程执行的：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/17.webp)

::: image-caption
图12 | 运行通义千问4B模型时，vLLM启动过程中各CPU核心的使用率变化，采样间隔为100毫秒。CPU核心使用率热力图显示，vLLM启动全程至少有一个CPU核心处于满载状态，极少出现多核心同时满载的情况。这说明冷启动的绝大部分代码逻辑为串行执行，并行度极低，无法利用多核算力。即便服务器配备数十核CPU，也难以通过多核并行加速启动。该特性解释了为何CPU单核主频、单线程性能是选型关键，同时也指明优化方向：对串行初始化、编译步骤做并行化改造，可有效提升启动速度。
:::

这张热力图非常直观地展示了 vLLM 启动过程的单线程特性：:mdnice-bold-italic[在整个启动过程中，始终只有一个 CPU 核心达到 100%的使用率，其他核心大部分时间都处于空闲状态。这说明 vLLM 的启动流程还有很大的并行化优化空间。]

### 4.3 存储与权重加载方式的影响

- **SSD vs DRAM**：如果直接从 SSD 加载模型权重，而不是从预热的 Linux 缓冲区缓存中加载，模型加载步骤会变慢约 50%。但由于模型加载只占总启动时间的 7-10%，所以总启动时间只慢了约 4%。
- **不同权重加载方式**：论文对比了三种主流的权重加载方式：

![文章插图](/articles/2026-06-09-vllm-e9810706/images/18.webp)

::: image-caption
图13 | 模型权重从固态硬盘（SSD）读取时，对vLLM各启动步骤产生的影响图。本图以内存加载为基准做归一化，结果显示仅模型加载步骤出现明显减速，耗时翻倍，其余步骤几乎不受SSD影响。由于模型加载仅占总启动时长的7%-10%，因此全局耗时仅增加4%。这表明vLLM冷启动只有权重加载属于I/O密集型环节，编译、初始化等CPU任务对磁盘速度不敏感。在频繁冷启动的容器化场景中，将模型缓存至内存是性价比最高的优化方式，可彻底规避SSD带来的延迟问题。
:::

::: block-1
**结论**：CoreWeave Tensorizer 的性能最好，比默认的 Safetensors 快 40-47%，因为它可以直接把张量加载到 GPU 内存，不需要经过 CPU 的中间 staging。Run:ai Model Streamer 通过重叠 I/O 和 GPU 传输，也能获得约 20%的提升。
:::

## 五、白盒预测模型：精准预估冷启动时间

> 基于对每个启动步骤的深入理解，论文构建了一个**模块化的白盒线性回归预测模型**，可以根据模型配置和硬件环境精准预估 vLLM 的启动时间。

![文章插图](/articles/2026-06-09-vllm-e9810706/images/19.webp)

::: image-caption
图16 | 本文所提出的启动耗时预测器的整体工作流程图。该预测器分为四大流程：采集模型与硬件配置、长时间采集实测耗时、分步骤训练回归模型、毫秒级输出预测结果。模块化白盒设计区别于传统黑盒模型，每个步骤的预测逻辑均可追溯，便于排查预测偏差。该工具不仅能预估冷启动耗时，还可评估vLLM休眠模式等优化方案的效果。在无服务器推理的自动扩缩容场景中，它可提前预判实例启动耗时，帮助平台规避流量峰值下的冷启动卡顿，提升服务稳定性。
:::

### 5.1 模型设计

> 模型的核心思想是：:mdnice-bold-italic[每个启动步骤都有清晰的线性依赖关系，因此可以为每个步骤单独训练一个线性回归器，然后将它们的预测结果相加得到总启动时间。]

这种设计有两个巨大的优势：

1. **可解释性强**：可以清晰地看到每个参数对总启动时间的贡献
2. **易于维护**：当 vLLM 某个步骤的实现发生变化时，只需要重新训练那个步骤的模型即可，不需要重新训练整个模型

## 六、核心创新与实践优化建议

### 6.1 主要工作与创新

1. **首次系统性分解**：第一次将 vLLM 的启动过程分解为 6 个清晰的、可量化的步骤，明确了 CPU 是主要瓶颈
2. **线性缩放规律**：发现每个步骤都有可解释的线性缩放规律，与特定参数强相关
3. **白盒预测模型**：构建了模块化的白盒预测模型，准确率高且可解释
4. **全面环境评估**：全面评估了不同硬件、软件配置的影响，给出了可操作的优化方向

### 6.2 生产环境优化建议

> 基于论文的研究结果，总结出以下最有效的冷启动优化方法：

1. **优先提升 CPU 单核性能**：而不是盲目升级 GPU，这是目前最有效的优化方向
2. **始终启用并持久化 torch.compile 缓存**：这可以将编译步骤的时间减少 70%以上
3. **使用 CoreWeave Tensorizer 加载权重**：比默认的 Safetensors 快 40-47%
4. **优化 Tokenizer**：尽可能使用小词汇量的模型，或者预加载 tokenizer
5. **只捕获必要的 batch size**：减少 CUDA 图捕获的时间
6. **并行化启动步骤**：例如同时加载权重和编译计算图，利用空闲的 CPU 核心
