加群可复现性是科学进步的基石。然而，要从大型语言模型（LLM）中获得可复现的结果却异常困难。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/04.webp)

例如，你可能会发现，向 ChatGPT 重复提出相同问题，得到的结果却不同。这本身并不奇怪，因为从语言模型中获取结果的过程涉及“采样”——即把语言模型的输出转化为概率分布，并基于概率选择一个 token（词元）的过程。

更令人惊讶的是，即便我们将温度参数（temperature，用于控制采样随机性的参数，值为 0 时模型会选择概率最高的 token，即贪心采样）调低至 0，从理论上使采样过程具有确定性，但是，LLM 的 API 在实际使用中仍然**不具备** 确定性（参见过往讨论Non-determinism in GPT-4 is caused by Sparse MoE[1]、A question on determinism[2]或How to make your completions outputs consistent with the new seed parameter[3]）。即便在自有硬件上使用开源推理库（如 vLLM 或 SGLang）运行推理，采样过程依旧不具备确定性（参见Frequently Asked Questions | vLLM或Troubleshooting and Frequently Asked Questions | SGLang[4]）。

但为何 LLM 推理引擎不具备确定性呢？一种常见假设认为，浮点数的不可结合性（指浮点数运算中 $(a + b) + c \neq a + (b + c)$）与并发执行相结合，会导致非确定性——具体取决于哪个并发核心先完成计算。我们将这种解释称为 LLM 推理非确定性的“并发+浮点数”假设。例如，最近一篇文章《Give Me FP32 or Give Me Death? Challenges and Solutions for Reproducible Reasoning》[5]中写道：

> GPU 中的浮点数运算具有不可结合性，即 $(a + b) + c \neq a + (b + c)$，这是由有限精度和舍入误差导致的。该性质直接影响 Transformer 架构中注意力分数和 logits（模型输出的未归一化概率）的计算——多线程间的并行操作会根据执行顺序产生不同结果。

你也能在其他文献中看到“并发+浮点数”假设的表述，例如A question on determinism[6]，该链接提到“存在速度权衡：为了让用户侧更快拿到计算结果，人们会使用 GPU，而 GPU 会执行并行【非确定性】计算。任何现代 GPU 上的神经网络计算都会受此影响。”，或此处[7]提到，“由于 GPU 高度并行化，每次执行时加法或乘法的顺序可能不同，这些微小差异会逐步累积，导致输出结果不同。”。

**尽管该假设并非完全错误，但它并未揭示全部真相**。例如，即便在 GPU 上，对相同数据重复执行相同的矩阵乘法，总能得到逐位相同的结果。我们显然使用了浮点数，且 GPU 的并发性也很强——为何在这个测试中看不到非确定性呢？

```
# 生成两个2048x2048的随机矩阵，设备为GPU，数据类型为bfloat16（16位脑浮点数）A = torch.randn(2048, 2048, device='cuda', dtype=torch.bfloat16)B = torch.randn(2048, 2048, device='cuda', dtype=torch.bfloat16)# 计算矩阵乘法的参考结果ref = torch.mm(A, B)# 重复执行1000次，验证结果是否与参考结果一致for _ in range(1000):    assert (torch.mm(A, B) - ref).abs().max().item() == 0
```

要理解 LLM 推理非确定性的真正原因，我们需要更深入地分析。

遗憾的是，即便要**定义** “LLM 推理具备确定性”的含义，也并非易事。或许有些反直觉，但以下表述实际上同时成立：

::: block-1
1. GPU 上的部分核函数（kernel，指在 GPU 上执行的核心计算单元）是**非确定性** 的。
2. 然而，语言模型前向传播（forward pass，指模型从输入到输出的计算过程）中使用的所有核函数都是**确定性** 的。
3. 此外，LLM 推理服务器（如 vLLM）的前向传播也可被认为是**确定性** 的。
4. 但从推理服务器使用者的视角来看，结果却是**非确定性** 的。
:::

在本文中，我们将解释为何“并发+浮点数”假设未能触及问题核心，揭露 LLM 推理非确定性的真正根源，并说明如何消除非确定性，在 LLM 推理中获得真正可复现的结果。

## 根源：浮点数的不可结合性

在讨论非确定性之前，有必要先解释为何会存在数值差异。毕竟，我们通常认为机器学习模型是遵循交换律、结合律等结构规则的数学函数——机器学习库难道不应该为我们提供“数学上正确”的结果吗？

问题的核心在于**浮点数的不可结合性**。即对于浮点数而言：

$(a + b) + c \neq a + (b + c)$

```
# 先计算0.1与1e20的和，再减去1e20(0.1 + 1e20) - 1e20>>> 0# 先计算1e20与1e20的差，再加上0.10.1 + (1e20 - 1e20)>>> 0.1
```

颇具讽刺意味的是，正是这种“破坏结合律”的特性，让浮点数变得有用。

浮点数的价值在于它能提供“动态”精度。为便于解释，我们使用十进制（而非二进制）浮点数，其格式为 $\text{尾数（mantissa）} \times 10^\text{指数（exponent）}$，其中尾数保留 3 位数字，指数保留 1 位数字。

例如，数值 3450 可精确表示为 $3.45 \times 10^3$，极小值 0.486 可表示为 $4.86 \times 10^{-1}$。通过这种方式，浮点数既能表示极小值，也能表示极大值。在科学计算中，我们可以说浮点数能保持固定的“有效数字位数”。

若两个浮点数的指数相同，它们的加法与整数加法类似。例如，123（即 $1.23 \times 10^2$）与 456（即 $4.56 \times 10^2$）相加，结果为 579（即 $5.79 \times 10^2$）。

**但如果两个浮点数的指数不同（如 1230 和 23.4），情况会如何呢？** 此时精确结果应为 1253.4，但由于我们一次只能保留 3 位精度，浮点数加法会**舍弃** 最后 2 位数字，得到 $1.25 \times 10^3$（即 1250）。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/05.webp)

::: image-caption
图1：表示 1230 需要 3 位精度，表示 23.4 也需要 3 位精度，但两者相加的结果（1253.4）需要 5 位精度才能精确表示。因此，我们的浮点数格式必须舍弃末尾的“34”——从某种意义上说，我们相当于先将 23.4 近似为 20.0，再进行加法
:::

此时，信息已被丢失。需要注意的是，每次对指数不同（即“量级”不同）的浮点数进行加法时，都可能发生这种情况——而这种操作在实际计算中极为常见。事实上，若能保证所有加法的操作数指数相同，我们直接使用整数即可，无需浮点数！

换句话说，每次以不同顺序累加浮点数，都可能得到完全不同的结果。举一个极端例子：对同一个数组求和，仅因累加顺序不同，就可能得到 102 种不同结果。

```
import random# 定义一个包含正负值的数组vals = [1e-10, 1e-5, 1e-2, 1]vals = vals + [-v for v in vals]# 存储所有可能的求和结果results = []# 设置随机种子以保证可复现性random.seed(42)# 随机打乱数组顺序并求和，重复10000次for _ in range(10000):    random.shuffle(vals)    results.append(sum(vals))# 去重并排序，查看不同结果的数量results = sorted(set(results))print(f"共有 {len(results)} 种不同结果：{results}")# 输出：# 共有 102 种不同结果：[-8.326672684688674e-17, -7.45931094670027e-17, ..., 8.326672684688674e-17]
```

尽管浮点数的不可结合性是数值差异的根本原因，但它并未直接回答“非确定性从何而来”——我们仍需理解：**为何浮点数的累加顺序会变化？这种变化何时发生？又该如何避免？**

答案藏在核函数的实现细节中。

## 为何核函数不总是以相同顺序累加数字？

如前所述，关于“核函数为何以不同顺序累加数字”，一种常见解释是“并发+浮点数”假设：若并发线程的完成顺序是非确定性的，且累加顺序依赖于线程的完成顺序（如使用原子加法时），则累加顺序也会是非确定性的。

> 原子加法（Atomic Add）是一种硬件级操作，用于确保多个并发线程对同一内存地址的累加操作具有原子性 —— 即操作要么完全执行，要么完全不执行，不会被其他线程干扰。其核心特性是正确性保证但顺序无关：硬件确保所有加法都会被计入最终结果，但无法保证不同线程的累加顺序，顺序完全取决于哪个核心先完成计算。例如，在多个线程同时对变量x执行x += 1时，原子加法能避免数据竞争（如两个线程同时读取旧值导致结果错误），但最终x的累加顺序可能因线程调度而不同。

但令人困惑的是，尽管这种情况确实会导致核函数非确定性，**并发（及原子加法）却与 LLM 推理的非确定性完全无关**！要解释真正的根源，我们首先需要理解：为何现代 GPU 核函数很少需要原子加法。

## 何时需要原子加法？

通常，GPU 会在多个“核心”（即流式多处理器，SMs，GPU 的核心计算单元）上并发执行程序。由于这些核心之间没有固有的同步机制，若核心需要相互通信（如所有核心都需向同一个元素累加值），就会面临挑战。此时，可使用“原子加法”（有时也称为"获取-加法，fetch-and-add"）——**这种硬件级操作能保证所有加法操作都被正确处理，但不保证操作顺序。**

具体来说，假设你要用 100 个核心对一个 100 元素的向量做归约（reduction，如`torch.sum()`求和操作）。尽管可以并行加载所有 100 个元素，但最终仍需将结果归约为单个值。一种实现方式是使用“原子加法”原语：硬件保证所有加法都会被处理，但不保证处理顺序。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/06.gif)

::: image-caption
图2：原子加法能确保每个核心的计算结果都被计入最终总和，但不保证这些结果的累加顺序——顺序完全取决于哪个核心先完成计算，而这一过程具有非确定性。因此，对同一个并行程序重复执行多次，可能会得到非确定性的输出
:::

这通常就是人们所说的“非确定性”：对同一个核函数输入完全相同的数据，两次执行却得到不同结果。这种现象被称为“运行间非确定性”（run-to-run nondeterminism）——即同一 Python 脚本在依赖环境完全相同的情况下，两次运行却得到不同结果。

尽管并发原子加法**确实** 会导致核函数非确定性，但**绝大多数核函数都不需要原子加法**。事实上，在 LLM 典型的前向传播过程中，通常**不存在任何原子加法**。

这可能令人惊讶——毕竟原子加法对并行归约有益。但:mdnice-bold-italic[有两个主要原因使得原子加法【并非必需】：]

::: block-1
1. “批量（batch）”维度通常具有足够的并行性，无需在归约维度上并行。例如，若你要归约的不是 1 个 100 维向量，而是 500 个并行的向量，则可让每个核心处理 1 个完整向量的归约，无需核心间通信。
2. 随着时间推移，大多数神经网络库都采用了多种策略，在不牺牲性能的前提下实现确定性。例如，可执行“拆分（或树形）归约”：将 100 元素的归约拆分为 5 个 20 元素的归约（实现 5 路并行），然后对剩余的 5 个结果，要么执行一次非并行的“清理”归约（因元素数量少，开销极低），要么使用信号量（semaphore，确保每个并发线程块以确定性顺序累加）。信号量策略的详细描述可参见NVIDIA/cutlass/issues/1421[8]。
:::

第二个因素提到信号量[9]，我们补充下内容：

> 信号量是协调并发单元（如GPU线程块）的同步原语，靠计数器控制“执行权限”，强制并发操作按固定顺序执行，避免随机顺序引发的问题。在神经网络归约中，若像“拆分归约”那样，把100元素求和拆为5个20元素并行计算，后续子结果合并时，信号量能让5个线程块按预设顺序累加，规避浮点数不可结合性导致的非确定性；而“批量维度并行”（如500个向量各由1个核心归约）无需核心通信，就用不到信号量。它是神经网络库实现“高性能+确定性”的关键策略之一。

得益于这两个因素，对绝大多数神经网络操作而言，避免原子加法的性能损失微乎其微。

仍有少数常见操作若要避免原子加法，会面临显著的性能损失——例如 PyTorch 中的`scatter_add`（即`a[b] += c`）。但在 LLM 中，唯一常用的此类操作是 FlashAttention 的反向传播（backward pass）。

> 趣闻：你知道吗？广泛使用的 FlashAttention 反向传播的 Triton 实现（一种基于 Triton 语言的 GPU 核函数实现），在算法上与 Tri Dao 的 FlashAttention-2论文[10]存在差异！标准 Triton 实现会在反向传播中增加额外的重计算，以避免原子加法，但这会导致计算量（FLOPs）增加 40%！

然而，LLM 的前向传播**不涉及任何需要原子加法的操作**。因此，LLM 的前向传播实际上是“运行间确定性”的。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/07.webp)

::: image-caption
图 3：从推理服务器的视角来看，它是确定性的：若输入的用户请求完全相同，输出也始终相同
:::

维基百科对“确定性算法”的定义是：“给定特定输入，总能产生相同输出的算法”。在此场景下，若输入（即推理服务器处理的请求）完全相同，前向传播的输出也始终相同。

但“前向传播本身具有确定性”，并不足以保证包含它的整个系统具有确定性。例如，若请求的输出依赖于并行处理的其他用户请求（如批量归一化 batch-norm 的情况），则由于单个请求无法预知其他并行请求的内容，从用户视角来看，整个 LLM 推理系统仍是非确定性的！

事实证明，请求的输出**确实** 依赖于并行处理的其他用户请求——这并非因为批量内的信息泄露，而是因为前向传播缺乏“批量不变性”（batch invariance）：单个请求的输出会随前向传播的“批量大小”（即同时处理的请求数量）变化。

### 批量不变性与“确定性”

为解释批量不变性，我们简化系统，仅关注矩阵乘法（matmul）。假设所有矩阵乘法实现都是“运行间确定性”的（尽管不完全绝对，但大多数常见实现都满足这一性质），但它们**不具备批量不变性** ——即当批量大小变化时，批量中的单个元素的计算结果可能不同。

从数学角度看，这是一种反常性质：矩阵乘法在批量维度上应是“独立”的——批量中其他元素的存在，或批量大小的变化，都不应影响单个元素的计算结果。

但实证结果却与此相反：

```
import torch# 设置默认计算设备为GPUtorch.set_default_device('cuda')# 定义批量大小和隐藏层维度B = 2048# 批量大小（batch size）D = 4096# 隐藏层维度（hidden dimension）# 生成两个随机矩阵：a的形状为[B, D]，b的形状为[D, D]a = torch.linspace(-1000, 1000, B*D).reshape(B, D)b = torch.linspace(-1000, 1000, D*D).reshape(D, D)# 方式1：取批量的第一个元素，执行矩阵-向量乘法out1 = torch.mm(a[:1], b)# 方式2：对整个批量执行矩阵-矩阵乘法，再取第一个元素的结果out2 = torch.mm(a, b)[:1]# 打印两种方式结果的最大绝对差值print((out1 - out2).abs().max()) # 输出：tensor(1669.2500, device='cuda:0')
```

需注意的是，这种现象**并非运行间非确定性**：若多次运行该脚本，输出结果始终相同。但它**不具备硬件/软件版本不变性** ——不同 GPU 或 PyTorch 版本可能返回不同值，但在相同环境下结果是确定的。

然而，当非批量不变的核函数被用于更大的推理系统时，整个系统会变得非确定性。当你向推理端（API）发送请求时，服务器的负载（即同时处理的请求数量）对用户而言是“非确定性”的——而负载会决定核函数运行时的批量大小，进而改变单个请求的最终结果！

![文章插图](/articles/2025-10-04-llm-0d359be2/images/08.webp)

::: image-caption
图 4：尽管推理服务器本身可被称为“确定性”的，但从单个用户的视角来看，情况却截然不同：其他并发用户的请求并非系统的“输入”，而是系统的非确定性属性——这使得 LLM 推理从用户视角来看具有“非确定性”
:::

若将核函数的“非不变属性”（如批量大小）与该属性的“非确定性”（如服务器负载）结合，就会得到一个非确定性系统。

换句话说，**几乎所有 LLM 推理端点都具有非确定性的主要原因，是服务器负载（及由此导致的批量大小）的非确定性变化**！这种非确定性并非 GPU 特有——在 CPU 或 TPU 上部署的 LLM 推理端点，也会存在这一来源的非确定性。

因此，若要消除推理服务器的非确定性，我们必须实现核函数的批量不变性。要理解如何实现这一点，首先需要明确：为何核函数天生不具备批量不变性？

## 如何实现核函数的批量不变性？

要实现 Transformer 模型的批量不变性，需确保所有核函数都具备批量不变性。幸运的是，我们可假设所有逐点操作（pointwise operation，指对每个元素独立执行的操作，如激活函数）都是批量不变的

> 尽管这在 PyTorch 等库中成立，但并非本质属性——例如，CPU 上的某些核函数实现可能对数组的不同部分使用向量化指令和非向量化指令，而这些指令的数值结果未必逐位相同。

因此，我们只需关注 3 种涉及归约的操作：RMS 归一化（RMSNorm）、矩阵乘法（matrix multiplication）和注意力机制（attention）。

> 与并行性相关的归约不在本次讨论范围内，但相同的原则同样适用。一个可能有用的趣闻是，在Blackwell以及配备CUDA 12.8+的Hopper上，NVLink-Sharp的交换机内归约是确定性的。和许多事情一样，这些信息可以在NCCL的GitHub issue[11]上找到。

有趣的是，这 3 种操作的批量不变性实现难度呈递增顺序——每种操作都需要额外的考量，才能在保证批量不变性的同时维持合理性能。我们先从 RMSNorm 开始。

### 批量不变的 RMS 归一化

![文章插图](/articles/2025-10-04-llm-0d359be2/images/09.webp)

::: image-caption
图 5：数据并行 RMSNorm。理想情况下，我们希望在并行策略中避免核心间的通信。一种实现方式是将每个批量样本分配给一个核心，确保每个归约操作（如求均值）都在单个核心内完成——这就是“数据并行”策略，即通过在无需通信的维度上并行来提高效率。例如，若有 4 个样本（行）和 4 个核心，每个核心可处理 1 个样本，实现核心的完全利用
:::

RMSNorm 的实现代码如下：

```
# x: [批量大小（batch_size）, 隐藏层维度（hidden_dim）]# weight: [隐藏层维度（hidden_dim）]def rms_norm(x, weight):    # 计算x在最后一个维度（隐藏层维度）上的均方根，再乘以权重    return x * torch.rsqrt(torch.mean(x ** 2, dim=-1, keepdim=True)) * weight
```

批量不变性的核心要求是：**无论核函数的批量大小如何，单个样本的归约顺序必须固定**。这并不意味着必须始终使用相同的归约策略——例如，若归约的元素数量变化，即便归约策略改变，仍可保持批量不变性（The Quack[12]博客文章中展示了多种归约策略的层级关系，如线程归约、warp 归约、块归约、集群归约等）。

因此，仅当批量大小影响归约策略时，才会破坏批量不变性。

我们先分析 RMSNorm 的标准并行策略。通常，并行算法的设计目标是最小化核心间的通信（本文中提及的“核心”可理解为 SMs，更准确地说，关键属性是核函数启动的线程块数量大于 SMs 数量）。一种基础策略是将每个批量样本分配给一个核心，如上图所示。

增大批量大小不会影响归约策略：若批量大小为 200 时，核函数已获得足够的并行性，那么批量大小为 2000 时，并行性会更充足。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/10.webp)

::: image-caption
图 6：更大批量的 data-parallel RMSNorm。将数据并行策略扩展到更大批量非常直接——无需让每个核心仅处理 1 个样本，而是允许每个核心依次处理多个样本。这种方式能【保持批量不变性】，因为单个样本的归约策略未发生变化
:::

相反，减小批量大小可能会带来挑战：由于每个样本分配给一个核心，当批量大小减小到低于核心数量时，部分核心会处于空闲状态。

遇到这种情况时，优秀的核函数工程师会采用前一节提到的解决方案（原子加法或拆分归约），在维持高并行性（进而保证高性能）的同时，避免核心空闲。但遗憾的是，这会改变归约策略，导致核函数失去批量不变性。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/11.webp)

::: image-caption
图 7：拆分归约 RMSNorm。若批量大小很小，数据并行策略可能无法提供足够的并行性来充分利用 GPU。此时，更高效的方式是将单个样本的归约拆分给多个核心，以实现 GPU 的完全利用——但这会【破坏批量不变性】，因为单个样本的归约顺序不再固定
:::

最简单的解决方案是直接忽略这些小批量场景——这并非完全不合理：小批量意味着核函数的执行速度通常很快，即便性能有所下降，影响也不会太大。

若确实需要优化小批量场景，一种思路是：始终采用一种“即便批量极小时也能提供足够并行性”的归约策略。这种策略在大批量场景下会导致并行性过剩，但能在所有批量大小范围内实现尚可（而非峰值）的性能。

### 批量不变的矩阵乘法

![文章插图](/articles/2025-10-04-llm-0d359be2/images/12.webp)

::: image-caption
图 8：数据并行矩阵乘法。与 RMSNorm 类似，矩阵乘法的标准并行策略也是“数据并行”——确保归约操作在单个核心内完成。最直观的方式是将输出张量拆分为二维瓦片（tile），并将每个瓦片分配给不同核心。每个核心只需计算分配给它的瓦片对应的点积（dot product），归约操作仍在单个核心内完成。与 RMSNorm 不同，矩阵乘法的高效实现需要考虑算术强度（arithmetic intensity，即计算量与数据访问量的比值）和张量核心（tensor cores，GPU 中专门用于加速矩阵运算的硬件单元）的利用——这迫使我们通过拆分输出瓦片（而非单个输出元素）来实现并行，而非像 RMSNorm 那样拆分单个样本
:::

本质上，矩阵乘法可视为“逐点操作（元素乘法）+ 归约（求和）”的组合。因此，若我们通过拆分**输出** 瓦片来并行化矩阵乘法，就能得到与 RMSNorm 类似的“数据并行”核函数策略——归约操作仍在单个核心内完成。

与 RMSNorm 类似，当矩阵乘法的“批量”维度（M 和 N，对应输出矩阵的行数和列数）过小时，我们可能需要沿归约维度（K，对应输入矩阵的公共维度）拆分——尽管矩阵乘法有两个“批量”维度，但要充分利用张量核心，每个核心需要处理足够多的计算任务。例如，对于一个[1024, K] × [K, 1024]的矩阵乘法，若采用标准的[128, 128]二维瓦片大小，数据并行策略仅能将其拆分为 64 个核心，远不足以充分利用 GPU。

沿矩阵乘法的归约维度拆分，被称为“拆分 K 矩阵乘法（Split-K Matmul）”[13]——与 RMSNorm 类似，这种策略会破坏批量不变性。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/13.webp)

::: image-caption
图 9：拆分 K 矩阵乘法。若矩阵乘法的批量维度（M/N）较小，数据并行策略可能无法提供足够的并行性，此时需采用拆分 K 矩阵乘法。例如，在上图中，我们将每个归约拆分给两个核心，各自累加后再合并结果——这种方式能利用 8 个核心，实现更高的并行性
:::

> 矩阵乘法还有一种有趣的并行策略称为“stream-k”，其不变性甚至比普通矩阵乘法更差：大多数矩阵乘法库虽不具备批量不变性，但至少具备“批量位置不变性”——即改变样本在批量中的位置，数值结果不会变化；而 stream-k 不具备这一性质，其核心思路是通过对不同输出瓦片采用不同的 K 维度拆分方式，实现更均衡的负载，但这会导致核函数失去批量位置不变性。

矩阵乘法的实现还面临一个额外挑战：张量核心指令。与 RMSNorm 的归约可逐行处理不同，高效的矩阵乘法核函数必须“逐瓦片”处理——每个张量核心指令（如`wgmma.mma_async.sync.aligned.m64n128k16`[14]）的内部归约顺序可能不同。选择不同张量核心指令的原因之一，就是批量大小过小。例如，若使用的张量核心 PTX 指令对应 256 长度的瓦片，但批量大小仅为 32，则大部分计算能力会被浪费；当批量大小为 1 时，最快的核函数通常根本不使用张量核心。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/14.webp)

::: image-caption
图 10：填充张量核心指令。若批量大小过小，可能会出现“输出无法容纳一个完整二维瓦片”的情况。此时，最高效的方式是切换到更小的张量核心指令，或完全不使用张量核心——但这两种选择都会导致核函数失去批量不变性
:::

因此，实现矩阵乘法批量不变性的最简单方式是：编译一个固定配置的核函数，并用于所有输入形状。尽管这会损失部分性能，但在 LLM 推理中，这种损失通常是可接受的。具体来说，拆分 K 矩阵乘法主要在**M 和 N 均较小** 时才需要——而幸运的是，在 LLM 中，N（即模型的维度）通常很大！

![文章插图](/articles/2025-10-04-llm-0d359be2/images/15.webp)

::: image-caption
图 11：尽管实现了批量不变性，与 CuBLAS（默认配置）相比，性能仅损失约 20%——且需注意，这并非优化后的 Triton 核函数（例如未使用 TMA，即 Tensor Memory Accelerator，张量内存加速器）。但性能曲线中的一些模式仍能说明批量不变性需求导致性能损失的原因：首先，在极小批量大小时，性能损失显著，这是因为指令过大且并行性不足；其次，随着批量大小增加，曲线呈现“锯齿状”，这是由量化效应（瓦片和 wave 量化）导致的——通常可通过调整瓦片大小缓解，更多细节可参见：What Shapes Do Matrix Multiplications Like? [medium][15]。
:::

### 批量不变的注意力机制

![文章插图](/articles/2025-10-04-llm-0d359be2/images/16.webp)

::: image-caption
图 12：FlashAttention2 策略。我们沿查询（Q）维度并行，同时对键（K）/值（V）维度执行归约——这意味着整个归约操作可在单个核心内完成，属于另一种数据并行策略
:::

在实现矩阵乘法的批量不变性后，注意力机制的实现面临两个额外挑战——恰如其分地，因为注意力机制包含两个矩阵乘法：

::: block-1
1. 与 RMSNorm 和矩阵乘法仅沿“特征维度”归约不同，注意力机制需同时沿“特征维度”和“序列维度”归约；
2. 受上述特性影响，注意力机制的推理优化（如分块预填充、前缀缓存等）会改变序列的处理方式，进而影响归约顺序。
:::

因此，要实现 LLM 推理的确定性，模型的数值结果不仅需“与同时处理的请求数量无关”，还需“与推理引擎对单个请求的分片方式无关”。

我们首先分析注意力机制的标准并行策略——该策略最初由 FlashAttention2 提出，与 RMSNorm 和矩阵乘法类似，默认策略是“数据并行”：由于注意力机制的归约沿键/值（K/V）张量进行，数据并行策略仅能沿查询（Q）张量并行。

例如，根据推理引擎的选择，一个序列可能被拆分为多个部分处理（如分块预填充，chunked prefill），也可能一次性处理（如不分块的预填充）。要实现“批量不变性”，需保证：**单个 token 的归约顺序，与序列中同时处理的其他 token 数量无关**。若将 KV 缓存（KV cache，用于存储历史 K/V 的缓存）中的 K/V 值与当前处理的 K/V 值分开归约（如 vLLM 的Triton 注意力核函数[16]），则无法满足这一要求。例如，处理序列的第 1000 个查询 token 时，无论 KV 缓存中有 0 个 token（预填充阶段）还是 999 个 token（解码阶段），归约顺序都必须完全相同。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/17.webp)

::: image-caption
图 13：含 KV 缓存的 FlashAttention。将 KV 缓存中的 K/V 值与当前 K/V 值分开处理，会破坏批量不变性，其原因与“边界条件”相关——这一点较为微妙。具体来说，假设你的块大小（block size）为 32，但 KV 缓存中当前有 80 个元素，且需额外处理 48 个未缓存的元素。此时，计算“P 缓存”（P cache，注意力分数的中间结果缓存）需要 3 个块（2 个完整块+1 个掩码块），计算“P”（当前注意力分数）需要 2 个块（1 个完整块+1 个掩码块）——总计 5 个块。但实际上，我们仅需处理 128 个元素（80+48），对应 4 个块——这种不匹配会改变归约顺序。例如，若 KV 缓存中没有元素，且一次性处理 128 个元素，则上述两种场景的数值结果需完全相同，才能保证注意力机制的“批量不变性”
:::

要解决这一问题，我们可在注意力核函数执行前，先更新 KV 缓存和页表（page table），确保无论处理多少个 token，键和值的存储布局始终一致。

结合这一细节（以及前一节提到的所有要点，如固定瓦片大小），我们就能实现批量不变的注意力机制！

然而，这里存在一个显著问题：与矩阵乘法不同，LLM 推理中注意力机制的输入形状，往往需要使用“拆分归约核函数”（通常称为拆分 KV 或 FlashDecoding）。原因是：若不沿归约维度（KV 维度）并行，注意力机制仅能沿批量维度、头维度（head dimension）和“查询长度”维度（query length）并行——而在注意力的解码阶段（decoding stage），查询长度通常很小（如 1），除非批量大小极大，否则无法充分利用 GPU。

遗憾的是，与 RMSNorm 和矩阵乘法不同，我们无法轻易忽略这种场景——例如，若 KV 缓存很长，即便仅处理一个请求，注意力核函数的执行时间也可能非常长。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/18.webp)

::: image-caption
图 14：固定拆分数量的拆分 KV 策略（即 FlashDecode）。当查询长度变得极小时（如解码阶段），核函数的并行性可能会非常低。此时，需再次沿归约维度（KV 维度）拆分——典型策略是：根据所需的并行性，将 KV 维度均匀拆分。例如，若 KV 长度为 1000，需 4 路并行，则每个核心处理 250 个元素。但这会破坏批量不变性，因为具体的归约策略依赖于“单次请求中处理的查询 token 数量”
:::

此外，注意力机制中常用的拆分归约策略，也对批量不变性构成挑战。例如，FlashInfer 的“平衡调度算法”（balanced scheduling algorithm）会选择“能充分利用 GPU 核心的最大拆分大小”，这导致归约策略不具备“批量不变性”。但与 RMSNorm/矩阵乘法不同，仅通过“固定拆分数量”无法解决注意力机制的问题——无论批量大小如何，固定拆分数量都可能导致并行性不足或过剩。

相反，要实现注意力机制的批量不变性，需采用“固定拆分大小”策略：即不固定拆分数量，而是固定每个拆分的大小，拆分数量则根据 KV 长度动态调整。通过这种方式，无论处理多少个 token，归约顺序都能保持一致（这需要对 FlexAttention 进行一些内部修改，目前尚未包含在我们的代码发布中，我们近期将对这些修改贡献到上游！）。

![文章插图](/articles/2025-10-04-llm-0d359be2/images/19.webp)

::: image-caption
图 15：固定大小的拆分 KV 策略。该策略与前一种策略的唯一区别是“拆分大小固定”。例如，若 KV 长度为 1000，不再将其拆分为 4 个 250 长度的拆分，而是拆分为 3 个 256 长度的拆分和 1 个 232 长度的拆分。这种方式能【保持批量不变性】，因为归约策略不再依赖于“单次处理的查询 token 数量”！
:::

我们基于 vLLM 实现了确定性推理的演示——利用 vLLM 的 FlexAttention 后端（一种灵活的注意力机制后端）和 torch.Library（PyTorch 中用于自定义和替换算子的模块）。

通过 torch.Library，我们能以“非侵入式”的方式替换 PyTorch 中大部分相关算子。你可在thinking-machines-lab/batch-invariant-ops[17]中找到“批量不变”核函数库，以及“确定性模式”下运行 vLLM 的示例代码。

## 实验

### 推理结果的非确定性有多严重？

我们使用 Qwen/Qwen3-235B-A22B-Instruct-2507 模型，在温度参数为 0 的条件下，对提示词“Tell me about Richard Feynman”采样 1000 次推理结果（非思考模式），每次生成 1000 个 token。令人惊讶的是，我们得到了**80 种** 不同的结果——其中最常见的结果仅出现 78 次。

分析结果的差异发现：所有结果的前 102 个 token 完全相同！差异首次出现在第 103 个 token：所有结果都生成了“Feynman was born on May 11, 1918, in”，但其中 992 个结果继续生成“Queens, New York”，另外 8 个结果则生成“New York City”。

相反，当我们启用批量不变核函数后，1000 次推理的结果完全相同——这与采样器的数学预期一致，但若无批量不变核函数，我们无法实现这一确定性。

### 性能

我们尚未投入大量精力优化批量不变核函数的性能，但通过以下实验可验证其性能是否“可用”。

我们搭建了一个单 GPU API 服务器，运行 Qwen-3-8B 模型，并发送 1000 个请求（每个请求的输出长度在 90-110 个 token 之间），实验结果如下：

| 配置 | 时间（秒） |
| --- | --- |
| vLLM默认配置 | 26 |
| 未优化的确定性vLLM | 55 |
| + 优化后的注意力核 | 42 |

性能下降的主要原因是：vLLM 中 FlexAttention 的集成尚未经过深度优化。尽管如此，实验结果表明，其性能仍未达到“无法使用”的程度。

### 真正的在线策略强化学习

正如研究者所指出的[18]，训练与推理阶段的数值差异，会隐式地将“在线策略强化学习（on-policy RL）”转化为“离线策略强化学习（off-policy RL）”。

显然，若两次相同的推理请求都无法得到逐位相同的结果，就更不可能让训练与推理阶段的结果逐位相同。因此，确定性推理不仅能消除推理阶段的非确定性，还能修改训练流程，实现“采样与训练阶段的逐位一致性”——最终得到真正的在线策略强化学习。

我们在 Bigmath[19] 数据集上的 RLVR（强化学习视觉推理）设置中进行了实验：强化学习策略基于 Qwen 2.5-VL instruct 8B 模型初始化，最大轨迹长度（max rollout length，指智能体一次交互的最大步数）为 4096。

实验结果表明：若训练时不使用离线策略校正（即重要性加权，importance weighting），奖励会在训练中途崩溃；而加入离线策略校正项后，训练可顺利进行。但如果能实现采样器与训练器的逐位一致性，我们就能完全处于在线策略状态（即 KL 散度为 0），训练同样能顺利进行。

我们还绘制了“采样器与训练器的 logits（未归一化概率）之间的 KL 散度（Kullback-Leibler 散度，用于衡量两个概率分布的差异）”——三种实验设置的行为差异显著：

::: block-1
1. 使用重要性加权时，KL 散度稳定在 0.001 左右，偶尔出现峰值；
2. 不使用重要性加权时，KL 散度会在奖励崩溃的同时出现显著峰值；
3. “真正的在线策略”设置下，KL 散度始终稳定在 0，表明训练策略与采样策略完全一致。
:::

## 结论

> 现代软件系统包含多层抽象。

在机器学习领域，当遇到非确定性和细微的数值差异时，人们往往倾向于“敷衍了事”——毕竟，我们的系统本身已具有“概率性”，多一点非确定性又有何妨？将失败的单元测试的绝对误差容限/相对误差容限（atol/rtol）调大一点，又有什么问题？训练器与采样器的 logits 差异，或许并非真正的 bug，不是吗？

我们反对这种消极态度。只需稍加努力，我们**完全可以** 理解非确定性的根源，甚至解决它！我们希望本文能为社区提供一个清晰的框架，帮助大家理解如何消除推理系统的非确定性，并启发更多研究者深入理解自己所使用的系统。
