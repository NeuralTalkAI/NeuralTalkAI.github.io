## 一、为什么原生 GPU 内核生成是 AI Infra 的核心难题

> 现代 AI 模型的推理与训练效率，**表面上看是架构与算法的竞争，底层实则是 GPU 内核优化能力的比拼。** 每一个新算子的落地、每一次算子融合的优化，都直接决定了硬件的实际利用率，也影响着大模型服务的成本与体验。

### 1.1 手工优化内核跟不上 AI 模型迭代速度

在深度学习发展的早期，主流算子相对固定，厂商提供的官方库基本可以满足需求。比如 NVIDIA 的 cuBLAS、cuDNN 库，针对矩阵乘法、卷积等标准算子做了极致优化，能够接近硬件的理论性能上限。但随着大模型技术的快速发展，这种模式的局限性越来越明显。

一方面，新型算子层出不穷。从 SwiGLU 激活、分组查询注意力，到各种自定义的融合算子，**新的计算模式出现的速度，远远超过了官方库的更新周期**。另一方面，**长尾算子与定制化融合的需求越来越多**。不同的模型架构会有不同的算子组合，手动为每一种组合都编写优化内核，需要大量的资深 GPU 开发工程师，周期长、成本高，根本无法跟上快速迭代的业务需求。

::: block-1
更关键的是，:mdnice-bold-italic[对于 CUDA 之外的新兴硬件生态，这个问题更加突出。国产 GPU、NPU 等加速器的软件栈还在快速发展中，官方算子库的覆盖度和成熟度都不如 CUDA]，大量算子需要手动移植和优化，成为制约国产硬件生态发展的核心瓶颈。
:::

### 1.2 现有方案的固有局限：从编译器到 DSL

> 为了解决算子开发效率的问题，行业已经探索了很多技术路线，最主流的是深度学习编译器和领域特定语言。

深度学习编译器比如 TVM、Ansor，通过将计算图转换为中间表示，然后在优化空间中自动搜索最优的调度方案，实现算子的自动优化。:mdnice-bold-italic[这种方法对于规则的算子效果不错，但对于复杂的融合算子、不规则的计算模式，搜索空间会急剧膨胀，优化效果和效率都大打折扣。]

领域特定语言比如 Triton，提供了比原生 CUDA 更高层的抽象，开发者只需要描述计算逻辑，不需要手动管理线程、内存等底层细节，编译器会自动生成优化后的内核。:mdnice-bold-italic[Triton 大大降低了 GPU 内核的开发门槛，但它本质上还是需要人来编写计算逻辑，对开发者的硬件理解能力仍然有较高要求，而且最终生成的代码性能，和资深专家手写的原生内核相比还是有差距。]

而大模型驱动的内核生成，目标是更进一步：只需要给出 PyTorch 的参考实现，就能自动生成优化后的原生底层内核，完全不需要人工介入。这是算子自动化的终极方向之一，也是当前行业的研究热点。

### 1.3 LLM 生成内核的三座大山

> 虽然方向很美好，但真正落地起来，难度远超普通的代码生成任务，核心有三座难以绕开的大山。

| 难点 | 描述 |
| --- | --- |
| **初始正确率极低（奖励稀疏）** | GPU内核需同时满足编译通过、内存访问合法、数值结果正确、符合硬件执行语义等多重约束，任一错误即完全失败；通用大模型初始生成成功率几乎为零，强化学习常出现整组样本全错，缺乏正向学习信号，难以优化。 |
| **奖励作弊** | 模型易投机取巧，如调用PyTorch已优化算子或使用高层API完成计算——结果正确、速度快，但未生成原生底层内核，本质未完成任务；若反作弊机制薄弱，模型将趋向“作弊高手”而非“内核高手”。 |
| **训练不稳定** | 基于执行反馈的强化学习易发生策略漂移：生成样本的模型（旧策略）与待更新模型（新策略）不一致，随训练推进差异扩大（离策略漂移），导致梯度方差增大、训练震荡甚至崩溃；内核代码长、逻辑复杂，加剧该问题。 |

## 二、MusaCoder 全栈训练框架总览

> 面对原生内核生成的诸多挑战，**MusaCoder 没有选择单一的技术路线，而是搭建了一套从数据到训练、从监督到强化学习的全栈闭环体系。** 整个框架遵循先学会走、再学会跑的渐进式思路，逐步搭建模型的内核生成能力，同时通过多项机制保障训练的稳定性与最终效果。

### 2.1 三段式训练流水线：从 SFT 到 RFT 再到 RL

如下图所示，MusaCoder 的整体训练流程分为三个大阶段，层层递进，逐步提升模型的内核生成能力。

![文章插图](/articles/2026-06-15-claude-opus-4-7-gpu-f531a124/images/07.webp)

::: image-caption
图 2：MusaCoder 训练流水线总览。
:::

- **第一阶段是多任务监督微调，也就是 SFT 阶段**。这个阶段的:mdnice-bold-italic[目标是让模型掌握 GPU 内核的基础知识、基本写法，还有相关的推理、审查、优化能力]。它不是只训练生成内核这一个任务，而是同时训练内核生成、错误审查、性能分析、优化重写、知识问答等多个任务，全面搭建模型的底层能力。
- **第二阶段是保留多样性的拒绝采样微调，也就是 RFT 阶段**。这个阶段的:mdnice-bold-italic[目标是让模型对齐最终的生成任务，把 SFT 学到的通用能力收敛到内核生成这个具体场景上]。和传统 RFT 只保留最好的一个结果不同，MusaCoder 会保留多个不同的正确实现，避免模型过早收敛到单一模板，为后续的强化学习保留探索空间。
- **第三阶段是执行反馈强化学习，也就是 RL 阶段**。这个阶段会:mdnice-bold-italic[让模型真实生成内核，然后通过执行沙箱编译运行，得到真实的正确性和性能反馈，用这些反馈来优化模型]。RL 又分为两步：先做单轮 RL 预热，优化首轮生成的质量；再做多轮反馈 RL，让模型学会根据错误反馈修复问题，进一步提升上限。

### 2.2 双后端支持：CUDA 与 MUSA 的统一架构

> MusaCoder 的另一个重要特点是，它从**设计之初就支持 CUDA 和 MUSA 双后端**，使用的是同一套训练框架和流程。

具体来说，数据合成、训练算法、验证环境的主体逻辑都是通用的，**只需要把后端相关的 API、编译命令、设备操作等替换成对应平台的版本，就可以快速迁移到新的硬件后端**。这种设计大大降低了跨平台迁移的成本，也证明了这套全栈训练框架的通用性。

::: block-1
对于新兴硬件生态来说，这一点尤为重要。过去每换一种硬件，都要重新搭建一套算子生态，成本极高。而有了 MusaCoder 这样的通用框架，就可以快速为新硬件生成原生内核，大大加速软件生态的建设速度。
:::

### 2.3 核心设计哲学：硬件感知的执行反馈闭环

> MusaCoder 最核心的设计哲学，就是**一切以真实的硬件执行为准。**

传统的代码生成模型，大多是基于文本相似度来训练的，也就是让生成的代码和人类写的代码尽量像。:mdnice-bold-italic[但 GPU 内核不是写得像就有用，必须真实编译通过、运行正确、速度够快，才有实际价值]。文本相似度高的代码，可能因为一个索引错误就完全跑不起来。

所以 **MusaCoder 的整个训练体系，都是围绕真实的执行反馈来构建的**。从数据阶段的自动验证，到 RFT 阶段的执行过滤，再到 RL 阶段的奖励计算，所有的判断标准都来自真实的编译与运行结果，而不是文本的相似度。:mdnice-bold-italic[这种硬件感知的执行反馈闭环，是它能够超越通用大模型的根本原因。]

> 高质量的训练数据是大模型能力的根基，对于 GPU 内核生成这种垂直领域更是如此。

通用代码数据集缺乏 GPU 底层编程知识，现有的 PyTorch 转 CUDA 数据集覆盖范围有限，无法支撑全栈后训练的需求，因此 **MusaCoder 搭建了三阶段的数据合成流水线。**

### 3.1 数据合成第一阶段：任务扩展与基础算子正确率增强

> 第一阶段数据建设的核心目标，是**扩大任务覆盖范围，打牢基础算子的正确率底子。**

首先是任务来源的扩展。**MusaCoder 从三个互补的来源构建参考任务：已有的开源内核生成任务、GitHub 上真实的 PyTorch 模块、还有 NNSmith 自动生成的计算图**。三个来源各有侧重，开源数据提供标准场景，GitHub 数据带来真实的业务代码，NNSmith 则系统补充了人工收集覆盖不到的长尾区域，:mdnice-bold-italic[最终覆盖了大约 162 种经过实际验证的算子。]

然后是基础算子的变体增强。前期实验发现，模型在很多基础算子上的正确率几乎为零，尤其是各种卷积变体，不同的步长、填充、膨胀系数、分组数，都会导致模型出错。而基础算子是复杂融合算子的积木，如果基础都不对，复杂算子肯定更做不好。所以 **MusaCoder 针对卷积、归约、归一化、softmax、广播这些易错的算子家族，构造了大规模的参数变体数据，覆盖不同的数据类型、形状、边界情况，专门补模型的短板。**

除了直接的生成数据，还补充了 GPU 内核知识问答数据。**很多内核生成的错误，本质上不是代码写不对，而是底层概念没理解**。比如线程索引怎么算、内存为什么要合并、异步执行对计时有什么影响。知识问答数据就是专门补这些底层概念，让模型不仅知其然，还知其所以然。

**最后还有自动化的单元测试生成**。每一份数据都配套生成了全面的单元测试，覆盖不同形状、数据类型、数值范围、边界情况，用来验证生成内核的正确性。:mdnice-bold-italic[只有通过了单元测试的数据，才会进入训练集，从源头上保证数据质量。]

### 3.2 数据合成第二阶段：结构化推理与空间逻辑约束

> 基础任务有了之后，第二阶段的重点是减少逻辑错误，尤其是形状推理、索引映射这类空间逻辑错误。

首先是引入了六步结构化推理模板。很多模型生成内核的时候，:mdnice-bold-italic[直接跳步从 PyTorch 代码写到底层实现，中间没有推理过程，很容易出现逻辑断层]。**六步模板把整个生成过程拆成了六个固定步骤：算子整体分析与拆解、标量数学公式推导、形状与维度计算、索引关系与内存映射、边界处理与类型安全、错误预判与负面约束。**

::: block-1
这个设计就像教学生做题的时候，要求必须写清解题步骤，不能直接写答案。通过强制模型按步骤推导，大大减少了跳步带来的逻辑错误，也让模型的思考过程更稳定。
:::

**然后是显式的张量形状标注**。形状推理错误是内核生成里最常见的错误之一，尤其是切片、转置、广播、非连续张量这些场景，形状和步长稍微错一点，后面的索引和内存访问就全错了。

MusaCoder 的做法是，:mdnice-bold-italic[在训练样本里显式加入每个关键张量的形状、步长、连续性信息，直接告诉模型，不用它自己瞎猜。这些信息可以通过 torch.fx 的形状传播工具自动提取，静态形状和动态形状都支持]。有了显式的形状标注，模型就可以把精力放在内核优化上，而不是反复推导形状，大大减少了形状相关的错误。

### 3.3 数据合成第三阶段：多轮 RL 预备与环境反馈解析

> 前两个阶段都是单轮生成的数据，**第三阶段的目标是为后续的多轮强化学习做准备，让模型学会看懂反馈、修复错误。**

- 第一类是多轮交互轨迹数据。**模拟真实的多轮修复场景，模型先生成一版内核，验证之后把错误信息加进去，让模型生成修复后的版本**，最多迭代多轮。:mdnice-bold-italic[这样模型在进入 RL 之前，就已经【习惯了带反馈的上下文】，知道怎么根据编译错误、数值错误来修改代码]，不会拿到反馈之后一脸茫然。
- 第二类是**内核评审员数据**。给模型一段 PyTorch 参考代码和一个候选内核，**让模型审查这个内核对不对，错在哪里，怎么改；如果是对的，就分析性能瓶颈在哪里，怎么优化**。这种数据训练的不是生成能力，而是:mdnice-bold-italic[审查和诊断能力]。模型只有能看出别人写的代码有什么问题，才能更好地修改自己的错误。
- 第三类是**性能反馈与优化重写数据**。一类是:mdnice-bold-italic[给模型内核和性能 profiling 数据，让它分析瓶颈在哪里；另一类是给一个功能正确但性能很差的内核，让它优化成高性能的版本]。这样模型就学会了看懂性能指标，知道从哪些方向去优化，为后续 RL 阶段的性能优化打下基础。

## 四、从 SFT 到多样性保留 RFT：对齐与探索的平衡

> 有了高质量的数据之后，首先通过监督微调（SFT）让模型掌握基本的内核生成范式，但单纯的监督学习还不足以对齐最终的执行目标。拒绝采样微调（RFT）是连接监督学习与强化学习的关键桥梁，但传统方法很容易导致模型熵坍缩，反而影响后续强化学习的效果。

### 4.1 多任务 SFT：不止是生成，更要会审查与优化

SFT 阶段【不是只训练内核生成】这一个任务，而是**混合了多种相关任务，形成多任务监督训练。**

::: block-1
**不同的任务有不同的作用**：内核生成数据提供直接的代码合成能力，评审员数据提升错误检测和修复能力，性能分析数据帮助理解硬件瓶颈，知识问答数据补充底层概念，优化重写数据学习性能提升的方法。:mdnice-bold-italic[多种任务互相补充，共同搭建模型的完整能力体系。]
:::

**任务的混合比例也不是固定的，而是通过前置诊断来动态调整**。先在小范围测试基础模型在不同算子上的表现，哪里弱就多采样哪里的数据，把训练资源集中在模型的短板上。

为了:mdnice-bold-italic[防止模型过拟合到内核生成的特定格式，还保留了大约 30%的通用指令和代码数据]，维持模型的通用编程能力和指令跟随能力，避免越训越窄。

对于多轮的样本，还采用了损失掩码策略：历史轮次的内容只作为上下文，不计算损失，只有最后一轮的正确输出才计算损失。这样模型就不会去模仿中间的错误尝试，只会学习最终的正确结果。

### 4.2 传统 RFT 的熵坍缩问题

> SFT 之后，通常会用拒绝采样微调（RFT）来进一步对齐任务。传统 RFT 的做法很简单：给每个任务采样多个候选结果，用验证器跑一遍，只保留最好的那一个，通常是最快的内核，然后用这些筛选后的结果继续微调模型。

这种方法确实能快速提升模型的正确率，**但有一个严重的副作用：熵坍缩。因为每个任务只保留一个最优解，模型很快就会收敛到只写那一种固定的模板**，生成的多样性急剧下降。

::: block-1
**而多样性对于后续的强化学习至关重要**。:mdnice-bold-italic[如果模型已经收敛到很窄的分布里，RL 阶段就没有足够的探索空间，很难找到更优的实现，很容易卡在局部最优。] 这就像考试之前把所有题的答案都背下来了，看起来分数很高，但遇到新题或者需要灵活变通的时候，就完全不行了。
:::

### 4.3 保留多样性的拒绝采样微调策略

> 针对这个问题，MusaCoder 提出了保留多样性的拒绝采样过滤策略。具体来说：

- 第一步是把所有通过正确性验证的候选都保留下来，而不是只选最快的那一个。
- 第二步是根据代码相似度、抽象语法树结构、内核数量、线程块配置、优化方式等特征，把这些正确的实现聚类，不同的簇代表不同的实现思路。
- 第三步是从每个簇里选代表，每个任务最终保留 4 到 8 个不同的正确实现。

训练的时候，每个 epoch 从对应的正样本池里随机选一个作为监督目标。这样模型学习的就不是单一的标准答案，而是一组合法的正确解分布。

这种设计既通过执行过滤提升了数据的正确率，又保留了实现方式的多样性，为后续的强化学习保留了充足的探索空间。这是 MusaCoder 的 RL 阶段能够有效提升的重要基础。

::: block-1
**保留多样性的拒绝采样微调，本质是在对齐正确性目标的同时，避免模型过早收敛到单一最优解，为后续强化学习保留充足的探索空间**，是平衡对齐效果与探索能力的关键设计。它解决了传统 RFT 正确率提升但探索能力下降的矛盾，让监督对齐和强化学习能够顺畅衔接。
:::

## 五、MooreEval：分布式验证环境与奖励引擎

> 强化学习的核心是奖励函数，而内核生成的奖励无法靠人工标注，必须通过真实的编译与执行来获得。

MooreEval 就是 MusaCoder 专门设计的分布式执行沙箱，同时承担了 RFT 数据过滤与 RL 奖励环境的双重角色，是整个执行反馈闭环的工程底座。

图 10：MooreEval 架构——可扩展的基于执行的评估环境。 该图展示 MooreEval 分布式异构架构，核心将 CPU 编译与 GPU 执行两大任务解耦，分别部署独立工作集群。整体由主机、编译工作器、执行工作器、Redis 任务队列、共享存储、奖励适配器构成，依托沙箱隔离、任务超时机制隔离恶意代码，避免非法内存访问、进程崩溃影响全局训练。同时内置多层反作弊检测，拦截调用 PyTorch 高层算子的行为。该架构是全栈训练的核心引擎，兼顾高吞吐、高容错与奖励准确性。

### 5.1 分层验证协议：正确性优先的四级校验

> **MooreEval 采用了严格的分层验证流程**，一级比一级严格，只有通过了前一级，才能进入下一级，:mdnice-bold-italic[确保正确性永远是第一位的。]

| 层级 | 检查内容 | 判定标准 |
| --- | --- | --- |
| 第一层 | 代码解析与结构检查 | 从模型输出中提取可执行代码，检查是否定义了符合接口要求的 `ModelNew` 类；结构不符或无法提取则判定为无效 |
| 第二层 | 编译检查 | 将提取的代码在隔离环境中编译；出现语法错误、编译失败、链接错误或编译超时，均归为编译失败 |
| 第三层 | 正确性检查 | 编译通过后，用随机生成的输入运行代码，与 PyTorch 的参考结果比对输出形状、数据类型、数值误差；全部通过才算正确 |
| 第四层 | 反作弊检测和性能测试 | 正确性通过后，先检测是否调用禁止的 PyTorch 算子（作弊行为）；确认无作弊后，进行性能测速，计算相对于基线的加速比 |

::: block-1
**这种分层设计的好处是，越往后的检查越消耗资源，就放在越后面，前面的层级先把明显不合格的过滤掉，大大提升整体的验证效率**。同时也保证了性能奖励永远建立在功能正确的基础上，不会出现代码跑不通但速度很快的荒谬情况。
:::

### 5.2 反作弊机制：严防 PyTorch 回退的奖励作弊

> 反作弊是内核生成验证里至关重要的一环，如果防不住作弊，整个强化学习就会走偏。

**MooreEval 采用静态分析加运行时钩子的双重检测机制**。

- 静态分析会检查代码里有没有调用禁止的 aten::*计算算子
- 运行时会钩子捕获实际执行过程中调用的算子

允许使用的只有形状查询、视图变换、内存拷贝、张量创建这类非计算操作，而矩阵乘法、卷积、归约这类计算算子是严格禁止的。

::: block-1
只要检测到调用了禁止的算子，直接判定为作弊，奖励给最低分。另外还会检查异常高的加速比，如加速比不符合物理规律，也会判定为作弊，**从根源上堵住了模型投机取巧的路径，保证奖励真正激励模型去写原生内核，而不是调用现成的 API。**
:::

### 5.3 分布式架构：CPU 编译与 GPU 执行解耦

> 强化学习的每个批次都会产生大量的候选代码，都需要编译和验证，单节点同步执行根本跟不上速度。所以 **MooreEval 设计成了分布式的异步流水线架构，把 CPU 端的编译和 GPU 端的执行完全解耦。**

整个系统分为几个核心组件：主机负责任务调度和结果聚合，编译工人负责 CPU 端的预编译，执行工人负责 GPU 端的运行验证，用 Redis 队列来做任务调度和状态管理，还有共享存储来存放代码和编译产物。

::: block-1
编译工人和执行工人可以独立横向扩展，编译任务多就加编译节点，执行任务多就加 GPU 节点，不会出现一方忙死另一方闲死的情况。**这种解耦设计大大提升了整体的吞吐量，能够支撑大规模 RL 训练的高并发验证需求。**
:::

**同时系统还有完善的故障隔离机制**。模型生成的代码是不可信的，可能会导致进程崩溃、GPU 挂死、超时等各种问题。:mdnice-bold-italic[系统通过沙箱子进程隔离、超时控制、失败重试、任务重入等机制，保证单个异常样本不会影响整个训练流程]，整个系统可以长时间稳定运行。

### 5.4 奖励函数设计：正确性门控下的性能激励

> 基于分层验证的结果，MooreEval 设计了精细的奖励函数，给每个候选内核打分。奖励函数的整体原则是：正确性优先，性能是加分项。

$$
s(c)= 
\begin{cases}
-1, & \text{if code extraction fails, compilation fails, or runtime fails}, \\
-1, & \text{if a disallowed PyTorch/aten::* fallback is detected}, \\
-1, & \text{if } q=0, \\
-0.5 + 0.5q, & \text{if } 0 < q < 1, \\
1 + \lambda \cdot \min\left(\max(\nu - 1, 0), \nu_{\text{max}}\right), & \text{if } q = 1 \text{ and the implementation is legal}.
\end{cases}
$$

其中，$c$ 代表候选代码，$q$ 代表随机测试中的正确率，$\nu$ 代表相对于 PyTorch 基线的运行加速比，$\lambda$ 控制性能奖励的权重，$\nu_{max}$ 用来截断异常高的加速比。

具体来看，奖励分为几个档次：完全失败的，包括提取失败、编译失败、运行失败、作弊、全错的，统一给-1 分；部分正确的，也就是一部分测试用例能过，给-0.5 到 0 之间的过渡分，正确率越高分越高，给模型一个渐进的改进方向；完全正确且合法的，基础分是 1，再加上加速比的奖励，加速越快分越高，但有上限。

**这种设计的好处是，模型会先追求写对，再追求写快，优化路径很清晰**。:mdnice-bold-italic[部分正确的过渡分也很重要，它避免了非对即错的极端情况，让模型在全错到全对之间有平滑的学习信号]，缓解了奖励稀疏的问题。

::: block-1
MooreEval 的奖励设计严格遵循正确性优先原则，性能奖励必须建立在功能正确与原生内核合规的双重前提下，从根源上避免了奖励作弊，保证了强化学习的优化方向与实际目标一致。它不仅是一个评估工具，更是整个执行反馈 RL 训练的核心数据引擎。
:::

## 六、执行反馈 RL：三大机制破解训练不稳定

> 有了验证环境和奖励函数，就可以通过强化学习进一步优化模型的内核生成能力，但内核生成任务的强化学习面临着远超普通代码生成的稳定性挑战。

针对奖励稀疏、多轮目标漂移、离策略漂移三大核心问题，MusaCoder 提出了三项互补的稳定机制，共同保障了强化学习的平稳有效。

### 6.1 两阶段 RL：单轮预热到多轮反馈

> 整个 RL 阶段分为两个步骤，循序渐进。

![文章插图](/articles/2026-06-15-claude-opus-4-7-gpu-f531a124/images/10.webp)

::: image-caption
图 4：多轮强化学习（RL）迭代执行流程。 该图模拟真实 GPU 内核开发的“编写-校验-修复”流程：模型首次生成代码后交由 MooreEval 校验，代码合规则终止迭代，若存在编译、数值错误，系统会将错误日志注入上下文，引导模型迭代修复，同时设置最大迭代轮数限制。该流程让模型学习解读硬件执行反馈并自主纠错，区别于静态样本训练。轮数限制在保障训练效率的同时，避免模型陷入无限修复循环，兼顾纠错能力与训练成本。
:::

- 第一步是单轮 RL 预热。每个任务只生成一次，没有反馈，直接用 MooreEval 的结果计算奖励，更新策略。这个阶段的目标是提升模型零反馈下的首轮生成质量，把基础正确率提上来。
- 第二步是多轮反馈 RL。如果第一次生成失败了，就把错误反馈加到上下文里，让模型生成修复后的版本，最多迭代多轮。这个阶段的目标是进一步提升上限，让模型学会利用反馈自我修正。

::: block-1
**之所以要先做单轮预热，是因为如果直接上多轮 RL，前期模型基础太差，前几轮都在犯低级错误**，比如格式不对、编译不过，反馈都浪费在这些基础问题上了，效率很低。**先通过单轮 RL 把基础打牢**，多轮阶段就可以专注于解决更难的问题，比如数值精度、边界情况、性能优化，效率更高。
:::

### 6.2 PrimeEcho：首轮锚定的多轮奖励机制

> 多轮 RL 有一个天然的问题：如果只优化最终的结果，模型会越来越依赖反馈，首轮生成的质量反而会下降。**就像学生总依赖答案改题，自己独立做题的能力反而会变差。**

**但在实际部署中，首轮生成的质量才是最重要的**。多轮修正虽然能提升正确率，但每多一轮就要多一次编译和验证，延迟会高很多。:mdnice-bold-italic[如果首轮就能生成正确的内核，推理成本会低得多。]

::: block-1
为了解决这个矛盾，MusaCoder 提出了 PrimeEcho，也就是首轮锚定的多轮奖励机制。核心思路是，多轮反馈只是补充，主要的优化目标还是首轮生成质量，过程如下图 5 所示：
:::

![文章插图](/articles/2026-06-15-claude-opus-4-7-gpu-f531a124/images/11.webp)

::: image-caption
图 5：多轮奖励机制设计。 该图展示 PrimeEcho 奖励机制的核心逻辑，打破传统仅使用最终轮结果打分的模式。机制将首轮生成得分与多轮迭代最优得分加权融合，还额外奖励早期修复成功的样本。设计核心是锚定首轮生成质量，把多轮修复仅作为辅助学习信号，防止模型过度依赖后续反馈、零样本能力退化。该机制平衡了模型单次生成效率与迭代优化能力，贴合工业场景对低延迟部署的需求。
:::

$$
R_{\tau _{i}}=\alpha s_{i,1}+(1-\alpha )\operatorname* {max}_{1\leq k\leq K}s_{i,k}+b_{early}(\tau _{i})
$$

其中，$s_{i,1}$ 是首轮生成的得分，$max_{1 \le k \le K} s_{i,k}$ 是整个多轮交互中的最高分，$\alpha$ 控制首轮的权重，默认是 0.75，**也就是主要看重首轮表现。$b_{early}$ 是早成功奖励，越早生成正确的内核，额外加分越多，鼓励模型尽早做对。**

![文章插图](/articles/2026-06-15-claude-opus-4-7-gpu-f531a124/images/12.webp)

::: image-caption
图 6：多轮强化学习的训练动态。(a) 平均迭代轮数变化 (b) 平均奖励值变化。 该组曲线反映多轮 RL 的整体收敛趋势：随着训练步数增加，模型完成任务所需平均迭代轮数持续下降，综合奖励稳步上升。小幅波动源于 KernelBench 任务难度分布不均，长尾复杂任务会临时拉低指标，但平滑曲线证明训练整体稳定。变化趋势说明模型逐步吃透 GPU 内核编写规则，首轮正确率持续提升，对编译、运行报错的理解与修复效率也同步增强，三大 RL 稳定技术有效抑制了训练震荡。
:::

::: block-1
简单来说，就是奖励主要看第一次写得怎么样，后面改得好可以加分，但加的不多。这样既利用了多轮反馈带来的探索信号，又不会让模型过度依赖反馈，保证了首轮生成的质量不会下降。
:::

![文章插图](/articles/2026-06-15-claude-opus-4-7-gpu-f531a124/images/13.webp)

::: image-caption
图 7：KernelBench 不同难度层级下的多轮评估指标。 该图对比不同难度任务的得分、正确率、平均迭代轮数三大指标。Level1 简单算子任务首轮正确率极高，几乎无需迭代；Level2、Level3 中高难度任务首轮表现明显下滑，但借助多轮反馈后最佳正确率大幅提升，且任务难度越高，平均迭代轮数越多。这表明基础算子模型已完全掌握，复杂内核的形状计算、数值稳定性、高级内存优化仍是难点，也证明多轮执行反馈是解决高阶内核问题的必要手段。
:::

### 6.3 缓冲动态重试 BDR：从全失败样本中回收信号

> 奖励稀疏是内核生成 RL 最头疼的问题之一。对于很难的任务，模型采样的一组样本全都是错的，没有一个正样本，组内的奖励都一样，优势函数算不出来，也就没有有效的学习信号。这些难题就一直卡在那里，模型始终不会做。

针对这个问题，MusaCoder 提出了缓冲动态重试，简称 BDR。**核心思路是，既然直接生成太难，那就改成带提示的修复任务，降低难度，把学习信号回收回来。**

![文章插图](/articles/2026-06-15-claude-opus-4-7-gpu-f531a124/images/14.webp)

::: image-caption
图 8：不同反馈方式下缓冲动态重试（BDR）的消融实验。 该曲线对比三种 BDR 反馈方案的训练效果：外部大模型反馈初期收敛更快，但因数据分布与真实推理场景不符，引发模型熵剧烈波动；叠加 KL 正则也无法彻底消除分布偏差。而采用 MooreEval 原生硬件执行反馈的方案，收敛节奏平稳、最终性能最优。实验证明，RL 训练的反馈必须与真实运行环境保持一致，外部人工或模型生成的提示会引入噪声，原生执行反馈才是解决难样本、稀疏奖励问题的最优选择。
:::

具体做法是，每轮训练结束后，扫描所有全失败的任务，**选一个有代表性的错误样本，配上 MooreEval 返回的错误信息，把原来的零样本生成任务，改造成一个带错误反馈的代码修复任务**。这些改造后的任务会放进一个 FIFO 的缓冲池里。

::: block-1
后续训练的时候，会以一个很小的概率从缓冲池里采样这些修复任务，混合到正常任务里一起训练。缓冲池用先进先出的淘汰策略，满了就把最老的样本踢出去，**保证池子里始终是当前模型刚好不会的那些边界难题。**
:::

之所以不用更强的外部大模型来写修复提示，是因为外部模型的反馈风格和训练数据分布不一样，容易引入分布偏移，反而导致训练不稳定。用 MooreEval 原生的执行反馈，分布一致，更稳定可靠。

### 6.4 MirrorPop：序列级离策略掩码，消除抵消偏差

> 强化学习的另一个大问题是离策略漂移。**生成样本的 rollout 模型和正在更新的模型不是同一个，随着训练进行，两者的差异会越来越大，导致梯度估计方差变大**，训练不稳定甚至崩溃。

常用的应对方法是序列级掩码，计算整个序列的重要性比率，偏离太多的序列就扔掉，不参与更新。但传统的计算方法有个缺陷：它用的是带符号的对数比率的平均值，正的偏差和负的偏差会互相抵消。

::: block-1
举个例子，两个 token，一个概率变成 10 倍，一个变成十分之一，它们的对数比率加起来刚好是零，平均值也是零，看起来好像和原来的策略一样。但实际上两个 token 都偏离得很远，只是方向相反，互相抵消了。这样就会把严重离策略的样本当成正常样本，导致训练不稳定。
:::

MirrorPop 就是为了解决这个抵消问题。它不用带符号的对数比率，而是用绝对值。不管是概率变高还是变低，只要偏离了，就算偏差。

$$
m_{i, t}=max (\rho _{i, t}, \rho_{i, t}^{-1})=exp (\left|log \rho_{i, t}\right| )
$$

每个 token 的镜像偏差 $m_{i,t}$，等于重要性比率和它的倒数里更大的那个，其实就是**对数比率的绝对值取指数。** 然后整个序列的平均镜像偏差，就是所有 token 镜像偏差的几何平均。:mdnice-bold-italic[如果平均偏差超过阈值，就把整个序列掩码掉，不参与更新。]

这样就不会出现正负抵消的情况，能更准确地识别出严重离策略的序列。把这些高风险的序列过滤掉之后，训练就稳定多了。**消融实验也证明，MirrorPop 是所有稳定机制里影响最大的，去掉之后性能掉得最多。**

::: block-1
PrimeEcho 锚定首轮优化目标、BDR 破解长难样本奖励稀疏、MirrorPop 解决离策略漂移的误判问题，三项机制从不同维度共同保障了执行反馈强化学习的稳定性与有效性，是 MusaCoder 性能提升的核心算法支撑。它们分别对应了多轮目标对齐、难样本探索、训练稳定性三个核心痛点，形成了互补的完整体系。
:::

## 七、实验结果：跨平台的性能验证

> 所有的设计最终都要落到实际效果上，MusaCoder 在 KernelBench 基准及其 MUSA 移植版本上进行了全面的实验验证，结果充分证明了全栈训练框架的有效性，**所有实验都在摩尔线程 MTT S5000 GPU 集群上完成**。

## 八、总结

> MusaCoder 不仅刷新了 GPU 内核生成的性能纪录，更开创性地验证了**全栈执行反馈训练** 在原生内核生成中的可行性。其核心技术贡献涵盖五方面：

- 一是构建端到端的原生内核生成训练框架，覆盖数据合成、监督对齐与强化学习优化全链路；
- 二是提出保留多样性的拒绝采样微调策略，在提升生成正确率的同时维系 RL 探索空间；
- 三是设计三项互补的 RL 稳定机制——多轮目标对齐、难样本信号回收、离策略漂移控制，系统性破解内核生成 RL 的核心难点；
- 四是实现 CUDA 与 MUSA 双后端统一支持，展现优异的跨平台迁移能力；
- 五是首次在国产 GPU 上完成大模型执行反馈 RL 训练闭环，实证国产硬件具备支撑复杂后训练任务的全栈能力。

回望整个行业，我们见过太多 “用硬件堆大模型” 的故事，**却很少见到 “用大模型反过来补硬件生态” 的尝试。**

::: block-1
MusaCoder 的价值，从来不止是刷新了一份 KernelBench 的榜单。它真正的分量，在于首次完整验证了国产 GPU 可以支撑从数据合成到强化学习的全链路大模型后训练，:mdnice-bold-italic[在于证明了专用 AI 模型可以成为硬件生态的 “效率放大器”—— 把原本依赖资深专家手工打磨的内核开发，变成可规模化、可自动化的能力，把国产硬件最薄弱的算子生态，变成可以用 AI 快速补齐的环节。]
:::

> 当大模型开始深度嵌入编译器、迁移工具、开发 IDE 的每一个环节，当内核生成从 “专家手艺” 变成 “基础设施”，:mdnice-bold-italic[我们看到的就不只是一个模型的成功，更是国产算力生态换道追赶的新可能。这一步跨出去，未来的异构计算世界，才真正有了更多元的答案。]
