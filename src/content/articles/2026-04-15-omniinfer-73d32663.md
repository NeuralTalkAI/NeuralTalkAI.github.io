## 一、OmnilnferCLI快速安装使用

> 一行命令，即可完成安装：

**macOS/Linux:**

```
curl -fsSL https://raw.githubusercontent.com/omnimind-ai/OmniInfer/main/scripts/install.sh | bash
```

**Windows (PowerShell):**

```
irm https://raw.githubusercontent.com/omnimind-ai/OmniInfer/main/scripts/install.ps1 | iex
```

安装脚本会自动检测当前平台与硬件环境，推荐最优后端，并引导完成模型配置，无需手动编译。

安装完成后，即可直接使用：

- 查看可用后端：`./omnifiner backend list`
- 选择后端（替换为实际可用项）：`./omnifiner select llama.cpp-linux`
- 加载模型（替换为本地模型路径）：`./omnifiner model load -m /path/to/your/model.gguf`
- 开始对话：`./omnifiner chat --message "你好"`

如需从源码构建，请参考仓库Build Guide[1]。

## 二、OmniInfer 解决问题的创新之道

OmniInfer 的核心目标非常清晰：**Easy, fast, and private LLM & VLM inference for every device**，即为每台设备提供简单、快速且私密的大模型推理。

### 2.1 核心创新点：统一调度与无缝多后端切换（Seamless Multi-Backend Switching）

> OmniInfer 并不是去“重复造轮子”写一个新的底层张量计算库，它的创新性在于**架构设计上的升维**。它引入了一个名为 `RuntimeManager` 的统一运行时生命周期管理机制，:mdnice-bold-italic[向下对接 `llama.cpp`、`mnn`、`mlx`、`executorch` 等多种后端引擎，向上则暴露出一套完全兼容 OpenAI 标准的 HTTP/SSE RESTful API。]

这种“网关-代理”模式的创新点在于：

- **动态最佳引擎选择**：用户（或上层应用 Omni Studio）只需指定所需加载的模型，:mdnice-bold-italic[OmniInfer 即可根据当前所处的操作系统和硬件环境，自动（或通过参数显式）路由到最优的后端]。例如在 Mac 上它可能唤起 MLX 引擎，而在老旧 x86 笔记本上则自动回退到 llama.cpp。
- **隔离与容错**：底层引擎往往是用 C++/C 编写，存在内存溢出（OOM）或张量分配错误导致进程崩溃的风险。:mdnice-bold-italic[Omnilnfer 的 Python 控制面（Control Plane）与底层引擎的数据面（Data Plane）进行了解耦隔离，对各推理引擎的异常返回做了统一收敛封装]，保证了服务的整体稳定性。

### 2.2 硬件感知与“开箱即用”

> 传统方案中，部署一个端侧模型需要开发者自己去编译包含 CUDA、Metal、Vulkan 各种后端的二进制文件。OmniInfer 构建了一套强大的打包和环境检测机制：

- **One Codebase, All Platforms**：统一的代码库同时支持 Linux、macOS、Windows（桌面及服务器）以及 Android、iOS。
- **细粒度硬件控制**：提供对 Context Length（上下文长度）、GPU Offloading（GPU 层数卸载）、KV Cache 显存分配策略的统一抽象。

## 三、自研框架：OmniInfer-Native

> OmniInfer 的自研能力现在统一收敛到 `OmniInfer-Native`。它作为一套统一的跨平台推理框架持续演进，集成新的优化技术。

### 3.1 基于 llama.cpp 的跨平台统一底座

`OmniInfer-Native` 以 `llama.cpp` 为基础，加入 `eagle3`、`TurboQuant` 等优化，面向 Linux、Windows、macOS、Android、iOS 提供统一支持。**它的重点不是简单封装开源后端，而是在成熟执行栈之上继续做低延迟、高吞吐、长时间稳定运行和多硬件适配的工程化优化。**

对 OmniInfer 来说，这样的统一底座有两个直接价值。

- 第一，桌面端和移动端可以复用同一套核心优化路径，而不是长期维护割裂的后端分支。
- 第二，框架命名、运行时能力和后续演进方向都能统一到 `OmniInfer-Native` 之下，整体架构更清晰。

### 3.2 安卓高通平台的定制化优化

> 在 Android 高通平台上，`OmniInfer-Native` 进一步做了针对 NPU 的定制化优化，追求极致速度。

框架在`OmniInfer-Native`中加入 NPU backend，加速LLM的推理过程。

::: block-1
在优化VLM时，`OmniInfer-Native` 魔改`ExecuTorch`推理框架作为文本推理的“伙伴”。使用自研NPU后端接口执行 VLM 中的 ViT 计算；视觉结果再发送给 `ExecuTorch`，由其负责文本推理的 LLM 部分。**这样做的好处是，视觉侧保留了 `llama.cpp` 在多模态路径上的灵活性，文本侧则能够更充分地利用高通 NPU 的计算加速能力。**
:::

与此同时，`OmniInfer-Native` 继续保留 Android 端需要的 Native runtime、模型装配和集成能力。它支持以 `omniinfer-native.env` 描述模型包，统一组织 tokenizer、decoder、vision encoder 等组件，也兼容单 `.pte` 的兼容模式与完整 package mode，便于真实端上部署。

`OmniInfer-Native`广度上可集成通用优化技术与自研优化技术，**适配全平台**；深度上**可针对单一平台做极致的性能提升**，可谓是诸武精通。

## 四、架构与数据流转分析

> 从下面架构图可清晰看到，**OmniInfer 采用分层解耦的经典架构**，整体可概括为五层递进结构：`Entry Points → Core Engine → Platform Abstraction → Inference Engines → Supported Models`。

其核心设计理念可凝练为：**上层统一接入，中层统一调度，下层按平台选择最优执行引擎**，全链路实现入口、调度、执行的分层解耦与高效协同。

### 4.1 五层结构（对应架构图垂直分层）

> 架构图以清晰的垂直分层界定各模块职责边界，五层逐级调用、各司其职，构成完整的本地推理运行时体系。

#### Entry Points（统一入口层）

作为架构最上层，提供**四类标准化入口**：`CLI`、`HTTP Gateway`、`Android`、`iOS`，分别对应命令行调用、服务化部署、移动端原生集成三种使用场景。三类入口交互形式不同，但**全部收敛至同一套核心运行时**，是架构“上层统一接入”设计的直接体现。

#### Core Engine（核心调度中枢）

位于架构中间核心位置，是全系统的调度“大脑”，包含6大核心模块，承担统一管控与协调职责：

- `Platform Detection`：自动识别操作系统、硬件规格与可用推理后端
- `Backend Management`：统一管理后端配置、性能档案与参数组织
- `Runtime Manager`：管控模型全生命周期，协调推理请求调度
- `Embedded Drivers`：提供Python、JNI等跨语言桥接能力
- `Configuration`：统一管理线程、内存卸载（offload）等运行时参数
- `Model Catalog`：维护模型来源、官方预设与多模态元数据

::: block-1
这一层通过模块化拆分，将平台判断、模型管理、后端配置、运行时启停完全解耦，既简化了模块维护，又为新增硬件、模型、后端提供了极强的扩展能力，是“中层统一调度”的核心载体。
:::

#### Platform Abstraction（平台适配抽象层）

> 作为核心引擎与执行引擎的中间桥梁，**专职屏蔽跨平台差异**，对应架构图中“分平台适配”的分支逻辑，按操作系统自动绑定适配后端：

| 平台 | 支持的运行时与后端 |
| --- | --- |
| Linux | `llama.cpp-cpu`、`cuda`、`rocm`、`vulkan`、`sycl` 及 `OmniInfer-Native` |
| Windows | `llama.cpp` 全家族（含 `cpu`、`cuda`、`vulkan` 等）及 `OmniInfer-Native` |
| macOS | `llama.cpp-metal`、`mlx-mac`、`turboquant-mac` 及 `OmniInfer-Native` |
| Android | `llama.cpp`（含 `cpu`、`neon`、`openmp` 等优化）、`MNN` 及 `OmniInfer-Native` |
| iOS | `llama.cpp-ios`、`mlx-ios` 及 `OmniInfer-Native` |

#### Inference Engines（推理执行层）

> 架构图最下层的执行单元，当前内置**4大推理引擎**，形成“自研主干+第三方互补”的执行矩阵：

- `OmniInfer-Native`：自研核心主干框架，基于`llama.cpp`深度优化，整合`eagle3`、`TurboQuant`等加速技术
- `llama.cpp`：保留通用基础推理能力，覆盖绝大多数平台基础场景
- `MNN`：专为Android移动端轻量化推理设计
- `MLX`：面向Apple Silicon芯片的原生高效引擎

特殊场景适配：

- 高通 Android 设备中，`llama.cpp` NPU路径负责ViT视觉推理，`ExecuTorch`专注文本推理，分工明确。
- iOS 平台，则对应三类运行时：`llama.cpp-ios`（通用推理路径）、`mlx-ios`（Apple Silicon 原生优化）、`OmniInfer-Native`（自研框架统一接入）。

#### Supported Models（模型能力层）

架构的最终能力输出边界，覆盖Qwen、Gemma、Llama、DeepSeek、Phi、Mistral、GLM、Yi等主流开源模型家族，支撑多场景、多模态本地推理需求。

### 4.2 数据流转（对应架构图数据流走向）

> 结合架构SVG的数据流闭环，一次完整推理请求的流转路径清晰规整，全链路遵循**统一入口→集中调度→平台适配→引擎执行→结果返回** 的逻辑：

1. 请求由`CLI`/`HTTP Gateway`/`Android`/`iOS`任一入口发起，进入核心运行时；
2. `Core Engine`读取平台信息、运行配置、模型元数据，自动筛选当前环境最优候选后端；
3. `Platform Abstraction`将标准化请求绑定到当前平台兼容的推理引擎，屏蔽底层差异；
4. 选定的`Inference Engines`完成模型加载、张量计算、流式推理等核心操作；
5. 推理结果沿原链路回流至入口层，以命令行输出、OpenAI兼容响应、Android、iOS 原生回调形式返回。

::: block-1
该流程的核心优势：**入口统一收敛、调度集中管控、平台差异下沉至抽象层、执行细节封装在引擎层**，全链路无冗余跳转，兼顾推理效率与架构简洁性。
:::

### 4.3 架构价值

> 从分层设计与数据流转来看，OmniInfer 架构的核心价值体现在三点：

1. **入口统一**：三类入口复用同一运行时，无需维护多套控制逻辑，大幅降低开发维护成本；
2. **平台解耦**：硬件/系统差异全部封装在`Platform Abstraction`层，上层接口保持稳定，扩展新平台无需改动核心逻辑；
3. **执行分层**：以自研`OmniInfer-Native`为主干承接核心能力，同时保留`llama.cpp`/`MNN`/`MLX`的平台专属优势，兼顾通用性与性能最优。

综上，OmniInfer并非单一推理后端的封装工具，而是**一套面向多入口、多平台、多模型家族的轻量化本地推理统一运行时**。
