## 一、内核优化智能体的现实天花板：通用 Agent 为何跑不到硬件极限

> 当下前沿大模型已经具备了写出高效 GPU 内核的能力，仅用通用的目标驱动编码智能体，就能在不少算子上媲美甚至超越专家手工调优的实现。**但这种能力存在清晰的边界，绝大多数优化循环最终都会停在一个自身无法突破的平台期。**

### 1.1 前沿大模型的内核优化基线：10 个算子 7 个超越专家

::: block-1
**很多观点认为，只要给大模型足够的迭代时间，它就能一直优化下去，直到逼近硬件的物理极限。** 但实际测试的结果并非如此。:mdnice-highlight[论文用 Claude Fable 5.1 搭配原生的 Claude Code CLI 目标模式，针对 10 个不同的算子任务做了最长 24 小时的无约束优化，最终结果呈现出非常明确的收敛特征。]
:::

测试覆盖注意力、门控增量网络、稀疏注意力链路等多个方向的前向和反向算子，参考实现来自 FlashAttention-4、FlashInfer、DeepGEMM 等业界顶尖的专家库。最终智能体在 7 个任务上超过了参考实现，几何均值提升 17%，其中包括 FlashAttention-4 的 GQA 注意力前后向、DSA 反向链路的全部三个 cuDNN 实现等。**但剩下的 3 个任务，智能体始终无法追上专家实现，差距最大的 DSA 稀疏注意力前向，落后超过 20%。**

> 更值得关注的是，无论最终结果是赢是输，所有任务都会收敛到一个固定点，智能体自身的循环再也无法让性能进一步提升。

![文章插图](/articles/2026-10-28-cake-kda-forgekernel-agent-h100-ae070871/images/07.jpg)

::: image-caption
表 5：/goal 模式 Agent 在 Hopper 平台的性能天花板，按内核分列。增益为该内核相对于对应固定专家参考的加速比；加粗标记未超越专家基准的项。该表是全文基线实验的核心数据，明确了通用编码智能体的能力边界。10 个测试任务覆盖注意力、GDN、DSA 稀疏链路三大类算子的前向与反向，最终 7 个算子超越专家参考，几何平均提升 17%，其中索引 Top-K 算子增益达 125.9%，体现大模型在简单算子上的优化潜力。而 DSA 索引器前向、稀疏注意力前向、GDN 反向三个算子显著落后，最大差距 25.1%，直接印证了「架构过早固化导致瓶颈」的核心观察，也为后续 ForgeKernel 的设计提供了明确的优化靶心。

这个固定点和参考实现的差距可大可小，但它是智能体自身能力的边界。**造成这个边界的核心原因有两个，也是这项工作要解决的核心问题。**

### 1.2 能力边界的根源：架构过早固化与知识无法跨轮沉淀

> **第一个原因是架构过早固化**。内核的性能由两层因素决定：

- 一层是架构决策，包括分块大小、流水线深度、线程束分工、张量布局等顶层设计，这些决策从根本上决定了性能的天花板；
- 另一层是战术调优，比如指令发射顺序、屏障等待深度、寄存器分配等，这些是在固定架构下的细节优化。

通用智能体通常在最初的几次尝试中就确定了整体架构，后面的所有迭代都在这个架构之内做微调，永远不会推翻顶层设计重新推进。如果一开始选择的架构本身就不是最优的，后续调优无法带来质的提升。

> **第二个原因是知识无法跨运行沉淀。每一次智能体运行都是无状态的，跑完一次之后，所有通过实际硬件测量得到的经验、验证过的有效技巧，都会随着会话结束而消失。** 下一次优化同一个算子，或者优化另一个同架构的算子，都要从头开始摸索，重复付出测量和试错的成本。

对于自迭代的优化来说，这意味着每一代优化都要重新支付上一代已经交过的学费，优化效率极低。

::: block-1
总之，通用编码智能体的内核优化存在两道天然枷锁：架构决策早收敛导致天花板自设，运行无状态导致知识不沉淀。:mdnice-bold-italic[这两个问题不解决，智能体优化就永远只能停留在局部最优的层面，无法持续逼近硬件的性能极限。 ForgeKernel 的整套设计，正是为了打破这两道枷锁。]
:::

## 二、ForgeKernel 整体架构：双智能体+三机制的自进化体系

> ForgeKernel 的核心设计思路，**是把内核优化的过程拆成架构设计和代码实现两个独立的环节，由两个不同的智能体分别负责，再通过标准化的工件衔接**。

在此基础上，通过黑盒反推、知识沉淀、自进化迭代三个核心机制，形成持续向上的优化闭环。

### 2.1 双智能体分工与三类核心工件

> 整个系统由两个核心智能体和三个核心工件组成。两个智能体分别是架构智能体和编码智能体：

- 架构智能体负责分析参考内核、制定优化里程碑、诊断优化瓶颈、调整优化方向；
- 编码智能体负责按照里程碑的要求，写出具体的内核代码。

三个工件分别是里程碑课程、硬件知识库、参考分析策略，作为两个智能体之间的交互媒介。

![文章插图](/articles/2026-10-28-cake-kda-forgekernel-agent-h100-ae070871/images/08.jpg)

::: image-caption
图 1：自进化的两种机制。左为单次目标模式运行，架构提前固化，知识随运行结束丢弃；右为ForgeKernel自进化智能体，内核逐代提升为参考，知识跨算子共享积累
:::

> **图 1 直观展示了 ForgeKernel 和传统单次智能体的核心差异。** 传统单次智能体的优化路径是一条先快后慢的曲线，架构很快稳定，之后的调优收益越来越小，最终停止，且所有经验都不保留。ForgeKernel 则有两条反馈路径：

- 一条是把每一代验证通过的内核封存，作为下一代的参考基准，让优化的起点不断抬高；
- 另一条是把所有经过硬件验证的优化技巧存入知识库，跨算子、跨代次复用，让后续优化的成本越来越低。

### 2.2 战役式优化与自进化闭环定义

> **整个优化过程以战役为单位，每一轮战役接收一个算子、一组输入形状、一个封闭的参考内核二进制，以及一个目标性能增益，最终输出一个通过正确性验证的优化内核**，以及生成它的里程碑课程。性能增益的定义是参考内核的运行时间除以优化后内核的运行时间，即：

$$
g(K, R) = t_R / t_K
$$

其中 $t_K$ 代表优化内核的设备运行时间，$t_R$ 代表参考内核的设备运行时间，两者必须在同一个 GPU 任务中完成计时，消除环境波动带来的测量误差。当优化内核的增益超过设定阈值，且通过正确性校验，这一轮战役就宣告成功。

::: block-1
自进化的过程就是不断重复这个战役流程：把上一轮输出的内核 $K_n$ 封存，作为下一轮的参考 $R_{n+1}$，继续优化。:mdnice-highlight[直到新一代相对上一代的增益降到测量噪声阈值以下，通常为 1%-5%，就认为已经逼近当前架构下的性能天花板，迭代终止。]
:::

### 2.3 两条核心设计原则

> 整个系统的设计遵循两条核心原则。

- **第一条是代码不跨界原则**：**参考内核的源代码永远不会传递给编码智能体**，只会以封闭二进制的形式送入 GPU 任务中运行，:mdnice-bold-italic[由驱动程序在外部强制保证隔离，避免出现抄袭或复刻代码的情况。]
- **第二条是测量即证据原则**：任何性能结论、任何门控判断、任何知识库条目，:mdnice-bold-italic[都必须基于实际硬件测量的结果，智能体自身的判断不能作为有效证据。]

:::

## 三、参考内核反推：从硬件行为中还原架构设计的黑盒分析法

> 传统的内核优化要么基于源代码改写，要么基于已知的算法范式重新实现。**ForgeKernel 走了一条完全不同的路径：不需要读取参考内核的一行代码，只通过硬件探针观测它的运行行为，就能反向推导出它的架构设计。**

### 3.1 架构决策的硬件指纹映射关系

::: block-1
:mdnice-highlight[这个反推过程的核心依据是：内核的每一个架构决策，都会在硬件层面留下可观测的特征信号。] 就像通过发动机的声音、转速、排气温度就能反推出它的气缸数、涡轮增压方式、燃烧策略一样，**通过 GPU 的性能计数器、流水线状态、访存模式，也能反推出内核的顶层架构。**
:::

架构智能体首先会运行一轮 NCU 剖析，获取参考内核的启动结构、占用率、流水线利用率、停顿原因分解等信息。从这些信息里，可以推断出多类关键的架构特征，具体对应关系如下表：

| 观测维度 | 可推断的架构特征 |
| --- | --- |
| 启动网格/块维度、每 SM CTA 数量 | 任务分解方式、计算分块大小 |
| **每线程束寄存器数量、占用率** | :mdnice-bold-italic[线程束分工模式，加载/计算/存储角色划分] |
| **TMA 与 L2 字节流量** | :mdnice-bold-italic[操作数流水线级数、各级缓存 staging 策略] |
| 屏障停顿分布 | 流水线深度、各阶段耗时占比 |
| 时间线探针（延迟受限场景） | 细粒度时序特征、串行链路瓶颈 |

对于无法通过现有探针明确判断的设计点，架构智能体会明确标记为待确认问题，不会凭空猜测。所有推断出的结论，都要有对应的硬件指标作为支撑。

### 3.2 里程碑课程：架构决策的有序拆解

> 基于这些观测结果，**架构智能体会把参考内核的架构拆解成一个有序的里程碑序列 $M_0 \to M_k$。每个里程碑都是用自然语言描述的决策点**，包含具体动作、设计目的、触发条件、性能开销、依赖关系。

使用自然语言作为载体，是因为参考内核的实现语言千差万别，可能是 CUDA C++、Triton、TileLang，也可能只有二进制没有源码。用自然语言描述的架构决策，可以跨语言落地，从 DeepGEMM 的 CUDA 代码里读出来的设计，可以指导编码智能体用 CuTe DSL 实现；为一个算子总结的优化技巧，也可以迁移到另一个算子上。

里程碑的排序严格遵循**先架构、后调优** 的原则。

- **$M_0$ 是最核心的架构决策层**，包含算法契约（分解方式、数据流、中间张量接口、精度）和硬件架构（分块形状、线程束分工、寄存器预算、共享内存布局、MMA 指令粒度），:mdnice-bold-italic[这些决策决定了整个内核的资源拓扑，必须和参考内核的特征签名对齐。]
- **$M_1$ 到 $M_k$ 则是在固定拓扑下的调优层级**，比如流水线段数、重排模式、等待深度等。:mdnice-bold-italic[如果后期发现瓶颈来自顶层架构，就会回溯到 $M_0$ 重新设计]，而不是在错误的架构下继续硬调。

### 3.3 分层里程碑设计与门控验证

> 每个里程碑的结尾都有严格的门控检查，包含三类验证项：正确性校验、带来源的性能指标、机制验证项。**其中机制验证项是最关键的，它通过特定的性能计数器特征，判断对应的优化机制是否真的落地了**，而不是碰巧出现了性能提升。:mdnice-bold-italic[比如要验证流水线重叠是否生效，不能只看速度变快了，还要看访存停顿和计算停顿的占比变化是否符合预期]。无法验证的项必须明确标记为延迟、不可行或不适用，并且附上对应的证据。

以分析 FlashAttention 内核为例，架构智能体不需要查看源码，通过 NCU 就能获取每个 SM 上的并发 CTA 数量、共享内存用量、寄存器用量、流水线级数、TMA 加载和 MMA 计算的重叠比例。从这些数据就能反推出它的分块大小、K 切片长度、流水线段数、寄存器分块策略，然后把这些点整理成里程碑，让编码智能体从零实现出性能相当的内核。

::: block-1
回顾一下，:mdnice-bold-italic[黑盒架构反推的本质，是把硬件行为当作架构的指纹，通过可观测的信号反向还原顶层设计决策。这个能力让 ForgeKernel 可以吸收任何闭源内核的设计经验]，哪怕只有二进制文件，也能拆解学习、消化吸收，最终实现甚至超越它。
:::

## 四、嵌套式优化循环：架构可调，让优化跳出局部最优陷阱

> 传统智能体的优化是单环结构：编码智能体不断改代码、跑测试、调参数，直到性能不再提升。这种模式的问题在于，**架构一旦定下来就再也改不了，很容易困在局部最优里出不来。ForgeKernel 用内外双环的嵌套结构，解决了这个问题。**

### 4.1 内环：编码智能体的战术级逐点落地

> 内环是编码智能体的实现循环，负责逐个落地里程碑里的决策。

每实现一个决策行，就会启动一次 GPU 任务，同时运行参考内核和当前候选内核，做配对计时和正确性校验。正确性不通过的版本直接回退；$M_0$ 阶段的架构决策会作为一个整体来评估，确保顶层设计的正确性和性能基线。**内环的职责是把给定的架构设计做到最好，属于战术层面的优化。**

### 4.2 外环：架构智能体的瓶颈诊断与课程修订

> 外环是架构智能体的调控循环，这是传统单次智能体不具备的能力。

当出现三种情况时，外环就会介入：

- 第一种是连续 3 次迭代都没有出现新的最优版本；
- 第二种是当前里程碑的决策图已经全部走完，但还没达到目标增益；
- 第三种是某个门控环节陷入僵局，多次调整都无法突破。

**外环介入后，架构智能体不会直接修改代码，而是完成三项工作**：

- 第一，对所有可调节的参数做定价，评估每个参数调整带来的收益幅度；
- 第二，运行针对性的诊断探针，分离单个因素和耦合因素的影响，定位真正的瓶颈来源；
- 第三，根据诊断结果修订里程碑课程。

### 4.3 架构重构的触发逻辑与验收标准

> 如果瓶颈只是战术层面的，比如某个参数没调好、某个指令顺序不对，就生成增量补丁，在内环里接着优化，不用改动整体架构。如果瓶颈是架构层面的，比如分块太大，导致共享内存不足，数据不得不反复倒换，那就属于 $M_0$ 的缺陷，需要生成基础补丁，从最早的依赖决策处重新开始优化。**这就是架构可调整的核心意义：当顶层设计成为瓶颈时，就推翻顶层设计重来，而不是在错误的框架里死磕细节。**

举一个直观的例子：如果一个内核的访存延迟很高，内环可能会反复调整 TMA 的描述符、调整预取的时机，但收益始终有限。外环介入后，通过探针分析发现根本原因是分块太大导致共享内存不足，这时候就会回溯到 $M_0$，调整分块大小的决策，重新设计整个内核的资源分配，虽然改动幅度大，但能带来质的性能提升。

:mdnice-bold-italic[候选内核的通过有严格的标准：同任务计时下的性能增益必须超过测量噪声底限，也就是 1%-5%的区间，确保收益是真实的，不是测量波动带来的假象]。任何无法通过测量验证收益的修改，都会被回退，并且记录到禁止尝试表中，避免后续重复踩坑。

::: block-1
总之，**嵌套双环的核心价值，是让优化具备了推翻重来的能力**。传统智能体只能在一条路径上走到黑，:mdnice-highlight[ForgeKernel 则能在发现路径走不通的时候切换方向，从根源上避免了架构过早固化带来的局部最优陷阱。]
:::

## 五、知识库锻造与复用：把硬件经验变成跨算子的可迁移资产

> 传统智能体的每一次优化都是一次性的，跑过就忘。ForgeKernel 则把每一次优化中验证有效的硬件机制、优化技巧、踩坑经验都沉淀下来，形成可复用的知识库，让后续的优化站在前人的肩膀上。

### 5.1 知识库的标准化配方结构

知识库中的每一条配方，都包含四个部分：机制原理、触发症状、最小可运行示例、已知坑点，并且按照 GPU 架构分类组织。所有配方的来源都只引用公开文档、公共 API 符号和探针验证结果，不会包含任何参考内核的专属命名或代码片段。这意味着，一条配方不会留下它来源参考的任何痕迹，从注意力反向算子中总结出来的经验，可以直接用到 GEMM 算子上，只要它们搭载同一款 GPU 架构。

### 5.2 测量认证的准入与可审计的复用

> 一条配方要进入知识库，必须经过测量认证。

不管是架构智能体提出的还是编码智能体提出的优化思路，都不能直接入库，:mdnice-bold-italic[必须在目标架构上运行一次硬件探针，确认这个机制确实有效、确实能带来对应的收益，才能正式收录。认证的过程会把真正起作用的核心机制和碰巧伴随出现的无关因素分离开]，确保知识库中沉淀的是可复用的硬件行为规律，而不是某个特定场景下的巧合配置。

::: block-1
知识库的使用是双向的。

- 正向是处方路径：架构智能体在制定里程碑课程时，会**根据对应的症状，直接引用知识库中的配方**，把成熟的优化技巧直接安排到优化步骤里，不用再从零摸索。
- 反向是审计路径：每一轮战役的日志都会记录，哪些配方是本轮发明的，哪些是复用了其他算子的配方，**最终交付的内核里落地了多少外来的经验，都可以清晰追溯**，知识库的贡献是可量化的，不是空口宣称。
:::

### 5.3 跨算子迁移的复利效应

> 除了有效的经验，踩过的坑也会沉淀下来，形成禁止尝试表，按照症状和重试前提条件索引。这样后续优化遇到同样的场景时，就可以直接跳过已经验证过无效的路径，少走弯路。

论文中的数据显示，整个知识库在 79 轮优化中积累了 71 条条目，分为 9 大类，**一共有 553 次条目-运行配对，也就是有 553 次复用了已有的知识。而且随着运行次数增加，复用的比例越来越高**：早期的运行平均每轮复用 4.9 条外来条目，中期是 4.1 条，到了后期平均每轮能复用 9.4 条。:mdnice-bold-italic[这说明知识库的价值是随着使用不断增长的，优化的算子越多，沉淀的经验越多，后续优化的速度就越快、起点就越高。]

有两个典型案例能体现知识库的迁移价值。注意力反向和 DSA 稀疏注意力前向的战役，一共贡献了 31 条条目，占了知识库的近一半，因为这两个算子的优化空间大，需要探索的新内容多。:mdnice-bold-italic[而 3D 卷积前向和 DSA 分数重计算这两个算子，优化收益很高，但全程没有发明任何新条目，全部靠复用其他算子沉淀下来的经验就完成了优化。这说明跨算子的知识迁移是真实有效的，很多硬件层面的优化规律具备通用性。]

## 六、自进化迭代：世代式自我超越，逼近硬件性能屋顶线

> 当优化超过了参考内核之后，是不是就到头了？ForgeKernel 给出的答案是否定的。既然参考内核只需要是一个可剖析的二进制，那系统自己写出来的内核，当然也可以当下一代的参考。这就是自进化的核心逻辑。

### 6.1 参考晋升的世代迭代机制

自进化的过程非常直接：把当前已知的最优内核封存起来，不管这个内核是专家写的、其他系统生成的，还是 ForgeKernel 自己上一轮写的，都当作新一轮战役的参考基准，用完全一样的流程重新分析、重新优化。每一代的目标增益设定为 5%，直到新一代相对上一代的收益降到噪声阈值以下，迭代终止。

::: block-1
- 这里很关键的一点是，源代码不会跨代传递。上一代的内核只会以二进制的形式传给下一代，下一代要重新通过硬件剖析来反推它的架构，就像当初分析专家内核一样。
- 但知识库是跨代传递的，上一代摸索出来的所有经验，下一代都可以直接使用。

:mdnice-highlight[这两条反馈路径缺一不可：内核晋升抬高了性能的锚点，知识库降低了达到更高性能的成本，两者共同推动性能不断向上走。]
:::

- GDN 预填充前向，通用智能体**已经比 FlashInfer 快了 82.6%，晋升为参考后，ForgeKernel 又在这个基础上再提升了 9.5%，累计比专家库快了 100%；**
- GQA 注意力前向，通用智能体**比 FlashAttention-4 快 22.8%，晋升后再提升 5%，累计快 29%。**

- DSA 稀疏注意力前向，第一代已经比参考快 2%，晋升后再优化，又提升了 7.2%，累计快 9%；
- GDN 预填充反向，第一代快 1.1%，晋升后再提升 2%，累计快 3%。

### 6.2 迭代收益的本质：强制重启打破局部最优

> :mdnice-bold-italic[为什么晋升之后还能持续找到收益？论文用迭代局部搜索的原理解释：每一代都从当前找到的最优点出发，并且设定了更高的门槛，相当于强制重启一次搜索]。内核优化非常需要这种重启，因为一旦架构定下来，内部的所有参数调完都可能还是达不到全局最优，换一个架构拓扑反而能打开新的优化空间。

### 6.3 DSA 稀疏注意力案例：架构重构的代际跃升

论文中的 DSA 稀疏注意力前向就是一个典型案例。

第一代内核是非持久化设计，每个 SM 一次跑一个 CTA，每个 CTA 的加载、计算、存储是串行的，中间没有重叠。**调优到最后，所有参数都调到头了，最多只能比第一代快 4.5%。后来架构智能体重新分析，发现瓶颈在 CTA 的边界上，输出存储的时间完全暴露在外，没有和计算重叠。** 于是重新打开 $M_0$ 决策，把内核改成持久化循环设计，让前一个工作项的写出和后一个工作项的加载重叠起来。:mdnice-bold-italic[仅仅这一个架构改动，就带来了 7.2%的性能提升，而且这不是调参数能调出来的，必须推翻顶层设计才行。]

![文章插图](/articles/2026-10-28-cake-kda-forgekernel-agent-h100-ae070871/images/12.jpg)

::: image-caption
图 7：DSA稀疏注意力前向的自进化改动示意图。左为第一代非持久化设计，每个SM一个CTA，CTA边界处没有MMA重叠；右为第二代持久化循环设计，前后工作项的加载和写出重叠，节省边界时间
:::

图 7 直观展示了这两代架构的差异。

- 第一代的每个 CTA 都是独立的，做完加载、计算、存储就结束，下一个 CTA 再从头开始，边界处的访存没有计算可以重叠。
- 第二代改成持久化循环之后，一个循环里处理多个工作项，前一个的写出和后一个的加载可以和中间的计算重叠起来，直接吃掉了边界处的空闲时间。

::: block-1
总之，:mdnice-highlight[自进化迭代的本质，是让系统成为自己的标尺，不断用更高的标准要求自己]。它打破了参考内核就是天花板的固有认知，让优化可以一直向前推进，直到逼近硬件的物理屋顶线。
:::

**结果显示，ForgeKernel 在 22 个测试单元中追平或超越了参考实现，几何均值提升 1.6%，最高提升 7.6%。** 其中：

- GEMM 和卷积类算子，面对 cuBLAS、cuDNN 这些经过多年调优的库，性能差距在-0.5%到+7.6%之间；
- FlashAttention-4 在 Hopper 的前后向、Blackwell 的反向都被超越；
- DSA 链路的所有反向算子都超过了 cuDNN-frontend，最高提升 6.2%。

### 7.4 消融实验：参考内核的核心价值验证

> 最后是消融实验，验证参考内核的作用。测试了三种情况：没有参考内核，只有 PyTorch 实现和一个参考时间数值；封闭二进制参考，也就是默认模式；可读源码参考。

![文章插图](/articles/2026-10-28-cake-kda-forgekernel-agent-h100-ae070871/images/17.jpg)

::: image-caption
图 5：参考内核消融实验。每个算子为一组，每组包含三种配置：无参考内核、架构 Agent 可 profiling 的密封二进制（默认配置）、可读源码的参考二进制。所有柱状图均为相对于同一专家库的加速比；前两组配置限制最多三轮元步骤。

结果显示：

- 没有参考内核的时候，三个算子的优化都卡住了，性能很差；
- 给了封闭二进制之后，三个都恢复了正常水平，和专家库的差距都在 1%以内；
- 给了源码之后，只有小幅的额外提升，几何均值从 1.5%涨到 2.5%。

这说明，:mdnice-bold-italic[参考内核的核心价值是传递架构信息，而不是代码本身，二进制提供的信息已经足够支撑绝大多数优化，源码的边际收益其实很小。]

### 7.5 方法边界与行业长期启示

> 当然，这套方法也有它的边界。论文里明确提到了三个局限性：

| 局限性 | 描述 |
| --- | --- |
| 依赖参考内核 | **必须有一个参考内核作为起点**，如果只有一个功能正确的朴素实现，没有高性能参考，系统的优化效果会大打折扣；它擅长超越已有的优秀实现，不擅长从零写出第一个高性能版本。 |
| 平台期为估计值 | **最终达到的平台期是估计值**，不是严格证明的硬件极限；只能说明这套循环找不到更多收益了，不代表完全没有提升空间。 |
| 算子与硬件覆盖有限 | 目前测试的算子只有四大类，覆盖了 NVIDIA 两代架构和一款昇腾芯片；**差异更大的稀疏模式和存储层级尚未验证**。 |

从我坐在工位前的视角来看，ForgeKernel 带来的启发远不止内核优化本身。它证明了两件事：

- 第一，对于复杂的工程优化任务，给大模型套上精心设计的外部流程框架，收益可能比单纯提升模型本身的能力还要大；
- 第二，知识的沉淀和复用是智能系统能力跃迁的关键，无状态的单次运行永远比不上有记忆的持续积累。

> 未来，:mdnice-bold-italic[随着模型本身的编码能力越来越强，ForgeKernel 框架里的很多引导性模块可能会逐渐失效，被模型内化的能力取代]。但经过硬件测量验证的、关于 GPU 硬件行为规律的**知识库，会一直保有价值**。因为硬件的物理规律是不变的，不管模型能力多强，都要遵循硬件的运行规则。

::: block-1
:mdnice-highlight[自进化非但不是终点，而恰恰是一种新的起点🐸]。当系统能够自己设定目标、自己积累经验、自己超越自己，优化就不再是一次性的任务，而是一个持续生长的过程。ForgeKernel 打开了内核优化的自进化大门，而这扇门背后，是更广阔的、所有工程优化领域都可以借鉴的全新范式。（害怕）
:::
