## 一、RAG 推理的致命瓶颈：检索与预填充的串行困境

> 检索增强生成（RAG）技术的出现，从根本上解决了大型语言模型参数知识的时效性、准确性和领域特异性问题。通过将用户查询与外部知识库中的相关文档拼接成完整 prompt，模型能够生成基于事实的、最新的回答。

**然而，RAG 系统的性能瓶颈已经从模型本身的推理速度，转移到了检索与推理的交互方式上**。在传统的 RAG 架构中，检索和推理是完全串行的两个阶段：:mdnice-bold-italic[系统首先向检索系统发送查询，等待所有相关文档检索完成并拼接成完整 prompt 后，才开始执行预填充阶段，生成第一个输出 token。]

### 1.1 检索延迟的不可忽视性

> 检索延迟是 RAG 系统中最大的延迟来源。根据论文中的数据：网页爬虫检索的平均延迟高达 9.9 秒，即使是优化较好的磁盘基 ANNS 检索，:mdnice-bold-italic[平均延迟也达到了 4.5 秒]。相比之下，Llama-3.1-8B 模型在 H200 GPU 上处理 :mdnice-bold-italic[10K token 的预填充延迟仅为几十毫秒]。**这意味着，在传统架构中，检索延迟占了首字延迟的 90%以上。**

检索延迟之所以难以降低，是由其本质决定的：

- 网页爬虫需要进行网络请求、DNS 解析、页面下载和内容解析，每个步骤都有不可避免的延迟，而且不同页面的加载时间差异极大。
- 大规模向量检索系统为了平衡成本和性能，通常使用磁盘基索引（如 DiskANN、SPANN），每次搜索需要进行多次磁盘 I/O 操作，延迟随着索引规模的增加而增加。
- 复杂的检索流水线还包括查询嵌入、结果过滤、重排序等步骤，进一步增加了端到端延迟。

### 1.2 传统架构的两难选择

> 面对高检索延迟，传统 RAG 系统只能在两个糟糕的选项之间做出选择：

- **选项一：等待所有上下文检索完成再开始推理**。这:mdnice-bold-italic[保证了回答质量，但首字延迟极高]，严重损害用户体验。对于需要实时交互的应用（如智能客服、对话助手）来说，数秒的延迟是不可接受的。
- **选项二：用部分上下文提前开始生成**。这可以:mdnice-bold-italic[降低首字延迟，但由于缺少关键信息，回答质量会显著下降]，甚至出现幻觉或错误。而且，如果后续检索到的信息与已生成的内容矛盾，系统无法回溯修改，只能继续生成错误的回答。

### 1.3 单请求流式处理的局限性

> 为了打破这一两难局面，**研究人员提出了上下文流式处理的思路：将检索到的文档分块，每收到一个块就立即输入模型，让检索和预填充阶段重叠执行**。这样，模型可以在检索后续文档的同时，处理已经收到的文档，从而显著降低首字延迟。

然而，:mdnice-bold-italic[现有的流式处理系统（如 PipeRAG 和 AquaPipe）都只针对单请求场景设计，无法适应生产环境的并发请求需求]。在并发环境下，多个请求同时流式输入上下文，会导致以下问题：

- **GPU 内存竞争**：每个请求的 KV 缓存会随着上下文的增加而不断增长，当总内存超过 GPU 容量时，系统需要抢占低优先级请求的缓存。
- **调度难题**：不同请求的上下文块到达时间是异步的，传统的基于到达时间或进度的调度策略无法适应这种动态变化。
- **缓存管理难题**：在更新模式下，上下文会被不断替换，传统的 KV 缓存管理机制无法高效处理动态变化的输入序列。

::: block-1
传统 RAG 系统的核心矛盾是检索延迟与首字延迟的串行依赖，:mdnice-bold-italic[单请求流式处理虽然缓解了这一矛盾，但无法解决并发环境下的资源竞争、调度和缓存管理难题，这正是 Stream2LLM 要解决的核心问题。]
:::

## 二、Stream2LLM 的核心设计哲学：解耦与统一

> Stream2LLM 的设计目标是构建一个支持并发流式输入的 LLM 推理服务系统，在保持系统吞吐量不变的前提下，最大限度地降低首字延迟。**为了实现这一目标，研究人员提出了两个核心设计原则：统一支持两种主流的上下文检索模式，以及将调度决策与资源获取完全解耦**。

这两个原则贯穿了 Stream2LLM 的整个架构设计，使其能够高效处理动态变化的并发流式工作负载。

### 2.1 部署假设：预填充-解码分离架构

> Stream2LLM 针对的是预填充-解码分离的部署架构，这是当前工业界大规模 LLM 服务的标准做法。在这种架构中，预填充阶段和解码阶段分别运行在独立的 GPU 池上：

- 预填充 GPU 池负责处理输入 prompt 的并行计算，生成 KV 缓存。
- 解码 GPU 池负责自回归生成输出 token，每个步骤只处理一个新 token。

这种分离架构的优势在于，预填充和解码具有截然不同的计算和内存特性，可以分别进行优化：预填充是计算密集型的，适合大 batch 处理；解码是内存带宽密集型的，适合小 batch 处理。**Stream2LLM 只优化预填充阶段的性能，不影响解码阶段的每 token 延迟（TPOT）**，这使得它可以无缝集成到现有的工业界部署架构中。

### 2.2 统一支持两种流式模式

> **Stream2LLM 的第一个核心设计原则是统一支持两种主流的上下文检索模式**：追加模式和更新模式。这两种模式对应了不同的检索系统特性，对调度和缓存管理有不同的要求。

- **追加模式适用于上下文单调增长的场景，比如网页爬虫检索**。在这种模式下，文档按到达顺序逐步追加到输入序列的末尾，不会修改之前已经收到的内容。:mdnice-bold-italic[追加模式的特点是 KV 缓存可以不断累积，不需要失效之前的内容。]
- **更新模式适用于上下文逐步精炼的场景，比如 ANNS 检索**。在这种模式下，检索系统会先返回部分结果，然后随着搜索的进行，用更相关的文档替换之前的结果，最终得到最优的 top-k 文档集。:mdnice-bold-italic[更新模式的特点是输入序列会频繁变化，需要频繁失效和重建 KV 缓存。]

传统的流式处理系统要么只支持追加模式，要么只支持更新模式，而 Stream2LLM 通过统一的 LCP 缓存失效机制，同时支持这两种模式，大大提高了系统的通用性。

### 2.3 解耦调度与资源获取

> **Stream2LLM 的第二个核心设计原则是将调度决策与资源获取完全解耦**。在传统的 LLM 推理调度器中，优先级排序、资源分配和抢占是紧密耦合在一个控制循环中的。这种设计在静态输入场景下工作良好，但在动态流式输入场景下，会导致以下问题：

- 固定策略耦合：当资源耗尽时，调度器必须立即按照静态规则抢占请求，这可能与调度策略的优先级概念相矛盾。
- 缓存失效耦合：当输入序列更新时，token 计数的变化和缓存块的失效会与调度和资源分配交织在一起，导致逻辑混乱和错误。

Stream2LLM 将整个调度过程分为两个独立的阶段：:mdnice-bold-italic[第一阶段只负责优先级排序和可行性分析，不修改任何系统状态；第二阶段只负责资源分配和自适应抢占]。这种解耦使得调度策略可以独立于资源管理机制进行设计和优化，大大提高了系统的灵活性和可扩展性。

::: block-1
Stream2LLM 的核心设计哲学是“解耦与统一”：通过统一的缓存机制支持两种主流检索模式，通过两阶段架构解耦调度决策与资源获取，从而实现并发流式输入下的高性能推理。
:::

## 三、两阶段调度架构：优先级与资源分配的分离

> 两阶段调度架构是 Stream2LLM 最核心的创新之一，它彻底改变了传统 LLM 调度器的设计思路。

通过将优先级排序与资源分配分离，Stream2LLM 能够在动态变化的流式工作负载下，灵活地调整请求优先级，同时高效地管理 GPU 资源，避免了传统调度器的固有缺陷。

![文章插图](/articles/2026-05-29-11-ttft-stream2llm-rag-08d1549a/images/04.webp)

::: image-caption
图 3：STREAM2LLM 两阶段调度器概览，该架构将调度决策与资源获取分离。第一阶段确定请求优先级与可行性，第二阶段分配 KV 缓存块并在内存压力下执行抢占。传统 vLLM 调度器将优先级决策、资源分配、抢占逻辑耦合，易出现策略固化、缓存管理混乱、优先级被资源限制干扰等问题。STREAM2LLM 创新性采用两阶段解耦架构，第一阶段仅做优先级排序与可行性预判，不占用硬件资源，保证优先级判断的客观性；第二阶段按预判结果分配 KV 缓存，内存不足时优先抢占低优先级请求。该设计让调度策略灵活适配动态负载，支持定制化抢占逻辑，显著提升并发场景下 GPU 资源利用率，为自适应抢占和缓存优化提供灵活的架构支撑。
:::

### 3.1 第一阶段：优先级排序与可行性分析

> 第一阶段的任务是根据选定的调度算法，对所有未完成的请求进行优先级排序，并进行可行性分析，确定哪些请求可以在当前调度步骤中执行。

- 在这一阶段，调度器首先调用调度算法（如 FCFS、MCPS 或 LCAS），计算所有未完成请求的优先级，并按照优先级从高到低排序。
- 然后，调度器按照优先级顺序，依次估计每个请求所需的 KV 缓存块数量（基于已处理的 token 数和新到达的 token 数），并检查是否有足够的空闲 GPU 块。如果有足够的块，则将该请求标记为可调度；否则，标记为不可调度。

需要特别强调的是，**第一阶段不进行任何实际的资源分配，也不修改任何请求的状态。它只是计算出一个优先级排序的可调度请求列表和不可调度请求列表**。这种纯计算的阶段使得调度器可以快速地重新排序请求，适应动态变化的块到达模式。

### 3.2 第二阶段：资源获取与自适应抢占

> 第二阶段的任务是为第一阶段选出的可调度请求分配 GPU 资源，并在内存不足时执行自适应抢占。

调度器按照优先级顺序，依次为每个可调度请求分配 KV 缓存块。

- 如果分配成功，则将该请求加入当前执行批次。
- 如果分配失败（即 GPU 内存不足），则调度器从不可调度请求列表中，按照反向优先级顺序（即最低优先级先）选择一个请求进行抢占。

抢占时，调度器使用成本感知的决策框架（将在第五章详细介绍），选择是通过重计算还是交换来释放内存。抢占完成后，重新尝试为当前请求分配资源，直到所有可调度请求都被处理或者没有更多资源可以释放。

### 3.3 请求生命周期管理

> Stream2LLM 将请求的生命周期分为三个状态：等待状态、运行状态和完成状态。

![文章插图](/articles/2026-05-29-11-ttft-stream2llm-rag-08d1549a/images/05.webp)

::: image-caption
图 4：STREAM2LLM 请求状态转换。STREAM2LLM 将请求生命周期划分为等待、运行、完成三个核心队列，状态转换由两阶段调度机制驱动。新请求初始进入等待队列，经第一阶段优先级筛选、第二阶段资源分配后转入运行队列；运行中请求若因内存不足被抢占，会返回等待队列，抢占策略决定其状态（交换缓存至 CPU 或丢弃缓存重计算）；请求生成完成后进入完成队列。清晰的状态流转可精准追踪每个请求的执行进度，适配上下文动态到达的异步特性，为调度器动态调整优先级、管理缓存生命周期提供状态依据，保障并发请求有序高效执行。
:::

请求的状态转换完全由两阶段调度架构控制：

- 当一个新请求到达时，进入等待状态。
- 当请求在第一阶段被选为可调度，并在第二阶段成功分配资源后，进入运行状态。
- 当运行中的请求完成所有预填充计算后，进入完成状态，并被发送到解码 GPU 池进行后续的 token 生成。
- 如果运行中的请求被抢占，则返回到等待状态。

这种清晰的状态管理机制，使得 Stream2LLM 能够准确跟踪每个请求的状态和进度，为调度和抢占决策提供可靠的依据。

::: block-1
两阶段调度架构通过分离优先级排序与资源分配，解决了传统调度器在动态流式输入下的耦合问题，使得系统能够灵活适应不同的调度策略和工作负载特性。
:::

## 四、LCP 缓存失效机制：动态上下文下的最小化重计算

> KV 缓存是 LLM 推理中最重要的性能优化技术之一，它通过存储之前计算的 key 和 value 值，避免了自回归生成过程中的重复计算。

然而，传统的 KV 缓存管理机制假设输入序列是固定不变的，这在流式上下文场景下不再成立。当输入序列发生变化时，如何高效地更新 KV 缓存，最小化重计算开销，成为了一个关键问题。

![文章插图](/articles/2026-05-29-11-ttft-stream2llm-rag-08d1549a/images/06.webp)

::: image-caption
图 2：STREAM2LLM 支持两种检索模式 —— 追加模式与更新模式，并通过最长公共前缀（LCP）匹配保留输入更新中的共享前缀，从而最小化缓存失效。作者明确上下文检索分为追加、更新两类典型模式，前者上下文单调递增、无内容替换，后者迭代优化、频繁更新上下文。两种模式对 KV 缓存管理需求差异极大，盲目全量失效缓存会产生巨额冗余计算。STREAM2LLM 引入 LCP 匹配机制，精准定位新旧输入的公共前缀，仅失效变化部分的缓存块，复用有效缓存。该机制统一适配两种检索模式，大幅降低更新模式下的缓存失效开销，平衡缓存复用率与计算效率，解决动态上下文场景下缓存浪费的核心痛点。
:::

### 4.1 传统缓存管理的局限性

> 在传统的 LLM 推理系统中，输入序列在请求到达时就已经确定，KV 缓存一旦生成就不会再变化。当输入序列发生变化时，系统只能采取两种极端策略：

- 全部失效：丢弃所有已生成的 KV 缓存，重新计算整个输入序列的 KV 值。这种策略简单但效率极低，尤其是当输入序列很长时，重计算开销非常大。
- 全部保留：继续使用原来的 KV 缓存，忽略输入序列的变化。这种策略会导致模型基于过时的上下文进行计算，生成错误的回答。

在流式上下文场景下，输入序列会频繁地追加或更新，这两种策略都无法满足性能要求。例如，在更新模式下，如果每次更新都全部失效缓存，那么流式处理带来的 TTFT 提升会被重计算开销完全抵消。

### 4.2 最长公共前缀（LCP）缓存失效

> Stream2LLM 提出了基于最长公共前缀（LCP）的缓存失效机制，完美解决了动态上下文下的 KV 缓存管理问题。**其核心思想是：当输入序列发生变化时，计算新旧输入序列的最长公共前缀，只失效前缀之后的 KV 缓存块，保留前缀部分的缓存。**

例如，假设原来的输入序列是[d1, d2, q]，对应的 KV 缓存已经生成。现在输入序列更新为[d1, d2', q]，其中 d2'是替换后的新文档。新旧序列的最长公共前缀是[d1]，长度为 1。因此，系统只需要失效 d2 和 q 对应的 KV 缓存块，保留 d1 对应的缓存块。然后，:mdnice-bold-italic[系统只需要重新计算 d2'和 q 的 KV 值，而不需要重新计算整个序列。]

**这种机制的优势在于，它能够最小化重计算开销，同时保证缓存的正确性**。无论是追加模式还是更新模式，LCP 机制都能自动适应，不需要任何特殊处理。在追加模式下，新旧序列的最长公共前缀就是原来的整个序列，因此不会失效任何缓存块，只需要追加新的缓存块即可。

### 4.3 缓存失效的语义与交互

> Stream2LLM 的 LCP 缓存失效机制具有清晰的语义：

- 当 k 个 token 在 LCP 之后被失效时，调度器会释放对应的 KV 缓存块，并将它们返回到空闲块池。
- 对于已经被交换到 CPU 内存的请求，调度器会先在 CPU 内存中失效对应的块，然后再将剩余的块交换回 GPU。
- 调度器会将已计算 token 数设置为 LCP 的长度，强制系统只重新计算 LCP 之后的 token。

这种设计确保了缓存失效与抢占机制的正确交互，避免了内存泄漏和状态不一致的问题。:mdnice-bold-italic[例如，当一个被交换到 CPU 的请求收到输入更新时，系统会先在 CPU 上失效对应的块，释放 CPU 内存，然后再将剩余的有效块交换回 GPU，最后重新计算失效的部分。]

::: block-1
基于 LCP 的缓存失效机制是 Stream2LLM 能够统一支持追加和更新模式的核心技术，它通过最小化重计算开销，使得流式上下文处理在动态输入场景下仍然具有性能优势。
:::

## 五、成本感知的自适应抢占：内存压力下的最优决策

> 在并发流式输入场景下，多个请求的 KV 缓存会同时增长，很容易耗尽 GPU 内存。当内存不足时，系统必须抢占低优先级请求的缓存，释放内存给高优先级请求。

传统的 LLM 调度器通常使用固定的抢占策略，要么总是重计算，要么总是交换。然而，这两种策略在不同的场景下各有优劣，固定策略无法在所有情况下都获得最优性能。

### 5.1 两种抢占策略的成本分析

> vLLM 支持两种抢占策略：重计算和交换。每种策略都有不同的成本特性：

- 重计算：丢弃被抢占请求的所有 KV 缓存块，释放内存。当请求恢复时，需要重新计算所有已处理 token 的 KV 值。重计算的成本是计算延迟，与已处理的 token 数成正比。
- 交换：将被抢占请求的 KV 缓存块从 GPU 内存转移到 CPU 内存，释放 GPU 内存。当请求恢复时，需要将缓存块从 CPU 内存交换回 GPU 内存。交换的成本是数据传输延迟，与缓存块的大小成正比，与 PCIe 带宽成反比。

对于一个有 l 个已处理 token 的请求 r，重计算的成本可以表示为：

$$
C_{recomp}(r) = l \cdot C_{prefill}
$$

其中，$C_{prefill}$ 是每个 token 的预填充延迟。

交换的成本（包括移出和移入）可以表示为：

$$
C_{swap}(r) = 2 \cdot \frac{\lceil l / k \rceil \cdot M_{block}}{BW_{PCIe}}
$$

其中，k 是每个 KV 缓存块的 token 数，$M_{block}$ 是每个块的大小，$BW_{PCIe}$ 是 PCIe 带宽。

### 5.2 硬件特定的成本模型

> Stream2LLM 的核心洞察是，**最优的抢占策略取决于硬件特性和请求状态**。不同的 GPU 具有不同的计算能力和内存带宽，因此重计算和交换的相对成本也不同。

为了实现最优的抢占决策，Stream2LLM **在离线阶段为每个目标硬件平台构建了两个性能模型：**

- 重计算延迟模型：预测在该 GPU 上重计算 l 个 token 所需的时间。研究人员在不同的 GPU（A40、H100、H200）上测量了不同 token 数（1K-128K）的预填充延迟，并拟合了分段线性模型，以考虑内存带宽饱和的影响。
- 交换延迟模型：预测在该平台上交换 m 个 KV 缓存块所需的时间。研究人员测量了不同块大小的传输延迟，并考虑了 PCIe 带宽的限制。

### 5.3 自适应抢占决策

> 在运行时，当需要抢占一个请求时，Stream2LLM 会使用离线构建的成本模型，分别计算重计算和交换的成本，然后选择成本较低的策略。

这种自适应抢占策略具有以下优势：

- 硬件感知：能够根据不同的 GPU 特性自动调整策略，在所有平台上都获得最优性能。
- 负载感知：能够根据请求的已处理 token 数动态调整策略。对于已处理 token 数较少的请求，重计算成本较低，适合重计算；对于已处理 token 数较多的请求，交换成本较低，适合交换。
- 模式感知：在追加模式下，请求的 KV 缓存会不断累积，重计算成本会越来越高，因此倾向于交换；在更新模式下，请求的 KV 缓存会频繁失效，交换的缓存很快就会被丢弃，因此倾向于重计算。

实验结果表明，**成本感知的自适应抢占策略在两种工作负载下都获得了最好的性能，显著优于固定的重计算或交换策略。**

::: block-1
成本感知的自适应抢占策略通过硬件特定的成本模型，动态选择最优的抢占方式，解决了内存压力下的性能退化问题，是 Stream2LLM 能够在生产环境中稳定运行的关键保障。
:::

## 六、调度策略对比：不同工作负载下的性能表现

> Stream2LLM 的两阶段调度架构支持多种调度算法，用户可以根据工作负载特性选择最合适的策略。

论文中实现并对比了四种调度算法：DEFAULT vLLM、FCFS、MCPS 和 LCAS。每种算法都有不同的设计目标和性能特性，适用于不同的场景。

### 6.1 四种调度算法的原理

> DEFAULT vLLM 调度器是 vLLM 原生的调度器，它基于到达时间对等待队列进行排序，处理新请求采用 FIFO 顺序。当 GPU 内存耗尽时，它会抢占运行队列中的最后一个请求（LIFO 抢占）。被抢占的请求会被重新插入到等待队列的前端，以保持优先级。

| 调度器 | 核心策略 | 内存不足时的抢占策略 | 主要优缺点 |
| --- | --- | --- | --- |
| **DEFAULT vLLM** | 忽略上下文块到达时间与更新成本，不适应流式动态负载 | 未明确说明（默认无主动抢占机制） | ❌ 无法响应流式输入变化；❌ 忽视重计算开销 |
| **FCFS** | 分两级：完整请求（输入完成）优先于部分请求（输入中）；同级按到达时间排序 | 按调度顺序**反向** 抢占（即最后调度的先被抢占） | ✅ 简单公平；❌ 忽略块时效性与重计算成本 |
| **MCPS** | 按**已处理 token 数** 降序排序（多者优先），平局按到达时间 | 抢占**已处理 token 数最少** 的请求 | ✅ 追加模式下高效，减少切换；❌ 更新模式下 LCP 缩短致优先级骤降，浪费计算 |
| **LCAS** | 分完整/部分两级；同级按**最近块到达时间** 升序（越新越优先） | 抢占**最久未收块** 的请求 | ✅ 响应及时，利于缓存局部性与更新处理；❌ 可能导致低活跃请求**饥饿** |

## 七、实验评估：真实世界负载下的性能验证

> 为了全面评估 Stream2LLM 的性能，研究人员收集了两个大规模的真实世界流式工作负载：网页爬虫负载（追加模式）和 ANNS 检索负载（更新模式）。

实验在 NVIDIA H100 和 H200 GPU 上进行，使用 Llama-3.1-8B-Instruct 模型，对比了 Stream2LLM 与非流式基线（vLLM-NS）和默认流式基线（vLLM-S）的性能。

### 7.1 实验设置与工作负载特征

> 研究人员首先收集了两个真实世界的流式工作负载，并对其特征进行了分析：

两个工作负载的块到达模式有显著差异：

- ANNS 负载的块到达间隔中位数为 36.7ms，大部分在 1-1000ms 之间，分布比较集中。
- 爬虫负载的块到达间隔中位数为 700.7ms，是 ANNS 的 19 倍，分布范围从几十毫秒到超过 30 秒，变异性极大。
- ANNS 负载的每个查询平均收到 1-3 个块，而爬虫负载的每个查询平均收到 6-10 个块。

这些差异导致爬虫负载对调度器的要求更高，因为它需要处理更长时间的空闲和更频繁的优先级变化。

### 7.2 首字延迟（TTFT）性能

- **流式架构同样显著优于非流式基线**。在 QPS 1.0 时，流式调度器的 P95 TTFT 比非流式快 2.49-2.63 倍。

:::

### 7.3 吞吐量与内存压力性能

> 为了验证 Stream2LLM 是否会牺牲吞吐量来换取更低的 TTFT，研究人员测量了不同调度器的跟踪完成时间（即处理所有请求的总时间）。

![文章插图](/articles/2026-05-29-11-ttft-stream2llm-rag-08d1549a/images/10.webp)

> 为了评估内存压力下的性能，研究人员通过增加块延迟来饱和 GPU KV 缓存池。结果如表 3 所示：

- **Stream2LLM 的 FCFS 和 LCAS 调度器在内存压力下仍然保持了优异的性能**。在爬虫负载下，FCFS 使用成本感知抢占策略，P99 TTFT 比非流式快 8.62 倍；LCAS 快 9.14 倍。在 ANNS 负载下，FCFS 快 2.04 倍。
- **成本感知的自适应抢占策略显著优于固定策略**。在爬虫负载下，FCFS 使用成本感知策略的 P99 加速比是 8.62 倍，而使用固定重计算是 10.03 倍，固定交换是 6.69 倍。:mdnice-bold-italic[成本感知策略平衡了两种固定策略的优势，获得了接近最优的性能。]

### 7.4 开销分析

> 最后，研究人员分析了 Stream2LLM 的额外开销：

- 调度开销：调度器的排序和预算分配每个调度步骤增加了亚毫秒级的开销。在 50 个并发请求下，FCFS/LCAS 的排序延迟为 15-16µs，MCPS 为 12-13µs。即使在 500 个请求下，P99 延迟仍然低于 165µs，与预填充计算相比可以忽略不计。
- 离线建模开销：硬件特定成本模型的离线建模每个 GPU 配置大约需要 5 分钟，并且存储为 JSON 文件，没有运行时开销。
- 缓存失效开销：在 ANNS 负载下，超过 10%的请求会失效超过 10,000 个 token。尽管存在这一开销，流式架构仍然获得了约 2 倍的 TTFT 提升，证明了收益大于成本。

::: block-1
**Stream2LLM 在真实世界负载下实现了最高 11 倍的 TTFT 提升，同时保持了与非流式基线相同的吞吐量**。在内存压力下，智能调度和成本感知抢占避免了灾难性的尾延迟退化，证明了其在生产环境中的实用性。
:::

## 八、相关工作：从单请求流处理到并发系统的跨越

> 上下文流式处理和 LLM 推理服务是当前 AI Infra 领域的研究热点，已经有大量的相关工作。

Stream2LLM 在这些工作的基础上，首次实现了支持并发流式输入的通用 LLM 推理服务系统，解决了之前工作的局限性。

### 8.1 检索-推理协同设计

> 检索-推理协同设计的核心思想是打破检索和推理的串行边界，通过重叠执行来降低端到端延迟。这一领域的代表性工作包括 PipeRAG 和 AquaPipe。

- **PipeRAG（Jiang et al., 2024）使用流水线并行技术，将检索和推理阶段重叠执行，实现了迭代的检索-生成流程**。然而，PipeRAG :mdnice-bold-italic[针对的是编码器-解码器架构，与当前主流的因果自注意力模型不兼容]。此外，PipeRAG :mdnice-bold-italic[只支持固定的批量大小，不支持动态的并发请求。]
- **AquaPipe（Yu et al., 2025）通过召回感知的预取技术，提前返回 ANNS 的部分结果，实现了更新模式的流式处理**。然而，AquaPipe :mdnice-bold-italic[只支持单请求场景，不支持并发请求的调度和资源管理]。此外，AquaPipe :mdnice-bold-italic[需要中断和重启预填充阶段]，这在生产级推理系统（如 vLLM）中是不支持的。

> Stream2LLM 与这些工作的主要区别在于：

- 支持并发请求：Stream2LLM 是第一个支持并发流式输入的通用 LLM 推理服务系统。
- 统一支持两种模式：Stream2LLM 通过 LCP 缓存失效机制，同时支持追加和更新两种检索模式。
- 兼容工业界标准：Stream2LLM 基于 vLLM 扩展，兼容预填充-解码分离的工业界部署架构，不需要修改底层推理引擎的核心逻辑。

### 8.2 LLM 推理服务

> LLM 推理服务领域的研究主要集中在提高系统的吞吐量和降低延迟。代表性工作包括 vLLM、Orca、Sarathi-Serve 以及预填充-解码分离架构。

- vLLM（Kwon et al., 2023）提出了 PagedAttention 技术，将 KV 缓存分为固定大小的块，实现了高效的内存管理和前缀共享。然而，vLLM 的调度器假设输入序列是固定不变的，不支持动态的流式输入。
- Orca（Yu et al., 2022）提出了连续批处理技术，允许在解码步骤之间添加或删除请求，显著提高了系统吞吐量。但 Orca 同样假设输入序列是固定的，不支持流式输入。
- Sarathi-Serve（Agrawal et al., 2024）通过分块预填充和流水线调度，最小化了流水线停顿，提高了系统的吞吐量和延迟性能。但 Sarathi-Serve 仍然针对静态输入设计，不支持动态上下文更新。
- 预填充-解码分离架构（Mooncake、DistServe、Splitwise）将预填充和解码阶段分别运行在独立的 GPU 池上，实现了更高效的资源利用。Stream2LLM 正是针对这一架构设计的，只优化预填充阶段的性能，不影响解码阶段。

**Stream2LLM 在这些工作的基础上，扩展了 vLLM 的调度器和缓存管理器，使其能够支持动态的流式输入**，同时保留了原有系统的高性能和可扩展性。

### 8.3 调度与缓存优化

> 调度和缓存优化是 LLM 推理服务的核心技术。代表性工作包括各种调度策略和 RadixAttention。

- 调度策略方面，已经提出了从 FCFS 到 SJF 的各种变体，以及 Sarathi-Serve 的流水线感知调度。然而，这些调度策略都假设输入序列是固定的，没有考虑流式输入下的动态优先级变化。
- 缓存优化方面，RadixAttention（Zheng et al., 2024）通过基数树实现了细粒度的前缀共享，进一步提高了 KV 缓存的利用率。但 RadixAttention 同样针对静态输入设计，不支持输入序列变化时的缓存失效。

**Stream2LLM 的 LCP 缓存失效机制与 RadixAttention 是互补的**。RadixAttention 优化了多个请求之间的前缀共享，而 LCP 机制优化了单个请求在输入变化时的缓存重用。未来可以将两者结合，进一步提高缓存效率。

::: block-1
Stream2LLM 是检索-推理协同设计领域的重要里程碑，它首次将单请求流式处理扩展到了并发生产环境，为大规模 RAG 系统的低延迟部署提供了可行的解决方案。
:::

## 九、结论与展望

Stream2LLM 的提出，标志着 RAG 系统的架构从串行检索-推理向并行流式处理的转变。它通过创新的两阶段调度架构、LCP 缓存失效机制和成本感知自适应抢占策略，在保持吞吐量不变的前提下，实现了最高 11 倍的 TTFT 提升，为 AI 推理服务领域带来了新的思路和方向。

### 9.1 结论总结

> Stream2LLM 是一个支持并发流式输入的 LLM 推理服务系统，它基于 vLLM 引擎扩展，针对预填充-解码分离的工业界标准部署架构，解决了上下文流式处理在并发环境下的核心挑战。

论文的核心贡献包括：

1. 提出了 Stream2LLM 系统，首次实现了支持并发流式输入的通用 LLM 推理服务，统一支持追加模式和更新模式两种主流检索工作负载。
2. 设计了两阶段调度架构，将优先级排序与资源分配解耦，实现了灵活的调度策略和自适应抢占机制。
3. 提出了基于最长公共前缀（LCP）的缓存失效机制，最小化了动态输入变化时的重计算开销。
4. 实现了成本感知的自适应抢占策略，根据硬件特性和请求状态动态选择最优的抢占方式。
5. 在两个真实世界的大规模流式工作负载上进行了全面的评估，证明 Stream2LLM 能够实现最高 11 倍的 TTFT 提升，同时保持与非流式基线相同的吞吐量。

论文的核心结论是：流式上下文处理是降低 RAG 系统首字延迟的必要条件，但仅有流式架构是不够的，**智能的调度和缓存管理是流式处理在生产环境中可用的关键。**

### 9.2 进阶分析

> 尽管 Stream2LLM 取得了显著的性能提升，但它仍然存在一些局限性和未解决的问题：

- 部署架构假设：Stream2LLM 是在预填充-解码分离的架构假设下设计的。如果部署架构不是分离的，而是预填充和解码共享 GPU 资源，那么 Stream2LLM 的性能会打折扣，因为它没有考虑解码阶段对 GPU 资源的竞争。
- LCP 机制的局限性：LCP 缓存失效机制在输入更新影响前缀时效果不佳。例如，如果第一个文档被替换，那么最长公共前缀为空，所有缓存都将失效，重计算开销与全部失效相同。对于频繁修改前缀的工作负载，LCP 机制的优势会消失。
- 饥饿问题：LCAS 调度算法虽然综合性能最好，但存在饥饿问题。如果一个请求长时间没有收到新的上下文块，它会被不断抢占，永远无法完成。论文中没有提出有效的解决方案来解决这个问题。
- 静态成本模型：Stream2LLM 的成本模型是离线静态构建的，没有考虑运行时的系统负载变化。当系统负载很高时，PCIe 带宽会被多个交换操作抢占，导致实际交换延迟高于模型预测值，从而影响抢占决策的准确性。
- 工作负载覆盖范围：论文只评估了网页爬虫和 ANNS 两种检索工作负载，没有评估其他流式场景，比如用户实时输入 prompt、多模态流式输入等。Stream2LLM 在这些场景下的性能还需要进一步验证。

### 9.3 未来工作

> 论文作者在文中指出了几个未来的研究方向：

- **支持更复杂的上下文更新模式**：目前 Stream2LLM 只支持追加和完全替换两种更新模式，:mdnice-bold-italic[未来可以扩展支持插入和删除操作，进一步提高缓存利用率。]
- **解决饥饿问题**：设计新的调度算法，在保持 LCAS 性能优势的同时，避免饥饿问题，确保所有请求都能在合理的时间内完成。
- **动态成本模型**：:mdnice-bold-italic[实现动态更新的成本模型，能够根据运行时的系统负载（如 PCIe 带宽利用率、GPU 计算利用率）实时调整重计算和交换的成本估计]，提高抢占决策的准确性。
- 支持更大的模型和更长的上下文：将 Stream2LLM 扩展到支持 70B 甚至更大的模型，以及 100K 以上的长上下文，验证其在大规模场景下的性能。

::: block-1
Stream2LLM 的出现，为 RAG 系统的性能优化打开了新的大门。随着技术的不断发展，我们有理由相信，未来的 RAG 系统将能够实现真正的实时交互，为用户提供更加流畅和自然的体验。
:::
