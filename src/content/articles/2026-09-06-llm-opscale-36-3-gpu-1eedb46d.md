## 一、LLM 推理扩缩容的本质困境：整模型调度的两大顽疾

> 在云原生 LLM 服务体系中，自动扩缩容是平衡服务质量与资源成本的核心机制。**当前业界主流方案均采用模型级扩缩容，即通过增减完整模型副本的数量来匹配流量波动。**

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/05.webp)

::: image-caption
图 1｜模型级与算子级 LLM 服务扩容范式对比。上方模型级扩容以完整模型实例为单位，流量增长时必须新增一整套副本，所有算子同步扩容，导致非瓶颈算子浪费 GPU 显存与算力，且加载全模型启动延迟极高；下方算子级扩容将缩放单元细化到单个算子，仅针对瓶颈算子增加副本，非瓶颈算子维持原配置。两种范式的本质差异是资源分配粒度从 "整块复制" 升级为 "按需补短板"。
:::

模型级扩缩容这种方式实现简单，与传统微服务扩缩容逻辑一致，**但与 LLM 推理的负载特性存在根本性错配，衍生出速度与粒度两大核心矛盾，最终造成 GPU 资源的系统性浪费。**

### 1.1 速度错配：十秒级扩容追不上秒级流量波动

> LLM 推理流量具有极强的突发性，生产环境中即使在 10 秒的时间窗口内，流量也会出现大幅波动。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/06.webp)

::: image-caption
图 2｜生产环境 LLM 推理流量的突发性。 上图为 10 秒时间窗口内的每秒请求数波动，峰均比（Chat 2.03x / Code 5.78x）显示即使在极短窗口内流量也存在大幅尖峰；下图为各扩缩容窗口内峰均比的频率分布，代码类负载的高比值区间占比显著更高。这种秒级波动是十秒级模型级扩容无法覆盖的根本原因。
:::

从数据来看，**聊天类服务的峰均比平均为 2.03 倍，代码类服务更是达到 5.78 倍。而模型级扩容需要加载完整的模型权重，70B 参数模型的平均加载时间超过 10 秒，即使采用最优的快速加载方案也难以进入秒级**。:mdnice-bold-italic[这种十秒级的扩容速度，完全无法匹配秒级的流量波动，最终只能走向两个极端：]

- 要么为了不触发 SLO 违规预留大量冗余资源，造成持续的资源浪费；
- 要么严格控制资源量，在流量突增时频繁出现首 token 时延超标。

扩缩容延迟越长，能够覆盖的流量波动就越少。随着时延从 2 秒提升到 30 秒，错过的短周期流量峰值呈指数级增长，这是模型级调度无法突破的先天缺陷。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/07.webp)

::: image-caption
图 3｜扩缩容延迟与可覆盖流量粒度的关系。 横轴为模型扩容延迟（2s–30s），纵轴为该延迟下无法被及时覆盖的流量峰均比。Chat 与 Code 两类负载均呈现延迟越大、错过的峰值越尖锐的趋势，说明模型级十秒级扩容在统计意义上必然丢失大量短周期流量尖峰。
:::

### 1.2 粒度错配：整模型同步扩缩容的资源浪费

> LLM 推理本质上是一个由算子组成的有向无环图，节点包括注意力、线性变换、归一化、激活等不同类型的算子，边代表数据依赖关系。**不同算子的计算复杂度、内存占用、对负载变化的敏感度天差地别。**

模型级扩缩容相当于强制所有算子同步增减副本，**瓶颈算子得到扩容的同时，大量非瓶颈算子也跟着被动扩容，这些额外的副本只会占用宝贵的 GPU 内存与计算资源，不会带来任何服务质量提升**。

- 比如:mdnice-bold-italic[短序列场景下线性算子是计算瓶颈]，注意力算子负载较轻；
- :mdnice-bold-italic[长序列场景下注意力算子成为核心瓶颈]，归一化等轻量算子仍有大量冗余。

整模型扩缩容无法针对性地给瓶颈算子扩容，也无法回收非瓶颈算子的闲置资源。

## 二、算子异质性：为什么算子级调度是可行的

> 算子级调度的核心前提，是 **LLM 内部不同算子对负载变化的敏感度存在显著差异**。:mdnice-bold-italic[论文通过系统性的算子画像研究，从计算、内存、SM 核心分配三个维度量化了这种异质性]，为细粒度资源调度提供了理论依据。

如果所有算子的资源需求随负载同步线性增长，那细粒度调度就没有任何价值。:mdnice-bold-italic[但实验数据表明，不同算子的资源敏感度差异可达数量级，且这种差异随模型规模增大、架构复杂化而愈发显著。]

### 2.1 计算敏感度：时延增长曲线的量级差异

> **计算敏感度** 衡量算子的执行时间随序列长度、批量大小的增长速率，不同算子因为底层计算逻辑不同，增长规律存在本质区别。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/08.webp)

::: image-caption
图 4｜不同模型架构下算子对序列长度的计算与内存敏感度。 每行一个模型（Qwen2-7B、Llama3-8B、Qwen2-57B-A14B、Mistral-8x7B、Qwen2.5-VL-32B），横轴为归一化内存，纵轴为归一化时延，每条曲线代表一个算子，数据点从 128 到 64K 序列长度从左到右排列。注意力算子（attn）在两个维度上均呈现最陡峭的增长，而 RMS Norm、Layer Norm 等轻量算子几乎平坦，直观证明算子异质性随模型规模增大而加剧。
:::

- **注意力算子的自注意力计算具有 $O(L^2b)$ 的复杂度**，其中 $L$ 为序列长度，$b$ 为批量大小，因此其**时延随序列长度呈二次方增长**。
- :mdnice-bold-italic[而 MLP、线性投影等算子为 $O(Lb)$ 的线性复杂度]，归一化、激活等轻量算子的增长速率更慢，固定启动开销占比高，大批量下甚至呈亚线性增长。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/09.webp)

::: image-caption
图 5｜不同模型架构下算子对批量大小的计算敏感度。 横轴为批量大小，纵轴为归一化时延，每条曲线为一个算子。MLP、线性投影等计算密集型算子随批量近似线性增长，而归一化、激活等算子因固定启动开销占比高，在大批量下呈亚线性甚至平台化趋势，说明不同算子对 batching 的收益差异显著。
:::

::: block-1
:mdnice-bold-italic[这直接导致了瓶颈的动态漂移：短序列场景下，线性算子与 MLP 算子占据主要计算量；随着序列长度增加，注意力算子的时延占比快速上升，成为新的瓶颈]。模型级扩缩容无法应对这种动态变化，而算子级调度可以精准地给当前瓶颈算子扩容。
:::

### 2.2 内存与 SM 敏感度：资源维度的双重差异

> 内存敏感度分为静态权重内存与动态激活/KV 缓存内存。权重内存是固定值，与负载无关；激活与 KV 缓存随负载动态变化。

- 得益于 FlashAttention 优化，注意力算子的内存增长从理论上的二次方降为近似线性，但仍是内存增长的主要来源；
- 多数其他算子的内存占用随序列长度线性增长，部分算子如索引选择、张量重塑的内存占用基本保持平稳。

> SM 核心分配的敏感度则呈现明显的阶段差异。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/10.webp)

::: image-caption
图 7｜Qwen2-7B 不同 SM 分配下各算子的性能与 SM 利用率。 (a) 为归一化时延随 SM 分配比例的变化，2K prefill 下注意力、MLP 等算子在 SM 减少时时延显著上升，而 1 token decode 下所有算子曲线几乎平坦；(b) 为对应 SM 利用率，decode 阶段利用率普遍低于 30%，说明 SM 空间共享在 prefill 阶段收益高、decode 阶段收益有限。
:::

- 在 prefill 阶段（2K 序列），计算密集型算子对 SM 分配高度敏感，减少 SM 分配会导致时延显著上升；
- 而在 decode 阶段（单 token），整体 SM 利用率很低，SM 分配对时延的影响很小。

这意味着 **prefill 阶段适合通过 SM 空间共享提升 GPU 利用率，decode 阶段的共享收益则相对有限。**

### 2.3 跨维度分析：每个算子都是独特的资源个体

> 将计算敏感度与内存敏感度放在二维平面中，可以看到算子的分布非常分散。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/11.webp)

::: image-caption
图 6｜Qwen2-7B 各算子平均计算敏感度 vs. 内存敏感度二维分布。 左轴为平均计算敏感度，右轴为平均内存敏感度，按算子类型排列。注意力算子属于 "高计算 + 高内存" 双高型，RMS Norm 属于 "低计算 + 高内存占比" 型，QKV 线性属于双中等型，索引选择 / 张量重塑等属于双轻量型。这种二维异质性意味着不能用单一扩缩容策略处理所有算子。
:::

上图中，注意力算子属于高计算敏感、高内存增长型；RMS 归一化属于低计算、高内存占比型；QKV 线性算子属于双中等型；还有部分算子属于双轻量型。

::: block-1
**这种二维异质性意味着，不能用单一的扩缩容策略处理所有算子**。:mdnice-highlight[比如扩容计算便宜但内存很重的算子，可能不仅解决不了计算瓶颈，还会加剧内存紧张；而给计算密集但内存增量小的算子扩容，往往能获得更高的资源性价比。]
:::

## 三、OPSCALE 系统设计：三层架构实现算子级全生命周期管理

> 基于算子异质性的核心洞察，论文设计了 :mdnice-bold-italic[OPSCALE 端到端算子级编排系统，分为控制平面与执行平面两大层级，包含画像、置备、放置、执行四大模块，解决了细粒度调度带来的空间爆炸与复杂度问题。]

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/12.webp)

::: image-caption
图 11｜OPSCALE 系统架构总览。 左侧为输入（模型拓扑、算子画像、流量分布），中间上方为控制平面（算子画像、算子置备、算子放置三大模块，异步运行），中间下方为执行平面（中心化副本管理器 + Worker 集群，含动态算子副本、弹性内存、多流优化、流水线调度），右侧为模型运行时接口。整体遵循 "离线画像建模 → 在线贪心决策 → 执行动态适配" 的分层解耦思路。
:::

**细粒度调度的最大挑战是复杂度爆炸**：调度单元从几个模型副本变成上百个算子副本，配置维度包括批量大小、副本数、张量并行度、SM 分配、设备映射等，直接穷举完全不可行。OPSCALE :mdnice-bold-italic[通过分层解耦的架构设计，将复杂问题拆解为多个可解的子问题。]

### 3.1 控制平面：算子调度的决策大脑

> 控制平面是 OPSCALE 的核心决策层，异步运行，由三个模块组成：

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/13.webp)

::: image-caption
图 12｜OPSCALE 控制平面两阶段决策流程。 Stage 1 算子置备：从初始 DAG 出发，识别瓶颈算子并按需复制，得到逻辑上的算子副本集合（无 GPU 共享时存在利用率气泡）；Stage 2 算子放置：将逻辑副本通过空间共享（Spatial-Temporal Capacity Sharing）打包到物理 GPU，消除利用率气泡。两阶段解耦将指数级配置搜索降为线性贪心决策。
:::

- **算子画像模块**：:mdnice-bold-italic[离线执行，负责量化每个算子的计算时延、内存占用、通信开销与干扰系数。] 模块采用稀疏采样加分段插值的策略，避免遍历所有配置组合；同时利用 LLM 的结构复用性，同类型算子跨层共享画像结果，大幅降低 profiling 成本。
- **算子置备模块**：:mdnice-bold-italic[在线执行，根据实时流量数据与算子画像，计算每个算子的最优批量大小、副本数量与张量并行度。] 模块采用贪心迭代算法，每次只优化最瓶颈的算子，将决策复杂度从指数级降到线性。
- **算子放置模块**：:mdnice-bold-italic[在线执行，将逻辑上的算子副本映射到物理 GPU 上。模块将放置问题转化为带干扰感知的多维装箱问题]，采用最佳适配递减启发式算法，同时考虑资源争用与通信开销，最小化物理 GPU 用量。

### 3.2 执行平面：调度策略的落地载体

## 四、核心算法详解：从资源建模到贪心调度的工程落地

> **算子级调度的核心挑战在于配置空间的组合爆炸。论文首先建立了理论优化模型，明确了问题的数学边界，进而设计了两套贪心启发式算法**，分别解决算子置备与放置问题，在保证近最优效果的同时实现毫秒级决策。

### 4.1 理论建模：SLO 驱动的多目标优化

::: block-1
论文首先将算子级扩缩容抽象为一个带约束的多目标优化问题，明确了输入、输出与优化目标。

问题的输入是算子有向无环图 $G=(V,E)$、请求到达率 $\lambda$ 与序列长度分布；输出是每个算子 $v$ 的配置：批量大小 $B_v$、副本数 $R_v$、张量并行分片数 $P_v$、设备分配 $A_v$、SM 分配 $S_v$。
:::

> **优化的首要目标是满足 SLO，即单次迭代的端到端时延小于 SLO 阈值**：

$$
T_{\text{itr}} = \sum_{v \in \mathcal{V}} \left(T_v + C_v + W_v\right) < T_{\text{SLO}}
$$

其中 $T_v$ 是算子 $v$ 的纯计算时间，$C_v$ 是到下游算子的通信时间，$W_v$ 是算子前的排队等待时间。排队时间基于 M/M/R 排队模型，通过 Erlang-C 公式计算，反映了请求到达率与服务速率的相对关系。

> **第二个目标是最小化总资源消耗**，即所有算子的分片-副本总数，同时满足每个 GPU 的内存容量约束与 SM 配额约束：

$$
\sum_{v \in \mathcal{V}: A_{v}=d} M_{v} \leq M_{d}^{cap }, \quad \sum_{v \in \mathcal{V}: A_{v}=d} S_{v} \leq 100, \quad \forall d \in \mathcal{D}
$$

这是一个 NP 难的整数非线性规划问题，全局最优解的计算成本随算子数量指数级增长，无法用于在线调度。因此论文设计了贪心启发式算法，在精度与速度之间取得平衡。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/14.webp)

::: image-caption
表 2｜画像驱动模型的预测精度（相对误差）。 算子画像敏感度预测平均误差 7%（P99 15%），SM 争用模型慢启动预测平均 5%（P99 9.4%），排队模型时延预测平均 0.8%（P99 1.9%）。低误差保证了在线置备决策的可靠性，其中排队模型精度最高，因为 M/M/R 解析模型与实际到达过程高度吻合。
:::

### 4.2 算子置备算法：关键路径迭代优化

> 算子置备算法采用两阶段贪心策略，核心思想是优先优化对时延影响最大的瓶颈算子，避免全局搜索。

- 第一阶段是初始化，先继承模型部署的初始并行度配置，然后对每个算子扫描可行的批量大小范围，计算支撑当前到达率所需的最小副本数，选择使单算子逗留时间最短的批量与副本组合作为基线配置。
- 第二阶段是迭代优化，循环计算全局端到端时延，与 SLO 阈值对比：

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/15.webp)

::: image-caption
算法 1｜贪心算子置备算法。 输入为算子 DAG、QPS、最大批量、并行度集合、画像时延函数与 SLO 阈值。第 1–7 行初始化：继承初始并行度，对每个算子扫描可行批量大小，用 Erlang-C 公式计算所需最小副本数，选择使逗留时间最短的配置；第 8–30 行迭代优化：若总时延低于 SLO−ε 则进入降容（relax）分支，在关键路径上尝试减少副本 / 增大批量 / 降低并行度，选择回收资源最多且不违反 SLO 的操作；若总时延高于 SLO 则进入升容分支，枚举增加副本 / 调整批量 / 提升并行度，选择单位资源投入带来时延下降最多的操作。每次增量计划生成仅需几毫秒，资源成本比穷举最优高 8%。
:::

这种贪心算法的资源成本仅比穷举最优解高 8%，但一次完整决策仅需几毫秒，完全满足在线调度的实时性要求。

### 4.3 算子放置算法：干扰感知的最佳适配递减

> **算子放置本质上是带干扰的多维装箱问题**，:mdnice-bold-italic[目标是将算子副本映射到最少的物理 GPU 上，同时保证共置干扰不会导致 SLO 违规。]

首先建立经验干扰模型，定义干扰因子 $I_{d,v}(b,p)$ 为算子共置时的时延与独立运行时延的比值，取值大于等于 1。通过离线两两算子共置测试，生成不同批量大小与 SM 分配下的干扰因子查找表，在线查询时间为 $O(1)$。三个及以上算子共置时，通过两两因子相乘近似，精度满足工程需求。

放置算法分为三步：

1. **分解与排序**：先保留最小数量的完整模型副本作为基线，保证服务稳定性；剩余的弹性算子副本按计算量降序排列，优先放置计算量大的算子，减少尾部资源碎片。
2. **贪心最佳适配**：逐个为算子副本寻找最合适的 GPU，优先选择放置后剩余资源最少的设备，同时验证干扰调整后的时延仍满足全局 SLO；只有现有设备都放不下时，才激活新的 GPU。
3. **局部性平局判定**：如果多个 GPU 适配度相近，优先选择通信开销更低的位置，优先级为同设备 > 同服务器 NVLink > 同 NVL 域 > 跨服务器 InfiniBand。

![文章插图](/articles/2026-09-06-llm-opscale-36-3-gpu-1eedb46d/images/16.webp)

::: image-caption
算法 2｜贪心算子级放置算法。 输入为算子 DAG、置备阶段输出的副本配置、设备集合与容量、干扰查找表。第 1–7 行分解与排序：先保留最小数量完整模型副本作为基线，剩余弹性算子按计算量降序排列；第 8–23 行贪心最佳适配：逐个算子副本遍历现有设备，检查内存 / SM 容量约束，用干扰模型 I_d,v (b,p) 调整时延并验证全局 SLO，只有所有设备都放不下时才激活新 GPU；第 24–29 行局部性平局判定：多设备适配度相近时优先选择通信开销更低的位置（同设备 > NVLink > NVL 域 > InfiniBand）。
:::

::: block-1
总之，:mdnice-highlight[OPSCALE 的算法设计以“抓重点、分优先级”为核心思想]，置备算法聚焦关键路径瓶颈，放置算法优先重算子与局部性，用极低的计算开销实现了接近理论最优的调度效果。
:::

## 六、讨论与延伸：算子级调度的适用场景与未来方向

> 算子级调度不是万能银弹，其收益高度依赖负载特性与模型架构。论文同时讨论了方案的适用边界、与现有技术的互补性，以及未来的拓展方向。

### 6.1 适用场景与边界

算子级扩缩容的收益最大化需要满足几个条件：

- **服务 SLO 不是极致严苛**。如果追求亚百毫秒的超低时延，采用 megakernel 将所有算子融合成单个大核的方案会更优，这种场景下算子没有拆分空间。:mdnice-bold-italic[而大多数在线服务、Agent 应用的 SLO 相对宽松，是算子级调度的最佳适用场景。]
- **模型算子异质性高**。:mdnice-bold-italic[大模型、MoE 模型、多模态模型的算子差异大，收益远高于小模型。] 7B 以下的小模型算子异质性低，算子级调度的收益有限。
- **负载波动大且 prefill 占比高**。:mdnice-bold-italic[prefill 阶段计算密集、负载波动大，算子级调度的收益最高]；纯生成的 decode 阶段负载平稳，收益相对有限。

### 6.2 与现有技术的互补性

> 算子级调度是对现有技术的拓展，而非替代，可以与多类优化方案形成叠加效应。

- **与 prefill-decode 拆分技术互补**。prefill 阶段算子级调度收益高，decode 阶段收益低，:mdnice-bold-italic[两者结合可以针对两个阶段分别采用最优策略。]
- **与多租户多模型调度互补**。现有多模型共享 GPU 大多以模型副本为单位打包，:mdnice-bold-italic[OPSCALE 可以直接以算子为单位跨模型打包，粒度更细，GPU 利用率更高。]
- **与单 GPU 优化技术互补**。DVFS 动态调频、SM 空间复用、kernel 级调度等都是单 GPU 内的优化，OPSCALE 是集群级的调度，两者层级不同，效果可以叠加。

### 6.3 未来拓展方向

> 论文也指出了几个后续研究方向：

- 一是拓展到多租户多模型场景，加入租户公平性调度与跨模型干扰建模；
- 二是结合更细粒度的 kernel 级空间复用，进一步降低算子共置干扰；
- 三是优化动态张量并行调整，目前水平扩副本的收益高于调整并行度，未来可以探索更灵活的并行度动态适配。

::: block-1
回顾一下，:mdnice-highlight[算子级调度是 LLM 推理资源调度从粗放到精细的必然演进方向]，它在更细粒度上的拓展与深化，能够与现有方案形成多层级的资源优化体系。
:::

## 总结

> OPSCALE 首次将 LLM 推理自动扩缩容的粒度从完整模型下沉到单个算子，打破了整模型调度的效率天花板。:mdnice-bold-italic[通过系统性的算子异质性画像、理论优化建模、贪心算法设计与全栈系统实现，团队证明了算子级调度不仅工程上可行，而且能够带来 30%左右的 GPU 成本节省与显著的 SLO 提升。]

对于 LLM 服务行业而言，这**意味着资源效率的提升不再只依赖硬件迭代与单算子优化，集群调度层面还有巨大的结构性优化空间**。:mdnice-bold-italic[随着模型规模持续增大、架构愈发复杂，算子级细粒度调度的价值还会进一步凸显，未来有望成为云原生 LLM 服务的标准资源调度范式。]
