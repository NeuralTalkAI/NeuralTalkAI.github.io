## 一、DL 框架测试的困局：动态 Fuzzing 很好，但还不够

> 深度学习框架是当前 AI 产业的核心基础设施，其正确性直接决定了自动驾驶、生物识别、金融服务等关键领域的系统可靠性。**一个隐藏在框架底层的缺陷，可能不会立刻引发崩溃，却会悄无声息地污染数值结果、引入内存安全风险。**

过去几年，DL 框架测试领域的进展主要集中在动态模糊测试方向。这类方法的核心逻辑是生成或变异深度学习程序，在框架上执行后通过崩溃判定、差异对比、数值校验、蜕变判定等机制识别缺陷。:mdnice-bold-italic[随着大语言模型的引入，新一代 Fuzzer 能够利用预训练学到的 API 语法与张量约束知识，生成更有效、更多样的测试用例，进一步提升了缺陷检出效率。]

### 1.1 动态测试的本质局限

> 动态测试的有效性建立在两个前提之上：一是能够构造到达缺陷路径的可执行输入，二是缺陷触发后能够产生可观测的故障。对于普通软件而言，这两个前提相对容易满足，但对于深度学习框架，这两个前提的成本正在变得越来越高。

现代 DL 框架普遍采用异构后端架构，同一个算子可能对应 CPU、CUDA、MPS 等十几种硬件实现，执行路径横跨 Python 前端、C++调度层、设备内核层。:mdnice-bold-italic[要触发某个特定后端路径上的缺陷，需要精确匹配张量形状、数据类型、布局、设备等多重属性，组合空间极其庞大。更关键的是，很多语义类缺陷不会立刻引发崩溃，只会导致静默的数值偏差，这类问题很难通过动态测试的判定器稳定识别。]

除此之外，动态测试的算力成本也不容忽视。每生成一个测试用例都需要完整执行一次前向或反向传播，**对于大模型算子、分布式算子，单次执行的时间与资源开销都很高**。要覆盖所有可能的路径与配置，需要消耗大量计算资源，投入产出比会随着覆盖率提升快速下降。

### 1.2 静态分析的天然互补性

> :mdnice-bold-italic[静态分析不需要实际运行程序，只通过扫描源代码就可以识别潜在缺陷。它的优势在于速度快、可扩展、不需要构造具体输入，能够在开发早期就发现逻辑层面的问题]。对于 DL 框架中大量潜伏的语义不一致缺陷，静态分析理论上可以在无需执行的前提下，直接检查跨层的契约一致性，填补动态测试的盲区。

但现实情况是，直到这项工作出现之前，行业内几乎没有可用的、面向 DL 框架的静态分析方案。**传统静态分析工具在 DL 框架上的表现极差，误报率高到完全无法落地。问题的根源在于，传统工具的设计假设与 DL 框架的实际架构完全不匹配。**

::: block-1
总得来说，动态测试与静态分析属于互补的两种测试范式，二者不存在互相替代的关系。:mdnice-highlight[前者擅长触发可观测的运行时故障，后者擅长在无需执行的前提下发现语义层面的不一致性，两者结合才能覆盖更完整的缺陷空间。]
:::

## 二、为什么传统静态分析在 DL 框架面前集体失效

> 传统静态分析工具已经发展了数十年，在通用软件的安全审计中发挥着重要作用。但面对深度学习框架这类特殊的系统软件，现有工具几乎全部陷入了高误报、低检出的窘境。

这种失效是底层设计逻辑的不匹配，而非工具实现得不够好。**DL 框架有两个独有的架构特征，直接击穿了传统静态分析的基本假设，分别是混合多语言架构与张量为中心的程序状态。**

### 2.1 多语言架构带来的语义断层

> 现代 DL 框架普遍采用**分层混合语言架构**：上层用 Python 提供灵活的 API 接口，中间用 C++实现调度、内存管理与通用算子逻辑，底层用 CUDA、Metal 等设备语言实现高性能内核。层与层之间通过外部函数接口与框架调度机制连接，控制流跨越边界时，语义契约也随之传递。

传统静态分析工具大多是单语言设计，Python 的分析工具只能看 Python 代码，C/C++的分析工具只能看 C/C++代码。

- Python 端的工具知道 API 层面的张量契约，但看不到后端内核的具体实现，无法验证契约在底层是否被遵守；
- C/C++端的工具能看到底层指针运算与内存访问，但不知道前端定义的输入约束，只能基于局部代码做判断。

论文中提到的 :mdnice-bold-italic[EmbeddingBag 缺陷就是典型例子。Python API 层定义了输入张量的秩约束，一维输入对应一维 offsets，但 C++后端实现没有强制执行同样的校验。这个缺陷发生在两层的语义衔接处，单语言工具无论站在哪一边，都看不到完整的语义链路，自然也就发现不了问题。]

### 2.2 张量语义的复杂性

> DL 框架的核心数据结构是张量，但张量不是普通的多维数组。:mdnice-bold-italic[它携带了形状、数据类型、步长、设备、布局、别名状态、分配信息、运行时状态等大量元数据，这些元数据会随着算子执行不断演化。绝大多数框架缺陷，本质上都是某一层代码消费张量属性时，依赖了一个没有被上层建立或保留的假设。]

要通过静态分析检测这类缺陷，需要**追踪张量所有属性在多层代码中的传递与变化**。如果用传统的手写规则方式，需要对每一个算子、每一个后端都编写对应的校验规则，不仅需要极深的领域专业知识，而且面对成千上万的 API 与后端路径，根本无法规模化。

这两个挑战共同指向了一个核心问题：**静态分析不能再停留在单语言语法层面，必须上升到跨语言张量传递的语义层面。这正是 PHOENIX 最核心的设计出发点。**

::: block-1
整体来说，:mdnice-highlight[传统静态分析工具的失效根源，在于其分析粒度停留在单语言语法层面，无法跨越 Python、C++、CUDA 的语言边界追踪张量语义的传递与演化]，也就无法识别跨层的契约不一致问题。
:::

## 三、PHOENIX 的核心基石：SBIR 语义桥接中间表示

> 要解决跨语言张量语义的分析难题，首**先需要一套统一的中间表示，既能屏蔽不同语言的语法差异，又能完整保留张量传递过程中的关键语义信息**。:mdnice-bold-italic[这就是 PHOENIX 提出的语义桥接中间表示，简称 SBIR。]

SBIR 的定位不是一套完整的程序中间表示，不需要编码 PyTorch 的所有执行细节。:mdnice-bold-italic[它是一种轻量级的语义抽象，只记录与缺陷相关的语义传递过程，目标是为 LLM 提供一个结构化的分析载体]，让 LLM 可以专注于检查语义一致性，而不用处理复杂的多语言语法。

### 3.1 SBIR 的形式化定义

> 从形式上看，**一个 PyTorch 程序的执行过程，可以表示为一系列语义桥组成的序列**。每个语义桥描述一次从源语言实体到目标语言实体的语义传递，同时记录传递的属性、类型与对应的代码上下文。其形式化语法定义如下：

$$
\langle P \rangle ::= \langle B^* \rangle
$$

$$
\langle B \rangle ::= \langle \langle E_{src} \rangle, \langle E_{dst} \rangle, \langle T \rangle, \langle \Phi \rangle, \langle \Gamma \rangle \rangle
$$

其中 $\langle P \rangle$ 代表完整的程序，由零个或多个语义桥 $\langle B \rangle$ 顺序组成。每个语义桥是一个五元组，五个字段的含义分别如下：

**第一个字段 $E_{src}$ 与第二个字段 $E_{dst}$ 分别代表源实体与目标实体**。实体的定义为：

$$
\langle E \rangle ::= \langle \ell \rangle.\langle e \rangle[.\langle f \rangle], \quad \ell \in \{Python, CPP, CUDA\}
$$

- $\ell$ 标识该实体所在的语言层，取值为 Python、CPP 或 CUDA；
- $e$ 代表具体的程序对象，可以是 API、函数参数、张量、指针、内核参数、类实例等；
- 可选的 $f$ 代表对象的具体成员或属性，比如形状、数据类型、数据指针、索引边界等。

如果分析针对整个对象，则可以省略 $f$。

**第三个字段 $T$ 记录传递类型，取值包括数据传播、别名传播、梯度转发、调度、守卫检查、控制依赖、元数据转换、突变、分配等**。这些类型覆盖了 DL 框架中常见的语义传递场景，足以表达维度检查缺失、数据类型/设备不一致、布局假设不安全、后端前置条件违反等常见缺陷模式。

**第四个字段 $\Phi$ 是语义约束的集合**，每个约束以键值对的形式存在：

$$
\langle \phi \rangle ::= \langle k \rangle = \langle v \rangle
$$

- 键 $k$ 的取值包括形状、数据类型、步长、布局、设备、是否求导、别名状态、容量、状态等张量属性与运行时状态；
- 值 $v$ 可以是标识符、数值、布尔值、数值向量、符号表达式或者谓词。

这种设计让 SBIR 既可以记录张量的元数据，也可以记录容量表达式、守卫条件等从代码中提取的约束。

**第五个字段 $\Gamma$ 是代码上下文集合，每个条目对应一个文件中的一段代码**。它的作用是把每一个语义桥和真实的仓库代码绑定，让后续分析始终有具体的代码作为依据，避免脱离实际的凭空推理。

### 3.2 SBIR 的设计优势

| 优势 | 描述 | 特点 |
| --- | --- | --- |
| 统一跨语言分析面 | 无论原始代码是 Python、C++ 还是 CUDA，均被抽象为相同结构的语义桥；分析时无需处理语法差异，仅需验证语义约束在传递过程中是否保持一致 | 消除语言异构性，聚焦语义一致性验证 |
| 轻量且聚焦 | 仅保留与缺陷相关的语义传递信息，不建模完整程序行为；作为 LLM 的分析输入，信息量充足且复杂度可控 | 降低推理负担，提升模型处理有效性与稳定性 |
| 可扩展性 | 传递类型与元数据键非固定设计；适配新框架组件或新缺陷类别时，可直接新增对应类型与属性，无需重构整个表示体系 | 支持渐进式演进，降低维护与扩展成本 |

::: block-1
:mdnice-highlight[SBIR 的核心价值，是将跨语言、张量为中心的程序语义，转化为结构化、可推理的语义桥序列]。它既屏蔽了不同语言的语法差异，又完整保留了张量属性、守卫条件与代码上下文，为后续 LLM 驱动的静态分析提供了统一的分析载体。
:::

## 四、四智能体协同：从缺陷知识到静态检测的完整流水线

> 有了 SBIR 作为统一表示，接下来:mdnice-bold-italic[需要一套完整的工作流，将历史缺陷知识转化为针对目标代码库的缺陷检测能力。PHOENIX 设计了四个分工明确的 LLM 智能体，通过三个阶段逐步完成从知识归纳到代码分析的全流程。]

### 4.1 阶段一：缺陷模式的标准化总结

> 工作流的第一步是构建缺陷知识库并做标准化归纳。原始的缺陷知识来自两个互补的来源，共同组成了包含 56 个条目的数据集。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/06.jpg)

::: image-caption
表 I：PHOENIX 用于漏洞模式摘要的漏洞数据集：该数据集由 40 条 PyTorch 历史张量修复 PR 与 16 条高风险 CWE 规则构成，分为张量契约、校验逻辑、内存资源、异构后端、通用安全缺陷五大类，总计 56 条样本，解决现有公开数据集缺少深度学习框架专属漏洞样本的问题。PR 样本提供框架专属算子、后端真实缺陷，用于向下游传递代码领域知识；CWE 规则补充通用内存、注入、越界等安全漏洞，拓宽漏洞检索边界。消融实验 w/o CWE 仅检出 8 个漏洞，w/o PR 检出 23 个漏洞，证明两类数据源具备强互补性，缺一不可，是支撑 PHOENIX 广覆盖漏洞检测的基础知识库。

**这两类原始数据都不能直接用来指导 SBIR 生成**。历史修复 PR 包含具体的补丁与开发上下文，信息详实但过于具体，且夹杂很多无关的实现细节，直接使用会导致检索范围过窄，无法发现同类的其他缺陷。CWE 规则提供了通用的安全弱点知识，但过于抽象，和 DL 框架的张量语义距离很远，直接使用无法定位到具体的代码层面。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/07.jpg)

::: image-caption
图 3：漏洞模式摘要提示词模板。该提示词为 LLM 定义深度学习框架安全专家角色，区分两类数据源采用差异化抽象逻辑，解决原始漏洞素材无法直接用于代码检索的痛点。针对宽泛 CWE 通用规则执行向下具象化，将内存越界、空指针等通用缺陷映射为张量形状、设备、布局专属漏洞模式；针对具体修复 PR 执行向上泛化，从单一算子补丁提炼可复用的跨语言张量约束违反范式。标准化输出统一包含漏洞类型、触发条件、违反约束、关联张量实体，为下游代码标识符提取、SBIR 生成提供精准语义锚点。
:::

**总结智能体的作用就是对这两类数据做标准化处理**，并且针对不同来源采用不同的抽象方向：

- 对于 CWE 规则，执行向下具象化，把通用的安全弱点细化为 DL 框架场景下的语义模式；
- 对于 PR 补丁，执行向上泛化，把具体的代码修复抽象为可复用的缺陷模式。

:mdnice-bold-italic[最终输出的标准化缺陷摘要，包含缺陷类型、触发条件、违反的语义约束、相关的张量与代码实体四个核心要素]。这份摘要就是后续所有步骤的语义锚点。

### 4.2 阶段二：ERG 策略生成可落地的 SBIR

> 得到缺陷摘要之后，下一步是**把抽象的缺陷模式和具体的代码库关联起来，生成对应的 SBIR**。如果直接让 LLM 同时完成代码定位与 SBIR 生成，很容易出现幻觉问题，比如编造不存在的文件路径、虚构张量属性、生成和真实代码不符的语义桥。

为了解决这个问题，PHOENIX 提出了 Extract-Retrieve-Generate 策略，简称 ERG，把代码接地和 IR 生成拆成两个独立步骤，严格保证 SBIR 必须基于真实检索到的代码生成。

**整个流程的第一步是标识符提取**。提取智能体根据缺陷数据与摘要，输出一个最精准的代码标识符，可以是 Python API、C++函数、CUDA 内核、辅助函数等具体的代码符号。:mdnice-bold-italic[这个标识符的作用是把检索范围从整个代码库缩小到相关的函数片段，大幅提升检索的精准度]。如果一次检索没有找到有效上下文，最多可以重试两次，更换标识符重新检索。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/08.jpg)

::: image-caption
图 4：标识符提取提示词模板。该模板承接漏洞摘要输出，约束 LLM 输出单一精准代码标识符，解决大模型直接检索全代码库产生范围漂移、上下文失效问题。输入融合原始漏洞素材与标准化漏洞摘要双重语义，引导模型输出算子 API、C++ 内核、CUDA 函数等代码符号，限定检索范围至函数粒度代码片段，大幅削减无关代码干扰。
:::

如果三次重试都没有检索到有效代码上下文，流程直接返回空值。这个失败分支非常关键，它从机制上杜绝了在没有真实代码依据的情况下生成 SBIR 的可能，是控制幻觉的第一道也是最重要的一道防线。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/09.jpg)

::: image-caption
算法 1：用于 SBIR 生成的提取 - 检索 - 生成（ERG）策略。该算法是 PHOENIX 抑制 LLM 代码幻觉的核心流程，分层隔离代码检索与中间表示生成，禁止模型直接全库搜索代码。流程设置 3 次标识符提取重试机制，解决单次符号提取偏差导致检索为空的问题；检索无有效代码上下文时直接返回空值，杜绝无落地代码支撑的虚假 SBIR 生成。
:::

**只有当检索到有效的函数级代码上下文后，生成智能体才会介入**。它接收原始缺陷数据、标准化缺陷摘要，以及检索到的代码片段，按照 SBIR 的形式化定义，生成 JSON 格式的语义桥表示。:mdnice-bold-italic[整个过程中，生成智能体不需要自己搜索代码，只需要对已有的代码片段做语义抽象，因此产出的 SBIR 始终和真实代码保持对应。]

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/10.jpg)

::: image-caption
图 5：SBIR 生成提示词模板。该模板向 LLM 输入 SBIR 完整形式化语法定义、漏洞原始数据、标准化摘要、检索得到的真实代码片段，强制以 JSON 输出跨语言语义桥表示。核心约束是生成过程仅基于已检索落地代码，禁止凭空编造文件、张量属性与跨层流转关系，从源头抑制 LLM 幻觉。SBIR 统一建模 Python、C++、CUDA 间张量 shape、dtype、布局、设备、内存守卫条件的传递关系，将多语言异构代码转化为统一可校验语义图谱。
:::

### 4.3 阶段三：基于 SBIR 的语义一致性分析

> **工作流的最后一步是缺陷判定，由分析智能体完成**。分析智能体接收生成好的 SBIR，结合代码上下文，检查从源实体到目标实体的传递过程中，所有语义约束是否被一致地保持。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/11.jpg)

::: image-caption
图 6：基于 SBIR 的漏洞分析提示词模板。该模板将 SBIR 作为唯一输入，赋予 LLM PyTorch 安全审计专家身份，核心任务校验跨语言张量约束传递一致性。模型遍历语义桥五元组（源实体、目标实体、传递类型、语义约束、代码上下文），判断前端定义的张量契约是否在后端完整保留。
:::

- 如果分析发现语义约束被违反，智能体输出完整的缺陷报告，说明缺陷类型、具体症状与建议的修复方式；
- 如果检查后确认所有约束都被正确保持，则输出无缺陷。这种保守的输出策略，让最终的缺陷报告只保留高置信度的语义不一致问题，避免了大量无依据的猜测。

和传统的手写规则相比，**基于 LLM 的分析可以处理更复杂的多约束交互场景**。:mdnice-bold-italic[很多框架缺陷是形状检查、布局假设、运行时状态等多个条件组合在一起产生的逻辑错误，这类规则很难通过人工枚举覆盖]。LLM 可以基于 SBIR 中的结构化约束，做整体的语义推理，识别出组合型的逻辑缺陷。

::: block-1
:mdnice-highlight[PHOENIX 的多智能体工作流本质上是一套知识归纳、代码接地、语义校验的闭环。先用历史知识锚定缺陷模式，再用代码检索保证分析的真实性，最后在统一的语义表示上完成一致性校验]，既发挥了 LLM 的跨语言理解与推理能力，又通过流程设计严格控制了幻觉风险。
:::

::: block-1
**PHOENIX 的分析始终围绕跨层语义约束展开，而这些约束恰恰是真实框架缺陷的核心成因**。因此它的告警和真实缺陷的相关性更高，既大幅降低了误报率，又显著提升了真实缺陷的检出数量。
:::

## 六、三个真实案例：静态分析到底能挖出什么 Bug

> 抽象的指标之外，PHOENIX 检出的真实缺陷覆盖了 CPU、CUDA、MPS 等多个异构后端，涉及张量布局、缓冲区容量、运行时状态等多种问题类型，能够直观展现跨语言语义分析的实际威力。

**截至论文发表时，PHOENIX 提交的 31 份缺陷报告中，已有 26 份得到 PyTorch 官方维护者的确认，20 份修复补丁正式合入上游仓库**。这些缺陷分布在不同的后端与组件中，没有集中在单一实现层，验证了 SBIR 的跨后端通用性。

### 6.1 CPU 后端：AvgPool3d 反向的布局步长错误

> 第一个案例来自 **CPU 后端的 AvgPool3d 反向算子，问题出在 Channels Last 内存布局下的批步长计算**。在 Channels Last 的 3D 布局中，张量的维度顺序为深度、高度、宽度、通道，因此一个批次的步长应该是深度乘以高度乘以宽度乘以通道数。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/17.jpg)

原始实现中，计算梯度输出指针的批偏移时，只乘了输出高度、输出宽度与通道数，漏掉了输出深度维度。这个错误会导致指针偏移计算偏小，梯度读取时会访问到错误的批次区域。

这类缺陷的危险之处在于它不会立刻引发崩溃，只会静默地产生错误的梯度值。如果测试用例没有做严格的数值校验，或者深度维度取值为 1，缺陷就会被掩盖，很难被动态测试发现。

在 SBIR 的视角下，这个场景对应从池化输出张量元数据到底层指针偏移表达式的形状/布局语义桥。分析时只需要检查地址计算是否完整保留了约束中的所有维度，就可以发现目标指针构造时丢弃了输出深度，违反了形状与地址计算的一致性约束。

### 6.2 CUDA 后端：分布式对称内存的通道校验优先级错误

> 第二个案例来自 **CUDA 分布式对称内存模块的通道校验函数**。该函数的作用是校验传入的通道索引是否在支持的合法范围内，合法通道数的计算逻辑是信号缓冲区总大小除以单世界大小的存储开销。

原始代码中，计算式遗漏了括号，运算符优先级出现错误。原本应该是总大小除以（单元大小乘以世界大小），实际执行顺序变成了总大小除以单元大小再乘以世界大小，大幅高估了合法通道的数量。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/18.jpg)

这个缺陷会导致边界校验失效，用户传入超出实际容量的通道索引也能通过检查，进而引发后续的越界内存访问。但要触发这个缺陷，需要特定的 CUDA 分布式内存配置与多进程环境，动态测试很难覆盖到这么偏的场景。

SBIR 将这个场景建模为从对称内存缓冲区布局到 CUDA 侧边界检查的分配/容量语义桥。核心校验逻辑是最大合法通道数必须与所有进程共用的物理缓冲区划分方式保持一致，通过对比容量约束与校验表达式，就可以识别出运算符优先级带来的约束违反。

### 6.3 MPS 后端：空指针校验前的解引用错误

> 第三个案例来自 Apple MPS 后端的错误检查函数。该函数从 MPS 错误缓冲区中读取错误信息，原始代码先直接访问了缓冲区中的第一条消息，之后才检查缓冲区指针是否为空、是否包含有效消息。

![文章插图](/articles/2026-08-11-python-c-cuda-pytorch-31-90b20e7d/images/19.jpg)

这是典型的守卫后置问题，解引用操作发生在空指针校验之前。如果错误缓冲区为空，代码就会触发空指针解引用导致崩溃。但这个路径只有在出现 MPS 错误时才会走到，正常执行流程下不会触发，因此属于潜伏性缺陷。

**在 SBIR 中，这个缺陷被建模为控制依赖与内存状态语义桥**。目标实体第一条消息的安全访问，必须满足源运行时状态非空且包含至少一条有效消息的前置条件。原始代码在守卫约束建立之前就访问了目标字段，违反了守卫先于解引用的不变式。

::: block-1
**以上这三个案例分别对应张量布局、缓冲区容量、运行时状态三类完全不同的缺陷**，但都可以通过统一的 SBIR 框架建模与检测，充分体现了语义桥表示的通用性与表达能力。

:mdnice-highlight[PHOENIX 检出的缺陷覆盖多个异构后端与多种缺陷类型，其中很多属于静默错误或罕见触发路径，很难被动态测试捕获]。这些真实案例验证了基于 SBIR 的跨语言静态分析，能够有效发现传统方法漏检的深层语义缺陷。
:::

## 总结与展望

> 作为首个面向深度学习框架的 LLM 驱动静态分析技术，PHOENIX 打开了 DL 框架测试的一个全新方向。它没有沿用传统静态分析手写规则的技术路线，也没有采用 LLM 无约束扫描代码库的方式，**其核心设计是通过 SBIR 这个精巧的中间表示，把 LLM 的跨语言推理能力约束在了有真实代码依据的语义桥上。**

这项工作的核心贡献可以归纳为四个层面。

| 层面 | 描述 |
| --- | --- |
| 第一是视角创新 | 首次将静态分析引入 DL 框架测试领域，明确将跨语言张量语义不一致作为核心检测目标，为框架缺陷检测提供了新的思路。 |
| 第二是技术创新 | 设计了 SBIR 语义桥接中间表示与多智能体协作的分析工作流，结合检索增强与 LLM 推理，解决了多语言语义追踪与幻觉控制两大难题。 |
| 第三是效果验证 | 在 PyTorch 真实代码库上实现了低误报率与高检出量，产出了大量得到官方确认与合入的真实缺陷修复。 |
| 第四是范式补充 | 证明了静态语义分析与动态模糊测试的高度正交性，两者结合可以显著拓展 DL 框架的缺陷覆盖范围。 |

当然，这项工作也存在一定的局限。

- 目前 SBIR 只覆盖了常见的语义传递类型，还不能表达所有的框架执行逻辑；
- 当前验证主要集中在 PyTorch 框架，向其他 DL 框架迁移的效果还需要进一步验证；
- 分析的规模也还有提升空间，未来可以通过更高效的检索与智能体协作，支持更大范围的代码库扫描。

::: block-1
从行业发展的角度看，DL 框架作为 AI 时代的核心基础设施，其质量与安全保障体系还在不断完善。:mdnice-bold-italic[动态 Fuzzing、静态分析、形式化验证、人工审计各有其适用场景与优势边界，没有单一方案可以解决所有问题。PHOENIX 的工作证明，基于大语言模型的静态语义分析是一条可行且有价值的技术路径，能够为 DL 框架的质量保障补上重要的一块拼图。] 未来随着技术的持续迭代，静态与动态深度结合的测试方案，将会成为 DL 框架质量保障的标准配置。
:::
