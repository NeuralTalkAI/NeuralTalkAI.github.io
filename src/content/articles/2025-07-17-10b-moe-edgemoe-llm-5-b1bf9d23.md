> 大型语言模型（LLM），例如 GPT 系列和 Mixtral-8x7B，因其在通用机器学习任务上的卓越能力而彻底改变了机器智能。**将 LLM 从数据中心迁移到边缘设备** 能够带来更好的隐私性和可用性，但受限于其庞大的参数规模以及随之而来的难以承受的运行时开销。

为此，我们提出 :mdnice-bold-italic[EdgeMoE——一个面向混合专家（MoE）LLM 的端侧推理引擎]。MoE 是一种流行的稀疏 LLM 形式，能够以几乎恒定的计算复杂度扩展参数规模。

::: block-1
EdgeMoE 通过:mdnice-bold-italic[将模型分层级地划分到存储体系结构] 中来同时:mdnice-bold-italic[实现内存与计算的高效性]：**非专家权重** 驻留在**设备内存** 中；**专家权重** 则存放在**外部存储**，仅在激活时才被调入内存。这一设计源于一个关键观察：:mdnice-bold-italic[专家权重虽然庞大，却因稀疏激活而极少被使用]。

为了进一步降低专家 I/O 换入换出开销，EdgeMoE 引入了两项新颖技术：

1. 专家级位宽自适应（expert-wise bitwidth adaptation），在**可容忍的精度损失下缩减专家体积**；
2. 专家预取（expert preloading），**提前预测将被激活的专家**，并通过计算-I/O 流水线将其**预加载**。
:::

在**主流 MoE LLM 和边缘设备上，EdgeMoE 展示了显著的内存节省和推理加速**，优于竞争基线。代码开源地址：https://github.com/UbiquitousLearning/mllm。

## 一、引言

大型语言模型（LLM），例如 GPT 系列[20,33,71-74] 与 LLaMa[81,82]，正以其在通用 NLP 任务上的出色表现、小样本学习能力和可扩展性重塑机器智能。虽然这些模型最初诞生于数据中心，但它们正逐渐下沉到个人电脑、智能手机甚至 IoT 等边缘设备，以获得更好的数据隐私、可用性与个性化。

::: block-1
在这一趋势中，**LLM 不仅显著优于传统 DNN、刷新端侧机器学习任务的最先进水平，还催生了许多令人兴奋的新应用** [5]。例如：

- 高通在智能手机上完整部署了超过 10 亿参数的文本到图像生成 LLM[15]；
- 华为将多模态 LLM 嵌入手机，以实现基于自然语言的精准内容搜索[3]。
:::

> 然而，将 LLM 落地到移动设备面临的核心挑战在于其巨大的参数规模以及由此带来的不可承受的运行时开销。为缓解这一问题，:mdnice-bold-italic[最近提出了混合专家（MoE）架构] [34,46]，该架构在**逐 token 解码时【仅激活 LLM 的一小部分】**。

**最具代表性的 MoE 设计是用多个专家** （每个专家是一个独立的前馈网络 FFN）**替换 Transformer 块中的单个 FFN**。在推理过程中，每个 Transformer 块内的可训练函数（即路由器）仅将输入路由到所有专家中的:mdnice-bold-italic[前 K（K=1 或 2）个]。有关 MoE LLM 的更多设计细节见第 II 节。此类基于 MoE 的 LLM 已被广泛研究[31,35,55,56,75,77,96]并在工业界采用[1]。

直观上，稀疏激活在 LLM 变得更大并作为各种任务的基础模型时非常有意义：:mdnice-bold-italic[不同任务或输入数据可能只需模型的极小部分即可工作]，正如人脑一样[39]。

### MoE 的利与弊

通过稀疏设计，MoE LLM 能够以几乎恒定的计算复杂度扩展参数规模和能力，使其**非常适合存储成本效益高且可扩展、但计算能力受限的边缘设备**。

- 经验上，为了容纳 105B 参数的 GLaM[31]，设备仅需 1 TB 外部存储，成本不到 100 美元；
- 然而，要以合理速度（如 10 token/秒）执行它，需要五块高端 GPU，成本约 65,000 美元。

然而，MoE LLM 太大，无法装入设备内存（详见 II-B）。

- 简单地缩减专家数量会显著降低模型性能[35]；
- 而频繁地在内存与存储之间交换权重又会因 LLM 的自回归特性带来巨大开销。

### EdgeMoE：面向移动设备的以专家为中心的 LLM 引擎

本工作提出 EdgeMoE，**【首个】可在端侧** 以内存和时间高效方式扩展模型规模（专家数量）的 LLM 推理引擎。EdgeMoE 的整体设计基于一个独特观察：

::: block-1
- **大部分计算集中在少量【非专家】权重** （“:mdnice-bold-italic[热权重] ”）上，这些权重**可常驻设备内存**；
- 而**专家权重占据大部分** 内存却**只占少量计算** （“:mdnice-bold-italic[冷权重] ”）。
:::

> 因此，EdgeMoE 将专家与非专家区分放置于存储层级结构（更快的 RAM vs 更大的磁盘）。具体而言：

- 所有“热权重”永久驻留内存，因为它们在每次 token 推理中都被使用；
- 其余内存预算则用作“冷专家权重”的专家缓冲区。

借助专家缓冲区设计，EdgeMoE 仅在专家被激活时才按需从存储加载到内存。然而，与计算相比，**这一 I/O 开销仍然显著**，例如在 Jetson TX2 上延迟高达 4.1×，详见 II-A。针对这一问题，通常有两种思路：

1. 一是直接减少 I/O 数据量，例如通过量化[22,38,61,63,88,94]；
2. 二是将 I/O 与计算流水线化以隐藏延迟[43]。

::: block-1
尽管这两个方向已被深入研究，但将其应用于 :mdnice-bold-italic[MoE 模型面临独特挑战]：

- 复杂的量化算法[18,50,95] 虽能实现更**高压缩率**，却带来**显著的反序列化与解压缩预处理时间** （见 III-B）。而更**朴素的量化** [44] 又**无法有效减少专家 I/O**。
- 与执行模式固定的静态模型不同，MoE 中的专家是动态激活的，系统无法事先获得路由器结果。
:::

因此，**EdgeMoE 无法提前加载将被激活的专家**。忽略专家激活知识，一种可能的做法是缓存激活频率更高的专家以提高命中率；然而，由于训练机制刻意保持各专家激活频率均衡[34]，这种做法收效甚微。

> 对此，EdgeMoE 提出下面两项创新设计：

### 创新点 1：专家级位宽自适应（Expert-wise bitwidth adaptation）

EdgeMoE 将轻量级预处理的量化方法——逐通道线性量化[51]——与专家级位宽自适应相结合。其核心观察是：不同层、甚至同层的不同专家对量化后模型精度的影响不同。因此，EdgeMoE 采用细粒度的专家级位宽自适应，充分利用模型冗余。

离线阶段，EdgeMoE 逐步降低对量化最鲁棒的若干专家的位宽，直到精度损失达到用户设定的可容忍阈值。选择哪些专家进一步量化时，还综合考虑更低位宽量化对推理速度的提升。

**最终，EdgeMoE 获得混合精度模型**，在目标精度下实现**最小模型体积，即最快加载时间**。

### 创新点 2：内存中专家管理（In-memory expert management）

为实现 I/O-计算流水线，**EdgeMoE 在路由器运行前** :mdnice-bold-italic[预测将激活的专家]。其设计源于一个新颖观察：实践中采用的**专家激活路径** （即每个 token 顺序激活的专家集合）**高度不平衡且呈长尾分布**。

这表明:mdnice-bold-italic[专家激活之间存在显著关联]，实验结果见 III-C1。因此：

- 离线阶段，EdgeMoE 构建统计模型，根据先前层的激活**估计当前层各专家的激活概率**。
- 在线推理时，EdgeMoE **查询该模型并提前预加载最可能的专家**，实现 I/O-计算流水线。

此外，EdgeMoE 为专家缓冲区设计了新的缓存替换策略，同时考虑激活频率及专家相对于当前执行位置的远近。总体而言，预测-预加载与缓存替换技术共同最大化激活时的专家缓存命中率。

### 方案结果

我们基于 PyTorch 实现了一个 EdgeMoE 原型，完整实现了上述全部技术。**开发者只需给出内存预算和可容忍的精度损失，系统即可自动优化执行延迟**。随后，我们用 7 个主流基于 MoE 的 LLM 和 2 个嵌入式平台（Raspberry Pi 4B (CPU) 与 Jetson TX2 (GPU)）进行了大量实验。

- 与把整个模型驻留在设备内存相比，EdgeMoE 将**内存占用降低了 1.05×–1.18×**；
- 与内存优化的基线（如动态加载专家的 IO-EXP 与 STI[43]）相比，EdgeMoE 实现了 **1.19×–2.77× 的推理加速**。

> EdgeMoE 首次在 Jetson TX2 等 COTS 边缘设备上实现了 >10 B 规模的 LLM 快速推理，且精度损失可忽略不计（≤2%）。

消融实验进一步表明，:mdnice-bold-italic[EdgeMoE 的每一项独立技术都带来了显著提升]。本文的贡献如下：

::: block-1
- 我们进行了先行实验，揭开了 MoE LLM 在边缘设备上的性能真相并分析了其启示。
- 我们提出了 EdgeMoE——首个面向移动设备的 MoE 推理引擎，其核心设计是把内存当作外部存储中未激活专家的缓存。
- 我们进一步引入两项新技术：专家级位宽自适应和内存专家管理，以降低 EdgeMoE 的专家 I/O 开销。
- 通过大量实验，我们证明了 EdgeMoE 的有效性。
:::

## 二、先导实验与分析

### A. 混合专家 LLM 入门

本工作聚焦于 encoder-decoder，这是当今最流行的大型语言模型架构之一。

- 编码器（Encoder）处理输入序列，并将其压缩为连续的中间表示；
- 解码器（Decoder）则基于这一中间表示生成（预测）输出序列。解码器的独特之处在于它以自回归（autoregressive）方式逐 token 生成，即在生成下一个 token 时，将上一个输出 token 追加到输入序列末尾（逐 token 依赖）。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/04.webp)

图 1(a) 展示了一个简化的三层 Transformer 的 LLM 推理过程的数据流图。编码器与解码器均基于 Transformer 层[84]，每层包含若干注意力头（用于提取词对关系）、FFN（前馈网络，用于以非线性增强信息表示）及其他次要算子，如图 1(b) 所示。

**近期趋势是在运行时通过小型、离线训练的“路由器”选择一组稀疏 FFN——即“专家”（experts），如图 1(c) 所示**。因此，:mdnice-bold-italic[MoE 架构可以在计算复杂度仅次线性增长的情况下扩展模型参数规模]。这是因为每个 token 仅激活固定数量（通常为 1 或 2）的专家/权重。例如，基于 MoE 的 LLM GLaM[31] 在自然语言处理任务上的精度显著高于 GPT-3，而计算量仅为其一半；Mixtral-8x7B[47] 也以仅 10% 的运行成本达到与 GPT-3.5 相当的性能。这种参数可扩展性使基于 MoE 的 LLM 在计算能力受限的边缘设备上成为良好候选。

### B. 端侧稀疏 LLM 推理

> “稀疏带来大规模”。稀疏扩展的 LLM 对边缘设备的关键资源——内存——提出了巨大压力。

为了更好地理解其对边缘设备的影响，特别是内存/计算权衡与执行特性，我们在两款商用现货 SoC（Jetson TX2 与 Raspberry Pi 4B）上刻画了 Google 最流行的基于 MoE 的稀疏 LLM 之一 Switch Transformer（简称 ST）的执行。我们得到以下关键观察：

#### B.1 专家权重迅速膨胀模型体积

虽然增加专家数量能提升模型精度，Google 已表明将每层 FFN 的专家数从 8 提升至 256 可显著增强模型容量[35]。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/05.webp)

然而，如图 2 所示，**专家数的增加导致峰值内存占用几乎线性增长，边缘设备难以承受**。例如，仅 8 GB 内存的 Raspberry Pi 4B 只能容纳最小专家数（每层 8 专家）的 Switch Transformer。因此，内存墙严重限制了基于 MoE 的 LLM 的可扩展性。即使设备内存足够（如 8 GB RAM 的 Jetson TX2）能完整容纳模型，巨大模型体积也使其易被操作系统回收，导致只能服务极少次推理。

#### B.2 专家权重体积庞大但访问频率低

对于基于 MoE 的 Transformer，MoE 结构中专家网络的权重称为专家参数，其余参数为非专家参数。我们发现**推理过程中大部分计算集中在少量权重（非专家）上，而大部分权重（专家）只占少量计算**。这归因于专家的稀疏激活特性。以 Switch Transformer base-16（简称 ST-base-16，16 表示每层 MoE 含 16 个专家）为例，专家占 86.5% 的总内存，仅贡献 26.4% 的计算。

:mdnice-bold-italic[直观上，上述特性天然契合设备存储层级（更快的 RAM vs 更大的磁盘）]。因此，可采用差异化换入策略：

- **所有非专家常驻内存，专家仅在路由器激活时才从磁盘换入内存，用完立即释放**。此时内存使用量可降至所有非专家权重加一个专家权重大小；
- I/O 开销也降至每层只需加载一个专家。

#### B.3 专家权重的计算与I/O之间的不对称性

不幸的是，**即便每层仅加载一个专家，也显著拖慢 MoE 的执行性能**。采用上述差异化换入策略后，我们发现 Jetson TX2 上每样本推理（生成多 token 序列）平均耗时超过 17 秒，且由于自回归特性，解码时间占主导。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/06.webp)

图 3 分解了延迟：**I/O（专家加载）占主要部分**。与无限内存的理想情况（无专家 I/O）相比，逐 token 解码时间在 Jetson TX2 上增加 3.2×–3.9×，在 Raspberry Pi 4B 上增加 3.3×–3.8×。

#### B.4 计算/IO流水线操作受到数据依赖的阻碍

有人可能借助计算/I/O 并行，类似 STI[43]，把:mdnice-bold-italic[专家加载与权重计算重叠。然而我们发现此做法不可行，原因如下]：

- 专家激活依赖：与 STI 针对的标准 Transformer 模型按层顺序预加载不同，**MoE Transformer 直到上一层计算完成后才知道需加载哪个专家**。这种专家级激活依赖**阻止了计算/I/O 流水线**。
- 专家激活频率均衡：有人可能按频率预加载“热门”专家到内存。然而我们发现此做法无益，因为**同一层内各专家激活概率相近** （如图 8 左）。训练机制有意保持均衡以最大化训练时 GPU 利用率[35]，这并不意外。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/07.webp)

#### B.5 专家激活路径遵循幂律分布

虽然单个专家的整体激活频率均衡，但我们发现专家激活路径（即一个 token 在所有 Transformer 层中依次激活的专家构成的向量）高度倾斜。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/08.webp)

图 4 展示了在:mdnice-bold-italic[两个 MoE 模型和两个数据集上得到的激活路径分布，呈幂律分布]：**最频繁的 20% 路径贡献了超过 99% 的 token 激活**。这一观察暗示**不同层的专家激活可能非独立同分布**，驱动我们后续在 III-C 更深入分析专家激活相关性。

## 三、EdegeMoE 设计方案

### 3.1 方案概览

#### 系统模型

> EdgeMoE 是首个在边缘设备上实现大型 MoE Transformer 模型快速推理的执行引擎。它支持通用 MoE Transformer 模型，用于文本生成、摘要等交互任务。

:mdnice-bold-italic[EdgeMoE 主要优化 Transformer 解码器]，因为在我们的实验中它**占 MoE 模型端到端推理时间的绝大部分（例如高达 93%）**。 EdgeMoE 以运行时库的形式链接到用户应用程序。与 EdgeMoE 一同安装到边缘设备的还有已按不同位宽压缩的 MoE LLM。系统由两个关键参数配置：

1. **内存预算 M，由用户或操作系统指定，范围 1.5 GB–3 GB**，比现有 MoE LLM 小一至两个数量级。灵活的约束可适应不同设备内存及系统内存压力。
2. 用户选定的**可容忍精度损失 P**。基于 P，EdgeMoE 在运行时调整各专家的位宽，构建待执行模型（注意这是软目标，因为现有 MoE LLM 无法提供精度保证）。

用户调用后，EdgeMoE 首先选出满足精度损失 P 的模型，并实例化专家预取/计算流水线以降低推理延迟：按层顺序加载所有非专家权重；根据先前激活的专家，机会式地预加载下一层专家，并与当前层计算重叠。最终，EdgeMoE 输出预测 token 集合（如文本生成）或摘要（如摘要任务）。EdgeMoE 不在运行时选择专家的位宽，因为难以预测后续专家对整体精度的影响，无法实现全局最优位宽分布。

::: block-1
执行期间，EdgeMoE 维护两个内存缓冲区：

1. 专家缓冲区，用于管理和缓存专家权重，常驻内存以支持多轮推理。
2. 工作缓冲区，保存所有中间结果，仅临时存在，每次推理结束后即可丢弃。
:::

#### 工作流程

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/09.webp)

::: block-1
如图 5 所示，EdgeMoE 分为两大阶段：

1. 离线专家量化（§III-B）。给定用户指定的可容忍精度损失（如 5%），EdgeMoE 离线预处理预训练模型：分析各专家重要性（对模型精度的敏感度），据此将专家量化为不同位宽。最终模型包含不同位宽的专家，甚至同一 Transformer 层内也如此。
2. 在线专家管理（§III-C）。运行时，EdgeMoE 实例化预取/计算流水线，通过专家缓冲区动态管理内存与磁盘间专家。利用离线阶段统计的专家激活信息，预先确定从磁盘取哪些专家、何时驱逐缓存。
:::

#### 适用性

EdgeMoE 框架通用，兼容仅解码器和仅编码器 Transformer 架构，支持动态路由（如 Switch Transformer[35]、GLaM[31]）和静态路由（如 Hash layer[75]、expert choice MoE[96]）的 MoE 层。

对于静态路由层，专家激活仅取决于原始输入 token 而非隐藏状态，EdgeMoE 直接按输入 token 指示预加载专家，无需预测。EdgeMoE 基于 MoE 模型推理解码阶段的专家激活稀疏性进行优化，因此**适合为单请求解码阶段加速，这正是 MoE Transformer 在边缘设备（如手机对话）的应用场景**。然而，对于单轮推理 token 数大于 1 的场景（预填充阶段或多输入请求），EdgeMoE 不适用。

EdgeMoE **可与其他效率优化方法叠加使用**；对于超大模型与算力弱的边缘设备，可采用量化进一步优化内存与计算速度。

### 3.2 Expert-wise Quantization

为了在给定内存预算 M 的条件下容纳专家权重，并平衡计算/I/O 不对称性，我们选择**基于字典的量化方法** [44]，该方法可直接应用于未经修改的预训练模型；我们不使用量化感知训练（QAT）[63]，以避免对 LLM 进行昂贵的重训练。虽然量化技术已广为人知，但 EdgeMoE 首次将其应用于单个专家，并挖掘精度与位宽之间的权衡。

#### 选择算法

我们调研了多种量化技术（如高斯离群值感知量化[95] 与对数量化[18]），最终选用逐通道线性量化[44]，因其在保持精度的同时解压缩速度最快。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/10.webp)

如图 6 所示，将所有专家权重量化为 4 bit 整数（INT4）仅带来 1.30%–1.44% 的精度下降；在 SAMsum 数据集上，专家甚至可进一步量化为 2 bit 整数，精度损失仅 5.82%，在我们的使用场景中可接受。图 7(b) 表明，与其他量化技术（如高斯离群值感知量化[95]）相比，**逐通道线性量化因简化解压缩过程（仅为一次线性映射）而快 1.1×–2.5×。**

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/11.webp)

逐通道线性量化使用缩放因子将量化整数均匀映射回原始浮点值；每个通道的缩放因子由该通道最大绝对值与位宽可表示范围共同决定，需要额外存储一个 float16 类型的缩放通道。

我们在 Jetson TX2 上用相同参数量测试，**逐通道量化的反量化时间仅为纯 I/O 加载时间的 2.7%，几乎可忽略**。 注意，量化权重不能直接使用（不同于 QAT[63]），使用前必须解压缩，解压缩过程是压缩的镜像流程。

#### Profiling expert importance

**针对专家，我们将其量化为不同位宽**，如 INT2/4/8。原因在于不同专家对模型精度的影响不同：**我们希望最重要的专家使用高位宽，从而对精度贡献更大**。

> EdgeMoE 将“重要”定义为：若某专家在低比特量化后导致更大精度损失，则其更重要。

具体做法：EdgeMoE 枚举所有专家，分别将其量化为 INT2，并在验证集（如 ST-base-8）上测试最终精度损失，结果以热力图形式示于图 7(a)。例如，将第 1 个 Transformer 块的第 1 个专家量化为 INT2 导致精度下降 0.44%，而将第 2 个专家量化为 INT2 导致 0.59% 下降，因此第 2 个专家对量化更敏感、更重要。**这一观察也得到先前研究[26] 的支持：不同专家倾向于处理不同难度的任务**。

由此，EdgeMoE 获得按“将该专家量化为 INT2 时模型精度”排序的重要性列表，该列表用于后续构建运行时模型。

#### Selecting expert-wise bitwidths

基于用户给定的可容忍精度损失，EdgeMoE 在离线阶段按如下方式精细地为每个专家选择位宽：

- 首先，EdgeMoE 为所有专家**确定一个位宽上下界作为基线**。为此，EdgeMoE 枚举所有可用位宽（如 INT2/4/8、FP32）应用于全部专家并分别测试模型精度，随后将位宽**上下界设为那些精度接近用户容忍损失的位宽**。
- 其次，EdgeMoE **在上述上下界内逐个调整专家位宽**。从重要性列表中选 Top-K 个最不重要的专家开始，将其量化为更低位宽（如 INT2），其余保持高位宽（如 INT4）。

测试所得模型精度，若精度损失仍低于用户目标，说明模型可承受更多低位宽专家，则继续沿列表增大 K，直至精度损失达到目标；否则减小 K，通过提升更多专家到高位宽来降低精度损失。

**通过上述过程，EdgeMoE 获得一个混合精度专家模型，在目标精度下实现存储最小化，即加载时间最短**。由于采用简单量化算法，无需训练/微调，这是 LLM 系统常被视为优点的特性。

#### Non-expert weights quantization decision

**是否量化非专家权重涉及复杂权衡**：可节省内存从而为专家留出更大缓存空间，但会降低精度，进而压缩在给定容忍损失下可分配给专家的量化空间。

EdgeMoE 仅对非专家权重迭代常见候选位宽（INT4/INT8/FP16/FP32），使用 GPTQ 算法[38] 找出性能最佳配置。经验上，非专家权重往往保持较高保真度（如 FP16），因为它们在每次推理中均被激活。

#### Complexity analysis

EdgeMoE 的离线阶段受预设精度损失主导，需迭代枚举各种位宽配置并动态调整专家分配，直至模型精度下降满足阈值。在线阶段仅应用已调配置，计算开销极低，满足实时推理需求。

### 3.3 In-memory Expert Management

#### 3.3.1 Preloading and pipeline:

为了把专家加载与权重计算重叠，必须在路由器输出前预测专家激活，而非被动等待上一 MoE 层的结果。

##### Estimating expert activation a priori

如何预测专家激活？我们利用关键观察：**连续层的专家激活在统计上相关**。即给定前 0…n−1 层的专家激活，可以以高置信度估计第 n 层各专家的激活概率，形式化为 P(Eₙ=i | E₀,E₁,…,Eₙ₋₁)。

为验证此相关性，我们在 SAMSum 数据集上运行 ST-base-8 模型。如图 8(左) 所示，若已知前两层激活，则第 3 层有 87.1% 概率激活第 5 号专家，即 P(E₃=5 | E₁=3, E₂=1)=87.1%；图 8(右) 进一步统计不同激活路径证实了这一点。

##### Opportunistic preloading

EdgeMoE 利用上述观察进行机会式预取：

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/07.webp)

- 离线阶段：基于上述观察，EdgeMoE 在多个数据集上执行模型，构建专家激活统计档案。生成一个字典，键为前两连续 MoE 层的专家激活状态，值为下一层各专家激活概率。该统计档案供在线推理使用。
- 在线阶段：在每个 MoE 层路由前，EdgeMoE 用前层激活作为键查询统计档案，按估计激活概率顺序预加载专家到专家缓冲区（若尚未存在）。预加载持续至路由器完成并获知真实激活专家为止。实践中，EdgeMoE 每层可预加载 1–3 个专家，具体取决于计算-I/O 速度差距。

##### Pipeline scheduling

EdgeMoE 实例化预取/计算并行：在当前 Transformer 块计算的同时，基于统计档案的预测并行预加载下一 Transformer 块。图 9 展示了 1-token 推理的流水线调度，分别对应预测成功/失败场景。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/12.webp)

**当预测正确（常见情况）时，端到端推理延迟显著降低，加载时间被计算掩盖**；最坏情况（我们从未观测到）是全部预测失败，此时推理时间等于按需加载专家。

#### 3.3.2 Cache eviction policy

EdgeMoE 在内存中维护一个受内存预算 M 限制的专家权重缓存。若已缓存专家被激活，则直接从缓存取权重（命中）；否则需从磁盘取专家，并在缓存满时驱逐旧专家。

##### 缓存替换策略

决定驱逐哪位专家——对性能至关重要，因为错误驱逐即将使用的专家会带来巨大 I/O 开销。

经典缓存策略（FIFO/LRU/LFU）主要面向操作系统，基于数据访问历史和频率。EdgeMoE 既利用专家激活频率，又利用 LLM 顺序堆叠 Transformer 层的特性：专家激活时机与其层索引（位置）相关。具体而言，**如果某专家所在层即将执行，则其应获得更高保留优先级。**

基于此启发，EdgeMoE 的驱逐策略同时考虑专家使用频率与 MoE 层索引。

> 核心思想是：优先驱逐使用频率低且所在层距离当前块较远的专家。

形式化地，对第 i 个 MoE 层的第 j 个专家，定义其驱逐分数：

$$
L_{i, j}=-\frac{f_{i, j}}{(S-i+I) \mod S}
$$

其中 I 为当前 MoE 层索引，$f_{i,j}$ 为第 i 层第 j 个专家的历史激活频率，S 为解码器中 MoE 层总数。分数越高越可能被驱逐。对编码器内的专家，我们设 $f_{i,j}=0$，因为这些专家仅在重新批处理后加载一次，应优先驱逐。初始化专家缓冲区时，我们按顺序加载编码器专家权重。对于仅编码器模型，缓冲区初始化为使用频率最高的专家。

## 四、评估

### 4.1. 实现与方法

#### EdgeMoE 原型

我们基于 transformers 库，用 1000 行 Python 代码完整实现了 EdgeMoE 原型。我们使用 PyTorch 作为 transformers 的后端，使用 CUDA 后端以更通用地支持不同平台。请注意，EdgeMoE 的技术也与其他深度学习库兼容。

#### 模型

我们使用 7 个流行的基于混合专家（MoE）的稀疏大语言模型来测试 EdgeMoE 的性能。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/13.webp)

这些模型大多基于 Switch Transformers [fedus2022switch] 架构，采用编解码器结构和 top-1 路由（即每层仅激活 1 个专家）。此外，GPTSAN [tanrei-gptsan-jp] 采用仅解码器结构，作为前缀输入 token 的移位掩码语言模型，使用 top-2 路由。这些预训练权重直接从 Hugging Face [huggingfacehubmodels] 下载。

#### 数据集

我们使用三个自然语言处理下游数据集评估 EdgeMoE：

1. Xsum 数据集 [huggingface-xsum]：包含 226,711 篇新闻文章，每篇都配有简洁的一句话摘要；
2. SAMsum 数据集 [huggingface-samsum]：该数据集包含约 16,000 个类似即时通讯的对话记录及其相应摘要；
3. Wikipedia-jp 数据集 [huggingface-wikipedia-japanese]：该大型数据集包含截至 2022 年 8 月 8 日的全部日语维基百科文章。Xsum 和 SAMsum 数据集专门用于摘要任务，我们在这些数据集上评估 Switch Transformers 模型的性能；
4. 相反，Wikipedia-jp 数据集作为文本生成任务的基础，我们在该数据集上评估 GPTSAN 的文本生成能力。

:mdnice-bold-italic[比较指标] 我们**主要报告 EdgeMoE 和基线方法的模型精度、推理速度（每 token 和每样本）、峰值内存占用和模型大小**。为评估模型精度，我们在实验中使用 Rouge-2 指标 [lin2005recall]。该指标是一组用于评估自动摘要和文本生成任务的指标，在摘要任务中，Rouge-2 通过比较自动生成的摘要与人工编写的参考摘要来量化相似度。

:mdnice-bold-italic[实验硬件] 我们在两个主流边缘设备上评估 EdgeMoE：**Jetson TX2（GPU）和 Raspberry Pi 4B（CPU）**。Jetson TX2 [tx2] 和 Raspberry Pi 4B [rpi4b] 均运行 Ubuntu 18.04 操作系统。由于混合专家大语言模型体积庞大，我们需要外部存储来容纳它们：

- 对于 Raspberry Pi 4B，我们使用 SD 卡（SanDisk Ultra 128GB [sdcard]）；
- 对于 Jetson TX2，我们使用两种硬盘，即 SSD（默认）和 HDD。
- SSD 型号为三星 860 EVO [samsungssd]，读写速度为 550/520 MB/s；
- HDD 型号为移动速度 YSUTSJ-64G2S [movespeed]，读写速度为 50/20 MB/s。

EdgeMoE 生成量化混合专家模型的离线阶段在配备 8 块 NVIDIA A40 的 GPU 服务器上执行。

:mdnice-bold-italic[性能比较基线] 我们将 EdgeMoE 与四种基线方法进行比较：

1. IO-FREE 假设所有模型权重都保存在内存中，因此无需交换 I/O。这是计算效率最高的方法，但由于内存限制而无法扩展；
2. IO-EXP 将内存视为专家的缓存，一旦激活就动态加载专家，与 EdgeMoE 类似；
3. IO-QEXP 将上述方法与 MoQE [kim2022mixture] 结合，将专家权重量化为 INT4，并在推理过程中动态加载。与 EdgeMoE 一样，量化权重需要转换回 FP32 才能在设备处理器上快速推理；
4. STI 通过模型分片最小化推理精度，并在紧张的内存预算下实例化 I/O/ 计算管道 [guo2023sti]。它不区分专家权重和非专家权重。为了公平比较，我们调整预加载分片的缓冲区大小，使 STI 和 EdgeMoE 具有相同的内存占用。

:mdnice-bold-italic[配置] 除非另有说明，我们将 EdgeMoE 的专家缓冲区设置为 10 倍专家大小；可容忍的精度损失为 5%。每个实验都系统地进行多次重复，报告的值基于各自的平均值。

### 4.2. 端到端结果

#### 内存占用

我们在边缘设备上评估了 EdgeMoE 和基线方法的内存占用。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/14.webp)

**结果表明，在所有模型和平台上，EdgeMoE 的性能显著优于基线方法，与 IO-FREE 相比，内存节省范围为 2.6 倍至 3.2 倍**。这一改进归功于 EdgeMoE 对非激活专家权重和激活的高效管理。此外，EdgeMoE 动态加载并缓存内存中激活的专家权重，以减少内存占用。

相比之下，**EdgeMoE 的内存占用与 IO-EXP 和 IO-QEXP 相似**。由于这两个基线不需要缓存先前的专家权重，因此 EdgeMoE 的内存占用略高。例如，当专家缓冲区设置为专家内存占用的 10 倍时，ST-base 模型比 IO-EXP 和 IO-QEXP 多消耗约 180MB 内存。根据 4.1 节中的设置，基线 STI 与 EdgeMoE 具有相同的内存占用。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/15.webp)

#### 每 token 推理延迟

在边缘设备上，EdgeMoE 与基线方法的每 token 推理延迟比较结果突出表明，在所有模型和平台上，EdgeMoE 实现了显著的性能提升。在 Jetson TX2 上，与 IO-EXP 相比，EdgeMoE 的加速比范围为 2.63 倍至 3.01 倍；在 Raspberry Pi 4B 上，加速比范围为 4.49 倍至 5.43 倍。这一显著的性能提升归因于几个关键因素：首先，EdgeMoE 对专家采用权重量化，有效减少了加载延迟；此外，EdgeMoE 采用高效的专家权重预加载策略，智能地将预加载过程与计算重叠，从而有效掩盖了大部分延迟。因此，与 IO-QEXP 相比，EdgeMoE 实现了 1.35 倍–1.5 倍的加速比，与 STI 相比，实现了 1.11 倍–2.78 倍的推理加速比。

然而，EdgeMoE 与 IO-FREE 之间仍存在性能差距，因为 EdgeMoE 的预加载阶段并不总是能预测下一个混合专家层将激活哪个专家。有些专家仍然需要动态加载。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/16.webp)

#### 硬盘读取速度的影响

结果还比较了 Jetson TX2 上 SSD 和 HDD 的每 token 推理延迟。值得注意的是，与 SSD 相比，EdgeMoE 在成本更低的 HDD 上实现了更高的加速率，特别是与基线 IO-EXP 相比。例如，与 IO-EXP 相比，EdgeMoE 在 HDD 上的加速比范围为 4.49 倍至 4.76 倍，在 SSD 上为 2.63 倍至 3.01 倍。这种差异是由于 HDD 的读取速度相对较慢，导致专家权重加载时间比 SSD 更长。EdgeMoE 在专家加载方面的改进更为显著，从而使每 token 推理延迟的提升更为明显。

#### 每样本推理延迟

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/17.webp)

我们还评估了在 Jetson TX2 和 Raspberry Pi 4B 上，EdgeMoE 与基线方法的每样本推理延迟。结果表明，EdgeMoE 始终优于基线方法。例如，在 Raspberry Pi 4B 上，EdgeMoE 处理的 50% 样本的延迟小于 46 秒，而 IO-FREE 处理的 50% 样本的延迟小于 106 秒。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/18.webp)

#### 存储和精度

我们还比较了 EdgeMoE 和基线方法的存储需求，同时测量了它们的精度损失。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/19.webp)

结果显示，在存储方面，EdgeMoE 显著优于基线方法，对于 ST-base-8，与 IO-FREE 相比提升了 3.03 倍，与 IO-QEXP 相比提升了 1.11 倍。这一优势源于 EdgeMoE 对专家权重采用混合精度量化方法。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/20.webp)

此外，精度损失与我们的预期一致。EdgeMoE 的精度损失接近可容忍的 5% 阈值。IO-FREE、IO-EXP 和 IO-QEXP 模型的精度损失也与其各自的位宽配置一致。与其他基线不同，STI 同时量化非专家权重和专家权重，导致显著的精度损失。

#### 缓存淘汰策略

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/21.webp)

我们在不同的专家缓冲区大小下，对我们提出的新型缓存淘汰策略与其他策略的缓存命中率进行了比较分析。在这些实验中，我们禁用了预加载功能，以减轻预加载对命中率的影响。结果表明，与其他几种策略相比，我们提出的新型淘汰策略效果更优。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/22.webp)

### 4.3. 敏感性分析

不同的内存预算。EdgeMoE 通过根据内存预算 M 定制专家缓冲区，适应具有不同设备内存的各种边缘设备（3.3 节）。在实验中，我们将内存预算配置为 1.6GB 至 3.5GB，反映了实际边缘设备的内存情况。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/23.webp)

我们在这些内存预算下广泛评估了 EdgeMoE 与基线方法的每 token 推理延迟，结果表明，随着专家缓冲区大小的增加，推理延迟降低。这是因为扩大的专家缓冲区可以保留更多先前激活的专家权重，从而提高缓存命中率并节省权重加载时间。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/24.webp)

在两种设备上，EdgeMoE 与 IO-QEXP 的比较结果一致表明，在所有内存预算配置下，与 IO-QEXP 的 INT4 和 INT2 版本相比，EdgeMoE 的推理延迟更低。

可容忍精度损失的影响。在不同期望精度损失 P 下的比较结果中，我们在 Jetson TX2 上运行 ST-base-8 和 ST-base-16 模型，评估了 5% 至 20% 精度损失水平下的推理延迟和模型存储。结果表明，**精度损失随模型大小和推理延迟而变化**。这证实了 EdgeMoE 通过调整专家的个体位宽，有效地适应可用资源（存储和延迟）。

![文章插图](/articles/2025-07-17-10b-moe-edgemoe-llm-5-b1bf9d23/images/25.webp)

### 4.4. 消融实验

然后，我们分别评估了 EdgeMoE 的每个关键技术带来的收益。**每 token 推理延迟评估结果表明，EdgeMoE 的每个关键技术都对推理加速有显著贡献**。例如，在 ST-base-8 和 Jetson TX2 上：

- 专家级量化首先将推理延迟从 0.789 秒减少到 0.392 秒；
- 预加载和管道进一步将延迟减少到 0.305 秒；
- 通过使用专家缓冲区，延迟最终降至 0.245 秒。

## 五、相关工作

### 深度神经网络内存优化

鉴于内存是移动设备关键且稀缺的资源，节省内存始终是移动计算社区的重要研究方向。例如：

- Split-CNN [48] 提出将单层的权重拆分为多个子窗口，并对其进行内存卸载与预取，以降低激活内存与权重内存。
- Melon [86] 结合重计算（recomputation）与微批次（micro-batch）技术，应对端侧训练时的高内存占用与碎片化问题。
- SwapNN [67] 通过在 SRAM 与外部 flash 之间精细地交换权重，使大型神经网络得以在资源受限的微控制器上运行。

EdgeMoE 与上述工作在底层理念与技术（量化与交换）上有共通之处，但针对 MoE 架构的独特机会，提出了以专家为中心的内存节省新思路。

### MoE 模型系统

近期研究聚焦于高效地服务或训练基于 MoE 的大模型 [32], [36], [52], [76]。例如，Edge-MoE [76] 引入逐专家计算（expert-by-expert computation）以最大化已加载专家的重用。然而，这些系统要么面向分布式云，要么面向非自回归模型（如 ViT [30]）。

- X-MoE [25] 解决了稀疏专家模型中的表示坍缩（representation collapse）问题；
- TA-MoE [23] 是一种面向大规模 MoE 训练的拓扑感知路由策略，从模型-系统协同设计角度，根据网络拓扑动态调整 MoE 的调度模式。

相比之下，EdgeMoE 是面向资源受限移动设备的高效系统，利用独特机会加速基于 MoE 的自回归大模型推理。

### 资源高效的大语言模型

资源高效 LLM 的研究一直活跃。先前工作采用知识蒸馏 [41], [57], [80], [85], [87], [93]、网络剪枝 [37], [65], [79]、量化 [22], [38], [61], [63], [88], [94]、架构设计 [29], [58], [64], [68], [69], [78], [91]、高效结构设计 [27], [28]、文本压缩 [24], [42], [83] 等方法实现资源高效 LLM。EdgeMoE 的核心设计与上述工作正交（orthogonal），可叠加使用。

### 端侧机器学习优化

端侧 DNN 推理优化主要有两类：

1. 系统级：如利用异构处理器 [21], [40], [45], [53]、缓存 [66], [90]、生成高性能 GPU kernel [59]、自适应卸载 [54], [89]；
2. 模型级：如量化 [49], [62] 或稀疏化 [19], [70]。

这些方法可优化小型模型，但无法应对 LLM 运行时内存比边缘设备大上百倍的场景。EdgeMoE 专为资源高效的基于 MoE 的稀疏 LLM 设计，与上述工作正交。

## 六、结论

本文提出了 EdgeMoE——首个面向专家混合（MoE）LLM 的端侧推理引擎。EdgeMoE 集成两项创新技术：

::: block-1
1. **专家级位宽自适应** （expert-specific bitwidth adaptation），在可接受精度损失下压缩专家大小；
2. **专家预加载** （expert preloading），通过计算-I/O 流水线提前加载预测激活的专家。
:::

大量实验表明，EdgeMoE 可在边缘 CPU 与 GPU 平台上实现 MoE LLM 的实时推理，同时保持可容忍的精度损失。
