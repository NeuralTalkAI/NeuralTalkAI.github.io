关键词：**线性注意力**、KV 缓冲、:mdnice-bold-italic[分块解码]、**推测解码**、SGLang

> "线性注意力拥有与上下文长度无关的恒定解码成本，但现有服务系统在每个解码步骤都递归计算和更新巨大的线性注意力状态，导致严重的内存访问瓶颈。"这是耶鲁大学最新发表的论文《KVBuffer: IO-aware Serving for Linear Attention》中提出的核心问题。

线性注意力作为长上下文大语言模型的关键技术，近年来受到了广泛关注。:mdnice-bold-italic[它通过移除 Softmax 操作，将注意力计算的复杂度从 O(n²)降低到 O(n)，并且在解码阶段只需要维护一个固定大小的状态，理论上可以支持无限长的上下文]。然而，这一理论优势在实际服务中并没有得到充分发挥。

::: block-1
**问题的根源在于线性注意力状态的大小**。以 Qwen3-Next 的 Gated DeltaNet 层为例，每个线性注意力状态的大小约为 2MB，比单个 token 的键值(KV)对大两个数量级。

现有服务系统如 vLLM 和 SGLang 在每个解码步骤都需要读取和写入整个线性注意力状态，这消耗了大量的 GPU 内存带宽，并且本质上是串行的操作。
:::

## 二、线性注意力的计算形式与服务挑战

### 2.1 线性注意力的三种计算形式

要理解 KVBuffer 的创新之处，我们首先需要回顾线性注意力的三种基本计算形式：并行形式、递归形式和分块形式。

#### 2.1.1 标准 Softmax 注意力

> 标准 Softmax 注意力的计算公式如下：

$$
Q, K, V = XW_Q, XW_K, XW_V
$$

$$
O = Softmax\left((QK^T) \odot M\right)V
$$

其中，$X \in \mathbb{R}^{L \times d}$ 是输入，$W_Q, W_K, W_V \in \mathbb{R}^{d \times d}$ 是可学习参数，$M$ 表示因果掩码，当 $j \leq i$ 时 $M_{ij}=1$，否则为 0。

::: block-1
在推理阶段，Softmax 注意力需要存储所有先前 token 的键和值，内存占用和访问量随着上下文长度 $L$ 线性增长。这就是为什么长上下文推理对 Softmax 注意力来说如此昂贵的原因。
:::

#### 2.1.2 线性注意力的并行形式

> 线性注意力移除了 Softmax 操作，其计算公式为：

$$
Q, K, V = XW_Q, XW_K, XW_V
$$

$$
O = \left((QK^T) \odot M\right)V \tag{1}
$$

我们将公式(1)称为线性注意力的**并行形式**，因为所有 token 的注意力输出可以同时计算。

对于单个解码步骤 $t$，同样的计算可以写成：

$$
q_t, k_t, v_t = x_tW_Q, x_tW_K, x_tW_V
$$

$$
o_t = \sum_{i=0}^{t} q_t k_i^T v_i \tag{2}
$$

其中，$x_t, o_t, q_t, k_t, v_t \in \mathbb{R}^{1 \times d}$ 分别表示第 $t$ 个 token 的输入、输出、查询、键和值向量。

#### 2.1.3 线性注意力的递归形式

> 公式(2)也可以通过维护一个固定大小的状态来递归计算：

$$
S_t = S_{t-1} + k_t^T v_t
$$

$$
o_t = q_t S_t \tag{3}
$$

其中，$S_t \in \mathbb{R}^{d \times d}$ 是第 $t$ 步的线性注意力状态。

与并行形式相比，**递归形式避免了存储和访问所有先前的键值对，因此具有与上下文长度无关的恒定内存访问和解码延迟**。这一特性使它成为长上下文推理的理想选择，也是现有服务系统在解码阶段普遍采用的形式。

#### 2.1.4 线性注意力的分块形式

> 通过将递归形式扩展到 $m$ 个步骤，我们可以推导出**分块形式**：

$$
o_j = q_j S_{t-m} + \sum_{i=t-m+1}^{j} q_j k_i^T v_i, \quad \text{for} \quad j=t-m+1, ..., t \tag{4}
$$

$$
S_t = S_{t-m} + \sum_{i=t-m+1}^{t} k_i^T v_i \tag{5}
$$

分块形式使用第 $t-m$ 步的线性注意力状态和第 $t-m+1$ 到 $j$ 个 token 的键值对来计算第 $j$ 个 token 的注意力输出。每经过 $m$ 个解码步骤，它才使用最近 $m$ 个 token 的键值对更新一次状态。

::: block-1
**这种设计允许状态更新被延迟并批量应用，这对于减少解码过程中的平均内存访问非常有用**。实际上，:mdnice-bold-italic[并行形式和递归形式都可以看作是分块形式的特殊情况]：当 $m=L$ 时就是并行形式，当 $m=1$ 时就是递归形式。
:::

### 2.2 现有线性注意力服务系统的效率问题

> 当服务基于线性注意力的模型时，现有系统如 vLLM 和 SGLang 通常会初始化一个状态池，并为每个请求分配一个状态槽。在将提示预填充到线性注意力状态后，它们使用公式(3)的递归形式在每个解码步骤更新状态并计算注意力输出。

$$
S_t = S_{t-1} + k_t^T v_t
$$

$$
o_t = q_t S_t \tag{3}
$$

然而，这种方法存在严重的效率问题。表 1 对比了线性注意力三种计算形式在解码过程中的内存存储和平均每 token 内存访问。

![文章插图](/articles/2026-05-30-qwen3-next-kvbuffer-io-e625c4f5/images/04.webp)

::: image-caption
表 1：不同线性注意力计算形式在解码过程中的内存存储和平均每 token 内存访问
:::

*注：$L$ 表示上下文长度，$d$ 表示隐藏维度，$m$ 表示分块大小。内存访问以字节为单位，假设线性注意力状态存储为 FP32，$q, k, v, o$ 存储为 FP16。对于递归形式，状态更新和注意力输出计算被融合到单个内核中。*

> 从表 1 可以看出：

- **递归形式** 虽然具有恒定的存储和内存访问，但它在每个解码步骤都需要读写整个 $d \times d$ 的状态矩阵。由于状态比单个 token 的 KV 对大 $d$ 倍，这导致了极高的内存带宽消耗。
- **分块形式** 虽然引入了读取缓冲 KV 对的额外内存访问，但它将状态更新分摊到了多个 token 上，从而减少了平均内存访问。
- **并行形式** 的存储和内存读取随着上下文长度 $L$ 增长，但它避免了维护线性注意力状态，因此当 $L < d$ 时更高效。

::: block-1
这一分析揭示了一个重要事实：**递归形式并不总是服务线性注意力的最有效选择。不同的计算形式在不同的场景下各有优势**。:mdnice-bold-italic[KVBuffer 的核心设计理念就是通过缓冲键值对，让服务系统能够根据不同的解码场景灵活选择最有效的计算形式。]
:::

## 三、KVBuffer 的设计与实现

### 3.1 设计概述

> KVBuffer 的设计如图 1 所示。

![文章插图](/articles/2026-05-30-qwen3-next-kvbuffer-io-e625c4f5/images/05.webp)

::: image-caption
图 1：KVBuffer 设计。我们将 KV 缓冲区的内存划分为块，每个块可以存储 6 个 KV 对。每个请求有两个块。在解码过程中，服务系统加载状态和缓冲的 KV 对来计算注意力输出。当缓冲区满时，状态会在 GPU 上使用所有缓冲的 KV 对进行更新，更新后的状态将写回状态槽。
:::

除了从状态池分配的线性注意力状态外，KVBuffer 还为每个请求引入了一个 KV 缓冲区。**为了适应动态增长的 KV 对，KVBuffer 借鉴了分页注意力(Paged Attention)的思想，从系统级共享内存池中为请求分配 KV 缓冲区**。分配的基本单位是块，每个块可以存储 8 或 16 个 KV 对，由用户配置。

::: block-1
这种设计允许请求的 KV 缓冲区动态调整大小，避免了内存碎片，从而高效地支持分块形式和并行形式的线性注意力解码。
:::

### 3.2 基于 KVBuffer 的分块解码

> 通过结合线性注意力状态和缓冲的 KV 对，KVBuffer 支持分块解码，这比递归形式更具内存效率。

在预填充阶段，服务系统将提示计算到线性注意力状态中。在解码阶段，系统加载状态和缓冲的 KV 对，使用公式(4)计算线性注意力输出，并将新生成的 KV 对放入 KV 缓冲区。

$$
o_j = q_j S_{t-m} + \sum_{i=t-m+1}^{j} q_j k_i^T v_i, \quad \text{for} \quad j=t-m+1, ..., t \tag{4}
$$

当 KV 缓冲区满时，KVBuffer 使用所有缓冲的 KV 对批量更新线性注意力状态，如公式(5)所示。

$$
S_t = S_{t-m} + \sum_{i=t-m+1}^{t} k_i^T v_i \tag{5}
$$

由于递归形式和分块形式都是内存绑定的，它们的解码延迟与内存访问次数成正比。因此，我们可以通过递归形式和分块形式之间的内存访问比率来估计加速比。

![文章插图](/articles/2026-05-30-qwen3-next-kvbuffer-io-e625c4f5/images/06.webp)

::: image-caption
表 1：不同线性注意力计算形式在解码过程中的内存存储和平均每 token 内存访问
:::

根据表 1 的假设，加速比可以表示为：

$$
Speedup_{chunkwise\_decoding}(m) \approx \frac{4(d+1)}{2d + \frac{4d}{m} + m + 7}
$$

其中，$m$ 是分块大小，$d$ 是隐藏维度。

通过对这个函数求导，我们可以发现当 $m = 2\sqrt{d}$ 时，加速比达到最大值。这对应于 KVBuffer 分块解码的最优缓冲区大小。

另一方面，虽然 KVBuffer 减少了每 token 的解码延迟，但当缓冲区满时，它必须刷新缓冲的 KV 对，这会为该步骤引入额外的状态更新延迟。然而，由于所有缓冲 KV 对的状态更新是在 GPU 上并行执行的，延迟仍然很小，并且不会随缓冲区大小线性增长。

![文章插图](/articles/2026-05-30-qwen3-next-kvbuffer-io-e625c4f5/images/07.webp)

::: image-caption
表 1：不同线性注意力计算形式在解码过程中的内存存储和平均每 token 内存访问
:::

根据表 1 的相同假设，公式(5)中状态更新的算术强度为 $m/(4 + 2m/d)$。当 $m$ 不是很大时（例如 $m=2\sqrt{d}$），状态更新仍然是内存绑定的。

::: block-1
因此，其延迟大约与其内存访问 $8d^2 + 4md$ 成正比。对于最优缓冲区大小，缓冲区大小相关的项 $4md$ 与状态访问项 $8d^2$ 相比相对较小。
:::

### 3.3 推测解码的并行验证

> 推测解码是一种通过并行验证多个草稿 token 来加速 LLM 解码的重要技术。然而，现有的线性注意力服务系统通过为每个草稿 token 维护和递归计算一个临时的线性注意力状态，直到确定接受的 token ，这带来了显著的内存开销。

KVBuffer 实现了内存高效的草稿 token 并行验证。在验证过程中，服务系统可以缓冲草稿 token 的 KV 对，并使用公式(7)的分块形式计算它们的注意力输出。

$$
O = QS_{t-j} + \left((QK^T) \odot M\right)V \tag{7}
$$

**在确定接受的 token 后，服务系统只使用接受 token 的缓冲 KV 对更新线性注意力状态**，如公式(8)和图 2 所示，从而减少了整体内存使用。

$$
S_t = S_{t-j} + K_{acc}^T V_{acc} \tag{8}
$$

![文章插图](/articles/2026-05-30-qwen3-next-kvbuffer-io-e625c4f5/images/08.webp)

::: image-caption
图 2：使用 KVBuffer 的推测解码。现有服务系统只有一个状态池，并使用递归形式进行推测解码验证。因此，它们必须为每个草稿 token 存储一个临时状态。在确定接受的草稿 token 是 0 和 2 后，该请求的状态被临时状态 $state_2$ 替换。相比之下，KVBuffer 为每个草稿 token 缓冲 KV，并只使用接受 token 的 KV 更新状态，减少了整体内存使用。
:::

不失一般性，我们假设 $m$ 个草稿 token 是连续的并且全部被接受。公式(7)和(8)中注意力输出计算和状态更新的算术强度分别为 $\frac{2md^2 + 2m(m+1)d}{4d^2 + 12md}$ 和 $\frac{m}{4 + 2m/d}$，**两者都表明是内存绑定操作。因此，预期的加速比可以通过内存访问的比率来近似，由公式(9)给出：**

$$
Speedup_{parallel\_verify}(m) \approx \frac{(m+1)d + 2m}{3d + 4m} \tag{9}
$$

当 $d >> m$ 时，这个值趋近于 $\frac{m+1}{3}$。

需要注意的是，对于递归形式，我们通过假设验证步骤被融合到单个内核中，并且因为草稿 token 是连续的，我们只读取初始状态 $S_{t-j}$ 一次来估计内存访问。

- 对于 $m=2$，使用缓冲验证的推测解码与递归形式的运行时间大致相同。
- 对于 $m>2$ 且 $d>>m$，加速比随 $m$ 线性增长。

此外，KVBuffer 减少了验证过程中每个请求的内存占用。它不需要为每个草稿 token 维护一个临时的线性注意力状态，而只需要缓冲草稿的键值对并并行验证它们。**由于状态比 KV 大得多，这种减少允许服务系统在相同的内存预算下支持大约 $m$ 倍的并发请求**。因此，KVBuffer 也提高了整体服务吞吐量。

### 3.4 短上下文的纯 KV 解码

> 如表 1 所示，对于具有 $d$ 个或更少 token 的上下文，存储和访问所有先前 token 的键值对比使用递归和分块形式维护线性注意力状态更具内存效率。因此，当上下文长度 $L < d$ 时，我们更倾向于使用并行形式计算注意力输出。

![文章插图](/articles/2026-05-30-qwen3-next-kvbuffer-io-e625c4f5/images/09.webp)

::: image-caption
表 1：不同线性注意力计算形式在解码过程中的内存存储和平均每 token 内存访问。该表量化了线性注意力三种计算形式的内存开销差异，是 KVBuffer 设计的核心依据。并行式存储与读访问随上下文长度 L 线性增长，仅适合短上下文；循环式存储固定但每次需读写 d² 大小的状态，带宽开销极高；分块式通过批量更新状态，折中了读写开销。KVBuffer 正是利用分块式的折中特性，通过动态调整块大小平衡缓存读写与状态更新开销，最优块大小为 2√d，以此将平均内存访问降至最低，解决循环式高频读写大状态的低效问题。
:::

KVBuffer 的分页内存管理自然支持并行形式，这需要缓冲多达 $d$ 个 token 的键值对。KVBuffer 允许动态分配和释放 KV 块以避免内存碎片，类似于分页 KV 缓存管理。

$$
q_t, k_t, v_t = x_tW_Q, x_tW_K, x_tW_V
$$

$$
o_t = \sum_{i=0}^{t} q_t k_i^T v_i \tag{2}
$$

在预填充之后，服务系统缓冲所有 token 的键值对。在解码过程中，服务系统缓冲新生成的键和值，并使用公式(2)的并行形式计算注意力输出。一旦上下文长度 $L \geq d$，服务系统可以将键值对压缩为线性注意力状态，如公式(5)所示，然后转向前面讨论的分块解码。

$$
S_t = S_{t-m} + \sum_{i=t-m+1}^{t} k_i^T v_i \tag{5}
$$

给定上下文长度 $L$，公式(2)中并行计算形式的算术强度为 $\frac{L}{L+2}$，接近 1。这表明并行形式也是内存绑定的。因此，加速比可以通过并行形式和分块形式之间的平均内存访问比率来近似，由公式(10)给出：

$$
Speedup_{kv\_only}(m) \approx \frac{d + 2d/m + m/2 + 7/2}{L + 2} \tag{10}
$$

当 $m=2\sqrt{d}$ 时，公式(10)简化为 $\frac{d + 2\sqrt{d} + 7/2}{L + 2}$。加速比随着 $L$ 的增加而单调下降。

状态大小通常与模型的内存检索能力密切相关。然而，在实践中增加状态大小可能具有挑战性，因为递归解码必须在每个解码步骤访问整个线性注意力状态，而不管上下文长度如何。**因此，大状态变得极其昂贵，特别是对于短上下文请求**。通过支持并行形式的解码，KVBuffer 使得在保持短上下文解码推理效率的同时扩展状态大小成为可能，进一步释放了线性注意力的潜力。

## 四、实验评估

### 4.1 实验设置

> 作者在 SGLang v0.5.10 中实现了 KVBuffer，并根据解码场景配置 KVBuffer 块大小：

- 对于分块解码，块大小等于缓冲区大小
- 对于推测解码，块大小设置为草稿 token 的数量
- 对于纯 KV 解码，使用 16 的 KVBuffer 块大小，这是 KV 缓存管理中常见的页面大小

可用块的总数由状态池中分配的状态数量决定，这由 SGLang 中用户定义的为状态保留的内存分数控制。对于纯 KV 解码，KVBuffer 不初始化状态池，因为不维护线性注意力状态。相反，块的总数直接从可用内存、用户定义的内存分数和块大小计算。

作者在 Qwen3-Next-80B-A3B-Instruct 上评估了 KVBuffer，这是一种使用 Gated Delta Networks(GDN)作为其线性注意力模块的混合架构。

- 对于 GDN，作者为每个 token 缓冲衰减因子 $\alpha$、键 $k$ 和增量值 $u$ 以支持分块计算。Qwen3-Next-80B-A3B-Instruct 的头维度 $d$ 为 128。除非另有说明，线性注意力状态存储为 FP32，而缓冲的键和值存储为 FP16。
- 对于推测解码，作者使用 Multi-Token-Prediction 作为 Qwen3-Next 的草稿模型，并在 ShareGPT 数据集上进行评估。

实验在配备四个 NVIDIA L40S GPU 的机器上进行。作者使用张量并行性在所有四个 GPU 上服务模型。KVBuffer 相关的内核使用 Triton 实现，包括分块解码、推测解码中的并行验证、批量状态更新和并行形式解码的内核。

## 五、相关工作

### 5.1 线性注意力

> 线性注意力作为 Softmax 注意力的高效替代方案，被广泛研究用于长上下文推理。通过移除 Softmax 操作，线性注意力减少了对序列长度的二次依赖，并能够使用固定大小的状态进行递归解码。然而，与 Softmax 注意力相比，普通线性注意力在长上下文检索和模型质量方面存在退化。

最近的变体通过引入更具表达性的内存控制机制来缓解这个问题，包括：

- 数据无关的衰减机制[5, 16, 12, 17]
- 数据相关的衰减机制[4, 2, 20, 13]
- 增量规则[21, 19]

这些进展使线性注意力越来越适用于实际的长上下文应用。

### 5.2 混合架构

> 最近的 LLM[15, 23, 10]越来越多地采用混合架构，将线性注意力层与标准 Softmax 注意力层交错。这些混合架构保留了 Softmax 注意力强大的内存检索能力，同时使用线性注意力层来减少长上下文推理的内存存储和解码成本。

Qwen3-Next[15]和 Kimi-Linear[23]等模型证明，混合架构可以实现有利的质量-效率权衡，使线性注意力成为 LLM 越来越重要的构建块。在这项工作中，作者使用 Qwen3-Next-80B-A3B-Instruct 作为代表性的混合架构模型进行评估。

### 5.3 线性注意力的服务

> 现代 LLM 服务系统，如 vLLM[7]和 SGLang[24]，通过分页 KV 缓存管理[7]、连续批处理[22]、前缀缓存[24]和推测解码[8, 9]等技术提高推理吞吐量。这些技术主要是为使用 Softmax 注意力的 Transformer 模型设计的，其中服务是以 KV 缓存为中心的。

相比之下，线性注意力维护一个固定大小的状态，不再保留所有先前 token 的键和值，这为服务系统引入了不同的内存管理问题。最近的一些工作已经开始研究混合架构 LLM 的服务技术：

- 对于前缀缓存，Marconi[11]提出了通过在适当位置检查点线性注意力状态来为混合 LLM 提供高效的前缀缓存管理
- 对于预填充-解码分离，Prefill-as-a-Service[14]通过利用混合线性注意力模型减少的内存占用，探索了跨集群的预填充卸载
- 对于推测解码，STree[18]提出了一种基于树的 SSM 模型[2, 4]并行验证算法。然而，它没有研究线性注意力模型以及分块形式计算所需的相应服务系统支持

在这项工作中，作者研究了线性注意力服务的内存管理，并**表明它可以在各种解码场景中提高内存效率**。与现有工作相比，KVBuffer 的优势在于：

- 它是**第一个系统地研究线性注意力三种计算形式在服务场景下效率差异的工作**
- 它提出了一种:mdnice-bold-italic[统一的机制，支持分块解码、推测解码并行验证和短上下文纯 KV 解码]
- 它在实际的混合架构模型 Qwen3-Next 上进行了全面的评估，证明了显著的性能提升

## 六、讨论与局限性

### 6.1 不同计算形式的服务

> KVBuffer 使线性注意力能够使用不同的计算形式进行服务。然而，在实践中为每个请求动态选择最有效的形式并非易事。分块解码和纯 KV 解码需要不同的内核，并且具有不同的批处理要求，因此根据提示长度切换计算形式可能会引入额外的调度开销。

在这项工作中，作者没有在服务过程中跨不同解码形式动态路由请求。随着混合模型的继续扩展和隐藏维度 $d$ 的增加，纯 KV 解码可能变得越来越重要。

- 一个可能的方向是**将短上下文和长上下文请求分离到不同的服务器上。**
- 另一个方向是**在同一批处理中交错不同的解码形式，类似于分块预填充[1]。**

作者将这种动态调度机制的设计留给未来的工作。

### 6.2 采样

> KVBuffer 也可以使基于采样的解码算法受益。

例如，在束搜索中，服务系统需要维护多个候选分支。如果每个分支都以递归方式服务，系统必须为每个候选分支计算和存储一个单独的线性注意力状态，导致大量的内存开销。使用 KVBuffer，系统可以改为缓冲候选 token 的键值对，并仅在确定接受的分支后更新线性注意力状态。

### 6.3 基于 KV 的前缀缓存

> 现有服务系统通常使用线性注意力状态作为前缀缓存的检查点。然而，由于线性注意力状态非常大，检查点通常以粗粒度执行，使得难以在任意位置分割或重用前缀。

在这项工作中，**作者表明线性注意力状态可以从缓冲的键值对重建**。这一观察结果提出了一种替代的前缀缓存设计：:mdnice-bold-italic[服务系统可以缓存选定前缀的键值对，并根据需要重建状态，而不是仅缓存线性注意力状态。这种设计可以为基于线性注意力的模型实现更细粒度的前缀重用和更灵活的内存管理。]

### 6.4 对齐预训练和推理计算

> 线性注意力模型通常使用分块计算进行预训练[20]。

然而，现有服务系统通常在推理过程中使用递归形式，这导致预训练中使用的计算形式与推理中使用的计算形式之间不匹配。**对于长上下文生成，这种不匹配可能导致 RL 后训练期间的准确性下降或不稳定性[3]。**

因此，KVBuffer 不仅提高了服务效率，还有助于对齐推理和预训练计算，潜在地提高了推理稳定性。

## 结论

> 在本文中，作者提出了 KVBuffer——一种 IO 感知的线性注意力服务机制。通过缓冲最近的键值对，KVBuffer 能够在不同的解码场景中使用灵活的计算形式，包括分块解码、推测解码验证和短上下文解码。这些形式减少了不必要的内存访问，并显著提高了服务混合模型的效率。

实验结果表明，KVBuffer 在 Qwen3-Next-80B-A3B-Instruct 模型上将线性注意力解码延迟降低了高达 45.17%。在推测解码场景下，当验证 4 个草稿 token 时，KVBuffer 将最大服务请求数增加了 5 倍，端到端吞吐量提升了 1.46 倍。对于短上下文请求，纯 KV 解码比递归和分块解码都更有效。

::: block-1
**KVBuffer 的提出为线性注意力的高效服务开辟了新的方向**。它不仅解决了现有服务系统的内存访问瓶颈，还为未来混合架构大语言模型的优化提供了重要的思路。随着长上下文应用的不断普及，KVBuffer 这样的技术将变得越来越重要。
:::
