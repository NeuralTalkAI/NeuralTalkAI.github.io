## 一、异构计算的隐形痛点：FPGA 生命周期管理的厂商锁死困局

> 异构计算正在成为边缘与数据中心的主流架构，主机处理器搭配 FPGA 加速器的组合，既能兼顾通用管控的灵活性，又能满足计算密集型负载的性能与能效要求。

随着 RISC-V 等开放指令集架构的崛起，越来越多的异构片上系统开始集成 RISC-V 处理器与 FPGA 逻辑，比如 Microchip 的 PolarFire SoC、OpenHW 的 CVA6 平台都在推动开放架构的异构落地。**但在繁荣的背后，FPGA 的比特流部署与全生命周期管理却始终没有跟上开放化的步伐。**

当前的 FPGA 管理方案大多绑定 ARM 或 x86 架构，**深度耦合 AMD/Xilinx 的 Vivado/Vitis、Intel 的 Quartus 等厂商生态，甚至 AWS EC2 F1 这类云服务也有专属的基础设施。这种紧耦合带来了两个核心问题**：

- 一是移植性极差，换个处理器架构或者换个 FPGA 厂商，整套管理体系就要推倒重来，形成了严重的厂商锁定；
- 二是运维效率低下，很多开发流程仍然依赖手动更新、物理访问和整机重启重配置，根本无法支撑大规模设备机群的运维需求。

:mdnice-bold-italic[对于 RISC-V 生态而言，这种现状更加棘手。RISC-V 的核心优势是开放、模块化，但 FPGA 管理却没有与之匹配的厂商中立、机群导向的架构模型，这直接限制了 RISC-V 在 FPGA 加速场景中的大规模落地]。没有标准化的生命周期管理体系，再灵活的硬件架构也难以发挥规模化的价值。

::: block-1
总之，:mdnice-highlight[专有工具链与主机架构的深度绑定，已经成为阻碍 RISC-V 进入 FPGA 异构大规模落地的核心瓶颈]，行业急需一套跨指令集、跨厂商的中立架构来破局。
:::

## 二、核心架构：双平面设计将 FPGA 管理下沉至操作系统层

> 本文提出的核心方案，是一套主机无关的控制平面架构，**其核心洞察在于：FPGA 的生命周期管理本质上是一套操作系统级别的运维问题**，无需绑定特定的处理器指令集与厂商工具链。

![文章插图](/articles/2026-09-04-linux-risc-v-fpga-a905b254/images/04.jpg)

::: image-caption
图 1：工作流的架构概览。整个架构完全基于标准 Linux 的原生能力构建，包括驱动接口、文件系统访问、进程隔离、安全通信等，这就从底层实现了与特定 ISA、特定厂商栈的解耦，无论是 ARM、x86 还是 RISC-V 架构的处理器，只要能运行标准 Linux，就可以作为 FPGA 系统的控制主机。
:::

### 2.1 控制平面与加速平面的职责划分

整个架构从逻辑上划分为两大平面：控制平面与可重构加速平面。

- 控制平面运行在支持 Linux 的主机处理器上，是整个系统的大脑，负责所有的管理与调度工作。
- 加速平面则由 FPGA 逻辑构成，承载一个或多个硬件加速器，比特流作为可版本化的部署制品，可以在运行时动态加载与卸载。

> 控制平面承担五大核心职能，覆盖全生命周期的各个环节：

| 核心职能 | 描述 |
| --- | --- |
| 比特流配置 | 通过标准 Linux 设备驱动触发 FPGA 重配置，比如向 `/dev/fpga0` 写入比特流文件，完全绕开厂商专属的配置工具。 |
| 版本管理与比特流存储 | 所有比特流都存储在对接 CI/CD 流水线的版本化云仓库中，附带硬件兼容性、软件依赖等元数据，远端设备按需拉取，支持灰度部署与版本回滚。 |
| 带依赖的部署编排 | 系统会在激活新比特流前，确保所需的内核模块、用户态服务、硬件依赖全部就绪，实现 FPGA 逻辑与主机软件的协同更新。 |
| 隔离与模块化服务控制 | 基于 FPGA 的服务运行在独立的进程或容器中，可以独立启停重启，不会影响其他不相关的系统组件。 |
| 后端安全通信 | 比特流与生命周期指令通过认证加密通道从云端拉取，比如采用双向 TLS 的 HTTPS，保障完整性与来源可追溯。 |

控制平面与加速平面的分离，从架构上保证了硬件重配置不需要整机重启，也不会影响不相关的软件服务，这是实现无感运维的基础。

### 2.2 OSGi：把软件生命周期管理延伸到硬件

> 这套架构的:mdnice-bold-italic[核心创新之一，是将成熟的软件生命周期管理方法论延伸到了硬件领域，其载体就是 OSGi 框架。OSGi 是 Java 生态中成熟的模块化服务框架，天生支持组件的生命周期管理、版本控制和热部署，在企业级与嵌入式系统中都有广泛应用。]

每个边缘设备上都会运行一个实时 OSGi 代理，负责管理本地的 FPGA 软件与硬件配置。云端则部署统一的设备管理器，负责机群级的调度与分发。:mdnice-bold-italic[这套设计的核心突破，是把 OSGi 对软件组件的生命周期与版本管理能力，扩展到了虚拟机之外的硬件制品——也就是 FPGA 比特流上。这样一来，FPGA 比特流就和普通的软件包一样，拥有了版本号、依赖关系、部署状态，可以被统一纳管、灰度发布、快速回滚。]

## 三、全链路工作流：从打包到回滚的 6 步自动化闭环

> **整套机群级生命周期管理的落地，依靠一套完整的自动化工作流支撑**，从制品打包到异常回滚形成完整闭环，全程无需人工介入与整机重启。

论文中将整个流程拆解为 6 个标准步骤，每一步都对应明确的职责与校验点，完整覆盖 FPGA 应用从开发到部署再到运维的全生命周期。

| 步骤 | 描述 |
| --- | --- |
| 制品打包 | FPGA 应用生成的比特流文件（.bit）和对应的原生库文件（.so），与 Java 组件一起打包成带版本号的 OSGi 部署包；控制逻辑与加速逻辑分开打包，实现加速层与编排层的模块化解耦，支持独立迭代与更新。 |
| 仓库集成与验证 | 打包制品上传至中央仓库，由自动化多级验证流水线执行一致性检查、集成测试、策略校验；全部通过后进入可部署状态，作为硬件版本的“质量门禁”，防止问题比特流流入生产环境。 |
| 远程部署 | CloudPlane 平台通过加密通道将验证通过的制品分发至指定边缘设备；支持按版本号统一推送、按环境差异化部署、按设备分组灰度发布，适配多样化运维场景。 |
| 原子重配置 | 边缘设备上由控制平面专用加载器调用 FPGA 驱动接口，执行原子级比特流重配置；由主机处理器调度完成，无需整机重启，不中断其他无关服务，实现业务无感的硬件切换。 |
| 运行时隔离 | 实时 OSGi 运行环境确保更新过程中非目标服务持续正常运行；重配置影响严格限定于目标加速组件，不扩散至系统其他部分，为机群级运维提供核心隔离保障。 |
| 回滚与版本控制 | OSGi 运行时支持一键可控回滚至前一稳定版本，保障业务连续性；所有变更均版本化管理，全程可追溯、可审计，满足企业级运维规范。 |

::: block-1
整体看下来，这套工作流:mdnice-highlight[将软件 CI/CD 的成熟方法论完整复刻到了硬件运维领域]，在保证模块化、运行时隔离、架构中立的前提下，真正实现了机群级的 FPGA 全生命周期自动化管理。
:::

### 4.1 广泛的硬件兼容模式

> **这套架构具备硬件无关性**，不局限于单一平台，能够适配目前主流的三种 FPGA 集成模式：

- **同片异构 SoC**：主机 CPU 与 FPGA 逻辑集成在同一芯片上，比如 AMD Zynq UltraScale+ MPSoC、Microchip PolarFire SoC，这也是最典型的边缘异构形态。
- **同 fabric 软核方案**：在 FPGA 内部划分出主机区域与加速器区域，用支持 Linux 的软核处理器（比如 OpenHW CVA6）来控制同一块芯片内的加速器模块，这种模式尤其适合纯 FPGA 平台。
- **离散加速器方案**：通过 PCIe 等高速互联连接的独立 FPGA 加速卡，比如 AMD Alveo 加速卡、亚马逊 EC2 F1 实例，这种模式常见于数据中心场景。

::: block-1
这三种模式都可以无缝适配 RISC-V 架构——不管是集成 RISC-V 硬核的异构 SoC，还是在 FPGA 里实现的 RISC-V 软核，**只要能运行标准 Linux，就能直接作为控制主机使用，不需要修改架构本身。**
:::

## 五、对 RISC-V 与异构产业的核心价值

> 这套架构更深层的意义在于补齐了 RISC-V 异构生态的关键短板，推动 FPGA 运维从厂商专属走向标准化。

- 首先，**它真正打破了 FPGA 的厂商锁定**。过去做 FPGA 运维，选了哪家的芯片就要用哪家的工具链、哪家的管理方案，从处理器架构到运维体系全被绑死。:mdnice-bold-italic[而这套方案把管理能力下沉到操作系统层，用标准 Linux 接口抽象了所有硬件差异，厂商工具链只需要负责生成比特流，不需要再介入部署与运维环节。]
- 其次，**它让 RISC-V 正式具备了机群级 FPGA 管控能力**。在此之前，RISC-V 在 FPGA 系统里大多只能做加速端的控制，或者单设备的简单配置，没有成熟的机群级生命周期管理方案。:mdnice-bold-italic[这套架构让具备 Linux 能力的 RISC-V 处理器可以直接作为控制主机，融入成熟的 CI/CD 一体化管理流程，不需要再依赖 ARM 或 x86 的专属基础设施。]
- 第三，**它为异构边缘基础设施提供了标准化的运维底座**。随着边缘设备规模越来越大，异构算力的运维复杂度指数级上升，如果每一种硬件组合都要一套专属的管理方案，成本会高到无法承受。这套主机无关的架构提供了一个统一的管理范式，不同指令集、不同厂商的硬件都可以纳入同一套管理体系。

## 六、总结与展望

> 这项工作提出了一套主机无关的控制平面架构，为机群级的 FPGA 比特流部署与生命周期管理提供了可移植的解决方案，尤其为 RISC-V 生态补上了异构运维的关键一块拼图。

**通过将生命周期管理的需求定义在操作系统层面，这套方案彻底解耦了 FPGA 管理与特定处理器厂商、专有工具链的绑定，大幅提升了跨平台可移植性**。它让具备 Linux 能力的 RISC-V 处理器能够作为控制主机，参与到成熟的、CI/CD 集成的 FPGA 管理工作流中，无需依赖专有主机基础设施。

当然，这套方案目前还有可以拓展的空间。

- 当前的实现基于 OSGi 框架，对于资源极度受限的边缘 RISC-V 设备，还可以:mdnice-bold-italic[探索更轻量的实现方案；]
- RISC-V 异构平台的增多，在**更多 RISC-V 原生 SoC 上的验证与优化** 也会是未来的重要方向。
- 这套架构还可以进一步和更多云原生运维工具对接，融入更广泛的 DevOps 生态。

::: block-1
长远来看，随着开放指令集与可重构硬件的深度融合，:mdnice-highlight[标准化、跨厂商的生命周期管理会成为异构计算的刚需]，这项工作正是朝着这个方向迈出的坚实一步。它不仅解决了 RISC-V FPGA 系统的实际问题，也为整个异构运维领域提供了一套可参考的开放架构范式。
:::
