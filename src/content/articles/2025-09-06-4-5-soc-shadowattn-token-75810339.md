## 关键问题

### 问题1：shadowAttn在非高通架构NPU上的泛化性问题

> 【具体问题】作者仅在搭载高通骁龙8 Gen2/3 NPU的小米14、Redmi K60设备上验证shadowAttn，而移动设备NPU架构存在显著厂商差异（如联发科天玑APU、华为麒麟NPU等），其量化精度支持、静态图优化逻辑与高通Hexagon NPU不同。那么shadowAttn的NPU计算图分桶、INT8估计等核心设计，在非高通架构NPU上是否会出现精度骤降或效率损失？其硬件泛化性如何保证？

**shadowAttn的硬件验证与核心实现目前高度依赖高通NPU生态**，尚未覆盖联发科、华为等其他厂商的NPU架构，其泛化性需结合现有设计逻辑与实验范围客观分析：

::: block-1
1. 硬件依赖层面：作者明确提到shadowAttn的NPU软件栈基于高通QNN SDK与Hexagon SDK开发（§4），测试设备仅为搭载骁龙8 Gen2/3（Hexagon V73/V75 NPU）的小米14、Redmi K60，未涉及联发科天玑APU、华为麒麟NPU等其他架构。这些非高通NPU的量化精度支持（如是否原生支持INT8 per-tensor量化）、静态图编译逻辑（如尺度因子处理方式）与高通存在差异，而shadowAttn的“NPU计算图分桶”“INT8估计”等核心设计，均基于高通NPU的静态图特性与量化能力设计（§3.3），其**在非高通NPU上是否会出现精度骤降或效率损失，论文未提供实验验证**。
2. 潜在适配性层面：:mdnice-bold-italic[作者提到shadowAttn“可集成到任何主流端侧LLM推理框架”（§3.1），且“计算图分桶”的核心思想（离线生成多尺度图以适配输入波动）具备一定通用性] ——理论上，若其他厂商NPU支持静态图编译与基础INT8计算，可通过适配其SDK重构分桶逻辑；但论文未提供该适配的可行性验证或 overhead 分析，因此泛化性仍存疑。
:::

### 问题2：离线预定义稀疏率在不同任务场景的适配性与动态调整问题

> 【具体问题】作者通过离线 profiling WikiText-2 corpus的128个样本确定各注意力头的稀疏率，且稀疏率在在线推理中固定。但不同移动LLM任务（如摘要生成、GUI自动化、API调用）的token重要性分布差异显著，当模型切换任务场景时，预定义的稀疏率是否会因适配性不足导致精度下降或计算冗余？动态调整稀疏率是否会引入不可接受的 overhead？

结合实验与设计逻辑，可从“现有任务适配性”与“动态调整缺失”两方面分析：

::: block-1
1. 现有任务适配性：论文离线阶段通过WikiText-2的128个样本 profiling 确定各头的稀疏率（§3.2），在线阶段固定该稀疏率；但测试覆盖了三类差异显著的移动任务——自然语言理解（ArxivSum）、GUI自动化（DroidCall）、API调用（Octopus）。实验结果显示，shadowAttn在这三类任务上的平均精度损失仅0.4 pp（§5.1，表6），且与CPU/GPU全注意力（C/G-Full）精度基本持平（平均36.4 vs 36.8），说明**离线预定义的稀疏率在论文测试的多任务场景中具备较好适配性**，未因任务差异出现明显精度下降或计算冗余。
2. 动态调整与overhead：论文明确稀疏率“在离线阶段确定，在线阶段固定”（§3.2），未提出动态调整稀疏率的方案；对于动态调整可能引入的overhead（如实时profiling token重要性分布、重新计算各头稀疏率的耗时），论文也未进行分析。因此，若任务超出论文测试的三类场景（如高信息密度的专业文档摘要、低冗余的指令跟随），预定义稀疏率是否适配、动态调整是否可行，**论文未提供答案**。
:::

### 问题3：高负载实时任务下的 latency 波动与CPU核心调度稳定性问题

> 【具体问题】论文测试shadowAttn与视频播放、音乐收听等常规移动应用共存时的性能，但未覆盖AR渲染、实时4K视频处理等高负载实时任务——这类任务会剧烈抢占NPU/CPU/GPU资源。此时shadowAttn的头级NPU-CPU/GPU流水线是否会因资源竞争出现 latency 波动幅度扩大？且论文依赖单CPU核心执行稀疏计算，若系统将该核心调度给高优先级任务，shadowAttn的推理稳定性如何保障？

实验范围与设计逻辑显示，其在高负载实时任务场景的表现仍存在未覆盖的空白：

::: block-1
1. 高负载任务的 latency 波动：论文仅测试了shadowAttn与“视频播放、音乐收听、购物APP”等常规移动应用共存的场景（§5.2，表9），这些应用对NPU/CPU的资源占用相对温和，实验结果显示 latency 稳定（14.5-15.5秒，无明显波动）。但对于AR渲染、实时4K视频处理等高负载任务，论文未进行测试——这类任务会剧烈抢占NPU（如AR的实时特征提取）与CPU资源，而shadowAttn的“头级NPU-CPU/GPU流水线”依赖NPU与CPU的并行调度（§3.4），资源竞争是否会导致流水线气泡增多、latency波动扩大，**论文无实验数据支撑**。
2. CPU核心调度稳定性：论文明确“仅使用一个CPU中核执行稀疏计算与控制流”（§4），但未提及任何系统级的核心调度保障机制（如绑定CPU核心、提升任务优先级）。若移动系统将该中核调度给高优先级任务（如实时通信、系统进程），shadowAttn的稀疏计算会被迫中断或延迟，但其推理稳定性如何保障，**论文未提出解决方案，也未测试该场景下的性能表现**。

## 一、引言

在设备端运行大型语言模型（LLMs）是实现隐私保护和普适人工智能的关键技术。近年来，通义千问（Qwen）系列[12, 44]等移动端尺寸的 LLMs 的出现，催生了内容摘要、图形用户界面/应用程序接口代理[8, 17, 61, 76]等杀手级应用。

### 1.1 以 NPU 为核心的 LLM 推理

移动设备通常集成了中央处理器（CPU）、图形处理器（GPU）和神经网络处理器（NPU）等异构处理器。理想情况下，LLM 推理应在移动 NPU 上端到端执行，且对 NPU 外资源的依赖最小化。这种以 NPU 为核心的 LLM 推理具有两大优势：

::: block-1
- 首先，移动 NPU 作为专为神经网络设计的硬件，具备高吞吐量整数计算能力，且比 CPU/GPU 更节能[16, 48, 57, 63]；
- 其次，它能避免与依赖 CPU 和 GPU 的其他通用移动工作负载产生资源竞争。若 LLM 推理与这些工作负载共存，极易影响用户体验（如导致手机卡顿、响应变慢），并增加系统调度的复杂度[19, 22, 52, 70, 80]。
:::

然而，我们发现在实践中，**最先进的设备端推理框架[16, 21, 37, 63]中，LLM 的注意力操作往往会回退到移动 CPU/GPU 上运行**。例如，:mdnice-bold-italic[llm.npu[63]会将非注意力操作卸载到 NPU，但注意力操作仍在 CPU 上运行——并非以 NPU 为核心。]

这种折中方案的核心原因是量化敏感性。

::: block-1
- 一方面，:mdnice-bold-italic[与权重相比，LLM 中的激活值具有更多难量化的异常值[29, 58]，而注意力操作需要对多个激活张量] ——即查询（Q，Query）、键（K，Key）、值（V，Value）张量——进行计算；
- 另一方面，:mdnice-bold-italic[NPU 的静态图阻碍了细粒度量化]，无法对张量进行更细致的量化操作，如按通道或按元素量化。静态图在编译阶段就需确定超参数——包括张量形状和比例因子等，以进行资源调度。这种模式导致整个张量共享一个固定的比例因子，进一步限制了注意力操作的量化。
:::

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/05.webp)

在后续实验（表 3）中，我们发现:mdnice-bold-italic[基于 NPU 的注意力操作会导致移动端 LLM/任务的准确率平均下降 18 个百分点。这印证了将注意力操作卸载到 CPU/GPU 的必要性。]

### 1.2 基于稀疏注意力的 NPU 核心 LLM 推理

:mdnice-bold-italic[最小化对 CPU/GPU 资源依赖的一个关键机遇在于注意力操作的高度稀疏特性：少量 tokens 可能比其他 tokens 重要得多，对这些 tokens 进行稀疏计算可在几乎不损失准确率的情况下，大幅减少 CPU/GPU 的计算量]。如第 2 节所述，在 WikiText-2 数据集上，Qwen2-1.5B 模型（参数量为 15 亿的 Qwen2 系列模型）中，平均超过 80%的 tokens 被分配到相对较低的重要性。

然而，令人意外的是，初步结果表明，在 LLM 推理中直接应用稀疏注意力并不能带来性能提升——**因为在执行稀疏计算前，需要一个估算阶段来评估 token 的重要性，而该阶段会在 CPU/GPU 上产生大量开销**。:mdnice-bold-italic[此阶段需要通过矩阵乘法计算 Q 和 K 中每个 token 的注意力分数] [56, 79]。

因此，:mdnice-bold-italic[在高稀疏度下，估算阶段主导了整个注意力计算]。例如，当稀疏率为 20%（即丢弃 80%的 tokens）时，仅估算阶段就占总开销的 60%以上，CPU/GPU 资源消耗仅减少约 20%。

:mdnice-bold-italic[直观上，我们可以对 Q 和 K 进行下采样来实现高效估算，但这会导致准确率显著下降。] 例如，通过将相邻 tokens 分组为块，仅计算块级重要性来消除估算开销时，与 token 级稀疏（指以单个 token 为单位选择重要 tokens）相比，移动端 LLM/任务的准确率平均下降 4 个百分点。

> 为此，shadowAttn 设计的核心问题是：如何在以 NPU 为核心的 LLM 推理中，准确且高效地计算稀疏注意力。

### 1.3 shadowAttn：基于 NPU 估算的动态稀疏注意力

本文提出 shadowAttn——一种系统-算法协同设计的设备端稀疏注意力模块，适用于以 NPU 为核心的 LLM 推理，同时最小化对 CPU/GPU 回退的依赖（例如，仅使用一个 CPU 核心）。其:mdnice-bold-italic[核心思想是：与端到端注意力相比，重要 tokens 的估算对量化具有更强的鲁棒性]。

原因在于，确定重要 tokens 只需注意力分数的相对值，而计算注意力的精确结果则需要绝对值。因此，:mdnice-bold-italic[shadowAttn 将估算阶段卸载到 NPU，仅将重要 tokens 的位置索引传输到 CPU/GPU，以进行后续的稀疏注意力计算。通过这种方式，仅极少量 tokens 需要在 CPU/GPU 上通过高精度浮点运算处理]。此外，:mdnice-bold-italic[shadowAttn 还发现了每个注意力头稀疏率的不均衡特性：它通过轻量级离线分析为每个注意力头确定稀疏率，进一步优化了精度-效率权衡。]

> 然而，在设计 shadowAttn 时，我们还需要解决现有文献中未涉及的以下主要挑战：

::: block-1
1. **NPU 静态计算图的灵活性不足**：NPU 的软件栈采用静态计算图，该图将张量形状和量化比例因子等参数指定为常量，以进行离线优化。但注意力输入张量具有高度动态性：其比例因子波动较大，张量形状在不同场景下也可能不同。直接为注意力操作生成一个静态计算图会导致准确率下降和 NPU 利用率不足。
2. **多方面的 NP 难 NPU-CPU/GPU 调度**：shadowAttn 稀疏注意力的两个阶段可通过按注意力头的细粒度流水线在 NPU 和 CPU/GPU 上实现重叠执行。然而，实现高效的细粒度调度并非易事，原因在于：（1）流水线优化涉及多个深层方面，若未仔细优化这些方面，流水线性能会下降；（2）流水线规划问题属于 NP 难问题。
:::

针对上述挑战，shadowAttn 结合深刻洞察，提出了以下技术：

::: block-1
1. **NPU 计算图分桶（第 3.3 节）**：为缓解静态计算图的局限性，shadowAttn 在:mdnice-bold-italic[离线阶段生成多个计算图，并将其分桶组织以用于在线选择]。具体而言，一个“桶”中包含具有不同张量形状但相同输入张量比例因子的计算图。在在线推理阶段，首先选择比例因子与输入张量最接近的桶，然后从该桶中选择具有适配形状的计算图。
2. **按注意力头的 NPU-CPU/GPU 流水线（第 3.4 节）**：shadowAttn 提出一种按注意力头的流水线，其设计基于以下洞察：为实现设备端的快速规划，shadowAttn 通过启发式贪心搜索简化了 NP 难规划的复杂度——在每一步选择能最小化流水线延迟的注意力头。
:::

### 1.4 实现与评估

我们使用 C++/Python 编写了超过 10000 行代码，实现了 shadowAttn 的原型。测试在搭载骁龙 8gen3/8gen2的市售智能手机小米 14（MI14）和红米 K60 冠军版上进行。**我们仅使用一个 CPU 核心处理必要的控制流和稀疏计算，其余计算全部在 NPU 上完成。**

我们既测试了注意力模块的分项性能，也测试了将 shadowAttn 集成到最先进的 NPU 框架 llm.npu[63]后的端到端性能。评估基于移动端 LLM（包括 Qwen2-0.5B/1.5B 和 PhoneLM-0.5B/1.5B），并在三个具有代表性的移动端特定任务数据集上报告结果。

在 CPU/GPU 资源高度受限的情况下，与四种设计替代方案相比，shadowAttn 的**分项加速比最高达 6.9 倍**，端到端加速比最高达 **4.5 倍**，能耗降低最高达 **7.7 倍**。:mdnice-bold-italic[与最先进框架的原生注意力相比，shadowAttn 仅需极少的 CPU/GPU 资源，就能实现相当甚至更优的性能]，且在四个模型和三个数据集上的平均准确率损失仅为 0.4 个百分点。

### 1.5 主要贡献

::: block-1
- 我们指出了移动端以 NPU 为核心的 LLM 推理面临的关键问题，并提出 shadowAttn——一种系统-算法协同设计的稀疏注意力模块，显著降低了对 CPU/GPU 浮点计算的依赖。
- 我们提出了多项关键技术，包括将 token 重要性估算卸载到 NPU、NPU 计算图分桶以及 NPU-CPU/GPU 流水线，解决了以 NPU 为核心的设备端注意力计算的主要挑战。
- shadowAttn 在最小化 CPU/GPU 资源依赖的同时，性能优于强大的基线方案，且可即插即用到任何主流设备端 LLM 推理框架。
:::

## 二、背景与动机

### 2.1 移动系统级芯片（SoC）上的大语言模型（LLM）推理

#### 移动 NPU：深度神经网络（DNN）推理的整数运算加速器

随着用户对个人数据保护和安全的关注度不断提升，越来越多的用户选择在个人设备上直接运行大语言模型。为实现更高性能，设备端 LLM 推理应在**神经处理单元（NPU）** 上执行——NPU 是专为深度神经网络推理设计的专用硬件，这种推理模式被称为“以 NPU 为核心的推理”。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/06.webp)

> 表 1 总结了主流移动/嵌入式系统级芯片（SoC）上的 NPU，包括高通骁龙系列[7,9]、德州仪器 TMS320F2812[10]、英伟达 Orin[4]等。

我们观察到，这些 NPU 的共性是**以低精度整数运算为核心**：所有 NPU 均支持整数运算，但浮点运算能力为零或较低。这一设计源于两方面原因：

::: block-1
1. 与通用计算任务相比，深度神经网络（DNN）可通过量化降至更低精度，从而实现高效执行和内存节省；
2. 支持多种数据精度会占用更多芯片面积，或为硬件单元复用带来显著的额外设计复杂度[31,32,40]。
:::

#### 移动 NPU 的静态计算图

为实现最优运行时效率的资源调度，移动 NPU 通常采用**静态计算图** （指运算流程、张量形状、量化参数等在编译前固定，无法动态调整的计算图）。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/07.webp)

图 1 展示了基于高通 QNN SDK[6]的静态计算图推理流程，分为三个阶段：

::: block-1
1. **离线阶段（Offline Stage）**：首先构建计算图并加载到设备内存，然后通过一系列优化步骤将计算图编译为二进制文件；
2. **在线阶段（Online Stage）**：将输入数据传入编译后的计算图并执行推理；
3. **离线释放（Offline Stage）**：推理完成后从内存中释放计算图。
:::

:mdnice-bold-italic[静态计算图要求在离线构建阶段指定并固定多个关键超参数]。如图 1 所示，这些参数包括：为 INT8 张量分配单个浮点值作为缩放因子（用于量化时的数值映射）、定义张量的精确形状。随后，张量、厂商提供的算子类型会被组装成计算图，最终通过优化编译为二进制文件。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/07.webp)

图 1 中标注了各阶段的延迟（基于 QNN SDK[6]的基础矩阵乘法运算测得）：离线阶段的耗时（:mdnice-bold-italic[构建图 5-10 秒、编译图 1 秒]）远高于在线阶段（:mdnice-bold-italic[加载图 10 毫秒、执行图 1 毫秒]），因此**无法为每个输入动态在线构建计算图。**

#### 主流设备端 LLM 推理框架中注意力运算的 CPU/GPU 回退问题

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/08.webp)

> 表 2 列出了代表性的设备端 LLM 推理框架，包括 llm.npu[63]、HeteroLLM[16]、llama.cpp[21]和 mlc-llm[37]——这些框架均将注意力运算委托给 CPU 或 GPU 执行。

- llm.npu 虽将非注意力运算卸载到 NPU，但注意力运算仍在 CPU 上运行，并未实现“以 NPU 为核心”；
- HeteroLLM 也采用类似的“NPU-CPU/GPU 协作”模式；
- 而纯 CPU 框架 llama.cpp 和纯 GPU 框架 mlc-llm 则完全依赖 CPU/GPU 执行所有运算。

这种设计妥协的核心原因是**注意力运算对量化高度敏感**，具体体现在两方面：

::: block-1
1. **激活张量的量化难度**：:mdnice-bold-italic[LLM 中的激活张量比权重张量存在更多“难量化异常值”[29,58]，而注意力运算恰好依赖 Q、K、V 这三个激活张量的计算；]
2. **NPU 静态计算图的量化限制**：NPU 的静态计算图要求量化参数（如缩放因子）在编译前固定，导致整个张量共享一个固定缩放因子——这种“张量级静态量化”粒度粗糙，无法采用 llama.cpp 的 K-quant[21]或 AWQ[29]等细粒度量化方法。
:::

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/05.webp)

> 表 3 显示，将注意力运算卸载到移动 NPU 会导致显著的精度损失。

::: block-1
- PhoneLM-0.5B 在 ArxivSum 数据集和 DroidCall 数据集上分别出现 14.7 个百分点（pp）和 7 个百分点的精度下降；
- 在三个数据集、四个模型的测试中，NPU-based 注意力的平均精度下降达 18 个百分点。
:::

这也印证了“将注意力运算卸载到 CPU/GPU 以保证精度”的必要性。

**这种“为保证精度而依赖 CPU/GPU 回退”的模式，使得设备端推理无法真正实现“以 NPU 为核心** ”：既无法充分利用移动 NPU 的高吞吐量运算能力和低功耗优势，还会导致 LLM 推理与其他依赖 CPU/GPU 的移动任务（如用户交互、界面渲染）产生严重的资源竞争，进而影响用户体验[19,22,52,70,80]。

### 2.2 稀疏注意力（Sparse Attention）

#### 稀疏注意力：减少 CPU/GPU 依赖的关键机遇

> 注意力运算的**高度稀疏特性**，为减少 CPU/GPU 依赖提供了核心机遇。:mdnice-bold-italic[我们观察到：注意力机制中 仅有少量 token 真正重要]，对这些重要 token 进行稀疏计算，可在几乎不损失精度的前提下大幅减少 CPU/GPU 的计算量。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/09.webp)

如第 2 节详细分析所示，在 WikiText-2 数据集上的 Qwen2-1.5B 模型中，平均超过 80%的 token 被分配到相对较低的重要性（即注意力分数接近零，对最终结果贡献可忽略）。

#### 稀疏注意力的工作流程

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/10.webp)

> 图 3 展示了通用稀疏注意力的工作流程，该流程可涵盖滑动窗口、垂直斜线等多种固定稀疏模式[23-25]，也支持无明显结构的动态稀疏模式，主要分为两个阶段：

1. **估计阶段（Estimation Stage）**：首先计算完整的注意力分数矩阵，公式为：$attentionScores = softmax\left(mask\left(\frac{Q \cdot K}{\sqrt{d_{k}}}\right)\right)$其中，Q（Query，查询）、K（Key，键）的所有 token 均参与计算；mask 为**掩码** （用于屏蔽无效关联，如因果掩码屏蔽未来 token 对当前 token 的影响）；$\sqrt{d_{k}}$ 用于防止 Q·K 矩阵乘法结果过大导致 softmax 梯度消失（$d_{k}$ 为 K 的维度）。随后，从注意力分数中筛选出 top-k（前 k 个）高分数值，并将其位置索引传入下一阶段。
2. **注意力计算阶段（Attention Stage）**：仅基于估计阶段输出的索引，对保留的重要 token 执行稀疏注意力计算，公式为：$O = softmax\left(mask\left(\frac{Q \cdot K}{\sqrt{d_{k}}}\right)\right) \cdot V$其中，V（Value，值）仅参与重要 token 的计算，O 为最终注意力输出。

#### 稀疏注意力的瓶颈：估计阶段

尽管稀疏注意力具备潜在优势，但我们的初步实验表明：:mdnice-bold-italic[直接将其应用于 LLM 推理无法获得预期性能提升——原因是在执行稀疏计算前，必须先通过“估计阶段”评估 token 重要性，而该阶段会在 CPU/GPU 上产生巨大开销]。估计阶段需对 Q 和 K 的所有 token 执行矩阵乘法以计算注意力分数[56,79]，因此**在高稀疏率下，估计阶段会主导整个注意力计算的耗时。**

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/11.webp)

例如：当稀疏率为 20%（即剪枝 80%的 token）时，估计阶段的开销占总开销的 60%以上，导致 CPU/GPU 资源消耗仅减少约 20%。

一种直观的优化思路是对 Q 和 K 进行下采样以简化估计（如分组相邻 token 为“块”，仅计算块级重要性），即**块稀疏注意力** [69]，**但这种方法会导致显著的精度损失**：如图 4b 所示，PhoneLM-1.5B 在 ArxivSum 数据集上因块级估计（64 个 token 为一个块）导致精度下降 6.1 个百分点。

> 因此，:mdnice-bold-italic[shadowAttn 设计的核心问题是：如何在以 NPU 为核心的 LLM 推理中，实现“高精度+高效率”的稀疏注意力计算。]

## 三、设计方案

### 3.1 概述

> shadowAttn 是一款面向移动 SoC 的“系统-算法协同设计”型、以 NPU 为核心的 LLM 推理框架，其核心目标是：**在最小化对 CPU/GPU 等通用处理器依赖的前提下，实现注意力运算的高精度、高效率执行。**

#### shadowAttn 的工作流程

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/12.webp)

> 图 5 展示了 shadowAttn 的工作流程，主要包括三个部分：

1. **离线阶段（Offline Stage）**：:mdnice-bold-italic[在通用语料库（默认采用 WikiText-2 的 128 个样本）上执行多种轻量级分析] （lightweight profiling，指在少量校准数据上的快速特征分析，无需大量计算资源）：

::: block-1
- 基于每个注意力头部的重要性和系统配置的全局稀疏率，确定每个头部的专属稀疏率；
- 生成多个静态计算图，并按“桶（bucket）”组织，用于在线推理时选择；
- 结合操作系统配置的可用 CPU/GPU 资源，分析关键算子的设备端执行开销，为流水线调度提供依据。
:::

该阶段主要在云服务器上完成（模型安装到移动设备前），耗时和资源开销可忽略。

1. **以 NPU 为核心的计算图（NPU-centric Compute Graph）**：:mdnice-bold-italic[shadowAttn 生成专用稀疏注意力模块，该模块可集成到设备端推理框架中，形成端到端的 NPU-centric 计算图]。如图 5 所示：

::: block-1
- 推理框架将非注意力算子（如 MLP）部署在 NPU 上；
- 注意力模块中，:mdnice-bold-italic[RoPE（旋转位置编码，Rotary Position Embedding，一种高效捕捉序列位置信息的编码方式）在 CPU/GPU 上执行；Q·K 的估计阶段以 INT8 精度在 NPU 上执行]；
- 获得 top-k 位置索引后，CPU/GPU 仅对碎片化的 Q、K、V 执行高精度（float32）稀疏计算，最终输出 O。
:::

```
 整个流程中，NPU 外的计算和数据传输被最小化。
```

1. **在线阶段（Online Stage）**：计算图以用户输入的提示文本（prompt）为输入，在移动 SoC 的 CPU/GPU/NPU 上分布式执行。:mdnice-bold-italic[推理过程中，进一步引入两项关键优化：NPU 计算图分桶（§3.3）和基于注意力头部的 NPU-CPU/GPU 流水线（§3.4）。]

### 3.2 shadowAttn 的动态稀疏注意力（Dynamic Sparse Attention）

#### 头部特定稀疏率（Head-specific Sparse Ratio）

> shadowAttn 的核心洞察之一是：注意力的稀疏率应**按头部定制**。根据可解释人工智能（XAI）[36]的研究成果，:mdnice-bold-italic[神经网络模块的重要性可通过“移除该模块后的损失变化（delta loss）”衡量：]

::: block-1
- 对于校准数据集 C，第 j 层第 i 个注意力头部的重要性可表示为：$headImp_{i} = loss\left(head_{i}=0, C\right) - loss(C) \tag{1}$其中，$loss(head_{i}=0, C)$ 表示“将第 i 个头部置零（即不参与计算）”时模型在 C 上的损失，$loss(C)$ 表示原始模型在 C 上的损失；差值越大，头部越重要。
- 第 j 层的重要性可表示为：$layerImp_{j} = loss\left(layer_{j}=0, C\right) - loss(C) \tag{2}$

同理，$loss(layer_{j}=0, C)$ 表示“将第 j 层置零”时的损失。
:::

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/13.webp)

> 图 6 展示了头部和层的重要性分布不均现象：

- 图 6(a)中，移除 PhoneLM-0.5B 第 1 层的不同头部后，损失值差异显著（如头部 2 的损失值增至 100 以上，而头部 8 的损失值仅增至 60 以下）；
- 图 6(b)展示了层级损失分布的不均性。

这种:mdnice-bold-italic[不均性的核心原因是：神经网络的不同部分会学习数据的不同特征[15,20,24]，尤其是在紧凑的移动 LLM 中，头部和层的功能分化更明显。]

> 综上，:mdnice-bold-italic[不同层的不同头部应采用不均等的稀疏率]：重要头部保留更多 token，次要头部保留更少 token。

给定全局平均稀疏率 r 和模型中所有头部的总数 N，第 i 个头部的稀疏率计算公式为：

$$
\frac{r \cdot N \cdot clamp\left(headImp_{i} \cdot layerImp_{j}\right)}{\sum clamp\left(headImp_{i} \cdot layerImp_{j}\right)}, \quad 1 \leq i \leq N \tag{3}
$$

其中，$clamp(·)$ 为**截断函数** （将超过 1e-3 的异常大值限制在合理范围，避免个别头部过度影响稀疏率计算）；j 为第 i 个头部所在的层索引（$j = i / headNumPerLayer$，headNumPerLayer 为每层的头部数量）。

每个头部的稀疏率在离线阶段确定，并在在线推理阶段保持固定，无额外开销。默认校准数据集为 WikiText-2 的 128 个样本，在配备单张 A100 GPU 的云服务器上，对一个移动 LLM 的离线分析仅需约 5 分钟，对大多数开发者而言成本可控。

#### 基于 NPU 的估计阶段（Running Estimation on NPU）

> shadowAttn 的另一核心洞察是：**token 重要性的估计阶段，对量化的容忍度远高于端到端注意力计算**。

具体而言：**确定重要 token 的位置仅需注意力分数的“相对大小”**，而计算注意力的精确结果需“绝对数值”——因此，估计阶段可卸载到低精度 NPU 执行，而不会显著损失精度。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/14.webp)

表 4 验证了这一洞察：

::: block-1
- 通过 NPU 的 INT8 张量级量化（per-tensor quantization）预测 Q·K 中重要位置的平均召回率，在不同模型和全局稀疏率下均超过 99%；
- 而直接用 NPU 计算端到端 QKV（注意力输出）时，精度损失显著（如 PhoneLM-0.5B 在 Octopus 数据集上损失 40.5%）。
:::

> 两者差异的核心原因是：**QKV 计算需严格的“数值等价性”，而重要位置识别仅需“相对大小关系”** （例如，Q·K 的原始结果为[0.4,0.3,0.2,0.1]，量化后为[0.5,0.4,0.08,0.02]，虽绝对数值变化，但 top-k 位置不变，不影响重要 token 识别）。

基于此，shadowAttn 的估计阶段工作流程如下：

::: block-1
1. 对 Q 和 K 张量进行量化，在 NPU 上以 INT8 精度执行稠密的 Q·K 矩阵乘法；
2. 将 NPU 输出的 Q·K 结果传输到 CPU/GPU，执行 top-k 操作以筛选重要 token 的位置索引；
3. CPU/GPU 基于索引，对 Q、K、V 执行高精度（float32）稀疏注意力计算。
:::

需特别说明的细节：

- **shadowAttn 不基于 Q·K 进一步计算掩码注意力分数** ——由于 softmax 是严格单调递增函数，Q·K（softmax 前）的 top-k 位置与 softmax 后的 top-k 位置完全一致，因此可直接用 Q·K 筛选 top-k；
- 同时，**因果掩码不应用于 Q·K 计算，而是在 CPU/GPU 的 top-k 操作中直接跳过掩码位置** （该操作在 CPU/GPU 上实现简单，开销可忽略）。

### 3.3 NPU 计算图分桶（NPU Compute Graph Bucketing）

#### 问题：缩放因子波动与静态计算图的矛盾

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/15.webp)

> 图 7 展示了 NPU 估计阶段中，Q 和 K 张量各头部的缩放因子分布（基于 INT8 张量级量化，数据样本与前文一致）。

**结果表明：Q 和 K 的缩放因子在不同头部间波动显著** ——例如，Q 张量中超过 30%的缩放因子大于 0.2，而 20%的缩放因子小于 0.1。

如 2.1 节所述，NPU 的软件栈为最大化运行效率，要求离线编译“参数固定的静态计算图”（包括缩放因子、张量形状等）。若对所有输入仅使用一个静态图，由于不存在“通用缩放因子”，会导致精度显著下降和 NPU 利用率不足。

#### 解决方案：计算图分桶（Bucketing the Graphs）

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/16.webp)

> :mdnice-bold-italic[为缓解静态计算图的局限性，shadowAttn 在离线阶段生成多个计算图，并按“桶”缓存，供在线推理时动态选择]。具体设计如下：

::: block-1
- **桶的定义**：一个桶包含“相同缩放因子、不同形状”的多个计算图。其中，$\lambda^Q$、$\lambda^K$ 分别表示 Q、K 的缩放因子，$\lambda = \langle \lambda^Q, \lambda^K \rangle$ 为 Q·K 计算图的核心参数（缩放因子对）；“形状”主要指头部维度（移动设备上几乎无批量输入，序列维度因现代 Transformer 的分块推理特性[63]也固定）。
- **离线阶段：生成桶**：在校准语料库上分析缩放因子的平均值 $\bar{\lambda}$，生成多个缩放因子对的桶，形式为 $\langle \bar{\lambda}^Q / \sigma, \bar{\lambda}^K / \sigma \rangle, \dots, \langle \bar{\lambda}^Q \cdot \sigma, \bar{\lambda}^K \cdot \sigma \rangle$（其中 $\sigma$ 为步长，默认 5e-1，详见 5.2 节）。每个 Q·K 计算图不含权重，仅占用 10-100 KB 内存，缓存多个桶的内存开销可忽略。
- **在线阶段：选择桶与图**：对于输入的 Q、K 张量，首先计算其缩放因子对 $\langle \lambda^Q, \lambda^K \rangle$ 与每个桶的 $\lambda$ 的均方误差（MSE）；选择 MSE 最小的桶（即缩放因子最匹配的桶），再从桶中选择形状与输入匹配的计算图，用于后续推理。
:::

该设计通过“分桶”为静态计算图注入动态适应性，确保 NPU 估计阶段的精度。

### 3.4 基于注意力头部的 NPU-CPU/GPU 流水线（Head-Wise NPU-CPU/GPU Pipeline）

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/02.webp)

#### 流水线设计的核心背景

考虑 shadowAttn 动态稀疏注意力的执行流程：图 9 以两个头部为例，每个头部需依次执行三个步骤——NPU 估计（蓝色部分）、CPU/GPU top-k 选择（橙色部分）、CPU/GPU 稀疏 QKV 计算（绿色部分）。形式化表示为：若用 $\zeta_{npu}^i$、$\zeta_{topk}^i$、$\zeta_{qkv}^i$ 分别表示第 i 个头部的三个步骤，则执行依赖关系为：

$$
\zeta_{npu}^i \leftarrow \zeta_{topk}^i; \quad \zeta_{npu}^i, \zeta_{topk}^i \leftarrow \zeta_{qkv}^i, \quad \forall i \in n
$$

其中，“←”表示依赖关系（如 $\zeta_{topk}^i$ 需在 $\zeta_{npu}^i$ 完成后执行，$\zeta_{qkv}^i$ 需在 $\zeta_{npu}^i$ 和 $\zeta_{topk}^i$ 均完成后执行）。

若按“逐个头部、顺序执行”的朴素方式（图 9(1)），会忽略多项关键优化机遇。shadowAttn 基于以下洞察设计流水线：

##### 洞察 1：操作重叠（Overlapping）

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/02.webp)

- $\zeta_{npu}^i$（NPU 估计）和 $\zeta_{qkv}^i$（CPU/GPU 稀疏计算）均为**计算密集型操作**，而 $\zeta_{topk}^i$（CPU/GPU top-k）为**内存密集型操作**；
- 且 $\zeta_{npu}^i$ 在 NPU 上执行，$\zeta_{topk}^i$ 和 $\zeta_{qkv}^i$ 在 CPU/GPU 上执行——两者无硬件资源竞争。

因此，根据上述依赖关系，若 $\zeta_{npu}^i$、$\zeta_{topk}^j$、$\zeta_{qkv}^k$（i、j、k 为不同头部）无依赖，可并行执行:mdnice-bold-italic[。如图 9(2)所示，通过三阶段流水线重叠这些操作，可显著降低端到端延迟。]

##### 洞察 2：NPU 内核融合启动（NPU Kernel Fused Launch）

NPU 专为高吞吐量稠密运算设计，若对单个头部单独启动内核，会导致 NPU 计算单元（如 IDU）利用率不足。例如：在 MI14 上，Q=[1,1,128,64]、K=[1,1,2048,64]（BHSD 布局）的 Q·K 计算图：

::: block-1
- 单个头部执行需 2 毫秒；
- 融合 2 个头部或 4 个头部后，仅需 3 毫秒或 4 毫秒。 同时，由于缩放因子桶的数量有限（如 5.2 节所示，少量桶即可满足需求），存在大量共享相同缩放因子的头部——*这些头部可被“融合启动”，进一步提升 NPU 利用率。*
:::

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/02.webp)

如图 9(3)所示，头部 1 和头部 2 因缩放因子相同被融合，流水线延迟进一步降低。

##### 洞察 3：重排序执行（Reordered Execution）

由于依赖关系，流水线中会存在“气泡”（空闲时间）；而每个头部的稀疏率不同（导致各步骤耗时不同），因此头部的执行顺序会影响气泡大小。**合理的顺序可“挤压”更多气泡，降低延迟**。如图 9(4)所示，先执行头部 2 再执行头部 1，相比原顺序进一步减少了延迟。

#### 流水线调度策略（Pipeline Planning Policy）

shadowAttn 的流水线整合了上述三项优化，但该流水线的调度问题具有 O(n!)时间复杂度（NP 难问题），无法在移动端实时求解。为此，shadowAttn 采用**多项式复杂度的贪心搜索算法** （如算法 1 所示），核心思路如下：

::: block-1
1. 调度初始阶段，先对共享相同缩放因子的头部执行“融合启动”（算法 1 第 15 行）；
2. 每个调度步骤中，选择当前能最小化流水线延迟的 $\zeta_{npu}^i$、$\zeta_{topk}^i$、$\zeta_{qkv}^i$ 组合（基于离线阶段测得的各步骤开销）；
3. 贪心搜索的每一步均以“当前延迟最小”为目标，避免全局最优解的高复杂度。
:::

该调度策略在移动端的在线开销可忽略（如 MI14 上耗时<1 毫秒），各步骤的开销来自 3.1 节提到的离线轻量级分析。

## 四、实现

我们使用 10000 行 C++/Python 代码（LoC，Lines of Code）实现了 shadowAttn 的原型。我们选择搭载高通（Qualcomm）系统级芯片（SoC）的商用现成智能手机——小米 14（MI14）和红米 K60 冠军版作为测试平台，shadowAttn 同样可在其他主流移动设备上运行。**我们仅使用 ARM CPU 的一个中核（mid core）作为可用的最小 CPU/GPU 资源，其他计算则完全在 NPU 上执行。**

- NPU 的软件栈基于高通骁龙（Snapdragon）NPU 的 QNN SDK [6]和 Hexagon SDK [2]构建；
- CPU/GPU 的软件栈则包含 ARM NEON [1]、OpenCL [5]以及 LLVM 生态系统 [3]，以保留动态图执行等最大程度的运行时灵活性。
- 我们将旋转位置编码（RoPE，Rotary Position Embedding）[50]、量化（quantization）、矩阵乘法（matmul）和 softmax 等多个操作融合到一个内核（kernel）中，以最小化冗余的内存拷贝（memory copy）操作。此外，我们将这些操作中一些非敏感指令（如内部乘法运算）进一步用半精度（half precision，如 FP16）执行。

> shadowAttn 与所有主流的端侧 LLM 推理库兼容。只需直接包含一个头文件（header file）即可将其集成到现有库中，对原始代码库的侵入性（intrusiveness）最小。

在后续的:mdnice-bold-italic[端到端实验中，我们选择了高性能框架 llm.npu] [63]——该框架的非注意力操作可在 NPU 上运行。据我们所知，这是目前唯一完全开源且可在 NPU 上运行的框架。

::: block-1
- 具体而言，**我们在预填充阶段（prefilling stage）用 shadowAttn 及其基线模型替换了原有的注意力算子** （attention operator）；
- 而在解码阶段（decoding stage），由于该阶段主要受内存限制，**我们直接在 CPU/GPU 上采用全注意力（full attention）计算。**
:::

- **数据集（Datasets）**：我们在以下三类数据集上测试 shadowAttn：
- **基线模型（Baselines）**：:mdnice-bold-italic[我们将 shadowAttn 与以下四种设计方案进行对比，所有方案均使用完整的 NPU 资源]，但 CPU/GPU 资源高度受限（仅使用一个 CPU 中核）：

4. **NPU 全注意力（NPU-Full）**：在 NPU 上运行 8 位整数（INT8）精度的全注意力计算，采用静态图（static graph）和逐张量量化（per-tensor quantization）[67]。
:::

- **实验设置（Settings）**：在后续实验中，我们将全局稀疏率（global sparsity ratio）设为 20%，尺度桶（scale buckets）数量设为 9（步长为 5e-1）。选择这些参数的理由将在 5.2 节详细说明。:mdnice-bold-italic[LLM 推理的默认可用 CPU/GPU 资源设为一个 CPU 中核。]

### 5.1 端到端性能

#### shadowAttn 的准确性

首先，我们在上述数据集和模型上对比了 shadowAttn 与其基线模型的准确率。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/19.webp)

> 如表 6 所示，相较于无精度损失的基线模型 C/G-Full**，shadowAttn 是准确率最高的方案，平均仅损失 0.4 个百分点**。

这得益于 shadowAttn :mdnice-bold-italic[精心设计的动态稀疏机制——尤其是细粒度的令牌级估计（fine-grained token-level estimation）和头特异性稀疏率（head-specific sparsity）]。其他基线模型相较于 C/G-Full 均表现出显著的精度损失，分别为 7.4、11.4 和 18 个百分点。

原因是多方面的：

::: block-1
- 根本原因在于稀疏性会给模型引入更多噪声，对于紧凑的端侧 LLM 和信息密度高的数据集而言尤其明显；
- 对于 C/G-Block-Sparse，块稀疏性（blocked sparsity）会导致模型更容易忽略重要令牌；
- 对于 NPU-Full，静态图和逐张量量化的局限性会导致精度下降，尤其是在注意力算子中——其输入为波动较大的激活值。
:::

#### shadowAttn 的速度

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/20.webp)

> 如图 10 所示，我们首先报告了小米 14 上注意力内核（attention kernel）的延迟。我们测试了不同输入长度（1024/2048/4096）下的内核性能，输入张量的值随机生成，每个注意力头的稀疏率设为全局稀疏率。

实验观察如下：

::: block-1
- :mdnice-bold-italic[相较于无精度损失的基线模型 C/G-Full，shadowAttn 的速度提升最高达 6.9 倍，平均提升 3.5 倍；]
- :mdnice-bold-italic[相较于有精度损失的基线模型，shadowAttn 的速度提升最高达 4.0 倍]。需注意的是，根据表 6，采用这些有精度损失的基线模型进行推理会导致显著的准确率下降。
:::

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/19.webp)

> 我们进一步报告了:mdnice-bold-italic[将 shadowAttn 及其基线模型集成到第三方框架后的端到端延迟]。

通过这种集成，我们**可实现 NPU 中心化推理** （NPU-centric inference），具体细节见第 4 章。实验在三个数据集上进行——这些数据集的输入序列对推理过程起主导作用（预填充阶段的输入长度分别为 3840/4096/1792，解码阶段的输入长度分别为 50/10/10），这是移动设备上最常见的工作负载模式（workload pattern）。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/21.webp)

结果如图 11 所示：

::: block-1
- :mdnice-bold-italic[相较于无精度损失的基线模型] C/G-Full，shadowAttn 的**端到端速度提升最高达 4.5 倍，平均提升 2.9 倍；**
- :mdnice-bold-italic[相较于有精度损失的基线模型]，shadowAttn 的**速度提升最高达 4.0 倍。**
:::

我们简要分析实验结果背后的原因：

- 对于 C/G-Sparse，尽管其稀疏率为 20%，但相较于 C/G-Full，其速度提升相对较低，这是因为估计待稀疏化位置和 Top-K 操作（选择前 K 个重要元素的操作）会带来额外开销；
- 对于 C/G-Block-Sparse，其速度提升更高，原因是通过对 Q 和 K 输入张量进行预池化降低了估计阶段的开销；
- 对于 NPU-Full，尽管 NPU 在矩阵乘法上具有高吞吐量，但 softmax 和掩码（masking）等操作会在一定程度上降低速度提升。

> 相比之下，shadowAttn 实现了最高的速度提升，这是因为它通过将估计阶段卸载到 NPU以及让 NPU 与 CPU/GPU 的执行过程重叠，最大限度地减少了估计阶段的开销。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/22.webp)

此外，与最先进的 NPU 框架 llm.npu 的原生注意力（native attention）相比，shadowAttn 在 CPU/GPU 资源显著减少的情况下，实现了相当甚至更低的延迟。:mdnice-bold-italic[llm.npu 支持两种注意力计算方式：在 4 个 CPU 核心（1 个大核 prime core +3 个中核）上运行全注意力，或在 GPU 上运行全注意力]，**而 shadowAttn 仅使用一个 CPU 中核，就能实现最高 3.0 倍的延迟降低。**

### 5.2 敏感性分析与消融实验（Sensitivity Analysis and Ablation Study）

#### 全局稀疏率

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/25.webp)

> 我们在图 13 中展示了稀疏率的敏感性分析结果。

::: block-1
- 将全局稀疏率设为 20%是合理的选择：
- 稀疏率过高（如 30%、40%、50%）时，延迟降低幅度较小；
- 稀疏率过低（如 5%、10%）时，会导致显著的精度损失。
:::

20%是维持无精度损失的最小稀疏率，即“拐点（knee point）”。**因此，shadowAttn 将 20%设为默认全局稀疏率，这也与第 3 章中的分析一致。**

#### 尺度因子桶

回顾可知，我们在 NPU 上缓存了用于 Q·K 计算的多种尺度的子图（subgraphs）。shadowAttn 的默认设置为：桶数量 9 个，步长 5e-1。

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/26.webp)

> 更多的桶会提供更细粒度的权衡空间（tradeoff space），从而带来更高的准确率（如图 14a 所示，桶数量从 5 增加到 9 时准确率提升）。

但:mdnice-bold-italic[桶数量的边际效应（marginal effect）明显——增加更多桶几乎不会带来性能提升，因此通常选择 9 个桶即可]。

图 14b 解释了为何选择 5e-1 作为步长：**其他数量级的步长会导致显著的性能下降**。有趣的是，**极小的步长（如 5e-3）虽能减少精度损失，但损失仍显著**。这主要是因为这种步长设置会导致所有样本都落入原始桶中——其他桶的尺度因子要么过大要么过小，无法匹配输入数据的尺度。

综上，shadowAttn 对桶的默认设置是合理的，可实现最佳性能。

#### 可用 CPU/GPU 资源

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/27.webp)

回顾可知，我们的默认设置是将可用 CPU/GPU 资源设为 ARM CPU 的一个中核。**我们在图 15 中通过将资源映射到不同计算能力的核心** （小核、中核、大核），**测试了资源变化对性能的影响。** 实验在小米 14 上进行——该设备包含 1 个大核、5 个中核和 2 个小核。

实验结果显示：

::: block-1
- 首先，shadowAttn 始终优于 C/G-Full；
- 其次，当计算资源增加时（如从小核到中核再到大核），shadowAttn 的绝对推理延迟也会降低，表现出较强的可扩展性（scalability）。
:::

总体而言，shadowAttn 在不同计算资源条件下都是一种稳健的解决方案。

#### 消融实验

![文章插图](/articles/2025-09-06-4-5-soc-shadowattn-token-75810339/images/28.webp)

> 我们通过逐步移除 shadowAttn 的关键设计模块来进行消融实验，结果如图 16 所示。

- 当移除流水线（pipeline）设计时，端到端延迟显著增加——这是**因为流水线实现了 NPU 与 CPU/GPU 延迟的重叠（overlapping）。**
- 在此基础上，若进一步移除尺度因子桶设计，准确率会明显下降（1.2 个百分点）——这是**因为桶帮助 NPU 更好地适应输入范围。**
- 再进一步，若让所有注意力头共享相同的全局稀疏率，准确率会从 60.1 个百分点降至 52.8 个百分点，原因是**忽略了每个头的内在重要性** （intrinsic importance）。
- 最后，若取消 CPU/GPU 上的稀疏计算设计，直接将全注意力卸载到 NPU，准确率会降至 34.8 个百分点，延迟增至 0.6 分钟——这是因为 **shadowAttn 不得不承受 NPU 上的量化损失（quantization loss），且 NPU 对稀疏计算的支持较差。**

> 综上，shadowAttn 的每个设计模块都对其性能有重要贡献，不可或缺。

## 六、相关工作

### 6.1 设备端大语言模型推理

在设备上运行移动大语言模型（LLMs）[11,26,28,34,51,55,77,78]已成为实现隐私保护型移动智能[14,27,38,41,49]的关键研究方向。目前已有多款主流框架，例如：

::: block-1
- :mdnice-bold-italic[HeteroLLM [16]提出了一种面向移动系统级芯片的 GPU/NPU 协同大语言模型推理框架，该框架优化了内存拷贝效 率]。然而，其注意力机制及部分多层感知机运算仍在 GPU 上执行——而 GPU 在移动设备使用过程中常处于高负载状态（如运行游戏、视频渲染等任务）。
- 与 HeteroLLM 类似，llm.npu [63]同样将注意力机制部署在 CPU/GPU 上，无法实现以 NPU 为核心的推理模式。
- **PowerInferV2 [67]则在 NPU 上执行稠密注意力机制** （即本文中的“NPU-Full”基线方案），但与 shadowAttn 相比，**该框架不支持稀疏注意力机制**；更严重的是，其仍会因注意力机制量化导致精度下降，尤其在移动尺寸大语言模型（如参数量为 0.5B~1.5B 的模型）和移动智能体任务中表现更为明显。**PowerInferV2 的核心研究重点是扩展移动设备的内存（RAM），以运行对注意力量化具有更强鲁棒性（即量化后精度损失更小）的大规模大语言模型**。
- 与 PowerInferV2 类似，QNN [6]也在 NPU 上执行完整的注意力机制运算，面临相同的精度下降问题。
:::

此外，还有部分框架将注意力机制与非注意力机制运算均部署在 CPU/GPU 上，例如：

::: block-1
- MLC-LLM [37]和 TFLite [54]在 GPU 上运行大语言模型
- 而 Llama.cpp [21]则在 CPU 上运行大语言模型。
:::

shadowAttn 通过仅在 CPU/GPU 上对重要令牌执行稀疏运算，实现了当前精度最高、效率最优的以 NPU 为核心的推理方案。

### 6.2 高效稀疏注意力机制

固定模式稀疏注意力机制[23-25,59]需在离线阶段（模型部署前）确定一种预设的稀疏模式，常见模式包括滑动窗口（仅关注当前令牌附近的局部令牌）、Λ 形和竖线形等。**与这类特定的固定模式相比，shadowAttn 的动态注意力机制是上述模式的超集。**

**块稀疏注意力机制** [53,66,69,75]会先对 Q（查询向量，代表当前令牌的查询信息）和 K（键向量，代表所有令牌的特征信息）进行池化操作，再在粗粒度的块级别选择 top-k（前 k 个重要性最高的）区域。如前文所述，:mdnice-bold-italic[这种模式精度较低——保留或丢弃整个块可能会遗漏块内的重要令牌，而 shadowAttn 的细粒度稀疏注意力机制（基于单个令牌的重要性选择）精度显著更高。]

近年来，还出现了:mdnice-bold-italic[训练原生稀疏注意力机制的研究趋势[33,74]，这类方法通过在模型训练阶段引入稀疏约束，使注意力机制在推理阶段天然具备稀疏性]。然而，其学习到的稀疏性无法直接迁移到下游任务（如文本摘要、API 调用等具体任务）和微调模型中，且预训练过程需消耗大量计算资源（如多块高端 GPU 长时间运行），并非所有开发者都能负担。**相比之下，shadowAttn 的稀疏注意力机制具有“即插即用”特性。**

### 6.3 移动智能

移动智能旨在边缘/移动设备上运行深度神经网络（DNNs），尤其是基础模型，以实现对人类/环境的感知或与信息物理系统的交互[13,30,39,62,64,65,68,71-73]。借助 shadowAttn 的以 NPU 为核心的推理方案，基础模型的执行过程将更具透明性，且对人类和环境的干扰更小。

## 七、结论

> 本文提出了 shadowAttn——一种面向**以 NPU 为核心的设备端大语言模型推理的稀疏注意力模块。**

该模块集成了多种创新技术，包括基于 NPU 的令牌重要性估计、NPU 计算图分桶（bucketing，将不同参数的计算图分类存储以适配动态输入的技术）以及 NPU-CPU/GPU 流水线（pipeline，使不同硬件的运算并行执行以降低 latency 的技术）。

在最大限度减少对 CPU/GPU 资源依赖的同时，shadowAttn 实现了无损（losslessly）性能提升，**端到端推理速度最高可达 4.5 倍。**
