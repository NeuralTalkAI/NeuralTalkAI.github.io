## 一、问题定义：长程自主开发的三道坎

> :mdnice-bold-italic[自主开发相比仓库级修 Bug 是性质不同的问题：修 Issue 有明确终点，但是从零造系统要求 Agent 自己翻译需求、协调组件、持续调试不断演化的系统，轨迹一长，三类失效模式就会集体出现]，这里三类问题我们会在下文 1.2 讲到👀。

论文先用下图划清两种开发模式的边界，再把长程开发的困难形式化为三条具体挑战，这三条挑战恰好一一对应 HoH 后续的三个设计决策。

![文章插图](/articles/2026-09-19-harness-of-harness-frontierswe-27-0ac7896f/images/05.jpg)

::: image-caption图 2：两种软件开发模式对比。左半部分为人在环中开发，编码Agent在人的持续监督、指导、评审和干预下生成代码；右半部分为自主软件开发，Agent无需人的指导与干预，独立把高层需求转化为完整、可用、可部署的软件系统。延伸来看，这张图的本质是把人的两类动作，观察报错与重新下达指令，从人类工程师手里收编进框架本身；HoH收编的正是人类在回路中承担的调度与验收职能，编码模型本身一行未换。
:::

### 1.1 从人在环中到完全自主

今天绝大多数编码 Agent 仍活在人在环中模式里：人定任务、人盯过程、人审代码、人在报错时把 Agent 重新拉起。然而，**上图 2 右侧的自主模式只接收一份高层需求，就要从零交付完整、可运行、可部署的系统。**

### 1.2 形式化定义与三大挑战

> 论文把任务写成一个简洁的映射。给定软件规格说明 $\mathcal{S}$，端到端开发的目标是构造出满足其功能与质量要求的完整软件制品 $A$；令 $M$ 为语言模型、$H$ 为模型与开发环境之间的编码 Harness，HoH 做的事情可以写成：

$$
\operatorname{HoH}_{M,H}:\mathcal{S}\longmapsto A
$$

其中 $\mathcal{S}$ 是那份只描述产品需求的规格文档，$A$ 是最终交付的软件，$M$ 与 $H$ 在一次运行中全程冻结、不随迭代更换。:mdnice-bold-italic[打个比方，$\mathcal{S}$ 是甲方给的一页纸需求书，$A$ 是最终交房的楼盘，$M$ 是施工队的手艺，$H$ 是工地的脚手架与塔吊，HoH 则是不换施工队、不换设备，只负责排工期、做监理的项目部。]

有了问题的形式化定义，作者又把长程开发的困难归纳为三条，每一条都对应后续一个具体设计。

| 长程开发困难 | 说明 |
| --- | --- |
| 状态遗忘 | 早期需求、设计决策、见过的故障、已验证过的行为，会在超长轨迹中与后续改动脱节。 |
| 下一步欠定 | 高层规格无法直接告诉你这一步该改哪里，局部合理的改动可能与既有行为冲突，反复检查与修补还会空耗轮次。 |
| 质量难观测 | 功能与质量要求散落在大量场景化行为里，缺失或错误很容易漏检，于是半成品被当成成品验收。 |

### 1.3 学术坐标：HoH 站在哪条路线上

> Harness 是决定模型能看到什么信息、能执行什么动作、执行结果如何回流下一轮决策的运行时操作层。近期研究工作分为两类：

- **一条研究路线是将 Harness 本身当作优化对象**，例如 AutoHarness 从环境反馈合成代码 Harness、Meta-Harness 搜索 Harness 代码、Self-Harness 让 Harness 诊断并修改自身；
- **另一条线是多智能体软件开发**，MetaGPT、ChatDev 用预设角色流水线生成软件，AgileCoder、EvoDev 按冲刺组织增量，EvoMAC 用测试反馈调整协作流。

:mdnice-bold-italic[HoH 与这两条线都不同：它不修改底层 Harness 一行代码，也不预设僵化的角色流水线，HoH 只把一个固定的 Harness-模型组合反复调用，让一个不断演化的真实软件项目在规划、实现、独立验收的循环中持续前进。] 作者特别指出，当前主流编码 Harness 通常仅在单个有界 Episode 内开展开发，难以跨版本持续保存项目决策、已验证功能及评估依据——而这正是 HoH 的核心补位所在。

::: block-1总之，:mdnice-highlight[自主软件开发的难点是在超长轨迹上维持连贯进展：遗忘、欠定、漏检三道坎，单靠拉长单次会话跨不过去，必须在 Harness 之上再建一层负责调度、记忆与独立验收] 的编排结构，而且这层结构不能换模型、不能改底层 Harness。
:::

## 二、总体架构：双状态通道与三角色闭环

> 作者提到，后续循环要继承的信息，只有最新一版代码是不够的，只拿到代码的 Agent，等于每次都要从施工现状反推全部施工历史。**HoH 为了达到这一目的，其策略可以拆成两层来看：跨轮之间靠两条状态通道传递记忆，单轮内部靠三个分权角色完成一次增量交付。**

### 2.1 跨循环的两条状态通道

HoH 在循环边界同时维护两类状态。

- **制品状态 $A_t$** 是第 $t$ 轮结束后的软件本体，:mdnice-bold-italic[包含源码、配置、资源与项目元数据，回答软件现在是什么；]
- **证据状态 $\mathcal{E}_t$** 是把 $A_t$ 对照规格与本轮开发目标评测后得到的执行证据，:mdnice-bold-italic[记录哪些行为已验证、哪些声明缺乏支撑、哪些故障仍待处理，回答下一步该怎么改。]

初始时工作区为空 $A_0$、证据为空 $\mathcal{E}_0=\emptyset$，跨轮转移写成：

$$
(A_{t-1},\mathcal{E}_{t-1})\xrightarrow{\text{loop }t\text{ under }\mathcal{S}}(A_t,\mathcal{E}_t)
$$

式中 $A_{t-1}$ 与 $\mathcal{E}_{t-1}$ 是上一轮留下的制品与证据，箭头表示在固定规格 $\mathcal{S}$ 约束下执行第 $t$ 轮，产出新的一对状态。

::: block-1举例来说👀：开发平台跳跃游戏时，$A_{t-1}$ 是上一版能跑但没有二段跳的工程，$\mathcal{E}_{t-1}$ 写着移动已验证、跳跃手感缺失、结算界面不存在。

**为此，我们可以让 Project Planner 负责设定优先级，Developer 负责实施变更，QA 则基于新产出开展验证并生成新证据——这三个角色分别对应后文图 3 中的几个角色**。其协作逻辑在于：:mdnice-highlight[制品的连续性保障开发以增量方式推进，而证据驱动的目标选择则确保开发以迭代方式演进。]
:::

### 2.2 三角色分权：定什么、怎么做、成不成

> 换言之，**增量关注“做多少”——通过持续交付可运行的制品片段，逐步累积完整功能；迭代关注“做什么”——依据实证反馈（如 QA 生成的新证据）动态校准目标与范围，使每次开发都更贴近真实需求与质量要求**。二者协同，既避免大块交付的风险，又防止盲目演进的偏差。

角色间职责清晰、反馈闭环：Planner 定方向，Developer 落实现，QA 提证据，证据再反哺 Planner 调整下一轮优先级——形成可持续、可验证、可调整的交付节奏。这就引出了 Harness-of-Harness 总体架构，如下图所示。

![文章插图](/articles/2026-09-19-harness-of-harness-frontierswe-27-0ac7896f/images/06.jpg)

::: image-caption图 3：Harness-of-Harness总体架构。HoH围绕不断演化的软件制品，反复调用项目规划者、开发者与QA测试者；确定性Runtime冻结每个角色的输入、强制其权限、把证据绑定到被测候选版本，并记录项目状态；模型、底层Harness、角色定义与运行时策略在一次运行内固定，演化的只有开发文档、软件制品与执行证据。具体来说，图上方规划阶段把未解决缺口转为优先任务、把已验证行为转为保护约束、把任务规格转为验收要求；左侧证据化测试用白盒加黑盒双通道；右侧工具链与技能按角色挂载。整条闭环里流动的是三类物化产物，开发文档 $D_t$、制品 $A_t$、证据包 $\mathcal{E}_t$，这正是HoH能跨轮不失忆的物质基础。
:::

论文指出，产出一个经验证的增量需要三种性质完全不同的决策：

- 下一步改什么，需要项目全局视角；
- 怎么实现，需要写权限与局部技术自主权；
- 做成没有，需要独立于实现者自述的判断。

> HoH 把这**三件事分别授予 Project Planner、Developer、QA Tester，且三个角色由同一个固定的 Harness-模型组合各调用一次**，顺序固定为规划、开发、测试。:mdnice-bold-italic[一次迭代在实现层面对应三次 Harness 调用，可以写成：]

$$
D_t=\operatorname{Plan}_{H}(\mathcal{S},\mathcal{E}_{t-1}),\quad A_t=\operatorname{Dev}_{H}(A_{t-1};\mathcal{S},D_t),\quad \mathcal{E}_t=\operatorname{Test}_{H}(A_t;\mathcal{S},D_t)
$$

其中 $D_t$ 是第 $t$ 轮的开发文档，由规划者综合固定规格与上一轮证据产出；开发者从 $A_{t-1}$ 热启动实现 $D_t$；测试者对着 $\mathcal{S}$ 与 $D_t$ 独立验收 $A_t$。

需要注意的是，规划者只读 $A_{t-1}$ 作为实现上下文、无权改代码，测试者只拿到冻结的只读副本，全工程只有开发者一个写者，作者称之为单一写者边界（single-writer boundary）。

### 2.3 算法主循环与 Runtime 契约

> 整套机制被压缩成七行伪代码，输入是规格、空制品与迭代预算 $T$，固定项是模型、Harness 与角色契约，输出是最终制品 $A_T$。

![文章插图](/articles/2026-09-19-harness-of-harness-frontierswe-27-0ac7896f/images/07.png)

::: image-caption算法 1：Harness-of-Harness主流程。输入为规格 $\mathcal{S}$、初始制品 $A_0$ 与迭代预算 $T$，固定模型 $M$、Harness$H$ 与角色契约；第 $t$ 轮先由规划者产出开发文档 $D_t$，再由开发者产出新制品 $A_t$，最后由QA测试者结合Runtime.check的确定性构建检查产出证据 $\mathcal{E}_t$，循环 $T$ 次后返回 $A_T$。read_only标注是算法层面的关键细节：规划与测试拿到的都是只读视图，写权限在语法层面就被收敛到开发者一处；Runtime.check则把能否构建、能否启动这类确定性检查从模型主观判断中剥离，成为机器兜底的硬门。
:::

在工程实现上，Runtime 是一份确定性契约：控制每次调用的输入、可用工具与写操作、必须满足的输出 Schema；角色提示词只说明职责与产物格式，不规定推理过程与工具序列，Schema 不合规直接重试。

作者把这条原则概括为约束可验证产出。**HoH 没有独立记忆模块，采用渐进式披露（progressive disclosure）：**

- 计划、报告、历史全部落盘，先暴露精简索引，相关时再调取细节；工具按角色组织，配轻量 Markdown 技能按需指导；
- 项目历史在角色级与迭代级双重版本化，重大回归时可退回已验证状态。

::: block-1整体看下来，HoH 的架构骨架就是:mdnice-highlight[两条状态通道加三个分权角色：$A_t$ 管代码累积，$\mathcal{E}_t$ 管经验累积；规划者定做什么、开发者决定怎么做、测试者独立判定成没成，再用确定性 Runtime 把权限、Schema 与回滚全部钉死，让自治只发生在边界之内。]
:::

## 三、单循环实现：把增量做小、把验收做硬

> **一个 HoH 循环要同时回答三个问题：这轮改哪里、怎么改出来、凭什么算改好**。论文分别用有界规划、测试左移与冻结候选三套机制作答。本章进入工程细节，看规划者、开发者、测试者各自的输入输出契约，以及证据如何被结构化成下一轮可以直接消费的格式。

### 3.1 项目规划：有界且局部完整

Project Planner 要调和规格 $\mathcal{S}$ 与上一轮证据 $\mathcal{E}_{t-1}$，同时把 $A_{t-1}$ 当实现上下文来读，但没有修改权，最终产出开发文档 $D_t$。

论文对增量提出两条成对的标准：

- **有界（bounded）** 限制一轮内被改动的无关行为，让实现与诊断保持可控；
- **局部完整（locally complete）** 要求所选能力包含让它真正能跑、能测的全部关联改动。

增量的边界由一条可观察的连贯行为定义，与改了多少个文件无关；无关重构与顺手扩功能被明确挡在本轮之外。$D_t$ 里装着一小组相关任务、必须保护的既有功能、以及可观察的验证条件，至于用什么算法、什么工具实现，交给 Developer 自主决定。

### 3.2 制品开发：单一写者与测试左移

::: block-1开发者从制品 $A_{t-1}$ 热启动，在现有工程结构上延展，每轮结束产出 $A_t$。

测试直接被编织进开发过程：动手前先为目标行为建立基线，每次有意义的改动后立刻重跑对应路径，检查受影响实现、运行结果与邻近回归面，这也称为软件工程里的测试左移（shift-left testing），让故障在离诱因最近的地方暴露。
:::

:mdnice-bold-italic[开发者自测与独立验收回答的是两个问题：自测只用于判断自己有没有资格提交候选、修复自己工作中撞上的故障，它不能证明产品需求已被满足；开发者的完成声明只是后续独立验收的一项输入，验收权保留在 QA 阶段。] 这套玩儿法，和真人无异👀。

### 3.3 独立质量保证：冻结候选与声明-证据绑定

> **QA Tester 拿到的是冻结的只读候选 $A_t$，外加确定性构建与运行检查结果**。冻结有两层用意：采证期间实现无法再变，每条观察都绑定唯一候选版本，杜绝把不同版本的行为拼出一份合格报告；只读权限则防止测试者边测边偷偷修掉自己本该上报的缺陷。

测试准则从 $\mathcal{S}$ 与 $D_t$ 现场派生。

- 黑盒测试从普通输入与渲染输出入手，考察用户可观察行为、状态转移与端到端流程；
- 白盒测试检查源码、配置、资源绑定、运行时状态与日志，用于定位故障、佐证那些单看输出无法判断内部条件的行为。

论文把这套采证过程形式化为声明-证据记录：

$$
\mathcal{C}_t=\operatorname{Claims}(\mathcal{S},D_t),\quad r_i=\operatorname{Observe}(A_t,c_i),\quad s_i=\operatorname{Assess}(c_i,r_i)
$$

$$
\mathcal{E}_t=\{(c_i,r_i,s_i)\}_{c_i\in\mathcal{C}_t}
$$

其中 $\mathcal{C}_t$ 是从公开需求、本轮目标、保护约束与验证要求实例化出的可检查声明集合，$c_i$ 是其中第 $i$ 条声明，$r_i$ 是针对它采集的公开执行记录，$s_i$ 是归一化后的 QA 状态，三元组 $(c_i,r_i,s_i)$ 就是一条带证据的结论。**以玩家移动为例，声明是玩家输入能改变角色运动，记录包含一份按键回放文件与一份位置变化的运行时轨迹，两者都支持，状态才判为 verified**。证据进一步被切成互不相交的两半：

$$
\mathcal{E}_t=\mathcal{E}_t^{\mathrm{ver}}\cup\mathcal{E}_t^{\mathrm{gap}},\qquad \mathcal{E}_t^{\mathrm{ver}}\cap\mathcal{E}_t^{\mathrm{gap}}=\emptyset
$$

$\mathcal{E}_t^{\mathrm{ver}}$ 只收录有可见证据支撑的声明，它们在下一轮自动变成保护约束；观察到的故障、未满足需求、回归风险与证据不足项全部进入 $\mathcal{E}_t^{\mathrm{gap}}$，变成下一轮的更新目标与复验要求。源码里写了相关代码，在这套体系里不算行为验证。

### 3.4 评估隔离：隐藏信息绝不回流

还有一条容易被忽视但极其重要的设计：基准评测与开发过程物理隔离。隐藏测试、基准打分、私有评分细则、评测公式与评分理由，一律不进角色提示词、不进证据包、永不回流到后续迭代。

**HoH 只能对可观察的执行与 QA 发现做适应，公开任务规格始终是唯一权威需求源**。这保证了实验测到的是框架本身的持续改进能力，从而杜绝了 Agent 偷看标准答案后的刷分。

## 四、基准实验：三套 Harness、三大基准、三轮迭代

> :mdnice-bold-italic[论文选了三个差异极大的基准，分别考游戏从零构建、仓库级软件工程与程序洁净室重建，又故意选了三个能力档位不同的 Harness-模型组合，就是为了证明增益与底子强弱无关]。下面我们按主结果、维度拆解、预算对照、定性对比、消融实验的顺序展开。

### 4.1 实验设置与评分口径

- GameCraft-Bench 含 15 个游戏家族共 140 个任务，要求在真实 Godot 引擎里从自然语言规格造出完整可玩工程，作者分层抽样 45 个任务；
- FrontierSWE 覆盖从零实现、性能优化与研究型任务，17 个任务中因外部 API 与驱动限制评测 15 个，含 4 个实现、9 个性能、2 个研究任务；
- ProgramBench 只给编译好的可执行文件与文档，要求重建行为一致的代码库。

三套组合分别是 Codex CLI 0.142.5 配 GPT-5.5 高推理档、OpenCode 1.14.30 配 DeepSeek-V4-Pro、Pi 0.80.10 配 MiniMax-M3。对照组 Vanilla 只做一次标准开发，HoH@T 做 $T$ 轮闭环，主实验取 $T=3$。

> 其中，三个基准中的 GameCraft-Bench 基准的总分公式可以展开来看，它本身就体现了可运行门槛：

$$
\operatorname{Overall}=100B\,(0.15M+0.35D+0.15V+0.35A)
$$

式中 $B$ 是二值门，工程编译运行失败直接取 0、成功才取 1；$M$、$D$、$V$、$A$ 分别是核心机制、内容深度、功能视觉、美术呈现四个维度的平均 rubric 得分，权重依次为 0.15、0.35、0.15、0.35。这套权重等于宣告：能跑只是入场券，内容深度与美术呈现才是拉开差距的主战场，这也解释了后文 HoH 的增益来源。

### 4.4 预算对照：增益并非靠 Token 硬堆

> **一个必然的质疑是：多跑两轮当然更好，HoH 是否只是让 Agent 多干了几遍？** 论文用 Vanilla Continuation 做控制实验：同一模型同一会话，每轮只追加一句继续开发与测试当前游戏，既没有独立开发文档，也没有 QA 证据。

![文章插图](/articles/2026-09-19-harness-of-harness-frontierswe-27-0ac7896f/images/11.jpg)

::: image-caption表 2：GameCraft-Bench 基准下，相同开发轮次中 HoH 与重复 Vanilla 开发的效果对比。实验采用 Codex 搭配 GPT-5.5（高推理模式）；得分代表 45 项任务的 GameCraft-Bench 总体平均分，token 数为每项任务累计消耗的编码框架 token 均值。该对比实验排除了 “更多开发轮次” 这一混淆变量，证明 HoH 的增益并非单纯来自更多的模型调用。相同的 1、2、3 轮开发预算下，HoH 得分均显著高于重复 Vanilla 开发，3 轮时 HoH 取得 71.52 分，比 3 轮 Vanilla 的 58.24 分高出 13.28 分。同时 HoH@2 仅用 5.67M token 就超过了 3 轮 Vanilla 6.33M token 的效果，token 效率提升明显。这一结果验证了 HoH 的核心价值不在于增加开发次数，而在于通过规划 - 编码 - 测试的结构化分工与证据反馈，让每一轮开发都更有针对性，避免了重复 Vanilla 模式下的盲目修改与无效劳动。
:::

其中边际效率公式为 $\eta(c)=(\overline{s}_{\mathrm{GC}}(c)-\overline{s}_{\mathrm{GC}}(\mathrm{Vanilla}))/(\overline{C}(c)-\overline{C}(\mathrm{Vanilla}))$，分子是相对基线多拿的分，分母是相对基线多花的平均 Token，$\eta$ 就是单位推理预算换来的质量。**这个对照想表达的是：同样是重复劳动，没有规划与证据结构的会话续跑会把大量预算花在重复巡检与无效修补上。**

## 五、多日无人值守：70 轮迭代造出一款完整 FPS

> 基准只能回答三四轮内的分数问题，作者给 HoH 真正的压力测试是：一个固定组合连续跑好几天、七十轮，项目还能不能保持 coherent，也就是前后一致地长大。

### 5.1 Fusepoint 案例与自主边界

::: block-1
**案例作品 Fusepoint 是一款单人叙事型第一人称射击游戏，初始工作区里只有一份 PRD**。产品说明规定：五分钟单人拆弹任务，按顺序攻占两个控制点，在最终目标点完成三阶段拆弹，18 名敌人按 3、5、10 固定分布在三个交战区，成功引爆与拆弹成功各有独立分支。
:::

**HoH 要自己把这份规定翻译成可执行的 Godot 工程，自行选择、实现并评估每一步增量**。运行配置是 Codex CLI 配 GPT-5.6-Sol 高推理档，引擎为 Godot 4.7，通过 Godot MCP 操作引擎，另配资产生成、UI/UX 呈现、测试三类 Markdown 技能，外部素材全部来自 CC0、CC BY 等可复用许可并保留署名。:mdnice-bold-italic[到分析截止时共完成 70 轮，人的介入仅限于恢复网络或 API 可用性，规划、实现、调试、测试、验收全部由系统完成。]

### 5.2 三阶段开发动力学

![文章插图](/articles/2026-09-19-harness-of-harness-frontierswe-27-0ac7896f/images/14.png)

::: image-caption图 1：HoH连续迭代自主开发FPS游戏的全过程，上方曲线为未解决Issue数量趋势，下方蓝色与紫色栅条分别标记每轮新发现与关闭的Issue，沿时间轴标注了从初始灰盒到可玩构建的全部里程碑，横跨六天。这条曲线是全文最有说服力的一张图：第1至27轮是初始构建期，可执行骨架与核心交互通路成型，能力变多的同时可测面扩大、Issue积压同步抬升；第28至49轮是能力扩张期，新功能与诊断修复并行，局部改动开始牵动任务状态、战斗、界面与运行时；第50轮后进入稳定期，功能增速放缓、关闭Issue占上风，曲线冲顶后回落。到第70轮，81个记录Issue关闭65个、剩16个未决，另有17个Issue在关闭后因后续改动回归而重开。
:::

> 17 次的 issue 重开也说明几个问题。**长程开发中的回归不可避免，有趣的点在于 HoH 对回归发生后系统如何反应**：每一条 issue 重开记录同时带着失败行为与它上一次被验证通过的历史，:mdnice-bold-italic[回归修复因此成为下一轮规划里显式可见的工作项，无需从最新代码里逆向考古。]

::: block-1
