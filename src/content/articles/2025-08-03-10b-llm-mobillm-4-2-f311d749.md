> 大语言模型（LLM）在移动设备上的应用及其潜在应用总是令人着迷。然而，由于极高的内存需求和缓慢的训练速度，**在设备上进行 LLM 微调** 带来了巨大的挑战。

即使采用**仅更新一小部分参数的参数高效微调** （PEFT）方法，:mdnice-bold-italic[资源受限的移动设备也无法承受]。

::: block-1
在本文中，我们:mdnice-bold-italic[提出了 MobiLLM，通过服务器辅助的侧调优，在移动设备上实现高效内存的 Transformer LLM 微调]。具体而言，MobiLLM **允许资源受限的移动设备仅保留一个冻结的主干模型**，同时:mdnice-bold-italic[将可训练侧网络的内存和计算密集型反向传播 【卸载】到高性能服务器上。]

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/02.webp)

与现有的在冻结主干内保留可训练参数的微调方法不同，MobiLLM 从主干中分离出一组并行适配器，创建一个反向传播旁路，在:mdnice-bold-italic[前向传播过程中仅涉及从移动设备到服务器的单向激活传输]，并采用低比特量化。

通过**这种方式，数据永远不会离开移动设备**，同时:mdnice-bold-italic[【设备】可以避免通过本地主干模型进行【反向传播】，并且其【前向传播】可以与服务器端执行并行] 进行。因此，MobiLLM 在显著减轻 LLM 微调的内存和计算负担的同时，保护了数据隐私。
:::

通过大量实验，我们证明了 MobiLLM 能够使资源受限的移动设备，甚至是仅配备 CPU 的设备，对 LLMs 进行微调，并显著减少收敛时间和内存使用。

## 关键问题（TL;DR）

### Q1：MobiLLM 如何突破移动设备的内存和计算限制，实现 LLM 微调？

MobiLLM 通过“拆分训练+侧网络设计”突破限制：

- **任务拆分**
- **量化与轻量设计**
- **并行优化**

### Q2：MobiLLM 如何在实现跨设备协作的同时保护用户数据隐私？

MobiLLM 通过“数据本地化+激活值脱敏”实现隐私保护：

- **原始数据留存**：用户数据（如消息、评论）始终存储在移动设备，仅在本地执行主干模型前向传播，不向服务器传输原始数据。
- **传输内容脱敏**：仅向服务器发送量化后的中间激活值。这些:mdnice-bold-italic[激活值是主干模型的抽象特征表示，已脱离原始数据语义] （如底层特征为通用低维表示），且经 FP4/NF4 量化进一步降低可识别性，难以反推原始数据。
- **架构设计保障**：移动设备无需上传模型参数或优化器状态，仅通过单向传输激活值完成协作，避免敏感信息泄露。

### Q3：MobiLLM 在效率提升（内存/速度）与模型精度之间如何平衡？

MobiLLM 通过精细化设计实现效率与精度的平衡：

- **精度损失可控**：与全量微调（Full-FT）相比，平均精度下降约 2%，但通过 NF4 量化（而非 FP4）可进一步缩小差距（如 OPT-1.3B 用 NF4 量化时精度仅降 0.2%）。
- **效率显著提升**：内存 usage 降低 4 倍（如 OPT-1.3B 从 20.895GB 降至 4.487GB），训练收敛时间减少 2.3 倍，使移动设备（含 CPU-only）可稳定微调 billion 级模型（如 OPT-1.3B），突破硬件限制。
- **权衡逻辑**：:mdnice-bold-italic[精度损失主要源于量化激活值和侧网络简化，但实验证明该损失在实际任务（如 GLUE 基准）中可接受]，且远小于“无法在移动设备上微调”的功能性损失，因此是合理的工程取舍。

## 一、引言

基于 Transformer 的大型语言模型（LLM）的突破，如 BERT[8]、LLaMa[24]和 GPT[2]，为人工智能（AI）带来了重大进展。它们理解上下文和细微差别的能力使其能够有效处理自然语言处理（NLP）、计算机视觉（CV）等领域的各种任务。虽然 LLM 通常在大型数据集上训练以提供新兴的泛化能力，但**移动设备上来自私人和不可访问的个人数据（如用户评论和消息）的持续生成，往往与公开预训练的 LLM 分布存在差异**。这就:mdnice-bold-italic[需要在设备部署后进行微调，以定制个性化模型，同时确保数据保留在移动设备上。]

硬件的进步也在加速这一愿景的实现。现代移动设备，如 NVIDIA AGX、iPhone 16 和 MacBook Pro，已经稳步获得了针对 AI 工作负载优化的强大设备端计算能力[4,15]。最近，针对边缘移动或物联网设备上的 LLM 应用，硬件方面也做出了巨大努力。

- 高通的骁龙 8 Elite 可以以每秒 70 个 token 的惊人速度执行 LLM[20]，凸显了实时设备端 LLM 任务的潜力。
- 谷歌也通过将 DeepMind 开发的多模态 LLM——Gemini AI[6]——集成到谷歌助手、Nest 设备和谷歌家庭应用中，正在彻底改变其智能家居生态系统。

这些创新为用户提供了在创造力、信息总结、图像生成以及通过文本、语音和照片进行更智能交互方面的有前景的工具[10]。总体而言，LLM 和移动硬件的快速发展正在推动更智能、更个性化的移动应用的发展，为移动设备上的持续 LLM 微调铺平了道路。

尽管这些应用前景诱人，但:mdnice-bold-italic[不断发展的当代 LLM 实际上很难微调]。**移动设备的有限资源与设备端 LLM 微调的大量资源需求之间的巨大差距使其更具挑战性**。

::: block-1
- 最近关于**参数高效微调（PEFT）的研究旨在通过冻结预训练主干并在其中各个点插入小型可训练模块来减少可训练参数**，但 PEFT 对于移动设备来说仍然负担过重。
- 此外，一些开创性方法探索了**多设备协同训练，将资源密集型的 LLM 微调任务分布在连接的移动设备上**，以减轻单个设备的计算和内存负担。例如，流水线训练范式将 LLM 划分为更小的子模型，这些子模型被连接并部署在协同的移动设备上[1,17,26]。
- 然后，**正向和反向传播通过多跳中继方式在参与的移动设备上执行**。为了加速这种流水线训练，**输入数据被划分为微批次，可以在移动设备上并发处理** [5,19,31]。
:::

> 然而，现有方法无法支持在“单个”移动设备上进行 LLM 微调，并且在实践中可能难以部署。我们确定了以下三个关键障碍：

1. :mdnice-bold-italic[现有的协同 LLM 微调方案通常依赖于分层模型划分和跨设备流水线训练，这要求所有设备都在具有稳定对等链路的局域网内]。然而，在具有有限能力的移动设备的边缘网络中，这往往不切实际，并且容易受到单设备故障的影响，更不用说多跳传输的低交付率和高错误率了。
2. :mdnice-bold-italic[训练 LLM 需要巨大的内存使用，这通常超过移动设备的容量] （例如，OPT-6.7B 模型需要>70 GB，而移动设备的典型 DRAM 为 4GB–12GB）。尽管 PEFT 方法有助于将内存占用减少高达 30%[16]，但它们无法从根本上解决内存问题，因为反向传播的梯度仍然需要通过整个预训练模型。这使得 PEFT 不足以在内存受限的移动设备上实现 LLM 微调。
3. :mdnice-bold-italic[微调过程通常遵循交替的正向和反向传播策略，其中反向传播的计算量更大]。像谷歌 Edge TPU 或高通 Hexagon 这样的设备端加速器通常针对推理（即仅正向传播）进行优化，缺乏对反向传播特定操作的加速支持。这可能会显著延长训练时间，甚至使资源受限的移动设备无法进行微调。

---

在本文中，我们介绍了 MobiLLM，一种新颖的系统框架和相应的实现，通过服务器辅助的侧调优在“单个”移动设备上实现 LLM 微调。**受侧调优[23]的启发，MobiLLM 的基本思想是**

::: block-1
1. 将 LLM :mdnice-bold-italic[微调解耦] 为**【冻结】的【预训练模块】** 和由**【可训练】模块组成的【侧网络】**；
2. 在移动设备和服务器之间分配 LLM 微调工作负载，即:mdnice-bold-italic[移动设备负责冻结的预训练主干模型]，服务器负责可训练的侧网络；
3. 让:mdnice-bold-italic[层间激活在移动设备和服务器之间交换]。通过这种方式，MobiLLM 在资源受限的移动设备上保持内存和计算高效的正向传播以及功能正常的 LLM 主干，同时将计算密集型和内存密集型的反向传播卸载到高性能计算服务器，同时确保数据从未离开本地移动设备。
:::

> 据我们所知，**MobiLLM 是第一个借助服务器在移动设备** （甚至是仅含 CPU 的设备）上**实现 LLM 微调的工作**，它利用现有的移动边缘网络架构执行正向和反向传播解耦，并突破了移动设备的内存和计算障碍。我们的贡献总结如下：

- 我们提出了 MobiLLM，一种新颖的设备端 LLM 微调框架。MobiLLM 将主要的计算和内存负担卸载到高性能服务器，允许资源受限的移动设备仅处理冻结的主干模型和适合其硬件能力的移动友好型操作。这使移动设备能够微调 LLM，同时将其数据保留在设备本地。
- 我们开发了一种为 MobiLLM 微调系统量身定制的量化适配器侧调优方法。通过堆叠一组并行适配器模块，可训练的侧网络与冻结的预训练 LLM 主干分离，创建反向传播旁路。它在正向传播期间仅需要单向激活传输，并利用低精度量化，这使得侧网络能够利用预训练模型的中间表示进行训练。
- 我们在几种流行的移动设备或开发套件上部署了 MobiLLM，包括 NVIDIA Xavier 和仅含 CPU 的笔记本电脑，并使用亚十亿规模的 LLM（OPT-350M）和十亿规模的 LLM（OPT-1.3B）在各种任务和系统配置上评估其性能。

结果表明，MobiLLM 使十亿规模的 LLM 微调能够在像 Xavier（仅 4.6 GB 可用 GPU 内存）这样的内存受限移动设备上进行。**与最先进的方法相比，MobiLLM 在有限的通信成本下，将内存使用显著减少高达 4 倍，将收敛时间加快高达 2.3 倍。**

## 二、背景与动机

### 2.1 参数高效微调

参数高效微调（PEFT）是一种可行的方向，它通过**仅训练少数可训练参数（而非更新所有参数）** 使预训练模型适应下游任务。PEFT 的一个:mdnice-bold-italic[主流研究方向是添加少量可训练参数并仅对这些参数进行调优]。例如：

- 适配器（Adapters）[12]是插入到 Transformer 层中的小型瓶颈模块，实验表明，训练带有层归一化层的适配器足以达到全量微调的性能。
- 类似地，LoRA[13]将可训练的低秩分解矩阵注入冻结的预训练模型中。
- 与在预训练模型中插入新参数不同，基于提示的方法[33]在输入中添加可训练参数，并在训练期间保持整个预训练模型不变。插入的提示通过学习利用预训练模型的知识来解决新任务。

除了引入新参数的方法外，**还有多种方法从预训练模型中选择稀疏的参数子集进行更新，而不添加任何新参数。**

- 其中一种代表性方法是 BitFit[32]，它更新模型中的每个偏置项。

:mdnice-bold-italic[尽管 PEFT 方法旨在通过最少的参数更新实现有竞争力的结果，但它们在微调过程中仍然需要大量的 GPU 内存，并且速度可能很慢]。这是因为更新的参数位于预训练的大型模型内部，需要通过模型进行完整的反向传播以计算梯度用于反向传播（指在训练中，为了更新参数而计算误差从输出层反向传递到输入层的过程）。这使得 PEFT 方法无法直接应用于许多计算资源有限的实际应用，因此也不利于在资源受限的移动设备的 GPU 上微调大型语言模型。

### 2.2 移动设备上的 LLM 微调

个人数据的设备端微调是使 LLM 适应特定用户任务同时保持隐私的有效解决方案，因为所有数据存储和计算都在本地进行，没有任何数据离开设备。为了使 LLM 适配移动设备，主要有两种技术：模型压缩和协同微调。

::: block-1
- **模型压缩将主干网络压缩为更小的网络，使其更易于训练**。像剪枝（移除冗余参数）和量化（减少表示权重所需的比特数）等技术分别减少权重数量和比特宽度[11]。然而，过度压缩会导致性能显著下降，因此需要在资源节省和模型精度之间进行谨慎平衡。
- **协同微调使具有微调任务的设备发现附近能够建立直接通信链路的节点，并分担微调过程的计算和内存负载**。这通常基于交换必要的中间参数。例如，多设备流水线并行将 LLM 按层拆分为更小的子模型，部署在不同设备上，正向和反向传播计算通过这些设备以中继方式执行[1,26]。通过将输入数据划分为微批次并在设备间持续馈送以提高并行性，可以进一步加速这种流水线[19,31]。这种协同微调范式有效地利用了网络内相邻节点的计算和传输能力，允许在个体计算和内存约束下灵活部署和执行任务。
:::

### 2.3 动机

> 在本小节中，我们揭示了实际的设备端 LLM 微调面临的三个关键问题：

#### **观察 1：跨设备流水线微调的局限性**

:mdnice-bold-italic[大多数最先进的协同 LLM 微调方案] 依赖于**分层模型划分** 和**跨设备流水线训练**，这通常要求所有设备位于具有稳定端到端多跳传输链路的**局域网** 内。然而，在现实世界的网络中，可能没有足够多有能力的移动设备形成稳定的协作环路，并且链中的单设备故障可能会扰乱系统，甚至破坏整个 LLM 微调。

此外，**多跳传输以低交付率和高错误率而闻名**。即使假设流水线微调运行良好，其“中继式”训练过程也不可避免地在每个参与的移动设备上引入等待时间（等待流水线中前一个设备的中间结果）。虽然一些并行训练方法可能通过使用过时的模型参数进行并发计算来减少设备的空闲时间，但这可能会损害模型收敛，并带来显著的协调开销。

再者，由于流水线中的每个设备仅维护 LLM 的本地部分，单个移动设备无法使用整个微调后的模型独立执行推理，这阻碍了本地设备端 LLM 服务的提供。

#### **观察 2：内存瓶颈带来的挑战**

图 1 显示了在批大小为 16 的情况下训练各种 LLM 的峰值内存使用情况。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/05.webp)

表 1 进一步详细分解了微调 OPT-1.3B 模型的内存占用。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/06.webp)

观察到的**内存需求通常是移动设备无法承受的** （例如，OPT-6.7B 模型需要超过 70 GB，而移动设备的典型 DRAM 为 4GB–12GB）。对于智能手机而言，情况更糟，因为只有一小部分内存可以分配给训练任务，而不影响用户体验。:mdnice-bold-italic[相比之下，推理（仅正向传播）消耗的内存要少得多] （例如，4.403GB），因为它不需要存储所有层的中间激活（指神经网络各层计算过程中产生的输出值，是反向传播计算梯度的必要数据），而这些激活对于训练期间的反向传播是必需的。

> 在微调中，这些激活占用了大部分内存，并且内存使用随着批大小、序列长度、隐藏层维度和层数的增加而迅速增加。

因此，鉴于 :mdnice-bold-italic[LLM 通常具有较大的维度和众多的层，序列长度的轻微增加可能导致移动设备内存溢出]，而移动设备只能支持具有较小序列长度的数据样本的 LLM 微调。

**这些严峻的内存挑战导致设备端 LLM 微调不可靠**，任务可能偶尔成功或失败。也很难评估特定的移动设备是否可以支持本地 LLM 微调。

#### **观察 3：设备端反向传播计算的低效性**

微调过程通常遵循交替的正向和反向传播策略，其中反向传播的计算量更大——大约是正向传播成本的两倍。虽然流水线并行训练[19]支持多批次并行处理，但每个设备上并发的正向和反向计算可能导致计算资源竞争。这些因素可能会严重延长处理时间，甚至导致资源受限的移动设备上的任务失败。先进的移动设备可能配备强大且快速发展的 DNN 加速器（NPUs，即神经网络处理器），例如谷歌 Edge TPU 和高通 Hexagon，但这些加速器是为推理而非训练量身定制的。它们缺乏对反向传播特定操作（如动态梯度更新）的良好支持[30]，这限制了它们对 LLM 微调任务的加速性能。

---

**总之，当前的移动设备无法处理 LLM 微调任务，因为对硬件资源的需求相当高**。仅仅冻结预训练参数或分散调优任务只能带来有限的改进。为了在移动设备上实现实用且资源高效的 LLM 微调，:mdnice-bold-italic[需要一种综合考虑模型架构、训练范式和网络支持的整体解决方案。]

## 三、MobiLLM 的设计

### 3.1 MobiLLM 概述

MobiLLM 是一个移动设备-服务器框架，旨在实现移动设备上内存高效的 LLM 微调。

> 其:mdnice-bold-italic[【核心思想】] 是**创建一个与冻结的主干 LLM 并行的反向传播旁路，并将 LLM 微调任务分配给移动设备** （负责固定的正向传播）**和服务器** （负责内存和计算密集型的反向传播），同时**将本地数据保留在设备上。**

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/02.webp)

上图图 2 展示了 MobiLLM 系统的概述。

MobiLLM 允许移动设备保留本地训练数据集和预训练的 LLM 主干。同时，一个侧网络部署在通过稳定无线传输链路连接到移动设备的服务器上并在其上训练。在微调过程中，移动设备仅在主干模型上执行正向传播，其中中间激活值被提取并通过捷径连接作为侧网络的输入。

通过这种方式，**MobiLLM 将移动设备与那些计算成本高昂的反向传播完全分离**，并在 LLM 微调期间节省大量的设备端内存（中间激活值和优化器状态）。

作为潜在的代价，MobiLLM 框架由于需要将激活值从移动设备传输到服务器，会引入一些通信开销和传输延迟。为了解决这些问题，我们**提供了一种使用激活量化的通信高效侧调优方法** （见 3.2 节），**并优化了设备-服务器训练流程** （见 3.3 节），以有效减少所提出的 MobiLLM 系统中的传输延迟，确保移动设备上的 LLM 微调具有内存友好、计算轻量和时间高效的特点。

### 3.2 量化适配器侧调优

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/02.webp)

> 在图 2 中，蓝色方框是原始的基于 Transformer 的 LLM 主干，绿色方框勾勒出我们的侧网络，该侧网络由一组可训练模块组成。

具体来说，我们:mdnice-bold-italic[将可训练模块与主干网络分离]，而不是将它们插入其中，从而**提供了一条专用的“通道”，所有可训练参数都位于这条通道上**。本小节的其余部分将详细阐述侧网络的设计及其与主干的连接。

#### **基于并行适配器的侧网络**

MobiLLM 建立了一个:mdnice-bold-italic[与主主干并行的侧网络，该侧网络对主干输出进行优化以产生更准确的表示]。具体而言，我们通过使用**堆叠的并行适配器模块来设计侧网络**。每个适配器的输入结合了主干中 Transformer 层的中间激活输出和前一个适配器的激活值。这确保了我们的并行适配器在针对新任务进行微调时，能够优化来自原始主干的特征表示。

每个适配器包含一个下投影矩阵（$w_{down} \in R^{n+m}$，用于将输入投影到较低维度的空间），其后是一个非线性激活函数 $\sigma(\cdot)$，以及一个上投影矩阵 $W_{up} \in \mathbb{R}^{m+n}$ 。 这里，$n$ 表示隐藏层的维度，$m$ 作为适配器瓶颈维度，是用于配置适配器的超参数。将 $h_{in}$ 表示为适配器的输入，适配器模块内的计算（带有残差连接）可以总结如下：

$$
h_{in} \leftarrow h_{in}+\sigma\left(h_{in} W_{down}\right) W_{up} . (1)
$$

与以前的侧调优方法使用从主干修剪的轻量级 Transformer 结构作为侧网络相比，:mdnice-bold-italic[我们的侧网络设计消除了多头注意力机制和前馈网络]。因此，它进一步减少了可训练参数的数量，并增加了微调的开销。

#### **带有量化激活的捷径连接**

MobiLLM 利用从主干模型的中间激活到侧网络的捷径连接。冻结主干的最后一层的输出和侧网络的输出被合并，并输入到 LLM 的头部进行预测。

**MobiLLM 允许将预训练主干的 Transformer 层分组为 M 个块，每个块连接到特定任务侧网络中的一个并行适配器**。相应地，有 M 条捷径将中间激活从主干馈送到侧网络中的相应适配器。令 $a_{1}, ..., a_{m}, ..., a_{M}$（其中 $a_{m} \in \mathbb{R}^{n \times d}$）表示激活输出，每个激活输出由 $n$ 个 token 组成，隐藏维度为 $d$。

**为了减少通信开销，MobiLLM 在将这些中间激活输入侧网络之前，对它们应用低精度量化**。这个过程包括将激活的原始数据格式（例如 32 位或 16 位浮点数）转换为更低位数的数据类型。通常，输入数据通过其元素的绝对最大值进行归一化，以适应目标数据类型的范围。以 FP4 量化为例，16 位浮点张量通过以下方式量化为范围在[0,15]的 4 位格式：

$$
X^{FP4} = round\left(\frac{15}{absmax\left(X^{FP16}\right)} X^{FP16}\right), (2)
$$

其中 $X^{FP16}$ 是浮点张量，$X^{4bit}$ 是 INT4 数据类型的量化对应物。**或者，通过使用 NF4 数据类型，MobiLLM 还允许以下量化过程**：

$$
X^{NF4} = T\left(\frac{X^{FP16}}{absmax\left(X^{FP16}\right)}\right), (3)
$$

这里，首先使用其绝对最大值对 $X^{FP16}$ 进行归一化，然后通过映射到分位数表（用 $T(\cdot)$ 表示）获得 4 位量化对应物。分位数表 $T(\cdot)$ 的构建确保每个量化区间从输入张量中分配相等数量的值[7]。MobiLLM 潜在地兼容各种量化技术和数据格式，这有助于通过利用激活值的分布特征来减轻信息失真。**我们在实验中测试了 FP4 和 NF4 两种数据类型，并通过经验证明 NF4 实现了更好的性能** （见 5.4 节）。

我们注意到，:mdnice-bold-italic[将主干划分为具有相同数量 Transformer 层的块并不是必须的]。一种实用的方法是将顶层（靠近主干输出的层）划分得更精细，而将底层划分得更粗略。**其【基本原理】是，预训练主干的底层通常学习在下游任务中共享的通用低级特征表示，在微调期间需要的调整最小**。这消除了在每个 Transformer 层上附加可调整适配器的需求，进一步减少了将激活值上传到服务器的通信开销。此外，这种设计增强了数据隐私，因为来自每个主干块的激活输出几乎会扭曲输入嵌入，使得很难推断原始输入样本。

### 3.3 MobiLLM 的流程

> 本小节详细介绍所提出的 MobiLLM 的训练流程。

我们首先介绍每次迭代中的 MobiLLM 拆分学习，然后介绍跨迭代的 MobiLLM 重叠训练策略，以获得更好的时间效率。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/02.webp)

**每次迭代中移动设备和服务器之间的 MobiLLM 拆分学习**。在每次迭代中，MobiLLM 将训练工作负载分配给移动设备和服务器。传统的拆分学习包括设备端的正向传播、服务器端的正向和反向传播以及设备端的反向传播，需要在切割层双向交换压缩数据。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/07.webp)

与之不同的是，MobiLLM 拆分学习简化了这一过程，**将反向传播计算完全委托给服务器，这得益于其将可训练侧网络与冻结主干网络分离的设计**，如图 2 和图 3 所示。因此，MobiLLM 在正向传播期间只需要从移动设备到服务器的单向中间激活（即压缩数据）传输。在不失一般性的前提下，我们:mdnice-bold-italic[将 MobiLLM 在一次迭代中的详细训练过程呈现如下]：

::: block-1
（1）:mdnice-bold-italic[初始化（移动设备和服务器）]：移动设备获取一个适合其本地计算和内存能力的预训练 LLM 主干。然后，服务器初始化一个侧网络，其中适配器模块中的权重来自具有适当选择标准差的零均值高斯分布。

（2）:mdnice-bold-italic[本地主干正向传播] （**移动设备**）：移动设备从其本地数据集中采样一个小批量数据，并通过冻结的主干模型执行正向传播，生成与每个 Transformer 块对应的中间激活输出。

（3）:mdnice-bold-italic[激活传输] （**移动设备 → 服务器**）：移动设备将主干模型的中间激活输出（$\overline{a_{1}}, ..., \overline{a_{m}}, ..., \overline{a\_{M}}$）量化为压缩格式。然后，移动设备将量化后的激活值以及相应的标签和元数据（例如批处理索引）传输到服务器。

（4）:mdnice-bold-italic[正向传播] （**服务器**）：服务器收到激活值后，将它们与其适配器模块（作为侧网络）的输入相结合。服务器通过侧网络执行正向传播，生成训练过程所需的输出。

（5）:mdnice-bold-italic[损失计算] （**服务器**）：服务器通过将侧网络的输出与从移动设备收到的真实标签进行比较来计算训练损失。损失度量取决于特定的下游任务（例如，分类任务使用交叉熵损失，回归任务使用均方误差）。

（6）:mdnice-bold-italic[反向传播和模型更新] （**服务器**）：服务器执行反向传播以更新侧网络。

（7）移动设备继续采样新的数据批次，并将它们输入到本地主干模型。**重复上述步骤以调整侧网络，直到其收敛。**
:::

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/07.webp)

图 3 使用 GPT 风格的 Transformer 架构[2]作为示例，说明了 MobiLLM 框架中的正向传播过程。为简单起见，每个 Transformer 层内的关键组件表示如下：多头自注意力（MSA）为 $f_{B_{1}}$，前馈网络（FFN）为 $f_{B_{3}}$。两个归一化（LN2）层分别表示为 $f_{B_{2}}$ 和 $f_{B_{4}}$。在侧网络中，适配器模块中的下/上投影和非线性层简化为 $f_{A_{1}}$，而层归一化表示为 $f_{A_{2}}$。在第 $l$ 个 Transformer 层中，模型生成两个不同的输出——一个用于主干，一个用于侧网络，可表示为：

$$
b_{l+1}=f_{B_{4}}\left(f_{B_{3}}\left(f_{B_{2}}\left(f_{B_{1}}\left(b_{l}\right)+b_{l}\right)\right)+f_{B_{2}}\left(f_{B_{1}}\left(b_{l}\right)+b_{l}\right)\right), \quad(4)
$$

和 $$
s_{l+1}=f_{A_{2}}\left(f_{A_{1}}\left(s_{l}+b_{l+1}\right)+s_{l}+Q\left(b_{l+1}\right)\right) . (5)
$$

这里，$Q(\cdot)$ 表示用于捷径激活连接的量化算子。

**在我们的 MobiLLM 中，公式 4 和公式 5 中的正向传播计算分别由移动设备和服务器执行，并且可以并行计算**。:mdnice-bold-italic[重要的是，我们观察到适配器的更新与主干的反向传播是解耦的] （即公式 4 独立于公式 5 运行），因为适配器并未嵌入到主干层中。此外，适配器将来自主干的中间激活作为其输入，这确保了侧网络在训练过程中能够利用预训练的表示。

接下来，我们给出第 $l$ 个适配器的可训练参数 $\theta_{l}$ 的梯度计算，其中 $\theta_{l}=\{\theta_{l}^{1}, \theta_{l}^{2}, ..., \theta_{l}^{n}\}$。我们用 $a_{l+1}$ 表示主干第 $l$ 层输出（即 $b_{l+1}$）和侧网络第 $l$ 层输出（即 $s_{l+1}$）的拼接。在损失为 $L$ 的反向传播中，关于 $\theta_{l}$ 的梯度为：

$$
\begin{aligned} \frac{\partial L}{\partial \theta_{l}} & =\frac{\partial L}{\partial a_{l+1}} \frac{\partial a_{l+1}}{\partial f_{A}} \frac{\partial f_{A}}{\partial \theta_{l}} \\ & =\frac{\partial L}{\partial s_{l+1}}\left(\frac{\partial s_{l+1}}{\partial f_{l}^{1}} \frac{\partial f_{l}^{1}}{\partial f_{l}^{2}} \frac{\partial f_{l}^{2}}{\partial f_{l}^{3}} \cdots \frac{\partial f_{l}^{m}}{\partial f_{A}}\right) \sum_{k=1}^{n} \frac{\partial f_{A}}{\partial \theta_{l}^{k}}, \end{aligned}
$$

其中 $f_{l}^{m}$ 是从第 $l$ 层输出到 $f_{A}$ 的中间过程。大多数现有的 PEFT 方法仅减少可训练参数 $\theta_{l}$ 的数量，即 $|\sum_{k=1}^{n} \frac{\partial f_{A}}{\partial \theta_{l}^{k}}|$，导致内存使用量略有减少。相比之下，MobiLLM 更进一步。它简化了中间过程 $\frac{\partial a_{l+1}}{\partial f\_{A}}$，并将必要的梯度计算沿着并行梯度通道卸载到内存充足的服务器。因此，MobiLLM 为移动设备节省了大量内存和计算时间。

此外，MobiLLM 有效地避开了移动加速器在处理训练特定操作时的低效性，并确保移动设备上可用硬件资源的高利用率。由于服务器的处理速度比移动设备快得多，服务器端的操作也加快了资源受限移动设备的 LLM 微调速度。

**跨迭代的 MobiLLM 设备端和服务器端训练重叠**。:mdnice-bold-italic[MobiLLM 不同于传统的一次正向一次反向交替更新规则，它允许移动设备不间断地执行正向传播计算]。在传输中间激活和训练侧网络的同时，移动设备通过持续将数据批次输入主干来重叠这一过程，以进行连续的训练迭代。这是基于这样一个事实：**设备端的主干模型在整个微调过程中保持不变，因此无需等待参数更新**。因此，实现了多批次并行性，而不会引入模型过时问题，这是其他重叠训练方法的常见缺点。此外，由高性能计算支持的服务器端侧网络训练通常比设备的执行和传输速度快几倍。这种精简的工作流程确保服务器能够及时接收最新的中间输出，消除了不必要的等待时间，并加速了协同微调。

### 3.4 MobiLLM 的优势

> 在本小节中，我们首先分析 MobiLLM 如何帮助节省移动设备上 LLM 微调的内存，然后讨论 MobiLLM 的其他优点。

#### **内存节省分析**

MobiLLM 将设备端操作限制为仅正向传播，从而大幅减少移动设备的内存使用。具体而言，**MobiLLM 减少了移动设备在微调过程中内存占用的两个主要贡献因素**，即:mdnice-bold-italic[中间激活值、优化器状态和模型状态]，分析如下：

::: block-1
1. **中间激活值**：在正向传播期间，只有少数选定层的激活值被临时存储在设备上，并且在传输到服务器后可以被丢弃。考虑一个具有 $L$ 层的 LLM，其中每层的激活值大小表示为 $A = S \cdot B \cdot H$。这里，$S$、$B$ 和 $H$ 分别表示序列长度、批大小和隐藏层维度。传统的微调方法需要在移动设备上存储所有层的激活值，这大约消耗 $L \cdot A$ 的内存。相比之下，MobiLLM 只需要 $\gamma \cdot A$，其中 $\gamma（\gamma \ll L）$ 是用于临时存储的选定层数。这将激活值的内存使用减少了大约 $L/\gamma$ 倍。
2. **优化器状态**：像 Adam 这样的经典优化算法需要存储额外的状态（例如动量和二阶统计量），通常会使可训练模型参数所需的内存增加一倍或两倍。在 MobiLLM 中，这些计算和状态完全卸载到服务器，避免了移动设备上的这种内存消耗。
:::

MobiLLM 设计中的这些优化共同减少了内存占用，使即使内存容量有限的移动设备也能高效地微调 LLM。

#### **内存效率之外的优势**

MobiLLM 还有其他优点，增强了其在资源受限环境中的实用性和性能，列举如下：

1. :mdnice-bold-italic[增强的系统可靠性]。MobiLLM **不依赖于多个移动设备之间脆弱的多跳流水线协作** [1,26]，而是仅采用一个具有足够计算资源的服务器提供帮助。这种简单的设备-服务器设计与现有的移动边缘网络架构一致，该架构具有成熟的物理层和网络层协议，支持终端-服务器协作以及高速传输。例如，5G/6G 基站通常配备高性能计算单元，为附近的移动用户提供服务，家庭物联网网络中的智能集线器可以通过高速 Wi-Fi 链路管理连接设备的工作负载。因此，MobiLLM 的设置本质上更可靠和实用。此外，MobiLLM 通过在整个 LLM 微调过程中将所有数据样本保留在移动设备上来保护本地数据隐私。
2. :mdnice-bold-italic[微调之外的多功能性]。**与在设备之间划分 LLM 的基于流水线的方法不同，MobiLLM 允许每个移动设备保留一个完整的轻量级 LLM**。这使移动设备除了设备端 LLM 微调之外，还能独立提供本地推理服务。换句话说，移动设备可以通过本地资源共享在持续的微调过程中响应急需的、对延迟敏感的推理请求，即:mdnice-bold-italic[同时提供 LLM 微调和推理服务]。此外，设备可以通过获取和合并在服务器上训练的特定任务适配器来定期更新其模型，并且服务器可以为不同的下游任务托管多个侧网络。**这使移动设备能够通过简单地更改服务器端所需的侧网络来在 LLM 微调任务之间切换**。这种灵活性提高了移动设备在 LLM 微调过程中及之后的实用性。

## 四、实验设置

### 4.1 MobiLLM 的实现

所提出的 MobiLLM 系统部署在由一台服务器和一台移动设备组成的测试平台上。**服务器配备了 NVIDIA A100 GPU** （:mdnice-bold-italic[6912 核 Ampere 架构 GPU，显存 40GB]）。在移动设备方面，我们考虑**两种典型的移动设备**：

1. :mdnice-bold-italic[NVIDIA Jetson Xavier NX]，配备 6 核 NVIDIA Carmel ARM CPU、384 核 NVIDIA Volta GPU 和 8GB 内存。
2. :mdnice-bold-italic[华为 Matebook 笔记本电脑]，搭载英特尔第 13 代酷睿 i5-13500H 处理器和 16GB 内存，这是一款仅含 CPU 的设备。

移动设备与服务器之间的通信基于 Wi-Fi 5 连接，采用 WebSocket 通信协议。

特别地，在 Jetson Xavier NX 上进行的 LLM 训练是本研究的主要实验结果来源。由于 Xavier 的 GPU 和 CPU 共享 8GB 内存，其可用于训练的最大 GPU 内存为 4.6GB。Matebook 笔记本电脑用于测试那些仅含 CPU 的移动设备的训练加速性能（见 5.3 节）。

### 4.2 模型、数据集和参数

我们使用 OPT 系列中两种流行的仅解码器 LLM——OPT-350M 和 OPT-1.3B，来评估 MobiLLM 的性能。上述模型的预训练权重来自 Huggingface[29]。

我们使用自然语言理解（NLU）任务来比较 MobiLLM 和几种基线方法在自然语言理解任务上的表现。我们采用 GLUE[25]基准，该基准包含 7 个分类任务和 1 个回归任务。该基准在多个不同任务上对模型进行评估，包括语言可接受性（CoLA[27]）、情感分析（SST-2[22]）、相似度和释义（MRPC[9]、QQP[14]、STS-B[3]）以及自然语言推理（MNLI[28]、QNLI[21]、RTE[22]）。我们报告 MNLI、QQP、QNLI、SST-2、MRPC 和 RTE 的准确率，STS-B 的皮尔逊相关系数，以及 CoLA 的马修斯相关系数[18]。

除非另有说明，MobiLLM 和所有基线方法使用相同的超参数设置：**FP16** （float16）训练精度、20 个本地训练轮次、16 的小批量大小、5e-4 的学习率，以及 256 的最大序列长度。**网络带宽设置为 60 Mbps**。

### 4.3 用于比较的基线方法

我们在不同的 LLM 任务下将 MobiLLM 与以下基线方法进行比较。

- Full-FT：微调整个 LLM。
- LoRA[13]：在冻结的预训练 LLM 中插入可训练的低秩矩阵，同时保持主干冻结。
- BitFit[32]：仅微调预训练 LLM 的偏置项，同时保持所有其他权重冻结。
- LST[23]：使用从主干修剪的轻量级 Transformer 结构作为侧网络。这里，我们用 $r$ 表示侧网络的缩减因子，$r$ 越大，侧网络的规模越小。
- MobiLLM-L（本地）：在移动设备上本地训练主干网络和侧网络。

## 五、评估结果与分析

### 5.1 端到端性能

> 不同基线方法在 GLUE 基准上的性能。我们首先研究了 MobiLLM 在 OPT-350M 模型上的性能。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/08.webp)

**表 2 总结了 MobiLLM 和其他基线方法在默认设置下在 GLUE 基准上的实验结果**。总体而言，:mdnice-bold-italic[MobiLLM 在所有方法中实现了最低的内存占用，同时保持了相当的准确率]。

- 特别是，MobiLLM 与 Full-FT 相比，内存使用量显著减少了 79.5%，而准确率仅下降了 2%。
- 与其他 PEFT 基线方法（即 LoRA 和 BitFit）相比，MobiLLM 的表现要好得多，平均减少了 75%的内存需求。
- 在不借助服务器的本地部署中，MobiLLM-L 与 LST 相比，内存使用量减少了 2.48 GB，这得益于其轻量级的基于适配器的侧网络设计。

**通过服务器辅助的侧调优，MobiLLM 进一步将内存使用量减少** 到 1.621 GB。相较于所有基线方法的显著改进，主要归功于 MobiLLM 的设计——它:mdnice-bold-italic[将主要的计算和内存负担卸载到高性能服务器，使得移动设备只需处理正向传播]，而其他基线方法都需要在移动设备上进行反向传播，很容易导致内存不足错误。

此外，如表 2 所验证的，MobiLLM 使移动设备能够以**接近设备端推理的内存成本进行 LLM 微调**。这使得设备端 LLM 微调变得切实可行，特别是对于内存受限的移动设备。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/09.webp)

> MobiLLM 使移动设备能够负担十亿级规模 LLM 模型的微调。

我们进一步使用十亿级规模的模型 OPT-1.3B 对 MobiLLM 进行了评估，并在表 3 中报告了结果。

- LoRA、BitFit 和 LST 的内存占用过大，超过 10 GB，这使得它们对于大多数主流移动设备来说不可行。
- 相比之下，我们的 MobiLLM 有效地支持在单个移动设备上对如此大规模的模型进行微调。例如，**MobiLLM 在 Xavier** （配备 4.6 GB DRAM）上**【仅】需要 4.487 GB 的内存**，就能顺利运行微调任务。

这些结果表明，即使是资源受限的移动设备，也能可靠地微调此类十亿级规模的 LLM，而不会有内存溢出的风险。

### 5.2 内存效率优势

> MobiLLM 在内存节省方面表现出色。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/10.webp)

图 5 报告了微调 OPT-1.3B 时不同方法的内存占用细分情况。LoRA 和 BitFit 都通过减少可训练参数的数量显著降低了内存消耗，从而显著减少了优化器状态所需的内存，如图 5 的放大视图所示。**MobiLLM 和 LST 通过建立用于侧调优的反向传播通道，进一步优化了内存使用**，这减少了为反向传播存储中间激活值的需求。因此，它实现了总计 2-4 GB 的内存减少。**与 LST 相比，MobiLLM 还额外减少了 6.4-6.7 GB 的内存**，这归功于两个关键因素：

1. MobiLLM 将侧网络的中间激活内存负担卸载到服务器。
2. MobiLLM 使移动设备仅执行正向传播，因此无需在移动设备上存储优化器状态。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/11.webp)

**MobiLLM 在各种训练配置下实现了近乎稳定的内存使用**。图 4（a）-4（b）进一步探讨了批大小、序列长度和模型大小对内存使用的影响。

::: block-1
- 图 4（a）显示，虽然所有方法的内存使用都随着批大小的增加而增加，但 MobiLLM 始终保持着所有方法中最低的内存占用。此外，:mdnice-bold-italic[随着批大小的增加，MobiLLM 的内存增长速度比其他基线方法慢]。这是因为，从内存使用的角度来看，批大小主要影响需要为反向传播存储的中间激活值的数量，而我们的 **MobiLLM 使移动设备完全无需执行反向传播。**
- 图 4（b）考察了不同序列长度下的内存使用情况。与批大小的影响类似，LST 和 MobiLLM 减轻了中间激活值内存占用的增长速度。值得注意的是，当序列长度设置为 256 时，MobiLLM 仅需要 LST 设备端内存使用量的 41%。
- 图 4（c）进一步评估了不同模型大小的影响。结果表明，MobiLLM 始终优于基线方法，并且随着模型大小的增长，其内存优势不断扩大。
:::

这些结果验证了 **MobiLLM 使移动设备的内存使用对批大小和序列长度等训练配置不敏感，内存成本近乎一致**。这缓解了在不同设置下微调特定模型时常见的“偶尔成功或失败”问题。它还有助于防止移动设备在处理更大的批大小和更长的序列时出现内存溢出，确保微调性能的可靠性。

### 5.3 微调加速优势

> MobiLLM 加速了设备端微调。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/12.webp)

图 6 和图 7 显示了评估 MobiLLM 和其他基线方法的准确率-时间性能的训练曲线。具体而言，图 6 中的结果是通过在配备 4.6 GB DRAM 用于模型训练的 Xavier 设备上微调 OPT-350M/1.3B 模型获得的。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/13.webp)

图 7 显示了在仅含 CPU 的笔记本电脑上的实验结果，与 Xavier 不同，该笔记本电脑缺乏用于神经网络计算的硬件加速，但拥有更大的可用内存。这里，我们排除了 Full-FT 方法的结果，因为其内存需求超过了这两种设备的能力。

总体而言，所提出的 **MobiLLM 在各种 LLM 和任务上始终优于同类设计，在保持相当准确率的同时实现了显著的训练加速**。与基线方法 LoRA 相比，MobiLLM 在 Xavier 上平均将微调达到目标测试准确率的速度加快了 1.8 倍，在笔记本电脑上加快了 2.3 倍。

特别是，如图 6 所示，**只有 MobiLLM 能够支持在 Xavier 设备上训练 OPT-1.3B 模型**。如 3.3 节所讨论的，:mdnice-bold-italic[与需要计算冻结主干参数梯度的 LoRA 和 BitFit 不同，MobiLLM 仅更新侧网络]。这避免了在主干模型上执行反向传播的大量计算成本，最终加快了微调速度。值得注意的是，MobiLLM 的性能优于 LST。LST 采用基于 Transformer 的侧网络。

尽管层维度有所减少，但由于 Transformer 架构中的计算密集型机制和前馈层，基于 Transformer 的侧网络仍然比我们的基于适配器的设计具有更高的 FLOPS（每秒浮点运算次数，用于衡量计算量）。**由于 MobiLLM 中的移动设备【仅专注于】与推理相关的计算，因此可以轻松集成尖端的以推理为中心的硬件加速技术，以进一步实现加速**。此外，高性能服务器加速了侧网络的正向和反向计算，这也加快了训练速度。

### 5.4 敏感性研究

> 表 4 说明了中间激活值的不同量化级别如何影响 MobiLLM 的性能。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/14.webp)结果表明，MobiLLM **在所有量化设置下都实现了相似的准确率性能**。

::: block-1
- 当采用 FP4 数据类型时，与非量化方法相比，MobiLLM 的平均准确率仅下降 1%，而每次迭代的传输量减少了约 4 倍。
- 当采用 NP4 数据格式时，准确率保持得更加稳定。

这些结果验证了 :mdnice-bold-italic[MobiLLM 可以通过适当选择激活量化级别来平衡微调准确率和传输负担]。此外，MobiLLM 与多种量化技术兼容，并能从它们的性能提升中受益，这使得 MobiLLM 能够在可接受的范围内容忍量化噪声，以实现理想的微调性能。

> **对传输速率的敏感性**。通过将激活量化级别固定为 4 位，我们还研究了不同传输速率对 MobiLLM 收敛时间的影响，如表 5 所示。

![文章插图](/articles/2025-08-03-10b-llm-mobillm-4-2-f311d749/images/15.webp)为了确保侧网络有效地从设备的数据中学习，移动设备偶尔会报告其中间激活值，其大小与批大小和序列长度的乘积成正比。在相对较高的上行速率下（例如 60 Mbps 和 100 Mbps），**尽管引入了传输延迟，但 MobiLLM 比【仅】使用设备的方法收敛更快。**

这是通过我们的重叠训练和激活量化设计实现的，这些设计允许移动设备在传输低位激活值的同时连续进行正向传播。此外，:mdnice-bold-italic[激活的量化有效地减少了传输延迟]。与仅使用移动设备相比，服务器高效的侧网络计算进一步加速了训练，从而减轻了传输延迟的影响。**即使在较低的传输速率下** （例如 10 Mbps），MobiLLM 也**保持了可接受的训练时间** （:mdnice-bold-italic[与仅使用设备的方法相比仅增加 7%）]，此时传输延迟成为瓶颈。

值得注意的是，当批大小大于 24 时，MobiLLM 仍然可以支持设备端微调，尽管更长的传输延迟会略微延长训练时间。**相比之下，仅使用设备的方法超过了设备的内存容量，无法在这些设置下执行微调。**

未来高速网络（例如 5G、6G 或 Wi-Fi 6）的部署或广泛覆盖将增强 MobiLLM 的能力，以在资源受限的移动设备上实现或加速 LLM 微调。

## 六、结论与未来工作

> 在本文中，我们介绍了 MobiLLM，这是一种用于在移动设备上微调基于 Transformer 的大语言模型（LLM）的新型框架。

MobiLLM 将并行适配器与主干网络分离，并将微调过程中主要的计算和内存负担卸载到高性能服务器。

::: block-1
:mdnice-bold-italic[它允许移动设备保留冻结的主干模型，仅执行与服务器端执行并行的正向传播，同时将数据保留在设备本地。]

对比分析表明，**MobiLLM 优于现有的微调方法，内存占用减少 4 倍，训练收敛速度加快 2.3 倍**。因此，MobiLLM 为资源受限的移动设备（甚至仅含 CPU 的设备）解锁了微调十亿级规模 LLM（如 OPT-1.3B）的潜力。
:::

作为未来的扩展，MobiLLM 可以将预训练主干模型的参数量化为低精度值，以进一步减少权重的内存占用。这有助于更轻松地在资源受限的移动设备上存储和部署大型 LLM。我们的**额外实验表明，当主干模型量化为 INT4 时**：

- MobiLLM 在微调 :mdnice-bold-italic[OPT-350M] （批大小=16，序列长度=256）时，**设备端内存使用量限制在 1.176 GB**。
- :mdnice-bold-italic[对于 OPT-1.3B]，**内存使用量显著减少到 2.751 GB** ——与 LoRA 微调相比减少了 5 倍以上，同时准确率仅下降 2%，几乎可以忽略不计。

此外，低精度数据通常在现代加速器上执行更快，因为它们利用了整数内核，而整数内核得到了广泛的硬件支持（如 NVIDIA GPU、Intel CPU、高通 DSP 等）。

下一步，我们将探索：

1. 将 MobiLLM **与先进的训练后量化技术相结合**，以在严格的内存约束下保持模型准确率的同时进一步实现硬件加速。
2. 我们还将**设计一种面向任务的激活过滤和传输机制，有选择地将重要激活传输到侧网络**，以进一步减少传输开销。
