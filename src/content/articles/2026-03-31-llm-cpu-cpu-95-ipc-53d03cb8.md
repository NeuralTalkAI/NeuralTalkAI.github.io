关键词：**硬件预取**、:mdnice-bold-italic[内存墙]、大语言模型、**CPU 微架构**、:mdnice-bold-italic[硬件-软件协同设计]

> 在追求单核性能的征途上，CPU 设计师们正面临一道难以逾越的天堑——“内存墙”。这道墙的另一边，是主存（DRAM）动辄数百个周期的访问延迟，而 CPU 核心的运算速度却已逼近物理极限。**为了填平这道墙，现代处理器普遍采用了一项关键技术：硬件数据预取（Hardware Prefetching）**。它像一个未卜先知的预言家，提前将程序未来可能用到的数据从主存搬进高速缓存，让 CPU 核心无需“空等”。

然而，**现有的硬件预取器正面临一个根本性的困境**。它们就像一群只会特定技能的工匠，有的擅长识别步长固定的模式（Stride），有的精于抓取连续的流式访问（Stream），有的则对复杂的空间模式（Spatial）情有独钟。**但真实世界的程序是千变万化的，不同阶段会展现出迥异的访问模式**。就好比让一个只会做木工活的工匠去修理一台精密汽车，结果可想而知。

::: block-1
为了解决这个问题，学术界提出了“预取器集成”（Prefetcher Ensemble）的思路，即组合多个专业的“工匠”，并设置一个“调度中心”来动态分配任务。但以往的调度策略，比如 Alecto 或 DOL，都依赖于在线学习，这带来了两个致命缺陷：

- 一是**需要漫长的试错才能收敛**，面对瞬息万变的程序阶段常常“慢半拍”；
- 二是**受限于芯片上的严苛面积和延迟约束，只能采用非常简单的启发式规则**，难以做出真正“聪明”的决策。
:::

这不禁让人深思：一个经验丰富的开发者，在阅读一段代码时，能否一眼就看出其中数据访问的模式，从而知道该用什么策略去预取？

图 1 银行账户管理 C 代码的内存访问模式示例，此图展示可轻松识别的内存访问模式。该模式包括：(a) 原子操作的无预取；(b) 结构体数组遍历的步幅预取；(c) 结构体成员访问的空间预取；(d) 字符串顺序读取的流预取。该图直观验证了研究的核心洞察 —— 静态代码上下文包含足够的内存访问模式信息，人类开发者可识别的模式，经过微调的 LLM 同样能学习捕捉。四种模式覆盖了处理器中最常见的内存访问类型，清晰说明单一预取器无法适配程序的全部访问场景，而传统集成预取器的在线动态调度存在收敛慢、适配滞后的问题。这一示例为 PF-LLM 从静态汇编代码分析并预测最优预取策略提供了直观的现实依据，也从根本上解释了为何基于静态代码的 LLM 提示能超越传统在线预取方法。

## 一、核心挑战：硬件预取器的“先天局限”与“后天困境”

> 在深入 PF-LLM 的技术细节之前，我们有必要先厘清它要解决的究竟是什么问题。正如引言所述，**硬件预取器的核心在于“预测”和“隐藏”内存延迟。**

为了达到这个目的，学术界和工业界发展出了种类繁多的预取器。本文在实验部分选取了 12 种具有代表性的预取器，它们各自擅长不同的访问模式，见下表：

![文章插图](/articles/2026-03-31-llm-cpu-cpu-95-ipc-53d03cb8/images/05.webp)

::: image-caption
表 2 所选子预取器及其目标模式。其中带星号 * 的预取器如 Pythia、Bingo，因为内部状态复杂，在 PF-LLM 中被排除在“需求请求过滤”之外，以保护其状态不被破坏。整体来说，该表格梳理了为 PF-LLM 配套的 12 种经典子预取器，按内存访问模式分类并明确各预取器的预取度支持性，对带星号的精密预取器排除需求请求过滤，是为了保护其复杂的内部状态，避免无关请求造成的训练噪声。研究基于 PF-LLM 的最优策略频率分布，最终仅选取 4 种高频最优预取器构建硬件，大幅降低了硬件面积和复杂度，且未造成性能损失。这一筛选过程充分体现了 LLM 的静态分析对硬件设计的直接指导价值，有效解决了传统集成预取器组件冗余、资源利用率低的问题。
:::

::: block-1
**这种多样性带来了一个根本性的问题：在一个程序中，没有任何一个单一的预取器能够始终表现得最好**。例如，一个简单的数组遍历（Stride 模式）可能在程序早期占主导，而后期可能变成一个链表的随机访问（Irregular 模式）。:mdnice-bold-italic[如果只用一个预取器，必然会在某些阶段表现不佳。]
:::

**集成式预取器（Ensemble）正是为了解决这个问题而生的**。它像一个指挥官，调度多个“士兵”（子预取器）协同作战。

![文章插图](/articles/2026-03-31-llm-cpu-cpu-95-ipc-53d03cb8/images/06.webp)

::: image-caption
图 2 预取器集成的编排层，(a) 需求请求的路由环节；(b) 预取请求的下发环节；(c) 编排器包含路由器和多路复用器，是预取器集成的核心控制模块。该图解构了传统预取器集成架构的核心痛点，编排层的需求请求路由和预取请求下发决策，直接决定了集成预取器的整体性能，而传统方法的在线动态决策逻辑，极易干扰 Pythia、DSPatch 等精密预取器的内部状态，导致模式检测失效。PF-LLM 通过离线生成的预取提示，为该编排层提供明确的静态指导，精准定义请求路由规则、预取度和过滤策略，将原本的动态复杂决策转化为静态硬件配置，从根本上解决了传统编排层适配性差、收敛慢的问题，让集成预取器实现零延迟的最优策略切换。
:::

> 如图 2 所示，集成式预取器需要一个“编排层（Orchestration Layer）”来做出两个关键决策：

1. 路由决策：当一个需求请求（Demand Request）到来时，应该把它发给哪个或哪些子预取器进行训练？
2. 选择决策：当多个子预取器同时发出预取请求时，应该选哪一个发给下一级缓存？

然而，现有的集成方法如 Alecto、DOL 的调度策略主要依靠在线学习。它们试图在运行时，:mdnice-bold-italic[通过观察每个子预取器的表现（例如，通过比较 IPC 或命中率），动态地调整调度策略。 这种在线学习机制存在两大硬伤：]

- **适应性差**：在线学习需要一个收敛期，在程序阶段快速变化时，:mdnice-bold-italic[它总是“事后诸葛亮”，无法立即适应新的模式。]
- **精度受限**：由于芯片面积和功耗的限制，在线学习策略只能使用非常简单的硬件逻辑，例如基于“置信度”的计数器或简单的马尔可夫模型。:mdnice-bold-italic[它们无法利用更广泛的程序上下文（如代码结构、语义）来做出更明智的决策。]

::: block-1
正是这些瓶颈，促使作者们思考一个全新的方向：**是否可以利用强大的、不受硬件资源限制的离线分析来为在线预取器提供指导？**
:::

## 二、创新破局：PF-LLM，让代码“说话”的 AI 大脑

> 既然在线学习受限于硬件，那何不将“理解”和“决策”的任务交给离线？这正是 PF-LLM 的核心思想。**它的创新之处在于，首次将大语言模型的代码理解能力与硬件预取器的实时执行能力相结合**，构建了一个“离线分析 + 在线执行”的全新架构。

![文章插图](/articles/2026-03-31-llm-cpu-cpu-95-ipc-53d03cb8/images/07.webp)

::: image-caption
图 3 PF-LLM 方法总览，(a) 利用架构仿真得到的真实预取策略作为标注，微调 PF-LLM 大语言模型；(b) 训练完成的 PF-LLM 从应用程序的汇编代码中，离线生成预取提示；(c) LMHint 硬件预取器在程序运行时，加载并利用这些预取提示做出精准的预取决策。
:::

PF-LLM 的整个工作流程如图 3 所示，可以分为三个阶段：

1. **数据集生成（Ground Truth）**：使用架构模拟器，通过暴力方式（对所有可能的预取器配置进行模拟），找到每个加载指令（PC）在理想情况下的最优预取策略，作为“标准答案”。
2. **模型微调（Fine-tuning）**：用包含汇编代码上下文和对应“标准答案”的数据集，对一个小型但强大的代码大模型（Qwen-2.5-Coder-0.5B）进行微调，使其学会“阅读代码，并预测策略”。
3. **离线推理与在线执行（Inference & Runtime）**：用微调后的 PF-LLM 模型，为任何一个新程序的二进制文件生成“预取提示表（Prefetch Hint Table）”。运行时，一个轻量级的硬件预取器 LMHint Prefetcher 加载这张表，并据此指导其在线行为。

### 2.1 PF-LLM 模型：一个会“看汇编”的预言家

> PF-LLM 选择了 Qwen-2.5-Coder-0.5B-Instruct 作为基座模型。:mdnice-bold-italic[这个选择非常明智：0.5B 的参数量保证了推理速度足够快，同时在代码任务上表现出色]。模型输入是围绕目标加载指令的 257 行汇编代码（目标指令前后各 128 行）。**为什么选择汇编而不是源代码？作者的理由很充分：**

- 通用性：直接适用于任何编译好的二进制文件，即使没有源代码也能用。
- 精确性：汇编代码直接反映了硬件的运行时行为，没有编译器优化带来的额外抽象，与最终需要输出的硬件提示（Hints）关系更紧密。

模型输出是一个结构化的 JSON 对象，包含三个关键的“提示（Hints）”：

- `PFSel` (预取器选择)：指定由哪个子预取器来为这个加载指令发起预取请求。
- `PF Degree` (预取度)：控制所选预取器的激进程度。这是一个归一化的值（1、2、3），会被映射到每个子预取器自身的度数范围内。例如，对于 DSPatch（度数范围 0-64），PF Degree=3（激进）会被映射为约 48。
- `Filter` (需求请求过滤)：指定一个子预取器，不要把这条加载指令的“需求请求”发送给它，从而避免用不相关的数据“污染”它的内部状态。

> 为了让模型能准确学习，作者设计了一个精巧的 Prompt 模板，见下图。

![文章插图](/articles/2026-03-31-llm-cpu-cpu-95-ipc-53d03cb8/images/08.webp)

::: image-caption
代码清单 PF-LLM 训练的提示模板。该提示模板是 PF-LLM 微调的关键设计，基于 Qwen-2.5-Coder 的官方对话模板，保证了模型的训练收敛效率；将和设为特殊令牌并加入模型嵌入表，让模型能精准定位加载指令，避免了代码理解的歧义。结构化的 JSON 输出要求，让模型生成的预取提示能直接被硬件解析，避免了后续的格式处理开销。系统提示直接明确任务目标，让模型无需学习通用代码理解，而是聚焦于预取策略预测，充分利用了 LLM 的零样本能力，大幅减少了所需的训练数据量，也是模型能快速收敛至 95% 预测准确率的重要设计原因。
:::

这个模板不仅告诉了模型任务是什么，还通过`<load>`和`</load>`标签精准地定位了目标指令，并且要求输出 JSON 格式，大大降低了模型的“学习难度”，加速了收敛。

### 2.2 数据集生成：暴力模拟，寻找“标准答案”

> 如何得到每个加载指令的“标准答案”？这是训练模型的关键。作者采用了一种“暴力美学”式的方法：

1. **针对每个基准程序，对 “子预取器” × “预取度” 的每一种组合运行一次完整模拟**。例如，对于支持度数控制的预取器，我们按 3 档度数（保守、适中、激进）分别模拟；对于不支持度数控制的预取器，则只模拟单次。:mdnice-bold-italic[整体模拟次数根据预取器特性动态确定，确保每种配置都被覆盖。]
2. **每次模拟，记录下每一条加载指令（通过 PC 识别）的平均内存访问时间** （AMAT）。AMAT 是衡量内存系统性能的关键指标，越低越好。
3. 对于每条加载指令，在所有模拟结果中，选出 AMAT 最低的那组配置，其对应的预取器类型和度数就是“最优策略”。同时，选出 AMAT 最差的那组配置，其对应的预取器就是要“过滤”的对象，除非该预取器内部状态太复杂，比如 Pythia。

![文章插图](/articles/2026-03-31-llm-cpu-cpu-95-ipc-53d03cb8/images/09.webp)

::: image-caption
表 1 数据集生成过程。针对每个加载程序计数器，从平均内存访问时间最优的配置中选取最佳预取器类型及预取程度；从平均内存访问时间最差的配置中筛选出待剔除的预取器。该表格是 PF-LLM 训练数据集的核心生成依据，通过对每个加载指令的程序计数器（PC）遍历不同预取配置，以平均内存访问时间（AMAT）为核心性能指标，筛选出最优预取策略和需过滤的最差策略，作为模型的标注数据。
:::

这样一来，PF-LLM 的训练数据集就完美地包含了“上下文”和“答案”。需要注意的是，训练数据集来自 SPEC 2006 基准程序，而 SPEC 2017 完全保留用于最终测试，确保模型从未见过测试程序。

### 2.3 LMHint Prefetcher 硬件：执行“上帝旨意”的执行者

> PF-LLM 生成的所有提示，最终会被加载到内存中的一张大表——预取提示表（Prefetch Hint Table, PHT）中。PHT 以加载指令的虚拟 PC 为索引，每个条目存储一个 8 位的提示数据（4 位选预取器，2 位选度数，2 位选过滤器）。

**运行时，为了低延迟访问，LMHint Prefetcher 在片上设计了一个 256 项 的预取提示缓冲区** （Prefetch Hint Buffer, PHB），用于缓存最近使用的提示条目。:mdnice-bold-italic[其功能类似 TLB 缓存页表项，但 PHB 缓存的是 PC 到预取提示的映射]，而非地址翻译。当一条加载指令执行时，用它的 PC 快速查询 PHB：

- 命中：立即获取其对应的提示，并据此控制子预取器。只有被选中的子预取器才能为这个指令发起预取；同时，被指定的子预取器将不会收到这个需求请求（用于训练）。
- 未命中：向内存中的 PHT 发送一个填充请求，在此期间使用一个默认策略。

::: block-1
**这个硬件设计非常精简，确保了它能够以单周期甚至更少的延迟完成查表操作**，完全不会成为 CPU 流水线的瓶颈。
:::

## 四、相关工作：对比与定位

> 为了更清晰地理解 PF-LLM 的贡献，我们可以将其与以下三类相关工作进行对比：

- **传统的硬件预取器**：如 Stride、Stream、Sandbox 等。它们是纯粹的在线硬件，仅依赖运行时的地址流，无法理解程序的高层语义。:mdnice-bold-italic[PF-LLM 则通过离线分析获得了这种语义理解能力。]
- **编译器/Profile-Guided 的软件预取**：如 GCC 的自动预取或 RPG2。它们也是离线分析，但严重依赖于源程序或特定的输入数据，且只能插入预取指令，无法对硬件预取器进行控制。:mdnice-bold-italic[PF-LLM 的分析对象是二进制，且通过“提示”控制的是硬件的多个预取器，而非直接注入指令。]
- **集成式预取器**：如 Alecto、DOL。它们试图在线学习，但受限于硬件复杂度和收敛速度。:mdnice-bold-italic[PF-LLM 将“学习”完全离线，在线部分仅负责执行，从根本上解决了这两个问题。]

::: block-1
从图 5（b）和图 7 中可以看到，:mdnice-bold-italic[Alecto 等集成方法的性能甚至不如最好的单预取器。这是因为它们的在线学习逻辑在面对复杂的空间预取器时，反而会破坏其内部状态]。PF-LLM 通过“过滤”提示，完美地避免了这一问题。
:::

## 五、未来展望与挑战

> PF-LLM 开创性地展示了 LLM 指导硬件微架构的巨大潜力，但这仅仅是开始。展望未来，还有许多问题值得探索：

- 通用性与扩展性：如何训练一个能适应不同缓存大小、内存带宽等机器配置的通用模型？**也许可以将机器配置作为额外的 Prompt 输入。**
- 新指令集的支持：本文仅验证了 x86-64。对于 ARM、RISC-V 等其他 ISA，可以通过微调或迁移学习来适应。
- 应对 ASLR 和 JIT：:mdnice-bold-italic[如何处理地址空间布局随机化（ASLR）？论文提出了一种可行方案：与 OS 加载器协同，对提示表也应用同样的随机化偏移。但需要注意的是，当前原型尚未实现这一机制，属于未来工作方向]。对于 JIT（即时编译），则可能需要在更底层的 IR（中间表示）上进行分析。
- 更广阔的领域：**既然 LLM 能指导预取，那是否也能用于指导分支预测、缓存替换、甚至乱序执行调度？** 这为未来的“AI for Architecture”研究打开了一扇新的大门。
