## 关键问题

### 问题一：针对系统设计假设与理论完备性

> 论文中提出**使用指数衰减函数 $f(t) = e^{-\lambda t}$ 来平衡 KV 缓存保留与重计算成本之间的权衡，并假设工具执行时间具有“无记忆性”**，即剩余时间与已执行时间无关。然而，**实际智能体系统中的工具调用（如远程 API、编译器、容器启动）往往表现出长尾或重尾分布**，论文作者也承认这一点。请问：:mdnice-bold-italic[在不满足无记忆性假设的现实场景下，指数衰减函数是否仍然是最优选择？] 如果不是，ThunderAgent 是否具备自适应调整衰减形式的能力？

首先，**作者承认工具执行时间的不可预测性，并指出这正是现有系统（如 Continuum）基于固定 TTL 策略失效的原因**。ThunderAgent 的核心创新在于将调度建模为成本优化问题，用衰减函数动态降低长时间闲置 acting 程序的缓存权重，从而在内存紧张时允许其被驱逐。:mdnice-bold-italic[虽然理论推导基于无记忆性，但实际实现中采用离散时间的几何衰减 $f(k)=x^{-k}$（实验中取 $x=2$），这一形式仍保留了“时间越长，优先级越低”的基本性质]。**实验表明，在高度随机的工具调用场景下，如下图 4c、4f，ThunderAgent 的吞吐量仍优于 Continuum 和 vLLM，说明即使近似最优，也能获得稳健收益。**

然而，论文并未提供自适应调整衰减参数或函数形式的机制。:mdnice-bold-italic[衰减底数 $x$ 和检测周期 $\Delta t$ 是静态超参数（见 5.4 节消融实验），需人工设定。这意味着若工作负载的统计特性发生剧烈变化，静态配置可能导致次优权衡。尽管如此，ThunderAgent 的调度器通过周期性内存压力检测（式 7）和状态感知优先级（式 10、11），已具备对实时负载的响应能力，一定程度上缓解了固定衰减函数的局限性]。未来工作可探索基于在线学习的自适应衰减，例如根据历史工具延迟分布动态调整 $\lambda$ 或切换函数形式，但这已超出当前论文范围。

综上，指数衰减在无记忆性假设下最优，但现实偏差下仍为有效近似；ThunderAgent 目前依赖静态超参数，缺乏自适应，但实验证明其鲁棒性，且系统设计为未来扩展留有余地。
:::

### 问题二：针对调度策略的最优性与可解释性

> 论文中提出的“最短优先驱逐策略”（shortest-first eviction）声称能最小化重计算成本，其依据是重计算成本与上下文长度的平方成正比（Lemma 4.1）。然而，**该策略忽略了工具执行阶段中可能存在的未来复用频率** （例如某些程序虽短但即将频繁调用工具，某些程序虽长但即将终止）。在实际多轮智能体工作流中，:mdnice-bold-italic[是否可能存在一种情况，即驱逐一个较长的但即将终止的程序，反而比驱逐多个较短的活跃程序更优？如果存在，ThunderAgent 是否考虑了这种未来行为预测，还是完全依赖当前状态做决策？]

首先，论文的证明仅针对**单次** 重计算成本，**未考虑未来多次调用** 的累积成本。但 ThunderAgent 的调度并非一次性的：程序被驱逐后，当再次需要时会重新恢复，恢复后的重计算成本仍按当前长度计算。若短程序未来多次被驱逐和恢复，其总重计算成本可能超过长程序的一次成本。然而，由于短程序的长度平方远小于长程序（例如 $100^2=10^4$ 对比 $1000^2=10^6$），**即使短程序被驱逐 10 次，总成本仍低于长程序一次。因此，从数量级看，最短优先策略在累积成本上仍可能占优。**

更重要的是，ThunderAgent 的调度策略并非仅依赖长度，还融入了**执行状态** （$\tau$）优先级：暂停时优先选择 Acting 程序 $S_{\text{pause}}$ 含 $\mathbb{I}(\tau=\mathbf{A})$，恢复时优先选择 Reasoning 程序 $S_{\text{restore}}$ 含 $\mathbb{I}(\tau=\mathbf{R})$ 。这一设计隐含了对未来活跃度的考量：

- Reasoning 程序即将生成下一个动作，可能很快进入工具调用，保留其缓存有助于减少即将发生的重计算；
- Acting 程序正在等待外部工具，其返回时间不确定，优先暂停它们可避免闲置缓存占用。

**这种状态感知在一定程度上缓解了“忽视未来复用”的问题**，因为频繁调用工具的程序往往在 Reasoning 和 Acting 之间快速切换，其处于 Reasoning 时会被优先保留，而处于 Acting 时虽可能被驱逐，但若其工具调用时间很短，衰减函数 $f(t)$ 会使其权重下降缓慢，驱逐概率降低。

::: image-caption

此外，论文未假设未来行为可预测，因此无法将未来复用频率纳入优化目标。**实际系统中，精确预测程序未来行为极为困难，容易导致误判**。ThunderAgent :mdnice-bold-italic[采用贪心策略，结合状态优先级，已在多种工作负载下取得显著性能提升见图 4]。未来若能引入轻量级预测模型（如基于历史调用模式），则可能进一步优化，**但当前设计已足够高效且鲁棒。**

## 一、引言

> 语言模型的最新进展使其应用范围从基础聊天机器人拓展至复杂的智能体[20,26]。这些智能体通过将长推理过程与外部工具调用（如编译器、检索器）相结合，解决代码开发[7,9]、计算机操作[2,24]等领域的实际问题，通常作为自治系统运行，无需实时人工干预即可执行多步骤工作流。

然而，随着待处理的智能体请求数量增加，现代推理系统的吞吐量会显著下降（图 1a）。同时，在强化学习（RL）中，滚动推理环节的耗时占总壁钟时间的 70%以上[4,17]。

随着智能体工作流在规模上的自治性不断提升：

- **系统整体效率由持续吞吐量决定，而非尾延迟**；
- 而有人工参与的应用则通常受用户响应时间主导。

因此，**更高的吞吐量能通过在更多已完成的工作流中分摊硬件成本**，直接降低服务开销。此外，在异步强化学习中，更高的滚动推理吞吐量能缓解数据收集所用参数与待更新参数之间的策略滞后问题。这使得模型能从时效性更强的数据中学习，同时提升收敛速度和最终策略质量[4,16,17,32]。

然而，**当前的智能体推理系统吞吐量表现欠佳，原因在于其由独立组件松散组合而成**：一个现成的模型推理引擎，如 vLLM[10]或 SGLang[33]，与一个通用工具编排器（如 Kubernetes）耦合:mdnice-bold-italic[。尽管智能体工作流涉及多轮模型和工具请求，但这些组件基于单个请求分别调度和分配资源，缺乏对整个工作流的端到端认知]。该设计带来了三个核心挑战：

| 核心挑战 | 详细说明 |
| --- | --- |
| 键值缓存抖动 | 基于请求感知的系统会在工具执行阶段过早地淘汰键值缓存，无法预见其在智能体工作流中的未来复用性。因此，当工具调用完成后，系统需要重新执行预填充（prefill，大语言模型推理中对输入上下文的首次计算过程）来恢复完整的交互历史。重新预填充的开销会使智能体工作流的平均端到端延迟增加高达 7.14 倍（见图 1b），并降低吞吐量。 |
| 跨节点内存失衡 | 在多节点推理部署中，基于请求感知的引擎存在资源利用率失衡问题。现有引擎会将同一智能体工作流的所有请求固定到单个节点，以最大化键值缓存命中率。但由于智能体工作流中的上下文长度会快速且不可预测地增长，在该路由策略下，部分节点会达到内存容量上限，而其他节点则处于低利用率状态。 |
| 工具生命周期感知缺失 | 基于请求感知的编排器难以确定何时释放和准备工具执行所需的资源与环境。因此，未使用的沙箱和应用程序接口（API）服务器会持续占用关键的磁盘空间和网络端口，导致资源累积耗尽并引发系统故障。同时，智能体工作流在开始推理前，需要等待极长的环境准备时间。 |

> 本研究提出 ThunderAgent，这是一款对智能体工作流具备端到端认知的智能体推理系统，能够实现高吞吐量的智能体服务和强化学习滚动推理。我们的具体贡献如下：

| 具体贡献 | 设计内容 |
| --- | --- |
| 程序抽象 | **将智能体工作流抽象为智能体程序，作为一级调度单元，可跨多次模型调用和工具执行持续存在，并向运行时暴露语义状态**。程序会跟踪工作流标识符、执行阶段（推理或动作）、调度状态、总令牌数和工具资源等元数据。:mdnice-bold-italic[该抽象将调度与执行后端（如 vLLM/SGLang）解耦，支持新工作流的无缝集成。] |
| 程序感知调度器 | **基于程序抽象，将智能体推理调度转化为带约束的优化问题**，在 GPU 内存容量限制下，最小化重新计算和缓存开销，最大化预填充和解码吞吐量。包含两个核心机制：（a）状态感知暂停：执行后端面临内存压力时，选择性暂停处于工具调用动作阶段的工作流，为推理阶段程序保留内存，避免非最优的键值缓存淘汰。（b）动态迁移：在数据并行（DP）GPU 节点间迁移智能体程序，所有数据并行节点共享全局程序感知等待队列，避免固定路由带来的内存失衡。 |
| 程序感知工具资源管理 | 针对长周期智能体工作负载，将 I/O 密集型的环境初始化与大语言模型推理过程重叠执行；对已完成程序，通过生命周期感知的垃圾回收器，利用程序终止信号回收 Docker 沙箱、网络端口等工具资源，防止资源累积泄漏，保障智能体推理持续高吞吐量。 |

上述贡献无法在基于请求感知的推理引擎中实现。若没有对程序状态和工作流依赖关系的显式表示，请求感知调度器无法区分工具的临时等待和任务终止，也无法协调GPU内存与程序级的资源调度。

## 二、研究背景

在本节中，我们将介绍支持智能体推理的特性和现有方法。

### 2.1 现有智能体工作流的系统特性

**当前的智能体工作流在生成过程中会在推理和动作阶段之间交替**。形式化地，在每个步骤 $t$，智能体接收一个观测值 $o_{t} \in O$，并生成一个输出 $e_{t}=(\ell_{t}, a_{t}) \in L ×A$，其中 $\ell_{t}$ 表示推理思考过程，$a_{t}$ 表示执行的动作。我们将步骤 $t$ 的累积上下文定义为 $c_{t}=(o_{1}, e_{1}, ..., o_{t})$，其记录了智能体工作流的交互历史。基于累积上下文 $c_{t}$，输出 $e_{t}$ 从策略 $\pi(e_{t} | c_{t})$ 中采样得到。

该工作流包含两个持久化状态：

1. GPU内存，其中 $c_{t}$ 对应的键值缓存作为工作流的内存。随着轨迹的增量式增长，$c_{t+1}$ 以 $c_{t}$ 为前缀进行扩展，理论上实现了步骤间近乎完全的键值缓存复用率。
2. 工具环境，在 $t=1$ 时初始化的外部资源（如沙箱、数据库连接）必须在整个执行过程中保持一致且可访问。

这些有状态的依赖关系要求从程序层面看待智能体推理轨迹，从而使系统能够协调异构资源，并在长时间运行的工作流中管理状态。**然而，现有推理系统将每个推理思考 $\ell_{t}$ 和动作 $a_{t}$ 都视为独立的、无状态的请求。**

### 2.2 现有智能体推理系统

> 现有研究主要关注优化智能体推理中的单个组件，包括大语言模型推理引擎或工具编排器，但极少有研究针对跨GPU、中央处理器（CPU）和远程资源的智能体工作流进行端到端优化。我们对这些现有系统进行综述。

Autellix 将多轮智能体工作流建模为纯GPU程序，并在中央进程表中跟踪累积的GPU执行时间[13]。但:mdnice-bold-italic[该系统忽略了工作流的局部性，允许并发工作流随意淘汰其他工作流的键值缓存，在高工作负载下引发键值缓存抖动。]

Continuum 是另一款近期推出的、专为多轮智能体工作流设计的服务系统[11]。它采用生存时间（TTL）机制将键值缓存固定在高带宽内存（HBM）中，从而缓解工具执行过程中的上下文抖动。:mdnice-bold-italic[但该系统仍无法解决键值缓存淘汰问题。原因之一是大多数工具的执行时间不可预测]。由于生存时间的估计误差，这类:mdnice-bold-italic[不可预测的工具会在 Continuum 中引发严重的缓存抖动和键值缓存内存闲置问题]。此外，一旦运行中工作流的解码内存超过GPU限制，系统会抢占并淘汰已固定的键值缓存，这会导致不可避免的缓存抖动，以及图 1a 中所示的吞吐量下降。

## 三、现有智能体推理系统的挑战

本节以 vLLM 与 Kubernetes 的组合为代表，分析多轮智能体推理的基准系统，并归纳其核心效率问题。值得注意的是，**这些局限性无法通过替换推理引擎（如 TensorRT、SGLang）或工具编排器解决，而是需要新的程序感知抽象**。默认情况下，我们在两个 8×H100 GPU节点上，基于 GLM-4.6 模型对 OpenHands 的强化学习滚动推理进行测试。

### 3.1 键值缓存抖动

> 智能体工作流在执行过程中理论上具备极高的键值缓存复用率。但在现有的大语言模型服务系统中，每个步骤都被当作独立的无状态请求处理。在高并发场景下，这种基于请求级的调度会导致键值缓存在工具执行阶段被频繁淘汰，以容纳新到达的请求，进而引发反复的缓存淘汰和重新预填充，我们将此现象称为键值缓存抖动。

### 3.2 跨节点内存失衡

> 当前在数据并行（DP）节点间的请求路由策略同样非最优。现有的多轮调度器[21,33]会贪婪地将请求分配至键值缓存局部性最高的目标数据并行节点，以最大化缓存复用率。但**该策略忽略了节点间的内存负载可能失衡这一事实**。

- 例如，vLLM 中的键值感知路由器[21]会将同一智能体工作流的所有请求发送至同一个节点。**由于不同工作流的键值缓存占用空间和执行时长存在高度异构性，该策略往往会导致节点间的内存严重失衡**，部分节点负载过高，而其他节点则利用率低下。
- 类似地，SGLang 中的前缀感知路由器会贪婪地将工作负载路由至存在匹配前缀的节点，以最大化缓存命中率。**由于智能体系统的提示词在所有工作流中均相同，该策略会将几乎所有请求发送至同一个节点，而其他节点则处于空闲状态。**

- 4.2 节将形式化定义一个成本模型，为系统设计提供指导；
- 基于这些基础，我们将在 4.3 节详细阐述键值缓存调度策略；
- 在 4.4 节介绍工具资源管理策略。

### 4.1 程序抽象

> 智能体程序是一种基础抽象，封装了智能体工作流的逻辑执行流程和系统级依赖关系。形式化地，我们将智能体程序 $P$ 定义为一个元组：

$$
P=< ID,c,{\mathcal {T}},{\mathcal {L}},\tau ,s> \tag{1}
$$

其中：

- $ID$ 表示全局唯一标识符；
- $c$ 表示上下文中的令牌数量，对应程序活跃执行时的键值缓存内存占用；
- $\mathcal{T}$ 跟踪程序使用的工具环境集合，以便在无程序需要这些环境时进行垃圾回收；
- $\mathcal{L}$、$\tau$ 和 $s$ 分别表示节点部署位置、执行阶段和调度状态，助力实现程序级的键值缓存抖动缓解和跨节点迁移。

### 4.2 成本模型

> 在多轮智能体推理过程中，只有用于活跃预填充和解码的资源会对系统的有效吞吐量产生贡献，而重新计算、已用容量和空闲缓存均属于资源浪费。

我们将这一特性融入GPU资源消耗的成本模型中，将有效成本与非生产性使用成本分离。我们采用时空积（STP）[1]作为核心度量指标，其定义为内存占用随处理时间的积分。某个处理阶段的时空积成本形式化定义为：

$$
Cost_{x}=\int_{0}^{t_{x}} M_{x}(t) d t \tag{2}
$$

其中，$t_{x}$ 为处理过程 $x$（如预填充）的持续时间。由于内存使用量 $M_{x}(t)$ 可通过大语言模型中使用的键值缓存令牌数直接量化，我们将成本模型定义为令牌数随时间的积分。

::: block-1
智能体推理的总成本包含五个不同的组成部分：解码成本、预填充成本、重新计算成本、闲置容量成本和空闲缓存成本。**我们明确区分了针对工具执行结果的增量预填充和针对历史交互的重新计算，后者因需要对整个上下文的淘汰键值缓存重新计算，会产生显著更高的成本。**
:::

形式化地，总成本分解如下：

$$
Cost_{total}\approx Cost_{decode}+Cost_{prefill}+Cost_{recompute}+Cost_{unused}+Cost_{caching} \tag{3}
$$

在该分解式中， - $Cost _{decode }$ 和 $Cost _{prefill }$ 代表对推理吞吐量有贡献的有效工作成本；
- 其余项为系统的浪费性开销：$Cost _{recompute }$ 由键值缓存抖动引发（3.1 节）；
- $Cost _{unused }$ 反映了数据并行（DP）推理后端副本间的内存失衡（3.2 节）；
- $Cost _{caching }$ 是外部工具执行过程中内存占用的累积成本（3.3 节）。

### 4.3 调度策略

> 基于上述成本模型，我们调度策略的优化目标是最小化非生产性开销组件：$Cost _{recompute }$、$Cost _{unused }$ 和 $Cost _{caching }$，从而最大化吞吐量。

#### 4.3.1 通过程序感知等待队列降低重新计算和缓存成本

> 如 3.1 节和图 1b 所述，键值缓存抖动是吞吐量下降的主要瓶颈。为解决该问题，系统必须通过显式控制活跃程序的数量来最小化 $Cost _{recompute }$。ThunderAgent 通过引入程序感知等待队列实现这一目标。

系统利用该队列调度程序执行，根据程序的令牌长度 $c$ 和执行阶段 $\tau$，决定哪些程序在GPU中执行、哪些程序被换出。在此，我们通过两个基本操作形式化定义调度器的行为：恢复（Restore）和暂停（Pause），具体如下：

- 恢复（Restore）：该操作将程序接入活跃执行状态。对于一个调度状态 $s = \text{Paused}$ 且部署位置 $\mathcal{L}=ø$ 的程序 $P=< ID, c, \mathcal{T}, \mathcal{L}, \tau, s>$，执行 $\text{Restore}(P)$ 会将程序 $P$ 分配至有可用容量的后端 $\mathcal{L}'$，并更新程序状态：$P \leftarrow\left< ID, c, \mathcal{T}, \mathcal{L}', \tau, \text{Active} \right> \tag{4}$
- 暂停（Pause）：该操作将程序从活跃执行状态移除。对于一个调度状态 $s = \text{Active}$ 的程序 $P=< ID, c, \mathcal{T}, \mathcal{L}, \tau, s>$，执行 $\text{Pause}(P)$ 会将程序 $P$ 与后端解耦，释放其键值缓存以供抢占，并更新程序状态：$P\leftarrow < ID,c, \mathcal{T},ø ,\tau ,\text{Paused}> \tag{5}$

> 基于这两个操作，我们接下来介绍用于最小化键值缓存抖动的调度策略。

##### 调度策略1：周期性抖动检测

4.1 节的程序抽象为我们提供了动作阶段程序的键值缓存大小，这是请求级系统无法实现的（见 3.1 节）。我们**将数据并行后端 $\mathcal{L}$ 的抖动条件定义为程序内存需求超过总容量的状态**：

$$
C_{total }<\sum_{p \in \mathcal{L}} c_{p} \tag{6}
$$

其中，$C_{total }$ 表示后端 $\mathcal{L}$ 的键值缓存池固定令牌容量。在解码过程中，智能体工作流的上下文长度 $c_{p}$ 会快速增长，即使没有新请求到达，也可能在执行过程中触发内存抖动。与基准调度器（如Continuum）仅在工作流到达时检查是否接入的方式不同，**我们实现了一个周期性监视器，以固定时间间隔 $\Delta t$ 评估内存使用情况**，从而能够抢先检测并缓解由上下文增长引发的内存压力。

- :mdnice-bold-italic[当键值缓存抖动即将发生时，ThunderAgent 会调用暂停操作挂起活跃程序，释放内存空间]$\Delta C=\sum_{p \in L} c_{p}-\lambda_{max } \cdot C_{total }$，直到总内存使用量降至阈值 $\lambda_{max } \cdot C_{total }$ 以下。
- :mdnice-bold-italic[当后端存在可用空间，即 $\sum_{p \in L} c_{p}<\lambda_{min } \cdot C_{total }$ 时，ThunderAgent 会通过恢复操作从等待队列中恢复暂停的程序，确保恢复后的程序总内存占用低于]$\lambda_{max } \cdot C_{total }$。其中，$\lambda_{max }$ 和 $\lambda_{min }$ 分别表示内存使用的高、低水位线，二者共同构成一个迟滞窗口，使调度过程更稳定。在实际应用中，我们将两个值均设为 1，因为程序间的共享提示词会隐式保留足够的内存缓冲区。

**通过这种程序级的周期性容量检查，ThunderAgent 能够通过为动作阶段的活跃程序保留内存，保证无键值缓存抖动发生**。:mdnice-bold-italic[但这一设计存在权衡：当程序执行长时间的工具调用时，动作阶段程序占用的GPU内存会处于空闲状态]。为平衡缓存成本和重新计算成本，:mdnice-bold-italic[我们在抖动检测中融入时间衰减机制，逐步降低动作阶段程序令牌的有效权重。这使得调度器能够在内存压力上升时，淘汰长期空闲的缓存，而非无限期持有：]

$$
C_{total}<\sum _{p\in \mathcal {L},\tau =R}c_{p}+\sum _{q\in \mathcal {L},\tau =A}c_{q}× f(t_{q}) \tag{7}
$$

具体而言，$t_{q}$ 为程序 $q$ 在当前步骤的工具执行时间；$f(t)$ 是一个时间衰减函数，用于平衡 $Cost _{caching }$ 和 $Cost _{recompute }$。通过动态降低动作阶段程序随时间的有效内存优先级，$f(t)$ 鼓励调度器淘汰持续空闲的缓存。

##### 调度策略2：通过最短优先淘汰最小化 $Cost _{recompute }$

基于上述淘汰和恢复条件，**处理缓存抖动的剩余问题是确定暂停哪一部分活跃程序，以最小化重新计算成本**。在本节中，我们证明淘汰键值缓存尺寸最小的程序能得到最优解。

---

引理 4.1（二次重新计算成本）：对于一个上下文长度为 $c_{i}$ 的程序 $P_{i}$，重新预填充其键值缓存产生的重新计算成本与 $c_{i}$ 呈二次方关系，即：

$$
Cost _{recompute }=\int_{0}^{t_{recompute }} c_{i}(t) d t \propto c_{i}^{2} \tag{8}
$$

定义 4.1（淘汰优化问题）：基于引理 4.1，在需要释放内存空间 $\Delta C$ 的情况下，调度器需选择一个程序子集 $S$ 进行淘汰，使得释放的容量满足约束条件，同时最小化总重新计算成本。该优化问题形式化定义为：

$$
min _{S} \sum_{i \in S} c_{i}^{2} \quad s.t. \quad \sum_{i \in S} c_{i} \geq \Delta C \tag{9}
$$

**该目标函数的严格最小值可通过选择更小的 $c_{i}$ 实现。因此，ThunderAgent 的策略是贪婪地暂停并淘汰上下文长度最短的程序**。基于上述分析，我们在调度器中采用以下分数作为程序恢复和暂停的依据：

$$
S_{restore }(P)=\frac{1}{c_{P}}+\mathbb{I}(\tau=R) \tag{10}
$$

$$
S_{pause }(P)=\frac{1}{c_{P}}+\mathbb{I}(\tau=A) \tag{11}
$$

其中，指示函数 $\mathbb{I}(\cdot)$ 强制将程序的执行状态 $\tau$ 置于上下文长度之上进行严格优先级排序。两种机制均遵循最短优先策略以最小化重新计算成本，而状态指示符确保调度器优先暂停动作阶段的程序（从而回收缓存内存，最小化 $Cost _{caching }$），同时优先恢复推理阶段的程序（从而最大化 $Cost _{decode }+ Cost _{prefill }$）。

> 3.1 节和图 2a 表明，节点间的内存失衡会产生显著的 $Cost _{unused }$，导致即使其他节点有足够的内存容量，程序仍会被不必要地暂停。为此，ThunderAgent 将所有后端副本的等待队列统一为一个全局程序感知等待队列。

**该设计的核心动机是：只有当部分副本存在空闲内存，而暂停的程序仍停留在等待队列中时，才会产生 $Cost _{unused }$。此外，一旦程序被暂停，其键值缓存会被视为已淘汰，因此重新计算成本与节点无关**。这使得我们能够在不牺牲键值缓存局部性的前提下，改善跨节点的内存平衡。恢复策略与负载均衡对齐，而非严格的键值感知路由，允许暂停的程序被调度至任何有可用内存容量的副本。因此，全局队列将闲置成本限制为：在时间间隔 $\Delta t$ 内，每个节点的 $C_{unused }< c_{min } \cdot \Delta t$（注：因 $\Delta t$ 远小于程序的生命周期，我们忽略单个时间间隔内已终止程序的影响），其中 $c_{min }$ 表示暂停程序中的最小令牌长度。图 3 展示了 ThunderAgent 中调度策略和全局等待队列的整体架构。

### 5.1 实验设置

基准测试和工作流。我们针对多样化的基准测试和工作负载评估 ThunderAgent：

1. 编码智能体服务。我们在 SWEBench-Lite [9] 数据集上部署 OpenHands 和 mini-SWEAgent。OpenHands 代表一个初始化负载很重的工作流，每个沙箱的平均磁盘占用超过 10GB，而 mini-SWEAgent 是一个轻量级工作流，占用空间很小（≈2GB）。
2. 其他智能体服务。我们在 HLE [15] 上应用 ToolOrchestra，在 ScienceAgentBench [3] 上应用 OpenHands。这些工作负载涉及由外部 API 调用和复杂科学模拟驱动的可变延迟。
3. RL 数据收集与策略生成过程。我们在两个 8× H100 节点上对相同的模型、工作流和样本应用 RL 数据收集与策略生成过程。

模型和部署。

- 我们使用 GLM-4.6 (355B) [20] 和 Qwen-3 (235B) [26] 模型，结合 OpenHands [23] 和 mini-SWEAgent [27] 框架。
- 模型被量化为 FP8（8 位浮点数格式），并在 8×H100 节点上应用张量并行。对于 ToolOrchestra [18]，我们使用搭载在一个 RTX 5090 上的 Qwen3-8B 模型，采用 FP16 精度。
- 我们将 LLM 推理引擎和 Docker 部署在不同的集群中。LLM 推理引擎在承载模型的 GPU 集群上运行，而智能体 Docker 环境则被卸载到一个专用的 CPU 集群。

ThunderAgent 配置。我们使用超参数 $\Delta t = 5$ 和优先级衰减函数 $f(t) = 2^{- t}$（在第 4.3 节中定义）来配置 ThunderAgent。vLLM 被用作我们的 LLM 推理引擎。我们使用每分钟步数作为吞吐量指标，其中一步包括工作流的一个推理和行动周期。

> 基线。我们与具有不同调度范式的最先进系统进行比较：

- vLLM (推理)：一个广泛采用的、请求感知的 LLM 推理引擎，作为无状态基线来评估推理性能，不包含任何智能体或程序特定的感知能力。
- Continuum (推理)：当前用于多轮智能体工作流的最先进系统。它通过预测工具执行持续时间并将 KV 缓存（键值缓存，用于存储注意力机制中的中间状态以减少重复计算）相应地固定在 HBM（高带宽内存，GPU 上的高速内存）中，来缓解 KV 缓存抖动。
- vLLM + SGLang Gateway (分布式数据收集与策略生成过程)：大规模分布式 RL 数据收集与策略生成过程的领先解决方案。SGLang Gateway 通过增强跨节点内存平衡和 KV 缓存命中率来优化分布式推理，使得这种组合成为分布式 RL 数据收集与策略生成设置中的一个强基线。

### 5.4 消融研究

图 6 为端到端延迟分解与 ThunderAgent 参数敏感性消融实验结果。(a) 端到端延迟分解：展示了 vLLM 与 ThunderAgent 在解码、环境准备、预填充和磁盘使用方面的延迟对比，ThunderAgent 在各环节均实现显著优化，尤其是预填充延迟从 12 秒降至 0.3 秒；(b) Δt（检测周期）和 f (t)（衰减函数）的消融实验：在单个 H100 节点上，ThunderAgent 离线部署 mini-SWEAgent 并以 GLM4.6 为基础模型，结果显示不同参数设置下 ThunderAgent 均保持高吞吐量，验证了方法的鲁棒性。

关于 $\Delta t$ 和 f(t) 的消融研究。我们研究了检测周期 $\Delta t$ 和衰减函数 $f(t) = x^{- t}$ 的敏感性。图 6b 展示了 ThunderAgent 在单个 H100 节点上使用 GLM4.6 作为基础模型离线服务 mini-SWEAGENT 的结果。:mdnice-bold-italic[我们观察到 ThunderAgent 在不同的参数设置下保持高吞吐量，证明了我们方法的鲁棒性。进一步增加 $\Delta t$ 可能会降低 KV 缓存命中率，从而减少吞吐量，因为抖动可能在检测周期中间发生]。此外，增加 $f(t)$ 中的 $x$ 允许更积极地驱逐行动中的程序，这会以重计算成本换取减少的缓存成本。这会降低吞吐量，因为工具执行时间短的行动中的程序被过早地驱逐了。

## 六、结论

> 我们介绍了 ThunderAgent，一个快速而简单的智能体系统，它建立在程序级抽象之上，该抽象在整个智能体工作流的生命周期中跟踪元数据。

**ThunderAgent 利用程序抽象进行运行时调度和资源管理**。具体来说，:mdnice-bold-italic[ThunderAgent 动态调度跨 GPU 节点的程序执行，以减轻 KV 缓存抖动和内存不平衡，同时管理工具资源以防止资源泄漏。]

实验结果表明，ThunderAgent 在服务方面比以前的系统性能提升 $1.48 - 3.58\times$，在 RL 数据收集与策略生成过程方面提升 $1.79 - 3.92\times$。
