关键词：混合专家模型、**MegaKernel**、:mdnice-bold-italic[RDMA]、**隐藏序列化**、Perseus

> "我们的研究表明，**限制多节点 megakernel 性能的是序列化**，而不是代理式与 GPU-direct 传输之间的选择。"这一来自康奈尔大学 Perseus 论文的核心结论，彻底颠覆了业界对多节点 MoE 推理性能瓶颈的传统认知。

长期以来，混合专家（MoE）架构凭借其参数规模与计算成本解耦的特性，成为了大语言模型规模化的首选方案。:mdnice-bold-italic[从 Qwen3、DeepSeek-V3 到最新的 Llama4，几乎所有前沿大模型都采用了 MoE 设计。然而，随着模型规模的不断增长，单节点 GPU 的显存容量已无法容纳全部专家参数，多节点部署成为必然选择。]

::: block-1
令人意外的是，**在单节点上表现优异的 megakernel 设计，在扩展到多节点时却遭遇了严重的性能崩溃**。论文实验数据显示，:mdnice-bold-italic[通信 bound 的 Qwen3-30B 模型在 8 节点部署时，性能比单节点趋势预测慢了高达 10 倍，且节点数越多，性能退化越严重]。这一问题严重制约了 MoE 模型的规模化部署效率。

通信 bound 即系统的整体执行时间主要由通信（数据传输、网络交互、同步等）决定，而不是由计算（ALU运算）或内存访问（带宽/延迟）决定。
:::

## 一、背景：MoE 推理的性能革命与多节点困境

### 1.1 混合专家模型与专家并行

> 混合专家模型的核心思想是"按需激活"，即每个 token 只激活模型中一小部分专家参数，从而在保持模型容量的同时，大幅降低推理计算成本。

这一设计使得 MoE 模型能够以远低于稠密模型的计算成本，实现更高的模型质量。例如：

- DeepSeek-V3 模型拥有 671B 总参数，但每个 token 仅激活 37B 参数；
- Qwen3-235B 和 Llama4 Maverick 则分别使用了 128 个专家。

然而，MoE 架构的效率优势也带来了独特的通信挑战。:mdnice-bold-italic[由于专家参数被分布在多个 GPU 上，每个 token 必须被路由到其分配的专家所在的 GPU，计算完成后再返回原始 GPU 进行聚合。这一过程被称为专家并行（Expert Parallelism, EP），其核心是两次全局的 all-to-all 通信：分发（dispatch）和合并（combine）。]

专家并行的四个核心步骤如下：

1. 本地门控计算：为每个 token 分配 k 个专家
2. 分发 all-to-all：将 token 发送到对应专家所在的 GPU
3. 专家计算：在接收的 token 上执行两次 GEMM 和激活函数
4. 合并 all-to-all：将专家输出返回原始 GPU 进行加权聚合

::: block-1
在这四个步骤中，**分发和合并通信位于每一层的关键路径上，其延迟直接决定了 MoE 模型的整体推理性能**。随着专家数量和 GPU 数量的增加，通信开销会呈线性增长，成为制约 MoE 模型扩展性的主要因素。
:::

### 1.2 传统 CPU 驱动执行模型的致命缺陷

> 传统的 ML 框架（如 PyTorch）采用 CPU 驱动的执行模型，即由主机 CPU 逐个向 GPU 流提交内核任务，每个内核运行完成后才会启动下一个。

这种执行模型在处理稠密模型时表现尚可，但在 MoE 推理中却暴露出了严重的效率问题。**首先是内核启动开销**：一个简单的 MoE 层可能需要启动数百个短生命周期的内核，每个内核启动都有固定的提交成本。:mdnice-bold-italic[当内核数量足够多时，主机 CPU 无法及时向 GPU 提交任务，导致 GPU SM 长时间处于空闲状态。]

**更严重的问题是集体通信的全局同步屏障**。传统的 all-to-all 集体通信是一个批量同步操作，要求所有 GPU 在开始计算之前完成全部 token 的接收，在开始合并通信之前完成全部专家计算。这种层粒度的序列化完全排除了更细粒度的计算与通信重叠的可能性，而这正是 MoE 推理中最具潜力的性能提升空间。

::: block-1
论文引用的测量数据显示，**在两个 A100 GPU 上进行 MoE 前向传播时，GPU 有 60-90%的时间处于空闲状态，其中内核启动间隙和非重叠的 all-to-all 通信各占了很大一部分**。如此低的资源利用率，显然无法满足大规模 MoE 模型的部署需求。
:::

### 1.3 Megakernel：单节点 MoE 推理的性能革命

> 为了解决传统执行模型的效率问题，一种名为"megakernel"的新设计应运而生。它将整个 MoE 层甚至整个模型融合成一个持久化的 GPU 内核，在 GPU 内部实现任务调度和通信发起。

**Megakernel 设计的核心优势在于实现了 tile 粒度的计算与通信重叠**。它将输入张量划分为固定大小的 tile（例如 128×64），每个 tile 独立地经历分发、计算、合并的完整流程。:mdnice-bold-italic[一旦某个 tile 的输入准备就绪，它就可以立即进入下一个计算阶段，而无需等待其他 tile 完成。]

为了实现这一细粒度的流水线，**megakernel 将 GPU 的协作线程阵列（CTA）划分为不同的角色：**

- 处理器 CTA：负责执行 tile 的计算任务（如 GEMM）
- 操作系统 CTA：包括订阅者和调度器，负责管理 tile 的依赖关系和任务分配

订阅者 CTA 持续轮询远程 GPU 的信号标志，当检测到某个 tile 的数据到达时，通知调度器将该 tile 的计算任务加入就绪队列。调度器则将任务分配给空闲的处理器 CTA 执行。**这种完全在 GPU 内部的任务调度，避免了主机往返的开销，能够实现高达 93%的 SM 利用率，远高于传统 CPU 驱动模型的 9-60%。**

:::

## 二、问题根源：代理式 RDMA 传输中的隐藏序列化

### 2.1 设备发起 RDMA 的两种提交路径

> 为了实现 GPU 内部的通信发起，megakernel 依赖于设备发起的 RDMA（Remote Direct Memory Access）技术。RDMA 允许一个 GPU 直接写入另一个 GPU 的内存，而无需涉及任何一方的 CPU。

设备发起的 RDMA 有两种不同的提交路径：

1. GPU-direct 提交路径：GPU 线程通过 NIC 暴露给 GPU 的硬件接口直接提交请求，无需 CPU 线程参与。典型代表是 NVIDIA 的 IBGDA。
2. 代理式提交路径：GPU 线程无法直接访问 NIC，而是将请求写入主机驻留的队列。一个专用的 CPU 代理线程负责排空队列，并代表 GPU 将请求转发给 NIC。

::: block-1
**虽然 GPU-direct 路径看起来更高效，但它需要特殊的 NIC 硬件支持**，而许多生产环境的网络架构（如 AWS EFA、HPE Slingshot-11 和基于 Broadcom 的云部署）都不支持 GPU-direct。**因此，大多数生产环境中的多节点 megakernel 部署都依赖于代理式提交路径。**
:::

![文章插图](/articles/2026-05-16-10-3-perseus-moe-megakernel-b0604a5b/images/05.webp)

::: image-caption
图 4 | 基于代理的 RDMA 提交路径。GPU 线程将网络请求排入主机驻留缓冲区，专用 CPU 代理将其转发至 NIC。NVSHMEM 每个处理单元（PE）使用单个代理通道，GPU 上所有 CTA 的请求均通过一条共享提交路径传输。该图揭示多节点代理式 RDMA 通信的底层路径，GPU 无法直接访问 NIC，请求需经主机缓冲区中转，单代理通道汇聚所有 GPU 线程请求。MoE 多节点部署时，大量并发传输（如 Qwen3 达 96 笔）挤入单通道，每笔传输的栅栏操作串行化请求，导致 NIC 流水线频繁排空、通信延迟激增，这是通信密集型模型性能断崖式下跌的关键底层原因。
:::

图 4 展示了代理式 RDMA 的提交路径。NVSHMEM（megakernel 最常用的通信库）为每个处理单元（PE，即每个 GPU）分配一个代理通道。GPU 上的所有 CTA 都将它们的网络请求写入这个通道对应的主机队列，代理线程按照 FIFO 顺序排空队列，并逐个将请求提交给 NIC。

在 MoE megakernel 中，每个 PE 需要向每个远程 PE 发送多个传输请求。具体来说，如果总共有 P 个 PE，每个 PE 托管 E/P 个专家，那么每个 PE 在每次分发阶段需要向每个远程 PE 发送 E/P 个传输请求。在 Qwen3-30B 的 4 节点 16GPU 配置中，每个 PE 需要向 12 个远程 PE 各发送 8 个传输请求，总计 96 个并发传输通过单个代理通道提交。

### 2.2 Put-with-signal 与 fence 的必要性

> Megakernel 实现 tile 粒度重叠的关键原语是 put-with-signal。它将数据传输和完成信号组合成一个原子操作，确保接收方只有在数据完全到达后才会开始计算。

put-with-signal 原语执行两个操作：

1. PUT：将数据非阻塞地写入远程对称缓冲区
2. SIGNAL：在数据保证可见后，写入远程 PE 上的一个小标志变量

为了保证 SIGNAL 在 PUT 之后对接收方可见，必须在 PUT 和 SIGNAL 之间插入一个 fence 操作。fence 操作会等待通道上所有先前的 PUT 完成，然后再提交 SIGNAL。

在单节点环境中，传输通过 NVLink 进行，代理不在路径上，因此这个 fence 操作没有可观测的开销。然而，在多节点环境中，代理式传输路径上的 fence 操作却成为了性能杀手。

### 2.3 隐藏序列化的本质与量化分析

> 代理式传输中的 fence 操作会强制代理停止排空新请求，直到通道上所有正在进行的 PUT 都从 NIC 返回完成。这导致了严重的序列化，使得 NIC 无法充分利用其流水线能力。

当多个 CTA 并发提交 put-with-signal 请求时，代理队列中会出现"PUT→FENCE→SIGNAL"三元组的交错。每个 fence 都需要等待它前面的所有 PUT 完成，包括其他 CTA 提交的 PUT。随着并发传输数量的增加，每个 fence 遇到的前置 PUT 数量也会增加，从而导致总的排空成本急剧上升。

**更糟糕的是，单个 fence 的排空成本还会随着节点数量的增加而增长**。因为随着部署规模的扩大，PUT 会指向更多不同的远程目的地，fence 需要等待所有这些目的地中最慢的一个完成，这是一种随着目的地数量增长的尾部延迟。

**图 5 展示了研究人员对 fence 开销的量化分析结果**。从图 5a 可以看到，在 8 节点 96 个并发传输的情况下，耦合 put-with-signal 的吞吐量仅为纯 put 上限的 2%。:mdnice-bold-italic[这意味着，原本设计用于实现细粒度重叠的机制，反而成为了阻碍重叠的最大瓶颈。]

**图 5c 进一步揭示了问题的严重性：在小消息大小下，fence 开销占总通信时间的比例高达 98%；** 即使在 4MB 的大消息下，这一比例仍然高达 19%。而 megakernel 恰恰工作在小消息 regime，因为它将数据划分为小的 tile（例如 128×64 BF16 tile，大小为 16KB）以实现细粒度重叠。

::: block-1
**多节点 megakernel 性能崩溃的根本原因，不是网络带宽不足，也不是代理线程的提交速率不够，而是代理式 RDMA 传输中 put-with-signal 原语所必需的 fence 操作导致的隐藏序列化**。这种序列化在小消息、高并发的 megakernel 工作负载下尤为严重，使得 NIC 的流水线能力几乎完全无法发挥。
:::

::: image-caption
图 6 | 96 个远程专家跨 12 个远程 PE 时，CTA 与代理交互。(a) 原始：每个 CTA 发出 PUT+栅栏+信号，96 次传输全串行。(b) Perseus：阶段 1 连续流水线化 96 个 PUT，NIC 自由流水线处理；阶段 2 发出 96 个信号，仅 12 个携带 NIC 栅栏标志（每组 1 个）。领导者 CTA（★）发出带标志信号；其余继续计算。该图对比原始与 Perseus 的 CTA-代理交互流程，原始模式下 96 笔传输因逐个栅栏完全串行，代理反复阻塞。Perseus 分两阶段执行，先批量提交 PUT 让 NIC 流水线并行处理，再由领导者统一提交带栅栏标志的信号，将栅栏次数从 96 次降至 12 次。非领导者 CTA 无需等待信号提交，可提前回归计算，兼顾通信并行与计算重叠，从流程层面大幅降低序列化开销。
:::

### 2.4 为什么简单的解决方案行不通

> 面对这一问题，人们很自然地会想到一些简单的解决方案，但这些方案都存在致命的缺陷：

1. **批量合并传输**：将多个小传输合并成少数几个大传输，可以减少 fence 的数量。但这会导致信号延迟，接收方必须等到整个批量传输完成后才能开始计算，从而失去了 megakernel 设计所追求的 tile 粒度重叠优势，退回到了传统的粗粒度同步模型。
2. **增加代理并行度**：使用多个代理线程或多个代理通道可以消除单 FIFO 瓶颈。但为了保持 put-with-signal 的语义，需要跨通道的排序机制，这会重新引入同步开销，并且增加了系统的复杂性。

这些方案的失败表明，**问题的核心在于细粒度信令与 fence 序列化之间的根本矛盾**。要解决这个问题，必须同时重新设计信令协议和代理传输层，在保留细粒度重叠的同时，消除序列化开销。

## 三、Perseus 设计：双重机制消除隐藏序列化

### 3.1 核心设计理念

> **Perseus 的核心设计理念是：通过在协议层减少 fence 的频率，在传输层消除每个 fence 的阻塞成本**，从而彻底解决隐藏序列化问题。

针对隐藏序列化的两个来源——fence 数量过多和每个 fence 的排空成本过高，Perseus 提出了两项互补的技术：

1. 解耦信令（Decoupled signaling）：将数据传输与信号分离，按目标 GPU 分组信号，将 fence 数量从每个专家一个减少到每个远程 GPU 一个。
2. NIC 端排序（NIC-side ordering）：将排序执行从软件代理转移到 NIC 硬件，使用硬件 fence 标志代替代理阻塞，使代理永远不会停止排空请求。

![文章插图](/articles/2026-05-16-10-3-perseus-moe-megakernel-b0604a5b/images/08.webp)

::: image-caption
图 2 | 3 个带信号传输的代理-NIC 交互（$p_i$=PUT，$S_i$=信号）。(a) 原始：每个耦合的 put+信号插入代理栅栏（3 次代理暂停）。(b) 解耦信号：连续提交 PUT；所有信号前仅 1 个代理栅栏（1 次代理暂停）。(c) NIC 侧排序：代理通过每个信号的栅栏标志（$s_i^F$）将排序委托给 NIC；代理永不阻塞，但每个栅栏标志序列化 NIC 流水线（0 次代理暂停，3 次 NIC 停滞）。(d) Perseus（两者结合）：仅首个信号携带栅栏标志（0 次代理暂停，1 次 NIC 停滞）。整体而言，对比四种信号传输模式的代理与 NIC 交互逻辑，原始模式每笔传输均触发代理栅栏，多次阻塞导致性能暴跌；解耦信号合并栅栏，大幅减少代理阻塞次数；NIC 侧排序将排序压力转移至硬件，消除代理阻塞但增加 NIC 停滞；Perseus 融合两种技术，仅产生 1 次 NIC 停滞，最大程度降低序列化开销，为解决多节点通信瓶颈提供了核心设计思路。
:::

图 2 直观地展示了这四种不同设计的代理-NIC 交互过程。可以看到，原始方案需要 3 次代理停止；解耦信令将其减少到 1 次；NIC 端排序消除了所有代理停止，但引入了 3 次 NIC 停顿；而 **Perseus 结合两者，实现了 0 次代理停止和仅 1 次 NIC 停顿，达到了最优的性能。**

### 3.2 解耦信令：减少 fence 频率

> **解耦信令的关键洞察是：fence 只需要在信号之前，而不是在每个 PUT 之后**。如果所有 CTA 先提交它们的 PUT，然后由一个指定的领导者 CTA 提交所有信号，那么只需要一个 fence 就可以保证所有信号都在对应的 PUT 之后。

基于这一洞察，Perseus 设计了一个两阶段的协议：

![文章插图](/articles/2026-05-16-10-3-perseus-moe-megakernel-b0604a5b/images/09.webp)

::: image-caption
算法 1 | 解耦信号，该算法详细定义解耦信号的两阶段执行逻辑，阶段 1 所有 CTA 并行完成数据传输，通过原子计数器同步分组进度，非领导者无需等待直接回归计算，最大化计算通信重叠。阶段 2 仅领导者执行一次栅栏并批量发信号，将栅栏次数从每专家一次降至每组一次。该算法无需修改 megakernel 核心调度逻辑，仅调整通信提交流程，易集成且高效，为 Perseus 的核心通信优化提供可落地的执行规范。
:::

- 在第一阶段，每个 CTA 暂存它的 token，发出一个不带信号的非阻塞 PUT，然后递增一个按组的原子计数器，通知领导者该 PUT 已提交。非领导者 CTA 在完成这些操作后，立即返回 megakernel 调度器，成为可用的计算资源，可以处理本地路由或通过 NVLink 传输的 token 的专家计算任务。这种通信与计算的重叠进一步提高了 CTA 的利用率。
- 在第二阶段，领导者 CTA 等待计数器达到组大小，这保证了组内所有 PUT 都已进入代理 FIFO。然后，领导者发出一个单一的 fence，接着为组内的每个专家发出信号。

这种设计的正确性是由以下几点保证的：

- 原子计数器确保所有 PUT 在 fence 之前进入代理 FIFO
- 单一代理线程保持提交顺序，因此 fence 跟随组内所有 PUT
- fence 保证所有 PUT 在 NIC 完成后才会处理任何信号
- 根据传递性，组内所有信号都在组内所有 PUT 之后

#### 分组粒度的选择

> **解耦信令的分组大小存在一个权衡：较小的组会保留较多的 fence，而较大的组会迫使每个 fence 等待更多未完成的 PUT**。为了找到最优的分组大小，研究人员将分组大小作为可调参数，对远程专家数量的所有约数进行了扫描。

![文章插图](/articles/2026-05-16-10-3-perseus-moe-megakernel-b0604a5b/images/10.webp)

::: image-caption

**图 7 展示了不同分组大小下的性能结果**。可以看到：

- 即使在组大小为 1（fence 数量与耦合基线相同）的情况下，解耦本身也能将延迟降低 12%（从 22.7ms 到 19.9ms），因为 NIC 可以连续流水线处理 PUT，而不会被交错的 fence 打断。
- 随着组大小增加到 28，fence 数量从 112 减少到 4，带来了额外 38%的延迟降低（从 19.9ms 到 12.3ms）。进一步增加组大小的收益则逐渐递减。

**Perseus 默认采用按 PE 分组，即一个组由发往同一个远程 PE 的所有专家组成**。这种分组方式位于解耦收益曲线的拐点附近，能够捕获大部分 fence 减少的收益，同时限制每个 fence 必须等待的传输数量。:mdnice-bold-italic[实验证实，在从 1K 到 64K 的所有序列长度下，这个默认值都在最优分组大小的 2%以内。]

### 3.3 NIC 端排序：消除 fence 阻塞成本

> 虽然解耦信令减少了 fence 的频率，但每个剩余的 fence 仍然需要支付完整的代理排空成本。NIC 端排序技术通过将排序执行从软件代理转移到 NIC 硬件，彻底消除了这种阻塞成本。

现代 RDMA NIC 都暴露了一个按请求的 fence 标志（例如 Libfabric 中的 FI_FENCE 和 InfiniBand verbs 中的 IBV_SEND_FENCE）。当 NIC 遇到一个带有 fence 标志的请求时，它会推迟该请求的处理，直到同一连接上的所有先前请求都完成。这种排序是通过 NIC 内部的硬件寄存器跟踪的，而不是软件计数器。

::: block-1
Perseus 利用这一硬件特性，将代理的阻塞排空替换为 NIC fence 标志。当请求一个 fence 时，代理设置一个挂起标志，而不是轮询完成，并且继续提交工作。下一个发送到 NIC 的信号会携带这个标志，指示 NIC 推迟该信号，直到其连接上的所有先前请求都完成。
:::

这种设计的正确性由以下几点保证：

- NIC fence 标志提供了与代理端排空相同的排序保证
- 代理按提交顺序发送 PUT 和带标志的 SIGNAL
- 在多队列对（QP）传输上，对等哈希路由将一个对等体的 PUT 和 SIGNAL 固定到同一个连接，因此每个连接的排序足以保证每个对等体的正确性

### 3.4 两种机制的互补性

> 解耦信令和 NIC 端排序是高度互补的，它们分别针对隐藏序列化的两个不同方面，共同覆盖了从开销主导到传输主导的所有工作负载 regime。

如果单独应用 NIC 端排序到原始的耦合信令，它会消除所有代理停止，但每个信号仍然需要一个 NIC fence 标志，导致 112 次 NIC 停顿（在 8 节点 Qwen3 配置中）。而结合解耦信令后，只有每组的第一个信号需要携带 fence 标志，因此只需要 28 次 NIC 停顿。

![文章插图](/articles/2026-05-16-10-3-perseus-moe-megakernel-b0604a5b/images/11.webp)

::: image-caption
图 8 | 解耦信号与 NIC 侧排序的综合效果（4 节点，Qwen3-30B）。基线：原始（红）、耦合+NIC 排序（绿）为水平线；解耦曲线遍历分组大小并启用 NIC 侧排序。(a) S=1K：NIC 侧排序主导，分组大小影响极小；(b) S=64K：三种效果均有贡献。该图验证 Perseus 两项核心技术的互补性，小序列长度（S=1K）时，NIC 侧排序消除代理阻塞，成为加速核心，分组大小影响微弱；大序列长度（S=64K）时，传输耗时增加，栅栏数量减少的效益凸显，两种技术协同发力。这说明 Perseus 适配不同负载场景，无论是开销主导的小批量推理，还是传输主导的大批量推理，均能显著降低延迟。

- 在小消息（S=1K）情况下，NIC 端排序将每个 fence 的成本降低到接近零，因此性能对组大小不敏感，加速主要来自 NIC 排序和提交重排序。
- 在大消息（S=64K）情况下，NIC 必须推迟每个带标志的 SIGNAL 直到前面的 PUT 完成，而较大的传输需要更长的时间才能完成，因此每个 fence 的成本不再可以忽略，fence 数量的减少重新获得了价值。

解耦信令减少了 fence 的频率，在 fence 数量占主导的场景下最为有效；NIC 端排序消除了每个 fence 的阻塞成本，在每个 fence 开销占主导的场景下最为有效。两者结合，能够在所有工作负载和规模下实现最优的性能。
:::

## 四、Perseus 实现与实验评估

### 4.1 实现细节

> Perseus 的实现具有极高的非侵入性，仅对现有系统进行了少量修改，确保了易于采用和移植。

- **解耦信令**：在 FlashMoE（最先进的开源 MoE megakernel）之上实现，:mdnice-bold-italic[仅修改了 RDMA 请求逻辑，核心 megakernel 组件（对称张量布局、订阅者、调度器、工作模块）保持不变]。**对于节点内通信，分发逻辑保持不变**。对于节点间通信，实现了两个阶段：
- **NIC 端排序**：在 NVSHMEM v3.5.21 的传输模块中修改了不到 100 行代码。它将代理的基于安静的排空（Libfabric 的 fi*cntr_wait，IBRC 的 check_poll_avail）替换为按请求的 NIC fence 标志（Libfabric 的 FI_FENCE，IBRC 的 IBV_SEND_FENCE）。这个修改完全在传输共享库（`nvshmem_transport*.so`）中，用户只需替换新库，无需修改应用程序代码或重新编译主机应用程序。任何使用 NVSHMEM 作为通信后端的系统都可以通过这种替换继承这个优化。
- **多 QP 传输适配**：在使用多个队列对（QP）的 IBRC 上，默认的轮询策略会将发往同一个对等体的操作分散到不同的 QP 上，但 IBV_SEND_FENCE 仅在单个 QP 内强制执行排序。这可能导致依赖的 PUT 和信号操作落在不同的 QP 上，从而破坏预期的排序。Perseus 通过将所有发往同一个对等体的操作固定到一个确定性的 QP（$\text{qp} = \text{pe} \ \% \ \text{num}_\text{qps}$）来解决这个问题。这样，依赖的操作共享同一个 QP 并继承其 FIFO 排序，而不同的对等体仍然分散在不同的 QP 上以保持聚合带宽。

1. NERSC Perlmutter 超级计算机：每个节点 4 个 A100 GPU，Slingshot-11 网络，最多 16 个节点（64 个 GPU），使用 Libfabric 代理传输。

- Qwen3-30B：通信绑定
- GPT-OSS-120B：平衡
- DeepSeek-V3：计算绑定

1. **Libfabric 传输上的巨大加速**：在 Perlmutter 的 Libfabric 代理传输上，Perseus 实现了最高 10.3 倍的端到端加速（Qwen3-30B，S=256，16 节点）。对于通信绑定的 Qwen3 模型，加速比随着节点数的增加而增加，这与原始系统的开销随节点数增长的趋势一致。对于平衡的 GPT-OSS 和计算绑定的 DeepSeek-V3，加速比分别达到了 2.8 倍和 2.2 倍。
2. **IBRC 传输上的显著提升**：在商业云的 IBRC 代理传输上，Perseus 实现了最高 2.47 倍的加速（Qwen3-30B，S=64K，4 节点）。
3. **代理传输反超 GPU-direct**：最令人印象深刻的结果是，基于 IBRC 代理传输的 Perseus，性能匹配甚至超过了 IBGDA GPU-direct 传输，最高达 1.2 倍。这一结果彻底颠覆了业界对 GPU-direct 传输必然优于代理传输的认知。研究人员解释说，IBGDA 需要消耗 SM 周期来进行 NIC 提交，这在 megakernel 中会与并发计算竞争；而 CPU 代理避免了这种干扰，但之前被 fence 诱导的序列化所瓶颈。Perseus 消除了这个瓶颈，使得代理传输能够发挥其优势。
4. **接近线性的弱缩放**：Perseus 使所有模型都实现了接近线性的弱缩放。原始系统中 Qwen3 模型在 16 节点时的 19 倍性能退化，被 Perseus 降低到了仅 3.5 倍。

## 五、相关工作

### 5.1 分布式 MoE 系统

> 分布式 MoE 系统的研究可以分为两个主要流派：基于集体的系统和基于 GPU 发起通信的系统。

- 基于集体的系统，如 DeepSpeed-MoE、Megatron-LM、Tutel 和 FasterMoE，基于 all-to-all 集体通信原语优化专家并行。:mdnice-bold-italic[这些系统依赖于 CPU 驱动的执行模型，因此受到层粒度同步的限制，无法实现细粒度的计算与通信重叠。]
- 基于 GPU 发起通信的系统，如 DeepEP、Mooncake EP 和 NCCL EP，用 GPU 发起的点对点通信代替了集体通信，以实现细粒度重叠。:mdnice-bold-italic[然而，这些系统都继承了底层传输中的隐藏序列化问题，在多节点部署时会遭遇严重的性能退化。]

::: block-1
**Perseus 与这些系统是互补的**：它解决了当 GPU 发起通信遍历代理式 RDMA 时出现的传输级序列化瓶颈，这是现有系统都没有解决的问题。
:::

### 5.2 Megakernel 研究

> Megakernel 设计的核心思想是将多个算子融合成一个持久化的 GPU 内核，以消除内核启动开销和粗粒度同步。

FlashMoE、Spector 等人的工作、MPK 和 Triton-distributed 都展示了 megakernel 在单节点 MoE 推理中的巨大性能优势，实现了高达 6 倍的延迟降低和 9 倍的 SM 利用率提升。

然而，:mdnice-bold-italic[这些工作都没有解决 megakernel 在多节点扩展时的性能崩溃问题]。Perseus 是**第一个系统地描述和优化多节点规模下 megakernel 传输行为的工作**，填补了这一重要的研究空白。

### 5.3 GPU 发起通信

> NVSHMEM、NCCL 设备 API、NCCLX 和 MSCCL++为 GPU 发起通信提供了基础构建块。

TransferEngine 和 UCCL-EP 针对跨异构 GPU 和 NIC 的可移植节点间通信，通过基于 WriteImm 的通知避免了发送方的 fence 开销。:mdnice-bold-italic[然而，这些系统需要与 megakernel 所依赖的基于内存的 put-with-signal 模型不同的接口。]

::: block-1
Perseus 则保留了现有的 put-with-signal 接口，并在**其内部消除了 fence 诱导的序列化，实现了无需修改应用程序的即插即用采用**。这使得 Perseus 能够立即惠及所有基于现有接口构建的 megakernel 系统。
:::

## 六、结论与展望

### 6.1 结论总结

> Perseus 系统通过两项互补的技术，成功消除了多节点 megakernel 通信中的隐藏序列化问题：

1. 解耦信令将数据传输与信号分离，按目标 GPU 分组信号，将 fence 数量减少了 8 倍。
2. NIC 端排序将排序执行从软件代理转移到 NIC 硬件，彻底消除了代理线程的阻塞。

实验结果表明，:mdnice-bold-italic[在代理式传输上，Perseus 实现了最高 10.3 倍的端到端加速]；更重要的是，:mdnice-bold-italic[基于 IBRC 代理传输的 Perseus，性能甚至超过了 IBGDA GPU-direct 传输最高达 1.2 倍]。**这一结果证明，限制多节点 megakernel 性能的是序列化，而不是代理式与 GPU-direct 传输之间的选择。**

Perseus 的实现具有极高的非侵入性，仅需替换 NVSHMEM 传输库即可获得性能提升，无需修改应用程序代码。**它在 Triton-distributed 上实现了最高 79 倍的加速，证明了其通用性。**

::: block-1
**Perseus 的核心贡献在于揭示了多节点 megakernel 性能崩溃的真正根源，并提供了一个优雅、高效且易于采用的解决方案**。它不仅大幅提升了现有多节点 MoE 推理系统的性能，更为未来大规模 AI 基础设施的设计提供了全新的思路和理论基础。
:::

### 6.2 进阶分析

> 尽管 Perseus 取得了令人瞩目的成果，但我们也需要客观地审视其方法的局限性和边界条件：

- 首先，**Perseus 的 NIC 端排序技术依赖于现代 RDMA NIC 对按请求 fence 标志的支持**。虽然这一特性在大多数当代数据中心 NIC 中都存在，但:mdnice-bold-italic[在一些较旧的硬件上可能不可用。在这种情况下，Perseus 只能使用解耦信令技术，无法获得 NIC 端排序带来的全部收益。]
- 其次**，解耦信令的性能依赖于合理的分组大小选择**。虽然 Perseus 的默认按 PE 分组在大多数情况下都能获得接近最优的性能，但在某些特殊的工作负载或硬件配置下，可能需要手动调优分组大小以获得最佳性能。
- 第三，**Perseus 在极端的专家路由倾斜下性能会有所下降**。虽然实验表明它在 Zipf 1.5 的倾斜下仍然保持了显著的加速比，但在更极端的倾斜情况下，分组大小的不平衡可能会导致某些 fence 需要等待过长时间，从而影响整体性能。
- 最后，Perseus 目前**主要针对 MoE 推理工作负载进行了优化**。虽然其传输层优化具有通用性，但解耦信令协议是专门为 megakernel 的 tile 级执行模型设计的。将其应用于其他类型的分布式工作负载可能需要进一步的适配和修改。

### 6.3 未来工作

> 论文作者明确规划了以下几个未来研究方向：

1. 与服务引擎的集成：**将 Perseus 集成到 vLLM、SGLang 等主流的 LLM 服务引擎中，使更多的生产部署能够受益于这一优化。**
2. 与训练框架的集成：探索将 Perseus 的技术**应用于 MoE 训练场景，优化分布式训练中的通信性能。**
3. GPU-direct 传输的进一步优化：初步评估表明，Perseus 的解耦信令技术在 GPU-direct 传输上也能带来最高 1.25 倍的加速。**未来将深入研究 GPU-direct 传输的优化空间，进一步提升其性能。**
4. 更大规模的评估：**在更大规模的集群上** （如 128 节点以上）评估 Perseus 的性能，验证其在超大规模部署下的可扩展性。

> 从更宏观的领域发展趋势来看，Perseus 的成果可能会催生以下几个重要的技术方向：

- 首先，Perseus 证明了代理式传输架构在消除序列化瓶颈后，性能可以与 GPU-direct 传输相媲美甚至超越。这将重新引发业界对代理式传输架构的兴趣，推动更多针对代理式传输的优化研究。:mdnice-bold-italic[未来可能会出现统一的 GPU 发起通信传输层，能够在代理式和 GPU-direct 传输之间自动选择最优路径，或者结合两者的优势。]
- 其次，Perseus 的成功为 megakernel 设计在更大规模集群中的应用铺平了道路。随着多节点性能问题的解决，megakernel 有望从单节点优化技术发展成为大规模分布式 AI 系统的标准执行模型。**未来可能会出现全栈的 megakernel 框架，支持自动算子融合、分布式任务调度和通信优化，大幅简化大规模 AI 系统的开发和部署。**
- 第三，Perseus 的传输层优化技术具有广泛的适用性，不仅可以应用于 MoE 推理，还可以推广到其他类型的分布式 AI 工作负载，如大模型训练、分布式推理、图神经网络计算等。未来的研究可以探索如何将 Perseus 的核心思想应用于这些领域，解决它们面临的类似通信瓶颈问题。
- 最后，Perseus 的成果也对 AI 硬件设计提出了新的启示。随着 GPU 发起通信成为主流，NIC 和 GPU 之间的接口设计将变得越来越重要。未来的硬件设计可能会提供更丰富的硬件原语，支持更高效的细粒度通信和排序，进一步消除软件层的开销，实现真正的零延迟通信。

::: block-1
总之，**Perseus 是多节点 MoE 推理领域的一个里程碑式的工作**。它不仅解决了一个长期困扰业界的关键性能问题，更为未来大规模 AI 基础设施的发展指明了新的方向。我们有理由相信，在 Perseus 及其后续工作的推动下，分布式 AI 系统的性能和效率将迎来新一轮的飞跃。
:::
