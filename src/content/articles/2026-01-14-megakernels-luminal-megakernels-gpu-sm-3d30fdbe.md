## 一、瓶颈问题

> 我们先来看一个典型的 Transformer 层执行时间线：

![文章插图](/articles/2026-01-14-megakernels-luminal-megakernels-gpu-sm-3d30fdbe/images/03.png)

::: image-caption
一个典型Transformer前向传播的简化示意图
:::

我们立刻就能发现两个问题：

::: block-1
1. 每当一个内核执行完毕并启动下一个内核时，GPU 会处于空闲状态，等待 CPU 发起下一个内核的启动指令。
2. GPU 中的部分流多处理器核心会提前完成任务，在其他 SM 还在处理剩余工作时处于空闲状态。
:::

内核启动开销是一个众所周知的问题，在英伟达 GPU 上，可以通过CUDA Graphs[1] 这类技术来部分缓解。但这种方法并非完美，正如Hazy Research 在其首篇关于融合巨核的文章中所论证的那样[2]。:mdnice-bold-italic[对于一个不执行任何实际任务的虚拟内核，其正常执行耗时为 2.1 微秒，即便启用了 CUDA 图，耗时仍有 1.3 微秒！]

第二个问题也是一种广为人知的现象，名为**波量化效应（Wave Quantization）**。当一个内核的任务无法均匀分配到所有 SM 上时，就会出现这种情况，导致部分 SM 提前完成任务陷入停滞，而其他 SM 则需要耗时更久才能完成内核执行。根据内核的总运行时间和任务形态，这些空闲间隙可能会变得**极其** 显著！

基于我们所关注的张量计算的特性**，实际上我们无需等待前一个操作完全同步，就能开始执行下一个操作**。以分块矩阵乘法（tiled matmul）为例：

![文章插图](/articles/2026-01-14-megakernels-luminal-megakernels-gpu-sm-3d30fdbe/images/04.png)

::: image-caption
分块矩阵乘法的数据访问模式，来源：《工程师矩阵乘法指南》| 皮特·沃登（Pete Warden）博客
:::

该运算无需等待张量 A 或张量 B 的全部数据加载完成再开始计算，因为它每次只需要从 A 和 B 中读取一个分块条带。只要这个条带准备就绪，我们就可以开始计算张量 C 的一个分块了！**这种完全同步的要求，是由标准内核执行模型强制规定的，而非数学运算本身的需求。**

实际上，还存在一个隐藏的第三大瓶颈，阻碍我们充分利用硬件的带宽和计算能力：每个内核在加载足够的权重数据之前，都无法执行任何计算。通常情况下，这意味着即便内核在主循环执行过程中能完美实现加载-计算重叠，也无法避免等待初始权重加载时的空闲时间。我们需要一个更精细的时间线，来展示数据加载和计算过程，才能看到这种影响：

![文章插图](/articles/2026-01-14-megakernels-luminal-megakernels-gpu-sm-3d30fdbe/images/05.png)

::: image-caption
单个SM执行过程的简化示意图
:::

现在我们可以看到，:mdnice-bold-italic[在开始计算之前，有大量时间被消耗在初始权重的加载上。这段时间里，我们昂贵的张量核心一直处于空闲状态！] 即便内核由专家编写，且在执行过程中能完美利用带宽，也无法解决这个问题。可编程依赖启动（Programmatic Dependent Launch）[3] 这类技术能起到一定缓解作用，它**允许下一个内核在当前内核运行时就开始准备工作（加载权重），但这种机制是在设备层面实现的**，而非针对单个 SM，因此仍然会留下明显的空闲间隙。

## 二、单内核驱动整模型

> 如果我们能将前向传播中的**所有操作** 融合为一个单独的内核，会怎么样？这将为我们带来几项优势：

1. 我们能直接消除内核启动延迟，因为整个前向传播过程只需要启动一个内核。
2. 对于当前操作提前完成任务的 SM，我们可以立即让它们开始处理下一个操作的任务，从而消除波量化效应的影响。
3. 我们能够在**当前操作的收尾阶段**，就开始为 SM 加载下一个操作的权重数据，进而消除计算阶段之间的空闲间隙。

这项技术由Hazy Research 在去年率先提出[4]，他们将 10 亿参数的 Llama 模型融合为一个单独的融合巨核（MegaKernel）。:mdnice-bold-italic[但他们的方案存在一个显著局限：这些融合巨核需要手动构建，开发者必须手动定义每条指令，并为其分配对应的 SM。而我们的目标是从源代码编译模型，因此希望这个过程是全自动的，并且能够适配任意复杂的模型架构。]

接下来，我们将详细介绍融合巨核（MegaKernel）的工作原理，然后深入探讨 Luminal 如何为任意复杂的模型自动生成融合巨核。

## 三、运行在 GPU 上的解释器

> 融合巨核的概念源于解释器（interpreter）。大多数程序员都熟悉 Python 这类解释型语言的工作原理：解释器会逐条读取、解码并执行指令。我们可以将 GPU 视为一个大型多核处理器，其中每个核心只能执行一套非常有限的指令集。

我们既可以基于每个核心，将指令直接存入共享内存，也可以将指令存储在全局内存中，形成一个所有核心共享的全局指令流。换句话说，:mdnice-bold-italic[我们需要决定，是将指令静态分配到每个 SM 的独立指令流中，还是让所有 SM 共享同一个指令流。]

我们简单分析一下两种方案的利弊：

- **静态调度**：优势在于能够一次性预取并加载大量指令，直接存入高速共享内存，因此获取新指令的开销极低。这种方案的:mdnice-bold-italic[缺点是，程序员或编译器必须提前将指令静态分配到各个 SM 上，而由于指令的延迟可能存在差异，这项工作的难度很高]。此外，SM 的运行过程中通常会存在抖动现象，导致部分 SM 的运行速度因硬件层面的不可预测因素而慢于其他 SM。
- **动态（全局）调度**：:mdnice-bold-italic[劣势在于每次获取新指令时，都需要从全局内存读取数据并执行原子锁操作，因此开销更高]。**但如果前一条指令的执行时间足够长，能够覆盖指令获取的延迟，那么这种开销就可以被隐藏**。全局调度的另一个优势是，程序员或编译器无需提前将指令分配到各个 SM，SM 可以在完成当前任务后，主动从指令队列中获取下一条指令执行。**这种方式能自然抵消抖动的影响——运行速度更快的 SM 会承担更多任务，弥补运行较慢的 SM 的效率缺口。**

> **我们认为动态调度带来的收益，足以抵消其额外开销**。因此，我们设计的融合巨核采用了一个所有 SM 共享的全局指令队列，这不仅简化了编译器的实现逻辑，还能适配延迟可变的指令。

由于指令之间通过全局内存完成数据通信，我们仍然需要采用与传统内核相同的算子融合策略。这意味着我们定义的指令粒度要足够粗，例如将“矩阵乘法+残差连接”或“RMS 归一化+矩阵乘法+旋转位置编码（RoPE）”这类组合操作封装为一条指令，以此减少全局内存的访问次数。

![文章插图](/articles/2026-01-14-megakernels-luminal-megakernels-gpu-sm-3d30fdbe/images/06.png)

::: image-caption
融合巨核在多个SM上执行时的性能剖析图
:::

从图中可以看到，当前指令的执行阶段和下一条指令的执行阶段存在重叠。我们还能观察到，在相同的时间范围内，部分 SM 能够执行多条指令，而部分 SM 只能执行一条指令，**这表明指令的延迟具有显著的可变性！**
:::

还有一个我们尚未讨论的关键问题：同步机制。正如前文所述，传统内核的一大缺陷是，下一个操作必须等待**所有** SM 完成当前内核的任务后才能启动。:mdnice-bold-italic[但换个角度看，这种机制也有一个优势：在下一个内核启动时，我们可以确保所有数据都已准备就绪]。一旦我们允许在前一个操作未完全结束时就启动后续操作，这个数据就绪的保证就不复存在了。**因此，我们需要实现一套细粒度的同步机制，确保在启动下一个操作时，其所需的输入数据已经准备就绪。**

我们采用的同步机制是标准的**屏障计数器（barrier counters）**。但与 Hazy Research 使用的屏障不同，:mdnice-bold-italic[我们采用了“先递增再递减”的屏障策略：算子在启动时，会先对其对应的屏障计数器执行递增操作；执行完成后，再对计数器执行递减操作]。这样一来，每个屏障都可以被视为一个“活跃生产者”计数器。借助这种机制，消费者无需知道需要等待多少个生产者完成任务，只需要等待活跃生产者计数器归 0 即可。

## 四、融合巨核的生成流程

> Luminal 是一款基于计算图的编译器，它会将模型表示为计算图的形式。我们面临的挑战是，**如何将计算图转换为一个指令队列，并正确建立指令之间的细粒度数据依赖关系**。我们的方案分为两个阶段：

1. 将现有的算子重写为**分块算子（block ops）**，这些算子会被分配到各个 SM 上执行，并具有结构化的输入、输出数据依赖关系。
2. 基于所有输入-输出算子对，推导屏障的步长参数。

第一阶段的实现相对直观。以矩阵乘法算子为例，我们可以将其重写为分块矩阵乘法算子（TileMatmul），使其每次只处理一个数据分块。在重写过程中，我们会在等式图引擎（egglog）中，借助**形状-布局代数（shape-layout algebra）** （与 CuTE 库的原理类似），为每个输入分块和输出分块推导正确的步长参数。:mdnice-bold-italic[我们的方案对算子的输入输出数据形状具有良好的灵活性]，例如，矩阵乘法这类算子更适合基于分块处理，而部分算子则更适合直接处理连续的行数据。

完成算子的分块划分后，我们需要为每个算子确定其需要等待的输入屏障（执行前需检查屏障计数器是否为 0），以及其需要更新的输出屏障（执行前后分别对计数器执行递增和递减操作）。我们回到之前的分块矩阵乘法示例，用具体的数值来解释这个过程：

![文章插图](/articles/2026-01-14-megakernels-luminal-megakernels-gpu-sm-3d30fdbe/images/04.png)

::: image-caption
《工程师矩阵乘法指南》| 皮特·沃登（Pete Warden）博客
:::

假设矩阵的尺寸为 $M=128, N=128, K=128$，我们将矩阵划分为 $32\times32$ 的分块。为了计算完整的矩阵 C，我们需要启动一个二维线程网格，其尺寸为 $(128/32)\times(128/32)=4\times4=16$，对应 16 个分块矩阵乘法实例。**我们的任务是，推导出一个映射表达式，将线程的启动索引（0-15）转换为读取张量 A 时对应的屏障索引。**

**实现这一目标的关键，是分析张量 A 的生产者的启动维度**。如果生产者在 M 维度上的尺寸与当前算子一致，那么我们可以证明，算子在 M 维度上的任务是相互独立的——因为每个算子实例只需要读取 M 维度上的一个分块数据。因此，我们在 M 维度上初始化 $128/32=4$ 个屏障，并将步长设置为 1，这意味着当线程在 M 维度上遍历不同分块时，屏障索引会逐次递增 1。而在 K 维度上，每个算子实例都需要读取完整的 K 维度数据，因此步长应设置为 0。

最终，张量 A 对应的屏障步长计算公式为：

$$
m \times 1 + n \times 0
$$

如果将其映射到一维的启动索引上，则公式可简化为：

$$
(x / 4) \times 1 + (x \% 4) \times 0 = x / 4
$$

这个公式可以将线程的启动索引（0-15）映射到对应的屏障索引（0-3）。

> 分析每个启动维度的核心思想，是尽可能保留任务的独立性。

- 在最坏情况下，所有生产者 SM 和消费者 SM 都需要共享同一个屏障，这相当于退回到了传统内核的完全同步模式。
- 而在最佳情况下，每个后续算子只依赖于前一个算子的一个实例，因此 SM 在完成当前任务后可以立即启动下一个任务。

上述逻辑最终被封装为如下结构体：

```
struct BlockOp {  src_a_data: Expression,  src_b_data: Expression,  src_a_barrier: Expression,  src_b_barrier: Expression,  dest_data: Expression,  dest_barrier: Expression,}
```

其中每个表达式都定义了一个映射关系，能够将逻辑启动索引转换为物理索引。这样一来，每个算子都明确知道：从何处读取源数据、执行前需要检查哪些屏障、将结果写入何处、以及需要更新哪个屏障的计数器。

接下来的步骤，是基于每个分块算子的定义，生成对应的算子实现代码。标准的实现代码结构如下：

```
__device__ void mk_op(    OpPayload payload, // 算子专属的负载结构体，存储元数据    const float* const source_ptrs[3], // 由解释器解析得到的源数据指针    float* out_ptr, // 由解释器解析得到的目标数据指针    const int current, // 当前算子的逻辑启动索引    int t // 当前线程块内的线程索引) {    // 函数体}
```

这个函数包含了执行分块算子所需的全部信息：解释器负责解析数据指针和屏障计数器，等待屏障满足条件后，将数据指针传入实现函数。算子还可以创建负载结构体，并将其存入指令队列，供实现函数读取。这些结构体通常包含元数据，例如运行时维度信息，或者指向外部键值缓存（KV cache）等特殊数据存储区的指针。由于我们不对算子可访问的元数据做任何限制，因此开发者可以灵活设计算子，实现一些在传统受限架构中无法完成的执行模式。

## 五、符号化工作队列

> 我们面临的一个早期挑战是，如何在多次执行之间重建工作队列（即指令队列）。如果每次执行前，都需要重新分配内存并调度所有操作，这个过程的开销会非常大，甚至成为新的性能瓶颈。虽然部分队列可以缓存供多次运行使用，但总的来说，我们不希望因为序列长度这类简单参数的变化，就付出重新分配和重建队列的昂贵代价。

![文章插图](/articles/2026-01-14-megakernels-luminal-megakernels-gpu-sm-3d30fdbe/images/07.png)

::: image-caption
我们希望避免这种情况！流水线技术（Pipelining）能够在一定程度上缓解这个问题，但最好的方案是从根本上避免重建队列的操作
:::

::: block-1
Luminal 给出的解决方案是：在工作队列中存储**指令本身**，而非**指令实例**。我们将这种队列称为**符号化工作队列（symbolic work queue）**。
:::

例如，对于一个尺寸为 $M\times K\times N$ 的矩阵乘法，若将其划分为 $(M/32)\times(N/32)$ 个分块矩阵乘法算子实例，我们不需要在队列中存储 $(M/32)\times(N/32)$ 个算子，只需要在队列中存入一个分块矩阵乘法算子，并将其启动维度标记为 $(M/32)\times(N/32)$ 即可。

同时，我们会初始化一个计数器，记录该指令需要启动的实例总数。在程序计数器推进之前，每个 SM 从队列中获取一个指令实例时，会对该计数器执行原子递减操作。

**这种设计的优势在于，我们可以用符号化的方式表示指令需要启动的实例数量**。再举一个例子：假设我们有一个尺寸为 $S\times128$ 的张量，以及一个逐行执行的归一化算子，我们需要启动 $S$ 个算子实例，而这一需求可以直接通过符号 $S$ 来表示。在运行时，我们只需要将符号 $S$ 替换为当前执行的实际序列长度，就能自动计算出需要调度的算子实例数量。

由于我们将数据指针和屏障都表示为步长的函数，因此也可以通过同样的表达式求值过程，在运行时解析出实际的数据指针和屏障索引。现在，即便我们修改了 $S$ 或者其他任何动态维度参数，也无需在运行时修改底层的工作队列或执行任何主机端操作！

剩下的工作就很简单了：在编译阶段，我们通过拓扑排序遍历所有分块算子，将指令及其负载结构体加入工作队列；在运行时，我们只需要启动一个内核并等待执行结果即可！

## 六、结论

> 回顾全文，我们已经取得了不少进展：

- 传统内核会导致三类性能间隙：内核启动开销、波量化效应、以及算子间的内存访问间隙。
- 通过将整个模型融合为一个单独的融合巨核，我们可以同时解决这三个问题。
- 生成融合巨核的过程分为多个阶段：首先将算子重写为可分配到 SM 上的分块算子，然后推导数据和屏障的步长参数，接着通过内联每个算子的实现函数生成解释器；之后再次遍历计算图中的算子，构建工作队列；最后将队列与解释器结合，完成执行过程！

融合巨核（MegaKernels）技术仍处于发展初期，许多相关的抽象概念和工具链尚未完善。但我们非常兴奋能够:mdnice-bold-italic[构建一个更简洁、性能更高的 GPU 及专用加速器编程模型，其核心目标是减少不必要的同步操作，让硬件资源始终处于忙碌状态。]
