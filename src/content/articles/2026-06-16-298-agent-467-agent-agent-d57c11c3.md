## 一、传统 AI 智能体评测：根深蒂固的行业痛点

> 随着独立大模型逐步演进为“大模型+工具+记忆”的复合型智能体，行业对评测的需求从单一能力考核，转向全场景、多维度的综合评估。**但现有评测架构，完全跟不上智能体的发展速度。**

### 1.1 多重弊端：传统评测的核心问题

| 问题维度 | 具体表现 | 核心影响 |
| --- | --- | --- |
| **集成成本高** | 基准与智能体强绑定，接口、输入格式、工具调用规则不通用；$N$ 套基准与 $M$ 款智能体需 $N \times M$ 次定制开发；如 OpenHands 需维护数十个基准适配目录 | 研发人力持续消耗，扩展性差，难以规模化评测 |
| **公平性与一致性差** | 各团队适配代码引入自定义逻辑，导致同一智能体在不同基准上表现偏差显著；评测框架常修改智能体原有逻辑 | “测试环境”与“线上生产环境”割裂，评测结果失真，无法反映真实落地效果 |
| **多智能体评测难** | 现有基准多为单智能体设计，缺乏对协作型、对抗型等多智能体场景的支持；实现多智能体评测需从零改造框架 | 定制成本进一步攀升，前沿研究难以被系统化评估，阻碍技术演进 |

### 1.2 标准化困境：为什么通用评测难以实现

> 行业并非没有尝试过统一评测标准，但始终陷入两难。

- 如果新标准追求**极致灵活，能适配所有智能体场景，规则就会变得复杂**，开发者不愿迁移；
- 如果标准设计得**过于轻量化，又无法覆盖终端、编码、网页交互等多样化评测场景。**

**除此之外，多数新标准选择从零设计专属接口，而非复用现有生态**。开发者需要同时改造智能体和基准两套代码，迁移阻力极大，这也是各类小众评测框架始终无法普及的核心原因。

::: block-1
传统智能体评测的核心矛盾，是“基准与智能体强耦合”以及“专属接口带来的生态割裂”，这也是本次研究想要彻底解决的底层问题。
:::

## 二、AAA 智能体化评测范式：重构评测底层逻辑

> 该研究跳出“基准是工具”的固有思维，提出颠覆性思路：:mdnice-bold-italic[基准本身就是一个具备任务分发、环境管理、结果打分能力的智能体。基于这一思路，研究者正式定义了 AAA（Agentified Agent Assessment）智能体化评测范式。]

AAA 范式并非凭空创造，而是基于两条落地原则设计：

- 一是基准任务必须做到**自包含**，像人类任务一样清晰易懂；
- 二是**优先复用行业已大规模普及的协议**，降低生态迁移成本。

最终 AAA 选定 A2A 协议负责智能体间任务交互，MCP 协议负责工具与环境调用，构建起统一的交互体系。

### 2.1 核心设计：从两套接口到一套通用接口

> 传统评测会分别为基准、被测智能体设计独立接口，两套接口的对接是集成成本的根源。AAA 将基准改造为裁判智能体后，整个流程只保留一套基于 A2A+MCP 的通用接口，所有角色都遵循同一套规则交互。

![文章插图](/articles/2026-06-16-298-agent-467-agent-agent-d57c11c3/images/03.webp)

::: image-caption
图 1：传统LLM/智能体基准与AAA范式的集成对比。AAA将集成数量从 $N \times M$ 降至 $N+M$，同时实现基准与被测智能体的完全解耦。
:::

如图 1 所示，上图是传统模式下，每一个基准都要单独对接每一个智能体，集成数量为两者乘积；:mdnice-bold-italic[下图 AAA 模式中，所有基准（裁判智能体）和被测智能体仅需适配通用协议，集成数量变为两者之和。这种变化从数学层面大幅削减工作量，也是范式效率提升的核心来源。]

:::

### 2.2 三大角色与标准交互流程

> :mdnice-bold-italic[AAA 范式定义了三类固定角色，构成完整评测链路，分别是委托者、裁判智能体、被测智能体。委托者发起评测需求，裁判智能体对应传统意义上的基准，负责执行评测逻辑，被测智能体就是待检测的各类 AI 智能体。]

![文章插图](/articles/2026-06-16-298-agent-467-agent-agent-d57c11c3/images/05.webp)

::: image-caption
图 3：AAA 范式的交互流程。裁判智能体的内部结构仅作示例参考，并非强制规范。该交互模型定义了委托方 - 裁判智能体 - 被测智能体三级角色，构建了标准化的多智能体通信链路，适配分布式 AI 集群的通信范式。AAA 并未强制规定裁判智能体内部实现逻辑，保留了架构灵活性，开发者可根据评测场景选择代码硬编码或自然语言提示两种实现方式。
:::

整套交互流程分为五个固定步骤，全程基于 A2A 消息流转：

1. 评测请求下发：委托者通过 A2A 向裁判智能体发送评测目标、被测智能体地址等配置；
2. 任务与环境准备：裁判智能体加载数据集、启动 MCP 工具服务，向被测智能体下发任务与环境权限；
3. 任务执行：被测智能体接收任务，调用 MCP 工具完成操作，过程中可与裁判智能体多次交互；
4. 结果打分：任务超时或完成后，裁判智能体回收环境权限，依据预设指标对被测智能体打分；
5. 结果回传：裁判智能体按照指定格式，将评测数据返回给委托者。

::: block-1
这套流程同样适配多智能体场景。对抗型任务（游戏、攻防演练）和协作型任务（联合开发）仅需在裁判智能体中预设角色规则，无需修改底层交互逻辑。
:::

### 2.3 两大落地优势

- **第一，支持自适应评测**。传统基准是固定数据集+固定打分规则，任务顺序无法调整。而裁判智能体可以动态生成任务：被测智能体表现较差时，直接跳过同类简单任务；表现优异时，自动提升任务难度，让评测更具针对性。
- **第二，组件可复用**。传统基准中的用户模拟、打分模块都是硬编码在框架内。AAA 将这些模块拆分为独立子智能体，可跨多个基准复用，进一步降低二次开发成本。

> 如图 2 所示，传统基准和专属运行框架深度绑定，用户只能替换内部的大模型，无法更换整套智能体。

![文章插图](/articles/2026-06-16-298-agent-467-agent-agent-d57c11c3/images/06.webp)

::: image-caption
图 2：传统基准与AAA范式的解耦差异。传统基准与运行框架强绑定，仅支持替换大模型；AAA可完整替换任意智能体。AAA 范式下，基准、运行框架、被测智能体完全分离，只要兼容 A2A 与 MCP，任意智能体都可接入评测，兼容性拉满。
:::

::: block-1
AAA 范式的核心创新，**是用“智能体对接智能体”替代“基准对接智能体”，依托成熟协议实现全链路解耦**，从架构上根除了传统评测的集成乱象。
:::

## 三、AgentBeats 系统：AAA 范式的工程化落地

> 理论范式需要工程系统承接，AgentBeats 就是 AAA 范式的完整落地产品。该系统重点解决开放协作、数据隐私、结果可复现三大工程问题，让抽象的评测范式适配真实产业环境。

在 AI Infra 落地中，理论方案往往会受限于隐私要求、部署环境、开源规则等现实约束。AgentBeats 没有局限于实验室场景，而是**设计了全链路生命周期管理能力，覆盖智能体开发、注册、执行三大阶段。**

### 3.1 评测全生命周期设计

> AgentBeats 将整个评测流程划分为三个标准化阶段，适配本地、云端等所有部署场景：

![文章插图](/articles/2026-06-16-298-agent-467-agent-agent-d57c11c3/images/07.webp)

图 4：AgentBeats 平台的完整评测生命周期。部分环节在不同运行模式下可选择省略。该生命周期将 Agent 评测拆解为智能体构建、注册、执行三个标准化阶段，完全对标软件工程的交付流程，可无缝对接自动化运维、持续集成系统。不同运行模式允许裁剪流程环节，适配本地开发、云端公有评测、私有离线评测等多样化部署场景，兼顾开发调试与正式评测的需求。

### 3.2 协议选型的工程考量

> **AgentBeats 坚持复用 A2A 与 MCP 两大现有协议，而非新建协议**，这是重要的工程取舍。新建协议意味着全生态重新适配，推广难度极大。而 :mdnice-bold-italic[A2A 已成为智能体间通信的主流标准，支持多模态传输、任务追踪；MCP 是工具调用通用协议，适配终端、浏览器、容器等各类环境。]

对于存量老旧智能体，无需重构内核，仅需增加一层轻量协议转发封装即可接入，迁移成本控制在最低水平。同时 AgentBeats 设计了 MCP 网关，无需被测智能体支持动态 MCP 服务加载，进一步兼容老旧架构。

::: block-1
**AgentBeats 的工程核心是“最小侵入”**，在不改动现有智能体架构的前提下落地 AAA 范式，这也是该系统能够快速被开发者接纳的关键。
:::

## 四、五大运行模式：适配多元现实部署场景

> 不同开发者、企业对评测的需求天差地别：个人开发者需要本地私密测试，企业需要云端公开评测，研发团队需要结合本地调试与云端验证。为此 AgentBeats 设计了五种运行模式，覆盖全场景。

五种模式基于同一套 AAA 内核，仅在角色部署位置、触发方式、结果展示上做出区分，个人开发者、企业团队、开源社区都能找到匹配的方案。下表汇总了五种模式的核心特征：

![文章插图](/articles/2026-06-16-298-agent-467-agent-agent-d57c11c3/images/08.webp)

::: image-caption
表 3：AgentBeats 平台的五种运行模式。
:::

从部署架构与使用场景分析，五种运行模式覆盖了 AI 开发全生命周期：

1. **本地模式**：最简单的部署形态，所有智能体都运行在本地设备，依靠本地脚本触发评测。适合个人开发者做私有调试，无需依赖云端平台，是入门首选。
2. **远程模式**：智能体部署在开发者自有远程服务器，仅将服务地址注册到 AgentBeats 平台。平台负责调度与结果展示，智能体代码完全保密，适合企业开展闭源智能体的公开评测。
3. **托管模式**：开发者提交代码仓库或 Docker 镜像，由 AgentBeats 平台完成智能体部署与运维。该模式简化运维，适合开源项目对外展示能力。
4. **代理模式**：打通本地开发环境与云端平台，本地调试中的智能体可通过代理通道对接云端裁判智能体，无需完整部署，大幅提升迭代效率，是研发团队的核心常用模式。
5. **CI 模式**：将评测嵌入代码提交流水线，代码更新后自动触发评测，结果留存至日志中。全程无中心化黑盒平台，审计性、可复现性最强，适合对合规要求高的团队。

::: block-1
五大运行模式构成了完整的部署矩阵，从个人调试到企业合规评测全覆盖，让 AgentBeats 从实验室工具变成可商用的工业级平台。
:::

## 五、开发者实践指南：两类智能体开发规范

> AAA 范式将智能体划分为被测智能体、裁判智能体两类，两类智能体的开发目标、适配要点存在明显差异。研究团队针对两类开发者分别给出落地建议，降低上手门槛。

框架的易用性直接决定生态规模。研究团队结合实战经验，梳理了存量改造、全新开发两种场景下的开发规范，同时区分了被测智能体与裁判智能体的设计逻辑。

:::

### 5.1 被测智能体开发要点

> 被测智能体的核心要求是兼容 A2A 任务接收与 MCP 工具调用，分为存量改造和全新开发两种场景：

1. **存量智能体改造**：**无需修改核心逻辑，仅添加一层薄协议封装**。例如终端类编码智能体，封装层负责将 A2A 任务转为终端指令，执行完成后再将结果封装为 A2A 消息回传，全程不侵入原有代码。
2. **全新开发智能体：可原生对接 A2A 与 MCP，推荐先基于单一裁判智能体做迭代优化，再扩展至全场景，提升开发效率。**

针对浏览器、远程终端等特殊环境，开发者可通过 A2A 传递环境地址，再依托 MCP 发起远程操作，无需额外定制接口。

### 5.2 裁判智能体开发要点

> 裁判智能体对应传统基准，核心是实现任务管理、环境初始化、打分逻辑。开发者有两种实现路径：

- 一是代码硬编码评测流程，适合规则固定的终端类基准；
- 二是自然语言描述评测逻辑，依托大模型完成打分，适合人机交互类基准。

通用设计原则包括：支持数据集动态选择、环境快速重置、拆分打分子智能体防范提示注入攻击。同时建议在结果中附加数据集编号、样本总量等元数据，方便后续统计分析。

::: block-1
**两类智能体的开发核心都是“协议适配优先，逻辑复用为主”**，最大化利用现有代码，是 AAA 范式降低生态迁移门槛的关键设计。
:::

## 六、系统扩展与生态兼容：强化平台能力边界

> 为适配复杂工业场景，AgentBeats 设计了一系列扩展组件，同时对接主流 AI 工具链、标准框架，让自身融入现有 AI Infra 生态，而非打造孤立体系。

基础协议与运行模式满足核心评测需求，而扩展组件则解决隐私、运维、观测等进阶问题。同时 AgentBeats 主动对接行业主流标准与工具，实现生态互通。

### 6.1 核心扩展组件

1. **智能体控制平面**：为远程智能体提供重启、日志拉取接口，解决云端实例故障排查、状态重置难题，提升可观测性。
2. **MCP 网关**：统一工具调用入口，动态管理工具权限，被测智能体仅需配置固定网关地址，无需适配动态 MCP 服务。
3. **容器与沙箱管理器**：统一管理容器化环境，规避多层 Docker 嵌套问题，适配编码、系统操作等需要隔离环境的评测场景。
4. **智能体注册表与排行榜**：提供智能体检索、能力排名功能，构建社区化评测生态。

### 6.2 第三方生态对接

AgentBeats 实现了多类主流工具与标准的兼容：对接 Hugging Face、MLflow 等实验管理工具；支持强化学习环境对接，将 Gym 接口转为 MCP 工具；兼容 CUBE 基准打包标准，裁判智能体可直接调用 CUBE 封装的评测环境。

这种生态互通能力，让 AgentBeats 无需从零构建上下游工具，快速融入现有 AI 研发链路。

::: block-1
扩展组件补齐工业级运维能力，生态对接实现互联互通，让 AgentBeats 跳出单一评测工具的定位，成为 AI Infra 的一环。
:::

## 七、大规模实证：竞赛与编码案例双重验证

> 理论与工程设计完成后，研究团队通过两轮实测验证方案的覆盖能力、实用性与保真度：为期五个月的社区竞赛验证大规模落地能力，编码智能体对照实验验证评测精度。

实测是技术方案落地的最终检验。两项实验分别面向通用场景和垂直场景，从生态适配、结果准确性、技术洞察三个维度，验证 AAA 范式与 AgentBeats 的价值。

### 7.1 社区公开竞赛：全场景生态验证

研究联合全球 AI 课程社区举办为期五个月的公开竞赛，全球开发者提交裁判智能体与被测智能体，最终收集到 298 个裁判智能体、467 个被测智能体，覆盖编码、金融、医疗、网页、游戏等 12 大场景。

从代码统计结果来看，98%以上的智能体基于 Python 开发，同时支持 TypeScript、Rust 等语言，协议层的兼容性不受开发语言限制。78.3%的裁判智能体通过自然语言定义评测逻辑，代码量平均仅 5.3 千行，证明上手难度极低。

大量经典基准（Tau2-Bench、MedAgentBench 等）完成 Agent 化改造，原本强耦合的框架顺利接入 AAA 体系，证明该范式具备全场景覆盖能力。

行业现有评测方案分为四大路线：专属框架路线、全新轻量接口路线、领域专用标准路线、复用现有终端协议路线。下表为多方案综合对比：

::: block-1
相较于其他方案，AgentBeats 的核心竞争力是生态兼容性与全场景适配，是目前最有可能成为行业通用标准的智能体评测框架。
:::

## 总结

> 从独立大模型到复合型智能体，AI 的形态已经发生质变，但评测体系长期停滞不前。AAA 范式与 AgentBeats 系统的出现，补上了 AI 智能体生态中缺失的标准化评测一环。

回顾整套工作，研究者从行业痛点出发，:mdnice-bold-italic[跳出“基准是工具”的传统思维，提出“基准即智能体”的 AAA 范式，依托 A2A、MCP 两大通用协议实现基准与智能体的完全解耦，将集成工作量从 $N \times M$ 降至 $N+M$。在此基础上落地 AgentBeats 工程系统，设计五种运行模式覆盖个人、团队、企业的全部署场景，同时给出完整的开发者规范。]

大规模社区竞赛证明方案的通用性与易用性，编码智能体对照实验证明评测的保真度与科研价值。横向对比主流框架，AgentBeats 在集成成本、场景适配、环境一致性上全面领先，是一套面向产业落地的工业级解决方案。

站在 AI Infra 发展的角度，**智能体是下一代 AI 的核心形态，而标准化评测是行业规模化发展的基石**。AgentBeats 的意义，不止于一款评测工具，而是搭建了一套开放、可复现、可协作的评测生态规则。未来随着 A2A、MCP 协议进一步普及，这套范式有望成为全球 AI 智能体评测的通用标准。

::: block-1
**同时该方案仍有延伸空间：结合 AI 治理规则实现合规评测、强化多模态智能体评测能力、优化自适应评测算法等**。随着生态不断壮大，AgentBeats 将从单纯的评测平台，演变为智能体迭代、对比、合规审计的综合基础设施，持续赋能整个 AI 智能体行业。
