## 一、我的 AI 编码一年：效率不升反降的悖论

我算是 vibe coding 的「老手」了，:mdnice-bold-italic[早在 2024 年末就基本不再手写代码，算下来已有一年多。我所产出的所有代码，几乎都来自不同时期的各类 LLM。]

::: block-1
最近 LLM 结合 Coding Agent 的能力大幅提升，我本以为可以做更多、下放更多工作，但事与愿违——整体效率，反而不如 LLM 尚未进化的去年。
:::

## 二、顺畅的开发链路，与失控的排障成本

> 从想法、设计、讨论（Coding Agent 从这里介入），到确定实现方案、编码、E2E 验证，一套流程走完，才算一个 feature 真正完成。这套链路曾经高效又和谐，我也靠着这套范式快速落地了很多东西。

但**天下没有免费的午餐**，更不存在零 bug 的系统。一旦问题出现，我依旧依赖 Coding Agent 去 debug，而排障花掉的时间，常常是完成功能本身的数倍。那些难缠的 bug，大多来自实现阶段被忽略的细节。

## 三、能力变强后，我反而丢掉了「代码体感」

在 LLM 能力没那么强之前，我必须花大量精力控制实现复杂度。那时模型能力有限，我得人工拆解任务，脑海里也会自然形成代码雏形。

::: block-1
随着 LLM 越来越强，实现阶段变得更高效，我脑子里只剩下自然语言层面的设计决策，不再细想、细看具体代码，把时间更多放在系统更上层的判断上。
:::

可这种**「只做顶层设计」的轻松，背后藏着巨大隐患。**

## 四、一次真实踩坑：SSD Cache 里的 O(n) 隐疾

> 举个很典型的例子：我设计的 SSD Cache，整体基于 FIFO 环形缓冲区，读采用乐观读，用 head、tail 维护整体状态。:mdnice-bold-italic[LLM 当时信誓旦旦说完全理解，E2E 和部分单测也都能跑通。可上线后出现一个棘手问题：SSD 的 p99 延迟异常偏高。]

我先后换了多款强模型的 Coding Agent（5.2 xhigh、opus 4.5、kimi 2.5）去定位，结果无一例外，给出的都是无效思路。直到某天午休，我突然回过神：它到底是怎么处理 FIFO 淘汰的？

::: block-1
一查才发现：模型写了一个 O(n) 的淘汰逻辑，淘汰时会扫描全部 SSD 索引。再整体看代码结构，更是写得混乱冗余，把简单逻辑过度复杂化了。
:::

类似的问题不止一例。我越来越像一个「专职善后」的人，不停为 LLM 的输出收拾残局，也不得不认真思考：**该如何从根上解决这类问题？**

## 五、回归本质：编程的核心，是控制复杂度

> 这时，《解构领域驱动设计》里的几句话点醒了我：

- 计算机编程的本质就是控制复杂度。
- 影响理解能力的第一要素是规模。

人性本懒，我们天然倾向简单，但「One size could not fit all」。系统的复杂度有其必要性：想要更好的性能，就要做更多定制化，抽象开始泄漏，复杂度随之上升。

代码像一种有损压缩，压缩了各种需求与场景。这世上几乎不存在小于 O(n) 的压缩算法——必须看完所有信息，才能知道如何压缩。想在有限空间里追求更高压缩率，就要投入更多计算：从 bloom filter 到 binary fuse filter，从压缩软件的不同等级选项，都是这个道理。

::: block-1
所以，想要更少的代码、更简洁的设计，就必须投入更多时间去消化、理解、设计系统本身。
:::

## 六、人脑的算力边界：复杂度排队效应

> 人类的能力终究有限。这世上本就没有天生的天才，我们不过是在自己定义的 loss function 上持续做强化学习：在尝试、成功、失败里学习，把经验刻进自己的「参数」。

**人没有影分身，无法并行，只能在有限时间里，用珍贵的精力不断试错、「训练」自己**，在自己的 loss function 上梯度下降。哪怕我用 Agent 集群写出一本《RDMA 工程开发大全》，我依然要花巨量时间，在实践、思考、笔记里真正内化它。我必须去想，必须去试。

::: block-1
人脑这台推理引擎，无论 prefill 还是 decode 吞吐都很有限：decode 吞吐和语速、信息强度相关，prefill 吞吐取决于理解新事物的速度，而且人很难做到全程 full attention。
:::

一旦 Coding Agent 制造复杂度的速度，快过我消化、控制复杂度的速度，就会出现**排队效应**：:mdnice-bold-italic[队列越堆越长，等到必须 drain 这个队列时，我要一次性吞下所有堆积的复杂度，也就是 LLM 留给项目的「技术债」。]

## 七、触及阿姆达尔定律：AI 红利的临界点

说到底，我现在正处在一个关键节点：

**LLM 的能力提升，已经无法再显著拉高我的效率，我触到了阿姆达尔定律（Amdahl’s Law）的极限。**

剩下拖慢整体的，都是人无法并行、必须串行完成的部分：理解、判断、控复杂度、填坑、做权衡。

AI 可以帮我写实现，但不能替我控复杂度；可以帮我省敲代码的时间，却不能替我承担系统长大的代价。

## 结尾

> AI 把「写代码」这件事变得越来越简单，却也把「控复杂度」这件事，重新扔回了工程师自己手里。

工具越强大，越容易让人误以为：只要会提需求、会 prompt，就能做好系统。可真正走过这一年才明白：**代码可以交给 AI，但复杂度必须握在自己手里。**

当 AI 制造复杂度的速度，超过我消化复杂度的速度，再强的模型也只是在帮我「延迟还债」，而不是「免除债务」。

所以，这一轮折腾、复盘、踩坑之后，我得出一个很朴素的结论：

::: block-1
LLM 依旧是我最得力的助手，但它不再是我「完全不写代码」的理由。
:::

**也许，是时候重新拾起手写代码了。**

> 不是倒退，而是回归平衡——让 AI 做它擅长的实现，让我做我不可替代的控制。
