## 一、MoE 训练的通信困局与现有方案的致命缺陷

> 当大语言模型的参数规模突破万亿级别，混合专家架构已经成为行业公认的唯一可行的规模化路径。从 GPT-5、Gemini3 Pro 到 DeepSeek-V3、Qwen3，所有顶尖大模型都无一例外地采用了 MoE 设计。

然而，MoE 架构在带来参数规模可扩展性的同时，也引入了前所未有的通信挑战。:mdnice-bold-italic[专家并行作为 MoE 训练的标准分布式策略，其核心是将不同的专家部署在不同的 GPU 上，通过 token 路由实现计算负载的均衡分配。但正是这个路由过程，成为了整个训练系统的最大瓶颈。]

### 1.1 专家并行的本质与通信开销来源

> MoE 层的工作流程可以分为前向传播和反向传播两个阶段，如图 1 所示。

![文章插图](/articles/2026-05-18-moe-38-seed-uniep-megakernel-8d9502b5/images/06.webp)

::: image-caption
图 1：MoE前向和反向流。图中清晰展示了MoE层前向和反向传播的完整流程，前向传播包括分发、GroupGEMM计算和合并三个阶段，反向传播则是前向的逆过程，但权重梯度计算需要使用转置GroupGEMM。这一流程中，分发和合并阶段的通信操作是主要的性能瓶颈。EP 模式下通信与计算深度交织，传统方案将两者拆分为独立内核，依赖 CPU 同步引发开销与数值波动。UniEP 将这些环节融合为超级内核，直接针对该流程瓶颈优化，为单流融合设计提供流程层面的依据，凸显 EP 优化的核心痛点。
:::

- **在前向传播阶段**，首先由门控网络计算每个 token 分配给各个专家的概率，然后根据 top-k 选择（通常 k=6 或 8）确定每个 token 的目标专家和目标 GPU。接下来，token 需要被重新排列并通过 AlltoAll 或 AllGather 原语发送到目标 GPU，这就是分发阶段。到达目标 GPU 后，token 通过 GroupGEMM 操作进行计算，经过 SwiGLU 激活后，再通过第二个 GroupGEMM 投影回原始维度。最后，计算结果被发送回源 GPU 并根据门控分数加权求和，这就是合并阶段。
- **反向传播阶段的流程与前向传播对称，但引入了一个关键的复杂性：权重梯度的计算需要使用转置 GroupGEMM。** 与前向传播的 GroupGEMM 沿 token 维度分区不同，转置 GroupGEMM 沿累加维度分区，这意味着输入批次的拆分将改变梯度的累加顺序。由于浮点数加法不满足结合律，特别是在 BFloat16 精度下，累加顺序的改变会导致梯度的比特级差异，从而影响训练的可重复性和模型精度。

::: block-1
论文中的实证分析表明，**MoE 层的分发、计算和合并三个阶段可以消耗总训练时间的 30%至 80%，其中通信操作占据了主导地位。** 随着专家数量的增加（从 64 到 384 甚至更多），通信开销还会进一步增大。在带宽受限的集群中，通信瓶颈甚至会导致 GPU 的计算利用率低于 30%，造成巨大的算力浪费。
:::

### 1.2 现有优化方法的两大核心缺陷

> 为了缓解 MoE 训练的通信瓶颈，研究人员从计算、通信和重叠三个方面提出了大量优化方法。

- **在计算方面，无填充 GroupGEMM 是最核心的优化**。
- **在通信方面，基于 NVSHMEM 的原语优化成为主流**。
- **在重叠方面，现有方法主要分为 tile 级重叠和批次级重叠两种**。

> 尽管这些优化方法取得了一定的效果，但论文指出它们存在两个致命的核心缺陷：

- **第一，现有方法将计算和通信视为独立的操作，依赖粗粒度的多流管理实现重叠。** 这种分离需要频繁的主机端干预来启动内核和同步流，引入了大量的 CPU 开销和同步气泡。在大规模分布式训练中，不同 GPU 之间的 rank 同步会进一步放大这些气泡，甚至完全抵消重叠带来的收益。更严重的是，批次级重叠需要拆分微批次，这会改变转置 GroupGEMM 的梯度累加顺序，导致数值不稳定，破坏训练的可重复性。
- **第二，现有框架缺乏统一的通信原语。** AllGather 在 top-k 较大时带宽效率更高，而 AlltoAll 在稀疏路由时性能更好。这种二分法迫使开发人员维护复杂的启发式规则和多个独立的内核，不仅增加了开发和维护成本，也限制了系统的可移植性和适应性。

::: block-1
现有 MoE 训练优化方法陷入了一个无法突破的悖论：:mdnice-bold-italic[要么通过拆分微批次实现高性能重叠，但牺牲数值一致性；要么保持数值一致性，但只能获得有限的重叠效果。 UniEP 的核心目标就是打破这个悖论，在严格保证数值一致性的前提下，实现最大化的计算通信重叠。]
:::

## 二、UniEP 的核心设计：统一 MegaKernel 架构

> UniEP 的核心创新在于将 MegaKernel 技术从推理场景扩展到训练领域，通过将 MoE 的通信和计算子图融合成单个 MegaKernel，在 GPU SM 级别实现细粒度的计算通信重叠。

**与传统的多流方法不同，UniEP 将整个调度逻辑完全卸载到 GPU SM 上，不需要主机端的任何干预**。这不仅消除了 CPU 开销和同步气泡，还通过动态 SM 调度实现了计算和通信资源的自动负载均衡。同时，UniEP 通过确定性 token 映射机制，严格保证了与顺序执行的比特级数值一致性。

### 2.1 核心洞察：从多流粗粒度重叠到单流细粒度融合

> UniEP 的设计基于两个关键的核心洞察：

- **第一个洞察是，GPU 的流式多处理器（SM）可以通过块级调度实现计算和通信的细粒度重叠，不需要主机端的多流管理**。传统的多流方法将整个 GPU 视为一个单一的资源，在不同的时间点分别分配给计算或通信任务。而实际上，GPU 由多个独立的 SM 组成，不同的 SM 可以同时执行不同的任务。:mdnice-bold-italic[UniEP 利用这一点，将不同的 SM 动态分配给通信或计算角色，在单个 CUDA 流中实现指令级的重叠。]
- **第二个洞察是，通过参数化抽象可以统一 AllGather 和 AllToAll 两种通信模式，不需要显式的内核切换。** AllGather 和 AlltoAll 的本质区别在于数据的分发方式：UniEP 通过中继 Worker 实现了一种混合模式，既保留了 AlltoAll 的低通信量优势，又具备 AllGather 的灵活性，同时通过参数化的配置空间自动适应不同的工作负载。

::: block-1
基于这两个洞察，UniEP 设计了两个核心的 MegaKernel：Dispatch+GroupGEMM MegaKernel 和 GroupGEMM+Combine MegaKernel。

这两个 MegaKernel 分别对应 MoE 层前向传播的两个主要阶段，同时也适用于反向传播的对应阶段。
:::

### 2.2 Dispatch+GroupGEMM MegaKernel 的实现细节

Dispatch+GroupGEMM MegaKernel 是 UniEP 最核心的组件，它将前向传播中的 token 分发和专家计算两个阶段融合成一个单一的内核。其实现基于持久化 Worker 架构、确定性 token 映射、记分板同步、动态 SM 调度和中继 Worker 带宽优化五个关键技术。

#### 持久化 Worker 架构

> UniEP 的 MegaKernel 采用持久化线程块设计。在内核启动时，会启动与 GPU 物理 SM 数量完全相等的线程块，每个线程块作为一个持久化 Worker，在整个内核执行期间占据一个 SM。这种一对一的映射消除了线程块上下文切换的开销，同时避免了因线程块数量超过硬件容量而导致的死锁问题。

每个 Worker 可以动态承担三种角色之一：

- 通信 Worker：负责发送 token 和发起跨 GPU 事务
- 计算 Worker：负责执行 GroupGEMM tile 计算
- 中继 Worker：负责管理同步信号和执行 GPU 内数据多播

#### 确定性 token 映射

> 数值一致性是生产级训练的基本要求，而 token 的发送和接收顺序是保证数值一致性的关键。为了确保无论并行执行顺序如何， token 在目标专家缓冲区中的顺序都是确定的，UniEP 提出了一种确定性全局 token 映射算法，如算法 1 所示。

![文章插图](/articles/2026-05-18-moe-38-seed-uniep-megakernel-8d9502b5/images/07.webp)

::: image-caption
算法 1：确定性全局 token 映射。 算法通过本地稳定排序、全局计数 AllGather、前缀和偏移计算，生成每个 token 唯一的全局（目标卡、专家、偏移）地址。全程无原子锁，并行计算无冲突，确保 token 在跨卡传输后顺序固定。这是 UniEP 数值稳定的核心算法，解决重叠调度导致梯度累加无序的痛点，保证反向传播中位级一致性，让高性能重叠与工业级精度复现兼得，是 UniEP 区别于现有方案的关键设计。
:::

**算法 1 的核心思想是，通过 AllGather 操作收集所有 rank 发送给每个专家的 token 数量，然后计算每个 rank 发送给每个专家的 token 的全局基偏移b**。具体来说，对于专家 e，来自 rank r 的 token 的全局基偏移是所有 rank 小于 r 的 rank 发送给专家 e 的 token 数量的前缀和。然后，将这个基偏移与本地稳定排序索引结合，就可以得到每个 token 的唯一、无冲突的目标地址。

这种映射机制允许通信 Worker 并行地发送 token ，而不需要任何运行时的同步，同时严格保证了 token 在目标缓冲区中的顺序。这确保了后续 GroupGEMM 和归约操作的累加顺序与顺序执行完全一致，从而保证了比特级的数值一致性。

#### 记分板同步机制

> 为了协调生产者（通信 Worker 和中继 Worker）和消费者（计算 Worker）之间的依赖关系，UniEP 实现了一个轻量级的全局内存记分板。记分板分为两个部分：

$$
Scoreboard=[\underbrace {\mathcal {S}_{token }}_{Token Arrival }|\underbrace {\mathcal {S}_{tile }}_{Tile Ready }]
$$

其中，$\mathcal{S}_{token}$ 段跟踪单个 token 的到达状态，$\mathcal{S}_{tile}$ 段信号完整的 GroupGEMM tile 是否准备就绪。

- **中继 Worker 负责监控 token 的到达状态**。当通信 Worker 成功将一个 token 写入目标缓冲区后，会更新 $\mathcal{S}_{token}$ 中的对应条目。中继 Worker 轮询这些条目，当一个完整的 GroupGEMM tile （例如 128 个 token ）的所有 token 都到达后，中继 Worker 会原子地设置 $\mathcal{S}_{tile}$ 中的对应标志。
- **计算 Worker 则轮询 $\mathcal{S}_{tile}$，当收到 tile 就绪信号后，立即执行该 tile 的 GroupGEMM 计算**。UniEP 采用了受 MegaBlocks 和 vLLM 启发的无填充 GroupGEMM 内核，通过动态指针算术处理不规则的 tile 形状，确保了高 Tensor Core 利用率。

#### 动态 SM 调度

> 静态的 SM 角色分配往往会导致负载不平衡，特别是在 MoE 路由负载动态变化的情况下。为了解决这个问题，UniEP 采用了基于全局原子计数器的动态角色重分配策略。

系统维护一个全局原子计数器作为任务队列的游标。任务空间被线性化：索引从 0 到 $N_{comm}$ 对应通信任务，从 $N_{comm}$ 到 $N_{comm}+N_{comp}$ 对应计算任务。在运行时，每个 SM 通过原子递增全局计数器来获取任务，返回的任务 ID 决定了 SM 的当前角色：

1. 如果 ID 对应通信任务，SM 成为通信 Worker
2. 如果 ID 对应计算任务，SM 成为计算 Worker（可能需要等待记分板信号）
3. 任务完成后，SM 请求新的任务 ID

这种机制自然地平衡了工作负载：**初始时，所有 SM 都处理通信任务；随着数据的到达和记分板的填充，SM 逐渐过渡到计算角色。**

#### 中继 Worker 的带宽优化

> 在标准的 MoE 路由中，一个 token 可能被路由到同一个目标 GPU 上的多个专家（例如 Top-8 路由中，两个专家都在同一个 rank 上）。**朴素的实现会通过 NVLink 多次发送同一个 token ，造成带宽的浪费。**

UniEP 通过中继 Worker 优化了这个问题： token 只需要发送一次到目标 rank，然后由目标 rank 上的中继 Worker 检测到这种情况，并执行本地内存复制，为不同的专家复制 token 。这将昂贵的跨 rank NVLink 传输替换为高速的 HBM 内存复制，显著减少了通信流量。

![文章插图](/articles/2026-05-18-moe-38-seed-uniep-megakernel-8d9502b5/images/09.webp)

::: image-caption
表 1：带宽缩减的概率分析（Top-8，8 GPU）。表格量化 Top-8 路由下，单个 token 多专家分配至同一 GPU 的概率，理论可减少约 34% 的 NVLink 流量。UniEP 的中继工作通过节点内组播，将昂贵的跨卡 NVLink 传输转为高速 HBM 本地复制，规避重复传输。该分析为 UniEP 带宽优化提供理论支撑，是区别于 COMET 等基线的关键创新，直接降低 EP 通信带宽依赖，缓解核心瓶颈。
:::

### 2.3 GroupGEMM+Combine MegaKernel 的关键差异

> UniEP 将相同的 MegaKernel 原则应用于 GroupGEMM+Combine 阶段，包括动态 SM 调度和记分板同步。其工作流程与 Dispatch+GroupGEMM 阶段对称：**计算 Worker 执行 GroupGEMM 计算并向通信 Worker 发送信号，通信 Worker 将部分结果发送回源 rank，最后由归约 Worker 聚合传入的数据。**

这个阶段的一个关键区别是 Top-k 累加约束。为了保证数值正确性，归约 Worker 必须在执行求和之前，等待一个特定 token 的所有 Top-k 贡献都到达。过早的归约（在发送之前在本地 rank 进行累加）会违反浮点数加法的非结合性，导致非比特一致的结果。UniEP 通过在归约 Worker 逻辑中强制执行严格的屏障，保证了这一点，同时仍然隐藏了底层传输的延迟。

::: block-1
UniEP 的 MegaKernel 设计实现了三个关键突破：

- 第一，完全消除了主机端的干预，所有调度逻辑都在 GPU 上执行；
- 第二，通过动态 SM 调度实现了计算和通信资源的自动负载均衡；
- 第三，通过确定性 token 映射和严格的归约屏障，在最大化重叠的同时严格保证了数值一致性。
:::

## 三、自动调优：从手动调参到硬件感知的最优配置

> UniEP 的 MegaKernel 暴露了一个复杂的配置空间，包括每个 Worker 的 Warp 数、通信 Worker 数量、中继/归约 Worker 数量等参数。这些参数之间存在复杂的权衡关系，手动调参不仅耗时费力，而且很难找到最优配置。

为了解决这个问题，UniEP 构建了一个严谨的解析性能模型，能够自动预测不同配置下的端到端延迟，并在毫秒级内找到最优配置。同时，UniEP 还引入了优先级 token 调度机制，进一步提升了重叠效率。

### 3.1 优化空间与参数权衡

UniEP 将 Dispatch+GroupGEMM 阶段的优化配置分为三个原语：每个 Worker 的 Warp 数 $w_{disp}$、通信 Worker 数量 $N_{disp}$ 和中继 Worker 数量 $N_{relay}$。GroupGEMM+Combine 阶段有对应的对称参数：$w_{comb}$、$N_{comb}$ 和 $N_{red}$。这些参数之间存在复杂的权衡关系：

#### 每个 Worker 的 Warp 数（$w_{disp}$、$w_{comb}$）

> 每个 SM 分配的 Warp 数是一个全局参数，在计算稳定性和通信吞吐量之间创造了一个基本的权衡。有效的搜索空间通常是{8, 16, 32}。

从计算角度来看，对于计算 Worker，Hopper GPU 上的经验分析表明，8 个 Warp 就足以饱和 Tensor Core 流水线。分配过多的 Warp（例如 32 个）会迫使 Warp 调度器激进地发射指令，导致高功率密度，触发硬件热节流，降低时钟频率，从而降低整体 FLOPS。

从通信角度来看，通信 Worker 是延迟绑定的，它们从更高的 Warp 数中获益显著。32 个 Warp 可以提供足够的指令级并行性（ILP）来隐藏内存访问延迟，饱和 NVLink 带宽。由于 MegaKernel 需要统一的网格配置，$w$ 必须被调整以平衡热节流的风险和带宽饱和的需求。

#### 通信 Worker 数量（$N_{disp}$、$N_{comb}$）

> 这个参数控制通信阶段的并行度，决定了生产者和消费者之间的资源分配。有效的范围是 $[1, N_{SM})$。调优这个参数会导致两种结果：

- 过度分配：如果 $N_{disp}$ 太大（接近 $N_{SM}$），内核开始时会出现通信突发，几乎所有 SM 都作为生产者。这会阻塞消费者端，阻止计算 Worker 的早期启动，实际上使执行串行化。
- 分配不足：如果 $N_{disp}$ 太小，系统会成为通信绑定。计算 Worker 消耗记分板的速度比生产者填充的速度快，导致计算 SM 空闲。

最优的 $N_{disp}$ 会随着工作负载的算术强度动态变化，必须针对每个问题大小进行调优。

#### 中继 Worker 数量（$N_{relay}$、$N_{red}$）

> 中继 Worker 通过 intra-rank 多播减少了 inter-rank 流量，但这种优化是以资源成本为代价的。标准的 EP 实现使用 AllGather 或 AlltoAll，AllGather 的通信量被世界大小 $W$ 放大：$W × N_{tok} × S_{tok}$，而 AlltoAll 的通信量被 Top-k 因子放大：$N_{tok} × topk × S_{tok}$。UniEP 将其优化到大约 $N_{tok} × 5.25 × S_{tok}$（对于 Top-8）。

为了实现这个收益，中继 Worker 必须消耗 SM 资源来处理记分板信号和执行 HBM 复制。这里有一个严格的约束：

$$
N_{disp} + N_{relay} < N_{SM}
$$

违反这个约束可能会导致死锁，因为可能没有足够的 SM 来调度解锁计算所需的中继 Worker。另一方面，必须分配足够的中继 Worker 以确保它们不会成为瓶颈（阻塞通信 Worker），同时最小化它们的数量以保留 SM 用于 GroupGEMM。搜索范围通常是 $[1, N_{SM} - N_{disp})$。

### 3.2 解析性能模型的构建

UniEP 的优化空间由元组定义：

$$
\mathcal{C}=\left(w_{disp }, N_{disp }, N_{relay }, w_{comb }, N_{comb }, N_{red }\right)
$$

为了自动找到最优配置，UniEP 构建了一个解析性能模型，能够预测任何给定配置 $c$、硬件规格 $H$ 和问题大小 $P$ 下的端到端延迟 $L_{total}$。表 2 总结了模型中使用的符号。

::: image-caption
表 2：性能模型的符号与含义。表格统一定义 UniEP 自动调优模型的硬件、问题、优化变量符号，涵盖 SM 数量、NVLink/HBM 带宽、GEMM 分块尺寸、工作分配参数等。标准化符号体系支撑解析模型构建，让模型可精准量化不同配置下的延迟，实现超 10^5 级配置空间的快速搜索。这是 UniEP 自动化调优的基础，平衡搜索效率与硬件行为拟合精度，保障调优结果可靠。
:::

#### 有效带宽

有效带宽函数 $B(n, \beta)$ 定义了给定 $n$ 个活动 SM 和峰值带宽 $\beta$ 时的实际可用带宽。令 $u$ 为每个 SM 的 Warp 数，$w_{sat}$（例如 1024）为饱和阈值。可用带宽受硬件峰值或活动 Warp 数的限制：

$$
\mathcal{B}(n, \beta)=min \left(n \cdot w \cdot \frac{\beta}{w_{sat }}, \beta\right)
$$

这个公式的含义是：

- 当活动 Warp 数不足以饱和带宽时，带宽与 Warp 数成正比；
- 当 Warp 数足够多时，带宽达到硬件峰值。

#### GEMM 块延迟

CalcGEMM 函数估计单个 GroupGEMM tile 的执行时间。对于 tile 大小 $B_M × B_N$ 和归约维度 $K$，延迟由峰值 FLOPS 乘以 MFU$\mu$（观察到的 FLOPS 与理论峰值的比率）得出。由于每个 tile 需要等待信号或设置信号，还需要添加一个同步开销 $\tau_{sync}$：

$$
t_{gemm }(K)=\frac{2 \cdot B_{M} \cdot B_{N} \cdot K}{\mathcal{P}_{peak } \cdot\left(\mu / N_{SM}\right)}+\tau_{sync }
$$

因此，$t_{up}=t_{gemm}(H_{dim})$，$t_{down}=t_{gemm}(H_{inter})$，其中 $H_{dim}$ 是隐藏大小，$H_{inter}$ 是 MoE 中间大小。$\mu$ 与 Warp 数 $w$ 相关，根据经验设置为：

$$
\mu (w=8)=0.7 \quad \mu (w=16)=0.65 \quad \mu (w=32)=0.6
$$

#### SwiGLU 延迟

SwiGLU 是严格的内存绑定操作。对于 $N_{tok}$ 个大小为 $S_{tok}$ 的 token ：

$$
L_{swiglu }=\frac{2\cdot N_{tok} \cdot S_{tok}}{\beta _{HBM}}
$$

#### Dispatch 延迟

Dispatch 延迟是 NVLink 传输（远程）和 HBM 写入（本地/中继）的成本之和。在有 $N_{disp}$ 个活动通信 SM 和 $N_{relay}$ 个活动中继 SM 的情况下：

$$
L_{disp }=\frac{V_{n v l}}{\mathcal{B}\left(N_{disp }, \beta_{N V L}\right)}+\frac{V_{h b m}}{\mathcal{B}\left(N_{relay }, \beta_{H B M}\right)}
$$

#### 计算延迟

一个阶段的总计算时间由在分配的计算 SM 上处理所有 tile 所需的波数决定。令 $N_{tiles}$ 为 GEMM 块的总数：

$$
L_{comp}(t_{block},N_{comp})=\left\lceil \frac {N_{tiles}}{N_{comp}}\right\rceil \cdot t_{block}
$$

#### Combine 延迟

与 Dispatch 类似，Combine 延迟计算通过 NVLink 的散射延迟。它还返回 $t_{red}$，即单个 SM 在 HBM 中执行传入 token 归约的时间：

$$
L_{comb }=\frac{V_{n v l}}{\mathcal{B}\left(N_{comb }, \beta_{N V L}\right)}
$$

$$
t_{red }=\frac{V_{h b m_{-} total }}{\mathcal{B}\left(1, \beta_{H B M}\right)}
$$

> 算法 2 整合了上述所有公式，模拟了计算和通信的重叠效果，预测了端到端延迟。

![文章插图](/articles/2026-05-18-moe-38-seed-uniep-megakernel-8d9502b5/images/11.webp)

::: image-caption

- 对于 Dispatch+UpGEMM 阶段，如果计算延迟 $L_{up}$ 大于通信延迟 $L_{disp}$，则有效延迟是通信时间加上计算的尾部；否则，有效延迟是通信时间加上单个 GEMM 块的延迟。

### 3.3 优先级 token 调度与运行时优化

> 在上述性能模型中，有一个强假设：计算和通信可以完美重叠。为了实现这一点，UniEP 引入了优先级 token 调度机制。

在朴素的实现中，通信 Worker 可能按照自然顺序（例如专家 0，然后专家 1，...）传输 token 。然而，远程计算 Worker 是确定性的：它按照专家 ID 升序处理 tile 。如果本地第一个专家的数据到达较晚，即使后面专家的数据已经在 HBM 中可用，计算 Worker 也会停滞。这种队头阻塞会严重降低重叠效率。

::: block-1
为了解决这个问题，UniEP 强制生产和消费之间的严格对齐。计算 Worker 按照升序处理专家（本地 $E_0, E_1, ...$），相应地，通信 Worker 对它们的传输队列进行排序，优先发送目标为远程专家 0 的 token ，然后是专家 1，依此类推。由于全局偏移是通过前缀和预先计算的，这种排序可以通过遍历专家偏移数组隐式实现，确保零开销的优先级。
:::

在运行时实现方面，UniEP 的初始 Python 版本的性能模型需要约 100 秒来遍历整个搜索空间，这对于在线调优来说是不可接受的。为了解决这个问题，研究人员用 C++重新实现了搜索算法，并使用 OpenMP 进行并行化，将搜索时间缩短到约 144 毫秒。此外，UniEP 还采用了分桶记忆化策略，将输入序列长度 $N_{tok}$ 离散化为 4096 token 的桶。只有当工作负载跨越桶边界时，才会查询性能模型，最优配置会被缓存并在后续迭代中重用。这将自动调优器的摊销开销降低到在长期运行的训练作业中可以忽略不计的水平。

::: block-1
UniEP 的自动调优框架将复杂的手动调参过程转化为一个自动化的硬件感知优化过程。通过严谨的解析性能模型，UniEP 能够在毫秒级内找到最优配置，实现了对不同工作负载和硬件环境的自适应。
:::

#### 基准分析

**Serial 基准尽管使用了 DeepEP，但性能仍然很差，这归因于标准 GroupGEMM 实现中的专家循环模式**。这种模式需要频繁的 CPU-GPU 同步来获取形状元数据，导致巨大的开销，远远超过了优化后的通信时间。

**与 COMET 相比，UniEP 的优势主要来自两个方面：**

1. **中继 Worker 通过 intra-node 多播减少了物理流量**，这是 COMET 没有实现的优化。
2. 分析跟踪显示，COMET 存在对齐气泡，这是由双流上内核的异步启动引起的空闲间隙。**UniEP 通过将操作融合到单流上的 MegaKernel 中，完全消除了这些气泡。**

#### 集群敏感性

> 加速比在带宽受限的 Cluster1 上更为明显，这是预期的：当系统是通信绑定时，重叠的效果最大化。在 Cluster2 上，主要的收益从带宽隐藏转移到了同步开销的减少。

## 五、相关工作对比

> MoE 训练效率是近年来深度学习系统领域的研究热点，研究人员从高性能内核、计算通信重叠和系统框架三个方面提出了大量的工作。

然而，这些工作大多存在零散优化、缺乏统一抽象、牺牲数值一致性等问题。UniEP 通过统一的 MegaKernel 架构，在严格保证数值一致性的前提下，实现了最大化的计算通信重叠，代表了 MoE 训练系统的一个重要突破。

### 5.1 高性能内核库与张量编译器

> 专家调优的高性能库是深度学习系统的基础。

在计算方面，CuBLAS、CuDNN 和 CUTLASS/CuTe 代表了计算绑定内核的最先进水平，通过手动管理内存层次结构（利用 TMA 和异步复制等功能）实现了接近峰值的 Tensor Core 利用率。FlashAttention 和 FlashInfer 等专门的注意力内核进一步优化了 IO 复杂度。

在通信方面，NCCL 是集体操作（AllReduce、AllGather）的事实标准。**然而，NCCL 主要针对稠密张量并行优化，缺乏对 EP 的稀疏、动态模式的专门支持**。:mdnice-bold-italic[为了解决这个问题，DeepEP 被开发出来，利用低级 NVSHMEM 原语（IBRC、IBGDA）直接从 GPU 发起对等通信，绕过主机 CPU 并饱和物理带宽。]

张量编译器和 DSL 的出现降低了内核开发的门槛。

- Halide 和 TVM 引入了计算定义与调度原语的分离。
- 最近的进展集中在以 tile 为中心的编程模型：Triton 和 TileLang 暴露了块级语义，平衡了易用性和性能。
- NVIDIA 的 CuTile 和 CuTeDSL 在 Python 中提供了类似的抽象。
- 在通信领域，MSCCL 和 MSCCL++允许使用原始操作（put/get/signal）可编程地合成集体算法，实现拓扑感知的优化。

**UniEP 建立在 Triton-distributed 之上，扩展了其能力以支持融合的计算和通信流水线**。与传统的内核库不同，UniEP 不将计算和通信视为独立的操作，而是将它们融合成一个统一的 MegaKernel，实现了细粒度的重叠。

### 5.2 计算通信重叠技术

> 计算通信重叠是隐藏分布式训练中通信延迟的关键技术。现有的方法主要分为多流方法和设备端信令方法两类。

多流方法是目前最主流的方法，被 Megatron-LM、Centauri 和 TorchTitan 等框架广泛采用。计算和通信内核被放置在不同的 CUDA 流上，依赖 CPU 来管理同步。这种方法存在两个局限性：

- 第一，将大的 GEMM 拆分成更小的块以适应重叠槽会减少每个内核的线程块数量，加剧波量化效应，其中线程块的尾波未充分利用 GPU，导致算术强度下降。
- 第二，依赖 CPU 干预来启动内核和同步流会引入不可忽略的抖动和开销，在大规模下经常破坏重叠调度。

设备端信令方法通过使用设备端信号量（全局内存标志）来同步不同的计算和通信内核，减轻了 CPU 开销。CoCoNet、COMET、FLUX 和 TileLink 都采用了这种方法。然而，它们仍然依赖双流执行。DeepSeek-V3 采用了更激进的策略，将下一个微批次的通信与当前微批次的计算重叠。虽然对特定架构有效，但这种双批次方法不适合 FSDP 训练，因为拆分两个批次会改变梯度累加顺序。由于浮点数加法的非结合性，这会破坏比特级的可重复性，这对于严格的训练场景是不可接受的。

**相比之下，UniEP 通过融合的 MegaKernel 在单流内实现重叠**。通过在 SM 级别调度资源，UniEP 消除了 CPU 开销和数值妥协的需要。:mdnice-bold-italic[最近的工作如 Mirage 和 Spector 等人使用 MegaKernel 进行推理，将整个 LLM 融合到一个 CUDA 内核中。这种整个 LLM 融合方法对于批量 1 的推理是有效的，但对于大批量训练，开发复杂性是难以承受的，性能提升也是边际的]。**UniEP 是第一个将 MegaKernel 技术成功应用于 MoE 训练领域的工作。**

### 5.3 MoE 训练与推理框架

> MoE 训练框架的效率是近年来的研究焦点。TransformerEngine 和 vLLM 提供了高度优化的 GroupGEMM 内核。以动态为中心的工作如 MegaBlocks 提出了块稀疏格式来处理可变 token 负载而无需填充。系统级工作如 HeterMoE 针对异构集群进行了优化，而 DeepSpeed-MoE 专注于模型压缩和通信调度。MegaScale-MoE 集成了 FLUX 以在大规模运行中隐藏通信成本。

尽管有这些进步，在生产级框架（如 Megatron-LM）中的采用仍然保守。临时优化内核的集成经常引入复杂性和脆弱性。UniEP 通过提供一个统一的、数学上严谨的抽象来弥合这一差距，它提供了激进重叠的性能优势，同时保持了工业级 LLM 训练所需的稳定性和精度。

在推理方面，包括 DeepSeek-EPLB、FasterMoE 和 MegaScale-Infer 在内的推理框架通过将专家权重复制到不同的 rank 来平衡不同专家的工作负载。UniEP 与专家放置策略是正交的，这两种方法在不同的级别上运行，可以结合起来进一步提高推理性能。

::: block-1
与现有工作相比，UniEP 的核心优势在于其统一的 MegaKernel 架构和严格的数值一致性保证。它解决了现有方法中普遍存在的性能与精度的悖论，为 MoE 训练系统提供了一个新的设计范式。
:::

## 六、结论与展望

> UniEP 代表了 MoE 训练系统领域的一个重要里程碑。它首次将 MegaKernel 技术从推理扩展到训练领域，通过统一的架构实现了细粒度的计算通信重叠，同时严格保证了数值一致性。

实验结果表明，UniEP 在生产级硬件和模型上实现了显著的性能提升，并且已经在 128GPU 的生产集群上得到了验证。然而，UniEP 仍然存在一些局限性，未来还有很多值得探索的方向。

### 6.1 结论总结

本文提出了 UniEP，一个统一的专家并行训练系统，通过可组合的 MegaKernel 架构缓解了专家并行中的通信瓶颈。与之前的工作不同，UniEP 实现了细粒度的计算通信重叠，同时通过确定性 token 排序严格保证了数值一致性。

UniEP 的核心贡献可以总结为三点：

1. 首次将 MegaKernel 架构应用于 MoE 训练，在单流内实现了高性能的计算通信重叠，同时严格保留了数值精度。
2. 引入了利用 token 重映射和参数空间搜索的统一 EP 抽象，自动适应不同的 MoE 工作负载，消除了手动原语选择的复杂性。
3. 在配备 NVIDIA Hopper GPU 的集群上对生产级工作负载（包括 DeepSeek、Qwen 和 Kimi 变体）进行了评估，实验证明 UniEP 在核级基准和端到端训练上都比最先进的工作实现了显著的加速，最高达到 1.38 倍。

UniEP 的 MegaKernel 实现已经开源在https://github.com/ByteDance-Seed/Triton-distributed，为社区提供了一个高性能、可扩展的MoE训练基础。

### 6.2 进阶分析：方法的边界与局限性

> 尽管 UniEP 取得了显著的成果，但我们必须客观地认识到它的边界和局限性，避免过度夸大其价值。

- 首先，UniEP 的性能优势主要体现在通信绑定的场景下。:mdnice-bold-italic[当 MoE 模型的计算强度非常高，或者集群的带宽非常充足时，通信瓶颈不再是主要问题，UniEP 的优势会显著缩小]。例如，在 Cluster2 的 32k 序列长度下，UniEP 相对于 COMET 的反向传播加速比只有 1.09 倍。**在未来的 GPU 架构中，如果互连带宽的提升速度超过计算能力的提升速度，UniEP 的性能优势可能会进一步减弱。**
- 其次，UniEP 目前依赖 Triton-distributed 框架。虽然 Triton-distributed 支持 AMD GPU，理论上可以将 UniEP 移植到 AMD 平台而无需重大修改，但实际性能还需要验证。此外，Triton 内核在最新的 GPU 架构上可能不如高度优化的 CUDA 内核性能好。虽然论文指出 UniEP 的设计是语言无关的，可以用 CUDA 重写来缩小这个差距，但这需要大量的工程工作。
- 第三，非比特一致版本的 UniEP 的性能提升有限，只有 2%-8%，而且在某些场景下反而会变慢。:mdnice-bold-italic[这说明，即使愿意牺牲数值一致性，现有的重叠技术已经接近了理论上限。 未来的性能提升可能需要从根本上改变 MoE 的架构，而不仅仅是优化通信和计算的重叠。]
- 第四，自动调优虽然已经优化到 144 毫秒，但**对于动态变化的工作负载，实时调优仍然有挑战**。例如，在训练过程中，如果门控网络的路由分布发生显著变化，之前缓存的最优配置可能不再是最优的。虽然分桶记忆化策略可以缓解这个问题，但对于极端动态的工作负载，可能需要更智能的在线调优方法。
- 最后，UniEP 目前只支持 NVIDIA Hopper 架构，对更早的架构（如 Ampere）和其他厂商的 GPU（如 AMD、Intel）的支持还不完善。这限制了 UniEP 在更广泛的硬件环境中的应用。

### 6.3 未来工作

> 论文作者明确指出了几个未来的研究方向：

1. 移植到其他硬件平台：UniEP 的概念可以推广到其他 GPU 平台，包括 AMD GPU 和最新的 NVIDIA GPU。Triton-distributed 对 AMD GPU 的支持为将当前实现迁移到 AMD GPU 提供了可能性，无需重大修改。
2. 用 CUDA 重写内核：虽然基于 Triton 的内核在 Hopper GPU 上可以实现与 CUDA 内核相当的性能，但在最新的 GPU 架构上可能存在差距。未来可以用 CUDA 重写 UniEP 的内核，进一步提升性能。
3. 扩展到更多的 MoE 变体和分布式训练场景：目前 UniEP 主要针对标准的专家并行训练，未来可以扩展到支持更多的 MoE 变体，如 Switch Transformer、GLaM 等，以及结合其他分布式训练策略，如张量并行和流水线并行。

#### NeuralTalk 视角

> 从更宏观的领域趋势来看，UniEP 的成果可能会催生以下几个新的技术方向：

- 第一，**将 MegaKernel 架构扩展到 3D 并行的其他维度**。目前 UniEP 只优化了专家并行的通信和计算重叠，未来可以:mdnice-bold-italic[将 MegaKernel 的思想扩展到张量并行和流水线并行，实现整个 Transformer 层的融合。这将进一步消除不同并行维度之间的同步开销，提升整个训练系统的效率。]
- 第二，**结合动态专家路由和负载均衡技术**。UniEP 目前假设专家路由是静态的，未来可以将动态专家路由和负载均衡技术集成到 MegaKernel 中，实现路由和计算的协同优化。:mdnice-bold-italic[例如，可以在 MegaKernel 中动态调整专家的负载，避免某些专家过载而其他专家空闲的情况。]
- 第三，探索 MegaKernel 在多模态 MoE 训练中的应用。随着多模态大模型的兴起，多模态 MoE 成为了一个重要的研究方向。多模态 MoE 的 token 路由更加复杂，涉及到不同模态的 token 和不同类型的专家。UniEP 的 MegaKernel 架构可以很自然地扩展到多模态场景，处理不同模态的 token 路由和计算。
- 第四，将自动调优框架与机器学习方法结合。目前 UniEP 的自动调优基于解析性能模型，未来可以将机器学习方法引入自动调优框架，通过学习历史调优数据来预测最优配置，进一步提高调优的速度和准确性。特别是对于动态变化的工作负载，机器学习方法可以更好地适应路由分布的变化。
- 第五，推动 MegaKernel 成为分布式训练的标准范式。长期以来，分布式训练系统都是基于计算和通信分离的设计范式。UniEP 的成功证明了 MegaKernel 架构在分布式训练中的可行性和优势。未来，MegaKernel 可能会成为分布式训练的标准范式，改变整个深度学习系统的设计思路。

::: block-1
UniEP 不仅是一个优秀的 MoE 训练优化系统，更代表了一种新的分布式训练设计范式。**它打破了计算和通信分离的传统思维，通过 GPU 级的细粒度调度和融合，实现了性能和精度的双赢**。随着硬件和软件技术的不断发展，MegaKernel 架构有望在未来的深度学习系统中发挥越来越重要的作用。
