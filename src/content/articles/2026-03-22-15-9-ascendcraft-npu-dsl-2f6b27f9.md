关键词：大语言模型、**昇腾 NPU**、**算子内核生成**、:mdnice-bold-italic[领域特定语言（DSL）]、代码 Lowering

> 在 AI 芯片领域，编写一个高性能的算子内核，就像是在一个精密、复杂且文档稀疏的机器上跳舞。大模型能写 CUDA，却为何在华为昇腾 NPU 面前“失语”？AscendCraft 团队给出了一个精妙的答案：不是让大模型直接“硬写”底层代码，而是为它创造一个“中间世界”——一个轻量级的领域特定语言（DSL）。:mdnice-bold-italic[通过将核心算法逻辑与硬件复杂性解耦，他们将生成内核的编译成功率提升至 98.1%，功能性正确率高达 90.4%，甚至让近半数生成的内核性能超越 PyTorch]。这不仅是代码生成的突破，更是对大模型理解硬件抽象能力的一次深刻探索。

## 一、 困境：为什么 LLM 写不好 NPU 内核？

要理解 AscendCraft 的价值，首先需要深刻理解它所面对的挑战。直接让 LLM 生成 NPU 内核，就像要求一个从未见过汽车引擎的学徒去修理它，而他手里只有一本关于内燃机原理的大学教材。

### 1.1 硬件架构的“异质性”

> 与通用的 GPU 不同，NPU 是为特定计算模式而生的。以华为昇腾（Ascend）NPU 为例，其核心计算单元分为三类：

- **标量单元（Scalar Unit）**：处理控制流和标量数据。
- **向量单元（Vector Unit）**：执行 SIMD（单指令多数据流）操作，如元素级加法和激活函数。
- **立方体单元（Cube Unit）**：这是 NPU 的“杀手锏”，专门用于矩阵乘加运算，可以在一个指令周期内完成一个 MxK 与 KxN 的矩阵乘法。

::: block-1
此外，它的内存层次结构也非常复杂，包括全局内存（GM）、L1 缓冲区、统一缓冲区（UB）和 L0 缓冲区。开发者需要显式地控制数据在这些层级间的移动。
:::

![文章插图](/articles/2026-03-22-15-9-ascendcraft-npu-dsl-2f6b27f9/images/04.webp)

::: image-caption
图 1：Ascend NPU 架构示意图，展示了从外部存储器到 AI Core 内部的多级存储单元和计算单元（标量、向量、立方体）的复杂层次。该图作为 AscendCraft 内核生成的硬件依据。文中指出昇腾 NPU 以 AI Core 为核心，集成标量、向量、Cube 计算单元，搭配多级存储与内存传输引擎，支持显式指令流水线。该架构要求内核遵循 CopyIn/Compute/CopyOut 执行逻辑，这也是 AscendCraft 设计轻量化 DSL 的核心，DSL 显式建模该架构语义，屏蔽底层复杂细节，大幅降低 LLM 生成 Ascend C 内核的难度，保障生成内核适配硬件特性。
:::

### 1.2 编程模型的“复杂性”

AscendC，这个为昇腾 NPU 设计的编程模型，正是基于这种硬件复杂性而构建的。它是一个基于 C++的流水线式编程模型。

- **显式流水线**：内核执行被明确划分为`CopyIn`（数据搬入）、`Compute`（计算）和`CopyOut`（数据搬出）三个阶段。开发者需要手动管理这些阶段的重叠和同步，以最大化硬件利用率。
- **内存管理**：`GlobalTensor`和`LocalTensor`的区分，以及对齐、粒度等硬件约束，迫使开发者必须像管理一个物理仓库一样管理内存。
- **队列与依赖**：为了协调不同计算单元和 MTE（内存传输引擎）的操作，AscendC 引入了队列（Queue）机制。数据在不同单元间流动，需要通过“入队/出队”来显式管理依赖关系。

对于 LLM 而言，要同时生成符合这些复杂语义的代码，无异于让它在黑暗中摸索。任何一个微小的错误——比如内存地址未对齐，或者队列顺序混乱——都会导致编译失败或运行时错误。这正是直接生成方式正确率低于 5%的根本原因。

## 二、 破局：AscendCraft 的设计思想与核心方法

> 面对直接生成的“不可能三角”（复杂性、约束性、稀缺性），AscendCraft 选择了一条优雅的迂回路线：**分而治之，降级编译**。其核心思想是：让 LLM 在**抽象层** 做它擅长的事，而将**具体实现** 交给一个结构化的、可控制的降级流程。

### 2.1 第一阶段：DSL 生成——为 LLM 搭建“乐高世界”

> AscendCraft 的核心创新是其引入的轻量级 DSL。这个 DSL 被精心设计，充当了 LLM 与复杂硬件之间的“缓冲区”。它的设计遵循三个原则：

1. **简洁、结构化的语法**：DSL 的语法非常紧凑，类似于 Triton。它去掉了 C++的繁文缛节，让 LLM 可以专注于核心的算法逻辑，比如分块（tiling）策略和数据流。如图 3 所示的 Softmax DSL 代码，结构清晰，一目了然。
2. **适当的抽象**：DSL 刻意隐藏了 AscendC 中那些“繁琐但非核心”的细节。例如，在 AscendC 中处理非对齐内存访问需要复杂的`DataCopyPad`配置，而在 DSL 中，这只是一个简单的`tl.load`。
3. **针对性的扩展**：DSL 显式地建模了 Ascend 特有的执行语义。例如，通过`tl.alloc_ub`来显式分配片上统一缓冲区，通过`copyin`、`compute`、`copyout`块来强制划分流水线阶段。

![文章插图](/articles/2026-03-22-15-9-ascendcraft-npu-dsl-2f6b27f9/images/05.webp)

::: image-caption
图 2：基于本文提出的昇腾 DSL 编写的 Softmax 内核示例。该示例展示了主机端执行规划与内核端片上计算的分离，以及 CopyIn、Compute、CopyOut 的分阶段执行模式，体现该 DSL 在抽象底层 Ascend C 细节的同时，表达分块计算、片上缓冲区使用与核间数据流逻辑的能力。该图以 Softmax 内核直观呈现 AscendCraft 专用 DSL 的设计优势。DSL 拆分主机与内核函数，主机负责核划分与分块策略，内核聚焦片上三段式流水线执行，屏蔽内存对齐、DataCopyPad 等 Ascend C 复杂细节。该设计让 LLM 专注核心算法逻辑，降低生成错误率。此示例验证 DSL 简洁且适配昇腾硬件，为后续转译 Ascend C 提供规范中间表示，是提升内核生成正确性的关键载体。
:::

在生成阶段，LLM 被提供了 DSL 规范以及“类别特定”的专家示例。例如，对于“规约（Reduce）”类算子，LLM 会看到专家如何通过 DSL 实现高效的分块规约策略。通过这种方式，LLM 学到了高级的优化模式，而不是被具体的 AscendC API 所困扰。

### 2.2 第二阶段：降级编译——DSL 到 AscendC 的结构化“翻译”

> 这是 AscendCraft 工程智慧的集中体现。:mdnice-bold-italic[他们并没有尝试让 LLM 一步到位地将 DSL“翻译”成 AscendC，而是将这个过程分解为四个有序的、由 LLM 引导的降级（Lowering）阶段。每个阶段只关注一个特定的转换任务，并且每个阶段都配备了一个精心设计的“提示词模板”。]

这四个阶段分别是：

#### 阶段 1：主机端翻译

- 任务：将 DSL 中的主机函数翻译成 AscendC 的宿主代码。这包括定义数据结构、计算分块参数（如每个核心处理的行数）和配置内核启动参数。
- 关键约束：确保所有主机侧计算出的参数都能正确传递给内核。

#### 阶段 2：内核初始化翻译

- 任务：生成内核的初始化逻辑。这包括将主机传入的参数赋值给内核成员变量、获取块 ID（`GetBlockIdx()`）以计算该核心的数据偏移量，以及初始化片上内存资源。
- 关键映射：DSL 中的`alloc_ub`缓冲被映射为 AscendC 中的`TQue`（传输队列）或`TBuf`（临时缓冲）。`TQue`用于实现流水线，`TBuf`用于临时存储。

#### 阶段 3：内核计算翻译（核心阶段）

- 任务：将 DSL 内核函数的`copyin`、`compute`、`copyout`块，分别翻译成 AscendC 中的同名函数（如`CopyInX`、`ComputeX`、`CopyOutX`）。
- 关键映射：
- 结构约束：通过强制将逻辑划分为这三个独立的函数，AscendCraft 从结构上防止了数据搬移和计算指令的错误交织，这是确保正确性的关键。

#### 阶段 4（可选）：对齐与填充优化

- 任务：处理硬件对齐的特殊情况。当 DSL 中的分块大小不满足 AscendC 的内存对齐要求时，此阶段会将普通的`DataCopy`替换为支持填充（padding）的`DataCopyPad`，并自动计算填充参数。

::: block-1
在每个阶段结束后，生成的代码都会尝试编译。如果编译失败，错误信息会被反馈给 LLM，LLM 会根据错误信息修正代码，然后进入下一个阶段。这种**带反馈的逐步降级** 机制，极大地提升了生成过程的鲁棒性。
:::

## 三、 实验验证：从“5%的绝望”到“90%的惊喜”

### 3.3 RQ3：泛化性——应对“未知”的挑战

> 为了测试 AscendCraft 能否应对全新的算子，研究者将其应用于一个刚刚提出的新型神经网络结构——mHC（Manifold-Constrained Hyper-Connections）。**这个模型结构在基准测试中不存在，因此没有任何先验的专家示例。**

结果令人振奋：**AscendCraft 在单次生成中，就为 mHC 的两个核心算子生成了功能正确的 AscendC 内核**，其性能分别是 PyTorch eager 模式的 **6.6 倍** 和 **3.0 倍**。

::: block-1
更令人印象深刻的是，研究者让一位经验丰富的 AscendC 开发人员以这些生成为起点进行优化。由于代码结构清晰、可读性强，开发人员在 LLM 的辅助下，**仅用一天时间** 就将性能进一步优化到了 PyTorch 的 **15.9 倍** 和 **7.2 倍**。
:::

这个案例生动地展示了 AscendCraft 的巨大价值：它不仅能自动生成高质量内核，还能为后续的专家级优化提供一个坚实、可靠的起点。

## 四、 相关工作：站在巨人的肩膀上

> AscendCraft 的工作并非凭空产生，它巧妙地融合了多个领域的前沿成果，并开创了新的方向。

- **LLM 驱动的代码生成**：这无疑是当前的热门方向。相关研究如`KernelBench`、`Astra`、`KernelEvolve`等，都在探索如何让 LLM 更好地生成 CUDA 内核。:mdnice-bold-italic[AscendCraft 的独特之处在于，它将目光投向了更冷门、更困难的 NPU 领域。]
- **GPU 内核自动生成**：以`Triton`为代表的 DSL，通过高级抽象极大地简化了 GPU 内核的开发。`AscendCraft`的设计思想，特别是其 DSL 的语法，受到了`Triton`的启发。:mdnice-bold-italic[但不同的是，`AscendCraft`的 DSL 是为 NPU 的独特执行语义（如显式流水线）量身定制的。]
- **中间表示与降级**：在传统编译器中，通过多层中间表示（IR）将高级语言降级为机器码是标准做法。AscendCraft 将这个思想引入到 LLM 驱动的代码生成中，:mdnice-bold-italic[创造性地将 LLM 作为“智能降级器”，将高层次的 DSL 一步步翻译成低层次的 AscendC 代码。]

::: block-1
AscendCraft 的创新之处在于，它并非简单地将某个现有方法移植到 NPU 上，而是深刻洞察了 NPU 编程的核心难点，并设计了一套完整的解决方案，其核心在于**通过 DSL 实现了问题空间的拆分，让 LLM 和结构化编译流程各司其职，最终在充满约束的 NPU 领域取得了显著成功**。
:::

## 五、 未来展望与总结

> AscendCraft 的工作无疑是开创性的，但它也揭示了未来值得探索的方向：

1. **性能瓶颈的突破**：对于`Reduce`和`Normalization`这类算子，AscendCraft 生成的代码性能仍有待提升。未来可以探索在 DSL 层面引入更细粒度的硬件原语，或者在降级阶段加入自动化的性能调优策略。
2. **DSL 的表达力扩展**：当前 DSL 主要覆盖了单算子，未来可以扩展其表达力，以支持更复杂的融合算子（如 Attention）的生成。
3. **从生成到优化闭环**：AscendCraft 的案例已经展示了“生成-优化”的工作流。未来可以构建一个闭环系统，让 LLM 不仅生成内核，还能根据性能 profiling 结果，自动迭代优化生成的 DSL 或 AscendC 代码。

### 总结

> AscendCraft 为我们展示了如何用优雅的系统设计来弥补大模型在特定领域的能力短板。它没有试图让 LLM 成为一个全知全能的“超人”，而是为它打造了一个最合适的“工作台”——一个既能表达核心思想、又能屏蔽底层复杂性的 DSL。

通过结构化的降级流程，它成功地将 LLM 的创意和智慧，安全、可靠地转化为能在昇腾 NPU 上高效运行的代码。

::: block-1
这项工作的意义远不止于技术本身。它启示我们，在未来异构计算的时代，当 AI 芯片百花齐放、编程模型千差万别时，也许**DSL + 结构化代码生成**，将成为连接高级算法与底层硬件的“通用翻译器”。AscendCraft 的实践，为“如何让 AI 学会驾驭 AI 硬件”这一难题，提供了一个极具启发性且效果卓著的答案。
:::
