## 关键问题

### Q1. 文中提到 WLB-LLM 通过延迟极长文档（ outliers ）的执行来平衡流水线并行（PP）层面的负载，且这类文档仅占训练 token 的小部分。但随着模型上下文窗口持续扩大（如超过 160K），极长文档的比例可能显著增加，此时延迟策略是否会因累积延迟的 token 占比上升而破坏数据采样的随机性，进而影响模型收敛？现有实验中 “平均延迟 0.5 次迭代” 的结论在超大规模上下文场景下是否依然成立？

关于**极长文档延迟策略** 在超大规模上下文场景下的有效性及对模型收敛的影响：

WLB-LLM 的延迟策略仅针对**占训练 token 比例极小的极长文档，且平均每个 token 仅延迟 0.5 次迭代**，这一设计最大限度保留了数据采样的随机性，实验中其训练损失曲线与固定长度打包（单全局批次）几乎一致，未观察到模型收敛受损。

对于更大上下文窗口（如 160K），通过实验表明，随着窗口增大，WLB-LLM 的加速比反而提升（达 1.40×），说明延迟策略在极长文档比例可能上升的场景下仍能有效平衡负载。尽管未直接验证超大规模上下文（如超过 160K）的情况，但:mdnice-bold-italic[其核心逻辑——通过限制延迟文档的比例（少量极长文档）维持随机性 ——在理论上可扩展]，因极长文档即使比例增加，相对总 token 仍属少数，且延迟机制通过多级别队列动态调整，可避免累积延迟过度破坏数据分布。

### Q2. WLB-LLM 在上下文并行（CP）层面通过离线 profiling 的 TFLOPs 数据估计注意力核延迟，进而自适应选择分片策略。但当训练硬件（如未来 GPU 架构）或模型结构（如非 Transformer 的新型注意力机制）发生变化时，离线 profiling 数据与实际运行时性能的偏差可能增大，这种依赖固定映射关系的自适应机制是否会失效？其泛化性如何保证？

关于 CP 层面自适应分片策略对硬件或模型结构变化的泛化性：

WLB-LLM 的自适应分片选择并非完全依赖固定的离线 profiling 数据，而是在 runtime 结合当前输入 tensor 形状（查询/键值 token 数量）动态计算。

其**核心理念是：通过离线 profiling 建立“ tensor 形状-TFLOPs-延迟”的映射关系，再在 runtime 根据实际形状估算 latency 并选择最优策略**。

:mdnice-bold-italic[这种机制对硬件或模型结构变化具有一定适应性]

- 若硬件架构（如未来 GPU）变化，可通过重新进行离线 profiling 更新映射关系；
- 若模型结构调整（如新型注意力机制），只要能通过 profiling 获取新的“操作 latency 与 tensor 形状”关系，即可复用该框架。

作者虽未明确验证极端结构变化的场景，但其设计的“ runtime 动态估算+离线 profiling 校准”模式，为泛化性提供了基础，而非依赖固定映射。

### Q3. 文中指出更大模型（如 70B）的加速比略低，因通信延迟占比上升。在超大规模模型（如 1T + 参数）训练中，4D 并行的通信开销（如 TP/CP 层面的 AllGather/ReduceScatter）可能成为主导因素，此时 WLB-LLM 的负载均衡优化是否会被通信瓶颈掩盖而失去效果？其性能提升的理论上限在哪里？

关于超大规模模型（1T+参数）中 WLB-LLM 优化效果是否被通信瓶颈掩盖：

更大模型（如 70B）的加速比略低，因**通信延迟占比上升，但这并不意味着负载均衡优化失效**。:mdnice-bold-italic[WLB-LLM 的核心价值是减少因负载不均衡导致的“同步等待开销”] （如最慢 GPU 拖慢整体进度），即使通信成为主导因素，这种等待开销仍可能存在（例如，通信前的计算负载不均衡会放大通信延迟的影响）。

文中对 4D 并行的 latency 传播链显示，**负载不均衡会在各层级累积放大，而 WLB-LLM 通过消除各层级（PP/CP）的不均衡，可减少这种放大效应**。

- 对于 1T+参数模型，只要存在计算或通信的负载不均衡，其优化就有意义；
- :mdnice-bold-italic[性能提升的理论上限取决于“负载不均衡导致的等待开销占总 latency 的比例”] ——若该比例为 α，则优化上限为 1/(1-α)，即使通信主导，α 不为零便有提升空间。

## 一、引言

大型语言模型（LLMs）已被广泛用作各种应用的核心，例如编码助手[23,39]、机器翻译[42]和聊天机器人[3,26]。大型语言模型令人瞩目的能力和广阔的应用前景，引发了大型科技公司之间的竞争，他们纷纷致力于训练质量更高、能力更强的大型语言模型[2,6,35]。**随着大型语言模型的规模和上下文窗口长度不断增大[13]，其训练过程消耗了大量的计算资源** [28]。例如，Meta 报告称，LLaMA3-405B 模型的训练使用了 16K 块 H100 GPU，耗时数月[6]。大型语言模型训练的巨大计算成本意味着，端到端训练效率的:mdnice-bold-italic[每一点提升都能转化为显著的成本节约。]

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/05.webp)

> 遗憾的是，在大规模大型语言模型训练任务中，由于**工作负载不平衡问题，相当一部分 GPU 未被充分利用**。

为说明这一点，我们在图 1（a）中展示了在我们内部的 8K-GPU 大型语言模型训练任务（上下文窗口为 128K）中，每个 GPU 上的归一化计算延迟。可以观察到，**不同 GPU 的计算延迟存在显著差异，最慢的 GPU 的计算延迟是其他 GPU 的 1.44 倍**。这种计算延迟的差异会导致训练效率大幅下降，因为:mdnice-bold-italic[训练的同步特性要求所有其他 GPU 都必须等待最慢的 GPU 完成计算]。

> :mdnice-bold-italic[工作负载不平衡的根源] 在于**注意力计算的输入依赖性以及训练数据中输入文档长度的变化**。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/05.webp)

如图 1（b）所示，输入序列由多个输入文档组成。为确保长上下文预训练中的模型质量，会应用注意力掩码（attention mask），以防止同一序列中来自不同文档的 token 之间进行自注意力计算[6]。**这种方法导致了每个 token 的算术强度** （计算量与数据量的比率）**存在异质性**，因为**长文档尾部位置的 token 需要更多的注意力计算**。因此，:mdnice-bold-italic[即使总序列长度相同，包含长文档的输入序列也会产生显著更高的计算工作负载。]

然而，现有的大型语言模型训练框架[19,22,30,32,33]未能识别到这种每个 token 的算术强度的异质性。具体来说，最先进的大型语言模型训练解决方案采用了 4D 并行范式，该范式结合了数据并行（DP）[30]、流水线并行（PP）[21]、上下文并行（CP）[25]和张量并行（TP）[32]。

- 在数据并行和流水线并行层面，输入文档被打包成固定长度的序列；
- 然后在上下文并行和张量并行层面，这些序列被分片并分配为多个块。

**这种固定且静态的训练流程将所有输入 token 视为同质的，并为每个 GPU 分配相同数量的 token ，这不可避免地导致了 GPU 之间的工作负载不平衡**。此外，模型规模更大、上下文窗口更长的趋势加剧了这一问题，增加了极长文档出现在输入批次中的可能性，从而延迟整个训练步骤。

解决工作负载不平衡问题的一个直观方法是对输入文档进行洗牌和重新打包，以在微批次间更均匀地分配计算工作负载。然而，这种方法既不高效也不实用，主要原因有两个：

- 首先，通过洗牌和重新打包实现有效的平衡需要一个足够大的、跨越多个全局批次的打包窗口，这会影响数据采样和加载的随机性，可能会影响训练过程中的模型收敛（如 3.3 节所讨论）。
- 其次，洗牌和重新打包仅能解决微批次间的工作负载不平衡，无法解决由序列分片导致的文档内不平衡。在 4D 并行训练中，输入序列被分割成块并分配到不同的 GPU 上。包含文档尾部的文档块会产生更高的计算工作负载，因为这些块中的 token 必须关注更多的前置 token ，从而导致 GPU 之间的文档内工作负载不平衡。

> 为克服上述挑战并解决大规模大型语言模型训练中严重的工作负载不平衡问题，我们为 4D 并行训练范式提出了一种灵活的、感知输入的文档打包和分片方法。

::: block-1
1. 数据打包和分片不再输出固定 token 数量的微批次，而是**让每个 GPU 获得具有相同总计算和通信工作负载的输入 token** 。
2. 此外，为最大限度减少对数据随机性的影响，我们提出**【仅】调整极长文档的执行顺序**。这是基于我们的观察：:mdnice-bold-italic[长文档的 token 在总训练 token 中仅占很小比例]，但对工作负载:mdnice-bold-italic[不平衡的影响最大]。
:::

基于上述设计思路，我们构建了 WLB-LLM，即用于大型语言模型训练的工作负载均衡 4D 并行技术。我们首先深入分析了 4D 并行下大型语言模型训练中的工作负载不平衡（第 3 节），确定了**特定并行层级的两个主要不平衡来源**：

1. 流水线并行层面的微批次间不平衡；
2. 上下文并行层面的文档分片间不平衡。

> 为解决这些不平衡，WLB-LLM 针对每个层面提供了量身定制的新颖解决方案。

- **在流水线并行层面，WLB-LLM 引入了变长文档打包**，允许:mdnice-bold-italic[将较短的文档组合起来形成较长的序列，从而使总计算工作负载与单个长文档的计算工作负载相匹配] （第 4 节）。此外，WLB-LLM 自适应地延迟极长文档的执行，在保持数据加载随机性的同时，实现了微批次间接近最优的工作负载平衡，且每个 token 的延迟相对较低。
- **在上下文并行层面，WLB-LLM 采用了一种新颖的逐文档分片策略**，:mdnice-bold-italic[确保上下文并行组内的每个工作节点都具有相同的工作负载] （第 5 节）。此外，我们观察到逐文档分片存在内核效率与分片平衡之间的权衡。为最大限度提高整体性能，我们提出了一种启发式算法，可在运行时根据输入序列自适应地选择最高效的分片策略。

总之，本文的贡献如下：

::: block-1
- 据我们所知，我们是第一个识别、分析并解决大规模 4D 并行大型语言模型训练中工作负载不平衡问题的研究。
- 在流水线并行层面，我们设计了变长输入打包和自适应异常值延迟策略，以实现微批次间接近最优的工作负载平衡，同时最大限度减少对数据加载随机性和模型收敛的影响。
- 在上下文并行层面，我们实现了一种细粒度的逐文档分片方法，并结合自适应分片选择机制，以在运行时为每个输入微批次实现最高效的分片。
- 我们进行了全面的评估，结果表明 WLB-LLM 在各种模型规模和上下文窗口大小下平均实现了 1.23 倍的加速比。
:::

## 二、背景知识补充

在本节中，我们将介绍 4D 并行 LLM 训练的背景，以及不同并行层次中负载不平衡问题的成因。

### 2.1 4D 并行 LLM 训练

> 训练具有数十亿甚至数万亿参数的超大型 LLM 极具挑战性，需要大量工程 effort 来调整多级并行策略[44]。最先进的 LLM 训练框架采用 4 维并行范式[8,11]，包括数据并行（DP）[30]、流水线并行（PP）[21]、上下文并行（CP）[25]和张量并行（TP）[32]。 图 2 展示了一个（TP=2，CP=2，PP=4，DP=4）的 4D 并行示例。![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/02.webp)

#### 数据并行（Data Parallelism）

在 DP 中，输入的全局批次会被分割并分配到各个 DP 工作节点，每个节点处理全局批次的一部分。默认情况下，模型参数在 DP 节点间复制。一些先进技术如 ZeRO[30]和 FSDP[27]会将模型参数、梯度和优化器状态在 DP 节点间分片，以减少内存消耗。

训练过程中，每个 DP 节点独立计算本地批次的参数更新，然后通过 AllReduce（或 FSDP 中的 ReduceScatter）与其他节点同步梯度。

#### 流水线并行（Pipeline Parallelism）

在**每个 DP 节点内部，设备通过流水线并行进一步划分为多个 PP 节点**。在 PP 中，:mdnice-bold-italic[模型按层分割，每个 PP 节点负责处理若干层]。DP 节点的输入批次也会被分为多个微批次（micro-batches）。

训练时，一个微批次会按顺序流经所有 PP 节点，反向传播时则反向流动。前向和反向传播过程中，需要通过点对点（P2P）通信传递激活值和梯度。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/02.webp)

#### 上下文并行（Context Parallelism）

CP **旨在解决长上下文训练中激活值的内存消耗问题**。如图 2 所示，CP 复制模型参数，但将输入和激活值沿序列长度维度分片到各个 CP 节点。

CP 要么采用基于环形的点对点通信[20]，要么在正向传播时通过 AllGather 收集所有 token 的 KV（键和值）张量，反向传播时通过 ReduceScatter 同步 KV 张量的梯度[6]。其他算子（如 Linear 和 LayerNorm）在所有节点上独立运行，类似 DP。

#### 张量并行（Tensor Parallelism）

TP 将层内的模型参数（如注意力层、FFN 层）分割并分配到多个 TP 节点。TP 通常与序列并行（SP）[14]结合使用，进一步分割输入张量和激活值。本文中提到的 TP 默认包含 TP 和 SP。

通过 TP，每个 GPU 仅持有部分输入和参数，导致训练中需要大量 AllGather 和 ReduceScatter 通信。因此，TP 通常在单个节点内应用，而其他并行层次则跨节点应用。

### 2.2 输入文档长度的变化

在大规模 LLM 训练中，输入文档的长度可能差异显著，尤其是使用大上下文窗口时。为了说明这一点，我们在图 3 中展示了 128K 上下文长度训练任务的训练数据特征。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/06.webp)

- 从单文档角度看，输入文档长度分布极不均衡。如图 3 左半部分所示，大多数输入文档相对较短，但存在一些极长文档，最长的可达整个上下文窗口大小。输入批次中出现极长文档很容易导致微批次间的负载严重不平衡。
- 从单 token 角度看，我们计算了上下文窗口内每个位置对应的平均文档长度。如图 3 右半部分所示，不同 token 位置的平均文档长度差异约为 1.4 倍。**中间位置的 token 更可能属于较长文档。这是因为数据加载器将文档打包成批次时，超过上下文窗口长度的长文档会被截断尾部，以确保总序列长度匹配上下文窗口**。该图清楚地表明了长上下文 LLM 训练中每个 token 的计算强度存在异质性。

这些观察结果凸显了需要一种感知输入的解决方案，通过考虑文档长度和每个 token 计算强度的变化来动态平衡负载。

## 三、研究动机

为了推动 WLB-LLM 的设计，我们首先深入分析 4D 并行 LLM 训练中不同并行层次的负载不平衡问题。然后介绍一种对跨批次文档进行重排和重新打包的基线解决方案。最后讨论为何该基线方案无法完全消除负载不平衡，并研究输入打包平衡与模型收敛之间的权衡。

### 3.1 不平衡分析

> 通过分析内部 8K-GPU、128K 上下文窗口训练任务的性能轨迹，我们确定了负载不平衡的两个主要原因：（1）流水线并行（PP）层的微批次间不平衡；（2）上下文并行（CP）层的序列分片间不平衡。为了说明这一点，我们统计了每个 GPU 上的注意力计算延迟，结果如图 4 所示。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/07.webp)

#### PP 层不平衡

如图 4（a）（1）所示，不同 DP 节点间的注意力计算延迟差异显著。在每个 DP 节点内，数据点形成“竖线”，每条线代表一个 PP 节点。每个 PP 节点的负载几乎相同，因为同一 DP 节点内的所有 PP 节点处理相同的微批次集。

根据图 4（a）（1）的结果，我们得出结论：**DP 和 PP 层的负载不平衡源于微批次间的不平衡，这是由输入打包过程导致的**。如图 4（b）左半部分所示，输入文档被打包成等长序列（微批次）。尽管这种固定长度打包策略确保每个 PP 和 DP 节点处理相同数量的 token，但每个 token 的计算强度差异导致了这些层次的负载不平衡。例如，包含单个长文档的微批次（红色高亮）比包含多个短文档的微批次（绿色高亮）负载更大。

#### CP 层不平衡

为了更清晰地展示 CP 层的不平衡，我们聚焦于一个特定的 PP 节点（也称为 CP 组）。如图 4（a）（2）所示，CP 节点间存在显著的负载不平衡（圆圈标记），而每个 CP 节点内的 TP 节点计算延迟相近（圆圈内的数据点）。CP 节点间的不平衡源于 CP 层的序列分片。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/07.webp)

如图 4（b）右半部分所示，输入序列被分割为等 token 数量的分片，然后分配给 CP 节点。最先进的方法将输入序列分割为 2×CP_{size} 大小的分片，第 i 个 CP 节点分配第 i 个和（2×CP_{size}-1-i）个分片，以实现更好的负载平衡[6]。

- 当序列仅包含单个文档时，这种分片策略效果良好。
- 但如果序列由多个文档打包而成，可能导致 CP 节点间的负载严重不平衡，如图所示。尽管序列分片会进一步分割并分配给 TP 节点，但 TP 层不存在不平衡。这是因为计算前，所有 TP 节点会执行 AllGather 操作收集整个序列分片，因此每个 CP 节点内的 TP 节点处理相同的序列分片，消除了 TP 层的不平衡。

#### 不平衡传播

训练过程中，负载不平衡会从内层并行传播到外层并行。不平衡会累积并放大，最终对端到端训练延迟产生显著影响。在 DP、CP 和 TP 中，训练时会执行 AllReduce、AllGather 和 ReduceScatter 等集合通信[24]。这些并行层次中的所有节点同步工作，因此**一个 DP、CP 或 TP 组的训练延迟由组内最慢的节点决定**。相比之下，PP 层中不同 PP 节点互为生产者和消费者。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/08.webp)

如图 5 所示，PP 的关键路径是最大微批次流经所有 PP 节点的延迟，加上剩余微批次在第一个 PP 节点上的前向和反向传播延迟。PP 节点间独特的数据依赖关系会放大不平衡，对总延迟产生更大影响。由于不平衡传播，微批次训练延迟升高可能有两个主要原因：

1. 内层层次传播的不平衡（如 CP 分片不平衡）；
2. PP 层打包导致的微批次固有负载过大。

这凸显了消除所有并行层次不平衡的重要性。

### 3.2 基线解决方案：固定长度打包

解决负载不平衡的一种潜在方案是优化输入文档的打包方式。当前 4D 并行框架要求所有微批次具有统一的序列长度[6]（等于上下文窗口大小），以实现高效的输入序列批处理。基于这种固定长度要求，我们实现了一种基线重排打包优化，将输入文档打包成等长微批次。

**具体来说，给定一组来自一个或多个全局批次的输入文档，目标是将它们打包成若干固定总长度的微批次，并平衡所有微批次的注意力计算负载**。为了不失一般性，我们以因果掩码为例计算注意力负载。在因果掩码下，微批次的注意力计算负载与 $\sum_{i=1}^{N} d_{i}^{2}$ 成正比，其中 $d_i$ 是微批次内每个文档的长度。寻找最优文档打包方案是 NP 难问题，因为它可以通过添加和约束及平方和目标从经典的数字分区问题[9]扩展而来。

**为了寻找最优打包方案，我们将该任务建模为整数线性规划（ILP）问题**。假设我们有 N 个文档，每个文档长度为 $d_i$，希望将它们打包成 M 个微批次，每个微批次总长度为 L。目标是最小化微批次间的最大负载：

$$
\begin{array}{ll}
minimize & max \left(\sum_{i=1}^{N} x_{i j} \cdot d_{i}^{2}\right), j=1, \cdots, M \\
\text{subject to} & \sum_{j=1}^{M} x_{i j}=1, i=1, \cdots, N \\
& \sum_{i=1}^{N} x_{i j} \cdot d_{i} \leq L, j=1, \cdots, M \\
& x_{i j} \in\{0,1\}
\end{array}
$$

其中 $x_{ij}$ 是表示打包方案的二进制变量。具体来说，$x_{ij}=1$ 表示第 i 个文档被打包到第 j 个微批次。基于此 ILP 模型，我们使用商业求解器[7]获得最优打包方案。

### 3.3 权衡分析

跨更多全局批次优化输入文档打包有助于实现更高程度的负载平衡。但这也会改变更多输入文档的执行顺序，影响数据采样和加载的随机性，可能对训练中的模型收敛产生负面影响（如 3.3 节所述）。

为了**评估打包平衡与模型质量之间的权衡**，我们使用不同打包窗口大小预训练了一个 550M 参数模型，共训练 52K 步。然后**评估不同设置下打包后输入批次的负载不平衡程度**。:mdnice-bold-italic[不平衡程度计算为]$\frac{Max\_Attn}{Avg\_Attn}$，其中 Max_Attn 是全局批次中最大的注意力计算负载，Avg_Attn 是全局批次中所有微批次的平均注意力计算负载。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/09.webp)

如图 6 所示，仅对单个全局批次优化打包时，微批次间的负载不平衡仍然较高。随着全局批次数量增加，固定长度打包优化能实现更好的负载平衡。但由于重排更多输入文档导致数据加载随机性降低，参与打包优化的全局批次越多，最终训练损失越大。这些结果**表明，简单的固定长度打包优化无法在不牺牲模型质量的前提下实现良好的负载平衡**，因此:mdnice-bold-italic[需要更复杂的解决方案]。

打包平衡与模型质量之间的权衡促使我们打破微批次的固定长度约束，设计更灵活的打包策略。在接下来的两节中，我们将详细介绍 WLB-LLM，包括 PP 层的变长打包和启发式异常文档延迟优化（第 4 节）以及 CP 层的细粒度自适应分片优化（第 5 节）。

## 四、针对流水线并行（PP）的变长打包和异常文档延迟策略

> 在流水线并行（PP）层面，我们致力于通过**工作负载感知的文档重新打包来平衡微批次间的工作负载。**

- 首先，我们设计了一种变长打包策略，与定长打包相比，在相同的打包窗口大小下实现了更高程度的工作负载平衡（§4.1）。
- 其次，我们提出了异常文档延迟方法，自适应地延迟极长文档的训练。这种方法有助于在最小化对数据随机性影响的同时，实现微批次间接近最优的工作负载平衡（§4.2）。
- 最后，我们设计并实现了一种高效的启发式算法，以可忽略的开销在运行时优化打包过程（§4.3）。

### 4.1 工作负载感知的变长打包

**基线定长打包的主要局限性** 在于：如果**全局批次中存在极长文档，就无法实现平衡**。例如，若某文档的长度等于上下文窗口大小，由于注意力计算的二次复杂度，就不可能创建另一个由较短文档组成的、具有同等计算工作量的微批次。:mdnice-bold-italic[为解决这一局限，我们提出了变长打包策略，允许每个微批次具有不同的序列长度。]

我们设计的**核心见解** 是：:mdnice-bold-italic[微批次的工作负载并非仅由注意力计算决定]。其他操作，如通用矩阵乘法（GEMM，一种基础的矩阵运算）、逐元素操作和集合通信（如 AllGather、ReduceScatter 等多节点间的数据同步操作），也对训练延迟有显著影响，且这些影响与每个微批次中的文档相关。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/10.webp)

为说明这一点，我们在图 7 中展示了操作延迟与文档长度的关系。可以观察到，**注意力计算延迟随输入文档长度呈二次增长**，而**其他操作** （如 GEMM、集合通信和逐元素操作）的**延迟与文档长度呈线性关系**。

:mdnice-bold-italic[这种关系为超越定长打包、进一步改善工作负载平衡提供了可能]。如果一个长文档的注意力计算延迟显著高于其他操作，我们可以将多个短文档打包在一起，延长其他操作的延迟，从而匹配长文档的总延迟。具体而言，我们**将定长打包扩展为变长方式。优化目标从【仅】平衡【注意力计算】工作负载，转变为平衡包括【所有操作】在内的【总工作负载】**：

$$
\begin{array}{cc}
minimize & max \left(\sum_{i=1}^{N}\left(W_{a}\left(x_{i j} \cdot d_{i}\right)+W_{l}\left(x_{i j} \cdot d_{i}\right)\right)\right), \\
& j=1, \cdots, M \\
\text{subject to} & \sum_{j=1}^{M} x_{i j}=1, & i=1, \cdots, N \\
& \sum_{i=1}^{N} x_{i j} \cdot d_{i} \leq L_{max }, j=1, \cdots, M \\
& x_{i j} \in\{0,1\} &
\end{array}
$$

其中，$W_{a}(\cdot)$ 和 $W_{l}(\cdot)$ 是投影函数，分别基于文档长度计算注意力计算延迟和所有其他操作的延迟。两者均可通过离线 profiling（性能分析）得出。$L_{max}$ 表示 GPU 内存约束允许的最大序列长度。

### 4.2 异常文档延迟

我们的变长打包策略通过允许将短文档打包成超过固定上下文窗口大小的较长序列，实现了更高水平的平衡。然而，在单个全局批次中，短序列的数量可能不足以平衡所有微批次的计算工作量。

为解决这一挑战，我们提出**自适应地延迟异常文档（即极长文档）的执行**。这种方法基于我们的观察：:mdnice-bold-italic[尽管这些异常文档对工作负载不平衡影响显著，但它们仅占训练 token 的一小部分]。通过选择性地延迟少数极长文档的 token 训练，我们可以在最小化对数据随机性影响的同时，实现微批次间更平衡的工作负载。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/11.webp)

**设计细节：如图 8 所示，我们为异常文档实现了多级等待队列**。

- 假设我们有 n 个异常队列，每个队列与一个超参数$L_{i}$相关联，该参数指定第 i 个队列中文档的最小长度，其中 $L_{1} < L_{2} < \cdots < L_{n}$ 。
- 当新的全局批次到达时，长度大于$L_{1}$的文档被视为异常文档，并被添加到相应的等待队列 i 中（满足 $L_{i} \leq Doc_len < L_{i+1}$，其中 Doc_len 表示文档长度）。异常队列中的文档会延迟执行，直到队列积累了足够多的异常文档。
- 一旦队列大小达到微批次数量，异常文档就会从队列中弹出并添加到每个微批次中。这确保了微批次间的工作负载平衡，因为每个微批次恰好包含一个异常文档。

### 4.3 启发式打包算法

尽管整数线性规划（ILP）求解器可以为给定的输入文档集得出最优打包方案，但求解时间过长，不切实际。为此，我们设计了一种**启发式算法，将变长打包与异常文档延迟优化相结合，高效生成工作负载平衡的打包微批次**。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/12.webp)

#### **算法 1：启发式变长打包算法**

- 输入：数据加载器 D、等待队列 Q、每次迭代的微批次数量 N、序列长度上限$L_{max}$
- 输出：用于训练的打包微批次 B

如算法 1 所示，该算法以数据加载器 D、异常文档的先进先出（FIFO）等待队列集 Q、每次迭代的微批次数量 N 以及序列长度上限$L_{max}$作为输入。最终输出一系列用于训练的、工作负载平衡的打包微批次。

打包过程首先遍历数据加载器 D 中的输入批次，将所有异常文档添加到 Q 中相应的等待队列进行延迟处理（第 3-10 行）。如果 Q 中的任何队列 q 的大小达到 N，则将队列中的文档弹出并添加到当前批次的待处理文档集 Doc_Set 中（第 11-15 行）。

打包采用贪心策略：待处理文档按长度降序排序。算法首先尝试将每个文档打包到工作负载最小的微批次中（使用公式 2 中定义的$W_{a}(\cdot)$和$W_{l}(\cdot)$计算），前提是总长度不超过上限$L\_{max}$。如果不可行，则尝试打包到长度最小的微批次中（第 16-25 行）。无法满足这些约束的文档将保存到下一次迭代（第 27 行）。我们的启发式方法将异常文档延迟与变长文档打包相结合，高效平衡所有微批次的计算工作负载。

## 五、针对上下文并行（CP）的细粒度自适应分片

在上下文并行（CP）层面，我们旨在通过实现细粒度的逐文档分片策略来改善文档分片间的工作负载平衡，确保每个上下文并行组内的工作节点都具有相等的计算工作量（§5.1）。此外，我们**观察到注意力内核效率与分片粒度之间存在权衡** （§5.2）。为最大化整体性能，我们进行了深入分析，并**为给定的输入批次在运行时自适应地选择最优分片策略** （§5.3）。

### 5.1 逐文档分片设计

在上下文并行层面，微批次的序列被分片到多个上下文并行工作节点（CP workers）。每个上下文并行工作节点处理一个专属的序列分片。**现有的上下文并行实现采用逐序列分片策略** （Per-Sequence Sharding），将整个输入序列均匀分片为$2×CP_{size}$个块。:mdnice-bold-italic[当输入序列由多个文档打包而成时，这种方法可能导致显著的注意力计算工作负载不平衡。]

为消除上下文并行层面的工作负载不平衡问题，我们提出**以细粒度方式对序列进行分片**。具体而言，我们:mdnice-bold-italic[采用逐文档分片（Per-Document Sharding），将每个文档划分为$2×CP_{size}$个文档块。]

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/13.webp)

如图 9 所示，每个上下文并行工作节点为每个输入文档获取一对对称的文档块。通过我们的细粒度逐文档分片策略，每个上下文并行工作节点不仅接收相同数量的 token （确保 GEMM 计算和集合通信的工作负载平衡），还获得相同的注意力计算工作负载。

无填充设计：我们的细粒度逐文档分片策略将每个输入文档划分为$2×CP_{size}$个文档块。然而，文档长度并不总是能被$2×CP_{size}$整除，这需要通过添加填充 token 来扩展文档长度。为避免填充带来的冗余计算，我们设计了无填充的逐文档分片方法。具体而言，我们将每个文档分为两部分：可被$2×CP_{size}$整除的部分和剩余 token 部分。假设第 i 个文档的长度为$L_{i}$，其中$L_{i}=D_{i}+R_{i}$，且$D_{i}=\left\lfloor\frac{L_{i}}{2 ×CP _{size}}\right\rfloor$。我们对$D_{i}$部分应用标准的逐文档分片，而$R_{i}$中的 token 则以轮询方式分配给上下文并行工作节点。由于$\sum_{i=1}^{n} L_{i}$和$\sum_{i=1}^{n} D_{i}$都能被$2×CP_{size}$整除，因此$\sum_{i=1}^{n} R_{i}=\sum_{i=1}^{n}(L_{i}-D\_{i})$也能被$2×CP_{size}$整除。这确保每个上下文并行工作节点接收相等数量的 token ，从而无需填充。

### 5.2 内核效率与分片平衡性的权衡

我们的**逐文档分片策略完全消除了上下文并行层面的工作负载不平衡**。然而，将每个文档**分割为多个较短的块可能会影响内核效率**，主要原因有两点：

#### 影响因素1：分片级计算浪费

注意力计算在 GPU 上以分片（tile）方式执行。例如，在 FlashAttention [5]的注意力前向内核中，分片大小设为 128。**如果 token 数量小于分片大小，线程块仍会加载 128 个 token 进行完整计算，这会造成浪费**。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/14.webp)

如图 10（左）所示，当查询 token 数量（Q_len）从 16 增加到 128 时，内核延迟保持不变。这是因为所有短文档都会被填充到 128 个 token 以进行内核级计算。相反，当 Q_len 从 128 增加到 256 时，内核延迟显著上升。

#### 影响因素2：张量内存加速器（TMA）使用效率低

TMA 是 NVIDIA Hopper 架构引入的特性，支持 GPU 上全局内存与共享内存之间的异步内存复制[1]。对于长文档（如 Q_len ≥256），多个线程块处理不同的 Q token ，同时共享同一文档块的 KV token 。这使得 KV 张量加载可以通过 TMA 加载多播（multicast）经由 L2 缓存共享，显著减少 KV 张量从全局内存传输到共享内存的延迟。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/14.webp)

如图 10（右）所示，当查询张量的长度从 128 增加到 256 时，实现的每秒万亿次浮点运算（TFLOPs）显著增加，体现了利用 TMA 加载多播的效果。

---

这些分析结果清楚地表明了注意力内核效率与上下文并行分片平衡性之间的权衡。如果**对由短文档组成的输入序列应用逐文档分片，可能会在核级引入冗余计算并降低实现的 TFLOPs**，最终导致更长的注意力计算延迟。

### 5.3 自适应分片选择

基于 5.2 节的分析，尽管细粒度的逐文档分片在上下文并行层面实现了最优的工作负载平衡，但它并不一定能保证更好的性能，因为注意力内核可能会因逐文档分片生成的更细粒度文档块而效率降低。为解决这一问题，我们提出在运行时为每个微批次自适应地选择最优分片策略。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/15.webp)

如图 11 所示，在上下文并行层面的前向传播过程中，会通过集合通信（AllGather）收集所有上下文并行工作节点的完整 KV 张量。然后，我们分别计算逐序列分片和逐文档分片情况下注意力内核的输入张量形状（查询 token 数和键/值 token 数）。最后，我们预测注意力内核延迟，并选择能使注意力计算延迟更低的上下文并行分片策略。

为准确估计注意力内核延迟，我们利用 5.2 节中的见解。

::: block-1
- 首先，计算注意力计算所需的总浮点运算量。通过将文档块填充到分片大小的倍数，考虑内核级填充。
- 接下来，使用离线分析收集的数据（包括 TMA 使用的影响）估计给定张量形状的实现 TFLOPs。
- 最后，通过将浮点运算量除以实现的 TFLOPs 来估计注意力内核延迟。通过自适应选择上下文并行分片，WLB-LLM 最小化了上下文并行层面的训练延迟。
:::

## 六、评估

在本节中，我们在不同的 LLM 规模和 4D 并行配置下对 WLB-LLM 进行评估，模型规模从 5.5 亿到 700 亿不等。

- 我们首先展示**端到端训练延迟的改进**。
- 接下来，我们**分别分析来自流水线并行（§4）和上下文并行（§5）级别的各个优化的加速贡献**。
- 最后，通过比较训练损失曲线，我们**证明 WLB-LLM 的优化不会影响模型质量或减缓模型收敛。**

### 6.1 实验设置

#### 硬件

我们在一个包含 32 个节点的集群上部署 WLB-LLM。每个节点配备 8 个 NVIDIA H100 SXM 80GB GPU，通过高带宽 NVLink（NVIDIA 的一种高带宽 GPU 间互联技术）互联，而节点间通信则通过基于融合以太网的 RDMA（RoCE，一种基于以太网的远程直接内存访问技术）实现。

我们在一系列内部类 LLaMA 模型上进行实验，涵盖四种不同规模：5.5 亿、70 亿、300 亿和 700 亿。

- 对于每个模型，我们使用两种不同的上下文窗口大小评估性能：64K 和 128K。
- 每种模型规模和上下文窗口大小都对应一种 4D 并行配置。
- 全局批大小设置为`PP_{size} × DP_{size}`，并且所有评估都使用 bfloat16 精度。

#### 基线

我们将 WLB-LLM 与两种基线进行比较：

- **Plain-4D**：这是我们用于大规模 LLM 训练的内部代码库，支持 4D 并行以实现高效训练，并可扩展到 10 万个 GPU。Plain-4D 直接使用从数据加载器获得的输入批进行训练，不优化输入打包。对于 CP 分片，Plain-4D 采用序列级分片方法，即在整个序列级别对输入序列进行分片。
- **Fixed-4D**：Fixed-4D 应用 3.2 节中描述的基线固定长度打包优化。为了最小化打包开销，使用贪心算法代替求解器，并且打包大小限制在单个全局批，以保持数据加载的随机性并防止训练损失增加。对于 CP 分片，Fixed-4D 在整个训练过程中使用固定的分片策略（要么是序列级分片，要么是文档级分片）。我们然后使用性能更好的结果进行比较。

#### Plain-4D 与 Fixed-4D

如图 12 所示，Fixed-4D 相对于 Plain-4D 仅实现了微小的改进，在所有设置下的平均加速比约为 1.03 倍。这种**有限的增益主要是因为 Fixed-4D 仅在单个全局批内调整文档打包，并且受限于上下文窗口大小**。它无法处理极长长度的异常文档（例如，长度等于上下文窗口大小的文档）。由于注意力计算的复杂度与文档长度成平方关系，在上下文窗口的限制下打包多个短文档无法匹配极长文档的计算工作量。

- 在 PP 级别，WLB-LLM 采用启发式变长文档打包算法，不受固定上下文窗口大小的限制。该算法还选择性地延迟异常文档的训练，与固定长度打包相比实现了更高程度的工作量平衡。
- 在 CP 级别，WLB-LLM 结合了序列级和文档级分片，为每个微批自适应地选择最优分片策略以最大化性能。

### 6.4 消融研究

> 在本节中，我们首先分析 WLB-LLM 中打包和分片优化的有效性。此外，我们证明 WLB-LLM 中的系统优化不会影响模型质量或减缓收敛。

#### 消融研究1：打包平衡和开销分析

为了**评估不同打包策略下微批之间计算工作量的平衡程度**，我们在应用不同打包方法和配置的 7B-128K 训练任务中，对每个微批的前向延迟进行了分析和比较。如 3.1 节所讨论，**PP 级延迟主要由最大的微批决定**。因此，我们使用以下指标来表示给定批的不平衡程度：`Max_Latency × PP_{size} / Total_Latency`，其中`Max_Latency`是最大微批的前向延迟，`Total_Latency`是所有微批的总前向延迟。不平衡程度越低，表示给定批的工作量越平衡。

如表 2 所示，固定长度贪心在单个全局批上进行打包时，可以略微缓解工作量不平衡。**跨多个全局批进行打包有助于实现更低的不平衡程度**，但正如 6 图所示，这会导致更高的训练损失。对于固定长度求解器，在相同数量的全局批下，它比固定长度贪心实现更低的不平衡程度。然而，基于求解器的解决方案存在显著的打包开销。例如，当跨 4 个全局批进行打包时，每个批的平均打包延迟超过 25 秒。

#### 消融研究2：CP 分片性能分析

为了证明 WLB-LLM 在 CP 级别上的文档级分片和自适应分片选择优化的有效性，我们在 CP 大小为 4 的 70 亿模型的单个 Transformer 层上进行了实验。我们比较了不同分片策略的前向和反向延迟，包括：（1）序列级分片（Per-Seq）；（2）文档级分片（Per-Doc）；（3）WLB-LLM，它在运行时基于给定的微批自适应地在 Per-Seq 和 Per-Doc 之间确定分片方式；（4）最优（Optimal），即总是选择 Per-Seq 和 Per-Doc 中延迟更低的分片方式。

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/21.webp)

如图 15 所示，在 64K 和 128K 上下文窗口大小下，文档级分片相对于序列级分片基线分别实现了 1.01 倍和 1.07 倍的加速比。这些结果证明了**文档级分片在减少 CP 级别工作量不平衡方面的有效性**。然而，:mdnice-bold-italic[细粒度的文档级分片可能会牺牲内核效率，特别是当输入序列由许多短文档组成时]。

为了克服这个问题，**WLB-LLM 利用自适应分片选择，在运行时为每个微批智能选择更好的分片策略**。图 15 中的结果显示，WLB-LLM 相对于静态的序列级或文档级分片实现了 7.5%和 3.4%的改进。此外，WLB-LLM 非常接近最优结果，证明了我们的自适应选择方法的有效性。

#### 消融研究3：模型收敛性分析

WLB-LLM 采用启发式变长打包优化，调整文档打包并延迟异常文档的执行。**为了证明这种优化不会影响模型收敛，我们展示了 5.5 亿模型的训练损失曲线。**

![文章插图](/articles/2025-08-05-1-23-wlb-llm-4d-3b6578a6/images/22.webp)

如图 16 所示，跨 8 个全局批进行打包导致训练损失显著增加（平均 1.6%）。这是因为跨多个全局批进行打包破坏了数据加载器中数据采样的随机性，导致每个批的数据分布与预期不同。相比之下，**WLB-LLM 的趋势几乎与跨单个全局批的固定长度打包相同，因为 WLB-LLM 使用的启发式变长打包算法仅延迟异常文档，而异常文档在所有输入 token 中占比很小**。

根据我们的分析，在 WLB-LLM 中，每个 token 平均延迟 0.5 个迭代。:mdnice-bold-italic[这种最小的延迟最大程度地保留了原始数据分布，使 WLB-LLM 能够在不影响模型质量的情况下提高训练效率。]

## 七、相关工作

### 分布式 LLM 训练框架

为了应对训练超大型 LLM 的挑战，先前的方法主要依赖 3D 并行[14,22,32,34,37,38,44]，它集成了张量并行[14,16,32]、流水线并行[10,17,18,22]和数据并行[30,31,43]。

尽管 3D 并行已被证明在扩展模型规模方面有效，能够训练数万亿参数的模型[34]，但它难以有效扩展上下文窗口大小。为了应对这一限制，一种新的并行维度——上下文并行被引入[25]，形成了 4D 并行训练范式。

**上下文并行将输入上下文分割成块，有效减少了与极长序列长度输入相关的内存瓶颈**。最初，上下文并行采用基于环的方法，使用点对点（P2P）通信来重叠通信和计算[20]。最近的方法利用集合通信方法（如 AllGather 或 AlltoAll）来聚合键和值张量，提供了更大的灵活性，并更好地支持各种类型的注意力掩码[6,11,25]。

> 上下文并行的引入使具有长上下文窗口的 LLM 的高效训练成为可能。然而，现有的 4D 并行框架忽略了 token 级算术强度的异质性，导致 GPU 之间存在显著的工作量不平衡。

### LLM 训练的输入填充和打包

LLM 的输入由不同长度的样本组成。为了在 LLM 训练中将输入文档批处理在一起并优化 GPU 利用率，必须将输入文档组织成相同长度的张量。这可以通过两种主要方法实现：填充[32]和打包[15]。填充涉及向微批中的较短文档添加零填充。然而，这种方法不可避免地引入了冗余计算、通信和内存开销。

为了解决这个问题，先前的工作集中在设计更高效的内核以减少冗余计算[40,41]，或优化批处理策略以最小化填充[12]。为了完全消除冗余计算，最近的工作提出将短文档打包在一起形成单个长输入序列[15]。打包后，必须应用额外的注意力掩码，以确保 token 仅关注同一文档内的其他 token [6,29]。**由于其在避免冗余计算方面的效率，打包已成为 LLM 训练中的主流选择**。例如，LLaMA-3 在其训练过程中采用输入打包[6]，并且最先进的高性能注意力实现（如 FlashAttention[4,5]）也支持带文档打包的高效注意力计算。WLB-LLM 专注于输入打包，并解决了输入文档打包在一起时出现的工作量不平衡问题。

## 八、总结

> 在本文中，我们提出了 WLB-LLM，这是一个用于 LLM 训练的工作量平衡的 4D 并行框架。

WLB-LLM 识别并解决了不同并行层级中的工作量不平衡问题。

::: block-1
- 在流水线并行级别，WLB-LLM 引入了一种新颖的启发式变长文档打包算法，有效缓解了微批之间的工作量不平衡。
- 在上下文并行级别，WLB-LLM 提出了一种细粒度且自适应的文档级分片策略，结合序列分片实现了最优的训练性能。
:::

全面的实验表明，在各种模型规模和并行配置下，WLB-LLM 的**性能均优于现有的 4D 并行框架，平均加速比达到 1.23 倍。**
