## 训练和推理侧

> 系统卡里对训练过程的描述不算详细，但有几个关键点。

训练数据是公开互联网数据（通过自家的 ClaudeBot 爬虫抓取，遵守 robots.txt）、公开和私有数据集、再加上其他模型生成的合成数据，经过去重和分类过滤。预训练之后做了后训练和微调，目标是让模型行为对齐 Claude 宪法里描述的价值观。**知识截止在 2026 年 5 月。**

推理侧的变化对写提示词的人影响更大：

- **思考默认开启**。Opus 5 用自适应思考（adaptive thinking），模型自己决定每个请求要不要思考、思考多深。你不再用 `budget_tokens` 去手动分配思考预算。
- **effort 参数成为主控旋钮**。一共五档：`low`、`medium`、`high`、`xhigh`、`max`。档位越高，思考越深、越慢、越贵。官方的成本曲线显示，`max` 并不一定比 `xhigh` 好——在 Frontier-Bench 上 `max` 的分数还略低于 `xhigh`，成本却更高。盲目拉满没有意义。

- **一个会直接报错的坑**：如果你手动关掉思考（`thinking: {"type": "disabled"}`），effort 就不能设成 `xhigh` 或 `max`，否则 API 直接返回 400。老代码迁移时先查这一条。
- 快速模式（fast mode）大约 2.5 倍速，价格翻倍；prompt 缓存的最低门槛从 1024 token 降到了 512。

## Opus 5 的脾气变了，旧提示词反而会帮倒忙

> 这是官方 Opus 5 专属提示词文档里最重要的信息：**模型更主动了，很多以前必须写进提示词的"脚手架"现在要删掉。**

具体来说，Opus 5 会主动做这几件事：验证自己的工作、派生子智能体（subagent）、汇报执行进度、根据自己的判断扩大任务范围。

如果你的旧提示词里写着"完成后用子智能体再验证一遍""每一步都要 double-check""随时汇报进度"，**这些指令会和模型的默认行为叠加**，:mdnice-bold-italic[结果就是过度验证、过度委派、过度汇报——更多工具调用、更多 token 消耗、更慢的产出，质量却没有变好。]

早期用户的实测也印证了这一点：**把为 Opus 4.8 精心搭建的复杂技能流程原封不动搬到 Opus 5 上，模型反而会提前收工、误判任务完成**。把冗余的验证和汇报指令删掉之后，简单的提示词表现更好。

### 官方建议

> 所以针对 Opus 5，官方的建议可以归纳成四条：

**第一，收敛任务范围。** 模型自主性高，会自己扩大地盘。不想让它动的地方要明写边界，比如"只修改 /src/components 目录下的文件"。:mdnice-bold-italic[同时区分两种模糊性：影响结果的歧义要让它来问你，无关紧要的细节让它自己做合理假设并说明]，别指望它自己分清这两者。

**第二，显式控制输出长度。** Opus 5 默认写得比以前长，还爱叙述执行过程。:mdnice-bold-italic[要短就直接说："只输出最终代码，不要叙述过程]。"做 PPT、写文档这类交付物，篇幅指令最好按结构拆细，比如封面页多少字、内容页多少字。

**第三，限制子智能体。** 模型派生子智能体的倾向很强，简单任务也可能派一个出来。官方建议明确告诉它什么时候该派、什么时候不该派：可以并行、需要隔离上下文、彼此独立的工作流才值得委派；单文件修改、需要跨步骤保持上下文的任务，直接做。:mdnice-bold-italic[成本敏感的场景可以加硬上限，比如"最多派 3 个子智能体"。]

**第四，用 effort 当预算工具，按任务分档。** 抽取、归类这类低歧义高并发的活儿放 `low` 或 `medium`；架构判断、长链路调试放 `high` 或 `xhigh`；`max` 留给确实证明了有收益的任务。官方给的起点建议是：:mdnice-bold-italic[编程和智能体工作从 `xhigh` 起步，其他任务从 `high` 起步]，然后用自己的评测往下扫，找到还能通过的最低档。

## 通用最佳实践：那些跨模型都管用的基本功

> Anthropic 的通用提示词最佳实践文档适用所有现役模型，结合 Opus 5 的特点，这几条原则带来的收益最大：

| 原则 | 说明 |
| --- | --- |
| 把话说清楚，把原因也说出来。 | 把提示词给不了解背景的同事看，他照着做会不会懵？会的话，模型也会。解释指令背后的动机（如“这份报告是给非技术高管看的，所以要避免术语”）比单纯下命令更有效。 |
| 示例比描述管用。 | 想控制输出格式、语气、结构，提供 3–5 个贴近真实用例、覆盖边界情况的示例（few-shot），并用`<example>`标签包裹。 |
| XML 标签切分提示词。 | 用`<instructions>`、`<context>`、`<input>`等描述性标签分别包裹指令、上下文、输入等内容，跨提示词保持标签名一致。 |
| 长文档放上面，问题放最后。 | 输入超 2 万 token 时，将长文档置于提示词顶部，问题与指令置于末尾；多文档用`<document>`标签加元数据分包，并可要求先引用原文再作答。 |
| 说“要做什么”，少说“不要做什么”。 | 正向描述目标格式，如“用连贯的散文段落来写”，优于“不要用 markdown”。 |
| 防止过度工程。 | Opus 系列易过度设计：如顺手重构未要求的代码、为一次性操作写抽象层、为极小概率场景加防御校验。核心要求是：只做明确要求或直接必要的改动；bug 修复不清理周边代码；仅在系统边界（用户输入、外部 API）做校验。 |
| 防幻觉就一句话：先调查再回答。 | 系统提示中加入：“没有打开过的代码不许评论；回答代码库问题前必须先读相关文件；不确定就给有依据的答案。” |

## 上下文工程的新规则：六条老经验作废了

> 与 Opus 5 发布同期，Anthropic 官方博客更新了《Claude 5 代模型的上下文工程新规则》，点名了几条"过去公认有效、现在建议作废"的做法。思路和提示词做减法一脉相承，但针对的是 CLAUDE.md、工具描述、记忆、参考资料这些**上下文组装** 的层面。

![文章插图](/articles/2026-07-25-opus-5-556e0551/images/06.webp)

::: image-caption
图 4：官方总结的六条规则变迁——给规则变为给判断力，给示例变为设计接口，全部前置变为渐进披露，重复自己变为简洁工具描述，CLAUDE.md 手动记忆变为自动记忆，简单 specs 变为丰富参照物。来源：Anthropic 官方博客
:::

| 过去的老经验 | 现在的新规则 | 变化的原因 |
| --- | --- | --- |
| 给 Claude 立规则 | 让 Claude 用判断力 | 硬规则是为防老模型犯低级错误的妥协，新模型的判断力已经能自己处理这些决策 |
| 给 Claude 示例 | 设计好接口 | 示例会把模型的探索空间锁死，参数设计本身就能教会模型怎么用 |
| 把所有信息前置 | 渐进式披露 | 模型已能在对的时机加载对的上下文，前置堆料只会稀释注意力 |
| 重要的事说三遍 | 简洁的工具描述 | 新模型不再需要重复强调，用法说明放进工具描述一处即可 |
| 手动写 CLAUDE.md 记忆 | 自动记忆 | 模型会自动保存与工作和你本人相关的记忆 |
| 简单的 specs | 丰富的参照物 | 模型能处理 HTML artifact、测试套件、评分 rubric 这类复杂参照 |

> 挑几条展开说。

**规则变判断力。**

旧版 Claude Code 的系统提示里写着"默认不写注释、绝不写多行 docstring、不创建计划文档"，这是为了防止老模型写错注释的硬护栏，代价是遇到文档类需求时规则本身就是错的。新版系统提示改成一句话：:mdnice-bold-italic[写代码要和周围代码一个风格——注释密度、命名方式、惯用法都对齐]。规则退了场，判断力顶上来。

**示例变接口。**

工具使用的老规矩是"一定给示例"，官方现在发现示例会把模型限制在某个探索空间里。官方举了自家 TodoWrite 工具的例子：

- 旧版描述约 9,100 个字符，堆满"什么时候该用"的清单和完整示例；
- 新版只有一句功能描述，加上一个枚举设计——`status` 只有 pending / in_progress / completed 三种取值，再补一条约束"同一时刻只有一个任务处于 in_progress"。

:mdnice-bold-italic[接口设计本身就在教模型怎么用]，这比写九千字的说明书管用。

![文章插图](/articles/2026-07-25-opus-5-556e0551/images/07.webp)

::: image-caption
图 5：TodoWrite 工具描述的今昔对比。左侧旧版约 9,100 字符，塞满使用场景清单和完整示例；右侧新版只有一句功能描述、一个状态枚举和一条"同一时刻只允许一个 in_progress"的约束。来源：Anthropic 官方博客
:::

**前置变渐进披露。**

以前的做法是把可能用到的信息全塞进系统提示，比如代码审查和验证的详细流程。现在这些能力被移进了独立的 skill，需要时才调用；部分工具改成"延迟加载"，模型先用 ToolSearch 搜出完整定义再使用，不占平时的上下文。你的 CLAUDE.md 同理：:mdnice-bold-italic[别再当成"所有经验的大仓库"，改成一棵文件树]，让模型在对的时机加载对的文件。

**重复变简洁。**

老模型对上下文末尾的指令更敏感，官方只好在系统提示和工具描述里各写一遍。现在这些重复全部删掉，用法说明只留在工具描述里。

**手动记忆变自动记忆。**

以前官方教你用 # 快捷键把要点写进 CLAUDE.md，现在模型会自动保存与当前工作、与你本人相关的记忆，不用再手动维护。

**简单 specs 变丰富参照物。**

计划模式过去依赖简单的 markdown 计划文件，现在模型能处理复杂得多的参照：一份 HTML artifact、另一个代码库里的一段函数、一整套测试套件，都可以直接当 spec 用。还可以给一份评分 rubric，模型会据此派生 verifier 子智能体去检验产出是否符合你的标准——比如"什么样的 API 设计算好"。

### 和上一章矛盾吗？不矛盾

> 读到这里你可能发现了两处表面冲突，这里统一说清楚：

- 上一章说"示例比描述管用"，针对的是**单次生成任务** 的输出格式、语气、结构，这条依然有效；本章说"别给示例"，针对的是**智能体的工具使用**，示例会锁死探索空间。
- 上一章说"长文档放上面"，针对**一次性的大文档问答**；本章说"渐进披露"，针对**多轮、多工具的智能体工作流**。场景不同，规则不同。

![文章插图](/articles/2026-07-25-opus-5-556e0551/images/08.webp)

## 两个可以直接抄的模板

### 模板一：代码审查（控制范围 + 防过度工程）

```
<task>审查本次 PR 的改动，找出真正可执行的问题，按严重程度排序。</task><scope>只关注 diff 涉及的文件。不要重构周边代码，不要提出与本次改动无关的"改进建议"。</scope><verification>每个问题必须指出具体文件和行号；没有实据的猜测不要写。</verification>
```

### 模板二：长文档研究（结构 + 引用 grounding）

```
<documents>  <document index="1">    <source>财报 Q2</source>    <document_content>...</document_content>  </document></documents><instructions>先逐条引用与问题相关的原文，再基于引用作答。结论要标注来自哪份文档。信息不足时直接说明，不要推测。</instructions><question>本季度毛利率变化的主要原因是什么？</question>
```

## 迁移清单：从 Opus 4.8 切过来之前

> 对 4.8 的迁移用户，最后给一个简化的检查顺序：

1. 先只换模型 ID、其他都不动，跑一遍真实任务看行为差异；
2. 然后删掉旧提示词里重复的验证、汇报、委派指令；
3. 加上任务范围边界；再对 effort 从低到高扫一轮，用"每个被接受的产出的成本"来比较，别只看单价；
4. 最后检查思考配置——默认开着，禁用只能在 `high` 及以下。

> 如果你还维护 CLAUDE.md 或自己的智能体，再补三条：

- **删掉系统提示里和工具描述重复的说明**，用法只留在工具描述一处；
- 把"万能仓库"式的 CLAUDE.md 拆成渐进披露的文件树；
- **检查提示词、CLAUDE.md、skill、工具描述之间有没有互相打架的指令** ——模型会把它们全部读到，并自己想办法调和。

::: block-1
:mdnice-highlight[总得来说，Opus 5 的提升是实打实的，但它奖励"做减法的提示词"和"做设计的上下文"。]

以前花时间教模型更勤快，现在模型更主动，反而要花时间告诉它哪里该停，再把省下来的篇幅换成更好的接口设计和参照物。这套思路转过来，这个模型才好用。
:::
