## 关键问题

### 问题一：MoE 与 RAG 复合部署场景下，LLM 推理两阶段瓶颈迁移逻辑兼容性及四维框架量化效能

> 作者确立的“Prefill 受计算约束、Decode 受内存约束”核心异质性规律，**在 MoE 稀疏激活与 RAG CPU-GPU 混合流水线复合部署的场景下，两阶段的瓶颈迁移逻辑是否会出现冲突或失效？** 现有四维分析框架能否精准量化这种复合范式下的性能边界与优化优先级？

论文提出的四维分析框架可有效应**对 MoE 与 RAG 复合部署场景，两阶段瓶颈迁移逻辑不会失效，但会呈现“叠加性约束”**，框架通过跨层整合能力实现精准量化：

#### 瓶颈迁移逻辑的兼容性

MoE 的稀疏激活带来 Decode 阶段路由开销与内存碎片化，RAG 则通过 CPU 侧检索扩展 Prefill 上下文长度并转移部分瓶颈至 CPU，:mdnice-bold-italic[二者并非冲突而是形成“GPU 计算/内存约束+CPU 检索约束”的叠加。]

**这种叠加【未打破】“Prefill 计算约束、Decode 内存约束”的核心异质性，【仅】增加了约束维度** ——Prefill 因 RAG 扩展上下文而强化计算压力，Decode 因 MoE 路由开销进一步加剧内存带宽依赖，瓶颈迁移仍遵循“输入长度主导相位切换”的规律（短输入时 Decode+MoE 路由为瓶颈，长输入时 Prefill+RAG 上下文扩展为瓶颈）。

#### 四维框架的量化能力

- 框架通过“微架构根源分析”量化叠加约束，如 Roofline 建模测算 MoE 路由导致的算术强度变化，内存行为分析捕捉 RAG 上下文扩展带来的 KV 缓存压力；
- **“系统扩展原则”验证多 GPU/边缘环境下的优化适配**，如张量并行缓解 Prefill+RAG 的计算压力，流水线并行降低 Decode+MoE 的内存阻塞，具体细节还是看后文；
- “新兴范式边界”模块本身已覆盖 MoE 与 RAG 的单独特性，:mdnice-bold-italic[复合场景下可通过多维度指标耦合，如检索 latency、路由开销、缓存命中率，实现性能边界量化，最终输出优化优先级]。比方说，优先解决 CPU 检索瓶颈以释放 GPU Prefill 算力，再优化 MoE 专家分区以缓解 Decode 内存碎片化。

### 问题二：边缘设备（Jetson AGX Orin）大参数量 MoE 部署，KV 缓存与路由开销叠加矛盾破解及功耗 - 推理效率平衡

> 作者指出 Decode 阶段主导能耗且与输出长度线性相关，而边缘设备（如 Jetson AGX Orin）存在内存带宽与功耗的双重约束，:mdnice-bold-italic[当在边缘部署大参数量 MoE 模型时，如何破解“Decode 的 KV 缓存内存密集访问”与“MoE 路由开销”的叠加矛盾]，在不突破设备功耗上限的同时保障推理效率？

破解边缘设备（如 Jetson AGX Orin）上“KV 缓存内存密集访问+MoE 路由开销”的叠加矛盾，**需基于作者提到的相位特性、能耗模型与系统扩展原则，采取“相位感知+稀疏优化+能耗约束”的协同方案：**

1. **MoE 路由开销的针对性优化**：利用论文揭示的“MoE 稀疏激活 decouple 模型容量与计算成本”特性，在边缘:mdnice-bold-italic[部署时采用“动态专家激活策略”——基于输入语义相似度限制 top-k 专家数量] （如从 top-8 降至 top-4），同时通过:mdnice-bold-italic[内核优化减少专家切换带来的碎片化内存访问]，抵消路由开销对 Decode 的拖累。
2. **KV 缓存的内存压力缓解**：结合论文中“Decode 内存绑定”的根源分析，针对边缘设备内存带宽限制，采用“缓存分层+量化存储”方案：:mdnice-bold-italic[对高频访问的 KV 张量实施低精度量化（如 BF16 转 INT8），对低频上下文采用稀疏存储]，同时利用论文验证的“Prefill 延迟与未缓存令牌线性相关”特性，预判缓存需求并动态释放无效上下文，降低内存占用。
3. **能耗与性能的平衡控制**：基于论文“Decode 主导能耗且与输出长度线性相关”的发现，在边缘设备上建立“能耗-输出长度-专家激活数”的联动模型：
4. **系统级并行策略适配**：依据论文:mdnice-bold-italic[“Prefill 适配张量并行、Decode 适配流水线并行”的结论，边缘设备上采用“混合并行架构”] ——张量并行拆分 MoE 专家与 RAG 扩展后的 Prefill 计算任务，流水线并行缓解 Decode 阶段 KV 缓存访问与路由开销的叠加阻塞，最终实现“内存带宽占用降低 30%+功耗控制在边缘设备上限内”的优化目标，:mdnice-bold-italic[作者就边缘部署 profiling 已验证该类并行策略可有效放大瓶颈缓解效果]。

## 一、引言

> 大型语言模型（LLM）推理已成为横跨数据中心到边缘设备的关键负载[6,16,36,50,55,58,60]。随着 LLM 部署在各类应用中不断扩展——从实时对话系统[24,34,49]到复杂的检索增强生成（Retrieval-Augmented Generation, RAG，一种结合外部知识检索的生成方式，提升模型输出准确性）流水线[10,14,22,30]——**优化推理效率变得愈发重要** [29,31,32,38,41,56,59,63]。

与传统深度学习负载不同，LLM 推理呈现出独特的两阶段执行模式：**可并行化的预填充（Prefill）阶段和串行的解码（Decode）阶段** [25,62]。这种:mdnice-bold-italic[固有的计算异质性产生了相互冲突的硬件需求，这些需求决定了系统在延迟、吞吐量和能效等指标上的性能表现。]

::: block-1
尽管预填充阶段的计算密集特性和解码阶段的内存密集特性已得到广泛认可，但**当前研究大多将这种二分法视为静态假设，而非通过动态定量分析进行验证**。模型架构日益复杂——尤其是向混合专家模型（Mixture-of-Experts, MoE，一种稀疏激活架构，通过多个“专家”子网络分工处理不同任务，降低计算成本）范式[4,11,43]的转变——再加上边缘计算、复杂检索增强生成（RAG）工作流等部署场景的不断扩展，使得硬件约束与软件特性之间的相互作用更加复杂。

:mdnice-bold-italic[这种现状催生了对系统性表征的迫切需求：该表征不仅需用严谨的微架构证据验证已有的认知，还需揭示执行模式、内存层次结构行为（指数据在 CPU/GPU 不同层级缓存和主内存间的访问模式和效率）与能耗分布之间的基本关系。]
:::

> 现有表征研究在不同研究领域呈现出显著的碎片化特征。

- 聚焦设备和能耗的分析主要刻画特定平台的延迟和功耗模式[3,12,26,35,40]，而量化研究则关注精度与性能的权衡[44]；
- 内核和编译器层面的研究剖析注意力（Attention）/通用矩阵乘法操作及优化策略[5,7,51,57]
- 面向系统的研究则探索服务部署、调度策略和缓存管理[20,28,42,46,47,52,53,62]。

:mdnice-bold-italic[尽管覆盖范围广泛，但当前研究仍处于“各自为战”的状态——缺乏跨层级、组件一体化的视角，而这种视角对于 LLM 推理的整体性表征至关重要。]

为填补这一空白，本研究提出了一个统一的实验框架：**该框架系统性地整合现有知识，同时探索新的分析方向**。这种一体化方法使我们能够在架构层面验证和完善已有的结论，并在以往研究不足的领域获得新的见解。**我们的系统性研究通过四个相互关联的分析维度展开：**

::: block-1
1. 两阶段异质性：通过跨场景测量确立预填充阶段与解码阶段的根本差异，将阶段异质性定义为 LLM 推理的核心范式；
2. 微架构根源：利用 Roofline 建模和线程束阻塞分析，从算子特性和数据复用模式中识别阶段差异的硬件根源
3. 扩展行为：在多 GPU 系统中验证面向阶段的并行化策略，并分析边缘设备中预填充与解码阶段瓶颈的加剧效应；
4. 新兴范式：表征混合专家模型（MoE）中的稀疏激活权衡，以及检索增强生成（RAG）工作流中的瓶颈迁移，为下一代系统设计提供参考。
:::

我们的研究结果为理解 LLM 推理建立了系统性框架。**这些见解既为未来模型-系统协同设计提供了理论基础，也为不同硬件环境下的实际部署提供了实用的优化指导。**

## 二、研究背景

### 2.1 LLM 推理

> 本文聚焦于仅解码器 Transformer 架构，如 Llama-3、Qwen2.5。

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/04.webp)

::: image-caption
图1. 大语言模型（LLM）推理过程示意图，包括预填充（Prefill）阶段和解码（Decode）阶段
:::

如图 1 所示，推理过程自然分解为两个不同的阶段：

::: block-1
1. 预填充阶段（Prefill Phase）：模型对整个输入提示（Prompt）进行并行处理。自注意力（Self-Attention）机制计算所有提示 tokens（文本的基本单位，如单词或子词）的键（Key）和值（Value）张量，并将其存储在键值缓存（KV Cache，存储预填充阶段计算的键和值张量，避免解码阶段重复计算，提升效率）中。这种并行计算为后续生成过程建立了初始上下文。
2. 解码阶段（Decode Phase）：模型以自回归方式逐一生成输出 tokens，每一步仅处理一个新生成的 token。为维持上下文，注意力机制利用 KV 缓存检索所有先前 tokens 的键和值张量，先针对完整历史计算注意力分数，再将当前步骤的键值对追加到缓存中。
:::

### 2.2 新兴范式：混合专家模型（MoE）与检索增强生成（RAG）

> 尽管密集型 Transformer 架构在早期 LLM 发展中占据主导地位，但两种新兴范式正从根本上重塑 LLM 推理的计算特性。

#### 混合专家模型（Mixture-of-Experts, MoE）

混合专家模型代表了从密集型计算到稀疏激活（:mdnice-bold-italic[sparse activation，仅激活部分模型参数或子网络，减少计算量]）的根本性架构转变。通过用专用的“专家”层（expert layers）替代密集型前馈网络（feed-forward networks），MoE 架构实现了模型容量与计算成本的前所未有的解耦。

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/05.webp)

::: image-caption
图2. 新兴范式概述：(a) MoE架构；(b) RAG工作流程
:::

如图 2（a）所示，路由网络（routing network）为每个 token 选择特定的专家进行处理，这使得模型能够拥有海量参数，同时仅激活极少的计算路径。:mdnice-bold-italic[这种稀疏激活显著降低了每个 token 的浮点运算次数（FLOPs），但也带来了新的系统挑战：在串行的解码阶段会产生显著的路由开销，而专家分区则会导致碎片化的内存访问模式]，从而形成新的、依赖阶段的优化方向。

#### 检索增强生成（Retrieval-Augmented Generation, RAG）

检索增强生成通过整合显式的知识检索组件，改变了 LLM 推理的过程。**这类系统构建了一个 CPU-GPU 异构流水线**：外部知识检索先于 LLM 执行，这从根本上重新分配了系统瓶颈。

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/05.webp)

::: image-caption
图2. 新兴范式概述：(a) MoE架构；(b) RAG工作流程
:::

**如图 2（b）所示，性能约束从 GPU 计算吞吐量转变为 CPU 端的检索延迟和内存带宽饱和**。此外，:mdnice-bold-italic[融入检索到的知识会大幅增加预填充阶段的有效上下文长度，带来额外的计算复杂度和内存需求]，进而**重塑整个推理过程的性能分布。**

RAG 工作流包含五个不同阶段：

::: block-1
1. 关键词提取（Keyword Extraction）：LLM 处理输入查询，提取语义关键词并生成嵌入向量（embeddings，将文本转化为数值向量，用于语义相似性计算）；
2. 知识图谱检索（KG Retrieval）：结合向量搜索和图搜索，检索相关的上下文信息；
3. 对话历史处理（Dialogue History Processing）：管理和预处理先前的对话轮次；
4. 提示构建（Prompt Construction）：将检索到的上下文、对话历史和当前查询整合为最终提示；
5. LLM 生成（LLM Generation）：对增强后的提示执行标准推理。
:::

知识图谱检索阶段进一步分解为六个功能子阶段：

::: block-1
1. 边/节点向量匹配（Edge/Vertex Vector Matching）：计算向量相似度以识别相关的图实体；
2. 边/节点遍历（Edge/Vertex Traversal）：遍历图结构以扩展检索范围；
3. 上下文获取（Get Context）：获取与检索到的实体相关联的文本内容；
4. 上下文处理（Context Processing）：对检索到的文本进行预处理，为整合做准备。
:::

其中，匹配子阶段负责相似度计算，而遍历和处理子阶段分别负责图导航和文本预处理。

## 三、表征方法学（Characterization Methodology）

> 本节详细介绍我们的表征方法学、实验设置和性能分析方法。

### 3.1 方法学（Methodology）

**我们的表征方法学旨在系统性地揭示 LLM 推理的性能图景，从现象观测逐步深入到优化指导**。四个步骤构成一个因果链：

- 首先确定核心性能现象是什么（What）
- 然后从硬件层面分析为什么会出现这些现象（Why）
- 接着验证这些原理在实际系统中如何起作用（How）
- 最后探索新兴范式正在将性能边界推向何处（Where）

具体实施如下：

#### 步骤1 现象观测：确立“是什么”——两阶段异质性

- **目标（Objective）**：识别 LLM 推理的基本宏观性能特征。
- **行动（Action）**：我们在 LLM 推理的各类应用场景中，系统性地测量延迟分布、吞吐量和能耗。
- **结果（Outcome）**：该步骤确立了一个核心实证事实——:mdnice-bold-italic[预填充阶段与解码阶段存在根本差异，并记录了两阶段各自独特的瓶颈分布、动态迁移规律和可预测行为]。这一步回答了“系统的性能现象是什么”的问题。

#### 步骤2 根源解释：揭示“为什么”——微架构成因

- **目标（Objective）**：诊断两阶段性能差异的根源。
- **行动（Action）**：我们采用 Roofline 建模（量化算术强度，算术强度指每字节数据访问对应的浮点运算次数，用于判断程序是计算密集型还是内存密集型）、线程束阻塞分析（定位流水线瓶颈）和内存行为分析（评估内存局部性，即数据在缓存中的复用程度）。
- **结果（Outcome）**：该步骤将宏观现象与微架构根源关联起来，揭示出：:mdnice-bold-italic[预填充阶段因高强度通用矩阵乘法（GEMM）运算，本质上是计算密集型；而解码阶段因低强度、依赖 KV 缓存的数据访问，本质上是内存密集型。]

#### 步骤3 扩展效应分析：验证“如何起作用”——系统级主导原则

- **目标（Objective）**：测试面向阶段的原理在扩展环境和约束环境中的通用性。
- **行动（Action）**：我们将分析扩展到多 GPU 环境和边缘设备：
- **结果（Outcome）**：该步骤展示了根源因素如何决定系统设计：:mdnice-bold-italic[验证了计算密集型的预填充阶段可通过张量并行实现性能扩展，而内存密集型的解码阶段更适合通过流水线并行优化；同时揭示了边缘设备中这些瓶颈的加剧效应。]

#### 步骤4 边界重定义：探索“走向何处”——范式转变

- **目标（Objective）**：研究新的架构和工作流创新如何重塑已有的性能边界。
- **行动（Action）**：我们表征稀疏激活的 MoE 模型和 RAG 工作流，量化它们新的效率权衡关系和瓶颈迁移规律。
- **结果（Outcome）**：该步骤展望性能图景的演变方向：:mdnice-bold-italic[展示了 MoE 如何将总参数与激活计算解耦，以及 RAG 如何将瓶颈从 GPU 转移到 CPU，从而为下一代系统重新定义优化边界。]

这种从“观测”到“解释”、“验证”再到“预测”的结构化流程，确保我们的表征不仅是描述性的，更是具有根本解释力和指导意义的。

## 四、现象观察——确立两阶段异质性

> 我们的特征分析首先从确立大语言模型（LLM）推理的基本宏观性能现象入手。通过系统性测量，我们客观记录了预填充（Prefill）阶段与解码（Decode）阶段之间的内在二分性——这两个执行阶段具有本质上不同的性能特征。

我们的分析表明：

- 这两个阶段在 **GPU 资源利用模式和能效特征上存在显著差异**；
- 此外，我们还观察到，随着输入/输出长度和模型规模的变化，:mdnice-bold-italic[阶段间会发生动态瓶颈迁移，同时还发现了强可预测性关系：预填充阶段延迟与未缓存 token（指未存储在 KV 缓存中的输入序列单元）数量呈线性依赖关系，而总能耗则随输出长度线性增长]。

本部分确立了 LLM 推理性能的核心“症状特征”，为后续的根源分析提供了实证基础。

### 4.1 预填充与解码阶段的资源利用差异

### 4.2 预填充与解码阶段的动态性能行为

> LLM 推理的性能具有内在动态性，这种动态性由工作负载属性（如输入/输出长度）、模型规模和系统配置（如批处理大小，指一次并行处理的请求数量）之间的复杂相互作用决定。

为系统性拆解这种行为，我们从三个关键维度分析其表现形式：

- 第一，考察不同条件下延迟瓶颈如何在阶段与主要算子（指 LLM 中的核心计算模块，如注意力机制、前馈网络等）之间迁移；
- 第二，刻画吞吐量（单位时间处理的 token 数量）与延迟（处理请求的时间）随批处理策略变化的动态权衡关系；
- 第三，研究预填充阶段延迟的可预测性，确立其与工作负载的确定性关系。

#### 4.2.1 瓶颈迁移

LLM 推理的特征之一是**动态瓶颈迁移，即主要性能限制会在执行阶段与核心算子之间转移**。本小节:mdnice-bold-italic[系统分析输入/输出长度、模型规模等关键因素如何主导这些转移，揭示推理性能的上下文依赖性。]

##### 阶段级瓶颈迁移

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/08.webp)

::: image-caption
图 3：(a) 聊天（Chat）场景下预填充与解码阶段的 SM 利用率和 DRAM 吞吐量概览；(b) 输入长度增加且输出长度固定（128 个 token）时，延迟主导权从解码阶段向预填充阶段转移的情况，基于单 GPU 上的 Qwen2.5-7B 模型测量
:::

如图 3(b)所示，这是 Qwen2.5-7B 模型，输出长度固定为 128 个 token $L_{out}$：

- 在输入长度 $L_{in}$ 较短时，解码阶段占总延迟的大部分；
- 但随着输入长度增加，预填充阶段的延迟占比逐渐上升，**超过某个临界点（约 2000 个 token）后，预填充阶段成为主导瓶颈。**

值得注意的是，解码阶段的每步延迟（生成每个输出 token 所需的时间）基本保持稳定，与输入长度无关。对不同模型和工作负载的实证分析表明，存在一致模式：

::: block-1
**随着输入长度增加，预填充与解码阶段的延迟占比存在明显交叉点**，:mdnice-bold-italic[【关键结论2】]：短输入时解码阶段占主导（形成“解码主导区”），超过临界长度后预填充阶段成为瓶颈（形成“预填充主导区”）。
:::

这种交叉源于两阶段的根本复杂度差异：

- 预填充阶段对整个输入执行一次性自注意力计算，复杂度为 $O(L_{in}^{2})$（二次复杂度）；
- 而解码阶段复用 KV 缓存并逐 token 增量计算，复杂度约为 $O(L_{out})$（线性复杂度），因此每步成本稳定。

##### 算子级瓶颈迁移

在 LLM 架构中，前馈网络（FFN）和注意力（Attention）模块合计占推理总延迟的 94%~96%（跨阶段与场景）。这种主导地位表明:mdnice-bold-italic[【关键结论3】]：**LLM 推理的绝大部分延迟由 FFN 和注意力算子占用。**

因此，我们研究了模型规模和上下文长度变化时，主导算子如何在 FFN 与注意力之间转移。

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/09.webp)

::: image-caption

:::

如图 4 所示：

- 基于典型上下文长度 1K~8K 的测量，趋势一致；
- 而已有研究[23,37]表明，在极长上下文（16K~32K+）下，注意力算子在两个阶段都会成为主要瓶颈，原因是其计算与内存开销会快速增加。

综上：:mdnice-bold-italic[【关键结论4】]，**随着模型规模和上下文长度变化，LLM 推理的主导算子会在 FFN 与注意力之间转移。**

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/10.webp)

::: image-caption
表 3 不同阶段、上下文长度与模型规模下的主导算子类型
:::

> 表 3 详细列出了这种转移模式。其底层机制在于 FFN 与注意力算子的计算复杂度随上下文长度 $n$ 的变化规律不同：

- 在预填充阶段，FFN 复杂度为 $O(n)$（线性），注意力复杂度为 $O(n^2)$（二次）；
- 在典型上下文（1K~8K）下，注意力的二次项尚未占据主导，因此 FFN 的显著固定成本成为主导。
- 在极长上下文下，注意力的二次成本超过 FFN，成为主要瓶颈。

在解码阶段，FFN 的每步成本大致恒定 $O(1)$ ，而注意力因需遍历全部 KV 缓存，复杂度为 $O(n)$（线性）；因此在典型上下文下，大型模型如 32B 参数模型，因 FFN 固定成本高而受 FFN 主导，小型模型如 8B 参数模型，则受注意力主导。**当上下文长度进一步延长，注意力的线性增长最终会超过 FFN 的固定成本，导致两种规模的模型在极长上下文下均受注意力主导。**

#### 4.2.2 吞吐量-延迟权衡

> 我们系统性刻画了 **LLM 推理中吞吐量与延迟之间的根本权衡关系**，:mdnice-bold-italic[重点分析批处理大小作为平衡该权衡的关键控制参数的作用。]

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/11.webp)

::: image-caption
图 5：不同批处理大小下的吞吐量与延迟权衡特征：(a) Qwen2.5-7B 模型；(b) Qwen2.5-32B 模型；(c) Qwen3-30B-A3B 模型
:::

如图 5 所示，基于三个代表性模型的批处理大小变化实验，分析揭示了一致模式：:mdnice-bold-italic[【关键结论5】：存在动态吞吐量-延迟权衡关系] ——**随着批处理大小增加，系统吞吐量（token/s）初期上升但随后边际收益递减（批处理大小增大到一定程度后，吞吐量增长速度放缓），而平均解码延迟则单调增长（持续增长，无下降），形成根本性的性能冲突。**

::: block-1
这种行为源于两个相互竞争的效应：

- :mdnice-bold-italic[更大的批处理大小能提高 GPU 利用率，并摊薄固定开销（如内核启动、调度），从而提升吞吐量；]
- 但:mdnice-bold-italic[同时也会增加排队延迟——因为批处理中的请求需共同完成，且解码过程逐 token 进行，步骤间依赖会延长平均等待时间。]

超过临界批处理大小后，吞吐量增长趋于平缓，而延迟惩罚加速上升，形成“延迟陷阱”。
:::

#### 4.2.3 预填充阶段延迟的可预测性

预填充阶段延迟（任务完成时间，JCT，指预填充阶段从开始到结束的总耗时）的可预测性对理解系统行为和构建高效调度模型至关重要。与自回归解码阶段（生成每个 token 时需依赖前一个 token 的结果，无法并行）不同，**预填充阶段的计算工作负载仅由输入 token 数量决定，因此具有内在确定性**。我们的实验结果验证了这一假设：

::: block-1
:mdnice-bold-italic[【关键结论6】] **预填充阶段的任务完成时间（JCT）与未缓存 token 数量呈强线性关系，可实现高精度延迟预测。**
:::

我们在三个代表性模型上系统性评估了预填充阶段的 JCT：

- 输入长度覆盖短至长上下文 $n_{input} \in \{1024, 2048, 4096, 8192\}$
- KV 缓存命中率设置为 $r \in \{0\%, 25\%, 50\%, 75\%, 90\%\}$，表示输入 token 能从 KV 缓存中找到对应键值对的比例，KV 缓存用于存储预填充阶段生成的 Key 和 Value 张量，供解码阶段复用

::: block-1
对于每个 $(n_{input}, r)$ 组合，我们执行“仅预填充”推理（生成恰好 1 个输出 token）多次，记录预填充阶段的 JCT 和未缓存 token 数量，未缓存 token 数量定义为：$n_{uncached} = n_{input} - n_{cached}$。
:::

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/12.webp)

::: image-caption
图 6：预填充阶段 JCT 与未缓存 token 数量的强线性关系（跨模型，相关性高，斜率代表每 token 成本）：(a) Qwen2.5-7B 模型；(b) Qwen2.5-32B 模型；(c) Llama-3-8B 模型
:::

**如图 6 所示，在三个模型上，预填充阶段的 JCT 与 $n_{uncached}$ 均呈强线性相关**：Qwen2.5-7B 的皮尔逊相关系数 $c=0.971$，Qwen2.5-32B 的 $c=0.991$，Llama-3-8B 的 $c=0.977$。

注：皮尔逊相关系数衡量两个变量线性相关程度的指标，取值范围[-1,1]，越接近 1 表示线性相关性越强

:mdnice-bold-italic[该关系可用线性模型很好地近似：$JCT \approx a + b \times n_{uncached}$，其中系数 $b$ 代表每个未缓存 token 的平均计算成本]，测量值约为：Qwen2.5-7B 为 0.0312 毫秒/ token，Qwen2.5-32B 为 0.0612 毫秒/ token，Llama-3-8B 为 0.0324 毫秒/ token。

值得注意的是，单位成本随模型规模增加而上升，表明大型模型的计算需求更高。在较短输入长度（约 1K）下观察到的相关性略有减弱，原因是该场景下固定开销（如内核启动、数据初始化等不随输入长度变化的耗时）和测量抖动（由于系统噪声导致的延迟测量值微小波动）的影响相对更大。

### 4.3 能耗分析

能效（单位能耗处理的 token 数量，衡量系统能耗经济性的指标），已成为 LLM 推理中的关键问题，**尤其是在大规模部署场景中——功耗直接影响运营成本和环境可持续性**。本小节:mdnice-bold-italic[全面分析不同阶段、输出长度和模型规模下的能耗模式，旨在建立可预测的能耗模型。]

::: block-1
我们的能耗测量在单 NVIDIA A100 GPU 环境中进行，测量方法采用精确的功率采样策略：

- 在每个推理任务前，记录 GPU 空闲功率 10 秒并计算平均值，记为 $P_{baseline}$；
- 推理执行期间，使用`nvidia-smi --query-gpu=power.draw`命令以 100 毫秒为间隔采样瞬时功率（某一时刻 GPU 的实时功耗）$P_{sample}(t)$。
- 最终，通过对任务持续时间内的基准校正功率进行积分，计算净能耗：

$$
E_{net} = \int_{start}^{end} \max(P_{sample}(t) - P_{baseline}, 0) dt
$$
:::

#### 4.3.1 能耗与工作负载的关系

> 为拆解预填充与解码阶段对能耗的贡献，我们在改变输入/输出长度的同时测量总能耗。

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/13.webp)

::: image-caption
图 7：能耗特征：(a) 输出长度固定（256 个 token）时，能耗与输入长度的关系，表明预填充阶段贡献极小；(b) 输入长度固定（64 个 token）时，能耗与输出长度的关系，表现出强线性依赖；(c) 工作负载固定（64 输入 token、256 输出 token）时，能耗随模型参数规模的变化趋势
:::

当输出长度固定为 256 个 token、输入长度从 16 增加到 2048 个 token 时如图 7(a)，总净能耗基本保持恒定（约 440 焦耳，波动在 ±2%以内），与输入长度的相关性极低:mdnice-bold-italic[（$R^2=0.071$，$R^2$ 为决定系数，衡量回归模型拟合优度的指标，取值范围[0,1]，越接近 1 表示模型拟合效果越好]）。这得出我们的第一个能耗见解：

**LLM 推理的能耗由解码阶段主导，预填充阶段对总能耗的贡献可忽略不计**。尽管预填充阶段计算密集，但它仅执行一次；相比之下，:mdnice-bold-italic[解码阶段包含数百次内存访问主导的迭代（每次生成 token 都需频繁访问 KV 缓存），KV 缓存操作的累积能耗最终占总能耗的绝大部分。]

**相反，当输入长度固定、输出长度变化时（图 7(b)），我们观察到完全不同的模式：** :mdnice-bold-italic[【关键结论8】] **能耗与输出 token 数量呈高度线性关系** （$R^2=0.999$）。拟合关系 $E=1.72 \times L_{out} - 6.48$ 表明，每个生成 token 的边际能耗成本约为 1.72 焦耳；较小的截距（约 6.5 焦耳）进一步证实了预填充阶段的能耗贡献极小。

#### 4.3.2 能耗与模型规模的关系

我们在固定工作负载（64 个输入 token、256 个输出 token）下，通过测量 Qwen2.5 系列模型的总净能耗，参数规模从 0.5B 到 14B，B 代表十亿参数，进一步**研究能耗与模型规模的关系**。

![文章插图](/articles/2025-12-24-gpu-llm-moe-rag-cc47383a/images/13.webp)

::: image-caption
图 7：能耗特征：(a) 输出长度固定（256 个 token）时，能耗与输入长度的关系，表明预填充阶段贡献极小；(b) 输入长度固定（64 个 token）时，能耗与输出长度的关系，表现出强线性依赖；(c) 工作负载固定（64 输入 token、256 输出 token）时，能耗随模型参数规模的变化趋势
:::

如图 7(c)所示，能耗对模型规模具有强依赖性：能耗随模型参数数量 $P$ 近似线性增长（$R^2=0.998$）。实验数据可通过幂律拟合（$E=76.6 \times P^{0.91}$，指数接近 1）和线性关系（$E=28.2 + 57.7P$）很好地刻画。

观察到的近似线性能耗增长源于：大型模型同时提高了瞬时功耗和执行时间，而能耗正是功率与时间的乘积。

#### 4.3.3 推理能耗的可预测性

我们的分析表明，**可根据执行前的提示（Prompt）特征准确预测 LLM 推理的能耗**。这种:mdnice-bold-italic[预测能力源于一个复合函数（由输出长度预测函数和能耗-长度关系函数组合而成）]：

::: block-1
已有研究[61]表明可通过提示预测输出长度$L_{out} \approx g(Prompt)$，而我们的结果证实能耗与输出长度呈强线性关系$E \approx f(L_{out})$。
:::

因此，$E \approx f(g(Prompt))$**可对传入请求（待处理的 LLM 推理任务）进行早期能耗估算。**

## 结论

> 本研究通过系统性实验与四维分析框架，全面揭示了 LLM 推理在 GPU 上的核心性能特征与优化方向，填补了现有研究的碎片化空白。

研究明确了 Prefill 与 Decode 两阶段的本质异质性：

- Prefill 受计算吞吐量约束，依赖高强度 GEMM 运算；
- Decode 受内存带宽限制，KV 缓存主导的数据访问构成核心瓶颈，且随输入长度增长呈现显著的瓶颈迁移现象。

二者形成 Decode 主导与 Prefill 主导的临界转换点。

::: block-1
微架构层面的根源分析验证了两阶段差异的硬件成因，而系统扩展实验表明，:mdnice-bold-italic[计算受限的 Prefill 适配张量并行，内存受限的 Decode 更适合流水线并行，且边缘设备中瓶颈效应进一步放大。]
:::

新兴范式方面：

1. MoE 通过:mdnice-bold-italic[稀疏激活 decouple 模型容量与计算成本，却带来路由开销挑战；]
2. RAG 则将瓶颈:mdnice-bold-italic[从 GPU 迁移至 CPU 侧检索与内存带宽，重塑了推理性能剖面。]

能量分析揭示，Decode 阶段主导总能耗，且能耗与输出长度、模型参数量呈强线性相关，为能效优化提供了量化依据。

:mdnice-bold-italic[本研究构建的实证基础与分析框架，既为 LLM 推理的模型-系统协同设计奠定了理论支撑，也为多 GPU 部署、边缘场景适配、MoE 与 RAG 等新兴范式优化提供了切实指导]。未来可基于此框架，进一步探索跨硬件平台的统一优化策略，以及更复杂场景下的动态瓶颈适配方案。
