## 一、引言

近年来，AI 编译器（如 Triton [1]、TVM [9]、MLIR [7]）已成为连接高层机器学习模型与底层 GPU 硬件的关键桥梁。这些编译器通过自动生成优化的 GPU 内核（kernel，在 GPU 上执行的函数），大幅降低了手工调优的门槛，支持快速部署 Transformer [10]、扩散模型 [11]等复杂 AI 模型。:mdnice-bold-italic[然而，面对不断演进的 GPU 架构] （如 NVIDIA Hopper 的 Tensor Core [2]、TMA 内存加载器 [12]）:mdnice-bold-italic[和日益复杂的算子] （如 Flash-Attention-3 [3]、Grouped GEMM [13]），:mdnice-bold-italic[编译器生成的代码性能仍常落后于专家手工优化的实现] （如 cuBLAS [4]、Flash-Attention [14]）。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/02.webp)

性能分析是提升编译器代码质量的核心驱动力。通过理解内核的实际执行行为（如计算与内存操作的重叠效率、资源闲置时间），开发者可以指导编译器优化（如调整软件流水线阶段、改进数据预加载策略）。

> 然而，现有性能工具难以满足现代 AI 编译器的需求，主要存在以下:mdnice-bold-italic[局限]：

1. **缺乏高层语义**：传统工具（如 NCU [5]、RocProf [15]）:mdnice-bold-italic[依赖底层硬件接口，只能观察指令级或寄存器级行为，无法关联到编译器层面的抽象] （如循环结构、算子分区策略）。例如，它们无法直接分析“软件流水线（software pipelining，通过重叠不同循环迭代的加载、计算、存储阶段来提高效率）”中各阶段的重叠效率[16]。
2. **反馈闭环低效**：现有工具通常:mdnice-bold-italic[独立于编译器工作流]，分析结果需手动转换为编译器优化策略。例如，开发者需从 NCU 报告中提取内存带宽数据，再手动调整 Triton 代码中的数据布局，这一过程耗时且易出错。
3. **可移植性差**：工具往往:mdnice-bold-italic[绑定特定硬件或厂商接口] （如 NVIDIA 的 NVML [17]、AMD 的 ROCm [18]），:mdnice-bold-italic[难以跨架构] （如从 NVIDIA GPU 移植到 AMD GPU）复用，增加了社区协作的门槛。

为解决这些问题，我们提出**KPerfIR**：一个编译器中心的多层中间表示（IR）性能工具生态系统。KPerfIR 的:mdnice-bold-italic[【核心思想】是将性能分析能力直接嵌入编译器的中间表示] （IR，编译器在编译 pass 中用于表示代码的中间形式）中，**通过编译器 pass 实现性能工具**。这种设计带来:mdnice-bold-italic[三个关键优势]：

::: block-1
- :mdnice-bold-italic[可编程性]：利用 IR 的高层语义（如循环结构、算子类型），KPerfIR 能**捕捉细粒度的内核内行为** （如软件流水线各阶段的执行时间），而传统工具因缺乏这些语义无法实现。
- :mdnice-bold-italic[闭环优化]：KPerfIR 的分析结果可直接**被编译器的优化 pass 使用，形成“分析-优化”的自动反馈循环** （如基于分析结果自动调整软件流水线的阶段数）。
- :mdnice-bold-italic[可重用性]：基于 MLIR 和 Triton IR 等跨硬件的中间表示，KPerfIR 工具**可轻松移植到不同 GPU 架构** （如 NVIDIA、AMD），促进社区驱动的工具开发。
:::

作为首个基于编译器 IR 的性能基础设施，KPerfIR 构建在 Triton 编译器[1]之上（支持 NVIDIA 和 AMD GPU），提供了一套标准化的 IR 操作符（如`RecordOp`用于标记分析区域、`ReadCounterOp`用于读取性能计数器），支持开发者快速构建定制化性能工具。我们展示了一个代表性工具：:mdnice-bold-italic[基于区域的 GPU 计时工具]，它能**实现内核内任意代码区域的高精度时间测量** （相对误差 2%），**揭示软件流水线、warp specialization** （warp specialization，一种让 GPU 的 warp（线程束，由 32 个线程组成的基本执行单元）专注于特定任务以提高效率的技术）等优化的实际效果。

我们的评估表明，KPerfIR 的平均性能开销仅为 8.2%，且能有效指导优化：在 Flash-Attention-3（FA3）内核中，我们通过 KPerfIR 识别出数据加载与计算的重叠不足问题，优化后性能提升 24.1%，超越手工调优版本 7.6%。

## 二、背景与相关工作

尽管所提出的方法同时支持 NVIDIA 和 AMD GPU，但为了不失一般性，我们将以 NVIDIA 的 GPU 为例进行说明，除非讨论 AMD 平台的特定功能。在下文里，我们会介绍 GPU 编译器和性能分析工具（profilers）的背景，重点关注它们在 AI 工作负载中的应用。

### 2.1 GPU 编译器

AI 编译器的设计取得了显著进展，其中 MLIR [26]（多 Level 中间表示，一种模块化的编译器基础设施，支持多层面抽象和定制化）的引入是迈向模块化、可扩展性和多层次抽象的关键一步。MLIR 通过一个可复用的框架简化了现代计算工作负载的复杂性，降低了编译器开发的学习门槛，同时支持自定义组件和第三方工具集成以推动创新。

在 MLIR 的基础上，Triton [47]是一款突破性的编译器，旨在连接 AI 工作负载和 GPU 硬件。Triton 具有专为 GPU 编程定制的方言（dialect，编译器中针对特定领域的中间表示形式），提供了高层抽象，简化了高效 GPU 核函数的开发，满足了计算密集型 AI 应用的需求。Triton 利用 MLIR 的模块化架构实现了可复用性、无缝集成和多层次优化，展示了如何在统一框架内满足特定领域的需求。Triton 的中间表示（IR）包含多种方言，包括 TTIR、TTGIR、Triton、TritonGPU、TritonNvidiaGPU 和 TritonAMDGPU，每种方言都针对 GPU 编程的特定阶段。

### 2.2 GPU 性能分析工具

GPU 性能工具对于分析工作负载执行特性和识别性能瓶颈至关重要。它们使开发人员能够理解应用行为和硬件利用率，这对于在 GPU 平台上实现最佳性能至关重要。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/05.webp)

GPU 性能工具可分为两大类。现成的性能分析工具包括 NVIDIA 的 Nsight Compute（NCU）[33]和 Nsight Systems（NSys）[34]，以及 AMD 的 RocTracer 和 RocProfiler [4]。

- NCU 为 CUDA 应用提供详细的核函数级分析，提供各种指标和可操作的优化建议。NSys 提供系统级的整体性能视图，捕获 CPU 和 GPU 之间的交互以诊断延迟和同步问题。
- 类似地，RocTracer [5]通过在异构环境中跟踪和分析应用，支持 AMD GPU 的性能优化。

这些性能分析工具的一个重要方面是:mdnice-bold-italic[计时开始和停止调用] （例如 cudaProfilerStart 和 cudaProfilerStop），它们被实现为**围绕核函数启动调用的主机端 API，而不是直接在核函数代码内部**。

- MosaicGPU 性能分析工具[10]通过高层 Python 绑定插入 PTX 指令，其理念与我们的方法最接近。然而，它在汇编代码级别而非高层 IR 上运行，限制了其提供全面且可复用的性能分析能力。
- ThunderKitten（TK）[44]是 NVIDIA 平台上一种有前景的领域特定语言（DSL），最近也开发了用于基于区域的跟踪的自定义计时接口。但该工具与其 DSL 设计紧密耦合，且仅支持 NVIDIA 平台。

像 CUPTI [32]、NVBit [48]、RocProfiler 这样的性能分析基础设施:mdnice-bold-italic[提供一定程度的定制插桩（instrumentation，在程序中插入代码以收集运行时信息）能力]。它们允许开发人员在运行时插入自定义指令，提供灵活的性能分析选项。然而，它们**与程序和插桩框架紧密耦合** [20]。这种方法**缺乏可移植性**，无法与编译器工作流无缝集成，限制了其支持跨平台开发的能力。

### 2.3 GPU 重叠技术

> 为了有效利用 GPU 设备的资源并释放其全部潜力，GPU 核函数必须安排不同的执行单元和内存单元以重叠它们的执行，从而实现更好的并发性。

随着专用**片上加速单元** （如 Tensor Core [16]（张量核心，GPU 中用于加速矩阵运算的专用硬件单元）和 **Tensor Memory Accelerator** [15]（张量内存加速器，用于优化内存访问的硬件单元））的引入，它们的**重叠变得更加重要且复杂**。

#### Wave 优先级和指令调度

:mdnice-bold-italic[实现重叠的最直接解决方案是通过显式优先级设置扩展调度器]。这被实现为主要由 **AMD 平台采用的 wave 优先级技术，通过基于编译器的 builtin 函数** （例如 LLVM 的 `builtin_amdgcn_s_setprio()`）在编译时控制 wavefronts（波前，AMD GPU 中与 warp 类似的线程组）在计算单元（CUs）上的调度和执行。**在运行时，当调度冲突的指令类型时，计算单元会选择优先级更高的波前**。通过:mdnice-bold-italic[设置合适的 wave 优先级，程序员可以通过显式重叠一个 wave 上的内存加载和另一个 wave 上的计算操作来充分利用执行流水线] [3]。重叠可以通过编译器调度内在函数（如 `builtin_amdgcn_sched_barrier()`）进一步细化，以控制矩阵运算的聚类和流水线处理。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/06.webp)

:mdnice-bold-italic[软件流水线（SWP）将独立循环迭代操作（即内存操作和计算操作）转换为多个阶段，以实现迭代间的重叠，如图 2-(b)所示]。通过使用**异步指令进行数据加载[8]和计算，不同的操作可以并发执行以重叠延迟**。然而，SWP **需要在加载的内存层次结构中** 额外的暂存器存储和寄存器来存储**每个阶段的中间结果**。软件流水线通常在多个级别采用，例如从全局内存到共享内存以及从共享内存到寄存器文件，以有效隐藏延迟。除了用于重叠数据加载和计算外，:mdnice-bold-italic[SWP 还用于重叠由独立硬件单元执行的不同计算部分]。VALU、VMEM 和 SMEM 指令[2,3]都可以独立调度——目标是让它们与张量/矩阵核心操作完全并行运行。**由于其提高利用率的关键优势，SWP 在高性能算子库[45]和编译器优化[22]中得到了广泛应用。**

:mdnice-bold-italic[线程束特化] （WS，Warp Specialization）是:mdnice-bold-italic[另一种基于生产者-消费者模型构建的重叠技术] [8,23]。将执行分为多个阶段后，WS 将阶段分配给专用的线程束（warp，NVIDIA GPU 中由 32 个线程组成的线程组）作为生产者和消费者。与 SWP 中不同循环迭代阶段之间的重叠不同**，WS 在不同线程束中的生产者和消费者阶段之间实现重叠，如图 2-(c)所示**。WS 先前被提出作为解决不规则和大型问题的方案，以重叠不平衡的工作负载并减少寄存器压力[17]。与 SWP（每个线程束同时作为生产者和消费者）相比，WS 分离了角色，以便寄存器可以合理分配。例如，数据加载阶段消耗的寄存器比繁重的计算阶段少得多。然而，由于缺乏硬件线程束级寄存器分配支持，这一特性未被充分利用。**最近，在 NVIDIA Hopper 架构[15]上，寄存器重分配和异步事务屏障等新特性使 WS 能够实现卓越的重叠性能** [42,45]。

### 细粒度理解

随着异构执行单元和异步数据流编程范式的复杂性增加，直观理解执行流水线变得具有挑战性。对于示例中所示的情况，用户可能会选择 SWP 或 WS 来协调数据加载和计算。然而，**为了最大化硬件利用率，他们必须仔细确定 SWP 中的阶段划分和阶段数量，或决定 WS 中的执行顺序和同步屏障**。现有性能分析工具提供的聚合结果缺乏关联性能指标所需的程序语义。要真正理解重叠行为，必须解析循环结构、分析跨线程束依赖关系，并跟踪整个执行过程中的细粒度指标。用户难以有效识别和解决低效问题。

> :mdnice-bold-italic[要点1]：性能分析工具需要**编译器的 IR 来提供** 细粒度的**性能指标**。

### 性能优化

全面理解执行行为为手动优化提供了机会。然而，在编译器 pass（编译器中的处理步骤）中实现自动优化时，挑战变得更大。编译器需要与现有 IR 设计相关联的可定制性能反馈，以确定最佳转换。如示例所示，选择 WS 和 SWP 的适当重叠设计需要每种方法的稳定性能估计。编译器 pass 必须依赖精确的性能分析数据来有效指导其优化选择。嵌入在编译器基础设施中的可编程性能工具是实现这一工作流的关键第一步。

> :mdnice-bold-italic[要点2]：编译器**优化 pass** 需要**可编程的性能分析工具** 来有效**指导其优化决策**。

## 四、编译器中心的性能工具

尽管当前的编译器设计对编译器和核函数开发者有益，但它缺乏对性能工具的支持。:mdnice-bold-italic[现有的 MLIR 方言] （MLIR 是一种用于构建编译器的基础设施，方言指其中针对特定领域的扩展）:mdnice-bold-italic[主要关注静态的、编译时的转换和优化 pass ，而很少考虑捕获动态跟踪或性能分析语义] （用于描述性能分析相关的代码含义）。这一差距使得**开发者在编译器生态系统中缺乏一个原生框架来分析运行时行为或微调核函数性能**。

将性能工具基础设施设计为 MLIR 方言并非易事。例如，在 Triton（一种 AI 编译器）中，这样的方言必须弥合高层张量 IR（中间表示，编译器中用于表示张量操作的中间代码）和低层特定目标 IR（针对特定硬件的中间代码）之间的抽象差距，同时保持清晰的抽象，以与现有的多级程序 IR 语义保持一致和兼容。:mdnice-bold-italic[理想的基础设施应该能够处理多样化的性能分析需求，并能很好地扩展以适应不断发展的 GPU 架构]。为解决这一复杂性，我们引入了 KPerfIR 方言，这是首个将插桩 pass （在代码中插入用于性能分析的代码片段）直接集成到编译器 IR 中作为性能工具基础设施的方言。该系统基于主流 AI 编译器 Triton[47]实现，Triton 采用 MLIR 作为其编译器基础设施。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/08.webp)

我们展示了 KPerfIR 基础设施的多级 IR 设计和运行时约定，如图 4 所示。我们还将进一步讨论 KPerfIR 的几个代表性用例。

### 4.1 IR 设计

> 在 Triton 的多级 IR 结构中，TTIR 和 TTGIR 是开发者主要交互的程序表示形式。:mdnice-bold-italic[我们将 KPerfIR 实现为与 Triton 的 IR 结构交互的多层 MLIR 方言]，并**将高层 MLIR 操作与 LLVM-IR 级分析** （LLVM 是一种编译器框架，LLVM-IR 是其使用的中间表示）**链接起来**。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/08.webp)

如图 4 所示，我们在 MLIR 方言中插入记录操作，并将其 lowering（编译器中将高层中间表示转换为低层中间表示的过程）为特定架构的 TritonGPU 操作。我们还在 LLVM IR 级别 lowering 并插桩一些脚手架函数（辅助性函数），例如从本地缓冲区到主机内存的数据复制。:mdnice-bold-italic[这种架构将编程语言构造与硬件相关特性链接起来以进行分析]。具体来说，我们**在不同级别定义新的操作来插桩性能分析语义并收集测量数据**。

> 重写后的 Triton 程序随后被 lowering 为 LLVM IR，以进行进一步的分析和代码生成。这种设计**通过高层 IR 设计和低层代码生成，平衡了可编程性和复杂性**。

:mdnice-bold-italic[插桩可以在 MLIR 或 LLVM IR 级别进行，这是在灵活性和通用性之间的一种权衡]。MLIR 级别的插桩可以访问高层构造，例如循环和数据对象（如张量、矩阵等）。然而，**插桩指令在编译器 pass 流水线中插入的位置越高，其准确性和可靠性就越容易受到编译器后端的指令调度** （编译器对指令执行顺序的安排）**和重排序的影响**。相比之下，LLVM IR 更接近低层汇编代码，并提供更多关于 GPU 设备的信息。尽管如此，在 LLVM IR 级别进行插桩可能会失去与高层程序语义的联系。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/09.webp)

:mdnice-bold-italic[因此，我们通过将高层 MLIR 方言与 LLVM IR 级分析链接起来，设计了编译器中心的性能工具，如表 2 所示]。我们在 TTIR 和 TTGIR 级别都提供了性能分析插桩接口，因为它们是通用的表示形式，隐藏了低层厂商特定的细节，并捕获了关键优化，如软件流水线、代码移动、循环融合和线程束专用化（warp specialization，一种让不同线程束负责不同任务以提高并行效率的技术）。**KPerfIR 是我们的最高抽象级别，它包括关键的 RecordOp 操作符**，代表一种**通用的程序标记**，其**语义解释完全取决于 KPerfIR 到 KPerfGPUIR 的 lowering pass 配置**。RecordOp 的输入包括 name（名称）和 isStart（是否为开始），用于指定程序中的注释位置和标识符。程序中使用 RecordOp 的示例如下：

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/10.webp)

:mdnice-bold-italic[KPerfIR 级别的 RecordOp 抽象掉了硬件细节，并被 lowering 为特定于 GPU 的 KPerfGPUIR 操作]。

- 在 KPerfGPUIR 级别，我们获得了与厂商无关但特定于 GPU 的硬件特性（例如，共享内存抽象）。
- 当 lowering 到 KPerfGPUIR 时，会给出各种 MLIR pass 选项来确定转换，例如 MetricType（指定性能计数器）和 Granularity（例如，线程束组、线程束、线程等）。例如，当分析 GPU 周期时，每个 RecordOp 被 lowering 为 ReadCounterOp 和 StoreCounterOp，编译器可以为适当的程序位置单独调度它们。

- ReadCounterOp 收集确切的 GPU 周期寄存器值。
- StoreCounterOp 将计数器值存储到带有偏移量的性能分析缓冲区中。相应的缓冲区和记账资源（用于跟踪缓冲区使用情况的资源）在 lowering pass 中根据可配置的约束进行确定和分配。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/09.webp)

**表 2 概述了 KPerfIR 和 KPerfGPUIR 中具有输入、输出和属性的关键操作符**。插桩的具体操作由 lowering/转换 pass 中的各种 MLIR pass 选项控制，包括 BufferType（缓冲区类型）、BufferStrategy（缓冲区策略）、MetricType（指标类型）、Granularity（粒度）和资源约束（例如，缓冲区大小）。**通过这些控制旋钮，编译器为性能工具生成特定的 KPerfGPUIR 操作，其性能分析位置由 RecordOp 标记指定**。例如，将 BufferStrategy 指定为循环（circular）、MetricType 指定为时钟（clock）、Granularity 指定为线程束组，会产生一个使用循环缓冲区来存储每个线程束组的时钟周期的核内性能分析器（参见第 5 节对该性能分析器的详细讨论）。在这种情况下，StoreCounterOp 操作被转换为 CircularStoreOp 来处理循环缓冲区事件记录。

此外，编译器还在 KPerfGPUIR 中生成脚手架操作，以设置和清理性能分析阶段的环境。InitOp 初始化性能分析状态（例如，缓冲区索引）。我们使用栈分配，使 LLVM 工具链能够对位于时钟测量关键路径上的缓冲区索引应用寄存器提升（register promotion，一种编译器优化，将内存中的变量提升到寄存器中以提高访问速度）。该操作返回分配的索引的地址，并且内存加载/存储操作将通过 LLVM 后端的优化将索引值保存在寄存器中而被优化掉。FinalizeOp 执行清理并写回性能分析记录。类似地，确切的缓冲区内存分配操作（LocalAllocOp、GlobalScratchAllocOp 和 StackAllocOp）也由从 KPerfIR 到 KPerfGPUIR 的 lowering pass 中的配置确定 2。

**最后，我们有 LLVM 级别的标记 startInstrumentationOp 和 stopInstrumentationOp 来控制基于低层库的插桩**。

- startInstrumentationOp 告诉 LLVM 级别插入起始内存分析/时间戳（包括线程束 ID、SM ID（流式多处理器 ID，GPU 中的计算核心单元））。
- stopInstrumentationOp 插入结束内存分析/时间戳，并将数据从本地缓冲区刷新到临时缓冲区/主机锁定内存（主机中不被换出的内存，用于快速与 GPU 交换数据）。

这允许低层 IR 级别的插桩与高层数据对象和流结构（例如，在仅存在于高层 IR 级别的数据对象和流结构周围的 LLVM IR 级别插入时间戳）链接起来。

仅在 MLIR 级别包装所有插桩会使派生工具难以扩展到机器学习框架，因为它们在支持的操作集上存在差异。相比之下，在 LLVM IR 级别插入指令允许开发灵活且可重用的工具。:mdnice-bold-italic[分析代码可以用任何语言编写，编译为 LLVM 字节码，并插入到 MLIR 框架代码中]。*这一特性在不链接 Clang（LLVM 的 C/C++编译器）或其库但包含 C++插桩函数的 MLIR 框架中特别有吸引力*。**换句话说，分析函数可以用 HIP/CUDA** （AMD/NVIDIA 的 GPU 编程接口）**编写**，并**在没有 C++代码的 MLIR 框架** （例如，Triton、PyTorch）**中使用。**

### 4.2 编译器 pass

> 然后，我们利用编译器 pass 将 RecordOp 插桩到目标程序中，并将其 lowering 到底层 IR。:mdnice-bold-italic[有两个主要级别的编译器 pass 处理它们的插入和转换]，包括将 **KPerfIR lowering 到 KPerfGPUIR**，以及**将 KPerfGPUIR lowering 到 LLVM**。

#### KPerfIR 到 KPerfGPUIR

该 lowering pass 将 RecordOp 转换为 ReadCounterOp 和 StoreCounterOp，并插入资源分配操作（例如，LocalAlloc）以及设置/清理操作（例如，InitOp 和 FinalizeOp）。在核函数（GPU 中执行并行计算的函数）入口，我们分配性能分析缓冲区、全局临时内存和记账资源。:mdnice-bold-italic[我们将在第 5.2 节中讨论内存管理，这里重点解释 lowering 过程]。

分配的性能分析缓冲区与每个 ReadCounterOp 相关联，以收集硬件性能计数器（例如，GPU 周期）。收集的原始数据通过 FinalizeOp 以预定义的内存布局写回 GPU 全局内存（GPU 中可供所有线程访问的内存），FinalizeOp 被插入到核函数的末尾。FinalizeOp 的输入包括性能分析记录的数量、性能分析缓冲区的基地址和性能分析器全局内存的基地址。

#### Triton 将 TTGIR lowering 到 LLVM 后端

**此过程以生成特定厂商的代码** （例如，ptx（NVIDIA GPU 的汇编语言）和 amdgcn（AMD GCN 架构的汇编语言）），**并执行低层优化，如冗余代码消除[18]和寄存器提升[28]。**

:mdnice-bold-italic[我们开发了一组 LLVM 转换模式来处理插桩的性能分析操作的代码生成]。具体来说：

- InitOp 被 lowering 为缓冲区索引的栈分配（llvm.alloca）。
- ReadCounterOp 被 lowering 为将性能计数器（例如，%clock）读取到寄存器中，StoreCounterOp 被 lowering 为带有标签创建和缓冲区索引管理的寄存器值存储。
- 对于 FinalizeOp，我们计算当前线程块的全局内存偏移量，并指定第一个线程作为工作线程将整个性能分析缓冲区写回全局内存。

我们提供了关于后端的主要支持，以减少高层插桩对优化（如指令重排序）的干扰。

- 对于 NVIDIA GPU，影响可以忽略不计，因为硬件负责指令调度，而 PTX（并行线程执行，NVIDIA 的 GPU 汇编语言）大多遵循与 KPerfIR 操作符相关联的插桩程序。指令不会围绕像 WGMMA（ warp 级矩阵乘法累加指令）这样的关键指令进行调度。
- AMD GPU 将指令调度暴露给软件，即使对于 amdgcn 中的 SMEM（共享内存）加载和 MFMA（矩阵乘法累加）指令也是如此，这使得插桩的操作符成为一个关键因素。因此，我们提供了三个级别的可由用户调整的配置：

#### 插桩 API

> 要使用 KPerfIR 方言构建定制的性能工具，用户必须显式修改核函数签名（函数的参数和返回值类型信息），并通过插桩 pass 更新 IR。我们提供了两个 API 供用户与 KPerfIR 交互，即命令行 API 和 Python API。

- 使用命令行 API 时，运行时遇到的所有 Triton 函数都会用指定的分析 pass 进行插桩。这允许方便地操作目标工作负载，但缺乏灵活性，因为用户不能跳过他们不感兴趣的核函数。
- Python API 允许用户指定插桩入口和要插桩的目标函数。这里的插桩入口指的是编译 pass 中的插入位置（即，在哪个 pass 之前/之后）。另一方面，由 RecordOp 指定的插桩点指的是 IR 中的位置。它包含核心 API `KPerfIR.patch`( `instrumentation_obj`, fn)，其中 `instrumentation_obj` 标识要插桩的编译器 pass （之前或之后），fn 是可选的，用于选择要插桩的核函数。如果 `instrumentation_obj` 指定 MLIR 插桩，我们采用 MLIR 的 pass 基础设施 `PassManagement`。我们将在编译过程的末尾对 LLVM 进行插桩。此外，我们提供了 `KPerfIR.unpatch()` API 来恢复所有现有的插桩。这涉及在 KPerfIR 运行时维护核函数的原始版本和插桩版本。

#### 运行时内存管理

> 第三方工具的另一个重要部分涉及缓冲区存储和性能分析结果的管理。

在顶层，我们用一个额外的最后一个参数（指向设备缓冲区的指针）重写核函数签名，并修改调用约定。**累积的性能分析数据随后返回到由 KPerfIR 运行时管理的主机缓冲区**。在这里，我们**采用基于丢弃的循环缓冲区** （一种内存缓冲区，当满了之后会覆盖旧数据）**设计**，这将在第 5.2 节中结合实际工具设计进行详细说明。

::: block-1
我们有两种方式来管理 GPU 设备缓冲区和主机缓冲区通信，遵循先前的研究[53,54]。

- 第一种方法是使用 CUDA 托管分配，使设备缓冲区分配在 GPU 和 CPU 都可见的内存空间中。
- 第二种方法是分配一个优先级高于 PyTorch 运行时所用流的优先级流（GPU 中用于调度任务的队列，高优先级的流会先执行），并使用该流将数据复制回 CPU。
:::

一旦数据被复制回 CPU，它就会被解码为类似于 CUPTI Activity API 的 C/C++结构体。第三方工具将在运行时初始化时注册一个回调来处理这些数据。一旦主机缓冲区被解码，回调就会被触发，允许这些工具处理数据，就像 CUPTI 活动一样。因此，这些工具可以对数据进行后处理，使其与自己的前端可视化工具（如 Chrome Trace[19]或 Hatchet[9]）兼容。

## 五、基于区域的计时工具

> 在本节中，我们:mdnice-bold-italic[深入探讨一个基于 KPerfIR 基础设施构建的强大第三方性能工具]，该工具用于执行基于区域的核内计时，以**帮助理解和优化 GPU 硬件资源的重叠** （指计算和内存操作等并行执行）行为。

为了使用 KPerfIR 方言构建定制化性能工具，用户必须实现插桩 pass 、配置文件数据管理以及第 4.3 节中介绍的后处理流程。下面将结合基于区域的工具详细阐述这些内容，包括其插桩工作流程（第 5.1 节）、内存系统（第 5.2 节）和跟踪重放后处理（第 5.3 节）。

### 5.1 工作流程

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/12.webp)

我们首先介绍该计时工具的两种接口工作流程，如图 7 所示，包括用户接口和编译器接口。根据目标程序的解析方式和性能分析区域的指定方式，会调用不同的接口来插桩性能分析记录。随后，KPerfIR 会编译并执行插桩后的程序，收集原始性能计数器。最后，我们利用原始元数据重放跟踪，并生成最终的时间线跟踪结果。该跟踪结果会输出并反馈给不同的接口，用于可视化或性能分析器引导的编译器 pass 。

:mdnice-bold-italic[用户接口是开发者对目标 GPU 程序的感兴趣区域进行性能分析的基本用法。] 我们**在 Triton 核函数中提供 Python 领域特定语言（DSL）绑定，还允许手动重写和覆盖为相关区域 dump 的中间级 IR**。开发者手动重写为相关区域 dump 的中间级 IR 即可，这在开发高性能核函数和调试效率问题时非常有用。KPerfIR 会用重写后的程序 IR 对原始程序进行插桩，并生成输出跟踪。开发者可以利用可视化工具（如 Chrome Tracer[19]）直观地查看程序时间线。

:mdnice-bold-italic[编译器接口是编译器与性能分析器交互的方式。] 与用户接口相比，编译器 pass 负责解析中间级 IR，并在相关区域插入性能分析记录。同样，插桩后的程序会被编译和执行，性能分析跟踪结果会反馈给编译器内部的编译器 pass 。

### 5.2 性能分析数据管理

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/13.webp)

> 接下来，我们介绍该工具的具体管理和解码技术。:mdnice-bold-italic[图 8 展示了适应各级内存层次结构存储的系统]。下面将自底向上演示数据结构和布局。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/14.webp)

#### **线程束级区域数据结构**

对于每个细粒度性能分析区域，会插入两个性能分析记录，即区域开始记录和区域结束记录。每个记录占 8 字节，包含 4 字节的标签和 4 字节的有效载荷，如图 9 所示。标签包含 1 个标志位（表示开始或结束）和 31 位控制位（其含义与后端相关，后续会解释）。有效载荷包含从硬件计数器捕获的 32 位时间戳指标（NVIDIA 的%clock 周期和 AMD 的 S_MEMTIME 指令的低 32 位）。这种设计在空间容量和写入速度之间取得了良好平衡，因为存储消耗低，且存储操作采用向量存储指令。

我们使用 32 位时钟捕获当前记录的周期数，这可能会导致值溢出。我们在后期处理过程中解决此问题，检测并抛出溢出异常。只要每个迭代的运行时间少于 40 亿个周期（1GHz 下为 4 秒），跟踪重放就可以补偿时钟环绕溢出。由于大部分执行时间都花在循环上，因此对于大多数情况，该限制可放宽到循环迭代级（少于 1 毫秒），使得 32 位周期数据是一个安全的选择。如有必要，KPerfIR 可以通过在 IR 中添加专用操作符和属性轻松扩展到 64 位时钟。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/13.webp)

#### **SM 级数据布局**

记录随后通过存储指令从本地寄存器文件复制到共享内存中的数据缓冲区。如图 8 所示，数据缓冲区按线程束组划分为性能分析空间，具有非重叠的记录槽。因此，编译时的记录索引决定了共享内存中的存储位置偏移量。例如，如果我们分配 64 个槽（0.5KB），且每个线程块包含 2 个线程束组（8 个线程束，256 个线程），则每个线程束组有 32 个槽。编译时，我们预先计算每个性能分析空间的基地址，并生成代码管理每个线程束组的索引。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/14.webp)

**图 9 展示了每个线程束组缓冲区的内存布局**。开始和结束记录在共享内存中交错排列，以支持嵌套区域和多迭代。:mdnice-bold-italic[图下方展示了三种性能分析模式：普通模式、嵌套模式和多迭代模式]。记录存储时不进行配对，在跟踪重放期间根据性能分析模式进行对齐以确保正确性。

#### **共享内存循环缓冲区**

:mdnice-bold-italic[由于共享内存容量有限，可能无法容纳所有性能分析数据，尤其是在长多迭代记录模式下]。例如，对于 2 个线程束组、4 个性能分析区域和 512 次迭代的循环，最多需要 4096 个记录槽，相当于 16KB 的共享内存存储。对于生产级核函数，我们通常发现用于核内性能分析数据缓冲区的可用共享内存空间在 1KB 到 4KB 之间，仅占 H100 设备[15]总 228KB 的 1.75%。

**我们为每个线程束组的数据缓冲区提出一种循环缓冲区结构，作为平衡准确性和可用性的解决方案**。当达到共享内存限制时，循环缓冲区循环保留跟踪的尾部记录。我们循环覆盖最旧的结果，而不是将它们刷新到更低级别的内存。其:mdnice-bold-italic[思路是，可视化最近的几次迭代足以识别瓶颈。我们通过预先计算的缓冲区容量环绕索引来实现循环缓冲区]。如果捕获的事件溢出缓冲区，则会重定向到已占用的槽。这会导致索引管理需要额外指令，这在编译时得到解决。我们只需要轻量级的模运算指令在运行时对索引进行取整。

此外，这种循环缓冲区是运行时的默认内存管理行为。用户可以切换到简单刷新策略，即当缓冲区满时，捕获的事件立即写回全局内存。这种策略可以保留所有性能分析事件，但会带来更多频繁的内存写入指令开销。在 KPerfIR 基础设施中，我们提供了一套全面的操作来支持各级内存（包括栈、共享内存、全局内存）的分配，以及包括循环和刷新在内的管理策略。用户可以利用这些抽象来开发自己的工具，结合使用缓冲区和管理策略。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/14.webp)

具体来说，我们为 AMD 后端实现了一种协作存储策略，以最小化性能分析开销。由于每个线程束或线程束组只需要记录一个时间戳，AMD GPU 利用线程掩码进行分支，通过谓词执行指令。然而，这种线程分歧可能导致意外的指令缓存未命中，造成高达 600 个周期的开销。为缓解此问题，我们强制所有线程写入相同的共享内存位置，只保留最后一个结果。为对齐记录，我们包含一个额外的 12 位签名，该签名源自 HARDWARE_ID REG 的最低有效位（LSB），如图 9 所示。该签名编码 wave_slot_id、SIMD_id 和 pipe_id，以注释性能分析的线程。在线程束组级别，我们确保所有四个线程束写入相同的共享内存位置。

#### **全局程序跟踪**

**最后，在从核函数返回之前，我们将所有 SM 的性能分析数据收集回 GPU 全局内存**。我们将临时性能分析数据保存在共享内存中，并在核函数结束时一次性复制整个数据缓冲区。我们为重建完整的程序执行跟踪附加一些额外的元数据，如线程块 ID、线程束组 ID 和每个记录的时间戳。

### 5.3 跟踪重放

> 在核内性能分析的基于区域的计时场景中，主要挑战是性能分析指令引起的扰动。

后处理技术（如定期采样[21]）通常用于通过定期采样性能指标并随后汇总结果来减少数据收集相关的开销。在基于区域的计时工具中，:mdnice-bold-italic[我们提出一种类似的后处理方法——跟踪重放]，**借助 KPerfIR 的设计，根据程序语义重新调整性能分析区域**。通过抵消时钟测量开销的常量，我们可以使用这种跟踪重放机制获得准确的可视化结果。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/15.webp)

**对于仅包含同步指令的区域，我们可以通过减去记录操作的开销轻松重建区域**。对于异步指令，如图 10 所示存在两种常见的不准确性。在普通执行时间线示例中，在 Tensor Core 上发出异步 MMA 操作后，会执行一系列连续指令。程序到达指令流中的屏障后，在功能单元产生结果之前会有一段等待时间。为了理解此处的异步行为，用户可以在连续执行中插入性能分析记录以更好地对齐操作。然而，此类记录的引入会导致等待时间测量不准确。在减少空转的情况下，由于性能分析带来的额外开销，等待时间被低估。在意外空闲的情况下，情况更糟，功能单元的执行时间无法覆盖性能分析开销，会观察到意外的空闲时间，从而误导优化。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/15.webp)

为解决此问题，我们提出在图 10-（b）所示的跟踪重放过程中减去准确的等待时间。我们不在异步指令之后放置一个 END 记录，而是在异步启动之前和等待屏障之后插入两个 START 记录，并在屏障之前插入一个 END 记录。这确保准确的等待时间 $T_{wait}$ 测量为 $T_{wait}=(CLK_2-T_a)-(CLK_1-T_a)=CLK_2 - CLK_1$，其中 $T_a$ 和 $T_b$ 分别是时钟读取指令前后记录区域的经过时间。**通过精心放置的两个记录，在后期处理中抵消了性能分析开销。我们可以类似地推导 $T_{exe}$ 时间**。:mdnice-bold-italic[这种方法要求 $T_{MMA}-T_{exe}>T_a + T_b$。] 如第 6.4 节所示，大多数情况下性能分析开销少于 25 个周期，功能单元的执行时间通常约为 1000 个周期，足以覆盖此处插入的记录。

## 六、评估

在本节中，我们评估所设计的基于区域的计时工具和 KPerfIR 方法的性能。

### 6.1 实验设置

**测试平台**：KPerfIR 的评估在配备最先进 GPU 卡的服务器上进行，包括 NVIDIA H100-HBM3 和 AMD MI300X。软件环境包括 Triton 3.0.0 和 LLVM 19.1，确保与最新的编译器技术和 GPU 架构兼容。

**基准测试**：为评估所提出工具的可用性和性能，我们在关键 AI 工作负载上进行了基准测试，特别是 :mdnice-bold-italic[GEMM[36]和 Triton 的实验性 Flash Attention 算子] [29]。这些算子是流行 AI 模型的基础，代表了训练和推理等任务中的大部分工作负载。我们选择了这些算子的主流实现（具有最先进的性能），并进行了敏感性实验以评估该方法的有效性和可扩展性。

### 6.2 Flash-Attention 3 的优化 pass

#### 6.2.2 GPU 重叠的性能建模

然后，我们展示如何采用所提出的编译器中心性能分析器设计来构建编译器 pass ，以:mdnice-bold-italic[确定最佳重叠设计]。这是通过**利用性能分析结果提取 FA3 核函数的关键路径，并使用重叠性能模型计算工作负载的利用率来实现的。**

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/18.webp)

表 4 概述了性能模型，:mdnice-bold-italic[重点关注计算和数据加载阶段]，同时简化了不太相关的方面（如初始化、尾声和整体核函数性能），这些在先前的工作中已得到广泛研究[22]。:mdnice-bold-italic[我们强调了重叠技术建模的非平凡部分。]

- 对于 SWP 模型，判别式 Δ 决定瓶颈在于数据加载还是计算。如果 $\Delta≥0$，则数据加载延迟被计算完全重叠，总延迟对应所有阶段的累积计算时间。相反，如果 $\Delta<0$，则延迟由最耗时的加载和计算阶段决定。

使用该模型，我们可以定量评估 FA3 核函数的重叠效率。基于区域的性能分析器收集详细的性能数据，使我们能够分析当前实现并改进重叠设计，以最小化延迟并提高资源利用率。例如，对于头维度为 128、头数为 16、批大小为 16 和序列长度为 4096 的注意力核函数，2 阶段 SWP 计算得 467.07 TFLOPs，原始 Triton FA3 达到 526.97 TFLOPs。通过整合优化 pass ，我们可以调整具有改进重叠的 FA3 核函数，实现 582.44 的预测 TFLOPs。

### 6.3 性能分析开销

> 我们从延迟和内存消耗两方面评估所提出的基于区域的计时工具的性能分析开销。特别关注共享内存使用，这是 GPU 工作负载性能工具设计中的关键瓶颈。

我们对具有 SWP 设计（分为 2 或 3 个阶段，标记为 GEMM-SWP-2/3）的最先进 GEMM 算子，以及具有原始重叠和基于性能分析见解的改进版本的 WS FA3 算子（标记为 FA3-WS-a/b）进行了基准测试。

#### 延迟开销

我们测量了插桩核函数的端到端延迟，并将结果归一化为其原始执行时间。图 13 展示了评估基准测试的延迟开销。在**大多数情况下，开销保持在 10%以下**，确保所提出的工具在实际场景中实用，不会显著影响核函数性能。对于**最复杂的 3 阶段 SWP GEMM 核函数**，我们插入了许多记录以覆盖其三个阶段。即使在这种情况下，开销也**保持在 15%以内**。这种最小的延迟影响对于启用实时性能分析和在优化工作流中保持生产级吞吐量至关重要。

#### 共享内存开销

如第 5.2 节所述，所提出的计时工具采用循环缓冲区设计，将最近的性能分析记录存储在 GPU 上有限的共享内存中。这种方法确保了与各种工作负载的兼容性（无论可用共享内存的大小如何），同时还允许灵活调整性能分析生命周期。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/21.webp)

图 14 展示了基准工作负载的共享内存使用情况。在本实验中，循环缓冲区大小设置为最大化可用共享内存空间或容纳工作负载的所有性能分析记录。结果表明，**该工具在共享内存约束下有效运行**，即使对于工业级核函数也是如此，**不会将性能分析记录溢出到外部内存**。

例如，在存储最密集的 3 阶段 SWP GEMM 核函数中，仍有 10.9 KB 的未使用共享内存空间。对于 4 个性能分析区域，计时工具可以跟踪多达 16 次迭代，提供足够稳定的覆盖范围来估计整个执行过程。:mdnice-bold-italic[这种高效的内存使用凸显了该工具对大规模 GPU 工作负载的适用性]。

### 6.4 低级深入分析

为了实证分析 KPerfIR 引入的优化性能下降，我们检查了其在低级指令级的影响。具体而言，我们识别了由 IR 级性能分析生成的插桩指令，并将其与原始对应指令进行比较，以评估性能分析 IR 如何影响编译栈。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/22.webp)

:mdnice-bold-italic[周期级开销]：在 GPU 汇编代码级（SASS ISA），每个 KPerfIR 记录节点被 lowering 为三条指令：时钟读取指令、整数移动指令和谓词存储指令。如图 15 所示，这些指令总共产生平均 33 个周期的开销。这种延迟代表了我们敏感性分析中观察到的每条记录的性能分析开销。对于基于循环的计时（性能分析记录插入到循环结构中），在循环入口会生成五条额外指令用于索引管理。每条性能分析记录的指令保持三条，其目的地根据循环迭代变量动态调整。

:mdnice-bold-italic[优化性能下降]：我们分析中的一个关键观察结果是，**性能分析插桩可能会干扰编译器的低级优化，如指令重排序和常量折叠**。如第 4 节所述，:mdnice-bold-italic[在 IR 级集成性能分析语义本质] 上是以一些**低级控制为代价，换取更好的工具可移植性和兼容性**。这种权衡在性能分析指令与相邻非性能分析指令交互时，可能引入意外的指令重排序风险。

为研究这种影响，我们将插桩核函数的理论执行时间建模为：

$$
T_{theoretical}=T_{vanilla}+N_{record}*Cycle_{record}. (1)
$$

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/22.webp)

其中 $N_{record}$ 是插桩记录的数量，周期数如图 15 所示。使用该模型，我们将理论执行时间与插桩工作负载的实际性能进行比较，以评估性能分析插桩引起的偏差。

![文章插图](/articles/2025-07-22-kperfir-triton-gpu-8-2-5104c07c/images/23.webp)

表 5 中的结果表明，**性能影响保持在 2%以内**。这表明:mdnice-bold-italic[编译器 IR 级的性能分析插桩引入的开销最小，同时保持了与编译器优化的兼容性]。这些发现凸显了所提出方法的实用性，确保准确的性能分析而不会导致显著的性能下降。

## 七、结果讨论

### 局限性

我们方法的一个:mdnice-bold-italic[局限性源于对某些厂商特定性能计数器的可见性受限]。由于 KPerfIR 直接在程序中插入性能分析指令以收集运行时信息，**可访问的指标集受厂商 ISA 的限制**。相比之下，厂商提供的工具（如 NVIDIA 的 Nsight Compute (NCU)和 AMD 的 ROCm 工具（如 ATT））具有对未向第三方开发者公开的未记录性能寄存器的特权访问。

这些**专有计数器只能通过其官方 API 或库** 使用。虽然我们的基础设施在原始计数器访问方面可能无法与这些工具完全媲美，但*我们的 IR 级插桩能够提供封闭源性能分析器难以获得的独特程序行为见解*。

### 工作负载通用性

- :mdnice-bold-italic[超越 AI 工作负载]：虽然 KPerfIR 目前通过与 Triton 编译器的集成针对 AI 工作负载，但我们方法**背后的核心思想（即用于性能工具的多级 IR 和转换 pass ）具有广泛的适用性**。这些技术可以推广到其他领域和编译器，如高性能计算（HPC）[39]或科学模拟[24]中使用的那些。
- :mdnice-bold-italic[分布式工作负载]：**KPerfIR 也适用于分布式 GPU 工作负载** [49,50]，这些工作负载通常结构为一系列涉及计算和通信的核函数。对于分别启动计算和通信核函数的工作负载，KPerfIR 已经提供了原生支持。**对于计算和通信融合在单个核函数中的融合核函数[12,37]，KPerfIR 理论上也可以插桩和分析它们**。然而，完全集成取决于上游扩展 Triton 对这种融合分布式执行的支持的持续努力。

## 八、结论

> 随着 AI 编译器和 GPU 架构的不断发展，性能工具也必须进步以满足现代编译器不断增长的需求。

::: block-1
为满足这一需求，我们引入了 KPerfIR，这是一种**基于 Triton 编译器的新型编译器中心性能分析基础设施**。

:mdnice-bold-italic[KPerfIR 弥合了编译器和性能分析器设计之间的差距]，支持可编程、可重用工具的开发，并**为性能分析和编译器优化开辟了新的可能性。**
:::

我们设想 KPerfIR 作为开放的、编译器中心生态系统的基础，使社区能够**构建适应 AI 工作负载动态需求的多样化和创新性能工具**。
