> LLM 的输出仅引导搜索方向，而不定义任何可执行行为。

## 一、推理优化的两难：编译器不够“聪明”，LLM 不够“靠谱”

> 过去十年，**AI 编译器的发展始终沿着“确定性规则+启发式搜索”的路径前进**，从 TVM 到 MLIR，从 Triton 到 torch.compile，我们不断:mdnice-bold-italic[把更多优化逻辑固化到流水线里，却始终无法解决一个核心矛盾：编译器能保证正确，却很难做出精准的语义决策。]

面对 Transformer 这种结构高度重复、但不同区域优化价值天差地别的计算图，传统编译器的规则引擎总会遇到瓶颈。它能识别出 MatMul、Softmax、Norm 这些基础算子，也能做简单的算子融合，**但面对混合了归约、逐点运算、复杂尾操作的子图，它很难判断“这个区域值不值得花成本做专用内核”，也不知道“在十几种候选实现里，哪几种最有可能跑出最优性能”。**

### 1.1 现有推理优化路径的天花板

> 当前主流的 Transformer 推理优化方案，分别在不同层级解决问题，但都有各自的能力天花板。

**首先是 PyTorch Eager 模式**。作为最通用的推理方式，它保留了完整的 Python 调度逻辑、动态缓存管理机制，但代价是极高的 per-token 开销。:mdnice-bold-italic[自回归解码的每一步，都要经历 Python 层的算子分发、内核启动、动态 KV 缓存更新，大量时间都浪费在了计算之外的调度开销上]，尤其是长序列生成场景，这种开销会被不断放大。

**其次是 torch.compile 方案**。它通过 Inductor 将计算图编译成融合内核，减少了框架调度与内核启动开销，在短输入短输出场景下效果显著。但随着输入长度增加，计算与 KV 缓存流量逐渐占据运行时主体，融合能消除的开销占比越来越小；同时动态缓存更新、形状变化、图断裂会导致频繁重编译，进一步抵消优化收益。:mdnice-bold-italic[论文数据显示，在输入 20480、输出 16384 的长序列场景下，Qwen3-4B 的 torch.compile 性能甚至不如原生 Eager 模式，加速比仅为 0.8 倍。]

**第三类是 vLLM 这类服务导向的推理运行时**。它们的核心优化集中在服务层：通过 PagedAttention 实现分页 KV 缓存管理，通过请求调度提升批量吞吐，本质解决的是多请求高并发场景的服务效率问题，和算子级、区域级的内核专用化优化是完全互补的关系，而非替代关系。

### 1.2 LLM 直接生成 CUDA 的本质风险

既然传统编译器不够“智能”，能否让大模型（LLM）直接写 CUDA 内核？近两年热度很高，但工业界几乎无人落地，主因是**正确性无法保障**。

CUDA 内核对细节极度敏感：索引需严丝合缝匹配张量布局，线程同步须覆盖所有并行路径，内存访问严禁越界，类型转换需控精度，启动参数要合硬件限制，内存假设须与 I/O 完全对齐。任一疏漏，轻则数值错误，重则显存崩溃。

而 LLM 生成的代码常“看似合理”，却隐含边界错误——肉眼难察，测试难尽。对推理服务而言，**结果正确是底线**；性能再高，出错即归零。正因如此，“LLM 写 CUDA”至今仍停留于实验与玩具阶段。

::: block-1
传统 AI 编译器强于确定性与正确性，但缺乏对计算图的语义级判断能力；LLM 擅长语义理解与优先级排序，但无法保障生成代码的正确性与可靠性。:mdnice-highlight[AgentCompile 的核心价值，正是找到了两者能力互补的协作边界。]
:::

## 二、AgentCompile 核心设计：LLM 做顾问，编译器掌实权

> AgentCompile 的整个设计，都围绕一个核心契约展开：**LLM 永远只提供“建议性元数据”，所有和可执行行为相关的决策，全部由编译器完成**。:mdnice-bold-italic[LLM 可以猜、可以排优先级、可以给提示，但永远不能直接生成代码，也不能直接决定哪个内核最终被使用。]

这个设计从根源上规避了 LLM 生成代码的正确性风险，同时又把 LLM 的语义能力用在了刀刃上。

### 2.1 核心问题的形式化定义

> 论文首先将整个优化问题做了严谨的形式化定义，为后续的流水线设计奠定了理论基础。

首先，**推理程序被建模为有向图**$G=(V, E)$，其中 $V$ 代表张量操作节点，$E$ 代表节点之间的数据依赖边。一个区域 $r$ 是图中的一个连通子图，它有明确的外部接口定义：输入张量、输出张量、边界依赖、数据类型与布局假设、归约轴、调用约定。一个 CUDA 替换方案只有完全符合这个接口，并且通过完整的验证协议，才允许被采纳。

对于每个区域 $r$ 和目标硬件/运行时配置 $H$，编译器会首先构建一个**有界可执行候选空间**$C(r, H)$。这个空间里的每一个候选，都对应一个确定的实现族和可落地的参数集合，包括融合边界、模板类型、分块大小、线程数、向量化宽度、归约映射、共享内存策略、启动接口等。

这个候选空间的生成是完全确定性的：由区域提取规则、可用模板库、张量元数据、硬件约束共同决定。:mdnice-bold-italic[LLM 只能在这个空间内对候选进行排序、提供参数建议]，绝对不能创造空间外的候选，也不能绕过编译器的约束检查。

### 2.2 LLM 的角色：仅提供四类建议元数据

> LLM 在整个流程中看不到原始源代码，只能拿到编译器生成的结构化区域摘要 $S(r)$，然后输出四类建议性的元数据，公式表达如下：

$$
\mathcal {A}_{LLM}(S(r),\mathcal {C}(r,H))=(\ell _{r},\pi _{r},\eta _{r},\rho _{r})
$$

公式中四个变量的含义非常明确：

- $\ell_{r}$ 是语义标签，比如 LLM 判断这个区域属于 RMSNorm 模式、带尾操作的 GEMM 模式，用来辅助编译器判断优化方向
- $\pi_{r}$ 是候选偏好排序，也就是 LLM 认为候选空间里，哪些实现方案更有可能跑出最优性能
- $\eta_{r}$ 是参数提示，比如建议向量化宽度设为多少、每个线程块分配多少线程、循环展开因子取多大
- $\rho_{r}$ 是风险标注，比如 LLM 认为某个候选可能存在兼容性问题、数值稳定性风险

所有这些输出，都只会被编译器当作“假设”来处理。不支持的语义标签直接丢弃，违反约束的融合方案直接拒绝，无效的参数建议直接忽略，超出候选空间的建议直接无视。**LLM 的所有输出，都没有强制执行的权力。**

### 2.3 验证与选型：实测性能说了算

> 候选内核的准入与最终选型，完全由编译器通过确定性流程完成，和 LLM 的置信度没有任何关系。

- 如果存在参考实现路径，编译器会做对应数据类型精度下的数值对比，误差在容差范围内才算通过验证；
- 如果没有参考路径，就通过结构测试、冒烟测试、端到端一致性检查来验证。

这是基于实测的经验性验证，而非形式化的等价证明。

在所有通过验证的候选集合 $V(r)$ 中，编译器会通过实测延迟选择最优方案：

$$
c^{*}=\arg min _{c \in V(r)} T(c)
$$

其中 $T(c)$ 代表候选内核的实测延迟。如果没有任何候选通过验证，或者所有候选的性能都不如原始框架路径，区域就会直接回退到原生框架或库实现，不会强行使用优化方案。

::: block-1
:mdnice-highlight[AgentCompile 的核心设计契约，是将 LLM 的角色从“代码生产者”降级为“搜索顾问”]。**LLM 仅在编译器划定的安全边界内提供语义级建议**，所有候选生成、约束检查、数值验证、性能选型与失败回退均由编译器确定性执行，从架构上守住了正确性底线。
:::

> AgentCompile 将整个编译流程拆分为三大阶段、八个子步骤，形成了一套“捕获-分析生成-验证发射”的完整闭环。整套流水线里，只有候选排序和语义标注这两个环节用到了 LLM，其余所有步骤都是确定性的编译器逻辑。

### 3.1 模型捕获阶段

> 模型捕获是整个流水线的入口，属于行业通用的成熟方案。它读取目标模型代码，通过示例输入对计算图进行追踪，得到包含张量形状、数据类型、内存布局、依赖元数据的追踪图，最终构建标准化的统一 IR 表示。

前端基于 torch.fx 实现图捕获，和 PyTorch 生态原生兼容，支持单文件模块、项目目录、HuggingFace 模型 ID 等多种输入形式。IR 构建阶段会统一算子命名，同时记录每个算子的数值契约，比如 Softmax 和 Norm 的精确行为、归约与矩阵乘的结合性、逐点运算的精度松弛规则，为后续的区域划分与代码生成提供准确的语义依据。

### 3.2 图分析器：确定性区域构建

> 在调用 LLM 之前，分析器会先完成计算图的区域划分，从根源上划定优化的边界。

**分析器首先构建完整的 use-def 依赖链，然后拓扑遍历整个 IR**。对于占位符、模型属性访问、view、reshape、连续化转换、转置、广播、切片这类非计算、仅布局调整的节点，不会单独作为优化区域，要么作为边界元数据处理，要么在安全的前提下附加到附近的计算区域。

**连续的逐点运算、激活函数、Softmax、归一化、归约节点，只要数据类型和内存布局兼容，就可以合并为同一个优化区域**。矩阵乘节点通常独立成区，但如果存在简单的尾操作，且依赖与接口约束允许，也可以附加到矩阵乘区域中。:mdnice-bold-italic[原地操作、副作用、未解决的内存别名、不支持的数据类型、模糊的动态形状，则会被作为硬边界，禁止跨区域融合。]

::: block-1
每个确认的区域，都会被记录完整的元数据：算子序列、张量形状、数据类型与累加类型、归约轴、主导操作类型、内存访问模式、估算的 FLOPs 与字节访问量、算术强度、动态形状标记。随后分析器会通过规则做第一轮语义分类，标记出 GEMM 区域、带尾操作的 GEMM 区域、类 Softmax 区域、类 RMSNorm 区域、逐点运算链、归约加逐点运算等类型。
:::

**LLM 只会在规则无法明确分类的场景下被调用**，比如混合区域、复杂 GEMM 尾操作、归约-逐点混合区域，且只有区域规模足够大、值得做语义分析时才会触发。:mdnice-bold-italic[LLM 的语义标签只能优化候选优先级与风险标注，绝对不能修改区域边界]，所有边界都必须经过确定性的依赖、别名、副作用检查才能确认。

### 3.3 确定性 CUDA 规划器

> 规划器的核心原则，是绝对不让 LLM 凭空发明实现方案。它会先将每个区域转换为一个有界的内核计划集合，LLM 只能在这个集合内进行排序和参数建议。

规划器通过四个子模块生成所有合法的设计选项组合：

| 子模块 | 功能说明 |
| --- | --- |
| 融合规划器 | 根据区域大小、副作用、数据类型一致性、布局兼容性，在单内核执行、全融合、不融合、部分融合四种方案中枚举合法选项 |
| 调度规划器 | 将识别出的计算模式映射到对应模板族，包括分块 GEMM、Tensor Core GEMM、行级 Softmax、块/warp 归约、行级归一化、网格逐点内核、面向解码的 GEMV |
| 内存规划器 | 配置共享内存策略、内存访问模式、向量化宽度等参数 |
| 并行规划器 | 配置网格/块形状、warp 映射、归约策略等并行参数 |

**生成所有计划后，编译器会先执行一轮硬约束过滤**：共享内存用量不能超过硬件上限、线程数符合硬件限制、向量化对齐满足要求、归约语义匹配、存在对应模板、启动签名与区域接口兼容，不符合的计划直接被淘汰。

**剩余的有效计划，首先通过确定性启发式规则排序**，排序依据包括融合收益、向量化程度、预估硬件占用率、模板匹配度、风险等级。**只有高价值区域，才会将结构化的候选摘要发送给 LLM**，让 LLM 对靠前的候选重新排序，或提供向量化宽度、块线程数、展开因子等参数建议。

LLM 的所有建议都必须经过二次校验：参数必须属于已枚举的计划空间，否则直接拒绝；同时通过多样性过滤机制，尽量保留多个不同的模板族，避免 LLM 的偏好导致候选单一化。

### 3.4 CUDA 代码生成与验证选型

> **代码生成器** 通过确定性的模板库，**将通过检查的内核计划实例化为真正的 CUDA 代码**。模板库覆盖了向量化逐点内核、归约内核、数值稳定的 Softmax、LayerNorm/RMSNorm 归一化、分块 GEMM、适配对应架构的 Tensor Core GEMM、面向解码的 GEMV 等主流实现。

**所有与执行正确性相关的细节**，包括索引计算、边界检查、数据类型转换、线程同步、共享内存布局、内核启动签名，**全部固化在模板中，LLM 完全无法触碰**。:mdnice-bold-italic[LLM 最多可以提供模板偏好建议，或者在编译失败后提供诊断提示]，但源代码的生成全程处于编译器的控制之下。

其中针对自回归解码场景定制的 GEMV 内核，是整个系统最核心的优化点之一。解码阶段每个 step 的有效 batch size 为 1，矩阵乘本质上退化为矩阵乘向量运算，使用通用 GEMM 内核会引入大量不必要的开销。

AgentCompile 生成的 GEMV 内核，将权重存储为[N, K]布局，使每个输出列读取连续的权重行；每个块分配 256 个线程执行归约，地址对齐时启用 128 位向量化加载；部分和通过 warp shuffle 指令完成归约，而非传统的共享内存树，既避免了共享内存 bank 冲突，又减少了同步开销。同时采用双路径自适应 N 策略，在输出维度 N 较大时调整并行度，保证 SM 上有足够的常驻线程块。:mdnice-bold-italic[和通用 GEMM 路径相比，这套专用实现移除了冗余的 GEMM 机制与布局处理，完美匹配解码阶段低算术强度、单行输入的工作负载特征。]

> 生成的候选内核需要经过完整的准入流水线：

1. 编译失败的候选直接淘汰
2. 接口检查验证张量形状、数据类型、内存布局、启动签名的兼容性
3. 存在参考路径的候选，执行数值一致性检查，误差控制在对应精度的容差范围内
4. 无参考路径的辅助内核，通过结构测试、冒烟测试与端到端一致性检查验证
5. 可选开启内存安全检测工具

所有通过验证的候选，都会在固定的预热与重复测试协议下实测延迟，每个区域选择延迟最低的内核作为最终方案。整个选型过程完全以实测性能为唯一标准，LLM 的置信度不会对结果产生任何影响。如果没有有效候选，或所有候选都不如原始路径，就直接回退到框架原生实现。

![文章插图](/articles/2026-07-19-vllm-7-agentcompile-llm-f01d0ed5/images/06.webp)

::: image-caption
算法 1：编译器控制的LLM候选搜索流程。算法完整呈现了AgentCompile的核心执行逻辑：先捕获模型图并构建标准化IR，再按规则将IR划分为多个区域；对每个区域，先生成结构化摘要与有界候选空间，再查询LLM获取建议元数据；所有建议必须经过编译器检查，无效内容直接拒绝；仅通过检查的候选才会实例化、编译、验证与跑分；最终选择最快的有效候选，无有效候选则回退到原框架路径。整个流程中LLM仅影响搜索顺序与风险标注，绝不直接生成或准入可执行CUDA代码。

### 3.5 混合运行时的集成边界

> 端到端推理性能的提升，并非全部来自编译器生成的内核，而是**一套混合运行时共同作用的结果**。论文特意明确了三类内核的边界，避免混淆优化贡献：

- 流水线生成内核：由编译器流水线生成的内核，是 LLM 引导编译的核心成果
- 运行时集成内核：手写实现的 Triton 或 C++扩展内核，用于消除常见的解码开销
- 第三方内核：FlashAttention、cuBLAS 等成熟的第三方库内核，提供基础性能底座

只有第一类内核属于编译器生成的成果，后两类用于构建具备竞争力的端到端解码运行时，是性能对比的基础环境。

其中手写的融合运行时内核，**针对解码阶段频繁出现、但不一定能被编译器识别为单个区域的操作进行优化**：融合 RoPE 内核在一次 Triton 启动中完成 Q 和 K 的旋转位置编码；融合残差-RMSNorm 内核将残差相加与归一化合二为一，使用 float32 做累加；融合激活乘内核覆盖 MLP 门控路径；C++扩展还提供了带 SiLU/GELU 的 Gate/Up GEMV、带残差相加的 Down 投影 GEMV 等融合尾操作。

**自定义的 CUDALinear 模块，替换了解码路径中的 PyTorch nn.Linear 层，通过 ctypes 或 C++扩展调度到自定义 CUDA GEMM/GEMV 内核**。模块在初始化阶段就完成权重转置，单 token 解码时自动选择 M=1 的 GEMV 路径，预填充或 CUDA Graph 捕获场景下回退到 cuBLAS。C++扩展路径可以进一步减少 Python 侧的调度开销，实现与混合运行时的深度集成。

KV 缓存管理则通过 FlashKVCacheManager 实现，它预分配固定大小的 K/V 缓冲区，在 GPU 端跟踪每层的序列长度，兼容 HuggingFace DynamicCache 的预填充状态，提供重置与长度更新接口。实际的注意力计算与 KV 原地追加，仍然通过 FlashAttention 的 KV 缓存更新 API 完成，管理器只负责缓冲区生命周期与有效长度元数据管理，充分复用成熟的第三方内核。

以 Qwen3-1.7B 为例，模型共 28 层 Transformer，每层包含 7 个投影层，单步解码就有 196 次潜在的 GEMV 调用。开启融合尾操作扩展后，4 个注意力投影继续使用生成的 GEMV 路径，3 个 MLP 投影使用融合运行时内核，两者占比约为 57%与 43%，这是组件数量的占比，而非性能贡献的占比。

::: block-1
:mdnice-highlight[AgentCompile 的流水线设计，本质是将 LLM 的能力严格限定在“非关键路径的语义优化”环节]。**所有影响正确性、可执行性、最终选型的核心环节，全部由确定性编译器逻辑把控**。这种“LLM 做启发式增强、编译器做确定性兜底”的架构，是其能够走向工业落地的核心前提。
:::

## 四、性能实测：5.66 倍提速背后的贡献拆解

> 所有的设计最终都要靠性能说话。AgentCompile 的实验分为两个层面：

- 编译器流水线层面，验证区域划分、候选生成、验证选型的完整流程是否通顺；
- 端到端自回归生成层面，和业界主流方案做横向对比，同时做逐层消融，搞清楚每一部分到底贡献了多少性能。

实验基于 NVIDIA A800 SXM4 80GB GPU 执行，软件栈包含 HuggingFace Transformers、FlashAttention-2、Triton、vLLM，以及生成内核对应的 CUDA 编译环境。测试模型为 fp16 精度的 Llama-3.2-1B-Instruct、Llama-3.2-3B-Instruct、Qwen3-1.7B、Qwen3-4B，覆盖输入长度 128 到 40960、输出长度 32 到 32768 的典型场景。

延迟统计包含预填充与解码阶段，排除缓存分配、注意力补丁加载、扩展加载、预热、CUDA Graph 捕获等一次性准备开销。测试采用 2 轮预热、10 轮实测的协议，取平均延迟作为最终结果。

### 4.2 与 vLLM 的对比与定位说明

> AgentCompile 与 vLLM 的对比需要谨慎解读，因为两者优化的是推理栈中完全不同且相互独立的层级，并非互斥的竞争关系。

vLLM 是面向服务的运行时，核心聚焦分页 KV 缓存管理、请求调度、生产级批量解码执行；而 AgentCompile 聚焦编译器选型内核、融合解码组件、自定义 KV 缓存缓冲区、单请求场景的 CUDA Graph 重放。**两者的优化方向完全互补，理论上 AgentCompile 的编译生成内核与融合内核，完全可以集成到 vLLM 这类服务级框架中，实现进一步的性能提升。**

> 论文通过 Qwen3-4B 的逐步消融实验，清晰拆解了每个组件的性能贡献，完整还原了 4.05 倍平均加速的构成。

2. 加入 CUDALinear 与自定义 GEMV 内核，平均提速 1.45 倍，主要消除了框架调度与动态缓存管理的开销

5. 最后加入 LLM 辅助编译路径与手写融合内核，在 CUDA Graph 基础上再提速 1.33 倍，最终完整系统实现 4.05 倍的平均加速

论文特别强调，:mdnice-bold-italic[最后一步的 1.33 倍加速，是 LLM 引导的候选搜索、生成 GEMV 内核、手写融合内核三者的联合贡献，而非 LLM 引导的孤立收益]。论文没有刻意夸大 LLM 的作用，而是如实呈现了全系统的叠加效果，态度非常严谨。

| 场景覆盖局限 | 当前 AgentCompile 主要优化 Transformer 风格推理区域，不支持的算子与区域直接回退至原生框架；虽 Transformer 为主流，但多模态模型、扩散模型及新型算子将持续涌现，需持续扩展模板库、区域划分规则与调度策略 | 持续扩充模板库，动态适配新型模型结构与算子，增强区域划分与调度策略的泛化能力 |
| LLM 作用边界与收益 | 当前消融实验中，LLM 引导收益与融合内核、GEMV 内核生成收益耦合，未分离 LLM 本身的独立贡献 | 开展细粒度消融实验，对比纯确定性启发式排序与 LLM 引导排序在性能与搜索效率上的差异，量化 LLM 的边际增益 |
| 候选空间扩展性 | 候选空间完全依赖现有模板库生成，LLM 仅能在有限模板与参数范围内提供建议；若最优实现不在候选空间内，LLM 无法发挥作用 | 丰富模板库覆盖范围，引入可组合、可参数化的模板结构，提升候选空间的表达能力与搜索广度 |

未来的发展方向上，论文也明确提到，**会持续探索更精细、更高效的 CUDA 内核模板**，进一步提升生成内核的性能上限；同时扩展支持更多模型架构与硬件平台，适配更丰富的部署场景。:mdnice-bold-italic[甚至可以将这种“LLM 做语义引导、编译器做确定性兜底”的设计思路，扩展到训练优化、跨平台编译、异构计算调度等更广泛的基础软件领域。]
