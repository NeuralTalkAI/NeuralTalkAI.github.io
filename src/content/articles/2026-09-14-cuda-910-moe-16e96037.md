## 一、研究背景：CUDA 垄断下的替代加速器现实

> CUDA 生态在大模型推理领域的统治地位，使得 GPU 供应、成本和采购约束成为很多团队的现实瓶颈。华为昇腾系列及其 CANN 软件栈，是目前成熟度最高的非 GPU 替代方案之一。

纸面参数上，16 卡昇腾 910 单机拥有足够的显存和互连带宽，可以托管前沿级别的 MoE 模型和多模态模型。**vLLM 这样的主流推理引擎也已经有了厂商维护的昇腾移植版本。但从 CUDA 基线迁移一个非平凡的推理负载，远不是重新编译一下就能搞定的事。**

### 1.1 呃！说说本文的独特视角

> 已有的大模型系统研究大多集中在推理引擎本身的算法创新——PagedAttention、连续批处理、FlashAttention、投机解码这些。**但很少有人研究当这些成熟技术被移植到非 GPU 架构上时，到底会发生什么。**

这篇论文的贡献有三个层面。

| 本文贡献 | 说明 |
| --- | --- |
| 结构化的问题分类 | 将昇腾平台上部署大 MoE 和多模态模型遇到的问题划分为八大类，每类均按“症状 → 证据 → 根因”逻辑展开，确保问题定位路径清晰、可追溯。 |
| 第一手的平台级证据 | 涵盖设备故障码、内核异常字符串、引擎日志片段等原始诊断信息，同时包含集成工作量、并发行为表现、端到端基准质量等可量化指标，支撑问题分析与验证。 |
| 通用替代加速器采纳策略 | 提出一套不绑定特定厂商的加速器迁移与适配方法论，覆盖正确性保证（如算子一致性验证）、容量规划（如显存与带宽预估）、容错机制（如任务重试与降级策略）、生态参与（如开源贡献与标准对齐）四大维度。 |

### 1.2 研究范围与边界

> 需要明确的是，这是一项定性的实地研究，带有配套的运维和基准测量数据。:mdnice-bold-italic[研究者关注的是硬件/软件平台本身。两个负载的作用仅仅是证明部署是真实的、结果是正确的，研究者并没有声称他们打的补丁是标准修复方案。😅]

论文中记录的所有限制，都是加速器本身、其编译器和算子库、以及厂商推理插件的属性，研究者预期这些问题会泛化到他们跑的特定模型之外，毕竟这是**整个非 CUDA 生态成熟度的问题。**

### 2.1 负载 A：LLM-as-a-judge 价值观与安全评估服务

> **第一个负载是一个离线批处理推理流水线，用大语言模型作为评判者。** 评判模型是 DeepSeek-V4-Flash-w8a8-mtp，通过 OpenAI 兼容的接口提供服务，给 20 个大模型的回答打分——包括 GPT-5.1、Gemini 3 Pro、Claude Haiku 4.5、DeepSeek-V3.2、Qwen3-Max、GLM-4.6、Kimi-K2、豆包、文心一言、混元、Mistral Large、Llama-4 Scout 等。

评判维度是价值观对齐和安全性。对于每一个（问题，回答）对，评判模型应用一个加权评分规则（每个问题的特定标准加上通用扣分项），输出一个结构化的 JSON 裁决和最终分数。整个评测活动每个模型覆盖数万条 prompt，这使得**持续吞吐量和可靠性成为硬约束，延迟反而不重要。这个负载是论文中并发和可靠性结论的主要来源。**

### 2.2 负载 B：多模态医学视觉语言模型

> **第二个负载部署的是 DeepSeek-V4-Flash-Vision，这是一个多模态模型**，通过一个训练过的合并器（merger）和残差 MLP 桥接层，把冻结的 Qwen3.5 视觉塔和冻结的 DeepSeek-V4-Flash MoE 解码器融合在一起。

### 2.3 显存预算为什么迫使多轴并行

> 如果要理解为什么必须用 $TP=8 \times PP=2$，而不是更简单的并行策略，需要看单卡显存占用。

![文章插图](/articles/2026-09-14-cuda-910-moe-16e96037/images/06.jpg)

::: image-caption
图 3：约540GB bf16多模态负载切分到16张昇腾910设备上的单卡显存占用（$TP=8 \times PP=2$）。这张图解释了一个很多人忽略的现实：大模型推理的显存瓶颈首先是权重，不是KV缓存，当你连放权重都快放不下的时候，任何额外的显存开销都会成为致命问题。具体来说，每张卡承载约34GB解码器分片加上约2GB复制的视觉塔，剩下约59GB工作预算（64GB的0.92）给KV缓存和激活。巨大的权重占用留下的余量很小，这和5.2节讨论的张量并行上限相互作用。
:::

当然，这张图也反映了一个残酷的现实：:mdnice-bold-italic[540GB 的模型，16 张 64GB 卡，理论总显存是 1024GB，看起来绰绰有余。但实际上 TP=8 之后每张卡要放 34GB 权重，再加上 2GB 视觉塔，留给 KV 缓存和激活的只有 28GB 左右，显存利用率已经到了 92%。这就是为什么任何额外的显存开销——比如图编译捕获的多个 batch size、或者流水线并行的中间缓冲区——都会直接导致 OOM。]

::: block-1
综上，两个负载的选择非常有讲究。精准打击了昇腾栈最脆弱的几个点：专家并行 MoE 路由、稀疏注意力路径、多模态输入流水线、流水线并行、MTP 投机解码、W8A8 量化:mdnice-highlight[。如果只跑一个稠密的 7B 模型，可能什么问题都没有；但前沿模型该有的复杂特性一个都不少的时候，生态成熟度的差距就会以最痛苦的方式暴露出来。]
:::

![文章插图](/articles/2026-09-14-cuda-910-moe-16e96037/images/07.jpg)

::: image-caption
表 2：观察到的限制类别和缓解措施总结。八大类问题，每一类都需要对应的缓解策略。注意看右边一列，没有一个是"升级到新版本就好了"，全部都是需要工程团队自己做的 workaround：启动时打补丁、关闭吞吐量特性、看门狗自动重启、强制eager模式、调整并发到最佳点、钉死版本🤦‍♂️。这就是非GPU加速器的真实工程税。

这八大类问题之间有深刻的内在联系。**不成熟的编译器和算子库是内核故障、图编译限制、低并发上限和慢启动的共同根源。** 多个特性组合覆盖薄———这也解释了并行脆弱性和大部分启动补丁。生产级可靠性和可观测性的缺失，把不可避免的故障变成了宕机。生态碎片化则放大了所有上述问题，让每一个修复都是版本特定的、难以共享的😅。

### 3.1 软件栈成熟度与算子覆盖缺口

> 症状非常直接：不管哪个负载，想跑起来就得先对厂商推理插件打一连串源码级补丁😅，甚至在初始化阶段就会崩，更别说输出正确结果了。**总共在启动时对安装的插件包程序化地应用了 12 个不同的补丁。**

![文章插图](/articles/2026-09-14-cuda-910-moe-16e96037/images/08.jpg)

::: image-caption
图 4：应用到厂商推理插件的12个启动补丁，按源文件分组。worker运行时（model_runner_v1.py）和模型定义（deepseek_v4.py）吸收了大部分修改，反映出流水线并行、多模态、MoE/稀疏注意力路径落在了插件的测试包络之外。7个补丁打在model_runner上，3个打在模型定义上，这说明问题不在边角料，核心执行路径本身就有bug。
:::

> 上述这些补丁覆盖了**加载器、worker 和注意力代码**，解决了多个独立缺陷。

举几个典型例子：

- 一个是流水线并行中每层注意力"sink"权重的保护问题——在不拥有该层的 rank 上直接做字典查找会抛出 KeyError；
- 一个是内存分析的 dummy run 对哈希路由 MoE 走了不一致的嵌入路径；
- 一个是稀疏注意力的 KV 状态和 Hadamard 变换被一个纯文本 model_type 的判断门控住了，导致多模态配置下根本不会分配——结果第一次真正的 prefill（不是启动时）就越界崩溃；
- 还有多模态嵌入合并在每个流水线并行 rank 上都跑，而不是只在第一个 rank 上跑；
- 还有一个持久化的流水线中间张量缓冲区，是用 decode 形状的 dummy run 算的大小，后来 prefill 的时候就不够用了。

**几个缺陷是潜伏的😱**，因为参考的纯文本部署只用单个流水线阶段，所以 $PP>1$ 的代码路径从来没被真正执行过。这是一个非常典型的软件成熟度问题：单个特性可能在 isolation 下工作，但特性的组合从来没被测试过。

::: block-1
:mdnice-highlight[根因在于，厂商插件是一个年纪轻轻😅、快速迭代的重新实现，其测试配置只是上游 vLLM 支持的子集]。**在 CUDA 上很常规的特性组合——流水线并行 × 多模态 × 带稀疏注意力变体的 MoE——落在了测试包络之外**，而覆盖缺口表现为直接崩溃，而不是优雅的回退。
:::

### 3.2 脆弱的多轴并行

> **把单个副本切分到 16 个设备上既受限又脆弱**。:mdnice-bold-italic[两个面向吞吐量的并行特性必须关掉才能得到正确结果，而且张量并行度有硬上限]。研究者用的是标准的张量/流水线/专家并行分解。

先说 TP 上限。注意力头分组因子是 8，这就把张量并行度硬限制在 $TP=8$。想用全部 16 个设备跑一个副本，就必须加第二个轴——bf16 多模态模型用流水线并行（$PP=2$），量化 LLM 用数据并行（$DP=2$）。这个上限不是你能调的，是架构决定的，因为你不能把一个注意力头劈到两个设备上。

然后是序列并行和 FlashComm。开序列并行（通过 FlashComm 路径）会按 TP 度分片隐藏状态，:mdnice-bold-italic[但多模态前向是通过完整尺寸的 inputs_embeds 注入图像嵌入的，分片后的张量和完整尺寸张量就不匹配了（扩展尺寸 N 必须匹配现有尺寸 $N/tp$）。研究者直接把它关了。]

还有融合 MC2 专家路由。融合 MoE 通信核从前向上下文读取 token id，但多模态内存分析的 dummy run 期间没有这些，所以也必须关掉。

**最危险的是流水线并行的正确性问题**。除了 3.1 节提到的崩溃之外，异构计算头的维度在层间的隐藏状态和残差流上，在每个 rank 上都被折叠了，然后在下一个 rank 上又重新展开，这导致网络中间的每个头状态变得完全相同，静默地破坏了输出。:mdnice-bold-italic[修复方案是把完整的多头流传过流水线边界，只在最后一个阶段折叠——这个 bug 只有在 $PP>1$ 的时候才会显现。]

下面这两行环境变量，就是为了正确性牺牲吞吐量的直接证据：

```
export VLLM_ASCEND_ENABLE_FUSED_MC2=0export VLLM_ASCEND_ENABLE_FLASHCOMM1=0
```

- 第一行关掉融合 MC2 专家路由，因为多模态内存分析时没有前向上下文 token id；
- 第二行关掉 FlashComm 序列并行，因为多模态通过完整尺寸 inputs_embeds 注入图像嵌入，分片后的上下文和完整隐藏状态不匹配。

::: block-1
:mdnice-highlight[上面的问题根因在于，并行特性主要是为单模态、单流水线阶段的情况实现和验证的]。它们和多模态输入注入、哈希路由 MoE、稀疏注意力变体的交互非常薄，**所以每增加一个并行轴，未测试代码路径的数量就会指数级增长**。安全的姿态是最小化并行特性，优先正确性而不是相关的吞吐量收益。
:::

### 3.3 内核级数值与稳定性故障

> **在持续负载下，服务会间歇性地因为底层设备执行故障而中止** 😅——包括"aicore"和"vector core"异常——这些会杀死 worker 进程，需要重启。

故障表现为 CANN 内部错误，运行时结果码 507015（aicore）和 507035（vector core），扩展消息指向 MTE 地址违例（"MTE 指令的 DDR 地址越界"）。

下面是 vector core 执行故障的典型日志：

```
RuntimeError: npuSynchronizeDevice: NPU function error:[Error]: The vector core execution is abnormal. AclrtSynchronizeDeviceWithTimeout, error code is 507035EZ9999: Inner Error!there is an exception of aivec error, core id is 21,error code = 0x800000 errorStr: The DDR address of the MTE instruction is out of range.Kernel task happen error, retCode=0x31, [vector core exception]. wait event to be complete failed, runtime result = 507035
```

这是 aicore 执行故障的典型日志：

```
RuntimeError: npuSynchronizeDevice: NPU function error:AclrtSynchronizeDeviceWithTimeout, error code is 507015[Error]: The aicore execution is abnormal. EZ9999: Inner Error!there is an exception of fftsplus aivector error, core id is 9, error code = 0x800000 errorStr: The DDR address of the MTE instruction is out of range.Kernel task happen error, retCode=0x26, [aicore exception]. wait for compute device to finish failed, runtime result = 507015
```

这些是设备抛出的内核内部内存寻址故障，不是应用层异常。因为它们起源于编译后的算子内部，只以不透明的错误码和寄存器转储报告，从服务层基本上无法调试。**它们的间歇性（和负载及特定 shape 相关）指向算子库中的边缘 case，而不是可以隔离的确定性 bug**。

::: block-1
**这是整个论文里最让人后背发凉的部分** 😱。:mdnice-highlight[这些不是你代码的 bug，不是你配置错了，是硬件算子库本身在某些 shape 和负载组合下会直接越界崩溃，而且你完全没法 debug——错误信息只告诉你"core id 21，MTE 地址越界"，不告诉你是哪个算子、哪层、哪个 shape 触发的。你能做的只有重启，然后祈祷下次不要在同一个地方崩。]
:::

### 3.4 不成熟的图编译

> 高性能图执行路径要么不可用，要么带有明确的稳定性警告，所以研究者经常回退到 eager 执行。

在多模态模型上，研究者用 enforce-eager 模式（不做图捕获）来避免捕获时失败。在量化 LLM 上用了 full-decode ACL 图模式，引擎对这个模式输出了明确的实验阶段警告：捕获太多 batch size 会导致 OOM 或推理挂起。引擎还日志记录了这个平台不支持 TorchInductor，所以只有 ACL 图模式可用，decode 路径里没有 JIT 算子融合。

下面是引擎的实际警告：

```
WARNING platform.py] FULL_DECODE_ONLY compilation enabled on NPU.WARNING platform.py] use_inductor not supported - using only ACL Graph mode* WARNING: You have enabled the *full graph* feature.* This is an early experimental stage and may involve various unknown issues.* A known problem is that capturing too many batch sizes can lead to OOM* (Out of Memory) errors or inference hangs. If you encounter such issues,* consider reducing gpu_memory_utilization or manually specifying a smaller* batch size for graph capture.
```

:mdnice-bold-italic[根因在于，图捕获和核编译比 CUDA 对应的版本成熟度低。没有 Inductor 等价的 JIT，未覆盖的 shape 和算子就回退到 eager 模式，而实验性的 full-decode 捕获用稳定性换吞吐量。实际后果就是在可靠但慢的 eager 路径和快但脆弱的捕获路径之间做艰难选择。]

::: block-1
在 CUDA 上，图编译是一个你开了就会变快、而且基本不会出问题的成熟特性。:mdnice-highlight[在昇腾上，这是一个"开了可能变快，也可能 OOM，也可能直接挂死，而且我们警告过你了"的实验特性。]
:::

### 3.5 高级功能缺口

> 在 CUDA 上稳定的高级推理功能，在这里更新也更不可靠，开启它们可能会让服务不稳定。

研究者在量化 LLM 上配置了多token预测（MTP）投机解码，用 1 个投机 token。在这个栈里，这个功能在不同版本间有废弃警告和重命名，而且投机量化设置会被平台静默覆盖。加上 5.3 节的内核故障，**最安全的配置是完全关掉投机解码，用吞吐量收益换可靠性。**

**根因在于，投机解码需要草稿路径、主模型和调度器之间的紧密协调；在一个每个组件本身都很年轻的栈里，组合出来的功能是所有功能中最不稳定的**。功能可用性还在插件版本之间变动，所以一个能用的配方是版本锁定的。

::: block-1
:mdnice-bold-italic[投机解码是目前大模型推理吞吐量优化的大杀器，在 CUDA 上可以轻松拿到 2-3 倍的端到端加速。但在昇腾上，这个功能不仅不稳定，甚至连配置都会被静默覆盖——你设了量化参数，它悄悄给你改了，你甚至都不知道。这种"静默错误"比直接崩溃可怕得多，因为你可能跑了半天才发现结果不对。]
:::

### 3.6 性能与可扩展性天花板

> 实际吞吐量在一个令人惊讶的低请求并发数就饱和了😅，而且首次服务时间很长。

![文章插图](/articles/2026-09-14-cuda-910-moe-16e96037/images/09.jpg)

::: image-caption
图 5：量化LLM服务的聚合服务吞吐量（左轴，实线）和稳态等待队列深度（右轴，虚线）随请求并发的变化。吞吐量是非单调的：在并发4附近达到峰值，然后超过"最佳点"后随着队列饱和而崩溃。这张图是整篇论文最反直觉的发现——你以为加并发能提高吞吐量，结果超过4之后吞吐量直接腰斩，等待队列从0暴涨到接近60。这不是调优问题，这是栈本身的属性。
:::

对于 LLM serving，**研究者发现并发"最佳点"大约是 4 个进行中的请求流**。低于这个数设备利用不足；在这个点引擎报告等待队列接近零；到 6 个或更多队列就饱和了（几十个请求在等），解析/超时失败上升，总吞吐量不升反降。

![文章插图](/articles/2026-09-14-cuda-910-moe-16e96037/images/10.jpg)

::: image-caption
图 6：每流吞吐量随并发的变化。超过最佳点后每增加一个流，每个流分到的份额就更小；并发为6时，每流吞吐量下降了大约5倍，说明过度订阅是降级而不是提升服务。这张图解释了为什么图5里总吞吐量会跌——不是卡坏了，是所有请求都在互相抢资源，每个都变慢，最后整体吞吐反而掉下来了。
:::

更反直觉的是，冷启动需要好几分钟，因为算子编译和权重/KV 缓存量化要在第一个请求能被服务之前完成。

::: block-1
:mdnice-highlight[根因在于，低并发上限反映了算子库和调度器行为没有像 CUDA 路径那样为这些模型提取那么多的 batch 级并行，所以过度订阅反而有害]。慢启动反映了提前编译和量化工作，CUDA 路径要么避免了这些，要么以不同方式摊销。两者都是栈属性，不是调优错误，必须围绕它们做规划——固定适度并发、长就绪超时。
:::

**这意味着你不能按 GPU 的经验来压测昇腾。GPU 上你可能开到 128、256 并发都还在涨，昇腾上开到 6 就已经开始崩了**。容量规划不能看理论 FLOPS，必须看你实际模型的实际并发最佳点，而且这个点可能低得超乎想象。

### 3.7 运维可靠性与可观测性

> 长时间运行的服务不会自己保持在线，而且当它们失败时诊断信息就有些晦涩了。

研究者把服务进程跑在一个外部看门狗下面，**每 30 秒健康检查 OpenAI 兼容接口，失败时自动重启引擎——没有它，后续实验章节的内核故障会导致无限期宕机**。:mdnice-bold-italic[研究者还观察到引擎反复日志记录 60 秒找不到共享内存广播块，这是进程挂起或做长时间编译/量化工作的症状，没有更细粒度的信号告诉你到底是哪个]。再加上不透明的设备故障转储，仅靠日志定位根因基本上是不可能的。

典型日志如下：

```
INFO shm_broadcast.py] No available shared memory broadcast blockfound in 60 seconds. This typically happens when some processes are hangingor doing some time-consuming work (e.g. compilation, weight/kv cache quantization).
```

**根因在于，栈把失败呈现为底层设备或 IPC 消息，而不是可操作的、分层的诊断，而且它缺乏一个生产服务路径应有的成熟弹性特性**。:mdnice-bold-italic[因此可靠性必须从外部提供——看门狗、重启策略、针对已知故障签名的日志抓取。]

::: block-1
:mdnice-highlight[说直白一点：这个栈本身不具备生产级高可用能力。你不能指望它自己健康运行，你必须在外层包一圈监控和自动恢复，就像你对待一个经常崩溃的桌面应用一样]。而且当它崩了，你基本没法知道为什么——日志只会告诉你"某个地方挂了 60 秒"或者"core 21 MTE 越界"。
:::

### 3.8 生态碎片化与可移植性税

> 获得并保持一个可用的部署，依赖于一个由厂商 fork、环境变量和启动补丁组成的矩阵，这些必须被重新发现和钉住。

行为由大量厂商特定环境变量控制（比如一整个 `VLLM*ASCEND_ENABLE`特性开关家族，加上 ACL_OP_INIT_MODE、HCCL_BUFFSIZE 和 NPU 分配器旋钮），还由容器启动时应用的模型/引擎特定源码补丁控制。正确运行依赖特定引擎版本、特定补丁集、特定环境变量配置；改任何一个都可能静默改变正确性或稳定性。

:mdnice-bold-italic[根因在于，因为厂商路径是一个落后并分叉于上游的 fork/插件，从 CUDA 部署移植过来不是免费的：每次版本升级都会产生持续的"税"——重新打补丁、重新调优、重新验证。社区小、公开文档薄，使得这个税比主流生态高得多。]

这就是"可移植性税"这个词的含义。:mdnice-bold-italic[你在 CUDA 上写的代码，升级 vLLM 版本大概率直接就能跑，可能还变快了。在昇腾上，每次升级都是一次赌博：你的补丁还能不能用？环境变量有没有改名？之前关的那个特性现在是不是默认开了？静默覆盖的 bug 修了没有？这些都得你自己重新测一遍。]

::: block-1
:mdnice-bold-italic[八大类问题，没有一个是"模型太大跑不了"这种硬件能力问题。全部都是软件栈成熟度问题： 算子没覆盖、并行组合没测过、内核会越界、图编译是实验性的、高级功能不稳定、调度器吃不下并发、出错了没法 debug、版本之间不兼容。] 这就是非 GPU 加速器今天的真实处境——硬件参数追上来了，软件生态还差着整整一代。
:::

## 四、跨问题的共性根因与危险模式

> 八大类问题共享少数几个交叉根因。理解这些共性，有助于分析以不同的形式出现在每一个非 GPU 加速器栈上的问题。

| 共性根因 | 说明 |
| --- | --- |
| 不成熟的编译器和算子库 | 位于内核故障、图编译限制、低并发上限和慢启动的上游；非个别算子质量问题，而是整体算子生态成熟度不足——CUDA 经十余年、数百万次生产部署打磨，覆盖大量 shape 与边缘 case；新加速器栈多仅在典型配置下验证，稍有偏差即出错。 |
| 特性组合的覆盖薄 | 单个功能表现良好，但功能交叉组合（如流水线并行 × 多模态 × MoE × 稀疏注意力）测试严重不足；16 种潜在路径可能仅 1 种被验证；CUDA 已由海量用户在真实场景中覆盖组合爆炸，新栈中用户实为“首测者”。 |
| 生产级可靠性和可观测性缺失 | 缺乏故障隔离、精准错误定位、自动降级等能力，导致本可局部处理的算子失败直接引发进程级宕机；成熟推理栈应能告知“哪层哪算子出何错”，并优雅回退；新栈中错误直透顶层，依赖外部脚手架补救。 |
| 生态碎片化 | 加剧前述所有问题，使修复难以复用与共享；CUDA 上的 bug 修复可经上游 PR 惠及全体用户；厂商 fork 版本差异大，补丁版本强耦合、易失效，且因配置矩阵各异，难以跨用户协作复用。 |

### 4.1 最危险的模式：启动正常但推理已坏

> 论文中反复出现的一个危险模式，值得所有从业者高度警惕：启动看起来健康，但推理已经坏了。

:mdnice-bold-italic[内存分析和预热走的代码路径和真实请求不一样，所以好几个缺陷只在第一次真正 prefill 的时候或者持续负载下才出现。比如稀疏注意力的 KV 状态分配 bug，启动时完全正常，因为 dummy run 走的是纯文本路径，直到第一个真实的多模态 prefill 进来才越界崩溃。] 还有流水线中间缓冲区大小的 bug，decode 形状的 dummy run 算出来的大小，到 prefill 的时候就不够用了。

::: block-1
这意味着"服务起来了"和"服务正确了"之间，差着十万八千里。:mdnice-bold-italic[你不能用启动成功作为部署正确的判据，你必须用真实流量、真实 shape、真实并发去压，而且要跑足够长的时间。很多团队部署非 GPU 加速器的时候，看到能输出"你好，我是 XXX"就觉得移植成功了，这是极其危险的] ——静默的数值损坏可能在你跑了几万条请求之后才被发现，那时候结果已经全错了。
:::

### 4.2 总拥有成本的真相

> 论文中最清醒的一句话是：所有这些都不代表平台不可用——两个负载最终都正确服务了。:mdnice-bold-italic[它意味着总拥有成本主要由工程投入（打补丁、调优、运维）构成，而不是采购硬件，而且为这些投入做预算是唯一最重要的规划决策。]

很多团队评估非 GPU 加速器的时候，算的是硬件采购成本：一张昇腾 910 比一张 H100 便宜多少钱，然后算个总拥有成本说能省多少。:mdnice-bold-italic[但实际，硬件成本可能是最小的一部分🤦‍♂️。真正的成本是：你需要几个资深工程师花几个月时间打补丁、调参数、写看门狗、做容错、升级版本重新验证。这些工程师的时间成本，以及服务上线延迟的机会成本，可能远远超过硬件本身省下来的钱。]

而且这不是一次性成本😅。每次引擎版本升级，每次 CANN 版本升级，每次你想换个模型架构，你都得重新走一遍这个流程。这是持续的"可移植性税"，只要你在这个生态里，就得一直交。但好处是，可能不容易失业了😅。

## 五、给实践者的具体策略与建议

> 论文最后给出了:mdnice-bold-italic[两类建议：一类是针对昇腾这个特定栈的具体战术，另一类是适用于采纳任何替代加速器的通用策略。后者的价值远远超出了昇腾本身，是所有想做硬件多元化的团队都应该认真践行的方法论。]

这些建议并非空泛的"要做测试"，都是研究者真金白银踩坑踩出来的具体可操作项。每一条背后都有至少一个血淋淋的 bug 作为支撑。

### 5.1 针对昇腾栈的具体战术

- **第一条：采纳正确性优先的配置。默认关掉脆弱的吞吐量特性（序列并行/FlashComm、融合 MoE 通信、投机解码），只有在针对你的负载做过验证之后才重新开启**。优先用 enforce-eager 模式，除非图捕获被证明对你的 shape 是稳定的。这一条听起来很简单，但:mdnice-bold-italic[在实际中很多团队会忍不住开各种"优化开关"追求性能数字，结果花在排查随机崩溃和数值错误上的时间，远远超过开特性省下来的那点吞吐量。]
- :mdnice-bold-italic[第二条：最小化并行轴。尊重张量并行上限，只加你真正需要的那一个额外轴（PP 或者 DP）；每多一个并行特性，未测试代码路径就乘一次。很多人觉得并行轴越多越先进、性能越好，但在成熟度不够的栈上，并行轴越多意味着出问题的概率指数级增长]。能用 TP=8×DP=2 解决的，就不要搞 TP=8×PP=2×EP=4 之类的复杂组合。
- :mdnice-bold-italic[第三条：把服务包在看门狗里。假设内核故障一定会发生；健康检查接口，自动重启。抓取日志中的已知故障签名（比如运行时结果 507015/507035、MTE 越界）来驱动告警。不要指望栈自己能恢复，它不能。你必须在外层做高可用]，就像你在 K8s 里给任何无状态服务做的那样——liveness 探针、readiness 探针、自动重启、崩溃回溯告警。
- :mdnice-bold-italic[第四条：调优到并发最佳点。测量等待队列保持接近零的那个点，把并发固定在那里，不要过度订阅。不要按 GPU 的经验设置并发数，也不要按理论计算能力反推。你的模型在这个版本的栈上的最佳并发点，必须你自己测出来，而且很可能比你想象的低很多]。超过那个点之后，吞吐量不仅不涨，还会跌，而且尾延迟会爆炸。
- **第五条：钉死一切，维护补丁集**。锁定引擎/插件版本，保持源码补丁幂等并在启动时应用，记录完整的环境变量矩阵，让部署在重启和跨机器时可复现。不要追最新版本，除非你有充分的理由和充足的测试资源。在一个快速迭代但成熟度不够的生态里，"最新"往往等于"最不稳定"。找一个你验证过能用的版本，钉死它，把所有补丁和配置都变成代码，不要手工操作。

### 5.2 采纳任何替代加速器的通用策略

> 这九条策略是厂商无关的，在研究者的经验中，它们才是真正决定迁移成本和风险的东西。

- :mdnice-bold-italic[第一条：对参考实现做差分测试。把一个可信实现（比如 CUDA 路径、CPU 路径、或者模型原生框架）当作正确性预言机，逐层对比中间张量和最终输出。研究者遇到的最难的 bug 几个都是静默数值损坏，不是崩溃；只有差分对比能抓到这些。这一条怎么强调都不过分。] 很多团队移植模型只看最终输出的 perplexity 或者几个样例，觉得差不多就过了。但 MoE 和多模态模型里，一个头的状态错了、一个专家路由偏了，可能在大多数样例上看不出来，只在特定输入下才会显现。逐层差分对比是唯一可靠的方法。
- :mdnice-bold-italic[第二条：在目标栈上做持续集成。每次引擎/插件升级，在目标硬件上跑真实的 prefill/decode 路径（不只是启动），在生产前抓到覆盖缺口和回归。CI 不能只跑单元测试，必须跑真实的推理路径]，必须用真实的 batch size 和序列长度，必须覆盖多模态和 MoE 这些复杂路径。启动成功不算通过，能正确跑完一批真实请求才算通过。
- **第三条：薄的可移植性层。把引擎和厂商特定的配置（环境变量、开关、补丁）隔离在一个小抽象后面，让服务系统的其余部分可移植，让"可移植性税"只在一个地方交**。:mdnice-bold-italic[你的业务逻辑、你的调度系统、你的 API 层，不应该知道底层是 CUDA 还是昇腾还是别的什么。所有硬件特定的东西都应该收敛到一个适配层里]，这样换硬件的时候你只需要重写适配层，而不是整个服务。
- :mdnice-bold-italic[第四条：金丝雀和影子部署。把新版本/补丁集先发布到一个镜像生产流量的金丝雀，影子运行真实请求，在全量发布前发现质量或稳定性回归。不要直接全量上线。在一个内核可能随机崩溃、数值可能静默错误的栈上，全量发布等于自杀]。先放 1%流量，观察几个小时，对比结果和 CUDA 基线的差异，确认没问题再逐步放大。
- :mdnice-bold-italic[第五条：特性开关兼容矩阵。维护一个显式的、经过测试的矩阵，记录哪些特性组合（并行度 × 模态 ×MoE× 量化 × 图模式）在哪个版本上是已知可用的，默认用最小的可用集合]。不要想当然地认为某个特性开了就能用。把"什么和什么能一起开"变成明确的、版本化的文档，而且每次升级都重新验证。
- **第六条：围绕测量到的限制做容量规划。从测量到的并发最佳点和冷启动时间来规划集群规模，而不是从理论峰值 FLOPS 或显存来算**。:mdnice-bold-italic[理论 FLOPS 是峰值，你永远跑不到🤣；显存容量是上限，但你实际能用的比这个少]。按你实际能稳定达到的吞吐量来算需要多少卡，预留足够的冗余给故障重启和冷启动。
- **第七条：默认容错服务。假设设备故障一定会发生；组合健康检查自动重启、请求重试/幂等性、故障签名告警，让孤立的内核故障优雅降级而不是导致宕机**。:mdnice-bold-italic[把硬件当成不可靠的——它确实在某些边缘 case 下不可靠——然后在软件层做容错]。重试必须是幂等的，因为你不知道请求是在哪个阶段崩的。
- :mdnice-bold-italic[第八条：内核级回退策略。默认优先用最可靠的执行模式（eager），有选择地采用图捕获或融合核，捕获失败时自动回退。不要把图编译当成必选项，把它当成一个可能失败的优化，失败了就回退到慢但可靠的路径]。在可靠性和性能之间，永远先选可靠性，除非你已经充分验证了性能路径的稳定性。
- **第九条：向上游贡献和合作。把修复和复现用例贡献回厂商插件，和社区互动；在一个薄的生态里，共享的修复能减少每个人的重复成本，缩短和上游的分叉距离**。不要觉得打了补丁自己能用就行了。你的补丁很可能也解决了别人的问题，而且上游维护者可能知道更好的修复方式。:mdnice-bold-italic[更重要的是，你贡献的代码越多，你对路线图的影响力就越大，未来版本破坏你部署的概率就越低。]

### 5.3 对生态的请求

> 论文最后对整个非 GPU 加速器生态提出了几个非常具体的请求。这些请求如果能实现，能消除论文中记录的大部分成本。

| 原则 | 具体要求 |
| --- | --- |
| 优雅回退机制 | 未覆盖的特性组合应明确提示“该组合暂不支持”，避免段错误或错误结果；禁止硬崩溃，需提供清晰、用户友好的错误信息。 |
| 分层可操作诊断 | 故障定位需映射到具体算子与执行上下文，例如“第32层注意力算子在序列长度4096时越界”，而非低层硬件错误（如“core 21 MTE 越界”），确保开发者可直接用于调试。 |
| 特性组合覆盖测试 | 测试需覆盖特性交叉乘积：并行度 × 多模态 × MoE × 稀疏注意力；拒绝仅验证单特性，必须模拟前沿模型真实组合场景。 |
| 版本与特性兼容矩阵 | 提供结构化、文档完备的兼容性矩阵，明确标注各版本支持的特性、特性间互操作性、实验性标记；消除用户试错成本，支持可预期的部署决策。 |

::: block-1
:mdnice-bold-italic[这九条通用策略，本质上就是把"新硬件生态不成熟"这个前提当成既定事实，然后用软件工程的最佳实践来对冲风险。 差分测试、CI、可移植性层、金丝雀发布、兼容矩阵、容量规划留余量、默认容错、自动回退、上游贡献——这些都是在任何成熟技术栈上的标准操作，但在非 GPU 加速器上，你必须加倍认真地做，因为栈本身不会帮你做🤦‍♂️。]
:::

## 六、结语：硬件能跑只是开始，工程才是真正的成本

> 这篇论文记录了在 16 卡华为昇腾 910 系统上用 CANN 和 vLLM-Ascend 部署大型 W8A8 MoE 语言模型和大型多模态视觉语言模型的实地研究。两个负载最终都正确服务了，但这是在打了 12 个源码补丁、为了保持数值正确性刻意关掉多个性能特性、以及用外部运维脚手架吸收反复出现的底层设备故障之后才做到的。

遇到的限制——软件栈和算子/功能覆盖不成熟、脆弱的多轴并行、内核级 aicore/vector-core 故障、不成熟的图编译、不稳定的高级功能、低性能/可扩展性天花板、弱可靠性/可观测性、生态碎片化——是平台属性，不是负载怪癖。

对于正在考虑这类加速器的团队，:mdnice-bold-italic[硬件是有能力的，但达到并保持正确性的工程成本才是主要考虑因素，应该明确规划。论文中给出的通用策略——差分测试、目标栈上的 CI、可移植性层、金丝雀/影子发布、围绕测量限制做容量规划、容错服务——在研究者的经验中，才是让这个成本可控的方法。]

::: block-1
这篇论文的意义远远超出了华为昇腾这一个平台。它实际上是给所有非 GPU 加速器、所有国产 AI 芯片、所有想做 CUDA 替代方案的团队，提供了一份非常诚实的成熟度基线。:mdnice-highlight[今天你在昇腾上遇到的问题，明天你在任何一个新的 AI 加速器上大概率都会遇到——算子覆盖不全、并行组合没测过、内核随机崩溃、图编译不稳定、高级功能缺失、并发上不去、debug 信息没用、版本之间不兼容。]
:::

这不是坏事。承认问题是解决问题的第一步。CUDA 也是这么走过来的——**十几年前的 CUDA 也到处是 bug、算子覆盖不全、调试体验极差。但它用了十几年时间、几百万开发者的反馈、无数个生产部署的打磨，才变成今天这个样子**。非 GPU 加速器现在缺的不是硬件能力，是时间和真实负载的打磨。

不要被纸面参数迷惑，不要被厂商宣传忽悠，不要以为"支持 PyTorch"就等于"能跑生产"。真正的成熟度，体现在边缘 case 的处理上，体现在特性组合的稳定性上，体现在出错时能不能 debug 上，体现在版本升级的平滑度上。这些东西没有任何捷径，只能靠真实的生产负载一遍一遍踩，靠开发者社区一个 bug 一个 bug 修。

如果你正在评估非 GPU 加速器，可以对照着每一条问厂商😂：

- 这个问题你们解决了吗？
- 那个特性组合你们测过吗？
- 内核故障你们怎么处理？
- 版本升级怎么保证兼容？

> 如果这些问题得不到清晰的答案，你就应该把工程税算进你的总拥有成本里，而且要往多了算。

最后，:mdnice-bold-italic[向这篇论文的作者致敬。在一个大家都喜欢报喜不报忧的行业里，愿意把踩过的坑、打过的补丁、遇到的崩溃原原本本写出来公之于众，这需要勇气，也体现了真正的工程师精神。正是这样的实地研究，才能推动整个生态向前走。]

::: block-1
大模型推理的硬件多元化是必然趋势，没有人愿意被单一供应链卡脖子。:mdnice-bold-italic[但多元化不是没有代价的，代价就是软件生态成熟度的差距。这篇论文没有说非 GPU 加速器不能用——它自己就成功跑起来了两个千亿级模型。它说的是：用之前，先算清楚工程账；用的时候，把容错和验证做足；遇到问题， upstream 回社区。硬件能跑只是开始，稳定运行于生产，才是真正的挑战。]
:::
