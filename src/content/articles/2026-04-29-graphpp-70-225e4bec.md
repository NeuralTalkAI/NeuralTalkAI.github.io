## 一、流水线并行的承诺与困境

> 流水线并行（Pipeline Parallelism，PP）的核心思想是将模型切分成多个阶段，分布到不同设备上执行。理想情况下，这能突破单卡显存限制，让超大模型训练成为可能。

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/03.webp)

::: image-caption
大模型训练中两种核心并行策略：按模型维度切分（左，如张量并行TP）和按模型深度切分（右，即流水线并行PP）。左侧维度切分将每一层的权重按特征维度拆分到所有GPU上，每个GPU处理所有层的部分计算，层间需要频繁的全局通信，适合显存受限但能承载部分维度的场景。右侧流水线并行则按模型深度分层，将连续的层分配给不同GPU（如GPU0处理层0-1，GPU1处理层2-3），数据按流水线方式在设备间流动，仅需相邻stage间的轻量通信，大幅降低全局通信开销，这也是流水线并行能支撑超大规模模型跨节点训练的关键优势。
:::

但现实并不完美。最棘手的问题是 **Pipeline Bubble（流水线气泡）** ——设备在等待前序阶段完成计算时产生的空闲时间。这些“气泡”严重拖累了 GPU 利用率，成为流水线并行效率的天花板。

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/04.webp)

::: image-caption
这张图揭示了流水线并行（PP）的核心低效问题——流水线气泡（Pipeline Bubbles）。左侧展示了模型按深度切分的流水线并行架构：不同GPU分别负责模型的连续层（如GPU0处理前两层、GPU1处理中间两层）。右侧的时间调度图直观呈现了气泡问题：横轴为时间，纵轴为设备，灰色部分代表设备空闲（Idle）。由于前向传播时，数据需从GPU0依次流向GPU3，后续设备必须等待；反向传播时梯度又需反向回流，导致大部分设备在大部分时间处于空闲状态，形成大片“气泡”。例如GPU0仅在最前和最后有任务，中间全程闲置，硬件利用率被大幅拉低，这也是Zero-bubble PP（如ZB2P）等优化方案要解决的核心痛点。
:::

## 二、调度优化的演进：从 1F1B 到 ZB2P

> 为了压缩气泡，研究者提出了各种调度策略。最经典的是 1F1B（一个 Forward 接一个 Backward），通过在稳态阶段交替执行前向和反向来减少空闲。

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/05.webp)

::: image-caption
ZB2P 调度的核心设计，专为流水线并行的气泡问题优化。上方是4设备的时空调度表，横轴为时间，蓝、青、绿分别代表前向（F）、反向（B）、权重梯度（W）任务，米黄色为优化器步骤；红框标出的初始阶段是流水线填充期，设备按对角线依次启动微批次任务。填充完成后，通过支持2个待处理反向任务、交错前向/反向/权重梯度执行，几乎消除了传统流水线的空闲气泡，设备实现持续运行。下方文字与小图揭示关键优化逻辑：微批次越小，后续设备启动越快，流水线填充延迟越短，整体硬件利用率越高，是零气泡流水线的核心调度策略之一。
:::

> 更进一步的是 **ZB2P（Zero-bubble Pipeline Parallelism with 2x pending backward）**。其核心洞察是：反向传播可以拆解为两部分——

- **B（Backward Input Grad）**：计算对输入的梯度，需要传递给前一个设备
- **W（Weight Grad）**：计算对权重的梯度，仅用于本地参数更新

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/06.webp)

::: image-caption
ZB2P 零气泡流水线并行调度，核心是通过多微批次填充消除传统流水线的 “气泡” 问题。红框标注了 Device1/2 的初始前向阶段，以连续的微批次快速填满流水线。下方示意图揭示关键优化逻辑：左侧对角线说明微批次越小，后续设备启动越快，填充延迟越短；右侧橙框展示用更多微批次持续填充前向间隙，让设备无空闲地交错执行 F/B/W 任务，仅末尾保留少量优化器步骤，大幅提升硬件利用率。
:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/07.webp)

::: image-caption
红框标出Device3/4的初始执行阶段，能看到Device4延迟了自身的F2前向任务，优先执行B1反向任务。下方示意图中，左侧对角线说明微批次越小，后续设备启动越快，流水线填充延迟越短；中间橙框展示用更多微批次填充前向间隙，让设备持续运行；右侧则点明Device4通过延迟自身前向任务，优先处理反向任务，快速解锁Device3的依赖，消除流水线气泡。这种“以延迟局部前向换取整体流水线流畅度”的优先级调度，大幅提升了硬件利用率。
:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/08.webp)

::: image-caption
红圈标注的B与W，说明反向传播被拆分为两个独立阶段。下方的计算图进一步呈现这一设计：前向为线性层+激活函数，反向被拆解为输入梯度（B）与权重梯度（W）两条独立路径。这种拆分让调度器能灵活交错F、B、W任务，比如优先执行B以解锁下游设备，延迟W填充间隙，几乎消除了传统流水线的空闲气泡，大幅提升硬件利用率，是ZB2P实现“零气泡”的关键设计。
:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/09.webp)

::: image-caption
红框标注的 Device3/4 执行段，直观体现了依赖解耦的效果。下方的反向计算图将反向传播拆分为独立的 B（输入梯度）和 W（权重梯度）路径，右侧说明进一步点明关键：Device3 的 B1 任务仅依赖 Device4 的 B1 输入梯度，无需等待其 W1 权重梯度完成。这种解耦让下游设备可优先执行 B 任务，快速解锁上游设备的反向流程，而 W 任务可延迟执行以填充流水线间隙，彻底消除传统流水线因反向依赖导致的气泡，大幅提升硬件利用率。
:::

ZB2P 利用这一特性，优先执行能“解锁”前序设备的 B 计算，将 W 计算延后填充气泡间隙。正如前几页 PPT 所示：“**Device 4 prioritizes unlocking Device 3 by delaying W。** ” 同时通过增加微批次数量（Fill gaps with more microbatches）来进一步压缩空闲时间。

## 三、专家混合模型的特殊挑战：DualPipeV

> 对于 MoE（Mixture of Experts）架构，情况更为复杂。MoE 层包含通信密集的 All-to-All Dispatch/Combine 操作。

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/10.webp)

::: image-caption
专为MoE模型设计的DualPipeV流水线并行调度。上方是4设备的时间维度调度表，以橙、绿、蓝区分前向、反向输入/权重梯度任务，橙绿重叠段为前后向重叠执行，数字标注stage与微批次，通过交错排布大幅消除流水线气泡。下方计算（112个SM）与通信（20个SM）的双层流水线，将MLP、Attention的前向/反向计算，与MoE的Dispatch/Combine通信及PP跨设备通信并行执行，让计算与通信资源同时被利用。这种细粒度双流水线调度，专门适配MoE的通信密集特性，最大化GPU利用率，是GraphPP编译优化的核心调度策略之一。
:::

> **DualPipeV** 调度专门针对这一场景设计，通过细粒度的计算-通信重叠来隐藏延迟。

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/11.webp)

::: image-caption
eager 模式下实现前后向重叠（overlapped forward-backward）的调度方式与核心痛点。上方采用双Python线程分别处理Autograd反向和前向任务，通过线程间调度，让前向的通信Dispatch(F)、计算MLP(F)，与反向的MLP(B)、通信Dispatch(B)、MLP(W)交错执行；下方调度图进一步展示GPU侧的硬件并行：计算（112个SM）与通信（20个SM）任务在不同硬件资源上同时运行，前向（黄色）与反向（绿色）任务的重叠执行，减少了流水线气泡。但右侧红色框点明了关键局限：跨nn.Module边界的细粒度重叠难以协调，比如DeepSeek的Dualpipe方案，需要模型作者手动实现反向传播逻辑，大幅增加了开发成本，这也凸显了GraphPP这类基于编译的图优化方案的价值——无需侵入式修改模型代码，即可自动实现高效的前后向重叠。
:::

上图揭示了实现这种重叠的困难：需要协调 Python 线程、手动管理 Autograd，而且“Coordinating fine-grained overlap across nn.Module boundaries is difficult”。DeepSeek-AI 的 DualPipe 实现甚至要求模型作者手写反向传播逻辑——这对普通开发者而言门槛极高。

## 四、现有方案的三大痛点

> 当前方法的核心问题有三点：

**第一，对反向传播的控制力有限。** 想要实现 ZB2P 或 DualPipeV 这样的高级调度，往往需要手动编写反向逻辑，不仅繁琐且容易出错。:mdnice-bold-italic[下面展示的代码片段说明了这一点——开发者必须继承 `torch.autograd.Function` 并精细控制梯度计算顺序，还要应对与 `torch.compile` 和激活检查点的兼容性问题。]

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/12.webp)

::: image-caption
Zero-bubble流水线并行中反向传播分解的手动实现方式：基于Megatron分支，通过自定义`torch.autograd.Function`重写`backward`方法，延迟权重梯度（W）计算、仅返回输入梯度（B），以实现反向分解调度，但这种方式需要手动编写反向逻辑，开发成本高。
:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/13.webp)

::: image-caption
两种反向传播分解的实现方式：上方Zero-bubble方案通过自定义`torch.autograd.Function`手动实现反向逻辑；下方`torch.distributed.pipelining`则用`autograd.grad`自动拆分输入与权重梯度。但两种方式都面临与`torch.compile`、梯度检查点的兼容性难题，限制了易用性与扩展性。
:::

**第二，线程与流管理复杂。** 实现计算-通信重叠需要精细的 CUDA 流调度和多线程协调，这超出了大多数模型开发者的舒适区。

**第三，组合性挑战。** 复杂的模型代码分支、激活检查点 API 的不兼容、与 `torch.compile` 的冲突，让高级调度策略难以落地。

## 五、GraphPP：图驱动范式的突破

> GraphPP 的核心思想是：**将流水线并行问题转化为计算图变换问题**。这一范式转移带来了三个根本性优势：

### 5.1 完全的反向控制权

通过函数式图捕获 API 和 AOTAutograd，GraphPP 能够自动获得完整的正向和反向计算图。**B/W 拆分不再是手写 autograd.Function，而是对计算图的节点依赖分析。**

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/14.webp)

::: image-caption
MLP层的反向传播计算图分解过程，核心目标是提取输入梯度`grad_x`的计算路径。左侧是MLP前向代码，包含门控投影、上投影、SiLU激活、门控乘积与下投影；右侧为反向传播计算图，从输出梯度`grad_out`出发逐层反向推导，通过“仅保留通向`grad_x`的节点”简化计算图，剔除权重梯度（如`grad_w1`、`grad_w3`）的计算分支，仅保留输入梯度的计算链，最终将`grad_x`拆分为两条路径的和，实现反向图的轻量化优化，减少计算冗余。
:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/15.webp)

::: image-caption
左侧是MLP前向逻辑，包含门控投影、上投影、SiLU激活、门控乘积与下投影；右侧是反向计算图，通过图变换将反向过程拆分为输入梯度（`grad_x`）与权重梯度（`grad_w1/2/3`）两条独立路径。本图聚焦权重梯度计算，剔除了通向`grad_x`的冗余节点，仅保留从`grad_out`到`grad_w2`、`grad_w1`、`grad_w3`的计算链（如`grad_w2`由`h.T @ grad_out`得到，`grad_w1/3`由`x.T`与中间梯度计算），实现反向图的轻量化拆分，适配不同场景的梯度计算需求。
:::

如上图所示，该过程只需标记哪些节点通向 `grad_x`（B 部分）或 `grad_w`（W 部分），编译器就能自动完成拆分。

### 5.2 无需手动线程管理

> 重叠调度可以在主线程之外运行，流管理变为可选而非必需。

下面展示了如何将正向和反向计算图“多路复用”成单一的不相交图，然后重新排序节点以实现最优重叠——**这一切都发生在图层面，无需侵入模型代码。**

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/16.webp)

::: image-caption

基于图的流水线并行（PP）调度的中间表示（IR）。上方是4个设备的时间维度调度表，以不同颜色区分前向（橙）、反向输入梯度（绿）、反向权重梯度（蓝）及前后向重叠操作，数字标注stage与微批次，直观展现多设备流水化执行的任务排布与重叠优化，减少空闲气泡。下方定义了标准化IR指令集，涵盖stage/微批次粒度的前向、反向（分输入/权重梯度）、前后向重叠，以及参数分片、梯度规约、通信收发等操作，为流水线并行的调度与执行提供了清晰的抽象，支撑高效大模型训练调度。

- `iFj`：运行阶段 i 的前向，处理微批次 j

- `Unshard i` / `Reshard i`：FSDP 参数的分片与聚合操作
- `iSEND_Fj` / `iRECV_Fj`：跨 PP 阶段的通信原语

:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/23.webp)

::: image-caption
FSDP（全分片数据并行）的关键优化：将包含通信操作的计算图拆分为独立的子图，以提升执行效率。左侧前向图（Fw Graph）被拆分为无通信的前向计算子图（处理分片参数、执行前向算子）和单独的参数收集子图（通过gather/all_gather还原完整参数）。右侧反向图（Bw Graph）则被拆分为无通信的反向计算子图（利用保存的激活值和梯度计算输入梯度与未分片参数梯度）和单独的梯度归约子图（通过all_reduce/reduce_scatter完成梯度聚合与分片）。这种拆分将原本分散的通信操作集中处理，减少了跨设备通信频率，同时让前向/反向计算与通信操作可以独立调度，大幅提升了FSDP在大规模模型训练中的计算效率与显存利用率。
:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/24.webp)

::: image-caption
反向传播的关键优化：将反向图（Bw Graph）拆分为输入梯度（dl）与参数梯度（dW）两个独立子图。左侧矩阵乘法示例清晰区分了前向、dl（计算输入梯度）和dW（计算权重梯度）的计算逻辑；原反向图本需同时执行激活重计算、dl和dW操作，输出输入梯度与未分片参数梯度。拆分后，dl图先接收前向激活与输出梯度，通过重计算和dl算子生成输入梯度与反向激活；dW图再利用这些反向激活，通过dW算子计算最终的参数梯度。这种拆分是流水线并行与FSDP优化的核心手段，它解耦了输入梯度与参数梯度的计算，让两者可以独立调度，大幅降低显存占用并提升通信效率。
:::

:::

![文章插图](/articles/2026-04-29-graphpp-70-225e4bec/images/26.webp)

::: image-caption
流水线并行中前后向计算重叠（Overlapping Fw-Bw Graphs）的图优化流程。首先，独立的前向图（Stage-i Fw Graph）接收参数与输入，通过fw_ops输出结果与激活值；反向图（Stage-m Bw Graph）则利用保存的激活和输出梯度，通过bw_ops生成梯度。优化分为两步：先将两者拼接为联合计算图，再通过多路复用（Multiplex）调度，将不同阶段、不同微批次的前向与反向算子交错排列，形成可并行执行的重叠图。这种设计让同一设备上的前向与反向计算得以重叠执行，减少了流水线气泡，大幅提升了大规模模型训练的设备利用率与吞吐效率。

## 九、本质洞察：图即程序，变换即优化

> GraphPP 的深层哲学是：**将并行策略视为对计算图的程序变换**。这一视角统一了看似迥异的优化技术：

- B/W 拆分本质是图的依赖分析
- 计算-通信重叠本质是图的节点重排
- FSDP 通信优化本质是集合通信节点的插入与调度

当一切都被表达为图变换，编译器就能自动应用这些优化，而无需开发者理解底层细节。这正是 GraphPP 能够同时实现高性能和高易用性的根本原因。
