- :mdnice-highlight[空间上，SM 比例与实际通信计算量不匹配，要么带宽闲置要么算力空转；]
- :mdnice-highlight[时间上，数据依赖产生的流水线气泡让大量 SM 处于空闲状态。]

## 一、MoE 分布式推理的通信困局：计算通信重叠的天花板在哪

### 1.1 专家并行下的通信代价

> MoE 架构用稀疏激活的专家网络替代稠密前馈网络，实现了模型容量的大幅扩展，同时保持单 token 计算量基本不变。**当模型规模增长到数十乃至上百个专家时，专家并行成为分布式推理的必然选择。**

所谓专家并行，就是将所有专家拆分到不同的 GPU 上，每个 token 根据路由结果被发送到对应专家所在的 GPU 进行计算。**这一模式让每个 MoE 层的执行都变成一次分布式计算，伴随大量跨 GPU 的 token 移动。**

一个完整的 MoE 层前向传播包含五个阶段：

1. 分发（Dispatch）：将每个 token 发送到其目标专家所在的 GPU
2. 上投影与门控 FFN（GEMM0）：专家网络的第一次矩阵乘法与激活
3. 激活函数（SiLU_Mul）：SiLU 激活与逐元素乘法
4. 下投影 FFN（GEMM1）：专家网络的第二次矩阵乘法
5. 聚合（Combine）：将多专家的输出加权求和，返回原始 GPU

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/07.jpg)

::: image-caption
图 3：专家并行模式下的 MoE 前向传播过程（2GPU、4 专家、top-k=3 路由）。分发操作将每个 token 发送到承载其目标专家的 GPU；专家子网络顺序执行上投影 + 门控矩阵乘、SiLU 激活与逐元素乘、下投影矩阵乘；聚合操作执行加权求和并将结果返回源 GPU。这张图直观展示了专家并行的核心逻辑：token 跨 GPU 流动，计算留在本地 GPU。每个 token 需要先被分发到对应专家的 GPU，完成三次计算操作后，结果再聚合回源 GPU。两次跨 GPU 通信夹着本地计算的结构，天然适合用计算通信重叠来掩盖延迟，这也是所有重叠优化的结构基础。
:::

> 其中 Dispatch 和 Combine 属于跨 GPU 通信操作，GEMM0、激活、GEMM1 属于本地计算操作。**通信与计算的速度差，正在随着硬件代际演进越拉越大。**

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/08.jpg)

::: image-caption
图 1：A100、H100、B200 三代 GPU 的计算能力与 NVLink 带宽演进对比。左侧蓝色纵轴为 BF16 精度下的稠密算力 TFLOPS，右侧红色纵轴为 NVLink 单向带宽 GB/s。从数据可以清晰看到算力与互联带宽的增速剪刀差：从 A100 到 B200，BF16 峰值算力增长了 2.3 倍，而 NVLink 单向带宽仅增长了 1.5 倍。这一趋势意味着通信开销在 MoE 推理中的占比会持续上升，单纯依靠硬件升级无法弥合计算与互联的速度差距，必须通过软件调度优化来更高效地利用有限的互联带宽，这也是计算通信重叠技术越来越重要的底层硬件动因。
:::

::: block-1
这一硬件趋势直接导致通信开销在 MoE 层延迟中的占比不断上升。论文指出，:mdnice-highlight[分发与聚合操作最多可占据 MoE 层延迟的 40%，并且这一比例还在随着算力提升继续增长。如果不能高效掩盖通信延迟，GPU 的算力优势就会被互联瓶颈彻底吃掉。]
:::

### 1.2 三代重叠方案的固有局限

> 为了降低通信开销，**业界主流思路是让计算与通信重叠执行，也就是用一部分 SM 专门跑通信，剩下的跑计算，让两类任务在时间上并行**。:mdnice-bold-italic[但现有方案都停留在静态或粗粒度动态的层面，无法适配 MoE 负载的动态性。]

根据对路由结果的感知粒度，现有计算通信重叠方案可以分为三代：

| 代际 | 描述 |
| --- | --- |
| 第一代 无显式 SM 分区 | 代表是 **Triton-Distributed（TD）**，所有 SM 串行执行分发、计算、聚合，:mdnice-bold-italic[仅靠操作边界的全局抢占实现极少量重叠，重叠效率最低]。 |
| 第二代 静态 SM 分区 | 代表是 **DeepEP 和 ParallelKittens（PK）**，在编译时就固定通信 SM 的数量，所有层都用同一个分区比例。:mdnice-bold-italic[这种方式实现了基础的重叠，但完全无法应对不同层、不同 GPU 的负载差异。] |
| 第三代 粗粒度动态分区 | 代表是 **Comet**，根据输入序列长度从预定义的内核库中选一个 SM 比例，每次迭代切换一次。这种方式能适配序列长度带来的整体负载变化，:mdnice-bold-italic[但依然无法响应每层路由结果的差异]。 |

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/09.jpg)

::: image-caption
图 2：四种 MoE 执行模式的执行时间线对比，涵盖无重叠、静态 SM 分区、粗粒度动态、细粒度动态四类方案。四张时间线图清晰呈现了重叠技术的演进路径：从完全串行的无重叠，到固定分区的基础重叠，再到粗粒度的迭代级动态调整，最终到 Weave 的层级细粒度动态调度。(a)：无重叠执行模式（Triton-Distributed）。所有流多处理器依次执行分发、通用矩阵乘法和聚合操作，计算与通信完全串行。这种模式下没有显式的 SM 角色划分，所有资源分时复用在通信和计算任务上，两者几乎没有并行执行的窗口，通信延迟完全暴露在关键路径上。其优势是实现简单，不需要修改内核结构，但在 MoE 场景下通信占比高，性能损失最为严重，是重叠优化的基线参考。(b)：静态 SM 分区模式（DeepEP）。负责通信和计算的 SM 组在编译阶段就固定划分，运行时不可调整，执行时间线中存在明显的空闲气泡。静态分区首次实现了通信与计算的并行执行，通过专用 SM 组让两类任务同时运行。但固定的比例无法适配不同层的负载变化，当通信量小时通信 SM 会提前空闲，当计算量小时计算 SM 会提前空闲，同时数据依赖导致的中间气泡也无法消除，资源浪费依然显著。(c)：粗粒度动态调整模式（Comet）。通信与计算的 SM 比例可以按每次推理迭代进行切换。这种模式相比静态分区前进了一步，能够根据输入序列长度调整整体的 SM 分配，适配不同的负载强度。但它的调整粒度是整个迭代，无法感知每层路由结果带来的负载差异，同一迭代内所有层仍然使用相同的 SM 比例，依然无法解决层间负载波动带来的不匹配问题。(d)：细粒度动态调度模式（Weave）。SM 的角色划分可以针对每一层、每一个 GPU 独立动态调整。 这是 Weave 提出的新模式，调度粒度从迭代级细化到层级，并且可以感知每个 GPU 的实际负载。通过路由结果实时计算最优分配，同时配合时间维度的调度优化，几乎消除了空闲气泡，让 SM 在整个层执行过程中都保持忙碌状态，实现了更高的资源利用率。
:::

> 这三代方案共同的问题，就是**都没有针对每层的实际路由结果调整 SM 分配，导致资源浪费体现在两个维度：**

- **空间维度的浪费**：最优的通信/计算 SM 比例由每层的路由结果决定，不同层、不同 GPU 上的通信量和计算量都不一样。:mdnice-bold-italic[固定的 SM 分区必然会出现一边干完了等另一边的情况，要么浪费 NVLink 带宽，要么浪费计算吞吐量。] 如下图所示：

::: image-caption

## 二、Weave 核心洞察：路由完成后，所有工作量都是确定的

### 2.1 从离线预设到运行时自适应的范式转变

> 为什么之前的方案都做不到每层动态调整？**核心原因在于它们都把 SM 分区决策放在了编译时或者迭代开始前，没有利用路由阶段产生的信息。**

Weave 的核心洞察非常直接：**路由完成的那一刻，整个 MoE 层的所有工作量就都确定了**。:mdnice-bold-italic[具体来说，路由结束后，系统可以明确知道：]

- 每个 GPU 要向其他 GPU 发送多少个 token
- 每个 GPU 会收到多少个来自远程的 token
- 每个 GPU 上的本地专家需要处理多少个 token-专家对

这些信息完全决定了本层的通信总量和计算总量。**既然工作量是已知的，那就没有必要沿用离线预设的固定 SM 比例，完全可以在运行时针对当前层、当前 GPU 计算出最优的 SM 分配方案。**

::: block-1
这一范式转变，:mdnice-highlight[把 MoE 的计算通信重叠从“离线配置的固定策略”升级为“基于实时负载的动态调度”，从根源上解决了空间维度的资源不匹配问题。]
:::

### 2.2 双维度调度的整体架构

> 光解决空间维度的浪费还不够，时间维度的流水线气泡同样会损失大量性能。**Weave 同时从空间和时间两个维度入手，用统一的代价模型做联合优化。**

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/12.jpg)

::: image-caption
图 7：Weave 系统整体架构。系统以路由结果作为软件输入（坐上）、以通信带宽和计算吞吐量曲线作为硬件输入（右上），在持久MegaKernel内部沿两个维度做出运行时决策：空间调度器负责 SM 在通信与计算间的划分，时间调度器负责两类工作单元的执行协调，最终输出针对当前层的优化执行计划。这一架构的核心特点是调度完全在 GPU 内核内部完成，不需要 CPU 参与，调度开销极低。输入的路由结果提供了实时负载信息，硬件曲线提供了资源性能模型，两者结合让代价模型可以快速算出最优配置。持久MegaKernel则消除了多内核启动开销，同时提供了统一的调度域，让跨操作的资源调度成为可能。
:::

> 如上图所示，Weave 的整体架构由输入层、持久MegaKernel、调度器三部分组成，我们依次来看：

输入分为两类：软件输入是每层的路由结果，决定了各 GPU 的通信量和计算量；硬件输入是校准后的通信带宽曲线和计算吞吐量曲线，也就是不同 SM 数量下对应的带宽和算力。

所有逻辑都运行在一个持久MegaKernel（Persistent Megakernel）中，这个内核融合了 MoE 层的全部五个操作（分发、GEMM0、激活、GEMM1、聚合），消除了内核启动开销，同时提供了更大的调度空间。

内核内部包含两个调度器：

- 空间调度器：决定把多少个 SM 分配给通信任务，多少个分配给计算任务，匹配当前层的通计比
- 时间调度器：决定两类任务的执行顺序，通过分块流水线和气泡窃取减少 SM 空闲时间

**两个调度器通过一个轻量级代价模型统一求解，在微秒级的时间内算出当前层的最优调度方案，然后内核按照方案执行**。整个决策过程都在 GPU 内核内部完成，不需要 CPU 参与，开销极低。

## 三、空间调度器：按真实负载动态切分 SM 资源

### 3.1 每层每 GPU 的工作量建模

> **要算出最优的 SM 分配比例，首先得把当前层的通信量和计算量量化出来**。Weave 基于路由结果，对每个 GPU 独立计算三类工作量。

首先定义基础参数：

- $N$：单个 GPU 的总 SM 数量（H100 为 132）
- $c$：分配给通信任务的 SM 数量，剩余 $N-c$ 个用于计算
- $H$：模型隐藏层维度
- $I$：每个专家 FFN 的中间层维度
- $B=2H$：单个 token 的通信字节数（BF16 格式每个元素 2 字节）

路由完成后，可以得到三个关键计数：

- $X_{local}$：路由到本地专家的本地 token 数量
- $X_{in}$：路由到本地专家的远程 token 总数（含重复）
- $X_{in}^{uniq}$：去重后的远程 token 数量（同一个 token 可能被多个本地专家选中，只传输一次）

> 由此可以算出三类工作量：

计算工作量，也就是所有本地专家需要完成的矩阵乘法总量：

$$
W_{comp} = (X_{local} + X_{in}) \cdot 6HI \quad \text{FLOPs}
$$

分发阶段的通信工作量，只需要传输去重后的远程 token：

$$
W_{dispatch} = X_{in}^{uniq} \cdot B \quad \text{字节}
$$

聚合阶段的通信工作量，每个 token-专家对都要返回一个结果，所以用去重前的数量：

$$
W_{combine} = X_{in} \cdot B \quad \text{字节}
$$

**这里特别解释下去重的意义：在 top-k 路由中，同一个远程 token 可能被本地的多个专家同时选中。如果不做去重，同一个 token 就会被传输多次，浪费带宽**。现有系统通常把去重作为一个独立操作放在计算前，而 :mdnice-bold-italic[Weave 把去重融合到了分发阶段，进一步减少了开销。]

### 3.2 最优通信 SM 数的求解逻辑

> 有了工作量，再结合不同 SM 数量下的硬件吞吐量，就能算出每种 SM 分配对应的总延迟，然后找到延迟最小的那个最优解。

硬件吞吐量有两个关键曲线：

- $BW(c)$：$c$ 个通信 SM 对应的 NVLink 带宽
- $TFLOPS(N-c)$：$N-c$ 个计算 SM 对应的 GEMM 吞吐量

**这两个曲线都不是线性的**。通信带宽随着 SM 数增加先线性增长，很快就达到饱和峰值，之后再加 SM 也不会更快。计算吞吐量随着 SM 数增加增长，但受限于功耗和缓存，也是亚线性增长。

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/13.jpg)

::: image-caption
图 4：SM 分区策略对计算通信重叠效果的性能影响，测试环境为 4 卡 H100 SXM、6 款主流 MoE 模型、prefill 序列长度 8192、专家并行度 4、BF16 精度。三张子图分别从通信带宽、计算吞吐量、总延迟三个维度完整呈现了 SM 分区的性能规律。其核心结论是：SM 分配存在最优平衡点，且该点随模型负载特征变化而移动。这一规律是空间调度器的理论基础，证明了动态调整 SM 比例的必要性和可行性。
:::

然后引入一个经验校准的 Tile 级重叠率 $\alpha$，表示有多少比例的通信可以和计算重叠，剩下的 $1-\alpha$ 作为尾部暴露在外。由此可以算出三个时间分量：

计算时间：

$$
T_{comp} = \frac{W_{comp}}{TFLOPS(N-c)}
$$

总通信时间（分发+聚合）：

$$
T_{comm} = \frac{W_{dispatch} + W_{combine}}{BW(c)}
$$

无法重叠的尾部时间：

$$
T_{tail} = (1-\alpha) \cdot \frac{W_{combine}}{BW(c)}
$$

整个 MoE 层的总延迟由两条路径中较慢的那条决定，再加上无法重叠的尾部：

$$
T_{total} = max\left(T_{comp} + T_{tail}, T_{comm}\right)
$$

空间调度器的目标就是找到最优的通信 SM 数 $c^*$，让总延迟 $T_{total}$ 最小：

$$
c^* = arg\min_c \ T_{total}
$$

这个逻辑的本质就是**让通信带宽和计算吞吐量刚好匹配**，不让任何一方提前完成后闲置等待。

- 如果计算慢，就多给计算分配 SM；
- 如果通信慢，就多给通信分配 SM。

由于每个 GPU 的路由结果不一样，每个 GPU 的最优 $c^*$ 也不一样，真正做到了每层每 GPU 的精细化适配。

## 四、时间调度器：用流水线与气泡窃取消除空闲间隙

### 4.1 分块流水线：打散 Combine 以实现细粒度重叠

> 就算 SM 比例调得再优，原始的执行顺序下，通信 SM 还是会在中间的计算阶段闲下来。**因为聚合必须等所有计算都做完才能开始，中间一大段时间通信 SM 都没事干，形成“中间气泡”。**

**为了消除这个中间气泡，Weave 提出了分块流水线机制：把所有 token 拆成 K 个小块（Chunk），每个块独立完成计算和聚合**。这样一来，第 0 块的聚合就可以和第 1 块的计算重叠执行，通信 SM 就不用等到所有计算都做完才开始工作。

具体来说，GEMM0、激活、GEMM1、聚合都拆成 K 个块，只有分发不拆分，尽可能早地把所有 token 发出去，给计算争取时间。:mdnice-bold-italic[当然，分块不是越多越好。K 越大，每个块的 token 数越少，GEMM 的计算效率就越低。论文测试显示，当 K=8 时，单块 GEMM 的吞吐量比 K=1 时下降了约 27%。]

> 为了量化这种影响，Weave 引入了分块效率因子 $eff_{chunk}(K)$，表示分块后的 GEMM 吞吐量与不分块时的比值。分块后的计算时间就变成：

$$
T_{comp}(c, K) = \frac{W_{comp}}{TFLOPS(N-c) \cdot eff_{chunk}(K)}
$$

同时，分块后只有最后一个块的聚合会作为尾部暴露，尾部时间缩小为原来的 1/K：

$$
T_{tail} = (1-\alpha) \cdot \frac{W_{combine}}{BW(c) \cdot K}
$$

:mdnice-bold-italic[K 的选择就是在“更小的尾部时间”和“更低的计算效率”之间做权衡。K 太小，尾部时间长；K 太大，计算掉速多。最优值就是两者平衡的点。]

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/14.jpg)

::: image-caption
图 8：空间调度器与时间调度器各阶段的执行效果细节对比，逐步展示每种优化机制带来的改进。 四张子图呈现了优化的递进过程：从基线的大空闲气泡，到空间调度缩小气泡，再到分块流水线进一步压缩气泡，最后到气泡窃取填满剩余间隙。图 8 (a)：基线模式（配置 c 个通信 SM）。已启用计算通信重叠，但没有时间维度调度，执行时间线中间存在较大的空闲气泡。图 8 (b)：加入空间调度优化。将通信 SM 数量调整到最优值 c*，中间空闲气泡的宽度有所减小。图 8 (c)：加入分块流水线时间调度（分块数 K=2）。将 token 拆分为多个微批次，创造了更多重叠机会，中间气泡进一步缩小。图 8 (d)：加入气泡窃取机制的完整 Weave 方案。利用空闲的通信 SM 执行 GEMM 计算 Tile，填满了剩余的中间气泡。每一步优化都针对性地解决了一部分资源浪费，最终实现了接近满负载的 SM 利用。这个递进过程清晰展示了 Weave 双维度调度的优化逻辑和每层机制的具体作用。
:::

### 4.2 气泡窃取：让空闲通信 SM 转去执行计算任务

> 分块流水线虽然大大缩小了中间气泡，但还是会有残留的空闲时间**。尤其是分发刚结束、第一批计算还没完成的间隙，通信 SM 还是处于空闲状态。**

**为了把这部分残留间隙也利用起来，Weave 设计了气泡窃取机制**：:mdnice-bold-italic[分发阶段结束后，通信 SM 如果暂时没有通信任务，就可以转去帮忙做 GEMM 计算，相当于“偷”一些计算任务来做，把空闲时间填满。]

::: block-1
为什么不把窃取分散在每个分块的聚合间隙？因为 SM 在通信角色和计算角色之间切换是有开销的，如果频繁切换，反而会得不偿失。Weave 选择把所有窃取的计算集中在分发结束后、聚合开始前，一次性完成角色切换，这样既利用了空闲时间，又避免了频繁切换的开销。
:::

窃取的计算量怎么算？首先算出分发阶段的总时长：

$$
t_{comm}(c) = \frac{W_{comm}}{BW(c)}
$$

在这段时间里，计算 SM 已经完成了一部分 GEMM 工作：

$$
W_{partial}(c) = t_{comm}(c) \cdot TFLOPS(N-c)
$$

剩下还没完成的 GEMM 工作量就是需要被窃取的部分：

$$
W_{steal}(c) = max\left(0, W_{comp} - W_{partial}(c)\right)
$$

分发结束后，所有 N 个 SM 都可以参与计算，所以这些待窃取的工作量由全部 SM 平分。每个 SM 窃取的 GEMM Tile 数为：

$$
n_{steal}(c) = \frac{W_{steal}(c)}{N \cdot W_{tile}}
$$

其中 $W_{tile}$ 是单个 GEMM Tile 的计算量。通过这种方式，原本空闲的通信 SM 在分发完成后立刻投入计算，直到聚合任务开始再切换回来，最大限度地减少了空闲时间。

## 五、统一代价模型与 Megakernel 工程实现

### 5.1 联合搜索最优(c, K)配置

> 空间调度的最优 c 和时间调度的最优 K 不是独立的，因为 c 会影响通信和计算的速度比，进而影响分块和窃取的效果。所以必须把两个变量放在一起联合搜索。

把分块效率和尾部缩放代入总时间公式，就得到了关于 c 和 K 两个变量的总延迟函数：

$$
T_{total}(c, K) = max\left(T_{comp}(c, K) + T_{tail}(c, K), T_{comm}(c)\right)
$$

调度器的目标就是找到最优的 $(c^*, K^*)$ 组合，让总延迟最小：

$$
(c^*, K^*) = arg\min_{c,K} \ T_{total}(c, K)
$$

论文通过实测验证了这个优化空间的单峰性：在 DSv2-Lite 模型、序列长度 8192 的测试中，延迟网格存在唯一清晰的最优点，位于 c=40、K=4，延迟 1.365ms。这说明 c 和 K 确实需要联合求解，分开独立优化达不到最优效果。

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/15.jpg)

::: image-caption
图 9：分块拆分的性能损耗特性，以及 (c, K) 二维参数空间的联合搜索最优解验证。 两张图共同说明了时间调度的核心权衡逻辑：分块能带来更多重叠收益，但也会导致计算效率下降。左图量化了分块的代价，分块越细，每个块的 token 数越少，矩阵乘法的计算效率越低。这是因为小矩阵无法充分利用 GPU 的并行计算能力，缓存命中率也会下降。分块流水线的优化必须在 “更多重叠收益” 和 “更低计算效率” 之间做权衡，不能无限制增加分块数。；右图验证了不同 (c, K) 配置组合下的实测延迟网格，存在唯一清晰的单峰最优值，验证了联合搜索的必要性。这为统一代价模型的设计提供了实证依据，证明了联合优化的可行性和必要性。

### 5.2 持久 MegaKernel 的落地细节

> 整个调度逻辑都实现在一个持久MegaKernel中，这是 Weave 工程实现上的核心特点。这种设计既消除了多内核启动的开销，又让调度决策可以在 GPU 内部直接完成，不需要 CPU 介入。

**Weave 基于 ParallelKittens 构建，整个 MoE 层的五个操作全部融合在一个内核里，内核启动时的 grid 大小就等于 GPU 的 SM 总数（H100 上是 132）**。内核启动后会一直驻留在 GPU 上，每层路由完成后，把路由结果作为参数传给内核，内核内部立刻执行代价模型，算出当前层的 $c*$和 $K*$。

具体的执行流程：

1. 路由完成后，路由结果传入内核
2. 内核 prologue 阶段运行代价模型，计算最优$(c*, K*)$和每个 SM 的窃取 Tile 数
3. 根据 blockIdx.x 分配 SM 角色：索引小于 $c*$的是通信 SM，负责分发和聚合；其余是计算 SM，负责 GEMM 和激活
4. 所有 SM 按照分块流水线的 DAG 顺序，通过原子加全局计数器动态领取任务 Tile
5. 分发完成后，通信 SM 窃取指定数量的 GEMM Tile 执行
6. 最后聚合阶段，所有 SM 全部参与，消除尾部空闲

除此之外，**Weave 还把 token 去重融合进了分发阶段**。路由完成后就可以识别出重复的远程 token，通信 SM 在分发时如果发现是重复 token，直接从本地 HBM 缓冲区读取，不需要再跨 GPU 传输，也不需要额外的去重操作步骤。

整个代价模型的运行开销极低：在 DSv3 模型上，代价模型的开销稳定在 0.54 微秒左右，不到 MoE 层时间的 0.021%，完全可以忽略不计。这保证了运行时调度不仅效果好，而且自身几乎没有成本。

## 六、实验评测：全面碾压五大 SOTA 基线

### 6.1 实验设置与评测对象

> 论文在 4 卡 H100 SXM 平台上完成了全面评测，覆盖 6 个主流 MoE 模型、3 种序列长度，对比 5 个现有 SOTA 系统，维度包括单层延迟、端到端延迟、硬件利用率等。

- 软件环境：CUDA Toolkit 12.9.86，NCCL 2.21.5，PyTorch 2.6.0。

- ParallelKittens（PK）：编译时固定 SM 分区，融合分发与上投影

这个结果的含金量在于，Weave 的优势是全场景的一致领先。这说明动态 SM 调度的思路具有普适性，对各种 MoE 架构都有效。

### 6.3 硬件利用率与消融实验验证

> 为什么 Weave 能带来这么大的提升？从硬件利用率指标可以看得很清楚：它同时实现了最高的 SM 活跃度、最高的互联与计算利用率，以及最高的计算通信重叠率。

论文用 Nsight Systems 做了性能剖析，对比了四个核心指标：

- SM 活跃率：SM 处于工作状态的时间比例
- NVLink 利用率：互联带宽的使用程度
- Tensor Core 利用率：张量核心的使用程度
- 重叠率：NVLink 和 Tensor Core 同时处于活跃状态的时间比例

![文章插图](/articles/2026-09-24-weave-moe-megakernel-sm-deepep-ef539fa0/images/19.jpg)

::: image-caption
图 11：MoE 前向传播窗口内的聚合 GPU 性能指标对比，测试基于 DSv2-Lite 模型、序列长度 2048、4 卡 H100、专家并行度 4。四项核心硬件指标全面领先，清晰解释了 Weave 性能优势的来源：通过空间调度匹配通信与计算的资源比例，提升了带宽和算力的利用效率；通过时间调度消除空闲气泡，提升了 SM 的活跃时间；两者共同作用实现了极高的计算通信重叠率，最终转化为延迟的大幅降低。这组数据从硬件底层验证了 Weave 调度机制的有效性。
:::

Weave 的 SM 活跃率达到 91.3%，计算通信重叠率达到 47.1%，都远高于第二名。而基线系统中，重叠率最高的 Comet 也只有 14.3%，DeepEP 只有 9.2%。

高重叠率的背后是三个设计的共同作用：空间调度让通信和计算的速度刚好匹配，不会一方早早干完；分块流水线把聚合打散到计算阶段中，延长了通信的时间窗口；气泡窃取把通信 SM 的空闲时间都用来做计算，没有浪费。

整体看下来，Weave 核心在于:mdnice-highlight[首次将 MoE 计算通信重叠的粒度从迭代级细化到了层级]，通过路由感知的运行时动态调度，同时解决了空间资源不匹配和时间空闲气泡两个维度的浪费，最终实现了硬件利用率的全面提升。
:::

## 七、总结与展望

> 本文介绍的 Weave 系统，是首个基于每层路由结果实现细粒度动态 SM 调度的 MoE 计算通信重叠系统。它抓住了“路由完成后工作量完全可知”这一核心洞察，通过空间+时间双维度的运行时调度，打破了传统静态分区策略的性能天花板。

论文的核心贡献可以总结为三点：

1. 指出了:mdnice-bold-italic[路由感知的 SM 调度是分布式 MoE 推理的关键优化点，证明了 SM 分区必须根据每层每 GPU 的路由结果动态选择]
2. 设计了空间+时间双维度调度器，通过动态 SM 分区、分块流水线、气泡窃取三种机制，最大化 GPU 资源利用率
3. 基于持久MegaKernel实现了完整系统，在主流 MoE 模型上取得了显著的性能提升，代码即将开源

当然，这项工作也有其局限性。目前的验证仅在 4 卡 H100 单节点、专家并行度为 4 的场景下完成，**更大规模的 GPU 集群、多节点部署场景下的效果还有待验证。未来工作将向更多 GPU 数量和多节点配置扩展。**

::: block-1
总的来说，:mdnice-highlight[Weave 代表了 MoE 推理优化的一个重要方向：从静态的、离线的优化策略，转向动态的、运行时的、感知负载的自适应调度]。随着 MoE 模型成为大模型的主流架构，**这类细粒度的运行时优化技术将会越来越重要，成为推理系统比拼的核心竞争力。**
:::
