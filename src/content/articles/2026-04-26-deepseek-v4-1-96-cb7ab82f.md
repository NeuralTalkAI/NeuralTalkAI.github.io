## 关键问题

### 问题 1. 细粒度流水线在极端小批量下是否失效？

> 作者指出 RL 推演等场景存在“长尾小批量”问题，并以此作为细粒度专家并行的关键优势。但波次调度引入的流水线启动与排空开销，**在批量极小时是否反而会吞噬重叠收益？当单个波次的计算量低于通信启动延迟时，这套方案的加速比是否会急剧退化，甚至劣于粗粒度方案？**

不但不会失效，反而恰是该方案的设计目标与最大优势所在。

DeepSeek 明确指出，RL 推演等场景存在"长尾小批量数据"问题，:mdnice-bold-italic[传统专家并行方案在批量较小时通信开销占比急剧上升，因为缺乏足够计算来隐藏通信时延。 细粒度专家并行正是为解决这一痛点而设计：将专家拆分为多个波次后，每个波次仅包含少量专家，当一个波次完成通信后其计算可立即启动，无需等待其他波次]。在稳态运行时，当前波次的计算、下一波次的 Token 传输、已完成专家的结果回传三者同步执行。**这意味着即使在极小批量下，只要单个波次的计算量足以覆盖通信启动延迟，流水线就能保持连续运转。**

实测结果也支撑这一结论：方案在强化学习推演、高速智能体服务等时延敏感场景中最高加速比达1.96倍，显著高于通用推理任务的1.50~1.73倍。:mdnice-bold-italic[这表明极端小批量场景非但没有导致性能退化，反而因更充分暴露了传统方案的通信瓶颈，使得细粒度重叠的收益被进一步放大。 启动与排空开销确实存在，但波次数量与专家总数相关而非批量大小，因此在设计上已对常见负载做了适配。]

### 问题 2. “计算通信比”公式是否过度简化了现实？

> 作者在单层 MoE 的计算-通信比分析中给出公式 $\frac{C}{B} \leq 2d=6144$（$C$ 为峰值计算吞吐量，$B$ 为互联带宽，$d$ 为中间维度），据此认为一旦带宽跨过该阈值，通信便可完全隐藏于计算，不再构成瓶颈。:mdnice-bold-italic[但该推导【仅】考虑单一 MoE 层的算术强度，完全忽略了多层堆叠时的流水线气泡、节点内拓扑竞争、以及通信与计算在片内资源（如 SM、内存带宽）上的争夺。在真实多节点训练中，该理想阈值是否具有实际指导意义？]

该公式是带有明确前提的理想化推导，DeepSeek 对此有清醒认知且并未声称其覆盖所有实际约束。

首先，:mdnice-bold-italic[该公式聚焦于单一 MoE 层内的通信与计算关系，旨在回答一个具体问题：在什么条件下，通信时延可以被计算完全隐藏？答案清晰——当互联带宽满足 $\frac{C}{B} \leq 2d=6144$ 时，每 1 GBps 带宽可支撑 6.1TFLOP/s 计算量并隐藏通信。这一结论的实践价值在于为硬件设计设定参照系]，作者紧接着明确指出："**一旦带宽达到该阈值，便不再成为瓶颈，继续增加芯片面积提升带宽会带来边际收益递减** "，这恰好说明公式并非要描述全系统行为，而是要划定带宽投入的收益边界。

其次，论文专门用"观察与建议"一节讨论了公式未覆盖的现实问题：功耗节流在全并发负载下成为核心性能限制因素；通信原语的推送/拉取模式选择影响实际时延；激活函数类型改变算术强度等。:mdnice-bold-italic[这表明作者将理想推导与工程约束分层处理——公式用于硬件设计方向判断， 具体部署中的拓扑竞争、资源争抢等问题则通过内核融合、波次调度、功耗预算建议等工程手段分别应对。因此该公式是有限范围的可用分析工具，而非对系统复杂性的全盘简化。]

## 一、专家并行中的细粒度通信-计算重叠

混合专家模型（MoE）可通过专家并行（EP）实现加速，但专家并行需要复杂的节点间通信，对互联带宽与时延提出极高要求。**为缓解专家并行的通信瓶颈，在更低互联带宽要求下实现更高的端到端性能，DeepSeek-V4 提出一种细粒度专家并行方案，将通信与计算融合为单一流水线内核，实现通信与计算的重叠执行。**

### 1.1 通信时延可被隐藏

> 本专家并行方案的核心思路是，MoE 层的通信时延能够被有效隐藏在计算过程中。

![文章插图](/articles/2026-04-26-deepseek-v4-1-96-cb7ab82f/images/03.webp)

### 1.2 细粒度专家并行方案

> 为进一步降低互联带宽需求、放大重叠执行的收益，DeepSeek-V4 提出更细粒度的专家拆分方案。受多项相关研究（Aimuyo et al., 2025; Zhang et al., 2025b）启发，DeepSeek-V4**将专家拆分并调度为多个波次，每个波次包含少量专家。**

**当一个波次内的所有专家完成通信后，计算可立即启动**，无需等待其他专家。:mdnice-bold-italic[稳态运行时，当前波次的计算、下一波次的 Token 传输、已完成专家的结果回传可同步执行，如图 5 所示。]

### 1.4 观察与建议

> DeepSeek-V4 分享内核研发的观察与经验，并向硬件厂商提出建议，以期助力高效硬件设计，实现更优的软硬件协同设计：

- **计算通信比**：通信与计算的完全重叠取决于计算通信比，而非单纯的带宽大小。设峰值计算吞吐量为 $C$，互联带宽为 $B$，当 $\frac{C}{B} \leq \frac{V_{comp}}{V_{comm}}$ 时，通信可被完全隐藏，其中 $V_{comp}$ 为计算量，$V_{comm}$ 为通信量。对于 DeepSeek-V4-Pro 模型，每个 Token -专家对需要 6hd 次 FLOP 运算（SwiGLU 门控、向上投影、向下投影），仅需 3h 字节通信量（FP8 分发+BF16 合并），公式可简化为：$\frac{C}{B} \leq 2d=6144 \text{ FLOPs/Byte}$:mdnice-bold-italic[即每 1GBps 的互联带宽，足以支撑 6.1TFLOP/s 的计算量并隐藏通信时延。一旦带宽达到该阈值，便不再成为瓶颈，继续增加芯片面积提升带宽会带来边际收益递减。DeepSeek-V4建议未来硬件设计瞄准此类平衡点，而非无条件提升带宽。]
- **功耗预算**：极致的内核融合会让计算、内存、网络同时处于高负载状态，:mdnice-bold-italic[功耗节流成为核心性能限制因素。DeepSeek-V4建议未来硬件设计为这类全并发工作负载提供充足的功耗余量。]
- **通信原语**：本方案采用拉取式通信方式，每个 GPU 主动从远程 GPU 读取数据，避免了细粒度推送式通信带来的高通知时延。:mdnice-bold-italic[未来具备更低时延跨 GPU 信令的硬件，将让推送式通信具备可行性，实现更自然的通信模式。]
- **激活函数**：DeepSeek-V4建议用**低成本的逐元素激活函数替代 SwiGLU，该激活函数无需指数或除法运算**，直接减轻矩阵乘法后的处理压力。:mdnice-bold-italic[在相同参数预算下，移除门控投影可扩大中间维度 $d$，进一步降低带宽需求。]

## 二、基于 TileLang 的灵活高效内核开发

> 在实际应用中，复杂的模型架构会产生数百个细粒度的 Torch ATen 算子。DeepSeek-V4采用 TileLang（Wang et al., 2026）开发了一套融合内核，替代了绝大多数原生算子，以极低的研发成本实现了最优性能。该语言还支持在验证阶段快速实现注意力变体等算子原型。这些内核在模型架构研发、大规模训练，以及最终推理服务的生产部署中都发挥着关键作用。

作为领域特定语言（DSL），TileLang 平衡了研发效率与运行时性能，支持快速开发，同时可在同一代码库中完成深度迭代优化。此外，DeepSeek-V4与 TileLang 社区紧密协作，打造更敏捷、高效、稳定的内核开发流程。

### 2.1 通过主机代码生成降低调用开销

> **随着加速器性能持续提升，CPU 侧的调度开销愈发突出**。对于小型、高度优化的内核，这类固定的主机开销极易限制硬件利用率与吞吐量。这类开销的常见来源是，主机侧逻辑（如运行时约束检查）通常采用 Python 编写以保证灵活性，每次调用都会产生固定开销。

**DeepSeek-V4通过主机代码生成缓解这一开销，将大部分主机侧逻辑迁移至生成的主机代码中**。具体而言：

- DeepSeek-V4首先在中间表示（IR）层协同生成设备内核与轻量级主机启动器，嵌入从语言前端解析的必要元数据（如数据类型、秩/形状约束、步幅/布局假设）。
- 随后，启动器被编译为基于 TVM-FFI（Chen et al., 2018）框架的主机源码，其紧凑的调用约定与零拷贝张量互操作能力共同将主机侧开销降至最低。
- 运行时，生成的主机代码负责参数校验与封装，将每次调用的检查逻辑移出 Python 执行路径。

::: block-1
测试结果显示，**CPU 侧校验开销从每次调用数十至数百微秒，降至 1 微秒以内。**
:::

### 2.2 SMT 求解器辅助的形式化整数分析

> TileLang 内核涉及复杂的张量索引运算，需要强大的形式化整数分析能力。在布局推导、内存冲突检测、边界分析等编译流程中，编译器必须验证整数表达式是否满足特定属性，才能开启对应优化。**因此，更强的形式化分析能力可解锁更高级、更复杂的优化可能。**

为此，DeepSeek-V4**将 Z3 SMT 求解器（De Moura and Bjørner, 2008）集成到 TileLang 的代数系统中**，为张量程序中的绝大多数整数表达式提供形式化分析能力。

DeepSeek-V4:mdnice-bold-italic[将 TileLang 整数表达式转换为 Z3 的无量词非线性整数算术（QF_NIA）表达式，在计算开销与形式化表达能力之间取得平衡]。基于整数线性规划（ILP）求解器的 QF_NIA，可无缝解决内核中常见的标准线性整数表达式；其内置的非线性推理能力，还能有效应对可变张量形状向量化等高级挑战。**在合理的资源限制下，Z3 显著提升了整体优化性能，同时将编译时间开销控制在数秒内。** 该优化在向量化、屏障插入、代码简化等多个编译流程中效果显著。

### 2.3 数值精度与比特级可复现性

> **在生产环境中，数值正确性与可复现性和原始吞吐量同等重要**。因此，DeepSeek-V4默认**优先保证精度**：:mdnice-bold-italic[在编译器层面禁用快速数学优化，仅通过显式可选的前端算子（如 `T.exp、T.log、T.__sin`）提供影响精度的近似计算]。反之，当需要严格遵循 IEEE-754 语义时，TileLang 提供符合 IEEE 标准、带显式舍入模式的内在函数（如 T.ieee_fsqrt、T.ieee_fdiv、T.ieee_add），让开发者可精准指定数值行为。

DeepSeek-V4还实现了**比特级可复现性，用于将内核与手写 CUDA 基线进行校验**。通过将 TileLang 的代数简化与编译规则与主流 CUDA 工具链（如 NVCC）对齐，避免因代码转换引入非预期的比特级差异。**布局注解** （如 `T.annotate_layout`）可让用户锁定布局相关的编译决策，保持计算与累加顺序和参考 CUDA 实现一致，从而在需要时实现比特级完全一致的输出。

::: block-1
测试结果表明，这些**面向精度与可复现性的设计并未牺牲性能：在保守默认配置下，TileLang 内核仍保持竞争力**，同时支持开发者选择性放宽数值约束以换取更高速度。
:::

## 三、高性能批不变与确定性内核库

为实现高效训练与推理，DeepSeek-V4研发了一套完整的高性能计算内核。除基础功能与最大化硬件利用率外，核心设计目标是保障训练可复现性，以及预训练、后训练与推理流程间的比特级对齐。因此，DeepSeek-V4实现了**端到端、比特级批不变、确定性的内核，且性能开销极低**。这些内核有助于调试、稳定性分析与一致的后训练行为。

### 3.1 批不变性

> 批不变性确保任意给定 Token 的输出，与其在批次中的位置无关，保持比特级完全一致。实现批不变性的核心挑战如下：

- **注意力**：要实现批不变性，无法使用拆分 KV 方法（Dao et al, 2023）——该方法将单序列的注意力计算分配到多个流多处理器（SM）以均衡负载，但放弃该技术会引发严重的波量化问题，影响 GPU 利用率。为解决该问题，DeepSeek-V4为批不变解码设计了双内核策略：为保证两个内核的比特级一致性，:mdnice-bold-italic[精心设计第二个内核的计算路径，使其累加顺序与第一个内核完全一致]。此外，:mdnice-bold-italic[第二个内核利用线程块集群内的分布式共享内存，实现 SM 间高速数据交换]。该双内核方法将批不变解码的开销控制在可忽略的水平。
- **矩阵乘法**：传统 cuBLAS 库（NVIDIA Corporation, 2024）无法实现批不变性，因此DeepSeek-V4用 DeepGEMM（Zhao et al., 2025）完整替代它。此外，极小批量场景下，传统实现通常采用拆分 K 技术（Osama et al., 2023）提升性能，但该技术无法保证 DeepSeek-V4 所需的批不变性。

因此DeepSeek-V4在绝大多数场景下放弃拆分 K 技术，这可能导致性能下降。为解决该问题，DeepSeek-V4引入一系列优化，让矩阵乘法实现在主流场景中达到甚至超越标准拆分 K 的性能。

### 3.2 确定性

> 确定性训练对软硬件问题调试极具价值；当训练出现损失激增等异常时，确定性可帮助研究者更精准定位数值原因，优化模型设计。**训练中的不确定性通常源于非确定性累加顺序，多由原子加法指令导致，该问题主要出现在反向传播阶段**，具体场景如下：

- **注意力反向传播**：传统稀疏注意力反向传播实现中，**采用原子加法累加 KV Token 的梯度，浮点加法的非结合性会引发不确定性**。为解决该问题，DeepSeek-V4 :mdnice-bold-italic[为每个 SM 分配独立的累加缓冲区，再对所有缓冲区执行全局确定性求和。]
- **MoE 反向传播**：不同节点的多个 SM 同时向目标节点的同一缓冲区写入数据时，写入位置协商会引发不确定性。:mdnice-bold-italic[为解决该问题，DeepSeek-V4设计单节点内的 Token 顺序预处理机制，结合多节点缓冲区隔离策略]，保证专家并行的发送结果与 MoE 反向传播累加顺序的确定性。
- **mHC 中的矩阵乘法**：mHC 的矩阵乘法输出维度仅为 24，极小批量场景下必须使用拆分 K 算法（Osama et al., 2023），原生实现会引发不确定性。为解决该问题，:mdnice-bold-italic[分别输出每个拆分部分，再通过后续内核执行确定性归约]，兼顾性能与确定性。

## 四、FP4 量化感知训练

> 为实现部署阶段的推理加速与内存节省，DeepSeek-V4在后训练阶段引入量化感知训练（QAT）（Jacob et al., 2018），让模型适应量化带来的精度损失。

DeepSeek-V4 对两个组件应用 FP4（MXFP4）量化（Rouhani et al., 2023）：

1. MoE 专家权重，这是 GPU 内存占用的主要来源（OpenAI, 2025）；
2. 压缩稀疏注意力（CSA）索引器中的查询-键（QK）通路，该通路的 QK 激活值全程以 FP4 格式缓存、加载与相乘，加速长上下文场景的注意力分数计算。

::: block-1
此外，DeepSeek-V4 在量化感知训练过程中，将索引分数 $I_{:,:}$ 从 FP32 量化为 BF16，该优化让 Top-K 选择器速度提升 2 倍，同时保持 99.7%的 KV 条目召回率。
:::

对于 MoE 专家权重，遵循量化感知训练的常规流程，优化器维护的 FP32 主权重先被量化为 FP4，再反量化为 FP8 用于计算。:mdnice-bold-italic[值得注意的是，本方案的 FP4 转 FP8 反量化是无损的——FP8（E4M3）相比 FP4（E2M1）多 2 个指数位，动态范围更大。只要每个 FP8 量化块（128×128 tile）内的 FP4 子块（1×32 tile）缩放因子的最大/最小值之比不超过特定阈值，细粒度缩放信息就能被 FP8 扩展的动态范围完全吸收]。实验验证当前权重满足该条件，这让整套量化感知训练流程可直接复用现有 FP8 训练框架，无需修改。反向传播阶段，梯度基于前向传播的 FP8 权重计算，直接回传到 FP32 主权重，等价于在量化操作中应用直通估计器（STE），同时避免了权重转置后的重新量化。

**在不涉及反向传播的强化学习训练推理与推演阶段，DeepSeek-V4直接使用真实 FP4 量化权重，而非模拟量化**。这保证了模型采样行为与线上部署完全一致，同时减少内核内存加载，实现实际加速并显著降低内存消耗。CSA 索引器的 QK 通路采用相同处理方式。

## 五、训练框架

本训练框架**基于 DeepSeek-V3（DeepSeek-AI, 2024）的可扩展高效基础设施构建**。在 DeepSeek-V4 的训练中，**DeepSeek-V4继承这一稳健基础，同时引入多项关键创新**，适配 Muon 优化器、mHC、混合注意力机制等新型架构组件，保持高训练效率与稳定性。

### 5.1 Muon 优化器的高效实现

> Muon 优化器需要完整梯度矩阵计算参数更新，**这与零冗余优化器（ZeRO）（Rajbhandari et al., 2020）结合时存在冲突**。传统 ZeRO 为 AdamW 等逐元素优化器设计，单参数矩阵可在多节点间拆分并更新。**为解决该冲突，DeepSeek-V4为 Muon 设计了 ZeRO 桶分配的混合策略。**

- **对于稠密参数，DeepSeek-V4限制 ZeRO 并行的最大规模，采用背包算法将参数矩阵分配到各节点，保证每个节点的负载大致均衡**。每个节点的桶会被填充至与全局最大桶尺寸一致，便于高效执行归约散射操作。在DeepSeek-V4 的配置中，每个节点管理不超过 5 个参数矩阵，填充带来的内存开销通常低于 10%。:mdnice-bold-italic[当数据并行总规模超过 ZeRO 限制时，DeepSeek-V4在额外的数据并行组中冗余计算 Muon 更新，用计算量换取桶总内存的降低。]
- **对于 MoE 参数，DeepSeek-V4独立优化每个专家**：先将所有层所有专家的 SwiGLU（Shazeer, 2020）向下投影矩阵展平，再展平向上投影矩阵与门控矩阵，随后填充展平向量，确保可在所有节点间均匀分配，且不拆分任何逻辑独立矩阵。由于专家数量庞大，DeepSeek-V4不对 MoE 参数设置 ZeRO 并行限制，填充开销同样可忽略。

此外，每个节点上相同形状的连续参数会自动合并，支持牛顿-舒尔茨迭代的批量执行，提升硬件利用率。**还发现，Muon 的牛顿-舒尔茨迭代在 BF16 矩阵乘法下仍保持稳定。基于该特性，将数据并行节点间同步的 MoE 梯度以随机舍入方式量化为 BF16 精度，将通信量减半**。为避免低精度加法器引发的累加误差，用两阶段方法替代传统的树形/环形归约散射集合通信：首先通过全交换操作在节点间交换局部梯度，再由每个节点以 FP32 执行局部求和，保证数值鲁棒性。

### 5.2 mHC 的低成本低内存实现

> 相比传统残差连接，mHC 的引入同时增加了激活内存占用与流水线阶段间的通信量。为缓解这些开销，实施多项优化策略：

1. 为训练与推理精心设计并实现 mHC 融合内核；
2. 引入重计算策略，选择性对中间张量进行检查点保存，重计算层间大部分隐藏状态与所有归一化层输入，同时避免重计算计算密集型操作，平衡内存节省与计算开销；
3. 调整 DualPipe 1F1B 重叠方案，适配增加的流水线通信，让 mHC 的部分操作可并发执行。

这些优化将 mHC 的实际时间开销控制在重叠 1F1B 流水线阶段的 6.7%以内。更多工程优化细节详见 mHC 专项论文（Xie et al., 2026）。

### 5.3 长上下文注意力的上下文并行

> 传统上下文并行（CP）对序列维度进行拆分，每个节点维护连续的 $s$ 个 Token 。这给压缩注意力机制（CSA 与 HCA）带来两大挑战：

- 一方面，训练样本由多序列打包而成，每个序列独立按 $m$（或 $m'$）倍压缩，不足 $m$ 的尾部 Token 会被丢弃，导致压缩后的 KV 长度通常小于 $\frac{s}{m}$，且各节点不一致；
- 另一方面，压缩需要连续的 $m$ 个 KV 条目，可能跨相邻两个 CP 节点的边界。

> 为解决这些挑战，设计两阶段通信方案：

- 第一阶段，节点 $i$ 将最后 $m$ 个未压缩 KV 条目发送给节点 $i+1$，节点 $i+1$ 将接收的条目与本地 $s$ 个未压缩 KV 条目一同压缩，生成固定长度为 $\frac{s}{m}+1$ 的压缩条目，其中包含部分填充条目；
- 第二阶段，所有 CP 节点执行全收集操作，汇聚本地压缩 KV 条目，再通过融合选择填充算子重组为完整的压缩 KV 条目集，总长度为 cp_size×$\frac{s}{m}$，所有填充条目置于尾部。

### 5.4 面向灵活激活检查点的扩展自动微分

- **传统激活检查点实现以整个模块为粒度**，决定反向传播时保留或重计算输出激活，这种:mdnice-bold-italic[粗粒度方式在重计算成本与激活内存占用间的权衡往往不够优。]
- 另一种方案是**手动实现整层的前向与反向逻辑，显式管理张量检查点状态**，:mdnice-bold-italic[虽能实现细粒度控制，但丢失了自动微分框架的便捷性，大幅提升研发复杂度。]

> 为在不牺牲编程效率的前提下实现细粒度控制，V4 **实现了支持自动微分的张量级激活检查点机制**。开发者仅需实现前向传播，选择性注解单个张量，即可自动完成检查点保存与重计算。本:mdnice-bold-italic[框架基于 TorchFX（Reed et al., 2022）追踪完整计算图，对每个注解张量执行反向遍历，定位重计算所需的最小子图，将其定义为重计算图，并插入反向逻辑中对应梯度计算的前一步。]

相比手动实现，该设计在训练阶段无额外开销。框架中的重计算通过直接释放注解张量的 GPU 内存、复用重计算张量的存储指针实现，无 GPU 内存拷贝。此外，由于图追踪会实际执行模型，可追踪每个张量的底层存储指针，自动对共享存储的张量（如 reshape 操作的输入与输出）去重计算，让开发者无需在注解重计算时关注底层内存细节。

本推理框架**主要继承自 DeepSeek-V3，仅在 KV 缓存管理上存在差异。**

> 为高效管理 DeepSeek-V4 混合注意力机制带来的异构 KV 缓存，设计了定制化 KV 缓存布局，布局形式如图 6 所示，具体说明如下：

- **状态缓存采用固定池预分配策略**，适配 SWA 与压缩分支尾部 Token 的状态管理；
- **传统 KV 缓存以 m 和 m' 的最小公倍数设计块大小，匹配 CSA/HCA 压缩规则**。该布局兼顾异构缓存策略与稀疏注意力内核的对齐需求，实现混合注意力 KV 缓存高效调度，显著降低长上下文推理的内存占用与访问开销。

#### DeepSeek-V4 中的异构 KV 条目

> DeepSeek-V4 系列的混合注意力机制引入多种 KV 条目，其 KV 缓存尺寸与更新规则各不相同。

- 用于稀疏选择的闪电索引器为 KV 缓存引入额外维度，嵌入尺寸与主注意力不同；
- CSA 与 HCA 的压缩技术分别将序列长度缩短为 $\frac{1}{m}$ 与 $\frac{1}{m'}$，降低整体 KV 缓存尺寸，导致不同层的 KV 缓存尺寸存在差异。
- 此外，滑动窗口注意力（SWA）层同样拥有独立的 KV 缓存尺寸、缓存命中与淘汰策略。

压缩分支中，每 $m$ 个 Token 生成 1 个 KV 条目，当剩余 Token 不足压缩数量时，所有待处理 Token 及其隐藏状态需保留在缓冲区，直至压缩操作可执行，这些缓冲 Token 作为位置上下文决定的序列状态，也纳入 KV 缓存框架管理。

#### 混合注意力 KV 缓存管理的挑战

混合注意力机制打破了 PagedAttention 及其变体的核心假设。尽管近期的混合 KV 缓存管理算法（如 Jenga（Zhang et al., 2025a）、Hymba（Dong et al., 2025））面向通用混合注意力模型或特定结构设计，但两大核心障碍导致无法在 PagedAttention 框架下统一管理所有层的 KV 缓存：

1. 多样化的缓存策略，如滑动窗口注意力所用策略；
2. 高性能注意力内核的约束，包括对齐要求。

> 为高效管理 DeepSeek-V4 的 KV 缓存，设计了如下对应策略攻克这两大挑战：

- **SWA 与未压缩尾部 Token 的状态缓存**：针对第一个障碍，DeepSeek-V4采用替代缓存管理机制。:mdnice-bold-italic[由于 SWA 设计初衷是在有限 KV 缓存尺寸下提升性能，可将其与压缩分支的未压缩尾部 Token 视为状态空间模型，对应 KV 缓存可看作仅依赖当前位置的序列专属状态]。据此，DeepSeek-V4预分配固定大小的状态缓存池，动态分配给每个序列。
- **稀疏注意力内核协同设计**：针对第二个障碍，传统高性能注意力内核通常假设每个块固定 $B$ 个 Token 以优化性能，对应 CSA 的 $B·m$ 个原始 Token 、HCA 的 $B·m'$ 个原始 Token 。:mdnice-bold-italic[通过采用高性能稀疏注意力内核，不同层可支持每个块可变 Token 数，且性能无下降。这需要 KV 缓存布局与稀疏注意力内核协同设计，例如将块填充至缓存行对齐以提升性能。] 因此，对于压缩比为 $m$ 的 CSA 与压缩比为 $m'$ 的 HCA，每个块的原始 Token 数可为两者最小公倍数 lcm($m$,$m'$)的任意倍数。

### 6.2 磁盘 KV 缓存存储

部署 DeepSeek-V4 时，采用磁盘 KV 缓存存储机制，避免共享前缀请求的重复预填充。

> 针对 CSA/HCA 的压缩 KV 条目、滑动窗口注意力（SWA）的未压缩 KV 条目，DeepSeek-V4 设计不同的存储管理方案：

- 对于 CSA 与 HCA，直接将所有压缩 KV 条目存储至磁盘。当请求命中已存储前缀时，读取并复用前缀对应的压缩 KV 条目，直至最后一个完整压缩块。对于尾部不完整块的前缀 Token ，仍需重计算以恢复未压缩 KV 条目，因为 CSA 与 HCA 的未压缩 KV 条目未存储。
- 对于 SWA KV 条目，由于其未压缩且存在于每一层，数据量约为压缩后 CSA 与 HCA KV 条目的 8 倍。

> 然而，为高效管理海量 SWA KV 条目，DeepSeek-V4提出并实现三种磁盘 SWA KV 条目管理策略，在存储开销与计算冗余间实现不同权衡：

1. **全 SWA 缓存**：存储所有 Token 的完整 SWA KV 条目，实现计算零冗余。**该策略下，仅需读取前缀内最后 $n_{win}$ 个 Token 的磁盘缓存，即可重建命中前缀的 SWA KV 条目**。:mdnice-bold-italic[但该策略对现代 SSD 存储系统效率较低] ——每个命中请求仅访问少量缓存，引发写密集型的不均衡访问模式。
2. **周期性检查点**：每 $p$ 个 Token （$p$ 为可调参数）对最后 $n_{win}$ 个 Token 的 SWA KV 条目做一次检查点保存。命中前缀时，加载最近的检查点状态，再重计算剩余尾部 Token 。通过调整 $p$，可按需权衡存储与计算成本。
3. **零 SWA 缓存**：不存储任何 SWA KV 条目。命中前缀时，需执行更多重计算以恢复 SWA KV 条目。具体而言，每层注意力的每个 Token SWA KV 条目仅依赖上一层最近 $n_{win}$ 个 Token 的 SWA KV 条目，因此借助已缓存的 CSA 与 HCA KV 条目，仅需重计算最后 $n_{win}·L$ 个 Token ，即可恢复 $L$ 层模型的最后 $n_{win}$ 个 SWA KV 条目。

DeepSeek-V4 根据具体部署场景选择最优策略，实现存储与计算的理想权衡。

## 结语

> DeepSeek-V4 以软硬件协同的全链路视角，构建了一套面向大模型高效训练与部署的通用基础设施。

其核心突破在于细粒度专家并行，将通信时延完全隐藏于计算中，在更低互联带宽下实现最高 1.96 倍加速；结合 TileLang 内核开发、批不变确定性算库与 FP4 量化感知训练，在保障数值精度与可复现性的同时，显著降低内存与计算开销。
