鉴于这些低延迟工作负载的重要性，我们想要探索在现代 GPU 上运行开源模型究竟能有多快。为了真正对现有系统进行压力测试，我们考虑了一个极具挑战性的低延迟场景：用 Llama-3.2-1B 生成单个序列。这个工作负载严重受限于内存——其性能主要取决于从 GPU 全局内存加载模型权重的速度。

::: block-1事实证明，流行的大语言模型推理引擎 vLLM 和 SGLang 在 H100 上运行此工作负载时，**最多只能利用 50% 的可用 GPU 带宽**。

**问题的根源** （我们将在下文详细描述）在于，**现有系统将模型的前向传递分解为大约一百个单独的内核**，每个内核执行一些操作（例如 RMS 归一化、注意力计算、多层感知器层+激活函数、旋转位置编码）。
:::

## 一、独立内核破坏效率

> 一般来说，在 GPU 上运行代码的方式是启动一个“内核”，它是一个执行特定操作（例如 RMS 归一化、多层感知器计算）的小程序。

如今，所有 AI 工作负载都是**由一系列相对较小的内核运行的**。为了有一个初步的了解，让我们看看 Llama-1B 的 Transformer 模块中的操作，以及一些可能的内核划分边界示例（图 2）。

![文章插图](/articles/2025-06-22-gpu-kernel-gpu-llama-1b-5918a98c/images/05.png)

::: image-caption图2：Llama-1B的Transformer模块的一组内核边界示例。红色框表示单个内核完成的工作
:::

如前所述，用 Llama-1B **解码** 单个序列是一个**纯粹受限于内存的工作负载**：我们的性能取决于能否始终从 GPU 全局内存加载权重。

> 那么，为什么现有的方法无法充分利用 GPU 的全部带宽呢？

当深入研究时，我们发现一个关键问题：当前**基于内核运行模型的方法会引入停顿**，使我们**无法持续加载内存**：

- 第一，GPU 内核的**启动有严格的顺序**，即一个内核中的线程块必须等待前一个内核中的所有线程块完全完成后才能启动。因此，**每次启动一个内核时，我们都必须等待前一个内核中所有延迟的线程块完成**。例如，如果一个内核运行 512 个线程块（如我们的 Llama-1B 下投影层），但我们只有 148 个流多处理器（如在 B200 上），最终会有 80 个空闲的流多处理器。
- 第二，正如我们之前强调的，**每个内核的启动和结束都会产生开销**。原则上，NVIDIA 的 CUDA 图可以帮助减少部分开销，但根据我们的测量，仍然存在很大的优化空间。在 H100 上运行一个简单的虚拟内核（记录开始时间、休眠、记录结束时间），我们发现使用 **CUDA 流启动内核的开销约为 2.1 微秒**，而使用 **CUDA 图时，启动开销仅降至约 1.3 微秒** ——**这些时间里 GPU 并没有做任何有用的工作！** 我们希望 GPU 把所有时间都用于执行有用的工作。
- 最后，即使启动了下一个内核，**在开始任何计算之前，我们仍然需要等待加载权重和激活值**。这些延迟会使 GPU 闲置数千个周期！理想情况下，我们希望在前一个计算和存储操作进行时，就开始加载下一个权重。**NVIDIA 为此构建了一种称为“可编程依赖启动”（PDL）的机制**，它允许下一个内核在前一个内核运行时就开始准备，但我们发现**它仍然会引入不必要的停顿**，**因为 PDL 的同步机制（cudaGridDependencySynchronize）非常粗糙**。例如，这意味着我们必须等待所有查询、键和值计算完成才能开始注意力计算，而不是在每个头准备好时就立即开始。我们稍后将展示在 Llama-1B 中，这一点在特定情况下的影响。

综上所述，这些形成了标题中提到的“内存管道空闲周期”，**这也是我们无法持续从内存加载数据的一个关键原因**。对于短时间的操作，这些停顿累加起来，浪费了大量潜在的带宽。部分原因是批处理大小为 1 的 Llama-1B（实际上有 12.4 亿个参数）规模较小：如果每个操作都非常快，那么操作之间的等待时间就会变得非常重要。

为了说明问题的严重性：在单个 H100 上以 16 位精度生成单序列时，内存限制为 3.35TB/s÷2.48GB ≈ 每秒 1350 次前向传递。但是，每层有 7 次内核启动，共 16 层，即使每个内核乐观估计有 5 微秒的停顿（包括延迟的线程块、内核启动和内存延迟），生成速度也只能达到每秒约 770 次前向传递。在实际情况中，往往更糟。在低延迟工作负载下，GPU 实际上只有一小部分时间在做有用的工作！

虽然 CUDA 确实提供了一些现有功能（例如图、流、PDL）来部分解决这些问题，但我们想看看是否有不同的方法可以彻底解决这些问题，即我们将整个模型的前向传递融合为一个内核。

## 二、如何构建大内核

**接下来，我们将展示如何将整个 Llama 前向传递融合为一个内核**，并介绍**解决三个关键问题的方法**：

::: block-1
- 从头开始融合数十个操作并非易事。我们需要一种在大内核中执行这些操作的**机制**。
- 为了在同一硬件上重叠多个操作，我们需要**防止对有限资源** （如共享内存）的**竞争**。
- 在传统的内核模型中，GPU 会在每个内核执行后进行同步。而没有了多个内核，我们必须**自己对 GPU 进行同步**！
:::

让我们从第一个问题开始：

### 2.1 问题 1/3：融合大量操作

传统的内核融合通常只将两三个操作合并在一起。相比之下，我们需要融合大约一百个操作。因此，我们**需要一种合理的抽象方式，以便实际对大内核进行编程。**

我们的方法**基于一个 GPU 上的解释器**，本质上是 ThunderMLA 底层基础设施的更复杂版本。**我们设计的解释器可以让 GPU 内的每个流多处理器（SM）接收一系列指令** （每个指令都使用相同的 CUDA 模板实现）**并执行它们**。我们在 Python 端提前为每个 SM 调度指令序列，值得注意的是，数百次前向传递都可以重用每个调度！

::: block-1对于端到端的 Llama 前向传递大内核，我们定义了以下一组指令：

- 融合的 RMS 归一化、QKV 和旋转位置编码（RoPE）指令。
- 注意力计算指令。
- 注意力归约指令（用于处理长序列的 ThunderGQA）。
- O 投影+残差指令。
- 融合的 RMS 归一化、上采样门控和 SiLU 指令。
- 下投影+残差指令。
- RMS 归一化和语言建模头指令，用于计算最终的令牌对数概率（logits）。
:::

我们**使用通用的 CUDA 模板** （包含加载、存储、计算的通用函数）**实现这些指令**，这有助于在我们的**解释器框架内实现互操作性**。

### 2.2 问题 2/3：共享共享内存以消除内存空闲周期（Sharing Shared Memory to Eliminate Memory Bubbles）

指令和解释器结构让我们能够清晰地组织大内核。然而，我们尚未解决关键问题：确保始终加载模型权重，以最大化内存带宽利用率。

> 大内核能够解决这个问题的原因在于，我们可以在指令之间进行内存加载的流水线操作：我们的解释器会尽快开始为下一条指令加载模型权重，即使前一条指令仍在完成（例如将其结果存储到全局内存）。

正是这种**指令之间的紧密转换，最大限度地减少了如果启动多个内核可能出现的内存空闲周期。**

然而，这里有个问题：如果没有地方存放加载的数据，那么为下一条指令从全局内存加载权重就没有多大意义！更确切地说，**我们所有的权重矩阵都是从 GPU 全局内存加载到 SM 的“共享内存”** （NVIDIA 对每个 SM 上的快速内存的称呼）中。共享内存是每个 SM 上的稀缺资源，如果前一条指令正在占用全部共享内存，我们就无法为新指令开始加载。

> 这就需要一种方法来跟踪哪个指令正在使用共享内存的哪一部分，并在当前指令完成后，快速将共享内存转移给下一条指令。

我们通**过共享内存分页来实现这一点**。我们首先将 H100 上的前 213kB 共享内存划分为 13 个 16KiB 的页，并将剩余的共享内存用于特殊目的，如存储指令参数。为了使用其中一个页，指令必须向解释器显式请求和释放。解释器会自动将释放的页传递给下一条指令，使其能够在共享内存可用时尽早开始发出内存加载请求。

### 2.3 问题 3/3：同步

> 虽然大内核让我们尽量减少了流水线空闲周期，但它也带来了一个新问题：同步。

**正常的多内核执行模型** 的**性能限制** 在于，**一个内核中的任何线程块都必须在前一个内核中的所有线程块完成后才能启动**。然而，正是这个特性使得管理数据依赖关系变得容易。当一个内核启动时，CUDA 保证该内核的所有输入张量都已生成，并且可以立即安全读取。

![文章插图](/articles/2025-06-22-gpu-kernel-gpu-llama-1b-5918a98c/images/06.png)

**对于大内核，我们没有这样的保证：当一个 SM 开始执行新指令时，其输入可能还未准备好！为了解决这个问题，我们在大内核内部显式地对指令进行同步。** 我们通过一个简单的计数器系统来实现这一点。在大内核启动之前，我们在 GPU 全局内存中初始化一个计数器数组（即整数数组），初始值为零。每当一条指令完成时，它就会增加其中一个计数器的值。**同样，每当一条新指令开始时，它必须等待某些计数器达到目标值，这表明其所有依赖项都已完成。**

这使得我们可以对 Llama-1B 中的大型多层感知器（MLP）进行一项优化。在使用 PDL 的简单实现中，必须等待整个隐藏状态计算完成后，才能开始下投影矩阵乘法。而我们将中间状态分四个块生成和处理，每个块都有自己的计数器。这样，下投影指令只需要等待其输入块完成即可。

## 三、总结

据我们所知，我们在 H100 上的大内核首次实现了在 GPU 上以低于 1 毫秒的时间完成 16 位、10 亿参数以上语言模型的前向传递。我们在 B200 上的实现更是将每次前向传递的时间缩短至 680 微秒以下！

**如图 1 所示，我们的大内核性能优于 vLLM 和 SGLang 基线** （它们使用 CUDA 图和 torch 编译）：

- 在 **H100** 上，我们的大内核运行速度**比 vLLM 快近 2.5 倍，比 SGLang 快 1.5 倍以上。**
- 在 **B200** 上，**与 vLLM 的差距扩大到 3.5 倍以上**，并且我们仍然比 SGLang 快 1.5 倍以上。

> 实际上，我们与 B200 上的理论极限（约每秒 3000 次前向传递）仍有较大差距。部分原因是这个理论极限纯粹基于内存带宽，但我们仍然需要等待加载激活值。

尽管这些激活值的数据量较小（不会消耗太多带宽），但加载它们时仍然存在无法隐藏的延迟。

::: block-1
**下面是我们当前 B200 前向传递运行时间** （总运行时间 600 微秒）的细分：

- **250 微秒用于存储激活值、等待一致性和加载激活值**。这比简单模型预计的要高约 20%：由于每条指令都依赖于上一条指令，我们每条指令需要承担两次加载延迟（检查是否准备好，然后加载激活值）和两次存储延迟（存储激活值，然后标记为准备好）。每次加载/存储的延迟约为 500 纳秒，这将带来约 200 微秒的开销。（我们怀疑剩余的 50 微秒部分来自于在全局内存中处理原子操作的时间。）
- **200 微秒用于实际运行 RMS 归一化和矩阵向量计算**。其中 95% 的时间用于矩阵向量计算。在 Blackwell GPU 上，我们发现使用张量核心对此略有帮助；在 Hopper GPU 上，我们发现直接在 CUDA 核心上运行效果更好。这种差异源于这两种 GPU 的 CUDA 核心性能相对相似，但 Blackwell 的张量核心速度要快得多。
- **30 微秒用于等待从全局内存加载权重** （流水线起作用了！）。其中 40% 的时间花在语言建模头（LM head）上，由于其同质性和巨大的规模，它是整个大内核中流水线效果最好的部分。
- **40 微秒用于线程束（warp）之间的低级同步开销**。这里的一个关键问题是，CUDA 的异步屏障相对较慢，即使在“通过”状态下，每次也需要约 60 纳秒。
- **80 微秒用于设置和各种其他开销** （例如传递指令屏障、标记页完成等）。
:::

我们认为在这些方面可能还有更多的优化空间，但这需要留到未来的更新中！
