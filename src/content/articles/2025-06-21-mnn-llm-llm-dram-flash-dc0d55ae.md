## 一、引言

近年来，大型语言模型（LLMs）发展迅速，成为自然语言处理领域最具革命性的技术之一。像 ChatGPT-4o[18]和 QwenMax[7]这样的杰出模型，由于其庞大的参数规模，通常使用 GPU 推理部署在云端。然而，较大的参数规模和计算需求导致用户成本较高，并且使用云服务可能涉及处理用户敏感数据，引发隐私和安全问题。针对这些问题，在移动设备上部署 LLM 的趋势正在兴起[19]。尽管移动设备应用广泛，但其**内存和计算限制使得直接运行大规模 LLM 具有挑战性。**

**![文章插图](/articles/2025-06-21-mnn-llm-llm-dram-flash-dc0d55ae/images/04.png)**

为了应对这一挑战，**许多开源预训练 LLM 发布了针对边缘环境的较小规模模型**。这些模型与云端模型架构相同，但参数更少，例如 Qwen2-1.5B[27]。根据缩放定律[16]，较小的模型能力有限，通常只能执行简单或特定的任务。然而，随着 phi-1[11]等模型的出现，研究表明**训练数据的质量可以显著增强小参数模型的能力**。此外，ChatGPT-o1[18]等模型中的**强化学习算法可以在不增加参数数量的情况下进一步提升 LLM 性能**。因此，小模型和大模型之间的差距正在逐渐缩小；例如，30 亿参数的 Qwen2.5-3B[24]在 MMLU 基准测试中获得了 64 分，超过了许多 300 亿参数的前身模型。LLM 能力的快速提升为在移动设备上部署 LLM 提供了更大的可行性。

![文章插图](/articles/2025-06-21-mnn-llm-llm-dram-flash-dc0d55ae/images/05.png)

尽管参数规模有所减少，但与用于边缘推理的传统计算机视觉模型相比，LLM 的计算需求仍然很大。由于硬件、内存和计算限制，在边缘设备上流畅运行 LLM 面临重大挑战。为解决这一问题，出现了一些用于在移动设备上部署 LLM 的框架。一些框架，如 PowerInfer-2[26]和 LLM in Flash[1]，需要对模型进行修改以实现兼容性。其他框架，如 llama.cpp[10]、MLC-LLM[23]和 fastllm[29]，可以直接使用，并且专注于 LLM。

本文介绍了 **MNN-LLM，这是一个通用的移动推理框架，支持 LLM 推理以及各种深度学习模型的部署**。MNN-LLM 是基于 MNN[15]开发的，MNN 是一个专为在移动设备上执行深度学习模型推理而设计的通用框架。它通过在模型导出、量化和计算图优化方面的针对性优化，应对大规模 LLM 带来的挑战。此外，**MNN-LLM 分析了推理过程，并采用了各种形式的组合量化，利用 DRAM-Flash 混合存储来减少运行时内存使用**。

> 通过优化高计算量的算子并根据不同硬件的特性重新排列数据，MNN-LLM 确保了边缘计算资源的最佳利用。

## 二、背景与动机

### 2.1 LLM 模型与推理

当前主流的 LLM 主要采用仅解码器（Decoder-Only）架构，其主要参数位于嵌入层（Embedding）和线性层（Linear operators）中。在**推理过程** 中，**最耗时的算子是线性层和注意力层（Attention）**。

推理过程可分为两个阶段：预填充阶段（prefill）和解码阶段（decode）。

- 预填充阶段指的是对输入文本的计算，处理用户的输入文本序列以生成第一个 Token。
- 解码阶段涉及文本生成，其中每个解码操作生成一个 Token，直到生成终止 Token 为止。这**两个阶段** 表现出**不同的计算特性**：具体而言，由于边缘设备的典型计算吞吐量和内存带宽限制，**预填** 充阶段往往是**计算密集型** 的，而**解码** 阶段则是**内存密集型** 的。

在注意力机制的推理阶段，有三个输入：查询（query）、键（key）和值（value）。

- 在解码阶段，仅需要当前输入 Token 生成的查询；
- 然而，所有先前计算的键和值都是必需的。

> 为了减少计算负载并避免冗余计算，通常采用键值（KV）缓存来存储先前计算的键和值。

### 2.2 移动设备分析

移动设备通常内存有限，而 LLM 的大参数规模会导致大量内存使用，尤其是随着上下文长度的增加，可能导致内存不足并终止进程。**尽管闪存（Flash memory）的读取速度比动态随机存取存储器（DRAM）慢得多，但其更高的容量使其对 LLM 推理至关重要。**

::: block-1移动设备利用 CPU 和 GPU，通常具有多个核心，并且经常遵循 big.LITTLE 架构[2]，这使得在 CPU 开发过程中需要进行并发优化。

- 不同 CPU 之间的指令集差异需要进行定制化优化以实现最佳性能。
- 移动 GPU 上的通用计算通常采用 Vulkan 和 OpenCL 标准，允许开发人员使用这些 API 实现任务并行化。
:::

硬件驱动程序管理指令调度和任务调度，增强了跨平台的代码可移植性。

## 三、MNN-LLM 概述

MNN-LLM 构建在深度学习框架 MNN[15]之上，利用 MNN 广泛的算子集和模型支持的多功能性来增强灵活性和适应性。**与特定于 LLM 的推理引擎不同，MNN-LLM 支持更广泛的模型**，提高了边缘计算环境中的可用性和开发人员友好性。

MNN 为计算机视觉（CV）模型（如 MobileNet[13]和 YOLO[22]）提供了强大支持，这些模型**通常在转换为 MNN 格式之前导出为 ONNX[8]格式**。虽然 MNN-LLM 使用这些导出和转换过程，但 LLM 的大参数规模可能导致**高内存使用和较长的转换时间**。

> 为了缓解这一点，已引入优化措施：**在图导出期间，线性算子被替换为自定义算子，允许 ONNX 导出专注于计算图而不包含参数**。

模型导出、转换和优化后，参数可以单独处理，简化了流程并利用了 MNN 的模型格式。此外，在**模型转换期间**，应用了如 **RMSNorm[28]融合和注意力融合等优化**。计算图还支持**运行时加载 LoRA[14]权重**，从而实现 LoRA 模型的无缝集成，而无需在推理框架中进行外部实现。

MNN-LLM 提供强大的量化能力，支持**模型转换阶段的整数（int）和浮点（fp）量化**，以及**运行时的激活值和 KV 缓存量化**。此外，它还支持**其他量化算法**，如 GPTQ[9]，并允许导入量化权重。

MNN-LLM 在**运行时对内存和计算进行了广泛优化**。为解决 LLM 的大量内存使用问题，它采用了 DRAM-Flash 混合存储和组合量化等方法。对于高计算负载，采用了针对硬件的数据重排、多核负载平衡、混合精度浮点运算和几何计算等策略。此外，还针对多 LoRA 场景实现了特定优化。

## 四、内存优化

### 4.1 DRAM-Flash 混合存储

> 在移动设备上部署大型 LLM 模型的主要瓶颈在于动态随机存取存储器（DRAM）的限制。

MNN-LLM 采用 **DRAM-Flash 混合存储策略** 来**减少内存使用**，确保在内存受限条件下 LLM 推理的可用性，同时**将性能影响降至最低**。

- 尽管闪存（Flash）的容量比 DRAM 大，但其读取速度明显较慢；
- 例如，LPDDR5X 的速度约为 58 GB/s，而 UFS 4.0 的速度在约 450 MB/s 到 3 GB/s 之间[26]。

> 这意味着 DRAM 的速度可能比 Flash 快 19 到 130 倍。虽然**混合存储** 可以减少内存需求并**提高可用性**，但可能会影响推理性能。

![文章插图](/articles/2025-06-21-mnn-llm-llm-dram-flash-dc0d55ae/images/06.png)

**如图 1 所示，MNN-LLM 的混合存储策略是根据模型的操作特性定制的**：

- 对于参数存储，它评估利用率并将低利用率的参数分配给 Flash，以最大限度地减少对速度的影响。
- 对于 KV 数据，采用预取技术来减少闪存读取的延迟，从而减轻其对性能的影响。

---

**LLM 模型的大参数规模是其高内存消耗的主要原因**。从结构上看，参数可分为三类：嵌入层（Embedding）、层（Layer）和语言模型头（Lm head）。

1. **嵌入层** 和**语言模型头** 参数的大小，通常计算为词汇量（vocabulary size）× 隐藏层大小（hidden size），并且由于词汇量通常较大，嵌入层参数不像其他参数那样参与计算。
2. **层** 指的是每个解码器层（Decoder Layer）中的参数，包括注意力层和多层感知机（MLP）的线性层，其大小通常为隐藏层大小 × 隐藏层大小或中间大小 × 隐藏层大小，且各层的参数规模一致。

如表 1 所示，在 Qwen2-7B[27]模型中，非计算性的嵌入层参数约占总参数的 15%。

![文章插图](/articles/2025-06-21-mnn-llm-llm-dram-flash-dc0d55ae/images/07.png)

在解码阶段，每个输入由先前生成的 Token 组成，这导致计算过程需要加载 $1/\text{词汇量}$ 的嵌入层参数，以及完整的层和语言模型头参数。因此，层和语言模型头参数应优先存储在 DRAM 中，而嵌入层参数可以存储在 Flash 中。以 Qwen2-7B 为例，在 bfloat16 格式下读取嵌入层数据时，解码阶段仅需要一个 Token 的嵌入值，每次解码的数据大小为 7 KB。UFS 4.0 的读取速度比 LPDDR5X 慢约 15 微秒。相比之下，从内存加载非嵌入层参数大约需要 103 毫秒。

在典型的移动设备中，解码阶段的计算特性属于内存受限型（Memory Bound），内存访问时间大致与参数访问时间相当。因此，**将嵌入层参数存储在 Flash 中仅使总推理时间增加约 1.4‱**。

> 因此，利**用 Flash 存储嵌入层可以使 DRAM 使用量减少 15%，而不会显著影响推理性能**。

例如，使用 bfloat16 存储时，Qwen-7B 可以减少约 2.18 GB 的 DRAM 使用量，大大提高了在内存受限的移动设备上进行模型推理的可行性。

在输入文本较长或生成长度较大的场景中，KV 缓存的持续增长会导致大量内存使用。**MNN-LLM 通过采用混合存储策略来应对这一挑战，利用 Flash 存储部分 KV 缓存，从而确保在长上下文条件下 LLM 推理的可行性**。

::: block-1
- 最初，所有 KV 缓存值都存储在 DRAM 中，但随着上下文扩展和 KV 缓存大小增加，超过一定阈值的部分会转移到 Flash。
- 由于每次计算仅产生一组新的 KV 值，Qwen2-7B 模型的 KV 值总数约为 1 KB，存储开销极小。
:::

**随着存储在 Flash 中的 KV 缓存值数量增加，从 Flash 加载它们所需的时间将逐渐增加，这可能会减慢推理速度，如图 2b 所示**。

> 为了减轻从 Flash 加载 KV 缓存对推理时间的影响，我们实现了预取技术。

具体来说，在当前层的 MLP 阶段和下一层的 qkv 投影阶段，从 Flash 预取 KV 缓存值到内存中。当预取时间小于或等于计算时间时，LLM 推理速度不受影响。

![文章插图](/articles/2025-06-21-mnn-llm-llm-dram-flash-dc0d55ae/images/08.png)

例如，在 Qwen2-7B 模型中，单层的 qkv 和 MLP 参数大小为 178.83 MB，解码阶段属于内存受限型。假设 LPDDR5X 加载这些数据需要约 3 毫秒的时间，由于 Flash 的连续内存块较大，我们假设其加载速度为 1 GB/s，因此可以在计算时间内加载约 3 MB 的 KV 值。

> 因此，当存储在 Flash 中的 KV 缓存长度小于 3072 K 时，Flash 加载的开销会被计算时间有效掩盖，如图 2c 所示。

- 然而，一旦 **Flash 中的 KV 缓存长度超过 3072 K**，如图 2d 所示，**预取无法完全抵消 Flash 加载的开销**；
- 每增加 1 K 的长度，大约会增加 1 毫秒的延迟。需要注意的是，DRAM 仍然存储着相当长度的 KV 缓存，这意味着只有在上下文**极长的场景中，LLM 的推理速度才会受到影响**。

尽管如此，将 KV 缓存存储在 Flash 中确保了即使在长上下文情况下，LLM 推理仍然可行。

### 4.2 组合量化

LLM 模型的大参数规模是其高内存消耗的主要原因，而量化可以显著减小参数规模，从而降低内存使用。

- 然而，量化会影响模型的推理精度；
- 通常，位数越低，信息损失越大，对精度的影响也越大。

量化有多种方法、数据类型和位数，因此**选择合适的方法来平衡内存使用、运行时性能和模型精度至关重要。**

> 对于嵌入层、层和语言模型头的参数，MNN-LLM 采用组合量化策略来平衡精度和计算开销。

- **嵌入层的权重** 约占模型总权重的 15%。由于在**每个解码步骤** 中**仅使用** 这些权重的**一小部分**，它们**存储在 Flash 内存** 中，不占用 DRAM。这允许使用 bfloat16 存储，确保计算精度。
- **非嵌入层参数** （包括层和 LM 头的权重）**每次计算** 都需要**完全加载**，其大小**对推理性能有显著影响**。特别是在内存受限的解码阶段，推理时间与这些参数的大小直接成正比。因此，对这些权重使用低位数量化至关重要。

::: block-1考虑到精度和硬件计算指令（边缘 CPU 特别适合 int8 计算），这些参数使用 int4 或 int8 进行量化。在计算过程中，激活值量化为 int8：

- 使 CPU 能够使用 W4A8 或 W8A8 计算方法来利用 int8 指令。
- 在 GPU 上，使用 W4A16 或 W8A16 方法来利用浮点计算能力。
:::

为了保持模型精度，所有这些参数均采用非对称量化。非对称量化公式如下：

$$
w_{\text{asy}} = \text{round} \left( \frac{w_{\text{float}} - w_{\text{min}}}{\frac{w_{\text{max}} - w_{\text{min}}}{\text{clip}_{\text{max}} - \text{clip}_{\text{min}}}} \right) + \text{clip}_{\text{min}} \quad (1)
$$

此外，由于 **LM 头对模型精度的影响比层更大**，因此**优先对其进行 int8 量化以提高整体精度。**

当处理长上下文时，KV 缓存的内存使用持续增长，量化策略可以有效减少这种内存消耗。MNN-LLM 根据键（key）和值（value）的计算角色为它们提供不同的量化方法。在注意力计算中，查询（query）、键（key）和值（value）的形状为 $[头数（headnum）, 序列长度（seqlen）, 头维度（headdim）]$ 。

在执行键和查询之间的矩阵乘法时，减少的维度是头维度，这是一个固定值。因此，可以**对键应用 int4/int8 量化，允许直接量化和存储新的键值**。相比之下，在注意力分数与值的矩阵乘法中，减少的维度是序列长度。

对值使用 int4/int8 量化可能会在添加新值时影响现有值的数据分布，需要更新它们的量化值并产生额外开销。为了解决这个问题，**MNN-LLM 对值采用 fp8 量化，允许直接量化新值而不影响现有值。**

## 五、计算优化

### 5.1 硬件驱动的数据重排

> 对 LLM 推理过程的分析表明，主要的耗时操作是线性层和注意力层，这两者从根本上都依赖于矩阵乘法。因此，对这两个算子的矩阵乘法进行优化是提高 LLM 性能的关键。

循环分块（Loop Tiling）是一种常见的优化技术，它可以增强内存访问的局部性，对性能产生显著影响。**循环分块的最佳分块大小[12]对最终的矩阵乘法性能有很大影响，并且受到设备内存、缓存和计算硬件的影响**。因此，必须**根据硬件和数据规模选择最合适的数据重组和计算方法**，以实现最佳性能。

> MNN-LLM 采用**硬件驱动的数据重排策略**，针对这两种算子类型的**计算特性来确定分块方法和大小**，优化 LLM 推理性能。

线性算子的矩阵乘法涉及激活值和权重值，其中激活值在推理过程中计算，权重值在模型加载时确定。在 MNN-LLM 中，权重通常量化为 int4 或 int8。

::: block-1假设激活值矩阵的大小为 $[e, l]$，权重大小为 $[h, l]$，结果大小将为 $[e, h]$。

在移动 CPU 上进行数据分块后，输入矩阵被重新排列为：激活值为 $[\frac{e}{e_p}, \frac{l}{l_p}, e_p, l_p]$，权重为 $[\frac{h}{h_p}, \frac{l}{l_p}, h_p, l_p]$，以优化内存访问频率。

这种分块允许在寄存器内重用值，将内存访问次数从 $2ehl + eh$ 减少到 $\frac{e}{e_p} \frac{h}{h_p} (l e_p + l h_p + h_p e_p)$。
:::

通过**使用内存访问频率作为优化目标，以硬件参数作为约束，我们可以计算不同硬件条件下的 $e_p$、$h_p$、$l_p$ 值**。设 R 为向量寄存器的数量，指令宽度（instruction width）为沿 l 维度在单个指令中计算的数据大小，则 $e_p$、$h_p$、$l_p$ 由以下公式给出：

$$
\min \frac{e}{e_p} \frac{h}{h_p} \left( l e_p + l h_p + h_p e_p \right)
$$

$$
\text{s.t.} \ e_p + h_p + h_p e_p \leq R \quad (3)
$$

$$
l_p = \text{instruction width} \quad (4)
$$

基于上述策略，各种 CPU 指令集的分块大小计算结果如表 2 所示。

**通过采用针对不同 CPU 架构的硬件驱动数据重排策略，MNN-LLM 可以更好地利用 CPU 计算能力。** 例如，ARM i8mm[5]上的 smmla 指令的吞吐量是 sdot[4]的两倍。当 MNN-LLM 检测到 CPU 支持 i8mm 时，它会在模型加载阶段将权重重新排列为 $l_p=8$。

> 这种排列格式相比 llama.cpp 中的数据布局提高了性能，从而提高了预填充阶段的效率。

**GPU 支持硬件加载/存储合并，这允许它们在连续工作项访问的内存地址连续时合并一定数量的内存访问指令**。此功能可**最大限度地减少内存访问指令的数量**。

此外，GPU 一次最多可以加载/存储 128 位数据。为了最大化内存加载效率，每个工作项应使用向量化加载/存储函数。在 OpenCL 中，GPU 内存对象分为缓冲区（Buffers）和图像（Images）。

图像可以自动处理边界，并根据设置返回适当的越界值。某些设备，如高通的 Adreno GPU[20]，拥有强大的纹理引擎和专用的 L1 缓存，能够高效地从图像对象加载数据。与普通缓冲区对象相比，图像提供更高的带宽，因此是存储的首选。

**为了利用这些内存加载优势，MNN-LLM 重新排列 GPU 权重数据并使用图像对象进行存储**。重新排列的数据结构为 $[\frac{l}{l_p}, h, l_p]$，其中 $l_p=32$。每个工作项一次加载 4 位权重，总计 128 位，这**满足 GPU 的最大加载带宽**，**对应 CL_RGBA 图像内存对象中四个浮点值的大小**。此外，每个工作项沿 h 维度连续访问数据，确保工作项之间的内存读取连续。最后，运行时根据实际维度动态调整并行性，为每个工作项分配合理数量的计算任务。

对于**注意力算子，采用了与线性算子类似的重排策略**。键和值直接存储在重新排列的数据布局中，确保每次计算时无需重新排列历史 KV。

### 5.2 多核负载平衡

> 现代 CPU 通常具有多个核心，因此在优化性能时有效利用多核计算能力至关重要。

MNN-LLM **利用 CPU 的多核并行性，沿序列长度（seqlen）和 $\frac{h}{h_p}$ 维度并行化操作**。考虑到移动 CPU 的 big.LITTLE[2]架构，MNN-LLM 在**启动时根据不同核心的实际计算能力为其指定计算负载**。在并行计算期间，MNN-LLM **根据核心的负载率分配计算工作负载**。与均匀工作负载策略相比，这种平衡的工作负载分配策略**可以提高多线程计算性能**。

**主流移动 SoC 通常具有一个 Prime 核心和三个性能核心**，如骁龙 8 Gen 3[21]。高负载计算通常使用 Prime 核心和性能核心。当线程数超过 1 时，Prime 核心和性能核心之间会进行并行计算，**如图 4 所示。在这种情况下，与均匀工作负载分配相比，负载平衡显著提高了多线程加速比**。

### 5.3 混合浮点精度

在之前关于矩阵运算的讨论中，采用了低位数量化方法来加速计算。**对于非矩阵乘法操作，MNN-LLM 还支持结果的混合精度**，以确保精度同时提高推理性能。

- ARMv8.2[6]及更新的 CPU 支持 float16 计算，与 float32 相比可以节省一半的内存，并且 float16 的 NOEN[3]指令的吞吐量是 float32 的两倍。然而，float16 具有一定的精度限制；
- 对于需要更高精度范围的计算，可能会发生显著误差，尤其是当值超过 65,504 时。

为了解决这个问题，MNN-LLM 采用混合精度策略来保持推理精度。

在 LLM 推理期间，**注意力中的 Softmax 计算对数据精度特别敏感**，因此 MNN-LLM **确保 Softmax 使用 float32**。在查询和键的矩阵乘法中，查询值可能较大，累积后可能导致溢出。为了缓解这一点，可以将除以 $\sqrt{d_k}$[25]直接应用于查询，减小其值范围并防止最终结果溢出。这种方法在保持精度的同时优化了整体内存使用和推理性能。

### 5.4 几何计算

LLM 的计算图还包括长尾算子，如转置（Transpose）、收集（Gather）和拼接（Concat）。尽管这些算子可能对整体执行时间贡献不大，但在数据规模较大时可能导致大量内存访问。**为了解决这些长尾算子的问题，MNN-LLM 采用几何计算[17]方法，将所有数据重排操作抽象为地址的线性映射**：

$$
f(\vec{x}) = \text{offset} + \text{stride} \cdot \vec{x}
$$

通过采用长度为 3 的偏移量（offset）和步长（stride），我们可以构建一个描述为区域（Region）的基本映射关系。这允许我们使用一个或多个区域来表示任何数据重排算子。

对于计算图中的连续数据重排算子，这种抽象会生成许多连续的区域。MNN-LLM **基于循环展开、循环交换、循环分块和循环融合等规则实现了自动区域融合算法**。该算法可以**自动合并兼容的区域，从而减少数据重排算子的读写操作次数，提高性能**。

> 通过将几何计算用于 LLM 模型推理，可以减少长尾算子的开销，性能提高约 3%。

### 5.5 LoRA 优化

在**移动设备** 上，**不同任务** 可能**需要不同的 LLM 模型**。由于模型参数数量庞大，直接使用多个模型会导致带宽和存储资源消耗过高。因此，**将基础模型与多个 LoRA（低秩适应）模型结合使用** 是**多任务场景下更高效的解决方案**。

MNN-LLM 支持合并后的 LoRA 模型部署和多个 LoRA 模型的在线加载。

::: block-1当使用多个 LoRA 模型时，MNN-LLM 首先加载基础模型，然后加载 LoRA 模型的计算图和权重，LoRA 模型共享基础模型的权重，因此内存开销极小。

在线加载 LoRA 模型比预合并方法更灵活，适用于多任务场景，尽管会引入额外的计算成本。LoRA 的计算图为涉及 LoRA 的层添加了旁路，将原始计算 $A' = W \cdot A$ 转换为 $A' = W \cdot A + (LoRA_A \cdot LoRA_B) \cdot A$，其中额外的计算可能会减慢模型推理速度。
:::

通过分析 LoRA 权重的特点，发现与原始参数相比，低秩矩阵 $R$ 的尺寸较小，因此可以利用矩阵乘法的结合律改变计算顺序，将 $(LoRA_A \cdot LoRA_B) \cdot A$ 转换为 $LoRA_A \cdot (LoRA_B \cdot A)$。假设矩阵 $A$ 的尺寸为 $[h, h]$，$LoRA_A$ 和 $LoRA_B$ 的尺寸为 $[h, r]$，**优化前后的计算内存访问量如表 3 所示**。由于 $R$ 通常较小（如 $r=8$），**重新排列计算顺序后，内存访问量仅为原来的 0.5%，** 从而有效提高了计算效率。

## 六、评估

实验基于量化模型 Qwen2-1.5B、Qwen2-7B 和 Llama3-8B，以小米 14 为测试设备，在 CPU（4 线程）和 GPU（OpenCL）架构上对比了 llama.cpp、MLC-LLM 和 fastllm 等推理引擎的性能。由于 MLC-LLM 不支持 CPU 推理，fastllm 不支持 GPU 推理，相关实验未包含这两种引擎。实验使用了不同长度的提示（64、256 和 1024 tokens），解码阶段限制最多生成 16 个 tokens。

![文章插图](/articles/2025-06-21-mnn-llm-llm-dram-flash-dc0d55ae/images/13.png)

由于 MLC-LLM 处理非对称量化模型的性能较差，其报告结果基于对称量化模型，而其他引擎均使用非对称量化模型进行推理。**性能结果以预填充和解码速度表示，如图 5 所示。**

- 在 **CPU 基准测试** 中，MNN-LLM 表现优异。
- 在 **GPU 测试** 中，由于 MLC-LLM 的对称量化技术优势，MNN-LLM 在处理短提示的 Qwen2-7B 时性能略低，但整体仍优于其他引擎。

## 七、结论

本文介绍了 MNN-LLM，这是一款专为移动设备 LLM 推理设计的高性能通用推理框架。

::: block-1该框架通过 **DRAM-Flash 混合存储** 和**组合量化** 技术**优化内存使用**，同时**利用硬件驱动的数据重排**、**多核负载平衡**、**混合精度浮点运算** 和**几何计算** 等策略提升推理速度。
:::

与主流框架相比，MNN-LLM 实现了高达 8.6 倍的性能提升，为移动设备上的 LLM 部署提供了高效、通用的解决方案，推动了隐私敏感型应用在边缘设备的落地。
