## 一、行业痛点：现有 LLM 容灾方案的底层无解缺陷

> 想要理解 Concordia 的创新价值，需要先拆解当下工业界两类主流 LLM 故障恢复方案的底层瓶颈，:mdnice-bold-italic[两类方案分别是业务层自定义 KV 日志、主机侧全量/增量页面检查点，二者均存在无法根除的性能或兼容性短板。]

长会话 LLM 推理的显存状态具备天然分层特征，三类状态的修改频率、数据规模差异极大，这是所有容灾系统必须适配的硬件特性，也是传统方案无法高效利用的核心前提。

### 1.1 长会话 LLM 推理的三类 GPU 驻留状态

LLM 持续推理时，显存中会稳定保存三类完全不同生命周期的存储区域，Concordia 将其标准化划分，也是后续分层增量快照的设计基础：

1. **不可变基础权重**：模型主干参数，加载完成后全程无修改，通常占显存的绝大部分，无需重复快照；
2. **高频稀疏可变 KV 缓存**：每生成一枚 token 仅修改 4KB 单页面，整体区域可达数百 MB，但单次更新仅极少量脏块；
3. **低频小体积可变区域**：LoRA 适配器、优化器状态，微调场景下仅占整体参数 1.75%。

::: block-1
传统容灾方案没有针对三层状态做分层识别，要么全量拷贝显存，要么需要业务代码手动标记每一处 KV 写入逻辑，无法做到通用透明。
:::

### 1.2 两类传统容灾路线的根本性短板

1. **应用层自定义 KV 日志路线**：该方案要求开发者侵入修改 PagedAttention、融合注意力内核、Triton 生成算子、NCCL 通信缓冲全部代码，手动记录每一次 KV 缓存写入操作。现实生产环境中，服务栈混合自研算子、第三方加速库、厂商闭包二进制库，:mdnice-bold-italic[无法统一拦截所有写操作，适配成本随框架迭代指数级上升，不具备通用性。]
2. **CPU 主机侧增量页面检查点路线**。主机侧方案的完整流程为：主机发起 CUDA 内存拷贝，将全部目标显存区域传输至主机内存，再通过 CPU 逐 4KB 页面对比，筛选脏页写入持久存储。:mdnice-bold-italic[该流程存在双重带宽瓶颈：PCIe 传输全量显存、CPU 内存带宽遍历全部页面]，哪怕仅 1 页脏数据，也要完整扫描整个数百 MB 区域，性能损耗呈线性增长。

### 1.3 量化佐证：CPU 侧脏页扫描的性能地狱

前文定性拆解了 CPU 侧脏页检测的双重带宽瓶颈，下面通过 Blackwell 平台量化实验图表直观量化两类方案的性能差距：

256MB 显存区域场景下：

- **CPU 方案** 拷贝耗时 4.72ms，页面对比耗时高达 106.65ms，:mdnice-bold-italic[95%以上耗时消耗在主机内存遍历]；

## 二、Concordia 核心底层洞察：常驻 GPU 持久内核是容错唯一底座

> 现有 CUDA Graph、动态并行技术仅优化算子调度延迟，无法提供故障发生前持续存活的设备侧控制流；**Concordia 提出的持久内核，核心定位是会话全生命周期常驻的容错专用执行器，区别于普通计算持久线程。**

持久内核的整套运行逻辑依托无锁环形缓冲区、版本化算子表两大核心组件实现，同时设计了严格的故障信任模型，将硬件资源开销压缩至行业最低水平。

### 2.1 持久内核的核心设计定位

> 持久内核与现有 GPU 调度技术存在本质边界区分：

1. **CUDA Graph**：面向静态固定算子 DAG，仅降低主机发起内核的调度开销，故障后图形上下文全部销毁，不具备持续存活的控制能力；
2. **CUDA 动态并行**：允许设备侧启动新内核，但仍依赖主机驱动管理上下文，故障时无法保留检查点执行逻辑；
3. **传统持久线程**：面向科学计算负载，仅优化计算调度，无 PTX/SASS 插桩、增量快照、分布式通信容错配套模块。

::: block-1
**Concordia 持久内核专属目标仅为故障容错，会话启动时一次性加载，全程驻留，仅占用单个 GPU 计算块**，在 NCCL 通信边界、算子同步点自动执行脏页扫描、日志追加任务，全程无需主机发起内核调用。
:::

- 主机侧完成 JIT 检查点算子编译、任务入队；
- 环形缓冲区为设备可见无锁 SPSC 队列；
- GPU 侧持久工作循环轮询任务，通过版本化算子表动态调用 JIT 生成的快照、恢复函数，虚线代表无停机算子热更新通路。

环形缓冲区每个任务描述符仅 64-128 字节，主机采用 store-release 内存序写入，GPU 通过 load-acquire 轮询，单次任务提交延迟低于 100 纳秒，相比同步 `cudaLaunchKernel` 的 7.6 微秒触发延迟，降低 76 倍。

### 2.3 故障模型与资源开销

> - **Concordia 采用标准停止故障模型**：应用算子、GPU 卡、NCCL 通信链路允许故障，持久内核本身作为可信控制环路，假设不发生独立软件崩溃；若持久内核心跳中断，系统判定整块 GPU 失效，直接读取 CXL/DRAM 存储的最后完整增量日志，在备用 GPU 完成恢复。
> - **资源开销量化数据**：RTX PRO 6000 总计 188 个 SM 计算单元，持久内核仅占用 1 块，资源占比 0.53%。

## 三、三大核心技术模块完整拆解

> Concordia **整套系统由二进制插桩、分层 JIT 增量快照、CXL 追加式日志三大耦合模块构成**，三者依托持久内核统一调度，单独拆分任意模块都无法实现完整透明容错能力。

- PTX/SASS 底层插桩解决跨框架安全点识别问题；
- 分层 JIT 快照针对 LLM 三类显存状态生成专用扫描逻辑；
- 追加式 AOF 日志分离持久化存储与稀缺 HBM 显存。

### 3.1 PTX/SASS 二进制底层插桩：跨框架安全点注入

> 插桩分为两条路径：

- 存在 PTX 源码的算子直接重写指令插入同步点钩子；
- 闭源 Cubin 二进制采用 SASS 反编译补丁。

在算子入口、CTA 屏障、NCCL 通信边界插入轻量级探测逻辑，全程不修改上层业务代码，实现全框架透明兼容。

![文章插图](/articles/2026-06-30-gpu-47-1-5-llm-ac572942/images/06.webp)

::: image-caption
图 3：Concordia PTX/SASS插桩与跨架构CTX编译流水线，从上层推理框架到底层硬件二进制完整链路。自上而下覆盖 vLLM、PyTorch 等推理框架，经过 Triton、CUDA 算子编译器生成 PTX/SASS 二进制，Concordia 拦截模块加载过程插入暂停、快照钩子；可选 CTX 可移植中间层实现 NVIDIA、AMD、Intel、Tenstorrent 异构 GPU 跨架构恢复。
:::

::: block-1
传统 LLVM IR 插桩仅能处理源码可见算子，无法覆盖厂商闭包库、Triton 即时生成内核，而 **PTX/SASS 直接拦截 GPU 二进制加载动作，是实现无侵入容错的关键前置能力。**
:::

### 3.2 面向 LLM 分层内存的 JIT 专用增量检查点

> 系统会对注册的每一块 GPU 显存区域生成专属快照处理函数，通过 NVRTC 实时 JIT 编译，写入持久内核算子表，针对三类显存生成差异化逻辑：

1. 基础权重（不可变）：仅在会话初始化生成一次基础快照，运行时不参与脏页扫描，消除 90%以上冗余数据拷贝；
2. PagedAttention KV 缓存：JIT 生成块表感知扫描器，直接读取分配器内置脏页位图，无需 GPU 影子缓冲区；
3. LoRA/优化器可变区域：生成稠密页面对比器，创建轻量化 GPU 影子缓存，4KB 粒度逐页比对脏数据。 增量快照四阶段流水线全部在持久内核内部串行执行，无主机交互：
4. 脏页发现：依托 HBM 带宽遍历注册显存，筛选修改页面；
5. 日志记录封装：写入区域 ID、版本号、脏页偏移、校验和元数据；
6. CXL/DRAM 追加传输：仅将脏页数据拷贝至主机侧持久日志；
7. 元数据同步：更新分配器版本标记、GPU 影子缓冲区。 复杂度公式对比：$CPU_{ckpt}= \frac{S_{total}}{B_{PCIe}} + \frac{S_{total}}{B_{CPU}}$$GPU_{ckpt}= \frac{S_{total}}{B_{HBM}} + \frac{S_{dirty}}{B_{PCIe}}$符号释义：

### 3.3 基于 CXL/DRAM 的 AOF 增量持久日志

> Concordia 借鉴 Redis AOF 追加日志设计，拒绝在 GPU HBM 中存储快照副本，HBM 资源仅用于推理计算，持久化存储卸载至主机 DRAM 或 CXL 内存池，解决显存容量稀缺痛点。

日志核心规则：

1. **仅追加不修改**：每一次算子/通信边界的增量脏页记录顺序写入，仅完整写入 commit 标记的记录作为有效恢复数据，故障时截断未提交尾部；
2. **后台日志压缩**：独立主机线程周期性将大量增量记录合并为基础快照+少量增量后缀，控制故障恢复时的重放开销；
3. **分层恢复**：恢复流程优先加载基础权重快照，再顺序重放增量 KV、LoRA 记录，无需完整拷贝全量模型。

分布式场景下，CXL 内存池可作为低延迟的共享存储介质，各 GPU 的增量日志可统一存放其中，便于备用节点快速读取恢复，降低存储部署复杂度。

::: block-1
分层 JIT 快照+二进制插桩+CXL 追加日志形成闭环，实现无业务代码修改、硬件带宽最优、不占用推理显存三大特性，是区别于所有传统 GPU 检查点工具的核心创新组合。
:::

## 四、分布式 NCCL 集群故障自愈流程

> 单 GPU 场景仅验证快照性能，真实云环境以多卡 NCCL 分布式推理为主，**Concordia 深度封装 NCCL 通信库，将集合同步边界作为天然快照触发时机，构建完整四级自愈流水线。**

系统配套三级就绪度 GPU 备用资源池，故障时自动调度替换卡，无需人工干预集群拓扑重构，将传统 47 秒宕机压缩至 1.5 秒总恢复时长。

### 4.1 NCCL 通信边界作为天然检查点时机

NCCL AllReduce、点对点收发等集合操作完成后，所有 GPU 显存状态达成全局一致，是语义安全的快照触发点，**Concordia 通过 API 拦截 NCCL 调用，在每次集合操作结束后自动提交快照任务至环形缓冲区。**

传统方案需要业务代码手动插入快照逻辑，实现成本高且容易出现快照时机与通信状态不同步的问题，增加了状态一致性的维护难度；依托 NCCL 边界自动触发，保证每次增量日志都对应全局一致的推理状态，从根源规避恢复语义错误。

### 4.2 四级故障恢复流水线：10ms 检测至 1.5s 完整上线

> 系统划分三类备用 GPU 节点，适配不同故障恢复速度需求：

Gandiva、Tiresias 等集群调度工具的容错逻辑依赖主机侧调度执行，故障后通常需要重启 GPU 进程、重新加载模型，恢复时长可达数十秒；容错机制未下沉至 GPU 二进制层，恢复粒度较粗。
