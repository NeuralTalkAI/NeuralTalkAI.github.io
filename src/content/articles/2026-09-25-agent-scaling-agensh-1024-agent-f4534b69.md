## 一、多 Agent 的并发梦，卡在了一个"项目经理"身上

> 单个 Agent 的能力边界，由一个上下文窗口、一条动作流、一条记忆流共同划定；它再聪明，同一时刻也只能沿着一条串行路径向前走。复杂任务动辄数小时的延迟，根子就在这里。

当我们想把延迟压下来，最直觉的工程手段就是并发：一个 Agent 干不完的活，分给一群 Agent 同时干。过去一年，Codex 的 sub-agent、Claude Code 的 sub-agent 与 agent teams、GitHub Copilot 的 fleet、Kimi 的 Agent Swarm 先后落地，多智能体系统从论文走向了真实开发流。

但这些框架几乎共享同一张图纸：orchestrator-worker，主管加工人的结构。一个主 Agent 负责理解目标、拆解任务、把子任务派发给并发 Worker，再回收和整合它们的产出。**Kimi Agent Swarm 甚至专门训练了一个 orchestrator 来做任务分解与调度，因为"派活"本身已经被证明是一项需要专门学习的能力。**

::: block-1
问题在于，这套结构把系统里最要命的部分留在了中心。**Worker 在边缘并行了，协调却仍然是串行的**：每一个子任务的分派、每一份进度汇报的消化、每一次结果的整合，都要从主管 Agent 的上下文窗口里过一遍。Worker 越多，主管要读的报告、要维护的依赖、要裁决的冲突就越多😅，它的上下文和动作流很快饱和，:mdnice-highlight[系统规模最终被一个 Agent 的管理带宽锁死]。
:::

> 这个现象对做体系结构和并行计算的人来说毫不陌生。1967 年 Amdahl 提出的加速比公式，讲的就是同一件事：

$$
S(N)=\frac{1}{s+\frac{1-s}{N}}
$$

其中 $S(N)$ 是 $N$ 个并行单元相对单个单元的加速比，$s$ 是任务中无法并行、必须串行执行的比例，$1-s$ 是可并行部分的比例。:mdnice-bold-italic[当 $N$ 趋向无穷大时，加速比的上限只有 $1/s$。举个例子，哪怕只有 20% 的工作必须串行，即 $s=0.2$，你堆再多核心，整体加速也不会超过 5 倍。中央编排器恰恰在制造一个随 Agent 数量增长的串行段：派活和收口都绕不开它，$s$ 降不下来，加人就迅速进入边际递减。]

Anthropic 在自家多 Agent 系统的工程复盘里也观察到类似代价：多 Agent 会成倍放大 token 消耗，而主管 Agent 的上下文是所有 Worker 输出的唯一汇聚点。**并发红利是真的，中心瓶颈也是真的😅。**

::: block-1
总之，**现有多 Agent 框架的根本矛盾是边缘并发、中心串行：Worker 数量可以随便加，协调能力却绑定在一个主管 Agent 的上下文窗口上**。按 Amdahl 的视角，这个串行段不消除，:mdnice-highlight[Agent 数量就无法成为一个真正可外推的 scaling 维度]。
:::

## 二、拆掉中心：把协调下沉为基础设施，请特权 Agent 退场

> **既然瓶颈是中心那个"全能管理者"，最彻底的解法就是把它从架构图里删掉**。Agensh 给出的答案是：:mdnice-bold-italic[没有主管，所有 Worker 地位平等，靠一套轻量的组织基础设施自组织协作。] 😅

**Agensh 这个名字可以理解为 agent 与 harness 的组合，即驾驭 Agent 的工装框架**。论文对它的定义很克制：一个没有中央编排器的、可扩展的自组织多 Agent harness。并发 Worker 异步运行，通过共享基础设施交换状态与进度，自己发现任务、自己认领、自己交付。

![文章插图](/articles/2026-09-25-agent-scaling-agensh-1024-agent-f4534b69/images/06.webp)

::: image-caption
图 2：多智能体系统对比。左图为以往工作，Worker 由中央编排器组织；右图为 Agensh，Worker 通过轻量基础设施自组织协作，该设施包含共享工作区、消息接口、共享上下文。左图是典型的星型拓扑，所有协作边都终止于中心节点，中心的上下文窗口就是全局瓶颈；右图中心退化为一个不带智能的交换节点，Worker 之间通过共享服务直连，拓扑上从"一个大脑指挥双手"变成"一群人共用一套协作系统"。
:::

这里有一个需要点破的关键洞察：**Agensh 消灭的是"管理者"这个角色，而管理本身一件都没有少**。任务分派、冲突仲裁、进度整合这些事依旧存在，它们被重新安放成了基础设施提供的能力。

- Worker 想知道别人在干什么，去读共享状态；
- 想宣布自己占了哪块活，往共享上下文追加一条记录；
- 代码要合入，交给版本控制系统检测冲突。

协调从"某个人的智能"变成了"系统提供的公共服务"。

> 用体系结构的语言类比，这是**从"一颗大控制核调度众多计算核"转向"众多对等计算核、片上网络、共享末级缓存与邮箱中断"**；用分布式系统的语言类比，这是** 从单体调度器转向带消息总线和共享存储的对等集群**。:mdnice-bold-italic[管理者的角色被下沉为三类原语：存放工作产物的地方、传递消息的通道、沉淀知识的黑板。]

Agensh 因此由两半耦合而成：**每个 Worker 各自执行的多 Agent 合作循环，以及全组织共享的 agentic organization infrastructure**。前者解决"一个 Worker 如何把个人进展变成被验证的组织贡献"，后者解决"积累的工作、发现和消息如何对全组织可见"。接下来两章我们分别拆开看。

## 三、五步合作循环：每个 Worker 都是自己的项目经理

> harness 的核心抽象是它的循环。Agensh 里每个 Worker 都并发、异步地执行同一个五步循环，不断把个人进展转化为经过验证、并入主干的组织贡献。

![文章插图](/articles/2026-09-25-agent-scaling-agensh-1024-agent-f4534b69/images/07.webp)

::: image-caption
图 3：Agensh 多智能体合作循环。Worker 并发地收集上下文、认领子任务、采取动作、验证结果、合并进度，自组织地重复直到用户目标达成；所有 Worker 异步推进，通过基础设施共享进度；绿色向上三角表示异步读，橙色向下三角表示并发写。这张图是全文方法的总纲：五步构成一个不断回环的圈，绝非跑一遍就结束的一次性流水线；每个 Worker 独立转圈、互不等待，循环的每一步都与底层三件基础设施有明确的读写关系。
:::

五步具体如下表。

| 步骤 | Worker 的动作 |
| --- | --- |
| Gather context，收集上下文 | 读取共享的用户目标、当前状态、同伴进度与消息、以及积累的发现，弄清楚哪些事已经做完、哪些还空着，同时与环境交互，规划下一步最有价值的动作 |
| Claim sub-task，认领子任务 | 自己提出一个要做的子任务，并把它的范围以一条 CLAIM 记录追加到共享上下文，相当于当众贴出"这块我包了"；如果两个人的 CLAIM 范围重叠或冲突，鼓励通过私信直接解决 |
| Take action，采取动作 | 在本地用可用工具与环境交互，真正动手解决自己提出的子任务；一旦做出可能帮到别人的发现，随时通过共享上下文汇报中间进展 |
| Verify results，验证结果 | 把本地产出与子任务的验收标准逐条比对，不达标就换方案重来，直到满足标准 |
| Merge progress，合并进度 | 把贡献合并进共享工作区，让同伴可用，同时发布一条更新，说明改了什么、背后的思路、验证证据，方便别人在其基础上继续；如果合并被冲突挡住，就吸收同伴的最新进展、解决冲突、再次合并 |

第 5 步完成后，Worker 直接回到第 1 步，基于刚并入的工作和同伴的最新更新，为下一个子任务收集上下文。整个过程没有全局栅栏、没有统一节拍，**每个 Worker 按自己的节奏转圈，谁也不用停下来等别人凑齐一轮**。

> **"自己提任务、自己认领"是这个循环最值得玩味的设计。** 传统编排器模式下，任务发现与分配是一条集中式队列，主管是唯一入口；**Agensh 把这件事分布式化了：任务在干活的现场被发现，由最接近问题的人主动认领，CLAIM 记录承担了乐观并发控制的角色，类似并行编程里的加锁与比较并交换（CAS）**：先声明占坑，撞上了再通信仲裁。:mdnice-bold-italic[任务发现从"自上而下派活"变成了"自下而上抢活"，中心队列就此消失]。

从聚合产出的角度，可以把一个 N 人组织的有效产出速率近似写成：

$$
R(N)\approx N\cdot r\cdot \eta(N)
$$

其中 $r$ 是单个 Worker 的产出速率，$\eta(N)$ 是取值在 0 到 1 之间的协调效率，刻画重复劳动、冲突阻塞、信息丢失带来的折损。裸奔的群聊式协作会让 $\eta(N)$ 随 N 增大快速衰减；Agensh 的循环与基础设施，核心目的就是让 $\eta(N)$ 在 N 很大时依然维持在可用区间。

::: block-1
回顾一下，五步循环给每个 Worker 同时装上了工程师、项目经理和质检的职能，再用 CLAIM 和合并验证把"自组织"约束成"有序的自组织"。:mdnice-highlight[个人循环是标准化的，任务发现与分配却是分布式的] ——这正是千人规模能够不依赖主管而运转起来的微观机制。
:::

## 四、组织基础设施三件套：工作区、消息板与共享上下文

> 一群对等 Worker 要协作，至少需要三样东西：访问彼此工作产物的地方、沟通进行中事务的通道、留住可复用发现的记忆。Agensh 用三个协调机制分别对应。

::: image-caption

### 4.1 共享工作区：用 Git 把"并发改同一套代码"变成可解的问题

共享工作区是一个文件系统，承载全组织开发中与已整合的工作，要求支持并发写与异步读：Worker 各自开发独立贡献，同时能访问别人已发布的成果；它还要保留版本历史、支持合并，并把合并冲突暴露出来供回溯解决。

> Agensh 直接用 Git 平台承担这一职责，实现上选用自托管的 Gitea：

- Worker 在私有检出和分支上修改，再把贡献整合进主干分支；
- Git 记录每次变更的来源、检测文本级合并冲突，并用 issue 和 pull request 承载评审流程。

这一选择的深意是：**多 Agent 协作里最难的"多人整合同一份代码"问题，Git 用二十年工程实践已经给出了成熟答案**：分支隔离、三路合并、冲突暴露、历史可追溯。Agent 组织不需要重新发明它，只需要让 Worker 学会遵守它。

### 4.2 消息接口：分优先级的异步通信，私信能"当场打断"

> **消息接口让 Worker 通过沟通协调进行中的工作、处理所有权重叠、解决依赖冲突**。Agensh 的消息接口在实现上用 Mattermost，包含两类通道：**共享任务频道承载团队公告，私信承载紧急的一对一沟通**。:mdnice-bold-italic[两者的投递时机经过精心设计：低优先级的频道消息在每次循环开始时投递，高优先级的私信在每次基础设施工具调用返回时就投递]。

**私信能在对方当前这一轮（turn）之内送达，是解决撞车最快的方式，代价是会打断对方正在做的事**。消息接口同时保留历史、异步投递，让 Worker 在同伴继续工作的同时，及时解决认领重叠、协商依赖、请求援助。

### 4.3 共享上下文：一条只追加的"组织黑板"，FAIL 是最值钱的记录

> **共享上下文用来沉淀全组织可复用的发现与工作认领**，思路取自 DeLM，即 Decentralized multi-agent systems with shared context。Worker 发布简短、带类型的条目，共五类，如下表。

| 条目类型 | 含义 |
| --- | --- |
| OBSERVED | 记录观察到的参考程序显著行为 |
| FACT | 记录已经确认的事实 |
| FAIL | **记录被证伪的失败思路，论文称其为最高价值的条目，因为它能阻止同伴继续在同一件事上花预算** |
| CLAIM | 声明进行中的工作认领，提示同伴选择别的方向 |
| PATCH_SUMMARY | 用 files=、idea=、evidence= 的固定格式描述已完成的改动 |

在按时长计费的 Agent 协作里，一条踩坑记录省下的，是后来者重复踩坑的全部探索成本。

**黑板是只追加（append-only）数据库**，保留近期记忆；条目有长度上限，普通条目 100 字符，PATCH_SUMMARY 300 字符，长内容放进 detail，由 board_unfold 展开。

**为了支撑更长的任务周期，Agensh 还提供 context grep 工具**：board_read 只返回最近 2,000 条，board_grep 则能跨完整历史按关键词检索，支持逗号表示 OR、& 符号表示 AND 的布尔语法。:mdnice-bold-italic[新条目被视为高优先级更新，会在其他每个 Worker 下一次工具调用返回时转发，让同伴的发现快速扩散到全组织。]

::: block-1
总之，三件套按"重状态、短协调、深知识"分层，覆盖了对等协作的全部基本需求。其中最具杠杆性的设计是共享上下文：:mdnice-highlight[它把一次次孤立探索，变成全组织可检索、不可重复的共同记忆]，FAIL 条目直接替整个组织止损，这正是协调效率 $\eta(N)$ 能在大规模下维持住的关键。
:::

## 五、工程实现：组织长在单 Agent 之上，循环写在提示词里

> Agensh 叠加在单 Agent harness 之上，作为组织层存在，并不取代底座；单 Agent harness 决定一个 Worker 如何思考与行动，Agensh 决定多少 Worker 接收事件、共享状态、协同贡献。

### 5.1 分层架构与即插即用

对每个 Worker，底层单 Agent harness 拥有本地 agentic loop：维护会话状态、调用模型、执行工具、产出下一步响应。Agensh 在这条循环之外供给组织级能力：Worker 身份、合作协议、事件路由、健壮派发、共享工作区访问、消息、共享上下文，以及恢复与活性机制。

两层之间的接口被刻意压到最小、即插即用。**合作循环通过写进每个 Worker 提示词的工作流指令来实现，而没有硬编码进运行时**；完整 Worker 提示词在附录 A，除了 Worker ID 之外对所有人完全相同。论文里那句"1024 coders, all equal. You claim what to build, you build it, you merge it, and you choose the next thing"，即 1,024 个码农人人平等，你认领、你构建、你合并、你决定下一件事，就是这套组织的全部宪法。借助轻量的 harness 专用适配器，Agensh 可以接 Claude Code、Copilot 等不同底座，而无需改动合作循环、共享服务或底座自身的 agentic loop。

### 5.2 事件驱动运行时：把分布式系统的可靠性原语搬给 Agent

> **作者还展示了这套组织能在千级规模稳定运转的工程内核**。每个 Worker 由事件驱动，配对一个 router：对 Gitea，通过 server-sent event 触发拉取比上次更新的通知；对 Mattermost，长连接投递消息，断线重连时补提漏接消息。

新活动写入 Worker 的持久队列并唤醒 dispatcher；每个事件带唯一 ID 用于去重。dispatcher 每次唤醒都从队列出发，把待处理事件排序、合并进下一个 prompt，投递给 Worker 的持久会话，本轮结束后才把事件标记为已发送；轮次中到达的事件排队等下一轮。失败投递按递增间隔重试；router 重启后未完成事件回到队列，Worker 的上一会话尽可能恢复。如果 Worker 空闲 10 分钟，空闲检测器会发提示催它继续；如果一整轮没有产出共享上下文条目，跟进提示会提醒它发布发现。

共享上下文与消息有两条投递路径。

- 新一轮开始时，router 把排队的工作区通知、新到消息和近期共享上下文追加进 prompt；
- 轮次进行中，任何基础设施工具调用外的包装器会把待处理私信和新上下文条目追加到工具返回结果里。这条路径作用于 MCP 工具返回，:mdnice-bold-italic[不会粗暴打断一个正在运行的任意进程]，只在 Worker 本来就要读工具结果时把新信息递到眼前。

### 5.3 千人部署：错峰启动与收尾冻结

> 1,024 个 Worker 分布在 16 个节点上，每节点 64 个 Agent。

为减少开局的范围争抢，Agent 错峰激活：

- 第一小时每 30 秒启动一个，之后每 3 秒一个。设首个 Agent 启动时刻为 $t$，在 $T=t+6$ 小时全部终止并导出提交；
- $T-45$ 分钟发出"停止派发新特性、确保根构建可用、落地在途 PR"的冻结提醒，$T-5$ 分钟再发"合并一切就绪内容、确认 compile.sh 与产物可用"的终局提醒。

底座统一为 Copilot 单 Agent harness，模型为高推理强度的 GPT-5.6-sol，输入上限 272,000 token、输出上限 128,000 token。

::: block-1
整体看下来，**Agensh 的工程实现是"最小智能假设加最大可靠性兜底"：** 循环只存在于一段人人相同的提示词里，运行时则用持久队列、事件去重、退避重试、心跳活性、断线恢复这套经典分布式原语兜底。:mdnice-highlight[创新是用成熟的系统工程把同一段提示词放大一千倍依然成立]。
:::

## 六、上千 Agent 实测：最终分数更高，到达分数的时间更短

> 论文用 ProgramBench 检验一个问题：:mdnice-bold-italic[把多 Agent 组织规模做大，能否在复杂长程任务上拓展 agentic 软件工程的新前沿。所有配置锁定同一模型、同一底座、同一 6 小时预算，只改 Agent 数量。]

ProgramBench 要求 Agent 在断网条件下、6 小时内从零重建参考软件的行为：每个容器挂载一个预编译参考二进制，Agent 可以运行它、喂各种输入观察输出，但不能读取它的二进制字节，最终提交的代码库要通过隐藏测试。论文挑出其中最难的五个系统，如下表。

![文章插图](/articles/2026-09-25-agent-scaling-agensh-1024-agent-f4534b69/images/09.webp)

::: image-caption
表 1：ProgramBench 五大最难任务的参考仓库规模，字段依次为任务、提交哈希、文件数、代码行数、代码体积，单位 MB。PHP-src 以 26,266 个文件、281 万行、119.76 MB 居首，FFmpeg 达 155 万行；即便是最小的 pandoc 也有 2,767 个文件、十万行量级。这类规模意味着任何单个上下文窗口都无法一次性装下全貌，任务天然要求分而治之与长程整合，是检验多 Agent 协作的理想试金石。
:::

### 6.1 主结果：从 1 到 128 Agent，均分相对提升约 49%

> 实验具体数字上，五任务测试通过率均值随 Agent 数 1、8、32、128 依次为 19.31%、20.68%、26.52%、28.78%，1 到 128 净增 9.47 个百分点。

![文章插图](/articles/2026-09-25-agent-scaling-agensh-1024-agent-f4534b69/images/10.webp)

::: image-caption
图 5：6 小时预算下，在五大最难 ProgramBench 任务上从 1 扩展到 128 个 Agent；最终测试通过率均值从 1 个 Agent 的 19.31% 升至 128 个 Agent 的 28.78%；六张子图分别为五任务均值及五个单项，横轴为 Agent 数量，采用以 2 为底的对数刻度。均值曲线单调上行，但分项暴露了真实的规模噪声：pandoc 从 33.89 升到 50.94、ctags 从 25.82 升到 45.62，是最大赢家；ctags 在 8 Agent 处反常跌到 18.37 后才陡升，FFmpeg 在 32 到 128 时从 13.22 微退回 12.89，gromacs 前三个档位几乎持平。自组织协作的收益总体显著，却并非每一步都严格为正。
:::

相对提升幅度可以直接算：

$$
\frac{28.78-19.31}{19.31}\approx 49\%
$$

::: block-1
其中百分号前的两个数分别是 128 Agent 与 1 Agent 的最终通过率，分子是绝对提升的 9.47 个百分点。论文据此判断，:mdnice-highlight[持续增加协作 Worker 数量，能够在长时程上稳定且可观地改善复杂软件复刻的质量。]
:::

### 6.2 延迟维度：更大的组织更早到达同一分数线

![文章插图](/articles/2026-09-25-agent-scaling-agensh-1024-agent-f4534b69/images/11.webp)

::: image-caption
图 6：6 小时运行的前 2 小时内，1 到 128 个 Agent 在五大任务上的测试通过率随时间变化；更大的组织通常更早达到更高通过率，横轴为分钟。以 pandoc 为例，128 Agent 在第 30 分钟就越过 30% 通过率，32 Agent 到第 60 分钟、8 Agent 到第 90 分钟才首次越线，单 Agent 在前两小时始终未能越过；PHP-src、FFmpeg 等单项也呈现同样的"人多到得早"。Agent 扩容同时买到了质量和速度两样东西。
:::

### 6.3 Agent 数量推到 1024：pandoc 上 55.06%，相对单 Agent 提升约 62%

![文章插图](/articles/2026-09-25-agent-scaling-agensh-1024-agent-f4534b69/images/12.webp)

::: image-caption
图 1：6 小时断网预算下，从零构建 pandoc 时从 1 扩展到 1,024 个 Agent；最终通过率从 1 个 Agent 的 33.89% 升至 1,024 个 Agent 的 55.06%；随组织长大，涌现的自组织协作从同伴协调逐级扩展到多 Worker 整合、标准化工作流与专业化角色。128 Agent 为 50.94%，1,024 Agent 再增 4.12 个百分点，相对单 Agent 净增 21.17 个百分点，相对提升约 62%。曲线仍在抬头但斜率放缓，说明千人量级收益为正、边际递减已经出现，这与 Amdahl 揭示的规律一致：剩余串行段，如最终集成与测试一致性，决定了曲线的天花板。
:::

相对提升同样可直接核算：

$$
\frac{55.06-33.89}{33.89}\approx 62\%
$$

在模型与底座全程不变的前提下，这些实验给出了一个干净的结论：**Worker 数量本身就是一条独立于模型规模的 scaling 曲线**，它同时改善复杂任务的最终质量，以及到达给定质量所需的时间。

::: block-1
回顾一下，实验在严格控制变量（同模型、同底座、同 6 小时预算，只改 Agent 数）下证明了两件事：:mdnice-highlight[128 Agent 带来约 49% 的相对分数提升，更大组织把达标时间从小时级压到分钟级]；1,024 Agent 在 pandoc 上继续拿到 55.06%。组织智能可以靠扩大自组织协作来增长，这是论文最硬的证据。
:::

## 七、规模之上涌现的"组织形态"：协作模式如何随规模生长

> 所有 Worker 遵循同一循环、拿到除 ID 外完全相同的提示词，没有人被分配岗位；但记录下来的轨迹显示，新的协作形式随组织长大逐级涌现，而且全部由 Worker 自发完成。

### 7.1 8 Agent：与同伴协调实现

Worker 能商定具体技术接口，再各自实现符合接口的组件。

- gromacs 中，Worker 宣布模块接口后独立实现了遵循它的命令模块；
- 它们也能自行发现并解决认领重叠：FFmpeg 里一个 Worker 在与同伴讨论重叠后，主动改变范围、接手互补工作。

### 7.2 32 Agent：管理跨多人的整合

多个 Worker 能共同打磨一份技术贡献。PHP-src 中，几位同伴起初批准了一份贡献，另一个 Worker 找出具体反例，先前的批准随即撤回，作者修复后同伴重新评审，最终由一名同伴合并。**更多人开始主动管理整合，参与沟通的同伴范围明显变广。**

### 7.3 128 Agent：自组织的专业化与工作流标准化

> 专业化在这一档出现：**Worker 根据相关历史经验挑选评审人**，并反复复用这些评审关系；也能把整合一份贡献的责任移交给专门解决冲突、验证合并结果的同伴。

**Worker 还会协商、遵循并复用标准化流程**。pandoc 中两名 Worker 建立了标准集成协议：作者更新并测试分支，再把提交哈希发给同伴验证合并，协议后来被其他人复用；几次失败后他们进一步修订协议，约定授权同伴完成更新、测试、检查、合并的完整周期，并明确接受、照此处理新的 pull request。

### 7.4 1024 Agent：组织尺度的角色专业化

这一档有多个 Worker 承担同一专业角色，或在同一技术领域形成专长。

pandoc 中出现多名整合工：一个 Worker 可以同时联系几位候选整合工，选第一个有效响应者、取消其他请求，选定后才交出待整合代码。同一技术领域的专长 Worker 还能在别人尝试失败后接手恢复，:mdnice-bold-italic[组织因此不再依赖任何单个 Worker，鲁棒性显著增强]。

> 这些观察解释了论文为何把"涌现"放在如此重要的位置：没有岗位说明书、没有额外训练、没有主管，**Worker 自己挑选合作者、划分职责、建立并修订流程**。

- 用社会科学的语言，这是惯例与组织分工在数字群体中的自发形成；
- 用系统工程的语言，冗余的同类角色带来了故障接管能力，:mdnice-bold-italic[去中心化在规模足够大之后，反而买到了可靠性]。

### 7.5 意义、边界与未尽之问

> 这项工作的真正分量，是:mdnice-bold-italic[把"Agent 数量"确立为与模型参数、数据规模并列的新 scaling 维度：模型和底座保持不动，仅靠组织扩张就能同时推高质量、压低延迟，为硬时间预算下的复杂任务提供了可落地的路径]。项目主页还公开了由 530 余万条活动事件构成的千 Agent 轨迹回放，让"涌现"可以被逐帧核验。

以 Infra 视角冷静审视，边界同样清晰。

- 其一，证据集中在五个任务、单一模型代际、单一底座，尽管适配器声称可迁移；1,024 Agent 的结果只在 pandoc 单个任务上取得，绝对通过率仍只有 28.78% 与 55.06%，离真正复刻这些系统尚有距离。
- 其二，**千人组织的 token 与算力开销极为可观，论文没有给出成本与质量的直接对照，约 62% 的相对提升对应多少倍的资源投入，是决策者必须自己算清的一笔账。**
- 其三，:mdnice-bold-italic[ctags 的 8 Agent 回撤、FFmpeg 的微退说明自组织存在协调噪声，规模收益并非无条件成立]；代码仓库在本文发稿时也尚未公开。

沿着这条线往下，**未来值得期待的是两条 scaling 曲线的乘积：更强的模型乘以更大的自组织组织，以及让协调效率 $\eta(N)$ 衰减更慢的下一代组织基础设施**。当 Agent 像今天的 GPU 一样可以按数量弹性扩容，组织层的操作系统，可能才是 AI Infra 下一个兵家必争之地。

::: block-1
总之，Agensh 用最克制的手段证明了一个有想象力的命题：:mdnice-highlight[去掉中心、给足基础设施，协作秩序与专业分工会从大规模群体中自己长出来]。它的边界提醒我们规模化仍有成本与噪声，它的方向则指明：:mdnice-highlight[Agent 数量的 Scaling，是通用智能前沿上一条刚刚被点亮的坐标轴]。
:::
