## 一、引言

> LLM 推理正日益成为人工智能（AI）成本的主要构成部分。为管控这些成本，运维人员需要调整大量可调节的系统设置选项，包括各类并行策略、缓存策略和调度算法等[4,31]。这些参数需根据模型、工作负载和硬件平台的迭代不断调整。:mdnice-bold-italic[通过试错式端到端评估寻找最优部署配置，不仅速度极慢且成本极高：即便是在 GPU 集群上评估单一配置，也可能需要数小时，且计算成本高达数千美元[4]。这一问题严重阻碍了 LLM 的生产部署和相关系统研究的推进。]

### 1.1 当前方法的局限性

**为应对这一挑战，研究界开发了离散事件模拟器** [4,12,20]，可低成本地对服务性能进行建模。:mdnice-bold-italic[这类模拟器具有显著优势：运行速度比真实执行快多个数量级，且易于修改以原型化新策略和优化方案]。然而，它们需要重新实现服务系统的所有核心组件，包括调度器、内存分配器和请求分发器等。

- **在系统较简单的早期，这种方法是可行的**：例如在 Vidur[4]中，为建模 vLLM 最初的连续批处理（Continuous Batching）调度器，仅需不到 150 行代码。
- **但如今，LLM 推理引擎已包含复杂功能**，如预填充-解码分离[10,23–25,32]和分布式前缀缓存[10,23]，这些功能的实现代码往往长达数万行。
- 此外，**LLM 推理服务系统的迭代速度极快**：每年有数百名贡献者提交数千次代码更新[28]，:mdnice-bold-italic[这导致模拟器始终落后于最新系统，维护负担不断加重。]

### 1.2 核心洞察

服务系统的**执行时间主要消耗在等待 GPU 计算上，而非控制决策** 如调度、批处理组合等。CPU 控制平面（负责调度、批处理、内存管理等逻辑）的执行时间仅为微秒级，而 GPU 操作（如核函数执行）的时间则长达数十毫秒，占总执行时间的 90%以上。

此外，控制流逻辑在很大程度上与 GPU 计算的输出无关——调度器仅基于请求、批处理、内存块等逻辑抽象工作，而 **GPU worker 仅负责物理计算，不参与控制流决策。**

::: block-1
:mdnice-bold-italic[这种分离为一种全新的方案提供了可能：直接运行真实的服务系统，同时通过“虚拟时间推进”跳过 GPU 等待时间]。我们将这种方案称为“时间跳跃仿真（Time-Warp Emulation）”。
:::

### 1.3 我们的方法

REVATI 直接运行 vLLM 或 SGLang 等真实服务框架，将 GPU 操作替换为“虚拟时间跳跃”。

- **当一个 worker 准备执行某个批处理任务时，它会先查询**：“在 H100 GPU 上执行该批处理需要多长时间？”基于预测的执行时长，worker 向一个中央“时间管理器（Timekeeper）”请求时间跳跃——:mdnice-bold-italic[该管理器负责协调所有分布式进程的虚拟时间。]
- **时间管理器确保所有进程同步推进虚拟时间，同时保持因果关系**：例如，若 worker A 需要 15 毫秒，worker B 需要 25 毫秒，则系统先将虚拟时间推进 15 毫秒（此时 A 完成任务，B 仍剩余 10 毫秒）。
- 此外，REVATI 还**包含一个 CUDA 仿真层，可透明拦截 GPU 调用，向服务框架提供“虚拟设备”**，同时绕过实际 GPU 执行。这使得服务系统的代码无需物理 GPU 即可在加速的虚拟时间中运行。

通过直接运行未修改的控制平面代码，REVATI 能自动捕捉系统的复杂行为，无需人工建模——例如自适应批处理、多层前缀缓存管理、预填充-解码分离等复杂功能均可“开箱即用”。**REVATI 的维护成本极低：为适配一个新的服务框架，仅需修改不到 25 行代码**。这种“高速、低成本、易适配”的特性，使得 REVATI 能够快速探索最优部署配置，同时加速最先进 LLM 推理技术的开发与落地。

## 二、背景与动机

> 性能建模对于 LLM 服务系统的高效部署至关重要，因为在 GPU 集群上进行真实实验的成本过高。然而，现有的基于模拟器的方法，由于功能迭代滞后于实际服务系统，难以保证建模精度。本节将阐述 LLM 服务的配置优化挑战，并说明为何离散事件仿真无法满足现代服务基础设施的需求。

### 2.1 配置优化问题（Configuration Optimization Problem）

现代 LLM 服务系统的配置空间极为庞大。以部署 Qwen3-235B-A22B 模型[30]为例，运维人员需选择以下参数：

| **参数名称** | **取值范围** | **参数说明** |
| --- | --- | --- |
| 张量并行度（TP degree） | 1-8 | 将模型张量分割到多个 GPU 上并行计算的方式 |
| 流水线并行度（PP stages） | 1-8 | 将模型层分割为多个阶段，在不同 GPU 上流水线执行的方式 |
| 专家并行度（EP degree） | 1-8 | 对混合专家（MoE）模型，将专家层分配到不同 GPU 上并行计算的方式 |
| 最大批处理大小 | 1-256 | 单次 GPU 执行处理的请求数量 |
| 分块预填充大小 | 256-8192 token | 将长输入序列分割为多个块进行预填充的长度 |
| KV 缓存淘汰策略 | LRU、LFU、成本感知等 | 当缓存空间不足时，选择淘汰哪些 KV 缓存条目的规则 |
| 路由策略 | 轮询、粘性、缓存感知等 | 将请求分配到不同 worker 的规则 |
| 分离策略 | 共置 vs 预填充/解码分离[6,25,32] | 是否将预填充阶段和解码阶段部署在不同节点上 |

:mdnice-bold-italic[这些参数的组合形成了极为庞大的配置空间。已有研究表明，根据模型和工作负载特性调整这些配置，可将吞吐量提升 3 到 5 倍] [4,32]。例如，Mitra 等人[22]的研究显示：

- 对于类检索增强生成（RAG）的“预填充密集型”工作负载（输入 16K token，输出 2K token），采用预填充-解码分离技术[24,32]部署 Llama70B 模型，吞吐量比“预填充-解码共置”方案[5]提升 1.8 倍；
- 但对于“解码密集型”工作负载（输入 2K token，输出 8K token），分离方案的收益极小（吞吐量提升<10%），甚至可能因 KV 缓存传输开销和流量模式动态变化而降低性能。

为有效部署 LLM 服务，**运维人员需在代表性工作负载上评估这些配置，选择满足延迟要求且吞吐量最大的方案**。然而：

- 评估单个配置需约 2-4 小时的性能分析（以收集不同请求负载下具有统计显著性的尾部延迟数据）[4]。
- 若使用 64-GPU 集群（当前云服务定价为每 GPU 小时 2.50-7 美元，以 H100 GPU 为例），仅评估 100 个配置就需消耗 12,800-25,600 GPU 小时，成本高达 32,000-179,200 美元。

:mdnice-bold-italic[这些因素使得广泛探索配置空间在经济和实践上均不可行，迫使从业者只能依赖经验法则（rule-of-thumb heuristics）进行配置选择。]

### 2.2 离散事件模拟器（Discrete-Event Simulators）

为降低配置评估成本，研究人员开发了离散事件模拟器（DES）[4,11–13,20,29]。这类工具**无需昂贵硬件**，即可低成本、快速地对服务系统性能进行建模。其核心原理是：

::: block-1
- 在简化的仿真框架中，人工重新实现服务系统的控制逻辑，包括调度器、内存分配器、请求路由器等；
- 通过性能模型预测批处理任务的 GPU 执行时间；
- 模拟器将自身时钟推进该预测时长，再处理下一个事件。
:::

由于无需实际执行 GPU 操作，模拟器的运行速度比真实系统快一个数量级，且无需物理 GPU。

### 2.3 模拟器的局限性

#### 语义鸿沟（Semantic Gap）

人工重新实现服务逻辑的过程，必然导致模拟器与真实系统的行为存在细微差异。早期系统的建模难度较低（例如，在 Vidur 中建模 vLLM 最初的调度器仅需约 150 行代码），但如今的生产级控制平面代码已超过数万行[26,28]，且包含分层前缀缓存、分离执行等复杂逻辑。**要准确捕捉这些功能的性能特性，需投入极大的工程 effort**；而模拟器逻辑**与真实系统的任何偏差，都会导致性能预测出现严重误差。**

#### 框架特异性（Framework Specificity）

**模拟器的通用性较差**，因为不同服务框架对同一功能的实现方式可能存在根本差异。例如，:mdnice-bold-italic[尽管 vLLM 和 SGLang 在高层均采用 Sarathi-Serve[5]中描述的批处理策略，但具体实现存在关键区别]：

- vLLM 同时支持分块预填充（Chunked Prefill）和混合批处理（将预填充请求和解码请求放入同一批处理），而 SGLang 默认不支持混合批处理，仅采用“预填充优先”策略。**这种差异会导致两者的延迟特性截然不同，而通用模拟器无法准确捕捉此类框架特异性**。
- 类似差异还存在于前缀缓存、分离执行等其他功能中：例如，vLLM 的分层缓存（基于 LMCache[3]）采用“写透策略”（即每个写入 GPU 缓存的元素，都会立即同步到 CPU、NVMe 等低层缓存），而 SGLang 则采用“选择性写透策略”（仅在首次缓存命中时异步复制数据到低层缓存）。

为准确建模不同框架，研究人员被迫为每个主流框架开发并维护专用模拟器：例如，Vidur[4]以 Sarathi-Serve[5]为建模对象，LLMServingSim2.0[11]以 vLLM 为建模对象。这种方式不仅:mdnice-bold-italic[灵活性低，还大幅增加了模拟器的开发成本。]

#### 维护负担（Maintenance Burden）

**LLM 服务框架的快速迭代，进一步加剧了离散事件模拟器的工程负担**。仅 vLLM 在 2025 年上半年就收到了超过 2800 次代码提交，贡献者达数百人[28]——每次提交都可能打破模拟器的建模假设。

因此，Vidur、LLMServingSim 等模拟器在发布后不久就会落后于实际框架。尽管研究人员尝试填补这一差距（例如，Frontier[13]和 LLMServingSim2.0[11]为前代模拟器增加了前缀缓存、预填充-解码分离等现代功能），但**随着领域的持续发展，这些努力仍无法摆脱“维护滞后”的宿命。**

::: block-1
**核心结论**：现有的离散事件仿真方法面临持续的维护负担，:mdnice-bold-italic[亟需一种全新的运行时建模方法——无需人工重新实现服务引擎的逻辑。]
:::

## 三、时间加速仿真

> 为解决离散事件仿真的局限性，本文提出一种新的建模范式：**时间加速仿真（Time-Accelerated Emulation）**。该方法:mdnice-bold-italic[无需重新实现服务系统逻辑，而是直接执行未修改的 LLM 推理引擎代码，在保证高建模精度的同时，保留模拟器的“高速、低成本”优势]。本节将详细介绍实现该范式的核心组件。

### 3.1 透明设备虚拟化（Transparent Device Virtualization）

深度学习训练性能建模领域的最新研究 :mdnice-bold-italic[Maya[31]已证明“透明设备仿真”的可行性：通过`LD_PRELOAD`（Linux 系统环境变量，可让程序优先加载指定的共享库）拦截 CUDA API 调用，创建“虚拟设备”，无需物理 GPU 即可对工作负载的运行时进行建模]。Maya 的实现分为两步：

1. 让工作负载在虚拟设备上执行，生成该工作负载所有 CUDA API 调用的轨迹（trace）；
2. 模拟器重放该轨迹，预测每个 API 调用的执行时间，最终输出端到端的运行时估计。

将这种技术应用于 LLM 推理服务，有望直接执行未修改的服务系统代码——从根本上消除离散事件仿真的核心局限性，为现代 LLM 服务系统提供鲁棒、可维护的运行时建模方案。

### 3.2 在线服务中的时间语义（Temporal Semantics in Online Serving）

然而，与“离线”的训练工作负载不同，LLM 推理是“在线”过程——请求到达的时间会直接影响控制流如批处理组合、调度决策。若忽略 GPU 执行时间，会破坏系统的时间语义，导致批处理决策错误。

::: block-1
**示例**：假设存在两个请求 A 和 B，两者的预填充阶段均需 500 毫秒。请求 A 在`t=0`时刻到达，请求 B 在`t=200`毫秒时刻到达。
:::

在真实系统中：

- 调度器在`t=0`开始处理请求 A（GPU 开始执行 A 的预填充）；
- `t=200`毫秒时，B 到达，但 GPU 仍在处理 A，因此 B 被加入队列；
- A 的预填充完成后，调度器才会调度 B（可能将 B 的预填充与 A 的解码阶段合并为一个批处理）。

但如果采用 Maya 的“离线仿真”思路（仅追踪 GPU 调用而不考虑真实时间），请求 A 会在`t≈0`时刻“瞬时完成”。当 B 在`t=200`毫秒到达时，系统会认为 GPU 空闲且队列为空，从而直接调度 B——此时，请求 A 和 B 的时间重叠关系被破坏，批处理模式完全改变，建模结果与真实系统严重偏离。

#### 一种初步方案（Strawman Approach）

:mdnice-bold-italic[为保留时间语义，仿真器需让控制平面“感知时间流逝”。一种简单且正确的思路是：通过“睡眠（sleep）”模拟 GPU 延迟] ——若预测某个批处理的执行时间为 500 毫秒，则让 CPU 线程睡眠 500 毫秒。这种方式可保证建模精度：

- 在 A 的预填充“睡眠”500 毫秒期间，壁钟时间（wall-clock time，即真实物理时间）正常推进；
- B 在`t=200`毫秒到达时，worker 处于“睡眠中”（模拟 GPU 忙碌），因此 B 会被正确加入队列；
- 系统状态动态和资源竞争关系与真实硬件完全一致。

**然而，“基于睡眠的仿真”虽然正确，速度却极慢** ——评估一个 2 小时的轨迹需要 2 小时的真实时间。对于需要数千次评估的配置搜索任务，:mdnice-bold-italic[这种“实时约束”使其完全不可行。我们将这种初步方案称为“基于睡眠的仿真（Sleep-Based Emulation）”。]

### 3.3 核心洞察：时间加速（Key Insight: Time Acceleration）

> “基于睡眠的仿真”的壁钟时间成本与真实 GPU 执行完全相同，但:mdnice-bold-italic[深入分析 LLM 推理引擎的设计可发现一个关键机会：这类引擎的核心优化目标是“最大化 GPU 利用率，同时最小化 CPU 开销”。]

![文章插图](/articles/2026-01-12-gpu-5-17-revati-vllm-afcd0e26/images/06.webp)

::: image-caption
图 3：CPU 与 GPU 执行时间对比。GPU 执行时间主导服务延迟，而 CPU 开销（5-10%）较小，这为通过时间加速实现数量级速度提升提供了可能
:::

图 3 量化了这一特性：我们以离线模式（所有请求在初始时刻全部可用）处理 100 个请求，分别测量“正常 GPU 执行”和“GPU 跳过模式（通过仿真绕过所有 GPU 执行）”的时间——其中，CPU 时间代表控制平面的关键路径开销，GPU 时间代表实际核函数执行时间。:mdnice-bold-italic[结果显示，在 vLLM 和 SGLang 中，GPU 计算占总执行时间的 90-95%，而 CPU 开销始终较小（与模型大小或服务框架无关）。这意味着，系统的绝大部分壁钟时间都在“等待 GPU 计算完成”。]

更关键的是，控制平面的逻辑**不依赖于 GPU 计算的具体结果**：

- 调度器仅基于请求、批处理、内存块等逻辑抽象工作
- 而 GPU worker 仅执行物理计算，不参与控制流决策

> 这两个特性共同为“时间加速”提供了路径：无需在 GPU 等待期间睡眠，而是直接“跳跃”虚拟时间。

::: block-1
注：在真实部署中，请求的终止由“结束符（EOS token）”的生成分辨，但在性能建模中，通常通过设置固定的 token 生成数量（结合特定采样参数）来控制每个请求的执行时长。
:::

#### 因果关系挑战（Challenge with Causality）

在服务系统中，多个独立进程（批处理调度器、worker、请求负载生成器）并发运行，每个进程对“下一个事件”的时间感知不同。例如：

- 一个 worker 可能准备跳跃 50 毫秒（模拟批处理执行）；
- 负载生成器则计划在 10 毫秒后注入一个新请求。

**若 worker 单方面将本地时钟推进 50 毫秒，会“跳过”新请求的到达事件** ——在虚拟时间中，请求会在批处理完成后到达，而真实场景中请求会在批处理执行期间到达，这:mdnice-bold-italic[可能改变调度器对下一个批处理的决策。这种“因果关系破坏”会导致队列行为错误和延迟测量无效。]

#### 文献中的时间加速（Time Acceleration in the Literature）

> 这是一个经典问题，在分布式事件仿真领域已被广泛研究：

- **乐观方法（Optimistic Approaches）** [17,18]：允许:mdnice-bold-italic[不同进程独立推进时钟，检测到因果冲突时回滚到上一个一致检查点。但这种方法无法应用于仿真] （Emulation）——因为服务系统的执行具有不可逆副作用（如发送网络消息、修改数据结构），无法回滚。
- **保守方法（Conservative Approaches）** [7–9]：:mdnice-bold-italic[更适合仿真场景，要求所有进程就“安全前瞻时间（lookahead time）”达成一致]，确保在该时间内推进虚拟时间不会破坏因果关系。

尽管文献中已有多种针对离散事件仿真的保守型时间加速实现[7–9]，但它们无法直接应用于“仿真（Emulation）”：

::: block-1
- 在事件驱动模拟器中，事件循环可直接控制事件的因果关系；
- 而在仿真系统中，所有分布式组件均在壁钟时间内异步运行，需在不引入额外开销的前提下透明加速时间。
:::

例如，Chandy-Misra-Bryant 算法[7,8]要求每个仿真 worker 向其他节点发送“空消息（null message）”，告知自身的下一个前瞻时间——该算法需要控制事件调度，无法直接用于服务系统的仿真。

因此，本文需提出一种新的时间加速方法，在仿真系统中保证因果关系不被破坏。

## 四、REVATI：系统设计

> REVATI 通过“时间跳跃仿真（Time-Warp Emulation）”，填补了并行分布式事件驱动仿真与仿真（Emulation）方法之间的空白。:mdnice-bold-italic[要实现这一范式，需解决分布式服务系统的异步特性与精准建模所需的严格因果关系之间的矛盾。]

本节剩余部分将详细介绍 REVATI 的设计，以及其如何应对虚拟时间相关的挑战。

### 4.1 概述

#### 4.1.1 进程模型（Process Model）

> 对 LLM 服务系统进行性能评估，主要涉及两个核心组件：

- 一是“基准测试运行器（benchmark runner）”，负责提交请求；
- 二是“LLM 推理引擎（LLM inference engine）”，负责处理这些请求（见图 4）。

![文章插图](/articles/2026-01-12-gpu-5-17-revati-vllm-afcd0e26/images/07.webp)

::: image-caption
图 4：跨进程协调虚拟时间。基准测试运行器和推理引擎作为独立进程运行，每个进程都包含请求时间跳跃的参与者（蓝色）和接收时间更新的观察者（粉色）。时间管理器协调跳跃请求并广播一致的偏移量
:::

在 REVATI 的执行模型中，这两个组件对应两种“时间角色”：

- :mdnice-bold-italic[主动体（Actors）：具有确定性计划，知道自身未来操作的完成时间]。例如，基准测试运行器的请求分发器明确知道何时分发每个新请求（如在`t=100ms`、`t=250ms`）；推理引擎的 GPU worker 知道批处理任务的执行完成时间。这些进程主动推动虚拟时间向前推进。
- :mdnice-bold-italic[观察者（Observers）：纯响应式组件，仅在事件发生时做出反应]。例如，基准测试运行器的输出处理器、推理引擎的请求调度器都属于观察者。

注：在真实部署中，请求的终止由“结束符 token（EOS token，即表示文本生成结束的特殊标记）”的生成分辨；但在性能建模场景中，通常通过设置固定的 token 生成数量（结合特定采样参数）来控制每个请求的执行时长。

#### 4.1.2 系统架构（System Architecture）

REVATI 包含两个核心组件：

1. **时间管理器（Timekeeper）**：同步分布式组件间的虚拟时间，管理时间跳跃以加速执行；
2. **设备仿真层（Device Emulation Layer）**：透明拦截并建模 GPU 操作，无需物理 GPU 硬件。

当执行开始时，主动体（Actors）会向时间管理器提交并发的时间跳跃请求——例如，基准测试运行器请求跳跃到下一个请求的到达时间，GPU worker 请求跳跃过批处理的执行时长。时间管理器计算所有主动体请求的“最小目标时间”，将全局虚拟时间推进到该时间点，并广播这一更新。

- 对于目标时间已达成的主动体，会立即返回；
- 仍有未达成目标的主动体则保持阻塞状态，在后续的“屏障同步轮次”中重新提交请求。

观察者（Observers）无需参与这一协调过程，仅需异步查询虚拟时间以给事件打时间戳。

> 将这些组件与 REVATI 集成，需对系统中的所有主动体进行补丁修改，使其在特定时机执行时间跳跃：

- 基准测试运行器需在请求分发间隙执行时间跳跃；
- 推理引擎的 GPU worker 需在 GPU 批处理执行间隙执行时间跳跃。

::: block-1
总体而言，**适配 vLLM 和 SGLang 这两个框架仅需修改约 50 行代码**。设备仿真层通过`LD_PRELOAD`（Linux 系统的环境变量，可让程序优先加载指定共享库，实现 API 拦截）加载，以拦截所有与 GPU 核函数 无关的设备管理调用。
:::

### 4.2 时间管理器（Timekeeper）

> **时间管理器是一个服务，负责管理所有连接客户端的虚拟时间**。它对外提供`TIMEJUMP(∆t)`接口，允许客户端请求时间跳跃并接收时钟更新。我们将时间管理器的客户端分为“主动体（Actors）”和“观察者（Observers）”两类：

- 主动体：仿真的主动驱动者，处理具有可预测时长的操作，必须主动请求虚拟时间推进；
- 观察者：响应式组件，仅使用虚拟时间为事件打时间戳，不阻碍虚拟时间的推进。

这种分类设计能最小化协调开销——仅需主动体参与同步，同时只需修改极少代码即可将 REVATI 与服务框架集成。

为确保可扩展性，该架构将“请求路径”与“更新路径”分离：

- 请求路径（扇入，fan-in）：主动体通过可靠通道向时间管理器单独提交时间跳跃请求；
- 更新路径（扇出，fan-out）：时间管理器通过广播通道向所有客户端同步推送时钟更新。

这种:mdnice-bold-italic[非对称设计使时间管理器能以“每轮固定序列化成本”更新数百个分布式 worker]，避免在高频屏障同步时出现瓶颈。

![文章插图](/articles/2026-01-12-gpu-5-17-revati-vllm-afcd0e26/images/08.webp)

::: image-caption
图 5：基于屏障的时间同步。当主动体请求不同的跳跃时长时，时间管理器会将虚拟时间推进到“最小安全偏移量”。例如，主动体 1 在`t=0`时请求 100ms 的时间跳跃；在执行跳跃前，时间管理器会等待所有主动体发布其安全偏移量。当主动体 2 在`t=20`时请求 30ms 的时间跳跃，屏障同步完成，时间管理器将时间推进 30ms。此时主动体 1 仍剩余 50ms 的跳跃需求，因此会重新提交剩余时长的跳跃请求。最终，主动体 1 原本 100ms 的跳跃需求分两轮完成，总壁钟时间仅需 50ms
:::

#### 4.2.1 虚拟时间协议（Virtual Time Protocol）

在分布式进程间协调虚拟时间，需要一种“**不控制进程执行但能保留因果关系** ”的协议。本节将介绍 REVATI 的“基于屏障的协议”，并分析其正确性。

##### 设计约束（Design Constraints）

> 将虚拟时间适配到实时仿真中，需应对传统离散事件模拟器中不存在的三个约束：

1. **无法回滚（No rollback）**：像“时间跳跃（Time Warp）”[17,18]这类乐观式方法，会先推测性推进时间，检测到因果冲突时再回滚到一致检查点。但 REVATI 执行的是真实系统代码，存在不可逆副作用（如发送网络消息、修改数据结构），因此该方法不可行。
2. **无法控制事件调度（No event scheduling control）**：像“Chandy-Misra-Bryant”[8]这类保守式协议，假设模拟器能控制事件处理顺序。但 REVATI 中的进程在壁钟时间内异步运行，协议需在不控制执行的前提下协调时间推进。
3. **优雅降级（Graceful degradation）**：当协调失败时（如出现滞后进程、网络延迟），系统需保持正确性——可牺牲速度，但绝不能产生无效结果。

##### 虚拟时间表示（Virtual Time Representation）

REVATI 将全局虚拟时间表示为“相对于壁钟时间的偏移量”，公式如下：

$$
t_{virtual} = t_{wall} + offset \quad (1)
$$

初始状态下，`offset = 0`，因此虚拟时间等于壁钟时间（即真实物理时间）。当主动体请求时间跳跃时，时间管理器会增大偏移量，使虚拟时间推进速度超过壁钟时间。:mdnice-bold-italic[这种表示方式让观察者无需参与协调即可查询虚拟时间——只需读取当前偏移量并加上壁钟时间。]

##### 基于屏障的协调（Barrier-Based Coordination）

当主动体调用`TIMEJUMP(∆t)`时，会先计算自身的“目标虚拟时间”，再将请求发送给时间管理器。时间管理器收集所有主动体的请求后，将虚拟时间推进到“所有请求目标时间中的最小值”。**这一“最小推进规则”能确保没有主动体跳过自身预期的时间点，从而保留因果关系**。例如：若 worker A 处理批处理需 50ms，worker B 需 10ms，若两者独立推进时间会破坏因果关系（虚拟时间为 1000ms 的主动体可能观察到虚拟时间仍为 500ms 的主动体的事件）。算法 2 展示了服务端的协议逻辑。

![文章插图](/articles/2026-01-12-gpu-5-17-revati-vllm-afcd0e26/images/09.webp)

::: image-caption
算法 2 | Server: ProcessTimeJumpRequests ()。服务端初始化请求队列与时间偏移，循环接收 Actor 请求，集齐所有请求后取最小目标时间，更新偏移量，广播时钟更新给客户端，重置队列，保障分布式环境下虚拟时间同步且不违因果
:::

单次`TIMEJUMP`调用可能跨越多个屏障同步轮次。例如：两个 worker 中，$W_A$ 调用`TIMEJUMP(50)`，$W_B$ 调用`TIMEJUMP(10)`。时间管理器根据 $W_B$ 的目标时间计算出最小目标时间 $t_{min}$，将虚拟时间推进 10ms，此时 $W_B$ 的调用返回；$W_A$ 因虚拟时间未达到自身目标，会留在循环中，在下一轮屏障同步时重新提交请求。

![文章插图](/articles/2026-01-12-gpu-5-17-revati-vllm-afcd0e26/images/10.webp)

::: image-caption
算法 1 | Client: TimeJump (∆t)。客户端先计算目标虚拟时间（当前虚拟时间加∆t），再循环发送该目标请求给 Timekeeper，等待确认后计算剩余时间，超时则等待时钟更新，直至虚拟时间达到目标，实现客户端虚拟时间推进
:::

算法 1 展示了客户端的协议逻辑：客户端先计算一次目标时间（第 1 行），然后循环等待，直到虚拟时间达到该目标；每轮循环中，客户端将目标时间发送给时间管理器、接收确认，并等待时钟更新广播（超时时间等于剩余所需虚拟时间）。

##### 优雅降级（Graceful Degradation）

算法 1 中的超时机制确保了故障场景下的正确性。若广播未到达（如网络问题或主动体停滞），客户端会在“剩余虚拟时间（$t_{remaining}$）”对应的壁钟时间后超时。此时，壁钟时间已推进 $t_{remaining}$，根据公式 $t_{virtual} = t_{wall} + offset$，虚拟时间也会相应推进，循环条件满足，`TIMEJUMP`返回。

这种情况下，操作虽能正确完成，但速度会退化为壁钟时间速度。:mdnice-bold-italic[最坏情况下，REVATI 会降级为“基于睡眠的仿真（Sleep-Based Emulation）”——速度慢但结果始终正确。这一特性保证 REVATI 不会产生无效结果或死锁，最多仅损失加速效果。]

##### 处理消息抖动（Handling Message Jitter）

实时仿真需考虑网络延迟和 CPU 调度抖动（指进程因 CPU 资源竞争导致的执行时间波动）。例如：

- 推理服务器在壁钟时间 $t_w=100ms$、虚拟时间 $t_v=3400ms$ 时生成一个 token；
- 基准测试运行器立即接收并记录 $t_v=3400ms$；
- 服务器处理下一个批处理（预测时长 20ms），在 $t_w=101ms$ 时将虚拟时间更新为 $t_v=3420ms$；
- 因网络延迟，运行器在 $t_w=102.5ms$ 时才读取下一个 token；
- 期间服务器已完成另一个批处理，在 $t_w=102ms$ 时将虚拟时间更新为 $t_v=3450ms$；
- 运行器在 $t_w=102.5ms$ 查询虚拟时间时，会得到 3450ms 而非 3420ms，导致延迟测量不准确。

若在消息生成时就附加虚拟时间戳，可消除这种歧义，但这需要修改服务引擎的大量代码（约数百行）。:mdnice-bold-italic[为简化集成，REVATI 还提供“有界抖动模型（bounded-jitter model）”：假设消息在传输后 J 时间内到达，通过在连续时间跳跃间插入 J 时长的“冷却期”，避免观察者读取到过期的虚拟时间。]

::: block-1
实验表明，在大多数实际场景中，$J≈500\mu s$（微秒）即可满足需求。
:::

### 4.3 设备仿真层（Device Emulation Layer）

服务框架通常与 CUDA 和 NCCL 深度集成。若修改所有 API 调用点，需对每个框架进行侵入式修改，违背 REVATI 的“透明性”目标。:mdnice-bold-italic[设备仿真层借鉴了 Maya[31]的“透明设备虚拟化”技术，针对推理工作负载拦截并仿真 CUDA API 调用——未修改的框架代码会误以为自己在访问目标硬件，从而正常执行。]

这种设计不仅保持了透明性，还支持“超出现有资源规模的评估”：例如，研究者若需在 128-GPU H200 集群上评估，但无实际硬件，只需配置 REVATI 仿真该硬件即可。

> 然而，与 Maya 的“离线仿真”不同，REVATI 的“实时仿真”面临以下独特挑战：

#### 4.3.1 保留分布式依赖（Preserving Distributed Dependencies）

在分布式服务中（如流水线并行、张量并行），NCCL 集体通信操作（如 ncclSend）会强制因果依赖——第 $i+1$ 阶段必须在第 $i$ 阶段完成 ncclSend 后才能继续。

由于无需实际 GPU 执行，REVATI 需将“仿真的第 $i+1$ 阶段”阻塞，直到“仿真的第 $i$ 阶段”完成对应的发送操作。具体而言，:mdnice-bold-italic[REVATI 将 NCCL 集体通信操作转换为“参与 worker 间的屏障同步点”，在不传输数据的情况下保留时间顺序。]

#### 4.3.2 分离状态内存模型（Split-State Memory Model）

> 与训练工作负载不同，服务系统常使用 GPU 通道进行控制平面通信。

例如，SGLang 通过 NCCL 广播批处理组合信息。若采用纯“黑盒仿真”，会导致 CPU 无法读取缓冲区中的有效数据，从而破坏通信。为解决这一问题，REVATI 将内存分配分为两类：

1. **元数据缓冲区（Metadata Buffers）**：小容量分配（默认小于 4MB），可能用于控制决策，由真实主机内存支持，其操作会被忠实地执行；
2. **计算缓冲区（Compute Buffers）**：大容量分配（如 KV 缓存、模型权重），仅分配虚拟指针（无物理内存 backing），其操作会被视为“空操作（no-ops）”，执行时长由运行时预测器估算。

::: block-1
**该模型的核心假设是“计算缓冲区不会被 CPU 读取”。** 为确保这一不变性，若应用尝试从虚拟计算缓冲区读取数据，REVATI 会抛出致命异常（而非返回无效数据）。因此，若仿真运行成功，可保证控制平面从未使用过“虚假数据”。
:::

### 4.4 运行时预测（Runtime Prediction）

REVATI 提供“可插拔接口”，支持“解析型（analytical）”和“基于性能分析的（profiling-based）”两种运行时预测器。

默认情况下，REVATI 扩展了 Vidur[4]的“算子级模型”，新增对“混合专家（Mixture-of-Experts，MoE）路由”、“融合注意力变体”和“优化的 all-reduce 集体通信”的支持。预测器接收“批处理组成信息（预填充请求数、解码请求数、序列长度）”和“目标硬件规格”，返回估算的执行时长。

## 五、实现

> 时间管理器的服务端和客户端库约 800 行 C++代码，并提供 Python 绑定（用于框架集成）；设备仿真层新增约 6000 行 C++代码；:mdnice-bold-italic[适配 vLLM 和 SGLang 这两个 LLM 服务框架的补丁代码各少于 50 行。]

消息层使用 ZeroMQ（一种低延迟消息队列库）实现通信。时间管理器服务端采用多线程架构：

- 专用 I/O 线程：处理序列化和 socket 操作；
- 后台线程：管理屏障状态和时间跳跃逻辑。

这种线程分离设计确保高频请求不会阻塞屏障同步的处理。

- **效率（Efficiency）**：与初步方案（指 3.2 节中的“基于睡眠的仿真”）相比，:mdnice-bold-italic[REVATI 能否有效加速评估过程？]

## 七、相关工作

### 7.1 分布式仿真中的虚拟时间

- Jefferson 提出的“时间跳跃（Time Warp）”[17,18]开创了“乐观式虚拟时间”技术：进程推测性推进时间，检测到因果冲突时回滚到上一个一致检查点。
- Chandy-Misra[7,8]提出“保守式协议”：进程通过交换“前瞻时间（lookahead time）”信息，确保安全推进时间。

这两种方法均假设模拟器能控制事件调度，但 REVATI 面临不同约束——进程在壁钟时间内异步运行，且存在无法回滚的真实副作用。REVATI 的“基于屏障的协议”将保守式原理适配到这一场景：通过“最小目标时间推进”保留因果关系，同时通过超时机制确保“优雅降级到实时执行”。

### 7.2 网络仿真中的时间拉伸

“时间拉伸（Time Dilation）”[14,15,27]通过减慢虚拟时间，让物理硬件“显得更快”——例如，1Gbps 网卡可通过将虚拟时间减慢 10 倍，仿真 10Gbps 网卡的性能。DieCast[14]、ModelNet[27]、Mininet[16]等工具均采用该技术进行大规模网络测试。

REVATI 则颠覆了这一逻辑：**并非通过减慢时间来“放大硬件能力”，而是通过加速时间来“跳过 GPU 计算”**。两者的核心共识是:mdnice-bold-italic[“应用可在与壁钟时间解耦的虚拟时间中运行”，但实现机制差异显著]：

- 网络仿真器通过拦截系统调用并缩放延迟来实现；
- REVATI 则通过“显式屏障同步”协调分布式进程，确保时间跳跃时的因果关系。

## 八、讨论

### 8.1 迈向完全透明的仿真

> REVATI 适配每个框架需修改约 50 行代码以调用时间跳跃，但这引发一个自然问题：:mdnice-bold-italic[能否像 Maya 对训练工作负载那样，通过“内核级拦截（kernel-level interception，通过操作系统内核层面捕获 API 调用，无需修改应用代码）”彻底消除这一修改需求？] 目前面临两个挑战：

1. 现代推理系统对某些复杂操作（如 flash attention、MoE 路由）采用框架特定的实现——仅通过核函数 API 签名预测其运行时，需对框架内部进行复杂逆向工程，这会引入 REVATI 旨在避免的维护负担；
2. 近期已有研究尝试“直接通过 GPU 核函数的源代码和输入参数估算运行时”[19,21]——这一方向为未来实现“完全透明仿真”提供了可能。

### 8.2 光速执行

> 系统社区一直致力于“**最小化服务系统的 CPU 开销** ”，以最大化 GPU 利用率——随着 GPU 世代迭代，速度和能力不断提升，这一目标愈发重要。

- 近期已有多项研究尝试用 C++和 Rust[1,2]实现高效执行（替代传统 Python 实现）；
- 现有框架如 SGLang 也开始将核心模块（如前缀缓存树）迁移到 C++以提升性能[26]。

这一趋势引发一个问题：**REVATI 的最大加速比能达到多少？随着仿真速度提升，系统可能面临新的挑战和瓶颈** ——例如，“分词/解分词（tokenization/detokenization，将文本转换为模型可处理的 token 及反向过程）”步骤可能带来不可忽视的开销。我们计划在未来工作中探索这些挑战。

## 九、结论

> LLM 服务系统的快速迭代，已使传统离散事件仿真变得难以维系——模拟器模型与前沿服务系统之间的差距，人工填补的成本过高。
>
> REVATI 通过“在原始服务框架上直接进行低成本、高精度的运行时建模”，彻底消除了这一差距。

本文证明：“透明设备仿真层”与“基于屏障的虚拟时间协议”相结合，既能实现高精度的运行时建模（误差<5%），又能同时达到“比物理执行快一个数量级”的加速效果。
