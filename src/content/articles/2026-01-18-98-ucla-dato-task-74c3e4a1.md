## 一、内存墙危机，数据流加速器的机遇与挑战

> 随着大型语言模型参数规模呈指数级增长，计算模式发生了根本性转变。

过去以计算为中心的架构设计，现在越来越多地被**内存受限的工作负载** 所主导。许多核心计算内核在数据移动、布局转换和同步上停滞，而不是在计算本身。

数据流加速器应运而生，它们通过将计算单元与暂存器和轻量级互连结构耦合，实现了持续的数据流水线处理。:mdnice-bold-italic[即使是通用 GPU 也采用了类似原则：最近的 NVIDIA Hopper 和 Blackwell GPU 引入了专用的张量内存加速器（TMA）来异步流式传输张量。]

::: block-1
这些设计通过通道和 FIFO 将数据移动提升为“一等公民”，能够将内存受限的工作负载转变为高吞吐量的流水线，保持计算单元饱和，同时大幅减少片外通信。
:::

然而，尽管硬件架构取得了这些进展，当前的编程模型仍难以完全释放数据流加速器的潜力，**困在性能与生产力的长期权衡之中**。

低级别通信控制虽然可以提高性能，但却严重阻碍了生产力。

例如，IRON 作为 AMD NPU 的编程前端，向用户暴露了所有 FIFO 和 DMA 细节——抽象级别类似于 GPU 的 CUDA。即使是一个简单的矩阵乘法内核也可能需要数百行代码。

基于块的编程语言（如 Triton）擅长表达每个块的计算，但对块间或内核间通信的控制很少。像 ARIES 这样的努力将类 Triton 语法适配到数据流加速器，但仍然强制执行固定的通信模式，限制开发者进行精细控制。

> **我们主张，数据通信必须成为数据流加速器编程模型中的一等抽象。**

为此，我们提出了 Dato——一个基于任务的编程模型，将数据通信和分片都提升为一等类型。在 Dato 中，程序员定义通过流类型连接的任务，并使用布局类型传入分片数据。

::: block-1
这些:mdnice-bold-italic[任务在空间结构上进行虚拟映射，编译器自动将虚拟映射转换为物理映射]。通过**在编程模型级别共同设计计算和通信**，Dato 明确地暴露任务间流式传输，减少片外通信，并减轻编译器开发负担。
:::

## 二、数据流加速器图景，从专用硬件到通用编程挑战

> 要理解 Dato 的价值，我们首先需要了解现代数据流加速器的架构特点及其编程挑战。

脉动阵列架构已成为现代深度学习加速的基石，因为它们能够为密集线性代数工作负载维持高吞吐量。

- 像 Google 的 TPU、AWS Trainium 和 Inferentia 这样的架构使用大型处理元素网格来流式传输矩阵乘法，在本地重用操作数，并将部分结果传递给邻居以减少片外内存通信。

## 三、Dato 编程模型，将数据通信提升为一等公民

Dato 的设计哲学是**让数据通信成为编程模型中的一等抽象**。为了实现这一目标，Dato 采用了基于任务的编程范式，其中计算被组织为通过显式流类型连接的任务图。

### 3.1 设计概述

> 为了最大化可用性和生产力，Dato 被设计为 Python 嵌入的加速器编程语言。**它建立在开源加速器编程框架 Allo 之上，并重用了 MLIR 基础设施**，同时:mdnice-bold-italic[引入了针对数据流加速器编程定制的显著新功能。]。

**构造 IR 后，Dato 生成捕获程序数据流结构的虚拟计算图**。由于数据流加速器通常具有有限数量的处理引擎，而用户程序可能表达更大的计算，Dato 执行虚拟到物理的映射步骤。这一步骤弥合了逻辑并行性和有限硬件资源之间的差距，实现在空间结构上的高效任务放置和调度。

**物理映射之后，编译器应用内核注入和布局优化通道来优化内存放置和计算操作**。最终优化的 MLIR 模块随后被 lower 为特定于后端的代码。

- 针对 AMD NPU，我们利用 MLIR-AIE 作为后端；
- 对于 FPGA，我们为高级综合生成 C++代码，并使用 AMD Vitis 进行综合。

## 四、流类型，硬件 FIFO 的直接建模

> 我们在前端暴露了一等流类型，以直接建模片上通信，消除数组到流的转换。流处理中的先前工作通常将流抽象为无界的高级语义结构，或在多生产者和多消费者设置中，与硬件容量约束解耦。:mdnice-bold-italic[现有的面向硬件的框架尝试形式化流，但通过功能或时空类型实现，依赖于运行时握手或调度对齐，而没有静态保证。]

相比之下，我们的流类型嵌入在命令式 Python 前端中，并忠实建模硬件 FIFO 的语义，并推广到标量 FIFO 之外。

::: block-1
流本质上是一个先进先出的结构，定义了两个任务之间的点对点连接。该类型定义为 `Stream[T, N, P]`，其中 `T` 是元素类型，`N` 指定以元素为单位的逻辑容量，`P` 定义每次传输捆绑的元素数量；默认情况下没有打包。两个操作 `.put()` 和 `.get()` 与此类型关联，并可用于启用任务间的通信，如下图 2c 的 L16 和 L21 所示。

![文章插图](/articles/2026-01-18-98-ucla-dato-task-74c3e4a1/images/07.webp)

::: image-caption
图 2(c) | Dato 程序示例。示例中 Dato 将流作为一等类型，通过 @task 定义任务并指定虚拟映射，利用布局类型自动处理数据分片，无需手动编写多 PE 函数，解决了 Allo 的语义间接性与重复编码问题，大幅简化数据流编程并提升代码可维护性
:::
:::

![文章插图](/articles/2026-01-18-98-ucla-dato-task-74c3e4a1/images/08.webp)

::: image-caption
图4 | 流类型的类型规则。Γ是普通的类型上下文，而Δ是一个多重集，表示跟踪必须被恰好使用一次的资源的线性上下文。⊎是多重集并集。𝑁是流的深度。
:::

图 4 呈现了流的类型规则，它精确地反映了硬件 FIFO 语义。每个元素占据头（出队）和尾（入队）之间的一个槽位，我们使用线性能力令牌 Free(S)和 Used(S)跟踪这些槽位：

- 仅当 Free(S)令牌可用时，`.put()`才是良类型的，将其转换为 Used(S)（尾前进）；
- 对称地，`.get()`仅当存在 Used(S)时才是良类型的，它立即将其转回 Free(S)，同时将有效负载作为线性就绪未来返回，这是一个无需阻塞即可用但需要被恰好使用一次的值。

在`.get()`时释放槽位一旦消费者接受项目就缓解了反压，因此生产者可以继续流式传输，即使消费者推迟使用。我们有意将数据移动与实际计算分离，并引入内部`.await()`操作来解包未来，即要使用的实际值。由于未来是就绪且线性的，编译器可以将唯一的`.await()`放置在延迟隐藏点，而不冒重复或死锁的风险。

循环令牌强制执行一个简单的不变量：每个`.put()`将 Free(S)减一并将 Used(S)加一，每个`.get()`则相反，因此溢出和下溢在构造上变得不可类型化。`.await()`是 FIFO 中性的，仅解包一个已经出队的元素，同时保持安全性和吞吐量。

为了类型检查使用流的程序，Dato 使用 `N` 个令牌 Free(S)和零个 Used(S)的多重集初始化每个 `Stream[T, N]`。在每个程序点，我们维护将流映射到其当前令牌多重集的抽象状态。类型检查通过控制流图（CFG）上的前向抽象解释执行。如果在退出每个区域时所有未来都被消费且没有令牌泄漏，则程序是良类型的。

![文章插图](/articles/2026-01-18-98-ucla-dato-task-74c3e4a1/images/09.webp)

::: image-caption
图 5 | 未通过类型检查的数据流程序示例。示例包含两类错误：一是.put () 与.get () 操作不一致（如循环内 put 次数超流容量），二是死锁（如两任务相互等待对方流数据）。Dato 的类型系统通过跟踪流的 Free/Used 令牌，在编译时拦截这类错误，保障数据流程序的正确性与安全性

### 6.2 映射原语

> 为了**将 VMG 中的每个节点映射到硬件上的实际物理 PE，我们引入了两个调度原语**`.bundle()`和`.chain()`，它们:mdnice-bold-italic[在保持程序语义的同时重塑图拓扑]。这些原语向用户公开，用于手动控制虚拟到物理映射，但它们也可以由 Dato 自动应用。

`.bundle()`原语将一组同构节点（即具有相同计算和 I/O 模式的节点）合并为单个多镜头节点。生成的节点被调度执行多次，每个原始任务一次，依次处理每个输入或输出。从概念上讲，`.bundle()`将显式的扇入/扇出转换为时分复用的连接或分割。这减少了物理节点和外部端口的数量，消除了中间缓冲区，并且在具有有限路由或端口可用性但具有足够计算能力在同一块上托管多个调用的硬件上尤其有效。

`.chain()`原语将两个连接的节点——通常是生产者-消费者对——融合为单个顺序节点。融合的节点保留所有外部边，并排序计算以尊重它们的数据依赖性。这通常移除了中间流及其关联的缓冲。通过将路径折叠到单个位置，`.chain()`提高了局部性并减少了路由压力。融合的节点仍然必须遵守平台的端口约束（例如，最多两个全局输入和输出，或兼容类型的共享端口）。

**映射原语仅当轻量级、架构感知的合法性条件满足时才应用**。这些条件受三个主要标准约束：

1. :mdnice-bold-italic[资源约束]，例如顶级 I/O 端口可用性、NPU 上每块的入口和出口限制，以及 FPGA 上的 BRAM 访问限制；
2. :mdnice-bold-italic[接口兼容性，要求节点具有匹配的元素类型、形状和生产者-消费者关系]，以确保外部行为等价；
3. :mdnice-bold-italic[依赖性健全性，仅允许那些独立或直接由生产者-消费者边连接的节点]，以避免由跨传递路径折叠可能引起的循环。

**对于 I/O 核算，只有全局端口受到约束**。并置节点内的本地通信被视为内部的，不计入全局端口预算——例如，NPU 上的块本地链接或 FPGA 中的片上布线。在这些规则下，每个并置步骤减少了同时活动节点的数量，同时遵守端口、路由和内存的平台约束，使算法在不同目标之间可移植。

## 七、优化技术，提升硬件效率的关键

在本节中，我们讨论数据流加速器必要的进一步优化。

### 7.1 内核注入

> 许多 NPU 为其 VLIW 核心提供手动调优的 C++向量内核，而 FPGA 提供预验证的 C++ HLS IP 块以供重用。

为了利用这些库函数，我们定义了一个具有显式契约的内核接口：

1. 可允许的形状和向量宽度
2. 所需的 I/O 布局（例如，分块或打包）
3. 成本/资源提示，如延迟和启动间隔——针对每个目标增加设备规格。

::: block-1
当计算图满足契约时，Dato 的降低通道选择适当的变体并合成一个包装器，将任务循环分块到内核的微分块，插入前奏/结尾布局适配器，并拼接流和 DMA 以重叠打包/解包与计算。
:::

**在 NPU 上，包装器强制操作数布局和向量宽度，以充分利用 VLIW 执行；在 FPGA 上，它发出 HLS 友好的循环，在内核调用周围具有显式流水线。**

### 7.2 细粒度布局优化

> 我们进一步引入了细粒度布局优化，它在单个 PE 内运行，因为高性能内核通常施加严格的输入/输出布局要求。

遵循 CuTe 和 Graphene，我们通过记录元组（偏移量、大小、步长）来显式表示张量布局。:mdnice-bold-italic[在注入的内核周围的朴素降低往往会留下小的重新格式化步骤链——分块、打包、转置、重新打包——这会增加带宽并给本地内存带来压力。]

::: block-1
为了解决这个问题，我们开发了两个互补的优化：规范化与折叠和 DMA 感知的提升。
:::

- **规范化与折叠：我们将布局变换建模为布局代数的元素**：受分块可除性约束的整数域上的仿射映射的组合。Dato 将每个 MLIR transform_layout 操作序列提升到此代数中，规范化组合（例如，合并相邻块，取消逆对），然后将其折叠为最小范式。具体来说，:mdnice-bold-italic[我们在 SSA 中维护布局元组，符号化地组合它们，并通过轻量级算术检查解除完整性侧条件]。结果消除了冗余的具体化，并将兼容的步骤融合为单个打包/解包循环或单个 DMA 描述符。:mdnice-bold-italic[与局部窥孔相比，代数规范化暴露了跨循环边界和生产者-消费者任务之间的全局取消机会。]
- **DMA 感知的提升：许多布局操作，如打包、交错、步长和固定模式排列，可以由 NPU DMA 引擎在 in-flight 中执行**。我们的通道跨流边界提升符合条件的布局工作，并将其折叠到 DMA 描述符中：打包成为跨步收集，转置成为 2D 步长交换。提升受到对步长范围、突发大小和存储体映射的合法性检查的保护，提高了有效带宽并释放了本地 SRAM。在 FPGA 后端，相同的变换降低为 HLS 友好的突发对齐循环。最后，调度器将这些 DMA 放置在生产者和消费者发起的时隙中，并依赖于多缓冲以在引擎执行变换时保持计算饱和。

## 八、实验结果，从理论到实践的验证

> 在本节中，我们首先讨论我们的实验设置并评估我们的编译流程。

### 8.1 实验设置

我们**在 NPU 和 FPGA 上评估 Dato，分别代表商业粗粒度和细粒度数据流加速器**。:mdnice-bold-italic[NPU 具有针对 VLIW 执行优化的固定功能 PE 阵列，而 FPGA 提供基于 LUT 的可重配置性，支持自定义数据流结构。]

对于 NPU 评估，我们与 IRON（基于 MLIR-AIE 的官方 AMD 流程）和 ARIES（最先进的 AIE 编译框架）进行比较。实验在具有 20 个计算块（4×5）的 AMD Ryzen AI NPU（XDNA1）上进行。

- 对于单内核基准测试，我们报告设备内核执行时间，不包括一次性主机-设备传输延迟，以更好地隔离硬件利用率——定义为实际计算吞吐量与理论峰值的比率。
- 对于多内核工作负载，我们测量端到端延迟，包括数据移动开销。

每个基准测试包括 20 次热身迭代，然后是 400 次定时运行，报告算术平均值。对于 FPGA 评估，我们以 AMD Alveo U280 板为目标，并与 Allo 进行比较。设计使用 Vitis 2023.2 合成，延迟取自 HLS 报告。

## 结论与未来展望

> 在本文中，我们介绍了 Dato，这是一个 Python 嵌入的、基于任务的编程模型，它**将数据通信和分片提升为一等类型，并将虚拟映射编译为数据流加速器上的高效物理部署**。:mdnice-bold-italic[Dato 通过其流类型和布局类型的创新设计，实现了硬件抽象与编程模型之间的紧密对齐]，为数据流加速器编程提供了一种既高效又易于使用的解决方案。

我们的实验结果表明:

- Dato 在 AMD Ryzen AI NPU 和 Alveo FPGA 上都**实现了卓越的性能**，同时显著**降低了编程复杂性**。
- 在 NPU 上，Dato 在 GEMM 内核上实现了高达 :mdnice-bold-italic[84%的硬件利用率]，在注意力内核上相对于最先进的商业框架实现了 **2.81 倍的加速**。
- 在 FPGA 上，Dato 生成的:mdnice-bold-italic[定制脉动阵列达到了理论峰值性能的 98%。]

**作为未来工作，我们将把编译器从本地决策扩展到全局图级优化**。我们还计划从任务规范自动生成高性能内核，减少对手写库的依赖。最后，我们将扩大目标范围，评估如 NVIDIA Hopper 及其具有 TMA 的后继者等加速器，以及其他可编程数据流结构。

::: block-1
随着人工智能计算的不断发展，数据流加速器将扮演越来越重要的角色。Dato 为这些复杂硬件的编程提供了全新的思路，有望成为下一代人工智能计算基础设施的关键组成部分。

:mdnice-bold-italic[Dato 的核心创新在于其类型系统的设计，将数据通信和数据分片都提升为一等类型，这使得编译器能够在早期阶段进行深入的分析和优化，而无需依赖复杂且容易出错的手动调度]。这种设计哲学不仅提高了性能，还显著降低了编程复杂性，为数据流加速器的广泛采用铺平了道路。
:::
