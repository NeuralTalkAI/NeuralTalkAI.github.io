## 关键问题

### 问题一：并行协作的效能边界：单点瓶颈揭示当前多智能体模式的根本局限

> 智能体并行协作的效率悖论：在项目中，当智能体尝试编译Linux内核时，所有智能体都被同一个bug阻塞，导致并行优势丧失。:mdnice-bold-italic[这是否意味着当前“多智能体团队”模式在本质上仍受限于一个“单点认知瓶颈”？如果核心问题只能被串行解决，那么大量智能体的主要价值是否仅在于加速那些可高度并行化的“琐碎任务”，而非解决真正的复杂系统挑战？]

在面对像“编译整个Linux内核”这样的单一、高度耦合的宏任务时，最初的并行架构确实会失效，智能体们会集体撞上同一个结构性障碍，陷入“伪并行”的窘境。

::: block-1
:mdnice-bold-italic[这暴露了当前模式下智能体协作的一个关键缺陷：缺乏高层级的、战略性的任务分解与协调能力。每个智能体都基于相同的提示和代码状态，独立判断“下一步最明显的任务”]，因此在遇到一个阻塞整个流程的系统性核心bug时，所有智能体的判断会趋同，导致资源冗余消耗。
:::

然而，作者也揭示了解决方案，这恰恰定义了当前多智能体价值的 “能力边界”：

| 场景类型 | 核心结论 | 具体说明 |
| --- | --- | --- |
| 可分解问题 | 多智能体并行价值巨大，效率近乎线性提升 | 项目前期可将问题拆分为大量独立子任务，如成千上万个编译器单元测试、编译众多独立小型开源库，智能体可同时修复数百个互不关联的bug |
| 耦合性单点瓶颈 | 需人类设计元策略激活并行潜力 | 纯粹放养式并行失效，需人类工程师设计高级测试与调试元框架，如引入GCC作为对照基准开展差分测试，将单一宏任务（编译内核）转化为大量可并行验证的微任务 |

::: block-1
当前的:mdnice-bold-italic[多智能体团队，其核心价值并非替代人类进行战略性架构思考，而是在人类或高级协调器（尚待开发）所设定的、经过巧妙分解的任务框架内，发挥其强大的、规模化的战术执行能力。它们擅长的是“饱和式修复”已知的、离散的问题点，而非自主发现并攻克一个未知的、系统性的深层障碍]。

这确实是当前AI在解决复杂系统工程时，“广度”与“深度”能力不匹配的体现。
:::

### 问题二：自主开发的可靠性困境：在“能运行”与“可信任”之间的巨大鸿沟

> “自主”开发的可靠性幻觉：作者承认，新功能和修复常会破坏现有功能，且最终编译器在效率、代码质量和功能完整性上均存在显著缺陷。:mdnice-bold-italic[当开发过程脱离人类的深度监督与架构把控，仅依赖AI自主迭代时，我们如何区分“表面上能运行”和“工程上可维护、可信任”？这是否揭示了当前AI在软件工程能力上存在“广度覆盖”与“深度正确性”之间的根本矛盾？]

对于功能正确性（Functional Correctness）与工程健壮性（Engineering Robustness）之间的差距。作者的编译器项目是这一矛盾的典型缩影。

| 问题维度 | 核心内容 |
| --- | --- |
| “表面能运行” vs. “深度正确性” | 1. 编译器可通过大量测试、编译可启动内核与运行《毁灭战士》，功能覆盖广度突出；2. 但存在16位x86代码生成超标、优化效率低、代码质量平庸、修复引发回归问题等短板。:mdnice-bold-italic[AI易找到可通过测试的脆弱路径，而非稳健高效的工程化路径。] |
| 缺乏一致性的架构心智模型 | :mdnice-bold-italic[人类工程师具备连贯演进的架构蓝图，多智能体【仅】基于有限上下文与瞬时任务决策，修改多为局部最优、全局次优。擅长打补丁，无长期架构视野，导致技术债积累、代码臃肿不一致，加剧广度与深度的矛盾]。 |
| 区分“能运行”与“可信任”的方案 | 完全自主AI迭代无法跨越鸿沟，需引入人类监督或高可靠自动化系统做深度评估：架构评审（结构清晰模块化）、性能基准测试（代码与编译器效率）、极端情况与安全性分析（边界条件与漏洞）、长期维护性评估（易理解、测试、扩展）。 |

作者构建严格CI流水线、针对常见错误模式设计测试，正是**试图通过自动化手段注入部分这些维度的评估**。但这仍是补救措施。

本文的实验卓越地证明了多智能体团队在探索解决方案空间、实现功能从0到1突破方面的巨大潜力。然而，它也清晰地警示我们，在实现从 “1到100”的工程化、产品化、可信任化的过程中，:mdnice-bold-italic[人类的架构设计、战略规划与深度评审角色不仅无法被替代，其重要性反而更加凸显。]

::: block-1
:mdnice-bold-italic[AI智能体是强大的“副驾驶员”和“执行军团”，但“领航员”和“机长”的责任，在可预见的未来，仍需由人类工程师担当。这并非技术的失败，而是对“人机协作”正确模式的深刻揭示]：

- 人类负责定义问题、设计框架、设定评估标准；
- AI负责在框架内进行海量的尝试、实施和调试。

两者的结合才能兼具广度与深度。
:::

## 一、实现 Claude 的长时间持续运行

> 现有的智能体运行框架如 Claude Code，需要操作人员在线并协同工作。如果你让模型解决一个复杂的长期问题，它可能会完成部分任务，但最终会停止工作，等待进一步输入——比如一个问题、状态更新或澄清请求。

为了让 Claude 能够持续自主地推进任务，我们构建了一个运行框架，**让 Claude 进入一个简单的循环，如果你了解 Ralph-loop，会觉得这个循环很熟悉。当 Claude 完成一项任务后，会立即开始下一项任务**。

*注：请在容器中运行此代码，不要在实际机器上运行。*

```
#!/bin/bashwhile true; do    COMMIT=$(git rev-parse --short=6 HEAD)    LOGFILE="agent_logs/agent_${COMMIT}.log"    claude --dangerously-skip-permissions \           -p "$(cat AGENT_PROMPT.md)" \           --model claude-opus-X-Y &> "$LOGFILE"done
```

在智能体提示词（agent prompt）中，我会告知 Claude 需要解决的问题，并要求它通过以下方式推进任务：将问题拆分为小任务、跟踪当前工作进度、确定下一步工作内容，并且持续推进直到任务完美完成。

*关于“完美完成”这一点，Claude 其实别无选择——因为这个循环会一直运行。不过有一次，我发现 Claude 意外执行了`pkill -9 bash`命令，结果把自己进程杀死，循环也随之终止。真是没想到！*

## 二、实现 Claude 的并行运行

> 让多个 Claude 实例并行运行，能够解决单智能体运行框架的两个短板：

1. 一次 Claude Code 会话只能处理一项任务。尤其是当项目范围扩大后，**并行调试多个问题的效率会高得多**。
2. 多个 Claude 智能体并行运行支持“分工专精”。:mdnice-bold-italic[可以让一部分智能体负责解决核心问题，同时让其他专精于特定领域的智能体例如维护文档、监控代码质量或处理专门的子任务。]

我设计的 Claude 并行运行方案比较基础：首先创建一个全新的空白 Git 仓库，然后为每个智能体启动一个 Docker 容器，将 Git 仓库挂载到容器的`/upstream`目录下。每个智能体都会将仓库克隆到本地的`/workspace`目录，完成任务后，再将本地修改推送到上游仓库（upstream）。

> 为了防止两个智能体同时处理同一个任务，该运行框架采用了一种简单的同步算法：

1. Claude 会通过在`current_tasks/`目录下创建文本文件的方式“锁定”任务。例如，一个智能体可能会锁定`current_tasks/parse_if_statement.txt`任务，另一个则锁定`current_tasks/codegen_function_definition.txt`任务。**如果两个智能体试图抢占同一个任务，Git 的同步机制会迫使后一个智能体选择其他任务。**
2. Claude 处理完任务后，会从上游仓库拉取最新代码、合并其他智能体的修改、推送自己的修改，最后解除任务锁定。**代码合并冲突很常见，但 Claude 能够自主解决这些冲突。**

这个“无限智能体生成循环”会在新的容器中启动一次新的 Claude Code 会话，如此循环往复。

需要说明的是，这只是一个早期的研究原型。我尚未实现任何其他智能体间的通信方式，也没有制定任何管理高层目标的流程，更没有使用“协调智能体”（orchestration agent）。

::: block-1
相反，我让每个 Claude 智能体自主决定行动方式。**在大多数情况下，Claude 会选择“下一个最明显需要解决的问题”。当遇到 bug 陷入停滞时，Claude 通常会维护一个实时文档，记录已尝试过的失败方案和剩余任务**。在该项目的 Git 仓库中，你可以查看提交历史，观察智能体对各类任务的锁定过程。
:::

## 三、与 Claude 智能体团队协作编程的经验教训

> 虽然运行框架让 Claude 进入了循环运行模式，但:mdnice-bold-italic[只有当 Claude 知道如何推进任务时，这个循环才有意义。我大部分精力都用于为 Claude 设计周边环境——包括测试用例、运行环境和反馈机制——确保它能在无需我干预的情况下明确工作方向]。

以下是我在协调多个 Claude 实例时发现的最有效的方法。

### 3.1 编写高质量的测试用例

Claude 会自主解决我交给它的任何问题。因此，**任务验证机制必须近乎完美，否则 Claude 可能会解决一个“错误的问题”**。

::: block-1
完善测试框架需要完成以下工作：寻找高质量的编译器测试套件、为开源软件包编写验证程序和构建脚本、观察 Claude 常犯的错误，并针对发现的这些错误模式设计新的测试用例。
:::

例如，在项目接近尾声时，Claude 每次实现新功能都会频繁破坏现有功能。为解决这个问题，我构建了一个持续集成（CI）流水线，并实施了更严格的约束机制，让 Claude 能够更好地测试自己的工作——确保新提交不会破坏已有代码。

### 3.2 站在 Claude 的角度思考问题

> 我必须不断提醒自己：:mdnice-bold-italic[这个测试框架是为 Claude 设计的，而不是为我自己。这意味着我需要重新审视自己对“测试应如何传递结果”的所有假设。]

例如，每个智能体都会被部署到一个全新的容器中，且没有任何上下文信息，因此它需要花费大量时间熟悉环境，尤其是在大型项目中。因此，:mdnice-bold-italic[在测试开始前，为了帮助 Claude 自主开展工作，我在提示词中加入了要求：让它维护详细的 README 文档和进度文件，并实时更新当前状态。]

同时，我也考虑到了语言模型固有的局限性——在设计框架时需要规避这些局限，具体包括：

| 问题名称 | 具体说明 |
| --- | --- |
| 上下文窗口污染（Context window pollution） | 测试框架需控制输出量，仅输出几行结果，重要信息存入便于自动处理的日志文件；错误需同行标记`ERROR`与原因，支持`grep`快速检索；预先计算汇总统计信息，避免Claude重复计算。 |
| 时间感知缺失（Time blindness） | **Claude无时间感知，易过度执行测试**；运行框架通过增量进度输出避免上下文污染，提供`--fast`选项随机运行1%或10%测试样本；单智能体样本固定、跨虚拟机样本随机，兼顾全文件覆盖与代码回退问题识别。 |

### 3.3 降低并行工作的难度

> 当存在多个独立的失败测试用例时，并行化会非常简单：每个智能体只需选择一个不同的失败测试用例来解决即可。当测试套件的通过率达到 99%后，每个智能体开始专注于让一个小型开源项目（如 SQlite、Redis、libjpeg、MQuickJS、Lua）能够通过编译。

但当智能体开始尝试编译 Linux 内核时，它们陷入了困境。与包含数百个独立测试用例的测试套件不同，:mdnice-bold-italic[编译 Linux 内核是一项庞大的单一任务——每个智能体都会遇到同一个 bug，修复该 bug 后，又会覆盖彼此的修改。此时，即使运行 16 个智能体也无济于事，因为它们都卡在同一个任务上。]

::: block-1
解决这个问题的方法是：将 GCC 编译器作为一个“在线已知正确的编译器基准”（online known-good compiler oracle），用于对比验证。
:::

我编写了一个新的测试框架，先用 GCC 随机编译内核的大部分文件，只留下少量文件用 Claude 开发的 C 编译器编译。

- 如果内核能够正常运行，说明问题不在 Claude 编译的那部分文件中；
- 如果内核运行失败，则可以进一步用 GCC 重新编译其中部分文件，缩小问题范围。

这种方法让每个智能体能够并行工作，修复不同文件中的不同 bug，最终使 Claude 的编译器能够编译所有内核文件。**即便如此，之后仍需使用“增量调试”（delta debugging）技术，找出那些单独编译时正常、一起编译时却失败的文件组合。**

### 3.4 多智能体分工

> 并行运行还支持“分工专精”。

- 语言模型编写的代码常常会重复实现已有功能，因此我专门安排了一个智能体，负责合并发现的重复代码；
- 让另一个智能体负责优化编译器本身的性能；
- 第三个智能体则专注于生成高效的编译后代码；
- 还有一个智能体的任务是从 Rust 开发者的视角审视项目设计，对项目结构进行调整以提升整体代码质量；
- 此外，还安排了一个智能体负责文档编写。

## 四、测试智能体团队能力的极限

> 该项目的设计初衷是作为一项“能力基准测试”。:mdnice-bold-italic[我希望通过测试，找出当前语言模型“刚好能够实现”的任务边界——这有助于我们为未来语言模型“稳定实现这些任务”做好准备。]

我将 C 语言编译器项目用作整个 Claude 4 系列模型的能力基准。与之前的项目一样，我首先明确了目标：**一款从零开始开发、支持优化功能、无依赖、兼容 GCC、能够编译 Linux 内核且支持多后端的编译器**。虽然我对设计的某些方面做了规定，例如，要求它具备静态单赋值中间表示（SSA IR），以支持多轮优化过程，但并未详细说明具体实现方式。

早期的 Opus 4 系列模型几乎无法生成可正常工作的编译器；Opus 4.5 是首个突破关键阈值的模型——它能生成通过大型测试套件的功能性编译器，但仍无法编译任何真正的大型项目。而我对 Opus 4.6 的目标，是再次测试语言模型能力的极限。

### 4.1 项目评估

> 在两周时间里，Opus 4.6 完成了近 2000 次 Claude Code 会话，处理了 20 亿个输入令牌（token），生成了 1.4 亿个输出令牌，总成本略低于 2 万美元。:mdnice-bold-italic[尽管与最贵的 Claude Max 套餐相比，这仍是一个成本极高的项目，但这个成本仅相当于我独自开发该编译器所需成本的一小部分——更不用说组建一个团队来开发了。]

该编译器是“干净室实现”（clean-room implementation，指在无外部代码参考的情况下独立开发）的成果，**开发过程中 Claude 全程没有访问互联网，仅依赖 Rust 标准库**。这款包含 10 万行代码的编译器：

- 能够在 x86、ARM 和 RISC-V 架构上编译出可引导的 Linux 6.9 内核
- 还能编译 QEMU、FFmpeg、SQlite、PostgreSQL、Redis 等软件
- 并且在包括 **GCC 折磨测试套件（GCC torture test suite，一种严苛的编译器正确性测试套件）在内的大多数编译器测试套件中，通过率达到 99%。**

此外，它还通过了开发者的终极验证测试：能够编译并运行《毁灭战士》（Doom）游戏。

![文章插图](/articles/2026-02-06-opus-2-16-claude-10-ca730942/images/03.png)

> 不过，这款编译器也存在一些局限性：

- 缺乏 16 位 x86 编译器——而这是 Linux 内核从实模式（real mode，CPU 启动时的初始工作模式，仅支持 16 位地址空间）引导所必需的。因此，在这一步它需要调用 GCC（x86_32 和 x86_64 架构的编译器是它自主实现的）。
- 没有自主实现汇编器和链接器——这是 Claude 最后开始自动化开发的部分，目前仍存在一些 bug。演示视频中使用的是 GCC 的汇编器和链接器。
- 虽然能成功编译许多项目，但并非所有项目都能编译——它尚未成为一款可直接替代现有主流编译器的产品。
- 生成的代码效率不高——即使启用所有优化选项，其生成代码的效率也低于禁用所有优化选项的 GCC。
- Rust 代码质量尚可，但远不及专业 Rust 开发者编写的代码质量。

**这款编译器的性能已接近 Opus 模型的能力极限**。我曾努力尝试修复上述部分局限，**但未能完全成功——新功能和 bug 修复常常会破坏现有功能。**

一个极具挑战性的例子是：Opus 无法实现引导 16 位实模式所需的 16 位 x86 代码生成器。尽管该编译器可以通过 66/67 操作码前缀（用于切换 CPU 的地址/操作数大小）输出正确的 16 位 x86 代码，但生成的编译结果大小超过 60KB，远超 Linux 内核规定的 32KB 代码限制。因此，:mdnice-bold-italic[Claude 在这里采取了“取巧”的方式——调用 GCC 完成这一步骤] （仅 x86 架构如此，对于 ARM 或 RISC-V 架构，Claude 的编译器可独立完成全部编译过程）。

该编译器的源代码已公开。你可以下载代码、阅读源码，并在自己熟悉的 C 语言项目上进行测试。**我一直认为，理解语言模型能力的最佳方式，是不断推动其能力极限，然后研究它在哪些地方会“失效”**。在未来几天里，我会继续让 Claude 推送新的代码修改，如果你想关注 Claude 为解决这些局限所做的持续尝试，可以保持跟踪。

## 五、未来展望

> 每一代语言模型都会带来新的协作方式。

- 早期的语言模型仅用于 IDE（集成开发环境）中的代码补全；
- 不久之后，模型能够根据函数的文档字符串（docstring）补全函数体；
- Claude Code 的推出让智能体成为主流工具，使开发者能够与 Claude 进行“结对编程”（pair-programming）。

但这些工具都基于一个共同假设：**用户定义任务，语言模型运行几秒或几分钟后返回结果，然后用户再提供后续指令。**

::: block-1
而智能体团队则展示了“自主实现完整复杂项目”的可能性。这让我们作为工具使用者，能够设定更宏大的目标。
:::

**目前，我们仍处于探索初期，完全自主的软件开发也伴随着切实的风险**。

- 当人类与 Claude 共同开发时，能够确保代码质量的一致性，并实时发现错误；
- :mdnice-bold-italic[但对于自主系统，人们很容易看到测试通过就认为任务已完成——而实际情况往往并非如此。]

我曾从事渗透测试工作，专门利用大公司产品中的漏洞——一想到开发者可能会部署自己从未亲自验证过的软件，我就感到担忧。

因此，尽管这个实验让我兴奋，但也让我感到不安。开发这款编译器是我近期最有趣的经历之一，但我完全没预料到，在 2026 年初，这项技术就已经接近实现这样的成果。语言模型本身以及我们与模型交互的运行框架，都在飞速发展——这为编写海量新代码打开了大门。预计其积极应用将超过消极影响，但我们正在进入一个全新的领域，需要制定新的策略来安全地应对挑战。
