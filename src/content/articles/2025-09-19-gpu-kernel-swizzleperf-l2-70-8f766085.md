在机器学习（ML）与高性能计算（HPC）领域，GPU 内核的性能直接决定了整个系统的运行效率。然而，传统 GPU 内核优化面临两大核心痛点：

::: block-1
1. 手动优化成本极高，资深性能工程师需花费数周时间针对特定硬件设计空间优化方案（如缓存 locality 提升）；
2. 现有自动化方法缺乏 “硬件感知”，仅围绕运行时盲目搜索，无法契合 GPU 的底层架构特性（如离散架构中的加速器复合芯片 XCD、专属 L2 缓存拓扑），导致优化效果有限。
:::

> 而 “Swizzling（重排）” 正是破解这一困境的关键技术：:mdnice-bold-italic[它通过重新定义数据 / 计算任务与 GPU 执行单元、存储位置的映射关系，精准提升数据的空间 / 时间局部性，让计算任务与硬件拓扑（如多 XCD 的 L2 缓存分配）深度适配。]

:mdnice-bold-italic[尤其对于 AMD Instinct™ MI300X 这类离散架构 GPU] （多个 XCD 各搭载独立 L2 缓存），默认的工作组轮询调度会导致关联计算块分散在不同 XCD，浪费 L2 缓存复用机会；:mdnice-bold-italic[而针对性的 Swizzling 能将关联计算块聚合到同一 XCD，直接提升 L2 命中率] —— 这一优化的实际结果极为显著：**不仅能降低跨 XCD 数据交互的开销，更能带来内核执行速度的倍数级提升**，是 GPU 内核从 “可用” 到 “高效” 的核心桥梁。

正是瞄准 Swizzling 的核心价值与现有方法的不足，《SwizzlePerf: Hardware-Aware LLMs for GPU Kernel Performance Optimization》提出了硬件感知的 LLM 驱动方案 SwizzlePerf，其成果直接验证了 Swizzling 在 GPU Kernel 优化中的不可替代性。

## 关键问题

### 问题 1：硬件感知上下文关键要素、冗余性及效果证明

> 【具体问题】论文中 SwizzlePerf 的核心创新在于为 LLM 注入硬件感知上下文，其上下文整合了 profiler 数据、架构规格等多类信息，那么在这些硬件感知上下文要素中，哪些是实现 L2 命中率提升 70%、加速比达 2.06 倍的关键刚需要素？是否存在信息冗余导致 LLM 推理效率下降，且如何证明移除冗余信息后优化效果不会显著衰减？

1. **关键刚需要素**：核心要素包括三类信息：一是**瓶颈指标数据** （如 rocprof 提取的 L2 命中率），作为优化的直接目标信号；二是**硬件架构参数** （XCD 数量、L2 缓存大小等 HIP 设备属性），为空间重排提供物理约束；三是**调度策略细节** （默认轮询调度规则），明确重排需适配的底层调度逻辑；四是**历史迭代缓冲** （过往代码差异与瓶颈报告），避免重复无效尝试并加速收敛。这些要素共同支撑了 L2 命中率 70%、加速比 2.06 倍的优化效果，例如 GEMM 核通过 XCD 数量与缓存分布信息，将相关 tile 聚合至同一 XCD 以提升复用率。
2. **冗余性与效果证明**：不存在实质性冗余。Hardware-overload 基线因输入 10k+无过滤架构文档导致过拟合与正确性问题，而 SwizzlePerf 仅保留与重排直接相关的结构化信息，既避免 LLM 推理负担，又确保信号聚焦。移除冗余的有效性可通过对比实验验证：Hardware-unaware 基线缺失硬件上下文，仅实现微小优化；SwizzlePerf 的结构化上下文在不同问题规模下（如 Stencil 2D 从 512×512 到 10240×1024）均保持稳定增益，证明关键信息已足够，冗余信息反而有害。

### 问题 2：“泛化性-最优性”权衡及框架改进空间

> 【具体问题】硬件过载基线（Hardware-overload）虽存在过拟合和正确性问题，但在特定配置下能实现比 SwizzlePerf 更高的 L2 命中率，而 SwizzlePerf 的核心优势是泛化性，这种“泛化性-最优性”的权衡是否为硬件感知 LLM 优化的固有矛盾？论文提出的框架是否存在机制设计上的改进空间以兼顾二者？

1. **是否为固有矛盾**：非固有矛盾，而是现有信息输入与优化逻辑导致的阶段性结果。Hardware-overload 的“最优性”是特定配置下的过拟合产物（如 transpose 核 32768×32768 尺寸的低比特交换适配），其本质是缺乏瓶颈指标引导与结构化上下文，导致优化依赖偶然适配；SwizzlePerf 的泛化性源于硬件参数、瓶颈信号的精准绑定，牺牲的是“局部最优”而非“全局最优”。二者的核心差异在于是否建立“硬件-瓶颈-重排”的闭环逻辑，而非泛化与最优的本质冲突。

### 问题 3：LLM 选型成本与动态内存访问模式适配

> 【具体问题】论文显示不同 LLM（如 4o、o3-mini）在不同核上表现差异显著，且 SwizzlePerf 对无预测性内存访问模式的核优化无效，那么该框架在实际工业场景中，如何解决 LLM 选型的适配成本问题？对于内存访问模式动态变化的复杂 GPU 核，其硬件感知逻辑是否存在根本性适配障碍？

1. **LLM 选型成本解决方案**：当前可通过“核-模型适配矩阵”降低成本，即针对不同核类型预设高效模型：GEMM 等结构简单的核可选用轻量化 4.1-mini；LayerNorm、FDTD 等复杂核优先使用 4o；Smith-Waterman 等推理需求高的核可尝试 o3-mini。长期来看，论文计划扩展至 Anthropic、Meta 等多厂商模型，建立“模型能力-核特征”的映射规则，实现选型自动化，进一步降低适配成本。
2. **动态内存访问模式的适配性**：当前框架存在阶段性局限，但非根本性障碍。其核心依赖静态重排优化可预测访问模式，对动态模式（如随机内存访问）无效。解决路径可包括：一是引入**实时 profiling 反馈**，将 runtime 内存访问轨迹动态注入上下文，驱动 LLM 迭代调整重排模式；二是结合**runtime 调度接口**，实现重排模式的动态切换，而非静态生成。但目前该方向尚未纳入框架，需后续扩展硬件感知的“动态模态”来突破。

## 一、引言

GPU 代码性能工程是构建高效机器学习（ML）系统和高性能计算（HPC）应用的必要环节。**性能工程需要通过理解特定工作负载在特定底层硬件上的执行方式，实现软硬件协同设计** （hardware-software codesign）。本研究通过模拟专业性能工程师所遵循的软硬件协同设计流程，实现了 GPU 内核性能优化过程的自动化。

> 这一目标的达成，:mdnice-bold-italic[关键在于为 LLM 赋予硬件感知上下文（hardware-aware context）——该上下文能解锁 LLM 的能力，使其可围绕底层硬件架构和调度方法构建 GPU 代码优化方案。]

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/02.webp)

::: image-caption
SwizzlePerf 方法学及重排结果示例。(a) 优化循环始于 CodeGen LLM 调用输入——该输入整合了瓶颈指标（bottleneck metrics）、GPU 特性（GPU characteristics）和调度策略（scheduling policy）的解析后上下文。LLM 会反思过往瓶颈问题，并在 CodeGen LLM 调用输出中提出新的重排公式。(b) SwizzlePerf 为 4-XCD 架构上的 GEMM 内核生成了该重排模式。此重排模式通过将复用矩阵 A 中行数据的块共置在同一 XCD 上，提升了 L2 缓存的局部性。尽管提升 XCD 内部局部性（intra-XCD locality）始终是核心目标，但具体的重排公式会因算法不同而有所差异。）
:::

SwizzlePerf 是我们提出的硬件感知型 LLM 工作流，**可自动生成重排模式** （swizzling pattern）。:mdnice-bold-italic[重排（Swizzling）是一种对数据或工作与它们的执行/存储位置之间的映射关系进行重新排序的转换技术，其目的是提升空间/时间局部性（spatial/temporal locality）并与硬件拓扑（hardware topology）对齐]。编译器和运行时系统会将重排技术用于数据布局（data layouts）和协作块聚类（clustering cooperating blocks）。

在本研究的案例分析中，重排是一种由程序员定义的 GPU 工作组程序 ID（PID，program IDs）重映射方式：**通过将相关数据块（tile）共置（co-locate）在同一加速器复合芯片（XCD，accelerator complex die）上，提升解耦架构 GPU 中每个 XCD 的 L2 缓存复用率（per-XCD L2 reuse）**。默认情况下，工作组会以轮询（round-robin）方式在多个 XCD 之间分配（见图 1b 和案例研究：矩阵乘法）。**对于具有可预测内存访问模式的应用，通过静态方式安排计算与数据以最大化本地 L2 缓存访问，可带来显著的性能收益。**

> 专业 GPU 性能工程师完成针对性空间优化通常需要数周时间，而 SwizzlePerf 能在**几分钟内** 为各类内核自主找到此类优化方案。本研究的贡献：

::: block-1
1. 我们通过**有意构建包含性能分析工具（profilers）和运行时（runtimes）所需硬件及调度信息的上下文**，为硬件感知型内核优化提供支持。
2. 我们为**开源自主性能工程工具 IntelliPerf 增强了硬件感知能力**，并通过生成 GPU 内核重排模式的案例分析对其进行了评估。
3. 我们:mdnice-bold-italic[在各类机器学习和科学计算 GPU 内核上展示了性能结果]：最高实现 2.1 倍加速比和 70%的 L2 命中率提升，这表明硬件感知能力是解锁特定于硬件的优化方案的必要条件。
:::

## 二、相关工作

> :mdnice-bold-italic[现有自主内核优化相关研究大多以运行时作为单一目标]，主要采用三类方法：

::: block-1
1. 启发式自动调优器与解析成本模型，这类方法会应用基于规则的调度策略（如分块（tiling）、循环展开（unrolling）、访问合并（coalescing））[27, 13, 6]；
2. 学习型成本模型，这类模型通过代码或调度特征预测运行时，并驱动组合搜索[9, 28, 1]；
3. 基于大语言模型（LLM）/强化学习（RL）的搜索方法，该方法会执行测试时探索或多轮优化，其应用范围涵盖竞赛编程系统[18, 23]到 GPU 内核框架[20, 8, 5, 17]。
:::

这些方法虽能解决软件层面的瓶颈问题，但通常会抽象掉具体的架构约束（如缓存拓扑、芯粒边界、块放置策略），且仅提供极少的任务特定机器反馈。若缺乏硬件感知能力，搜索空间会变得过于宽泛，同时由于启动开销、重叠瓶颈及计算饱和等因素，目标（运行时）会存在较大噪声。要收敛到特定于硬件的优化方案，大语言模型需要获取能实现硬件感知的相关上下文信息。

> 我们通过模拟人类性能工程师的工作流程来解决这一问题：分析工作负载、定位瓶颈、实施针对性修复，并精确评估优化效果。

:mdnice-bold-italic[在实际操作中，这意味着要主动提供与优化任务相关的分析上下文、架构上下文及调度上下文，并以瓶颈指标为导向提供反馈——该指标需能提供与转换过程一致的稳定信号]。通过将此指标提升为核心优化目标，我们可将搜索范围缩小到直接针对瓶颈的修改上。

在本文针对缓存效率瓶颈的案例研究中，我们将 L2 命中率作为衡量空间局部性的直接、低噪声代理指标。据我们所知，:mdnice-bold-italic[SwizzlePerf 是目前唯一 能将多类分析工具提供的丰富上下文整合进来的研究]，其可直接反映缓存局部性的提升效果，并改进大语言模型的优化性能。

**在此框架下，我们为解耦架构 GPU 如 AMD Instinct™ MI300x [24]设计了重排（swizzling）模式**。这类 GPU 包含多个加速器复合芯片（XCD），每个 XCD 均配备专用 L2 缓存。默认情况下，工作组会以轮询（round-robin）方式在各 XCD 间进行调度（图 1b、案例研究：矩阵乘法）。然而，对于具有可预测访问模式的应用，:mdnice-bold-italic[通过重排技术将协作块（cooperating tiles）静态共置到同一 XCD 上，可显著提升共享 L2 缓存中的数据复用率]。

> 我们的研究贡献在于增加了硬件感知能力，并围绕瓶颈指标进行优化，从而使搜索更具针对性、信号更稳定，且最终生成的转换方案能与底层硬件相匹配。

图 4 展示了代码优化输出签名的结构。输出签名是 DSPy 工具中的一个参数，用于定义 LLM 的输出格式。:mdnice-bold-italic[首先输出非结构化的思维链推理过程，然后明确分析每一次先前迭代的不足，最后说明新实现的设计思路并输出相应代码。]

### 3.2 解析后上下文（Parsed Context）

我们从公开的分析工具和文档中构建结构化上下文：通过 rocprofv3[4]提取瓶颈指标，通过 HIP 设备属性[3]收集 GPU/XCD/缓存参数，通过架构指南推导默认的块调度策略。该解析后上下文会呈现所关注的指标（对于重排优化而言，此指标为 L2 命中率）以及重映射必须满足的空间约束。相关研究未在上下文中纳入任何分析工具提供的信息，而 IntelliPerf 仅会对输出代码进行分析以获取瓶颈指标。

### 3.3 代码生成输出（CodeGen Output）

借助 DSPy [15, 16]，我们指定了输出格式，要求模型必须**评价过往尝试** 并**提出新的重排模式**。大语言模型会返回两部分内容：

1. **对比新旧** 映射的推理过程记录；
2. **重排公式的实现代码**。随后，我们会编译新代码、对照基准实现验证正确性，并运行 rocprofv3 以获取更新后的瓶颈报告。我们复用了 IntelliPerf 的编译/验证/分析框架，但代码生成过程由具备硬件感知能力的上下文和固定目标指导，而非依赖无约束搜索。

### 3.4 瓶颈历史缓冲区（Bottleneck History Buffer）

每次迭代都会**将代码差异和瓶颈报告追加** 到持久化历史缓冲区中。:mdnice-bold-italic[后续调用会查看该历史记录，反思失败情况（如无效映射、L2 命中率无变化等），并提出多样化的重映射方案]。

我们:mdnice-bold-italic[以 L2 命中率为主要指标对候选方案进行排序，并保留验证效果最佳的内核]。该缓冲区通过反馈特定于瓶颈的信号，闭合了软硬件循环，从而加速收敛到与架构匹配的重排模式。

### 案例研究：通用矩阵乘法（GEMM）重排

在分块 GEMM 实现中，输出矩阵 C（维度为 M×N）中位置越接近的块，共享的输入矩阵 A（维度为 M×K）和矩阵 B（维度为 K×N）的数据越多。矩阵 C 中同一行的块共享矩阵 A 的行数据，同一列的块共享矩阵 B 的列数据。

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/07.webp)

然而，在图 5 所示的(M=4)、(N=5)、(XCD 数量=4)的示例中，由于默认的轮询块调度机制，相邻块被分配到不同的 XCD 上，导致每个 XCD 共享的 L2 缓存命中率低于理论最大值。虽然我们无法直接将块重新调度到新的 CU 上，但**可以通过重新计算每个块的程序 ID（PID），让每个 CU 处理不同的输入数据并写入不同的输出块**。这种方式:mdnice-bold-italic[本质上是在 CU 之间进行任务交换，计算开销极小，且能提升许多核函数的 L2 命中率。]

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/07.webp)

> SwizzlePerf 能够为任意核函数算法、硬件架构或默认块调度方案自动生成重排模式。

图 5 中的 GEMM 重排示例，专家性能工程师花费了两周时间才完成设计与验证，而 SwizzlePerf 在不到 5 分钟的时间内就生成了功能相同的方案，且额外处理了边界情况。**在计算每个 XCD 的块数时，SwizzlePerf 采用了向上取整除法来处理边界情况**，:mdnice-bold-italic[这一细节在专家设计的重排模式中并未体现]。

> 表明 SwizzlePerf 并非简单复用现有方案，而是能自主应用新的优化技术。

## 四、实验结果

### 4.1. 实验设计：对比方案与评估配置

**对比方案**。我们将具备硬件感知能力的 SwizzlePerf 与两个基线方案进行了对比：

::: block-1
- **硬件无感知型（Hardware-unaware）**：未包含硬件或调度信息的基础 IntelliPerf 循环；
- **硬件信息过载型（Hardware-overload）**：输入包含未经筛选、超过 10000 个 token 的公开 GPU 架构文档数据集。
:::

**评估对象**：我们对 10 个与实际工作负载相关的 GPU 内核进行了评估，其中包括 6 个机器学习（ML）内核（通用矩阵乘法（GEMM）、融合逐元素运算、层归一化、softmax、朴素稀疏矩阵向量乘法（SpMV）、转置）和 4 个科学计算（Science）工作负载内核（Black-Scholes 期权定价模型、二维时域有限差分（FDTD）、Smith-Waterman 序列比对算法、二维模板（Stencil 2D））。

**测试条件**：我们在中等问题规模（约 5 毫秒）下进行基准测试，并对照参考实现（机器学习内核使用 PyTorch，科学计算内核使用 CPU 实现）验证正确性。

### 4.2 SwizzlePerf 的加速比表现

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/08.webp)

> 在图 2 中，**“×”表示交错重映射** （swizzling）:mdnice-bold-italic[对 L2 命中率无影响的情况]，**“×⃝”表示重映射失效** （broken remappings）的情况。

在 10 个内核中，SwizzlePerf 实现了**平均 1.29 倍的加速比**，其中转置内核的加速比最高，达 2.06 倍。

- 转置内核的大幅**性能提升源于其通过在 XCD 之间对 $M \times N$ 瓦片网格进行跨步（striding）处理**，:mdnice-bold-italic[使原始读取操作和转置写入操作均局限在同一 XCD 的 L2 缓存内]，从而**消除了跨 XCD 的缓存颠簸** （thrashing）问题。
- 对于 softmax 内核，SwizzlePerf 通过:mdnice-bold-italic[在其两阶段归约过程（先求最大值，再进行指数运算与求和）中将所有行块（row chunks）分配到同一 XCD，使行值在 L2 缓存中保持驻留状态，减少了冲突缺失] （conflict misses），最终实现了 1.54 倍的加速比。:mdnice-bold-italic[这些结果表明，SwizzlePerf 生成的重映射模式能够持续提升分布式架构 GPU 的端到端运行时间和整体系统效率。]

> 这些结果表明，SwizzlePerf 生成的重映射模式可持续提升分布式架构 GPU 的端到端运行时间与整体系统效率。

### 4.3 L2 命中率优化与关键洞察

**相较于仅通过运行时间衡量优化效果，L2 命中率更能准确反映优化是否成功**：运行时间可能因内核启动开销、计算饱和（compute saturation）和重叠瓶颈（overlapping bottlenecks）而产生波动，而 :mdnice-bold-italic[L2 命中率可直接体现缓存感知型重映射是否有效]。

SwizzlePerf:mdnice-bold-italic[找到的重映射模式使 L2 命中率最高提升 70%，平均提升 23.9%；] 其中 **4 个内核的交错重映射实现接近 100% L2 命中率**，这表明 SwizzlePerf 能够帮助硬件逼近缓存效率的理论上限。

::: block-1
- 对于 GEMM 这类**计算密集型** （compute-bound）内核，:mdnice-bold-italic[14%的 L2 命中率提升仅转化为 1.03 倍的温和加速比；]
- 相反，对于二维模板（Stencil 2D）和转置这类**内存敏感型** （memory-sensitive）内核，:mdnice-bold-italic[当 L2 局部性成为性能瓶颈时，命中率的提升会带来显著的加速效果。]
:::

> 所有内核的性能提升均表明，**无论内核的具体瓶颈是什么，主动提供相关硬件上下文都至关重要**。相比之下，硬件无感知型和硬件信息过载型方案的交错重映射模式仅能带来极小的 L2 命中率提升，且从未实现任何加速效果。

### 4.4 SwizzlePerf 交错重映射通用有效性验证

硬件感知能力与明确的引导指标使 SwizzlePerf 能够可靠地发现优化模式，这些模式：

1. 验证了交错重映射的通用有效性（详见下面 4.4.1 优化循环进程 和4.4.2 不同问题规模下的性能评估）
2. 转化为显著的端到端加速比。

为更充分验证“交错重映射的通用有效性”这一结论，下面我们从两个核心维度展开分析：

- 聚焦**优化循环的迭代进程**，通过多轮实验对比 SwizzlePerf 与基准方案（硬件无感知、硬件信息过载）的表现，观察重排模式的生成效率与稳定性；
- 从**问题规模的多样性** 切入，通过消融实验验证重排模式是否能适配不同输入规模，避免仅针对单一规模过度拟合，进一步夯实“通用”这一核心特性。

#### 4.4.2 消融实验：不同问题规模下的性能评估

> 本实验的核心目标是：验证 SwizzlePerf 生成的重排模式是否具备“通用性”——即能否适配多种输入规模，而非仅对某一特定规模过度拟合。

我们选取 LayerNorm、Smith-Waterman、2D 模板三个典型核函数，通过扩大问题规模的方式，测试重排模式的性能稳定性。

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/10.webp)

上图 15，表示三个核函数（LayerNorm、Smith-Waterman、2D 模板）的 L2 缓存命中率与问题规模的关系图。

##### 1. LayerNorm 核函数

实验中，其问题规模从 64×1024×1024 元素逐步扩大至 512×8192×1024 元素。结果显示：

- SwizzlePerf 生成的重排模式，能稳定将 L2 命中率从 46%提升至 60%；
- 且无论张量规模如何增大，这一命中率提升幅度始终保持稳定。

这种“规模无关”的性能优势，直接**证明重排模式具备通用性，而非针对特定规模优化**。

##### 2. Smith-Waterman 核函数

我们将其序列长度进行 5 次翻倍，从 $512^{2}$ 个双精度（DP）单元扩大至 $8192^{2}$ 个 DP 单元。结果显示：

- 重排后的核函数 L2 命中率从 50%提升至 65%，而未重排的基准方案命中率最高仅接近 56%；
- **更关键的是，两者的命中率差距随规模扩大而增加** ——从最小输入规模的约 3%，扩大到最大输入规模的约 10%，对应 15%-20%的相对性能提升，且**规模越大，优化效果越显著。**

##### 3. 2D 模板核函数

我们将其网格边长扩大 20 倍，从 512×512 单元增至 10240×10240 单元。结果显示：

- 未重排方案的 L2 命中率随规模扩大从 65%降至 53%，而重排方案的命中率始终稳定在 74%-82%之间；
- 在最大问题规模下，重排方案的命中率优势达 20%-30%（相对提升超 40%），这:mdnice-bold-italic[表明重排模式能让该核函数的雅可比迭代（Jacobi update）缓存局部性基本不受规模变化影响，进一步验证了其通用有效性。]

### 4.5 案例研究：其他重排模式示例及解读

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/11.webp)

在图 6 所示的层归一化（LayerNorm）重排中，我们对 pid_m 进行重新映射，使同一输入行的所有 BLOCK_SIZE_N 列块都路由到同一个 XCD。该核函数会将该行的:mdnice-bold-italic[部分和（均值与方差）以及加载的权重/偏置向量保留在该 XCD 的 L2 缓存中，供多次加载操作复用，从而大幅提升行内数据的复用率]。同时，将不同的行均匀分配到 8 个 XCD 上，可避免单个 L2 缓存出现颠簸，最终实现了 34%的命中率提升。

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/12.webp)

在图 7 所示的 Softmax 重排中，由于 Softmax 对每一行需执行两阶段归约（先求最大值，再进行指数运算与求和），:mdnice-bold-italic[将某一行的所有 BLOCK_SIZE 块分配到同一个 XCD 上，可使该行数据在两阶段归约过程中始终驻留在该 XCD 的 L2 缓存中，避免数据在 DRAM（动态随机存取存储器）与缓存之间频繁传输]。同时，:mdnice-bold-italic[将不同的行均匀交错分配到 8 个 XCD 上，可避免单个 XCD 成为热点，从而减少冲突缺失与缓存淘汰]，最终实现了 66%的 L2 命中率提升。

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/13.webp)

在图 8 所示的时域有限差分（FDTD）重排中，该模式将每个 2D FDTD 块映射到 XCD 上，使位于同一垂直跨度（即 x 范围相同但 y 范围不同）的块分配到同一个 XCD。同时，通过“xcd_id = pid_y % num_XCD”步骤将这些垂直跨度按轮询方式分配到 8 个 XCD 上，可避免单个 XCD 承载过多依赖相邻块的任务，从而防止缓存颠簸。:mdnice-bold-italic[这种将 FDTD 的相邻访问需求与 XCD 间负载均衡相结合的方式，最终实现了 20%的 L2 命中率提升。]

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/14.webp)

在图 9 所示的 2D 模板重排中，该模式对块进行重新映射，使 M 或 N 方向上相邻（因此在模板计算中共享数据）的块分配到同一个 XCD 的 L2 缓存中。:mdnice-bold-italic[通过将网格按对角线跨度分组布局，每个 XCD 可在多次块调用过程中保持对“中心块及相邻块”数据的缓存驻留]；同时，**轮询调度机制避免了单个 XCD 出现颠簸**，最终实现了 70%的 L2 命中率提升。

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/15.webp)

在图 10 所示的转置重排中，该模式将 M×N 块网格的线性化索引按跨度分配到 8 个 XCD 上。具体而言，先对每个块的行优先索引取模（模 XCD 数量）以确定其所属 XCD，再将剩余块按连续方式重组。最终，每个 XCD 会“接管”输入矩阵的完整“行带”及其对应的输出矩阵“列带”。对于转置核函数，这种布局意味着：当加载一个 BLOCK_SIZE_M×BLOCK_SIZE_N 大小的块并将其转置为 BLOCK_SIZE_N×BLOCK_SIZE_M 大小后，:mdnice-bold-italic[原始读取与转置写入操作均会命中同一个 XCD 的 L2 缓存，避免了跨 XCD 的缓存颠簸]；同时，**块的均匀分配避免了单个 L2 缓存成为热点**，最终实现了 34%的命中率提升。

### 4.6 案例研究：硬件信息过载导致按位重排

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/17.webp)

在针对特定核函数与问题规模的实验中，:mdnice-bold-italic[“硬件信息过载”优化循环通过采用按位移位（SHIFT）与加法（ADD）重排（如图 13 所示）实现了显著的加速。]

![文章插图](/articles/2025-09-19-gpu-kernel-swizzleperf-l2-70-8f766085/images/18.webp)

其中，“无硬件感知”方案采用简单的基于大小的重排模式（如图 12 所示），而 SwizzlePerf 则生成了更复杂的、针对 MI300X 的专属映射（如图 11 所示）。

:mdnice-bold-italic[按位重排方案的 L2 命中率最高可比 SwizzlePerf 高出 70%，但该方案过度拟合特定问题规模，且常出现正确性问题]。例如，在$M=32768$、$N=32768$的转置核函数中，低位交换操作可完美实现块的同 XCD 分配，但类似模式在其他核函数上均失效。

这些结果表明，**“硬件信息过载”的重排方案不具备通用性：**

::: block-1
- 若块数量与 XCD 数量不匹配、BLOCK_SIZE_M/N 参数变化，或 GPU 的 XCD 数量不同，这种**硬编码的交换操作会破坏数据复用。**
- 此外，许多“硬件信息过载”模式还存在**双射性问题——当网格形状变化时，块会被分配到不存在的目标位置。**
:::

尽管“硬件信息过载”方案提供了可融入 SwizzlePerf 的有趣思路，但其在不同问题规模下的鲁棒性不足，限制了实际应用。相比之下，SwizzlePerf 在不同核函数与问题规模下均能正确实现通用优化，即使并非在所有配置下都能达到最优性能。

在图 16 中，我们评估了不同 LLM 对 SwizzlePerf 生成重排模式的影响。过往研究已发现，不同 LLM 在代码优化[23]与计算机体系结构[21]任务中的能力存在差异。我们在 GEMM、LayerNorm、FDTD 和 Smith-Waterman 核函数上，分别采用 OpenAI 的 4o、4.1-mini 和 o3-mini 模型运行 SwizzlePerf。

- 在 GEMM 核函数上，三个模型均收敛到与专家方案等效的重排模式——这一结果符合预期，因为 GEMM 的局部性结构相对简单。
- 在 LayerNorm 和 FDTD 核函数上，仅 4o 模型能发现有效方案：4.1-mini 模型规模过小，难以处理复杂映射；o3-mini 模型虽为推理优化模型且在多数基准测试中表现更优，但在该任务中仍存在性能不足。

> 这些结果表明，:mdnice-bold-italic[不同模型在不同核函数上的表现存在差异，且针对推理的训练并不总能提升硬件感知优化能力（即使已提供明确的上下文）。最优模型的选择通常取决于核函数类型、硬件架构与问题规模]。

## 五、讨论与未来工作

### 5.1 SwizzlePerf的核心价值：填补硬件感知空白与验证闭环反馈

> SwizzlePerf 的关键突破在于解决了当前自主性能工程框架中**硬件感知能力缺失** 的核心痛点。

通过为大语言模型（LLM）注入包含硬件架构参数、调度策略细节与瓶颈指标（如 L2 命中率）的结构化上下文，其不仅能在几分钟内为各类 GPU 内核复现专家级性能优化推理过程，更实证了**闭环“硬件-软件”反馈循环** 的核心作用——这一循环让优化脱离低效的无约束搜索，转而精准对准硬件瓶颈生成适配方案，成为释放效率提升空间的关键。

### 5.2 超越性能：重排模式的能效附加价值

尽管 SwizzlePerf 当前以性能优化为核心目标，但其局部性感知重排模式还带来了显著的**能效增益**，形成“性能-能效”双重收益。从原理上看，该模式通过两大路径降低能耗：

1. **减少跨层级数据传输**：将原本需访问设备内存（device memory）的缓存缺失转向片上 L2 缓存，避免数据在完整内存层级中传输的高能耗；
2. **稳定缓存驻留与减少片外流量**：通过将协同块聚类到单个加速器复合芯片（XCD），降低片外数据交互频率，即便在算术吞吐量主导的核函数中，也能减少每条指令的平均能耗。

这种能效优势在计算密集型场景中仍具韧性，甚至可通过动态电压频率调节（DVFS）机制进一步放大：

::: block-1
- L2 命中率提升会降低瞬时功耗，使核函数远离 DVFS 节流阈值，既支持更高的持续时钟频率，也能为共存核函数（co-resident kernels）释放资源；
- 即便 DVFS 限制频率，重排模式也能通过将能耗聚焦于计算而非内存访问，提升“能效比”（energy-to-solution）。
:::

未来，我们计划通过[19,14,26]等文献的评估方法，对该能效收益进行严谨量化，并融入面向能效的重排决策设计。

### 5.3 未来研究方向：扩展LLM硬件感知模态与能效优化升级

展望后续研究，我们认为突破点将集中于两大方向，推动 SwizzlePerf 从“性能优化工具”向“性能-能效协同优化智能体”演进：

#### 5.3.1 扩展LLM的硬件感知模态

当前 SwizzlePerf 依赖文本化的硬件参数与瓶颈数据（如 rocprof 日志），但非文本模态（如交错重映射模式可视化、缓存访问轨迹图）因与具体算法强绑定，仍存在应用挑战。其中，**注意力内核（attention kernels）** 是理想的研究起点——其功能一致性与多实现路径（[11, 22, 2, 10, 12]），为探索“非文本模态-优化效果”的关联提供了清晰场景，可逐步破解非文本模态适配难题。

#### 5.3.2 将能效优化升级为核心目标

当前能效收益是性能优化的“附加价值”，未来计划将其升级为核心优化目标：通过建立“重排模式参数-能效指标”的映射模型，结合前述 DVFS 机制的量化分析，实现性能与能效的协同调度，满足现代 GPU 对低功耗运行的需求。

### 5.4 核心探索问题：面向能效的重排优化

> 最终，我们的研究将回归一个根本性问题：:mdnice-bold-italic[在真实复杂的工作负载中，哪些硬件感知模态（文本参数、可视化轨迹、能耗曲线等）的组合，能让 LLM 真正具备人类性能工程师的系统性思考能力——既理解硬件约束边界，又能平衡性能与能效，还能适配动态场景（如输入规模变化、多内核共存）的需求？]

这一问题的解答，将为下一代硬件感知型 LLM 性能工程智能体奠定技术基础。
