## 一、现有基准的盲区：推理工程为什么需要生产级评估？

> 代码智能体的能力评估早已进入仓库级时代，但面向推理服务这一核心场景，现有基准始终缺失生产全链路的验证维度。:mdnice-bold-italic[当智能体生成的代码在本地单元测试中全部通过，部署到生产推理服务中却出现模型加载失败、接口请求异常、并发状态错乱等问题时，我们才意识到：本地正确性与生产正确性之间，隔着一整条推理服务栈的距离。]

现有智能体基准主要分为三类，各自都无法覆盖生产推理工程的完整需求。

| 类别 | 描述 |
| --- | --- |
| 通用仓库级软件工程基准 | 包括 SWE-bench Verified、SWE-bench Pro、DeepSWE 等，**评估智能体对现有代码仓库的修改能力**；不针对推理工程场景，也不涉及 GPU 依赖的执行环境。 |
| **终端智能体基准** | 如 Terminal-Bench 3，扩展至交互式系统任务，共 74 个任务，其中仅 3 个涉及推理工程（占比 4.1%），缺乏体系化评估能力。 |
| 推理性能基准 | 包括 KernelBench、SOL-ExecBench、InferenceBench、ISO-Bench 等，:mdnice-bold-italic[聚焦 GPU 内核生成与性能优化；仅覆盖孤立内核或局部性能优化，不涉及仓库级生产功能实现，也不考虑全链路服务正确性]。 |

::: block-1
:mdnice-highlight[推理工程的特殊性在于，它是要在完整的服务栈中实现功能，需要协调模型支持、运行时执行、调度策略、缓存管理、公共 API 等多个层级的变更]。

一个变更在隔离环境中运行正常，不代表在完整的服务链路中、在持久化状态下、在并发请求场景下依然正确🥱。比如 Gemma 4 MoE 核心服务任务中，近半数智能体生成的补丁通过了所有组件测试，却无法通过真实服务进程的公共接口正确提供模型服务。
:::

正是为了填补这一空白，SWE-Serve 基准应运而生，**专门面向生产推理工程场景，评估智能体是否能真正实现生产级的正确性。**

## 二、SWE-Serve 基准设计：源自真实生产的全链路评估体系

> SWE-Serve 的核**心设计目标，是把真实生产环境中的推理工程工作，转化为可执行、可量化、可复现的基准任务**。它所有:mdnice-bold-italic[任务都源自 SGLang 开源推理服务系统的真实生产合并请求，而非人工构造的玩具问题]，同时建立了严格的任务构建与验证流程，确保每个任务都具备生产级的难度与有效性。

::: image-caption

### 2.1 任务构建：从生产变更到标准化基准

> SWE-Serve 的任务构建经历了三个完整阶段，确保任务的真实性与有效性。

- **第一阶段是源发现与筛选**，通过四种路径（发布说明扫描、发布说明与关联 PR 人工审核、维护者路线图议题、SGLang 团队直接建议）识别了 786 条任务源记录，经过多轮筛选后保留 203 个源候选。
- **第二阶段是任务构建**，对源候选去重后生成 156 个任务候选，每个任务都包含指定的基础提交版本、任务说明、参考解决方案、可复现执行环境和隐藏测试用例。
- **第三阶段是资格验证与准入**，通过可执行控制校验、智能体辅助对抗性探测、人工评审三个环节，最终准入 53 个任务，整体准入率为 34.0%。

::: block-1
为了保证任务的严谨性，:mdnice-highlight[每个准入任务都通过了两项核心控制校验：无操作控制（no-op）必须失败所有 F2P 测试（Fail‑to‑Pass，由失败变通过测试）、通过所有 P2P 测试（Pass‑to‑Pass，保持通过测试，回归保护测试）]，确保任务在基础版本上是非平凡的；**参考解决方案（oracle）必须通过所有适用测试，确保任务是可解的**。此外，**每个任务还经过了智能体辅助的对抗性探测，寻找验证器的漏洞与盲区**，比如是否接受不完整的捷径方案、是否拒绝合理的替代实现等，最大程度保证评估的公平性。
:::

### 2.2 六大任务家族：覆盖完整推理服务栈

> 这 53 个任务覆盖了六大推理工程领域，完整覆盖了推理服务栈的核心工作方向：

| 工程家族 | 任务数量 | 核心工作内容 |
| --- | --- | --- |
| 模型与后端启用 | 12 | 新模型支持、后端适配、硬件兼容 |
| 推测与高级解码 | 14 | 推测解码、高级采样策略、解码算法优化 |
| 内核、量化与性能 | 8 | CUDA 内核开发、量化优化、性能调优 |
| 缓存与运行时状态 | 7 | KV 缓存管理、运行时状态持久化、缓存策略 |
| 分布式执行与调度 | 4 | 分布式调度、任务分发、优先级调度 |
| 服务 API 与运行时正确性 | 8 | 公共 API 实现、接口兼容性、运行时校验 |

从任务规模来看，SWE-Serve 的任务中位数包含 200 字的任务说明，参考解决方案中位数修改 553 行代码、涉及 7 个文件，最大的任务修改 6077 行代码、涉及 35 个文件。:mdnice-bold-italic[与 SWE-bench 系列、DeepSWE 等基准相比，SWE-Serve 的参考解决方案平均修改更多代码行和文件，而任务说明更短，这意味着智能体需要自主探索仓库结构、规划实现方案，而非遵循详细的步骤指示，更贴近真实的工程场景。]

### 2.3 评估标准：定义生产正确性

> **SWE-Serve 采用行为导向的评估方式**，而非对比智能体生成的补丁与参考解决方案的相似度。:mdnice-bold-italic[每个任务都包含隐藏的可执行验证器，从三个维度评估补丁的正确性：]

1. **失败转通过测试（F2P）**：验证任务要求的新功能是否正确实现，这些功能在基础版本中不存在
2. **通过转通过测试（P2P）**：验证基础版本中已有的功能是否被保留，即回归保护
3. **端到端服务测试与性能门限**：在适用任务中，启动独立的真实服务进程，通过公共接口验证全链路行为；性能相关任务还会设置标定的性能阈值

:mdnice-bold-italic[智能体只有通过全部测试才算通过任务]。这一定义了**生产正确性** 的完整内涵：在完整的推理系统中满足任务的所有行为要求，同时保留现有功能，并且满足任务特定的性能约束。

## 三、核心发现：本地正确性与生产正确性的量化鸿沟

> :mdnice-bold-italic[SWE-Serve 最核心的贡献，是第一次用可执行的量化结果证明：在推理工程场景中，本地通过所有组件测试的代码，很可能无法通过生产级的端到端验证]。这一“生产正确性差距”不是个例，真的是普遍存在于所有被测模型中，且差距幅度远超行业预期😅。

### 3.1 端到端测试：筛掉三分之一的“本地正确”补丁

论文通过严格的控制变量实验，量化了端到端服务测试带来的通过率差距。在 19 个包含模型服务端到端测试的任务中，共 627 个智能体生成的补丁，使用完整验证器时的通过率为 45.9%；而移除端到端测试、保留所有其他测试不变时，通过率提升至 69.4%，相差**23.4 个百分点**。**也就是说，约三分之一在本地组件测试中全部通过的补丁，在真实的端到端服务场景中会失效。**

> 为了排除“移除任何测试都会提升通过率”的普遍效应，论文还设计了匹配测试移除对照实验。

在 12 个符合条件的任务中，每次移除相同数量的端到端测试和非端到端测试，且保证测试的 F2P/P2P 角色匹配，重复 10000 次随机抽样。**结果显示，移除端到端测试平均带来 16.1 次失败转通过的变化，而移除匹配的非端到端测试仅带来 8.0 次，前者是后者的 2.0 倍**。在 92.2%的随机抽样对中，移除端到端测试都带来了更多的通过率提升，:mdnice-bold-italic[证明端到端测试对应的生产正确性验证，确实是更难通过的核心关卡。]

::: block-1
以 Gemma 4 MoE 核心服务任务为例，33 个智能体生成的补丁中有 16 个通过了所有非端到端测试，却至少在一个端到端测试中失败，占比达 48.5%。

这些端到端测试涵盖了加载官方检查点、通过模型的 128 个专家中的前 8 个路由每个 token、通过公共接口提供文本和图像服务、带对数概率的有序原生批量生成等真实生产场景，这些都是组件测试无法覆盖的全链路行为。
:::

### 3.2 更多生产属性：跨域、状态与并发的三重考验

> 除了端到端服务测试，**还有三个生产相关的任务属性也会带来显著的通过率差距**，这些都是本地单测难以覆盖的生产场景特性：

| 差距类型 | 描述 |
| --- | --- |
| 运行域广度差距 | 单运行域任务的平均通过率为69.0%，而跨多个运行域的任务通过率仅为47.7%，相差21.3个百分点。运行域涵盖请求I/O、调度与请求生命周期、模型执行、KV缓存与资源管理四个层面，跨域任务需要协调多个层级的行为，复杂度呈指数级上升。 |
| 持久状态差距 | :mdnice-bold-italic[需要验证持久状态的GPU任务，通过率比不需要的低20.8个百分点。持久状态意味着操作之间或生命周期阶段之间需要保持状态一致性]，比如KV缓存的生命周期管理、会话状态的持久化等，这些在单次执行的本地测试中很难暴露问题。 |
| 并发协调差距 | 明确测试并发协调的6个GPU任务，通过率比不测试的低29.0个百分点。并发场景下的资源竞争、状态一致性、时序依赖等问题，在单线程测试中几乎无法复现，却是生产环境中的常见故障源。 |

## 四、11 款主流模型横评：性能、成本与可靠性的全面权衡

> **论文使用统一的 mini-SWE-agent 框架，对 11 款主流大模型进行了标准化评测，共覆盖 31 种模型-推理努力配置**。评测不仅关注:mdnice-bold-italic[通过率指标，还全面衡量了成本、token 消耗、执行步数、耗时等资源维度]，展现了不同模型在生产推理工程场景下的综合表现。

### 4.1 整体排行榜：头部并列，资源消耗差异巨大

在每种模型的最优配置下，平均 pass@1（单次运行通过率的均值）呈现出 40 个百分点的分布区间。

- Claude Opus 5 和 GPT-5.6 Sol 并列第一，均达到 75%；
- Claude Sonnet 5、Kimi K3、GPT-5.6 Luna、GPT-5.6 Terra 四款模型并列第二梯队，均为 64%；
- DeepSeek V4 Flash 为 55%；
- GLM-5.2 和 Gemini 3.6 Flash 均为 48%；
- Laguna S 2.1 为 46%；Inkling S 最低，为 35%。

> 一个非常值得关注的现象是，**同样处于 64%的通过率梯队，不同模型的资源消耗差异巨大。**

- 成本方面，GPT-5.6 Luna 单任务成本仅 0.95 美元，而 Claude Sonnet 5 需要 12.26 美元，相差 12.9 倍；
- 耗时方面，GPT-5.6 Terra 单任务平均耗时仅 25.5 分钟，而 Kimi K3 需要 99.9 分钟，相差 3.9 倍；
- 输出 token 方面，GPT-5.6 Sol 仅需 52k，而 Inkling S 需要 147k，相差 2.8 倍。

这说明，**通过率相同的情况下，不同模型的工程落地成本可能有数量级的差异**，实际选型需要根据性能、成本、时延的优先级综合权衡。

### 4.2 推理努力的边际收益与性价比

::: block-1
论文对 Claude 和 GPT-5.6 系列的 5 款模型，分别测试了低、中、高、xhigh、max 五个推理努力等级。:mdnice-highlight[结果显示，更高的推理努力始终会带来更高的成本，但性能提升幅度在不同模型和不同等级间差异很大。]
:::

以 Claude Opus 5 为例，从 high 提升到 max 努力，pass@1 仅从 74%提升到 75%，仅提升 1 个百分点，但平均成本却从 9.89 美元涨到 17.40 美元，上涨 76%。**这说明单纯追求 pass@1 的边际收益会快速递减，工程应用中需要找到性价比最优的努力等级，而非盲目开启最高推理模式。**

### 4.3 可靠性与分领域表现

> 除了单次通过率，**重复运行的可靠性也是工程应用的关键指标**。论文引入了 pass@3（三次运行中至少通过一次的比例）和 passˆ3（三次运行全部通过的比例）两个指标。比如：

- 同样是 55%的 pass@1，DeepSeek V4 Flash 的 pass@3 为 74%，高于 GPT-5.6 Luna 的 64%，说明 DeepSeek 的能力上限更高；
- 而 GPT-5.6 Luna 的 passˆ3 为 45%，高于 DeepSeek 的 42%，说明 Luna 的结果更稳定。

分任务家族来看，所有模型在“内核、量化与性能”类任务上表现最好，平均通过率达 74.6%；而**在“模型与后端启用”类任务上表现最差，平均仅 42.9%。这是因为内核与性能优化通常有明确的功能边界和验证标准，而模型与后端启用涉及全栈的适配与联调，复杂度更高**。:mdnice-bold-italic[Claude Opus 5 和 GPT-5.6 Sol 在六个任务家族中的五个都取得了最高通过率，综合实力最强]；GPT-5.6 Luna 则在分布式与调度类任务上领先。

## 五、评估方法的严谨性与适用边界

基准评测的结论是否可靠，很大程度上取决于评估方法的严谨性。SWE-Serve 在评估体系设计上做了多重严格控制，同时也验证了不同 Agent 框架、闭卷执行等因素对结果的影响，明确了基准的适用边界与局限性。

### 5.1 Agent 框架对结果的影响

> 为了验证统一评估框架的公平性，**论文对表现最好的两个配置——GPT-5.6 Sol max 和 Claude Opus 5 max，分别使用它们各自的原生开发框架（Codex 和 Claude Code）进行了对比测试。**

**结果显示，使用原生框架并没有提升通过率**：:mdnice-bold-italic[mini-SWE-agent 下两者均为 75.5%，而 Codex 下 GPT-5.6 Sol 为 73.6%，Claude Code 下 Claude Opus 5 为 69.8%，反而更低]。这说明使用统一的 mini-SWE-agent 框架进行横向对比是公平的，不会因为框架偏向而高估特定模型的能力。

**不过框架选择会显著影响资源消耗：原生框架的执行速度更快，但推理成本更高**。:mdnice-bold-italic[比如 Claude Code 比 mini-SWE-agent 快 16%，但成本高 21%；Codex 比 mini-SWE-agent 快 10%，但成本高 4%。] 企业在实际落地时，可以根据自身的成本与时延偏好选择合适的 Agent 框架。

### 5.2 闭卷评估的必要性与实现

SWE-Serve 采用严格的闭卷执行模式，即智能体无法通过公共网络检索上游的解决方案。论文在开卷预实验中发现：

- 所有被测模型都会尝试外部检索，且推理努力越高，检索比例越高：
- xhigh 努力下，超过 54.7%的任务会出现外部获取，32.1%的任务会出现明确的带外内容检索。

**如果采用开卷模式，评测结果反映的更多是模型的检索能力而非工程能力。**

因此正式评测全部采用网络隔离的闭卷模式，并且对每个执行轨迹进行完整审计，所有违规检索尝试都被阻断，确保评测结果真实反映模型自身的推理工程能力。

### 5.3 基准的局限性

> 论文也坦诚地指出了 SWE-Serve 当前的局限性：

- **任务全部源自 SGLang 项目，未来扩展到 vLLM、TensorRT-LLM 等其他推理系统**，将有助于验证结论的普适性
- 执行环境仅限 CPU 或单 H100 GPU，没有覆盖多 GPU、多节点的分布式并行任务，而这是大规模推理服务的核心场景
- 可执行评分只能衡量功能、回归、集成、端到端和特定性能要求，无法评估代码可维护性、架构适配性、工程规范性等上游就绪度维度
- **闭卷执行和轨迹审计可以防止评测过程中的检索，但无法排除模型训练语料中已经包含相关代码的可能性**，为此每个任务都加入了基准金丝雀字符串，支持后续的训练语料去污染验证

## 六、行业启示与未来展望

> SWE-Serve 代表了智能体评估从“玩具问题”走向“生产真实”的重要转向。

首先，**智能体评估标准需要从“本地功能正确”升级到“生产链路正确”**。过去我们评估代码智能体，总是停留在“能不能实现功能”的层面，而 SWE-Serve 告诉我们，生产级的工程能力远不止于此。:mdnice-bold-italic[真正的生产正确性，需要考虑端到端全链路、持久状态、并发场景、跨域协同等一系列生产环境特有的约束]。如果基准只覆盖本地测试，评估出来的能力很可能只是“实验室幻觉”，无法落地到真实生产环境。

其次，**推理工程智能体的技术演进需要聚焦全栈能力**。当前智能体在内核优化、单模块修改等局部任务上已经表现不错，:mdnice-bold-italic[但在跨层级、全链路的功能实现上还有明显差距]。**未来的推理工程智能体，需要强化对完整服务栈的理解，提升端到端的调试与联调能力**，而不仅仅是擅长写孤立的内核或函数。同时，:mdnice-bold-italic[对持久状态、并发场景等生产特性的处理能力，也应该成为智能体能力进化的重要方向。]

最后，企业落地代码智能体必须建立生产级验证体系。对于推理服务企业来说，在生产环境中引入代码智能体时，不能只看本地测试的通过率，必须建立完整的生产级验证链路。:mdnice-bold-italic[尤其是推理服务场景，链路长、组件多、状态复杂，局部正确不代表全局正确。智能体生成的代码必须经过端到端服务测试、并发压力测试、持久状态验证等全流程校验，才能进入生产环境。]

::: block-1
SWE-Serve 为生产推理工程智能体建立了全新的标尺，它量化了本地与生产的差距，也为未来的技术进步指明了方向。随着智能体能力的不断提升，我们期待看到这一差距逐步缩小，:mdnice-highlight[最终实现推理工程的【全流程】智能化。]
:::
