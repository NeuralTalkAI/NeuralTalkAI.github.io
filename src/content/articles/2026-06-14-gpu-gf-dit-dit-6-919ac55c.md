关键词：**Diffusion Transformer**、弹性并行调度、:mdnice-bold-italic[无组通信]、生成式 AI 服务、**vLLM-Omni**

> GPU 并行度不应该是部署时就拍板的静态配置，而应该像操作系统调度 CPU 时间片一样，在运行时动态分配给最需要它的请求。

这是 GF-DiT 论文中最具颠覆性的核心洞察。当 Diffusion Transformer（DiT）已成为文生图、文生视频的主流架构，**当 Wan2.2、Qwen-Image 等模型不断刷新生成质量，服务端系统却仍在用几十年前的静态并行思维** —— :mdnice-bold-italic[每个请求一进来就被分配固定的 GPU 数量，然后从头到尾不变。这种僵化的资源分配方式正在造成巨大的算力浪费。]

::: block-1
**DiT 工作负载天然具有三重异构性：**

- 不同请求之间，输出分辨率、视频时长、去噪步数可能相差数个数量级；
- 同一请求内部，编码、去噪、解码三个阶段对并行度的偏好截然不同；
- 系统负载随时间动态变化，轻载时大并行度降延迟，重载时小并行度提吞吐。静态并行配置永远无法同时最优。
:::

## 一、为什么静态并行正在杀死 DiT 服务效率

### 1.1 DiT 执行的三重异构性

> **DiT 与 LLM 的执行结构有着本质区别**。LLM 是预填充 + 自回归解码的两阶段，而 :mdnice-bold-italic[DiT 是编码、数十步去噪、解码的三阶段流水线。其中去噪阶段占据 90% 以上的执行时间。]

![文章插图](/articles/2026-06-14-gpu-gf-dit-dit-6-919ac55c/images/06.webp)

::: image-caption
图 2：扩散模型服务请求的执行架构。编码阶段生成条件嵌入特征，去噪阶段迭代推进扩散轨迹，VAE 解码阶段输出最终图像 / 视频。轨迹任务的分界点为运行时动态适配提供了具备语义合法性的重调度时机。
:::

> 理解 DiT 服务的低效根源，必须从其执行结构说起。**一个典型的 DiT 生成请求包含三个独立阶段：**

- 文本 / 图像编码器将提示词转换为嵌入向量；
- 去噪阶段通过数十次迭代逐步细化潜在状态；
- VAE 解码器将最终的干净潜在状态转换为像素输出。

**这三个阶段对并行度的需求天差地别。**

- 文本编码器本质上是单秩执行，多 GPU 几乎没有收益；
- VAE 解码器有特定的扩展曲线；
- :mdnice-bold-italic[【只有】计算密集的去噪阶段才能有效利用多 GPU 并行。]

如果给整个请求分配 4 个 GPU，那么编码和解码阶段就有 3 个 GPU 在空转。

**请求级别的异构性更加显著**。生成一张 512×512 图片与生成一段 720×1280、81 帧的视频，计算量相差两个数量级以上。小请求用多 GPU 会被通信开销吞噬收益，大请求不用多 GPU 则延迟不可接受。:mdnice-bold-italic[静态并行配置要么让小请求过度配置浪费资源，要么让大请求配置不足延长延迟。]

**系统级别的异构性则完全被现有系统忽视**。轻载时，给每个请求分配更多 GPU 可以最小化延迟；重载时，减少每个请求的并行度、增加并发数反而能提升整体吞吐和 SLO 达成率。:mdnice-bold-italic[但静态系统一旦启动就无法调整，只能在一种配置下硬扛所有负载场景。]

### 1.2 静态并行的两大致命缺陷

> 静态并行带来两个根本问题：长请求引发队头阻塞，短请求必须等待；资源利用率低下，轻量阶段无法有效利用多 GPU。

**图 1 直观展示了静态并行的困境**。当一个长请求占用全部 4 个 GPU 执行时，即使后续涌入大量短请求，它们也必须排队等待。这就是队头阻塞（Head-of-Line Blocking）—— 一个大请求堵死整个系统。

![文章插图](/articles/2026-06-14-gpu-gf-dit-dit-6-919ac55c/images/07.webp)

::: image-caption
图 1：弹性并行机制体现出调度策略的取舍关系。固定 4 路序列并行（SP4）能够保障长请求的延迟，但会让短请求持续等待；将并行度缩减为 1 路（SP1）可让短请求优先被处理，代价则是拉长长请求的执行耗时。
:::

**图 3 的微基准测试量化了这些损失**。不同阶段的扩展行为完全不同：去噪任务随 GPU 数量增加延迟持续下降，文本编码器基本保持单秩性能，VAE 解码器则有独特的扩展曲线。单一的请求级并行配置必然顾此失彼。

![文章插图](/articles/2026-06-14-gpu-gf-dit-dit-6-919ac55c/images/08.webp)

::: image-caption
图 3：DiT 弹性服务的实验动机验证。(a) 不同执行阶段展现出差异化的扩展特性与资源需求；(b) 并行带来的性能增益取决于请求的形态特征；(c) 不同负载场景适配不同的并行配置，说明不存在普适的最优并行方案。
:::

**请求形状也决定了最优并行度**。大分辨率、长视频的请求能从更多 GPU 中获益，而小请求增加 GPU 反而因为通信开销导致性能下降。即使是同一个模型、同一个执行阶段，最优并行配置也强烈依赖于请求形状。

::: block-1
:mdnice-bold-italic[没有任何单一的并行配置能够在所有阶段、所有请求、所有系统状态下都保持最优。这是静态并行架构的根本局限性，也是 GF-DiT 要解决的核心问题。]
:::

## 二、GF-DiT 的核心抽象：并行度作为可调度资源

### 2.1 轨迹任务：可重调度的执行单元

> DiT 有两个独特性质使其特别适合在线并行度适配：执行状态轻量，仅几 MB 到几十 MB 的潜在状态和嵌入；执行结构可预测，去噪轨迹在执行前就基本确定。

**GF-DiT 的第一个关键洞察是将 DiT 请求分解为独立可调度的轨迹任务**。编码、解码、每一步去噪都成为单独的任务。完成一个任务会产生语义完整的执行状态，可以安全地转移、恢复或在不同资源配置下继续执行。

这就创造了显式的重调度边界。每完成一个轨迹任务，运行时都可以重新考虑任务顺序、放置位置和 GPU 分配。**并行度不再是部署时的决定，而是运行时管理的资源。**

::: block-1
轨迹任务之间通过**逻辑数据对象** 进行通信。这些数据对象（也称 *artifact*）是任务间传递的中间数据载体，代表数据流的抽象单元。它们可以是条件特征、潜在状态、调度元数据、解码输出等。
:::

在抽象层面，数据对象仅描述**依赖关系** 和**语义角色** （例如“输入”“输出”“控制信号”），不规定具体存储格式或内存布局。

同一数据对象在实际执行时，会根据生产者与消费者的需要，动态具象为不同物理形式：

- 复制张量，如广播给多个消费者；
- 序列并行分片，如按序列维度切分；
- 模型特定元数据，如注意力掩码结构、KV缓存索引等。

这种设计解耦了逻辑语义与物理实现，兼顾表达力与执行灵活性，有两个深远影响：

- 首先，任务边界是显式的重调度点，GPU 分配可以随时改变。
- 其次，任务图和请求形状在准入时就基本已知，运行时可以在任务执行前估计剩余工作量并比较候选并行配置。

### 2.2 执行布局与可编程策略接口

> **GF-DiT 策略通过分配执行布局来调度就绪的轨迹任务**。执行布局包含有序的逻辑执行组和描述任务如何使用该组的并行规范。

在每个调度点，策略观察就绪任务、请求元数据、资源可用性、可选的截止时间或优先级，以及候选布局的成本估计。它返回形式为 (任务，执行布局) 的调度决策。

**这个接口让策略可以联合控制任务顺序、放置和并行度。**

- 策略可以优先处理短请求，为紧急请求分配更多秩，或者在下一个轨迹边界收缩正在运行的请求以接纳新工作。
- 策略只操作逻辑任务、数据对象和执行组，不需要构造通信器、调用模型阶段或规划张量传输。

这就是策略可编程性的核心：同一套运行时底层（substrate）能灵活支持多种调度策略——无论是追求高吞吐、低延迟、满足服务等级目标（SLO），还是用户自定义逻辑——全部通过统一的策略接口实现。例如，先来先服务（FCFS）、最短剩余时间优先（SRTF）、最早截止时间优先（EDF）等不同调度策略，都构建在同一个运行时之上，无需更换基础设施，仅通过策略配置即可切换行为。

### 2.3 系统整体架构

> GF-DiT 分为策略感知控制平面和轨迹执行平面。控制平面做调度决策，执行平面负责任务执行，两者通过异步事件解耦。

![文章插图](/articles/2026-06-14-gpu-gf-dit-dit-6-919ac55c/images/09.webp)

::: image-caption
图 4：GF-DiT 系统整体架构。接入的请求会被转换为轨迹任务图，由控制平面通过可编程策略接口完成调度，并按照动态执行布局下发至工作节点。无组集合通信与布局感知的数据迁移机制，保障动态布局在运行时可正常执行。
:::

图 4 展示了完整的系统架构。模型特定适配器将每个传入请求转换为轨迹任务和逻辑数据对象。控制平面维护图依赖、数据对象元数据、资源状态和策略可见的请求信息。当任务就绪或资源释放时，它调用策略并在分配的执行布局下分派选中的任务。

执行平面由 GPU 工作节点、模型执行器和通信运行时组成。工作节点异步执行任务并向控制平面报告进度，允许调度和 CPU 端准备与 GPU 执行重叠。无组通信支持动态执行组，布局感知数据对象迁移在策略跨任务边界改变放置或并行度时重建中间数据对象。

关键的设计选择是分派完成与设备完成分离。控制平面分派任务后，运行时解析逻辑执行组、准备输入、分配输出数据对象句柄、记录预期布局并将任务发送给参与的工作节点。一旦这个 CPU 端分派完成，控制平面就可以准备后继状态、规划后续迁移并发出独立工作，而 GPU 任务仍在运行。

设备执行单独跟踪。工作节点在任务执行周围记录 CUDA 事件，监控线程向控制平面报告执行开始和完成事件。这些事件标记设备完成、物化输出数据对象、释放工作节点资源、检测故障并用测量的任务持续时间校准运行时成本模型。

::: block-1
:mdnice-bold-italic[分派完成与设备完成的分离使调度与 GPU 执行异步。策略评估、依赖更新、迁移规划和其他 CPU 端工作与设备执行重叠，而不是在每个轨迹边界延长 GPU 关键路径。]
:::

## 三、无组通信：动态并行的技术基石

### 3.1 进程组通信的根本局限

> 在 8-GPU 服务器上预创建所有大小为 2 和 4 的组需要 **98 个进程组**。在 72-GPU 的 NVL 域上，同样的受限集合增长到 **1,031,346 个组**。穷尽预创建即使不考虑其他组大小也不切实际。

动态并行面临的主要挑战，源于传统集体通信库（如 NCCL、RCCL）所采用的进程组模型。这类库通过通信器或进程组来组织通信子集，每个进程组在创建时就固定了参与的进程（即“秩”），并为组内所有集体操作维护所需状态。这种设计天然适配静态模型并行场景——例如张量并行或序列并行配置，在服务器整个生命周期中保持不变、反复复用。

然而，策略可编程的扩散服务打破了这一前提。:mdnice-bold-italic[吞吐优先的策略，可能将多个请求动态调度到同一小组以提升并发；而截止时间敏感的策略，则可能临时扩大进程组，为紧急请求分配更多资源。更关键的是，单个请求在其执行过程中也可能切换组]：编码器阶段可能仅需单个秩；早期 DiT 计算可能扩展至更大的序列并行组；后期阶段则可能随负载波动而收缩组规模，甚至迁移至其他秩。因此，固定进程组的静态模型难以支撑这种细粒度、时变的通信需求。

显式的 `new_group` 调用本身极快（亚毫秒级返回），但首次在该子组上执行集体通信时，会触发“冷路径”初始化——耗时数百毫秒，并额外占用约 0.5 GB GPU 显存。后续在该子组上的集体操作则很快（即“热路径”）。**问题在于：动态策略每次为新选的秩集合创建子组，都需重复承担这一笔高昂的初始化开销和内存占用。**

::: block-1
这正是 GF-DiT 提出“无组通信”（Group-Free Collectives, GFC）的出发点。其核心思想是：在系统初始化阶段，一次性完成全局通信基础设施的设置；之后所有动态子组不再实际创建通信组，而是仅以轻量级元数据形式表示——既规避了重复初始化，又显著降低了内存开销。
:::

### 3.2 对称缓冲区与逻辑组

> 无组通信将通信状态与子组成员解耦。初始化时，GF-DiT 仅执行一次全局设置：为所有秩分配并注册对称通信缓冲区。这些缓冲区作为跨秩数据移动与同步的统一可寻址基础。

运行时，子组由逻辑组描述符表示，其中包含参与秩的有序列表、运行时组 ID，以及本地秩在该顺序中的位置。创建逻辑组纯属元数据操作：不构建通信器，不分配每组通信状态，也无需非成员加入。只要各参与秩从控制平面收到相同描述符，即可立即使用该逻辑组执行任务。

**在 GF-DiT 实现中，注册耗时约 60 微秒** ——仅含 CPU 端描述符记录与一次主机到设备的秩 ID 复制，无需通信器初始化或子组预热。**相较 NCCL 的 778 毫秒，提速达三个数量级。**

描述符为每个秩提供足够信息，以正确解析组内集体操作语义。例如，它明确本地秩索引（供序列并行 DiT 执行器使用），并将组内对等体映射至全局秩以支持通信。对称缓冲区则提供与这些对等体交换数据所需的存储空间与寻址能力。描述符与全局缓冲区协同，完全替代了传统动态执行中每个子组所需的进程组功能。

### 3.3 基于边的同步协议

> 逻辑组描述符与对称缓冲区支持子组内可寻址通信，但不保证集体操作的一致性。由于逻辑组允许重叠，同一对进程（秩）可能在不同时刻属于不同组并参与不同集体操作。因此，运行时系统必须确保：当某进程为某个集体操作写入同步信号时，其通信对端能准确识别该信号所属的具体集体实例。

![文章插图](/articles/2026-06-14-gpu-gf-dit-dit-6-919ac55c/images/11.webp)

::: image-caption
图 5：动态重叠通信组的信号状态设计方案。(a) 为每个逻辑组分配独立信号槽可避免冲突，但会产生组合爆炸式的每组状态开销；(b) 多组共享信号槽会导致连续重叠的集合通信发生信号冲突；(c) GF-DiT 为每个 GPU 节点链路分配双缓冲相位状态，让共享链路在不同组中统一切换信号槽，无需为每个通信组单独分配状态。
:::

GF-DiT 最核心的技术创新是**基于边的翻转一致性协议**。图 5 展示了三种设计思路的对比：

- **为每个逻辑组单独分配槽位**：逻辑正确，但槽位数量随组合增长而急剧膨胀，导致开销过大；
- **跨逻辑组共享槽位**：结构紧凑、资源高效，但缺乏一致性保障，存在安全隐患；
- **GF-DiT 的方案**：在每条有序秩边（ordered rank edge）上附加一个相位位（phase bit），既保持槽位复用的紧凑性，又通过边级翻转约束确保逻辑一致性与安全性。

该设计在正确性、安全性与资源效率之间取得了关键平衡。

![文章插图](/articles/2026-06-14-gpu-gf-dit-dit-6-919ac55c/images/12.webp)

::: image-caption
算法 1：无组集合通信（GFC）的单链路翻转同步协议。该算法是 GFC 实现重叠通信组可靠同步的核心逻辑，打破了传统以通信组为单位的同步模式，转而基于两两 GPU 链路做状态管理。每条链路配备双信号槽与 1 位相位标记，通过相位交替翻转避免信号被覆盖，结合控制平面的有序任务提交规则，保证全网通信时序一致。算法无需为动态创建的通信组分配独立同步状态，极大削减资源开销；同时借助通信令牌区分不同组的请求，杜绝信号混淆与分布式死锁。整体协议逻辑轻量、执行高效，在保障通信正确性的前提下，支撑 GF-DiT 高频次、动态切换执行组的核心运行模式。
:::

算法 1 详细描述了该协议。每个有序秩对包含两个信号槽：一个用于接收对等体发来的消息（传入槽），另一个用于向对等体发送响应（互惠槽）。槽的选择由本地序列计数器的奇偶性决定——例如，偶数序号用槽 A，奇数序号用槽 B。由于控制平面在两端以完全相同的顺序提交共享对的集体实例，双方自然选中匹配的槽，无需额外同步槽状态。

该协议无需独立的确认阶段。每个秩在有序通信流上依次提交边实例：实例 $N$ 使用某个槽，而该槽要到实例 $N+2$ 才会再次被使用。由于秩必须先收到 $N+1$ 的返回，才能提交 $N+2$；而该返回的前提，是对等体已成功消费了实例 $N$ 的令牌。因此，仅靠双缓冲机制，就可确保令牌不会在对等体读取前被覆盖。

::: block-1
:mdnice-bold-italic[基于边的同步是 GF-DiT 最核心的技术突破。它让任意 GPU 子集可以在 60 微秒内形成执行组，而不需要数百毫秒的通信器初始化。没有这个技术，动态并行调度就只是理论上的美好设想。]
:::

## 四、运行时实现与策略编程

### 4.1 模型适配器与数据对象迁移

> GF-DiT 将模型专属逻辑封装在轻量级适配器接口之后。该适配器把扩散流水线拆解为三个运行时组件：请求转换器、任务执行器和数据对象编解码器。

请求转换器控制调度可见的任务粒度。它为文本编码、VAE 解码等流水线阶段生成独立任务，并为每个去噪步骤也生成一个任务。每个任务执行器接收任务描述与执行布局，调用对应模型阶段；当并行需求涉及集体通信时，自动调用通信运行时。

数据对象编解码器桥接模型特有的张量结构与位置无关的任务图。对每个逻辑数据对象，它识别哪些字段需复制、哪些需分片、哪些仅为元数据，并报告该对象在指定布局下的全局形状及各设备（rank）上的局部切片。运行时据此判断数据能否直用，或是否需迁移。

这一设计使调度策略完全脱离模型内部细节。策略仅需感知就绪任务、请求元数据、资源状态与成本估算，无需了解张量如何分片、调度器状态如何序列化，或模型阶段如何触发集体操作。新增扩散流水线时，只需实现对应适配器，无需修改调度策略，也无需将模型专属迁移逻辑硬编码进调度器。

> 当相邻轨迹任务采用不同执行布局时，运行时需重建逻辑数据对象，且迁移决策对调度策略完全透明。**GF-DiT 通过三步从生产者与消费者的数据视图中推导出所需数据传输：布局交换、迁移规划、分布式执行。**

- **布局交换**：源组领导者向所有参与的秩收集各迁移数据对象的源视图与目标视图。适配器的编解码器标明每个字段的处理方式（复制、分片或仅传递元数据）；对张量字段，还提供其在各布局下的全局形状及每秩切片信息。
- **迁移规划**：领导者基于源视图与目标视图生成迁移计划。对分片张量字段，规划器计算每个源秩已持有切片与每个目标秩所需切片的交集；每个非空交集生成一条传输条目，含源秩、目标秩、源张量范围、目标张量范围及对应字节数。
- **分布式执行**：领导者将完整计划分发至所有参与秩。各秩提取自身需执行的操作，打包本地张量范围，通过点对点通信与对应秩交换数据，并将接收数据按目标布局写入消费者数据对象。此后，消费者即可按其分配的布局正常读取数据。

### 4.2 三种代表性调度策略

> GF-DiT 将调度决策上移至策略层。策略根据就绪任务、请求元数据、资源可用性及成本预估，为每个任务输出排序顺序与执行布局。

GF-DiT 实现了三种典型策略，体现策略可编程的灵活性：

- **FCFS + 工作负载感知分组**：集群划分为多个工作节点组，请求按先到先服务（FCFS）顺序处理；任务就绪时，被分配至当前排队负载最低的可行组。该策略侧重吞吐，排序简单，负载均衡由组间独立运行实现。
- **SRTF + 每秩本地队列**：请求先按预估排队负载分配到可行的秩（rank），随后各秩在本地按最短剩余轨迹时间（SRTF）调度就绪任务——依据请求形状、轨迹位置及任务成本预估。相比 FCFS，SRTF 利用更稳定的扩散成本预测降低平均延迟，且排序完全在本地完成。
- **EDF + 最优拟合并行度**：面向 SLO 场景，按最早截止时间（EDF）排序就绪任务；通过成本模型评估多种并行布局，选择满足截止时间的最小并行配置；若预测可能超时，策略可在下一轨迹边界自动扩容分组。整个过程无需修改执行器，实现 SLO 感知的动态调度。

这些策略设计简洁，仅在任务排序与布局选择上存在差异；依赖追踪、异步分发、动态组通信与数据迁移均由底层运行时统一处理。

### 4.3 模拟器与策略探索

> 相同的抽象机制也支持离线策略探索。最优调度策略取决于具体工作负载构成、请求特征、服务目标以及可用资源规模，因此实际部署前通常需对比多个策略效果。

模拟器通过成本模型模拟任务执行，替代真实工作节点，但仍完整保留任务就绪判断、依赖更新、资源分配及策略调用等关键调度行为。其成本模型依据模型类型、任务类别、请求特征和并行配置，查表填充分析所得的任务延迟。

由于模拟器与在线运行时共用同一套策略接口，离线筛选出的策略可直接部署，无需修改决策逻辑。

- 在模拟中，调度器的分派决策触发成本模型生成“完成事件”；
- 在线运行时，同一决策由 GPU 工作节点实际执行，并上报真实完成事件。

因此，模拟器并非独立的调度模型，而是复用相同调度轨迹抽象的替代执行后端。

## 五、实验评估：6 倍吞吐量是如何炼成的

EDF 通过按截止时间对轨迹任务排序，并基于预估完成时间动态选择并行度，从而提升了截止时间达成率——这比固定执行顺序和静态并行配置更灵活有效。

::: block-1
**延迟表现说明：不存在一种策略能在所有目标上全面占优。** Legacy 和 SRTF-SPmax 采用大执行组，可缩短单个大任务的服务时间，但在混合工作负载下会降低并发度、加剧排队。因此，小并行度策略反而在延迟上更具优势：SRTF-SP1 在多个 Qwen-Image 场景中实现了最低平均延迟；FCFS-SP1 则在 A100 上的 Qwen-Image 短工作负载中取得最低 P95 延迟。
:::

此外，大组策略引发的并发下降，还导致 A100 Qwen-Image 场景出现容量崩溃。面对前台突发负载，Legacy 和 SRTF-SPmax 仅完成 **37% 和 39% 的提交请求**，而其他策略几乎全部完成。这些失败源于请求长期滞留在串行化的 SP8 队列中，最终超过客户端超时限制。

:::

## 六、总结与展望

> GF-DiT 代表了生成式 AI 服务架构的范式转移。它不是又一个 DiT 推理优化，而是**从根本上重新思考了我们应该如何在多 GPU 系统上服务扩散模型。**

论文的核心贡献有四个层面。

- 第一，提出**将并行度作为第一类可调度资源的新抽象**，这是自适应 DiT 服务的概念基础。
- 第二，设计 GF-DiT 运行时，**通过异步执行和可重调度轨迹任务实现在线 GPU 重新分配。**
- 第三，**发明无组通信技术**，通过消除昂贵的通信器构造使动态执行组形成变得实用。
- 第四，在 vLLM-Omni 中完整实现并进行了全面评估，证明相比静态并行执行有数量级的性能改进。

::: block-1
更广泛地说，GF-DiT 预示着生成式 AI 服务的未来方向。:mdnice-bold-italic[今天的 LLM 和 DiT 服务系统大多仍在使用静态资源分配 —— 固定的张量并行度、固定的流水线深度、固定的批处理大小。但就像操作系统从早期的单任务批处理演进到多任务分时系统一样，AI 服务系统也必须演进到运行时管理的弹性资源分配。]
:::

GF-DiT 选择 DiT 作为起点不是偶然的。DiT 的轻量执行状态和可预测执行结构使其特别适合这种范式。但同样的原则 —— 将并行度作为可调度资源、动态执行组、策略可编程运行时 —— 最终将应用于所有生成式 AI 工作负载。

这就是为什么 GF-DiT 不仅仅是一篇优秀的系统论文。:mdnice-bold-italic[它为整个 AI Infra 领域指明了方向：未来的生成式 AI 服务系统应该超越静态资源分配，将运行时管理的并行性作为基本的系统抽象。]

> 从 778 毫秒到 60 微秒，从静态配置到动态调度，**从 1 倍到 6 倍吞吐** —— 这就是技术革命的样子。而这，仅仅是开始。
