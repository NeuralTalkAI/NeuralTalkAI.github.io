## 一、被忽视的另一半：Agent 系统里，模型之外还有一副框架

> 一个 Agent 系统由两个部分组成：负责思考的语言模型，以及把模型包裹起来、替它安排一切的那副框架。过去两年，几乎所有的聚光灯都打在前者身上，后者一直被当成透明的管道。

论文把这副被忽视的框架称为 harness，这个词原意是马具、挽具，套在马身上、把马的力量传导到车上的那套装备。在 Agent 语境下，harness 指的是模型之外的一切 scaffolding：系统提示词、用户指令、可用的工具列表与工具描述、记忆与上下文管理、防死循环的检查脚本，乃至把多个模型调用串起来的编排逻辑。模型负责输出 token，harness 决定模型在什么信息下输出、输出之后触发什么动作、出错之后如何被纠回正轨。

理解 harness 价值的最佳入口是论文里的预算审批 Agent 案例。这个 Agent 的职责是处理公司各部门的设备采购申请：收集申请、查询价格与预算政策、给每位经理回复报价总额、对超支部门按公司削减政策砍单，并把结果写进工作区的文件里。**当前沿模型 gemini-3.1-pro 套着一副通用框架上场时，它能凭一己之力推断出整套流程，拿到 97.3%的准确率**。:mdnice-bold-italic[而 27B 规模的小模型 gemma-4-26b-a4b 套着同一副框架，准确率只有 75%：它不知道该先干什么后干什么，面对一堆原始 MCP 工具频频选错，还会对着同一个联系人反复发送同一条消息，陷入死循环。]

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/03.webp)

::: image-caption
图 1：小模型被天真地换进为前沿大模型设计的Agent框架时往往表现糟糕。适配后的框架可以提供详细的执行计划来引导工作流、用精简的工具集避免调用错误、用监控钩子避免死循环，这些适配让小模型以大模型8%的成本达到与其持平的水平。这张图是全文的题眼：纵轴是性能，横轴是成本，通用框架下的小模型落在"低成本、低性能"象限，大模型落在"高成本、高性能"象限，而适配后的框架把小模型平移到了"低成本、高性能"的理想区域。注意图中框架的三处修改——预设计划、过滤工具、监控钩子——恰好对应后文三类适配策略，后文图4会给出这套框架的真实代码。
:::

这个案例里有一个值得咀嚼的细节：**小模型缺的并非"智商"，缺的是流程知识、工具使用纪律和防错机制**。这三样东西恰好都可以由框架提供。:mdnice-bold-italic[一旦框架把"先做什么后做什么"写成明确步骤，把用不上的工具藏起来，再加一个检测重复发送的钩子，小模型的短板就被系统性地补齐了]。论文用一句话概括这种思路：**前沿模型足够强，套通用框架也能跑好；小模型的能力缺口更常见，因此专门的框架适配对小模型格外值钱。**

::: block-1
模型决定 Agent 能力的上限，框架决定这个上限能被兑现多少。把 Agent 的失败全部归咎于模型，等于放弃了系统里另一半可优化的空间。
:::

## 二、先诊断，再开方：五类失败模式与三类适配策略

> **要给框架动手术，先得搞清楚病人到底得了什么病。论文的第一个方法论贡献，是建立了一张从"失败模式"到"适配策略"的映射表**，让框架优化从玄学变成有章可循的工程。

与 MAST、AgentErrorTaxonomy 等前人按系统模块归因的失败分类不同，这张表按模型能力来索引失败，因为能力缺口才能直接对应到补救手段。论文调研了近期模型卡和 Agent 基准，归纳出五类失败模式。

| 失败类型 | 描述 |
| --- | --- |
| 工具使用失败 | 选错工具、工具调用格式畸形、工具用法错误，在工具集庞大、工具 schema 复杂、需要组合多个工具时尤其高发。 |
| 指令遵循失败 | 违反系统或用户指令，包括任务要求、输出格式、工作流规范，指令越长越复杂越容易翻车。 |
| 知识失败 | 缺少完成任务所需的领域知识、环境知识或常识假设。真实世界的指令往往是欠规范的，Agent 要靠预训练知识或环境交互自行补全缺失的细节，补不上就会调错工具、误解约束。 |
| 长上下文失败 | 在长轨迹中检索和使用信息的能力退化，表现为忘记早先的指令、重复已经失败过的动作、忽略关键观测、被无关上下文带偏。 |
| 规划与推理失败 | 无法把高层目标拆解成子目标、无法选出有效的下一步动作、拿到新观测后不会修正计划，典型症状包括过早给出答案、低效探索、不懂回退。 |

> 针对这五类失败，论文把文献和主流框架（如 Claude Code、Codex）里反复出现的**适配手段归为三大类别。**

- **上下文适配**：改变呈现给模型的信息，包括添加上下文（给示例、强化指令、把隐性知识显式化、提供现成计划）和管理上下文（渐进式披露、外置存储、摘要压缩、剪除无关观测、拆给多个 Agent 分担）。
- **工具适配**：重塑 Agent 的动作空间，包括创建工具（把反复出现的复杂工具序列包装成简单接口，把领域知识和计划编码进工具实现）和管理工具（过滤无关工具、裁剪工具 schema 让工具更直观）。
- **智能体循环适配**：改变模型推理外围的控制逻辑，包括插桩代码（在特定工具调用前后挂载确定性检查，即 hooks，安全领域也称符号护栏）和编排多智能体（主从、对等、独立汇合等拓扑）。

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/04.webp)

::: image-caption
图 2：Agent失败模式与Harness适配的映射。当模型能力低于任务要求时，这种错配会在轨迹中表现为Agent失败；这些缺口可以用框架适配来弥合，论文把适配归为三类：适配上下文、适配工具、适配智能体循环。图左侧的五种色块对应五类失败模式，右侧的A1/A2、T1/T2、L1/L2分别对应添加上下文、管理上下文、创建工具、管理工具、插桩代码、编排智能体六条策略路径，连线标明哪条策略治哪种失败。这张图的实用价值在于它是一张工程速查表：线上Agent出了问题，先按症状归到左侧某一类，再沿连线找右侧的候选疗法，这正是后文元智能体自动诊断时遵循的决策骨架。
:::

**论文同时诚实地指出了适配的代价，没有任何一种策略是免费的午餐**。加上下文会加重长上下文负担和指令遵循压力；管理上下文会增加模型的探索负担，可能诱发规划失败；造太多工具会让工具选择重新变难；编排多智能体则推高推理成本和延迟。:mdnice-bold-italic[所以框架适配不存在一劳永逸的银弹，正确的姿势是针对具体任务、具体模型的具体失败，做有针对性的取舍]。**这个判断直接催生了论文的下一步：既然人工试错又慢又贵，那就让机器来搜索。**

::: block-1
失败模式按能力归因、适配策略按框架部件归类，这张映射表把"怎么给 Agent 治病"从经验玄学变成了可检索、可组合、可自动化的工程决策。
:::

## 三、元智能体优化器：把框架设计变成可自动搜索的问题

> 映射表给出了疗法目录，但从目录里挑出对的那副药，依然是个巨大的搜索问题。论文引用强化学习之父 Sutton 的"苦涩教训"：**依赖人类知识的方法终究会输给利用搜索与学习的通用方法，框架设计也应当如此。**

手工适配框架的痛点有三个：失败模式常常交织在一起（比如工具用错会连带上下文膨胀），每种失败通常有多个候选疗法，而且模型每升级一代框架就可能要重做一遍。**CMU 团队的答案是造一个元智能体**，由前沿模型 gemini-3.1-pro 扮演"框架工程师"，自动完成"跑任务、看轨迹、改框架"的闭环。

### 3.1 搜索空间：给元智能体一套可编辑的零件

> 完全开放式的框架设计空间对自动搜索来说太危险，论文的做法是基于开源框架 software-agent-sdk 的 API，给元智能体提供一组结构化的可编辑零件：

| 类别 | 内容 |
| --- | --- |
| 上下文 | 系统提示词（任务指令、示例）、技能（skills）、按需追加的动态上下文 |
| 工具 | 基础工具（文件编辑器、bash、浏览器）、用类定义的自定义工具、自定义脚本 |
| 钩子 | 基于工具使用触发的自定义脚本 |
| 上下文管理 | 外部文件系统、上下文压缩器 |
| 子智能体 | 拥有独立上下文的自定义 Agent |

这个空间既覆盖了第二章里的大部分适配策略，又保持了足够强的结构性，让元智能体的每次修改都是合法、可执行、可评估的代码变更。

### 3.2 优化循环：采样、诊断、验证的三步迭代

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/05.webp)

::: image-caption
图 3：自动化框架优化循环概览。整个系统维护一个"框架池"，循环执行三步：第一步从池中采样一个框架并在训练实例批次上评估，记录完整轨迹；第二步由内循环的元智能体结合轨迹、当前框架代码、搜索记忆和设计空间文档诊断失败并提出新框架，新框架先过一个廉价的健全性检查，不通过就让元智能体修复重试；第三步在同一批次上验证新框架，有改进就在验证集上完整评估并更新框架池。只要预算没花完就继续迭代。值得注意的是"搜索记忆"这个设计：它记录过往提案及其效果，防止元智能体反复尝试同一种无效修复，这个细节在第六章的经验总结里被证明至关重要。
:::

采样环节采用了 GEPA 风格的遗传搜索：**从帕累托前沿上挑候选，即被选中的框架至少在某个训练实例上是最优的**。这种选择策略保证了池子里的框架各有所长，不会被单一平均分指标早早同质化。每个任务-模型组合的优化预算是 20 美元，覆盖元智能体分析、任务 Agent 运行和候选框架评估三类开销，作者在预实验中观察到超过这个预算后优化趋于饱和。每个组合独立跑 3 次搜索，保留验证分最高的框架。

### 3.3 一个真实的优化成品：23 次迭代后的预算审批框架

> 下图 4 里藏着这篇论文最锋利的工程观点：防死循环这种关键可靠性保障，用一段几十行的确定性 Python 代码就解决了，完全不需要模型具备"意识到自己在循环"这种元认知能力。:mdnice-bold-italic[框架把模型最不擅长的工作（长程规划、工具甄别、自我纠错）接了过去，模型只需要在每一步做局部、受限的决策，这恰好是小模型能够胜任的颗粒度。]

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/06.webp)

::: image-caption
图 4：元智能体为预算审批任务找到的简化版框架代码。上半部分是通用框架：一句空泛的系统提示词加6个原始MCP工具，小模型必须自己规划全流程、自己选对工具，准确率75%，远低于大模型的97.3%。下半部分是优化后的框架：系统提示词被改写成逐步执行的工作流，工具集从6个过滤到5个，用正则屏蔽了诱导死循环的get_conversation_history工具，并挂载了anti_loop_hook.py脚本，一旦检测到向同一收件人重复发送完全相同的消息就拒绝执行并返回警告。中间展示了钩子的核心代码：一个纯确定性的Python判断，不依赖任何模型。这个案例完美诠释了"把脆弱环节从模型手里拿出来，交给提示词、过滤器和运行时检查"的设计哲学，23次迭代后小模型追平大模型，成本只有8%。
:::

::: block-1
框架优化的本质是一个预算受限的程序搜索问题：:mdnice-highlight[结构化的搜索空间让每次修改合法可评，遗传式采样保持候选多样性，而前沿模型扮演的元智能体负责把失败证据翻译成精准的代码修复。]
:::

## 四、实验设计：七个业务任务、三个小模型、一个前沿基线

> 作者搭建了一套任务套件，覆盖了企业里最常见的例行工作流，并且在任务多样性上做了梯度设计，为后面"什么时候适配有效"的追问埋下伏笔。

- 七个任务分别是：考勤审计（核对考勤与工资记录并产出汇总表）、预算审批（按预算约束审查采购申请）、库存告警（监控库存水位并按预定义条件告警）、异常检测（分析 IoT 时序数据识别异常）、Playwright 测试生成（为静态网站编写端到端测试并调试通过）、网站管理（通过浏览器完成购物网站后台管理操作）、代码重构（按用户指令重构代码仓库）。
- 这些实例取自 TheAgentCompany、LOCA-Bench、WebGenBench、WebArena、RefactorBench 等公开基准，全部带有客观可验证的评估标准，比如与标准答案比对、运行生成的测试、检查重构后代码的 AST。

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/07.webp)

::: image-caption
表 1：作者整理的一组多样化的业务相关Agent任务，共七个，每个任务都建立在结果可验证的现有基准之上。表中N为实例数，Common workflow是各实例共享的典型流程，Evaluation criteria是评估方式，Task creation process说明实例来源。这张表的隐藏信息在Common workflow一列：前四个任务的流程高度固定（收集、处理、输出三步走），属于低多样性任务；而代码重构、网站管理的流程随实例剧烈变化，属于高多样性任务。正是这个梯度让第五章的RQ2分析成为可能——读者可以留意，后文适配收益最大的恰好是流程最死的任务。
:::

模型方面，三个小模型分别是 qwen3-coder-30b-a3b、ministral-3-8b 和 gemma-4-26b-a4b，覆盖了 MoE 和稠密架构、8B 到 30B 的参数量级，基线是前沿模型 gemini-3.1-pro-preview 套通用框架。成本按官方 API 定价计算，gemini 与 gemma 用 Google Vertex AI 价格，qwen 与 ministral 用 AWS Bedrock 价格。每个任务按 20/20/60 划分训练、验证、测试集，每种配置跑 3 次取平均。

**为了量化"任务多样性"，论文设计了一个巧妙的操作化指标：收集大模型在同一任务不同实例上的运行轨迹，提取工具调用序列，计算序列之间的平均成对归一化 Levenshtein 距离**。:mdnice-bold-italic[Levenshtein 距离是编辑距离的学名，衡量把一个字符串改成另一个至少需要多少次插入、删除、替换操作]。把这个距离归一化后，值越接近 0，说明各实例的工作流越雷同，任务越"例行公事"；值越大，说明每个实例需要不同的工具和顺序，任务越"千人千面"。此外作者还构造了可控多样性实验：为考勤和预算两个任务准备多个流程模板（如预算任务的总额追踪、剩余额度计算、紧急备用金处理、政策审批四种模板），通过调整数据集里混入的模板数量来精确控制多样性。

## 五、实验结果：4%的成本，89.7%的性能

> 四个研究问题串起了整组实验：适配能否抹平大小模型的差距、任务多样性如何影响适配效果、模型基础能力如何影响适配效果、以及成功的适配到底用了哪些策略。答案逐层展开：

### 5.1 RQ1：适配后的小模型能追平大模型吗

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/08.webp)

::: image-caption
表 2：各评估设置下的性能与推理成本汇总。每个单元格报告准确率（上）、单实例平均成本（中，美元）、平均端到端延迟（下），绿色、白色、红色分别标注最好、一般、较差的表现。逐行读这张表可以发现三个层次的信息：其一，通用框架下三个小模型的平均准确率分别只有31.4%、26.9%、9.5%，全面崩盘，印证"直接换模型必死"；其二，优化框架后gemma-4-26b-a4b的平均准确率飙到80.2%，在预算审批、异常检测、Playwright测试三个任务上反超了大模型的97.3%、98.9%、85.7%（对应99.4%、98.1%、98.3%里有两项更高），且单实例成本从0.043美元涨到0.071美元，仍不到大模型1.735美元的零头；其三，最弱的ministral-3-8b在库存告警和异常检测上适配后仍是0分，提前预告了RQ3"能力下限"的结论。
:::

汇总来看，**21 组任务-小模型组合中 16 组获得显著提升，7 组完全抹平与大模型的差距**。:mdnice-bold-italic[最佳的 gemma-4-26b-a4b 恢复大模型 89.7%的性能，成本仅为 4%，延迟还下降 25%。] 更妙的是经济账：每个任务的 20 美元一次性优化成本，按单次运行的成本节省折算，平均跑 13 次就能回本，之后每次运行都是净赚。对于日均调用成千上万的业务场景，这是一笔稳赚不赔的投资。

### 5.2 RQ2：任务越“标准化”，框架适配效果越显著

> 分析表明：任务越具重复性、流程越统一，优化后的框架提升越明显；反之，任务越多样、差异越显著，适配效果越弱。

跨任务统计显示，任务多样性（以工具序列编辑距离衡量）与优化后性能呈极强负相关（Spearman 等级相关系数 $\rho = -0.96$）。该系数不依赖具体数值，只反映排序一致性——$\rho \approx -1$ 意味着：**多样性最高的任务，其优化后性能几乎最低；多样性最低的任务，性能提升最显著。**

因果验证进一步支持该结论：当数据集中混入的工作流模板从 3 个增至 20 个，框架优化后的平均性能从 89.1% 降至 68.0%，下降 21.1 个百分点。

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/09.webp)

::: image-caption
图 5：任务越多样，越难优化。左图横轴为任务多样性（工具序列编辑距离），纵轴为平均优化后得分（不同模型均值）；右图横轴为混入的任务模板数量，纵轴为各任务平均性能。两图均呈明显下降趋势，左图揭示强相关性，右图通过控制变量验证因果性。核心机理在于：框架依赖共性模式压缩知识。当任务高度相似（如考勤审计），错误集中于缺知识或格式错误，单一框架即可精准覆盖；而高度异构任务（如跨仓库代码重构），每个实例语境与需求各异，强行统一建模反而导致框架臃肿、指令理解失准，尤其不利于轻量模型。
:::

### 5.3 RQ3：模型底子越好，适配收益越大

![文章插图](/articles/2026-07-24-better-harnesses-smaller-llm-cmu-620569ea/images/10.webp)

::: image-caption
图 6：能力越弱的模型越难优化。横轴是Artificial Analysis智能指数（模型综合能力基准分），纵轴是平均性能，每个模型有两根柱子分别对应基础框架与优化框架。图中趋势一目了然：三个小模型加一个大模型，能力越强，基础性能越高，适配后的绝对水平也越高。更关键的是增量对比：较强的gemma-4-26b-a4b适配后提升48.8个百分点，较弱的ministral-3-8b只提升15.5个百分点。这说明框架能接走的只是"可外化"的任务难度——流程、知识、纪律；而任务内核里那些必须现场推理的部分，比如Playwright测试要求看懂HTML并写出能跑的测试代码、库存告警要求长上下文中不丢信息，仍然压在模型肩上。框架是杠杆，但杠杆需要一个支点，这个支点就是模型的基础能力。
:::

### 5.4 RQ4：成功适配究竟在解决哪些问题？

> 分析所有优化后的框架发现，绝大多数成功适配（81%）聚焦于两大核心短板：**指令理解偏差** （模型没听懂任务要求）和**知识缺失** （模型缺乏领域或任务相关常识）；其次常见的是**工具调用失败** （62%）和**长上下文处理失效** （33%）。在应对策略上，最普遍的做法是**增强系统提示中的上下文信息** （86%），其次是**开发新工具** （43%）和**精简/重构已有工具集** （29%）。

以 gemma-4-26b-a4b 在异常检测任务中的最优框架为例，其优化逻辑清晰务实：

- 新建 `query_mock_bigquery` 工具，绕过默认 MCP 工具引发的长上下文瓶颈；
- 将原始 40 余个 MCP 工具大幅压缩至 7 个，降低调用复杂度；
- 将实际环境中的表命名规则直接写入系统提示词，让模型“一眼看懂”数据结构。

一个值得注意的现象是：**所有成功案例均未采用子智能体编排**。作者认为，当前中小规模模型尚不具备稳定调度与协同多个子 Agent 的能力。此外，适配方案高度“模型专属”：ministral-3-8b 常在文件编辑工具上出错，qwen3-coder-30b-a3b 则偶尔将 JSON 工具调用误写为裸 XML——不同模型的“失败特征”各不相同，换模型即需重新优化。

::: block-1
整体来看，适配能**平均恢复约 90% 的原始性能，同时降低 96% 的推理成本**；但其效果有明确前提：任务流程需高度重复、基座模型本身能力扎实，且每次更换模型都必须重新定制适配方案——它不是“一次配置，处处通用”，而是“一模一策”的精细化调优。
:::

## 六、优化器的经验：20 美元的预算该花在哪里

> 作者还分享了两条打造框架优化器的实战经验，对想复现这套方法的团队而言，这可能是全文工程密度最高的部分。

先把预算问题形式化。总预算 $B$ 的消耗可以写成：

$$
B = \sum_{t=1}^{T} \left( b^{\text{analyze}}_t + b^{\text{evaluate}}_t \right)
$$

其中 $T$ 是优化迭代的总轮数，$b^{\text{analyze}}_t$ 是第 $t$ 轮花在"分析失败"上的钱（元智能体读轨迹、写诊断、改代码的推理开销），$b^{\text{evaluate}}_t$ 是第 $t$ 轮花在"评估候选"上的钱（让任务 Agent 套着新框架跑训练批次的推理开销）。**预算固定时，每一块钱都要在三件事之间分配：分析得更深、评估得更广、迭代得更多**。论文的总预算是每次优化 20 美元，主实验 21 个组合共 1260 美元。

### 6.1 经验一：把钱优先砸在诊断质量上。

> 优化器的瓶颈在诊断而非评估，候选框架再好也不如提案本身好。两个具体做法：

- **给元智能体看保真度最高的失败证据**，作者早期把结构化 JSON 轨迹转成人类友好的 Markdown，反而丢掉了关键细节，直接喂原始 JSON 效果更好，因为前沿元智能体自己有能力操作和检查冗长的结构化数据；
- **元智能体的模型不能省**，把 gemini-3.1-pro 换成更便宜的 gemini-3-flash，省下的钱虽然能多跑几轮迭代，但低质量诊断造成的损失远超多出来的探索收益。

有趣的是，给元智能体塞大模型成功轨迹示范、或者人工编写的"什么失败配什么疗法"启发式，都没有稳定收益——拿到忠实的失败证据和可编辑的框架之后，强元智能体自己就能推断出对症的修复。

### 6.2 经验二：探索的质量与多样性优先于数量。

> Agent 评估太贵，框架优化的搜索步数远少于单轮提示词优化，每一轮迭代都金贵。两个做法被验证有效：

- 维护搜索记忆，记录过往编辑及其结果，否则元智能体会反复"重新发现"类似的修复，白白烧掉预算；
- 把同样的预算拆成多次独立搜索，比一次长跑更能覆盖设计空间的不同区域，提高至少一次撞中强力适配的概率。

::: block-1
预算分配的黄金法则是"**诊断优先、多样其次、数量垫底** "：:mdnice-highlight[最好的元智能体配最保真的失败证据，再辅以搜索记忆和多次独立搜索，20 美元就能榨出最大价值。]
:::

## 总结：工作启示与这项工作的边界

> 一篇好的实证研究，价值不止于"我们做到了"，更在于它改变了从业者接下来的决策。论文按三类读者分别给出了行动建议，也坦诚划定了结论的适用边界。

| 角色 | 建议 |
| --- | --- |
| Agent 开发者 | 例行公事型的业务任务不应直接交由前沿大模型处理；应先整理任务实例与客观评估标准，再用一批小模型候选在自动框架中进行适配测试。选型时优先参考基准分（与适配后性能正相关），小 MoE 模型（如 gemma-4-26b-a4b）常以极低推理成本提供足够能力，是性价比最优选择。 |
| 模型开发者 | 训练实用小模型不能仅追求基准分提升，还需重视“框架兼容性”——确保模型在各类提示词脚手架与工具脚手架下稳定运行。这要求训练阶段即引入多样化环境、提示格式与工具配置，增强泛化鲁棒性。 |
| 研究者 | 自动框架优化尚处早期，多个方向亟待探索：更细粒度的任务画像（基于失败模式预测适配收益）、混合框架设计（对实例聚类后为各簇定制专用框架，并引入路由器动态分流）、以及面向任务分布漂移的在线监控与框架版本管理机制。 |

> **边界同样要写清楚**。实验的任务都有清晰的成功标准和干净的环境，真实部署的脏数据、脏接口会打折扣；Agent 运行和优化过程本身高度随机，尽管有多轮重复缓解；优化依赖闭源前沿 API，API 一旦变更或下线，精确复现会变难。:mdnice-bold-italic[此外 7 组任务-模型组合抹平差距不代表全部场景，多样性高的开放性任务（如开放式编程）目前仍是大模型的主场。]

从 AI Infra 的视角看，这项工作的深远意义在于它把"降本"的主战场从模型侧掰开了一道口子。过去行业的降本叙事围绕着量化、蒸馏、KV Cache、投机解码这些模型内部的技术打转，而这篇论文证明：**系统侧的框架层同样蕴藏着数量级的成本优化空间，而且可以用自动化搜索持续挖掘。当"为每个任务、每个模型自动定制框架"成为标准动作，Agent 部署的成本结构将被重新书写。**

::: block-1
这篇文章的核心启示可以浓缩成一句话：:mdnice-highlight[在例行业务场景里，省钱的关键不在于找到更聪明的小模型，在于给够用的小模型配一副为它量身定做的框架——并且这件事已经可以交给元智能体自动完成。]
:::
