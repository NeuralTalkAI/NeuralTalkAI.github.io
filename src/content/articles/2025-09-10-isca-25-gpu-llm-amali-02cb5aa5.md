## 关键问题

### 问题1. AMALI 模型通过指令修饰符和吞吐量来建模张量核心性能，显著降低了预测误差，但这种基于特定指令（如 HMMA）和微基准测试的建模方式，在面对未来 LLM 推理中可能出现的新型张量核心指令集或动态变化的计算模式（如混合精度计算比例调整）时，是否仍能保持高精度？其泛化能力的边界在哪里？

关于 AMALI 对新型张量核心指令集或动态计算模式的泛化能力，作者提到其核心**依赖于通过微基准测试捕捉张量核心的吞吐量** （如 FMAs/周期）及**指令修饰符** （如 tensor size、数据类型）**的影响**。

在 H100 的验证中，AMALI 能准确预测张量核心吞吐量从 256 FMAs/周期提升至 512 FMAs/周期后的性能变化，说明其**对同架构下指令集扩展有一定适应性**。

但:mdnice-bold-italic[作者未提及对完全新型指令集的处理，其泛化边界可能在于需针对新指令重新设计微基准测试以获取吞吐量参数]，否则可能因无法捕捉新指令特性而精度下降。

### 问题2. 论文提到 AMALI 将 MAPE 从 127.56%降至 23.59%，但 23.59%的误差在 GPU 架构设计空间探索中是否仍可能导致关键决策偏差（例如对张量核心吞吐量提升带来的性能增益误判）？该误差水平对于不同规模的 LLM 推理任务（如小模型实时交互与大模型批量处理）的影响是否存在显著差异？

对于 23.59%的 MAPE 是否导致设计决策偏差，作者指出在 GPU 架构设计空间探索中，AMALI 对 A100 和 H100 的预测误差平均仅为 8.2%和 13.2%，远低于整体 MAPE，说明核**心设计参数（如张量核心吞吐量）的预测误差可控，足以支持决策。**

针对不同规模 LLM 任务，AMALI 在 prefill 阶段（MAPE 15.56%）和 decode 阶段（MAPE 34.90%）、不同 prompt 长度（128-6144 tokens）及 batch size 下均保持稳定精度，**误差对小模型实时交互和大模型批量处理的影响无显著差异。**

### 问题3. AMALI 的多 warp 模型通过捕捉 warp 指令分布差异提升精度，但 LLM 推理中 warp 特性（如指令数量、计算强度）会随输入长度（prefill 与 decode 阶段）和模型结构（如注意力头数、隐藏层维度）剧烈变化。这种情况下，模型对 warp 分布的动态适应性如何？是否需要针对不同 LLM 架构或推理阶段重新训练微基准参数，从而增加使用成本？

关于**多 warp 模型对动态 warp 特性的适应性**，作者提到 AMALI 通过指令分歧（ID）建模 warp 指令数量差异，并在 Llama3-8B/15B、不同 prefill/decode 阶段（warp 特性差异显著）中有效。

微基准参数（如 α、β、γ）是针对 GPU 架构（如 A100）而非 LLM 任务的，同一架构下不同 LLM 模型或推理阶段无需重新训练，仅需通过 SASS Tracer 获取线程块大小等任务参数即可，**未增加额外使用成本。**

## 一、引言

由于大语言模型（LLM）前所未有的性能，LLM 推理已迅速应用于大量场景，如 OpenAI 的 ChatGPT[40]和 Github 的 Copilot[16]。此外，预计 LLM 推理应用在不久的将来将继续激增[7]。这些应用在很大程度上依赖于现代 GPU，这些 GPU 具有专门支持（如针对 LLM 的张量核心）以实现高性能（例如，更高的 token 生成速率、更短的首次 token 生成时间（TTFT）和 token 间生成时间（TBT））。

> 随着 LLM 推理应用的快速发展，拥有**能快速识别现代 GPU 上 LLM 推理性能瓶颈并提供深刻见解的工具变得至关重要**。这类工具为 GPU 微架构增强和 LLM 推理应用的性能优化提供了思路。

事实上，在人工智能时代，:mdnice-bold-italic[在 GPU 架构的早期设计阶段，性能评估的速度比准确性更重要]，因为在过去十年中，在快速发展的机器学习（ML）工作负载的推动下，GPU 架构演变迅速[52]。

GPU 架构的性能评估工具大致可分为两类：周期精确模拟器[9,13,17,18,28,30,43,50,52,57]和分析模型[8,21-25,29,47,55,56,60]，两者都是不可或缺的。

- 周期精确 GPU 模拟器虽然准确，但速度极慢。此外，由于其复杂性，这些模拟器无法提供易于理解的见解。
- 相比之下，GPU 分析模型比周期精确模拟器快几个数量级，但准确性较低。

此外，**分析模型可以提供易于理解且深刻的见解**。例如，除了预测 GPU 内核消耗的总周期数外，:mdnice-bold-italic[分析模型还可以构建每指令周期数（CPI）堆栈，通过展示各种停顿事件在执行中的占比，帮助计算机架构师轻松发现内核在不同 GPU 架构上的瓶颈] [24,56]。如前所述，在人工智能时代，**GPU 架构师更需要快速的性能评估工具**。因此，我们专注于研究 GPU 分析模型，并希望现有模型能成功应用于 LLM 推理。

::: block-1
然而，我们发现现有 GPU 分析模型[21-25,29,55,56]在足够准确地建模现代 GPU 上的 LLM 推理性能方面存在不足，原因有二。

- 首先，这些模型不适当地建模甚至没有建模现代 GPU 的微架构增强，包括张量核心、即时常量缓存和指令缓存。
- 其次，这些模型没有考虑 LLM 推理的特性，而 LLM 推理与传统机器学习工作负载和其他 GPU 应用有显著差异。
:::

因此，将最先进的（SOTA）分析模型 GCoM 应用于 LLM 推理时，与真实 GPU 硬件相比，误差显著偏高（例如，127.6%）（见第 6 节），这是不可接受的。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/02.webp)

> 为解决这些问题，我们提出了一种分析模型 AMALI，以足够的准确性建模现代 GPU 上的 LLM 推理。我们**仔细分析了现代 GPU 架构以及 LLM 推理特性**，并:mdnice-bold-italic[提出了三项创新]。

- 首先，通过分析张量核心如何与特定指令（如 HMMA）协同工作，我们:mdnice-bold-italic[提出了一种基于指令修饰符和吞吐量 的张量核心模型]，通过精确捕捉数学流水线节流停顿，有助于准确建模 LLM 推理中大量使用的通用矩阵乘法（GEMM）操作的性能。
- 其次，我们:mdnice-bold-italic[通过设计微基准测试 来测量内核启动延迟，对即时常量缓存 和指令缓存 进行建模]。这种启动延迟正是由即时常量缓存未命中和指令缓存未命中引起的停顿。因此，这项创新显著提高了我们的分析模型与真实 GPU 硬件相比的准确性。
- 最后，我们**发现最先进的 GPU 分析模型 GCoM[29]所使用的线程束分布不能反映 LLM 推理应用的特性**。因此，我们提出利用线程束指令分布来构建多线程束模型，以建模 GPU 上的 LLM 推理应用。

具体而言，本文的主要贡献如下：

::: block-1
- 我们开发了一种张量核心模型，以准确捕捉不同数据类型和张量大小下由张量核心引起的数学流水线节流停顿。
- 我们通过开发微基准测试来测量内核启动延迟，对即时常量缓存未命中和指令缓存未命中引起的停顿进行建模。
- 我们对 LLM 推理的线程束指令分布进行建模，以增强内核周期预测。
:::

> 综合上述内容，我们构建了一个名为 AMALI 的模型来预测 LLM 推理的内核周期。

我们在 NVIDIA A100 GPU 上使用几个典型的 LLM 推理应用对 AMALI 进行了验证。实验**结果表明，AMALI 实现了 23.59%的 MAPE**，表明在 kernel **总周期预测方面比 GCoM 的 127.56%有显著改进**。

## 二、研究背景

### 2.1 GPU 架构

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/02.webp)

为不失一般性，我们以 NVIDIA GPU（图形处理器）为例介绍 GPU 架构。图 1 展示了 Ampere GPU 架构[1,11,39]。可以看出：

::: block-1
- GPU **由多个通过片上互连网络连接的流式多处理器** （SM，GPU 中的核心计算单元）组成。
- 为了缓冲 SM 与内存之间的数据，在**全局内存、常量内存和互连网络之间设计了 L2 数据缓存。**
- 每个 SM 包含一个 L1 缓存/共享内存和多个子核心。L1 缓存/共享内存由子核心共享。注意，SM 中的 L1 缓存和共享内存共享相同的硬件，其中一部分可配置为 L1 缓存，另一部分为共享内存。
- 每个子核心包含一个线程束调度器（用于调度线程束执行的组件）、寄存器文件、一个常量缓存、一组 CUDA 核心和一组张量核心（GPU 中用于加速矩阵运算的专用计算单元）。
- 线程束调度器选择已准备好的线程束（由 32 个线程组成的执行单元，以锁步方式执行）执行。在每个周期中，线程束调度器从选中的线程束中发出一条指令。如果指令的操作数未准备好，线程束调度器会暂停该线程束，并采用某种调度策略（如松散轮询（LRR）[31,38]或先贪心后最旧[45]）选择另一个线程束执行。
:::

张量核心是定制的计算单元，每个时钟周期可以对 4×4 矩阵执行一次矩阵乘加运算。这显著加速了如 $C = A×B + C$ 这样的通用矩阵乘法（GEMM）计算。其中，A 和 B 分别是 $m×k$ 和 $k×n$ 的矩阵，C 是累加器矩阵。因此，张量核心是 LLM 推理和其他 AI 工作负载的关键组件。

用于编程张量核心的典型指令如下：

$$
HMMA.16816.F32, R0, R108, R140, R0 (1)
$$

$$
HMMA.1688.F32, R0, R180, R196, R0 (2)
$$

**指令名称“HMMA”代表半精度矩阵乘加，表明输入是半精度数据**。这些指令包含位于点符号后的修饰符，这些修饰符会影响指令行为。第一个修饰符（如 16816 或 1688）表示这些指令的张量大小。例如，16816 表示输入张量 A 和 B 分别是 16×8 和 8×16 的矩阵；1688 表示输入张量 A 是 16×8、张量 B 是 8×8 的矩阵。第二个修饰符（如表达式（1）和（2）中的 F32）表示累加器张量的数据类型。

表达式（1）和（2）所示的每个张量核心指令包含四个寄存器。R0 是用于存储累加器/结果矩阵（C）的寄存器；寄存器 R108 或 R180 存储输入矩阵 A，R140 或 R196 存储输入矩阵 B。注意，这些寄存器由线程束中的所有线程共享。相比之下，对于 CUDA 核心，线程束中的每个线程只能访问自己的寄存器，而不能访问其他线程的寄存器。**换句话说，在张量核心上运行的线程束中的线程以线程束级方式访问寄存器，而在 CUDA 核心上运行的线程以线程级方式访问寄存器**。线程级方式下每个线程的行为是确定的，而线程束级方式下每个线程的行为是不确定的。

此外，NVIDIA GPU 有一个小型常量内存（如 64KB），用于存储常量变量（如线程束 ID、块 ID）和其他数据结构（如数组）。常量内存是全局内存的一部分，并且有一个常量缓存（如图 1 所示）。

::: block-1
- 当常量缓存未命中时，需要花费内存读取时间（如数百个周期）从常量内存中获取数据；
- 当常量缓存命中时，可以像访问寄存器文件一样快速获取数据[38]。
:::

注意，不仅 Id 指令可以显式访问常量内存，其他指令也可以隐式访问常量内存。例如，指令 `IMAD.MOV.U32 R1, RZ, RZ, c[0x0][0x28]` 访问常量内存，因为内存地址带有特殊符号“c”，表明该地址位于常量内存中[37]。

### 2.2 CUDA 编程模型

统一计算设备架构（CUDA）[15]是为 NVIDIA GPU 设计的编程模型，它允许程序员使用类 C 函数编写 GPU 函数（称为内核）。CUDA 设计了一种名为单指令多线程（SIMT，一种并行执行模型，一个指令控制多个线程）的执行模型来执行内核，该模型具有三级层次结构。最低级是线程，执行 GPU 指令（如 SASS 指令，CUDA 的汇编指令）。

- 32 个线程组成一个线程束，以锁步方式执行。
- 上一级是线程块，包含多个线程或线程束。
- 最高级是网格，由多个线程块组成。

这种三级层次结构便于管理大量线程或对三维图形进行编程（如 x、y 和 z 维度）。

### 2.3 大语言模型

基于 Transformer（一种基于自注意力机制的深度学习模型）[14,34,51]的大语言模型（LLM）已被广泛应用于多个领域，如 OpenAI 的 ChatGPT[40]和 Copilot[16]。**Transformer 块由两个关键组件组成：多头注意力** （将输入数据投影到多个并行的注意力头进行计算）**和前馈神经网络** （由线性层和非线性激活函数组成的网络结构）。:mdnice-bold-italic[这两部分的核心计算都是通用矩阵乘法] （GEMM，矩阵运算的基础操作），这些操作在 GPU 上使用张量核心执行以获得优化的计算效率。

在**多头注意力机制中，** 输入数据被并行投影到多个缩放点积注意力中。这涉及通过线性变换（本质上是矩阵乘法）为每个注意力头计算查询、键（K）和值（V）矩阵。前馈块位于注意力机制之后，由两个线性层组成，中间带有非线性激活函数（如 ReLU）。**这些操作非常适合在张量核心上执行**。

LLM 推理通常包括两个阶段：预填充和解码。

- 预填充阶段接收由 token 组成的请求（也称为提示词）并并行处理它们。
- 解码阶段以自回归方式输出响应。

为了加速 token 生成，对 K 和 V 矩阵的计算结果进行缓存，称为 KV 缓存（缓存注意力计算中的键和值矩阵以加速解码）。更长的提示词需要更大的 KV 缓存。

LLM 推理的常用软件框架包括 Pytorch[41,46]、CUDA[15]和其他层（如 vLLM[54]）。通常，模型实现用 Pytorch 编写，而 GEMM 实现用 CUDA 编写。Pytorch 提供了方便调用 CUDA API 的工具。一次 LLM 推理可能会从 Pytorch 代码中调用数千个 CUDA 内核。

### 2.4 停顿分类

> 识别停顿（程序执行过程中因资源不足等原因导致的暂停）对于分析应用在特定 GPU 上的性能瓶颈极为重要。

**GSI（一种 GPU 停顿分析工具）[2]将停顿分为七类**，最先进的 :mdnice-bold-italic[GPU 分析模型 GCoM[29]采用了这种分类]：

::: block-1
1. 因线程/指令不足导致的空闲停顿；
2. 因内核代码分歧（指令缓存未命中）导致的控制停顿（Ctrl）；
3. 因线程屏障导致的同步停顿（Sync）；
4. 因未完成的内存加载导致的内存数据停顿（MemData）；
5. 因加载/存储端口不可用导致的内存结构停顿（MemStruct）；
6. 因指令操作数尚未由其他指令生成导致的计算数据停顿（ComData）；
7. 因所需计算资源不可用导致的计算结构停顿（ComStruct）。
:::

**这种分类基于通用处理器的视角，不能准确反映 NVIDIA GPU 的特定特性** （如常量内存）。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/06.webp)

相比之下，**NVIDIA 的分析工具 Nsight Compute** （NCU，NVIDIA 的 GPU 性能分析工具）[36]**基于线程束状态提供了 GPU 特定的停顿分类，如表 1 所示**。例如：

::: block-1
1. `math_pipe_throttle`（数学流水线节流）是指线程束等待可用的执行流水线时发生的停顿；
2. `no_instructions`（无指令）是指因指令缓存未命中导致无法获取指令时的停顿；
3. `imc_miss`（即时常量缓存未命中）是指因即时常量缓存未命中导致的停顿。
:::

表 1 中“未建模”的停顿未被先前的 GPU 分析模型[21-25,29,55,56]建模。事实上，:mdnice-bold-italic[基于这些 GPU 特定停顿构建模型比使用通用处理器视角的停顿分类能使分析模型更准确。]

## 三、基线模型与动机

### 3.1 基线模型

> 为了建模 GPU 性能，先前的研究[24,29,55,56]构建了具有增强区间分析（将程序执行划分为多个区间，分析每个区间的停顿情况）的 GPU 分析模型。

实际上，**区间分析是成功用于 CPU 性能建模的强大工具[27]。它将线程的执行划分为多个区间，区间的时间边界是停顿发生的时刻**。但这不足以准确建模 GPU 性能。

::: block-1
- 因此，GPU 分析模型 MDM[56]通过考虑 L1 缓存到设备内存访问过程中内存资源竞争导致的内存停顿，增强了区间分析。
- GCoM[29]在 MDM 的基础上进一步考虑了计算资源竞争、现代 GPU 的详细架构（如 SM 中的四个子核心和分段 L1 数据缓存）以及工作负载不平衡，提高了模型准确性，进而成为最先进的 GPU 分析模型。
:::

> 由于我们的 GPU 分析模型基于 GCoM，我们首先简要介绍 GCoM 并将其作为基线。

**GCoM 通常采用分层建模方法** （从 SM 到子核心，再到子核心组件如 L1 数据缓存）**来建模 CUDA 内核消耗的周期** （称为内核周期）。:mdnice-bold-italic[由于 CUDA 内核通常以指定的线程块和网格维度启动，因此它会在多个 SM 上并行运行]。在最高层级，:mdnice-bold-italic[GCoM 将此类 CUDA 内核的内核周期] 建模为该内核在**所有活跃 SM 上消耗的周期的算术平均值**，如公式（3）所示：

$$
C^{\text{kernel}}=\left(\sum_{i=0}^{\text{numSMs}-1}C_{i}\right)/\text{numSMs} \quad (3)
$$

其中，$C^{\text{kernel}}$ 是 CUDA 内核的内核周期，$\text{numSMs}$ 是运行该内核的活跃 SM 数量，$C_{i}$ 是该 CUDA 内核在第 $i$ 个 SM 上消耗的周期。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/02.webp)

为了建模 $C_{i}$，GCoM 首先在图 1 所示层次结构的下一层级，将内核在每个子核心上消耗的周期（$\text{subC}_{j}$）建模为活跃周期和空闲周期的总和。

::: block-1
- 空闲周期由子核心之间的负载不平衡引起，因此 GCoM 将其建模为当前子核心的活跃周期与同一 SM 中运行时间最长的子核心的活跃周期之间的差值。
- 另一方面，活跃周期可能受到数据依赖以及长延迟内存访问的影响。
:::

因此，GCoM 将子核心的活跃周期建模如公式（4）所示：

$$
\text{subC}_{j}^{\text{active}}=\text{subC}_{j}^{\text{base}}+\text{SubCS}_{j}^{\text{ComData}}+\text{subC} S_{j}^{\text{MemData}} \quad (4)
$$

其中， - $\text{subC}_{j}^{\text{active}}$ 是内核在第 $j$ 个子核心上消耗的活跃周期
- $\text{subC}_{j}^{\text{base}}$ 是内核在第 $j$ 个子核心上无任何冒险（指令执行过程中因资源冲突等导致的延迟）时执行线程束指令所用的周期
- $\text{SubCS}_{j}^{\text{ComData}}$ 是由数据（如操作数）冒险导致的停顿周期
- $\text{subCS}_{j}^{\text{MemData}}$ 是由长延迟内存访问导致的停顿周期。

因此，GCoM 用公式（5）计算 $C_{i}$：

$$
C_{i}=\left(\sum_{j=0}^{\text{numSubcs}-1}subC_{j}\right)/\text{numSubcs}+S_{i} \quad (5)
$$

其中，$\text{numSubcs}$ 是第 $i$ 个 SM 中的子核心数量，$S_{i}$ 是第 $i$ 个 SM 的停顿周期。

:mdnice-bold-italic[GCoM 对 $S_{i}$ 的建模深入到图 1 所示层次结构的最低层级，既考虑 L1 数据缓存未命中导致的内存停顿，也考虑计算资源竞争导致的停顿以及内存资源竞争导致的停顿]。公式（6）展示了 $S_{i}$ 模型：

$$
S_{i}=S_{i}^{\text{comStruct}}+S_{i}^{\text{memStruct}}+S_{i}^{\text{MSHR}}+S_{i}^{NoC}+S_{i}^{\text{DRAM}} \quad (6)
$$

其中，$S_{i}^{\text{comStruct}}$ 是计算资源竞争导致的停顿，$S_{i}^{\text{memStruct}}$ 是内存资源竞争导致的停顿，$S_{i}^{\text{MSHR}}$ 是缺失状态/处理寄存器（MSHR）竞争导致的停顿，$S_{i}^{NoC}$ 是片上网络竞争导致的停顿，$S_{i}^{\text{DRAM}}$ 是 LLC 未命中导致的内存访问延迟。注意，公式（6）中的后三项由 MDM[56]建模，而 GCoM 建模前两项。

> 我们现在介绍 GCoM 如何建模 $S_{i}^{\text{comStruct}}$ 和 $S_{i}^{\text{memStruct}}$。

由于资源竞争直接影响线程束指令的发射周期，GCoM 首先建模发射周期。为此，它首先确定存在多个并发执行的线程束时的活跃子核心数量，如公式（7）所示：

$$
\text{numActSCs}(x)=\min(x, \text{numSubcs}) \quad (7)
$$

其中，$x$ 是并发执行的线程束数量，$numSubcs$ 是一个 SM 中的子核心数量。随后，GCoM 分别用公式（8）、（9）、（10）和（11）建模第 $k$ 个区间的最大发射周期、计算资源充足时第 $k$ 个区间的发射周期、第 $k$ 个区间向第 $m$ 个功能单元（FU）的发射周期以及第 $k$ 个区间向 L1 数据缓存的发射周期：

$$
C_{k}^{\text{IssueMax}}(x)=\max_{m\in FU}\left\{C_{k}^{\text{IssueBase}}(x), C_{k,m}^{\text{Issue}}(x), C_{k,L1}^{\text{Issue}}(x)\right\} \quad (8)
$$

$$
C_{k}^{\text{IssueBase}}(x)=\frac{I_{k}\cdot x}{\text{numActSCs}(x)\cdot \text{IssueRate}} \quad (9)
$$

$$
C_{k,m}^{\text{Issue}}(x)=\frac{I_{m}\cdot II_{m}\cdot x}{\text{numActSCs}(x)\cdot \text{IssueRate}}\quad(I_{m}\leq I_{k}) \quad (10)
$$

$$
C_{k,L1}^{\text{Issue}}(x)=\left\lceil\frac{b_{k}}{B_{k}^{L1}}\right\rceil\times x \quad (11)
$$

其中，$x$ 是第 $k$ 个区间中并发执行的线程束数量，$\text{numActSCs}$ 是一个 SM 中的活跃子核心数量，$\text{IssueRate}$ 是线程束指令发射率，$I_{k}$ 是代表性线程束在第 $k$ 个区间中的线程束指令数量，$I_{m}$ 是分派到第 $m$ 个功能单元的线程束指令数量，$II_{m}$ 是第 $m$ 个功能单元的启动间隔（同一类型功能单元两次操作之间的周期数），$b_{k}$ 是代表性线程束引起的 L1 数据缓存访问量，$B_{k}^{L1}$ 是第 $k$ 个区间中 L1 数据缓存的有效带宽。

最后，GCoM 用公式（12）建模计算资源竞争导致的停顿：

$$
S^{\text{ComStruct}}(x)=\sum_{k\in \text{intervals}}\left(C_{k,m}^{\text{Issue}}(x)-C_{k}^{\text{IssueBase}}(x)\right) \quad (12)
$$

当 $C_{k,L1}^{\text{Issue}}$ 成为 $C_{k}^{\text{IssueMax}}(x)$ 时，GCoM 用公式（13）建模内存竞争导致的停顿：

$$
S^{\text{MemStruct}}(x)=\sum_{k\in \text{intervals}}\left(C_{k,L1}^{\text{Issue}}(x)-C_{k}^{\text{IssueBase}}(x)\right) \quad (13)
$$

### 3.2 先前工作的局限性

> 在简要介绍 GPU 分析模型 GCoM 之后，我们现在分析其局限性。

#### 局限性 1：启动间隔建模不适用于张量核心

如公式（10）所示，GCoM 需要使用第 $m$ 个功能单元的启动间隔（$II_{m}$）来计算第 $k$ 个区间向第 $m$ 个功能单元的发射周期（$C_{k,m}^{\text{Issue}}(x)$）。:mdnice-bold-italic[启动间隔是指同一类型功能单元两次操作发射之间的周期数[20]。不同类型功能单元的启动间隔可能不同]。包括 GCoM[29]在内的先前 GPU 分析模型[8,29,48,60]用它来建模计算资源竞争，如公式（14）所示：

$$
\text{initiation_interval}=\frac{\text{warp_size}}{\text{functional_unit_lanes}}\quad(14)
$$

其中，$\text{warp_size}$ 是一个线程束中的线程数量（通常为 32），$\text{functional_unit_lanes}$ 是一个子核心中的功能单元数量。

因此，:mdnice-bold-italic[启动间隔实际上建模了功能单元的吞吐量[20]，因为它可以计算为功能单元两次连续计算结果之间的周期数的倒数]。当 $\text{functional_unit_lanes}$ 小于 $\text{warp_size}$ 时，会发生计算资源竞争，线程束调度器需要花费与启动间隔相同的周期来发射一条线程束指令。这种方法适用于建模 CUDA 核心，因为在线程束中的线程竞争计算资源（即 CUDA 核心）时会发生线程竞争。

然而，这对于张量核心并不适用。**当线程在 CUDA 核心上运行时，每个线程束线程仅访问自己的寄存器来执行指令**。相比之下，如第 2 节所述，:mdnice-bold-italic[当线程在张量核心上运行时，线程束中的所有线程共享相同的寄存器文件。这使得线程能够以统一的方式协同执行如矩阵乘法（如 HMMA 指令）之类的操作，而不是单独执行]。因此，张量核心的启动间隔可能显著小于公式（14）计算的值。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/07.webp)

我们通过在 RTX 3090 上运行 Llama2-7B 推理时，将 NCU 定义的数学流水线节流停顿与 GCoM 使用启动间隔建模的计算资源竞争进行比较，来验证这一分析。图 2a 显示了结果。可以看出，:mdnice-bold-italic[与真实硬件上发生的情况相比，GCoM 显著高估了 Llama2-7B 推理中 GEMM 内核因资源竞争导致的数学流水线节流停顿。这种高估是因为对张量核心的初始间隔估计相对于实际情况过大。]

#### 局限性 2：忽略指令修饰符导致张量核心建模不准确

> 包括 GCoM[29]在内的现有 GPU 分析模型[8,29,48,60]没有考虑指令修饰符（如数据类型 F32）。这对于 CUDA 核心指令可能是可接受的，但对于张量核心指令则不可接受，因为**张量大小修饰符对张量核心指令的性能有显著影响。**

为了证实这一点，我们**首先开发微基准测试来测量张量核心指令的性能**。随后，我们利用 cuAssembler[12]修改微基准测试的 SASS 跟踪，仅将 HMMA 的指令修饰符（张量大小）从 16816 改为 1688，同时保持其他因素（如修饰符 F32 和指令计数）不变。:mdnice-bold-italic[图 3 显示，带有 16816 修饰符的 HMMA 指令每个指令的浮点乘加（FMA）次数是带有 1688 修饰符的指令的两倍]。HMMA 带有 16816 和 1688 修饰符时的总周期也是如此。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/08.webp)

这表明，带有 16816 的 HMMA 的每指令周期数（CPI，可视为吞吐量）是带有 1688 的 HMMA 的两倍。原因如下：带有 16816 的 HMMA 执行 16×8×16=2048 次 FMA，而带有 1688 的 HMMA 执行 16×8×8=1024 次 FMA。每周期 FMA 次数是 GPU 张量核心的一个设计参数。例如，A100 GPU 的每个张量核心设计为在单个周期内执行 8×4×8=256 次 FMA[39]。因此，A100 张量核心执行带有 16816 的 HMMA 需要 8 个周期，执行带有 1688 的 HMMA 需要 4 个周期。也就是说，**带有 16816 的 HMMA 的 CPI 为 8，是带有 1688 的 HMMA 的 CPI（4）的两倍**。总之，我们的:mdnice-bold-italic[实验和理论分析都表明，修饰符显著影响张量核心指令的吞吐量，因此在建模张量核心的吞吐量时必须考虑修饰符]，详见第 4.7 节。

#### 局限性 3：常量缓存建模未考虑隐式常量内存访问，且忽略了指令缓存建模

我们发现，NCU 定义的 imc_miss（即时常量缓存未命中）可能不仅由显式常量内存访问引起，还由隐式常量内存访问引起。包括 GCoM[29]在内的现有 GPU 分析模型[8,29,48,60]通**过显式加载和存储指令（如 LDC 和 STC）来建模常量内存访问**。然而，常量内存也会被隐式指令大量访问。

$$
IMAD.MOV.U32 R1, RZ, RZ, c[0x0][0x28] \quad (15)
$$

表达式（15）展示了一个示例。可以看出，:mdnice-bold-italic[常量内存地址 c[0x0][0x28]通过符号“c”被编码为指令的操作数。忽略这些指令会导致即时常量缓存的建模不准确。]

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/07.webp)

另一方面，**先前的模型也没有建模指令缓存未命中，这使得它们在建模 NCU 定义的 no_instruction 停顿时不准确**。如图 2b 所示，GCoM 未能考虑常量缓存未命中和指令缓存未命中导致的停顿。因此，它显著低估了 Llama2-7B 推理中 VELE 内核的周期。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/09.webp)

此外，图 4 显示，在:mdnice-bold-italic[即时常量缓存未命中和指令缓存未命中导致的停顿周期之和在 CPI 堆栈中可能占很高的比例（如 70%），这表明在 GPU 分析模型中不能忽略它们。]

#### 局限性 4：现有 GPU 分析模型未考虑 LLM 推理的线程束特性

包括 GCoM[29]在内的 GPU 分析模型[8,29,48,60]采:mdnice-bold-italic[用 K 均值算法选择一个代表性线程束来代表 CUDA 内核中的所有线程束。先前的研究声称这种方法足够准确] [24,29,56]。对于来自 Rodinia[10]和 Parboil[49]基准测试套件的内核，这可能是正确的。然而，:mdnice-bold-italic[我们发现 LLM 推理应用的 CUDA 内核中的线程束执行流程存在显著差异，如图 5 所示。]

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/10.webp)

> 从中可以得出几个有趣的观察结果。

【首先】，**LLM 推理中的不同 CUDA 内核具有显著不同的线程束数量**，从几十个到几千个不等。:mdnice-bold-italic[这是因为 LLM 比 DNN 包含更多的算子]。

- 以 GEMM 为例，一个 LLM 应用中的 GEMM 比传统 DNN（如 RNN[42]）中的 GEMM 具有显著更高的异构性。
- 例如，LLM 注意力层中的 GEMM 通常是内存受限的，而 FFN 层中的 GEMM 是计算受限的。:mdnice-bold-italic[相比之下，如[42]所示，一个 DNN 中的 GEMM 通常是计算受限的。]

此外，**LLM 中 GEMM 的维度可能存在巨大差异**。例如，在 LLM 推理中，$bs×\text{seq_lth}$（bs-批大小，$\text{seq_lth}$-序列长度）对应于 GEMM $M×k×N$ 中的 M。

- 在预填充阶段，假设 seq_lth 为 32768，bs 为 4，则 M 为 131072。
- 在解码阶段，由于自回归方式，seq_lth 始终为 1，而 bs 仍可为 4，则 M 仅为 4。

也就是说，预填充阶段 GEMM $M×k×N$ 的 M 是解码阶段的 32768 倍！

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/10.webp)

【其次】，**同一 CUDA 内核中某些线程束的指令数量与其他线程束存在显著差异**。以内核 ELE_4096_160 为例，图 5a 左侧的柱形显示，3000 个线程束中的每个线程束仅包含几百条指令。相比之下，图 5a 右侧最高的柱形显示，同一内核中 2800 个线程束中的每个线程束包含超过 6000 条指令。最后，某些内核（如 `GEMM_bf16_4096_172`）的线程束指令数量差异极大，从不到 100000 到超过 600000。

---

总之，:mdnice-bold-italic[LLM 推理中同一 CUDA 内核的线程束指令数量存在如此显著的差异，使得使用一个代表性线程束来代表 CUDA 内核的所有线程束是不可行的]。然而，对于区间分析，需要使用一个代表性线程束。我们在第 4.9 节中解决这一极端挑战。

## 四、AMALI 模型

> 为解决在现代 GPU 上运行 LLM 推理时存在的上述局限性，我们提出了一种名为 AMALI 的新型 GPU 分析模型。它**用于预测 LLM 推理应用的 CUDA 内核所消耗的总周期。**

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/03.webp)

### 4.1 概述

图 6 展示了 AMALI 的概述。可以看出，它由下面六个组件组成：

::: block-1
- SASS 跟踪器（SASS Tracer）：收集 CUDA 内核的指令轨迹及相关信息。
- 缓存模拟器（Cache Simulator）：基于 SASS 跟踪器获取的内存访问轨迹模拟缓存行为。
- SASS 解析器（SASS Parser）：从 SASS 轨迹中提取所需信息。
- 区间分析器（Interval Analyzer）：将线程束的执行划分为多个区间。
- 区间解析器（Interval Parser）：利用生成的区间构建模型来预测内核消耗的周期。
- 内核启动延迟计算模块（KLL comp）：用于计算 CUDA 内核的启动延迟。
:::

要使用 AMALI，我们需要知道 GPU 的架构参数。为此，我们开发了微基准测试，并遵循[4,33]中描述的指针追逐法（一种用于测量内存访问延迟的技术）来测量功能单元（FU）和内存系统的延迟与吞吐量。

### 4.2 SASS 跟踪器

它:mdnice-bold-italic[基于 GPU 插桩工具 NVBit[53]开发，用于收集 CUDA 内核的 SASS（CUDA 汇编）指令轨迹及相关信息]。具体来说，它收集指令名称、指令修饰符、指令使用的寄存器、内存访问地址、网格大小、线程块大小、消耗的共享内存大小、消耗的寄存器文件大小、线程束 ID 和 SM ID。

先前的工作[3,19,29,60]已经证明，:mdnice-bold-italic[使用 SASS 进行建模比使用 PTX（并行线程执行，CUDA 的中间语言）具有更高的准确性，因此我们的 SASS 跟踪器专注于收集 SASS 指令的信息。]

### 4.3 SASS 解析器

我们的 SASS :mdnice-bold-italic[解析器从 SASS 跟踪器生成的轨迹中提取所需信息，如网格大小和线程块大小]。由于区间建模需要一个代表性线程束，我们利用 SASS 跟踪器基于每个线程束使用的功能单元构建单线程束表示，将每个线程束编码为一个向量。

为此，SASS 解析器采用 K 均值聚类算法，遵循与 GCoM[29]和 GPUMech[24]类似的方法，并捕获 NCU 中定义的“selected”停顿事件。注意，每个线程束通过子核心 `ID=线程束 ID%4` 的方案调度到子核心，如[26]中所述。

### 4.4 缓存模拟器

:mdnice-bold-italic[缓存模拟器结合指定的 GPU 架构配置参数，使用 SASS 跟踪器获取的内存访问地址模拟缓存行为]。缓存模拟的目标是确定平均内存访问时间（AMAT，Average Memory Access Time）。然后，AMAT 和功能单元延迟用于区间分析，如[27]中详细描述的那样，将线程束的执行划分为离散的区间。

### 4.5 区间分析器

> 我们的区间分析器利用缓存模拟器生成的 AMAT 和 SASS 解析器获取的线程束配置文件，将线程束的执行划分为离散的区间。我们**现在讨论如何在区间分析中匹配数据依赖导致的停顿事件。**

首先，AMALI 使用公式（16）估计内核的总周期：

$$
C = S_I + S_{IP} + KLL + ID \quad(16)
$$

其中，$C$ 是内核的估计周期。$S_I$ 和 $S_{IP}$ 分别表示区间分析器和区间解析器捕获的停顿周期。$KLL$ 是内核启动延迟，$ID$ 是由指令分歧导致的空闲周期。起初，AMALI 将“selected”停顿周期建模为代表性线程束发出的指令数量，如公式（17）所示：

$$
S_{\text{Selected}} = I_{\text{warp}} / \text{IssueRate} \quad(17)
$$

其中，$I_{\text{warp}}$ 是代表性线程束中的指令数量，“Selected”是表 1 中定义的“selected”类型的停顿周期。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/06.webp)

> 我们在区间分析器中:mdnice-bold-italic[采用传统的区间分析方法[24,27]来建模由全局或共享内存访问以及计算指令导致的数据依赖]。

::: block-1
- 对于每条指令，我们标记其结束周期。
- 对于全局内存指令，其结束周期为当前周期加上 AMAT。
- 对于共享内存指令，其结束周期为当前周期加上取决于加载/存储操作的共享内存访问周期[1]。
:::

对于在 CUDA 核心上执行的指令，AMALI 基于架构参数中的固定延迟建模其性能。相比之下，张量核心指令的延迟通过基于修饰符（包括数据类型和张量大小）的吞吐量来表征（详见第 4.7 节）。当指令使用的数据不能立即获得时，会插入一个停顿区间，直到指令可以发出。区间分析的结果通过公式（18）计算：

$$
S_I = S_{\text{Selected}} + S_{\text{wait}} + S_\text{{short_scoreboard}} + S_{\text{long_scoreboard}} \quad(18)
$$

其中，$S_I$ 是区间的预测周期，$S_{\text{wait}}$ 是由计算指令的数据依赖导致的停顿周期，$S_{\text{short_scoreboard}}$ 是由共享内存导致的停顿周期，$S_{\text{long_scoreboard}}$ 是由全局内存导致的停顿周期。

对于一个停顿区间，AMALI 捕获停顿原因，这些原因分为计算、共享内存访问或其他内存访问停顿。然后，区间分析器分析代表性线程束的这些信息，得到三个停顿周期：$S_{\text{wait}}$、$S_{\text{short_scoreboard}}$ 和 $S_{\text{long_scoreboard}}$。它们的总和可以通过公式（19）和（20）计算：

$$
S_i = \sum_{k \in \text{intervals}} S_k \cdot P(i, flag[k])
$$

$$
P(x, y) = \begin{cases}1 & if\ x = y \\0 & otherwise\end{cases}
$$

其中，$i$ 和 $flag[k]$ 表示区间停顿原因，可能包括 wait、long_scoreboard 或 short_scoreboard。$flag[k]$ 表示第 $k$ 个区间的停顿原因，$S_k$ 表示第 $k$ 个停顿区间的周期长度。注意，$x = y$ 表示停顿原因相同。

### 4.6 区间解析器

我们的区间解析器捕获 `math_pipe_throttle`、`lg_throttle`、`tex_throttle` 和 `mio_throttle`。我们使用公式（21）计算这些停顿周期的总和：

$$
S_{IP} = S_{\text{math_pipe}} + S_{mio} \quad(21)
$$

其中， $$
S_{IP}
$$

是区间解析器得到的周期。

$$
S_{\text{math_pipe}}
$$

、 $$
S_{lg}
$$

和 $$

$$

分别表示 math_pipe_throttle、lg_throttle 和 mio_throttle 导致的停顿周期。

为了计算三个“throttle”导致的前两个停顿周期，我们使用 GCoM[29]的核心建模方法，如公式（22）和（23）所示：

$$
S_{\text{math_pipe}} = S^{\text{ComStruct}} \quad(22)
$$

$$

其中，$S^{\text{ComStruct}}$ 和 $S^{\text{MemStruct}}$ 分别是由计算结构冒险和内存结构冒险导致的停顿周期。$S_\text{{math_pipe}}$ 表示由计算资源冒险导致的停顿周期，而 $S_{lg}$ 表示由 L1 数据缓存访问竞争导致的停顿周期。

对于最后一个“throttle”导致的停顿周期（`mio_throttle`），AMALI 使用 MDM 来建模内存侧的竞争，即 MSHR、NoC 和 DRAM 竞争，如公式（24）所示：

其中， $$

$$

和 $$
S^{DRAM}
$$

分别是由 MSHR（缺失状态/处理寄存器）、NoC（片上网络）和 DRAM 竞争导致的停顿周期。

### 4.7 张量核心建模

> 与先前的研究[24,29,56]在不考虑指令修饰符的情况下建模 CUDA 核心性能不同，**AMALI 在建模张量核心性能时考虑了指令修饰符。**

实际上，:mdnice-bold-italic[AMALI 结合从微基准测试中获得的吞吐量和修饰符来建模张量核心]，如公式（25）所示：

$$
II_{TC} = \frac{\text{FMA_count}}{TP_{dt}} \quad(25)
$$

其中，$II_{TC}$ 表示基于当前 HMMA 指令的张量核心启动间隔。$\text{FMA_count}$ 表示指令的 FMA（浮点乘加）运算次数，受修饰符影响。$TP_{dt}$ 表示基于数据类型 $dt$ 的峰值吞吐量（以 FMA 运算次数/周期为单位）。**实际上，FMA 运算次数/周期是张量核心的一个设计参数**。$II_{TC}$ 用于替换公式（10）中的 $II_m$，以预测区间内张量核心的发射周期。$L_{TC}$ 实际上是张量核心指令的延迟，可以用公式（26）表示：

$$
L_{TC} = II_{TC} \quad(26)
$$

其中，$L_{TC}$ 是单个张量核心指令的延迟，用于区间分析。

### 4.8 常量/指令缓存建模

> 我们使用内核启动延迟（KLL，Kernel Launch Latency）来建模由常量缓存未命中和指令缓存未命中导致的停顿周期。

内核启动延迟（KLL）由公式（27）表示：

$$
KLL = s \cdot GS + k \quad(27)
$$

其中，$KLL$ 是内核启动延迟，$s$ 是一个取决于线程块大小的参数，$k$ 是特定于架构的固定值，$GS$ 是内核的网格大小，可从 SASS 跟踪器获取。参数 $s$ 和 $k$ 通过微基准测试确定。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/11.webp)

> 图 7 显示了在 A100 GPU 平台上的微基准测试结果。

对于 Ampere 架构，在固定线程块大小的情况下，内核启动延迟与网格大小呈线性关系。然而，该直线的斜率相对于线程块大小是非线性的。为了建模这个斜率，我们采用线程块大小的二阶函数，如公式（28）所示：

$$
s = \alpha \cdot (BS)^2 + \beta \cdot (BS) + \gamma \quad (28)
$$

这里，$s$ 表示直线的斜率，$BS$ 是内核的线程块大小，从 SASS 跟踪器获取。系数 $\alpha$、$\beta$ 和 $\gamma$ 是常数，可通过基准测试确定。

### 4.9 线程束指令分布建模

> GCoM 通过考虑整个 GPU 中线程束数量分布导致的工作负载不平衡来提高模型准确性。但我们发现在 :mdnice-bold-italic[LLM 推理中，工作负载不平衡并不体现在线程束【数量分布上】，而是体现在线程束【指令数量分布上】。]

为了准确建模 LLM 推理中的内核周期，对指令分歧（ID，Instruction Divergence）进行建模很重要。我们使用公式（29）建模 $ID$：

$$
ID = \left(\text{maxsub}_{\text{coreInstr}} - I_{\text{SC}_{\text{Repr.warp}}}\right) / \text{IssueRate} \quad(29)
$$

其中，$\text{maxsub}_\text{coreInstr}$ 是内核中某个子核心上的最大线程束指令数量。$I_{\text{SC}\_\text{Repr.warp}}$ 是执行代表性线程束的子核心的线程束指令数量。$\text{IssueRate}$ 是指令发射率（以指令数/周期为单位）。因此，$ID$ 的单位是周期。:mdnice-bold-italic[通过将其添加到公式（16）所示的其他停顿周期中，我们可以提高 LLM 推理中内核周期建模的准确性。]

## 六、结果与分析

### 6.1 确定测试的 token 数量

由于每个 token 的跟踪文件体积较大，我们无法在单 GPU 机器上用过多的 token 来评估 AMALI。但:mdnice-bold-italic[我们的实验需要测试多少个 token 呢？我们通过观察不同输入和输出 token 数量下 token 之间的时间来确定]。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/13.webp)

图 8 显示，在第一个生成的 token 之后，后续 token 的执行周期数相同。这一结果使我们只需测试前两个 token：第一个 token 的推理是预填充阶段，第二个是解码阶段。遵循先前的工作[29]，我们使用 NCU 测量`gpc__cycles_elapsed.avg`指标 10 次，取平均值以获得可靠的内核执行耗时周期的基准值。

### 6.2 确定系数 α、β 和 γ

我们开发微基准测试来确定方程（28）中使用的系数 α、β 和 γ。在 A100 上，α、β 和 γ 分别为 0.0036、0.0366 和 1.1891。在不同的 GPU 上，这些系数可能不同。

### 6.3 AMALI 的准确性

我们首先:mdnice-bold-italic[使用平均绝对百分比误差（MAPE）来评估 AMALI 在 A100 上对 Llama-8B 推理中高频执行且相对较长的内核的准确性]。我们还评估了在 GCoM 基础上的各项扩展对准确性的提升：张量核心建模（TCM）、内核启动延迟建模（KLL）和线程束指令分布（ID）。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/14.webp)

> 图 9 显示了结果。从中可以得出几个有趣的发现：

- 首先，由于:mdnice-bold-italic[对张量核心、内核启动延迟和线程束指令分布的正确建模，AMALI 的准确性显著高于 GCoM。]
- 其次，:mdnice-bold-italic[对于 GEMM 内核，AMALI 中基于吞吐量的张量核心建模（TCM）是其高准确性的主要贡献因素]。相比之下，GCoM 使用 CUDA 核心的建模方法来建模张量核心，这是不合理的，导致对这些内核周期的严重高估。最后，对于使用 CUDA 核心的元素级操作（ELE_...），GCoM 显著低估了它们的耗时周期。相比之下，AMALI 通过内核启动延迟（KLL）和线程束指令分布（ID）的建模，能够准确预测其周期。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/15.webp)

图 10 显示，对于 GEMM 内核，TCM 的改进最为显著，而对于 ELE 内核，KLL 优化的效果最为明显。总体而言，AMALI 在预测 GEMM 内核时的 MAPE 为 17.84%，在预测 ELE 内核时为 27.29%，而 GCoM 的 MAPE 分别为 183.95%和 77.81%。总之，GCoM 对这些内核的平均 MAPE 为 127.6%，而 AMALI 仅为 23.5%。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/16.webp)

> 接下来，我们使用不同提示长度（从 128 个 token 到 6144 个 token）的 Llama3-8B 评估 AMALI 的端到端性能预测准确性。

图 11 显示了结果。可以看出，对于所有实验的提示长度，AMALI 的 MAPE 显著低于 GCoM，且 KLL、ID 和 TCM 都在不同程度上降低了 GCoM 的 MAPE。

- 在预填充阶段，AMALI 的 MAPE 为 15.56%，而 GCoM 的误差显著更高，为 163.68%。同样，在解码阶段，AMALI 保持了较好的性能，MAPE 为 34.90%，而 GCoM 的误差仍高达 82.29%。
- 此外，对于相同的长提示（如>1024 个 token），GCoM 在预填充阶段的 MAPE 显著高于解码阶段。这是因为长提示的预填充涉及比解码阶段大得多的 GEMM，而这些 GEMM 在张量核心上执行，但 GCoM 对张量核心的建模不准确。

相比之下，由于准确的张量核心建模，AMALI 在所有提示长度的预填充和解码阶段都实现了显著较低的 MAPE。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/17.webp)

此外，我们使用具有 256 个 token 提示但不同批大小的 Llama3-8B 推理来评估 AMALI 的性能。如图 12a 所示，AMALI 在所有实验的分析模型中仍然表现最佳。**这表明 AMALI 适用于不同批大小的 LLM 推理**。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/17.webp)

另外，我们使用更大的 LLM 来评估 AMALI，这可以对硬件进行某种极端压力测试。为此，我们基于 Llama2-13B 构建了一个名为 Llama-15B 的模型，数据类型为 BF16。该模型的权重和 4096 个 token 的 KV 缓存所需的内存容量接近我们 A100 GPU 的 80GB。图 12b 显示了结果。可以看出，AMALI 在所有实验的分析模型中仍然实现了最低的 MAPE。这表明 AMALI 能够准确预测不同 LLM 推理模型的性能。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/18.webp)

> 接下来，我们比较了 MDM、GCoM 和 AMALI **在不同提示长度的 Llama3-8B 推理上的性能预测准确性**。图 13 显示了结果。可以看出，AMALI、MDM 和 GCoM 的 MAPE 分别为最低、次低和最高。

- 正如预期的那样，AMALI 实现了最低的 MAPE，因为它准确地建模了张量核心吞吐量、线程束指令分布和内核启动延迟。
- 然而，GCoM 的 MAPE 高于 MDM，这一点有些违反直觉，因为 GCoM 是在 MDM 的基础上扩展了计算核心建模。尽管如此，这是事实，原因如下：:mdnice-bold-italic[GCoM 准确地建模了 CUDA 核心，并使用相同的方法来建模张量核心，而张量核心的性能与 CUDA 核心有显著差异]。另一方面，**MDM 既不建模 CUDA 核心，也不建模张量核心，因此没有计算误差**。这导致当 GCoM 预测大量使用张量核心的 LLM 推理性能时，其误差甚至高于 MDM。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/19.webp)

> 最后，我们使用非 LLM 应用比较了 MDM、GCoM 和 AMALI 的准确性：DeepBench[35]中的 CONV 和 GEMM，以及 Rodinia[10]中的 BP、B+树、DWT 和 PF。

图 14 显示了结果，可以看出：

- 对于卷积和其他非 GEMM 内核，GCoM 和 MDM 都表现出较高的准确性，但:mdnice-bold-italic[由于常量缓存、指令缓存建模和线程束指令分布建模，AMALI 的准确性更高。]
- 对于 GEMM 及类似内核，:mdnice-bold-italic[由于 AMALI 准确地建模了张量核心，其准确性显著高于 MDM 和 GCoM。]

### 6.4 设计空间探索

:mdnice-bold-italic[AMALI 基于 FMA 操作数/周期（吞吐量）的张量核心建模能够在不同的张量核心吞吐量设置下进行准确的性能预测]。实际上，FMA 操作数/周期可以作为 NVIDIA GPU 张量核心的一个设计参数，新一代的张量核心可能具有更高的 FMA 操作数/周期。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/20.webp)

> 图 15 比较了 AMALI 和 GCoM 在 128、256 和 512 FMA 操作数/周期下的内核周期预测。

可以看出，**当张量核心具有更高的 FMA 操作数/周期（如 512）时，AMALI 预测所有 GEMM 内核消耗的周期更少**。相比之下，GCoM 在不同的张量核心能力下预测的周期相同，这是错误的。这是因为 GCoM 使用 CUDA 核心的建模方法来建模张量核心，无法反映具有不同 FMA 操作数/周期的张量核心对整体内核性能的影响。

我们:mdnice-bold-italic[进一步利用 AMALI 探索张量核心吞吐量设计，使用它来预测 DeepBench[35]中的五个 GEMM 内核的性能，并将预测结果与在 A100 和 H100 上的测量性能进行比较]。A100 和 H100 的张量核心的 FMA 操作数/周期分别为 256 和 512。我们将它们作为 AMALI 中的张量核心吞吐量设计值，以预测这五个内核在 A100 和 H100 上运行时消耗的周期。更高的张量核心吞吐量有望产生更低的 `math_pipe_throttle`，进而减少内核周期。

![文章插图](/articles/2025-09-10-isca-25-gpu-llm-amali-02cb5aa5/images/21.webp)

> 图 16 显示，一个内核在 H100 上的 `math_pipe_throttle` 仅为在 A100 上的一半，因此在 H100 上的性能更高（由红色虚线分隔的一个块中的左右相邻条分别表示相同内核在 A100 和 H100 上消耗的周期）。这是因为 **H100 的张量核心吞吐量是 A100 的两倍。**

这表明 :mdnice-bold-italic[AMALI 能够准确评估设计参数对特定停顿事件的影响]。此外，与测量的内核周期相比，AMALI 的预测误差可低至 1.03%，最大误差不超过 23%。在 A100 和 H100 上的平均误差分别仅为 8.2%和 13.2%。这些结果表明，**AMALI 在早期阶段对于 GPU 设计空间探索具有足够的准确性。**

### 6.5 讨论

我们提出了指令分歧（ID）来减少内核中线程束指令不平衡的影响。

- 选择内核中最大的线程束作为代表性线程束来建模周期是不合理的。
- 区间分析假设所有线程束都是相同的线程束，因此使用最大的线程束作为代表性线程束会导致极大的高估。

因此，我们:mdnice-bold-italic[【仅】建模线程束之间的已发射指令数量差异，这表现出较高的准确性]。但通过研究**更好的策略来建模线程束指令数量分歧，仍有进一步提高准确性的空间。**

## 七、相关工作

### 7.1 分析模型

GPU 分析模型借鉴了 CPU 分析模型中的许多分析技术方面，区间分析[27]是来自 CPU 分析研究的强大工具之一。

::: block-1
- Huang 等人提出了 GPUMech[24]，这是第一个基于区间分析的 GPU 分析模型。
- MDM[55,56]考虑了内核中的内存分歧。
- Lee 等人[29]**在分析模型中添加了现代 GPU 架构细节，包括分段缓存、SM 中的子核心、计算资源竞争，并考虑了工作负载不平衡**。但他们:mdnice-bold-italic[基于功能单元的数量来建模延迟，而不是吞吐量，并且忽略了线程束的指令分歧。]
:::

除了基于区间分析的 GPU 分析模型外，还有其他建模 GPU 的方法。

::: block-1
- Hong 等人[21]基于内存线程束并行度和计算线程束并行度构建了一个模型，并通过提出用于 GPU 的集成功率和性能（IPP）预测模型[23]进一步扩展了 MWP-CWP 模型。
- Jain 等人[25]**分析了 GPGPU-Sim 的 GPU 模拟准确性**，表明其在计算密集型任务上准确性较高，但在内存受限工作负载上误差显著。
- Lym 等人[32]**发现了深度学习算法（如卷积）中的内存访问模式，并采用了特定的分析模型**，但他们专注于内存流量，无法捕捉计算资源竞争导致的停顿。
- SeyyedAghaei 等人[47]利用应用程序**在小型设备上的行为来估计在大型平台上的性能**。
- AIO[44]是一种**适用于各种加速器的性能模型**。
:::

然而，这些模型都**没有** 对 GPU 的张量核心进行建模。

### 7.2 GPU 模拟器

GPU 模拟器是探索内核瓶颈的实际标准。

::: block-1
- Bakhoda 等人[9]构建了一个**详细的 GPU 模拟器 GPGPU-sim**，并通过开发 Accel-Sim[28]进一步扩展了其功能，该模拟器引入了对 SASS 的支持。
- Leng 等人[30]将 **GPUWattch 与 GPGPU-sim 集成** 以建模功率性能。
- Ubal 等人[17,50]提出了 Multi2Sim，这是一个开源、模块化且可完全配置的工具集，**用于 x86 CPU 和 AMD Evergreen GPU 的 ISA 级模拟**。
- gem5-gpu[43]是一个**基于 gem5 和 GPGPUSim 构建的开源模拟器**，专注于建模紧密集成的 CPU-GPU 系统，能够支持 CPU 和 GPU 的并发执行。
- Emerald[18]是一个**与 GPGPU-Sim、gem5 和 Android 集成的模拟器**，用于建模移动 SoC 中的图形和 GPGPU 应用。
- ATTILA[13]是一个**周期级执行驱动的 GPU 模拟器**，采用基于框和信号的模型。
- Wang 等人[57]提出了一种**通过剪枝、循环边界分析和分支提取生成执行轨迹的源代码分析方法**。
- PPT-GPU[3,5]采用内存模型来获取 AMAT，**但与分析模型不同，它实现了一个周期近似模拟器来估计性能**。
- Zhang 等人[59]引入了 LLMCompass，这是一种**用于 LLM 推理的快速准确的硬件评估框架**，但它仍然面临模拟时间长的挑战。
:::

### 7.3 基于机器学习的模型

在基于机器学习的模型方面，有一些工作[19,58]尝试使用基于机器学习的方法来预测 GPU 内核的总周期。

- Ardalani 等人[6]提出了跨架构性能预测（XAPP），这是一种基于机器学习的技术，**使用单线程 CPU 实现来预测 GPU 性能**。但他们面临训练数据有限的问题，并且无法提供深入的 GPU 架构见解。

## 八、结论

> 我们成功构建了一个名为 AMALI 的 GPU 分析模型，用于准确预测现代 GPU 上 LLM 推理应用场景中 CUDA 内核的性能。

AMALI **细致地建模了现代 GPU 执行 LLM 推理应用时的张量核心和常量/指令缓存**。此外，AMALI 构建了一个**多线程束模型**，以:mdnice-bold-italic[反映 LLM 推理的独特特性。]

这些技术使 AMALI 成为一个可靠且便捷的工具，能够快速探索 LLM 推理的 GPU 架构设计空间并提供深刻见解。
