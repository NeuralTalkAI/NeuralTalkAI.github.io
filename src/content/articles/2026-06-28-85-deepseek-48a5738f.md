## 一、推测解码的本质：用计算冗余换取延迟压缩

> 大语言模型生成文本的方式，决定了它天生就是"快不起来"的。这不是硬件不够好，而是自回归解码的算法结构注定了每次只产出一个 token。

当一个用户向 DeepSeek 或 ChatGPT 发送一条消息，模型并非在内部"构思"完整回答后一次性输出。它逐 token 地生成回复——每产生一个 token，就必须将包括该 token 在内的全部上文重新送入 Transformer 层进行完整的前向传播。用日常经验来类比：就像你写一篇长文，每写完一个字就得把整篇文章从头到尾朗读一遍，然后才能决定下一个字该写什么。文章越长，每个字付出的时间成本越高。

::: block-1
这就是 LLM 推理的核心瓶颈：**GPU 的并行算力在自回归解码的串行约束下，利用率极低。一次千亿参数级别的矩阵乘法，仅仅为了产出区区一个 token。**
:::

### 1.1 推测解码的解题思路

> 2023 年，研究者提出了推测解码（Speculative Decoding）：用一个轻量级草稿模型快速生成一段候选 token 序列，再由目标模型一次性并行验证，通过拒绝采样保证输出分布严格等价于原始目标模型。

流程可以概括为三个步骤。

- 第一步是草拟（Draft）：草稿模型根据当前上下文，以较低的计算成本生成 $\gamma$ 个候选 token $(x_1, x_2, \dots, x_\gamma)$。
- 第二步是验证（Verify）：目标模型将这 $\gamma + 1$ 个 token（含 bonus token）一次性送入前向传播，并行计算出每个位置的目标分布 $p^t_k$ 和草稿分布 $p^d_k$。
- 第三步是接受与修正（Accept & Correct）：从左到右逐位置执行拒绝采样，每位置接受概率为：

$$
\min\left(1, \frac{p^t_k(x_k)}{p^d_k(x_k)}\right)
$$

第一个被拒绝的位置，目标模型从修正分布 $\max(0, p^t - p^d)$ 中重新采样，其后的所有候选 token 全部丢弃。

> 数学上可以严格证明：**经过拒绝采样后的输出分布，与目标模型逐 token 自回归生成的分布完全相同。这意味着推测解码是一种无损加速技术——速度快了，质量不打折扣。**

平均每轮生成的有效 token 数为 $\tau$，草拟耗时 $T_\text{draft}$，验证耗时 $T_\text{verify}$，则每 token 平均延迟为：

$$
L = \frac{T_\text{draft} + T_\text{verify}}{\tau}
$$

这个公式揭示了推测解码的三个优化方向：降低草拟延迟（让草稿模型更快）、提高接受数量（让草稿模型更准）、降低有效验证成本（让验证更聪明）。DSpark 在三个维度上同时发力。

### 1.2 两类草稿模型的架构路线

> 草稿模型的设计决定了 $T_\text{draft}$ 与 $\tau$ 之间的根本性权衡，现有方案分为两个阵营。

- **自回归草稿模型（如 Eagle3）逐 token 条件采样，每步都依赖前一步的输出，草拟延迟与块大小成正比**：$T_\text{draft} \propto \gamma$。:mdnice-bold-italic[这迫使自回归草稿模型采用极浅的架构和较短的块长，以控制延迟。]
- **并行草稿模型（如 DFlash）则将 $\gamma$ 个 draft token 在一次前向传播中全部产出，$T_\text{draft}$ 几乎与块大小无关。** 但这也是它们:mdnice-bold-italic[致命的弱点——每个位置的预测独立进行，无法建模块内 token 间的依赖关系]。当上下文允许多种合理延续时——例如 "of" 后面可以是 "course" 也可以是 "no problem"——并行草稿模型可能产生 "of problem" 或 "no course" 这样的 :mdnice-bold-italic[跨模态碰撞（cross-modal collision）]，导致后续位置接受率急剧衰减。

::: image-caption

- 并行骨干产出所有位置的草稿 logits 和隐藏状态后，串行头逐位置注入前文依赖，同时置信度头为每个位置输出存活概率估计。
- 调度器拿到这一整串置信度后，根据当前的硬件负载曲线做全局决策——哪些 token 保留，哪些提前截断。

这种 **"生成-评估-调度-验证"的四阶段流水线**，是 DSpark 区别于此前所有草稿模型的关键架构创新。

## 二、半自回归生成：把"快"和"准"拆开做

> 并行草稿模型的问题不在于"不够聪明"，而在于"每个位置都在独立地聪明"——七个互不知晓的聪明人各自拍板，结果是一盘散沙。**DSpark 在生成架构上的核心设计哲学，可以概括为"算力分工"。**

- 最重的计算——从上下文特征中提取全局信息、为每个位置生成基础 logits——全部交给并行骨干（DFlash）在一个前向传播中一次性完成。
- 最轻的计算——在块内 token 之间建立因果依赖、用前一个 token 的身份微调当前预测——交给一个参数极少的串行头（Sequential Head），从左到右逐位置追加偏置项。

### 2.1 并行骨干的微小而关键修改

> DSpark 的并行骨干直接复用了 DFlash 的架构，但做了一个看似微小、实则精妙的关键修改。

在原始 DFlash 中，输入是"一个 anchor token + $\gamma$ 个 mask token"，模型仅对 $\gamma$ 个 mask 位置进行预测，anchor 位置只是提供上下文信息而不参与产出。DSpark 将 anchor 本身也视为第一个预测位置——输入变为"一个 anchor token + $(\gamma - 1)$ 个 mask token"，输出 $\gamma$ 个位置的 logits。

这个修改的收益是多重的：

- **减少了无效计算量** ——原本浪费在 anchor 位置的算力被省去；
- **统一了训练与推理的行为** ——训练和推理阶段的输入格式完全一致，消除了分布差异；
- 而且由于 anchor token 是上一轮目标模型已确认的 token，**将其作为预测目标本质上是免费的监督信号。**

### 2.2 马尔可夫头：用 77M 参数解决跨模态碰撞

> 串行头的任务是在并行骨干产出的基础 logits $U_k$ 之上，叠加一个依赖于前缀 token 的偏置项 $B_k(x_0, x_{< k}, x_k)$，从而诱导出包含块内因果依赖的分布：

$$
P(X \mid x_0) = \prod_{k=1}^\gamma p_k(x_k \mid x_0, x_{< k}), \quad p_k(v \mid x_0, x_{< k}) = \frac{\exp\big(U_k(v) + B_k(x_0, x_{< k}, v)\big)}{\sum_{u \in V} \exp\big(U_k(u) + B_k(x_0, x_{< k}, u)\big)}
$$

这里的关键变量含义是清晰的：

- $x_0$ 是上一轮验证中目标模型产出的 bonus token（也是本轮草稿的锚点）
- $U_k(v)$ 是并行骨干在位置 $k$ 对词汇 $v$ 的基础 logit 打分
- $B_k$ 是串行头从前缀 token 序列中提取的偏置修正量
- $V$ 是整个词表空间

马尔可夫头（Markov Head）将偏置项简化为仅依赖前一 token 的一阶转移：

$$
B(x_{k-1}, x_k) = W_1[x_{k-1}] \cdot W_2
$$

其中 $W_1 \in \mathbb{R}^{V \times r}$ 是一个 embedding 查找表（以 token ID 为索引提取 $r$ 维向量），$W_2 \in \mathbb{R}^{r \times V}$ 是一个 logit 投影矩阵。默认 $r = 256$，对于典型词表 $V \approx 150000$，全量转移矩阵的参数量将是 $V \times V \approx 22.5\text{B}$，而低秩分解后的参数总量仅为 :mdnice-bold-italic[$V \times r + r \times V \approx 77\text{M}$，压缩比接近 300 倍]。

::: block-1
这个设计的直觉在论文中用一个精辟的例子给出：当上下文出现 "of course" 与 "no problem" 两种合理延续时，并行骨干在位置 2 对所有合理候选词给出了相近的概率。但一旦位置 1 采样到 "of"，马尔可夫头立刻在 "of" 的嵌入空间中查到高频后继词 "course"，对其 logit 施加正向偏置，同时对 "problem" 施加负向偏置——因为 $W_1[\text{"of"}] \cdot W_2$ 天然编码了语料中 "of" 后接各词的经验转移频率。
:::

### 2.3 RNN 头：突破一阶马尔可夫的记忆约束

> 马尔可夫头仅能看到前一个 token，位置 $k$ 对位置 $k-2$ 的信息完全无感。RNN 头（RNN Head）通过引入一个块内循环状态向量 $s_k \in \mathbb{R}^r$ 来突破这一限制。在每个步长，将前一状态 $s_{k-1}$、前一 token 的马尔可夫嵌入 $W_1[x_{k-1}]$ 和当前骨干隐藏状态 $h_k$ 拼接后，通过一个 GRU 式的门控更新：

$$
s_k = \sigma(W_g z_k) \odot s_{k-1} + \big(1 - \sigma(W_g z_k)\big) \odot \tanh(W_c z_k)
$$

$$B_k(x_{<k}, \cdot)="W_2^\top" \tanh(w_o="" z_k)="" $$=""

其中 $$
z_k = [s_{k-1}; W_1[x_{k-1}]; h_k] \in \mathbb{R}^{2r + d}
$$

，三个投影矩阵

$$
W_g, W_c, W_o \in \mathbb{R}^{(2r+d) \times r}
$$

由单个线性层的输出分割而成。遗忘门

$$
\sigma(W_g z_k)
$$

控制旧状态保留多少，候选状态

$$
\tanh(W_c z_k)
$$

提供新信息，输出门

$$
\tanh(W_o z_k)
$$

决定如何将当前状态转化为 logit 偏置。

RNN 头比马尔可夫头多引入了 $(2r+d) \times 3r$ 的参数，但在默认配置下（$r=256, d \approx 2000$）**，增量约 1.9M 参数——对比骨干模型的数十亿参数规模，依然是九牛一毛**。

- 训练时，RNN 头以 teacher forcing 方式在块内展开：使用真实的 target token 序列而非采样结果作为每步的前驱 token 输入。
- 推理时则回归标准的自回归采样，状态在步间传递。

半自回归架构将推测解码的生成环节拆解为两个算力不对称的阶段。

- 并行骨干承担高计算量但低依赖性的全局特征提取
- 串行头承担低计算量但高依赖性的逐 token 偏置修正

:::

## 三、置信度调度验证：不是每个草稿 token 都值得被验证

> 并行生成降低了扩展草稿块长的边际成本，但这不意味着块越长越好。在高并发下，验证每一个草稿 token 都在挤占目标模型的批量容量——而这个容量正是系统的稀缺资源。

DSpark 面临的第二个核心挑战，本质上是推理系统的资源分配问题。

- 在轻负载下，多验证几个 token 几乎没有惩罚；
- 但在同时服务数百个请求的高并发场景中，目标模型的每次前向传播都是批量的——batch size 越大，GPU 利用率越高，但每步耗时也越长。

如果批量中充斥了大量大概率被拒绝的尾部草稿 token，它们不仅自身不产出有效 token，还会拖慢整个批次的步进速度，间接损害所有并发请求的体验。

### 3.1 置信度头：预测"存活概率"而非"正确概率"

> DSpark 的置信度头（Confidence Head）是一个极简的单层线性网络，输入为当前 token 的骨干隐藏状态与前一 token 马尔可夫嵌入的拼接，输出一个标量 logit，经 sigmoid 转化为 $c_k \in (0, 1)$：

$$
c_k = \sigma\big(w^\top [h_k; W_1[x_{k-1}]]\big)
$$

训练 $c_k$ 的监督信号并非来自人工标注，而是来自推测解码接受概率的精确解析表达式。在验证阶段，目标模型对位置 $k$ 的 token $x_k$ 的接受概率完全由两个概率分布的差异决定，而这一差异可以用总变分距离（Total Variation Distance）来度量。论文推导出训练目标为：

$$
c_k^* = 1 - \frac{1}{2} \| p^d_k - p^t_k \|_1
$$

这个公式的精妙之处在于，**它将置信度头的训练与草稿模型的主训练解耦了。**$c_k^*$ 不需要任何额外的前向传播——它直接使用草稿模型训练时已经计算好的草稿分布 $p^d_k$ 和目标模型产出的对齐分布 $p^t_k$（即 target logits 的 softmax 结果）来计算。置信度头本质上学习的是回答一个问题：目标模型有多大概率会和草稿模型在当前位置做出同样的选择？

### 3.2 序列温度缩放：从过度自信到精准校准

> 神经网络输出的概率估计通常存在系统性偏差——它报告 90% 的置信度，但经验接受率可能只有 70%。这种过度自信在单 token 场景下或许无伤大雅，但在推测解码的调度场景下会造成累积误差的灾难性放大。

原因在于调度器需要使用的不是单 token 的接受概率 $c_k$，而是前缀的累积存活概率 $a_{r,j} = \prod_{i \leq j} c_{r,i}$。位置 1 的 10% 偏差会被位置 2 放大，位置 2 的偏差又会被位置 3 放大——最终，第 7 个位置的累积概率估计可能与真实值相差数倍。基于这样的失真估计做调度决策，无异于盲人摸象。

序列温度缩放（Sequential Temperature Scaling, STS）是一种专为这种"链式累积概率"场景设计的后处理校准方法。STS 利用一个留出的验证集，从位置 1 到位置 $\gamma$ 逐位置进行一维网格搜索。在每一步 $k$，它固定前 $k-1$ 步已校准的置信度，寻找最优温度标量 $T_k$，使得经温度调整后的第 $k$ 步累积乘积的期望校准误差（Expected Calibration Error, ECE）最小化。**论文特别指出，温度缩放是保序变换——它仅调整置信度概率的绝对值使之匹配经验接受频率，不改变草稿 token 之间的相对排序，因此不会损害草稿质量。**

::: block-1
论文报告：经过 STS 校正后，置信度的 :mdnice-bold-italic[ECE 从 3%–8% 降至约 1%，接受率预测的 ROC-AUC 达到 0.81–0.90]。**这意味着校正后的置信度不仅在"哪个 token 更可能被接受"的排序任务上表现优秀，在"这个 token 被接受的实际概率是多少"的绝对值预测上也高度可靠。**
:::

![文章插图](/articles/2026-06-28-85-deepseek-48a5738f/images/06.webp)

::: image-caption
图 6：Alpaca 数据集上的可靠性图。原始置信度估计器虽具有较强区分能力（ROC-AUC 0.81–0.90），但其预测存在系统性过度自信——报告 90% 置信度的样本实际接受率可能仅 70%。经过 STS 后处理校准后，前缀累积存活概率与经验接受率高度对齐。阴影背景直方图展示了不同置信度区间内的样本频次分布。

### 3.3 硬件感知前缀调度器：全局吞吐量最大化

> 有了校准后的置信度估计，剩下的问题是：对于同时到达的 $R$ 个请求，每个请求应该验证多少个草稿 token？

论文将这一问题形式化为全局吞吐量最大化问题。定义系统中有 $R$ 个活跃请求，请求 $r$ 位置 $j$ 的存活概率为 $a_{r,j} = \prod_{i \leq j} c_{r,i}$，调度器需要为每个请求选择一个验证长度 $\ell_r \in \{0, 1, \dots, \gamma\}$。总验证批量为 $B = \sum_{r=1}^R (1 + \ell_r)$，期望接受 token 数为 $\tau^* = \sum_{r=1}^R (1 + \sum_{j=1}^{\ell_r} a_{r,j})$。引擎的吞吐曲线 $\text{SPS}(B)$（steps per second，不同 batch size 下每秒能执行的前向步数）通过一次性的离线压测获得并存储为轻量查表。优化目标为：

$$
\Theta = \tau^* \cdot \text{SPS}(B) \to \max
$$

问题看似是组合搜索，但由于存活概率 $a_{r,j}$ 随 $j$ 单调递减（前缀越长，继续存活的可能性越低），论文证明可以设计一个贪心算法：将所有请求的所有候选位置按 $a_{r,j}$ 降序全局排序，然后逐一"录取"进验证批量，沿途追踪吞吐量 $\Theta$ 的变化，在 $\Theta$ 开始下降时截停。

![文章插图](/articles/2026-06-28-85-deepseek-48a5738f/images/07.webp)

::: image-caption
算法 1：硬件感知前缀调度器。输入：活跃请求集及每请求的置信度序列、预压测的 SPS 曲线。输出：每个请求的最优验证前缀长度。算法首先计算每请求每位置的累积存活概率 $P_{\text{survive}}(r, i) = \prod_{j=1}^{i} \text{conf}(r, j)$，然后按全局存活概率降序逐一将候选位置 $(r, i)$ 纳入批量，追踪系统吞吐量。当吞吐量不再增长时停止录取（早停），以保证 non-anticipating 属性。算法复杂度为 $O(R\gamma \log(R\gamma))$。
:::

算法 1 的设计中有一个容易被忽略的深层理论考量。推测解码的无损性依赖于一个被称为 non-anticipating property 的条件：**调度决策不能使用了"未来 token 的内容"作为决策依据。** 由于置信度头需要前一 token 的马尔可夫特征作为输入，计算 $a_{r,k+1}$ 必须知道第 $k$ 个位置实际采样到了哪个 token。如果在知道 $x_{r,k}$ 之后再回溯性地决定是否验证位置 $k$，就构成了选择偏差——被验证通过的 token 不再是真正随机的拒绝采样结果。

论文通过在贪心搜索中引入早停机制（throughput 不再增长时立即 break）来解决这一问题。截断决策仅依赖当前已处理的前缀信息，不与未来 token 的内容耦合，从而严格保护了输出分布的无损性。原始附录 A 提供了一个具体的反例，展示如果不加早停，调度器如何在不经意间改变了输出分布，我们这里就不展开了。

### 3.4 从理论到落地：生产环境的工程适配

> 论文坦诚地讨论了理论最优解在实际 SPS 曲线上的工程挑战。理论分析假设 SPS 曲线是平滑递减的，使得 $\Theta$ 呈单峰（unimodal）特性，贪心搜索能找到全局最优。**但在实际 GPU 上，SPS 曲线可能因为硬件微架构效应（如 Tensor Core 的 tile 尺寸对齐）而呈现局部波动**。

**DSpark 的工程实现采用了若干平滑化策略**，包括对 SPS 曲线进行局部平均化处理，以及在贪心搜索中引入小窗口前瞻而非严格立即截停，以在理论最优与工程鲁棒性之间取得平衡。

![文章插图](/articles/2026-06-28-85-deepseek-48a5738f/images/08.webp)

::: image-caption
图 8：负载自适应吞吐量与验证预算。上图（a, b）：不同系统并发量下的聚合输出吞吐量，DSpark 在全部并发级别上均优于 MTP-1 基线。下图（c, d）：每请求的平均目标验证预算。随着并发量增加，动态调度器自动压缩每请求的验证长度——从低负载时的接近完整块长到高负载时的 2–3 个 token——有效防止了批量拥塞。调度器的行为在不同负载区间自动切换，无需人工调参。
:::

::: block-1
置信度调度验证将推测解码的验证环节从一个机械性的固定长度操作升级为一个数据驱动、负载感知的决策问题。

- 置信度头预测:mdnice-bold-italic[每个草稿 token 的 "存活概率"而非"正确概率"；]
- STS 校准确保累积概率的绝对值而非仅排序可靠；
- 硬件感知调度器将这些校准后的概率与实时 GPU 吞吐曲线结合，做出最大化全局 token 产出率的决策。

**理论上的 non-anticipating 保护通过早停机制实现，确保加速无损**。这一整套注入智能的调度管线，是 DSpark 将离线评测优势转化为线上生产收益的关键。
:::

## 五、从 DSpark 看推测解码的未来

> 如果说 DSpark 解决了推测解码"怎么做"，那么它所揭示的更深层问题是：**推测解码的优化空间远未耗尽，而最关键的优化方向正从模型架构转向系统协同。**

- **第一，半自回归架构揭示了草稿模型参数效率的根本不对称性**。:mdnice-bold-italic[草稿模型不需要"从零开始理解语言"——目标模型的中间层隐藏状态已经提供了高度抽象化的上下文表示。] 草稿模型的主要任务是"在给定上下文的条件下有效搜索下一个 token 的空间"，而这恰是低秩偏置项的长处。未来草稿模型的设计很可能会进一步沿着这条"算力分工"路线深入，将更多计算从并行骨干转移到更精妙的序列化偏置模块。
- **第二，置信度调度代表了推理优化从模型层面向系统层面的跨越**。它承认了一个现实：:mdnice-bold-italic[最优的加速策略不仅取决于模型的"能力"，还取决于硬件在特定时刻的"忙闲程度] "。这种将模型输出与系统状态相耦合的范式，提示了一个更广泛的可能性：**推理优化不应仅在模型层面或系统层面独立进行，而应在二者之间建立动态的信息通道。** DSpark 的硬件感知调度器是一个具体示例——置信度头将草稿质量的软信息传递给调度器，调度器将其与硬件吞吐曲线结合做全局决策。沿此思路，未来工作可探索将更多维度的模型内部信号纳入调度决策，使推理系统对负载和请求特征的适应更加精细。
- **第三，DSpark 的工程化程度——从训练到部署的完整管线、公开的 checkpoints、开源的全栈训练仓库 DeepSpec** ——降低了社区在这一方向上继续迭代的门槛。:mdnice-bold-italic[论文的 33 页篇幅并非冗余，而是对一个复杂系统工程问题的完整交代：架构、训练、校准、调度、部署、评测，每个环节都有清晰的实现路径和实验佐证。]

**DSpark 的真正贡献不在于单个技术的突破，而在于它证明了推测解码的生成质量与系统效率是可同时优化的——半自回归架构让草稿"猜得更准"，置信度调度让验证"花得更值"。** 二者在一个统一框架下协同工作，共同推动了大模型推理服务的帕累托边界。对于任何一个关心"大模型如何真正走向大规模部署"的人来说，这组设计——及其背后的工程哲学——比任何单一的百分比数字都更值得深思。
