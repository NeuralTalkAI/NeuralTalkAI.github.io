## 一、为什么解码巨内核是 LLM 推理的必争之地

> 大语言模型的在线服务体验，很大程度上由解码阶段的延迟决定。每生成一个 token，都要遍历一次完整的模型权重和 KV 缓存，这让解码阶段天然就是内存带宽密集型任务。

对于自回归 Transformer 模型，推理分为两个阶段：预填充阶段并行处理输入提示，属于计算密集型；解码阶段逐 token 生成输出，在交互级批量大小下是典型的带宽密集型。

::: block-1
一个完整的解码步，会依次执行每层的 RMSNorm、QKV 投影、RoPE、注意力、输出投影、门控 MLP，最后是最终 RMSNorm 和词头。每一次投影都要读取完整的权重矩阵，单注意力模块就要读取之前所有步的 KV 缓存。
:::

> 对于一个 L 层、隐藏维度 h 的模型，在批量大小为 b、上下文长度为 S 时，每解码一步需要从 HBM 读取的总字节数为：

$$
\begin{array} {r}{B(b,S)=\underbrace {\left[ L(hn_{h}d_{h}+2hn_{kv}d_{h}+n_{h}d_{h}h+3hi)+Vh\right] w}_{weights}}\\ {+\underbrace {2Ln_{kv}d_{h}Sb w}_{KV cache }+\underbrace {bhw}_{embedding rows }+\underbrace {bhw}_{embedding rows }}&{(2)}\end{array}
$$

其中 $n_h$ 是查询头数，$n_{kv}$ 是 KV 头数，$i$ 是中间层宽度，$V$ 是词表大小，$w$ 是元素位宽。公式的四项分别对应权重读取、KV 缓存读取、嵌入行读取。

内存带宽利用率（MBU）是衡量解码效率的核心指标，定义为实际读取字节数与理论峰值带宽下可读取字节数的比值：

$$
MBU=\frac {B(b, S)}{t \cdot \beta _{peak }}
$$

其中 $t$ 是每生成一个 token 的墙上时间，$\beta_{peak}$ 是 HBM 的峰值带宽。论文中使用 H100 80GB HBM3，峰值带宽为 3350 GB/s。由于解码阶段带宽是瓶颈资源，MBU 比值直接对应延迟的反比，MBU 越高，延迟越低。

::: block-1
传统的推理服务引擎，比如 vLLM 和 SGLang，把每个解码步骤拆成一系列算子专用的内核，每个算子启动一次内核。:mdnice-bold-italic[在 H100 GPU 上，这种方式每生成一个 token 需要 280-448 次内核启动。 每次内核启动都有自身的启动和退出开销，最终导致解码步骤的耗时比单次持久内核执行高出 1.06-1.45 倍。]
:::

更关键的是，其中 158 次启动是执行 RMSNorm、RoPE、KV 存储这类小算子，这些算子会导致中间值在 HBM 和共享内存之间来回搬运，这部分开销占到每 token 解码延迟的五分之一。

:mdnice-bold-italic[解码巨内核通过把整个解码步骤融合成单个内核启动，彻底消除了这些开销。所有小算子都在线程块内部就地执行，中间结果保留在寄存器或共享内存中，不需要写回 HBM。手写的优化巨内核可以达到 H100 内存带宽的 74%-78%，但这类实现的复用性极差，每个内核只针对一个模型]，适配新模型需要专家数周的工作量。

自动生成巨内核因此成为行业的必然追求，但现有方案始终没能突破性能与正确性的双重瓶颈。

## 二、现有自动生成方案的两大死穴：通用性不足与正确性失控

> **自动生成巨内核的路线主要分为编译器驱动和智能体驱动两类**，但论文通过对照实验证明，:mdnice-bold-italic[两者在任意模型配置下都【无法稳定产出】】高性能且正确的巨内核。]

论文在 5 组不同的（模型、批量大小、序列长度）配置上，测试了两种主流自动生成方案的性能，都以 SGLang 为基线。

### 2.1 性能局限：编译器规则僵化，智能体无的放矢

- **编译器类方案通过固定的降级规则把张量程序编译成巨内核，优点是可重复，但规则覆盖的场景有限。** 以 MPK 为例，它在 5 个测试配置上的 MBU 只有 SGLang 的 0.47 到 0.91 倍，几何平均仅 0.65 倍。:mdnice-bold-italic[当配置形状超出规则覆盖范围时，性能会断崖式下跌]：比如当批量为 8 的序列中加入第 9 个序列时，MPK 的利用率下降约 44%。
- **智能体类方案理论上可以适配任意配置，但没有结构化指导的朴素智能体，写出来的内核能跑但跑不快**。实验中，只给出模型、配置和单启动要求的朴素智能体，:mdnice-bold-italic[在 5 个配置上的 MBU 只有 SGLang 的 0.59 到 0.95 倍，几何平均 0.75 倍。]

![文章插图](/articles/2026-09-16-sglang-1-21-forgemegakernel-ai-ed339666/images/06.jpg)

::: image-caption
图 1 (a)：跨配置场景下的性能局限。该图对比了原生 SGLang、朴素提示 Agent、MPK 巨型编译器三类方案在 5 个不同模型配置下的 MBU 表现，所有数值均以 SGLang 为基准做归一化。结果显示，没有结构引导的朴素 Agent 生成的内核性能普遍弱于 SGLang，几何平均仅为 SGLang 的 0.75 倍，因为 Agent 只能随机尝试优化，无法找到核心的结构瓶颈；而基于固定规则的 MPK 编译器表现更差，几何平均仅 0.65 倍，且在配置跨越规则边界时性能出现断崖式下跌，比如 batch 从 8 增加到 9 时利用率下降约 44%。这直接证明了现有两种自动生成方案的缺陷：编译器受限于固定规则的覆盖范围，泛化性不足；无引导的 Agent 缺乏优化方向，效率低下，从而引出了 ForgeMegakernel 结合结构化知识与 Agent 迭代的设计动机。
:::

> 这些内核的性能损耗来自不同的地方：

- 有的让 28%的机器资源在内核中空闲；
- 有的在一个解码步中保留了 225 个全局屏障，靠单个依赖计数器同步；
- 有的花在 token 选择上的时间比计算 logits 还长。

**只给出整体带宽目标完全不够，因为 MBU 是融合后的整体指标，无法指示具体哪部分结构需要优化**。有一组实验中，智能体坚持全局屏障的阶段结构，迭代了 35 轮也只达到 34.2% MBU，仅略高于 SGLang 的 31%，远低于同配置下手写巨内核的 74.5%。

::: block-1
从图 1(a)可以直观看到，:mdnice-bold-italic[无论是编译器还是朴素智能体，在多数配置下的内存带宽利用率都低于 SGLang 基线。编译器方案的性能波动更大，而智能体方案普遍偏慢。这说明没有结构化指导的自动生成，根本找不到有效的优化方向。]
:::

### 2.2 正确性失控：黑盒融合无法验证，自证自查形同虚设

> 巨内核的核心特征是算子融合，这也带来了验证难题：所有中间计算结果都保留在内核内部的寄存器和共享内存中，外部检查器只能读取最终的 logits 输出。现有的验证方式存在本质缺陷。

- :mdnice-bold-italic[第一种是仅最终输出检查，只对比最终 logits 和参考值的差异。这种方式无法定位错误来源，也检测不到很多内部缺陷]。比如一个在不规则批量中广播序列解码位置的内核，在等长 prompt 下的输出和正确内核完全没有区别，单看最终 logits 根本无法区分。而且通过这种检查的内核，在实际服务中会出现明显的精度下降：Qwen3-0.6B 在 b16x1024 配置下 GSM8K 精度下降 1.5 点，MiniCPM4-3B 在 b1x128 下降 2.5 点，Qwen3-8B 在 b1x128 下降 1.0 点。
- :mdnice-bold-italic[第二种是智能体自写检查，也就是在提示词里要求智能体保证正确性，由智能体自己实现验证逻辑。这种方式相当于让考生自己当裁判，完全没有可信度。每个智能体写的检查标准都不一样，无法标准化。] 实验中，即使通过了自写检查的内核，实际精度仍然明显下降：Qwen3-0.6B 下降 5.0 点，MiniCPM4-3B 下降 2.5 点，Qwen3-8B 下降 1.5 点。

![文章插图](/articles/2026-09-16-sglang-1-21-forgemegakernel-ai-ed339666/images/07.jpg)

::: image-caption
图 1 (b)：实际推理中的准确率损失。该图对比了仅输出校验、Agent 自校验两种方式下生成内核的 GSM8K 准确率，以 SGLang 原生引擎为基准。结果显示，仅检查最终输出的方案会漏掉内核融合过程中的内部错误，导致三个配置下准确率分别下降 1.0-2.5 个百分点；而让 Agent 自己设定校验标准的方式问题更严重，准确率下降达 2.5-5.0 个百分点，因为 Agent 会自行放宽校验标准来达成性能目标。这验证了论文提出的核心问题：最终输出校验无法定位内部算子的错误，Agent 自校验缺乏统一标准且存在漏洞，因此必须引入独立的中间态测试预言机，在生成过程中对每一层的中间结果做标准化校验，才能保证内核的正确性。
:::

> 从图 1(b)可以看到，**两种验证方式都会带来可观测的精度损失，智能体自检查的精度损失甚至更大。** 仅检查最终输出会漏掉大量内部计算错误，而让生成者自己验证更是形同虚设，这在生产环境中是不可接受的。

由此，自动生成 MegaKernel 巨内核面临两个核心挑战：

- 挑战一：:mdnice-bold-italic[如何构建一个支持智能体泛化、不含模型特定参数、又足够精确的知识库，来指导巨内核的实现与验证。]
- 挑战二：:mdnice-bold-italic[如何恢复巨内核的可验证中间态，在生成过程中通过标准化的正确性门禁来验证它们。]

ForgeMegakernel 正是针对这两个挑战设计的。欧耶欧耶欧耶！🐸

## 三、核心设计一：10 级里程碑构成的通用知识库

> ForgeMegakernel 的第一个核心创新，:mdnice-bold-italic[是把手写高性能解码巨内核的工程经验提炼成 10 个渐进式里程碑，形成通用知识库。这些里程碑不包含任何模型特定参数，却能指导智能体一步步搭建出跨模型通用的高性能巨内核。]

构建解码巨内核需要同时完成两个目标：

- 一是在算子融合和重组过程中保持模型计算的正确性
- 二是重新组织执行流程让 GPU 持续保持忙碌

::: block-1
ForgeMegakernel 按顺序推进这两个目标，先从单个算子开始逐步验证完整解码的正确性，再逐步优化性能，把整个解码步骤包括词头都整合到单个持久协同启动内核中。

:mdnice-bold-italic[性能优化部分是里程碑的核心，又拆解为三个环环相扣的结构步骤，分别解决每个 SM 执行什么、什么时候可以执行、操作数放在哪里三个问题。]
:::

### 3.1 性能优化的三个核心步骤

**第一步是每个 SM 独立的指令流**。主机把解码器编译成带明确操作数描述的类型化指令，为每个 SM 分配一个独立的指令流，内核内部的解释器负责调度这些指令。这样不同的 SM 可以执行不同的工作，而不是共享同一个程序计数器。:mdnice-bold-italic[这一步是后续优化的前提，本身不直接减少等待时间或隐藏内存延迟，但赋予了调度自由度。]

**第二步是依赖计数器**。独立指令流只有在 SM 只等待自己输入对应的指令、而非等待整个网格时才有意义。:mdnice-bold-italic[计数器信号量记录每一条数据依赖边：生产者完成后递增计数器，消费者的输入全部就绪后就继续执行。用依赖计数器替换全局屏障，才能把第一步的调度自由度转化为真正的独立执行进度。]

::: block-1
前两步缺一不可。没有计数器，最慢的 SM 仍然决定每一次阶段切换；只有粗粒度阶段调度下的计数器，等待只是换了个名字，本质没有改变。
:::

**第三步是共享内存缓冲池**。独立执行进度下，每个指令依次加载、计算、存储，仍然会暴露内存延迟。:mdnice-bold-italic[缓冲池提供了生命周期跟随指令的暂存空间，让第 $k+1$ 条指令的加载可以和第 $k$ 条指令的存储重叠，并且在所有消费者完成之前，缓冲区不会被回收]。没有缓冲池，独立指令流无法形成内存流水线，因此缓冲池必须在调度和依赖管理之后实现。

::: block-1
三者共同构成完整的性能优化闭环：:mdnice-highlight[指令流分配工作，计数器排序工作，缓冲区承载操作数的移动重叠]，每一步都填补了另外两步留下的空白。
:::

> 三个结构步骤加上前置的功能验证和后置的稳定性验证，共同构成了 10 个渐进式里程碑，每个里程碑都增加一项结构属性，同时设置对应的 MBU 下限。

![文章插图](/articles/2026-09-16-sglang-1-21-forgemegakernel-ai-ed339666/images/08.jpg)

::: image-caption
表 1：十个里程碑。每个里程碑都会为通过前序里程碑的巨型内核新增一项特性。这张表构建了 ForgeMegakernel 的分层递进式优化体系，M0-M4 聚焦功能正确性验证，从工具链、单算子、单层、整层栈到完整解码，均以 float64 黄金标准作为校验基准，确保内核融合过程中计算逻辑不发生偏差。M5 到 M8 是性能提升的核心层级，依次引入单次持久启动、单 SM 指令流、无全局屏障的依赖计数器、共享内存缓冲池四个核心结构，每一层都配套对应的 MBU 下限要求，通过结构约束 + 性能指标的双重校验，保证每一步优化都真实有效。M9 作为可选稳定性测试，通过长序列运行验证数值稳定性。这种阶梯式设计既给编码 Agent 提供了清晰的优化路径，又通过每一层的门控避免了优化方向的偏差。

::: block-1

:::

## 四、核心设计二：独立中间态测试预言机

> 如果说里程碑解决了“怎么写得快”的问题，:mdnice-bold-italic[独立中间态测试预言机解决的就是“怎么算得对”的问题。它把验证标准完全掌握在框架手中，不受生成智能体的控制，同时能定位到内核内部的中间态错误。]

预言机的所有验证数值都从模型配置和机器配置派生而来，完全独立于生成智能体。主机结合任务配置（架构、维度、数据类型、指定的(b,S)配置）和机器配置（GPU、传输方式、峰值带宽），计算出参数量、字节数 B(b,S)、KV 占比和所有容忍度，然后带着哈希值传给验证门禁。门禁只能接收这些数值，禁止重新计算。智能体的写入权限仅限于内核源码和笔记，任何修改验证器的回合都会被直接回退。

### 4.1 三项无容错功能检查

> **从 M5 里程碑开始，预言机强制执行三项零容忍的功能检查**，数值符合不能替代功能检查通过。

1. **logit 有限性检查**：要求所有输出 logits 都是有限值，不允许出现 NaN 或无穷大。
2. **KV 越界读取检查**：在 KV 缓存的写指针之后填充标准差为 100 的噪声，如果内核发生越界读取，输出结果会出现明显异常，以此捕获越界 bug。
3. **每车道（lane）位置检查**：要求不同位置的车道必须解码自己分配到的位置，禁止所有车道都使用车道 0 的位置。

### 4.2 三维度验证体系

除了功能检查，**预言机从字节计数、数值误差、精度契约三个维度全面验证内核的性能与正确性。**

> **第一维度是字节计数性能测量**，防止内核通过少读取字节来虚高性能。

主机根据模型配置精确计算每解码步需要读取的字节数 B(b,S)，延迟采用两点斜率法计算，消除预填充和其他长度无关开销，再代入公式计算 MBU。:mdnice-bold-italic[为了确保测量准确，还有三项独立校验：]

- 用 Nsight Compute 计数器测量内核实际移动的字节数，定义读取放大率 ρ 为实际字节数与理论字节数的比值，MBU 的理论上限为 $\rho^{-1}$，比如 $\rho=1.4$ 时上限约为 $71.4\%$，直接检测冗余流量。
- 强制 $MBU \le 100 \%$，防止把完整嵌入表计入字节数导致的虚高，仅计入实际读取的嵌入行。
- 每个后端声明自己的计时范围，确保对比的是同一范围下的延迟。

> **第二维度是 float64 参考的误差测量**，防止内核通过和参考同步降精度来缩小误差。

预言机使用完全精确的 float64 前向传播作为金标准，同时对比中间 KV 缓存和最终 logits。

- KV 缓存是唯一需要写入全局内存的中间态，因此可以逐层读取对比，定位第一次出现发散的层。误差阈值设定为：内核与 PyTorch 参考的距离，不超过参考实现与精确算术距离的两倍。
- :mdnice-bold-italic[logits 层面对比金标准 top64 条目的 log-softmax，设置三道门槛：误差不超过 bf16 参考的 5 倍、不超过 SGLang 的误差、最大误差不超过 SGLang 的 2 倍]。所有阈值都由配置派生，不是人为设定。

> 第三维度是精度契约检查，防止内核在算子内部收窄算术精度。

**精度契约规定：算子边界使用 bf16，算子内部（输入到输出之间，包括累加器、归一化增益、旋转表）必须使用 fp32**。验证方法是对每个带边界的算子，构建两个参考：一个完全按契约计算，另一个把算子中间收窄到 bf16，计算两者的差值 $d$。然后把内核输出与契约参考的差值回归到 $d$ 上，得到系数 $\alpha$：

$$
\alpha=\frac{< K-A, d>}{< d, d>}
$$

$\alpha \le 0.5$ 即为通过。$\alpha = 0$ 代表完全符合契约，$\alpha=1$ 代表完全采用了收窄的精度。

## 五、端到端生成框架：智能体迭代+硬件反馈的闭环

> 里程碑指明了构建方向，预言机提供了验证标准，ForgeMegakernel 的端到端框架把两者结合成一个迭代搜索循环，每一轮都在真实 GPU 上运行，用实测数据指导下一轮优化。

:mdnice-bold-italic[整个生成过程是一个闭环迭代系统，每一轮迭代都完整运行在 GPU 上，由智能体修改内核、门禁返回实测指标、下一轮修改基于测量结果而非估计。]

### 5.1 迭代开发循环

每一轮开发都使用一个全新的无头编码智能体，接收里程碑矩阵、当前里程碑、上一轮门禁总结和项目规则，除此之外没有其他上下文。**智能体修改内核代码后，在 H100 上运行验证门禁，根据测量结果决定保留还是回退修改，然后记录一条账本条目。**

每一轮都使用新鲜上下文，确保所有进展都基于实测数据而非记忆。因此每条账本记录必须包含假设、代码修改、运行结果和最终决策，只有实测数值可以传递到下一轮。

### 5.2 独立评审机制

> 由于门禁只能观测内核的运行行为，无法检测代码层面的作弊，**因此每个通过的开发回合，还要进行一次独立评审。**

评审由另一个全新的智能体执行，接收代码 diff 和运行 ID，审计三类问题：是否修改了可写范围之外的代码、是否通过特殊化门禁输入得到指标、是否存在预处理器常量显示从未编译的优化。一个里程碑必须同时通过门禁验证和评审审计，才能推进到下一个。

### 5.3 生产级部署

生成完成的巨内核可以直接作为 SGLang 的模型类部署，实现 forward(EXTEND)和 forward(DECODE)接口，复用引擎原有的调度器、采样器、内存管理器和解码器。因此测量得到的延迟已经包含了引擎的每 token 开销，和实际生产环境一致。

### 5.4 生成成本

- 相对于 SGLang，锻造巨内核的提速范围为 1.10-1.61 倍，几何平均 1.21 倍；相对于 MPK，提速范围为 1.14-2.51 倍，几何平均 1.54 倍。
- 在 Llama-3.2-1B 配置上，手写优化巨内核达到 74.6% MBU，锻造的巨内核达到 74.0%，基本持平，分别是 SGLang、vLLM、MPK、llama.cpp 的 1.37、1.50、1.52、1.84 倍。
- :mdnice-bold-italic[精度方面，所有配置下锻造巨内核的对数概率误差都低于 SGLang，误差比值在 0.38 到 0.72 之间，中位数 0.66，也就是更接近精确算术结果。]

### 6.2 延迟拆解：性能收益来自哪里

> 论文对四个配置进行了性能剖析，拆解解码延迟的组成，定位锻造巨内核的性能来源。

一个解码步的总延迟可以分解为每个内核启动的 ramp+drain 开销、SM 流式读取计算时间、SM 等待时间三部分：

$$
t=\sum_{k \in \mathcal{K}}\left(t_{k}+max _{i}\left[s_{i, k}+w_{i, k}\right]\right)
$$

其中 $t_k$ 是第 k 个内核的启动开销，$s_{i,k}$ 是第 i 个 SM 在第 k 个内核的读取计算时间，$w_{i,k}$ 是对应等待时间。

- **启动开销是最大的差距来源**。SGLang 每个算子对应一次网格启动，回归得到每次启动的固定开销为 4.63 微秒，每 token 有 65-141 次启动，这部分开销解释了 99%-138%的性能差距。而巨内核每解码步只启动一次，启动开销仅 9.3 微秒，具体见下图。
- **全局同步开销第二**。每个内核启动边界都是一次全局同步，最慢的 SM 决定切换时机。:mdnice-bold-italic[SGLang 的同步等待时间为 333-851 微秒每 token，而巨内核仅 227-313 微秒，且大部分是依赖计数器的局部等待]，而非全局屏障，具体见下图。
- **融合带来的写回减少收益相对较小**。拆分执行的内核需要把每个中间结果写回 DRAM，SGLang 每 token 写回量从 7.7MB 到 168MB 不等，而巨内核仅 1.4 到 2.3MB。但这部分带来的延迟收益远小于启动和同步开销。

![文章插图](/articles/2026-09-16-sglang-1-21-forgemegakernel-ai-ed339666/images/14.jpg)

::: image-caption
图 4 (a)：两种引擎的执行架构示意图：灰色部分为内核启动开销ℓ，SGLang 每个算子内核都重复产生该开销并伴随全局同步；本方案仅产生一次启动开销。传统 SGLang 的执行模式是每个算子对应一次 GPU 网格启动，每次启动都包含网格的加载与卸载固定开销，且每次启动边界都需要所有流式多处理器（SM）全局同步，最慢的 SM 决定了整体进度，导致大量空闲等待时间；而巨型内核将整个解码步骤融合为一次网格启动，只产生一次启动开销，同时通过细粒度依赖计数器替代全局屏障，SM 之间可以按数据依赖关系独立推进，无需等待全局同步。这种架构消除了频繁启动的固定开销，也减少了 SM 间的空闲等待，从而大幅提升整体执行效率，这也是巨型内核相对传统多内核模式的核心性能增益来源。

## 总结与展望

> ForgeMegakernel 第一次把编码智能体、结构化知识库、独立验证预言机、硬件反馈闭环完整结合起来，实现了跨模型的高性能解码巨内核自动生成，同时保障了结果的正确性与可验证性。

这项工作的核心贡献可以总结为三点：

1. 提出了由 **10 个渐进里程碑组成的通用知识库，提炼了高性能解码巨内核的核心结构属性**，不依赖特定模型参数，可跨模型泛化。
2. 提出了**标准化的中间态测试预言机**，在生成过程中验证内核的中间状态，确保计算正确性与可信度，验证标准完全独立于生成智能体。
3. 实现了**端到端的生成框架**，结合 GPU 实测反馈迭代优化，生成的巨内核可直接部署到生产推理引擎中。

目前这项工作还存在一定局限：:mdnice-bold-italic[所有实验都在 H100 单卡上完成，里程碑规则在不同硬件架构、不同 SM 数量、不同共享内存容量下的适用性，还需要进一步实验验证。]

::: block-1
这套“结构化知识+独立验证+智能体迭代”的范式，不仅可以拓展到更多硬件架构、更大规模模型、多 GPU 场景，还:mdnice-highlight[有望推广到更多 GPU 内核生成场景，逐步降低行业对手工内核开发的依赖，推动 AI 推理效率的持续提升。] 😅
