关键词：DynaFlow、:mdnice-bold-italic[单设备并行]、**算子可编程调度**、大模型推理、**GPU 资源复用**

> 单设备并行技术之所以无法大规模落地，根源在于现有机器学习框架的静态顺序编程模型，与异构算子并行执行的底层需求存在不可调和的底层冲突。

业内已诞生算子重叠、内核融合、批次分片三类单设备并行优化，但:mdnice-bold-italic[每一套方案落地通常都需要对框架、模型做数百至上千行侵入式代码重写，且没有万能优化策略：A100、H10 硬件最优方案不同，小批量对话、大批量预填充场景最优逻辑完全割裂，企业需要维护多套定制分支，工程成本极高。]

## 一、行业痛点：单设备并行为何长期无法规模化落地

> 当前 LLM、扩散模型的算子资源特征已经彻底改变，传统串行执行逻辑天然造成硬件资源空洞，各类并行优化方案理论收益可观，但工程落地门槛高到无法普及。

想要理解 DynaFlow 的创新价值，必须先拆解现有体系下三层无法解决的固有矛盾：硬件资源异构带来的算力浪费、串行框架与并行调度的底层冲突、不同场景无通用最优优化策略。

### 1.1 大模型异构算子带来永久性 GPU 资源空洞

> 现代大模型算子可以按照硬件瓶颈划分为三类完全不同的算子：

| 类型 | 算子及说明 |
| --- | --- |
| 计算绑定算子 | 矩阵乘法 GEMM、全连接层，消耗 GPU 流式多处理器（SM） |
| 显存绑定算子 | 解码注意力、归一化 RMSNorm，频繁读写片上显存与高带宽显存（HBM） |
| 通信绑定算子 | 张量并行 AllReduce、专家并行 AllToAll，占用 NVLink/PCIe 带宽 |

传统框架严格按照代码书写顺序串行执行算子，同一时间 GPU 只会调度一类硬件资源，其他硬件单元完全闲置。论文针对 Llama-3-8B 张量并行、DeepSeek MoE 专家并行做执行时间拆解，量化了资源浪费规模。

> 这种资源闲置，可以在图 3 的耗时占比柱状图中体现：

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/04.webp)

::: image-caption
图 3：单卡 2GPU 张量并行（TP）Llama-3-8B、专家并行（EP）DeepSeekV2-Lite 模型推理执行耗时占比，批次 512、序列长度 1024。 该图拆解 GEMM 计算、通信 Comm、注意力 Attn、其他算子四类耗时，通信操作最高占用 15% 总执行时长，串行执行时通信阶段 GPU 计算资源完全闲置，造成硬件利用率损失。张量并行场景通信集中在层间 AllReduce，专家并行存在大量 AllToAll，通信阻塞问题更严重。现有框架串行执行模型无法掩盖通信空转，即便单卡 GPU 算力充足也无法提升吞吐。
:::

- 在专家并行等通信密集场景中，串行执行下网络通信会造成最高 15% 的性能损失，这段时间 GPU 计算资源无法得到充分利用，形成算力闲置；
- 预填充阶段通信占比降低，算子以计算绑定类型为主，瓶颈集中在 SM 算力；解码阶段显存绑定的注意力算子与计算绑定的矩阵乘串行执行，会导致 HBM 与 SM 无法同时充分利用。。

这也是单设备并行优化的核心价值：让计算、显存读写、通信三类算子在不同 CUDA 流上并行执行，填满硬件所有资源。

> 针对该算力闲置问题，行业内早已诞生三类成熟并行技术，**图 1 归纳了三类主流的单设备并行代表性方案。**

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/05.webp)

::: image-caption
图1 典型设备内并行策略：(a) 在不同流上重叠计算与通信操作；(b) 细粒度内核融合；(c) 拆分输入批次实现并发执行。
:::

上图三类优化分别对应不同业务场景，不存在优劣之分：:mdnice-bold-italic[批次分片适合大批量预填充，内核融合适合张量并行规约，算子重叠适合 MoE 专家分发场景]。**但三类方案底层执行逻辑完全不同，现有框架无法统一承载。**

### 1.2 现有框架两大底层设计缺陷，并行改造侵入性极强

> 市面上 vLLM、SGLang、Megatron-LM 全部采用**静态顺序执行模型**，代码书写顺序直接等于 GPU 算子执行顺序，这是并行改造成本爆炸的根本原因。具体来说：

1. 执行顺序与模型代码强绑定：开发者写完 Attn、Expert、Combine 串行代码后，框架只能依次调度算子。想要插入并行逻辑，必须修改模型前向传播全部代码，重构算子依赖关系。例如，在 SGLang 中实现 DBO 双批次重叠优化，需要新增 1300 行定制代码，耗时两个月，且仅适配单一 MoE 模型。
2. 缺乏全局调度抽象：现有优化只能针对单一算子做局部改写，没有统一接口定义全局并行逻辑。想要同时实现分片+重叠+融合，需要多层嵌套定制内核，代码耦合度极高，后续模型迭代、PyTorch 版本升级会直接导致优化失效。

### 1.3 优化策略的场景敏感性，迫使企业维护多套定制分支

> 不存在一套适配所有硬件、负载的万能并行策略，图 2 量化了硬件、负载带来的性能差异。

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/06.webp)

::: image-caption
图 2：基于张量并行、使用 4 张 GPU 服务 Llama-3-70B 模型时，不同执行环境下各类设备内并行策略的性能表现。左子图区分 Prefill 预填充、Decode 解码两大 LLM 阶段，批次拆分策略在 Prefill 场景提速 1.18 倍，小批量解码场景反而降至 0.84 倍；右子图对比有无 H100 多内存指令（multimem）硬件特性，全重叠在开启 multimem 时提速 1.15 倍，关闭后仅 0.91 倍。该图直接论证论文核心痛点：不存在全局最优并行策略，性能高度依赖执行阶段与 GPU 硬件架构。A100 无 multimem，全重叠会引发 SM 资源争抢；H100 依托硬件卸载规约计算，全重叠收益显著。

**这就带来第二个工程难题：企业必须针对不同 GPU、不同输入长度、批量大小维护多套并行实现**，每一套都需要侵入式修改框架代码，迭代、测试、运维成本成倍上涨。

::: block-1
:mdnice-bold-italic[现有 ML 框架串行编程模型与异构算子并行需求底层冲突]，三类并行优化无统一接入抽象，且最优策略高度依赖硬件与负载，改造、维护成本极高，**行业亟需一层解耦调度中间层。**
:::

## 二、DynaFlow 核心洞察：逻辑模型与物理调度完全解耦

> DynaFlow 跳出了“修改模型代码实现并行”的传统思路，:mdnice-bold-italic[新增一层独立可编程调度中间层，用户上层完全保留原生顺序模型写法，并行执行逻辑全部在中间层定义]，无需改动模型核心推理、训练逻辑。

这套解耦架构需要同时解决两大矛盾：

- 调度灵活性不能带来极高运行开销
- 动态非顺序调度不能破坏 CUDA Graph、TorchInductor 等成熟底层优化

### 2.1 架构设计核心取舍

> 团队在设计阶段面临三组互相冲突的技术选择，最终做出如下权衡：

1. **调度粒度取舍：放弃单张量运算级细粒度调度，以 Attention、RMSNorm、Expert 等逻辑模块作为最小调度单元**。:mdnice-bold-italic[极致细粒度会带来海量调度开销，过粗完整层拆分则无法挖掘层内通信、计算并行机会；逻辑模块粒度刚好平衡开销与优化空间。]
2. **调度模式取舍：不采用声明式图重写规则，选用 Python 动态调度函数**。规则式无法根据实时批量、硬件动态切换策略，Python 原生函数可在运行时实时判断负载选择并行逻辑，适配场景敏感性。
3. **底层兼容取舍：不重新自研 GPU 执行引擎，基于 TorchDynamo、TorchCompile 构建**。复用 PyTorch 官方编译链路，天然兼容现有全部大模型生态，用户无额外学习成本。

### 2.2 DynaFlow 完整系统工作流

> 下图 4 完整展示从上层 AI 系统到底层 GPU 内核的全链路流转，是理解整套框架的核心示意图。整套流程分为三个标准化阶段，任何 PyTorch 框架接入都遵循相同步骤：

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/07.webp)

::: image-caption
图 4：DynaFlow 系统整体架构与完整工作流程。
:::

1. **模型初始化阶段**：开发者使用 DynaFlow 注解 API 对模型逻辑模块打标签，划分可调度子图；
2. **调度策略定义阶段**：开发者重写统一 schedule 调度函数，使用 split、execute 等原语定义分片、重叠、融合逻辑；
3. **推理/训练运行阶段**：框架前向传播触发 DynaFlow 拦截，调用自定义调度函数生成并行执行计划，异步后端分发算子至不同 CUDA 流执行。

整套流程中，原始模型代码无任何逻辑修改，仅增加少量标注与调度函数，从根源消除侵入式改造。

::: block-1
DynaFlow 核心创新为模型逻辑、物理调度双层解耦架构，以逻辑模块为调度粒度、Python 动态调度为核心模式、PyTorch 编译链路为底层底座，平衡灵活性、运行开销与生态兼容性。
:::

## 三、DynaFlow 前端：注解式图划分+统一可编程调度 API

> 前端是开发者直接交互的接口层，分为两大模块：图划分注解体系、通用调度原语。前者负责把静态模型切分为独立可调度子图，后者提供一套通用函数实现分片、重叠、融合全部并行逻辑。

整套前端 API 完全 Python 原生，无需学习新 DSL，现有 PyTorch 开发者 1 小时即可完成并行策略开发。

### 3.1 三层图划分注解体系

> 图 5 列出三类基础划分 API，覆盖所有模型代码场景：

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/08.webp)

::: image-caption
图 5：用于计算图划分的 DynaFlow 前端 API 定义。调度粒度过细会增加调度开销，过粗无法挖掘层内并行，因此 API 聚焦 Attention、RMSNorm 等逻辑粗粒度算子而非底层四则运算。传统图改写工具仅支持全局静态切分，无法精准定位 MoE Dispatch、Expert 等关键并行算子；DynaFlow 三类标注覆盖模块、函数、自定义代码段全场景，开发者仅需少量标注即可划分可调度子图，无需手动遍历完整计算图。
:::

1. **SplitModule**：针对 nn.Module 模块划分，例如 RMSNorm、Attention 层，直接按模块边界切割子图；
2. **SplitFunc**：针对自定义算子函数划分，例如 dispatch 专家分发、all_reduce 通信函数；
3. **mark 上下文管理器**：无固定模块、函数的零散代码块，使用 with 标记自定义调度单元。

三类注解仅用于给算子打上 tag 标签，不修改模型计算逻辑，接入 vLLM 稠密模型平均仅增加 4 行注解，MoE 模型平均约 8 行。

> 图 6 定义三大核心调度函数，所有单设备并行策略都可以基于这三个原语组合实现：

## 四、DynaFlow 后端：零拷贝内存+静态优化兼容异步执行引擎

> 前端生成的动态并行执行计划，全部由后端异步执行引擎落地，后端需要解决两大性能风险：微批次拆分、合并带来的显存拷贝开销，动态非顺序调度与 CUDA Graph、TorchInductor 静态优化的冲突。

为此，后端设计两大核心模块：双阶段零拷贝内存管理系统、子图粒度静态优化兼容机制，搭配异步依赖调度引擎，保证动态调度不引入显著性能损耗。

### 4.1 双阶段零拷贝数据流内存管理

> 批次分片、微批次合并会频繁调用 `torch.cat`、`tensor.split`，原生实现会产生大量显存拷贝，直接抵消并行带来的吞吐收益。

为了解决该问题，算法 1 设计静态分析+运行时预分配双阶段内存管理方案。

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/11.webp)

::: image-caption
算法 1 注释：DynaFlow 后端静态分析、运行时零拷贝内存管理流程。
:::

算法核心流程拆解：

1. 初始化静态分析阶段：遍历完整计算图，统计每个张量的引用计数，标记后续需要合并的张量，打上 prealloc 预分配标签；
2. 运行时执行阶段：调度算子输出时，直接写入提前预分配的连续显存缓冲区对应分片，不需要拷贝张量；张量引用计数归零后自动释放显存，精准控制峰值显存占用。

传统批次拆分实现频繁张量复制，显存带宽成为新瓶颈，抵消并行吞吐收益；**本算法通过静态元数据预规划内存布局，实现微批次拆分合并全程零拷贝。同时引用计数自动管理中间张量生命周期，控制峰值显存，解决多微批次并发下内存膨胀问题**，:mdnice-bold-italic[消融实验图 14 验证了零拷贝内存机制对性能的正向贡献，是三大核心优化模块之一。]

### 4.2 子图粒度兼容 CUDA Graph、TorchInductor

> CUDA Graph、TorchInductor 均要求静态无变化算子图，而 DynaFlow 调度生成的全局执行计划是动态可变的，二者天然冲突。团队采用“子图独立编译”方案化解矛盾：

1. TorchInductor：对每一个划分后的调度子图单独编译生成代码，不同微批次复用同一套编译产物；
2. CUDA Graph：为每个子图、每个微批次单独捕获图形，搭建全局 CUDA Graph 内存池复用，减少图形重复捕获开销。

> 图 8 量化了底层优化带来的 CPU 调度开销差异。

![文章插图](/articles/2026-07-02-1-29-uw-dynaflow-vllm-6e5c4b2d/images/13.webp)

::: image-caption
图 8：vLLM 框架下不同 DynaFlow 配置单次前向传播 CPU 耗时，批次 1 与 128 两条虚线代表 GPU 平均执行耗时。
:::

原生 vLLM 静态执行 CPU 耗时约 4.4ms；开启完整底层优化的 DynaFlow 动态调度模式 CPU 耗时为 10.8ms，顺序降级模式仅 4.7ms，与原生基线几乎持平；关闭 CUDA Graph 等底层优化后，非优化版本 CPU 耗时可达 68.7ms。

**CPU 调度延迟是 GPU 空闲的核心诱因**，若算子分发耗时超过 GPU 计算时长，会持续造成算力闲置。DynaFlow 将静态编译下沉至子图级别，复用 CUDA Graph 池减少重复捕获开销，顺序降级模式 CPU 耗时仅 4.7ms，与原生 vLLM 几乎持平。**该微基准证明底层编译兼容设计是控制调度 CPU 开销的关键**， 也佐证 CUDA Graph、零拷贝内存两大后端优化是吞吐提升核心来源。

### 4.3 异步依赖调度引擎

> 后端采用回调式异步架构，运行逻辑分为双向消息循环：

1. 前端调度函数调用 execute，向后端引擎投递算子分发请求；
2. 引擎维护全局算子依赖状态，算子执行完成后更新依赖，将就绪子图列表回传给前端 `get_ready_ops` 接口；
3. 开发者的调度函数仅需要处理业务层并行逻辑，算子依赖、异步队列、CUDA 流管理全部由后端接管，无需手动维护复杂数据流。

::: block-1
DynaFlow 后端依靠双阶段零拷贝内存消除分片显存开销，子图独立编译方案兼容 CUDA Graph 与 TorchInductor，异步引擎屏蔽底层硬件调度细节，动态并行调度几乎无额外性能损耗。
:::

## 六、对比现有相关工作：DynaFlow 差异化定位

> 行业现有三类单设备并行相关工作，各有明确短板，**DynaFlow 属于通用中间层底座，与所有方案形成互补而非竞争。**

### 6.1 专用单设备并行框架（NanoFlow、TokenWeave）

这类框架仅实现单一优化策略，无法兼容重叠、融合、分片多种路线，想要叠加多类优化需要二次深度改造；同时强绑定特定推理框架，无法迁移至 Megatron 训练、xDiT 视频生成场景，通用性极差。DynaFlow 可在同一套代码内组合多类优化，兼容训练、推理、多模态全部场景。

### 6.2 PyTorch、XLA 通用编译器

PyTorch TorchCompile 仅支持固定图重写规则，无法运行时动态切换并行策略；XLA 不暴露 CUDA 流、批次分片底层接口，无法实现细粒度算子重叠。二者均以静态图为基础，无法适配负载、硬件敏感的动态调度需求，DynaFlow 在编译上层新增可编程调度层，补足动态能力短板。

### 6.3 内核融合专用系统（Comet、Flux）

Comet、Flux 聚焦定制通信融合内核，仅解决单一细粒度融合场景，不支持批次分片、跨流算子重叠；DynaFlow 可以直接调用二者的融合内核作为 execute 的 replace_func 参数，将融合能力与分片、重叠自由组合，作为上层调度底座兼容各类内核优化。

::: block-1
现有方案均为专用单点优化，通用性、动态性存在固有缺陷；DynaFlow 是目前少有的通用可编程单设备并行中间层方案，可承载、组合全部现有并行优化路线，覆盖训练、推理、多模态全场景。
:::

- 接入 DynaFlow 后，一套调度代码可通过运行时判断自动适配全部场景，优化开发人力缩减 90%以上，新并行策略落地周期从数月缩短至 1-2 天。

### 7.2 多模态视频模型拓展潜力

论文验证 xDiT 扩散模型、FastVideo 视频生成模型可通过 DynaFlow 实现通信重叠优化，与 HuggingFace Transformers、Megatron-LM 等系统整体最高提速 1.15 倍；其中视频模型因注意力计算主导整体耗时，长序列场景下通信重叠的加速效果相对有限，视频模型注意力算子耗时随序列长度二次增长，但层间通信、归一化依然存在大量空闲资源，视频大模型的层间通信与归一化算子仍存在并行优化空间，DynaFlow 的调度体系可作为优化底座进行适配与拓展，降低并行方案的开发成本。

### 7.3 AI Infra 底层框架演进方向

> DynaFlow 证明“模型逻辑与物理调度解耦”是下一代大模型运行时的核心演进方向：

1. 上层开发者保留原生顺序编程习惯，降低 AI 算法开发门槛；
2. 中间调度层统一管理 GPU 硬件资源并行，由 Infra 工程师统一迭代优化；
3. 底层复用 PyTorch 成熟编译、CUDA 优化生态，避免重复造轮子。

未来 vLLM、SGLang 等推理框架大概率会内置类似可编程调度中间层，统一承载各类单设备并行优化。

## 八、局限与未来改进空间

### 8.1 当前框架存在的固有局限

1. TorchDynamo 兼容性限制：部分高度定制的 autograd 反向传播逻辑无法被图解析，Megatron-LM 部分训练反向并行收益受限；
2. 极小批量场景 CPU 调度开销凸显：bs=1 纯对话场景动态调度 CPU 耗时高于原生，必须依赖串行降级模式；
3. 仅支持 NVIDIA GPU：暂未适配 AMD、昇腾等异构 AI 加速卡，生态覆盖存在短板。

### 8.2 未来优化方向

1. 拓展多硬件后端支持，适配 AMD、昇腾等更多异构 AI 加速卡；
2. 研究自动调度搜索算法，基于负载与硬件特征自动生成最优并行策略，降低人工编写调度函数的成本；
3. 探索多设备间的调度联动，实现单设备并行与张量并行、流水线并行的全局协同优化；
4. 优化 CUDA Graph 的捕获与复用机制，降低额外显存占用与启动初始化时间。

::: block-1
DynaFlow 是单设备并行领域里程碑式通用中间层，大幅降低大模型 GPU 优化工程门槛，同时存在多硬件兼容、自动调度等优化空间，代表 AI 运行时分层解耦的长期演进趋势。
:::

## 总结

> 现有大模型框架的静态串行编程模型，与异构算子并行执行存在底层冲突，算子重叠、内核融合、批次分片三类优化落地需要数千行侵入式代码，且最优策略随硬件、负载动态变化，规模化落地几乎不可行。

华盛顿大学、上海交大联合团队提出 DynaFlow，核心创新为模型逻辑、GPU 物理调度双层解耦架构，**依托注解式图划分、三通用 Python 调度原语、零拷贝异步后端，实现四大核心优势：**

1. **透明接入**：vLLM、SGLang 等 6 大主流 AI 系统仅数十行代码修改即可集成；
2. **极简开发**：单类并行优化平均仅 40 行代码，对比原生侵入式实现开发成本降低一个数量级；
3. **全场景加速**：稠密 LLM、MoE 专家、视频多模态最高 1.29 倍吞吐，多节点低带宽通信场景最高 2.06 倍；
4. **生态兼容**：原生适配 CUDA Graph、TorchInductor，不破坏现有底层成熟优化。

::: block-1
该工作为 GPU 单设备并行优化提供了一套低侵入、高灵活的通用开发范式，**给 AI 推理服务商、底层框架研发团队提供了一套通用、低成本、高收益的性能优化底座**，指明了下一代大模型运行时分层解耦的演进路线，相关开源代码已公开：https://github.com/uw-syfi/DynaFlow。
:::
