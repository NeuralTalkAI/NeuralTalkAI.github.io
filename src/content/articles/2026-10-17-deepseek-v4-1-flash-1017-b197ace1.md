## 一、指纹变了：一次没有公告的线上换血

> 10 月 17 日，X 用户 @teortaxesTex 发帖称，DeepSeek API 中 deepseek-flash 模型的 system_fingerprint 发生变更（原帖链接[1]，发布时间 2026 年 10 月 17 日 11:24）：

- 旧指纹：`aeb56401ca74e127821c4f9126dcb669`
- 新指纹：`e72d3c7f663d3e1383b00b3884cb4501`

他的判断是 DeepSeek V4.1-Flash-1017 已经上线，体感上"更聪明了，可能更简洁"。

![文章插图](/articles/2026-10-17-deepseek-v4-1-flash-1017-b197ace1/images/02.webp)

::: image-caption
@teortaxesTex 推文及配图。推文给出新旧两组 system_fingerprint 哈希值；配图为一段探测脚本输出，上半部分显示 /models 端点目前只列出 deepseek-flash（名称 DeepSeek-V4.1-Flash）和 deepseek-v4-pro 两个模型，均支持 low、high、max 三档 effort；下半部分的 routing probe 显示直接请求 `deepseek-v4.1-flash-1017` 和 `deepseek-v4.1-flash` 均返回 400 错误，而 deepseek-flash、deepseek-v4-flash、deepseek-chat 三个别名实际都路由到同一个新指纹 e72d3c7f 开头——说明新权重已在 deepseek-flash 别名后面上线，但尚未以独立模型名开放。
:::

::: block-1
先解释一下 system_fingerprint 是什么。它是 OpenAI 兼容 API 响应里的一个字段，标识这次请求命中的后端系统配置。模型权重、推理栈、关键系统参数有变动，指纹就会变。DeepSeek 的 API 兼容 OpenAI 协议，自然也带这个字段。
:::

这个字段的存在意义在于可复现性：开发者可以据此判断两次调用之间后端有没有变。它另一个没有写在文档里的用途，是让外部观察者能在厂商不发公告的情况下，发现线上模型换了。DeepSeek 有静默更新的前科——今年 8 月 V4 Pro-0813 就是不发公告直接替换线上权重，事后才补的文档。社区对指纹的监控，正是从那次之后变成常规动作的。

## 二、三条独立的证据链

这次"1017 上线"的判断在三条互相独立的证据。

### 1. 指纹字符串里的命名信息

teortaxesTex 在主贴发出约 3 小时后跟帖确认：deepseek-flash 的新指纹是字符串 `fp_dsv41f_1017_prod0820_fp8_kvcache_20260402_fp` 的 MD5 哈希。拆开看：fp 即 fingerprint，dsv41f 即 DeepSeek V4.1 Flash，1017 是 10 月 17 日，prod0820 指向 8 月 20 日的生产构建，fp8 和 kvcache 是部署配置标识。Linux.do 社区也有用户让 agent 独立比对新旧指纹的底层数据，读出了同样的字符串，两条路径结论一致。

这基本坐实了两件事：新检查点的内部命名就是 V4.1-Flash-1017；它的生产构建在 8 月 20 日就完成了，压了将近两个月才放出来。

### 2. 模型列表出现又秒删

> 模型监控机器人 AITrackerBot 在 10 月 17 日抓到 DeepSeek API 的模型列表里出现了 `deepseek-v4.1-flash-1017` 条目，备注"1 added model entry"，几十分钟后该条目被撤下。

这条证据排除了"命名巧合"的可能。如果只是指纹数据里残留的旧字符串，解释不了模型列表端点真实地上架过一个新条目。**更合理的推测是：工程师在灰度过程中短暂地把新模型名挂到了公开列表上，发现后撤回了。** 推文配图里的 routing probe 也印证了这一点——直接请求 `deepseek-v4.1-flash-1017` 这个名字会收到 400 错误，错误信息提示"受支持的 API 模型名"里不含它，但 deepseek-flash 别名背后的指纹已经是新的了。

这里要分清两件事：撤下的是模型名，不是权重。`deepseek-v4.1-flash-1017` 这个独立名称的调用入口关了，但新权重一直挂在 `deepseek-flash` 别名后面正常服务，routing probe 里该别名返回 200。**也就是说，指纹切换之后，所有走 deepseek-flash 别名的请求命中的就是 1017 的权重。**

下面要说的第三方实测，走的正是这条路。

### 3. GitHub 上的第三方实测

> 指纹和列表只能证明"换了"，证明不了"变强了"。目前唯一的量化证据来自 GitHub 项目 JiegeOSBench（wangrunji0408/JiegeOSBench）。该项目通过 deepseek-flash 别名调用模型，别名背后已是新权重，因此测到的就是 1017。

这是一个黑盒 agent 基准：给模型一台空机器，要求从零写一个能交叉编译并跑通官方 nginx 的 RISC-V 操作系统，全程不看中间过程，只验最终结果。项目 README 已经收录了 1017 的成绩，与 9 月 10 日的 0910 版同路线对比：

- 高思考强度、标准模式下，活跃 61 分钟，零停顿（无空闲间隔）
- 40 分钟时 host 侧首次拿到 HTTP 200（`Server: nginx/1.28.3`）
- 写出的内核约 7400 行，同时实现 legacy 和 modern 两套 virtio-net 驱动、sendfile、内核侧 sigreturn trampoline 信号处理
- nginx 官方源码一行未改，sha256 校验通过
- 峰值上下文 645K，总花费 0.65 美元

"61 分钟零停顿"这个指标值得单独说。长程 agent 任务里，模型中途卡住、空转是常见失败模式，连续 61 分钟有效输出说明 1017 在长上下文工程任务上的稳定性有可观察的提升。0.65 美元的成本则延续了 Flash 系列的定位——用极低的价格跑重型任务。

需要交代清楚的是：这是单一项目、单一任务的实测，样本量为 1，不能外推为全面的性能结论。

## 三、官方仓库的异常动作

> DeepSeek 官方至今没有任何公告。API 文档的更新日志最新一条停在 9 月 10 日，也就是 V4.1-Flash 正式版发布那天。

但官方 HuggingFace 仓库 deepseek-ai/DeepSeek-V4.1-Flash 最近一周并不安静。通过 HuggingFace API 查到的提交记录显示：

- 10 月 16 日：`fix(encoding): preserve tool image order and current-turn thinking`——修复多模态工具调用中的图片顺序和当前轮思考链保留问题
- 10 月 12 日：连续多个提交，包括 `Restore each indexer's K cache on incomplete compression steps`——修复 KV cache 压缩步骤不完整时索引器 K 缓存的恢复问题，另清理了误提交的 `__pycache__`
- 10 月 1 日：添加 chat template

**这些提交全部落在 inference/ 和 encoding/ 目录的推理与编码代码上**，没有动 safetensors 权重文件。9 月 10 日发版后这个仓库安静了一个月，偏偏在 1017 灰度上线前后一周密集修推理栈。

::: block-1
两种解读都成立：一是官方在为 1017 的正式发版和权重开源做配套代码准备，10 月 16 日那条"preserve current-turn thinking"的修复尤其像在为带思考链的新检查点铺路；二是这只是常规维护，时间上的接近纯属巧合。单凭提交记录无法定论，但它至少说明官方这周在 actively 动这个模型的推理代码。
:::

另有一个可以确认的事实：HuggingFace 上不存在 DeepSeek-V4.1-Flash-1017 这个仓库，也没有任何近期上传的新权重。**也就是说，1017 目前只在官方 API 线上环境可用，权重尚未开源。想自部署验证的，现在没戏。**

## 四、现在能确定什么，不能确定什么

把信息按可信度分层，目前的状态是这样：

**能确定的（有技术实锤）：**

1. deepseek-flash 别名背后的线上权重在 10 月 17 日发生了变更，system_fingerprint 改变
2. 新检查点内部命名为 V4.1-Flash-1017，生产构建日期为 8 月 20 日
3. API 模型列表曾短暂出现该模型名，随后撤下；该名称目前不可直接调用
4. 官方 HuggingFace 仓库在 10 月 12 日至 16 日有多次推理栈代码提交

**有依据但样本有限的：**

1. JiegeOSBench 的单次实测显示 1017 在长程工程任务上表现稳定（61 分钟零停顿，0.65 美元完成 OS 构建任务）
2. 部分用户体感"更聪明、更简洁"——体感类反馈参考价值有限，DeepSeek 社区历史上也出现过指纹变更后性能感知两极分化的先例

**纯属猜测、目前没有依据的：**

1. "1017 就是 V4.1 Pro 的伪装测试"——没有任何证据支持
2. "性能大幅升级"——0910 发布时官方口径就是全面超越 V4 Pro，1017 是检查点级更新，幅度预期不宜拉高。今年 8 月 V4 Pro-0813 静默更新的教训就在眼前：换血是真的，体感提升有限也是真的
3. "1017 何时开源权重"——官方没有任何信号

## 五、DeepSeek 的静默更新，已经成了一种发布模式

> **把视角拉长，这已经是 DeepSeek 今年第二次被社区用指纹监控抓到静默更新。** 8 月的 V4 Pro-0813，10 月的 V4.1-Flash-1017，路径一模一样：线上先换，社区先发现，官方后补文档（如果补的话）。

对大模型厂商来说，灰度发布本身是标准工程实践——先小流量验证，再全量，再官宣。**DeepSeek 的特别之处在于它的用户里有相当比例的开发者，API 行为变化会直接影响下游应用的行为。** system_fingerprint 这个字段本来是给可复现性用的，现在成了社区的事实上变更通知机制，这本身就说明官方沟通机制存在缺口。

社区的应对也在升级。从这次的证据链看，已经有人把指纹监控、模型列表监控脚本化自动运行，:mdnice-bold-italic[AITrackerBot 这类机器人能在条目上架几十分钟内留下记录，GitHub 上也有仓库在持续归档指纹历史。厂商想静默，社区不让它静默。] 😅

接下来就等待三个更新：API 文档 changelog 是否补更、HuggingFace 是否出现新权重仓库、官方公众号或 X 账号是否发公告。按 0813 的先例，第一条通常先到。

::: block-1
对正在用 deepseek-flash 做开发的团队，一句实操建议：:mdnice-highlight[如果你的应用对输出行为敏感，把 system_fingerprint 记录进日志]。这次的事件证明，它是你能在第一时间知道"模型换了"的唯一渠道。
:::
