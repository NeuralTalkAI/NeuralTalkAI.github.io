关键词：**软硬件协同设计**、智能体 AI、**RISC-V**、:mdnice-bold-italic[芯片自动化]、分布式异构集群

> *当前AI芯片设计研究高度碎片化、难以复现：领域论文数量指数级增长，但大多是依赖定制胶水脚本的孤立方案，:mdnice-bold-italic[研究者需手动将LLM输出对接Verilator、把仿真结果回传Claude Code迭代，任务变更即需重构全套流程。该定制化模式导致各团队成果无法公平对标，行业长期缺乏统一的标准化实验跑道。]*

CHIA直击行业核心痛点，厘清AI芯片设计落地的三大关键瓶颈。

- **一是验证效率瓶颈**：Agent可实现设计想法到代码实现的近实时迭代，:mdnice-bold-italic[但协仿真占用50%–66%机器耗时，依据Amdahl定律，单纯并行化无法根治效率短板。]
- **二是工艺与机密壁垒**：商用PDK无法接入公有云大模型，开源PDK优化泛化性差，例如Sky130工艺下的Issue Queue重构优化，迁移至16nm先进工艺仅保留约70%增益，多数策略无法通用。
- **三是生态割裂问题**：现有设计工具互不兼容，行业缺失统一互操作基座。

::: block-1
CHIA并非替代传统设计工具，而**作为通用底层基座打通各类工具、统一碎片化设计流程**。项目即将在chialoops.ai全面开源，:mdnice-highlight[其核心价值是为业界提供可公平对比、可复现、可协同的统一实验跑道，解决领域研究零散、无法对标、难以沉淀的问题，推动AI芯片设计研究规范化迭代。]

## 一、行业背景与现存核心痛点

> 在 Agentic AI 爆发前，**软硬件协同设计本身就存在跨层割裂难题**；:mdnice-bold-italic[当 LLM、进化智能体介入芯片设计后，原有工程缺陷被指数级放大。]

现代 SoC 设计横跨软件编译器、指令集、微架构、RTL 逻辑、门级综合、版图多层抽象，每一层工具链输入输出格式互不兼容，传统研发依靠工程师手动流转结果，人力成本极高。引入 AI 后，新增的大模型调用、迭代搜索流程进一步加剧碎片化问题。

### 1.1 传统硬件开发流程固有缺陷

> 现代处理器、加速器研发需要串联数十款独立工具：

| 流程 | 独立工具 |
| --- | --- |
| 1. RTL 生成与编译 | Chisel/FIRRTL、CIRCT |
| 2. 功能仿真 | Verilator、Spike |
| 3. FPGA 加速仿真 | FireSim |
| 4. 微架构性能仿真 | gem5、ChampSim |
| 5. ASIC 物理综合 | Hammer、Vivado |
| 6. 验证套件 | riscv-dv、SPEC 基准测试 |
| 共性挑战（传统胶水脚本缺陷） | 每款工具具备独立输入/输出、依赖环境及授权要求；当前多依赖手工编写的 shell/Python 脚本串联 |
| 7. 资源调度缺陷 | 无标准化调度逻辑，无法自动分配 FPGA、GPU 或高端计算节点 |
| 8. 容错能力缺失 | 仿真运行数天后崩溃即全量失败，不支持断点续跑 |
| 9. 性能采集分散 | 缺乏统一采集机制，难以量化流水线各环节算力消耗 |
| 10. 扩展性受限 | 无法并行扩展至数十或上百台异构机器，仅支持单节点小规模测试 |

### 1.2 AI 智能体介入后新增三大关键矛盾

> 随着 ArchAgent、LLM-RTL 等工作出现，AI 被用于自动写 RTL、探索缓存算法、优化时序，**但原有脚本架构完全无法适配智能体迭代流程：**

1. **智能体循环迭代流程天然是闭环（生成 → 仿真 → 评估 → 反馈重生成）**，线性脚本难以表达带分支、循环的复杂控制流；
2. **LLM、进化算法会产生大量候选设计，需要大规模并行仿真评估**，传统单机脚本算力天花板极低；
3. 安全与实验可信度缺失：大模型可读取、篡改验证用例，存在“作弊”优化风险，缺少 AI 与验证环境强隔离机制。

### 1.3 现有相关工作的局限性

> 论文梳理同期 EDA 智能体、分布式调度框架，**明确现有方案无法覆盖全栈软硬件协同需求：**

| 问题类别 | 描述 |
| --- | --- |
| 专用 AI RTL 工具（RTLLM、ACE-RTL） | 仅聚焦代码生成单一环节，不支持仿真、综合、跨层评估全链路 |
| 通用分布式调度（Airflow、LangGraph） | 缺少 FPGA、Vivado、芯片仿真专用资源抽象，无法管理硬件加速设备 |
| 架构探索沙箱（ArchGym） | 仅绑定单一仿真器，不兼容 RTL 级高精度评估，无法输出 ASIC 面积时序指标 |
| 自研实验脚本 | 仅适用于作者自身实验环境，无通用组件库，无法跨团队复用 |

::: block-1
当前行业内，不存在一款原生支持智能体闭环迭代、异构云本地混合调度、全链路工具复用、强实验隔离的标准化软硬件协同设计框架，CHIA 正是为填补该空白而生。
:::

## 二、CHIA 核心定义与顶层设计目标

> CHIA 全称 Co-designing Hardware/software with Intelligent Agents，最初缩写为 Chipyard Intelligent Agents，后因适用范围远超单一 Chipyard 框架重新定义名称，**目标是让任何 AI 硬件研发流程都能低代码、可扩展、可复现搭建。**

框架整体分为两大核心抽象：CHIA Loop（流程有向环图）、CHIA Cluster（异构资源集群），二者组合构成完整 CHIA Workflow 工作流。

### 2.1 五大顶层设计目标

> 论文明确框架必须满足五大核心需求，所有底层抽象均围绕目标设计：

| 核心需求 | 描述 |
| --- | --- |
| 低代码构建大规模参数化迭代流水线 | 用户无需从零编写分布式调度逻辑，复用库节点快速搭建智能体闭环； |
| 异构资源弹性调度 | 统一管理本地 CPU、FPGA、GPU 与公有云弹性实例，支持动态扩缩容、故障自动迁移任务； |
| 模块化即插即用工具生态 | 内置主流仿真、EDA、LLM、进化算法节点，新增工具仅需实现标准化接口； |
| 混合控制流支持 | 同时支持程序式硬编码调度、AI 智能体自主工具调用两种控制范式； |
| 标准化实验科学支撑 | 原生隔离、全链路性能剖析、缓存断点、可复现执行，保障 AI 硬件实验严谨性。 |

### 2.2 两大核心抽象：Cluster 与 Loop

::: image-caption

#### 2.2.1 CHIA Cluster：混合异构资源管理层

> Cluster 是所有执行载体的集合，通过容器化隔离环境，屏蔽本地/云硬件差异，底层基于 Ray 分布式计算引擎实现任务调度。分层架构分为三层：

1. **物理机器层**：本地服务器、FPGA 板卡、AWS/GCP 云实例等原始硬件；
2. **逻辑 Worker 层**：资源虚拟化抽象单元，绑定 Docker 镜像、所需硬件资源标签（FPGA、Claude 密钥、Vivado 授权等）；
3. **任务调度层**：Ray 根据节点资源需求，自动匹配具备对应 Worker 的物理机。:mdnice-bold-italic[容器化是 Cluster 核心能力]：

#### 2.2.2 CHIA Loop：智能体闭环流程有向环图

> Loop 是描述完整软硬件协同迭代流程的 Python 程序，使用**节点+边** 的有向循环图抽象全链路任务：

1. 节点（Node）：被`@ChiaFunction`装饰的 Python 函数，对应单一硬件工具、LLM 调用、综合、仿真、评估操作，每个节点声明运行所需资源；
2. 边（Edge）：分为程序式、智能体式两类：

有必要说的是节点的核心特性：

- 异步调度：调用`.chia_remote()`立即返回 Future 对象，多任务并行执行；
- 统一生命周期：支持重试、缓存、旁路跳过、进程回收、自动性能埋点；
- MCP 工具封装：任意节点可注册为智能体可调用工具，实现 AI 自主操控 EDA 工具。

![文章插图](/articles/2026-07-11-chia-agent-ai-rtl-1-96f9ff32/images/06.webp)

::: image-caption
代码清单 2：示例工作流的 CHIA 循环代码片段。核心通过@ChiaFunction装饰器定义程序式节点，声明资源需求后调用.chia_remote()即可调度至集群异步执行并返回 Future 对象，天然支持并行计算；智能体节点通过ChiaTool封装为 MCP 工具供 LLM 调用，实现智能体驱动的控制流。代码完全遵循 Python 原生编程习惯，学习门槛极低，同时统一了程序式与智能体式两种控制流的编程范式，支持任意复杂的 AI 驱动设计流程。
:::

> 一个典型四阶段标准 Loop 范式：

| 阶段 | 描述 |
| --- | --- |
| 输入准备 | 提供硬件规格、基准 RTL（寄存器传输级设计）、测试用例；作为整个流程的初始输入基础。 |
| Agent 生成 | 大语言模型（LLM）读取硬件规格，生成候选 RTL 设计或微架构参数（如流水线深度、缓存配置、总线宽度等）。 |
| 并行仿真综合 | 同时执行三项任务：• Verilator：进行快速单元级 RTL 仿真，验证功能正确性；• FireSim：在 FPGA 上运行长周期基准测试，评估系统级行为与性能；• 门级综合：将 RTL 映射为目标工艺库，生成门级网表并提取时序信息。 |
| 评估分支 | 对仿真与综合结果进行联合评估：• 若性能（如 IPC、吞吐量、延迟）与时序（如关键路径延迟、是否满足目标频率）均达标，则流程结束；• 若任一指标不达标，则将仿真反馈（如瓶颈模块、时序违例路径、覆盖率缺口）回传至 Agent，触发新一轮迭代优化。 |

### 2.3 底层依赖技术栈

> CHIA 分层实现栈清晰，各组件分工明确：

1. 分布式底座：Ray，提供细粒度资源调度、分布式容错、异步任务，优于 Airflow、LangGraph；
2. 容器：Docker 实现 Worker 环境隔离；
3. MCP 工具层：fastmcp，封装节点给 LLM 调用；
4. 云集成：AWS Boto3、GCP 客户端；
5. 可视化与剖析：TensorBoard、Weights & Biases、GraphViz；
6. 持久化：SQLite/AWS S3 存储实验指标、缓存任务结果。

## 三、CHIA 运行时核心关键能力

> 仅提供工具封装不足以支撑大规模芯片实验，框架内置六大运行时特性，解决分布式 AI 硬件实验的工程痛点，所有能力对用户透明启用。

这也是 CHIA 区别于简单工具胶水脚本的核心壁垒。

### 3.1 异构动态调度与负载均衡

Ray 作为底层调度器，实现动态节点分配：

1. 只有节点全部输入就绪、集群存在满足资源需求的空闲 Worker 时才会调度；
2. 自动负载均衡，多物理机均匀分配同类型任务；
3. 支持混合长短任务：毫秒级 LLM 调用、数天 FPGA 仿真统一管理。

### 3.2 分布式故障容错

硬件仿真、云实例长时间运行极易出现宕机，CHIA 提供全自动容错：

1. 机器/Worker 崩溃自动检测，未完成任务重新入队调度至其他可用 Worker；
2. `chia up --add`可在线扩容集群，恢复失败任务；
3. 缓存机制配合断点续跑，崩溃后无需从头执行全部循环。

### 3.3 进程全生命周期追踪

所有节点创建的子进程由框架统一管控：

- 手动终止 Loop 时，自动销毁 Vivado、Verilator、FireSim 后台进程；
- 杜绝仿真、综合进程后台长期占用算力，解决资源泄漏问题。

### 3.4 原生全链路性能剖析

所有`@ChiaFunction`自动埋点采集指标：任务起止时间、执行机器、资源消耗、输入输出数据； 自动重建完整任务依赖图，输出 Gantt 时序图，直观展示仿真、LLM、综合各环节算力占比，论文三大 RISC-V 扩展案例均使用该能力统计机器时长分配。

### 3.5 缓存与旁路（Bypass）双机制

1. 缓存：指定节点执行结果持久化磁盘，重复输入直接读取缓存，跳过耗时仿真/综合；
2. 旁路：手动注入仿真结果跳过真实执行，用于快速调试 Loop 逻辑；

二者结合实现实验快速复现，规避非确定性 LLM 调用重复消耗 API 费用。

## 七、现存局限与未来研究方向

### 7.1 当前框架局限性

1. **专有工艺 PDK 数据无法输入公有大模型**：Sky130 开源 PDK 可完整闭环，但商用 16nm 等保密工艺数据不能喂给 Claude 等公有 LLM，优化结果存在偏差；
2. **评估仍是算力瓶颈**：仿真、随机指令验证占用绝大部分机器时长，:mdnice-bold-italic[并行仅能缓解，无法从根本缩短基准运行时间；]
3. **工具库仍在持续扩充中**，新增工具需遵循标准化接口封装，社区可按需贡献适配节点。

### 7.2 未来研究路线

1. **敏感工艺数据抽象**：将时序、面积指标脱敏后提供给 LLM，保护商用 PDK 知识产权；
2. **本地轻量化模型适配**：支持本地部署小模型，完全隔离专有硬件数据；
3. 缩短基准套件：开发轻量化高代表性测试集，降低仿真算力开销；
4. 丰富工具库：持续新增 HLS、GPU 架构、模拟电路相关 EDA 节点；
5. 构建统一 AI 硬件基准平台，基于 CHIA 标准化各 LLM、进化算法对比实验。
