> *异构 GPU 基础设施带来了二进制兼容性挑战：由于指令集、执行模型和驱动程序栈的差异，为:mdnice-bold-italic[一家供应商的 GPU 编译的代码无法在另一家的 GPU 上运行]。*

我们提出了 HetGPU，这是一个新系统，由编译器、运行时和抽象层组成，共同实现**单个 GPU 二进制文件在英伟达（NVIDIA）、超微半导体（AMD）、英特尔（Intel）和 Tenstorrent 硬件上执行**。

::: block-1
HetGPU 编译器生成与架构无关的 GPU 中间表示（IR），并插入用于管理执行状态的元数据。然后，HetGPU 运行时将此 IR 动态转换为目标 GPU 的本地代码，并提供线程、内存和同步的统一抽象。

我们的设计应对了关键挑战：:mdnice-bold-italic[不同的] 单指令多线程（SIMT）与多指令多数据流（MIMD）:mdnice-bold-italic[执行方式] （英伟达/超微半导体的线程束与 Tenstorrent 的多核精简指令集计算机（RISC-V））、:mdnice-bold-italic[不同的指令集]、:mdnice-bold-italic[调度和内存模型差异]，以及:mdnice-bold-italic[实时迁移所需的状态序列化]。

我们详细介绍了 HetGPU 架构，包括 IR 转换流程、用于 GPU 实时迁移的状态捕获/重载机制，以及连接以线程束为中心和以核心为中心设计的抽象层。
:::

初步评估表明，**使用 HetGPU 编译的未经修改的 GPU 二进制文件可以在不同的 GPU 之间以最小的开销进行迁移**，为与:mdnice-bold-italic[供应商无关的 GPU 计算] 开辟了道路。

## 关键问题：

### Q1. HetGPU 如何处理不同 GPU 的执行模型差异？

答案：通过 HetIR 抽象执行模型，不预设 warp 概念，运行时**针对 SIMT 设备** （如 NVIDIA）**直接利用硬件 warp 调度**，**对 MIMD 的 Tenstorrent 提供两种模式：单核心向量单元模拟 warp** （32 lanes）或**多核心分区执行**，通过核心间同步协议（如共享分支标志）协调执行，确保跨架构行为一致。

### Q2. 状态迁移的具体实现机制是什么？

答案：利用 HetIR 的 barrier 作为安全点，通过合作式协议暂停内核：编译器插入条件检查代码，运行时设置 pause_flag，线程到达 barrier 时将寄存器、共享内存状态写入全局内存，主机收集后在目标设备重新加载，通过分段执行（将内核拆分为带 barrier 的段）实现断点续跑，避免底层 PC 映射复杂性。

### Q3. HetGPU 的性能开销主要来自哪些方面？

答案：开销主要包括三部分：①**JIT 翻译时间** （首跑 NVIDIA PTX→SASS 需 50-100ms）；② **抽象层额外操作** （如 Tenstorrent 的 DMA 同步）；③ **迁移时的数据拷贝** （2GB 矩阵迁移需 0.5 秒）。但计算密集型任务因动态优化，overhead 通常 < 10%，内存密集型任务开销更低。

## 一、引言

现代计算在很大程度上依赖于多家供应商的 GPU，如英伟达（NVIDIA）、超威半导体（AMD）、英特尔（Intel）以及像 Tenstorrent 这样的新兴企业[7]。

> 然而，**GPU 二进制文件无法在不同供应商之间实现移植**。为英伟达编译的 CUDA 程序，由于**指令集架构（ISA）和体系结构不兼容**，无法在 AMD 或 Intel 的 GPU 上运行。这种供应商锁定的情况，迫使拥有大量 CUDA 代码库的机构花费大量精力，对代码进行移植或重写，以便使用其他加速器。

:mdnice-bold-italic[虽然高级框架（如 OpenCL、SYCL/oneAPI 或 HIP）支持编写可移植的源代码，但它们无法解决二进制文件的可移植性问题] [1-5, 9, 10]，即仍然必须*针对每个平台重新编译，而且预编译库仍然与特定的 GPU 供应商绑定*。

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/05.webp)

> 二进制兼容性的缺失，阻碍了异构集群中灵活的 GPU 调度，妨碍了 GPU 工作负载的实时迁移，并使采用新的 GPU 硬件变得更加复杂。

:mdnice-bold-italic[通过虚拟 GPU 指令集和运行时层，可以将 GPU 二进制代码与底层硬件解耦]。我们的编译器并非直接针对英伟达的 SASS 或 AMD 的 GCN，而是**针对一种统一的 GPU 中间表示（IR）**，它以一种**与架构无关的方式捕捉 GPU 并行性和内存语义**。:mdnice-bold-italic[在加载时，HetGPU 运行时会即时编译或将此 IR 转换为针对检测到的 GPU 的本地代码，针对架构特性执行任何必要的修补，然后执行代码]。

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/06.webp)

通过在这一抽象层次管理执行，HetGPU 还能够以一种与设备无关的格式捕获和恢复 GPU 状态，从而实现正在运行的内核在不同 GPU 类型之间的实时迁移。

::: block-1
要实现这一愿景，需要克服几个研究挑战。

- :mdnice-bold-italic[架构多样性]：
- :mdnice-bold-italic[指令集多样性]：CUDA 二进制文件使用并行线程执行（PTX，Parallel Thread Execution）/表面汇编语言（SASS，Surface Assembler），AMD 使用图形核心网络（GCN，Graphics Core Next）/RDNA 指令集架构（ISA，Instruction Set Architecture）等。
- :mdnice-bold-italic[内存和一致性模型]：不同 GPU 在内存暴露方式上存在差异（统一内存与离散内存、缓存一致性、片上暂存内存）。
- :mdnice-bold-italic[状态管理]：为了迁移正在运行的计算任务，必须以一种能够在不同 GPU 上重新实例化的形式捕获线程寄存器、程序计数器和内存。

这些差异并非微不足道——例如，Tenstorrent 的内核缺乏隐式线程束或分支处理功能，需要软件管理的谓词，而且英伟达的内部执行状态（如线程束执行掩码）在其他硬件上甚至可能不存在。

## 二、研究动机

### 2.1 与供应商无关的 GPU 二进制文件的理由

从深度学习训练到高性能计算，GPU 加速计算已无处不在。然而，这一生态系统:mdnice-bold-italic[被特定供应商的软件堆栈所分割]。

- 一个云平台或集群可能同时包含英伟达（NVIDIA）和超威半导体（AMD）的 GPU；
- 为一种 GPU 优化的代码若不经过大量移植工作，无法在另一种 GPU 上运行。

这抑制了灵活调度和负载均衡——如果最初目标 GPU 繁忙或出现故障，作业无法在运行时轻松重新分配到不同类型的 GPU 上。

> **无法在异构硬件间迁移 GPU 工作负载会带来实际代价**：例如，在大规模训练运行中，GPU 故障可能导致长时间的重新训练，或者需要高昂的冗余成本。

此外，供应商锁定存在经济和创新方面的影响。CUDA 的主导地位意味着许多算法都是用 CUDA 编写的，并且仅针对英伟达 GPU 进行编译。随着 AMD 和英特尔 GPU 在性价比方面的提升，用户可能希望利用它们，但为新的 API（HIP、SYCL 等）重写甚至重新编译代码会带来高昂的工程成本。

最近的一项研究强调了在无需完全重写的情况下，在 AMD 硬件上执行传统 CUDA 程序的必要性。目前，选择有限：可以维护单独的代码库（例如，一个用 CUDA，一个用 OpenCL 或 HIP），或者使用像 HIPIFY 这样的源到源转换器将 CUDA 代码转换为 HIP。**这些方法在源代码层面操作，无法解决二进制兼容性问题，它们需要重新编译，而且往往还需要手动修正。**

通用 GPU 二进制格式的缺失与 CPU 形成了鲜明对比。**在 CPU 领域，可移植的字节码（如 Java、.NET）或虚拟化技术能够将软件与特定的 CPU 指令集架构解耦**。:mdnice-bold-italic[GPU 二进制兼容层将带来类似于 GPU 的“Java 虚拟机”的好处]：开发者可以发布一个可在任何 GPU 上运行的二进制文件，并且系统可以动态地将 GPU 任务分配到任何可用设备上，自由混合不同厂商的产品。这也将:mdnice-bold-italic[促进硬件创新]：**如果现有的二进制文件能够通过兼容层在新的 GPU 设计（如 Tenstorrent 的 Tensix 内核）上运行，那么这些新设计将更容易被采用**。

### 2.2 跨 GPU 执行中的挑战

要实现这一愿景面临着一些技术挑战，这些挑战源于 GPU 供应商在并行执行的实现方式上存在很大差异：

- :mdnice-bold-italic[发散执行模型]：英伟达（NVIDIA）和超微半导体（AMD）的图形处理器（GPU）采用单指令多线程（SIMT）执行方式（英伟达为 32 线程束，AMD 为 32/64 线程束），这些线程束同步执行，硬件通过线程掩码处理分支发散。相比之下，Tenstorrent 由许多带有向量单元的 RISC-V 内核组成；它没有硬件线程束调度器。每个内核获取自己的指令，任何同步执行行为都必须通过软件进行协调。**连接单指令多线程（SIMT）和多指令多数据（MIMD）需要一个统一的模型：我们要么通过软件模拟线程束，要么设计不依赖于线程束同步执行的抽象模型**。
- :mdnice-bold-italic[分歧与控制流]：在单指令多线程（SIMT）架构的 GPU 中，分歧在很大程度上被隐藏起来——当分支出现分歧时，硬件会屏蔽不活动的线程，并在之后隐式地重新聚合它们。而在类似 CPU 的核心（如 Tenstorrent）中，每个线程都有自己的程序计数器，会独立进行分支操作，**因此分歧必须通过显式协调来处理**。例如，在 Tenstorrent 硬件上，程序必须设置并检查掩码寄存器，以模拟在一个线程束执行某一路径而其他线程闲置时的效果。如果独立执行的线程失去同步，软件必须插入 barrier 来重新对齐它们。**当在无线程束架构上运行基于线程束的代码（例如 CUDA 内核）时，我们的解决方案必须注入或管理这种预测和同步逻辑**。相反，当在 SIMT 架构的 GPU 上运行本质上是多指令多数据（MIMD）的代码时，我们必须仔细地将独立线程映射到线程束上（确保不违反 SIMT 的假设，比如一个线程束中的所有线程都运行相同的代码）。
- :mdnice-bold-italic[内存模型与数据共享]：**不同的 GPU 具有不同的内存层次结构**。英伟达（NVIDIA）和超威半导体（AMD）的 GPU 为线程块中的线程提供快速的片上共享内存以及缓存一致性的全局内存，并提供特定的一致性保证（例如，在执行`__syncthreads()` 后，线程块中的线程可以看到彼此对共享内存的写入）。相比之下， Tenstorrent 的架构为每个核心提供了一个本地暂存区，并且需要通过显式的直接内存访问（DMA）在本地存储和全局内存之间移动数据。不存在跨多个核心的隐式共享内存 —— 任何核心间的数据共享都要通过显式通信（网状网络或全局内存）来实现。这意味着，当 32 个线程位于不同的 Tenstorrent 核心上时，依赖于快速共享内存来实现 32 个线程协作的 CUDA 内核可能需要进行重构或模拟。**在 HetGPU 中确保一致的内存模型至关重要：我们的抽象层必须呈现出程序所期望的共享内存和一致性全局内存的假象，同时使用底层硬件的原语**。例如，HetGPU 可能通过为每个线程块分配一块全局内存区域并进行管理，或者通过限制一个线程块在一个核心上执行，以便该核心的本地内存可以充当该块的共享内存，从而在 Tenstorrent 上实现 CUDA 的共享内存。
- :mdnice-bold-italic[指令集和平台差异]：GPU 二进制文件不仅在编码上不同，而且在可用操作上也不同。英伟达的 PTX 虚拟指令集架构（ISA）拥有丰富的内部函数集（例如，线程束表决函数、数据交换、张量核心指令），而这些在 AMD 的 GCN ISA 或 Tenstorrent 的 RISC-V 向量 ISA 中没有直接对应的指令。AMD 的 ISA 可能有其独有的特殊指令（例如，位操作、硬件调度器/barrier 内部函数），这些指令在其他架构中不存在。一些 GPU 支持诸如独立线程调度等特性（英伟达 Volta 架构在线程束中引入了每个线程的程序计数器），而较旧的 GPU 则不支持。图形处理与计算方面的差异也会出现（英特尔的 GPU 传统上通过 DirectX/Vulkan 着色器来提供功能，这些着色器与 CUDA 程序有不同的限制）。**因此，我们的编译器必须对某些指令进行限制或转换，以保持可移植性**：例如，CUDA 的线程束数据交换（`__shfl`）在 AMD 上可以通过类似的内部函数来实现（如果 ROCm 中有可用的函数），或者在本地不支持的情况下，通过使用共享内存作为暂存缓冲区来实现；在 Tenstorrent 上，可以通过将值写入每个核心内存中的某个位置，然后通过直接内存访问（DMA）收集这些值来实现数据交换。在可能的情况下，**HetGPU 的抽象层为这些操作提供统一的内部函数，而后端则以特定于设备的方式实现**。
- :mdnice-bold-italic[状态捕获与迁移]：一种特别具有挑战性的应用场景是将正在运行的 GPU 内核从一个设备实时迁移到另一个设备（例如，抢占并移动一个长时间运行的内核以释放设备资源或避免故障）。
- :mdnice-bold-italic[转换为 PTX 级程序状态]。先前的研究指出，从低级机器状态重建高级（PTX）状态视图是多对一或多对多的——优化后的代码会重新排序或消除指令，因此不存在清晰的映射关系。这意味着，要在抽象层面进行迁移，可能需要以最小化优化进行编译，或者在状态映射明确的地方插入周期性同步点。

总之，**HetGPU 的设计初衷是打破特定厂商 GPU 二进制文件的限制，在 GPU 加速系统中实现真正的可移植性和动态灵活性**。

> 这些挑战涉及架构、编译器和运行时领域，**需要一个深度理解 GPU 语义的协同设计解决方案**。

接下来，在介绍我们应对这些挑战的设计之前，我们将讨论现有方法的背景以及它们的不足之处。

## 三、背景知识

### 3.1 GPU 架构与编程模型

不同厂商的 GPU 都有大规模并行计算这一通用目的，但实现方式所采用的架构理念各有不同：

#### 英伟达（单指令多线程架构）

英伟达 GPU（例如图灵、安培架构）将执行组织在流式多处理器（SM）中，每个流式多处理器都能够并行执行多个线程。线程以 32 个为一组进行调度，这些线程组每次执行一条通用指令（单指令多线程）——如果线程出现分支，非活动线程将被屏蔽，直到再次聚合。

- 程序员通常使用 CUDA 编程模型：通过线程块网格启动内核，每个线程块由硬件进一步细分为线程组。英伟达的工具链将 CUDA C++编译为 PTX（并行线程执行）虚拟指令集架构，然后再编译为 GPU 的 SASS（实际机器码）。PTX 作为一个稳定的中间层，但它是英伟达特有的。
- 内存：CUDA 提供了一个层次结构，包括全局内存（所有线程都可访问的设备 DRAM）、共享内存（同一线程块中线程使用的片上暂存器）以及每个线程的寄存器/本地内存。在同步点上确保线程块内的内存一致性（`__syncthreads()`函数确保共享内存写入可见）。全局内存跨线程块可见，但不保证一致性，除非使用原子操作或显式内存 barrier。较新的英伟达 GPU（伏特及更高版本）引入了独立线程调度，这意味着一个线程组中的每个线程都有自己的程序计数器（尽管执行时仍分组）。这使得捕获线程状态稍微容易一些（每个线程都有一个显式的程序计数器寄存器），但这通常是一个不向软件公开的内部细节。

#### AMD（GCN/RDNA 架构）

AMD 的 GPU（图形核心下一代和 RDNA 架构）具有类似的单指令多数据（SIMD）执行模型。AMD 的硬件将工作组调度到计算单元（CU）上，在一个 CU 内，32 或 64 个线程组成一个波前（相当于 NVIDIA 的线程束）以同步方式执行。

编程通常通过 OpenCL、HIP 或 Vulkan 计算着色器进行。AMD 的编译器（例如 hipcc 或 OpenCL 驱动程序）将内核代码编译为一种中间表示形式（过去是 AMD 中间语言（IL）或 LLVM 中间表示（IR）），然后再编译为 GPU 的机器指令集架构（ISA）（较旧的代次通常称为 GCN ISA，现在 RDNA 架构为 GFX10/11）。

**AMD 支持类似的内存层次结构概念** （共享内存称为本地数据共享（LDS），它是每个 CU 上每个工作组的，而全局内存位于显存（VRAM）中）。传统上，**AMD 的 GPU 在工作项之间的内存一致性方面需要显式同步，这与 CUDA 的模型类似。主要区别**：过去 AMD 使用 64 宽度的波前（因此分支意味着 64 个通道，对于分支代码有时效率较低），而较新的 RDNA GPU 默认使用 32 宽度的波前，与 NVIDIA 的线程束大小一致。

#### 英特尔 GPU（Xe 架构及更早版本）

英特尔的 GPU（集成显卡和独立的 Arc 系列）采用通过 SYCL/oneAPI 或 OpenCL 公开的执行模型。它们支持类似于线程束的子组操作（根据硬件不同，通常为 8、16 或 32 路宽度）。

英特尔 oneAPI 堆栈将代码编译为中间表示（通常是 SPIR-V，即 Khronos 为 GPU 制定的标准中间表示），英特尔图形驱动程序再将其编译为硬件指令集架构（针对执行单元，称为 EU ISA 或类似名称）。

内存模型：集成 GPU 共享系统内存，并与 CPU 拥有一致性缓存（对于采用英特尔一致性内存架构的现代产品而言），而独立 GPU 则有独立的内存。英特尔 GPU 还支持显式向量指令和谓词操作。

#### Tenstorrent（Tensix 内核）

Tenstorrent 的架构与传统 GPU 的单指令多线程（SIMT）不同。它由许多（例如，几十到几百个）Tensix 内核组成，这些内核是通用的 RISC-V 中央处理器（CPU），并配备了一个宽向量或矩阵单元（VPU）。每个内核运行自己的指令流（内核间采用多指令多数据（MIMD））。在一个内核内，VPU 可以并行处理例如 32 路数据（向量指令）。

**为了利用大规模并行性，工作负载在空间上进行分块**：例如，一个大型矩阵乘法可能会被分解为跨 Tensix 内核网格的子任务。Tenstorrent 提供了一个软件栈，包括 Metalium（一种针对其内核的类似低级汇编语言，具有向量内联函数）和 TT-MLIR（一个编译器栈，用于将高级机器学习操作映射到内核和网状网络）。

:mdnice-bold-italic[如果有人想在 Tenstorrent 上运行类似 CUDA 的内核（SIMT 模型），由于缺乏硬件线程束（warp）概念，主要有两种方法]：

1. 在一个内核的向量单元内执行整个线程束（使用 VPU 通道模拟 32 个并行线程，并使用掩码寄存器） 处理分歧）；
2. 将线程束分布在多个核心上（每个核心处理一部分线程，并通过核心之间的显式同步来模拟线程束级别的协调）。

**Tenstorrent 的内存是显式的**：每个核心的本地内存是私有的，必须使用直接内存访问（DMA）从片外内存引入数据；核心之间通过高速网格进行通信。这实际上是一种类似片上分布式系统的分块架构。

### 3.2 可移植式 GPU 编程模型

多年来，有几个框架试图在源代码或中间表示（IR）层面提供跨厂商的 GPU 支持：

:mdnice-bold-italic[OpenCL 和 SPIR-V]：OpenCL 是一种并行编程的开放标准，可面向多家供应商的 GPU。在 OpenCL 中，内核使用基于 C 语言编写，并在运行时编译为目标设备的指令集架构（ISA）（或预先编译为一种名为 SPIR 或 SPIR-V 的中间表示形式）。**SPIR-V 是一种用于并行计算和图形的标准化中间表示形式，类似于 GPU 的 “字节码”**。:mdnice-bold-italic[供应商支持接收 SPIR-V（例如，通过 Vulkan 或 OpenCL 驱动程序）并将其编译为硬件可执行代码。因此，SPIR-V 提供了一定程度的二进制级可移植性] —— 可以发布 SPIR-V 二进制文件，供英伟达（NVIDIA）、超微半导体（AMD）、英特尔（Intel）等公司的驱动程序使用。**然而，它也存在一些局限性**：SPIR-V 旨在作为高级编译器（如 GLSL 或 OpenCL C）的目标，并假定驱动程序会针对特定 GPU 进行优化。它**没有封装某些特定于供应商的功能（例如，SPIR-V 有子组操作的概念，用于抽象类似线程束的操作，但它们在映射时的线程束大小等方面可能会有所不同）**。此外，仅靠 SPIR-V 并不能解决捕获执行状态或使正在运行的二进制文件在不同设备间迁移的问题；它只是一种静态代码表示形式。

:mdnice-bold-italic[HIP 和 SYCL（oneAPI）]：这些是源级可移植性框架。AMD 的 HIP 本质上是一个类似 CUDA 的 API，可以在 AMD 和 NVIDIA GPU 上运行（使用相应的编译器进行编译时）。它需要重新编译——针对 AMD 的 HIP 代码通过基于 ROCm 的 LLVM 编译器编译为 GCN ISA，针对 NVIDIA 实际上可以使用 NVCC。SYCL/oneAPI（由英特尔、Khronos 开发）是另一种面向 CPU 和 GPU 的单源 C++并行编程模型；它使用 LLVM 编译为 SPIR-V，然后通过特定设备的后端进行处理。:mdnice-bold-italic[这些方法统一了编程模型，但没有统一二进制文件]：输出在编译时仍然是特定于供应商的。它们没有解决在不同 GPU 上运行相同二进制文件的问题；相反，它们使维护一个可为每个 GPU 构建的代码变得更容易。

:mdnice-bold-italic[胖二进制文件]：NVIDIA 的 CUDA 支持“胖二进制文件”，这些文件可以包含适用于多种 GPU 架构的 PTX 和机器码（例如，在一个可执行文件中包含适用于 sm_90、sm_100 等的代码）。类似地，苹果的通用二进制文件概念可以包括适用于 x86 和 ARM 的代码。**然而，这些仍然需要提前准备每种架构的代码** ——它们并非真正的单个可动态适配的二进制文件；它们**只是多个二进制文件的捆绑**。此外，胖二进制文件目前都是厂商内部的（英伟达支持英伟达的多种 GPU 代际，而非 AMD 的；苹果的胖二进制文件是针对其 CPU 的）。:mdnice-bold-italic[HetGPU 的方法有所不同，其二进制文件包含一个抽象代码版本，而非 N 个不同的后端，因此可能体积更小且更易于生成/维护]。

:mdnice-bold-italic[GPU 虚拟化与 API 仿真]：**实现可移植性的另一种途径是拦截 API 调用，并在另一家厂商的硬件上模拟某一家厂商的接口**。例如，开源项目 ZLUDA[8]是一个运行时，它通过拦截 CUDA API 调用并将 PTX 翻译成一种中间形式，然后针对其他 GPU 进行即时编译，从而让 CUDA 应用程序能够在英特尔或 AMD 的 GPU 上运行。**ZLUDA 本质上就像非英伟达硬件上的 CUDA 驱动程序，它利用 LLVM 将 PTX/SASS 编译成 AMD 代码**。尽管前景看好，但这类方法极其复杂，且成效有限——一项研究发现，ZLUDA 仅能对一小部分指令（在某个基准测试中约占汇编模式的 2.5%）实现正确的底层翻译，这表明**要在 AMD 上完全涵盖 CUDA 语义颇具难度**。另一个较早的项目 GPU Ocelot 提供了一个即时编译框架，该框架可以获取英伟达的 PTX，并在包括 AMD GPU 甚至 CPU 在内的各种后端上执行。它实现了 CUDA 运行时 API 和一个 PTX 即时编译器，将 PTX 翻译成 AMD 的 IL 或 x86 以在 CPU 上执行。Ocelot 是一个研究原型，不支持其所处时代之后的较新 CUDA 特性，但它**证明了动态翻译的可行性**。这些努力为我们的工作提供了参考——HetGPU 的运行时同样会拦截或实现 GPU 操作，但:mdnice-bold-italic[通过设计我们自己的中间表示（IR）并控制编译器，我们旨在比纯粹的黑盒二进制翻译实现更完整的覆盖范围和优化]。

:mdnice-bold-italic[检查点与实时迁移工具]：在容错和虚拟化的背景下，诸如 Cricket 和 CRIUgpu 之类的工具专注于捕获 GPU 状态，以便对进程进行检查点操作，并有可能在其他地方恢复。Cricket 是一个 GPU 虚拟化层，它允许在无需修改的情况下远程运行 CUDA 应用程序并进行检查点操作，但它假定使用 NVIDIA GPU（源和目标），并通过在客户机和主机之间对 CUDA 调用进行 RPC 操作来运行。CRIUgpu 扩展了用户空间中的检查点/恢复（CRIU）项目，以处理 GPU 状态，利用新的驱动程序 API 来转储内存和上下文状态。这些解决方案凸显了官方支持的重要性（NVIDIA 最近的驱动程序为内存提供了一些检查点功能）以及捕获 GPU 执行过程中状态的难度。他们大多将 GPU 视为一种可在相同硬件上冻结和恢复的设备（例如，保存所有 GPU 内存的状态，随后在同类型的 GPU 上重新加载）。:mdnice-bold-italic[相比之下，HetGPU 致力于跨架构迁移：这需要捕捉一种可在不同类型 GPU 上实例化的抽象状态]。这是这些问题的超集——**实际上，“对于跨架构迁移，PTX 级重新编译是目标，但预计要处理细微差别** （控制流、部分指令序列等）”。我们的工作通过控制中间表示（IR）并限制不支持的行为，明确地解决了这些细微差别。

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/07.webp)

总之，**现有的可移植式 GPU 解决方案要么在源代码层面运行（需要重新编译），要么是适用范围有限** 的专用翻译器。:mdnice-bold-italic[目前没有系统能够在 NVIDIA、AMD、英特尔和 Tenstorrent GPU 之间提供通用的二进制级兼容性，并支持实时状态迁移]。

> HetGPU 旨在通过在一个统一的框架中结合编译器中间表示（IR）的可移植性、动态翻译和虚拟化等要素来填补这一空白。

## 四、HetGPU 方案设计

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/08.webp)

> 在本节中，我们介绍了 HetGPU 的设计，它由:mdnice-bold-italic[三个主要组件组成]：

::: block-1
1. 一个**可移植的 GPU IR 和编译器**，从 GPU 程序生成该 IR，
2. 一个**运行时系统**，在不同的 GPU 上加载、翻译和执行 IR，同时管理状态和资源，
3. 一个**抽象层**，为 **GPU 操作** （线程、同步、内存）提供**跨硬件的统一接口**。
:::

### 4.1 可移植 IR 和编译器设计

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/09.webp)

#### HetIR（异构 IR）

> 我们定义了一个与目标无关的中间表示 HetIR，它作为我们系统中的“虚拟 GPU ISA”。HetIR 的灵感来自现有的 GPU IR（如 SPIR-V 和 PTX），但针对可移植性和运行时适应性进行了定制。

HetIR 的主要特征包括：

- :mdnice-bold-italic[SPMD 执行模型]：HetIR 假设一个单程序多数据模型，其中大量线程在不同的数据上执行相同的程序（内核）。每个线程都有索引（例如，线程 ID、块 ID）用于协调工作，就像在 CUDA/OpenCL 中一样。我们有意不在 IR 级别硬编码特定的 warp 大小或分组。相反，HetIR 语义中，线程块中的所有线程在概念上都是独立的，并且通过显式原语（如 barrier）进行协调。**这抽象了 SIMT 与 MIMD 的差异——warp 不是 HetIR 中的调度单元**；

相反，当映射到具有它们的硬件（NVIDIA、AMD）时，warp 将是一个新兴概念；或者当映射到没有它们的硬件（Tenstorrent）时，warp 将不存在。

- :mdnice-bold-italic[显式同步和预测]：HetIR 提供了同步指令（例如，线程可以在块内调用以同步的 barrier()）和预测执行（掩码）。高级代码中的分歧控制流使用结构化原语在 HetIR 中表示（很像 PTX 或 SPIR-V 使用重新收敛点用于 if/while）。我们包括一个用于活动掩码管理的伪指令：例如，set_predicate(cond)设置每个线程的布尔谓词，并且后续指令可以被标记为以该谓词为条件。这允许显式表示 warp 级分歧。
- :mdnice-bold-italic[统一的内存操作]：我们**将 HetIR 中的内存操作设计为抽象的，但有足够的细节以有效地映射**。例如，HetIR 可能具有像 LD_GLOBAL、ST_GLOBAL 这样的全局内存操作码，以及像 LD_SHARED、ST_SHARED 这样的共享内存（暂存内存）访问操作码，以及 BAR.SHARED 作为共享内存上的 barrier。在具有真正共享内存的硬件（NVIDIA、AMD）上，这些自然映射。在没有共享内存的硬件（跨核心的 Tenstorrent）上，LD_SHARED 和 ST_SHARED 可以由我们的运行时实现，可能作为访问全局内存的保留区域，或者通过将线程块限制在一个核心上，以便该核心的本地内存可以充当该块的共享内存。
- :mdnice-bold-italic[虚拟化特殊功能]：GPU 内核通常使用特殊操作：原子操作、投票或 shuffle 函数（投票哪些线程满足条件，在 warp 内交换寄存器）、纹理采样单元等。我们**在 HetIR 中将这些作为抽象操作纳入其中**。例如，VOTE_ANY(pred)如果块（或 warp）中的任何线程具有 pred = true，则可能返回 true；SHUFFLE(idx, val)可以提供来自另一个线程的值。在没有 warp 作为第一类概念的情况下，这些可以相对于线程团队（例如，在块内）定义。

运行时/抽象层将在每个平台上实现这些：

::: block-1
- 在 CUDA 上，VOTE_ANY 映射到使用 warp 投票的`__any()` built-in 函数；
- 在 AMD 上，它可能使用类似的 wave 投票；
- 在 Tenstorrent 上，我们的运行时可能必须在核心内或通过向量进行归约以产生结果。
:::

通过在 IR 中提供这些，我们确保即使硬件本身不提供它们，也支持常见的并行模式。

#### 编译器前端

> HetGPU 编译器可以摄取用 CUDA、HIP、SYCL 或其他语言编写的 GPU 代码。

在我们的原型中，我们专注于作为输入的 CUDA C++。我们**利用 Clang/LLVM 解析 CUDA C++并生成带有 CUDA 特定构造的 LLVM IR** （使用 NVIDIA 基于 LLVM 的 NVVM IR 用于 CUDA）。从那里，我们**不是使用 NVIDIA 的 ptxas，而是将 LLVM IR 降低到 HetIR**。我们实现了一个 LLVM 后端，输出 HetIR 指令。这需:mdnice-bold-italic[要在 LLVM 中将 HetIR 定义为目标——类似于 SPIR-V 或 PTX 本身如何成为目标]。在需要源代码级别信息的情况下（例如，识别 warp 级内置函数），我们添加了映射到我们 HetIR built-in 函数的编译器内置函数。例如，CUDA __syncthreads()调用被识别并转换为我们的后端中的 HetIR BAR.SHARED 指令。

:mdnice-bold-italic[编译器在 IR 级别执行优化，但以与目标无关的方式执行]。也就是说，**我们可以在 LLVM IR 或 HetIR 上进行与设备无关的优化** （公共子表达式消除、内联等），但我们避免任何假设特定硬件特征的优化（如 warp 大小特定的展开）。**这些决定被推迟到运行时或后期，以便它们可以针对每个设备进行调优**。编译器的目标是生成正确的、相对通用的 IR，并带有注释以协助以后的翻译。一组关键的注释是状态的映射信息：

- 我们用将指令链接到源代码行或变量名的元数据标记 HetIR 指令（很像 DWARF[6]调试信息）。
- 我们还标记代码中潜在的安全挂起点——默认情况下，barrier 和内核退出就是这样的点。

这些标签帮助运行时知道在哪里可以安全地捕获状态或迁移（因为在 barrier 处，块中的所有线程都对齐并处于已知状态，使得快照更容易）。

示例：假设我们编译一个简单的内核，将两个数组相加。CUDA 伪代码：

```
__global__ void add(float *A, float *B, float *C) {    int i = threadIdx.x + blockIdx.x * blockDim.x;    C[i] = A[i] + B[i];}
```

HetIR 输出可能如下所示：

```
%tid = GET_GLOBAL_ID 0%A_elem = LD_GLOBAL.F32 [%A + %tid * 4]%B_elem = LD_GLOBAL.F32 [%B + %tid * 4]%sum = FADD.F32 %A_elem, %B_elemST_GLOBAL.F32 [%C + %tid * 4], %sumRET
```

这类似于 PTX 或 SPIR-V 表示，但请注意我们没有提到任何 warp 或通道。如果有更复杂的构造，如 `if (i<N) {... }`，我们可能会生成如下内容：

```
%pred = CMP_LT %tid, NPJUMP %pred, L_true, L_falseL_true:    ... (true case) ...    JUMP L_continueL_false:    ... (false case) ...L_continue:    (converge)
```

我们会标记在 L_continue 处，线程重新收敛（这充当 warp 重新收敛点）。我们的编译器还可以选择具有显式谓词的结构化构造，而不是跳转，但想法是以可以映射到硬件的方式编码控制流，无论是通过真正的跳转（在 MIMD 上）还是通过硬件预测（在 SIMT 上）。

:mdnice-bold-italic[后端 ISA 模块]：**虽然 HetIR 是通用表示，但我们将后端特定代码生成模块的概念纳入设计中**。在运行时，当 IR 被翻译为本机代码时，一些特定于目标的决策可以由离线准备的代码指导。例如，对于 NVIDIA 目标，我们可能会包含一个 PTX 模板，或者使用 NVIDIA 的编译器从 PTX 进行 JIT。实际上，HetGPU 可以附带一个小的 PTX 生成模块，将 HetIR 转换为 PTX（因为 NVIDIA 的驱动程序可以使用 PTX）。

类似地，**对于 SPIR-V** 目标（Intel、AMD 通过 Vulkan 或 OpenCL），我们有一个**从 HetIR 发出 SPIR-V 的模块**。对于 Tenstorrent，我们**构建了一个代码生成模块，从 HetIR 发出 Metalium 汇编**。这些模块本质上充当运行时内 JIT 编译器中的后端。该设计允许，如果出现新的 GPU 厂商，我们为该目标 ISA 实现一个新的翻译模块，并将其插入到运行时中。

### 4.2 运行时系统

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/10.webp)

> HetGPU 运行时**负责获取 HetIR 二进制文件并在实际 GPU 硬件上执行它**。它扮演几个角色：

:mdnice-bold-italic[模块加载和 JIT]：当使用 HetGPU 的程序启动时，运行时识别可用的 GPU 设备及其类型（通过 PCI ID、驱动程序 API 等）。当请求内核启动时（通过我们的 API，它镜像 CUDA 的内核启动语义），运行时检查它是否已有该内核在目标设备上的本机代码。如果没有，它调用适当的后端模块将 HetIR 翻译为本机代码。

::: block-1
- 对于 NVIDIA，我们从 HetIR 生成 PTX，然后通过 CUDA 驱动程序 API 加载它（例如，cuModuleLoadDataEx）——NVIDIA 驱动程序将 JIT 编译 PTX 为 SASS。
- 对于 AMD，我们从 HetIR 生成 SPIR-V，并使用 OpenCL 运行时为其编译 GPU。
- 对于 Intel，同样通过 Level Zero 使用 SPIR-V。
- 对于 Tenstorrent，我们与他们的工具链集成：我们将 Metalium 汇编（或 TT-MLIR）提供给 Tenstorrent 编译器，以获得可以加载到设备上的二进制文件。
:::

运行时缓存这些翻译的内核，因此重复启动不会产生翻译开销。它还处理胖二进制文件回退：例如，如果目标是 NVIDIA，并且我们的 PTX 翻译器对于某些复杂内核不完美，我们可以选择性地在 HetIR 二进制文件中包含 NVIDIA 的本机 cubin 作为回退。在我们的原型中，我们主要依赖翻译，但这是一个工程扩展。

:mdnice-bold-italic[抽象层和设备接口]：**运行时实现了一个抽象层，为应用程序或库的上层提供一组统一的操作**。这包括管理内存分配（我们提供一个与设备无关的 gpuMalloc，在底层调用 NVIDIA 上的 cuMemAlloc，或 AMD 上的 ROCm 内存分配等），数据传输（gpuMemcpy，路由到适当的 API）。至关重要的是，它实现了内核启动和调度抽象。我们定义了一个内核启动的概念，其中包含线程块网格（就像 CUDA 一样）。当用户请求在设备上启动具有给定网格维度的 N 个块和 M 个线程的给定内核时，运行时将：

- 如果设备本机支持启动网格（NVIDIA AMD，Intel GPU 可以通过硬件启动许多线程），我们将内核与请求的网格维度一起传递给设备（例如，对于 NVIDIA，我们只需使用驱动程序以这些维度启动内核；对于 AMD，同样通过 ROCm/HIP）。
- 如果设备不支持动态启动许多线程（Tenstorrent 的编程模型更明确），我们的运行时必须在线程之间调度硬件核心。对于 Tenstorrent，我们有两种模式：

:mdnice-bold-italic[状态管理和迁移]：**运行时最重要的职责之一是管理 GPU 状态的检查点，以便可能进行迁移**。我们在 HetGPU 中实现了一种协作检查点机制。:mdnice-bold-italic[我们不完全依赖外部中断或特定于厂商的抢占] （这些在不同设备上可能不一致），:mdnice-bold-italic[而是设计我们的运行时和编译器]，以便在安全的点上协同暂停执行：

- 状态表示：我们定义了一个数据结构，以与架构无关的方式保存线程块状态的快照。它包括每个线程的寄存器文件数组（用于块中的所有线程），存储 HetIR 级“虚拟寄存器”的值，每个线程的程序计数器（HetIR 中的指令索引）的记录（如果线程在该点统一，则为单个 PC），以及任何相关共享内存内容的副本。我们还包括元数据，例如哪些谓词（分歧掩码）对 warp 处于活动状态。这反映了重新启动计算所需的内容：每个线程的通用寄存器、其在代码中的位置以及不在全局内存中的任何本地状态。
- 捕获状态：运行时可以通过 API 调用（用户请求检查点）或作为迁移请求的一部分来触发捕获。为了安全地捕获，我们希望块（或网格）中的所有线程都达到已知状态。我们利用 HetIR 的 barrier：在块范围的 barrier 处，该块中的所有线程最终都将到达 barrier。我们的运行时使用两阶段协议：首先，向 GPU 注入一个特殊命令，在下一个 barrier 之后暂停新工作。具体来说，对于 NVIDIA，我们可以使用 CUDA 驱动程序在 CTA 边界处进行抢占或 NVTX 标记，但我们选择了一种协作方法：我们的编译器在每个 barrier 处插入一个检查：

```
if (pause_flag) { // 将寄存器复制到全局内存 // 向主机发出信号 // 循环等待或退出 }
```

使用 NVBit（NVIDIA 的动态检测框架），我们在对应于 HetIR barrier 指令的点上向正在运行的内核注入代码，执行以下操作：如果（pause_flag）将寄存器复制到全局内存并跳转到内核退出。**NVBit 可以拦截所有加载/存储和寄存器访问，因此我们可以以编程方式获取寄存器值**。类似地，在 AMD 和 Intel 上，我们有自己的 IR，因此我们使用条件编译内核，该条件检查内存中的位置。如果设置，线程将其状态写入缓冲区（因为我们控制代码，我们可以使其将所有活动变量写入缓冲区）。

- 因此，**捕获状态成为与正在运行的内核协调的问题**：运行时设置 pause_flag 并等待。所有块到达它们的下一个 barrier 或内核结束，执行转储，然后我们拥有它们的状态在内存中。然后，运行时通过正常的内存复制 API 将此内存复制回 CPU。
- **在另一个设备上恢复**：一旦我们有了状态，我们通过为目标重新编译相同的内核（如果尚未完成），然后创建一个特殊的启动来绕过正常的内核启动并跳转到中间，从而在另一个 GPU 上重新启动。由于 NVIDIA 不允许在任意指令处启动线程，我们将内核分为由全局 barrier 分隔的段（我们无论如何都用于同步）。编译器自动在循环的每 X 次迭代中插入一个全局 barrier 以创建段。每个段都是一个单独的内核。在迁移中，我们提前在 GPU A 上结束段，传输状态，然后使用保存的数据作为输入在 GPU B 上从下一个段开始。例如，如果内核在某个点有一个 barrier，或者我们在那里插入了一个 barrier，所有线程都完成了第 1 部分。然后，我们将第 1 部分的输出（寄存器、共享内存）视为第 2 部分的输入。我们将第 2 部分生成为一个单独的内核，该内核接受输入结构（快照）并继续。这样，我们使用标准的启动机制。运行时协调此流程：它在迁移时知道下一个段是哪个，并将捕获的状态传递给一个特殊的加载器，该加载器将表示线程寄存器的数组填充到新 GPU 上。

:mdnice-bold-italic[内存传输]：当移动到新 GPU 时，运行时移动内存快照。HetGPU 使用统一的内存抽象，但如果 GPU A 和 GPU B 不共享物理内存，我们会执行复制。由于我们的状态捕获，我们在主机上有所有全局内存缓冲区（或者如果支持，我们可以直接从 GPU A DMA 到 GPU B）。每个块的共享内存内容存储在快照中，并重新加载到 GPU B 端的等效结构中（例如，如果我们用全局内存模拟共享内存，我们会分配一个缓冲区并将其复制到其中）。

通过围绕 barrier 和段进行设计，我们避免了处理极其低级的 warp PC 映射问题（在 PTX 级迁移博客中描述，否则将尝试将一个 GPU 上的任意程序计数器映射到另一个 GPU 的二进制文件中的指令）。我们牺牲了一些通用性（我们可能无法在任意指令处处理任意暂停，除非它在一个已知的同步点）以换取可靠性。这与建议一致，即可能需要强制执行 PTX 和 SASS 对齐的点。

##### 内存分配：

- 抽象：gpuMalloc(size)返回一个可通过我们的 API 在任何 GPU 上使用的设备指针。
- 实现：我们在活动 GPU 的内存上分配（通过 cuMemAlloc、hipMalloc 等）。如果该指针后来需要在另一个设备上使用（例如，迁移后），运行时将分配一个新缓冲区在新 GPU 上并复制数据。我们保留一个“虚拟 GPU 指针”到每个设备物理分配的映射。或者，我们可以要求统一内存或 CUDA UVA，但并非所有组合都支持 UVA。因此，我们根据需要进行跟踪和修复指针。

:mdnice-bold-italic[同步和启动控制]：例如，如果应用程序调用 gpuDeviceSynchronize()（类似于 CUDA 的设备同步以等待所有工作完成），我们的运行时将确保所有待处理的翻译和执行完成（并合并可能触发的任何迁移）。

:mdnice-bold-italic[错误处理]：如果设备上发生错误（例如，内核非法内存访问），我们会捕获它，并可以决定失败，或者可能在另一个设备上运行作为回退（尽管这可能不安全；主要是我们以统一的方式传播错误）。

抽象层被设计为最小但足以覆盖类似 CUDA 的使用。它确保从程序员的角度来看（在 HetGPU 之上），程序的行为相同，无论它实际在哪个 GPU 上运行。例如，barrier 将正确同步线程，无论它们是在 SM 上（使用硬件同步）还是跨多个 Tensix 核心（使用我们插入的软件 barrier）。

### 4.4 处理调度模型：SIMT 与 MIMD

一个核心的设计元素是我们如何在底层处理 SIMT 与 MIMD 执行。我们系统地总结：

:mdnice-bold-italic[SIMT 硬件（NVIDIA、AMD、Intel）]：硬件自动调度 warp。我们主要依靠硬件以分歧掩码并行执行线程。我们的 HetIR 到 PTX（或 SPIR-V）翻译发出使用本机控制流的代码。例如，HetIR 中的分歧分支在 PTX 中成为分歧分支；硬件处理掩码。HetIR 中的 barrier 在 CUDA 中变为 bar.sync，或在 AMD GCN 中类似。我们确保编译的代码尊重任何约束（例如，我们避免生成假设旧 GPU 上没有每个线程 PC 的独立线程调度的代码），尽管现代 GPU 支持独立线程调度。

> 具有向量单元的 MIMD 硬件（Tenstorrent）：我们提供两种映射策略，运行时可以选择：

- :mdnice-bold-italic[核心上的向量化 warp]：一个核心处理整个 warp 的线程。我们使用向量单元以锁步方式执行有效的 warp。这在单个核心中模拟 SIMT。分歧通过向量掩码寄存器处理（编译器/运行时生成的 Metalium 使用指令根据分支条件更新掩码）。优点是核心间通信最少——分歧和同步都在一个核心内。缺点是，如果一个核心只能处理 32 个线程，并行性有限，但我们分配更多核心以独立处理不同的 warp 或块。
- :mdnice-bold-italic[多核分区]：单个线程块跨多个核心拆分。所有这些核心本质上运行相同的指令流，但每个核心都在线程子集上（例如，核心 0 处理线程 0–7，核心 1 处理线程 8–15 等）。我们构建了一个小型同步机制：在每个分歧分支或 barrier 处，核心交换最少的信息以集体决定下一步。对于分歧：一个核心可能为其某些通道评估分支为采用，另一个核心可能不评估。为了模拟 warp 的行为，它们必须都同意首先执行哪个路径。我们实现了一个协议：所有核心共享一个位，指示任何线程是否采用了“if”分支。如果是，它们都为其具有该分支的线程执行该路径（其他线程通过掩码空闲），然后它们都执行剩余线程的“else”。在 barrier 处，我们使用 Tenstorrent 的网状 barrier。这允许将 warp 扩展到一个核心的容量之外。在实践中，我们发现许多 GPU 内核使用 32 个线程的 warp，而 Tenstorrent VPU 是 32 个通道，因此策略 1 足以保证正确性（策略 2 用于更大的块或性能探索）。

运行时根据每个内核或甚至每个块的启发式方法决定哪种策略。用户还可以通过环境变量提供提示，为某些内核选择策略 2。对于高度分歧的工作负载，强制 SIMT 行为是不利的，因此我们的运行时可以改为独立运行每个线程（纯 MIMD），以并行性换取更简单的执行。

### 4.5 设计属性总结

> 我们的设计使程序员的模型尽可能接近标准 GPU 编程（具有 barrier 和内存空间的类似 CUDA 的 SPMD），同时极大地改变了代码的编译方式和执行编排方式。

通过引入可移植的 IR 和自定义运行时，我们付出了一些开销（在翻译中，以及可能比特定于厂商的编译器实现的低级优化代码更少），但获得了灵活性。我们显式处理分歧和同步，以在没有 warp 的硬件上运行，并且我们在定义明确的点结合了状态保存/恢复功能，以实现迁移等功能。

一个关键的设计哲学是在可用时使用现有机制：例如，使用厂商 JIT 编译器（CUDA 的 PTX JIT，SPIR-V 的 OpenCL 驱动程序）来承担每个设备的指令调度和优化的繁重工作。这有助于将我们的工作重点放在新颖的部分（状态管理、协调多核执行等）。然而，我们必须通过我们自己的检测来扩展它们，以进行检查点，并为 Tenstorrent 提供自定义代码生成，Tenstorrent 缺乏用于任意代码的成熟 JIT（我们最终使用了他们的 MLIR 接口）。

另一个原则是可移植性的保守执行回退：如果某些 GPU 内存模型较弱，我们假设较弱（如果需要，我们插入 barrier，以便程序看到一致的行为）。如果某个架构功能在一个设备上缺失，我们会模拟它，即使速度较慢（例如，在没有本机投票的设备上的__ballot 变为归约，速度较慢但正确）。这确保了跨平台的正确性，但在某些情况下以性能为代价。

接下来，我们描述了我们如何实现这一设计，然后评估它在实践中的效果如何。

### 5.1 编译器工具链

我们通过扩展 LLVM 21.0 基础设施实现了 HetGPU 编译器。前端使用支持 CUDA 的 Clang。我们修改了 Clang 的 CUDA 代码生成，以发出与设备无关的 LLVM IR（通**常 Clang 会发出对 NVIDIA 内置函数的调用；我们将这些重新映射到我们自己的内置函数的调用**）。

:mdnice-bold-italic[我们引入了新的 LLVM built-in 函数，表示我们的抽象操作] （例如，`llvm.hetgpu.barrier`，`llvm.hetgpu.ld.shared`），以便它们出现在 IR 中并传递到代码生成。

然后，我们创建了一个名为 HETTarget 的自定义 LLVM 后端，输出 HetIR 汇编。我们选择基于文本的汇编形式以便于调试，并且它允许内联注释。我们的汇编中向量加法内核的示例输出片段：

```
.func _Z6vaddKernel(%rd<1> %A, %rd<1> %B, %rd<1> %C, %32 %N) {  .reg .u32 %i;  %i = GET_GLOBAL_ID 0;  @PRED(%i < %N) {    %f0 = LD_GLOBAL.F32 [%A + %i * 4];    %f1 = LD_GLOBAL.F32 [%B + %i * 4];    %f2 = FADD.F32 %f0, %f1;    ST_GLOBAL.F32 [%C + %i * 4], %f2;  }  RETURN;}
```

这里阐述下语法：

::: block-1
- %rd<1>表示指针寄存器（64 位）
- %32 表示 32 位标量（<1>是全局的寻址空间标签）。
- GET_GLOBAL_ID 0 获取维度 0 中的全局线程索引。
- @PRED(cond) { ... }表示一个预测块，仅当条件为真时才执行。在 SIMT 环境中，该预测变为分歧（对于 pred=false 的线程，在该区域中什么也不做）。在 MIMD 环境中，它变为正常分支。

编译器确保寄存器采用静态单赋值（SSA）形式，并使用有限寄存器集抽象（如PTX）。为简单起见，我们选择了无限虚拟寄存器集，让后端（或后续的即时编译器，JIT）分配物理寄存器。
:::

> 集成到运行时中的后端代码生成模块：

:mdnice-bold-italic[NVIDIA/PTX]：我们**编写了一个从 HetIR 到 PTX 的翻译器**，分两步。

- 首先，我们**将 HetIR 汇编转换为内存中的 PTX IR** （我们在可能的情况下重用 NVIDIA 的 NVVM 库）。我们将每个 HetIR 指令映射到一个或多个 PTX 指令。例如，GET_GLOBAL_ID 变为读取 ctaid 和 tid 寄存器并计算 blockIdx * blockDim + threadIdx 的 PTX 序列。HetIR 中的预测块我们映射到 PTX @predicate–guarded 指令或 PTX 级控制流。
- 然后，我们**调用 NVIDIA 的 ptxas** （通过 CUDA 驱动程序 API JIT 函数）**来获取 cubin**。这需要链接 CUDA 驱动程序 API，并使用 JIT 模式，您可以在其中提供 PTX 文本。我们确保 PTX 具有正确的.target 和.address_size 指令（与 GPU 的计算能力匹配）。

:mdnice-bold-italic[AMD/SPIR-V]：我们**使用开源 SPIRV-Tools 库开发了从 HetIR 到 SPIR-V 的转换器**。我们定义了一个对应关系，例如：

- LD_GLOBAL →OpLoad from StorageClass Uniform（或 CrossWorkgroup），
- LD_SHARED →OpLoad from Workgroup storage（我们将共享内存视为 Workgroup storage）。

我们为每个内核的共享内存使用声明一个 Workgroup storage 中的数组变量。barrier 变为 OpControlBarrier，具有适当的内存范围（共享内存同步的 Workgroup 范围）。

预测更棘手，因为 SPIR-V 期望结构化控制流：我们生成 OpSelectionMerge 和 OpBranchConditional 用于 if-else，确保每个分歧区域有一个重新收敛点（SPIR-V 要求结构化合并，我们的编译器通过结构化的@PRED 块固有地具有这些合并）。然后，我们将 SPIR-V 二进制文件传递给 AMD OpenCL 运行时（通过 clCreateProgramWithIL）或 Intel 上的 Level Zero 模块创建。这些驱动程序 JIT 将 SPIR-V 编译为硬件。

:mdnice-bold-italic[Intel]：如上所述使用 SPIR-V 适用于 Intel。我们使用 Level Zero API 摄取 SPIR-V 并编译为硬件 ISA。

:mdnice-bold-italic[Tenstorrent/Metalium]：我们**与 Tenstorrent 工程师合作，获得了 Metalium（他们的汇编）和 TT-MLIR 编译器的文档**。我们决定从 HetIR 输出 Metalium 汇编，然后使用 Tenstorrent 的工具进行汇编。对于每个内核，我们生成一个 Metalium 函数。关键任务：

- 为每个 HetIR 寄存器分配 RISC-V 寄存器（我们使用简单的线性扫描寄存器分配，因为 Tensix 核心的寄存器数量有限）。如果需要溢出，我们将溢出到核心的堆栈或 DRAM 区域。
- 为并行部分插入向量指令。例如，对于没有预测的 HetIR FADD.F32 %f2, %f0, %f1，我们生成一个 Metalium vadd 指令（例如，vadd v2, v0, v1），它将 v0 和 v1 的 32 个通道相加到 v2 中。如果由某个谓词 p 预测，我们根据 p 设置 vmask，并使用指令的掩码形式（Metalium 允许 vadd v2, v0, v1 [vmask]仅在掩码=1 的通道上执行）。
- 内存操作：Tenstorrent 没有统一的内存空间；我们生成使用其 DMA 引擎的代码。我们采用一个约定：HetIR 中的全局内存指针是 Tenstorrent DRAM 中的物理地址。因此 LD_GLOBAL [%A + %i*4]变为一个序列：核心计算地址 = A_base + i * 4；然后发出 DMA 读取，从该地址到本地缓冲区，然后将其移动到向量寄存器中。我们执行同步 DMA 以确保正确性（发出 DMA 并轮询完成）。
- 共享内存：Tenstorrent 的本地暂存内存很小，因此如果块在一个核心上，我们的实现为每个核心的本地暂存内存分配一个切片。如果一个块跨多个核心，我们在指定核心上或全局内存中分配一部分。通过为共享内存定义编译时地址，这些细节对代码是隐藏的。
- barrier：Tenstorrent 的 Metalium 提供了一个可以跨一组核心操作的 barrier 指令，以及一个用于内存的 fence。我们在每个同步点插入带有标签的 barrier 指令，并将其与 fence 配对，以确保内存操作（DMA 写入）可见。

在生成 Metalium 汇编后，我们通过 Tenstorrent 的汇编器传递它，以获得二进制文件，然后通过他们的运行时 API 将其加载到设备上，并在特定核心上启动。

:mdnice-bold-italic[编译器优化和标志]：为了实现更便捷的状态映射，在**启用迁移功能时，我们通常会采用优化程度较低的编译方式** （例如，在LLVM上使用 -O1而非 -O3，并包含行映射）。这与使用特别针对迁移友好型构建的建议是一致的。在**运行时若不启用迁移功能，我们会采用更高程度的优化，以便对比性能**。

### 5.2 运行时和系统集成

运行时被实现为一个C++库（libhetgpu.so）。应用程序与该库链接，并使用我们定义的API（为方便起见，该API模仿CUDA运行时API）。在内部，运行时通过环境变量或配置文件来检测设备（对于Tenstorrent设备，可能无法通过PCI扫描发现）。它会动态加载特定供应商的库（例如，使用dlopen("libcuda.so")，或者加载ROCm的libhip库或OpenCL库），以避免在这些库不存在时出现硬依赖。

:mdnice-bold-italic[内核启动实现]：当调用`hetgpuLaunchKernel(kernel, gridDim, blockDim, args, stream)`时，运行时会在一个内部表中查找内核。每个内核在编译时都嵌入了一个唯一标识符。如果当前设备尚未加载该内核，运行时会按所述进行即时编译。然后：

- CUDA/AMD/英特尔：使用其API将任务排入设备的流/队列（我们预先分配一个默认流，或者使用提供的流）。
- Tenstorrent：管理核心池。我们维护一个空闲核心列表。如果启动 X 个块，且每个块需要 Y 个核心（在单核模式下Y = 1，例如在拆分模式下Y = 4 ），我们就分配这些核心，将二进制文件加载到它们的指令存储器中，并触发启动。核心会一直运行，直到终止（内核通过内存标志发出完成结束信号）。由于Tenstorrent的API需要主动等待，我们会生成一个主机线程来等待核心完成或轮询完成缓冲区。

:mdnice-bold-italic[内存管理]：我们通过**调用相应的后端** （例如cuMemAlloc、hipMalloc、zeMemAllocShared等）**来实现hetgpuMalloc()**。我们将返回的设备指针封装在一个结构体中，该结构体包含它所属设备的标识符。如果该内存稍后在不同的设备上使用（例如在迁移后），运行时会自动复制数据。我们保留一个主机镜像指针（固定内存）以方便快速复制。在迁移时，我们对活动数据执行cudaMemcpyDeviceToHost操作，然后对新设备执行hipMemcpyHostToDevice操作。

:mdnice-bold-italic[状态捕获机制]：我们实现了一个函数 hetgpuCheckpoint（stream，state_out），应用程序（或测试工具）可以调用它来检查给定流中的所有内核。在底层：

- 我们为该流中的内核设置全局 pause_flag（用于我们的协作方案）。每个平台的实现不同：
- 我们要么使用NVBit在下一个程序计数器（PC）处进行插桩，要么依靠我们插入的代码。借助NVBit（英伟达），我们在屏障点注入如下代码：if (pause_flag) { 将寄存器复制到全局内存；向主机发信号；跳转到末尾 } 。NVBit的应用程序编程接口（API）使我们能够获取一个线程束（warp）的寄存器数量及其值。在AMD/英特尔平台上，我们在编译内核时，在屏障处添加一个条件语句来检查缓冲区的值。如果设置了该值，线程就会将其状态写入缓冲区。
- 一旦内核到达安全点，它们就会转储寄存器。NVBit检测工具会将寄存器值写入全局内存中的一个数组。我们还会记录每个线程束的程序计数器。类似地，在Tenstorrent上，我们包含一个汇编例程：当设置了暂停标志时，每个内核会将其向量寄存器和标量寄存器文件写入一个保留内存区域，然后暂停。
- 然后运行时收集这些缓冲区并组合成state_out，这是一个包含所有块状态的二进制大对象。运行时使用cudaMemcpy（或等效函数）将数据带回主机。全局内存也会被复制。

:mdnice-bold-italic[状态恢复机制]：hetgpuRestore(state, device) 则反向执行该过程：

- 加载状态二进制大对象。对于每个保存的块，在目标设备上分配一个块。
- 启动一个特殊的“恢复”内核。内核代码首先将保存的寄存器值复制到共享内存（对于SIMT GPU）或直接复制到寄存器（对于Tenstorrent）。例如，在NVIDIA上，我们将寄存器数据作为数组参数传递；在内核启动时，我们执行：

```
if (threadIdx.x == 0) {  for (i = 0; i < blockDim.x; ++i) {    sharedRegs[i] = savedRegs[i];  }}__syncthreads();myRegs = sharedRegs[threadIdx.x];
```

这通过共享内存走私初始寄存器值。我们也类似地处理共享内存内容。

- 然后，内核跳转到保存的程序计数器（PC）。我们通过使用ID标记潜在的恢复点，并将一个ID传递给内核来实现这一点。在起始位置的一个开关跳转到正确的基本块。在Tenstorrent上，我们在汇编语言中直接从内存加载寄存器。
- 内核在新设备上继续执行直至完成。

运行时会编排此流程，清理旧的设备上下文，并在需要时调整任何指针（例如，如果基地址不同）。

性能考虑和注意事项：额外的代码和检查会带来开销。在 barrier 处检查 pause_flag 会增加少量成本（如果 barrier 很少，可以忽略不计）。即使在不暂停时，NVBit 检测也会产生中等开销，因此我们仅在检查点启用它。在测试中，通常在禁用检测的情况下运行内核，并且仅为检查点启动特殊的检测版本，足以进行计划的迁移。这是一个限制：意外中断（例如，强制抢占）将需要始终开启的检测，这很昂贵。未来的硬件功能（厂商支持的检查点）可以提供帮助。

### 5.3 验证正确性

> 我们通过一套微基准测试验证了 HetGPU 执行的正确性：

- 基本算术内核：向量加法、SAXPY，将所有四个平台的输出与 CPU 参考进行比较。
- 分歧重的内核：前缀和，确保分歧处理在 Tenstorrent 上产生与 NVIDIA 上相同的结果。
- 共享内存使用：使用**shared** 的基于平铺的矩阵乘法。我们调整了内存地址计算以确保正确性。
- Warp built-in 函数：投票表决内核（统计一个翘曲内有多少线程满足某个条件）。在英伟达/超微半导体公司的硬件上，使用了硬件投票表决；在天腾公司的硬件上，我们采用了网格规约进行模拟。结果相符。
- 迁移：一个持久内核，在循环中递增数组，具有内部状态。我们在几次迭代后触发迁移，并验证最终总和与非迁移运行匹配。这交叉检查了寄存器状态（循环计数器）是否正确移动。

这些测试还涵盖了边缘情况，例如当只有一半线程到达 barrier 时迁移（它们按预期旋转直到 barrier）。

### 6.1 可移植性和正确性

我们编译了一个包含 10 个内核的 HetIR 二进制文件：向量加法、SAXPY、矩阵乘法（16x16 共享内存的平铺大小）、归约（数组求和）、包含扫描（使用 warp shuffle）、使用 warp 投票的位计数、蒙特卡洛 pi 估计（具有分歧和原子）以及一个小型神经网络层（矩阵向量加 ReLU）。

:mdnice-bold-italic[我们在每个 GPU 上运行相同的二进制文件，并根据已知的正确结果验证输出。所有测试都通过了，证明了功能可移植性。] 一些内核需要稍微重写（例如，包含扫描中的 warp shuffle 使用 VOTE_ANY 和循环重写，因为我们没有实现 SHUFFLE）。原子被映射到每个平台的本地原子（在 Tenstorrent 上，我们使用全局内存中的自旋锁模拟 atomicAdd）。

我们可以从 CUDA 源代码（通过我们的编译器）生成二进制文件，并在 AMD 上运行它，而无需编写 AMD 特定代码或调用 hipcc。这验证了“一次编写，到处运行”。编译器目前只接受 CUDA C++作为输入；支持 OpenCL C 是未来工作。

### 6.2 性能

> 微基准性能：我们测量了 HetGPU 与本机相比的几个内核的运行时：

::: block-1
- 向量加法（1 M 元素）：
- 矩阵乘法（1 024x1 024）：启动 4 096 个块，每个块 256 个线程。在 H100 上，cublas（张量核心）峰值达到 9 TFLOPs。我们的本地 CUDA（无张量核心）达到 3.8 TFLOPs；HetGPU 达到 3.5 TFLOPs（<8%开销）。AMD：hipBLAS 7 TFLOPs，我们的 HIP 内核 3.5 TFLOPs，HetGPU 3.3 TFLOPs（<6%开销）。Tenstorrent：HetGPU 达到其优化内核吞吐量的 80%。
- 归约（1 M 元素）：在 NVIDIA 上：本地 0.16 ms vs HetGPU 0.17 ms。AMD：0.18 ms vs 0.20 ms。Intel：0.30 ms vs 0.33 ms。Tenstorrent：1.4 ms（无直接本地比较）。开销 5–15%。
- 分歧内核（蒙特卡洛 pi）：启动许多线程，每个线程执行随机点检查。在 NVIDIA 上：本地 150 M 点/秒，HetGPU 148 M。AMD：140 M vs 135 M。Intel：80 M vs 75 M。Tenstorrent：
- 独立线程模式（MIMD）：120 个核心，每个核心一次运行一个线程，分批运行：25 M 点/秒。
- 向量化 warp 模式（SIMT 仿真）：一个核心运行 32 个通道；通过掩码处理分歧：18 M 点/秒。
:::

独立线程模式优于向量化模式，这与观察结果一致，即不规则内核在 Tenstorrent 上使用纯 MIMD 性能更好。

:mdnice-bold-italic[JIT 开销]：首次执行包括翻译时间：

::: block-1
- NVIDIA：PTX →SASS 通过 ptxas 耗时 50–100 ms，小内核耗时 10 ms。
- AMD：LLVM →GCN：100–200 ms。
- Intel：SPIR-V 80 ms。
- Tenstorrent：TT-MLIR：30 ms。

对于长期运行的程序而言，这些开销是可以接受的。对于短期任务，人们可以提前进行预编译。
:::

:mdnice-bold-italic[内存和 API 开销]：使用hetGPU的抽象对内存拷贝（封装底层API调用）增加的开销可以忽略不计。同步操作最多增加几微秒。

### 6.3 用例：跨 GPU 实时迁移

我们展示了长时间运行的矩阵乘法（通过基于分块的迭代内核将一个16384×16384的矩阵进行自乘）的实时迁移。我们:mdnice-bold-italic[从英伟达H100开始。中途，迁移到AMD 9070 XT，然后迁移到Tenstorrent BlackHole 150显卡。]

使用hetGPU，我们在迭代边界处进行检查点操作。检查点操作耗时0.5秒（通过PCIe将2GB矩阵数据从H100复制到主机）。然后我们初始化AMD GPU并恢复状态——恢复和内存上传耗时0.6秒（9070 XT支持PCIe5.0）。计算在AMD GPU上恢复并正确继续进行，产生了与未迁移运行相同的结果（在浮点精度范围内）。然后迁移到Tenstorrent耗时1.1秒（到开发板的PCIe速度）。**在一个30秒的任务中，总停机时间为2.2秒——在高性能计算环境中，这样的停机时间对于避免整个任务重新启动来说是可以接受的。**

我们还在:mdnice-bold-italic[训练过程中将一个正在运行的卷积神经网络（CNN）训练迭代从H100迁移到英特尔Xe - Iris]，在批次边界进行检查点操作。复制模型参数和激活值（4GB）耗时3秒。训练在英特尔GPU上恢复并正常收敛，证实了多核序列可以迁移。:mdnice-bold-italic[开销较高，但这是异构故障转移概念的一个验证]。

### 6.4 开销讨论

::: block-1
**HetGPU 引入的开销来自**：

- 翻译/JIT：首次运行每个内核 10–200 ms。
- 抽象：内存操作和分歧处理中的轻微开销。
- :mdnice-bold-italic[迁移数据移动]：**主要成本**，尤其是对于大内存。预复制或点对点传输可以减少停机时间。
:::

计算受限内核与本机相比减速<10%，内存受限内核甚至更少。对于许多应用程序，动态兼容性的灵活性超过了适度的性能损失。

## 七、相关工作

> 在:mdnice-bold-italic[异构计算中实现可移植性] 一直是一个长期目标。我们的:mdnice-bold-italic[工作建立在来自几个领域的见解之上]：GPU 虚拟化、二进制翻译、可移植编程框架以及检查点/恢复系统。

:mdnice-bold-italic[GPU 虚拟化和 API 仿真]：rCUDA 和 VirtualCL 等系统允许通过网络或在 VM 中使用 GPU，通过拦截 API 调用并将其转发到实际 GPU。例如，

- rCUDA 在远程 NVIDIA GPU 上运行 CUDA 调用，但假设两端都是 NVIDIA。
- Cricket 为 CUDA 提供了一个虚拟化层，可以检查点和迁移 GPU 工作，但仅在 NVIDIA 硬件上通过 RPC 进行。

这些为我们的方法提供了信息，以将应用程序与物理 GPU 解耦，但它们没有将执行转换为不同架构。HetGPU 将“虚拟 GPU”推广到一个厂商之外。

:mdnice-bold-italic[二进制翻译和跨 ISA 执行]：GPU Ocelot 是首批通过 JIT 将 PTX 编译为 AMD IL 或 x86 在非 NVIDIA 硬件上运行 CUDA 程序的系统之一。ZLUDA 重新审视了这一想法，通过拦截 PTX 并将其翻译为目标 GPU 的 LLVM IR，在 Intel/AMD GPU 上运行 CUDA。**ZLUDA 的正确性和性能各不相同，因为某些低级 CUDA 语义无法干净地映射到 AMD**。我们的工作在概念上相似，但更广泛：**我们处理实时状态和多架构支持，设计一个新的 IR 以避免直接 PTX 翻译的陷阱**。我们还集成了调度适应（SIMT 与 MIMD），这在以前的系统中是不存在的。

:mdnice-bold-italic[可移植 IR 和编译器]：SPIR-V（Khronos）和 HSAIL（AMD）等方法旨在作为可移植 GPU ISA。HSAIL 的采用有限；SPIR-V 广泛用于图形和计算可移植性。我们的 **HetIR 提供了 LLVM IR 中没有的更高级别的语义** （barrier、线程索引）。SYCL/oneAPI 使用 SPIR-V，但需要每个目标重新编译。HetGPU 在设备上运行一个二进制文件，运行时处理差异。

:mdnice-bold-italic[检查点/恢复和异构调度]：CRIUgpu 等工具在相同硬件上处理 GPU 状态检查点。PTX 级状态转储提炼了将低级状态映射到 PTX 以进行迁移的问题。我们的设计选择（基于 barrier 的快照、调试友好的构建）与这些见解一致。我们更进一步，进行跨架构迁移。

:mdnice-bold-italic[调度模型——SIMT Vs。其他模型]：关于在CPU或空间架构（如FPGA）上执行GPU编程模型的研究已经对线程束模拟进行了考察。Tenstorrent博客描述了三种策略。**hetGPU实现了其中两种**：在单核上进行矢量化线程束处理以及多核分区，并针对通用内核实现了自动化。对于不规则内核，纯多指令多数据（MIMD）模式具有更好的性能，我们的运行时会相应地选择模式。

:mdnice-bold-italic[限制和比较：]

HetGPU 的新颖之处在于它将可移植的编译器中间表示（IR）、多目标运行时和实时迁移结合在一起。先前的系统只处理了其中的一部分，如：

::: block-1
- Ocelot实现了多指令集架构（ISA），但没有实现迁移；
- CRIUgpu实现了迁移，但仅限于相同的指令集架构；
- SPIR-V和SYCL实现了跨供应商支持，但需要重新编译。
:::

**HetGPU 的抽象增加了开销和复杂性**，但随着 GPU 的多样化，这种权衡变得越来越可以接受。

## 八、讨论

> 虽然我们的评估证明了hetGPU的可行性，但也揭示了一些局限性和待解决的问题：

:mdnice-bold-italic[每个架构的性能调优]：我们**目前的中间表示（IR）主要关注通用能力**，因此**无法利用特定厂商的特性** （例如英伟达的张量核心或AMD的矩阵核心）。**未来的工作可以添加特定架构的优化层**：检测某些操作（如矩阵乘法），并将它们映射到厂商库或专门的中间表示内部函数。这将以牺牲一定的可移植性为代价来提高性能。

:mdnice-bold-italic[内存一致性和统一地址空间]：我们假设使用离散内存，并在迁移时显式复制数据。新兴系统（例如英伟达的Grace Hopper、超威半导体的加速处理器）提供统一内存，简化了迁移过程。hetGPU可以利用这一点来减少数据移动。跨供应商的一致性互连（例如，未来用于加速器的Compute Express Link）可能会完全消除数据复制。预复制技术（提前复制大部分数据，仅在停止时迁移差异数据）可以减少停机时间。

:mdnice-bold-italic[迁移的粒度]：我们目前在内核（或 barrier）边界处迁移。更细粒度的方法可以在不同的 GPU 上同时运行块的子集（用于负载平衡）。这需要跨设备 barrier，我们将通过主机通信进行模拟。Legion/StarPU 等框架在 GPU 之间分配任务，但需要多个代码版本。将 HetGPU 扩展到多设备协作执行是未来工作。

:mdnice-bold-italic[安全性和安全性]：在硬件上运行未显式编译的二进制文件会带来安全问题。如果我们的翻译器有错误，它可能会生成无效代码。我们依靠厂商编译器进行最终代码生成来缓解这种情况。检查点注入是微妙的：写入保留寄存器可能导致未定义行为。我们必须信任运行时作为系统软件组件。在多租户环境中，迁移工作负载不应跨上下文泄漏信息（我们刷新内存等）。这些类似于 OS 上下文切换问题。

:mdnice-bold-italic[复杂内核功能]：我们的原型不支持某些 GPU 功能：动态并行性（内核启动内核）和协作组（跨块同步）是不允许的。支持它们需要拦截设备端内核启动或添加全局同步原语。此处未涉及图形管道/着色器。

:mdnice-bold-italic[可扩展性]：我们测试了单进程场景。在许多进程的场景中，运行时开销可能变得显著（同时管理 JIT 编译和迁移）。全局缓存翻译的内核会有所帮助。处理数百万个线程的状态可能意味着大型快照；例如，1 M 个线程，每个线程 32 个寄存器（约 128 MB）加上内存。转储该状态可能需要几秒钟。仅保存活动寄存器（而不是整个寄存器文件）等优化会有所帮助。

:mdnice-bold-italic[替代方法]：**硬件级别的通用 ISA** （例如，如果 GPU 本机支持 SPIR-V）将解决兼容性问题，但由于性能和商业原因，这是不太可能的。纯二进制翻译（在 AMD 上模拟 NVIDIA）会非常慢。

HetGPU 的编译时+运行时，随着加速器虚拟化标准的出现，我们的运行时可以适应使用这些功能（例如，标准化的检查点功能或统一的 IR 支持）。

> 总之，HetGPU 可能不会取代特定于厂商的工具链以获得最大性能，但它为在 GPU 计算中将软件与硬件解耦提供了一个有价值的框架。**随着 GPU 的多样化，这种可移植性层将变得越来越重要。**

## 九、结论

> 我们提出了hetGPU，这是一个追求宏大目标的系统，旨在使GPU二进制文件在各大厂商的架构上实现通用兼容性。

通过引入可移植的GPU中间表示（IR）、多目标运行时以及连接不同执行模型的抽象层，hetGPU能让单个编译后的程序只需极少修改，就能在英伟达（NVIDIA）、超微半导体（AMD）、英特尔（Intel）和天腾（Tenstorrent）的GPU上运行。

::: block-1
我们的设计解决了统一单指令多线程（SIMT）和多指令多线程（MIMD）范式、处理不同指令集和内存系统，甚至在异构GPU间捕获和迁移执行状态等方面的根本性挑战。

通过一个原型实现，我们证明了hetGPU可以在各种硬件上不加修改地运行真实的GPU内核，甚至能在执行过程中在GPU之间实时迁移计算。鉴于获得的极大灵活性，观察到的性能开销通常较小（在计算密集型内核上在10%以内，通常更小）。我们不知道之前有任何系统能达到这种跨平台GPU透明度水平。我们整合了来自社区工作的见解（线程束模拟策略、PTX级状态映射）来深入了解GPU内部机制。
:::

这项工作为未来的探索开辟了几条途径。

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/16.webp)

- 一是通过扩展我们的中间表示（IR）和后端，将支持范围扩大到其他加速器（现场可编程门阵列（FPGA）、数字信号处理器（DSP）），朝着统一的加速器运行时发展。
- 另一个是在运行时融入更多智能，以针对目标设备自动进行优化（例如，自动调优或机器学习引导的优化）。

我们还计划与硬件供应商合作，探索用于虚拟化的最小硬件挂钩（例如，标准化的检查点功能或直接的IR执行单元）。

![文章插图](/articles/2025-07-13-gpu-nvidia-amd-intel-tenstorrent-4a3a4773/images/17.webp)

总之，hetGPU朝着打破异构计算中的二进制壁垒迈出了决定性的一步。它为开发者和系统提供了一条途径，使其能够利用任何GPU硬件，而无需局限于特定的生态系统或重写代码。我们认为，随着加速器专业化程度的提高，这个方向至关重要——软件必须适应硬件的多样性，而hetGPU展示了一个极具吸引力的系统级解决方案。
