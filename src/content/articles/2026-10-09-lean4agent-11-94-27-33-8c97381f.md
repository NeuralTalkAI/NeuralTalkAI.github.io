## 一、Agent 可靠性的核心痛点：长链路执行的信任危机

> 随着 LLM Agent 从演示场景走向生产落地，复杂多步工作流正在被部署到代码开发、金融分析、工业控制等高风险领域。:mdnice-bold-italic[Agent 执行链路越长，出现逻辑断层、上下文丢失、信息不一致的概率就越高，而行业始终缺乏系统性的可靠性保障手段。现有 Agent 验证方法不仅碎片化严重，更受限于底层形式化语言的表达能力，无法同时覆盖工作流设计时的语义正确性和运行时的轨迹合法性。]

当前主流的 Agent 验证思路大致可以分为两类：自然语言评判和轻量形式化检查。

**早期的 LLM-as-judge 方法用另一个 LLM 来评估 Agent 的输出，这种方法灵活但不可靠。** LLM 本身的幻觉和过度自信问题会传递给评判结果，尤其是在长周期执行中，评判器很难完整追踪全链路逻辑，漏判和误判都非常普遍。

近几年行业开始引入形式化方法，但都只解决了局部问题。

- 比如基于 Hoare 逻辑的工具调用合约，只能检查单步工具调用的输入输出是否符合规范；
- 基于 SMT 求解器的动作级策略验证，难以表达高阶推理逻辑；
- 基于时序逻辑的工件检查，无法建模数据依赖的属性。每一种方法都只覆盖了 Agent 行为的一个侧面，没有形成统一的验证体系。

::: block-1
:mdnice-highlight[更本质的矛盾在于，Agent 系统的行为同时涉及静态的工作流设计和动态的执行轨迹，二者的正确性相互关联又需要不同的验证手段。] 工作流设计有缺陷，执行再稳定也会出错；执行轨迹偏离设计，工作流再正确也没用。现有方法往往只关注其中一端，无法形成闭环。
:::

**这一困境恰好对应了 20 世纪数学基础危机的核心矛盾：用自然语言描述的证明永远存在模糊性，只有用形式化语言重写，才能实现真正的可验证性。** 在数学领域，依赖类型理论的发展催生了 Lean、Coq 等定理证明器，已经实现了对复杂数学定理的机器级验证。:mdnice-bold-italic[而在 Agent 领域，将这一套成熟范式迁移过来，用表达力足够强的形式化语言统一建模工作流和轨迹，正是解决可靠性问题的关键路径。]

Lean4Agent 就是沿着这个思路做出的首次完整尝试。

## 二、Lean4Agent 框架总览：三层验证+双模式进化

> Lean4Agent 的:mdnice-bold-italic[核心设计哲学是“正确构造+迭代进化”：先用形式化方法从设计层面保障工作流的语义自洽性，再通过运行时轨迹验证定位故障，最终驱动工作流的针对性优化。整个框架构建在 Lean4 定理证明器之上，依托依赖类型理论的强大表达能力，实现了从结构到语义、从静态到动态的全层级验证覆盖。]

从架构上看，Lean4Agent 分为两大模块：**负责验证的 FormalAgentLib 和负责进化的 LeanEvolve**。

![文章插图](/articles/2026-10-09-lean4agent-11-94-27-33-8c97381f/images/04.webp)

::: image-caption
图 1：Lean4Agent 框架。Lean4Agent 框架包含两大核心组件。(a) FormalAgentLib 是三层结构的 Lean4 库，用于 Agent 行为的形式化建模与验证：第一层通过工作流图验证结构正确性；第二层构建谓词系统建模执行前后置条件，基于 LLMExec 假设验证语义自洽性；第三层结合 Lean、外部程序与 LLM 裁判检查执行轨迹，定位违规步骤。(b) LeanEvolve 利用验证结果优化工作流，构建形式化引导的进化机制，并辅以纯 LLM 进化扩展提升能力。
:::

> FormalAgentLib 是整个框架的基础，它采用三层递进的验证体系：

| 层级 | 描述 |
| --- | --- |
| 第一层 结构验证 | **相当于编译器的语法和类型检查，确保工作流图本身是合法的**，没有变量未定义、节点不可达、边转移非法这类基础错误。这一层是 LLM 无关的，只检查工作流的结构属性。 |
| 第二层 静态语义验证 | :mdnice-bold-italic[基于谓词系统和 Hoare 逻辑合约，在部署前验证工作流的语义自洽性。这一层会引入 LLMExec 假设，也就是假设 LLM 在满足前置条件的情况下能够正确完成单步任务，进而推导整个工作流的语义正确性。] 通过这一层验证的工作流，可以认为是“正确构造”的。 |
| 第三层 执行轨迹验证 | **在运行时检查实际的执行路径是否满足每一步的前后置条件**。如果执行失败，这一层能够精准定位到是哪一步违反了哪个谓词，为后续修复提供诊断信息。 |

基于第三层的诊断结果，LeanEvolve 模块负责驱动工作流的进化优化。它采用双模式设计：

- 形式化引导进化是核心，基于精准的故障定位进行针对性修改；
- 纯 LLM 进化作为补充，进行更广泛的探索性修改。二者结合，在精准性和创新性之间取得平衡。

**Lean4Agent 形成了一个完整的闭环：设计时用两层验证保障工作流质量，运行时用轨迹验证定位问题，然后用进化模块迭代优化工作流**。:mdnice-bold-italic[这也是首个覆盖 Agent 全生命周期的形式化验证框架]。

## 三、FormalAgentLib 深度拆解：三层验证的技术内核

> FormalAgentLib 是整个框架的技术核心，它用 151 个类型定义、611 个函数和 41 个定理构建了完整的 Agent 工作流形式化模型。三层验证体系逐层深入，对应着 Agent 工作流不同维度的正确性要求。

从基础的结构良构，到静态的语义自洽，再到动态的轨迹合规，每一层都建立在下一层的基础之上，共同支撑起“正确构造”的设计方法论。

### 3.1 第一层：结构验证——编译器级别的基础检查

> 结构验证层的目标是检查工作流的“语法正确性”，就像编译器检查程序有没有语法错误、类型不匹配一样。团队首先定义了两套基础类型系统：BaseType 和 StepType。

- BaseType 定义了工作流中变量的数据类型，除了常见的字符串、整数、浮点数、布尔值、JSON 等基础类型，还包含字典、列表、集合、可选类型、记录类型等复合类型，甚至预留了 Unknown 类型支持渐进式类型检查。
- StepType 定义了执行节点的类型，其中最核心的是 step 和 task 两类：step 节点执行时会携带完整的对话历史，适合需要上下文的推理任务；task 节点执行时没有历史上下文，适合独立的原子任务。

**基于这两套基础类型，每个工作流节点被形式化为 WorkflowNode 结构，包含节点 ID、名称、步骤类型、读取的变量列表、写入的变量列表和 LLM 指令。** 节点之间的转移则被定义为 WorkflowEdge，支持顺序边、分支边、循环边、并行分叉边、并行合并边、开关边等多种控制流结构。

> 最终，一个完整的 Agent 工作流被形式化为一个带类型的有向图：

$$
\mathcal{W}=\left(V, E, v_{entry }, X, P\right)
$$

其中 $V$ 是带类型的节点集合，$E$ 是带类型的边集合，$v_{entry}$ 是唯一的入口节点，$X$ 是出口节点集合，$P$ 是初始参数列表。

![文章插图](/articles/2026-10-09-lean4agent-11-94-27-33-8c97381f/images/05.webp)

::: image-caption
- 图 2：触发第一层验证失败的工作流图。该图可视化了一个典型的结构验证失败案例：四个并行分支各自生成搜索结果变量，但缺少 gather 汇聚步骤将变量导出到外层作用域，导致下游合并节点读取变量时触发「无生产者」错误。这类作用域错误非常隐蔽，人类设计并行工作流时极易忽略，而结构验证层可以通过读写一致性检查自动拦截。

:mdnice-bold-italic[结构验证可以检测出多种基础错误，比如节点不可达、边的起点或终点不存在、读取的变量没有被定义或不可达等。最典型的场景是并行分支的变量作用域问题：如果并行分支内产生的变量没有通过汇聚步骤传播到外层，下游节点读取这些变量时就会触发读一致性错误。] 这些错误很多时候非常隐蔽，人类设计工作流时很容易忽略。
:::

### 3.2 第二层：静态语义验证——Hoare 合约与谓词系统

> 如果说结构验证检查的是“有没有语法错误”，:mdnice-bold-italic[那语义验证检查的就是“逻辑上能不能跑通”。这一层是 FormalAgentLib 最核心的创新，它用谓词系统和 Hoare 逻辑实现了工作流的静态语义验证。]

**谓词系统的作用是把自然语言描述的需求转化为机器可检查的逻辑约束**。团队在 Lean 中定义了归纳类型 PredicateType，内置了几十种基础谓词，比如检查字符串非空、JSON 格式合法、URL 格式正确、符合指定 JSON Schema、包含特定子串、文件存在等等。:mdnice-bold-italic[每个谓词都对应一个 toProp 解释函数，把谓词映射为 Lean 中的逻辑命题，从而可以用定理证明器来检查。]

如果内置谓词不够用，系统还支持两种扩展方式：custom 谓词用于只有自然语言定义的约束，保留名称检查和自然语言说明，后续可以用 LLM 来检查；ext 扩展机制可以注册用户自定义的谓词，无需修改现有类型定义。

> **除了针对单个变量的谓词，系统还引入了隐式变量和图级谓词，用来建模工作流全局的约束。** 比如信息流谓词追踪每个步骤的信息生产和消费关系，上下文管理谓词规定步骤可以访问的历史上下文范围。这些图级约束能够检测出很多局部检查发现不了的问题，比如上下文断裂、信息泄露、判断不独立等。

在此基础上，团队把每个 LLM 步骤都建模为 Hoare 风格的前后置条件对：

$$
s_{i}=<\rho_{i}^{(pre )}, v_{i}, \rho_{i}^{(post )}>
$$

:mdnice-bold-italic[简单来说，前置条件就是执行这一步之前必须满足的条件，后置条件就是执行完这一步之后应该达成的结果。这和软件工程中的 Hoare 逻辑完全一致：如果前置条件满足，执行后后置条件也满足，那这一步就是正确的。]

整个语义验证建立在 LLMExec 公理之上：如果一个 LLM 步骤在满足其前置条件的环境中执行，那么执行后的环境一定满足其后置条件。形式化表示为：

$$
\forall s_{i} \in \mathcal{S}, \forall \Pi ,\Pi \vDash \rho _{i}^{(pre) }\Rightarrow \exists \Pi ^{\prime }=LLM\left(v_{i},\Pi \right) \land \Pi ^{\prime }\vDash \rho _{i}^{(post) }
$$

其中 $\Pi$ 代表当前的谓词上下文，也就是目前已经成立的所有约束。

::: block-1
有了这个公理，系统就可以沿着工作流图一步步传播谓词，检查每个节点的前置条件是否都能被前面的后置条件满足。如果所有节点都通过检查，说明这个工作流在语义上是自包含的，只要 LLM 的单步能力符合假设，整个工作流就能正确执行。

**这一层的价值在于，它能在工作流真正运行之前，就发现逻辑上的缺陷**。:mdnice-highlight[这种“正确构造”的设计思路，能够从源头上避免大量低级错误，大幅提升工作流的下限]。
:::

### 3.3 第三层：执行轨迹验证——运行时故障精准定位

> 静态语义验证建立在 LLMExec 假设之上，但现实中 LLM 不一定总能正确完成单步任务，边界情况、能力不足都可能导致执行失败。**第三层执行轨迹验证的目标，就是在运行时检查假设是否成立，并定位故障点。**

对于不同类型的谓词，第三层采用不同的验证方式：

- 对于 Lean 内置可判定的谓词，直接用 Lean 命题进行形式化检查，结果是数学级别的严格正确；
- **对于超出 Lean 判定能力的谓词，比如 URL 连通性、第三方服务可用性等，调用外部 Python 验证器进行检查；**
- **对于只有自然语言定义的 custom 谓词，使用 LLM-as-judge 模块进行评估**，同时可以结合环境反馈（比如单元测试的错误信息）辅助判断。

## 四、LeanEvolve：形式化诊断驱动的工作流自我进化

> 通过静态验证的工作流只能保证逻辑自洽，无法覆盖所有实际执行中的边界情况。**LeanEvolve 的核心价值就是把验证的诊断能力转化为进化的驱动力，让工作流可以在运行中持续迭代优化。**

它采用**形式化引导为主、纯 LLM 探索为辅的双模式设计**，既保证了优化的精准性，又保留了探索创新的空间。

::: block-1
:mdnice-bold-italic[形式化引导进化是 LeanEvolve 的核心模式。当工作流执行失败时，第三层轨迹验证会输出精准的诊断信息：失败的步骤编号、违反的谓词、相关的环境反馈。系统把这些信息输入给 LLM，让它针对性地修改对应步骤的指令或者工作流结构。]

比如在论文的案例中，一个 SWE 任务的 verify_fix 步骤失败了，轨迹验证定位到问题是该步骤没有完整追踪错误链，只检查了表面症状就认为修复成功。LeanEvolve 就会指导 LLM 修改这一步的指令，要求它必须追踪完整的错误链，并用相关测试验证修复，而不是停留在第一个表面原因。修改后的工作流再次执行就成功通过了测试。
:::

> 对于没有明确环境反馈的任务，比如 AI 论文理解题，**形式化引导进化完全依赖轨迹级的谓词违反信息，同样可以精准定位问题步骤进行修正。**

纯 LLM 进化是补充模式。对于允许多次尝试的任务，这种模式不依赖形式化诊断，直接让 LLM 根据执行轨迹和结果对工作流进行全面重写。它的优势是可以跳出原有设计的框架，探索更创新的解决方案；缺点是修改不够精准，容易引入新的问题。

> 两种模式结合之后，LeanEvolve 既可以做精准的靶向修复，也可以做大范围的探索优化，能够应对不同类型的失败场景。

## 五、实验验证：跨模型跨任务的一致性收益

> 研究团队:mdnice-bold-italic[在两类典型的 Agent 任务上对 Lean4Agent 进行了全面评估，覆盖 5 款主流大模型，包含大模型和小模型两个梯队]，充分验证了方法的通用性和有效性。

实验设计严格对照，直接对比通过验证和未通过验证的工作流的表现，结论具有统计显著性。实验采用两个基准：

1. **软件工程任务** 使用 SWE-Bench-Verified 的 50 道难题子集，这些问题通常需要人类工程师花费一小时以上才能解决；
2. **AI 论文理解任务** 使用 ELAIP-Bench 的 100 道选择题子集，考察 Agent 的文献阅读与推理能力。

> 实验方法非常严谨：首先让 LLM 生成多个候选工作流，经过第二层语义验证后，随机选出 3 个通过验证的和 3 个未通过验证的，分别测试任务通过率，对比二者的差异。

![文章插图](/articles/2026-10-09-lean4agent-11-94-27-33-8c97381f/images/09.webp)

::: image-caption
表 1：FormalAgentLib 第二层验证的主要实验结果。

> 从实验结果可以得出三个核心结论：

- 第一，形式化验证的筛选效果非常显著。综合两个任务，通过验证的工作流比未通过的平均性能高出 11.94%，且所有模型所有任务上都呈现一致的正向收益。SWE 任务上的提升更大，平均达到 14.80%，说明越复杂的任务，工作流质量的影响越大。
- 第二，**小模型从验证中的收益远大于大模型。这意味着形式化验证是提升小模型 Agent 能力的性价比极高的手段，用很小的成本就能带来巨大的性能提升**。Gemma-4-31B 在 SWE 任务上的提升达到了惊人的 27.33%，几乎是大模型平均水平的两倍。:mdnice-bold-italic[这是因为能力越弱的模型，越难自己修正工作流中的缺陷，而形式化验证相当于从外部给工作流套上了正确性约束，大幅降低了对模型本身能力的要求。]
- 第三，验证通过的工作流普遍具有更合理的设计。SWE 任务中，高质量工作流通常有更精确的变量定义、结构清晰的重试循环、合理的上下文管理；而未通过的工作流往往存在前置条件缺失、重试机制无效、上下文断裂等问题。:mdnice-bold-italic[论文理解任务中，很多失败的工作流把选项评估拆成了带上下文的独立步骤，导致前面的判断影响后面的结果，违反了选项独立评估的原则，而这些问题都被图级谓词精准检测出来了。]

## 六、局限与未来展望

> 尽管 Lean4Agent 取得了非常有价值的突破，**但它依然存在三方面的局限性，这些局限也是形式化方法与黑盒 LLM 结合时的普遍矛盾**，代表了领域未来的探索方向。

| 问题点 | 说明 |
| --- | --- |
| 黑盒 LLM 的行为无法被完全形式化 | Lean4Agent 将 Agent 行为拆解为结构化步骤，把自然语言需求抽象为可检查的谓词，从而在接口层面实现形式化验证；:mdnice-bold-italic[但 LLM 内部推理过程仍是黑盒，LLMExec 假设本质上是概率性假设，非绝对数学真理，因此验证结果仅为条件性正确，而非绝对正确]。 |
| 谓词注解的质量依赖 LLM 的能力 | 实验中使用的谓词均由 LLM 从自然语言指令中自动生成，可能引入谓词指定错误或注解遗漏；**尽管 Lean 检查本身严格形式化，但若输入谓词有误，验证结果亦会产生偏差**。 |
| 结构层面的错误已显著减少 | 现代 LLM 生成的工作流中结构错误已较少见，导致结构验证层的定量价值难以通过大规模实验体现，更多依赖针对性案例验证；这反映 LLM 工作流生成能力已较成熟，也意味着形式化验证重心正逐步转向语义与轨迹层面。 |

::: block-1
未来这个方向有很多值得探索的方向：:mdnice-highlight[比如进一步提升谓词自动生成的质量和覆盖率，把形式化验证信号融入 LLM 的训练过程，发展能够自我验证、自我进化的端到端 Agent 系统]，以及把这套范式拓展到更多高风险领域，比如自动驾驶、工业控制、金融交易等场景的 Agent 系统。
:::

## 七、总结

总之，Lean4Agent 首次将依赖类型形式化语言完整引入 LLM Agent 领域，构建了从结构到语义、从静态设计到动态执行的全栈验证体系，并实现了形式化诊断驱动的工作流自我进化。:mdnice-bold-italic[11.94%的平均性能提升和 7.47%的进化增益，充分证明了形式化方法是提升 Agent 可靠性的有效路径，也为构建可证明正确的长链路 Agent 系统打下了坚实的基础。]
