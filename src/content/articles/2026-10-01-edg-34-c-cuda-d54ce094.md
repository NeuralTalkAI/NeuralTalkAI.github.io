> 如果你没听过 EDG，很正常。这家公司 1992 年成立，34 年来基本不做面向普通开发者的产品，只做一件事：把 C/C++ 前端卖给其他编译器厂商。

经典的 Intel C++ 编译器、NVIDIA 的 nvcc、PGI、Oracle/Sun、德州仪器、Green Hills、Cray、SGI，前端用的都是 EDG。GCC、Clang、MSVC 是大家熟知的三极，EDG 是藏在商业工具链里的第四极——你跑过的大部分 CUDA 代码，编译的第一步其实就是它处理的。

::: block-1
关于标题里的一个说法"EDG 藏在 nvcc 背后"这里我们要多嘴一句🥱，这个说法需要多补一句。nvcc 本质是一个编译器驱动（compiler driver）。

编译 `.cu` 文件时，host 代码（CPU 端）会被抽出来交给系统的 GCC、Clang 或 MSVC；:mdnice-highlight[真正由 EDG 处理的是 device 代码（GPU 端）和 CUDA C++ 语法——也就是 `__global__`、核函数调用 `<<< >>>` 这些关键字的解析工作。]

NVIDIA 论坛的专家多次确认过这一点：CUDA 工具链里的 `cudafe++` 和 `cicc` 第一阶段用的就是 EDG 前端，版本号直接写在工具输出里（"Based on Edison Design Group C/C++ Front End, version 4.10"）。第三方对 CUDA Toolkit 13.0 的逆向分析也确认（之前我们有一篇文章似乎提到过），`cudafe++` 基于 EDG 6.6。所以准确的说法是：**nvcc 管道里的 CUDA C++ 前端是 EDG 做的**，而不是整个 nvcc 都是 EDG。这是两个不同的概念。
:::

## 一、仓库里有什么

> 打开 GitHub 仓库 github.com/edgcpp/compiler[1]，README 第一句话就说得很清楚："The EDG C/C++ front end is the primary focus of this repository." 但这可不是一份简单的词法分析器代码。

官方列出来的组件包括：C/C++ 前端本体、一个 C 代码生成后端、一个 C++ 源到源变换后端、prelinker（自动模板实例化）、最小运行时库、中间语言（IL）读写工具、名字反修饰器，还有一套内部开发工具。

### 1.1 目录结构

> 从仓库根目录看，EDG 的代码组织很老派，也很清晰。没有复杂的 monorepo 设计，每个目录干什么一眼就能看懂：

| 目录 | 内容说明 |
| --- | --- |
| `src/` | 前端核心源码，包括解析、语义分析、C/C++ 生成后端、prelinker |
| `include_c++` / `include_c99` | 标准头文件，分别对应 C++ 与 C99 标准 |
| `lib_src/` | 最小运行时支持库（不含 iostream 等完整库） |
| `dev_tools/` | 开发专用工具链与 Python 脚本库 |
| `dev_annex/` | 开发附件：调试技巧、教程、测试二分脚本 |
| `doc/` | Sphinx 文档源文件，使用 shibuya 主题生成 |
| `tests/` | 测试套件 |
| `benchmarks/` | 性能基准测试 |
| `bases/` | 基础配置与基础设施 |

*表 1：EDG 仓库顶层目录结构*

GitHub 语言统计显示 C 占 58.6%，C++ 占 41.3%，剩下不到 0.1% 是 Python 和 Shell。但 Hacker News 上 EDG 工程师 Daveed Vandevoorde 补充了一个细节：虽然是 C++ 编译器前端，源码主体其实是 C 风格，C++ 代码也沿用了 `.c` 扩展名。

整个项目**不使用 C++ 标准库**，别的语言可能用继承的地方，EDG 用的是 C 风格的 `union { ... } variant;`。**这在今天的 C++ 项目里几乎是活化石级别的写法。** 😅

### 1.2 怎么编译

> 目录下的 BUILD.md 和 HACKING.md 把构建方式说得很清楚。依赖很轻：Python 3.6+、CMake 3.19+、一个现代 C++ 编译器（g++ 5.2+、Clang 3.4+ 或 MSVC 2017+），再加一个强烈推荐的 Ninja。CMake 预设覆盖了最常见的平台：macOS ARM Clang、Linux GCC/Clang、Windows MSVC，各有 debug/release 两档。

**EDG 在开发环境上花了不少心思，主要体现在 Docker 上**。HACKING.md 强调前端开发目前在 Linux x86_64 上支持最好，Docker 的作用是"确保一致的开发环境、方便问题复现、降低不同发行版的配置麻烦"。

- 项目提供了 `dev-init.py` 脚本，支持 `docker` 和 `native` 两种初始化方式；
- 进环境后，`edg-docker-test` 跑测试，`edg-docker-shell` 提供一个带 gdb 和 rr（Mozilla 的记录回放调试器）的 shell。

对于一个 1992 年开始写的代码库来说，这种现代化的开发体验说明维护者在开源前确实做了不少准备工作。

README 还建议用 partial clone：`git clone --filter=blob:none`，这样保留完整 git 历史，但只下载最新版本的文件。这说明仓库历史很厚重——开放时已经有超过 6.2 万次提交。

### 1.3 代码风格

> Hack News 讨论区里，老程序员们对 EDG 的代码风格聊得很多。总结下来有几个特点：

| 规则特点 | 说明 |
| --- | --- |
| 注释位置 | 函数注释不写在上方注释块里，而是放在函数签名之后、左花括号之前。HN 用户 cyberax 说："看起来怪，但逻辑上更自然——先看到定义，再看到解释，还不用重复函数名。" |
| 类型前缀 | 大多数类型名用 `a_` 前缀（如 `a_statement_ptr`），以元音开头的则用 `an_`（如 `an_object_lifetime_ptr`）。HN 用户 spatulon 挑出了这条规律，很多人表示第一次见。 |
| 扩展名 | C++ 源码用 `.c`，不用 STL，整体风格接近早期 C++（"C with Classes" 时代）。 |

::: block-1
一位在嵌入式编译器领域工作了近 20 年的网友说：":mdnice-highlight[我们当年用 EDG 前端，很少遇到编译器 bug 是他们的错]。"另一位则说：":mdnice-highlight[那个年代的代码早于 web、早于大量开源风格指南、甚至早于大多数开源代码本身，所以人们自己发明风格。GNU 标准的影响当时还没来。] "
:::

## 二、核心组件

README 对前端能力的描述很克制，没有性能数字，只给了三个词：parsing compatibility（解析兼容性）、extensive documentation（深度文档）、extreme configurability（高度可配置）。

这三条里，第一条是最硬的🐂。

### 2.1 bug-for-bug 兼容

> EDG 的兼容性是"GCC 能编通的代码，EDG 也能编通——包括那些悄悄依赖编译器怪癖的代码"。:mdnice-bold-italic[官方叫 "bug emulation"，民间叫 bug-for-bug 兼容。这不是贬义，是 EDG 三十年的核心竞争力，也是 Intel、TI 这类厂商选它的原因：存量代码不用改就能换编译器。]

一个经典例子是 C++98 的 `export template`。这是 C++ 标准历史上最麻烦的功能之一，允许把模板定义放在 `.cpp` 文件里而不是头文件里。**因为实现难度太高，GCC、Clang、MSVC 全都不支持**。

而 EDG 是**世界上唯一真正实现了 `export template` 的编译器前端**。标准委员会的 Herb Sutter 在 2025 年的会议 trip report 里专门讲过这件事：EDG 其实是最反对 export template 的，John Spicer 在委员会里一直指出这个功能的技术问题；但委员会最终决定标准化它，EDG 没有旁观，而是把它做了出来——"耗时比实现一整个 Java 编译器前端还长"。几年后委员会果然废弃了 export template，因为 John 和 EDG 的反对是对的。

### 2.2 两个后端

源码里有两个文件值得单独说：`src/c_gen_be.c` 和 `src/cp_gen_be.c`，分别是 C 生成后端和 C++ 生成后端。按 EDG 工程师 Daveed Vandevoorde 在 HN 上的解释，:mdnice-bold-italic[EDG 前端只做三件事：解析语言、完整语义分析、可选地把表示下放到近似 C 语言语义的中间层。那个"下放到 C 语义"就是由 `c_gen_be.c` 完成的。如果你需要在没有原生 C++ 编译器的平台上跑 C++ 代码，这个后端可以把 C++ 翻译成 C，再交给 C 编译器。]

`cp_gen_be.c` 是 C++ 源到源变换后端，用来做代码重构、静态分析、以及任何需要读写 C++ 源码的场景。README 明确说这对"source-to-source transformation applications"有用。**也就是说，EDG 开源的不只是"能吃下 C++ 的解析器"，还有"能吐出 C++ 的生成器"。**

### 2.3 prelinker

> **prelinker 是 EDG 仓库里最有历史价值的组件之一**。它的工作逻辑在今天看来很反直觉：编译时模板不实例化，链接前由 prelinker 扫描程序到底用了哪些实例，然后回填源码再编译一轮。老 Intel 编译器那个独立的 prelink 步骤就是这么来的。

现在 GCC/Clang 的即时实例化已经是默认做法，prelinker 看起来像个古董。但正因为开源了，你可以第一次读到这套机制的完整实现，而不只是论文里的一张图。对研究编译器历史或者维护遗留工具链的人来说，这是很有价值的参考。

## 三、为什么现在开源

官方 FAQ 第 4 条写得很直接："EDG as a corporation is going away, but the front end has been open-sourced and will continue to be developed." 公司要关了，开源是关门前的遗产处理。

### 3.1 从三人到六人

> Hacker News 上 Daveed Vandevoorde 亲自讲了 EDG 的人员变迁：

- 创始人 Steve Adamczyk 一开始单干，1992 年 John Spicer 加入后变成三人；
- 1999 年 Daveed 加入替代退休的 Mike Anderson，还是三人；
- 2004 年 Mike Miller 加入变四人；
- 2007 年 Mike Herrick 加入变五人；
- 2020 年代初短暂到七人，随后 Ellen Herrick 退休回到六人；

再后来，最年轻的三个工程师大约一年前去了 NVIDIA。创始人 Steve Adamczyk 曾对 Daveed 说，:mdnice-bold-italic[他开公司是为了"享受工作，而不是把它做大到夺走那份快乐"。这解释了为什么 EDG 三十四年始终保持极小团队——它作为不追求扩张的创业公司，一直以来都是几个专家的手工作坊。]

### 3.2 谁来接手

开源后，EDG 前端由非营利组织 C++ Alliance 以财政赞助（fiscal sponsorship）方式托管，模式跟 Boost 类似。创始人 John Spicer 亲自当财政赞助委员会主席，原 EDG 工程师做初始维护人。FAQ 第 8 条说："Over time, the goal is an open process that welcomes community contributors while keeping the technical quality EDG is known for."

许可证方面，官方 FAQ 第 6 条写的是 "under the LLVM license"。打开仓库根目录的 LICENSE.txt，实际文本是 **Apache License 2.0 with LLVM Exceptions**。这个许可证组合在 LLVM 项目里很常见：前半段是标准 Apache 2.0，后半段加了关键例外——允许把编译产物嵌入到目标代码里再分发时，不必遵守 Apache 2.0 第 4(a)、4(b)、4(d) 条；同时如果跟 GPLv2 代码链接产生专利条款冲突，可以自动豁免。**这意味着商用基本没障碍，也解释了为什么 FAQ 第 7 条能直接说"Yes"——组织可以继续用 EDG 做商业产品。**

### 3.3 社区怎么看

> HN 上的讨论情绪比较复杂。

一方面，代码质量得到很高评价。用户 jcranmer——他自己就是编译器开发者——说："**世界上基本只有四个 C++ 前端：gcc、clang、MSVC 和 EDG。几乎每个 C++ 编译器都是这四个之一的换皮版**。"另一位用户补充说，Visual C++ 的 IntelliSense 用的就是 EDG 前端，而不是 MSVC 自己的前端，"这本身就说明了问题"。

但另一方面，很多人意识到这不是"开源带来新生"的故事。jcranmer 直接说：":mdnice-bold-italic[EDG 前端开源是因为 EDG 本身正在关门，开源只是过渡方案，让客户有时间迁移到 Clang😒。所以这其实不是好消息——意味着一个前端基本走到了生命末期]。"另一位用户说得更直接："据我所知，并没有一个围绕 EDG 的蓬勃社区在多年恳求源代码释放。*Clang 和 GCC 已经足够好了。这更像是几个退休的人想确保他们一生的工作不会消失在历史里，同时避免坑害最后几个客户。"*

::: block-1
C++ 标准委员会的 Gabriel Dos Reis 也在官方公告里发了感言。他曾任微软技术研究员，主导了 C++20 Modules 的 IFC 格式设计。他说：":mdnice-bold-italic[EDG 的前端让我印象最深的是工程质量——它同时认真对待 C++ 标准的细枝末节和与其他编译器兼容的混乱现实。我们开玩笑说，EDG 比其他 C++ 前端更兼容那些前端自己。"但他也承认，开源后的 EDG 能不能持续得到投入，取决于社区愿不愿意在 GCC/Clang 之外再维护一条完整的 C++ 前端。]
:::

## 四、这件事的意义

抛开情怀，EDG 开源在技术上至少有三层实际意义。

### 4.1 意义一：工业级 C++ 前端在 GCC、Clang 外的第三份参考

> 一个工业级 C++ 前端怎么写，公开参考从此有了第三份——而且可能是文档最全的一份。

GCC 的前端历史包袱重、代码风格独特；Clang 虽然设计现代，但深度嵌入 LLVM 生态，单独剥离前端并不容易。EDG 的代码虽然老派，但相对独立，而且自带 Sphinx 生成的完整文档体系。

README 里 "extensive documentation" 不是空话——doc/ 目录下有一整套用 Sphinx + shibuya 主题构建的文档，开发者可以直接 `pip3 install Sphinx shibuya` 后本地生成 HTML。

### 4.2 意义二：把静态分析、重构引擎、源到源翻译的工具门槛降低了

以前要写一个能处理真实世界 C++ 的静态分析工具，要么基于 Clang（但会被 LLVM 的复杂性淹没），要么自己养一个解析器团队（几乎不可能追上 C++ 的演进）。

现在可以直接基于 EDG 这个文档化的前端，利用它的 C++ 生成后端做代码变换，或者读它的 IL 格式做深度分析。

### 4.3 意义三：为了 AI Agent

> README 里的一句话值得注意。"To further aid **humans and AI agents** in product development there is additional documentation for tips, tricks, and tutorials..."

一个 1992 年创建的 C++ 前端，在 2026 年开源时，把 "AI agents" 写进了目标读者名单。这不是为了蹭热点——EDG 的客户里有 NVIDIA😅，而 NVIDIA 正是当下 AI 基础设施的核心推手。编译器代码库的目标读者定义已经变了，这件事不得不做🦆。

## 五、写在最后

> 你写过的第一行 C++ 是被哪个编译器处理的？GCC、MSVC，还是根本不在乎前端是谁的 nvcc？

对大多数开发者来说，编译器是个黑箱——代码进去，可执行文件出来，中间发生了什么没人关心。EDG 三十四年的全部意义，就是藏在这个黑箱最深处，把最脏最累的活（解析 C++）干完，让上面的厂商可以专心做优化器和代码生成。

现在黑箱打开了一角。**公司要消失了，但代码留了下来** 😅。它可能不会成为下一个明星开源项目，但对那些想知道"一个工业级 C++ 前端到底长什么样"的人来说，这 6.2 万次提交、三十四年的商业锤炼、无数标准委员会会议的反馈闭环，已经是一份很难复制的教材。

编译器是 C++ 世界的地基。地基里的每一块砖，都值得看看👀。
