## 一、为什么 LLM 推理会“不准”？确定性推理的本质困境

> 在很多人的认知里，同一个模型、同一个提示词，无论什么时候跑、和多少请求一起跑，输出结果都应该完全一样**。但在实际的生产推理系统中，这一认知并不成立。**

批处理大小、提示词分块方式、预填充与解码阶段切换、KV 缓存的复用与淘汰，**这些日常的调度优化策略，都可能让最终输出的 logits 出现位级差异。**

### 1.1 推理不确定性的来源

> 推理不确定性的来源分为两个层级，分别对应 GPU 内核与推理引擎两个层面。

- **第一个层面是 GPU 内核层面。深度学习中的大量运算本质是浮点加法与乘法，而浮点数加法不满足结合律，计算顺序的改变会导致最终结果的位级差异**。:mdnice-bold-italic[GPU 内核会根据输入张量的形状选择分块策略与归约顺序，比如不同的批大小会让内核采用不同的 tile 划分方式，累加的顺序就会发生变化]，最终结果也就不一样。
- **第二个层面是推理引擎层面。调度器与 KV 缓存管理器决定了输入给内核的 token 序列与 KV 状态**。:mdnice-bold-italic[比如不同的批处理组合会改变 token 的打包方式，分块预填充会把长提示拆成不同大小的块逐步计算，KV 缓存复用会直接使用之前请求留下的缓存] 而不是重新计算。这些变化都会改变内核接收到的输入内容，进而影响最终输出。

::: block-1
针对这个问题，行业内已经出现了批不变量内核的思路，通过固定内核的分块策略，让不同批大小下的计算顺序保持一致。

不到一年时间，这一思路就从博客文章走向了生产落地：:mdnice-highlight[vLLM 推出了批不变量模式，SGLang 推出了确定性模式，DeepSeek-V4 更是把端到端的批不变量内核融入了训练栈。]
:::

> 但这些方案都存在一个根本的局限：**批处理组合只是服务器改变执行路径的方式之一**。提示词分块、预填充与解码的切换、KV 缓存的复用与淘汰，这些同样会改变执行路径的因素，都没有被覆盖。更重要的是，**目前没有一个系统级的形式化定义，说明确定性推理到底要求整个系统满足什么条件。**

为了直观展示现有方案的不足，论文对 vLLM 0.28.0 与 SGLang 0.5.19 的不同模式进行了全面测试，覆盖批处理组合、分块预填充、预填充-解码等价、前缀复用四大场景。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/06.jpg)

::: image-caption
表 1：Vosti与生产级推理引擎的确定性激励测试。每个单元格表示位级匹配的logit对数占总比较对数的比例，绿色代表完全一致，红色代表至少存在一处不匹配。从测试结果可见，现有生产系统的确定性模式仅在部分模型与场景下能实现完全匹配，在Gemma3-4B等模型上普遍存在不匹配，尤其是分块预填充、预填充-解码切换与前缀复用场景，SGLang确定性Triton模式的预填充-解码匹配率仅为3/384，说明现有方案的确定性覆盖不完整。
:::

> 从测试结果可以看出几个明显的规律：

- 在 Llama3.1-8B 模型上，vLLM 批不变量模式与 SGLang 确定性 FA3 模式能够通过所有测试，**但 SGLang 确定性 Triton 模式在预填充-解码场景下只有 3/384 的匹配率**；
- **在 Gemma3-4B 模型上，所有四种生产级确定性配置都在所有类别中出现了不匹配，哪怕是表现最好的 vLLM 批不变量 Triton 模式**，批处理匹配率也只有 242/296，预填充-解码匹配率只有 192/384。

::: block-1
论文特别指出，这些测试并不是穷尽验证，通过了也不代表在所有场景下都确定；但只要出现一个不匹配，就说明存在数值差异。:mdnice-highlight[这些差异不一定是 bug，而是说明单一批不变量内核，不足以覆盖分块、预填充解码切换、缓存复用等所有执行变化带来的影响。]
:::

## 二、从模糊到精确：确定性 LLM 推理的系统级形式化定义

> **要系统性解决确定性问题，第一步是精确定义“什么是确定性推理”**。在此之前，行业里的“确定性模式”更多是工程层面的约定，没有严格的数学定义，也就无法进行全链路的证明与验证。:mdnice-bold-italic[论文的第一个核心贡献，就是给出了系统级的确定性 LLM 推理形式化定义，把“结果一致”这个模糊的工程需求，变成了可验证、可推导的严格命题。]

- 首先，定义的前提是固定推理配置，包括模型权重、数值精度、平台与实现中所有影响数值的方面。在这个前提下，输出记录是 logit 位模式与输出 token 的二元组。
- 然后，**论文引入了“单请求视图”的概念**。:mdnice-bold-italic[因为推理引擎会同时处理多个请求，每个步骤可能输出部分请求的结果，不同执行的调度顺序、批处理组合都不一样，直接对比整个系统的执行序列没有意义。] 单请求视图会把调度细节、批处理位置、其他请求的输出都去掉，只保留单个请求的输出记录序列，按执行顺序排列。

> 在此基础上，确定性推理的定义是：对于任意两次有限执行，只要两个请求的提示词与初始采样器状态相同，它们的单请求视图就是前缀可比的。

$$
view_{r_1}(T_1) \preceq view_{r_2}(T_2) \vee view_{r_2}(T_2) \preceq view_{r_1}(T_1)
$$

这里的 $\preceq$ 表示前缀关系，意思是较短的视图，必须和较长视图的开头完全一致。**换句话说，两个执行只要都输出到了第 $n$ 个 token，那前 $n$ 个 token 对应的 logits 和 token 必须位级完全一样，不管中间是怎么调度的。**

::: block-1
这个定义有几个非常重要的特点：

- 第一，它只约束可观测输出，不假设系统内部的实现方式，不管用不用批处理、分不分块、有没有 KV 缓存，只要输出满足前缀可比，就是确定性的。
- 第二，它不是活性属性，不保证请求一定会被调度、一定会执行完成，只保证只要输出了，结果就一致。
- 第三，它不是功能正确性定义，不保证输出符合模型的预期语义，哪怕结果全错，只要每次错得都一样，就满足确定性。
:::

这个定义把确定性推理的边界划清楚了，为后续的设计与验证提供了明确的目标。:mdnice-bold-italic[之前的工程方案都是在解决具体的点问题，而有了这个定义，就可以系统性地构建全链路的确定性系统。]

## 三、Vosti 的架构设计：双层验证的确定性推理引擎

> 有了严格的定义，接下来就是实现与验证。Vosti 没有走“工程调优+大量测试”的经验主义路线，而是**采用了引擎层与内核层分离的双层验证架构。** 两层验证在抽象边界上对接，各自负责自己的领域，最终组合成全系统的确定性保证。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/07.jpg)

::: image-caption
图 1：Vosti推理系统与双层验证架构。括号标注了各验证工具的作用范围；Verus以共享内核合约为假设前提，内核验证器负责证明这些合约成立。引擎层负责调度、批处理与KV缓存管理，通过Verus归纳证明每个输出logit仅由请求的token历史决定；内核层负责Triton内核的位级一致性验证，通过Z3证明不同执行场景下内核输出一致。两层通过内核合约对接，共同构成完整的确定性证明。
:::

> Vosti 遵循一个核心设计原则：对于固定的模型与部署配置，运行时可以改变 token 批处理方式、状态存储方式、状态访问方式，但必须保留每个位置的浮点操作序列不变。

这个原则并不要求整个系统只能用一个内核，也不要求 tile 大小必须唯一，而是说**内核的选择只由固定的模型与环境决定，不能随运行时的批大小、分块大小等状态变化**。比如矩阵乘法的块大小可以根据层的权重维度变化，但不能随运行时的批大小变化。

> 基于这个原则，Vosti 把验证拆成了两层：

- **第一层是引擎层。用 Verus 验证语言进行归纳证明，证明每一个引擎步骤都维护了系统不变量，每个输出的 logit 向量都只由请求的 token 历史决定**。:mdnice-bold-italic[这一层把 GPU 内核运算抽象成一个黑盒函数，假设这个函数满足内核合约]，也就是相同的逻辑输入会得到相同的输出，然后只关注调度、缓存、批处理这些引擎逻辑。
- **第二层是内核层。用自研的 Triton 分析器把带注解的 Triton 代码转换成 tile 级中间表示，然后用 Z3 定理证明器证明内核合约成立**，:mdnice-bold-italic[也就是同一个逻辑输入，不管批大小、查询长度、KV 缓存布局怎么变，输出都是位级一致的。]

::: block-1
:mdnice-highlight[两层验证在“内核合约”这个边界上对接：引擎层假设合约成立，内核层证明合约成立，两者组合起来，就得到了端到端的系统确定性证明。] 这种分层验证的思路，既降低了每一层的验证复杂度，又保证了全链路的严谨性。
:::

## 四、引擎层：基于不变量的调度与 KV 缓存确定性保障

> 引擎层的核心任务，是保证不管怎么调度请求、怎么复用 KV 缓存，输入给内核的逻辑输入，永远和请求的 token 历史一一对应。:mdnice-bold-italic[为此，Vosti 在引擎设计上做了三个关键选择，并通过维护一组不变量，用形式化证明保证了每一步调度都不会破坏确定性。]

### 4.1 三个关键设计选择

| 关键设计 | 描述 |
| --- | --- |
| 固定内核配置 | :mdnice-bold-italic[系统初始化时即绑定模型与固定内核配置，含特化内核版本及 tile 参数。配置仅取决于模型与部署环境，与批大小、预填充分块大小、请求阶段（预填充/解码）无关]。推理全程无运行时自动调优，不回退至验证集外配置；缺失对应配置则直接拒绝请求。 |
| 精确前缀匹配 | **缓存页仅限生成该页的 token 前缀复用。** 1. 缓存管理器先通过滚动哈希筛选候选页，再严格校验 token 序列、前缀深度及物理父页；2. 仅完全匹配才复用，哈希碰撞不会引发误复用。内存紧张时，仅淘汰无引用的叶子页；3. 只要子页引用父页，父页即保留，不被回收或复用。 |
| 缓存复用与生成分离 | :mdnice-bold-italic[调度器每步起始先解析全部前缀缓存命中，再注册本步将生成的新缓存页。新页仅在后续步骤中可被复用，当前步不可用。] 已存在的共享前缀页为只读，不可修改；新增 KV 值统一写入私有后缀槽。 |

这三个设计，从内核选择、缓存匹配、读写时序三个维度，把运行时变化可能带来的不确定性都隔离在了外面。

### 4.2 KV 缓存不变量

> **引擎层证明的核心，是 KV 缓存不变量。** 简单来说，就是每一个有效的 KV 缓存条目，不管是活跃请求正在用的，还是保留下来等待复用的，都等于从头开始冷启动计算对应 token 前缀得到的 KV 值。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/08.jpg)

::: image-caption
图 2：跨共享、保留、淘汰与重算场景的 KV 缓存不变量示意：每个已初始化的活跃或保留缓存项，都等于对应 token 前缀冷启动前向计算得到的 KV 值。示例中 $P_i$ 表示第 $i$ 个物理 KV 缓存页，每页存储两个 token 的 KV 值。该图通过四个阶段直观演示了 KV 缓存不变量的维护逻辑，是引擎层确定性证明的核心基础。共享阶段两个请求复用公共前缀页，保证相同前缀对应相同物理 KV 值；保留阶段请求结束后后缀页仍留存缓存，其数值有效性不随请求生命周期变化；淘汰阶段仅移除无引用的叶子页，不影响被引用的父页；重算阶段新请求复用公共前缀并重算后缀，新生成的页仍符合前缀 - 值的对应关系。这种设计确保缓存的复用、淘汰、重算都不会改变对应前缀的计算结果，从根本上规避了缓存状态差异带来的输出波动。
:::

**这个不变量的意义在于，不管缓存是怎么来的，是刚算出来的、是之前请求留下的、是共享的还是重计算的，逻辑上的值都是确定的，和 token 前缀严格一一对应。** 这样就把物理缓存的变化，和逻辑上的数值解耦了。

:mdnice-bold-italic[为了维护这个不变量，系统还同时维护了请求一致性、布局一致性、写隔离等其他不变量]，共同构成了完整的不变量集合。

### 4.3 不变量的保持与归纳证明

> 论文证明了，每一个引擎步骤，从初始化、请求接入、规划执行到状态更新，都会保持所有不变量成立。比如缓存复用的场景：

- 当一个请求复用了之前保留的缓存前缀，**因为 KV 缓存不变量，这些缓存的值等于对应前缀的冷启动值；**
- 把这些缓存映射到新请求的页表后，新请求的已缓存前缀对应的 KV 值，还是等于冷启动值，所以不变量保持成立。

在此基础上，通过归纳法就可以证明：对于任意请求，每一步输出的 logits，都等于对这个请求的 token 历史做冷启动前向计算得到的结果。**换句话说，输出只由 token 历史决定，和执行路径无关。**

## 五、内核层：关系型合约与 Triton 内核的位级一致性验证

> 引擎层保证了输入的确定性，:mdnice-bold-italic[但如果同一个逻辑输入，内核在不同批大小、不同布局下计算结果不一样，那最终输出还是不确定的。 内核层的目标，就是证明同一个逻辑输入，不管怎么打包成批、不管是预填充还是解码阶段、不管 KV 缓存怎么分页，内核输出的结果都是位级一致的。]

### 5.1 关系型内核合约

首先，**内核层用“关系型合约”来定义跨调用的一致性要求**。每个合约关联两次内核调用的输入输出区域，按逻辑索引选择张量单元，要求选中的输出位级相等，其他输入不做约束。

::: block-1
举个最简单的矩阵乘法例子：输入是 $M×K$ 的激活和 $K×N$ 的权重，输出是 $M×N$ 的结果。合约比较任意选中的一行激活，和单例运行时的对应行，只要这行的输入和权重都相等，输出的对应行就必须相等。其他行的输入是什么样，不影响这行的结果。
:::

**这种行级的保证，正好对应引擎层的请求级批不变性**，不管 token 怎么打包成批，每个 token 对应的计算结果都是独立且确定的。

### 5.2 结构分析与控制流对齐

> 为了证明合约成立，验证器会把带注解的 Triton 代码转换成 tile 级中间表示，然后进行结构分析，检查两次调用的控制流是否对齐，操作顺序是否一致。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/09.jpg)

::: image-caption
图 3：矩阵乘法契约、tile 中间表示与 Z3 验证检查点。圆圈数字标注了语句与反向依赖的对应关系；切片为半开区间，加载操作做零填充，存储操作做边界掩码；mma 表示 tile 点积运算，parfor 表示独立网格迭代。该图拆解了批量不变矩阵乘法的验证流程，是内核级关系验证的典型范例。验证流程从带注解的 Triton 代码出发，首先将代码翻译为 tile 级中间表示，明确每个 tile 的计算流程与内存访问模式；再通过反向依赖分析，从输出相等的目标倒推所需的输入约束；最终通过 Z3 SMT 求解器自动验证约束的满足性。其核心逻辑是：当 tile 尺寸由权重维度固定、不随运行时批量变化时，不同批量下对应行的计算会经历完全相同的操作顺序与运算数，因此浮点结果按位一致。这种方法无需穷举所有批量取值，即可证明任意批量下的等价性，验证效率远高于测试用例覆盖。
:::

对于矩阵乘法来说，每个 tile 的计算都是从零初始化累加器，然后加载激活 tile 和权重 tile ，循环累加，最后存储输出。tile 的大小由固定的 N 和 K 决定，和运行时的 M 无关。**验证器会把打包调用中的选中行，和单例调用中的对应行配对，检查循环范围、初始化、累加操作、存储操作是否完全对齐。**

::: block-1
:mdnice-highlight[因为浮点数加法不满足结合律，所以只要操作的顺序完全一样，输入也一样，结果就一定位级相同。] 结构分析就是要保证，对于选中的输出区域，所有的数值相关操作，顺序都是完全一致的。
:::

### 5.3 值感知分析与因果一致性

> **对于注意力算子来说，只有结构分析还不够，因为注意力有因果掩码，不同长度的 key 序列，循环次数不一样。** 如果简单要求循环次数相同，那就无法证明预填充和解码的一致性。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/10.jpg)

::: image-caption
图 4：尽管查询索引与物理页分布不同，预填充与解码阶段使用的查询与 KV 前缀在逻辑上等价，因此输出按位一致。其中 $q_p$、$KV_p$、$o_p$ 均按逻辑位置索引，未来 KV 位置被因果掩码屏蔽。该图解释了预填充与解码阶段输出等价的核心原理，是 Vosti 支持预填充 - 解码一致性的关键。预填充阶段一次性处理完整序列，解码阶段逐 token 增量计算，二者的输入张量形状、物理页映射、批量维度完全不同，但对应逻辑位置的查询向量与历史 KV 前缀完全一致。因果掩码确保每个位置仅关注历史 token，超出前缀的 KV 区域被完全屏蔽。Vosti 通过值感知的区域分析证明，额外的无效 KV tile 迭代不会改变选中位置的计算状态，因此即使输入长度与布局不同，对应逻辑位置的注意力计算过程完全等价，最终输出按位一致。
:::

> **为此，验证器引入了值感知的区域分析，用抽象解释的方法跟踪张量中已知为零、负无穷、布尔值的区域，然后反向推导依赖关系。** 比如被因果掩码屏蔽的位置，得分都是负无穷，对应的权重都是零，这些位置的计算不会影响选中的输出。

**通过值分析可以证明，额外的 key tile 迭代，对于选中的输出来说，所有掩码都是 false，计算会保留原来的状态，不会改变结果**。:mdnice-bold-italic[这样，不同长度的 key 序列，只要前缀相同，选中位置的输出就一定相同。]

这就解决了预填充与解码的一致性问题：同一个逻辑位置，不管是在预填充阶段和很多 token 一起计算，还是在解码阶段单独计算，用到的查询和 KV 前缀都一样，操作顺序也一样，结果就位级一致。

::: block-1
回顾一下，:mdnice-highlight[内核层通过关系型合约定义跨调用的一致性要求，通过 tile 级结构分析保证操作顺序完全一致，通过值感知分析消除因果掩码带来的冗余依赖，最终证明了内核在不同批大小、查询长度、KV 布局下，对相同逻辑输入输出位级一致。]
:::

## 六、实测表现：确定性与性能的平衡

> 形式化验证保证了确定性，但工程上还要看性能。如果确定性是以数倍性能下降为代价，那很难在生产环境中落地。**Vosti 的测试结果显示，它在解码密集型工作负载下，性能甚至优于 vLLM 的批不变量模式，实现了确定性与性能的平衡。**

### 6.1 确定性测试结果

论文用 7 个模型进行了全面的确定性测试，包括 Llama3.1-8B、Llama3.2-3B、Gemma3-4B、Gemma3-12B、Gemma3-27B、Gemma4-12B、Gemma4-31B，覆盖批处理组合、分块预填充、预填充-解码等价、前缀复用四大场景，总共 5488 项位级对比测试。

测试结果是，**Vosti 全部通过了所有测试，没有一例假阳性。而作为对比的生产级系统，在 Gemma 系列模型上普遍存在不匹配，尤其是分块、预填充解码切换、前缀复用场景。**

> 论文还分析了**生产系统出现不匹配的原因，主要有两类：**

| 类别 | 描述 |
| --- | --- |
| 元数据依赖的特化 | 例如 FA3 依据批级的 K 长度边界动态决定是否启用局部窗口掩码；该决策直接影响内核特化策略与分块方式，因此批处理组合的变动会导致注意力输出发生变化。 |
| 路径依赖的数值行为 | 例如 SGLang 在 Triton 实现中，预填充路径与解码路径采用不同的数值计算算法；又如 vLLM 在其不变量 Triton 路径中，查询分块会改变所访问的全掩码 softmax tile；:mdnice-bold-italic[在处理这些 tile 时，可能将负无穷对应的最大值替换为零，从而引入额外的舍入误差，影响后续计算结果。] |

这些差异都不是 bug，而是**工程优化带来的副作用，也说明了单靠内核层面的批不变性，不足以实现全系统的确定性。**

### 6.2 吞吐量性能

> 论文在 H200 GPU 上测试了不同引擎的预填充与解码吞吐量，随缓存上下文长度的变化。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/11.jpg)

::: image-caption
图 5：不同缓存上下文长度下的预填充（上）与解码（下）吞吐量（数值越高性能越好）。该图完整呈现了 Vosti 与主流引擎在两个核心计算阶段的性能差异，反映了确定性算子设计的场景化特性。预填充阶段处理长序列，生产引擎可自适应调整 tile 尺寸优化吞吐，Vosti 受固定配置限制性能偏低；解码阶段处理短序列小批量，Vosti 的小 tile 配置反而更适配场景，性能显著优于 vLLM 不变模式。整体来看，Vosti 在解码主导的工作负载下具备实用性能，而预填充性能的差距也指明了未来优化方向：通过验证跨 tile 配置的算子等价性，实现场景自适应的内核调度，同时保留确定性保证。
:::

具体来说，**解码吞吐量方面，Vosti 是 vLLM 不变量配置的 1.36 到 3.19 倍。预填充吞吐量方面，Vosti 低于两个引擎的默认模式和确定性模式。**

> 这种差异和内核的 tile 大小选择有关。

- SGLang 受益于 DeepGEMM 和高效的注意力实现，包括 FA3 和 Triton 解码路径的分裂 KV。
- Vosti 和 vLLM 不变量模式都用 Triton 矩阵乘法，但 vLLM 的更大 tile 更适合预填充场景，Vosti 的更小 tile 更适合解码场景。

### 6.3 端到端会话性能

> 对于编码智能体、文档分析这类场景，通常会跨调用复用长上下文，新的消息逐步扩展历史，这种工作负载是解码密集型的。论文用合成的智能体工作负载测试了端到端的会话完成时间。

![文章插图](/articles/2026-10-05-vosti-llm-7ba23ea6/images/12.jpg)

**测试结果显示，解码时间占了 Vosti 总会话时间的 91%到 93%，预填充的开销影响很小。** Vosti 完成会话的时间比 vLLM 不变量模式快 1.14 到 2.20 倍，当然还是比两个引擎的默认模式和 SGLang 的确定性模式慢。

## 七、总结与展望

> Vosti 的工作，**第一次把确定性 LLM 推理从工程经验层面，提升到了系统级形式化定义与全链路验证的高度。** 它不仅解决了现有确定性模式覆盖场景不全的问题，更建立了一套从定义到实现再到验证的完整方法论，为整个领域树立了新的标杆。

整体来看，论文的核心贡献可以总结为三点：

- 第一，**首次给出了系统级的确定性 LLM 推理形式化定义**，明确了确定性推理的边界与衡量标准，结束了之前“各自定义、各自优化”的零散状态。
- 第二，**设计实现了双层验证的 Vosti 推理引擎**，引擎层通过不变量保证调度与缓存的确定性，内核层通过关系型合约保证计算的位级一致性，两者结合实现了端到端的确定性保证。
- 第三，实测结果显示，Vosti 在保证全场景确定性的同时，在解码密集型工作负载下性能优于 vLLM 批不变量模式，证明了形式化验证的确定性方案完全可以具备实用的性能。

> 当然，Vosti 目前还有很多可以扩展的方向：

| 方向 | 说明 |
| --- | --- |
| 跨内核关系验证 | 当前 Vosti 固定内核选择；未来支持验证多个不同内核间的位级等价性，实现按负载动态调度内核，同时保持确定性。 |
| 支持更多模型架构 | 当前未覆盖线性注意力架构、混合专家模型等；这些架构引入新不确定性来源，需扩展不变量与合约以全面覆盖。 |
| 多 GPU 推理的确定性 | 当前仅支持单 GPU；扩展至多 GPU 需解决张量并行、流水线并行、分布式 KV 存储带来的新问题；需为分布式操作设计对应的关系型合约与状态不变量。 |

::: block-1
从更宏观的角度看，确定性推理对于很多场景都至关重要：强化学习中训练与推理的一致性、智能体工作流的可复现性、线上服务的故障排查、合规场景的可追溯性，都需要推理结果是确定可复现的。:mdnice-highlight[Vosti 的工作，用形式化验证的方法为这些需求提供了坚实的技术基础，也为构建更可靠的 AI 基础设施提供了新的思路。]
:::
