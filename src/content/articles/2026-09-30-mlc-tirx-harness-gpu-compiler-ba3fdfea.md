代码智能体已经能够自动化这一流程中的重要环节，:mdnice-bold-italic[但在我们针对 KDA 等负载的实验中，智能体的大量精力都消耗在了优化工作之外的环节：预判内核代码如何映射到硬件执行行为、排查依赖时序的偶发故障或受 GPU 并发活动干扰的失真测试结果，以及寻找适配特定任务的实现方案或优化策略]。最终导致 token 效率急剧下降：**智能体将计算预算耗费在解决优化过程中的不确定性上，而非探索优化方案本身，因此很多本可行的优化方案在实际搜索预算内根本无法被探索到。**

## 一、围绕可靠迭代构建 TIRx Harness

这些组件分别解决了同一优化循环中不同来源的不确定性问题。**TIRx Harness 提供面向编译器的环境，而智能体工作流利用这些能力来组织搜索过程**。我们针对智能体驱动内核优化过程中观察到的每一类典型故障模式，设计了对应的组件。

### 1.1 TIRx 基础层：让编译器行为可预测

> 编程基础决定了智能体能将其编写的代码与 GPU 实际执行的行为对应起来的直接程度。**高层抽象对提升开发效率很有价值，但在我们的实验中，它们会让优化的逻辑更难推导。** 智能体:mdnice-bold-italic[可能知道它想要尝试的执行策略，却不知道编写怎样的源代码才能让编译器生成对应的执行逻辑]。冗长的编译路径还会给调试带来另一重不确定性：当出现数值错误时，智能体必须同时考虑其编写的内核本身，以及编译器对其施加的各类转换。

**我们从两个方面解决这些不确定性问题**。首先，我们**让 TIRx 尽可能贴近硬件**。其精简的 PTX 级编程接口让智能体可以更直接地表达指令与执行策略，而非依赖高层抽象间接生成想要的执行行为。

![文章插图](/articles/2026-09-30-mlc-tirx-harness-gpu-compiler-ba3fdfea/images/04.jpg)

::: image-caption
TIRx Harness 的核心编译基础层特性，核心是一层轻薄的编程接口，打通了上层内核操作与底层生成代码的直接映射。TIRx 采用贴近硬件的 PTX 级编程抽象，刻意保持极简设计，除硬件接口本身外极少引入额外独立语义，维持了中间表示与编译路径的精简稳定。不同于高层抽象会经过多层复杂编译转换，这层薄接口让智能体编写的每一行内核操作代码，都能直接对应到最终生成的硬件指令逻辑，既降低了优化推理的难度，也减少了调试时编译转换带来的不确定性。
:::

其次，**TIRx 在设计上刻意保持精简**。除了硬件接口本身，它尽可能少地引入独立语义，保持中间表示与编译路径的精简和稳定。:mdnice-bold-italic[依托如此薄的抽象层，PTX 指令集架构（ISA）就成为了指令语义的核心事实来源。这也让系统更易于扩展：新增一项 PTX 能力通常只需要在编程接口上做轻量补充，无需新增高层抽象或扩展庞大的编译栈]。我们仍保留了循环、条件分支等基础结构，以便支撑框架的其余部分对程序进行分析。

精简的编程接口实现了内核操作到生成代码的直接映射。选择源代码行即可查看其映射关系。

### 1.2 工具集：提供超越基准测试的详细反馈

> **即便编程基础更简化，故障依然可能难以排查**。一个内核可能多次运行都正常通过，却因偶发的同步 bug 或数据竞争而失败，最终智能体只能得到一个通过/失败的信号，缺乏更多信息。:mdnice-bold-italic[这也催生了支撑框架的广义设计原则：工具应当提供关于程序行为的有效反馈，而不仅仅是测试结果。]

![文章插图](/articles/2026-09-30-mlc-tirx-harness-gpu-compiler-ba3fdfea/images/05.jpg)

::: image-caption
TIRx Harness的编译分析模块，它突破了基准测试仅输出通过/失败结果的局限，可为智能体提供程序行为的多维度深度诊断反馈。模块涵盖三类核心分析能力：数值仿真可在无GPU硬件的场景下模拟程序数值行为，提供离线验证维度；同步分析专门排查并发执行中的时序缺陷，例如复用内存屏障导致的世代推进异常；数据竞争分析则检测线程间内存访问的冲突风险。这些工具能帮助智能体精准定位故障根源，大幅提升调试与优化效率。
:::

- 我们打造了同步分析与数据竞争分析工具，可直接检查并发行为。**当无法使用 GPU 执行时，数值仿真工具可以在无 GPU 的情况下模拟数值行为**，提供另一维度的反馈。
- 在性能诊断方面，我们**集成了 NCU、IKET 等现有性能剖析工具**。这些工具共同为智能体提供了更多信息，帮助其判断下一步该研究和修改什么。
- 编译分析模块可返回数值、同步与数据竞争相关的诊断结果。选择组件即可查看其反馈详情。

### 1.3 知识库：复用已知思路，探索全新方向

> 可预测的编程基础与更完善的诊断工具，仍然无法为智能体提供开发新内核所需的实现与优化知识。在早期运行中，智能体需要花费大量精力学习编程模型，重新发现那些已经被验证有效的优化模式。

:mdnice-bold-italic[为了避免每次运行都重新学习这些思路，一个自然的方法是总结过往运行的经验。然而在我们的实验中，由智能体生成的总结往往会对刚调试完成的案例产生过拟合，丢失有用的实现上下文。因此我们选择保留具体的实现方案]，而非抽象总结。

**内核库（kernel zoo）** 是知识库的核心。它包含 60 余个 TIRx 内核，为智能体提供了具体的开发起点与可复用的优化模式。:mdnice-bold-italic[但内核库仅收录了已在现有内核中出现过的思路，PTX 文档则作为补充，展示了可开辟新优化方向的硬件能力。内核库帮助复用已知思路，指令集架构帮助探索全新方向。]

![文章插图](/articles/2026-09-30-mlc-tirx-harness-gpu-compiler-ba3fdfea/images/06.jpg)

::: image-caption
TIRx Harness 知识库体系中的内核库（Kernel Zoo）模块。作为知识库的核心组成，内核库收录了 60 余个经过验证的 TIRx 内核实现，为代码智能体提供具象化的开发起点与可复用的优化模式范本，让智能体无需从零搭建内核逻辑，可直接参考、适配库中成熟的实现方案与优化策略，避免每次优化任务都重复发现已知的设计模式。内核库与 PTX 指令集文档互为补充：内核库负责沉淀已验证的成熟思路，支撑已知优化方案的快速复用；PTX 文档则暴露底层硬件能力，助力智能体开拓全新优化方向。
:::

内核库提供可复用的实现方案；硬件与指令集架构文档揭示新的可能性。选择知识源即可进行探索。

### 1.4 基准测试服务器：让性能测量具备可比性

> 正确性测试、耗时统计与性能剖析决定了一个候选方案是否被采纳，以及智能体下一步尝试哪种优化，因此一次有偏差的测量会影响多次尝试，而非单次。**当智能体在自身环境中直接发起 GPU 任务时，有两个目标让这类测量的可靠性难以保障。**

- :mdnice-bold-italic[第一个是规模问题：我们希望多个智能体并发运行，但它们共享 GPU 时，耗时的变化可能反映的是其他智能体的活动]，而非候选方案本身的性能提升或下降，智能体也就无法将性能变化归因于自己的代码修改。
- **第二个是平台覆盖问题**：我们希望优化的目标硬件不止数据中心 GPU，还包括 :mdnice-bold-italic[Thor 这类边缘设备，但这些平台并不适合作为代码智能体的运行宿主，因此将智能体绑定到待优化的机器上会限制其可覆盖的硬件范围。]

> 这两个问题都指向同一个设计方案：将评估环节与智能体分离。

:mdnice-bold-italic[因此 TIRx Harness 采用了以我们的基准测试服务器 KCoral（相关博客即将发布🌟）为核心的远程评估架构。KCoral 掌管所有 GPU，每当智能体需要使用 GPU 时——无论是测试正确性、对内核做基准测试，还是收集性能剖析数据——它都会向 KCoral 发送请求，而非在本地发起任务。]

![文章插图](/articles/2026-09-30-mlc-tirx-harness-gpu-compiler-ba3fdfea/images/07.jpg)

::: image-caption
KCoral 基准测试服务器的核心架构逻辑，核心是将智能体开发环境与 GPU 执行环境完全解耦分离，并对所有性能测量任务进行集中调度。代码智能体在本地开发环境中完成内核代码的编写与优化，当需要验证正确性、运行基准测试或采集性能剖析数据时，无需直接调用 GPU，而是向 KCoral 发送远程请求。KCoral 统一掌管所有 GPU 资源，对所有请求进行中心化队列调度，确保同一 GPU 同一时间仅运行一个任务，避免并发干扰导致测量失真，同时支持接入数据中心 GPU 与边缘设备，智能体无需部署在目标硬件上即可完成优化。任务完成后 KCoral 会返回测量数据与诊断产物。
:::

KCoral 对所有请求进行统一调度，确保不同任务的执行互不干扰，并在请求完成后返回测量结果与诊断数据。智能体的每一次测量都能获得可控、可信的环境，而支撑框架只需将新硬件接入 KCoral 即可扩展优化目标，无需让每个智能体都在对应硬件上运行。

KCoral 将智能体开发与 GPU 执行分离，并对测量任务进行集中调度。选择组件即可探索其作用。

## 二、TIRx Harness 的能力价值

上述组件的重要意义在于，它们改变了智能体在优化过程中能做到的事情。除了生成更多候选方案，支撑框架还能帮助智能体发现未曾考虑过的硬件能力、跨内核迁移优化策略，以及排查存在隐患的候选方案——而不仅仅是给出通过/失败的反馈。**下文的运行轨迹展示了这些作用的实际案例；下一部分将评估最终生成的内核性能。**

### 2.1 探索全新优化方向

> **硬件文档可以拓展智能体的搜索空间**，而不仅仅是解答语法问题。:mdnice-bold-italic[在一次 MSA 稀疏预填充的运行轨迹中，智能体在 PTX 指令集中发现了 tcgen05.mma 的输出通道掩码特性，并将其转化为一项有效的优化手段]。**该掩码并不会减少矩阵乘加（MMA）的运算量，反而提升了 GPU 的实际运行频率，带来了 2%–3%的性能提升。**

TIRx 贴近硬件的编程接口还让智能体可以直接针对硬件资源做权衡。

::: block-1在 KDA 反向传播中，智能体将转置、对角缩放和逐行点积运算都迁移到了张量核心（Tensor Core）路径上。:mdnice-bold-italic[对于点积运算，它计算了完整的 64×64 矩阵后只保留对角元素，刻意通过增加张量核心的运算量，来消除繁忙线程束（warp）中的共享内存中间结果与规约操作。这种反直觉的权衡——利用利用率较低的硬件路径执行更多算术运算，来缓解瓶颈路径的压力——将延迟降低了约 15%。]
:::

### 2.2 迁移优化策略

内核库为智能体提供了可以适配复用的具体策略。在 MSA 场景中，智能体适配了 FlashAttention-4 的原生与软件指数混合计算策略，通过普通熔合乘加（FMA）运算缓解原生指数计算路径的压力，将延迟降低了约 2.9%。

**在 KDA 前向传播中，智能体迁移了门控 DeltaNet（GDN）的分层逆分解方法，用小块矩阵求逆与基于 MMA 的合并操作替代了串行的 32×32 递推运算，将延迟降低了约 17%。** 这些案例印证了我们保留具体实现方案的原因：它们承载的分解逻辑与数据流设计可以跨不同内核迁移复用。

### 2.3 排查存在隐患的候选方案

> 分析工具可以捕捉到普通测试可能遗漏的正确性问题。:mdnice-bold-italic[在一条 KDA 运行轨迹中，一个候选方案通过了基准测试的正确性校验，但同步分析仍然识别出了一个潜在 bug：一个被复用的内存屏障（mbarrier）可能在滞后的消费端完成上一轮等待之前，就进入了下一世代。智能体可以在这个依赖时序的问题实际暴露在执行中之前，就修复同步协议。]

以上案例共同展示了支撑框架从三个层面改变优化循环：

- 指令集架构拓展了搜索空间
- 内核库提供了可迁移的策略
- 分析工具将有隐患的候选方案转化为具体的诊断结果

基准测试服务器则提供可控的性能反馈，用于决定保留哪些方案。

## 四、闭环优化

> **内核演化不仅能优化内核本身，也能反哺支撑框架**。当一次运行暴露出工具缺陷、不支持的行为或缺失的检查项时，其运行轨迹就提供了具体的复现用例，可用于改进分析工具。:mdnice-bold-italic[成功优化的内核则会走上另一条路径：它们会被纳入内核库，作为更优的开发起点与可复用的优化策略，供未来的运行使用。]

这就是我们对 TIRx Harness 自我迭代的理解：**一次演化运行产生的有价值成果，会成为下一次运行可依托的环境的一部分**。我们不会要求智能体总结其学到的经验，而是保留具体的产出物——经过验证的工具改进，或是经过实测的内核实现——供后续运行直接复用。

## 五、未来规划

> 我们认为 TIRx Harness 的下一阶段有三个发展方向。

- 第一，我们希望评估该支撑框架适配新 GPU 架构的速度，包括智能体能够多快地利用新指令与硬件特性。
- 第二，我们希望推动 TIRx 进一步贴近硬件，暴露更多底层机制，让智能体可以更直接地挖掘性能潜力。
- 第三，我们希望将正确性工具扩展到巨型内核（megakernels）场景，随着更多计算融合到单个程序中，验证同步、内存访问与数值行为的难度也会大幅提升。
