关键词：多模态模型服务、Walk Graph、M*、数据流图、推理性能优化

> “AI 正在进入复合模型架构的新时代，但现有模型服务框架建立在对模型结构的狭隘假设之上，完全无法适配这种全新的架构多样性。”这篇来自斯坦福大学、华盛顿大学与卡内基梅隆大学的联合研究，开篇就点破了当前多模态部署领域的核心矛盾。

当我们谈论多模态模型服务时，大多数人的认知还停留在“给 LLM 加个视觉编码器”的阶段。但现实是，今天的多模态模型早已不是简单的“骨干+外挂”结构：统一多模态模型用同一个 Transformer 骨干同时做理解和生成，全模态模型用双 Transformer 级联实现实时语音交互，世界模型用循环推演预测未来状态，机器人策略模型用多分支并行完成动作规划。

::: block-1
这些形态各异的复合模型，有着完全不同的执行模式：有的是自回归循环，有的是固定步长的扩散循环，有的是分支并行执行，有的是流式逐块输出。:mdnice-bold-italic[传统的 LLM 服务框架，从 vLLM 到 SGLang，本质上都是为单一路径的自回归文本生成设计的，即便扩展出 Omni 版本，也只是把模型拆成两三个阶段的 DAG 流水线，根本无法承载这么复杂的执行逻辑。]
:::

## 一、多模态模型的架构革命，正在倒逼服务系统重构

> 过去三年，多模态模型的创新重心已经从“能不能支持多种模态”，转向“能不能用更灵活的组件组合实现更复杂的能力”。模型架构的复杂度指数级上升，但服务系统的底层抽象几乎还停留在三年前。

这种技术代差，直接导致了今天多模态部署的两大痛点：

- 一是新模型上线慢，每出一种新架构就要写大量胶水代码适配服务框架，甚至要自研专用推理引擎；
- 二是资源利用率低，不同任务、不同模态的模型组件不能灵活调度复用，硬件资源被大量浪费。

### 1.1 从“外挂编码器”到“原生组合”：多模态模型的结构变迁

> 早期的多模态模型，比如第一代视觉语言模型，结构非常简单：一个独立的视觉编码器把图片转成 token 序列，拼接到文本 prompt 后面，然后送入标准的 LLM 做自回归生成。**整个执行路径是一条笔直的流水线：编码 → 预填充 → 解码，和纯文本 LLM 的区别只在于多了一步前置编码。**

对于这种结构，传统 LLM 服务框架只需要加一个前置处理模块就能支持，完全不需要改动核心抽象。但今天的新一代多模态模型，已经跳出了这种“外挂式”结构，进化出了高度多样化的复合架构。论文中将其归纳为五大类，每一类都对服务系统提出了全新的要求。

**第一类是统一多模态模型，典型代表是 BAGEL**。这类模型用同一个 Transformer 骨干同时支持视觉理解、图像生成、图像编辑三类任务，**不同任务会调用不同的编码器、解码器和不同的权重分支**。:mdnice-bold-italic[也就是说，同一个模型，输入不同的任务，执行路径完全不一样，用到的组件子集也不一样。这就要求服务系统不能默认所有请求都走完整流水线，必须能按需执行部分组件。]

**第二类是语音语言模型，比如 Orpheus-TTS**。这类模型在 LLM 后面接一个神经音频编解码器，把 LLM 输出的音频 token 转成波形。对于实时语音场景，输出必须流式生成，边生成边返回给客户端，不能等全部生成完再输出。:mdnice-bold-italic[这就要求服务系统原生支持流式张量传输，而不是等整个阶段执行完再传递数据。]

**第三类是全模态模型，典型代表是 Qwen3-Omni**。这类模型采用 Thinker-Talker 双 Transformer 架构：Thinker 负责理解输入、生成文本和高层隐状态，Talker 负责把隐状态转成音频编码 token，最后再由音频解码器生成波形。:mdnice-bold-italic[两个 Transformer 之间是流式级联关系，Thinker 输出一个 token，Talker 就处理一个，不是等 Thinker 全部跑完再开始。]

**第四类是视觉语言动作模型，主要用于机器人场景**。这类模型融合视觉编码器、文本编码器、Transformer 骨干和动作解码器，输入图像和指令，输出机器人的动作序列。

**第五类是世界模型，比如 V-JEPA 2**。这类模型有一个迭代式的隐状态预测器，可以一步步推演未来的视频帧，推演的步长是可变的，根据任务需求从几步到几十步不等。每一步推演都依赖上一步的结果，本质上是一个很长的循环结构。

::: block-1
这五类模型虽然形态各异，但有一个共同特点：推理过程不再等价于单一的自回归前向循环。**它们有不同的执行路径、不同的循环结构、不同的并行模式、不同的输出方式**。而这，正是传统服务框架最难适配的地方。
:::

### 1.2 现有服务框架的三重困境：抽象失配的本质

> 论文将复合多模态模型给服务系统带来的挑战总结为三点，恰好对应了现有框架的三重天花板。

- **第一重困境是架构多样性的适配难题**。现有框架的核心假设是“所有请求走同一条执行路径”，但复合模型的执行路径是随任务变化的。比如统一多模态模型，文生图任务要走文本编码器+LLM+流头+VAE 解码器，图像理解任务要走文本编码器+ViT 编码器+LLM+LM 头，路径完全不同。:mdnice-bold-italic[现有框架要么只能支持其中一种，要么需要为每种路径写单独的胶水代码，维护成本极高。]
- **第二重困境是模块化与性能的两难**。如果追求灵活性，比如用 HuggingFace Transformers 直接搭模型，那性能会很差，没有连续批处理、分页注意力这些服务级优化；如果追求性能，比如用 vLLM 或者专用语音框架，那灵活性又很差，只能支持特定的模型结构。:mdnice-bold-italic[鱼和熊掌不可兼得，是当前多模态服务的普遍现状。]
- **第三重困境是物理部署的灵活性不足**。复合模型的各个组件计算量、显存占用差异很大，比如 VAE 编码器计算量小、LLM 骨干计算量大，最优的部署方式是把编码器放小卡、LLM 放大卡，甚至给不同组件配置不同的副本数。:mdnice-bold-italic[但现有框架的部署粒度是“阶段”，一个阶段里包含多个组件，不能拆开单独部署，更不能根据任务动态调整组件的放置位置。]

::: block-1
这三重困境，根源都是同一个问题：**底层抽象和模型架构不匹配**。就像用造三轮车的图纸去造汽车，再怎么修修补补，也跑不出汽车的速度。
:::

### 1.3 为什么阶段式 DAG 走不通：vLLM-Omni 的天花板

> 为了适配多模态模型，vLLM 和 SGLang 都推出了各自的 Omni 版本，**核心思路是把模型拆成多个“阶段”，阶段之间用 DAG 连接，每个阶段是一个独立的推理引擎**。比如 Thinker 是一个阶段，Talker 是一个阶段，解码器是一个阶段，数据在阶段之间传递。

这种阶段式 DAG 的抽象，比纯文本的单流水线确实进了一步，能支持两到三级的流水线结构，比如 Thinker-Talker 这种两级模型。**但面对更复杂的复合模型，它就力不从心了，本质上有三个无法突破的局限。**

| 局限 | 说明 |
| --- | --- |
| **循环隐藏在阶段内部** | 扩散模型的去噪循环、世界模型的推演循环等，只能由阶段内 Python 代码实现，系统无法感知循环结构，因而无法应用连续批处理、CUDA 图捕获等底层优化，导致性能受限。 |
| **阶段内并行不可见于系统** | 如 CFG（无分类器引导）需并行执行三个推理分支再合并结果，但该并行逻辑被封装在单个阶段中，系统无法识别与调度——无法自动分配至不同 GPU，也无法跨分支复用显存或计算资源。 |
| **部署粒度粗、调度僵化** | 阶段是唯一部署单元，无法拆分其内部组件（如将编码器、解码器单独部署）；无法为不同组件配置差异化并行策略（如编码器多副本、预填充与解码分离），严重制约资源利用率与弹性调度能力。 |

打个比方，阶段式 DAG 就像把整条生产线分成了三个大车间，每个车间内部怎么干活系统不管，只管把半成品从一个车间运到下一个车间。而 M*的思路是，把每个工位都拆出来，系统直接调度每个工位的执行、每个零件的流转，自然能做到更精细的优化。

::: block-1
复合多模态模型的架构多样性，本质上是组件组合模式的多样性；阶段式 DAG 抽象的天花板，就在于它把组合逻辑封闭在阶段内部，系统无法感知和优化跨组件的执行模式。想要突破这个天花板，必须把抽象粒度下沉到单个模型组件。
:::

## 二、Walk Graph：M*的核心抽象，一套规则覆盖所有复合模型

> M*的核心创新，是找到了一套足够通用、又足够高效的中间抽象，把所有复合多模态模型的执行模式统一了起来。

这套抽象就是 Walk Graph。它的核心洞察非常朴素：**无论多模态模型的架构多么复杂，都可以拆成两个东西：一张由模型组件构成的有向计算图，以及一组在这张图上的遍历路径**。每个用户请求，就是按顺序执行若干条遍历路径的过程。

### 2.1 核心洞察：模型是图，请求是遍历

::: block-1
Walk Graph 的定义非常简洁：一个模型可以表示为一个二元组 $(G, W)$，其中 $G=(N, E)$ 是一张有向计算图，节点 $N$ 代表一个个模型组件（比如编码器、Transformer 骨干、解码器），边 $E$ 代表张量在组件之间的流动；$W$ 是一组命名的 Walk，每个 Walk 都是图 $G$ 的一个带标签的子图，对应模型执行的一个阶段。
:::

打个通俗的比方，计算图就像城市的地铁线路网，每个组件是一个地铁站，边是连接站点的轨道。而 Walk 就是一条条具体的地铁线路，比如 1 号线、2 号线，每条线路只经过全网的一部分站点。**一个用户请求就像一次出行，需要依次乘坐几条线路，从起点坐到终点。**

比如在 BAGEL 模型里，“图像理解”这个请求，对应的出行路线是：先坐“文本预填充”线，再坐“ViT 预填充”线，最后坐“解码”线。而“图像生成”请求，对应的路线是：先坐“文本预填充”线，再坐“图像生成循环”线。不同的任务，走不同的线路，但共享同一个地铁网络。

模型作者需要做的事情只有三件：

- 第一，定义计算图里有哪些节点、哪些边；
- 第二，定义有多少条 Walk，每条 Walk 经过哪些节点；
- 第三，写一个简单的状态机，根据请求的模态和当前 Walk 的输出，决定下一个该走哪条 Walk。剩下的所有执行细节，包括调度、批处理、张量传输、显存管理，全部交给运行时处理。

::: block-1
**这个设计最大的价值，就是把“模型长什么样”和“系统怎么跑”彻底分开了**。以前出新模型要改系统代码，现在只要改配置文件，定义新的图和 Walk 就行，运行时不用动。这就是所谓的“day-zero support”，新模型出来当天就能部署，不用等框架适配。
:::

### 2.2 四大组合原语：搭积木一样构建执行逻辑

> 光有图和 Walk 的概念还不够，还需要一套标准的组合规则，让大家能用统一的方式描述各种复杂的执行模式。Walk Graph 提供了四个可嵌套的组合原语，所有复杂的执行逻辑都可以用这四个原语搭出来。

| 原语类型 | 说明 |
| --- | --- |
| **顺序执行（Sequential）** | 最基础的组合方式，子图按序串联，前一个子图的输出作为后一个子图的输入。典型应用：编码→解码→输出，对应传统流水线结构。 |
| **并行执行（Parallel）** | 多个子图并列运行，共享同一输入，同步执行，输出汇总。典型场景：CFG 无分类器引导（三分支并行推理）、模型预测控制中多动作序列评估。系统可自动识别并行分支，调度至不同 GPU，免去手动分布式编码。 |
| **固定循环（Loop）** | 子图重复执行预设次数（如扩散模型 50 步去噪）。提供两个输出通道：• **单次迭代输出**：回流至循环输入，支撑下一次迭代；• **累积输出**：聚合全部迭代结果，一次性输出至下游。双通道分离，逻辑清晰。 |
| **动态循环（DynamicLoop）** | 类似 Loop，但支持按需提前终止（非固定次数）。典型应用：自回归解码（遇 EOS 停止）、世界模型推演（各请求步长不同）。每次迭代边界检查终止信号，满足条件即退出。 |

这四个原语是可以嵌套使用的，比如循环里面可以套并行，并行里面可以套顺序，组合方式非常灵活。论文里 BAGEL 的 CFG 版本图像生成 Walk，就是“顺序套循环，循环套并行”的结构：最外层是顺序结构，里面先是一个 49 次的循环，循环里面先是三个分支的并行，然后是合并节点，最后循环结束后接 VAE 解码。

可以对比一下，:mdnice-bold-italic[如果用阶段式 DAG 来描述这个逻辑，你只能把整个循环加 VAE 都塞到一个阶段里，系统根本不知道里面有循环、有并行，自然也没法做对应的优化]。**而 Walk Graph 把这些结构都显式地暴露给了系统，系统就能针对性地做调度和加速。**

### 2.3 流式边与分块策略：搞定实时语音这类流式场景

> **对于实时语音、视频生成这类场景，数据不是一次性生产、一次性消费的，而是生产者一点点输出，消费者一点点处理**。比如 Thinker 生成一个 token，Talker 就要立刻处理这个 token，不能等所有 token 都生成完再开始。

**为了支持这种模式，Walk Graph 设计了流式边（StreamingGraphEdge），专门用来描述流式的张量传递**。和普通边不同，流式边的生产者每次只输出一个张量片，消费者不会收到一个就立刻执行，而是先攒在缓冲区里，攒到满足一定条件再触发执行。

什么时候触发执行，由分块策略（ChunkPolicy）决定。论文里实现了三种通用的分块策略，覆盖了他们测试的所有场景。

- 第一种是固定分块策略（FixedChunkPolicy），每攒够 K 个张量片就触发一次执行。比如 Qwen3-Omni 里 Thinker 到 Talker 的连接，就是 K=1 的固定分块，来一个就处理一个，实现低延迟流式交互。
- 第二种是滑动窗口分块策略（SlidingWindowChunkPolicy），缓冲区满了 W 个就触发一次，然后往前滑动 S 个。这种适合需要重叠上下文的场景，比如语音的分块处理。
- 第三种是左上下文分块策略（LeftContextChunkPolicy），每个 C 帧的分块前面，都带上 L 帧的左上下文。这种主要用于音频解码器，比如 Code2Wav，每个音频块前面带一点上文，能让生成的音频更连贯，没有拼接痕迹。Qwen3-Omni 里 Talker 到 Code2Wav 的连接，用的就是这种策略。

这个设计最巧妙的地方在于，分块策略是可插拔的，运行时完全不感知具体的策略逻辑。以后有新的流式场景，只要加新的策略类就行，不用改运行时的核心代码，扩展性非常好。

### 2.4 案例拆解：两类典型模型的 Walk Graph 表达

光讲概念太抽象，我们用两个典型模型，看看 Walk Graph 实际用起来是什么样的。

> 第一个是 BAGEL 统一多模态模型。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/02.webp)

::: image-caption
图1：模型架构示例，(a)统一多模态模型（BAGEL），(b)全模态模型（Qwen3-Omni）。复合模型结构多样，但均可表示为计算图。
:::

它的计算图一共有 7 个节点：ViT 编码器、VAE 编码器、LLM 主干、两个 CFG 分支 LLM、CFG 合并节点、VAE 解码器。整个模型一共定义了 6 条 Walk，分别对应不同任务的不同阶段。

不同的任务对应不同的 Walk 序列：

- 图像理解是文本预填充 →ViT 预填充 → 解码；
- 图像生成是文本预填充 → 图像生成循环。

**所有 Walk 都共享同一个 LLM 主干节点**，部署的时候只要把 LLM 节点放在同一个 GPU 上，所有任务的请求就会自动复用这一份 LLM 副本，不用每个任务单独部署一套。

> 第二个是 Qwen3-Omni 全模态模型。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/03.webp)

::: image-caption
图1：模型架构示例，(a)统一多模态模型（BAGEL），(b)全模态模型（Qwen3-Omni）。复合模型结构多样，但均可表示为计算图。
:::

它是三分区拓扑：Thinker、Talker、Code2Wav 三个部分，中间两条流式边连接。**整个模型定义了 8 条 Walk，不同的输入模态有不同的预填充 Walk，Talker 又分预填充、末次预填充、解码三种 Walk**。通过 Walk 的组合，可以灵活支持文本输入、语音输入、图像输入等各种模态组合，以及流式和非流式两种输出模式。

更有意思的是 V-JEPA 2 世界模型，同一个预测器组件，被 5 条不同的 Walk 复用：有单次预填充的，有批量循环推演的，有流式推演的，还有多分支并行的 MPC 规划。同一份权重，支持五种完全不同的执行模式，这在阶段式 DAG 框架里是根本做不到的。

::: block-1
**Walk Graph 用四个组合原语加流式边，就能覆盖所有已知的复合多模态模型执行模式**，真正实现了“一套抽象，全场景适用”。它的表达能力严格包含阶段式 DAG，而阶段式 DAG 永远也表达不了循环、并行和流式这些跨组件的结构。
:::

## 三、从抽象到落地：M*运行时的设计与实现

> 有了好的抽象只是第一步，能不能把抽象的开销降到足够低，同时把各种成熟的推理优化都集成进去，才决定了一个系统能不能真正落地。

很多灵活的框架都死在了“抽象税”上——为了通用性，牺牲了太多性能。而 M*的厉害之处在于，它不仅通用，性能还能超过专用框架。这背后，是它运行时的一系列精心设计。

### 3.1 整体架构：Conductor 调度+Worker 执行的分布式结构

> M*的运行时采用了经典的中心化调度+分布式执行的架构，主要由三个部分组成：API 服务器、Conductor 调度器、GPU Worker。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/04.webp)

::: image-caption
图2：M*概览。左侧：模型开发者将模型定义为计算图（图1）与一系列图遍历路径。右侧：运行时\根据用户指定的部署方案，将各组件子图分配至不同GPU工作节点
:::

**API 服务器负责接收用户的 HTTP 请求，把请求转发给 Conductor。Conductor 是整个系统的大脑，每个服务实例有一个，它维护着每个请求的执行状态**：当前走到了第几个 Walk，当前在哪个节点上。然后它根据全局的负载情况，把任务分发给对应的 GPU Worker。

**GPU Worker 是单进程的，每个 GPU 对应一个 Worker 进程。Worker 负责执行本地的子图，也就是部署在这个 GPU 上的所有组件节点**。和很多框架不同，M*的张量传输不绕 Conductor，两个 Worker 之间可以直接传张量，避免了中心节点的带宽瓶颈。跨 Worker 的图边，就对应一次跨进程的张量传输。

::: block-1
张量传输层是可插拔的，目前支持三种传输方式：同机的共享内存、跨机的 RDMA、通用的 TCP，后面两种通过 Mooncake 传输引擎实现。对于流式边，消费者 Worker 会给每个请求维护一个输入缓冲区，收到的张量片先存在缓冲区里，满足分块策略的条件再触发执行。
:::

### 3.2 组件级引擎：两类引擎覆盖所有组件

> 每个图节点（也就是每个模型组件）都会对应一个执行引擎，M*目前实现了两类引擎，分别对应有状态和无状态的组件。

- 第一类是 KVCacheEngine，也就是带 KV 缓存的 Transformer 引擎。这是整个系统的核心引擎，基于 FlashInfer 实现了分页注意力 KV 缓存，支持连续批处理、CUDA 图捕获、采样插件。所有带自回归循环的 Transformer 组件，比如 LLM 主干、Thinker、Talker，都用这个引擎。
- 第二类是 StatelessEngine，也就是无状态引擎。那些每次执行都不需要保留状态的组件，比如 VAE 编码器、VAE 解码器、音频编解码器，都用这个引擎。它的执行路径更轻量，没有 KV 缓存管理的开销。

这两类引擎虽然功能不同，但都支持连续批处理、CUDA 图重放和 torch.compile。也就是说，无论是有状态的还是无状态的组件，都能享受到现代推理引擎的核心优化。一个 Worker 上可以同时跑多个引擎，比如一个 Worker 上同时放 LLM 和 VAE 解码器，两个引擎共享同一个 GPU，由 Worker 的本地调度器按轮询策略驱动。

### 3.3 调度优化：把通用抽象的性能损耗补回来

> 抽象粒度变细了，调度的开销自然会变大。为了把开销打平，甚至实现超越专用框架的性能，M*的运行时做了三层关键的调度优化。

| 层级 | 描述 |
| --- | --- |
| **第一层：CPU 调度与 GPU 执行重叠** | 当第 N 批任务在 GPU 上执行时，CPU 已在后台调度第 N+1 批任务，避免 GPU 等待。Worker 交替处理两类任务：一是沿 Walk 继续推进的当前批次后续图节点；二是其他就绪的、无关批次任务，从而缓解队头阻塞，防止大任务阻塞小任务。 |
| **第二层：注意力计划双缓冲** | 使用 FlashInfer 进行分页注意力时，每批需重建注意力计划，开销较大。M*采用双缓冲设计：在独立线程与独立 CUDA 流中异步构建下一批次的注意力计划；当前批次执行完毕时，下一批计划已就绪，实现零等待切换。 |
| **第三层：循环级 CUDA 图捕获** | 利用循环体输入输出形状固定的特点，将整个循环体捕获为一张 CUDA 图，每次迭代直接重放，显著减少 Python 解释与 CUDA API 调用开销。相比之下，阶段式 DAG（如 vLLM-Omni 中扩散模型的去噪步骤、语音 Codec 预测）无法复用 CUDA 图，只能以 eager 模式运行，性能明显受限。 |

对于动态循环，M*还做了投机调度：终止检查推迟到下一次迭代的开头，而不是当前迭代的结尾。这样不用等检查结果出来再决定下一步，最多浪费一次迭代的计算，但换来的是每次迭代都不用停顿，吞吐更高。如果有的场景不能接受浪费一次迭代，也可以按节点关闭这个功能，非常灵活。

### 3.4 灵活部署：组件级放置与资源复用

> Walk Graph 带来的另一大好处，就是部署的灵活性。部署者可以通过 YAML 配置文件，指定每个图节点放到哪个 GPU 上，完全不用改模型代码。

最基础的是组件级放置。

- 你可以把计算量小的编码器、解码器放到显存小的 GPU 上，把计算量大的 LLM 主干放到显存大的 GPU 上；
- 也可以给访问量高的组件多配几个副本做数据并行，访问量低的就少配。所有组件的扩缩容都是独立的，不用整个模型一起扩。

更进一步，还可以按 Walk 指定放置。同一个逻辑节点，在不同的 Walk 里可以放到不同的 GPU 上。最典型的应用就是预填充-解码分离：预填充阶段的 LLM 放一张卡，解码阶段的 LLM 放另一张卡，避免两个阶段互相干扰。这个在阶段式 DAG 里也能做，但粒度只能到整个阶段，而 M*可以精确到单个组件在单个阶段的放置。

**最有价值的是跨 Walk 的资源复用。如果同一个节点在多条 Walk 里都配置了同一个 GPU rank，系统就会自动复用同一个物理引擎实例**。比如 BAGEL 的 LLM 节点，在图像理解、图像生成、图像编辑的 Walk 里都有，只要都指向同一个 GPU，所有任务的请求就会共享这一个 LLM 副本，自动做批处理。这意味着不同任务、不同模态的请求，可以共享同一个骨干模型的算力，硬件利用率会高很多。

除此之外，张量并行也是节点级的。模型作者只要把节点里的 Linear、MLP、Attention 层换成系统提供的分片实现，然后在配置里写一下张量并行的度数，剩下的所有事情——比如调度、同步、不同并行度节点之间的张量传输、KV 缓存传输——都由系统自动处理，不用用户操心。

::: block-1
M*的运行时将分页注意力、连续批处理、CUDA 图等成熟优化下沉到组件级，再通过图级调度串联起来，既保留了组件级的极致性能，又实现了跨组件的全局优化。所谓的“抽象税”，被这些精细化的优化完全抵消，甚至实现了反超。
:::

## 四、实测对比：四大典型场景的性能表现

> 评价一个服务系统，最终还是要看实测性能。M*选了四类完全不同的模型做测试，覆盖统一多模态、全模态语音、专用语音、世界模型四大场景，对比的都是当前业界最优的基线系统。

从结果来看，M*不仅在所有场景都打赢了，而且在很多场景优势非常大，甚至超过了专用优化的框架。

### 4.1 BAGEL：一套配置打满三类任务

> 第一组实验用的是 BAGEL-7B 统一多模态模型，测试了文生图、图像编辑、图像理解三类任务，基线是 vLLM-Omni。实验用的是 H100 GPU。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/05.webp)

::: image-caption
图 3：BAGEL 图文生成端到端延迟测试，批大小 B=1，3 卡 CFG 并行；柱状实心为 p50 延迟，斜线填充为 p95 尾延迟。
:::

首先看文生图和图像编辑任务，采用 3 卡 CFG 并行配置，也就是三个 CFG 分支分别放三张卡。在批量为 1 的情况下，M*的文生图 p50 端到端时延比单阶段版本的 vLLM-Omni 低 20%，也就是 1.25 倍的速度提升；图像编辑任务的优势更大，比默认配置的 vLLM-Omni 快 2.64 倍。

这个性能优势主要来自 KV 缓存管理的差异。vLLM-Omni 的 CFG 实现，是给每个分支单独维护一份稠密的 KV 缓存，每一步去噪都要把三个分支的 KV 张量拼接起来，开销很大。而 M*是把三个 CFG 分支当成同一个分页 KV 池里的三个标签，每一步直接用分页注意力读取对应的页表，根本不需要拼接。不仅更快，还天然继承了分页、换入换出、按引用传输、连续批处理这些能力。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/06.webp)

::: image-caption
图 4 (a)：BAG 图像转文本任务首 token 延迟，单 H100，输出长度 64~256，横轴并发批大小，纵轴对数刻度 TTFT。图 4 (b)：BAGEL 图像转文本吞吐量指标，单 H100，输出 64~256token，数值越高性能越好。图 4 (c)：BAGEL 图像转文本端到端延迟，单 H100，输出 64~256token。
:::

然后看图像理解任务，单卡 H100，输出 token 长度在 64 到 256 之间。**随着批量增大，M*的吞吐优势越来越明显**，批量为 16 的时候，吞吐比 vLLM-Omni 高 32.7%，端到端时延低 25.5%。同时，M*的首包时延（TTFT）始终比 vLLM-Omni 低，批量为 1 的时候低 33%，批量为 16 的时候还低 14%，而且尾部性能更稳定。

但这组实验最有价值的结论，是“一套配置打所有”。vLLM-Omni 需要两种不同的配置：默认配置适合文生图和图像理解，但图像编辑性能很差；单阶段配置适合文生图和图像编辑，但图像理解性能砍半，还不支持连续批处理和 token 流式输出。

而 M*只用一套配置，三类任务都能跑出最优性能。这意味着部署的时候，你不用为不同的任务维护多套集群，所有请求都可以混部在同一个集群里，资源利用率会高很多。这对于实际生产的价值，比单纯的时延降低还要大。

### 4.2 Qwen3-Omni：语音合成全面领先

> 第二组实验用的是 Qwen3-Omni-30B 全模态模型，测试文本转语音任务，基线是 vLLM-Omni 和 SGLang-Omni。实验用了两张 H200 GPU，Thinker 放 0 号卡，Talker 和 Code2Wav 一起放 1 号卡。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/07.webp)

::: image-caption
图 5 (a)：Qwen3-Omni 语音合成实时因子 RTF，2 张 H200 拆分部署，数值越低实时性越好；实心 p50、斜线 p95。图 5 (b)：Qwen3-Omni 语音合成音频吞吐量，2 张 H200 拆分部署，数值越高单位时间生成音频越多。
:::

结果非常悬殊：在所有批量大小下，M*的实时因子（RTF，处理时间除以生成音频时长，越小越好）都显著低于两个基线。批量为 16 的时候，M*的吞吐量分别是 vLLM-Omni 的 2.7 倍、SGLang-Omni 的 4.0 倍。

论文分析了两个核心原因。

**第一个原因是 CUDA 图的覆盖范围不同**。M*可以把整个 Talker 子模块，包括里面的多 token 预测循环，整个捕获成一张 CUDA 图，执行效率非常高。而 vLLM-Omni 的 Code Predictor 部分明确禁用了 CUDA 图，只能用 eager 模式跑，自然慢很多。

**第二个原因是部署拓扑的差异**。M*把 Talker 和 Code2Wav 放在同一个 Worker 进程里，两个组件之间的张量传递就是同进程内的指针传递，没有任何开销。而 vLLM-Omni 和 SGLang-Omni 都是每个阶段一个独立进程，阶段之间传数据要走 IPC，开销很大。

后续他们又给 Thinker 加了 2 路张量并行，用 3 张 H200 跑，对比 SGLang-Omni，性能优势和两卡的时候基本一致，说明张量并行也没有引入额外的开销。

### 4.3 Orpheus-TTS：通用框架打赢专用框架

> 第三组实验用的是 Orpheus-3B 语音语言模型，单张 H200，基线是专门优化语音的 VoxServe 服务系统。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/08.webp)

::: image-caption
图 7 (a)：Orpheus 语音模型单 H200 实时因子 RTF，对比专用语音推理框架 VoxServe。图 7 (b)：Orpheus 语音模型单 H200 音频吞吐量，对比 VoxServe。
:::

按常理说，专用框架应该比通用框架快，毕竟可以做很多针对性优化。但结果是 M*全面胜出：批量为 16 的时候，M*的 p50 RTF 比 VoxServe 低 13.6%；吞吐量的优势更大，批量为 1 的时候高 52%，批量为 8 的时候还高 20%。

**一个通用框架，性能超过了垂直领域的专用框架**，这是非常有说服力的结果。这说明 Walk Graph 的抽象不仅没有“抽象税”，反而因为底层的组件级优化更彻底，整体性能反而更高。比如融合的注意力层、CUDA 图兼容的采样、投机式的 FlashInfer 计划构建，这些通用优化放到语音场景，一样能带来很大的收益。

### 4.4 V-JEPA 2：机器人规划最高提速 12.5 倍

> 第四组实验是最夸张的，用的是 V-JEPA 2 世界模型，测试动作条件下的推演任务，也就是机器人规划里常用的世界模型 rollout。基线是 Meta 官方的原生实现，单张 H100，批量为 1，测试不同推演步长下的速度。

![文章插图](/articles/2026-07-07-20-12-5-m-d749605a/images/09.webp)

::: image-caption
图 8：V-JEPA2 机器人世界模型推演延迟，单 H100，B=1，横轴推演步数，数值越低速度越快。
:::

结果是，推演步长越长，M*的优势越大。步长为 4 的时候，提速 2.08 倍；步长为 15 的时候，提速 3.76 倍；步长为 30 的时候，提速达到了惊人的 12.5 倍。

为什么差距这么大？因为 Meta 的原生实现非常朴素，就是一个手写的 Python 循环，每次推演都要把整个序列重新做一遍预填充，没有 KV 缓存，也没有任何批处理优化。序列越长，预填充的开销就越大。

而 M*把整个推演过程表达成一个动态循环，用 KVCacheEngine 执行，天然就有分页 KV 缓存，每一步只需要处理新的 token，不用重复计算历史。**步长越长，省掉的重复计算就越多，提速倍数就越大。**

这个场景其实最能体现 M*的价值。:mdnice-bold-italic[世界模型、机器人规划这类带长循环的场景，是传统服务框架最不擅长的，一般都只能用原生实现慢慢跑。而 M因为原生支持循环抽象，直接就能把 LLM 服务的那套成熟优化搬过来，瞬间带来数量级的性能提升。]

::: block-1
**M*在统一多模态、全模态语音、专用语音、世界模型四类典型场景下，性能均达到或超过当前最优的专用框架**，真正实现了“通用且高效”的设计目标。其中循环类场景的收益最大，因为这类场景恰恰是传统框架的能力盲区。
:::

## 结语

> 回顾 AI 服务系统的发展史，每一代模型架构的变革，都会催生新一代的服务系统。纯 Transformer 时代，催生了 vLLM、SGLang 这批以分页注意力、连续批处理为核心的 LLM 服务框架；而复合多模态时代，必然会催生出以组件化、图抽象为核心的新一代服务系统。

M*不是第一个做多模态服务的，但它是第一个**把“图遍历”这个抽象做透、并且证明了通用抽象可以比专用框架更快的工作**。它的出现，相当于给整个多模态服务领域打了一个样：原来不用牺牲通用性，也能做到极致的性能。

随着全模态模型、世界模型、机器人模型的快速普及，复合架构会成为多模态模型的主流。到那个时候，类似 Walk Graph 的组件化图抽象，大概率会成为所有推理服务框架的标准配置。而 M*，就是这条路上第一个里程碑式的工作。
