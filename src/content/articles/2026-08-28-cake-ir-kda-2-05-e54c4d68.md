## 一、GPU 内核自动化的困境：黑盒试错的天花板

> 过去两年，大语言模型驱动的代码智能体快速渗透到 GPU 内核开发领域，从简单的算子翻译到复杂的性能调优，**Agent 已经能够在部分场景下产出可用的内核实现。但随着优化进入深水区，现有方案的天花板也逐渐显现。**

绝大多数内核 Agent 系统都遵循:mdnice-bold-italic[同一个基础范式：Agent 生成代码、编译运行、拿到时延和正确性结果、再修改代码。这个闭环看似完整，实则反馈信号极度贫瘠]，如同蒙着眼睛走迷宫，只能靠一次次撞墙来摸索方向。

### 1.1 内核 Agent 的黑盒困境：反馈信号的贫瘠

> :mdnice-bold-italic[传统内核 Agent 将整个编译与运行时视为黑盒，每次迭代仅能获取三类信号：编译通过或失败、数值正确或错误、端到端时延数值]。

- 编译失败通常仅返回后端报错信息，不会指明是哪项调度决策导致同步错误、硬件契约违反或资源超限；
- 运行崩溃可能直接挂死，连完整错误栈都无法输出；
- 时延数值只是最终结果，无法区分瓶颈来自流水线未打满、存储带宽限制还是屏障同步开销。

这种**黑盒反馈直接导致 Agent 优化的盲目性**。Agent 无法判断上一次修改为何带来性能变化，只能依赖随机尝试与经验积累。对于局部调优，例如调整循环展开因子，这种模式尚可奏效；但如果从零设计内核整体调度，例如 warp 分工、流水线级数、多级存储搬运策略，黑盒反馈的效率会急剧下降。:mdnice-bold-italic[很多时候 Agent 消耗大量 token，却在错误方向上反复试错，最终无法触及专家内核的性能水平。]

::: block-1
论文提出一项关键洞察：*专家程序员的高效性，源于其脑中承载的硬件模型、对每个决策影响的预判，以及将遇到的问题沉淀为可复用规则的能力。*

**现有 Agent 系统没有将编译器已有的硬件知识与分析能力开放给 Agent**，反而将其封闭在黑盒之后。:mdnice-highlight[编译器本身具备结构化操作词汇、资源模型、合法性检查、静态分析、成本模型、降级规则等完整能力，将这些能力开放给 Agent，可极大提升进化效率。]
:::

### 1.2 DSL 的两难：抽象粒度与控制力的失衡

> 除反馈信号贫瘠外，**Agent 可用的编程语言本身存在抽象粒度的矛盾**。:mdnice-bold-italic[现有 GPU 编程 DSL 大致分为两派，均未适配 Agent 的工作模式。]

- **一派是高层 tile 级 DSL，代表为 Triton、Helion、TileLang 等。这类语言将硬件细节隐藏在 tile 抽象之后**，自动完成调度，编写门槛低。:mdnice-bold-italic[但代价是专家内核的核心决策——warp 专业化分工、屏障精确编排、多级存储放置策略——全部被封装屏蔽，Agent 无法触及这些优化点]，自然无法产出专家级性能的内核。
- **另一派是低层 DSL，代表为 CUTLASS 的 CuTe DSL。这类语言能暴露极细的硬件控制力，但要求使用者掌握布局代数**，即用一套数学体系描述张量内存布局。:mdnice-bold-italic[该体系对人类专家都存在较高学习门槛，对 Agent 而言更易出错，且错误难以定位]。布局代数的错误可能不会直接导致编译失败，但会引发数据错位、性能暴跌，在黑盒反馈下 Agent 几乎无法排查根因。

:mdnice-bold-italic[中间路线的尝试如 Gluon，在 Triton 编译栈上暴露更低层的布局、内存搬运与异步控制，但本质是在原有 DSL 基础上做补丁]，未从根上解决面向 Agent 设计的问题。

### 1.3 被忽视的中间层：编译器的分析能力

> **编译器本身已具备丰富的分析能力**，包括资源使用检查、同步合法性验证、数据依赖分析、性能估算等，**但这些能力仅服务于编译器内部流程，未向上层 Agent 暴露**。Agent 拿到的只有最终编译结果，没有中间分析过程。

这种局面造成了显著的效率浪费：:mdnice-bold-italic[编译器明明知晓程序的问题所在，却不向 Agent 反馈，仅返回报错或时延数字。Agent 不得不花费大量时间猜测、试错，重新发现编译器已知的事实。]

CAKE 的核心洞察之一，就是**将编译器的分析能力转化为 Agent 可消费的结构化反馈**，让 Agent 在编译前即可掌握程序合法性与性能瓶颈，无需等待实际运行。同时，当 Agent 遇到编译器无法覆盖的场景时，可**反哺编译器完成能力升级**，填补缺口。

::: block-1
总之，当前 GPU 内核自动化的核心瓶颈不在 Agent 模型本身，而在于:mdnice-highlight[编程表示与编译环境的设计没有面向 Agent 优化]。黑盒反馈导致优化盲目，DSL 的抽象粒度失衡导致控制力与易用性不可兼得，编译器的内置分析能力没有得到充分利用。CAKE 正是从这三个痛点切入，通过编译器与 Agent 的协同设计，打破现有范式的天花板。
:::

## 二、CAKE 的核心设计：编译器与 Agent 的双循环协同进化

> **CAKE 的全称是 Compiler–Agent Co-Design for Frontier Kernel Evolution**，直译即为**面向前沿内核进化的编译器-智能体协同设计**。:mdnice-bold-italic[该工作核心是一套将两者协同设计的完整体系]，而非一个更强的内核 Agent 或一门新的编程语言。

整个系统的核心架构是**双循环嵌套结构，内层为内核进化循环，外层为编译器-运行时进化循环**。两个循环相互促进，形成正向进化飞轮。

### 2.1 双循环架构：内核进化与编译器进化的嵌套

> 图 1 直观展示了 CAKE 与传统方案的架构差异。传统内核 Agent 系统仅存在内层单循环：**优化 Agent 生成内核候选，送入基准测试环境运行，拿到正确性与时延结果后返回修改**。编译器在该循环中仅作为固定翻译工具，不会进化，遇到能力缺口则永久停滞。

![文章插图](/articles/2026-08-28-cake-ir-kda-2-05-e54c4d68/images/06.jpg)

::: image-caption
图 1：Cake 整体架构。CAKE 在外层嵌套了编译器-运行时进化循环。内核进化过程中产生的全部证据——包括验证结果、失败案例、性能数据、调试日志——都会反馈至外层循环，用于优化编译器本身，例如新增验证规则、补充 IR 原语、校准成本模型、添加优化提示。编译器的改进反过来提升内层内核进化的效率与上限，形成双向进化的正反馈。
:::

::: block-1
**这种双循环设计的本质，是将专家程序员沉淀经验的过程自动化。** 人类专家积累足够内核开发经验后，会将遇到的问题转化为检查清单，将常用模式沉淀为可复用模板，将性能规律总结为估算方法。:mdnice-highlight[CAKE 的外层循环承担了同样的职能，由 Agent 执行沉淀过程，最终固化到编译器框架中，所有后续内核开发均可复用这些经验。]
:::

### 2.2 三大设计承诺：IR 结构化、反馈本地化、框架可进化

> CAKE 的整个体系建立在三项核心设计承诺之上，共同支撑双循环的有效运转。

| 承诺内容 | 核心机制 | 类比或效果说明 |
| --- | --- | --- |
| Agent 编辑类型化中间表示，而非原始 CUDA 代码 | 使用 Cake IR 作为结构化中间表示，显式表达所有硬件决策，支持生成前的检查与分析 | 传统模式如直接砌砖，出错需推倒重建；CAKE 模式如先绘施工图，结构问题可在施工前发现并修正 |
| 编译器返回本地化的正确性与性能诊断，而非通过/失败二值信号 | 失败时明确指出问题对应的资源、角色、阶段及违反的硬件契约类别；性能诊断指明瓶颈类型（如计算密集、访存密集、同步开销过高） | Agent 可依据精准反馈定向修改，避免盲目试错 |
| 编译框架本身作为进化目标 | 将重复失败模式转化为新验证规则，系统性预测偏差用于成本模型校准，新硬件模式驱动 IR 原语扩展；所有改动经内核语料库测试验证 | 系统能力边界随处理内核数量增长持续扩展，突破初始设计限制 |

### 2.3 两种入口模式：存量内核迭代与从零生成

> CAKE 支持两种工作入口，对应实际内核开发的两类典型场景。

- **第一种是从现有生产内核出发，持续迭代优化**。例如 FlashInfer 或 CUTLASS 中的成熟内核，需要适配新架构优化或新增功能变体。此时可将现有内核作为起点，在内层循环中持续进化，提升性能。
- **第二种是全新工作负载从零启动，无成熟参考实现**。例如新型模型结构仅具备数学描述或 Triton 参考实现，无专家级 CUDA 实现。此时 Agent 可直接在 Cake IR 中设计 warp 分工、数据布局、流水线结构，由编译器完成正确性验证与最终代码生成。

论文评估同时覆盖两种场景，既包含从零开始的冷启动实验，也包含现有生产内核的迭代优化，以及前沿新内核的合成，全面验证了系统能力。

::: block-1
回顾一下，CAKE 的核心创新是:mdnice-highlight[将编译器与 Agent 作为一个整体进行协同设计]。通过双循环嵌套架构、三大设计承诺和两种工作入口，:mdnice-bold-italic[它把内核开发从 Agent 单方面的黑盒试错，变成了编译器与 Agent 双向进化的协同过程，从范式层面提升了内核自动化的上限。]
:::

## 三、Cake IR：专为 Agent 打造的硬件显式调度语言

> Cake IR 是整个 CAKE 体系的核心载体，是 Agent 与编译器之间的交互语言。:mdnice-bold-italic[它是从大量生产内核中自底向上抽象出来的，目标是在不要求布局代数的前提下，给 Agent 提供足够细的硬件控制力。]

传统的 IR 设计通常是语言专家自上而下定义规范，再去适配各种内核；Cake IR 的生成路径正好相反，**从真实的生产内核出发，不断提炼共性模式、补充能力缺口**，逐步形成完整的词汇表。

> **上述进化过程可进一步拆解为五个步骤：语料收集、抽象提取、硬件导向设计、原则驱动迭代、移植驱动扩展**。每一步均有明确目标，确保 IR 进化有序，不会沦为杂乱的功能堆砌。各个步骤具体如下：

| 步骤 | 详细说明 |
| --- | --- |
| 语料库构建 | 从各类生产级库中收集高质量CUDA内核作为初始素材；原本采用其他领域特定语言（DSL）编写的内核，先由编码智能体统一翻译为包含内联 PTX 的 CUDA 代码。 |
| 抽象提取 | 智能体对内核语料库进行分析，将屏障编排、流水线分级、Warp角色划分、TMA描述符配置、TMEM累加器生命周期等反复出现的硬件调度模式，归纳为候选抽象。 |
| 硬件感知设计 | 结合专家经验，让抽象设计贴合Blackwell编程模型：将张量内存作为一等资源，将Warp专业化作为核心并行范式，将异步屏障作为同步原语，采用集群级操作实现多流多处理器（SM）协同。 |
| 原则驱动的迭代 | 每个候选抽象都需对照八项设计原则进行验证，下文会提到；存在不符合项的抽象会被优化修正，不满足要求的则直接被淘汰。 |
| 移植驱动的扩展 | 持续开展新内核的移植验证工作：移植成功则确认对应抽象的合理性，若暴露出能力缺口，则触发IR扩展或其下层转换（lowering）优化的提案；该流程持续循环运行，每一类新内核家族或新暴露的能力缺口都会推动IR进一步进化。 |

#### Cake IR 的设计遵循八项核心目标

- 一是**易用性**，保持编辑模型符合NumPy/PyTorch用户的使用习惯，避免不必要的目标参数传递或网格维度维护工作；
- 二是**性能透明性**，让所有与性能相关的硬件决策可被观测，下层转换（lowering）的行为可被查验；
- 三是**范式统一性**，每类操作优先采用唯一的规范表达形式，而非多种等价的不同写法；
- 四是**静态类型校验**，通过类型规则约束操作的下层转换过程，在程序构建阶段就拒绝类型不合法的程序；
- 五是**便于分析性**，开放支持各类静态分析所需的全部信息；
- 六是**测试门禁机制**，所有IR变更都需通过内核矩阵测试集的静态分析与编译验证；
- 七是**分析一致性**，IR数据模型的每次变更都同步配套更新对应的分析逻辑；
- 八是**硬件锚定性**，明确记录每个操作对应的预期硬件行为。

::: block-1
其中，便于分析性与分析一致性原则保障了新原语可被静态分析，测试门禁原则防范 IR 演化过程中出现功能回归，性能透明性与硬件锚定性原则让硬件映射关系对人类开发者和智能体都清晰可读，:mdnice-bold-italic[这一设计体系服务于 Cake 打造可审查、可复用构件的核心目标，这一思路与陶哲轩关于 AI 生成数学证明的观察相契合：当生成能力极大丰富后，技术瓶颈会从产物生产转向产物的验证与理解。]
:::

### 3.2 显式机器调度的四大核心属性

> **Cake IR 记录机器驱动的完整调度逻辑**：哪些 warp 承担哪些角色、缓冲区设置几级流水、哪个屏障管控哪次数据交接、哪种指令形式消费哪个操作数。调度负责定义“做什么”，降级（lowering）过程负责推导“怎么做”——屏障地址、相位位、TMEM 偏移、描述符编码、warp 标识等机械性细节，均由编译器从声明中计算生成，无需 Agent 手写。

完整程序由显式操作、声明资源、warp 角色、网格与流水线配置组合而成，核心具备四项属性。

- **第一是类型检查的词汇表**。计算、内存搬运、同步、数学运算、warp 控制均使用固定 IR 词汇，而非内嵌 C 代码或 PTX。:mdnice-bold-italic[每个操作都有明确类型约束，不符合要求的在构造阶段即被拒绝，不会遗留至编译阶段报错。]
- **第二是声明式资源**。内存区域、同步状态、流水线仅需声明一次，IR 可感知每个缓冲区的形状、数据类型与生命周期。:mdnice-bold-italic[Agent 无需管理原始地址，仅需定义资源属性，大幅降低出错概率。]
- **第三是显式角色**。warp 组具备命名标识，每次跨角色数据交接均可见，而非依赖隐含约定。:mdnice-bold-italic[例如加载 warp 与计算 warp 的同步关系通过显式声明定义，编译器可直接检查生产者与消费者的匹配关系。]
- **第四是自动推导元数据**。所有机械性元数据由降级过程生成，无需 Agent 编写。屏障具体地址、流水线相位标记、TMA 描述符编码等具备固定规则的体力劳动，全部交由编译器处理，Agent 仅需关注调度决策本身。

### 3.3 反常识的设计选择：不做布局代数的底层逻辑

> Cake IR 存在一项反常识的设计选择：**故意不将布局作为一等抽象**。当前多数新型编译系统将布局代数作为核心，例如 CuTe 的布局代数、Triton 的线性布局、Axe 的命名轴抽象，均通过数学体系统一描述张量内存布局。

Cake IR 选择了完全相反的技术路线。**Agent 无需操作布局代数，仅需直接写下具体存储与访问决策** ——例如共享内存视图偏移、操作数字节偏移、TMEM 列范围、重排标记、TMA 描述符坐标。:mdnice-bold-italic[合法性检查由编译器完成，负责验证这些约定是否符合目标硬件的指令与资源约束。]

::: block-1
:mdnice-highlight[该设计的核心动因是适配 Agent 的工作模式。布局代数是严谨的数学体系，但对 Agent 而言学习成本高，且易写出语法正确但语义错误的布局，故障调试难度大]。直接编写具体访问决策更符合 Agent 的代码生成模式，直观性更强。编译器承担布局兼容性检查的工作，将复杂逻辑隐藏在后台，仅向 Agent 反馈结果。
:::

诊断信息会指向相关 IR 决策与大致不匹配类别，不会抛出大量布局代数术语。**该设计保留了协同进化特性**：新原语可扩展验证覆盖范围，无需 Agent 学习独立的布局语言。

:::

## 四、编译运行时：从黑盒反馈到结构化诊断的进化

> 如果说 Cake IR 是 Agent 和编译器之间的交互语言，那么编译运行时就是支撑整个进化过程的工作环境。它不止承担将 IR 编译为可执行代码的职能，**更重要的是提供结构化的分析、验证与性能诊断，在 GPU 运行前即可完成大部分候选筛选与排序。**

编译运行时本身也是进化对象，内核进化中遇到的问题会不断沉淀为新的分析能力，让整个环境持续进化。

### 4.1 预编译阶段的七层验证体系

> 编译启动前，运行时会对类型化调度执行全面检查，覆盖七大类验证，将大部分错误拦截在编译之前。

这七类验证按处置方式分为门禁、报告、提示三个等级。

![文章插图](/articles/2026-08-28-cake-ir-kda-2-05-e54c4d68/images/10.jpg)

::: image-caption
表 1：Cake 工具链提供的分析与验证类别。该表定义了编译器与 Agent 之间的结构化反馈契约，按处置强度分为三类：类别 1 预编译门禁（4 类）：程序安全、硬件一致性、数据一致性、调度语义检查，均在编译前执行，可快速拦截非法候选，返回定位到具体资源 / 角色 / 阶段的错误原因，避免无效 GPU 资源消耗；类别 2 执行门禁（1 类）：数值验证，编译运行后与权威基准对比，保障结果正确性；类别 3 报告与提示（2 类）：性能分析输出瓶颈归因与成本估算，用于候选排序；优化指导给出非强制优化建议，用于引导探索方向。这种分级反馈机制替代了传统的 “通过 / 失败” 二值信号，是 Agent 从盲目试错转向定向优化的核心基础。
:::

四类预编译门禁构成第一道防线，在编译前执行。

- 程序安全检查识别同步、顺序与内存使用风险，例如屏障配对正确性、死锁风险、内存访问越界；
- 硬件一致性检查强制资源、指令与架构契约，例如指令架构兼容性、资源硬件上限校验；
- 数据一致性检查数据流与生产者-消费者表示兼容性，例如生产与消费数据格式匹配度；
- 调度语义检查声明调度的结构不变量，例如角色分配冲突、流水线阶段数合法性。

::: block-1
**这些检查会拒绝大量数学上合理但不符合目标执行模型的候选**。每项检查结果都会定位到具体程序区域与违反的契约类别，**为 Agent 提供明确的修复目标**。:mdnice-highlight[该机制与传统编译器的后端报错存在本质区别，Agent 可直接根据诊断信息修改对应调度部分，无需自行推断错误原因。]
:::

数值验证构成第二道防线，需要实际编译运行，与权威外部参考结果对比。最终验收要求在对应目标框架中完成端到端验证，确保不存在数值偏差。

### 4.2 性能建模：在 GPU 运行前预判瓶颈

> 除正确性验证外，运行时还提供校准后的成本模型，可估算候选性能并返回高层瓶颈归因与优化指导。

**成本模型的核心作用是对候选完成排序与过滤**，而非精确预测时延。实际 GPU 运行的时间与硬件资源成本很高，如果每个候选都需上卡实测，进化效率会极低。:mdnice-bold-italic[通过成本模型可在编译前完成初步估算，过滤明显性能不佳的候选，仅将有潜力的方案送去实测。]

论文明确指出，板载测量与性能分析始终是最终基准，成本模型仅承担排序与筛选职能。该设计既利用了静态分析的低成本优势，又保证了最终结果的准确性。

:mdnice-bold-italic[性能分析报告不仅输出估算时延，还会指明瓶颈类别，例如计算密集、访存密集或同步开销过高。优化指导会给出非阻塞优化建议，例如尝试加深流水线、调整 warp 分工]。建议不强制采纳，但可为 Agent 提供优化方向参考。

图 4：证据驱动的编译器进化。该图展示了编译器进化的两条互补路径，构成了 “自生长” 能力的核心：主动进化路径（左）：基于生产内核语料与 IR 设计原则，主动挖掘新硬件模式（如新指令、资源类型、同步惯用法），扩展 IR 原语与编译能力，向上突破能力边界；被动进化路径（右）：从内核进化的失败反馈中提炼共性问题，将运行时崩溃转化为验证规则、非法降级模式转化为静态检查、预测偏差转化为成本模型校准，向下完善分析能力。两条路径均通过内核语料库的测试门禁，确保进化不破坏现有兼容性，实现 “能力扩展 - 验证增强” 的正向循环，且整个过程主要由 Agent 执行，人类仅负责最终合并审核。
:::

- **第一条是主动挖掘路径**。Agent 分析生产内核与硬件文档，寻找新架构下缺失的模式——例如新指令形式、资源类型、描述符变体、同步惯用法——并提出编译器修改方案。每个方案实现前都需对照 Cake IR 设计原则完成检查，确保符合性能透明性与验证友好性要求。
- **第二条是被动沉淀路径**。Agent 从失败候选的反馈中——包括计算消毒器报告、失败案例、正确性不匹配、调试日志——提炼重复出现或代价高昂的失败模式，转化为新的分析能力。例如一次不明原因的运行时崩溃，可沉淀为验证器规则，后续遇到同类模式可在编译前拦截；反复出现的非法降级模式，可转化为静态检查；系统性预测偏差，可转化为成本模型的校准目标。

两条路径相互耦合。新原语为编译器暴露更多硬件事实，支撑更深入的分析；新分析又会约束未来原语的设计空间，保证新原语的可分析性。

> 所有编译器改动都需经过内核语料库的测试门禁，因为原语与其分析必须同步进化。仅增加语法而无对应效果与合法性规则，会降低 IR 的可分析性；仅新增验证规则而无语料验证，可能误判合法内核。

进化过程主要由 Agent 执行，人类仅在合并关卡完成审核。该机制保证系统能力可持续扩张，无需人类专家手动添加每条规则，同时保障质量可控。

::: block-1
总之，编译运行时的核心价值是:mdnice-highlight[把编译器的内部能力变成 Agent 可以消费的结构化反馈]，同时让自身也具备进化能力。预编译验证大幅降低了试错成本，性能模型提升了筛选效率，自进化机制保证了系统能力的持续成长。它不再是一个被动的翻译工具，而是主动参与内核进化的协作方。
:::

## 五、Agent 工作流与库级泛化路径

> 有了 Cake IR 和编译运行时，Agent 的进化工作就有了清晰的执行舞台。整个内核进化过程遵循标准化的四阶段工作流，外部工作负载契约是唯一权威标准，所有决策可审计，所有发现可复用。

论文中所有 Agent 任务均使用 GPT-5.6-sol 模型，推理强度设置为 xhigh。固定模型与 Agent 支架，是为了让性能对比的差异归因于环境设计，而非模型能力本身。

### 5.1 四阶段进化闭环：生成-过滤-评估-反馈

> 一次完整的进化运行分为四个阶段，形成闭环迭代。

第一阶段是生成。Agent 生成结构差异化的 Cake IR 候选。此处强调结构差异而非局部微调，目的是探索更大的设计空间，发现更优的调度方案。

第二阶段是过滤。在消耗 GPU 运行资源前，通过 IR 构造检查、验证器硬门禁、成本模型排序完成候选筛选。明显不合法的候选直接丢弃，性能估算不佳的候选靠后排序，仅通过筛选的候选进入下一阶段。该步骤是提升进化效率的关键，可将大部分劣质候选拦截在 GPU 运行之前。

第三阶段是评估。幸存候选与外部基准对比，运行基准测试，通过性能分析工具获取实测数据。外部基准具备权威性，例如 PyTorch 参考实现或业界最优基线，保证结果可信度。

第四阶段是反馈路由。根据评估结果，将证据分发至对应模块。候选本身的问题返回修改候选；验证器漏判则更新验证规则；成本模型预测失准则完成校准；IR 无法表达的模式则扩展 IR 词汇。

闭环每迭代一轮，不仅内核候选得到优化，整个环境也同步进化。所有结果均会留存，决策可审计，重复发现可沉淀为可复用资产。

### 5.2 工作负载契约：固定评估标准避免过拟合

> 为保障进化结果的可靠性，全过程遵循固定的外部工作负载契约。契约预先规定测试形状、参考基准、数值公差、目标硬件、允许引用范围。这些内容运行前确定，中途不可修改。

该机制可有效避免过拟合。如果评估标准可随意调整，很容易出现内核在特定测试形状上性能优异，更换形状后性能暴跌的情况。固定契约可保证进化出的内核具备真实性能提升，而非针对特定用例的刷分结果。

不同实验对应不同的参考访问策略。冷启动与前沿内核合成实验中，Agent 仅可查看数学规范、评估契约、正确性基准与高层代码，不可访问 CUDA、PTX、SASS 等低层实现，因为这些实现已包含调度决策，实验目标是测试 Agent 独立发现调度的能力。已知内核复刻实验中，Agent 可查看参考实现，测试目标为在已有结构基础上实现进一步优化。

### 5.3 从单形状调优到库级分发的两阶段路径

> 论文特别强调了多数基准测试会忽略的环节：将单形状调优的内核转化为支持任意形状的库级实现。CAKE 将其设为独立阶段，具备不同的优化目标、排序信号与失败模式。

单形状优化目标明确，即针对特定形状实现极致性能，可执行深度特化。若以广覆盖作为评分标准，会稀释优化信号。因此泛化阶段仅在单形状优化产出足够强的种子后启动，评分标准为包含分发逻辑在内的固定工作负载性能。不正确或性能不佳的种子会返回内层循环继续优化，不会隐藏在路由逻辑之后。

泛化阶段的核心工作是将已测量的种子按形状分组，生成特化或共享变体，在显式回退路径前排列守卫条件。调优可修改实现参数，但不可变更输入形状。汇总结果前，验证需覆盖代表性输入与留出输入、边界与尾部情况、重叠或缺失守卫、回退路径。

为防止评估泄露，有效形状域在调优前完成声明。分发谓词可划分该域，但不可随意新增评估用例。覆盖范围通过同一来源的确定性未见分片扩展。该机制保证分发器并非在声称泛化的集合上调优，结果具备可信度。

::: block-1
回顾一下，标准化的四阶段工作流保证了进化过程的有序高效，:mdnice-highlight[固定的工作负载契约保证了结果的客观可信]，独立的库级泛化阶段解决了从实验室基准到生产可用的最后一公里问题。整个工作流设计严谨，兼顾了探索效率和结果可靠性，符合生产环境的实际需求。
:::

## 六、实验验证：从零开始到前沿内核的全面突破

> 论文评估部分回答了三个核心问题：

1. 编译运行时能不能驱动从零开始的冷启动进化，超过已调优的基线；
2. CAKE 能不能在没有低层实现参考的情况下合成前沿内核；
3. 能不能复刻专家内核，对标业界最优的基线。

所有测试都在 B200 上进行，使用 GPU 上的正确性检查和 CUPTI 计时，每次计时采样前都会刷新 L2 缓存，保证测量的准确性。

### 6.1 冷启动基准测试：Flash-KMeans 的从零超越

该实验为严格的控制变量对照，固定编码 Agent 与支架、模型与推理强度、任务描述、正确性基准、测试框架与单个目标形状。实验组使用 Cake IR，对照组直接编写 CUDA C++与内联 PTX。每组执行三次重复运行，统计 8000 万 token 预算下的结果。

### 6.2 前沿内核合成：新架构的性能突破

> 前沿内核合成验证针对无成熟低层实现的新型模型架构，Agent 能否自主发现物理调度，产出高性能内核。

代码行数的对比也具备参考意义。所有 Cake IR 实现的代码量均短于对应参考设备内核。尽管语言与统计范围存在差异，不能直接作为生产力指标，但可**证明硬件调度可通过 Cake IR 紧凑表示，同时保留分析与降级所需的全部决策。**

:::

## 总结与展望：内核开发范式的新拐点

> CAKE 这项工作，:mdnice-bold-italic[本质上是把 GPU 内核开发的专业知识，从人类专家的脑子里，沉淀到了编译器框架里，再通过 Agent 来规模化地应用。它是从环境和工具的角度入手，通过协同设计来释放 Agent 的潜力。] 这套范式一旦跑通，会从根本上改变 GPU 内核开发的模式。以后新架构出来、新模型结构出来，不需要等少数专家慢慢手写优化，Agent 可以在编译器框架的辅助下快速产出高性能内核，并且在迭代过程中持续提升框架本身的能力。

目前 CAKE 支持从 Ampere 到 Blackwell 全系列 NVIDIA 架构。调度语言、角色模型、分析基础跨架构通用，指令形式、合法性规则、成本锚点为架构专属。这是移植成本的真实体现。:mdnice-bold-italic[非 NVIDIA 目标尚未验证，后端降级路径需要完整重建。]

**覆盖范围存在不均衡性，大部分性能数据来自 B200**，时序模型仅完成 B200 与 H100 的校准，其他架构不会随意输出预测。:mdnice-bold-italic[静态分析与性能模型刻意保留不完整性，仅在进化过程中承担排序与筛选职能，最终基准始终是 GPU 实际运行]。编译器进化目前在**合并关卡仍由人类引导**，尚未完全自动化。

这些均是发展中的问题，而非范式缺陷。双循环协同进化的框架本身具备自我完善能力。随着处理内核数量增长，IR 词汇会持续丰富，验证规则会逐步完善，成本模型会愈发精准，支持的架构也会不断扩展。

::: block-1
从更广阔的视角看，CAKE 代表了一种通用思路：:mdnice-bold-italic[当 AI 智能体进入专业领域时，最优方案是为其设计专门的交互语言与工作环境，将领域知识沉淀到工具中，让工具与 Agent 共同进化。如此才能真正结合 AI 的规模化优势与领域专业知识，释放最大生产力。]
:::

内核开发是首个落地领域。未来编译器-Agent 协同设计的思路，可能扩散至更多底层软件开发场景，例如网络协议栈、数据库内核、操作系统模块。凡是具备明确正确性与性能标准、拥有成熟编译与分析工具的领域，均可借鉴类似范式，让 Agent 成为生产力工具，而非简单的代码助手。

::: block-1
总之，CAKE 提出的:mdnice-highlight[编译器与 Agent 协同设计范式]，打破了 GPU 内核自动化的黑盒困境。**通过面向 Agent 的 Cake IR、结构化的编译反馈、双循环的进化机制，它不仅在性能数据上交出了亮眼的答卷，更重要的是探索了一条可持续进化的内核开发新路径**。这项工作很可能成为 GPU 内核开发从手工时代向自动化时代转型的标志性节点。
:::
