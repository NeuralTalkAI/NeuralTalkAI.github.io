## 一、引言

> 大语言模型（LLM）的快速普及催生了对高效推理框架的旺盛需求。当前该领域主要分为两大技术路线：基于高性能 GPU 的系统[13,24]与易部署的 CPU 端系统[7]。其中，llama.cpp[7]作为 CPU 推理的开创性框架，凭借高效的 C++实现实现了 LLM 在 CPU 上的落地运行。

但主流 CPU 推理框架难以适配广泛部署于 Web 服务器与高端网络设备的**众核 CPU 平台**。:mdnice-bold-italic[这类平台普遍采用非统一内存访问（NUMA）架构，将 CPU 核心与内存划分为多个节点；在该架构下，跨节点访问远程内存的开销远高于本地内存访问，如图 1 所示。]

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/03.webp)

::: image-caption
图 1：在众核 CPU 平台中，CPU 核心与内存采用非统一内存访问节点（NUMA 节点）进行组织。图中展示了一个拥有 128 个核心、4 个 NUMA 节点的平台。
:::

::: block-1
现有框架普遍忽视这一**跨 NUMA 内存访问墙**，当 LLM 推理扩展至数十核心时，数据同步与非本地内存访问开销成为性能瓶颈，导致系统无法触及理论算力上限。
:::

对 llama.cpp 这类成熟框架**进行 NUMA 感知改造难度极大，需要从底层内存分配、线程管理到顶层模型定义做全栈式“精细化重构”**。此外，主流框架持续迭代导致代码日益臃肿，遗留代码与复杂抽象让内部逻辑不透明，阻碍研究者实现细粒度优化或快速适配新兴模型架构。

> 为弥补这一缺口，本文提出**ArcLight** ——一款从零设计、面向众核 CPU 的轻量级 LLM 推理架构。:mdnice-bold-italic[ArcLight 遵循极简与模块化设计理念，仅保留高性能推理所需的核心组件]，清晰的模块边界让开发者无需维护单体代码库即可轻松扩展功能、集成新模型。**更关键的是，ArcLight 针对众核环境提供定向优化，包含 NUMA 感知内存与线程管理、细粒度可控张量并行，有效缓解跨节点内存访问开销。**

实验结果表明，在众核 CPU 平台上，ArcLight 相较当前主流的 llama.cpp 推理吞吐量**最高提升 46%，显著超越主流框架的性能上限**。本文核心贡献如下：

1. 轻量级推理架构：开源一款模块化框架，凝练 LLM 推理核心能力，为研究者提供透明可定制的 CPU 端 LLM 部署底座，无传统框架的冗余开销。
2. 众核 CPU 多维优化：提出众核 CPU 全维度优化方案，通过线程调度与内存访问墙优化，大幅突破 CPU 端 LLM 推理性能边界。

## 二、系统设计

ArcLight 采用简洁清晰的模块化设计，以极简方式实现 CPU 推理核心功能，便于后续扩展与迭代。本章阐述 ArcLight 整体架构与核心设计细节。

### 2.1 整体架构

> 如图 2 所示，ArcLight 采用解耦式架构，分为高层解码前端与底层推理后端。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/04.webp)

::: image-caption
图 2：ARCLIGHT 架构
:::

该设计让核心计算保持轻量与硬件无关性，同时支持推理引擎内的定向优化。

- 推理后端实现 CPU 高性能推理所需的最小模块集，包含五大核心模块：内存管理器、线程管理器、张量库、前向计算图构建器、计算图调度器；此外引擎内置专用算子库，包含 LLM 计算所需的数学核函数（如 GEMM、Softmax）。
- 引擎向前端暴露精简 API，前端负责权重加载、模型定义与自回归解码循环。

整个架构仅由约 10 个 C++头文件与源文件构成。

### 2.2 张量库

> 张量库定义 ArcLight 的张量及所有运算（计算核函数除外）。与 llama.cpp 采用的 C 风格定义不同，**ArcLight 基于 C++类实现严格的面向对象封装**，提升模块化与可维护性。

ArcLight 张量由**头信息** 与**数据区** 两部分组成：

- 张量头存储核心元数据，包括张量名称、形状、数据类型、运算类型、辅助参数，以及用于构建计算图的源张量指针；
- 数据区为连续虚拟内存块。

该库提供高层接口管理上述属性，如获取/设置名称与形状、计算内存分配所需总字节数等方法。

### 2.3 内存管理器

> 内存管理器负责运行时内存生命周期管理，核心职责是程序启动时向系统预分配足够大的内存池，再分配给权重张量与激活张量。

与 llama.cpp 采用的统一内存访问（UMA）单体缓冲区不同，ArcLight 启用 NUMA 后，会在:mdnice-bold-italic[每个 NUMA 节点的本地内存中独立分配缓冲区，如图 3 所示，大幅简化张量与 NUMA 节点的显式绑定。]

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/05.webp)

::: image-caption
图 3：统一内存访问（上）与非统一内存访问（下）缓冲区管理策略对比。在统一内存访问策略中，非统一内存访问节点对系统是透明的。
:::

此外，为降低逐层推理的内存开销，我们为激活缓冲区实现**双缓冲机制**，两个激活缓冲区按层奇偶交替使用，显著降低运行时内存占用，如图 4 所示。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/06.webp)

::: image-caption
图 4：双缓冲机制
:::

### 2.4 线程管理器

> 线程管理器在推理启动前创建一组工作线程，运行时协同执行张量计算。llama.cpp 等常规线程管理方案将工作线程组织为单线程池，执行同一计算任务，仅适用于单前向计算图。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/07.webp)

::: image-caption
图 5：多视图线程组织结构
:::

> 为灵活支持单图与多子图执行，ArcLight 引入**多视图线程组织**，如图 5 所示：

- 在线程池内新增线程组逻辑抽象，池初始化与图执行时提供显式接口与算子，动态重构内部线程组织；
- 当线程池被划分为 n 个组时，这些组可并行执行 n 个独立张量运算。

线程组内的屏障同步是推理框架常规设计，所有线程同时通过屏障以保证执行进度一致。引入多逻辑线程组织后，屏障管理变得复杂，因此我们新增**全局屏障** 实现整个线程池的跨组同步，如图 6 所示，与传统组内屏障区分。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/08.webp)

::: image-caption
图 6：局部屏障与全局屏障。“g0t0”表示第0组中的第0号线程。
:::

- 未启用全局屏障时，同步仅发生在逻辑线程组内部；
- 启用后，所有逻辑组线程必须共同到达并通过全局屏障。

### 2.5 前向计算图构建器

> 与 llama.cpp 类似，ArcLight 采用静态计算图，执行前完成全图构建。

计算图构建器实现并暴露一组张量运算接口，用于定义图节点；这些接口接收源张量指针与必要参数，返回当前节点对应的输出张量。**前端定义模型时，只需选用并组合这些接口即可构建完整计算图。**

此外，我们**简化了主流框架常用的拓扑排序流程**：模型定义顺序天然遵循拓扑序，因此在每个节点构造函数末尾将其追加至顺序容器，避免重新分析图结构的开销。

计算图模块同时实现 KV 缓存管理，包含 KV 缓存张量创建、写入（set）、读取（get）等基础操作。本计算图构建设计大量复用 llama.cpp 的实现思路。

### 2.6 计算图调度器

> 计算图构建完成后，所有节点执行顺序已确定并存储于顺序容器。调度器按顺序遍历该容器，依次执行每个节点关联的计算（如 GEMM、注意力），再进入下一节点。

为保证执行正确性、避免节点间干扰，每个节点计算完成后执行屏障同步。多 NUMA 优化下，计算图构建与调度逻辑更复杂，将在下一章详细说明。

### 2.7 张量运算

> 执行调度器按顺序处理计算图中的张量运算。

所有算子接口在 ops.h 中声明，实现与硬件特性相关：

- 拷贝、reshape 等硬件无关运算在 common.cpp 中实现；
- GEMM、FlashAttention 等 CPU 依赖算子则根据目标硬件实现。

例如 ARM CPU 不同世代对 GEMM 提供不同等级硬件加速，NEON 提供 SIMD 指令，i8mm 加速 8 位整数乘法。ArcLight 未自研算子库，而是重组并复用 llama.cpp 的算子实现。

## 三、跨 NUMA 张量并行

众核平台中，本地内存访问与跨节点访问的延迟差距极大。llama.cpp 等主流框架未针对 NUMA 引发的内存屏障做显式优化。基于前述推理基础设施，我们提出**跨 NUMA 张量并行**，突破众核平台性能限制。

### 3.1 跨 NUMA 内存访问

> 我们首先测量不同 NUMA 节点间的内存访问速度，在 4-NUMA 测试机上对不同核心–内存组合做基准测试，结果如表 1 所示。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/09.webp)

::: image-caption
表 1 不同核心–内存组合的内存访问速度（GB/s）
:::

系统中每个 NUMA 节点管理 6×DDR4 内存与 48 个 ARM 核心，**结果显示核心访问本地内存的速度约为跨节点访问远程内存的4 倍**，充分验证众核平台上严重的跨节点内存访问墙。

llama.cpp 仅对众核平台提供基础支持，暴露`--numa`选项，设为 distribute 时线程池线程均匀绑定到不同 NUMA 节点核心，但未将张量绑定到指定 NUMA 节点，导致计算与内存访问频繁不匹配。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/10.webp)

::: image-caption
图 7：llama.cpp中的GEMM内存亲和性。蓝色表示权重，红色表示激活值。
:::

如图 7 所示，线程分布在各 NUMA 节点，对应权重区域也相应切分；根据首次访问策略，操作系统为每个权重分区在首次访问的 NUMA 节点分配物理内存页，这一分配本身合理。

以 GEMM1 为例，若初始激活值仅存于节点 0，节点 1–3 的权重分区必须远程访问激活值，产生非本地内存访问。

- GEMM1 完成后，输出激活张量均匀分布到所有节点；再执行 GEMM2 时，权重仍切分在各节点，但每个权重分区仅 1/4 激活访问为本地，其余 3/4 为远程。该模式在后续 GEMM 运算中持续存在，形成长期性能瓶颈。

### 3.2 权重切分

> 张量并行（TP）可减少连续 GEMM 间的跨节点数据访问，广泛用于多设备 LLM 训练[19]。当 CPU 上跨 NUMA 内存访问成为瓶颈时，张量并行可从原理上缓解该问题。

如图 8a、8b 所示，与原始 MLP 相比，合理切分的矩阵乘法序列可完全消除跨节点内存访问。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/11.webp)

::: image-caption
图 8：标准多层感知机、张量并行多层感知机与注意力机制的简化计算图
:::

Transformer 模型中，$w_q$、$w_k$、$w_v$、$W_{gate}$、$W_{up}$ 按行切分，$w_o$、$W_{down}$ 按列切分，即 $w_q$、$w_k$、$w_v$ 按注意力头切分。

以图中 MLP 为例，原始计算为 $Y=\sigma(A X)$，$Z=B Y$；张量并行下变为 $[Y_1,Y_2]=[\sigma(A_1 X),\sigma(A_2 X)]$、$[Z_1,Z_2]=[B_1 Y_1,B_2 Y_2]$，最终 $Z=Z_1+Z_2$。**所有参与张量并行的张量均拆分到各 NUMA 节点的缓冲区，有效隔离跨节点内存访问。**

### 3.3 并行计算图

> 未启用张量并行时，所有线程协同执行同一运算（如 GEMM）；CPU 上启用张量并行后，多个算子可并发执行，计算图变为一组并行子图，需要灵活切换单图与多子图执行模式，如图 8 所示。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/12.webp)

::: image-caption
图 8：标准多层感知机、张量并行多层感知机与注意力机制的简化计算图
:::

我们实现两个核心算子：**Scatter（分发）** 与**Gather（聚合）**。

- Scatter 算子将线程池重构为多个组，为每个子图输入创建视图张量；Scatter 完成后，子图并行执行。
- Gather 算子收集并求和所有子图输出张量，将线程池恢复为单组；Gather 完成后，执行回到非张量并行模式。

### 3.4 线程同步

> 如前所述，进入多子图张量并行模式后，子图相互独立、无数据依赖，即便执行相同 GEMM 也可异步运行。

![文章插图](/articles/2026-04-16-numa-arclight-cpu-faa7ac59/images/13.webp)

::: image-caption
图 9：不同线程组同步方式的对比。虚线表示屏障。
:::

启用张量并行后，线程组间同步有两种方案，如图 9 所示：

- 方案 A 所有线程组使用全局同步，每组完成一个算子后共同进入下一个；
- 方案 B 同步仅限制在每个线程组内部，仅在开始与结束使用全局屏障。

图示与实验结果均表明，**子图异步执行** 显著减少线程空闲时间，进一步加速张量并行执行。

- 张量运算使用 NEON 向量指令，实验模型为 Qwen3-4B，量化格式 Q4_0[21]。

## 五、相关工作

> 当前主流 LLM 推理框架包括：

- GPU 端的 vLLM[13]、TensorRT[17]
- CPU 端的 llama.cpp[7]、ONNX Runtime[15]等

这些框架通过 FlashAttention[4]、PagedAttention[13]、流水线并行[10]、序列并行[12]等技术，解决特定设备的内存管理与数据访问瓶颈，**但普遍忽视众核 CPU 平台的跨 NUMA 瓶颈。**

## 六、结论与局限

> 本文实现一款面向 CPU 的轻量级 LLM 推理架构，重新设计内存管理、线程调度与计算图执行逻辑，并针对众核平台做定向优化。

相较主流框架，ArcLight 取得显著性能提升，我们将长期维护并开源迭代，目标是打造易用实用的开发工具与教学平台。

::: block-1
本工作仍存在若干局限：

- 目前仅在 ARM 平台完成验证，对 x86 等架构的支持留待后续；
- Scatter 与 Gather 算子实现仍较初步，后续优化将聚焦降低内存开销、提升并行效率。
:::
