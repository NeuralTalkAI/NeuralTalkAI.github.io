::: block-1

该系统的多个实例（具有不同的 e-GPU 配置）采用台积电 16 nm SVT CMOS 工艺实现，工作频率为 300 MHz，电压为 0.8 V。

:::

## 关键问题

### 问题 1. e-GPU 作为针对 TinyAI 的 GPU 方案，与现有超低功耗专用加速器（如 CGRAs、 systolic arrays）相比，在处理非高度并行化的控制密集型任务时，核心竞争力体现在何处？

e-GPU 在处理**非高度并行化的控制密集型任务** 时，核心竞争力体现在其**可编程性与灵活性**。相比专用加速器的固定架构：

::: block-1
- **e-GPU 通过开源可配置的 RISC-V 架构及 Tiny-OpenCL 框架，能适应不同任务需求**；
- 其**统一内存架构减少数据传输开销**，即使在控制密集的 delineation 阶段仍实现 3.1× 到 13.1× 加速，且能耗降低 1.5× 到 2.7×，在保持一定效率的同时兼顾任务多样性。
:::

### 问题 2. Tiny-OpenCL 框架的调度开销在矩阵尺寸小于 256×256 时不可忽略，而许多 TinyAI 任务数据规模更小，该框架如何优化以适应这类场景？

对于小数据规模的 TinyAI 任务，可**通过 e-GPU 的可配置性优化 Tiny-OpenCL 框架的调度开销。**

::: block-1
- 例如*调整线程数量、缓存线大小及银行数量，减少资源分配迭代次数*；
- 利用**框架支持的自定义参数** （如内核基地址、栈大小），匹配小任务资源需求；
- 且**共享数据缓存设计** 可减少数据传输，间接降低相对开销。
:::

### 问题 3. e-GPU 的可配置性带来了面积、功耗与性能的权衡，在实际 TinyAI 应用部署中，如何根据具体任务需求确定最优配置参数，是否存在普适性的配置策略？

实际部署中需根据任务特性确定 e-GPU 配置：

::: block-1
- 高度并行任务（如 FIR 滤波）可增加线程数（如 16T）提升性能；
- 内存密集型任务调大缓存或调整线大小；
- 资源受限场景减少计算单元。
:::

**普适策略** 包括:mdnice-bold-italic[依据任务并行度匹配线程数、按数据量优化缓存参数，及利用开源特性定制化调整]，论文中 4T、8T、16T 配置的实验即体现此思路。

## 一、引言

对基于机器学习的实时计算的需求日益增长，推动了边缘计算的快速发展。通过在本地处理数据而非依赖云服务器，边缘计算减少了延迟、增强了隐私性并提高了能源效率，使其成为众多边缘应用的理想解决方案。然而，:mdnice-bold-italic[这些工作负载对计算性能、实时响应能力和功耗提出了限制，因此需要专用的硬件架构[1]。]

**应对这些挑战的一种有前景的方法是采用异构架构**，即将主机中央处理器（CPU）与领域专用加速器集成，以平衡效率和性能[2], [3]。在这些加速器中，:mdnice-bold-italic[图形处理器（GPUs）在利用机器学习和信号处理任务的数据并行性方面表现尤为突出]。:mdnice-bold-italic[当与主机 CPU 结合时，GPU 形成加速处理单元（APU），实现了一个能够高效处理通用任务和计算密集型工作负载的统一平台。]

> 尽管存在从高性能到嵌入式解决方案的各种 GPU 实现，但在**超低功耗边缘设备（TinyAI）背景下，它们的权衡仍未得到充分探索**。

::: block-1
- 这些电池供电设备在严格的功率约束下运行（通常在几十毫瓦范围内），因此需要高效的 GPU 架构。其小巧的外形也带来了严格的面积限制，整个片上系统（SoC，指将计算机的各个组件集成在一块芯片上的系统）通常仅占几平方毫米。
- 此外，由于**缺乏文件系统和多线程支持，传统的 GPU 编程框架（如标准开放计算语言（OpenCL）实现）无法使用[4]，因此需要自定义优化。**
:::

:mdnice-bold-italic[由于上述限制，超低功耗设备通常依赖专用加速器]，如粗粒度可重构阵列（CGRAs，一种通过调整内部结构来适应不同计算任务的硬件，适合低功耗场景）[5], [6]、脉动阵列（一种通过数据流在内部节点间流动来实现高效并行计算的结构）[7]以及近存计算[8]或存内计算[9]解决方案，而 GPU 在该领域的潜力仍未得到充分挖掘。

> 本研究通过提出一种开源、可配置的 RISC-V 平台（嵌入式 GPU，即 e-GPU），探讨了将 GPU 用于 TinyAI 应用的可行性和权衡。

::: block-1
- 该平台的广泛可配置性使其能够实现面积和功率优化，以满足该领域的需求。
- 此外，自定义的微型开放计算语言（Tiny-OpenCL）实现克服了上述限制，为资源受限设备提供了专门开发的轻量级编程框架。
:::

为展示所提出平台在实际场景中的适应性，我们:mdnice-bold-italic[将 e-GPU 与可扩展异构节能平台（X-HEEP）[10], [11]集成，构建了一个面向 TinyAI 工作负载的 APU。]

所提出系统的多个实例（具有不同的 e-GPU 配置）采用台积电 16 nm SVT CMOS 工艺实现，工作频率为 300 MHz，电压为 0.8 V。**我们对其面积和泄漏特性进行了分析，以确保符合 TinyAI 的约束条件**。

为评估运行时开销和应用级效率，我们采用了两个基准测试：通用矩阵乘法（GeMM）和生物信号处理（TinyBio）工作负载。GeMM 基准测试用于量化 Tiny-OpenCL 框架引入的调度开销，而 TinyBio 基准测试则用于评估相对于基线主机的性能和能耗改进。

本研究的主要贡献如下：

::: block-1
- 我们:mdnice-bold-italic[主张领域专用 GPU 是 TinyAI 领域的合适解决方案。]
- 我们提出了 e-GPU[12]——一种专为 TinyAI 工作负载设计的开源、可配置 RISC-V GPU 平台。我们分析了该应用领域的编程限制，并引入了面向资源受限设备的 Tiny-OpenCL 框架。
- 我们探索了将 GPU 用于 TinyAI 应用的可行性和权衡。
- 我们发布了一个开源代码库，包括完整的 e-GPU1，以便研究人员根据其 TinyAI 领域定制该平台。
:::

## 二、现有技术（STATE-OF-THE-ART）

> 本节分析了对我们平台设计选择有启发的最相关的商业和学术 GPU 解决方案。

### A. 商业 GPU

商业边缘 GPU 领域存在**多种平衡性能和能效的解决方案**。

::: block-1
- 高通的 Adreno GPU 集成在骁龙系统级芯片（SoC）中，为移动和边缘应用提供高能效计算。特别是 Adreno 600 系列，通过先进的节能机制，广泛用于机器学习推理。
- 类似地，ARM 的 Mali GPU 嵌入在各种系统级芯片中，其架构不断优化以提升能效。例如，Mali-G52 和 Mali-G72 系列中的细粒度电源门控（一种通过关闭不使用的电路模块来节省能量的技术）等创新，提高了能效，使其适用于低功耗场景。
- 另一个重要参与者是 Imagination Technologies 的 PowerVR GPU，它注重高能效性能，其 Series8XT 系列在边缘设备中展现出有竞争力的计算能力。
:::

尽管取得了这些进展，:mdnice-bold-italic[商业 GPU 并非专门为 TinyAI 应用设计。它们的功耗通常在数百毫瓦到数瓦之间]，超过了这些应用的严格要求（TinyAI 应用通常要求功耗在数十毫瓦级别）。此外，:mdnice-bold-italic[这些 GPU 的专有性质阻碍了对其性能和功耗的详细表征，限制了它们在研究和能效设计探索中的使用。]

### B. 学术 GPU

学术 GPU 研究主要:mdnice-bold-italic[致力于为各种计算领域开发可编程 和可配置的架构]。

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/02.webp)

**表 I 基于六个关键特征对 GPU 平台进行了比较**：（1）开源代码（便于快速获取）；（2）开源指令集架构（ISA，便于自定义扩展）；（3）可配置性（以适应特定应用需求）；（4）可综合的寄存器传输级代码（RTL code，用于准确评估性能和功耗）；（5）与主机 CPU 的集成能力（以研究 CPU-GPU 交互）；（6）面向 TinyAI 应用的超低功耗设计。

> 学术 GPU 解决方案涵盖从软件模拟器到硬件实现的范围。

#### 1) 软件模拟器

- GPGPU-Sim [13] 对基于 CUDA 的 GPU 进行建模，模拟 NVIDIA Fermi 和 GT200 等架构。
- gem5gpu [14] 通过集成 gem5 [15] 的 x86 CPU 和内存模型对此进行了扩展，便于研究 CPU-GPU 交互。
- 另一个例子是 Multi2Sim [16]，它模拟 AMD Evergreen GPU 系列以及多线程 x86 处理器。

虽然软件模拟器有助于快速进行架构探索，但它们对 TinyAI 研究存在显著限制，包括:mdnice-bold-italic[缺乏可综合的 RTL 代码（无法进行准确的功耗和能量分析）、缺乏开源 ISA（限制了扩展机会），以及主要面向高性能计算（不适合超低功耗边缘应用）。]

#### 2) 硬件实现

> 一些学术 GPU 项目提供可综合的 RTL 代码（描述硬件电路的代码，可用于芯片制造），能更深入地了解功耗和性能指标。

::: block-1
- **Skybox [17] 是一个 RISC-V GPU 框架**，专为图形研究设计，支持 Vulkan API。然而，它:mdnice-bold-italic[依赖于通过 PCIe 与主机 PC 通信，不适合集成到超低功耗应用] 中常用的系统级芯片（SoC）中。
- **ZJX-RGPU [18] 将 RISC-V CPU 和片段引擎集成到一个 12.25 mm² 的芯片** 中，工作频率为 200 MHz，功耗约为 20 mW，但:mdnice-bold-italic[其闭源性质和有限的文档限制了其在架构探索中的使用。]
- **Vortex [19] 是一个重要的进展，它是支持 OpenCL 和 OpenGL 的可配置 RISC-V GPU**。使用 15 nm 教学单元库合成单个计算单元时，其在 300 MHz 下的功耗为 46.8 mW。然而，:mdnice-bold-italic[其硬件若不经过大量修改则无法直接综合，且面向 PC 级主机环境]。这些特性阻碍了其集成到系统级芯片中——在超低功耗应用中，轻量级互连和紧密的软硬件耦合至关重要。
- **METASAT 平台 [20] 为安全关键型 RISC-V 系统级芯片适配了 Vortex，将其与 NOEL-V 处理器和 SPARROW 单指令多数据（SIMD，一种并行计算模式，一条指令同时处理多个数据）加速器集成**。该平台设计为在 RTEMS 和 XtratuM hypervisor（虚拟机监控程序）下运行，去除了 OpenCL 依赖，使 GPU 能在分区实时环境中使用。然而，其 GPU 继承了 Vortex 的局限性，仅作为将 GPU 集成到未来太空系统的概念验证，而非以能效为主要关注点的 TinyAI 计算解决方案。
- **Virgo [21] 基于 Vortex 构建，引入了一种离散的 GPU 架构，具有集群级矩阵单元**，与核心耦合设计相比，提高了数据重用率并降低了能耗。尽管 Virgo 实现了高能效且完全开源，但其:mdnice-bold-italic[面向大规模通用矩阵乘法（GEMM）操作和数据中心级深度学习工作负载]，限制了其在小问题规模的 TinyAI 场景中的灵活性。此外，Virgo 依赖相对复杂的内存层次结构和计算单元间复杂的同步机制，可能难以适配具有严格面积和功耗约束的极简系统级芯片设计。
- :mdnice-bold-italic[Ventus [22] 基于 RISC-V 向量扩展（RVV），引入了一种高性能通用计算 GPU（GPGPU）架构，具有用于单指令多线程（SIMT，一种并行执行模式，单个指令控制多个线程）执行、谓词分支、同步和张量操作的自定义指令]。它可扩展至 16 个计算单元和 256 个线程束（warp，一组同时执行的线程），与 Vortex 相比，指令周期数（CPI）减少高达 87.4%，指令数减少 83.9%。然而，:mdnice-bold-italic[Ventus 专为大规模 FPGA 部署设计，尚未集成到系统级芯片中，面向 PC 级主机]。尽管使用 TSMC 12 nm 库报告了频率和面积的综合结果，但未提供低功耗或流片优化。因此，:mdnice-bold-italic[Ventus 面向高吞吐量应用和架构研究]，而非 TinyAI 场景。
:::

## 三、背景知识

> 本节基于标准 OpenCL 定义总结所需术语。这些术语按平台模型、执行模型和运行时模型进行组织。

::: block-1
- **平台模型** 定义主机系统与负责执行内核的计算设备之间的关系。
- **执行模型** 描述内核如何启动以及工作项和工作组如何在可用硬件上组织和执行。
- **运行时模型** 规定内核在硬件级的执行行为，包括线程调度、同步和执行资源的利用。
:::

### A. 平台模型

在平台模型中，主机指运行 OpenCL 主机代码的主系统（通常是 CPU），负责管理和调度计算设备上的内核执行。设备是执行 OpenCL 内核的加速器（如 GPU）。

- 每个设备由一个或多个计算单元组成，计算单元是负责执行工作组的架构模块。
- 计算单元内部包含多个处理元素，它们是最低级别的执行资源，执行工作项的算术和逻辑操作。

### B. 执行模型

执行模型**控制计算的组织和启动方式。**

- 主机代码从主机端协调整个执行过程，向设备发布命令并管理数据传输。
- 内核是在计算设备上运行的 OpenCL 函数，由多个工作项并行执行。
- 每个工作项对应内核执行的一个实例，处理输入数据的特定部分，通过唯一的全局 ID 标识。
- 工作项被分组为工作组，工作组被分配给计算单元。
- 同一工作组内的工作项可通过本地内存共享数据，并使用屏障（barrier，同步点，确保所有工作项到达该点后再继续执行）进行同步。
- 全局大小指定要启动的工作项总数，本地大小决定每个工作组中的工作项数量。

### C. 运行时模型

运行时模型描述内核在**硬件级的执行方式**。

- 线程代表在处理元素上运行的一个内核实例，拥有自己的私有寄存器集。
- 线程通常被分组为线程束（warp），线程束中的线程同步执行（即共享相同的程序计数器，同时执行相同的指令）。

根据硬件能力，流水线中可同时有多个活跃的线程束，从而实现细粒度并行和执行资源的高效利用。

### A. 计算单元

计算单元基于 Vortex 核心[19]。它**采用乱序执行的 RISC-V 架构**，具有内部可配置选项，可用于调整并行线程和并发 warp（线程束，一组同时执行的线程）。调整线程数量可通过改变处理元件的数量来修改数据并行性，而配置 warp 数量则通过细粒度多线程使多个 warp 能够并发执行，从而提高资源和内存带宽的利用率。

由于**功耗和面积限制，我们移除了浮点单元**，以**优先支持整数和定点算术运算**，因为该平台面向基于整数的 TinyAI 模型。此外，我们通过自定义的 SLEEP REQ 指令扩展了 RISC-V 指令集架构（ISA），以提高能效。在内核处理结束时，该指令会等待所有先前取指的指令执行完毕，然后向 GPU 控制器生成一个事件，表明操作已完成。这种机制使 GPU 控制器能够在计算单元不再使用时（如果支持的话）通过时钟门控或电源门控将其断电，从而提高整体能效。在设计阶段，可以通过配置计算单元的数量来权衡面积、功耗和处理需求。

### B. 内存层次结构

> 内存层次结构采用统一架构，其中主机主内存和 e-GPU 全局内存映射到主机上的同一物理内存。这种共享内存模型通过消除不同内存区域之间的显式数据传输需求，增强了可编程性。特别是，不再需要复杂的显式双缓冲方案来在主机主内存和 e-GPU 全局内存之间移动输入和输出数据。

每个计算单元都包含一个私有指令缓存，以减少内存访问延迟并提高性能，而所有计算单元共享一个数据缓存。

**缓存逻辑基于 Vortex 缓存[19]，采用直接映射的多 bank（存储体，内存的一种组织方式，多个存储体可并行访问以提高带宽）架构，并使用线交织寻址方案**。对未完成请求的支持使后续 warp 能够在先前的 warp 因缓存未命中而停滞时发起新的缓存访问。在设计阶段，可以根据目标应用的特定需求调整缓存大小、bank 数量和线大小。我们集成了专用的内存封装器，以无缝实例化每个指令 bank 的量产级 SRAM 宏。

:mdnice-bold-italic[每个计算单元都连接到一个私有指令缓存。当多个计算单元执行相同的内核时，这种设计会随着计算单元数量的增加而提高可扩展性，并避免使用共享指令缓存时可能出现的冲突]。实际上，无法保证每个计算单元在每个时钟周期都取相同的指令。因此，使用独立的私有指令缓存有助于减少未命中率并减轻性能下降。此外，当不同的计算单元执行不同的内核时，独立的缓存可提高 locality（局部性，指数据或指令在短时间内被重复访问的特性）。

在**数据方面，所有计算单元共享一个公共数据缓存**。这种设计在较慢的主机主内存和较快的计算单元寄存器文件之间提供了一个中间存储层，从而提高了数据访问效率。此外，使用共享缓存使计算单元之间能够直接共享数据，而无需额外往返于主机主内存。

输入数据在第一个内核开始时从主机加载到共享数据缓存中，并且在中间内核的整个执行过程中保持可用（假设缓存足够大以容纳整个工作集）。这种方法通过最小化数据传输来提高性能，最终提高能效。

最后，我们重新设计了数据缓存接口，以支持所有计算单元的多线程并行请求。:mdnice-bold-italic[每个计算单元会发出多个同时请求（每个活动线程一个），但接收单个统一响应。输入和输出数据会根据请求线程进行选择性屏蔽]。这种对多维请求的支持通过在无 bank 冲突时允许对共享缓存的并发访问，提高了带宽利用率。

在系统边界处，内存接口有效地将缓存请求转换为主机内存事务。这分为三个步骤：

::: block-1
1. 在未命中时，缓存请求一个完整的多字线，然后将其序列化为单个 32 位事务；
2. 将缓存协议转换为 OBI 协议[23]（一种在边缘系统中广泛采用的低功耗总线协议）；
3. 仲裁器[24]管理对共享输出端口的访问，确保公平高效的资源分配。
:::

### C. 控制器

我们设计了一个专用控制器来管理 e-GPU 的操作。一组内存映射的配置寄存器支持诸如复位、启动和暂停加速器等操作。此外，该控制器集成了一个电源控制器，该电源控制器与第 IV-A 节中描述的低功耗 RISC-V 扩展协同工作。

内核启动后，电源控制器会监控每个计算单元的执行结束事件。

- 一旦收到事件，相应的计算单元就会断电。
- 一旦收到所有事件（表明所有计算单元都已完成执行），控制器会生成一个外部中断以通知主机 CPU。

## 五、e-GPU 软件

> :mdnice-bold-italic[本节介绍 Tiny-OpenCL 框架，这是一个轻量级且高度优化的 OpenCL 实现]，旨在编译内核以在 e-GPU 上执行。该框架在最大限度地**提高与现有 GPU 软件兼容性** 的同时，确保**跨平台的可移植性**。

### A. Tiny-OpenCL 框架

该框架包括以下软件组件：

::: block-1
1. SIMT（单指令多线程，一种并行执行模式，单个指令同时控制多个线程）RISC-V 扩展 API[19]，用于访问低级计算单元功能，例如激活和停用线程与 warp、通过拆分和合并处理分支分歧（不同线程执行不同路径的情况）以及管理同步屏障；
2. 启动函数，负责初始化 e-GPU 并执行必要的设置操作，包括计算每个线程的栈指针；
3. 调度函数，用于在可用计算资源（计算单元、线程和 warp）之间协调工作项的执行，确保工作负载的高效分配。这些组件使用标准的 RISC-V GNU 工具链预编译为静态库。
:::

随后，OpenCL 内核由解析脚本进行分析，该脚本执行必要的代码转换，将其转换为具有等效功能的标准 C 函数。然后，可以使用 RISC-V GNU 工具链编译该 C 函数以生成相应的目标文件。这些转换实现了与现有编译工具的无缝集成，消除了对专用编译器的需求。内核经过处理和编译后，会与 Tiny-OpenCL 静态库链接以生成最终的二进制文件。

在内核地址空间中，为内核参数保留了一个内存区域，这些参数由主机在执行前写入。这些参数包括执行参数（如全局大小和本地大小）、输入和输出缓冲区的指针以及其他配置细节。

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/06.webp)

为了增强灵活性，该框架允许用户自定义表 II 中列出的参数。其中包括内核的基地址（作为 e-GPU 的启动地址，使内核能够在系统内的任何地址偏移处执行）。线程栈的位置和大小也可以配置，以确保根据目标应用的特定需求进行适当的映射和大小调整。

### B. Tiny-OpenCL 执行

> 如第 VI-C 节所述，当在主机上运行的 OpenCL 运行时启动 e-GPU 加速后，内核执行开始并经历三个阶段：启动、调度和处理。

- 在**启动阶段，每个计算单元以单线程模式执行**，即只有一个线程和一个 warp 处于活动状态。在此阶段，执行启动函数以初始化系统。这包括激活所有并行线程和并发 warp，以及设置资源（如每个线程和 warp 的栈指针）。初始化完成后，计算单元返回单线程模式，调度阶段开始。
- 在**调度阶段**，调用调度函数。这些函数从内核参数区域读取全局大小和本地大小，以确定工作组的数量和每个组中的工作项数量。这些值与从控制和状态寄存器（CSR）中检索到的硬件资源信息（计算单元、线程和 warp）相结合。基于这些数据，调度函数激活必要的资源，并在可用线程之间分配工作项，以最大限度地提高并行性并最小化执行时间。此外，它们会停用未使用的资源以降低功耗并提高整体能效。
- 一旦工作项在 threads 上启动，**处理阶段** 就开始了。在此阶段，用户定义的内核执行目标算法。从内核参数区域获取输入和输出参数，工作项根据其全局 ID（可以表示为一维或二维索引）计算其特定的数据部分。由于调度函数预先执行了边界检查，用户内核无需处理此类逻辑。

## 六、APU 系统

> 本节将介绍如何将 e-GPU 与主机集成，以实现面向 TinyAI 应用的加速处理单元（APU）。本节**首先详细说明 e-GPU 的接口，然后介绍所选主机系统及其配置。最后，将介绍专门开发的轻量级主机端 Tiny-OpenCL 运行时**，以克服资源受限设备固有的编程限制。

### A. e-GPU 接口

e-GPU 暴露以下端口：

1. 用于配置的从 OBI（开放总线接口协议）端口；
2. 用于从主机主存读写内核指令和数据的主 OBI 端口；
3. 连接到主机中断控制器的中断线，用于在核执行完成时通知 CPU。

**e-GPU 在专用电源域内运行，支持细粒度电源管理**。时钟门控（一种在短暂空闲时关闭时钟以降低功耗的技术）可减少短暂空闲期间的功耗，而电源门控（一种在长时间不活动时完全关闭加速器电源的技术）则可在长时间不活动期间完全关闭加速器。这些机制的控制信号连接到主机电源管理器，确保高效、自主的能源管理。

### B. 主机配置

X-HEEP 系统[11], [25], [26]被选为平台主机，因其具有可配置和可扩展的架构，便于加速器集成。所选配置包括：

::: block-1
1. 轻量级 CPU[27]，优化用于执行控制任务，同时将计算密集型任务卸载到加速器，确保低功耗；
2. 两个 32 KiB 的 SRAM bank，配置为连续寻址模式（即内存地址连续排列的模式），支持 CPU 和加速器的独立内存分配，减少访问冲突；
3. 全连接交叉开关（一种用于连接多个输入和输出的高速数据传输结构），提供高带宽数据传输能力；
4. 中断控制器，用于管理内部和外部中断；
5. 电源控制器，负责管理内部和外部节能策略，包括时钟门控和电源门控；（6）调试单元，通过 JTAG（联合测试行动小组，一种用于芯片测试和调试的标准接口）实现对整个系统的完全控制；
6. 可扩展加速器接口（XAIF），配置有一个 OBI 主端口、一个 OBI 从端口和一个中断接口，用于连接 e-GPU 的相应端口。
:::

### C. Tiny-OpenCL 运行时

标准开源 OpenCL 实现（如 PoCL[4]）要求主机能够运行操作系统以支持其运行时，该运行时与加速器交互并控制加速器。然而，X-HEEP 是一款 RISC-V 微控制器，缺乏运行 Linux 等操作系统所需的 ISA 支持。相反，它依赖于 Newlib[28]——一个为边缘系统优化的开源 C 标准库，该库提供全套基本函数，包括 I/O、内存和字符串工具，通常在没有带文件系统和多线程支持的完整操作系统时使用。

由于没有文件系统，主机应用程序必须编译为单个二进制文件，消除了动态库链接的需求。同样，由于缺乏多线程，主机应用程序必须在单线程中执行。

为克服这些限制，第 V 节介绍的 **Tiny-OpenCL 框架扩展了一个专门为 X-HEEP 等支持 Newlib 的微控制器设计的运行时**。该运行时:mdnice-bold-italic[使用标准 GNU RISC-V 工具链编译，实现了标准 OpenCL 运行时 API 的一个子集]。这些函数提供从主机对 e-GPU 的完全控制，包括数据缓冲区初始化、核参数配置、核调度以及通过等待操作完成实现的同步。

本节介绍用于**实验的 e-GPU 配置**。然后介绍所采用的基准测试，这些基准测试旨在展示所提出平台对具有代表性的 TinyAI 应用领域（生物信号处理）严格要求的适应性。随后，**详细说明系统的实现方式，并描述用于提取性能、功耗和面积指标的方法。**

### A. e-GPU 配置

> 所选配置汇总于表 III。

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/07.webp)

**每个实例包括两个计算单元和数量递增的并行线程（每个计算单元从 2 个到 8 个不等）**。这种设置:mdnice-bold-italic[在提供足够的核执行性能的同时，保持了面积和功耗之间的平衡]。为隐藏内存访问延迟，每个计算单元配备 4 个并发线程束（一组同时执行的线程）。鉴于共享数据缓存的访问延迟为 4 个周期，这种配置允许缓存流水线填充 4 个未完成请求，从而实现每个周期一次访问的最大吞吐量。

:mdnice-bold-italic[指令缓存采用单 bank 配置。这种安排在面积和功耗方面具有效率，有助于提高整体能源效率。] 16 B（4 条指令）的行大小最大化了空间局部性，并增强了内核代码的预取，而 4 KiB 的总指令缓存大小（每个计算单元 2 KiB）确保我们基准测试中的每个内核都能适配。

**共享数据缓存采用多 bank 配置，具有行交错寻址方式**。它包含两个 bank（每个计算单元一个），以最大化并行访问效率。行大小设置为 T×4 B，其中 T 表示每个计算单元的并行线程数。这种设计允许所有线程在访问连续内存位置时同时读取数据，因为单次缓存行读取就足够了。最后，提供 16 KiB 的总数据缓存大小，以容纳所需的内核数据，从而最小化缓存与主机主存之间的流量。

### B. 基准测试

采用了两个基准测试：通用矩阵乘法（GeMM）和微型生物信号（TinyBio）工作负载。GeMM 基准测试包括大小递增（从 32×32 到 256×256）的通用矩阵乘法核。相比之下，TinyBio 领域包括用于分析从人体获取的生物信号并提取有意义特征的核[29], [30]。其中，我们选择 MBio-Tracker 应用[31]，该应用专门开发用于测量认知负荷。该应用具有四个阶段的流水线：预处理、 delineation（信号特征提取，如峰值和谷值识别）、特征提取和预测。这些异构核包含各种具有不同复杂度和内存需求的算法，使其成为我们实验的合适选择。

在预处理阶段，对原始输入数据应用有限脉冲响应（FIR）滤波器。在 delineation 阶段，识别滤波信号的峰值和谷值，以确定吸气和呼气时间。然后，使用提取的值计算时域特征（如均值、中位数和均方根（RMS）），而频域特征则通过对滤波信号执行斯托克姆快速傅里叶变换（FFT）获得。最后，使用支持向量机（SVM）算法估计认知负荷。

### C. 方法学

每个系统都采用台积电 16 纳米 FinFET SVT CMOS 工艺进行综合，工作在 300 MHz 和 0.8 V 下。进行综合后仿真以提取用于功耗分析的开关活动。这些数据随后用于估算能耗。

### A. 静态表征

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/08.webp)

> 图 2 展示了所分析系统的面积分解情况。

e-GPU 系统的总面积在(0.24 ~mm^2)到(0.38 ~mm^2)之间。这些**结果表明，所提出的系统适合部署在微型人工智能（TinyAI）应用** 中，因为目标设备的小尺寸对面积有严格限制，整个片上系统（SoC，指将处理器、内存等组件集成在一块芯片上的系统）通常仅限几平方毫米。

此外，**与独立的主机系统（面积为(0.15 ~mm^2)）相比，e-GPU 仅带来 1.6 倍到 2.5 倍的面积开销**，而在运行 TinyBio 基准测试时，如图 4 所示，可提供高达 3.6 倍到 15.1 倍的加速比。

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/09.webp)

从总面积的构成来看，指令缓存在所有 e-GPU 配置中保持不变。这一现象符合预期，因为当增加线程数量和性能时，指令缓存不会被修改或扩展。

相比之下，:mdnice-bold-italic[尽管数据缓存的总容量在不同配置间保持不变，但其面积略有增加。这种增加源于为了在更高并行度（即更多线程数量）下最大化内存访问带宽而对内存层次结构进行的调整]。具体来说，需要更多的缓存端口（每个线程一个端口）和更大的缓存行（每个线程一个字）。更大的行大小通过增加 bank 数量来实现：4 线程 e-GPU 为 2 个 bank，8 线程版本为 4 个 bank，16 线程版本为 8 个 bank。**与具有相同总大小的单个 bank 相比，拆分为多个子 bank 的面积效率更低。**

最后，计算单元的面积显著增长，并且随着性能配置的提升，其占比几乎翻倍。这种增长反映出需要集成额外的资源，如更多的算术单元、更大的寄存器文件和扩展的控制逻辑，以有效支持更多的并行线程。

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/08.webp)

**在分析泄漏功率时也观察到类似趋势，如图 2 所示**。e-GPU 系统的泄漏功率在 130.13 µW 到 305.32 µW 之间，与独立主机系统（消耗 29.50 µW）相比，开销为 4.4 倍到 10.3 倍。这进一步**证实了所提出的设计适合微型人工智能应用**，因为电池供电设备必须遵守严格的功率预算，通常在几十毫瓦量级。

> 总体而言，**面积和泄漏分析一致表明，最显著的变化集中在计算单元内，而缓存除了数据缓存的适度调整外相对稳定**。这些结果突出了所提出的 e-GPU 架构的**可扩展性**，证实了其在严格的微型人工智能部署约束下，能够有效地权衡面积和泄漏开销以获得显著性能提升的能力，如图 4 所示。

### B. 开销表征

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/10.webp)

> 图 3 展示了在选定的 e-GPU 系统上执行不同大小的矩阵乘法时，开销与计算时间的分解情况。考虑两种类型的开销：传输开销和调度开销。

#### 开销类型1：传输开销

**传输开销指的是将内核数据填充到数据缓存所花费的时间**。这发生在:mdnice-bold-italic[内核执行之前，数据从主机内存移动到 e-GPU 缓存，带宽为 32 位/周期]。假设缓存足够大以容纳整个工作集，传输的数据在后续内核执行期间将保持驻留，从而提高性能和能效。对于高范围 e-GPU 系统，这种传输延迟随着矩阵大小的增加而增加，从约 27 µs 到 1.7 ms，因为需要传输的数据越来越多。

在固定矩阵大小下，使用:mdnice-bold-italic[更多并行线程来提高性能会导致传输时间略有减少。这一效果可归因于更大的缓存行，使得每次读取缺失时可以将更多数据预取到数据缓存中]。因此，计算和数据传输之间的重叠增加，减少了仅用于数据移动的时间占比。

> 总体而言，随着矩阵大小的增加，传输开销稳定在略高于执行时间的 20%，因为传输时间的增加被由于性能逐步提高而减少的计算延迟所补偿。

#### 开销类型2：调度开销

**与传输开销互补的是调度开销，它指的是分配计算资源并将工作项分配给这些资源所需的时间**。e-GPU 依赖于第 V 节中描述的 Tiny-OpenCL 框架提供的运行时调度。:mdnice-bold-italic[随着工作项数量的增加，这种开销变得更加明显，因为需要对可用资源进行更多次迭代。]

在我们的实验中，我们对矩阵乘法内核进行了配置，:mdnice-bold-italic[使得工作项的数量与可用线程的数量（计算单元 × 并发线程束 × 并行线程）相匹配]。这种方法优化了调度时间并提高了整体内核性能。因此，**无论系统性能或矩阵大小如何增加，调度时间都保持在约 25 µs。**

> 然而，随着问题规模的增加，其在总执行时间中的相对占比从约 15%下降到 1%以下。这证明了**所提出的 Tiny-OpenCL 框架的可行性**，该框架提供了高度的灵活性和改进的可编程性，并且对于大于 256×256 的矩阵大小（或等效问题规模），其调度开销可忽略不计。

### C. TinyBio 基准测试表征

![文章插图](/articles/2025-08-21-tinyai-risc-v-gpu-e-643c7085/images/09.webp)

> 图 4 展示了在分析的 e-GPU 系统上执行第 VII-B 节中描述的 TinyBio 基准测试的每个内核时，相对于基准主机系统所获得的加速比和能量减少量。

- 在**预处理阶段**，执行 FIR 滤波器（一种常见的数字滤波器，用于信号处理）。该:mdnice-bold-italic[算法具有高度的可并行性，因为每个输出样本可以独立计算，允许多个线程同时处理不同的样本]。计算涉及固定数量的乘加操作，这些操作可以有效地映射到 e-GPU 的处理单元。此外，FIR 滤波器具有规则和顺序的内存访问模式，增强了局部性并实现了高效的合并内存访问，从而最小化延迟并最大化带宽利用率。

由于这些有利特性，e-GPU 系统相对于主机系统实现了 **3.6 倍到 15.1 倍的加速比，能耗减少了 1.7 倍到 3.1 倍。**

- 相比之下， **delineation 阶段** 的特点是:mdnice-bold-italic[使用控制密集型算法来检测局部最大值和最小值。这种工作负载仅部分可并行化，无法充分利用 e-GPU 的能力]。此外，GPU 并非为控制主导的代码（涉及频繁分支）而优化，在这种情况下，发散的执行路径通过线程掩码进行序列化，从而降低并行效率。

尽管存在这些限制，e-GPU 系统相对于主机仍**实现了 3.1 倍到 13.1 倍的加速比，以及 1.5 倍到 2.7 倍的能耗减少。**

- 在**特征提取阶段**，执行 Stockham FFT 算法（一种快速傅里叶变换算法）。与传统的 Cooley-Tukey FFT 不同，Stockham FFT 通过在每个阶段重新排序数据，消除了对单独位反转置换的需求。它:mdnice-bold-italic[采用双缓冲（乒乓）方案，在两个数组之间交替存储中间结果]。在其(\log_2(N))个阶段中的每个阶段，它执行独立的蝶形操作，具有规则和顺序的内存访问，使其特别适合并行架构。在计算结束时，输出数据已经处于正确的顺序，无需显式的最终置换步骤。

然而，该阶段的主要限制是连续阶段之间需要同步，这减少了可用的并行性并限制了整体性能。尽管如此，e-GPU 系统仍实现了 **3.3 倍到 14.0 倍的加速比，以及 1.6 倍到 2.9 倍的能耗减少。**

> 总体而言，考虑整个应用，e-GPU 系统在处理阶段实现了 3.4 倍到 14.3 倍的整体性能提升，以及 1.6 倍到 2.9 倍的能耗减少。

### D. 整体讨论

所评估系统的特性突出了在设计或选择微型人工智能应用平台时必须考虑的关键权衡。

基准主机系统复杂度最低，非常适合计算需求适中且资源约束严格的场景。其轻量级设计确保了最小的面积和功耗，这对于能量供应严重受限的应用（如电池供电的边缘设备）至关重要。:mdnice-bold-italic[然而，这些优势是以计算能力为代价的。主机 CPU 难以有效处理更密集的微型人工智能工作负载，导致执行时间延长，进而导致更高的整体能耗]。随着微型人工智能应用越来越需要更强的处理能力来支持更复杂的模型和数据分析，基准主机 CPU 在这类用例中变得不太适用。

**相比之下，与主机系统相比，e-GPU 系统在面积和泄漏方面引入了适度的开销**。然而，这些额外成本被性能和能效的显著提升所抵消。**e-GPU 提供 3.6 倍到 15.1 倍的加速比，并实现 1.7 倍到 3.1 倍的节能**。这些改进对于涉及密集数据处理但仍必须在严格的面积和功率预算内运行的微型人工智能应用特别有价值。尽管控制密集型工作负载对于 e-GPU 仍然更具挑战性（由于单指令多线程架构在处理发散分支时的固有低效性），但系统处理这类情况的效果足以维持性能和能效。

> 总体而言，e-GPU 系统成为微型人工智能应用的高效且多功能的解决方案。其架构成功地平衡了计算吞吐量、能效和灵活性，解决了资源受限环境中的关键挑战。通过在保持适度面积和功率占用的同时显著提高性能和降低能耗，e-GPU 满足了现代微型人工智能工作负载的严格要求。

## 九、结论

对基于机器学习的实时计算的需求不断增长，加速了边缘计算的采用。通过在本地处理数据而不是依赖云服务器，边缘计算减少了延迟、增强了隐私性并提高了能效，使其成为众多边缘应用的理想解决方案。然而，**这些工作负载对计算性能、实时响应性和功耗施加了限制，需要专门的硬件架构[1]。**

在可用的加速器中，图形处理器（GPU）在利用机器学习和信号处理任务的数据并行性方面具有巨大潜力。然而，它们在微型人工智能设备中的权衡在很大程度上尚未被探索。

为了应对这些挑战，本研究引入了 e-GPU，这是一种专为微型人工智能应用设计的开源且可配置的 RISC-V GPU 平台。其广泛的可配置性支持细粒度的面积和功率优化，而:mdnice-bold-italic[专用的 Tiny-OpenCL 框架提供了为资源受限环境量身定制的轻量级且灵活的编程模型。]

::: block-1
e-GPU 与 X-HEEP 主机[10]集成，以实现为微型人工智能应用优化的加速处理单元（APU）。所提出的系统的多个实例（具有不同的 e-GPU 配置）采用台积电 16 nm SVT CMOS 工艺实现，并在 300 MHz 和 0.8 V 下运行。

通过分析了它们的面积和泄漏特性，以确保符合微型人工智能的约束。为了评估运行时开销和应用级效率，我们采用了两个基准测试：通用矩阵乘法（GeMM）和生物信号处理（TinyBio）工作负载。**GeMM 基准测试用于量化 Tiny-OpenCL 框架引入的调度开销。结果表明：**

- 对于大于 256×256 的矩阵大小（或等效问题规模），延迟可忽略不计。TinyBio 基准测试则用于评估相对于基准主机的性能和能量改进。
- 高范围 e-GPU 配置实现了高达 15.1 倍的加速比，并将能耗降低了高达 3.1 倍，同时仅带来 2.5 倍的面积开销，且在 28 mW 的功率预算内运行。
:::

通过提供具有竞争力的**面积、功率和可编程性的开源且高度可配置的 GPU 平台**，本研究为微型人工智能应用的 GPU 平台进一步研究奠定了基础，为边缘的灵活和能效计算开辟了新的机会。
