关键词：**CUDA 基准测试**、阻塞内核、L2 缓存刷新、统计收敛准则、参数轴扫描

> 如果你曾经认真给一个 CUDA Kernel 计过时，大概率会撞上同一堵墙：第一次跑很慢、第二次飞快，重复十次能给出十个差异 20% 的数字；换一台机器、换一个驱动版本，结果完全对不上。

## 一、快速上手与使用

> NVBench 是一个 CMake 风格的 C++17 头文件 + 静态/动态库的项目，最快验证它的方式是把 examples 跑起来：

```
git clone https://github.com/NVIDIA/nvbench.git && cd nvbenchmkdir -p build && cd build# 把 70 换成你 GPU 实际的 compute capability，如 Ampere=80、Hopper=90cmake -DNVBench_ENABLE_EXAMPLES=ON -DCMAKE_CUDA_ARCHITECTURES=80 .. && make -j./bin/nvbench.example.cpp17.throughput
```

环境要求最低 CMake ≥ 3.30.4、CUDA Toolkit ≥ 12.0、g++ 7–14 或 clang++ 14–19，详细的兼容矩阵参考 README.md[2]。

一个最小的 benchmark 文件只需要三行有效代码：

```
// 来源：docs/benchmarks.md（最小示例）void my_benchmark(nvbench::state& state) {  state.exec([](nvbench::launch& launch "") {    my_kernel<<<num_blocks, 256, 0, launch.get_stream()>>>();  });}NVBENCH_BENCH(my_benchmark);
```

链接 `nvbench::main` 就能得到一个带 `--help`、`--list`、`--csv`、`--json` 等完整 CLI 的可执行文件，参数轴语法、设备选择、输出格式等细节可以参考 docs/cli_help.md[3]。如果不想从头集成，官方推荐去 fork nvbench_demo[4] 模板项目。Python 用户可以直接 `pip install cuda-bench[cu12]`，对应实现在 python/[5] 子目录。

## 二、架构总览与设计哲学

### 2.1 一次 `state.exec` 背后发生了什么

> NVBench 的整个运行链路可以画成这样一张图：

```
NVBENCH_BENCH(fn) ─► benchmark_manager（全局注册表）                              │                       option_parser 解析 CLI                              │                       benchmark_base::run()                              │                       runner<BenchmarkType>::run()                              │                       state_generator 笛卡尔积展开                              │                  for each (device, type_config, axis_values):                       kernel_generator(state) ──► state.exec(launcher)                                                       │                                  ┌────────────────────┼─────────────────────┐                                  │                    │                     │                          measure_cold              measure_hot         measure_cpu_only                          （冷启动+收敛）           （批量摊销）         （CPU only）
```

注册靠的是 `NVBENCH_BENCH` 宏，它本质是一段在全局静态区构造对象的代码：

```
// 来源：nvbench/create.cuh#define NVBENCH_BENCH(KernelGenerator)                                            \  NVBENCH_DEFINE_UNIQUE_CALLABLE(KernelGenerator);                                \  nvbench::benchmark_base &NVBENCH_UNIQUE_IDENTIFIER(obj_##KernelGenerator) =     \    nvbench::benchmark_manager::get()                                             \      .add(std::make_unique<                                                      \           nvbench::benchmark<NVBENCH_UNIQUE_IDENTIFIER(KernelGenerator)>>())     \      .set_name(#KernelGenerator)
```

这种"用宏触发静态对象构造把自己塞进全局表"的手法在 Google Test、Catch2 里也很常见，但 NVBench 把它和 C++17 的模板 NTTP（非类型模板参数）结合得很紧：`benchmark<KernelGenerator>` 本身是个模板类，把用户函数的类型（而不是函数指针）作为类型参数，从而让编译器有机会内联用户的整个 launcher——这对一个频繁调用、单次只有几微秒的测量循环至关重要。

### 2.2 三个核心抽象：state、launch、kernel_generator

> 整个 API 表面只有三类对象：

- **`nvbench::state`：** 见 `nvbench/state.cuh`[6]。一个 state 对应"一组确定的轴取值 × 一个 device"，承载所有 setter/getter，例如 `get_int64("NumInputs")`、`add_global_memory_reads<T>(n)`、`skip("reason")`、`set_timeout(...)`。
- **`nvbench::launch`：** 见 `nvbench/launch.cuh`[7]，只是个 stream 的轻量包装，传递给用户 lambda。
- **`KernelGenerator` / `KernelLauncher`：** 用户写的两层 callable。Generator 负责分配数据、声明吞吐；Launcher 是真正在循环里被反复调用的那一段。

::: block-1
二者的分工非常关键：内存分配、kthrust::device_vector 构造这类"昂贵但只需做一次"的事必须留在 Generator 里；而 Launcher 必须瘦到只剩 `kernel<<<...>>>` 一行，因为它会被执行成百上千次。
:::

### 2.3 模板元编程到底解决了什么

> NVBench 大量使用 `nvbench::type_list<...>` 与 `nvbench::tl::foreach<>` 来在编译期展开"类型轴的笛卡尔积"。例如下面这种最常见的用法：

```
// 来源：docs/benchmarks.mdusing input_types  = nvbench::type_list<char, int, unsigned int>;using output_types = nvbench::type_list<float, double>;NVBENCH_BENCH_TYPES(benchmark, NVBENCH_TYPE_AXES(input_types, output_types))  .set_type_axes_names({"InputType", "OutputType"})  .add_int64_power_of_two_axis("NumInputs", nvbench::range(10, 30, 10))  .add_float64_axis("Quality", {0.5, 1.0});
```

底层在 `nvbench/runner.cuh`[8] 用一段 `nvbench::tl::foreach` 静态展开为 N 个不同的模板实例，每个实例都让编译器看到完整的模板参数——这意味着用户的 `__global__` 函数可以是模板，而无须运行时的虚函数派发。

代价就是 README 里所说的"组合爆炸"：4×4×4×3×5 = 960 个配置、192 次模板实例化。NVBench 没有去回避这个问题，而是给了你 `state.skip("...")` 和"运行时轴重定义"两把剪刀让你自己裁。

## 三、计时的核心难题与 `blocking_kernel` 解法

### 3.1 `cudaEventRecord` 凭什么不准

> CUDA 的事件机制是异步的：当你在 host 端调用 `cudaEventRecord(start_event)` 时，它只是把"在 stream 当前位置插入一个时间戳"这件事推进了驱动队列，并立即返回。真实在 GPU 上记录时间戳的，是 GPU 端的 Copy Engine 或者 SM 在轮到这个事件时执行的。

问题在于：从 host 把 kernel 启动命令塞进驱动队列、再到驱动把这一批命令通过 PCIe 推给 GPU、再到 GPU 真正开始消费它们，这段"工作提交延迟"在不同负载下可以从几微秒跳到几十微秒。如果你的 kernel 本身只跑 30 μs，那么这个不可控的开销就足以把测量结果搞乱。

### 3.2 写一个故意死循环的"阻塞内核"

> **NVBench 用一个反直觉的方法来解决**：先在 stream 上塞一个永远空转的 kernel 把它"卡住"，然后从容地把整个测量序列（`start_event` → `my_kernel` → `stop_event`）全部 push 进队列，再让 host 端写一个 flag 通知阻塞内核退出。这样三个命令几乎在同一时刻被 GPU 看到，启动延迟被完全摊平。

实现就是一个用 `cudaHostRegister` 映射到设备地址空间的 flag，加一段 GPU 端的 busy-wait：

```
// 来源：nvbench/blocking_kernel.cu__global__ void block_stream(const volatile nvbench::int32_t *flag,                             volatile nvbench::int32_t *timeout_flag,                             nvbench::float64_t timeout){constauto start_point   = cuda::std::chrono::high_resolution_clock::now();constauto timeout_ns    = cuda::std::chrono::nanoseconds(                               static_cast<nvbench::int64_t>(timeout * 1e9));constauto timeout_point = start_point + timeout_ns;constbool use_timeout = timeout >= 0.;auto now               = cuda::std::chrono::high_resolution_clock::now();// GPU 端忙等：直到 host 把 flag 置 1，或超时while (!(*flag) && (!use_timeout || now < timeout_point)) {    now = cuda::std::chrono::high_resolution_clock::now();  }if (now >= timeout_point) {    *timeout_flag = 1;    __threadfence_system();   // 保证 host 能看到超时位    printf("...Possible Deadlock Detected...\n", timeout);  }}
```

host 侧用 `cudaHostRegister` + `cudaHostGetDevicePointer` 把同一块栈上的 int32 同时映射给 GPU，从而做到零拷贝置位：

```
// 来源：nvbench/blocking_kernel.cublocking_kernel::blocking_kernel(){  NVBENCH_CUDA_CALL(cudaHostRegister(&m_host_flag, sizeof(m_host_flag),                                     cudaHostRegisterMapped));  NVBENCH_CUDA_CALL(cudaHostGetDevicePointer(&m_device_flag, &m_host_flag, 0));  // ... 同理注册 timeout_flag}void blocking_kernel::block(const nvbench::cuda_stream &stream,                            nvbench::float64_t timeout) {  m_host_flag = 0;  m_host_timeout_flag = 0;  block_stream<<<1, 1, 0, stream>>>(m_device_flag, m_device_timeout_flag, timeout);}
```

`unblock()` 只需要把那个 volatile int 写成 1，GPU 上的 while 循环立即跳出，整个测量片段瞬间被释放执行。

### 3.3 这个技巧的"危险等级"

> 阻塞内核违反了 CUDA 编程模型的一条潜规则——"不要让 device 等 host"。它带来三个非常锋利的坑，源码注释里写得毫不掩饰：

- 排队的 kernel 不能太多。每个 driver/device 对未启动的命令队列长度有上限，溢出后整个 stream 会僵死。NVBench 自己在 `measure_hot.cuh` 里把"被阻塞期间允许压入的 launch 数"硬编码为 `std::min(batch_size, 2)`：// 来源：nvbench/detail/measure_hot.cuhconstauto blocked_launches = std::min(batch_size, nvbench::int64_t{2});constauto unblocked_launches = batch_size - blocked_launches;cleanup.block_stream();m_cuda_timer.start(m_launch.get_stream());for (nvbench::int64_t i = 0; i < blocked_launches; ++i) this->launch_kernel();cleanup.unblock(); // 释放，让 GPU 开始消费for (nvbench::int64_t i = 0; i < unblocked_launches; ++i) this->launch_kernel();
- 用户 launcher 自己调用 `cudaDeviceSynchronize` 会立刻造成 host ↔ device 互等死锁。NVBench 给的对策是要求显式打 `nvbench::exec_tag::sync` 标签，否则会被 30 秒超时器抓到并抛 `runtime_error`。
- 性能分析工具（Nsight）启动时，这个 trick 会干扰其捕获。所以 CLI 提供了 `--profile` 开关一键禁用阻塞内核并只跑一次。

这是个非常体现工程取舍美学的地方：明知道这条路充满地雷，但只要把雷的位置画得足够清楚，就比"放弃使用、容忍噪声"要好得多。

## 四、两条测量轨：Cold vs Hot

### 4.1 Cold——单次干净 L2 + 在线统计收敛

`measure_cold` 是默认模式，对应论文里"single-shot, cache-cleared timing"。它的执行流程在 `measure_cold.cuh`[9] 一目了然：

```
// 来源：nvbench/detail/measure_cold.cuhvoid operator()() {this->check();this->initialize();this->run_warmup();         // 至少一次 JIT 与 driver 加载this->run_trials_prologue();this->run_trials();         // 收敛前持续采样this->run_trials_epilogue();this->generate_summaries();}void run_trials() {constbool disable_blocking_kernel = m_run_once || m_disable_blocking_kernel;kernel_launch_timer timer(*this, disable_blocking_kernel);do {    this->launch_kernel(timer);      // 每次启动前都会 flush L2    this->record_measurements();  } while (!this->is_finished());    // 让 stopping_criterion 决定何时停}
```

每一次"sample"开始之前都要把 GPU 的 L2 缓存污染掉，否则 kernel 第二次跑时会因为命中缓存而失真。NVBench 实现的方法非常朴素——根据设备属性查到 L2 大小，分配一段一样大的全局内存，每次测量前 `cudaMemsetAsync` 写零：

```
// 来源：nvbench/detail/l2flush.cuh__forceinline__ l2flush(){int dev_id{};  NVBENCH_CUDA_CALL(cudaGetDevice(&dev_id));  NVBENCH_CUDA_CALL(cudaDeviceGetAttribute(&m_l2_size, cudaDevAttrL2CacheSize, dev_id));if (m_l2_size > 0) {    void *buffer = m_l2_buffer;    NVBENCH_CUDA_CALL(cudaMalloc(&buffer, static_cast<std::size_t>(m_l2_size)));    m_l2_buffer = reinterpret_cast<int *>(buffer);  }}__forceinline__ void flush(cudaStream_t stream) {if (m_l2_size > 0) {    NVBENCH_CUDA_CALL(      cudaMemsetAsync(m_l2_buffer, 0, static_cast<std::size_t>(m_l2_size), stream));  }}
```

效果是每个 sample 都模拟"刚开机第一次跑"的冷状态，复测之间的方差因此被压到极低。

### 4.2 Hot——批量摊销时间

`measure_hot` 走的是另一条路：连续把 kernel 排队执行 N 次，只测一次总时间，再除以 N 得平均。它适合那种确实需要"流水线打满"语境下的指标。关键在于它会根据 warmup 的耗时动态预估 batch size：

```
// 来源：nvbench/detail/measure_hot.cuhvoid run_trials() {  m_walltime_timer.start();// warmup 给出的时间 × 0.95，留一点冗余应对噪声constauto time_estimate = m_cuda_timer.get_duration() * 0.95;auto batch_size = static_cast<nvbench::int64_t>(m_min_time / time_estimate);do {    batch_size = std::max(batch_size, nvbench::int64_t{1});    // ...（前面 3.3 中已展示阻塞内核 + 批量 launch 部分）    m_cuda_timer.stop(m_launch.get_stream());    this->sync_stream();    m_total_cuda_time += m_cuda_timer.get_duration();    m_total_samples   += batch_size;    // 用已观察到的均值倒推还需要多少 iteration    batch_size = static_cast<nvbench::int64_t>(      (m_min_time - m_total_cuda_time) /      (m_total_cuda_time / static_cast<nvbench::float64_t>(m_total_samples)));    if (m_total_cuda_time > m_min_time && m_total_samples >= m_min_samples) break;    if (m_walltime_timer.get_duration() > m_timeout) {      m_max_time_exceeded = true; break;    }  } while (true);}
```

它体现了一种"自适应批"的思想：第一批先按估计跑，根据真实观察修正下一批大小，最少跑到 `m_min_time`（默认 0.5 秒）+ `m_min_samples` 就退出。

### 4.3 两条轨为什么必须共存

读者可能会问：为什么不只用 Cold？因为对"启动开销远大于计算时间"的小 kernel 而言，单次测得的几乎全是 launch latency，毫无参考价值；而 Hot 模式能把多次启动摊成一次，凸显稳态吞吐。反过来，对带 L2 副作用的 kernel，Hot 模式会因为缓存命中报出虚高数字。NVBench 默认两个都跑，让用户在 markdown 表里同时看到 `GPU Time` 和 `Batch GPU`，自行解释——这是它在文档中反复强调"NVBench 测的是 critical region，而不是端到端性能"的底层原因。

## 五、统计收敛：怎么知道"测够了"

### 5.1 默认的 `stdrel` 准则

`measure_cold` 的退出条件是一个抽象接口 `stopping_criterion_base`：

```
// 来源：nvbench/stopping_criterion.cuhclass stopping_criterion_base{public:void initialize(const criterion_params &params)  { m_params.set_from(params); this->do_initialize(); }void add_measurement(nvbench::float64_t m) { this->do_add_measurement(m); }bool is_finished()                         { returnthis->do_is_finished(); }protected:virtual void do_initialize() = 0;virtual void do_add_measurement(nvbench::float64_t) = 0;virtual bool do_is_finished() = 0;};
```

默认实现 `stdrel` 是"相对标准差"准则：累积所有样本的在线均值与方差（Welford 算法），当相对标准差降到 `max-noise`（默认 0.5%）以下，且总测量时间超过 `min-time`（默认 0.5 秒）时退出：

```
// 来源：nvbench/detail/stdrel_criterion.cxxstdrel_criterion::stdrel_criterion()    : stopping_criterion_base{"stdrel",                              {{"max-noise", 0.005},   // 0.5% stdrel                               {"min-time",  0.5}}}    // 0.5 seconds{}bool stdrel_criterion::do_is_finished() {// 太多无效噪声估计 → 直接放弃if (m_consecutive_invalid_noise_estimates >= invalid_noise_estimate_limit) returntrue;constauto total_measured_time = m_measurements_summary.get_mean() *        static_cast<nvbench::float64_t>(m_measurements_summary.get_size());if (total_measured_time <= m_params.get_float64("min-time")) returnfalse;if (m_noise_tracker.empty())                                  returnfalse;// 噪声跌破阈值，收敛if (m_noise_tracker.back() < m_params.get_float64("max-noise")) returntrue;// 否则看最近的窗口是否已"稳定地"高于阈值——避免在固有噪声大的 benchmark 上死等// （此处省略噪声稳定性窗口检测）returnfalse;}
```

这里有两点工程细节值得品味：

- 第一，方差用的是 unbiased 估计（带 Bessel 修正）以兼容历史结果；
- 第二，对于"本来就 inherent noisy"的 benchmark，它不会无限循环，却在相对方差"稳住"后认输——否则用户跑一个矩阵乘扫描可能要等几个小时才会触发超时。

### 5.2 进阶的 `entropy` 准则

> NVBench 还提供了一个基于"熵"的高级准则。直觉是：如果你的测量值是真随机噪声，那么它们落入不同 bin 的频率分布会越来越均匀（熵在增长）；当熵的增长曲线趋于平稳（线性回归的斜率近 0、R² 高），说明分布已经收敛，可以停了：

```
// 来源：nvbench/detail/entropy_criterion.cxxbool entropy_criterion::do_is_finished(){if (m_entropy_tracker.size() < 2) returnfalse;if (m_total_samples % 2 != 0)     returnfalse;const nvbench::float64_t slope = m_regression.slope();if (!std::isfinite(slope))        returnfalse;// 斜率换算成角度后 < max-angle（默认 0.048 弧度）才认为"平了"if (statistics::slope2deg(slope) > m_params.get_float64("max-angle")) returnfalse;const nvbench::float64_t r2 = m_regression.r_squared();if (!std::isfinite(r2))           returnfalse;if (r2 < m_params.get_float64("min-r2"))                              returnfalse;returntrue;}
```

为了让这套统计可以在线增量计算而不是"每来一个 sample 就重算一次"，源码里用了一个 ring buffer + 在线线性回归（`online_linear_regression.cuh`[10]），用 `slide_window(old, new)` 在窗口移动时 O(1) 更新 `Σx`、`Σy`、`Σxy`、`Σx²`、`Σy²` 几个累加量，再由此推出斜率与 R²。这比每一步重新扫描整个窗口快一个数量级，是支撑"长时间高频采样"的关键。

## 六、其他几个值得点名的工程细节

### 6.1 用 `nvbench::tl::foreach` 遍历类型组合

参数轴里类型轴是最特殊的：它必须在编译期展开。`runner::run_device` 里的核心循环是：

```
// 来源：nvbench/runner.cuhnvbench::tl::foreach<type_configs>(  [&self = *this, &states = m_benchmark.m_states,   &type_config_index, &device, &skip_remaining]  (auto type_config_wrapper) {    using type_config = typenamedecltype(type_config_wrapper)::type;    for (nvbench::state &cur_state : states) {      if (cur_state.get_device() == device &&          cur_state.get_type_config_index() == type_config_index) {        // 在这里编译期已知 type_config，可以触发模板实例化        auto kernel_generator_copy = self.m_kernel_generator;        kernel_generator_copy(cur_state, type_config{});      }    }    ++type_config_index;  });
```

`type_config` 是一个 type list 的"行"——例如 `(int, float)`。这一段编译后会被展开为 N 个分支，每个分支调用一个不同模板实例的 `kernel_generator`。

### 6.2 setup/teardown 与可见性

`nvbench::exec_tag::timer` 是 NVBench 给"需要每次重置输入"场景的解法。Launcher 多一个 `auto& timer` 参数，用户自己用 `timer.start()`/`timer.stop()` 划出真正想计时的区间——计时器内部会做好同步、L2 flush 等所有该做的事，把 reset 部分自然排除在外。

### 6.3 错误处理：`stop_runner_loop` 与 skip

当用户在某个 state 里抛 `nvbench::stop_runner_loop`（一个 `std::runtime_error` 子类），runner 不会让整个进程崩溃，而是把"后续所有 state 标记为 skip"，并继续把 skip 信息写到输出：

```
// 来源：nvbench/runner.cuhtry {if (skip_remaining) {    if (!cur_state.is_skipped())      cur_state.skip("Skipped because a previous state requested ...");  } else {    auto kernel_generator_copy = self.m_kernel_generator;    kernel_generator_copy(cur_state, type_config{});  }} catch (nvbench::stop_runner_loop &e) {  skip_remaining = true;  self.handle_sampling_exception(e, cur_state);} catch (std::exception &e) {  self.handle_sampling_exception(e, cur_state);}
```

这种"软失败"对长时间扫描特别友好：你不会因为一个 OOM 配置而丢掉前面跑了两小时的结果。

### 6.4 输出与可观察性

`json_printer.cu` 体积接近 21 KB，是项目里最大的非 CUPTI 文件之一。它的作用是把所有 state、device info、measurement、summary 序列化成机器可读的 JSON，供下游工具（如 CCCL 自己的 nvbench-viewer）做回归对比。同时 markdown printer 保证 `make test` 跑完后开发者眼睛就能看懂结果，体现"人类友好 + 机器友好双重输出"。

## 七、为什么 NVIDIA 不直接用 Google Benchmark

> 最后我们来回到那个看似讽刺的问题。Google Benchmark 是工业界 CPU 微基准事实标准，但它对 GPU 几乎一无所知：

1. **不会刷 L2** ——所有 GPU 测量会被缓存污染。
2. **不能消除 launch latency** ——它只在 host 端计时。
3. **不懂 SM 降频** ——长时间跑会因 GPU 自动调频得到 30% 的偏差。
4. **不知道 CUPTI** ——拿不到 DRAM 带宽、L1/L2 命中率这些金标指标。

NVBench 把这些 GPU 专属问题逐一拆解、用阻塞内核 + L2 flush + GPU frequency 检测 + 可选 CUPTI 来逐一解决，最后给出的是一个"专门为 CUDA Kernel 量身定做"的基准框架。这一点和它在 README 末尾自己讲的同样诚实：它**不替代** Nsight 那样的端到端 profiler，也**不优化** CPU 微秒级测量，它只是把"测一个 CUDA Kernel 的关键区段"这件事做到极致。

::: block-1
这种"窄而深"的工程取舍，恰恰是它能成为 Thrust、CUB、libcudacxx 等 CCCL 全家桶性能回归基石的真正原因。当你下次再看到 PR 描述里出现一张密密麻麻的 `Cold | Hot | BW%` 表格时，你已经能看穿它背后这套精巧的机器了。
:::
