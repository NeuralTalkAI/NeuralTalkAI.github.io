关键词：Test-Time Scaling、Large Language Models、System Perspective、Inference Optimization、Speculative Decoding、Latency and Cost Optimization

> 传统缩放定律指导 LLM 预训练时通过模型、数据和计算量优化性能，但随着 LLM 从预训练转向推理部署，其局限性凸显：**复杂推理任务性能提升有限，且推理成本成为核心瓶颈。**

为此，测试时扩展（TTS）兴起，通过 SFT、特定提示等技术**以低代价解锁 LLM 潜在推理能力**，但现有 TTS 仅聚焦性能与计算的帕累托前沿（多目标优化领域的核心概念，用于描述多个相互冲突的目标之间，“最优权衡关系” 的边界），却忽略了一个简单事实：**计算最优并不总能等同于系统最优。**

相关工作中，缩放定律侧重预训练优化，现有 TTS 未考虑延迟、每 token 成本等系统指标，且硬件异质性对缩放行为的影响被忽视。

## 关键问题

### 问题 1：现有 TTS 聚焦计算最优而忽视系统最优的核心症结与偏离根源

> 现有 TTS 聚焦计算最优而忽视系统最优的核心症结是什么？硬件异质性与推理任务特性（如长序列）如何共同导致计算-系统最优的偏离，且缺乏统一量化标准？

【核心症结】在于**现有 TTS 范式受传统缩放定律影响，将优化目标局限于性能（如准确率）与理论计算量（FLOPs、生成 token 数）的权衡，未纳入生产系统实际面临的资源约束维度**。硬件异质性通过内存层级、互联带宽、内核调度差异，使相同模型在不同平台呈现迥异缩放行为，而现有方法未考量这一变量。

**推理任务特性（如长序列推理）进一步加剧偏离**：此类任务:mdnice-bold-italic[瓶颈在序列处理效率而非批次吞吐量，与计算最优所依赖的“大批次并行”假设相悖]，导致计算最优方案在延迟、每 token 成本等系统指标上表现糟糕，且缺乏量化这些偏差的统一标准。

### 问题 2：张量并行性能未达预期与推理任务特性的深层关联

> 实验中 14B 模型张量并行仅达 1.7 倍延迟提升、1.5B 模型多 GPU 劣于单 GPU 的现象，除 intra-GPU 同步瓶颈外，是否与推理任务“长序列而非大批次”的本质特征存在更深层关联？

除 intra-GPU 同步瓶颈外，根源在于推理任务**“长序列而非大批次”的本质特征与张量并行的优化逻辑不匹配**。张量并行其**效率依赖于【高并行度】的【计算密集型】任务，而长序列推理的核心开销在于【序列内依赖】处理** （如注意力机制的长上下文计算），:mdnice-bold-italic[此类开销难以通过多 GPU 拆分有效分摊。]

![文章插图](/articles/2025-09-28-test-time-scaling-are-we-8dddf6ff/images/03.webp)

实验中 1.5B 模型多 GPU 性能劣于单 GPU、14B 模型仅 1.7 倍加速的结果，正是这一矛盾的直接体现——**多 GPU 引入的同步开销超过了并行计算带来的增益，暴露了张量并行对长序列推理任务的适配缺陷。**

### 问题 3：范式转移中的推测解码成本波动解决与硬件适配突破

> 推动 TTS 向“系统-性能”评估范式转移时，如何解决推测解码在 14B 模型上成本波动的问题？现有硬件（如 GH200）与优化策略的适配性瓶颈该如何突破以实现可复现的系统最优？

**推测解码在 14B 模型上的成本波动可通过优化推测模型稳定性缓解**：论文指出**波动源于推测模型无法保证每步正确 token 数量的随机性**，可通过结合任务特性（如数学推理的步骤规律性）设计专用预测器、动态调整推测 token 数（当前固定为 5）等方式降低不确定性。

硬件适配瓶颈突破需双管齐下：

- 一是针对 GH200 等硬件的内存 hierarchy 与互联特性，**【定制】张量并行的同步策略以【适配长序列】推理**；
- 二是优化 vLLM 等引擎对推理任务的支持，如**强化长序列场景下的内存管理与调度**，最终实现系统指标（延迟、成本）与性能的可复现最优平衡。

## 一、引言

基于 Transformer 架构的大型语言模型[41, 32]的普及，使得通用人工智能的前景愈发可期，将其从遥远的梦想转变为切实的追求目标。近年来，在模型架构[50, 40, 9]、训练技术[1, 36]和硬件基础设施[11, 30]同步发展的推动下，我们见证了 LLMs 在能力与可及性方面的显著提升。LLaMA[40, 39]、DeepSeek[9]、通义千问（Qwen）[46, 45]等强大的开源模型，使得最先进的语言建模技术得以普及，进而赋能了一系列广泛的应用场景，包括智能助手[2, 27]、代码生成[4]和推理智能体[29, 12]等。

> 推动这一快速发展的关键动力之一，是缩放定律（scaling laws）的发现与应用——该**定律通过实证表明，LLMs 的性能会随三个因素（模型规模、数据集大小和计算预算）呈可预测的幂律函数（power-law function）增长** [18, 14]。

:mdnice-bold-italic[这些定律为行业提供了至关重要的路线图：研究人员和工程师可在训练开始前预测性能提升效果，从而指导更大规模模型的设计[11, 50]。]

然而，随着 LLM 领域逐渐**从离线预训练转向在线推理**，这些**传统的缩放定律正暴露出其局限性。**

::: block-1
- :mdnice-bold-italic[首先，当前 LLM 的主流应用场景集中在复杂推理任务上] [33, 6, 20]——这类任务涉及多步骤问题求解与规划。尽管更大规模的模型在表层基准测试（如简单文本匹配、基础问答等不需要深度推理的任务）中表现出优异的记忆与泛化能力[24, 21, 16]，但在需要结构化推理的任务中，若缺乏任务特定的微调，其性能提升可能微乎其微[44, 38, 3]。
- :mdnice-bold-italic[其次，随着 LLMs 迅速从研究原型转变为生产系统，推理成本（而非训练成本）已成为长期发展的主要瓶颈]。大规模部署大型模型会产生巨大的计算、内存和能耗开销，在对延迟敏感的应用（如实时对话系统、在线智能客服等需快速响应的场景）中尤为明显[19, 53, 35]。**模型性能与推理实际成本之间的相互影响构成了关键的权衡关系，而这一关系恰恰超出了传统缩放定律的覆盖范围。**
:::

> 为应对这些现实约束，测试时缩放（test-time scaling，TTS）已成为一种新的极具潜力的方法[37, 15, 31]。与预训练阶段的缩放定律不同，**TTS 的核心是在推理过程中提升模型性能**。

这一范式涵盖了多种高效技术，例如**有监督微调** （supervised fine-tuning，SFT，指利用带标签的任务数据对模型进行微调的技术）[25]、**特定提示策略** （如思维链提示等引导模型生成推理步骤的方法）[42, 47]以及强化学习[10, 28]——:mdnice-bold-italic[这些技术仅需预训练成本的一小部分，就能激活 LLMs 的潜在推理能力]。

尽管前景广阔，但现有 TTS 范式仍局限于关注“性能-计算量”的帕累托前沿（即性能与计算量之间的最优权衡，其中计算量通常以浮点运算次数 FLOPs 或生成 token 数量衡量）。**这一局限忽略了生产系统的一个关键现实：计算最优并不等同于系统最优**。

- 一方面，以往研究表明，**加速 LLM 推理需要大量系统级优化**，例如高效内存管理（如分页注意力、KV 缓存优化等减少内存占用的技术）[19, 53, 35, 52]、快速 GPU 内核（指针对 GPU 硬件特性优化的计算核心程序，可提升计算效率）[26, 8, 7, 48]以及灵活的解码策略[23, 5]。:mdnice-bold-italic[一个真正的系统最优解决方案，理论上应在延迟、内存甚至能耗等更广泛的实际指标间实现平衡。]
- 此外，**“计算最优”的定义无法涵盖硬件异构性** （指不同计算设备在架构、性能上的差异，如不同型号 GPU、CPU 与 GPU 的差异等）的影响：由于内存层次结构（指计算机中不同速度、容量的内存层级，如寄存器、L1/L2 缓存、显存、内存等）、互联带宽（设备间数据传输速率）和内核级调度（操作系统对硬件计算核心的任务分配与调度）存在差异，:mdnice-bold-italic[同一模型在不同计算平台上可能表现出截然不同的缩放行为[17, 13]。]

> 在本研究中，我们提出从系统驱动的视角研究 TTS——即将关注焦点从理论计算量转向实际系统指标。

具体而言：

1. 我们**旨在探索推理模型在系统指标（即延迟和每 token 成本）下的缩放行为，并揭示现有 TTS 方法在系统层面考量的缺失**。

- 我们还将**评估张量并行、投机解码等主流优化策略如何助力实现更优的“面向系统的 TTS”**。

:mdnice-bold-italic[我们的目标是通过初步分析，更全面地理解 TTS 的真实性能]。最终，我们呼吁人工智能与系统领域的研究者在评估推理策略时实现范式转变：不再仅关注准确率，而是纳入智能推理的全面系统级成本（如延迟、内存、能耗等）进行考量。

## 二、 相关工作

### 缩放定律（Scaling Laws）

缩放定律最初作为神经网络的一种重要范式在文献[18]中提出，该文献指出，语言模型的性能（以测试损失衡量）会随着模型规模参数数量、数据集规模和训练计算量的增加，按可预测的幂律（power-law，一种数学关系，核心是变量间呈“某一变量的幂次”形式关联，例如常见的$y = kx^a$，其中$k$、$a$为常数）形式提升。

**其初步研究结果表明，扩大模型规模是实现性能提升的最关键因素**。随后，Chinchilla（一款大型语言模型）进行了更全面的分析，并得出结论：:mdnice-bold-italic[在给定计算预算（compute budget，指完成模型训练可投入的总计算资源量）的情况下，要实现最优性能，并非训练尽可能大的模型，而是应在规模相对较小的模型上使用显著更多的数据进行训练] [14]。

这些原则已成为大型语言模型（LLM）预训练的核心方法，指导了后续众多主流最先进模型的开发[50, 11, 22, 46]。

### 测试时缩放（Test-time Scaling, TTS）

由于大型语言模型在各类语言任务上表现出广泛的有效性，它们已成为许多主流应用“事实上的后端模型执行器”[27, 2]。**随着基于大型语言模型的实际应用需求不断增长，在推理阶段实现合理的缩放变得愈发重要**。

测试时缩放（TTS）方法旨在以相对较低的成本，提升大型语言模型在复杂推理任务（如数学推理[42, 25]）上的性能。其中包含：

- **思维链（chain-of-thought, CoT** [42]，一种提示策略，通过引导模型生成“逐步推理过程”而非直接输出答案，来提升复杂任务表现）:mdnice-bold-italic[旨在通过特定指令引导预训练大型语言模型生成更优答案]；
- 而 **S1 方法[25]则通过构建高质量数据集并采用有监督微调** （supervised fine-tuning, SFT，一种模型优化技术，利用标注好的任务数据对预训练模型进行进一步训练，使其适配特定任务）:mdnice-bold-italic[来实现更优的 TTS 缩放效果。]

然而，现有方法普遍关注实现“计算最优”，而非“系统最优”。

- **Kinetics 方法从稀疏注意力** （sparse attention，一种注意力计算优化技术，仅对输入序列中“关键位置”进行注意力计算，而非全序列，以此降低计算复杂度）**角度探索了 TTS 缩放**，:mdnice-bold-italic[但它所关注的系统指标仅限于“层延迟”] （per-layer latency，即模型单一层级的计算延迟）[34]。

> 本文则旨在从更全面的系统视角揭示 TTS 缩放规律。

### 大型语言模型系统（LLM Systems）

基于大型语言模型的应用激增，推动了众多旨在提升推理效率的系统级设计的发展。**系统层面的进展包括**：

::: block-1
- 内核级优化[8, 7, 48]（kernel-level optimizations，针对深度学习框架底层计算内核的优化，如优化 GPU 指令执行逻辑以提升计算速度）
- 高效内存管理[19, 53, 35, 52]（如分页注意力、KV 缓存等技术，减少内存占用并加速数据访问）
- 灵活的调度策略[49, 43, 51]（如任务优先级调度、负载均衡等，提升多请求场景下的系统吞吐量）
:::

其中，**开源的 vLLM** [19]（一款高效的大型语言模型服务框架）和 **SGLang** [53]（一种面向大型语言模型的结构化编程与服务框架）**已成为生产级系统后端的默认服务引擎**。:mdnice-bold-italic[然而，这些系统尚未充分理解“长序列推理”的工作负载特征]，指任务在计算、内存、数据传输等方面的需求模式。本文旨在迈出填补这一空白的第一步。

## 三、分析

### 3.1 实验设置

#### 模型与任务

我们选择两类主流推理模型进行初步分析，分别是 DeepSeek-R1-Distilled-Qwen[10, 46]和 S1.1[25]，并设置了三种模型规模配置：15 亿参数（1.5B）、70 亿参数（7B）和 140 亿参数（14B）。

- 我们使用 MATH500 数据集[20]（一个用于评估数学推理能力的数据集），并报告零样本准确率（zero-shot accuracy，指模型在“未见过该任务训练数据”的情况下，直接在测试集上的准确率）结果
- 同时将输出长度，即模型生成的文本序列包含的 token 数量设置为 1K 至 16K

#### 系统设置

我们使用包含 4 块 NVIDIA GH200-96GB GPU 的私有集群进行评估，并基于 vLLM v.0.7.3、PyTorch 2.6.0 和 CUDA 12.6 构建服务引擎。

**所有评估均使用 FlashAttention v.2.7.2** （一种高效的注意力计算库，通过优化内存访问模式提升注意力层计算速度）作为后端。在系统级指标方面，我们同时报告：

1. 每个请求的端到端平均延迟；
2. 每 token 成本，其计算方式为“**使用的 GPU 数量乘以延迟，再除以生成的总 token 数”。**

#### 优化策略

> 为研究现有优化方法对系统级 TTS 的影响，我们选择了两种主流方法：

1. **基于简单 n 元语法预测器模型的投机解码**。
2. **张量并行** （tensor parallelism，一种分布式计算策略：将模型的张量（如权重矩阵）分割到多个 GPU 上，每个 GPU 仅计算部分张量，从而降低单 GPU 内存压力并提升计算速度）[36]。

我们将投机 token 数量设为 5，最小和最大查找次数（lookup，指 n 元语法模型查询历史 token 以预测下一个 token 的次数）分别设为 1 和 4。

### 3.2 结果

![文章插图](/articles/2025-09-28-test-time-scaling-are-we-8dddf6ff/images/05.webp)

![文章插图](/articles/2025-09-28-test-time-scaling-are-we-8dddf6ff/images/03.webp)

> 图 1 和图 2 展示了初步结果。在延迟缩放方面（latency scaling），即指延迟与模型性能、规模之间的变化关系方面，我们得出三个关键结论：

- 首先，**随着推理过程耗时增加，准确率性能有所提升，但超过某个阈值后，性能提升会逐渐减弱并趋于平缓**。这与之前的“面向计算的缩放”形成对比——在面向计算的缩放中，准确率与生成的 token 数量呈线性关系。
- 其次，**即使使用简单的 n 元语法模型，投机解码在延迟方面也始终优于朴素贪心解码策略** （naive greedy decoding strategy，一种基础解码方法：每次都选择“概率最高的下一个 token”，计算简单但效率较低），这:mdnice-bold-italic[表明投机解码在大型模型上具有巨大的应用潜力。]
- 第三，**通过张量并行将推理“简单扩展”到更多 GPU 上，并不能带来成比例的性能提升**。例如，在 DeepSeek-R1-Distilled-Qwen 模型的案例中，14B 版本扩展到 4 块 GPU 时，延迟仅平均降低 1.7 倍；而对于 15 亿参数（1.5B）模型，:mdnice-bold-italic[多 GPU 的结果甚至比单 GPU 更差]。这种现象可能源于推理任务的工作负载特性——推理任务更关注“长序列”而非“大批量”（batch size，指一次同时处理的请求数量），:mdnice-bold-italic[这使得推理过程受限于 GPU 内部同步] （intra-GPU synchronization，指同一 GPU 内不同计算核心、模块之间的数据传输与协同过程，:mdnice-bold-italic[同步开销过大会抵消并行计算带来的增益]）。

> 在**每 token 成本分析方面**，结果揭示了两个【关键见解】：

- 首先，得益于延迟加速，**投机解码在降低 token 成本方面的表现优于张量并行**。然而，对于**规模更大的 14B 模型，其缩放行为比基准方法更不可预测**。这可能是由于:mdnice-bold-italic[投机模型的随机性——它无法保证每一步都生成相同数量的正确 token] （若候选 token 正确率波动大，会导致大模型验证/修正的开销不稳定，进而影响成本）。
- 其次，由于延迟性能较差，张量并行导致的 token 成本高于基准方法。这一结果印证了“计算最优不等于系统最优”这一事实。

## 四、结论与讨论

> 本文提出了一种“面向系统”的视角来研究测试时缩放（TTS）。我们的**核心见解是：计算最优并非天然等同于系统最优**，:mdnice-bold-italic[而在计算、内存和能源有限的实际部署场景中，系统最优往往更为重要]。我们的结果表明，**投机解码在面向系统的 TTS 中具有潜力，而张量并行则存在局限性。**

尽管本文仅展示了有限工作负载场景下的结果，但“**要达到真正的 TTS 帕累托前沿** （Pareto frontier，多目标优化中的核心概念：指不存在任何一个解能在“不损害至少一个其他目标”的前提下改进某个目标，所有这类“非劣解”构成的集合），**必须考虑整体系统级成本”这一核心启示，适用于不同的模型和硬件**。

通过倡导从传统的“准确率 vs 计算量”评估范式，转向“系统感知”的评估范式（即评估时需纳入延迟、成本等系统指标），本文旨在**为验证现有方法在实际场景中的实用性提供新视角**。这将鼓励研究人员在模型架构和推理策略上进行创新——不仅追求更高的准确率，还需兼顾资源效率，从而开发出一类“**针对低延迟和低成本优化** ”的新型大型语言模型。

> 最终，本文呼吁在 TTS 方法的开发中采用更成熟、更务实的方法，同时关注算法进展和相应的适配系统设计，即**算法创新需与系统优化同步推进，而非孤立发展。**
