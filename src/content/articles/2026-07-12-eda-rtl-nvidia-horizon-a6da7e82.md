## 一、行业痛点：大模型 RTL 自动化长期无法逾越的核心瓶颈

> 过去四年，全球学术界与头部企业围绕 LLM 生成 Verilog 开展大量优化工作，衍生出 RTLCoder、ChipNeMo、ScaleRTL 等多款领域微调专用模型。

但无论模型参数量、领域训练数据如何扩充，单轮生成模式始终存在无法根除的底层缺陷，无法适配真实芯片工程的开发逻辑。

### 1.1 单轮 LLM 生成 RTL 的先天缺陷

> 普通软件代码仅需要满足语法、逻辑功能正确，而 RTL 硬件描述语言存在独有的硬件约束，这些约束无法通过自然语言完整传递给大模型，也是单次生成方案失效的根本原因。

| 问题类别 | 具体描述 |
| --- | --- |
| **RTL 行为约束复杂** | RTL 具备位宽、时序、周期级行为约束；功能正确的 Verilog 必须严格匹配复位信号、握手协议、存储读写时序；大模型难以从文字描述中精准推断数据流位宽、FSM 跳转逻辑；即使语法无误，仿真仍易出现时序不匹配、数据错位等功能性 bug。 |
| **验证资产强耦合** | 硬件验证流程依赖测试激励、检查器、断言、覆盖率统计脚本等配套资产；完整芯片设计需多组件协同；单轮生成无法同步产出整套验证文件；孤立生成的模块无法通过仿真校验。 |
| **自然语言信息缺失** | 芯片需求文档常省略行业默认规范（如总线标准、时钟分频规则）；大模型仅基于有限文本推理，缺乏仿真反馈闭环；输出结果天然存在逻辑漏洞与隐含假设。 |

论文统计数据可以直观印证该缺陷：CVDP 基准中代码生成类任务首轮平均通过率仅 47.8%，其中代码补全、测试检查器生成两类最难任务首轮通过率分别低至 3.2%、3.8%，单轮模型完全无法覆盖工程级硬件设计需求。

### 1.2 现有迭代式 RTL Agent 的底层局限

> 行业内已经出现 AutoChip、RTLFixer、ACE-RTL 等带迭代修复能力的智能体工具，**这类工具搭建了“生成-编译-仿真-修复”简易反馈链路，但全部存在架构层面的短板，无法规模化落地全基准测试。**

| 问题描述 | 具体表现 |
| --- | --- |
| 无统一版本管理载体 | 所有工具仅针对单个 RTL 模块做临时文件读写；缺乏版本快照与修改差分记录；修复完成后无法回溯历史修改方案；多轮迭代产生的调试日志、仿真波形无法持久存储；过往修复经验难以复用。 |
| 智能体与评估工具深度耦合，通用性极差 | 每款工具需单独适配仿真、编译脚本；更换基准数据集或 EDA 仿真工具时需大规模重构代码；无法标准化适配各类 RTL 测试套件。 |
| 反馈链路碎片化，缺少统一接受判定标准 | 修复循环仅以单次仿真报错作为优化依据；缺乏标准化的接受谓词（Acceptance Predicate）；无法自定义多维度评估指标，如测试覆盖率、时序 PPA、代码整洁度等复合目标。 |

这类工具本质是“模块级专用修复脚本”，不具备通用化、规模化自主演化能力，无法实现论文中跨全部基准全自动跑完测试集的效果。

### 1.3 仓库级自主演化技术的前世脉络

> HORIZON 并非凭空诞生，:mdnice-bold-italic[其底层仓库演化思路源自 NVIDIA 团队前期三款软件自主演化工作：AlphaEvolve、SATLUTION、ABCEvo，三者完整搭建了“LLM 智能体+自动化评估器+版本仓库”的技术范式，但全部局限于软件代码优化，从未延伸至硬件设计领域。]

- AlphaEvolve 首次验证大模型搭配自动化评估器，能够自主迭代优化算法内核代码；
- SATLUTION 将该思路拓展至完整 C/C++ SAT 求解器仓库，依靠分布式仿真反馈自主优化整套工程；
- ABCEvo 落地 EDA 逻辑综合工具 ABC，百万行代码依靠多智能体自主重构优化。

::: block-1
**三者统一遵循一条核心准则：代码修改只有通过可执行工具校验，才允许提交至版本仓库**。:mdnice-highlight[但三者的优化对象都是工程师使用的 EDA 软件、算法程序，而非工程师产出的硬件 RTL 设计文件，这是过去仓库演化范式最大的空白，也是 HORIZON 最核心的创新切入点。]
:::

## 二、HORIZON 核心范式：将硬件设计等价为 Git 仓库可执行演化任务

> HORIZON 完全重构硬件智能体的运行载体，放弃临时文件缓存模式，将每一个芯片设计需求封装为独立隔离 Git 工作树，所有迭代、修改、仿真校验、版本保存操作全部基于原生 Git 指令完成。

整套框架不绑定特定大模型后端，仅定义标准化输入、评估、演化闭环，任何 LLM 都可作为智能体策略后端，具备极强通用性。

### 2.1 框架顶层整体架构与输入输出链路

> 整套框架运行链路分为四个固定阶段：

![文章插图](/articles/2026-07-12-eda-rtl-nvidia-horizon-a6da7e82/images/05.webp)

::: image-caption
图 1 展示了 HORIZON 的核心流程：人类定义的结构化 Markdown 测试套被转换为项目包（含任务目标、领域技能、评估器、正确性闸门及 Git / 运行时策略）；自包含的智能体循环在 Git 追踪的仓库状态上求解任务；可执行任务实例提供评估器反馈与奖励，深度 k 的轨迹缓冲区记录版本历史、状态增量、评估结果及运行时摘要。
:::

1. 人工输入结构化 Markdown 配置 Harness，定义设计目标、领域硬件知识、仿真评估规则、任务通过判定条件；
2. Bootstrap 引导智能体读取 Harness，自动编译生成标准化 Project Pack 项目包，统一封装智能体提示策略、可执行评估器 $E_p$、接受谓词 $A_p$、版本控制策略 $\Gamma_p$、领域知识库 $\Omega_p$；
3. 全自动自治循环启动，智能体读取当前 Git 仓库快照，编辑 RTL、测试激励等文件，调用 EDA 仿真工具运行评估器，生成仿真反馈证据；
4. 依据接受谓词判定本轮修改是否达标，达标则创建 Git 提交快照保存版本，不达标则记录差分文件、报错日志回滚至修改前仓库状态，启动下一轮迭代修复。

### 2.2 Markdown Harness 到 Project Pack 的编译转化逻辑

> 论文给出引导编译的数学定义公式：

$$
p=G_{\phi}(m), p=\left(\pi_{agent}, E_{p}, A_{p}, \Gamma_{p}, \Omega_{p}\right)
$$

公式变量逐一定义：

- $m$：人类编写的原始 Markdown 配置 Harness，包含设计目标、硬件领域规范、仿真脚本路径、任务通过标准；
- $G_{\phi}$：Bootstrap 引导智能体，固定 LLM 驱动的编译转换函数；
- $p$：编译完成输出的 Project Pack 项目包，是整套任务的控制平面；
- $\pi_{agent}$：智能体运行策略，包含提示词模板、工具调用接口规范；
- $E_p$：可执行评估器，RTL 场景下包含代码编译、仿真、覆盖率统计、断言校验全套 EDA 流程；
- $A_p$：接受谓词，布尔判定函数，仿真全部通过输出 1，存在报错输出 0；
- $\Gamma_p$：Git 版本控制与文件管理策略，定义分支、提交注释、日志存储规则；
- $\Omega_p$：硬件领域知识库，包含总线协议、复位规范、时序约束等静态行业知识。

该公式体现了工程师写一份描述“生成 UART 串口 RTL+配套测试激励”的 Markdown 文档，引导智能体自动打包一套可直接运行的任务环境，内置串口硬件知识、Verilog 仿真脚本、判定“仿真无报错、覆盖率达标才算通过”的规则，无需工程师手动配置仿真环境、版本仓库。

::: block-1
这套转化逻辑的核心优势是任务标准化，无论简单组合逻辑模块，还是复杂全流程验证用例，全部统一转化为同结构 Project Pack，框架底层演化循环无需针对不同任务做定制修改。
:::

### 2.3 基于 Git 仓库的半马尔可夫状态建模与数学定义

> HORIZON **借用半马尔可夫决策过程的数学语言，对 Git 仓库每一轮迭代的状态、智能体动作、评估反馈做标准化建模**，方便后续轨迹分析、离线强化学习训练，需要明确：:mdnice-bold-italic[该建模仅用于存储、解析迭代轨迹，框架运行过程中不会训练更新 RL 策略，智能体大模型权重全程固定。]

#### 第一，仓库迭代快照状态定义公式

$$
s_{t}=\left(tree\left(w_{t}\right), p, z_{t}, \ell_{\leq t}, \mu_{t}\right)
$$

变量释义：

- $s_t$：第 $t$ 轮迭代完成后的仓库完整状态快照；
- $tree(w_t)$：当前隔离 Git 工作树的全部文件版本快照，即本次迭代的硬件代码、测试文件；
- $p$：固定不变的 Project Pack 项目包；
- $z_t$：本轮任务全局运行状态，包含迭代次数、资源消耗、仿真运行时长；
- $\ell_{\leq t}$：从第 0 轮到第 $t$ 轮全部历史日志、仿真波形、报错记录；
- $\mu_t$：智能体持久化会话记忆，缓存历史调试经验，降低重复 Token 消耗。

#### 第二，智能体单次迭代动作定义公式

$$
a_{t}=\left(\Delta_{t}, u_{t, 1: K_{t}}, \rho_{t}\right)
$$

变量释义：

- $a_t$：第 $t$ 轮智能体执行的完整动作序列；
- $\Delta_t$：本轮智能体生成/修改的文件差分补丁，对应 Git diff 修改内容；
- $u_{t,1:K_t}$：本轮内部执行的 $K_t$ 次 EDA 工具调用、仿真指令、日志读取操作；
- $\rho_t$：本轮最终提交决策，分为提交通过、回滚拒绝两类。

#### 第三，评估反馈与版本更新判定公式

$$
s_{t+1}= \begin{cases}Commit\left(w_{t} \oplus \Delta_{t}, y_{t}, \Gamma_{p}\right), & A_{p}\left(y_{t}\right)=1, \\ RejectLog\left(s_{t}, \Delta_{t}, y_{t}\right), & A_{p}\left(y_{t}\right)=0 .\end{cases}
$$

变量释义：

- $y_t=E_p(w_t\oplus\Delta_t)$：评估器 $E_p$ 基于修改后的仓库文件输出仿真结果证据；
- $A_p(y_t)=1$：仿真全部满足接受标准，执行 Commit 操作，保存新版本 Git 快照；
- $A_p(y_t)=0$：仿真存在报错，执行 RejectLog 操作，记录本次失败差分、报错日志，仓库回滚至 $s_t$ 状态，进入下一轮迭代。

::: block-1
整套数学模型将模糊的“智能体调试硬件代码”过程，拆解为可存储、可复现、可量化的标准化轨迹 $\tau_{0:D}=\left\{\left(s_{t}, a_{t}, r_{t}, s_{t+1}, y_{t}\right)\right\}_{t=0}^{D-1}$，$D$ 代表迭代总轮次，完整轨迹可以用于后续离线分析、智能体策略微调、调试经验复用。
:::

### 2.4 无人工干预自治 Agent 循环完整运行流程

> 整套循环全程无需人工介入，从初始化到全部任务收敛自动运行，单轮外部迭代完整流程分为 5 步：

1. 状态读取：智能体读取当前 Git 仓库完整快照 $s_t$，读取历史迭代日志、过往仿真报错、缓存会话记忆 $\mu_t$；
2. 规划与文件修改：基于历史失败记录、硬件领域知识，生成代码修改差分 $\Delta_t$，写入 Git 工作树；
3. 批量工具调用：自动调用编译、仿真、覆盖率采集 EDA 工具，执行 $K_t$ 次工具操作，收集仿真输出证据 $y_t$；
4. 接受谓词判定：调用 $A_p$ 校验仿真结果是否达标，生成多维度奖励向量 $r_{t}=R_{p}\left(y_{t}\right)=[\Delta pass, \Delta coverage, \Delta QoR,- tokens, - time ]$；
5. 版本提交/回滚：达标则创建 Git 提交，将奖励、仿真日志存入 Git 注释；不达标则记录失败轨迹，回滚仓库，开启下一轮迭代。

奖励向量包含五大维度指标，论文实验仅重点观测通过率提升 $\Delta pass$、测试覆盖率提升 $\Delta coverage$、Token 消耗 $-tokens$ 三项，时序功耗面积（QoR）优化留作未来研究方向。

### 2.5 会话缓存机制：大幅削减大模型 Token 开销的关键设计

> 论文实验数据显示全部 Token 中 91%为缓存输入 Token，大幅降低大模型 API 调用成本，核心依托持久化模型会话缓存设计。

传统迭代智能体每一轮都会完整重复输入全部配置文件、历史日志、领域知识，大量重复文本反复消耗 Token；:mdnice-bold-italic[HORIZON 复用全局持久会话，将固定不变的 Harness、Project Pack、稳定源码、历史调试上下文全部存入模型服务端缓存，每一轮仅需要传输本次文件差分、最新仿真报错、智能体本轮输出，新增 Token 消耗被压缩至极低水平。]

数学层面，智能体动作采样满足 $a_{t}\sim \pi _{\theta }(\cdot | s_{t},h_{t})$，$h_t$ 代表缓存会话记忆，每轮迭代更新记忆 $h_{t+1}=M(h_{t},s_{t},a_{t},y_{t})$；所有缓存记忆仅作为辅助上下文，仓库 Git 快照才是任务唯一可信数据源，缓存失效也不会影响迭代闭环完整性。

::: block-1
总体而言，HORIZON 以 Git 隔离工作树为底层载体，通过标准化 Markdown 配置自动生成可执行评估任务；依靠半马尔可夫模型标准化存储全迭代轨迹；自治循环完整覆盖代码修改、EDA 仿真、版本提交全链路；持久会话缓存机制将 91%输入 Token 复用，显著降低大模型调用算力成本。
:::

## 三、全维度实验验证：100%基准通过率背后的数据真相

> 论文选用行业主流四类 RTL 基准套件，覆盖简单单模块生成、复杂代码修改、验证激励/检查器生成、硬件调试全场景，实验统一采用 GPT-5.3 作为智能体大模型后端，固定模型权重不做微调。

所有实验部署在 AMD EPYC 9334 32 核 512GB 内存服务器，开源仿真基准使用开源 EDA 工具，测试激励、断言类验证任务依赖商用仿真工具完成评估。

### 3.1 实验环境、基准套件与评估协议说明

实验覆盖四大类基准测试集，覆盖不同硬件设计难度层级：

1. 轻量基础生成套件：ChipBench、RTLLM-2.0、Verilog-Evalv2，以简单组合逻辑、时序模块生成任务为主，仅依赖开源仿真工具；
2. 复杂全流程 CVDP 基准：包含 9 大类硬件设计任务，共 783 个人工编写真实工程用例，细分代码补全、自然语言转 RTL、模块修改、代码复用、代码优化、测试激励生成、检查器生成、断言生成、硬件调试九大类别，其中测试相关三类任务需要商用 EDA 仿真器完成覆盖率评估。

评估协议统一标准：

1. 一轮迭代定义为完整一次“文件修改-EDA 仿真-提交判定”外部循环；
2. Iter.0 代表第一轮迭代完成后的仓库通过率，并非单独大模型单次生成 Pass@1 指标，智能体首轮会主动简化调试步骤，不会追求单次最优结果；
3. 收敛迭代次数定义为首次达到该基准 100%通过率的最小迭代轮次；
4. 全部实验采用单智能体运行模式，无多智能体协作、并行演化加速策略。

## 四、理性审视：当前框架的核心局限与行业待解难题

> 论文在开篇与讨论章节反复强调一项核心立场：**100%基准通过率不代表智能硬件设计问题已经被彻底解决**，当前实验结果仅能证明仓库级可执行反馈可以让受控基准任务收敛。

真实芯片工程的复杂度远高于现有基准测试集，HORIZON 框架当前依然存在两项无法回避的核心局限，也是整个硬件智能体领域共同面临的行业级难题。

### 4.1 奖励反馈接口的固有风险：奖励黑客与过拟合问题

当前框架的迭代逻辑建立在完整仿真反馈的基础上，智能体每一轮都可以读取全部仿真报错、失败波形、测试用例细节，:mdnice-bold-italic[这一设计完全复刻了真实工程师的调试流程，也是多轮修复能够持续收敛的核心前提。但正是这种全透明的反馈机制，天然存在过求解的风险，也就是行业常说的奖励黑客问题。]

具体来说，智能体在多轮调试中，可能不会真正理解设计的完整语义，而是针对可见的固定测试用例生成针对性的适配代码，只保证在当前这套测试脚本下通过，却无法满足规格定义的全部功能边界。**最终的通过结果，只能证明代码满足了可见测试用例的校验，不能证明代码完整实现了设计需求，这种情况在测试用例数量有限、场景覆盖不全的基准中尤其容易出现。**

::: block-1
这一问题并非硬件领域独有，软件工程领域的智能体基准早已给出成熟的解决方案。:mdnice-highlight[SWE-bench 采用了测试集分离机制，智能体调试阶段只能拿到问题描述和部分公开测试，最终评分使用的测试集全程隐藏，仅在最终提交补丁后执行校验，从机制上避免了智能体针对测试用例过拟合]。后续研究也证实，弱测试集、信息泄露等问题会显著虚高智能体的实测表现，很多通过基准测试的补丁依然存在潜在的逻辑缺陷。
:::

论文据此提出了硬件智能体基准的未来建设方向：建立两级评估协议，调试阶段向智能体开放诊断日志与公开测试集，最终评分阶段使用隐藏的随机化测试、独立参考模型、形式化等价检查、不同仿真器配置等多重校验手段，同时增加测试扰动鲁棒性、覆盖率闭合度等辅助指标，区分真正的设计修复与针对基准的定向适配。

### 4.2 反馈延迟瓶颈：从 RTL 仿真到全流程 PPA 评估的算力鸿沟

> 当前实验中所有基准都属于小规模 RTL 模块，单次仿真耗时极短，智能体可以在短时间内完成几十轮迭代，这也是朴素的修改-评估-修复循环能够成立的基础。**但如果将场景拓展到真实芯片工程，评估反馈的延迟会呈指数级上升，彻底改变智能体系统的设计逻辑。**

真实芯片设计中的质量评估，远不止功能仿真这一项。要判断一次 RTL 修改的优劣，往往需要经过逻辑综合、布局布线、静态时序分析、功耗估算、全芯片回归测试等多个环节，根据设计规模和签核精度的不同，单次评估的周期从几小时到几天甚至数周不等。论文中也提到，:mdnice-bold-italic[同属仓库级演化的 SATLUTION，评估一次完整的 SAT 求解器性能，需要 800 个计算节点并行运行两小时；而面向 EDA 工具的 ABCEvo 演化、面向 RTL 的 PPA 优化场景，单次完整评估的周期会更长。]

长延迟反馈会直接击穿当前的迭代模式：如果每修改一行代码都要等待数天才能拿到评估结果，整个演化的效率会低到无法接受。:mdnice-bold-italic[这种场景下，智能体必须学会在稀疏、延迟、高成本的反馈下做决策，比如一次性生成多组候选方案批量评估、用轻量预测模型提前预判修改效果、减少无效的试探性修改，这些都是当前框架尚未覆盖的能力，也是未来硬件自治设计领域最核心的研究挑战之一。]

### 4.3 基准覆盖范围的天然局限

> 除了机制层面的局限，现有 RTL 基准本身的覆盖范围也存在明显边界。当前所有测试集都以单模块设计为主，需求描述完整明确，边界条件清晰，只聚焦代码生成、调试、验证等单一环节，和真实芯片项目的复杂度差距极大。

**真实芯片开发过程中，会存在大量不完整的规格、动态调整的约束、上下游模块的集成适配、多团队协作的人工评审、面积功耗时序的多目标权衡**，这些复杂要素都没有体现在当前的基准测试中。因此，:mdnice-bold-italic[HORIZON 在基准上的 100%通过率，只能证明其在受控、明确的单任务场景下具备完全自主收敛的能力，不能直接等同于可以落地到工业级芯片设计全流程。]

::: block-1
总体而言，当前硬件智能体存在两大行业共性瓶颈。一是测试与评分不分离导致的奖励黑客风险，二是真实工程中长周期评估带来的反馈延迟难题；现有 RTL 基准无法覆盖真实芯片设计的全复杂度，基准收敛仅代表技术可行性，距离工业落地仍有大量研究空白。
:::

## 五、行业价值与未来展望：从基准收敛到真实芯片设计自治

> HORIZON 的出现并非单纯刷新了 RTL 基准的通过率榜单，而是第一次将仓库级自主演化的成熟范式从软件领域延伸至硬件设计领域，为整个 EDA 自动化行业提供了一套标准化的智能体底座框架。

其价值不止于提升 RTL 生成的准确率，更在于重构了硬件智能体的技术路径，从“追求单次生成最优”转向“构建可迭代、可追溯、可评估的自主演化闭环”。

### 5.1 对硬件 EDA 行业的落地价值

> 对于芯片设计与 EDA 行业而言，HORIZON 的落地价值体现在三个核心维度。

| 特性 | 描述 |
| --- | --- |
| 标准化的任务封装能力 | 统一的 Markdown 配置到项目包的编译流程，可快速将各类硬件设计需求转化为可自动迭代的任务，无需为每个场景单独开发智能体脚本或适配工具链，大幅降低硬件智能体的落地门槛；企业内部的常规模块开发、验证脚本编写、legacy 代码修复等重复性工作，均可快速接入该框架实现自动化。 |
| 全链路可追溯的调试轨迹 | 所有代码修改、仿真结果、提交决策均以原生 Git 提交记录存储；完整的演化轨迹既可用于审计设计过程、回溯问题根因，也可作为高质量训练数据用于微调专用硬件大模型，形成“设计-调试-数据-模型”的正向闭环。 |
| 兼容现有 EDA 工具生态 | 框架不替换现有仿真、综合、布局布线工具，而是作为上层调度层封装工具调用；企业可直接接入内部成熟的商用 EDA 流程和自研工具链，无需重构现有开发体系，具备极强的落地兼容性。 |

### 5.2 技术演进的核心研究方向

> 结合论文提出的局限，未来硬件自主设计框架的演进会围绕四个核心方向展开。

| 研究方向 | 内容 |
| --- | --- |
| 多目标联合演化 | 当前框架主要以功能正确性为核心目标，未来可以将时序、面积、功耗、可靠性等 PPA 指标纳入奖励向量，构建功能与性能联合优化的自主设计循环，这也是最贴近工业实际需求的落地方向。通过调整接受谓词与奖励权重，框架可以适配不同设计阶段的优化目标，从前端功能验证到后端签核全流程覆盖。 |
| 长延迟反馈下的高效决策 | 针对综合、布局布线等慢反馈场景，需要研发小样本高效优化策略，比如引入贝叶斯优化、性能预测模型、批量候选方案并行评估等机制，减少真实工具评估的次数，降低迭代的时间与算力成本，让仓库级演化能够适配全流程设计场景。 |
| 鲁棒性验证体系建设 | 引入隐藏测试集、形式化等价检查、随机扰动测试等多重校验机制，从基准设计层面避免智能体过拟合测试用例，保证生成的硬件设计具备真实工程可用性，而不是仅能通过特定测试脚本的“刷榜”产物。 |
| 全流程场景拓展 | 当前框架主要覆盖 RTL 编码与验证环节，未来可以向上拓展到架构探索、微架构设计，向下延伸到物理设计、签核验证，逐步覆盖芯片设计全流程的自主演化，最终实现端到端的芯片设计自治。 |

### 5.3 对工程类智能体的通用范式启示

> 跳出硬件设计领域，:mdnice-bold-italic[HORIZON 的范式对所有工程类大模型应用都具备通用参考价值。它验证了一套可复制的自治系统思路：对于任何具备可执行评估标准、可版本管理的工程任务，都可以通过“结构化配置定义+自动化评估器+Git 版本追踪+大模型智能体循环”的模式实现自主演化。]

这套范式不局限于 RTL 设计，同样可以推广到嵌入式开发、工业控制代码、编译器优化、基础库性能调优、安全漏洞修复等多个工程领域。只要能定义清晰的通过标准、搭建可自动执行的评估脚本，就可以复用同一套仓库级演化框架，实现不同场景的自动化迭代。

同时，持久会话缓存的设计也为长周期工程类智能体的成本优化提供了成熟参考。通过缓存固定的配置、知识库、历史上下文，仅传输增量文件差分与最新反馈，可以将 90%以上的输入 Token 复用，大幅降低长迭代任务的大模型调用成本，这一经验可以复制到所有多轮迭代的智能体场景。

## 结语

> HORIZON 框架的诞生，**标志着硬件大模型正式从“单次生成辅助工具”迈入“自主演化闭环系统”的新阶段**。100%的基准通过率不是行业的终点，而是整个赛道全新的起点——当功能正确性的收敛已经被验证可行，下一阶段的技术竞争将聚焦于迭代效率、多目标优化、工程鲁棒性三大核心方向。

对于芯片设计行业而言，这类自治智能体不会立刻替代硬件工程师，而会成为工程师的“自动化调试助手”，承担重复性的代码补全、测试编写、bug 定位与修复工作，让工程师将精力聚焦在架构创新、性能权衡、系统集成等高价值环节。它的本质是提升硬件开发的人效，而非取代工程师的创造力。

::: block-1
未来随着评估工具链的完善、长反馈优化策略的成熟，:mdnice-bold-italic[仓库级自主演化的范式有望逐步渗透到芯片设计的全流程，推动 EDA 行业进入智能自治的全新阶段。而 HORIZON 作为首个实现全基准零人工收敛的通用框架，也为整个领域划定了技术基线，开启了硬件自主设计的全新研究方向。]
:::
