## 一、为什么需要一个架构特定的 PTX 基准

> PTX 是 CUDA 开发者能够显式控制的最低层可编程接口，高性能内核往往需要在 PTX 层级做优化，才能充分释放架构专属机制的效率。随着 NVIDIA 每一代 GPU 引入新的张量核、存储单元与同步机制对应的 PTX 指令，一份可移植的 CUDA 内核即便功能正确，也可能完全浪费了新硬件的核心能力。

过去一年，GPU 内核生成类基准快速涌现，从 KernelBench 到 TritonBench，再到各类生产环境评测集，:mdnice-bold-italic[核心目标都是验证大模型能不能写出更快的 GPU 算子。但这类基准普遍存在一个共同的盲区：它们只衡量端到端的功能正确性与整体性能，无法区分性能的真实来源]。模型生成的内核速度快，可能是因为调用了 cuBLAS、cuDNN 等厂商库，可能是因为做了通用的循环展开与访存合并，也可能是真的用到了对应架构的专属张量指令。**对于想要评估模型底层硬件驾驭能力的研究者来说，这种黑盒式的结果远远不够。**

更关键的是，:mdnice-bold-italic[新架构的专属指令往往是性能突破的核心来源。以 Hopper 架构的 WGMMA 指令与 TMA 异步搬运为例，FlashAttention-3 正是通过深度组合这两类机制，才实现了相对于上一代的大幅性能提升。] 如果模型只会写通用 CUDA，永远碰不到这些底层指令，那就永远不可能摸到硬件的性能上限。而高层内核语言虽然易用，但新硬件发布后，编译器对新指令的支持往往滞后数月甚至更久，这段空窗期的硬件潜力，只能靠手写 PTX 来释放。

> PTXBench 的定位，就是做一个**可控的能力探针**。它给模型指定明确的目标指令族，要求内核必须通过这些指令完成核心计算，并且用动态运行时校验确认指令确实被执行了，而不是躺在死代码里凑数。它不替代现有的端到端基准，而是**补全了“架构特定能力”这一缺失的评测维度，让研究者可以精准地知道模型到底会不会用某一代硬件的核心特性。**

::: block-1
总之，现有 GPU 内核生成基准无法区分性能来源，PTXBench 的核心价值在于:mdnice-highlight[把“架构特定指令的真实执行”从端到端结果中剥离出来]，形成可审计、可复现的底层能力评测标准。
:::

## 二、PTXBench 的设计：三层评测维度与多轮智能体框架

> PTXBench 围绕架构特定 PTX 编程的三个核心评价维度构建评测体系，分别是功能正确性、目标指令运行时执行率，以及相对于前沿库的性能加速比。

为了贴近真实内核开发的迭代流程，基准内置了多轮智能体 MiniPTXAgent，允许模型基于编译与运行反馈反复修正内核代码。

### 2.1 任务设置与受控上下文

> :mdnice-bold-italic[每一个 PTXBench 测试用例都由四部分组成：前沿库实现的参考算子、固定的输入工作负载、目标 GPU 架构，以及要求必须使用的架构特定 PTX 指令族。模型需要从零开始生成带有内联 PTX 的 CUDA 内核，也就是论文中所说的 CUDA-PTX]，不允许从现有实现修改，更禁止直接包含 cuBLAS、cuDNN 等厂商库的头文件——哪怕运行结果正确，只要调用了外部库就算失败。整个基准基于 FlashInfer-Trace 统一 schema 构建，工作负载、解决方案、正确性校验都遵循同一套规范，未来可以平滑扩展更多兼容的任务集合。

为了避免评测变成“文档检索能力大赛”，所有测试轮次都会给模型提供完全相同的架构专属知识包，内容包括架构参数、PTX 指令的 C++封装函数、数据布局、同步规则、内存一致性约定，以及针对成熟算子的专家验证调度原则。单个知识包的体量在 2 万到 3 万 token 之间，相当于把一份精简的架构编程手册直接放进提示词。

![文章插图](/articles/2026-08-24-cmu-radixark-ptxbench-gpu-llm-e1f98be5/images/04.jpg)

::: image-caption
表 3：Gemini 3.1 Pro在架构特定提示词知识下的消融实验结果。该表对比了三种不同丰富度的提示知识下，目标指令正确率与最佳加速比的差异。仅提供架构参数时，8轮测试无任何目标指令成功执行；加入PTX模板函数后开始出现合格内核；再补充架构契约后，8轮目标指令正确率达到38.5%，比仅模板提升18.7个百分点。这说明模型无法自发掌握新架构的PTX用法，必须提供显式的指令封装与约束规则，且完整的契约对可靠执行至关重要。峰值加速比的排序与正确率不同，说明契约主要提升指令执行的可靠性，不必然带来最快的性能。
:::

消融实验结果非常明确：

- 只给架构参数时，模型连一个能执行目标指令的正确内核都写不出来；
- 加上 PTX 模板函数后，开始出现合格内核，性能也明显提升；
- 再补上完整的架构契约，也就是布局、同步、一致性规则后，目标指令正确率再上一个台阶。

::: block-1
这直接证明，:mdnice-highlight[没有显式的架构知识注入，大模型根本不会主动使用新的底层指令]，哪怕知识截止时间覆盖了架构发布时间也不行。
:::

### 2.2 多轮评测协议与核心指标

> 真实的内核开发是编译、报错、修改、再编译的反复迭代。PTXBench 内置的 MiniPTXAgent 就模拟了这个流程，采用多轮评测协议。

- 每一条测试轨迹允许最多 8 次模型调用，每一轮生成的内核都会先送入 CPU 容器用 nvcc 编译，编译失败就直接把错误信息返回给模型修改；
- 编译通过的内核才会送入隔离的 GPU 性能分析服务，依次完成内存安全检查、运行时错误捕获、功能正确性验证与延迟测量。

所有历史内核与反馈信息都会保留，供模型在后续轮次参考。

**这套评测最核心的创新，是对“目标指令正确性”的定义**。它不满足于静态查看编译后的 SASS 里有没有对应指令，而是:mdnice-bold-italic[将检查过程分成两步做动态校验：第一步先用 cuobjdump 检查最终 SASS 里是否存在目标指令族，如果没有直接判定不通过；如果有，再用 NVIDIA Nsight Compute 在真实工作负载下运行]，统计对应指令的谓词启用线程数，只有线程数大于 0，才判定目标指令真实执行了。

::: block-1
这里静态检查好比翻菜谱看有没有某道菜的做法，动态检查则是看厨师今天上班有没有真的做这道菜。:mdnice-bold-italic[很多时候模型会把目标指令写在一个永远不会被调用的内核里，SASS 里能看到，但运行时根本不会执行，静态检查就会产生假阳性。动态运行时校验彻底排除了这种情况，让评测结果完全可审计。]
:::

> 针对不同架构，研究选择了最具代表性的张量路径作为目标指令：H100 选择 GMMA 张量计算与 UTMA 数据搬运，也就是 Hopper 架构核心的 WGMMA 与 TMA 机制；B200 则选择 TCGEN05 张量路径下的 UTC*、LDTM 与 STTM 指令，仅支持 TMA 不算通过，因为 TMA 是从 Hopper 继承来的，不算 Blackwell 专属能力。

功能正确性方面，校验器先检查输出形状与数据类型，再用`torch.allclose`做数值对比，绝对误差与相对误差阈值均为 1e-2。性能测试采用标准的基准测试流程：10 次预热迭代后，运行 50 次取中位延迟，加速比定义为参考库延迟除以候选内核延迟。参考库均采用对应领域的前沿实现：GEMM 用 cuBLAS，普通注意力用 cuDNN，GQA 类注意力用 FlashInfer。

为了同时反映成功率与性能分布，研究定义了两个聚合指标：

$$
Fast_p = \frac{1}{N} \sum_{i=1}^{N} 1\left[C_i=1 \land s_i>p\right]
$$

$$
Fast_p^{Inst.} = \frac{1}{N} \sum_{i=1}^{N} 1\left[C_i=1 \land I_i=1 \land s_i>p\right]
$$

其中 $N$ 是总测试轮数，$C_i$ 是第 $i$ 轮的功能正确性标记，$I_i$ 是目标指令执行标记，$s_i$ 是该轮内核的加速比。$Fast_p$ 表示所有轮次中，功能正确且加速比超过阈值 $p$ 的比例；$Fast_p^{Inst.}$ 则进一步要求目标指令真实执行。**这个指标可以画出完整的性能分布曲线，既看得到成功率，也看得到峰值性能。**

## 三、实测结果：四大模型在两代 GPU 上的能力全景

> 研究选取了四款发布时间相近的主流模型，在 H100 与 B200 两代 GPU 上完成全量测试，覆盖 GEMM 与四类注意力工作负载。

整体结果呈现出鲜明的不均衡特征：:mdnice-bold-italic[模型在前向计算上表现尚可，但在复杂的反向注意力上成功率暴跌；即便成功执行了目标指令，也大多无法达到前沿库的性能水平。]

### 3.1 正确率与性能的整体格局

> 测试的四款模型分别是 Gemini 3.1 Pro、Claude Opus 4.8、GLM-5.2 与 Qwen3.6-27B，覆盖闭源商用与开源可微调两类。从知识截止时间看，Gemini 3.1 Pro 的截止时间与 Blackwell PTX 发布同月，Claude Opus 4.8 晚 12 个月，GLM-5.2 与 Qwen3.6-27B 未公开截止时间，按发布时间估算滞后 15 到 17 个月。

![文章插图](/articles/2026-08-24-cmu-radixark-ptxbench-gpu-llm-e1f98be5/images/06.jpg)

::: image-caption
表 1：H100与B200上的目标指令与无限制轮次正确率。表格按GPU与模型分类，展示GEMM、四类注意力负载下的目标指令正确率，括号内为不限制指令的总正确率，每组数据按1轮、4轮、8轮依次展示。H100上Claude Opus 4.8全面领先，GEMM 8轮正确率达94.8%，但反向因果注意力降至44.8%；B200上所有模型的注意力正确率大幅下滑，反向负载普遍不足15%。Qwen3.6-27B在H100上无任何正确内核，B200仅GEMM有一个正确结果且未执行专属指令。

H100 平台的结果呈现出清晰的梯队。

- Claude Opus 4.8 的目标指令正确率全面领先，GEMM 任务 8 轮达到 94.8%，MHA 前向两类负载在 75%到 90%之间，即便难度最高的反向因果注意力也有 44.8%。
- Gemini 3.1 Pro 紧随其后，整体低 5 到 10 个百分点。
- GLM-5.2 在 GEMM 上与 Gemini 表现相当，但注意力任务差距明显，尤其是带因果掩码的负载，正确率只有 Claude 的一半左右。
- Qwen3.6-27B 在 H100 所有负载上均未生成功能正确的内核，Hopper 架构的 PTX 编程完全超出其基线能力。

**到了更新的 B200 平台，所有模型的表现都出现大幅下滑**，尤其是注意力类负载。

- Claude Opus 4.8 的 GEMM 8 轮正确率仍有 80.2%，但 MHA 前向掉到 38.5%，反向注意力仅 10.4%。
- Gemini 3.1 Pro 的正确率更低，但峰值性能和 Claude 接近，说明它虽然成功率不高，但写对的内核质量不差。
- GLM-5.2 在 B200 注意力上几乎全军覆没，多数负载正确率不足 3%。
- Qwen3.6-27B 只生成了一个功能正确的 GEMM 内核，且没有执行任何 Blackwell 专属指令，本质还是通用 CUDA 实现。

> 性能层面的差距比正确率更悬殊。

- **H100 上表现最好的 Claude Opus 4.8，GEMM 最佳加速比达到 0.976 倍 cuBLAS，基本追平厂商库**；但 MHA 前向只有 0.8 倍左右，反向注意力直接跌到 0.5 倍。
- :mdnice-bold-italic[B200 上 GEMM 最好的 Claude 做到了 1.012 倍 cuBLAS，略微超过参考库，但注意力负载的最佳加速比普遍只有 0.2 到 0.3 倍，几乎没有实用价值。]

::: block-1
从知识截止时间的影响来看，Gemini 的知识截止和 Blackwell PTX 发布同月，依然能做到 0.892 倍的 GEMM 性能，:mdnice-bold-italic[说明通用编码能力可以部分弥补知识滞后；但注意力这类更复杂的算子，还是知识更新更全的 Claude 表现更好。整体来看，较新的知识与更强的通用编码能力都有帮助，但都无法填平新架构复杂算子的能力鸿沟。]
:::

### 3.2 三个核心发现

- 第一，**架构特定 PTX 能力严重不均衡**。简单的 GEMM 与前向注意力，模型已经能做到较高的正确率与不错的性能；但反向注意力尤其是带因果掩码的反向，难度陡增，正确率腰斩甚至只剩零头。:mdnice-bold-italic[新架构比旧架构难度高一个量级，所有模型在 B200 上的表现都出现断层式下滑。]
- 第二，**执行目标指令不等于拥有竞争力的性能**。很多内核虽然成功调用了 GMMA 或者 TCGEN05 张量路径，但调度策略不合理、流水线没做满、访存有瓶颈，最终性能只有前沿库的几分之一。:mdnice-bold-italic[写出能跑的张量指令是一回事，把指令的效率吃满是另一回事，后者需要更精细的硬件理解与工程调优。]
- 第三，**没有任何被测模型能在全部测试项上稳定追平前沿库**。最好的模型也只能在 GEMM 上勉强打平，注意力负载普遍有明显差距，反向注意力更是差距巨大。:mdnice-bold-italic[目前 LLM 写内核，依然只能覆盖简单场景，距离全面替代专家优化的内核库还有很长的路。]

::: block-1
整体看下来，当前大模型的底层 GPU 编程能力呈现:mdnice-highlight[“简单负载追平、复杂负载断层、新架构适配滞后”] 的格局，距离全面替代专家优化的内核库还有显著距离。
:::

## 四、高层语言 vs 底层 PTX：架构代际下的效率反转

> 既然直接写 CUDA-PTX 难度高、效果不稳定，那**用 Triton 这类高层内核语言的表现如何？** 研究专门对比了同一模型分别用 Triton 与 CUDA-PTX 生成内核的性能差异。:mdnice-bold-italic[结果呈现出明显的架构依赖性：在成熟的 Hopper 架构上两者接近，但在较新的 Blackwell 架构上，高层语言的优势被急剧放大。]

![文章插图](/articles/2026-08-24-cmu-radixark-ptxbench-gpu-llm-e1f98be5/images/08.jpg)

::: image-caption
图 3：Gemini 3.1 Pro在H100与B200上Triton与CUDA-PTX的Fast_p分布对比。H100上CUDA-PTX与Triton性能差距较小，GEMM接近持平，因果MHA前向甚至略高（0.768倍 vs 0.759倍）；但B200上注意力负载的差距显著拉大，例如两项反向负载中Triton分别达到0.484倍和0.436倍，而CUDA-PTX仅为0.133倍和0.015倍。
:::

**Hopper 架构上，两种路径的表现非常接近**。GEMM 任务两者基本打平，因果 MHA 前向任务中，CUDA-PTX 的峰值性能甚至略高于 Triton。:mdnice-bold-italic[这说明当架构足够成熟、训练数据充足时，直接写底层 PTX 有机会摸到和高层语言相当甚至更高的上限]，毕竟跳过了一层编译器，有更细的控制粒度。

**但到了 Blackwell 架构，局面完全反转**。:mdnice-bold-italic[注意力类负载上，Triton 的性能全面大幅领先 CUDA-PTX，反向负载的差距甚至达到数倍]。研究认为有两个核心原因：

- 其一，Blackwell 新增了更多专用计算与存储机制，直接用底层指令协调所有细节的复杂度指数级上升，模型很容易在某个环节出错；
- 其二，Blackwell 比 Hopper 晚发布约两年，训练数据中可用的 Blackwell 专属 CUDA-PTX 代码样本少得多，模型没见过足够多的正确范例。

这背后的逻辑其实很直观：:mdnice-bold-italic[高层内核语言把底层的指令调度、内存同步、流水线编排都封装在了编译器里，模型只需要关注高层的计算逻辑与分块策略，出错的维度少很多。新架构刚出来的时候，虽然编译器也在适配，但毕竟有工程团队的专业积累，兜底能力远强于大模型从零写 PTX]。而当架构成熟之后，大量手写 PTX 的优质代码进入训练数据，模型就有机会学到更极致的优化，突破编译器的通用策略上限。

研究还尝试了给 CuTe DSL 做专门的提示词工程，但内核成功率极低，无法完成有意义的对比。这也侧面说明，越偏向底层的抽象，模型生成的难度就越高，对领域知识的要求就越强。

::: block-1
总之，:mdnice-highlight[高层内核语言在新架构适配阶段的价值不可替代]，它用编译器的工程积累抵消了模型的底层经验不足；而底层 PTX 则在架构成熟期提供了进一步突破性能天花板的可能。
:::

## 五、Fixit 修复式微调：用失败样本提升底层编程能力

> 既然基线开源模型的底层 PTX 能力不足，**那能不能通过针对性的后训练来定向提升？** 研究提出了 Fixit 修复式监督微调方法，以 Qwen3.6-27B 为基底做了系统性的消融实验。

**其核心思路是从模型自身的失败案例出发**，用教师模型生成修复方案与原理说明，再反过来训练学生模型，形成从错误中学习的闭环。

### 5.1 Fixit 方法的核心流程

> **高质量的 PTX 内核数据非常稀缺，它既需要深厚的硬件专家知识，又需要反复迭代验证，制作成本极高**。如果全靠专家写正确样本来做微调，数据量很难上去。:mdnice-bold-italic[Fixit 的思路就是绕开这个瓶颈，用“失败样本+教师修复”的方式低成本构造训练数据。]

整个流程分为三步：

- 第一步，**收集失败样本**。用待适配的基线模型生成内核，筛选出功能错误的样本，连同对应的编译或运行时反馈一起保存下来。:mdnice-bold-italic[这些失败样本是模型自己容易踩的坑，天然贴合它的能力边界。]
- 第二步，**修复教师生成正确内核**。用能力更强的修复教师，也就是 Gemini 3.1 Pro，基于原始问题、失败内核、错误反馈，生成修正后的内核，:mdnice-bold-italic[只保留通过功能正确性校验的修复结果。]
- 第三步，**推理教师生成原理解释**。用推理教师 GLM-5.2，基于问题、失败样本、反馈、正确内核，生成从错误到修复的推理解释，:mdnice-bold-italic[讲清楚哪里错了、为什么错、怎么改、改了为什么对。]

最终每个训练样本的输入是“问题描述+架构知识+失败内核+错误反馈”，监督目标是“推理解释+正确内核”。模型学习的不只是正确答案，还有从错误走到正确的思考过程。

**选择 Qwen3.6-27B 作为适配目标有三个原因**：它的 262K 上下文窗口能容纳很长的 PTX 提示词与内核轨迹；参数量适中，可以做可控的 LoRA 适配与自托管评测；基线能力弱，提升空间明显，方便观察不同训练配方的效果差异。

### 5.2 消融实验：什么因素真正决定微调效果

> 研究一共设计了 7 组不同的数据配方，从训练格式、数据覆盖与均衡性、推理教师三个维度做对照实验。

:::

![文章插图](/articles/2026-08-24-cmu-radixark-ptxbench-gpu-llm-e1f98be5/images/10.jpg)

::: image-caption
图 5：不同SFT数据配方的评测结果对比。四组子图分别展示正确率、目标指令成功率、最佳加速比、目标指令最佳加速比，横向为不同模型与配方。结果显示均衡配方s1和s5覆盖了全部五类问题，而样本更多但不均衡的配方反而存在任务盲区；推理教师的更换会导致能力大幅下滑。
:::

- **第一个对比维度是训练格式**：Fixit vs 直接学习正确样本的 KernelGen。两者覆盖同样的八类问题，用同一个推理教师，样本量相近。结果显示，Fixit 在 GEMM、因果前向注意力、反向注意力上优于直接监督，但在普通前向注意力与因果反向注意力上不如直接学习。:mdnice-bold-italic[这说明修复式训练并不是全面优于直接学正确答案，它的优势集中在模型容易反复出错的任务上，效果随任务类型波动。]
- **第二个对比维度是数据覆盖与均衡性**。这是整个消融实验最反直觉的结论：**数据均衡比数据量重要得多**。样本量更少但任务分布均衡的 s1 和 s5 配方，能够覆盖全部五类测试问题；而样本量是 s1 的 1.6 倍、但分布不均衡的 s2，反而做不出反向因果注意力。样本量是 s4 的 2.4 倍的 s3，同样在反向因果上失败。从 s4 升级到样本量多 50%且更均衡的 s5，四项任务的正确率提升，四项任务的峰值性能提升。:mdnice-bold-italic[这和通用指令微调的结论高度一致：任务的多样性、平衡性与筛选质量，远比无脑堆样本数量更重要。]
- **第三个对比维度是推理教师的质量**。s5 与 s6 用完全相同的 Fixit 样本，唯一区别是推理教师从 GLM-5.2 换成了学生模型自己 Qwen3.6-27B。结果 s6 只能完成 GEMM 任务，其他所有注意力任务全部失败。:mdnice-bold-italic[这说明失败样本本身是有价值的输入，但能不能把修复的逻辑讲清楚、讲正确，高度依赖更强的推理教师。让弱模型自己给自己讲错题，等于瞎讲，越学越偏。]

### 5.3 泛化边界与跨语言迁移

> 研究选择了样本量最小但能覆盖全部任务的 s1 配方，做详细的泛化能力测试。s1 训练时只用了头维度 128 的四类 MHA 任务，测试时泛化到 GEMM、头维度 64 的全部 MHA、头维度 96 的前向 MHA，都取得了非零的正确率与不错的性能，说明相近尺寸的同类算子有不错的迁移效果。

但泛化的边界非常清晰。头维度 96 的反向注意力完全做不出来，因为 96 和 H100 WGMMA 的 64 分块不对齐，属于训练分布之外的情况。GQA、分页注意力等更复杂的注意力变体也全部失败，无法迁移。**这说明微调学到的更多是固定尺寸下的模板化优化，而不是通用的底层设计能力，一旦跳出训练分布就会失效。**

**更有意思的是跨语言迁移效果**。用 CUDA-PTX 微调后的模型，去生成 Triton 代码，轮次正确率全面下降，:mdnice-bold-italic[说明语法层面出现了负迁移，模型更容易把两种语言的写法搞混]。但在部分任务上，正确内核的峰值性能反而大幅提升，比如因果前向注意力从 0.238 倍涨到 0.632 倍，因果反向从 0.043 倍涨到 0.331 倍。:mdnice-bold-italic[这说明微调学到的优化思路、硬件直觉，可以迁移到高层语言上，哪怕语法正确率降了，写对的那些内核质量更高。]

**微调还改变了模型的错误分布**。基线模型大量死在编译阶段，连可执行文件都生成不了；:mdnice-bold-italic[微调后，错误更多转移到运行时错误与数值错误，推理长度也明显变长，尤其是早期轮次]。这相当于模型从“不会写”进化到了“能写出来，但逻辑可能有问题”，是能力阶跃的典型表现。

![文章插图](/articles/2026-08-24-cmu-radixark-ptxbench-gpu-llm-e1f98be5/images/11.jpg)

::: image-caption
图 9：GEMM任务的轮次错误状态转移对比。左为基线Qwen3.6-27B，右为微调后s1版本。基线在所有轮次均无正确内核，且大量为编译错误；微调后第0轮就有3个正确内核，后续多数轮次都能产出正确结果，错误也更多集中在运行时与数值层面。

回顾一下，修复式微调确实能让基线模型获得底层 PTX 编程能力，但:mdnice-highlight[泛化边界非常清晰]：相近尺寸、同类算子可以迁移，尺寸不对齐、新的注意力变体就会失效；数据均衡与教师质量的影响远大于样本数量本身。
:::

## 六、SFT vs 上下文监督：权重更新与推理提示的较量

> 提升模型专业能力通常有两条路径：**一是更新权重**，也就是监督微调；**二是不碰权重**，在推理时给更多指导，比如专家规则、检索相似案例与解决方案。

研究专门对比了这两种方式的效果，**结论很有启发：纯上下文指导救不了基线模型，但微调后的模型能更好地利用提示信息。**

![文章插图](/articles/2026-08-24-cmu-radixark-ptxbench-gpu-llm-e1f98be5/images/12.jpg)

::: image-caption
表 4：SFT与提示时监督下的目标指令与无限制轮次正确率。表格对比了六种条件下四类注意力任务的正确率。基线模型即便加上专家指导，也写不出正确的MHA内核；而微调后的s1即便不加专家指导，也能生成正确内核。仅检索修复笔记没有效果，必须同时给出修正后的内核才能大幅提升正确率，而这本质上是把答案放进了提示词。加上专家指导后，s1在全部四类问题上都获得了非零正确率。
:::

- **第一组对照是基线模型加专家指导**。研究把专家总结的七条内核编写规则放进提示词，包括张量形状约定、TMA 描述符规范、错误检查要求、在线 softmax 更新规则、同步约束等，相当于开卷考试给了重点。但基线 Qwen3.6-27B 依然写不出任何正确的 MHA 内核。:mdnice-bold-italic[这说明底层 PTX 编程这类深度专业领域，光给规则没用，模型没有对应的基础能力，根本读不懂、不会用这些规则。]
- **第二组对照是微调后的模型加不加专家指导**。s1 模型哪怕没有专家指导，已经能写出正确的 MHA 内核；加上专家指导后，覆盖的任务更多，正确率也有提升。:mdnice-bold-italic[这说明 SFT 真正内化了基础能力，让模型能够理解并运用专家规则。没有能力打底，再多提示也没用；有了能力之后，提示可以起到锦上添花的作用。]
- **第三组对照是检索增强**。用 BM25 从训练数据里检索最相似的失败案例，只给修复笔记不给正确内核，基线模型依然做不对；同时给修复笔记和正确内核，正确率大幅提升。:mdnice-bold-italic[但这种提升参考价值有限，因为它本质上是把接近标准答案的代码放进了提示词，更接近记忆复用而不是能力生成]。现实场景中，很难每次都找到完全匹配的正确内核。

::: block-1
总之，:mdnice-highlight[底层硬件编程这类强专业领域，SFT 带来的能力内化是不可替代的]，上下文提示只能作为锦上添花的辅助，无法填补基础能力的鸿沟。
:::

## 总结与展望

> PTXBench **第一次把 LLM 的 GPU 内核优化评测推进到了架构特定指令的层级**，用可审计的三维指标体系，**清晰地画出了当前模型的能力边界**。这项工作不仅是一个基准工具，更为后续的模型适配与训练提供了可复用的方法论。

这项工作的核心贡献可以归纳为三点。

- 其一，**提出了首个面向架构特定 PTX 编程的基准 PTXBench**，分离功能正确性、目标指令运行时执行、相对性能三个独立维度，通过动态运行时校验确保评测结果真实可信，并且基于统一 schema 具备良好的可扩展性。
- 其二，:mdnice-bold-italic[完成了横跨四款主流模型、两代 GPU 架构、五类核心负载的系统性能力评测，揭示了当前 LLM 在底层硬件编程上的不均衡格局，量化了从正确执行到性能达标的三重鸿沟。]
- 其三，**提出了修复式监督微调方法 Fixit**，通过受控消融验证了数据均衡、教师质量等关键因素的影响，:mdnice-bold-italic[为开源小模型定向提升底层编程能力给出了明确的实践路径。]

当然这项工作也存在局限。目前的测试负载只覆盖了 BF16 精度的 GEMM 与注意力算子，还不能代表全部 GPU 算子的情况；适配实验仅使用了 Qwen3.6-27B 一个基底模型，且采用小规模 LoRA 微调，*相关结论不一定能直接推广到更大规模的全参数训练或其他模型家族。*

::: block-1
站在行业视角看，PTXBench 的出现标志着 LLM GPU 内核优化的评测，从“能不能跑”进入了“会不会用硬件”的新阶段。随着 GPU 架构演进越来越快，新的计算与存储机制越来越复杂，大模型能否快速驾驭新硬件，会成为影响 AI 基础设施迭代效率的关键因素。:mdnice-bold-italic[未来这个方向还有很多值得探索的方向：扩展更多算子与硬件架构、研究更强的后训练方法提升泛化能力、结合强化学习实现更长周期的自动迭代优化。PTXBench 这样的可控基准，会成为推动整个领域前进的核心基础设施。]
