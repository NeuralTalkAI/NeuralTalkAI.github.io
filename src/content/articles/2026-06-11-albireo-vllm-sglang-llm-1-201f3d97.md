## 一、问题的本质：张量并行的“阿姆达尔陷阱”

> 阿姆达尔定律是并行计算领域最基础也最残酷的定律。它告诉我们，一个系统的最大加速比，取决于其中串行部分的占比。如果一个程序有 10%的代码是串行的，那么无论使用多少个处理器，最大加速比永远不会超过 10 倍。

在 LLM 推理领域，这一定律正在以一种意想不到的方式发挥作用。长期以来，我们认为 LLM 推理是高度并行的任务，因为前向传播中的矩阵乘法和注意力计算都可以完美地并行化。但实际上，完整的 LLM 推理流水线包含了大量的串行任务，这些任务在张量并行的场景下无法被加速，最终成为了系统性能的瓶颈。

### 1.1 LLM 推理的流水线与不可扩展开销

> 要理解不可扩展开销的来源，我们首先需要拆解 LLM 推理的完整流水线。论文指出，在 vLLM、SGLang 等主流推理引擎中，**每一次迭代（无论是预填充阶段还是解码阶段）都包含五个核心任务：**

1. 调度（$T_1$）：选择下一批要处理的序列，分配 KV 缓存块，生成调度输出
2. 输入处理（$T_2$）：将调度输出转换为模型输入，更新缓存，将张量传输到 GPU 并广播到所有 TP 节点
3. 前向传播（$T_3$）：模型计算得到每个序列下一个 token 的概率分布（logits）
4. 采样（$T_4$）：根据 logits 和采样策略（贪婪、top-k、核采样等）选择下一个 token
5. 输出处理（$T_5$）：将采样得到的 token 追加到序列，进行反 token 化，检查终止条件，更新序列状态

在这五个任务中，**只有前向传播 $T_3$ 是完全可并行的**，可以通过张量并行在多个 GPU 上加速。而剩下的四个任务 $T_1$、$T_2$、$T_4$、$T_5$ 都是非可扩展的：

- $T_1$ 和 $T_5$ 完全运行在 CPU 上，与 TP 度无关
- $T_2$ 虽然涉及 GPU 数据传输，但广播操作的开销会随着 TP 度的增加而增加
- $T_4$ 在现有系统中只运行在主 GPU 上，其他 GPU 处于空闲状态

### 1.2 最优张量并行度的存在性与量化公式

> 张量并行的核心矛盾在于：一方面，增加 TP 度可以扩展可用内存，减少 KV 缓存的换入换出，从而提升吞吐量；另一方面，增加 TP 度会引入更多的跨 GPU 通信开销，同时放大不可扩展开销的影响。

这一矛盾导致了**最优张量并行度 $t_e$ 的存在**：

- 当 $t < t_e$ 时，内存收益占主导，吞吐量随 TP 度增加而增加；
- 当 $t > t_e$ 时，通信和不可扩展开销占主导，吞吐量随 TP 度增加而下降。

论文通过大量实验验证了这一现象，并提出了一个简单的经验公式来估算 $t_e$：

$$
t_e = \lceil 4M / C \rceil
$$

其中，$M$ 是 LLM 的权重大小（单位：GB），$C$ 是单 GPU 的内存容量（单位：GB）。

::: block-1
**这个公式背后的直觉是：为了给 KV 缓存留出足够的空间，模型权重占用的内存不应超过总内存的 25%。** 例如，对于 32B 参数的模型（FP16 权重大小 64GB），使用 80GB 的 H100 GPU，计算得到 $t_e = \lceil 4*64/80 \rceil = \lceil 3.2 \rceil = 4$。但在 vLLM 中，由于不可扩展开销的存在，实际的最优 TP 度只有 2，远低于理论值。这是因为当 t=4 时，不可扩展开销的影响已经超过了内存收益，导致吞吐量下降。
:::

### 1.3 现有系统的性能天花板：41%的不可扩展开销

> 为了进一步验证不可扩展开销的影响，论文测量了 vLLM 在不同 TP 度下的吞吐量，并与理论上的线性扩展进行了对比。结果显示，对于 Llama-3.1-70B 模型，当 TP 度从 4 增加到 8 时，vLLM 的吞吐量只提升了约 58%，远低于理论上的 100%，甚至出现了扩展效率下降的情况（2×T(4) ≈1.27×T(8)）。

这一现象完全符合阿姆达尔定律的预测。根据阿姆达尔定律，系统的加速比为：

$$
A = \frac{1}{(1-P) + P/t}
$$

其中，$P$ 是可扩展部分的占比，也就是前向传播的时间占比。在 vLLM 中，$P ≈ 59\%$，因此：

- 当 t=4 时，理论加速比为 $1/(0.41 + 0.59/4) ≈ 1.87$；
- 当 t=8 时，理论加速比为 $1/(0.41 + 0.59/8) ≈ 2.15$。

也就是说，**当 TP 度从 4 增加到 8 时，理论加速比只提升了 15%，这与实际测量的结果基本一致。**

这意味着，:mdnice-bold-italic[对于 Qwen-2.5-32B 模型在 TP=4 的配置下，只要不可扩展开销的占比保持在 41%左右，无论我们使用多少个 GPU，系统的最大加速比永远不会超过 2.44 倍。这就是现有 LLM 推理系统的性能天花板。要突破这一天花板，唯一的方法就是降低不可扩展开销的占比，也就是提高 $P$ 的值。]

::: block-1
LLM 推理的核心瓶颈不再是 GPU 计算能力，而是占据单迭代 41%时间的不可扩展开销。这些开销限制了张量并行的最优度，导致现有系统的性能远低于理论值。突破阿姆达尔极限的唯一方法是消除这些不可扩展开销。
:::

## 二、Albireo 的核心设计：三重优化打破阿姆达尔极限

> 阿姆达尔定律告诉我们，要提升并行系统的性能，最有效的方法是减少串行部分的占比。Albireo 正是遵循这一原则，将不可扩展开销分为两类：可重叠的（调度、输入处理、输出处理）和不可重叠的（采样）。

- 对于前者，通过异步执行与计算重叠；
- 对于后者，**通过并行化将其转化为可扩展部分。**

### 2.1 乐观异步调度：打破迭代间的资源依赖

> 现有推理引擎使用的是同步调度：第 n+1 次迭代的调度必须等待第 n 次迭代的输出处理完成，因为调度需要知道哪些序列已经结束，从而释放 KV 缓存资源。这种严格的顺序执行导致调度任务完全串行，无法与前向传播重叠。

异步调度的核心挑战在于资源依赖：在第 n 次迭代还在执行时，我们无法准确知道哪些序列会在本次迭代中结束，因此无法准确计算下一次迭代需要的 KV 缓存块数量。如果预测错误，就可能导致 KV 缓存不足，引发请求抢占或换出，反而降低性能。

> 为了解决这一问题，Albireo 提出了**乐观单迭代预测策略**：

1. **假设所有序列都不会在当前迭代中结束**，因此每个序列都需要额外一个 KV 缓存块
2. 基于这一假设，**提前计算下一次迭代** 需要的 KV 缓存块数量，并进行预分配
3. 当第 n 次迭代结束后，根据实际完成的序列，**修正** KV 缓存的分配

这一策略的有效性基于一个简单的事实：对于一个生成 N 个 token 的序列，预测会成功 N-1 次，只有最后一次会失败。因此，:mdnice-bold-italic[最坏情况下，每个序列只会浪费一个 KV 缓存块]。论文的实验表明，这种额外的内存开销可以忽略不计，因为 KV 缓存是以块为单位分配的（通常每个块包含 16 个 token），即使一个序列提前结束，剩余的块空间也可以被其他序列使用。

为了实现异步调度，Albireo 还引入了迭代依赖的序列管理机制，为每个序列跟踪三个状态：

- 预期长度（EL）：第 n 次迭代开始时的序列长度
- 当前长度（CL）：第 n 次迭代结束时的序列长度
- 新 token 数量（NNT）：第 n 次迭代预期生成的 token 数量

通过这三个状态，调度器可以在不知道第 n 次迭代结果的情况下，准确预测第 n+1 次迭代的资源需求。这种单迭代异步调度的优势在于：

- 完全隐藏了调度的 CPU 开销，将调度时间从 4ms 降低到了 5μs
- 避免了多迭代异步调度带来的调度失效问题（新请求到达时需要重新调度）

### 2.2 早期反馈回填：实现输入输出处理与计算的完全重叠

> 输入处理的核心依赖是前一次迭代的采样结果：第 n+1 次迭代的模型输入需要包含第 n 次迭代生成的 token。在现有系统中，输入处理必须等待第 n 次迭代的输出处理完成才能开始，这导致输入处理无法与前向传播重叠。

Albireo 的早期反馈回填机制打破了这一依赖。它的核心洞察是：**输入处理中只有最后一个 token 依赖前一次的采样结果，其他所有部分（元数据计算、张量分配、数据传输）都可以提前完成。**

具体来说，Albireo 将输入处理分为三个步骤：

1. 计算元数据 $X_M$（如 KV 缓存的位置信息）
2. 分配所有张量，包括最后一个 token 的占位符 $X_T$
3. 将除 $X_T$ 之外的所有张量传输到 GPU

当第 n 次迭代的采样结果生成后，通过一个快速通道直接回填到 $X_T$ 的位置。这样，输入处理的大部分工作都可以在第 n 次迭代的前向传播过程中完成，只有最后的回填操作需要等待采样结果。

同样，输出处理也可以通过早期反馈机制提前开始。当一个 token 被采样出来后，立即发送给输出处理器进行反 token 化和终止条件检查，而不需要等待整个批次的采样完成。这进一步隐藏了输出处理的开销。

::: block-1
通过早期反馈回填机制，Albireo 将输入处理时间从 4ms 降低到了 40μs，输出处理时间从 0.5ms 降低到了 25μs。**这意味着，输入和输出处理的开销几乎完全被前向传播所隐藏。**
:::

### 2.3 序列并行采样：将串行采样扩展到多 GPU

> 采样是唯一无法通过重叠来隐藏的不可扩展开销，因为它必须等待前向传播完成才能开始。在现有系统中，采样只运行在主 GPU 上，其他 GPU 在采样期间处于空闲状态。对于 TP=4 的配置，采样时间占比 16.9%，这意味着有 16.9%的时间，3/4 的 GPU 资源被浪费了。

采样难以并行化的原因有两个：

1. 张量并行是沿着词汇表维度分割的，每个 GPU 只拥有部分 logits。要进行采样，需要先将所有 GPU 的 logits 收集到主 GPU 上，这会引入昂贵的集合通信开销
2. 采样需要每个序列的元数据（如温度、惩罚系数等），序列化和广播这些元数据会引入额外的开销

**Albireo 提出的序列并行采样** 从根本上解决了这两个问题。它的核心思想是：**沿着批次维度而不是词汇表维度分割采样任务，让每个 GPU 独立处理一部分序列的采样。**

具体来说，序列并行采样的工作流程如下（如图 7 所示）：

![文章插图](/articles/2026-06-11-albireo-vllm-sglang-llm-1-201f3d97/images/10.webp)

::: image-caption
图 7：序列并行采样执行流程。 传统推理中采样仅由主 GPU 执行，多 GPU 集群算力严重闲置，序列并行采样则按批次维度切分采样负载，结合散射、全交换、聚合通信实现分布式采样。方案将采样元数据散射操作与 GPU 前向计算重叠，天然掩盖通信开销；用全交换操作替代传统聚合，在转置 Logits 数据的同时不增加额外传输量。同时搭配批量填充、确定性随机数生成等细节优化，保证并行采样结果与串行完全一致。该优化补齐了张量并行仅加速前向计算的短板，在高 TP 度的大模型部署场景中收益尤为显著。
:::

1. 主 GPU 在**前向传播开始时**，将采样元数据分散（scatter）到各个 GPU。这一步与前向传播重叠，因此不会引入额外的开销
2. 前向传播完成后，每个 GPU 拥有部分词汇表的 logits。通过 all-to-all 操作，将 logits 沿着批次维度重新分布，使得每个 GPU 拥有完整批次中一部分序列的完整 logits
3. 每个 GPU 独立对自己负责的序列进行采样
4. 主 GPU 收集（gather）所有 GPU 的采样结果，进行后续处理

这一设计的关键优势在于：

- all-to-all 操作的通信量与原来的 gather 操作完全相同，没有引入额外的通信开销
- 元数据的分散与前向传播重叠，完全隐藏了元数据传输的开销
- 采样任务被均匀分布到所有 GPU 上，采样时间与 TP 度成反比

为了保证采样结果的确定性，Albireo 还采用了确定性随机数生成策略：在所有 GPU 上预生成所有需要的随机数，每个 GPU 只使用自己负责的部分。这虽然会消耗少量的 GPU 内存（每个请求约 128KB），但避免了随机数同步的开销。

通过序列并行采样，Albireo 将采样时间从 6ms 降低到了 1.5ms（TP=4），减少了 75%的采样开销。对于 TP=8 的配置，采样时间可以进一步降低到 0.75ms，几乎可以忽略不计。

::: block-1
Albireo 通过三重核心优化，消除了超过 89%的不可扩展开销：乐观异步调度将调度开销降低了 99.9%，早期反馈回填将输入输出处理开销降低了 99%，序列并行采样将采样开销降低了 75%。这使得可扩展部分的占比从 59%提升到了超过 95%，从而突破了阿姆达尔定律的限制。
:::

## 三、实现细节与工程优化

> 一个优秀的系统设计不仅需要精妙的算法，还需要扎实的工程实现。Albireo 在设计之初就考虑了易用性和兼容性，采用了框架无关的插件式架构，同时在多个工程细节上进行了深度优化，确保了系统的高性能和稳定性。

Albireo 的核心代码约 8500 行 C++，**以插件的形式实现**，可以轻松集成到任何现有的 LLM 推理框架中。论文中展示了**与 vLLM 的集成，仅需要修改约 200 行代码**。这种模块化的设计使得 Albireo 可以快速跟进上游框架的更新，同时也方便其他框架采用其优化技术。

### 3.1 框架无关的插件式设计

> Albireo 的架构设计遵循了最小侵入原则，它没有修改现有推理框架的核心逻辑，而是**通过新增四个独立的组件来替换原有的调度、输入处理、输出处理和采样模块**。这四个组件通过定义良好的接口与框架交互：

- 异步调度器：替换原有的同步调度器，提供相同的调度输出接口
- 异步输入处理器：接收调度输出，生成模型输入队列
- 并行采样器：接收模型输出的 logits，生成采样结果队列
- 异步输出处理器：接收采样结果，更新序列状态，返回生成的文本

这种设计的优势在于：

- 兼容性好：可以集成到任何支持张量并行的推理框架中
- 可维护性高：核心优化逻辑与框架解耦，便于独立开发和测试
- 可扩展性强：可以轻松添加新的优化技术，而不需要修改框架代码

### 3.2 并行输出处理的工程优化

> 虽然输出处理的原始占比只有 1.4%，但在:mdnice-bold-italic[高负载情况下，输出处理的开销可能会显著增加。这是因为现有框架通常使用 Python 循环来处理每个序列的输出，串行执行反 token 化和终止条件检查]。当批量大小较大时，这部分开销可能会超过前向传播的时间。

Albireo 对输出处理进行了深度优化，将其分为四个独立的步骤，并对每个步骤进行了并行化：

1. 序列更新：将新采样的 token 和概率追加到序列
2. 解码：将 token ID 转换为文本
3. 终止检查：检查序列是否满足终止条件
4. 资源释放：释放已完成序列的 KV 缓存和其他资源

其中，序列更新和终止检查是完全独立的，可以通过线程池并行执行。解码步骤由于依赖线程不安全的反 tokenizer，无法直接并行，但 Albireo 通过两个快速查找表来加速解码过程：

- 单 token 查找表：缓存所有 token ID 对应的文本，实现 O(1)查找
- 双 token 查找表：缓存常见的 token 对对应的文本，解决反 token 化中的上下文依赖问题

::: block-1
根据 Zipf 定律，自然语言中的 token 对分布是高度倾斜的，少数常见的 token 对占据了绝大多数的出现次数。Albireo 缓存了 $10^9$ 个最常见的 token 对，实现了超过 99%的命中率。当查找失败时，才调用原始的反 tokenizer 进行解码。
:::

通过这些优化，Albireo 将输出处理的时间从原来的约 7ms（完整处理时间）降低到了不到 2ms，确保了输出处理的开销永远不会成为系统的瓶颈。

### 3.3 确定性与性能的平衡

> 在推理系统中，结果的确定性是一个非常重要的要求。对于相同的输入和随机种子，系统应该产生完全相同的输出。**序列并行采样引入了多 GPU 并行计算，可能会导致结果的不确定性。**

为了保证确定性，Albireo 采取了以下措施：

1. **确定性随机数生成**：在所有 GPU 上预生成相同的随机数序列，每个 GPU 只使用自己负责的部分
2. **确定性集合通信**：使用确定性的 all-to-all 和 gather 操作，保证数据传输的顺序
3. **批量填充**：当批量大小不能被 TP 度整除时，使用合成数据填充批量，确保每个 GPU 处理相同数量的序列

**这些措施虽然会引入少量的额外开销（批量填充的通信开销小于 10KB），但保证了采样结果与串行采样完全一致**。论文的实验验证了，在相同的输入和随机种子下，Albireo 与 vLLM 产生的输出完全相同。

- 在 A100^N 上，Albireo 的吞吐量提升最高达 1.7 倍
- 在 A100^P 上，吞吐量提升最高达 1.4 倍

A100 上的收益略低于 H100，是因为 A100 的计算能力较弱，前向传播的占比更高，不可扩展开销的影响相对较小。**这也验证了论文的核心洞察：随着 GPU 计算能力的提升，不可扩展开销的影响会越来越大，Albireo 的收益也会越来越明显。**

> 最令人兴奋的结果是，Albireo 实现了超线性的张量并行扩展。如图 10 所示：

![文章插图](/articles/2026-06-11-albireo-vllm-sglang-llm-1-201f3d97/images/13.webp)

::: image-caption
图 10：张量并行度（TP）对吞吐率的影响。虚线代表最优经验张量并行度 $t_e$。虚线左侧区间内，Albireo 不仅性能优于基线方案，还实现超线性扩展，即张量并行度为 $2n$ 时的吞吐率超过并行度为 $n$ 时的 2 倍。 vLLM、SGLang 的最优 $t_e$ 偏低，提升 TP 度后通信与串行开销快速上涨，吞吐率持续下滑，严格受阿姆达尔定律约束。Albireo 有效抬高了各类模型的最优 $t_e$：中规模模型 $t_e$ 从 2 提升至 4，大规模模型从 4 提升至 8。在 $t_e$ 以内区间出现超线性扩展，核心原因是更高 TP 度拆分模型权重，释放大量显存用于 KV 缓存，减少缓存置换、请求抢占等性能损耗。这一现象说明：消除非可扩展开销后，系统能充分利用张量并行的内存优势，在固定 GPU 预算下实现集群吞吐最大化。

从图中可以看到：

- 在 vLLM 和 SGLang 中，吞吐量随 TP 度的增加呈现**亚线性增长**，即 $T(2t) < 2T(t)$。
- 而在 Albireo 中，当 $t ≤ t_e$ 时，吞吐量呈现**超线性增长**，即 $T(2t) ≥ 2T(t)$。

::: block-1
这是因为，**随着 TP 度的增加，Albireo 不仅没有被不可扩展开销拖累，反而通过序列并行采样进一步降低了采样开销，同时更大的内存容量减少了 KV 缓存的换入换出，从而实现了超线性扩展。**
:::

- **对于 Qwen-2.5-32B 模型，Albireo 将最优 TP 度从 2 提升到了 4**，因此在 8-GPU 节点上，可以部署 2 个 TP=4 的实例，:mdnice-bold-italic[总吞吐量达到了 vLLM 的 1.9 倍。]
- **对于 Llama-3.1-70B 模型，Albireo 将最优 TP 度从 4 提升到了 8**，因此在 8-GPU 节点上，可以部署 1 个 TP=8 的实例，:mdnice-bold-italic[总吞吐量达到了 vLLM 的 1.9 倍。]

## 五、相关工作

LLM 推理优化是当前最活跃的研究领域之一，涌现出了大量的优秀工作。这些工作主要可以分为三类：异步执行优化、内核与运行时优化、KV 缓存优化。**Albireo 与这些工作是互补的，它解决了这些工作没有触及的不可扩展开销问题。**

### 5.1 异步执行优化

> 异步执行是提升 GPU 利用率的重要方法，其核心思想是将 CPU 任务与 GPU 计算重叠。代表性工作包括 Llumnix、SGLang 的零开销调度器和 vLLM 的异步调度器。

- Llumnix 提出了动态调度机制，通过分离调度和执行来提升 GPU 利用率。
- SGLang 的零开销调度器将调度逻辑移到了 C++中，减少了 Python 的开销。
- vLLM 的异步调度器实现了单迭代的异步调度，减少了调度延迟。

**但这些工作都存在一个共同的局限性：它们只实现了调度的异步，没有实现输入处理、采样和输出处理的完全异步。** 这是因为它们没有打破这些任务之间的数据依赖。:mdnice-bold-italic[例如，vLLM 的新兴异步调度器虽然将调度时间降低了最多 7.1%，但输入处理和采样仍然是串行的，因此整体性能提升有限。]

::: block-1
Albireo 通过早期反馈回填机制，打破了输入输出处理与采样之间的数据依赖，实现了所有 CPU 任务与 GPU 计算的完全重叠。同时，Albireo 还将采样任务并行化，进一步消除了 GPU 侧的空闲时间。
:::

### 5.2 内核与运行时优化

> 内核优化是 LLM 推理优化的传统方向，主要关注如何加速前向传播中的注意力和矩阵乘法计算。代表性工作包括 FlashAttention、FlashInfer、POD-Attention 和 vAttention。

- FlashAttention 通过重排注意力计算的顺序，减少了内存访问，显著提升了注意力计算的速度。
- FlashInfer 提供了高度优化的注意力和采样内核，支持多种注意力变体和采样策略。
- POD-Attention 融合了预填充和解码阶段，实现了两者的完全重叠。
- vAttention 使用 CUDA 虚拟内存来动态管理注意力状态，减少了内存碎片。

**这些工作都极大地提升了前向传播的速度，但它们都没有解决不可扩展开销的问题**。正如论文所指出的，:mdnice-bold-italic[当前向传播的速度越来越快时，不可扩展开销的占比会越来越高，这些内核优化的收益会被逐渐抵消。]

::: block-1
Albireo 与这些内核优化是完全兼容的。它可以与 FlashInfer、POD-Attention 等技术结合使用，进一步提升系统的性能。**实际上，论文中的实验已经使用了 vLLM 内置的 FlashAttention 内核。**
:::

### 5.3 KV 缓存优化

> KV 缓存是 LLM 推理中内存消耗最大的部分，因此 KV 缓存优化也是研究的热点。代表性工作包括 KV 缓存压缩（PyramidKV、SnapKV）、KV 缓存共享（RadixAttention）和多层 KV 缓存设计（InfiniGen、CachedAttention）。

这些工作通过压缩或共享 KV 缓存，减少了内存消耗，从而可以支持更大的批量大小和更长的序列长度。但它们都没有解决张量并行的扩展问题。当 KV 缓存的需求超过单 GPU 内存时，仍然需要使用张量并行，而不可扩展开销的问题仍然存在。

Albireo 通过提升最优张量并行度，间接扩展了 KV 缓存的容量。例如，对于 Qwen-2.5-32B 模型，Albireo 将最优 TP 度从 2 提升到 4，KV 缓存的可用容量从 96GB 增加到了 256GB，这相当于将 KV 缓存压缩了 2.67 倍。

::: block-1
现有 LLM 推理优化工作主要集中在加速前向传播和优化 KV 缓存上，没有触及不可扩展开销这一核心瓶颈。Albireo 填补了这一空白，通过消除不可扩展开销，突破了现有系统的性能天花板。Albireo 与现有优化技术完全兼容，可以结合使用以获得更高的性能。
:::

## 六、结论与展望

> 这篇论文通过深入的性能剖析，揭示了 LLM 推理中被长期忽视的不可扩展开销问题，并提出了一套完整的解决方案。Albireo 系统的成功，不仅为 LLM 推理优化指明了新的方向，也为未来的 AI 系统设计提供了重要的参考。

### 6.1 结论总结

论文的核心贡献可以概括为四个方面：

1. 性能分析：通过详细的性能剖析，发现非可扩展任务占据了 LLM 推理单迭代时间的 41%，是现有系统的核心瓶颈。同时，验证了最优张量并行度的存在性，并提出了简单的量化公式。
2. 可扩展并行化：提出了三重核心优化技术：乐观异步调度、早期反馈回填和序列并行采样，消除了超过 89%的不可扩展开销，将可扩展部分的占比从 59%提升到了超过 95%。
3. 系统实现：开发了 Albireo 推理系统，采用框架无关的插件式架构，可以轻松集成到现有推理框架中，仅需要约 200 行代码的修改。
4. 全面评估：在多个测试床上对 8 个不同大小的模型进行了全面评估，结果显示 Albireo 相比 vLLM 实现了最高 1.9 倍的吞吐量提升、48%的时延降低、28%的 GPU 利用率提升和 54%的能耗下降，在生产环境中达到了 2 倍的吞吐量提升。

Albireo 的成功证明了，**当 GPU 计算能力不再是瓶颈时，系统层面的流水线优化和任务并行化将成为未来 LLM 推理性能提升的主要来源。**

### 6.2 进阶分析

> 尽管 Albireo 取得了显著的性能提升，但我们也需要客观地认识到它的局限性和适用场景。

- 首先，Albireo 并没有从根本上解决阿姆达尔定律的问题，而是:mdnice-bold-italic[通过将不可扩展开销降低到几乎可以忽略的程度，在实际应用中突破了现有系统的性能天花板。理论上，仍然存在少量的不可扩展开销（如最后的结果收集和资源释放），但这些开销的占比已经低于 5%，对系统性能的影响可以忽略不计。]
- 其次，**Albireo 的收益与模型大小和 TP 度密切相关**。对于小型模型（如 7B），由于最优 TP 度是 1，序列并行采样无法发挥作用，因此性能提升只有约 1.3 倍。:mdnice-bold-italic[对于需要多节点流水线并行的超大型模型（如 1TB 以上），Albireo 的当前设计无法直接应用，因为流水线并行会引入新的不可扩展开销（如阶段间的通信气泡）。]
- 第三，Albireo 的:mdnice-bold-italic[乐观异步调度策略存在一个隐性的内存开销：每个序列最多可能浪费一个 KV 缓存块。对于非常短的序列（如生成 1-2 个 token），这一开销的占比会相对较高]。但在实际应用中，大多数生成长度都超过 16 个 token，因此这一开销可以忽略不计。
- 最后，Albireo 的性能提升是在高负载下实现的。在低负载下，由于批量大小较小，不可扩展开销的占比相对较低，因此 Albireo 的收益会有所减少。但即使在低负载下，Albireo 仍然能够带来一定的吞吐量提升。

### 6.3 未来工作

> 论文作者在最后指出了未来的研究方向：

1. 扩展到多节点混合并行部署：当前的 Albireo 仅支持单节点内的张量并行优化。未来需要将其扩展到混合张量并行-流水线并行的多节点部署中，解决阶段间的通信效率和负载不平衡问题。
2. 结合新的硬件特性：随着 GPU 硬件的不断发展，新的特性（如更快的集合通信、更灵活的内存管理）将为进一步消除不可扩展开销提供新的机会。

随着 LLM 模型的不断增大和 GPU 计算能力的不断提升，不可扩展开销的问题会变得越来越重要。Albireo 的工作只是一个开始，未来还有更多的优化空间等待我们去探索。
