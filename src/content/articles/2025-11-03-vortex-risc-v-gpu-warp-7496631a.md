## 关键问题

### 问题 1. 如何基于核函数特性、内存访问特征与面积约束，建立量化决策模型以精准选择 Vortex RISC-V GPU 中 Warp 级特性的软硬件实现方案？

> 本文中硬件实现方案虽以仅 2%的每核面积开销实现了最高 4 倍的 IPC 性能提升，但实验显示 mse forward 核在软件方案中因减少内存访问反而相对硬件方案更具优势，那么在实际场景中，**应建立怎样的量化决策模型** （如结合核函数类型、内存访问特征、性能需求与面积约束等维度），**才能精准判断何时选择硬件方案、何时选择软件方案**，而非仅依赖定性的场景描述？

关于建立量化决策模型以精准选择软硬件方案的问题，当前研究虽未直接提出完整模型，但可基于文中实验数据与方案特性推导核心决策维度及初步量化逻辑：

1. **核函数类型与 Warp 级特性依赖度**：文中实验表明，依赖 Warp 级函数（如 vote、shuffle）或归约操作的核（reduce、reduce tile），硬件方案因指令直接访问寄存器而非内存，可实现近 4 倍 IPC 提升，此类核应优先选择硬件方案；而无 Warp 级集合操作的核（如 matmul），软件方案因循环序列化产生 30%性能损失，硬件方案仍更优，但优势幅度缩小。
2. **内存访问特征**：仅 mse forward 核因软件方案通过循环序列化减少内存访问，展现出相对硬件方案的优势，这提示:mdnice-bold-italic[“内存访问密集且可通过软件优化降低访问量”是软件方案的核心适用场景]，可:mdnice-bold-italic[通过量化“Warp 级操作内存访问占比”判断] ——若该占比高于某阈值（如文中 mse forward 的内存优化收益覆盖软件指令开销），则软件方案更优。
3. **面积约束阈值**：硬件方案每核总资源开销约 2%，其中 CLB 资源增长最显著（SLR0 增 1.08%、SLR1 增 0.43%），可将“硬件资源余量是否高于 2%核面积”作为基础量化指标——若面积余量低于该阈值（如资源受限的边缘计算场景），则强制选择软件方案；若余量充足，再结合前两维度进一步判断。

综上，初步量化决策模型可按“**面积约束筛查 →Warp 级特性依赖度判断 → 内存访问特征验证** ”的流程构建，文中实验数据（如不同核的 IPC 提升幅度、硬件面积开销）可作为模型中各维度的量化基准，但具体阈值（如内存访问占比临界值）需后续补充更多核类型实验以校准。

### 问题 2. 硬件实现中多 Warp 合并的线程依赖冲突如何通过现有架构规避，调度单元 overhead 是否会削弱性能优势及如何进一步优化？

> 本文硬件实现通过新增 vx_tile 指令动态调整 Warp 大小以支持协作组，且默认基于“块级同步转化为 Warp 级同步”的设计思路，然而**该设计未提及如何处理多 Warp 合并后可能出现的线程依赖冲突** （如不同 Warp 原有的寄存器访问优先级冲突），以及**当协作组粒度频繁变化时调度单元的 overhead 增长问题**，这些潜在问题是否会削弱硬件方案的性能优势，又该如何在架构设计中进一步优化以规避？

关于多 Warp 合并后的线程依赖冲突与调度单元 overhead 问题，文中虽未直接提及冲突规避细节与 overhead 量化数据，但可从现有架构设计与实验结果推断潜在解决方案及影响边界：

1. **线程依赖冲突规避**：文中提到硬件方案通过“添加交叉开关替代多路复用器”确保数据在执行阶段的可用性，同时“由带 Warp 配置的调度器控制交叉开关，管理执行单元以保证正确执行”，且要求“为每个 Warp 分配正确的寄存器组并确保仅该 Warp 可访问”——这一系列设计已从硬件层面规避寄存器访问优先级冲突，即通过专属寄存器组隔离与交叉开关的精准数据路由，防止多 Warp 合并后的资源竞争。
2. **调度单元 overhead 影响**：文中指出硬件方案的所有修改（含协作组同步逻辑）“均局限于调度单元”，且实验显示硬件方案仅增加 2%核面积，未出现因调度 overhead 导致的性能抵消——这表明调度单元的修改幅度可控，其 overhead 在当前架构设计中未削弱性能优势。若需进一步优化，可结合文中“动态调整 Warp 大小”的逻辑，在调度器中增加“Warp 合并粒度预测模块”，避免频繁的粒度切换（如优先维持固定粒度，仅在协作组指令强制要求时调整），以降低调度 overhead。

综上，**文中硬件架构设计已包含冲突规避的核心机制，调度单元 overhead 当前未对性能优势产生显著影响**，:mdnice-bold-italic[进一步优化可围绕“减少 Warp 粒度切换频率”展开]，且现有设计预留了优化空间（如调度器的 Warp 配置管理功能可扩展预测逻辑）。

## 一、引言

> 近年来，GPU 编程模型通过 warp 级特性实现了细粒度并行，扩展了 GPU 编程的范围。这种扩展允许 GPU 在 SPMD 编程模型内运行，同时通过细粒度线程控制偏离传统 SPMD 范式。

特别是 CUDA[1,2]（最广泛使用的 GPU 编程模型之一）引入了**协作组（cooperative groups）** 和 **warp 级函数** 等 warp 级特性，以**促进细粒度线程控制和同步**。

::: block-1
这些 warp 级特性提供了超越固定大小粒度和同步的抽象，支持更复杂的代码并减少对块级同步屏障的需求。
:::

因此，在 RISC-V GPU[3-9]中支持 warp 级特性可以通过增强其通用性和适用性来创造机会。尽管 RISC-V GPU（如 Vortex RISC-V GPU[3-5]）通过公开可用的软硬件栈为支持 GPU 应用提供了有前景的路径，并为多样化的 GPU 硬件特性提供了高度可重构性，但它们缺乏对 warp 级功能等最新高级特性的支持。因此，它们错过了通过结合 warp 级特性利用其可重构硬件特性（如线程和 warp 数量）来探索更高性能的机会。

> 为了高效支持 warp 级特性，我们通过考虑纯软件和硬件支持的方法及其各自的权衡，在 Vortex GPU 上探索实现方法。

- 虽然硬件扩展可以提供性能优势，但也会产生额外的面积成本。
- 相反，纯软件方法避免了硬件开销，但需要额外的指令开销和编译器支持。

**为了支持这两种方法，我们在 Vortex RTL 中实现这些特性并扩展编译器支持。**

::: block-1
通过对两种实现方法的比较分析，本文评估了这些方法如何支持 warp 级特性并适应 Vortex GPU 架构。结果表明，支持 warp 级特性所需的硬件开销极小，逻辑面积仅增加 2%，而在微基准测试中，**软件和硬件实现之间的性能差异可达 4 倍。**
:::

## 二、背景

### A. Vortex RISC-V GPU

> 最近，一些研究[3-5]提出了名为 Vortex GPU 的 RISC-V GPU，其特点是高度可重构的架构和模块化、全面的软件栈。

Vortex GPU 支持各种硬件配置（如调整线程和 warp 数量），其**软件栈提供对 CUDA[1,2]和 OpenCL[10]等多种编程模型的编译器支持**。由于其软硬件栈完全开源，一些研究[11-13]扩展了 Vortex GPU 以增强 GPU 特性并探索新的优化。

![文章插图](/articles/2025-11-03-vortex-risc-v-gpu-warp-7496631a/images/03.webp)

::: image-caption
图1：Vortex GPU及软件栈
:::

> 图 1 显示了 Vortex GPU 硬件架构及其软件栈的概述。

- **GPU 架构** 由集群（Cluster）、插槽（Socket）和核心（Core）**三级层次结构** 组成。
- 集群和插槽通过 L1 和 L2 缓存连接，核心具有六级流水线，包含自己的寄存器文件、程序计数器（PC）和 warp 调度器。
- 软件栈由两种不同的编译器组成：前端编译器（如支持 CUDA 的 CuPBoP[14]）和将内核翻译成 Vortex 指令集架构（ISA）设备内核的后端编译器。
- Vortex 还支持 Vortex 运行时库，用于管理主机 CPU 和 GPU 之间的通信。
- 集群和插槽通过L1和L2缓存相连，核心具有六级流水线，以及自己的寄存器文件、程序计数器（PC）和线程束调度器。

该软件栈包含两种不同的编译器：

::: block-1
- 一种是前端编译器，例如用于支持CUDA的CuPBoP [14]；
- 另一种是后端编译器，用于将核函数转换为包含 Vortex 指令集架构（ISA）的设备核函数。
:::

Vortex 还支持 Vortex 运行时库，以管理主机 CPU 和 GPU 之间的通信。

### B. CUDA Warp 级特性

> CUDA[1,2]是 NVIDIA 提出的广泛使用的编程模型之一。

CUDA 编程模型采用三级层次结构：内核表示在 GPU 上执行的函数，作为包含多个线程块的网格启动，每个线程块包含一组线程。块内线程可以通过共享内存和同步协作，而执行遵循 SPMD 模型。

::: block-1
然而，为 SPMD 范式设计的**传统 CUDA 编程模型** 【缺乏】**细粒度线程控制和超越块或 warp 级的高效同步**。:mdnice-bold-italic[这些限制会降低需要频繁线程间通信或细粒度并行的工作负载的性能。]

**为解决这一问题，CUDA 引入了 warp 级特性**，如 warp 级函数和协作组。
:::

#### Warp 级函数（Warp-Level Functions）

通过交换寄存器值实现线程间快速数据共享，并在 warp 内提供细粒度同步[2]。CUDA 提供了几种 warp 级原语，包括 shuffle（洗牌）、reduce（归约）、vote（投票）和 match（匹配）。特别是 shuffle 原语促进线程间的值交换，而 vote 原语聚合 warp 内特定条件的满足状态。

#### **协作组** （Cooperative Groups）

支持灵活的用户定义线程层次同步和分组，超越传统编程模型层次结构[2]。

最初，CUDA 仅提供用于同步块内线程的屏障，后来引入了 warp 级同步。协作组提供了在块内不同粒度同步线程的安全方法，并将同步能力扩展到传统屏障之外，以提高程序效率。此外，协作组提供了用于定义和管理不同级别线程组的抽象。有组织的接口允许开发人员显式表达线程分组逻辑，并编写安全、可维护和高效的代码。

---

由于 warp 级特性可以改进 GPU 编程范式，**在 Vortex GPU 中支持这些特性可以扩展其通用性和适用性**。

> 本文重点关注**通过纯软件和硬件支持两种方法支持协作组和 warp 级函数** （shuffle 和 vote），从性能和面积角度分析其效率。

> 为了在硬件层面支持 warp 级函数和协作组，我们需要架构修改和 ISA 扩展。

![文章插图](/articles/2025-11-03-vortex-risc-v-gpu-warp-7496631a/images/05.webp)

::: image-caption

:::

**Warp 级函数**：为了支持 vote 和 shuffle 函数，我们修改了 ALU 以分别交换和计数寄存器值，并修改了解码器以支持新指令 vx_vote 和 vx_shfl。如表 I 所示，vote 和 shuffle 操作都支持四种不同模式，由指令的功能字段决定。此外，vote 的立即数字段包含存储成员掩码的寄存器地址，在执行前被获取。类似地，shfl 的立即数字段包括通道偏移量和存储钳位值的寄存器地址。

**协作组**：我们通过修改架构以支持可变 warp 结构来实现协作组，从而实现跨不同粒度的同步。我们的设计基于这样的思想：warp 内的线程可以同步，而跨线程块的同步被转换为 warp 级同步。默认情况下，warp 以固定大小启动，并在有协作组指令时通过合并或拆分动态重塑以匹配组大小。

为支持这一思想，我们引入了 vx_tile 指令，该指令将组掩码和线程计数作为操作数来区分线程执行。

![文章插图](/articles/2025-11-03-vortex-risc-v-gpu-warp-7496631a/images/06.webp)

::: image-caption
表II：按区块设置的配置
:::

例如，表 II 提供了当核心中的硬件线程大小为 32 时四种不同线程执行模式的配置。使用协作组时，核心可以用 4 个线程的 warp 初始化，并动态将它们合并为用户指定线程数的更大 warp，如 16 个线程。

在合并时，Vortex 必须通过为每个 warp 分配正确的寄存器组并确保仅该 warp 可访问来防止错误执行。因此，我们添加了一个交叉开关（cross-bar）而非多路复用器，以确保执行阶段的数据可用性。具有 warp 配置的调度器通过控制交叉开关管理执行单元，以确保正确执行。此外，我们修改了执行单元，以保证当输出依赖于组大小时的正确操作。同步由现有的单 warp 支持处理，或通过修改合并 warp 的组同步退出条件处理，所有更改都局限于调度单元。

## 四、软件解决方案

> 本节提出了一种扩展的并行区域转换算法，以在没有 Vortex 硬件支持的情况下支持 warp 级特性。

::: block-1
并行区域转换的核心思想是识别 GPU 内核中可以并行执行的区域（称为并行区域），并应用循环序列化将软件线程块映射到硬件线程[14,15]。
:::

基于这一思想，我们通过合并嵌套循环和发散控制来扩展并行区域转换算法，以支持 warp 级特性。

提出的并行区域转换算法（PR 转换）包括以下过程：

::: block-1
1. 前端编译器识别并行区域。并行区域的边界由跨线程操作定义，包括同步、块分区、warp 级操作和协作组操作。
2. 编译器执行控制结构分裂，以便在 if 或 if-else 结构跨越多个并行区域时应用发散控制。例如，应用 if-else 分裂后，图 3a 中的内核被分为四个有色并行区域，如图 4a 所示。
3. 之后，编译器移除仅包含同步和分区函数的并行区域。因此，图 4a 中的灰色 PR 被移除。
4. 编译器应用循环序列化，考虑第 四-A 节中的 warp 级特性转换规则。 通常，每个并行区域使用单个循环转换，如图 4b 中的橙色块。然而，编译器对 warp 级函数使用嵌套循环序列化。例如，编译器对 vote 函数应用嵌套循环序列化，如图 4b 的蓝色区域所示。
5. 编译器应用优化来处理特殊变量，包括线程和块索引。变量被替换为其序列化对应物。例如，threadIdx.x 在单个循环中被替换为 loopIdx，或在嵌套循环中被替换为 outerIdx×warpSize+innerIdx。如图 4b 所示，线程局部变量被转换为数组，线程索引的引用被替换为循环索引。
:::

## 五、评估

> 我们通过扩展 Vortex RISC-V GPU[3,4]评估我们的软件和硬件解决方案。

- **为进行性能评估，我们使用 Vortex GPU 的 SimX 周期级模拟器[4]和六个不同的基准测试**。基准测试包括两个计算内核（mse_forward[16]、matmul）、两个功能测试（shuffle、vote[17]）和两个归约内核（reduce、reduce_tile[17]）。
- **为进行面积成本估计，我们使用 Xilinx U50 FPGA（xcu50-fsvh2104-2-e）的 Vivado Design Suite 2023.1 进行配置综合**。

对于这两种评估，Vortex GPU 配置为每个核心 8 个线程/ warp 和 4 个 warp/线程块。

> 图 5 显示了硬件和软件解决方案的 IPC（每周期指令数），硬件解决方案相比软件解决方案实现了 2.42 倍的几何平均加速。

- mse_forward 内核使用 shuffle_down 函数，因此具有软件解决方案的该内核通过减少内存访问比硬件解决方案受益于循环序列化。
- matmul 不涉及 warp 级集合操作，但该内核在软件解决方案中表现出循环序列化开销，导致**与硬件解决方案相比性能损失 30%。**
- vote、shfl（测试 shfl_sync）、reduce 和 reduce_tile 内核通过**硬件解决方案实现了近 4 倍的加速**，因为:mdnice-bold-italic[指令直接访问寄存器而非使用内存。]

尽管硬件解决方案总体上表现出良好的性能，但 mse_forward 和 matmul 的结果表明，**从性能角度来看，基于软件的解决方案对于【某些】内核【可能】是可行的替代方案。**

## 六、结论

> 本文探讨了支持 warp 级特性的硬件和软件方法，并评估了它们的权衡。

硬件实现在最小开销下扩展了 Vortex ISA，每个核心利用约 2%的 CLB 资源，从而为某些内核带来性能提升。虽然硬件支持提供了卓越的性能优势，**但当面积成本至关重要时，基于软件的解决方案是可行的**。因此，:mdnice-bold-italic[用户可以根据应用需求和面积约束在硬件和软件实现之间进行选择。]

未来的工作可能探索复杂操作的硬件加速，如归约，以及在利用硬件特性的同时支持将可变 CUDA 线程映射到 Vortex 线程。
