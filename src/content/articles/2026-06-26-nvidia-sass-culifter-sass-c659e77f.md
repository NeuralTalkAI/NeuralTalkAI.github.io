## 一、行业痛点：SASS 二进制逆向长期无解的底层根源

> 很多异构、AI Infra 从业者会疑惑，**CPU 二进制反编译工具早已形成完整生态，为什么 GPU 底层 SASS 汇编的逆向工具始终空白？** 二者看似都是硬件机器码，底层存储、执行模型的结构性差异，造成了逆向难度天差地别。

CPU 架构将整数、浮点数拆分至两套完全独立的寄存器堆，浮点运算只能使用 XMM/YMM 寄存器，整数运算仅使用通用寄存器，硬件天然携带类型线索。编译器即便做激进优化，也不会出现同一物理寄存器交替承载浮点、整数数据的场景，**逆向工具可直接从寄存器编号区分数据类型。**

### 1.1 CPU 与 GPU 底层汇编的结构性鸿沟

> 下表对比 GPU 原生机器码 SASS 与编译器通用中间表示 LLVM IR 的核心设计差异，也是**现有工具无法直接复用 CPU 逆向方案的根本原因。**

![文章插图](/articles/2026-06-26-nvidia-sass-culifter-sass-c659e77f/images/05.webp)

::: image-caption
表 1：SASS 与 LLVM IR 的核心结构差异对比表。本表直观解释现有 CPU 二进制提升工具（McSema、rev.ng）无法复用至 SASS 的底层鸿沟。SASS 采用无类型统一寄存器、谓词隐式条件执行、硬件专属张量指令；LLVM IR 是强类型 SSA、显式分支、通用抽象张量内建函数。SASS 寻址、控制流、张量操作均绑定 GPU 硬件架构，无通用抽象层，无法直接转换为 LLVM。

- LLVM IR 是全编译链路的通用交换介质，漏洞检测、性能调优、跨架构移植全部依赖该格式；
- 而 SASS 完全抛弃类型、结构化控制流，二者存在不可逆信息损耗，直接导致传统提升工具无法落地 GPU 场景。

::: block-1
二者底层表达差异迫使本文从零设计三阶段提升流水线，无法复用成熟 CPU 逆向工具链，清晰论证 CuLifter 研究工作的必要性，同时明确各阶段需要解决的结构映射问题。
:::

### 1.2 SASS 编译过程中三大不可逆信息丢失

> CUDA 源码编译链路分为两层：源码 →PTX→SASS。PTX 保留完整类型标注、结构化循环分支，**但 PTX 经过硬件专属编译器降级至 SASS 时，三层核心信息会被永久抹除**，且无任何硬件存储备份。

1. **数据类型信息**：统一寄存器堆消除所有数据标识，编译器为了加速运算频繁执行类型双关（bit reinterpret），:mdnice-bold-italic[例如下图快速平方根倒数运算中，寄存器先作为浮点数运算，不经任何转换指令直接读取为整数提取指数位。]

![文章插图](/articles/2026-06-26-nvidia-sass-culifter-sass-c659e77f/images/06.webp)

::: image-caption
Listing 1：编译后的 rsqrt 逆平方根代码，寄存器 R25 无任何转换指令就切换浮点、整数两种使用类型。R25 先经 FADD、MUFU 浮点运算，紧接着 IADD3 当作指数整数解析，无硬件转换指令分隔；CPU 提升工具分离浮点、通用寄存器，不会遇到同类问题。若缺失约束传播冲突检测，LLVM IR 会强制 R25 单一 Float32 类型，整数减法语义完全错误，产生无报错静默数值偏差。
:::

1. **结构化控制流**：SIMT 单指令多线程模型使用谓词寄存器掩码实现条件执行，不再使用 CPU 式 if-else 分支，:mdnice-bold-italic[同一基础块内多条指令受不同谓词控制，标准 SSA 重命名算法会直接覆盖寄存器有效值，产生语义错误。]
2. **高层运算语义**：编译器将 64 位加减、张量乘加、异步共享内存拷贝等:mdnice-bold-italic[高阶算子拆分为多条独立 SASS 指令，单条汇编无法还原原始运算意图，逐行提升会丢失访存融合、同步屏障等关键硬件语义。]

### 1.3 现有 SASS 工具全部存在底层能力短板

> **行业现存四类 SASS 处理工具，全部无法输出可用于编译分析的带类型 LLVM IR**，【仅】能完成基础汇编展示或插桩，:mdnice-bold-italic[不具备二进制提升能力：]

1. 官方反汇编工具 nvdisasm、cuObjDump：仅输出平铺无结构汇编文本，无 CFG 控制流图、无类型标注，无法做数据流分析；
2. 动态插桩框架 NVBit、静态插桩 SASSI：仅支持运行时指令计数、内存日志采集，不具备反编译、中间表示生成能力；
3. 汇编优化 CuAsRL、跨架构翻译 CASS：前者基于强化学习调度指令，后者仅完成 AMD 汇编层级转译，二者均不恢复类型与控制流；
4. 局部 CFG 构建工具 GPUscout：仅针对 SASS 做内存访问模式匹配分析。

::: block-1
现有工具全部停留在“指令观测”层面，:mdnice-bold-italic[没有一套完整流水线修复编译器抹除的类型、控制流、高层语义三类关键信息， CuLifter 是首个打通从原始 SASS 到合法 Typed LLVM IR 全链路的框架。]
:::

## 二、CuLifter 核心洞察：GPU 逆向是三重丢失结构的修复工程

> 过去 GPU 逆向研究普遍单独针对控制流或单独针对类型做局部优化，:mdnice-bold-italic[没有建立全局统一修复框架。 CuLifter 团队提出全新顶层框架：SASS 逆向本质是三类编译丢失信息的【分步重建】，且三类修复存在严格先后依赖关系。]

若颠倒处理顺序，先做类型推理再构建控制流，未完成 SSA 转换的寄存器多定义问题会让数据流图完全错乱，类型约束传播会产生海量虚假冲突，推理结果完全失效。

### 2.1 三类丢失结构对应的分层修复方案

> **CuLifter 划定固定处理顺序：控制流重建 → 高层语义模式归一化 → 寄存器类型恢复**，:mdnice-bold-italic[每一层对应一类信息丢失的修复目标：]

1. **第一层（控制流重建）**：解决谓词隐式分支、多定义寄存器、内核内嵌 device 函数问题，生成自研 SSIR 中间表示与完整 def-use 数据流图；
2. **第二层（语义归一化）**：匹配编译器拆分的多指令复合算子，还原张量、异步内存、协同组同步等高阶 CUDA 语义；
3. **第三层（类型恢复）**：依托完整数据流图执行约束迭代推理，识别隐式类型转换边界，插入 bitcast 类型转换指令。

- 类型恢复作为收尾步骤，基于归一化、无冗余指令图完成全局类型标注。

### 2.2 最核心瓶颈：统一寄存器带来的类型推理困境

> **三类丢失结构中，类型恢复是唯一“一票否决”环节。** 消融实验数据证明，即便控制流、模式归一化模块全部正常工作，缺少类型推理步骤会直接导致 IR 无法编译、仿真执行全部报错。

:mdnice-bold-italic[底层根源在于 LLVM IR 语法硬性约束：每一条运算指令、每一个操作数必须标注明确数据类型，不存在“无类型寄存器”合法语法。] SASS 单寄存器堆让硬件无法提供任何天然类型线索，90%指令可通过操作码锁定类型，但剩余 10%透明指令（MOV、按位运算、普通内存读写）无任何类型提示，必须沿着数据流传递约束完成全域推导。

同时编译器主动插入数百万次隐式类型双关，浮点比特直接作为整数读取，两类数据无交集，约束集合相交得到空集 $\perp$，必须识别该边界并插入显式 bitcast 转换，否则数值运算全部失真。

## 三、核心技术一：基于格约束传播的类型恢复算法

> :mdnice-bold-italic[类型恢复是 CuLifter 的技术核心，团队将寄存器类型推理抽象为格论下固定点迭代问题，设计播种、传播、冲突拆分三步标准化流程]，可自动识别所有隐式类型转换边界。

传统 CPU 类型推理依赖分离寄存器的强线索，**GPU 场景线索稀疏，团队构建分层类型格模型**，统一管理 1bit 布尔、16bit 浮点、32bit 基础类型、64bit 宽值、128bit 内存分组全部候选类型。

初始时所有寄存器候选集合为顶层 $\top$（全部类型都可能）；浮点加法 FADD、整数比较 ISETP 等种子指令直接裁剪候选集合，例如 FADD 输出值候选集合直接收缩为{Float32}。

> 定义初始类型集合：任意寄存器 $v$ 初始化候选集合 $T_0(v) = L$，$L$ 为格顶层全集。

$$
T(v) \leftarrow T(v) \cap C(I)
$$

符号解释：

- $T(v)$ 代表寄存器 $v$ 当前候选类型集合；
- $C(I)$ 为指令 $I$ 自带的强制类型约束集合；
- $\cap$ 为集合交集运算。

::: block-1
示例：FADD 指令约束 $C(I)=\{Float32\}$，寄存器经过浮点加法赋值后，候选集合与该集合取交，仅保留 Float32 一种可能类型。
:::

指令分为两类，对应两种约束来源：

1. **种子指令**：FADD、HMMA、ISETP 等:mdnice-bold-italic[带固定数据运算的操作码，直接生成强约束，覆盖 93%的硬件指令；]
2. **透明指令**：MOV、STL、按位逻辑运算，无原生类型约束，仅传递上下游寄存器的候选集合。

![文章插图](/articles/2026-06-26-nvidia-sass-culifter-sass-c659e77f/images/09.webp)

:::

### 3.2 三步约束迭代固定点算法

> 完整类型推理分为三个标准化阶段，依托 def-use 数据流图反向拓扑迭代，收敛速度平均仅 3.5 轮迭代，最大迭代次数不超过 6 轮。

1. **播种阶段**：遍历所有指令，通过操作码裁剪对应寄存器候选集合，完成:mdnice-bold-italic[初始约束注入]；
2. **传播阶段**：对透明指令上下游寄存器候选集合做交集传播，沿数据流双向同步约束，重复迭代直至所有寄存器候选集合不再变化，达成固定点；
3. **冲突处理阶段**：若寄存器约束交集等于空集 $\perp$，判定存在隐式类型边界，拆分寄存器并插入 bitcast 类型转换指令。

$$
\mathcal{T}^{k+1}(r)=\mathcal{T}^{k}(r) \sqcap \prod_{c \in constraints(r)} solve(c, \mathcal{T}^{k})
$$

符号解释：

- $\mathcal{T}^{k}(r)$ 为第 $k$ 轮迭代寄存器 $r$ 的候选类型集合；
- $\sqcap$ 代表格下交运算（集合取交集）；
- $constraints(r)$ 为所有关联该寄存器的数据流约束；
- $solve(c, \mathcal{T}^{k})$ 根据关联寄存器当前类型集合推导本寄存器约束。

迭代顺序选用数据流反向拓扑序，可大幅减少收敛所需迭代轮次。

### 3.4 模糊类型兜底判定策略

> 迭代收敛后仍存在部分寄存器候选集合包含多种合法类型（无冲突但无种子锁定），采用**优先级判定规则自动赋值：**

$$
resolve(v)= \begin{cases}Int32, & Int32 \in \mathcal{T}(v) \\ Int64, & Int64 \in \mathcal{T}(v) \\ Int128, & Int128 \in \mathcal{T}(v) \\ 集合内任意浮点类型, & 无整数候选\end{cases}
$$

规则说明：

- GPU 内核寻址、循环计数绝大多数使用 32 位整数，优先分配 Int32 兜底，保证生成 IR 可正常编译；
- 极少无任何约束的死代码寄存器，统一强制赋值 Int32，杜绝无类型数值。

::: block-1
类型恢复算法核心优势：依托格论固定点迭代自动识别编译器生成的数百万次隐式类型双关，无需人工预设类型转换模板，**跨 SM75 至 SM120 全架构通用，与硬件指令集无关。**
:::

## 四、核心技术二：适配 SIMT 谓词执行的 ψ-SSA 重构

> 标准 SSA 算法面向无分支、无条件执行的基础块设计，而 SASS 每条指令均可附加谓词掩码，同一物理寄存器在单基础块内存在多条互斥谓词写入，传统 SSA 重命名会直接覆盖有效值，造成数据流丢失。

团队借鉴 :mdnice-bold-italic[IA-64 架构 ψ 函数理论，适配 GPU SIMT 线程分歧、收敛屏障、双谓词分支三大特有硬件机制，将多谓词寄存器写入统一转换为 LLVM 原生 select 选择指令。]

### 4.1 标准 SSA 在 GPU 谓词代码下的原生失效

> 标准 SSA 假设一个基础块内同一寄存器仅存在一次有效赋值，而 SASS 谓词执行完全打破该假设。示例逻辑：

```
// 1. 生成分支判定谓词pp = x > 0          // 计算布尔判定条件，将「x大于0」的真假结果存入谓词寄存器p（SASS中P0/P1这类掩码寄存器，用于控制指令是否执行）// 2. 正向谓词保护赋值@p R = x << 1     // @p是谓词保护标记；仅当谓词p为true（x>0）时执行本条指令：R = x * 2（左移1位等价乘2）；// 若p为false，本条指令等价空操作NOP，不修改R// 3. 反向取反谓词保护赋值@!p R = x + 100   // @!p代表谓词取反；仅当p为false（x≤0）时执行本条指令：R = x + 100；若p为true，本条指令NOP，不修改R// 4. 读取使用寄存器Ruse(R)            // 后续代码读取寄存器R的值；由于两条赋值指令互斥执行，R仅有一条有效赋值路径
```

同一寄存器 `R` 在同一块内存在两条互斥谓词写入，标准重命名会仅保留第二条`@!p0` 赋值，丢弃 `p` 成立时的数值，执行结果完全错误。**IA-64 提出 ψ 函数解决该场景：$R=\psi(P0:val1,\neg P0:val2)$，语义等价于 LLVM select 指令。**

### 4.2 ψ 函数到 LLVM select 的转换算法

> 先看算法演示示例：

```
// 计算布尔判定谓词p，对应SASS的ISETP指令，记录当前线程x>0的真假状态p = x > 0// 分支1：x大于0时的运算结果，存入独立临时变量val1val1 = x << 1// 分支2：x小于等于0时的运算结果，存入独立临时变量val2val2 = x + 100// LLVM内置select选择指令，等价论文中的ψ函数；每条线程依据p的值二选一赋值给RR = select(p, val1, val2)// 读取最终寄存器R，此时R仅有唯一定义，符合SSA静态单赋值规范use(R)
```

> 再看算法 1：单基础块 ψ 函数构建流程

1. 遍历基础块所有指令，建立映射表 $Defs$，存储`{寄存器：(谓词，赋值数值)}`列表；
2. 取寄存器基础块入口 live-in 值作为默认返回值；
3. 逆序遍历该寄存器所有谓词写入，逐层嵌套生成 select 表达式；
4. 删除全部原始谓词写入指令，在块末尾插入无条件寄存器赋值；
5. 更新基础块 live-out 数据流信息。

![文章插图](/articles/2026-06-26-nvidia-sass-culifter-sass-c659e77f/images/13.webp)

::: image-caption
Algorithm 1：单个基本块的 ψ 函数构造算法：算法遍历块内所有带谓词寄存器写操作，记录（谓词，值）映射对，反向遍历生成嵌套 select 链替代原生谓词写入，最终删除原条件指令、新增无条件选择赋值。专门适配 SIMT 收敛屏障，屏障分割区块独立处理 ψ，避免未同步线程数值合并错误。
:::

该转换将多条互斥条件写入压缩为单条类型合法 select 指令，完美适配 LLVM SSA 规范。

### 4.3 SIMT 特有硬件机制扩展处理

> 基础 ψ 函数仅适配普通谓词代码，GPU **三类特有执行逻辑需要额外扩展处理：**

1. 谓词线程退出`@!P0 EXIT：`转换为条件 `return` 指令，未满足谓词线程正常执行后续代码，不标记块终止；
2. 双谓词分支`@!P0 BRA P1`：区分执行掩码谓词与分支条件谓词，构建嵌套条件分支，避免 CFG 图断裂；
3. 收敛屏障 BSSY/SSY：屏障分割的代码块独立构建 ψ 函数，不跨屏障合并寄存器值，防止线程未同步产生数值错误。

### 6.1 阶段 1：控制流重建（SSIR 中间表示生成）

> 本阶段为全流程前置依赖，输出完整 CFG、def-use 数据流图与标准化 SSIR 指令，包含四项子步骤：

1. SASS 原始文本解析，基于架构表展开隐式寄存器组，拆分多定义硬件指令；
2. 基础块切分，谓词掩码变更、跳转目标、函数入口均作为块分割标记；
3. 谓词感知 CFG 构建，区分普通分支、双谓词分支、线程退出指令；
4. ψ 函数转换生成标准 SSA，同步构建跨寄存器数据流依赖图。

### 6.2 阶段 2：高层语义模式归一化

基于变量统一匹配器扫描全部基础块，匹配编译器拆分的复合算子、同步指令、线程索引访问；同时清理 NVCC 插入的无效无限循环填充指令，删除无副作用冗余指令，简化数据流链条，减少后续类型传播迭代次数。

### 6.3 阶段 3：类型推理与 LLVM IR 发射

### 9.1 现有工程短板

1. 指令集覆盖不全：SM90 QGMMA 新型张量指令未实现解析器，少量新型专用指令识别失败；
2. 仅支持过程内分析：类型传播、数据流分析仅限单内核函数，无跨 device 函数全局类型推导；
3. 硬件特性缺失：纹理采样、集群级同步指令暂无 CPU 仿真分解逻辑，对应内核仿真执行失败；
4. 类型兜底策略偏保守：无任何约束线索的寄存器会强制分配 Int32 类型，仅保留比特原始信息，无法还原其真实运算语义。

### 9.2 下一代拓展思路

1. 扩展指令匹配库，持续跟进 SM120 及后续新架构张量、异步内存指令；
2. 新增跨函数全局数据流分析，打通内核与 device 函数间类型约束传播；
3. 补充纹理、集群硬件算子的 LLVM 分解逻辑，完善 CPU 仿真覆盖范围；
4. 引入轻量概率类型预测模型，降低无约束寄存器 Int32 兜底带来的语义偏差。

## 十、领域深远产业与学术影响

> 长期以来 GPU 二进制分析存在基础设施空白，CPU 生态成熟的漏洞挖掘、二进制优化、跨架构移植工具完全无法迁移至 SASS 机器码，闭源 CUDA 库成为黑盒，大模型、HPC 领域难以做底层性能溯源、安全审计。

**CuLifter 首次搭建完整、可工业化使用的 SASS 至 Typed LLVM IR 提升流水线**，99.98%全域函数处理率证明工程实用性，消融实验夯实类型恢复的理论核心地位。工具打通了闭源 GPU 二进制的全链路编译分析通道，安全团队可对厂商黑盒库做漏洞污点分析，AI Infra 工程师可逆向优化大模型推理内核访存效率，**异构编译研究者可将英伟达专有内核一键移植至 ARM、FPGA 等非 GPU 硬件。**
