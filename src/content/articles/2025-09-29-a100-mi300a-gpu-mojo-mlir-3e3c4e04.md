**尽管 Mojo 的学习曲线和编程要求仍处于相对底层的水平**，但在科学计算与人工智能融合的背景下，它**能够填补碎片化的 Python 生态系统中的重大空白。**

## 关键问题

### 问题 1. 针对 Mojo 性能短板的核心矛盾：源于编译器适配不足还是语言封装缺陷？

> 针对 Mojo 性能短板的核心矛盾：Mojo 在计算受限场景（尤其是原子操作与快速数学计算）与 CUDA/HIP 存在显著差距，这究竟是源于 MLIR 编译器对 GPU 硬件特性的适配深度不足，还是其语言层对底层硬件指令的封装设计存在结构性缺陷？

Mojo 在计算受限场景的性能差距，核心源于**MLIR 编译器对 GPU 硬件特性的适配深度不足**，而非语言封装的结构性缺陷。从论文实验看，Mojo 的类 CUDA 语法设计已实现对底层硬件操作的基础封装（如内存层级访问、线程块调度），其在内存受限内核（七点模板、BabelStream）上能与 CUDA/HIP 媲美，证明语言层封装逻辑可满足基础硬件调用需求。

**性能缺口集中于原子操作、快速数学计算等硬件相关优化场景**：在 AMD MI300A 的原子操作测试中，Mojo 未能充分利用 AMD GPU 的专用原子指令集；而快速数学计算受限的内核中，其编译器未能生成与 CUDA/HIP 匹配的硬件加速指令（如 NVIDIA 的 Tensor Cores、AMD 的 Matrix Cores 调用）。:mdnice-bold-italic[这反映出 MLIR 作为通用编译基础设施，在针对特定 GPU 架构的深度优化（如硬件专用指令绑定、低延迟内存同步）上仍落后于厂商原生编译器（CUDA 对 NVIDIA、HIP 对 AMD）。]

### 问题 2. 围绕可移植性与性能的平衡难题：“一写多跑”是否必然牺牲极致性能？

> 围绕可移植性与性能的平衡难题：Mojo 宣称兼顾跨 GPU 架构可移植性与高性能，但其在 AMD 与 NVIDIA GPU 上的表现差异（如 AMD 原子操作短板）已暴露适配不均问题，这种“一写多跑”的实现路径是否必然以牺牲部分硬件平台的极致性能为代价？

Mojo 的实践表明，**“一写多跑”的可移植性并非必然以牺牲极致性能为代价，但需突破“通用编译适配”与“硬件特性深挖”的协同瓶颈**。论文中，Mojo 在内存受限场景实现了跨 NVIDIA H100、AMD MI300A 的性能对齐（与原生编译器差距＜ 5%），说明在硬件共性需求（如高带宽内存访问、基础线程并行）上，通用编译可实现接近原生的优化。

**性能牺牲主要出现在硬件差异化特性场景**：:mdnice-bold-italic[AMD GPU 的原子操作单元、NVIDIA 的快速数学计算管线存在架构差异，Mojo 的通用编译逻辑难以同时适配两类硬件的“专属优化路径”，导致在 AMD 原子操作、双平台快速数学计算中性能落后] （差距 15%-30%）。但这并非“可移植性的固有缺陷”，而是当前 Mojo 编译器对硬件差异化特性的适配覆盖不足——**若未来 MLIR 后端能实现“通用语法 → 硬件特性动态绑定”（如根据目标 GPU 自动调用对应原子指令、加速单元），理论上可在保持可移植性的同时逼近极致性能。**

### 问题 3. 关于生态竞争力：Mojo 能否突破路径依赖替代 CUDA？

> Mojo 试图填补 Python 生态的碎片化缺口，却仍保留底层编程的学习曲线，在 CUDA 生态已形成技术壁垒、Python 已有 Numba 等加速工具的现状下，其“生产力+性能”的核心优势能否突破现有生态路径依赖，真正替代 CUDA 成为跨厂商 GPU 编程的主流选择？

短期内 Mojo 难以替代 CUDA 成为主流，但有望在**“Python 生态延伸的高性能场景”中开辟差异化市场，长期竞争力取决于生态协同与硬件适配速度**。

从现状看，**CUDA 的技术壁垒不仅在于性能，更在于其绑定的完整生态** （如 cuDNN、cuBLAS 等专用库、大量优化过的科研代码库），而 Python 已有 Numba 等工具实现“轻量级加速”，Mojo“底层编程+Python 互操作”的定位需面对双重路径依赖。但论文也揭示了其核心优势：

::: block-1
- 相比 CUDA 的厂商锁定，Mojo 可跨 NVIDIA/AMD GPU 移植；
- 相比 Numba 的“黑盒加速”，Mojo 能直接操控 GPU 硬件资源（如内存层级、线程调度），更适配科学计算与 AI 融合的复杂负载（如 Hartree–Fock 量子化学计算）。
:::

:mdnice-bold-italic[若 Mojo 能快速补齐编译器优化短板（如硬件专用指令适配），并打通与 Python 科学生态（如 NumPy、PyTorch）的深度协同（如直接调用 Mojo 优化内核），则【可能】在“需要跨 GPU 移植、且需底层硬件控制的科研场景”中快速渗透]，逐步形成对 CUDA 的补充乃至局部替代，但**短期内难以撼动** 其在 NVIDIA 生态中的主导地位。

## 一、引言

Mojo[42]是当前用于填补 Python[56]语言及生态系统（包括人工智能负载场景）中性能与开发效率差距的最新技术。由 Modular 公司开发的 Mojo 是一门独立语言，它**完全基于多级中间表示（MLIR[36]）提供预编译** （AOT，指在程序运行前就完成编译的方式，能提前优化代码，提升运行时性能）**和即时编译** （JIT，指在程序运行过程中实时编译代码，能根据运行时信息动态优化，适配不同运行场景）**两种编译选项**，而 MLIR 是被广泛采用的 LLVM[35]编译器基础设施的下一代技术。

> Mojo 通过模块互操作性（指不同软件模块之间相互调用、数据共享的能力）实现了 Python 丰富库生态的复用，从而提升开发效率，同时还能跨不同厂商的 GPU 实现性能可移植性。目前，Mojo 已支持最新的 NVIDIA GPU，近期还新增了对 AMD MI300 系列 GPU 的支持。

因此，与 Julia[8]和 Rust[40]等现代编程语言类似，**Mojo 旨在缓解因使用多种语言和生态系统以实现高级特性（如 Python 的开发效率、Rust 的安全性）与编译型语言如 C++、C、Fortran 的底层性能所导致的高昂碎片化问题** （指因多种工具、语言混用而产生的开发流程复杂、维护成本高、兼容性差等问题）。

近几十年来，异构计算架构如中央处理器 CPU 与 GPU 加速器组合的架构，一直是超级计算和人工智能领域发展的主要驱动力。2025 年 6 月发布的 TOP500（全球超级计算机排名榜单）Linpack[20]排名显示，:mdnice-bold-italic[全球运算速度前十的超级计算机中，有 9 台采用 GPU 加速]。此外，对人工智能超级计算机（如 xAI 的 Colossus 超级计算机）的大规模投资，持续推动着对 GPU 的需求[47]。基于此，GPU 的可编程性和可移植性对于整个高性能计算生态系统至关重要。

为满足可移植性需求，业界主要通过新的标准（包括 OpenMP[44]、OpenCL[53]、OpenACC[58]和 SYCL[18]）以及第三方编程模型（包括 Kokkos[54]和 RAJA[5]），针对 C、C++和 Fortran 等 HPC 语言开展相关研究。自 2025 年 6 月起，Mojo 通过其语言标准库，直接为用户提供了支持可移植 GPU 编程的能力。

> 本文试图解答以下研究问题：科学计算用户能否从 Mojo 的高性能可移植 GPU 代码中获益？

尽管 Mojo 语言相对新颖，许多设计决策仍处于开发阶段，且直至 2026 年才会完全开源，但本文仍对 Mojo 独特的价值主张即利用其标准库编写高性能可移植 GPU 核函数，进行了初步探索。**与科学数值库中定义明确的人工智能方法和数学核函数不同，自定义科学计算核函数可能具有独特的计算特性，这些特性会影响其性能**。

为此，我们将四个广泛使用的科学计算核函数移植到 Mojo 环境中，使其能够利用 Mojo 的可移植 GPU 代码能力，这四个核函数分别是：（1）七点模板（内存带宽受限型）、（2）BabelStream（内存带宽受限型）、（3）miniBUDE（计算受限型）以及（4）哈特里-福克（含原子操作的计算受限型）。随后，我们对这些核函数的性能和分析指标（在适用情况下）进行评估，并与对应的 CUDA 和 HIP 基准版本进行对比。

## 二、背景

### 2.1 Mojo 编程

> Mojo 的价值主张在于将 Python 的易用性和灵活性与 C++等编译时编程语言的性能相结合。

![文章插图](/articles/2025-09-29-a100-mi300a-gpu-mojo-mlir-3e3c4e04/images/02.webp)

作为首个完全基于多层中间表示（MLIR）构建的语言，Mojo 得以实现这一目标。**图 1 展示了 Mojo 解决编译型语言与 Python 生态系统之间碎片化问题的方法**。鉴于 2025 年 6 月 Mojo 宣布除了支持技术成熟的 NVIDIA Hopper 和 Ampere 系列 GPU 外，还新增了对 AMD MI300 系列 GPU 的支持，我们对 Mojo 在科学领域中用于特定计算任务的关键代码模块上的表现尤为关注。

> 值得注意的是，复用相同的、与厂商无关的 Mojo GPU 模块，为嵌入式语言级别的 GPU 可移植性增添了非常独特的特性。

这与其他高性能计算语言形成鲜明对比——在那些语言中，此类支持需由标准的第三方库提供。事实上，**Mojo 在多个方面都具有【独特性】：**

::: block-1
- **基于 MLIR 的编译时特性**，支持即时编译（JIT，程序运行时才编译部分代码，可适应动态需求）或提前编译（AOT，程序运行前就完成全部编译，启动更快），能实现高性能可移植的 GPU 编程。
- 包含**与 Python 及其丰富库生态系统的运行时互操作性**，互操作指不同程序或语言之间在运行时相互调用、交换数据的能力。
- 通过变量生命周期（变量从创建到销毁的过程）和所有权（决定哪个部分代码能修改变量的规则）实现内存安全如避免了内存泄漏、野指针等问题，**无需垃圾回收，自动回收不再使用的内存的机制。**
:::

代码清单 1 展示了 Mojo 的语法示例，其中体现了上述关键特性。

> Mojo 采用较低层级的、类 CUDA/HIP 的编程模型，用于 GPU 设备内存分配和核心程序启动。

:mdnice-bold-italic[由于 Mojo 旨在借助 MLIR 进行编译，因此像问题规模、块大小（GPU 编程中用于划分计算任务的单位）、数组布局（数据在内存中的存储方式）以及变量类型等对性能至关重要的信息，必须在【编译时】明确定义]。后者还使得即时编译（JIT）和提前编译（AOT）在生成中间表示时难以区分，因为两种机制都会获取相同的信息。**这种固定布局的编程风格在计算早期很适用，但此后主流高性能计算语言发生了转变**，尤其是 C 语言和 Fortran 90 语言，它们支持动态内存分配——而**动态内存分配正是大多数高性能计算代码的基础构建模块**。

与之不同的是，**Mojo 与 Python 的运行时互操作通过【模块】实现**，且不使用 MLIR 进行预编译，因此保留了 Python 的动态特性。由此，:mdnice-bold-italic[Mojo 在【语言内部】引入了这种【碎片化】：一方面是经 MLIR 编译的即时或提前编译型高性能代码，另一方面是仅作为运行时实体的 Python 互操作模块，（不经过 MLIR 优化），主打灵活性和生态复用，性能依赖 Python 本身。] 二者在编译方式、性能表现、适用场景上差异显著，形成了语言内部的 “碎片化”。

大多数高性能计算软件应用只有在运行时才能获取大量信息，即“一次编译，多次运行”，而 **Mojo 依赖 MLIR 优化的特性，限制了其程序必须在编译时提供对性能至关重要的信息**，如内存占用大小、数据类型、内存布局和变量生命周期。尽管这一点对于即时编译（JIT）方案（如 Julia 语言采用的方案）是理想的，但**在部署仅能在运行时获取特定信息的代码（如实时工作流、自适应网格代码、统计随机游走模拟代码）时，可能会面临挑战**。此外，Python 的调用栈无法通过 Mojo 的提前编译（`mojo build`命令）得到有效编译，因此 Python 交互仍保持动态特性，且只能通过与 CPython（Python 的官方解释器）的互操作在运行时实现。

> Mojo 还采用了基于值所有权的内存模型，无需依赖垃圾回收机制就能同时保证性能和内存安全，具体可拆解为 3 个关键点：

::: block-1
1. **核心逻辑：单所有者规则**。Mojo 对堆分配的内存（运行时动态创建的数据，如复杂对象、数组）实行 “单一所有权”—— 同一时间，一块堆内存仅归一个变量 / 代码块所有，避免了多持有者导致的内存引用混乱（如重复释放、野指针）。
2. **自动释放：生命周期 + 析构函数**。当持有内存的 “所有者” 生命周期结束（比如变量超出作用域、函数执行完毕），Mojo 会自动调用该内存对应的 “析构函数”，直接释放内存资源。这个过程是确定性的（不像 GC 需等待 “内存扫描”），既避免了内存泄漏，又无需额外的 GC 线程占用资源，保障了高性能。
3. **差异化优势：避开 GC 与 C++ RAII 的痛点**
:::

**在 Python 生态系统中，Mojo 提升性能的方式与其他解决方案截然不同**。它并非从 Python 内部进行优化，而是**清晰区分编译时的高性能关键代码段与运行时的 Python 互操作部分**。虽然基于 C 或 C++的 Python 库早已通过高性能可移植互操作库（如 pybind11、nanobind）实现了类似的区分，但 Mojo 的:mdnice-bold-italic[【独特之处】在于将这些方面整合到语言本身，通过减少需要 GPU 性能和类 CUDA 核心程序的类 Python 软件项目中的碎片化问题，提升开发效率。]

另一个重要方面是 **Mojo 与 GPU 厂商工具及生态系统的互操作性**。根据我们的早期使用经验，:mdnice-bold-italic[Mojo 代码调试【仅】支持 NVIDIA 的 Nsight Compute 命令行工具（`ncu`，用于分析 GPU 程序性能的工具）或 CUDA-GDB 调试器] （Mojo 提供了基于 LLDB 的调试器）。遗憾的是，我们:mdnice-bold-italic[未能找到官方支持的工具，【无法成功】使用 AMD 的 rocprof 工具（AMD 推出的用于分析 GPU 程序性能的工具）对 Mojo 代码进行性能分析]。工具支持是高性能计算软件开发的重要环节，而这在 Mojo 中仍属于活跃开发领域。

### 2.2 Mojo 中的科学计算核心程序

> 下文将概述所选的科学计算核心程序及其实现方式，我们将通过这些核心程序**评估 Mojo 在 GPU 上的性能可移植能力**。研究对象为以下应用程序，均是用于模拟真实应用程序关键特性的简化程序中的核心程序：

- 七点模板（Seven-point stencil）：是科学计算中用于模拟扩散传输现象（如热传导、流体扩散等）的核心计算模型，属于典型的**内存带宽受限型** 程序，其性能瓶颈集中在 “内存数据传输速度” 而非计算本身。
- BabelStream：**内存** 传输操作基准测试程序[17]（用于衡量不同编程模型下 GPU 内存传输性能的工具）。
- miniBUDE：用于蛋白质预测的硅基分子对接（通过计算机模拟预测分子间结合模式的技术）核心程序[49]，即通过计算分子间的相互作用（如氢键、范德华力等）能量，判断分子结合的稳定性与最优结合构象，整个过程依赖大量浮点运算，如距离计算、能量公式迭代。属于**计算受限型** 核心程序。
- 哈特里-福克（Hartree-Fock）：量子多体近似方法[23]（用于计算原子、分子电子结构的量子力学方法），:mdnice-bold-italic[属于含原子操作（用于保证多线程访问共享数据时正确性的特殊操作）的计算受限型核心程序。]

这些核心程序初步覆盖了科学领域众多代码中典型的内存操作和计算操作。

2. 工作组大小（wg，GPU 中同时执行的线程组规模）；
3. 配体数量（参与对接的小分子数量）；
4. 蛋白质数量（参与对接的大分子数量）。

每个应用程序均**从基于厂商特定编程模型（NVIDIA 的 CUDA 或 AMD 的 HIP）的基准实现移植而来**。我们将代码清单 2、3、5 中展示的 Mojo 可移植语法与现有的 CUDA 和 HIP 实现进行对比。针对每种情况，我们使用能反映特定应用程序用途的指标进行评估。

### 3.1 各核心程序的评估指标

#### 七点模板

我们采用原始基准测试中**使用的有效内存带宽指标，该指标表示模拟步骤中处理的单元格数据量（单位：GB/s）**。

为简化计算，我们假设 x、y、z 三个方向的尺寸`L`保持恒定。该指标通过公式（1）定义，其中`L`为网格尺寸，`T`为运行中使用的元素类型（32 位浮点数 Float32 或 64 位浮点数 Float64）的大小（单位：字节）。

首先计算有效读取大小（`fetch_size_effective`）和有效写入大小（`write_size_effective`）：

$$
\text{fetch_size}_{effective} = \left[ L^3 - 8 - 12(L - 2) \right] \cdot sizeof(T)
$$

$$
\text{write_size}_{effective} = (L - 2)^3 \cdot sizeof(T)
$$

然后计算有效带宽， $$
\text{bandwidth}_{effective} = \frac{(\text{fetch_size} + \text{write_size})_{effective}}{\text{kernel_time}} \tag{1}
$$

其中，`kernel_time`为核心程序的执行时间（单位：秒）。

#### BabelStream

我们采用的**有效内存带宽指标** 仅基于数组大小（向量大小）和每种操作对应的数组数量。该方法通过公式（2）对每种基本操作进行总结。值得注意的是，:mdnice-bold-italic[尽管所有操作均在设备全局内存中分配数组，但点积（Dot）操作利用块级共享内存实现了更快的一级归约操作。]

首先定义基础数组带宽（`bandwidth_Array`）：

$$
bandwidth_{Array} = \frac{sizeof(T) \cdot Vector\_size}{kernel\_time}
$$

再根据不同操作类型计算对应带宽：

$$
bandwidth_{Copy} = 2 \cdot bandwidth_{Array}
$$

$$
bandwidth_{Mul} = 2 \cdot bandwidth_{Array}
$$

$$
bandwidth_{Add} = 3 \cdot bandwidth_{Array}
$$

$$
bandwidth_{Triad} = 3 \cdot bandwidth_{Array}
$$

$$
bandwidth_{Dot} = 2 \cdot bandwidth_{Array} \tag{2}
$$

其中，`Vector_size`为向量中元素的数量。

#### miniBUDE

鉴于 miniBUDE 的`fasten`核心程序属于**计算受限型**，其性能指标采用**每核心程序执行时间内完成的浮点运算次数** （单位：十亿次浮点运算/秒，GFLOP/s）。该指标通过原始基准测试中的计算方法得到，公式如下：

首先计算每个工作组的运算次数（`ops_workgroup`）：

$$
ops_{workgroup} = 28 \cdot PPWI + nligands \cdot \left[ 2 + 18 \cdot PPWI + nproteins \cdot (10 + 30 \cdot PPWI) \right]
$$

再计算总运算次数（`total_ops`）：

$$
total_{ops} = ops_{workgroup} \cdot \frac{poses}{PPWI}
$$

最后计算 miniBUDE 的总性能（`miniBUDE-total_gflops`）：

$$
miniBUDE - total_{gflops} = \frac{total_{ops}}{time_{kernel}} \cdot 10^{-9} \tag{3}
$$

其中，`nligands`为配体数量，`nproteins`为蛋白质数量，`poses`为总姿态数，`time_{kernel}`为核心程序执行时间（单位：秒）。

#### 哈特里-福克

该核心程序的性能评价指标直接与将原始算法[23]移植到 GPU 后获得的**加速比** 相关。为在不同语言间进行对比，我们直接**测量核心程序的墙上时钟时间** （wall-clock time，即实际流逝的时间），不进行额外转换。我们选择了氦原子系统的基准测试用例，原子数量最多为 256 个，每个原子对应 3 个高斯函数。如代码清单 5 所示，**由于核心程序内部存在原子操作，其并行性受到严重限制**。:mdnice-bold-italic[我们的目标是衡量这种代码模式对 Mojo GPU 可移植原子操作能力的影响。]

### 3.2 实验设计原则

针对所有选定案例，我们确保评估方法在性能和可移植性之间取得平衡，从而公平评价 Mojo GPU 代码。方法概述如下：

::: block-1
1. **预热步骤**：对于所有代码，在测量中剔除第一次运行结果，以减少即时编译（JIT）或缓存（临时存储高频访问数据的高速内存）带来的影响。
2. **可变性控制**：使用专用硬件进行实验，且每个实验至少执行 100 次，以捕捉结果的可变性。核心程序的执行时间已通过性能分析工具验证。
3. **一对一对比**：GPU 代码未进行精细调优，且与现有基准配置（如 GPU 的块数、线程数）保持一致。:mdnice-bold-italic[对于 BabelStream，我们使用经过优化的厂商特定 CUDA 版本，而 Mojo 移植版本采用混合式、与厂商无关的实现]，以确保在 NVIDIA 和 AMD GPU 上的可移植性，并实现最佳性能权衡。
4. **性能分析**：对 Mojo 性能优于厂商编程模型或性能差异稳定的案例进行重点分析。
5. **结果一致性**：对每种编程模型使用统一的颜色编码，且所有展示应用程序运行结果的图表均采用一致的性能评价指标。
6. **即时编译（JIT）与提前编译（AOT）对比**：由于 Mojo 具有编译时特性，我们发现即时编译和提前编译的核心程序执行性能无显著差异。而使用 NVIDIA 的 Nsight 命令行工具（`ncu`）和 AMD 的 rocprof 工具对 Mojo 代码进行性能分析时，仅支持提前编译的 Mojo 代码。
:::

图 5 展示了使用 NVIDIA Nsight 工具**对三元运算（Triad）内核进行的更深入的逐行汇编级（assembly-level）对比分析**。该内核的性能与加法（Add）内核相似，我们得出了三个重要观察结果：

::: block-1
1. **Mojo 常量内存利用更高效**：常量内存是 GPU 中用于存储高频访问、只读数据的高速缓存，CUDA 常需通过`__constant__`等注释显式声明才能使用，且可能因代码设计生成冗余的 “加载常量” 操作；:mdnice-bold-italic[而 Mojo 无需额外标注，能自动将符合条件的数据分配到常量内存，减少不必要的加载指令，间接降低内存访问延迟，这是其在部分内存操作中性能接近甚至略优于 CUDA 的原因之一。]
2. **寄存器使用与计算指令的权衡**：“活动存活寄存器” 是线程执行时需实时占用的寄存器数量，数量越少，GPU 可同时调度的线程数越多（寄存器资源有限），**Mojo 更少的存活寄存器有助于提升线程并行度；但代价是增加了IADD3（整数加法）指令 —— 推测是 Mojo 为减少寄存器占用，将部分复杂操作拆分为更多基础整数运算**，不过因 Triad 是内存受限内核（性能瓶颈在内存传输，非计算），:mdnice-bold-italic[额外的计算指令未显著影响整体性能，反而因线程并行度提升抵消了指令增加的开销。]
3. **全局内存操作一致性保障性能基准**：全局内存是 GPU 中容量最大但访问最慢的内存，Triad 内核的核**心逻辑是 “读取两个数组、计算后写入第三个数组”，其性能高度依赖全局内存的加载（LDG）和存储（STG）效率。Mojo 与 CUDA 的 LDG/STG 操作一致**，说明二者在核心数据传输路径上设计相同，:mdnice-bold-italic[这是 Mojo 能在该内核上与 CUDA 保持性能对齐的关键 —— 避免了因全局内存操作差异导致的性能断层。]
:::

上述分析足以理解性能和吞吐量差异，进一步分析超出了我们对性能可移植性的关注范围。

### 4.1 性能可移植性指标

基于在两个选定 GPU 平台上的结果，我们应用了一个性能可移植性指标（Φ），该指标在最近的多篇文献中都有讨论[38, 39, 45, 46]。**使用“应用效率”的定义$\bar{\Phi}$，即某一应用在同一架构类别的一组平台上观察到的性能效率的算术平均值**。

> 该指标的本质是回答：在同一类架构（如所有 GPU）的多个平台上，Mojo 跑应用的性能，平均能达到厂商专属方案（CUDA 对应 NVIDIA、HIP 对应 AMD）的百分之几？

因此，该指标定义为最佳可能结果的算术平均值：

$$
\begin{aligned}
\overline{\Phi}_{\text{Mojo }}&=\frac{\sum_{i \in T} e_{i}(a)}{|T|} \\
e_{i}(a)&=\frac{\text{ Mojo }_{\text{perf -i}}}{\text{ vendor(CUDA / HIP) }_{\text{perf -i}}}
\end{aligned} \tag{4}
$$

- **$e$：表示 Mojo 性能的效率，定义为 Mojo 性能指标与特定于厂商的 CUDA 和 HIP 实现性能指标的比值**
- $T$：表示特定应用程序和架构类别（如仅 GPU）的运行子集。$|T|$是$T$包含的平台数量（即统计样本数）

例：若测试了 H100（$e_1=0.867$）和 MI300A（$e_2=0.92$）两个 GPU 平台，则平均效率$\bar{\Phi}=(0.867+0.92)/2≈0.893$。

### 4.2 讨论与观察

> 接下来，我们总结在分析新型 Mojo 语言的:mdnice-bold-italic[开发和评估过程中得出的观察结果和发现。]

#### 观察 1：性能可移植性

在没有进行任何进一步优化的情况下，Mojo 的单 GPU 代码性能在所有内存受限内核实验中，与 AMD 的 HIP GPU 代码持平。**在计算受限内核中，性能差异主要源于缺乏快速数学优化能力**。

- 对于七点模板操作，:mdnice-bold-italic[Mojo 和 NVIDIA CUDA 之间存在差距，这是因为 CUDA 具有额外的寄存器级优化。]
- 令人惊讶的是，**BabelStream 操作（点积 Dot 除外）可以通过 Mojo 进一步优化，从而提供略高于 CUDA 的性能**。这可以通过 Mojo 的 MLIR 优化来解释——正如我们的剖析工具分析所证实的，:mdnice-bold-italic[MLIR 优化减少了所需的寄存器内存操作。]
- 在 miniBUDE 案例中，其**性能对快速数学编译非常敏感，这导致 Mojo 实现中出现了明显的性能差距**。我们期待在不久的将来，这种优化能力能应用于这些工作负载。

总体而言，我们的结果表明，Mojo 有助于缩小 Python 生态系统中的性能差距，但它仍存在差距，并且对于底层编程概念而言，学习曲线较为陡峭。

#### 观察 2：编译时与高性能计算（HPC）

1. **核心挑战：HPC从业者需适应“编译时定规则”的新习惯**。Mojo的:mdnice-bold-italic[编译时特性要求开发者在代码“打包编译”阶段，就把影响性能的关键信息（比如计算规模、硬件调度参数）全确定好]；但过去HPC领域的代码更习惯“运行时灵活调”——就像传统做饭是“炒到一半能加调料”，而Mojo要求“开火前必须把调料种类、用量全定死”。这种从“灵活调整”到“提前规划”的转变，会让熟悉旧模式的HPC从业者觉得有学习难度。
2. **潜在价值：靠MLIR探索编译器优化新可能**。Mojo基于MLIR（一种灵活的编译框架），支持“提前编译（AOT，像提前做好预制菜）”和“即时编译（JIT，像现点现做）”两种模式。这就像给编译器配了个“万能工具包”，能:mdnice-bold-italic[尝试过去传统编译做不到的优化方向（比如跨硬件适配、更精细的性能调优），为HPC领域的编译器技术提供了新的探索空间]。
3. **关键缺口：“运行时动态分配”仍需突破，且要接受优化权衡 。** “运行时动态分配”（比如程序跑起来后，根据数据量临时分配内存，像做饭时发现食材不够能临时补买）是HPC场景的刚需功能，但Mojo目前还没有。哪怕这个功能会让MLIR的优化效果打折扣（比如“临时补买食材会打乱提前规划的烹饪流程”），HPC从业者也非常期待——:mdnice-bold-italic[因为对实际业务来说，“灵活补资源”比“极致优化”更实用，只是这种“要灵活还是要优化”的权衡还需要进一步明确。]

#### 观察 3：Python 与高性能计算（HPC）的互操作性

- **Mojo策略：将非性能关键代码交给成熟的Python生态处理**；
- 关键疑问：这种“借力Python”的方式，如何与HPC技术栈（如多节点计算相关组件）配合，目前尚不明确；
- 核心悬案：MPI（HPC 多节点通信核心标准）的适配是关键缺口 ——Python 的 mpi4py 已很成熟，但 Mojo 的编译时特性与 Python 互操作是独立的，二者如何结合实现 MPI 通信，仍未解决。

#### 观察 4：库与生态系统

**Mojo 仍是 NVIDIA CUDA 和 AMD HIP 的一种底层编程替代方案**。许多高性能计算代码依赖于与高度优化的高级库的交互，而对于该语言的更广泛采用而言，此类功能（例如可移植的 BLAS 操作）的支持仍在制定中。在工具方面，:mdnice-bold-italic[对于我们的分析以及一般的高性能计算代码而言，非常有利的一点是：Mojo 可以生成编译后的可执行文件，该文件无需修改任何源代码，即可与 NVIDIA ncu 和 AMD rocprof 生态系统开箱即用（out-of-the-box）地兼容。]

## 五、相关工作

### 5.1 Mojo 相关研究

由于 Mojo 是一门较新的语言，关于其语言特性和能力的研究非常有限。

- Akre 等人[1]近期对 Mojo 作为高性能编程语言的潜力进行了**全面综述**，并整理了 GitHub 上可用的库和框架列表。他们的论文总结了该语言的应用机会，并通过初步基准测试表明，其性能相较于纯 Python 和 NumPy 代码有数量级的提升。
- Raihan 等人[50]提出了 **Mojobench 基准测试** ——鉴于针对这种新型编程语言的训练数据稀缺，该基准测试旨在:mdnice-bold-italic[填补基于大型语言模型（LLM）的 Mojo 代码生成领域的空白。]
- Huang 等人[29]引入了 **MojoFrame**，这是:mdnice-bold-italic[首个利用该语言性能特性的数据帧（dataframe）库]，突显了 Mojo 生态系统的新颖性。

### 5.2 面向科学计算的高层语言

> 在面向科学计算的高层语言领域，**Python 和 Julia 社区已做出大量努力，以缩小高生产力与性能可移植性之间的差距。**

#### 5.2.1 Python 生态系统相关工作

有多项研究致力于实现性能可移植的 GPU 编程，而无需依赖 C/C++可移植代码的包装器（wrapper）。

- 在供应商层面，NVIDIA 最近通过 cuda-python 为 Python 提供了原生支持，随后 AMD 通过引入 hip-python-as-cuda，提供了与 HIP 和 CUDA 类似的互操作性支持。
- Mattson 等人引入了 PyOMP[41]——这是 Numba[34] JIT 编译器的 OpenMP 实现，可绕过 Python 全局解释器锁（GIL，Global Interpreter Lock）。这项工作最近通过 OpenMP 卸载（offload）技术扩展到了 GPU 领域[24]，并使用 HeCBench[30]内核进行了基准测试。
- 类似地，Piñeiro 和 Pichel 提出了 OMP4Py[48]——这是一种纯 Python 实现的 OpenMP 指令，结合了 CPU 多核与 MPI 并行化。
- 最近，PyOpenCL[32]和 Cupy[43]通过字符串接口传递 C/C++自定义内核代码进行编译，除了已完善支持的 NVIDIA 生态系统外，还扩展了对 AMD GPU 的支持。
- 同样，pyKokkos[4]提供了 Python 与 Kokkos 库[54]之间的性能可移植接口，可生成 C++ Kokkos 内核和用于互操作的语言绑定。
- 最近，Briand 等人[9]对比了 Julia 和多种编程模型（包括 Kokkos.jl 包装器）与 C++ Kokkos 的性能，结果表明，在选定的计算流体动力学（CFD）内核上，Julia 的性能与 C++ Kokkos 持平。

#### 5.2.2 Julia 生态系统相关工作

基于 LLVM 的开源语言 Julia 也致力于解决软件开发过程中的碎片化问题，主要面向科学计算和 AI 领域。

- Churavy 等人[13]总结了为建立大规模计算统一生态系统所做的努力。
- Valero-Lara 等人[55]引入了 JACC——这是一个最近开发的高层性能可移植库，可抽象掉 CPU/GPU 上的底层硬件特定选项，同时与 Julia 的特定于供应商的后端（CUDA.jl[7]、AMDGPU.jl[51]和 oneAPI.jl[6]）相比，几乎没有额外开销。
- 同样，Churavy 等人开发了 KernelAbstractions.jl[12]——该库通过类似于 CUDA 和 HIP 模型的细粒度并行化方法，支持可移植的 GPU 内核编程。
- Lin 和 McIntosh-Smith[37]分析了 Julia 编程模型在 CPU 和 GPU 上运行 BabelStream 和 miniBUDE 的性能。他们的研究表明，**在多种 CPU 和 GPU 上，Julia 的性能与编译型语言（C/C++等）持平或略低**。
- Godoy 等人[27]评估了 Julia、Numba 和 Kokkos 编程模型在 CPU、NVIDIA GPU 和 AMD GPU 上的性能可移植性。该研究表明，N**umba 在 AMD GPU 上的性能和可移植性存在不足，而 Julia 的 GPU 功能显示出巨大潜力** ——尽管在简单的矩阵乘法内核上仍存在一些性能差距。
- De la Calle 等人[16]引入了 Juliana 工具，通过将 CUDA.jl 代码移植到 KernelAbstractions.jl，为 Julia 添加了 GPU 性能可移植性；该工具在包括 miniBUDE 和 BabelStream 在内的多个内核上仅引入了少量开销。

### 5.3 其他相关努力

在 HPC 领域，缩小生产力、性能和可移植性差距的努力早已存在。美国国防高级研究计划局（DARPA）的高性能计算系统（HPCS）项目[19]资助了三种语言——Chapel[10]、IBM 的 X10[52]和 Sun 的 Fortress[2]，并倾向于采用分区全局地址空间（PGAS，Partitioned Global Address Space）模型。:mdnice-bold-italic[目前只有 Chapel 仍在积极开发中，并逐步向供应商中立的 GPU 编程方向发展[31]。] 在专有领域，Parallel Matlab[11]是早期利用流行的 Matlab 语言进行并行计算的尝试。

> 因此，Mojo 与当前寻找高效、【供应商中立】的编程模型的趋势相符，旨在推动未来极端异构计算系统的发展[57]。

## 六、结论

> 本文呈现了我们在新型编程语言 Mojo 上的初步实践经验。具体而言，我们阐述了其新增的一项能力——为 NVIDIA 和 AMD GPU **编写具备性能可移植性的内核。**

我们**针对四个常见的科学计算内核展开研究**，分别是：（i）七点模板（内存受限型）、（ii）BabelStream（内存受限型）、（iii）哈特里-福克（计算受限且含原子操作型）以及（iv）miniBUDE（计算受限型）；**并将相同的 Mojo 代码分别与运行在主流 NVIDIA H100 GPU 上的 CUDA 代码、运行在 AMD MI300A GPU 上的 HIP 代码进行了性能对比。**

研究结果表明，在低级别实现层面，对于内存带宽受限的场景，Mojo 的性能与 AMD 的 HIP 性能相当。在将 Mojo 与 NVIDIA CUDA 的特定实现进行对比时，我们观察到了性能差距：

::: block-1
- 在七点模板计算中，Mojo 性能达到 CUDA 的 89%；
- 在 BabelStream 的点积（Dot）内核中，涉及共享内存操作的场景下，Mojo 性能达到 CUDA 的 78%。从积极面来看，Mojo 在 BabelStream 中简单的一维数组操作上经过了高度优化，甚至**凭借更少的缓存内存操作，性能略微超过了 CUDA**。我们通过厂商工具获取的剖析信息，:mdnice-bold-italic[对比分析了 Mojo 与 CUDA 实现之间的性能差异。要充分发挥 Mojo 的可移植性潜力，需在编译器底层进一步理解这些差异]，避免因忽视差异而导致潜力无法释放。
- 对于 miniBUDE 和哈特里-福克这**两个计算受限且包含原子操作的工作负载，Mojo 与 CUDA、HIP 相比仍存在若干性能差距**。目前尚不明确 Mojo 何时会新增基础的快速数学（fast-math，一种通过牺牲部分数学精度来提升计算速度的优化手段，常用于对精度要求不极致但对速度要求较高的科学计算场景）优化功能，而这类优化对于本次测试中的计算受限内核至关重要。此外，鉴于 Mojo 在原子操作任务中表现出的特殊结果——:mdnice-bold-italic[性能超过 CUDA 却不及 HIP，我们还需对原子操作进行更深入的分析和理解。]
:::

基于所得的性能结果，我们采用了一项性能可移植性指标进行评估。但我们认为，随着 Mojo 语言的不断成熟、新增能充分利用 MLIR（多级中间表示，一种编译器基础设施，可实现跨硬件平台的代码优化和生成）的功能，以及整合开源高性能计算（HPC）社区的反馈，**其实际的性能可移植性还将持续演进。**

与其他试图加速 Python 或从底层编译至 LLVM 的编程模型（如 Julia、Rust）不同，**Mojo 通过提供一种超集语言来缩小性能差距。这种超集语言具备三大特性**：

1. 借助 MLIR 实现丰富的编译时元编程
2. 标准库中内置具备性能可移植性的 GPU 编程能力
3. 在运行时与 Python 生态系统实现互操作

> 我们预计，Mojo 将沿着这一编程范式持续发展——按照计划，它将于 2026 年开源[6]——并逐步成为一种适用于高性能计算与人工智能（HPC + AI）领域的实用编程语言。
