## 关键问题

### 问题 1：eGPU 的 PTX 注入与 NVBit 的二进制重写在底层机制上的差异，及 eGPU 低延迟优势的原因

> 【具体问题】论文提出 eGPU 通过动态 PTX 注入实现 eBPF 字节码向 GPU 的卸载，以避免现有 NVBit 等工具的高开销与内核中断问题，但 NVBit 同样支持 GPU 动态二进制插桩，那么 eGPU 的 PTX 注入在“不中断运行中 GPU 内核”和“控制 instrumentation 开销”上，与 NVBit 的二进制重写技术存在哪些底层机制差异？这些差异为何能让 eGPU 在 128KB 以上内存访问场景中仍保持比 NVBit 更低的 latency？

从底层机制看，二者核心差异体现在**插桩层级** 与**内核干扰方式**：

1. **插桩层级不同**：NVBit 作为二进制插桩框架，需在 GPU 已编译的机器码（SASS）层面进行修改，面临二进制指令解析复杂、需兼容不同 GPU 架构的问题，易引入额外开销；而 eGPU 基于 PTX（GPU 中间表示）注入，PTX 是高于 SASS 的设备无关层，JIT 编译时可直接将 eBPF 字节码转化为 PTX 片段，无需处理已优化的机器码逻辑，操作更轻量高效，这也是其比 NVBit 性能更优的核心原因之一。
2. **内核中断与否**：NVBit 的插桩常需中断运行中的 GPU 内核以完成二进制重写，而 eGPU 依托动态 PTX 注入技术，通过 device hooks 将 PTX 片段直接注入正在执行的 GPU 内核，配合 inlineHook 实现 CUDA 代码的无中断插桩，避免了内核重启带来的延迟损耗。
3. **数据交互优化**：eGPU 通过共享内存 eBPF Maps 实现 CPU 与 GPU 的数据互通，减少了传统工具中“GPU 数据回传 CPU”的频繁拷贝开销；而 NVBit 在数据收集时易依赖主机内存拷贝，进一步放大延迟。这使得 eGPU 即便在 128KB 以上内存访问场景中，仍能保持比 NVBit 更低的 latency。

### 问题 2：小而短的 GPU 内核场景中，eGPU 的 PTX 注入与 JIT 编译开销是否会抵消优势，及现有优化方案

> 【具体问题】论文仅通过 GPU 内存访问延迟的微基准测试验证了 eGPU 的低开销，未针对大规模 LLM 训练、HPC 模拟等真实复杂 workload 开展评估，且提及“小而短的 GPU 内核可能放大 PTX 注入与 JIT 编译的开销”。那么在频繁启动小内核的真实 AI/HPC 场景中，eGPU 的 PTX 注入与 JIT 编译开销是否会抵消其“低 instrumentation 开销”的优势？现有设计中是否有针对小内核场景的优化方案？

论文明确指出当前评估局限——未针对小而短的 GPU 内核场景开展深入测试，且承认“PTX 注入与 JIT 编译在 kernel 初始化阶段的开销，在小内核、高频启动场景下可能更显著”，但也提及了可缓解该问题的**潜在优化方向**：

1. **持久化内核（Persistent Kernels）设计**：eGPU 通过减少 GPU 内核的重复启动次数，将 PTX 注入与 JIT 编译的开销平摊到更长的内核生命周期中，降低单次小内核执行的相对开销。论文提到该设计可“避免频繁内核 launches， streamline 计算流水线”，间接缓解小内核场景的开销问题。
2. **依托 bpftime 用户空间 eBPF runtime 优化**：bpftime 将 eBPF 的验证、编译从内核空间迁移至用户空间，减少了传统内核态 eBPF 的上下文切换开销；这种优化可延伸至小内核的 eBPF-PTX 交互流程，降低跨空间调度带来的额外延迟。
3. **硬件特性适配**：论文提及未来可利用 Grace Hopper 架构的硬件加速上下文与 CXL 内存池，通过硬件层面的低延迟互联与内存共享，进一步降低小内核场景下的数据同步与编译开销，不过当前尚未落地相关优化。

### 问题 3：共享内存同步是否会成为新瓶颈，及与传统 CPU-GPU 数据拷贝的权衡

> 【具体问题】eGPU 依赖共享内存（eBPF Maps）实现 CPU 与 GPU 的数据交互以减少拷贝开销，同时通过 CPU 侧原子操作、GPU 侧内存屏障保障同步。但 GPU 具有多流多 SM 并行执行特性，当多 SM 同时读写共享 eBPF Maps 以记录观测数据（如 LD/ST 指令的地址、时间戳）时，同步机制是否会成为新的性能瓶颈？这种同步开销与传统 CPU-GPU 数据拷贝开销相比，在高并发场景下如何权衡？

## 一、引言

数据密集型和计算密集型工作负载（涵盖大规模机器学习、高性能计算（HPC）模拟[10,13,19]、图形渲染[12]及大型语言模型[6]等）的快速增长，使得系统对 GPU 加速的依赖日益加深，以实现预期的性能与吞吐量。

> 随着这些 GPU 驱动的系统不断扩展，精确的可观测性与低开销的插桩变得至关重要，这对运行时诊断性能瓶颈、优化资源使用及识别异常行为不可或缺。

**现有的 GPU 插桩方法** （如 NVIDIA 的 CUDA 性能分析工具接口（CUPTI）[11]以及 NVBit[14]等二进制插桩框架）虽能提供 GPU 性能洞察，但往往会产生**显著开销**，或**需要进行侵入式修改以中断 GPU 内核。**

与此同时，Linux 的扩展 Berkeley 数据包过滤器（eBPF）已成为一种强大的可观测性框架，传统上用于网络分析[5]和系统性能分析[16,18]。**eBPF 支持轻量级、沙箱化的插桩程序在内核空间执行，无需对内核进行侵入式修改，也不会产生性能损耗**。然而，现有 eBPF 技术仍以 CPU 为中心，受限于频繁的内核-用户空间上下文切换，且对 GPU 执行模型的可见性有限。

> **将 eBPF 应用于 GPU 工作负载面临独特挑战**：GPU 执行模型具有异步内核启动、并行线程执行及专用内存层次结构等特点，这使得插桩难度显著增加，且容易产生高开销。此外，若缺乏新颖的转换与运行时适配策略，eBPF 固有的以 CPU 为中心的设计无法直接扩展到 GPU 硬件。

为填补这一空白，本文提出 eGPU——首个通过运行时 PTX 注入将 eBPF 插桩动态扩展到 GPU 内核的可观测性框架与 eBPF 运行时。具体而言，**eGPU 在运行时将 eBPF 字节码编译为 NVIDIA 的并行线程执行（PTX）中间表示，并将该插桩直接注入正在执行的 GPU 内核中**。:mdnice-bold-italic[通过利用用户空间 eBPF uprobes（用户探针）、共享内存映射及实时 GPU 遥测数据，eGPU 实现了细粒度的 GPU 插桩，且运行时开销极小]。与以往的 GPU 性能分析方案不同，我们的方法支持在 GPU 内核运行期间动态添加、修改或移除插桩，而无需中断其执行。

此外，尽管 eGPU 最初通过精确的 GPU 可观测性得以展示，但其将 eBPF 动态注入 GPU 的广泛意义远不止于插桩本身。我们的方法为可编程 GPU 计算打开了大门，有望实现运行时自适应内核优化、动态 GPU 资源管理、实时安全策略执行，以及其他现有静态或高开销插桩方法无法实现的新型 GPU 运行时修改。相关代码已在https://github.com/victoryang00/bpftime-super仓库开源。

## 二、背景

> 在本节中，我们将介绍支撑后续章节讨论的基础概念。

### 2.1 bpftime

基于内核的 eBPF 操作（尤其是用户探针 uprobes）会因频繁的上下文切换而产生显著开销。通过将这些操作迁移到用户态，**bpftime 消除了多次上下文切换的需求，性能提升可达 10 倍**。这种方法还提高了**可配置性，降低了与内核级权限相关的安全风险，并支持在进程内高效地进行系统调用挂钩** （syscall hooking）。此外，bpftime[17]:mdnice-bold-italic[支持共享内存中的用户态 eBPF 映射（eBPF Maps）]，且与 clang、libbpf 等现有 eBPF 开发工具保持兼容，甚至:mdnice-bold-italic[通过 BTF（BPF Type Format）提供 CO-RE（Compile Once – Run Everywhere，一次编译、到处运行）支持]。最终，bpftime 为用户态 eBPF 提供了一个更简洁、灵活且安全的运行时环境。

从历史上看，扩展伯克利包过滤器（eBPF）程序大多局限于内核态，这是因为它们与网络、追踪、安全 enforcement 等底层系统操作紧密集成。**eBPF 中的用户探针（uprobes）机制允许在用户级函数的入口或出口点进行插桩**，但当由内核管理时，这种机制常会因用户态与内核态之间的执行上下文切换开销而导致性能损耗。

:mdnice-bold-italic[这些开销源于每次探针触发时操作系统必须执行的额外步骤，包括保存处理器状态以及将控制权转移到内核]。在存在多个探针或高事件频率的场景下，这种延迟会变得十分显著，最终会限制系统吞吐量和数据收集速度。**通过将这些用户探针及其他挂钩点迁移到用户态，bpftime 框架大幅减少了此类上下文切换，在不损失功能的前提下加快了追踪操作的速度。**

这种用户态方案还**绕开了对某些内核级权限的需求**，缩小了内核的攻击面，同时降低了开发者和运维人员在不具备完整管理员权限的情况下使用 eBPF 的门槛。此外，bpftime 系统采用二进制重写技术实现了安全高效的函数挂钩，无需重启系统或重新编译代码，就能为进程提供基于 eBPF 的高级可观测性能力。凭借对共享内存 eBPF 映射的支持，bpftime 将其功能扩展到了多进程场景和控制平面交互，同时仍与成熟的 eBPF 工具链保持兼容，并保留了 CO-RE 特性。

### 2.2 PTX 即时编译（JIT）

> PTX（并行线程执行，Parallel Thread Execution）是 **NVIDIA GPU 的中间表示形式，为并行计算提供了设备无关层**，其速度优于 NVBit[9,14]等工具。在文献[7,8]中使用的 PTX 即时（JIT）编译技术，允许开发者实时将 PTX 代码转换为 GPU 专用的机器指令，从而能够实时地调整和优化程序。

这种能力不仅限于简单的运行时编译：它还**支持动态插桩**，:mdnice-bold-italic[用户可在 PTX 指令被转换为最终机器代码（SASS，Shader Assembly Language）之前对其进行拦截和修改]。通过这种方式，开发者可以将性能分析计数器、内存检查或自定义分析逻辑直接嵌入 GPU 内核，且开销极小。由于 PTX JIT 在更高层级的中间表示（IR）上运行——而非像 NVBit 等框架那样在原始二进制级别运行——它通常能实现更优的性能，因为它避开了重写完全编译后的机器指令所带来的复杂性。这使得生成的代码能够根据特定 GPU 架构进行高度优化，充分利用寄存器使用、warp 调度等架构特性。

此外，PTX JIT 与 NVCC、NVRTC 等现有 NVIDIA 工具链自然集成，用户无需脱离熟悉的工作流程，就能优化或生成专用内核，且无需在每次需要修改或插桩内核时进行耗时的离线重编译。

## 四、eGPU 设计

![文章插图](/articles/2025-09-15-egpu-ebpf-gpu-ptx-ebpf-c7a0b33b/images/05.webp)

> 图 1 展示了一个统一的用户空间 eBPF 环境，该环境与现有 eBPF 工具链、基于 CUDA 的组件以及传统内核级 bpf 系统调用（bpf syscall）相集成。

从左上角开始，eBPF 程序源通过 clang、bpftool 或 bpftrace 等标准工具进行编译，生成 eBPF 字节码。这些字节码随后进入用户空间 eBPF 运行时，在执行前会被加载，且可能经过插桩或转换处理。

在中间部分，存在一个 eBPF 用户空间应用层，该层引用了一个用户空间库（例如 libbpf）。此库支持与 eBPF 函数 API 的交互，使应用能在运行时加载或调用 eBPF 函数。该层中的关键组件是`bptime-syscall.so`，它提供了用户空间验证器和即时编译器（JIT 编译器）。这两个组件承担了传统内核级 eBPF 的典型任务（如验证程序安全性、将字节码转换为原生指令），但无需依赖内核级权限。最终，用户空间 eBPF 程序在保留验证、即时编译等熟悉特性的同时，还获得了灵活性和可移植性。

在用户空间下方，存在一个 bpf 系统调用接口，该接口可选择性地将用户空间层与内核 eBPF 子系统连接。:mdnice-bold-italic[尽管图中重点展示了以用户空间为核心的工作流，但 bpf 系统调用的存在确保：若系统设计需要更深度的内核集成，或需将 eBPF 挂载到传统内核钩子上，可将 eBPF 字节码或 eBPF 映射（eBPF maps）加载到内核中。]

在中下部区域，存在一个用于存储 eBPF 映射的共享内存区域。该共享内存不仅可被用户空间组件访问，还可被右侧所示的 CUDA 代码访问。通过将这些映射注册为固定内存（pinned memory）或类固定内存（pinned-like memory），GPU 和 CPU 上下文能够观测并更新相同的数据结构，无需重复复制的开销即可实现事件和统计数据的动态交换。这种设计对于高吞吐量插桩或数据收集场景十分有利。

![文章插图](/articles/2025-09-15-egpu-ebpf-gpu-ptx-ebpf-c7a0b33b/images/05.webp)

图的右侧展示了一个 CUDA 环境，在该环境中，用户空间 eBPF 可扩展以生成或注入 PTX 代码。此环境中的 JIT 编译器会将 eBPF 字节码转换为 PTX 或其他 GPU 兼容格式，随后这些支持 GPU 扩展的 eBPF 特性可挂载到 GPU 领域内的用户探针（uprobe）或跟踪点（tracepoint）等钩子上。图中的“inlineHook”（内联钩子）表示能够在 CUDA 代码内部的特定点插入插桩，使开发人员能以类似于 eBPF 在 CPU 进程内核中运行的方式，跟踪 GPU 端操作。在此处注入的 eBPF 程序可与系统其他部分共享的 eBPF 映射进行交互，确保监控、收集或过滤逻辑在 CPU 和 GPU 边界之间保持一致。

该图还凸显了另一重要特性：**系统支持多种“挂载”目标**。内核 eBPF 通常支持内核探针（kprobe）、套接字（socket）和跟踪点（tracepoint），而此处所示的用户空间 eBPF 变体则可根据用户需求，挂载到更高级别的事件上，包括应用级函数调用或 GPU 钩子。这种统一的方法构建了一个单一的用户空间 eBPF 解决方案，该方案可扩展至 GPU 领域，同时根据部署需求，通过 bpf 系统调用选择性地回连到内核。

从设计价值来看，通过将验证和编译迁移到用户空间，该设计提高了 eBPF 的可访问性，使开发人员无需修改特权内核即可开发、调试和部署基于 eBPF 的解决方案。同时，借助 PTX 注入，系统实现了与 GPU 资源的紧密集成，支持设备端跟踪、性能分析或自定义事件处理。共享内存设计确保了用户空间应用、GPU 代码与 eBPF 映射之间的低延迟通信，这对于实时或性能关键型插桩至关重要。总体而言，该架构在保留与标准工具链和生态系统兼容性的同时，将 eBPF 的传统能力扩展到了新领域，提供了一个灵活的环境。

## 五、eGPU 实现

本节将详细介绍 eGPU 的实现细节。

### 5.1 自修改代码

:mdnice-bold-italic[ParallelGPU OS（简称 POS）[8]是一种新型的操作系统级 GPU 检查点与恢复系统，可与 GPU 应用的执行过程并发运行。]

> 其核心贡献与创新点包括：POS 无需对应用进行任何修改，它会**拦截 GPU 驱动 API 调用**，并构建一个运行时内核有向无环图（DAG），以捕获细粒度语义。

具体而言，即**内核执行期间哪些 GPU 缓冲区被读取或写入**。通过从内核参数中推测性提取缓冲区访问模式（并通过运行时验证确保准确性），POS 能够模拟“软写时复制”“软脏位”和“软按需加载”等特性。这种方法克服了 GPU 的固有局限性（GPU 缺乏原生脏位和写时复制支持），支持协同的并发检查点与恢复操作。**POS 将检查点/恢复操作与正常 GPU 执行过程重叠进行，大幅减少了停机时间**。这种并发性是通过利用内核 DAG 调度内存复制、管理依赖关系实现的，无需暂停应用进程。我们将 POS 用于 PTX 自修改代码的实现。

### 5.2 共享内存

在实现中，我们使用`boost::managed_shared_memory`（Boost 库中的托管共享内存）促进不同进程间的透明数据交换。该共享内存区域存储了 CPU 和 GPU 内核均可并发访问的关键数据结构，例如 eBPF 映射、输入批次或中间状态。在设计该内存时，我们充分考虑了直接 GPU 兼容性，从而减少了通过高开销复制操作来回编组数据的需求。此外，:mdnice-bold-italic[我们预见了下一代硬件（如 Grace Hopper 架构和 CXL 内存池）的潜力——这些硬件有望通过低延迟互连统一大型内存区域，从而无缝扩展`managed_shared_memory`的容量和性能]，使内核能在更广泛的数据集上运行，且不会产生频繁的同步或复制开销。

### 5.3 同步机制

由于多个 CPU 线程和 GPU 内核共享数据结构，必须谨慎管理同步过程，以避免竞争条件并确保内存一致性。我们依赖于在不同层级运行的多种同步机制：

- 在 CPU 端，使用标准的基于锁或无锁的数据结构（例如，使用`std::atomic`或 Boost 进程间原语），确保主机进程不会在共享区域中引入不一致状态；
- 在 GPU 端，使用 CUDA 原子操作和设备级内存屏障，序列化对全局或共享内存的更新。在`managed_shared_memory`中定义清晰的数据布局为上述策略提供了支持，确保异步更新对所有参与者可见。**对于频繁的小规模同步事件，我们通过仅让一小部分线程执行原子操作来最小化 warp 级冲突**，而内核的其余部分则继续并行处理数据。

### 5.4 PTX 生成与注入

我们的系统会将 eBPF 或应用特定代码转换为 PTX，以支持 GPU 端插桩和计算。当用户空间或 eBPF 逻辑请求将特定函数卸载到 GPU 上，或在 GPU 上跟踪特定函数时，系统的 JIT 编译器会生成专用的 PTX 代码片段，并通过设备驻留钩子将其动态注入到正在运行的内核中。我们将此技术**称为“PTX 注入”，它无需销毁现有内核上下文即可拦截或插入指令**，与“停止内核 → 重新编译整个代码库 → 重新启动”的传统方式相比，大幅降低了开销。

注入完成后，PTX 代码可与 eBPF 映射或其他共享内存缓冲区互操作，能够直接访问 CPU 端使用的相同数据结构。PTX 注入为 GPU 插桩、跟踪点和用户定义逻辑提供了灵活的环境，可随着新工作负载的到来或插桩需求的变化实时调整。通过谨慎管理内存屏障和代码修补点，我们确保新注入的 PTX 能与之前运行的内核组件正常交互。

总而言之，**eGPU 集成了检查点/恢复（C/R）、共享内存、可靠同步和基于 PTX 的卸载技术，提供了一种低开销、自适应的 GPU 计算模型**。持久化内核消除了重复启动的开销，共享内存降低了数据复制成本，同步原语防范了数据风险，PTX 注入则支持细粒度动态插桩。展望未来，Grace Hopper 架构和 CXL 内存池中的改进硬件特性有望进一步增强这些优势，降低系统开销并扩大用户扩展 GPU 工作负载的应用范围。

## 六、使用案例

### 6.1 GPU Memory Observer and CXL.mem Simulator

为实现对 GPU 内存行为的细粒度可观测性，eGPU 对底层内存操作（具体为 NVIDIA GPU 架构上的加载（LD）和存储（ST）指令）进行插桩。这些指令是 GPU 内存访问模型的核心，通过捕获每一次 LDR 和 STR 操作，我们的工具能够提供以往研究无法实现的内存带宽利用率、访问模式以及竞争情况的深入洞察。

我们利用**基于 eBPF 的插桩技术，挂钩到与 LD 和 ST 操作对应的 GPU 内核事件**。:mdnice-bold-italic[通过在 CUDA 驱动栈的关键函数处放置探针，我们捕获每次操作的元数据]，例如内存地址、访问大小和时间戳。这种详细的日志记录能够计算实时指标（如内存带宽）。例如，时间窗口$T_{window}$内的带宽可表示为：

$$
BW=\frac{\sum_{i=1}^{N} Bytes _{i}}{T_{window }}, \tag{1}
$$

其中，$Bytes_i$是第 i 次操作中传输的字节数，N 是该时间窗口内观测到的内存操作总数。此外，聚合数据还能揭示访问模式（如合并访问与离散访问）以及多个流式多处理器（SM）并发执行内存操作时的竞争程度。

**除观测功能外，我们还通过在观测到的内存操作中引入动态延迟插入，利用 CXL.mem 模拟第二层内存**。该模拟的目标是仿真 CXL 附加内存的行为——与本地 GPU 内存相比，CXL 附加内存通常具有更高的延迟和更低的带宽。在我们的模型中，内存操作的有效访问延迟表示为：

$$
T_{access }^{(CXL)}=T_{access}^{(local)}+\Delta t\left( pattern, BW_{curr }\right), \tag{2}
$$

其中，$T_{access}^{(local)}$是访问本地 GPU 内存的原生延迟，$\Delta t(pattern, BW_{curr})$是动态延迟函数，其值取决于观测到的访问模式（如顺序访问与随机访问）和当前内存带宽利用率$BW_{curr}$。例如，**与随机访问相比，顺序（流式）访问可能会产生更小的附加延迟；而当竞争程度较高时（即$BW_{curr}$接近 CXL 链路容量时），$\Delta t$会进一步增大。**

这种动态延迟模型能够仿真双层内存系统——在该系统中，数据可能驻留在快速的本地内存中，也可能驻留在较慢的 CXL 附加内存中。我们的实验对比了启用和未启用 CXL.mem 模拟时 GPU 内核的性能。:mdnice-bold-italic[特别是内存密集型内核，在承受附加延迟时，其有效延迟会显著增加（最高达 2-3 倍）]，这一结果凸显了内存容量增加与访问速度降低之间的权衡关系。这些发现与以往关于 CXL.mem 系统的研究[15]一致。

### 6.2 LLM CPU-GPU Collaborative Caching

> 大型语言模型（LLM）很容易耗尽 GPU 内存，因此需要一种 CPU-GPU 协同缓存方案来处理其庞大的状态数据。:mdnice-bold-italic[核心挑战在于确定哪些数据应保留在速度更快的 GPU 内存中，哪些数据应驻留在 CPU 内存中（需用时再传输）]。一个高效的缓存不仅要智能地淘汰数据，还要预取数据以最大限度减少传输开销。

eGPU 在此过程中发挥关键作用：它能够详细呈现缓存的行为，以及跨越 CPU 和 GPU 的底层内存访问模式。通过记录页错误、DMA 复制调用和统一内存迁移等事件，我们的工具可以揭示哪些模型参数和激活值被频繁访问，哪些则处于闲置状态。工程师随后可优化缓存策略，例如确保访问频率最高的权重保留在 GPU 中，而活跃度较低的数据则留在 CPU 端，直至需要时再传输。

**淘汰策略对于管理有限的 GPU 内存至关重要**。最近最少使用（LRU）是一种常用策略：当缓存已满时，淘汰最长时间未被访问的数据。许多 AI 框架的 GPU 缓存默认采用 LRU 策略，会:mdnice-bold-italic[先将最近最少使用的层或“专家网络”卸载到 CPU 内存中]。另一种选择是:mdnice-bold-italic[最不常用（LFU）策略，该策略保留访问次数最多的项]。在一小部分权重占主导使用的场景中，LFU 的性能可能优于 LRU。将 LRU 或 LFU 等动态策略与静态缓存相结合也很常见——在静态缓存中，某些数据会根据领域知识固定在 GPU 内存中（例如模型中最关键的层）。混合策略可能会在多轮对话中淘汰最旧的对话上下文，同时对所有会话数据应用 LRU 策略。通过监控缓存命中率和传输量，eGPU 有助于验证这些策略的有效性。

除淘汰策略外，**CPU 与 GPU 之间的共享内存配置** 也对性能有重大影响。NVIDIA 的统一内存（Unified Memory）创建了一个跨越 CPU 和 GPU 的单一地址空间，能够根据页错误自动迁移页面。:mdnice-bold-italic[虽然统一内存简化了开发流程，但其性能取决于页面在 CPU 和 GPU 之间往返迁移的频率]。eGPU 可轻松识别重复的页错误或不必要的传输，进而提示何时采用手动方法（如使用固定主机内存）可能更优。固定内存支持更快的 DMA 传输，而直接主机访问（Direct Host Access）等技术则允许 GPU 内核通过 PCIe 直接从 CPU 内存读取数据。这些优化通常会将数据移动与计算重叠，以减少延迟。

**进一步的优化包括零复制缓冲区（zero-copy buffers）和流有序预取（stream-ordered prefetching）**。零复制缓冲区允许 GPU 线程直接访问主机内存（无需冗余复制），而预取则会在数据被需要前将其发送到 GPU。实际应用（如 DeepSpeed Zero-Inference 中的模型卸载，或为 Transformer 层缓存键/值向量）:mdnice-bold-italic[通过结构合理的协同缓存可获得显著收益]。通过展示每种缓存方法的性能，eGPU 加快了开发周期，并降低了大规模 LLM 的推理时间。

![文章插图](/articles/2025-09-15-egpu-ebpf-gpu-ptx-ebpf-c7a0b33b/images/06.webp)

图 2 展示了与文献[9]的微基准测试对比，阐明了我们内存缓存方法的有效性。**我们对比的基准方案名为 gpumemtrace**，它对 mov 指令进行插桩，并将其逻辑重定向以将内存传输到主机。然而，如图所示，NVBit 的插桩开销成为瓶颈——尤其是当哈希映射的值大小超过 32KB 时。超过此阈值后，数据无法放入 eBPF 栈中，必须驻留在全局映射中，从而影响性能。

## 七、实验评估

我们在配备双路 Intel Xeon E5-2697-v2 处理器（48 核，2.7 GHz，30 MB 末级缓存）、256 GB DDR3 内存和 NVIDIA P40 GPU 的系统上对 eGPU 进行了评估。

### 7.1 Micro-benchmark 性能

我们首先通过一个以延迟为核心的微基准测试，评估了 eGPU 引入的插桩开销。具体而言，我们在对加载和存储操作进行插桩的同时，测量了 GPU 内存访问延迟，并将 eGPU 与基于 NVBit 的插桩方案（gpumemtrace [14]）进行了对比。我们使用一组不同内存访问大小的操作对两种系统进行了评估。

![文章插图](/articles/2025-09-15-egpu-ebpf-gpu-ptx-ebpf-c7a0b33b/images/06.webp)

如图 2 所示，我们的微基准测试结果表明，**与基于 NVBit 的方案相比，eGPU 引入的插桩开销显著更低**。

- NVBit 由于沉重的插桩开销，导致延迟大幅增加；
- 而 eGPU 在较小内存访问大小（128 KB 以下）的情况下，保持了相对稳定且较低的延迟。:mdnice-bold-italic[当内存访问大小超过 128 KB 时，延迟略有增加，但仍低于基准方案。]

这些结果验证了我们的核心设计决策：在运行时动态注入轻量级 PTX 插桩，与传统 GPU 插桩方法相比，能显著降低开销。

### 7.2 实验结果与局限性分析

尽管我们的微基准测试清楚地证明了 eGPU 的低插桩开销，但我们承认**当前的评估范围存在局限性**。具体而言，我们:mdnice-bold-italic[尚未在复杂的实际工作负载（如大规模机器学习模型或高性能计算（HPC）模拟）上进行全面的端到端性能评估]。此外，虽然在我们的测试中，内核初始化时 PTX 注入和 JIT 编译的开销相对较小，但:mdnice-bold-italic[在涉及大量小型、短生命周期内核的工作负载中，这种开销可能会更加显著。]

未来的评估将通过在真实 GPU 工作负载上评估 eGPU（包括对总体运行时间、吞吐量和系统资源利用率的详细对比）来解决这些局限性。此外，我们还将研究进一步的优化措施（以降低 PTX 编译开销）和增强的同步方法，以确保 eGPU 在各种生产场景中具有更广泛的适用性和更高的效率。

## 八、结论

> 我们的早期测试表明，**eGPU 通过避免频繁的内核启动有助于降低开销，并通过共享内存支持更快的数据交换**。它还能够:mdnice-bold-italic[处理动态代码注入，且不会中断正在运行的内核]。通过让 GPU 持续运行长时间内核，我们:mdnice-bold-italic[简化了计算流水线，并更有效地平衡了工作负载]，这**对于流处理任务或非规则任务而言尤其有帮助。**

我们借助`boost::managed_shared_memory`实现了 CPU 与 GPU 在共享数据空间上的协同工作。这不仅降低了数据来回传输的成本，还简化了并发处理流程。同时，在运行时注入 PTX 代码使我们能够实时调整或插桩 GPU 代码，而无需重启整个系统——这对于任何需要实时灵活性的应用来说都是一项显著优势。

当然，**目前仍存在一些有待解决的问题**。:mdnice-bold-italic[即时编译（JIT）本身会引入额外开销]，且在检查点-恢复（checkpoint-restore）机制下管理:mdnice-bold-italic[小型内核也具有一定挑战性]。我们认为，通过微调每个内核使用的流多处理器（streaming multiprocessors）数量，或利用新一代 GPU 架构上的硬件加速上下文，有望进一步提升性能。

展望未来，我们将探索更广泛的设备上下文和内存共享方法——尤其是在即将推出的 Grace Hopper GPU 以及 CXL 内存池上——以扩展该方法的应用场景和适用范围。

> 总体而言，我们目前的研究结果表明，加强同步机制并增加更灵活的、基于 PTX 的插桩技术，有望为构建面向 GPU 驱动型工作负载的高响应性、高吞吐量框架奠定基础。
