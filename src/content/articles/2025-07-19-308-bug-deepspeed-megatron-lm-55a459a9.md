LLMPerf：GPU性能建模与大型语言模型的融合

> 随着大型语言模型（LLMs）的快速发展，DeepSpeed 等分布式训练和推理框架已成为跨多个 GPU 或节点扩展模型训练和推理的关键基础设施。

然而，这些框架日益增长的复杂性引入了非 trivial（不简单的、需要认真处理的）软件漏洞，这些漏洞可能会损害训练性能、导致意外故障，并造成大量资源浪费。理解框架漏洞的特征是质量保证的基础步骤，有助于设计更有效的调试和修复方法。

::: block-1
因此，本文首次:mdnice-bold-italic[对三个广泛使用的分布式训练和推理框架] （**DeepSpeed、Megatron-LM 和 Colossal-AI**）的 :mdnice-bold-italic[308 个已修复漏洞] 进行了大规模:mdnice-bold-italic[实证研究]。

我们考察了**漏洞症状、根本原因、漏洞识别和修复工作**，以及常见的**低难度修复策略**。我们的研究结果表明，:mdnice-bold-italic[最常见的症状包括崩溃、功能错误和构建失败，而漏洞的根本原因主要是 API 误用、实现错误、配置错误和前置条件缺失]。

此外，这些框架的**分布式特性引入了独特的漏洞根源**，如分配策略错误和分布式通信错误。由于:mdnice-bold-italic[症状与根源脱节、漏洞复现成本高以及底层或跨组件交互等因素，诊断和修复复杂漏洞仍然具有挑战性]。有趣的是，我们观察到 **48%的漏洞修复只需最少的代码更改** （≤10 行代码），并遵循简单策略，如条件逻辑优化、参数处理增强或版本兼容性处理，这表明存在自动化潜力。
:::

基于这些见解，我们为提高分布式训练和推理框架及其依赖的 LLM 项目的可靠性提供了**若干启示**，同时也指出了**利用基于 LLM 的工具进行自动化调试和修复** 的机会。

## 关键问题

### Q1：分布式训练和推理框架中最常见的 bug 症状是什么？

解答：根据研究，:mdnice-bold-italic[最常见的 bug 症状] 为**训练崩溃、功能错误和构建失败**。

- 训练崩溃指程序能编译启动但执行中意外终止（如 DeepSpeed 中因张量不匹配导致 LoRA 过程错误终止）；
- 功能错误指程序运行正常但输出不正确（如 DeepSpeed 中推理结果因位置编码逻辑不一致导致非确定性）；
- 构建失败指编译阶段因编码错误或环境问题无法完成（如 DeepSpeed 因未支持 M2 芯片导致安装失败）。

此外，系统挂起（程序停滞无输出）是最不常见的症状。

### Q2：这些框架中 bug 的主要根本原因是什么？分布式特性带来了哪些独特原因？

解答：主要:mdnice-bold-italic[根本原因] 包括**API 误用、错误实现、配置错误和缺少前提条件**。

- API 误用指未充分考虑 API 的参数设计或调用方式（如 Megatron-LM 调用 load 函数时遗漏关键参数）；
- 错误实现指技术方案应用或算法实现错误（如 Colossal-AI 中 OPTActor 模块未正确加载预训练权重）；
- 配置错误指固定参数或脚本配置缺陷（如 DeepSpeed 多节点安装脚本默认依赖共享文件系统，不支持自定义路径）；
- 缺少前提条件指未检查关键前置条件（如 DeepSpeed 创建张量时未检测输入参数为空的情况）。

分布式特性带来的独特原因包括：

- 分配策略错误（资源分配逻辑缺陷，如 DeepSpeed 未正确处理 arange 和 eye 函数的设备分配）；
- 分布式通信错误（节点间通信处理不当，如 Colossal-AI 工作节点错误状态未传递给主节点）；
- 分布式张量错误（跨节点张量处理问题，如 Megatron-LM 中 view 操作处理非连续张量失败）；
- 并发错误（并行执行场景问题，如 Colossal-AI 多进程梯度通信时内存访问无效）。

### Q3：诊断和修复这些框架中复杂 bug 的主要挑战是什么？

解答：主要挑战包括：

1. **症状与根本原因脱节**：症状与原因无直接关联，增加定位难度（如 DeepSpeed 中 loss scaler 警告实际源于分布式通信中 fp16 数据以 bf16 状态传输）；
2. **复现成本高**：复现需大量计算资源，如 DeepSpeed 中某 bug 仅在 8 张 A100 GPU 训练大参数模型时触发，资源不足则无法复现；
3. **低级别或跨组件交互复杂**：底层架构设计缺陷（如 DeepSpeed 推理引擎与优化器强耦合）、算法逻辑错误（如分布式注意力机制实现问题）或跨模块交互（如 Colossal-AI 中模型分片与流水线引擎协调问题）均增加修复难度。

## 一、引言

近年来，人工智能领域在模型规模、架构复杂性和训练数据量方面经历了指数级增长[1], [2]。这一趋势在大型语言模型（LLMs）的开发中尤为突出，这些模型通常包含数十亿到数千亿个参数，为满足计算和内存需求，需要跨多个 GPU 进行分布式训练和推理[3], [4]。虽然 TensorFlow 和 PyTorch 等通用框架提供了分布式训练的基本支持，但在扩展到 LLM 级工作负载时，它们存在关键局限性。**这些局限性包括 GPU 内存饱和、跨节点的亚线性扩展（sublinear scaling，指随着节点增加，性能提升低于线性比例），以及梯度同步过程中的通信瓶颈[5]-[7]。** 为应对这些挑战，DeepSpeed[8], [9]、Megatron-LM[10], [11]和 Colossal-AI[12], [13]等:mdnice-bold-italic[专门的分布式训练和推理框架应运而生，成为关键基础设施]。这些框架集成了一整套优化技术，包括先进的并行策略（如数据并行、模型并行、管道并行和张量并行）和内存优化技术（如混合精度计算和 ZeRO[14]），以提高训练和推理的可扩展性和效率，同时缓解内存限制。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/04.webp)

如表 I 所示，这些分布式训练和推理框架的官方 GitHub 仓库明确列出了使用这些框架训练的主要 LLM，或指定了它们支持训练/微调及推理的模型。一个典型例子是 BLOOM[15]模型，它是使用 Megatron-DeepSpeed 框架训练的。这种组合方案集成了 Megatron-LM 的 Transformer 实现、张量并行和数据加载功能，以及 DeepSpeed 提供的 ZeRO 优化器、模型管道和通用分布式训练组件。:mdnice-bold-italic[BLOOM 的训练过程消耗大量资源，耗时 3.5 个月，消耗 1,082,990 小时，使用了分布在 48 个节点上的 384 块 NVIDIA A100 80GB GPU] [15]。如此巨大的资源投入凸显了框架可靠性的关键需求，因为**潜在的漏洞可能会降低效率、导致进程挂起或崩溃**，从而浪费昂贵的计算资源。

尽管这些框架作用关键，但它们并非没有软件漏洞，GitHub 上报告的与漏洞相关的实际问题就证明了这一点。例如，由于 DeepSpeed 的梯度累积过程中缺少 grad_accum 属性，OpenRLHF[16]——一个拥有 6900 个 GitHub 星标、依赖 DeepSpeed 作为核心组件的知名人类反馈强化学习（RLHF）工具包，在 Llama 模型训练期间出现了意外的训练崩溃。这个漏洞[17]引起了其他开发者的关注。:mdnice-bold-italic[一位开发者称其为“严重漏洞”，另一位则问道：“有没有什么权宜之计或解决方案可以快速修复这个问题？] ” 尽管分布式训练和推理框架中的漏洞具有严重性和普遍性，但之前的研究并未系统地描述这类专门系统中漏洞的性质。**理解框架中漏洞的特征是质量保证任务的基础步骤，有助于设计有效的调试和漏洞修复方法**。因此，我们从 DeepSpeed、Megatron-LM 和 Colossal-AI 的 GitHub 仓库中收集了 308 个已修复的漏洞（表 I）。:mdnice-bold-italic[我们的研究围绕以下四个研究问题（RQs）展开]：

### RQ1：分布式训练和推理框架中的漏洞有哪些症状？

我们的分析表明，最常见的症状是训练崩溃、功能错误和构建失败。相比之下，性能不佳和 CI/CD 错误等症状出现的频率较低，而系统挂起是最不常见的。

### RQ2：这些漏洞的根本原因是什么？

最普遍的根本原因包括 API 误用、配置错误、实现错误和前置条件缺失。此外，这些框架的分布式特性引入了几种独特的故障模式，包括分配策略错误、分布式通信错误、分布式张量错误和并发错误。我们观察到，几乎所有这些根本原因都可能导致四种最常见的症状：崩溃、功能错误、构建失败和性能不佳，这凸显了利用特定症状识别漏洞根本原因的挑战性。

### RQ3：在分布式框架中，阻碍有效根本原因识别和漏洞修复的关键挑战是什么？

6%的漏洞开放时间超过一个月，且积累了十多条评论，这表明调试工作量大。此外，20%的漏洞需要超过 50 行代码（LOC）的补丁。通过对这些案例的深入分析，我们确定了根本原因识别和漏洞解决中的关键挑战，包括观察到的症状与其潜在原因脱节、漏洞复现的高计算开销、底层架构复杂性、特定算法逻辑错误以及跨组件交互。

### RQ4：对于通过最少代码更改修复的漏洞，常用的修复策略是什么？

48%的漏洞通过不超过 10 行代码的小补丁得到解决。这些低难度修复通常遵循常见模式，如条件逻辑优化、参数处理增强、API 替换、配置调整和版本兼容性处理。这些策略表明未来有开发自动化修复技术的潜力。

> 基于这些发现，我们为框架开发者、用户和研究人员提供了一些实用启示。

为减轻框架漏洞风险，开发者应加强 API 输入验证、增强版本兼容性测试（如 PyTorch），并通过模拟模式（用于轻量级复现）和富含上下文的日志（如节点 ID、张量形状）改进调试支持。

::: block-1
- 建议框架用户采用**静态-动态混合分析工具**，以识别框架中的漏洞如何影响其下游项目组件。
- 小型、反复出现的修复的普遍性表明，**有机会将基于模板的修复与 LLM 相结合**。
- 此外，**特定领域的漏洞** （如分配策略错误）和**复杂的跨组件问题** 需要将检索增强生成（RAG）与面向推理的 LLM（如 GPT-o1[18]、DeepSeek-R1[19]）以及程序依赖分析相结合，以实现:mdnice-bold-italic[系统级解决]。
:::

本文的:mdnice-bold-italic[主要贡献如下]：

（1）我们首次对三个广泛使用的**分布式训练和推理框架的 308 个漏洞进行了大规模实证研究**，并对其进行了特征描述。此外，我们:mdnice-bold-italic[公开了带注释的数据集]，以促进未来的研究[20]。  
（2）我们的**分析揭示了诊断和解决复杂漏洞的主要挑战**，以及具有:mdnice-bold-italic[潜在自动化可能] 的常见低难度修复策略。  
（3）我们得出了关于提高分布式训练和推理框架及其下游 LLM :mdnice-bold-italic[项目可靠性的启示]，同时也指出了**利用工具进行自动化调试和修复的机会**。

## 二、研究过程设计

### A. 框架选择

我们的研究设计概述如图 1 所示。![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/05.webp)

> 为确定具有代表性的分布式训练和推理框架，我们定义了三个选择标准。

首先，借鉴先前关于深度学习框架漏洞分析的研究[21], [22]，我们**优先选择积极维护的、具有大量社区参与的分布式训练和推理框架**，以 GitHub 星标和分支数量衡量。其次，我们要求官方文档明确列出使用这些框架训练的主要 LLM，或它们声明支持训练、微调的特定模型。最后，我们**只纳入有标记为“bug”的已关闭问题且这些问题与已合并的拉取请求** （PRs）相关联的框架。

有几个分布式训练和推理框架因以下原因未满足我们的选择标准：

- EasyParallelLibrary[23], [24]和 Alpa[25]已超过两年未更新；
- MindSpeed-LLM[26]的星标和分支数量极少；
- Meta Lingua[27], [28]缺乏标记为“bug”的已关闭问题。

**最终，我们选择了三个广泛使用的框架**：DeepSpeed（微软）[8], [9]、Megatron-LM（英伟达）[10], [11]和 Colossal-AI（HPC-AI Tech）[12], [13]。这些框架采用了一整套优化技术，以提高分布式训练或推理的可扩展性、效率和内存使用。例如，DeepSpeed 通过集成多种复杂策略的核心架构体现了这些进步：

1. 3D 并行：DeepSpeed 引入了 3D 并行，这是一种结合数据并行、模型并行和管道并行的混合策略。通过整合这三种并行形式，DeepSpeed 在数千个 GPU 上实现了高可扩展性，同时保持了高吞吐量并最小化了通信开销。
2. 内存优化技术：在传统设置中，每个 GPU 都维护模型状态的完整副本，包括参数、梯度和优化器状态，这极大地限制了可扩展性。

### B. Bug 数据收集

为系统地研究分布式训练和推理框架中漏洞的特征，我们借鉴了先前对机器学习和深度学习框架漏洞的分析方法[22], [29]-[32]，分析每个框架仓库中标记为“bug”且明确关联到已合并 PRs 的已关闭问题。已关闭的问题意味着开发社区正式确认并解决了该漏洞。

::: block-1
我们采用这种基于问题的方法，而非直接分析修复漏洞的 PRs，主要有四个原因：

1. PRs 通常包含功能增强、性能优化或其他非缺陷更改，若不与问题明确关联，难以识别漏洞修复；
2. 许多修复漏洞的 PRs（如[33], [34]）缺乏足够的文本信息，难以推断漏洞的症状和根本原因；
3. 相比之下，问题描述通常记录了开发者遇到的故障，如训练崩溃，提供了 LLM 训练过程中漏洞实际症状的宝贵上下文；
4. 标记为“bug”的问题的评论数量及其时间戳（即创建和关闭日期）使我们能够评估根本原因识别的难度和漏洞的开放持续时间。
:::

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/04.webp)**表 I 中的“漏洞”列报告了三个分布式训练和推理框架中标记为“bug”的已关闭问题的数量统计**，每个问题都关联到相应的已合并 PR。我们还确认，我们数据集中的所有漏洞都是独特的，确保每个条目代表本研究中分析的一个 distinct（独特的）漏洞实例。

### C. 手动标记漏洞症状与根本原因

我们通过**两阶段过程系统地标记每个漏洞的症状、根本原因和发生阶段** （训练或推理）。

首先，我们随机抽取 40%收集到的标记为“bug”的问题及其 PRs 进行试点标记，以制定初始分类法。具体而言，按照开放编码方案[35]，两位作者**借鉴了先前深度学习框架漏洞研究[21], [29], [30]中的通用症状/根本原因分类法**，并进行了调整。他们通过**添加框架特定类别（如分布式通信错误）和删除不相关类别来完善这些分类法**。一位在分布式训练和推理框架方面有专业知识的**独立第三研究者通过共识讨论仲裁分歧**，在正式标记开始前确定最终分类法。

对于数据集剩余 60%的正式标记，两位作者分四轮独立标记（每轮为总数据集的 15%），每轮后通过科恩卡帕系数（Cohen’s Kappa）[36]衡量评分者间一致性。

- 第一轮的卡帕系数为 0.5，促使他们与仲裁者进行深入讨论，解决不一致并明确标记标准。
- 第二轮的卡帕系数超过 0.8，最后两轮超过 0.9，仲裁者持续调解所有轮次的分歧，确保所有数据的标记一致性。

### D. 漏洞根本原因识别与修复中的挑战及常见修复策略

我们使用先前研究中广泛采用的三个指标来量化漏洞解决工作量[22], [37], [38]：

::: block-1
1. 漏洞开放持续时间，定义为标记为“bug”的问题从打开到关闭的时间间隔；
2. 评论数量，代表漏洞生命周期中开发者和用户的讨论量；
3. 补丁大小，以修复漏洞修改的代码行数（LOC）衡量。
:::

为确保测量有意义，我们排除了对测试、基准和文档等非生产文件的更改，并从 LOC 计数中移除空行。

借鉴先前研究[22], [39]，**我们分析开放时间至少一个月且收到超过 10 条评论的标记为“bug”的问题，以研究根本原因识别的挑战**。为探索高难度修复，我们检查补丁大小位于数据集前 20%的漏洞，识别解决复杂漏洞的常见困难。此外，我们分析补丁大小不超过 10 LOC 的漏洞修复，识别可能实现自动化的常见低难度修复策略。漏洞根本原因识别和修复挑战的手动标记，以及常见修复策略的分类，遵循与第二节 C 部分描述的症状和根本原因标记相同的流程。

### A. 研究问题 1: 症状分析

**图 2 展示了三个分布式训练和推理框架中按已识别症状划分的漏洞分布**。值得注意的是，:mdnice-bold-italic[崩溃、功能错误和构建失败是这三个框架中最常见的三种症状]。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/07.webp)图 3 显示了三个框架在模型训练或推理阶段出现的漏洞数量。由于一些标记为“bug”的问题缺乏足够信息来确定漏洞发生在训练还是推理阶段，这些漏洞未纳入图 3 的统计。

- 训练阶段出现的与崩溃、功能错误、构建失败和性能不佳相关的漏洞数量是推理阶段的两倍多。
- 此外，挂起漏洞仅出现在模型训练阶段。

#### 崩溃

这种症状指程序能够成功编译和启动，但在执行过程中由于潜在漏洞意外终止。例如：

- 在 DeepSpeed 的 Issue #3543[40]中，由于未考虑张量不匹配，在 LoRA（低秩适应，一种参数高效微调方法）过程中出现错误，导致 RLHF（人类反馈强化学习）异常终止。
- 在 Megatron-LM 的 Issue #437[41]中，分组查询注意力计算中的 view 操作存在漏洞，当启用管道并行时，由于张量形状/步长不兼容导致运行时崩溃。
- 在 Colossal-AI 的 Issue #5187[42]中，自定义分片策略因层分布不一致触发 TypeError，导致崩溃。

#### 功能错误

这种症状指程序正常运行但产生错误输出。例如：

- 在 DeepSpeed 的 Issue #1950[43]中，程序执行成功，但在使用相同输入和固定种子重复运行时，推理结果不一致（非确定性）。
- 在 Colossal-AI 的 Issue #3746[44]中，提示数据加载器未能正确迭代批次，导致程序重复加载相同的提示。

#### 构建失败

这类症状指程序在编译阶段由于编码错误或环境问题无法完成编译过程。例如：

- 在 DeepSpeed 的 Issue #3364[45]中，当时 DeepSpeed 不支持 Apple M2 芯片，导致用户无法在该设备上安装和编译。
- 在 Colossal-AI 的 Issue #3620[46]中，脚本 train_prompts.sh 在单 GPU 上无法执行。

#### 性能不佳

这类症状指程序运行正确且产生预期结果，但执行时间明显长于正常情况，或消耗过多内存。例如：

- 在 Colossal-AI 的 Issue #5937[47]中，程序为每个 epoch 保存检查点，导致磁盘空间浪费。
- 在 DeepSpeed 的 Issue #1635[48]中，优化缺陷导致 Adam 优化器在 AVX512 指令集上的执行时间增加四倍以上，严重影响训练效率。

#### CI/CD 错误

这种症状表明库的发布过程中存在漏洞，阻碍用户及时获取最新版本。例如：

- 在 Colossal-AI 的 Issue #3848[49]中，由于工作流触发器和条件检查不一致，CI/CD 流水线中的 Docker 镜像推送阶段被意外跳过，导致用户无法获取程序的最新 Docker 镜像。

**值得注意的是，CI/CD 错误是 Colossal-AI 独有的，因为 DeepSpeed 将 CI/CD 错误归为非漏洞问题**，使用专门的“CI Failed”标签，且只有 9 个已关闭的问题与 PRs 无直接关联，而 Megatron-LM 目前尚未记录 CI/CD 错误。

#### 挂起

这种症状指程序因特定原因在某个执行阶段停滞，不产生任何输出或提示信息，难以判断程序是否仍在正常运行。例如:

- 在 DeepSpeed 的 Issue #1995[50]中，程序未能正确处理终止信号，导致其成为僵尸进程。
- 在 Colossal-AI 的 Issue #4164[51]中，配置参数干扰了分布式训练节点之间的协调机制，使程序在多节点初始化阶段无限期停滞。

> 发现 1：崩溃、功能错误和构建失败是这三个分布式训练和推理框架中最常见的三种症状，而挂起出现的频率最低。

如图 3 所示，虽然 API 误用、执行顺序错误和分布式张量错误在训练和推理阶段导致的漏洞数量相近，但其他:mdnice-bold-italic[根本原因在训练阶段导致的漏洞数量明显更多]。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/09.webp)

由于这些框架是为分布式训练和推理设计的，具有复杂的资源分配、节点通信和张量并行特性，因此出现了四种独特的根本原因：分配策略错误、分布式通信错误、分布式张量错误和并发错误。由于篇幅限制，我们仅提供这四类根本原因的源代码示例，以更详细地解释这些根本原因。

#### API 误用

这种错误通常是由于开发者在设计或使用过程中未能充分考虑 API 的参数设计、调用方法或底层实现机制。例如：

- 在 DeepSpeed 的 Issue #2244[52]中，由于忽略了 os.makedirs 函数中的权限约束，导致目录不可写。
- 在 Megatron-LM 的 Issue #624[53]中，调用 load 函数时遗漏了关键参数，导致测试套件无法正常执行。

#### 配置错误

这种错误源于库代码、配置文件或命令脚本中固定参数的配置缺陷，导致程序安装和执行过程中出现异常。例如：

- 在 DeepSpeed 的 Issue #11[54]中，多节点安装脚本默认使用共享文件系统，且缺乏自定义主机文件路径的参数，导致在非共享文件系统环境中无法跨节点分发安装文件，造成安装失败。
- 在 Colossal-AI 的 Issue #4027[55]中，代码中将节点间通信桶大小错误地设置为 12T，降低了运行时效率。

#### 实现错误

这种错误源于开发者在函数/算法实现中错误地应用或实现技术方案。例如：

- 在 DeepSpeed 的 Issue #1950[43]中，推理内核实现中位置编码和融合计算的逻辑不一致，导致推理结果非确定性。
- 在 Colossal-AI 的 Issue #3063[56]中，OPTActor 模块初始化时未正确加载预训练权重，导致自定义模型的架构与预训练模型的状态字典不匹配。

#### 前置条件缺失

这种错误是指在执行后续逻辑之前未检查关键前置条件，导致在特定场景下出现异常或系统崩溃。例如：

- 在 DeepSpeed 的 Issue #4095[57]中，开发者在创建张量时未检测输入参数为空的情况，导致程序在处理空张量创建时直接崩溃。
- 在 Colossal-AI 的 Issue #3620[46]中，程序未处理单 GPU 前置条件（即 dist.get_world_size() == 1），导致数据采样器变量未定义，在单节点部署时初始化失败。

#### 分配策略错误

这种错误主要源于参数、优化器状态或内存的资源分配策略实现中的逻辑缺陷。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/10.webp)

例如：

- 在 DeepSpeed 的 Issue #3678[58]中，如图 5 所示，在张量创建的包装函数 wrapped_fn 中，动态获取当前设备（通过 LOCAL_RANK）并注入 device 参数，以确保张量在目标 GPU 上创建（第 229-232 行）。原始代码仅包装了 empty、zeros、ones 和 full 等函数（第 427-431 行），但未处理 arange（算术张量）和 eye（单位矩阵）。当这两个函数在未显式指定设备的情况下被调用时，张量默认在 CPU 上创建，导致设备不匹配。因此，修复后的代码为 arange 和 eye 添加了包装器（第 483-484 行）。

#### 分布式通信错误

这种错误是由于开发者对分布式节点之间的通信处理不当造成的。例如：

- 在 DeepSpeed 的 Issue #1995[50]中，开发者对跨节点的终止信号逻辑处理不当，导致无法正常关闭。
- 在 Colossal-AI 的 Issue #2447[68]中，当工作节点遇到错误时，未能通过通信机制将错误状态传输到主节点，因此 CLI（命令行界面）始终显示工作节点“运行正常”。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/11.webp)

如图 6 所示，修改后的程序通过第 288-293 行的代码检查节点错误：如果任何节点返回“失败”，则将 has_error 设置为 True。如果存在错误，程序返回 1，CLI 将显示非零退出码（第 308-311 行）。

#### API 不兼容

这种不兼容可分为内部 API 不兼容和第三方库 API 不兼容。内部不兼容源于库内部 API 的重命名和方法签名更改未完全同步，导致参数不匹配引发运行时错误。例如：

- 在 DeepSpeed 的 Issue #7014[59]中，类重命名和方法签名更改未完全同步，导致参数不匹配引发运行时错误。第三方不兼容主要源于 PyTorch 版本更新。
- DeepSpeed 的 Issue #5603[60]、Issue #5534[61]、Issue #4853[62]以及 Colossal-AI 的 Issue #4829[63]、Issue #2938[64]，均因未能及时适配 PyTorch 版本变化所致。

#### 条件错误

这种错误源于分支语句中有缺陷或不完整的条件检查，导致程序在特定条件下意外终止。

- 在 DeepSpeed 的 Issue #3751[65]中，权重传输逻辑中的错误条件检查阻碍了操作完成。
- 在 Colossal-AI 的 Issue #3237[66]中，CI/CD 工作流在条件中使用了未定义的 steps.commit.outputs.status，导致条件始终失败，工作流从未触发。

#### 环境不兼容

这种错误是由于开发者忽略了库与硬件架构之间的兼容性。例如：

- 在 DeepSpeed 的 Issue #3364[45]中，开发者未提供对 M2 arm64 芯片的库支持，导致用户无法在配备 M2 arm64 芯片的设备上安装该库，造成程序构建失败。
- 在 Colossal-AI 的 Issue #6058[67]中，开发者在代码中使用了特定于 Linux 系统的模块，导致程序在 Windows 环境中因无法导入这些模块而构建失败。

#### 执行顺序错误

这种错误源于代码块的顺序不当。例如：

- 在 DeepSpeed 的 Issue #6569[69]中，学习率调度器的更新操作（lr_scheduler.step()）在优化器更新（optimizer.step()）之后执行，导致优化器仍使用默认学习率（如 1e-3）。

#### 分布式张量错误

这种错误源于对分布式节点间张量的处理不当，导致计算失败或异常。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/12.webp)

在 Megatron-LM 的 Issue #437[41]中，如图 7 所示，当用户启用 pipeline-model-parallel-size=2（2 个设备组的管道并行）时，张量的内存布局在跨设备传输后可能变得不连续。原始代码的 view()操作（第 679 行）假设内存连续，导致跨设备张量处理失败。修改后的代码使用 reshape()函数（第 682 行），该函数能够处理非连续内存。

#### 并发错误

这种错误源于开发者在并发执行场景中未能考虑相关问题。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/13.webp)

例如，在 Colossal-AI 的 Issue #4402[70]中（图 8），多个进程并行执行梯度计算、通信和参数更新。在原始代码中，一旦某个进程完成梯度通信，就调用 reset 来清除桶中的所有参数和梯度（第 113 行）。如果其他进程仍在使用这些数据，会导致访问无效内存或空列表，造成崩溃或错误结果。修改后的代码引入了 cur_offset 机制（第 124-128 行）：仅删除已在通信中使用的参数和梯度，保留未处理的部分（第 130 行）。

#### 异常处理错误

这种错误源于开发者对程序异常的处理存在缺陷，主要表现为错误消息不准确或缺失。

- 在 DeepSpeed 的 Issue #3669[71]中，抛出异常时错误消息缺少具体行号，增加了问题诊断难度。
- 在 Colossal-AI 的 Issue #6019[72]中，模型状态字典加载过程中缺失键的计算逻辑存在偏差，导致错误消息与实际键匹配条件不一致，影响问题定位效率。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/09.webp)

如图 9 所示，几乎所有根本原因都可能触发四种最主要的症状——崩溃、功能错误、构建失败和性能不佳。这表明，**当这些症状出现时，定位根本原因尤为困难，因为潜在原因范围广泛**。此外，CI/CD 失败主要与 API 误用、配置错误、API 不兼容和条件错误相关，而挂起主要源于环境不兼容、分布式通信错误和并发错误。

> 发现 2：API 误用、实现错误、配置错误和前置条件缺失是四个最主要的根本原因。:mdnice-bold-italic[这些框架的分布式特性导致了四类独特的根本原因：分配策略错误、分布式通信错误、分布式张量错误和并发错误]。几乎所有根本原因都可能导致四种最主要的症状——崩溃、功能错误、构建失败和性能不佳。

### C. 研究问题 3: 根本原因识别与漏洞修复中的挑战

图 10 展示了漏洞开放持续时间、评论数量和补丁大小的小提琴图。

![文章插图](/articles/2025-07-19-308-bug-deepspeed-megatron-lm-55a459a9/images/14.webp)

Colossal-AI 的漏洞开放持续时间比 DeepSpeed 和 Megatron-LM 短，这可能是因为开发者在问题报告后及时处理，这与每个问题的评论数量较少相关。然而，:mdnice-bold-italic[三个框架的补丁大小相近，中位数在 8 到 14 行代码之间]。

> 借鉴先前研究[22], [39]，**我们分析了开放时间超过一个月且收到 10 条以上评论的标记为“bug”的问题，约占所有案例的 6%。** 这些:mdnice-bold-italic[长期开放的问题反映了大量的调试工作]。通过分析这些案例，我们确定了框架中:mdnice-bold-italic[漏洞根本原因识别的三个主要挑战]。

1. **漏洞症状与原因脱节**：当:mdnice-bold-italic[症状与根本原因无直接关联时，定位漏洞的难度通常会显著增加]。例如，在 DeepSpeed 的 Issue #2911[73]中，用户报告说，尽管 bf16/fp32 模式的特征已关闭，但系统日志仍显示损失缩放器警告。起初，问题提出者怀疑警告模块异常。然而，社区开发者的联合分析揭示了核心问题：在分布式通信中，fp16 数据以 bf16 状态传输，导致梯度值无限大，从而触发警告。
2. **漏洞复现的高资源开销**：在使用:mdnice-bold-italic[分布式训练和推理框架进行 LLM 训练时，复现漏洞通常需要大量计算资源]。例如，在 DeepSpeed 的 Issue #3481[74]中，仅当在 8 个 A100 GPU（80GB）和 1024GB 内存上训练大参数模型、初始化优化器状态并尝试将梯度分区固定到内存（pin_memory）时，才会触发错误。随后，另一位用户尝试使用有限的硬件资源复现该漏洞，但**发现模型在训练期间停滞了一小时，未能复现错误**。在讨论中，DeepSpeed 的一位开发者承认，**仅针对大参数模型的内存固定操作对内存需求极高**。换句话说，设备内存不足会阻碍这些操作的成功完成，从而**阻碍漏洞复现。**
3. **分布式训练和推理框架中的底层漏洞**：这种挑战指的是源于分布式训练和推理框架基本架构设计的底层漏洞。例如，在 DeepSpeed 的 Issue #2449[75]中，当推理期间未配置优化器时，DeepSpeed Stage 3 无法加载检查点。从传统推理工作流的角度来看，优化器不是必要的配置项，这促使开发者惊讶地表示：:mdnice-bold-italic[“这非常违反直觉”]。通过随后深入且持续的讨论，开发者逐渐确定该漏洞的**根本原因是库的架构设计缺陷**。由于推理引擎与优化器之间存在:mdnice-bold-italic[不合理的强耦合]，即使在不需要优化操作的推理场景中，仍必须配置优化器。这种架构不合理性显著增加了根本原因识别的难度。

> 为理解:mdnice-bold-italic[分布式训练和推理框架中漏洞修复] 需要大量工作的原因，我们借鉴先前研究[22], [39]，**手动审查了补丁大小位于前 20%的 PRs**，每个补丁超过 50 行代码。我们:mdnice-bold-italic[确定了漏洞修复中的三个关键挑战]。

1. **框架底层漏洞的修复**：修改分布式训练和推理框架中的底层操作及其相关功能存在显著挑战。例如，在 Colossal-AI 的 Issue #3471[76]中，用户报告 ColoTensor 缺乏原地操作支持。作为 Colossal-AI 中用于分布式训练内存优化的张量类型，ColoTensor 是框架中的基本数据类型。为支持原地操作，开发者修改了其底层实现，重构了所有使用 ColoTensor 的库组件。**这项工作耗时近五个月，涉及 37 个生产代码文件的修改，编辑了 1775 行代码**。
2. **分布式训练和推理中算法实现逻辑的修复**：修复库中的功能漏洞或算法逻辑错误通常需要协调修改相关模块和测试用例，这显著增加了开发复杂性，并需要大量时间进行逻辑重组和任务协调。例如，在 DeepSpeed 的 Issue #1950[43]中，用户报告分布式注意力机制中位置编码和融合模式处理不一致，导致推理结果不可复现。开发者迅速修补了 Transformer 模块的注意力实现（如位置编码、矩阵操作、注意力流），全面改造了 C++逻辑和 Python 接口。经过约两周的工作和 1155 行代码的修改，问题得以解决。
3. **跨多个组件的漏洞修复**：修复:mdnice-bold-italic[跨多个模块的漏洞面临显著挑战]。开发者必须确保功能完整性，同时防止附带影响，这:mdnice-bold-italic[需要深厚的模块知识和大量协作努力]。在 Colossal-AI 的 Issue #5187[42]中，自定义分片策略导致管道层分布不一致。解决此问题需要协调模型分片、混合并行、管道引擎和分片策略模块。**五名开发者花费了约三个半月的时间，修改了 14 个生产代码文件才完成修复**。

> 发现 3：分布式训练和推理框架中根本原因识别和漏洞修复的挑战主要源于漏洞症状与原因脱节、复现的高资源开销、框架底层漏洞及其修复、算法实现逻辑修复以及跨组件漏洞修复。

### D. 研究问题 4：常见修复策略

我们发现 **48%的漏洞修复仅涉及不超过 10 行代码，这表明简单修改即可解决问题**。通过手动检查这些补丁，我们确定了几种可能实现自动化的小代码量修复策略。

#### 条件逻辑优化

这种策略通过优化条件逻辑，增强程序处理潜在场景的能力。例如：

- 在 DeepSpeed 的 Issue #3777[77]中，开发者添加了对模型参数 requires_grad 属性的检查，以避免不必要的梯度内存分配。

#### 参数处理增强

这种策略为程序引入额外参数或增强参数处理，为开发者提供更全面的配置选项，以灵活适应实际需求并有效解决问题。例如：

- 在 Colossal-AI 的 Issue #4903[78]中，开发者通过向 attention_forward 函数添加**kwargs 参数，解决了库更新冲突。这使得函数在保留原始参数结构的同时，能够动态接受未声明的关键字参数，从而增强了兼容性。

#### API 替换

这种策略通过用更合适的替代 API 替换所使用的 API（在保持功能的前提下），解决因特定上下文 API 限制导致的问题。例如：

- 在 Megatron-LM 的 Issue #437[41]中，开发者将张量操作中的 view API 替换为 reshape，后者是一个更健壮的 API，能够处理分组查询注意力操作中生成的非连续张量，从而确保并行计算中张量的正确性。

#### 配置调整

这种策略通过调整程序的配置参数，纠正因配置偏差导致的功能异常。例如：

- 在 Colossal-AI 的 Issue #4027[55]中，代码默认将分布式节点之间的通信桶大小配置为 12T，这显著影响了运行时效率。开发者随后将其调整为 12MB，并基于运行时状态进行动态优化。

#### 版本兼容性处理

这种策略通过纳入对第三方库版本或硬件配置的检查，主动缓解版本差异导致的问题。

- 一个显著的例子是 Colossal-AI 的 Issue #4829[63]，开发者通过实现条件版本检查解决了 PyTorch 版本不兼容问题。具体来说，修复后的代码根据检测到的运行时环境，动态导入兼容的调度器基类：PyTorch 2.0 以下版本使用_LRScheduler，2.0 及以上版本使用 LRScheduler。

> 发现 4：近一半（48%）的漏洞修复涉及最少的代码更改（≤10 行代码），并且可以通过五种简单策略解决：条件逻辑优化、参数处理增强、API 替换、配置调整和版本兼容性处理。

## 四、结果讨论和进一步分析

### A. 308 个 bug 带来的启示

我们为分布式训练和推理生态系统中的三个主要利益相关者提供一些实用启示：

#### A.1 对框架开发者的启示

1. 很大一部分漏洞源于 API 误用、实现错误、配置错误和前置条件缺失。为减少此类问题，:mdnice-bold-italic[开发者应实施严格的输入验证，并在 API 边界加入防御性检查，以尽早发现错误使用。]
2. 许多漏洞[60]-[64]是由与特定版本的 PyTorch 或 CUDA 不兼容引发的。:mdnice-bold-italic[在 CI/CD 流水线中维护版本感知的测试矩阵，并明确记录兼容性要求]，有助于避免这些问题。
3. 从调试角度来看，复现某些漏洞通常**需要访问大规模 GPU 集群**，这为及时诊断和解决问题设置了巨大障碍。为缓解这一问题，我们建:mdnice-bold-italic[议支持模拟模式或轻量级执行路径] （例如，在单台机器上模拟多节点设置），以促进本地复现和更快调试。
4. 可观察:mdnice-bold-italic[症状与其根本原因的脱节]，以及:mdnice-bold-italic[底层或跨组件漏洞]，使得漏洞定位特别具有挑战性。**提供结构化、详细且一致的运行时日志** （包括节点标识符、张量形状和通信状态），可以显著提高可诊断性，并减轻开发者的调试负担。

#### A.2 对框架用户的启示

通过分析 GitHub 仓库的依赖文件（如 requirements.txt），我们发现分布式训练和推理框架在开源生态系统中被广泛采用。例如，仅 DeepSpeed 就被 375 个拥有超过 100 个 GitHub 星标的项目使用，其中包括 147 个星标超过 1000 的项目和 22 个星标超过 10000 的项目。虽然 Colossal-AI 和 Megatron-LM 的采用率相对较低，但它们仍被 15 个和 10 个受欢迎的项目（星标超过 100）使用。重要的是，这些项目中的大多数专注于 LLM 开发。这些统计数据凸显了:mdnice-bold-italic[分布式训练和推理框架中的漏洞可能对下游应用产生的关键影响]。然而，由于这些框架的模块化和分层架构****，其复杂且不透明的调用网络常常**阻碍用户识别哪些 API 或组件受到已知漏洞的影响。**

我们的研究进一步表明，**有些漏洞仅在特定运行时条件下才会显现**。例如，DeepSpeed 的 Issue #3481[74]仅在训练大参数模型时触发，这使得:mdnice-bold-italic[开发者难以通过静态检查预测故障]。这种**依赖上下文的行为限制了传统代码审查和静态分析技术在识别所有漏洞路径方面的有效性**。因此，我们**建议框架用户** （特别是那些构建大规模 LLM 系统的用户）采用**结合静态代码结构和动态执行轨迹的高级分析工具**。:mdnice-bold-italic[构建整合静态调用关系和运行时行为的混合调用图]，可以帮助用户将其应用代码映射到可能存在漏洞的框架组件。此外，**将运行时上下文** （如输入数据大小、模型参数数量）**纳入这些分析**，可以提高识别漏洞可能发生的时间和位置的精度。此类策略可以帮助用户在部署前主动评估风险并缓解故障。

#### A.3 对框架研究者的启示

虽然基于 LLM 的方法在程序修复任务中表现出强大性能[79]（例如 SWE-bench 基准测试[80]），但它们在分布式训练和推理框架中的适用性仍未得到充分探索。

1. **近一半的框架漏洞通过最少的代码更改得到解决**，这表明:mdnice-bold-italic[将修复模板或模式与 LLM 相结合的修复方法具有巨大潜力]。在这种模式中，从历史补丁中挖掘的模板提供结构指导，而 LLM 生成上下文感知的代码来完成修复。
2. 这些框:mdnice-bold-italic[架中独特的故障模式] （如分配策略错误、分布式通信错误和分布式张量错误）**需要超越传统修复技术的专门诊断和推理能力**。将 LLM 与检索增强生成（RAG，一种结合外部知识检索和生成模型的技术）相结合可能有助于弥补这一差距。例如，当遇到分配策略错误时，RAG 增强的方法可以检索涉及内存分片的相关设计文档或先前报告的问题，从而提供更精确的诊断和修复建议。
3. 我们的研究进一步强调，**复杂漏洞** （特别是那些涉及非明显的症状-原因关系、有缺陷的算法逻辑、跨组件交互或底层数据结构如 ColoTensor[76]的漏洞）**仍然难以诊断和解决**。解决此类漏洞:mdnice-bold-italic[需要深入的架构理解和多步推理]。面向推理的 LLM 的最新进展（如 GPT-o1[18]、DeepSeek-R1[19]）为模拟经验丰富的开发者的深思熟虑过程提供了有前景的途径。我们展望未来的研究将探索这些模型与程序分析工具的集成，以创建能够解决分布式框架中语义复杂漏洞的混合方法。

### B. 有效性威胁

> 我们的发现对所有分布式训练和推理框架的可推广性可能受到两个因素的限制。

- 首先，我们仅关注开源框架，而工业级 LLM 训练通常依赖专有、闭源框架（例如深度求索的内部分布式训练和推理系统[81]）。这些闭源框架的不可访问性引入了偏差，因为它们的漏洞特征（如根本原因、修复策略）可能与开源框架不同。
- 其次，分析的漏洞数量与最近对传统机器学习库（如 Yang 等人[22]分析了 7 个流行数据科学库的 202 个性能漏洞）和深度学习库（Chen 等人[21]每个深度学习库分析 250 个漏洞）的研究相当或更少，这主要是因为 LLM 分布式训练和推理框架尚处于萌芽阶段，漏洞积累和文档记录进展缓慢。

**为减轻这些威胁，我们选择了被广泛采用且拥有活跃开发者社区的开源框架，确保我们的样本能够反映最具代表性的开源生态系统**。未来的工作将扩大数据收集范围，纳入新兴的流行分布式训练和推理框架，并延长时间跨度，以验证我们发现的可推广性并研究漏洞的演化模式。

**另一个有效性威胁源于手动标注过程，这可能引入主观性风险**。为解决这一问题，两位作者使用与先前实证研究一致的开放编码方案独立标注数据。任何标注差异都通过与经验丰富的独立第三研究者的迭代讨论来解决，确保评分者间一致性和解释的一致性。此外，由于我们无法获取漏洞定位和修复难度的直接测量值（如开发者调试所花费的时间），我们采用了与先前研究[22], [37], [38]一致的替代指标。具体而言，漏洞开放持续时间和问题评论数量作为根本原因识别复杂性的代理指标，而补丁大小则量化修复难度。

## 五、相关工作

### 传统并行/分布式训练漏洞

> 关于并行/分布式系统或程序中漏洞的实证研究主要集中在传统共享内存架构（多个处理器通过共享内存进行通信的架构）和通用分布式系统上[82]-[84]。

然而，用于大型语言模型（LLMs）的分布式训练和推理框架在硬件架构和程序特性上与这些范式存在显著差异。与共享内存并行系统中处理器通过直接内存访问进行通信不同[85]，LLM 的分布式训练和推理依赖于跨 GPU 的设备间通信协议，这些 GPU 拥有独立的内存空间。**这些独特特性使得 LLM 分布式训练和推理中的漏洞与传统并行/分布式训练系统或程序中的漏洞存在本质区别**。

因此，我们不详细阐述传统范式下现有的漏洞分析研究。**迄今为止，仅有 Liu 等人[86]分析了 Stack Overflow 和 GitHub 上报告的 1131 个分布式训练相关的实际开发者问题，重点关注使用 TensorFlow、PyTorch、Keras 和 Horovod 开发深度学习程序进行分布式训练时遇到的挑战**。相比之下，:mdnice-bold-italic[我们的研究明确针对分布式训练和推理框架自身固有的漏洞]。此外，我们分析的框架是更常用于 LLM 分布式训练和推理的框架。

### 机器学习/深度学习漏洞

> 现有的关于机器学习和深度学习漏洞的研究大致将漏洞分为两类：程序漏洞和框架漏洞。

关于程序漏洞的研究[87]-[93]主要关注因错误使用机器学习/深度学习框架 API 而产生的问题。这些漏洞源于用户错误，而非框架底层实现中的漏洞。例如，Islam 等人[88]研究了使用 Caffe、Keras、TensorFlow、Theano 和 Torch 实现的深度学习程序中的漏洞，分析了漏洞类型、根本原因、影响以及深度学习 pipeline（流程）中最易出现漏洞的阶段。

相比之下，**近期的一些研究[21]、[22]、[29]-[32]、[94]-[97]考察了机器学习/深度学习框架自身的漏洞，探索了主流框架的漏洞症状、根本原因和修复模式**。例如，Chen 等人[21]进行了迄今为止最广泛的分析，研究了 TensorFlow、PyTorch、MXNet 和 DL4J 中的 1000 个漏洞，考察了这些漏洞的根本原因和症状，以及深度学习框架中哪些层级更容易出现漏洞。

我们的研究与 Chen 等人[21]的发现存在一些重叠：错误实现、配置错误和 API 误用在深度学习框架和分布式训练推理框架中都是常见的根本原因。然而，**我们独特地识别出了分布式特有的漏洞根源，如分配策略错误和分布式通信错误**。此外，虽然 Chen 等人[21]报告崩溃和挂起是主要症状，但我们发现挂起在分布式训练和推理框架中较为罕见。**重要的是，Chen 等人[21]没有分析根本原因识别和漏洞修复的挑战，也没有讨论常见的低难度修复策略——而这些都是我们研究的核心贡献。**

## 六、结论

> 在本文中，我们对三个广泛使用的分布式训练和推理框架（DeepSpeed、Megatron-LM 和 Colossal-AI）中的 308 个已修复漏洞进行了首次大规模实证研究。

通过系统分析这些漏洞的症状、根本原因、诊断与修复挑战以及常见的低难度修复策略，我们**揭示了这些框架中漏洞的关键特征**。

::: block-1
我们的研究结果表明，:mdnice-bold-italic[崩溃、功能错误和构建失败是最常见的症状]，而 **API 误用、实现错误、配置错误和前置条件缺失是主要的根本原因**。

此外，这些框架的**分布式特性引入了独特的漏洞根源**，如分配策略错误和分布式通信错误。

我们还发现，:mdnice-bold-italic[症状与根本原因的脱节、漏洞复现的高资源开销以及底层或跨组件交互，使得复杂漏洞的诊断和修复极具挑战性]。值得注意的是，**48%的漏洞通过不超过 10 行代码的小补丁修复**，遵循条件逻辑优化、参数处理增强等简单策略，这表明存在显著的自动化潜力。
:::

基于这些发现，我们为框架开发者、用户和研究人员提供了实用启示，以提高分布式训练和推理框架及其下游大型语言模型（LLMs）项目的可靠性。我们还**强调了利用基于 LLM 的工具** （结合检索增强生成（RAG，一种结合外部知识检索和生成模型的技术）和面向推理的模型）**实现自动化调试和修复的机会。**

我们:mdnice-bold-italic[公开的带注释数据集[20]为未来研究奠定了基础]，包括探索更复杂的跨组件漏洞修复、开发针对分布式场景的专用调试工具，以及评估自动化修复技术在这些框架中的有效性。通过持续关注这些方向，我们有望显著提高分布式训练和推理系统的可靠性，从而加速大型语言模型的开发和部署。
