## 一、为什么现有基准无法反映真实生产水平？

> 过去两年，LLM 生成 GPU 内核的能力迭代速度远超预期。从最早的能编译通过，到后来的正确性达标，再到性能超过基础 PyTorch 实现，**一连串亮眼的分数让不少人觉得 LLM 写内核已经快要追上人类专家。**

但如果把评测场景从实验室精心设计的题目，**切换到真实线上推理集群的实际负载，这些结论还站得住脚吗？答案是否定的。**

### 1.1 现有基准的三重偏差

> 现有基准之所以测不准生产能力，核心是在**三个决定生产价值的维度上全面偏离真实场景：**

| 问题类型 | 具体描述 |
| --- | --- |
| 算子形状分布偏差 | **生产集群的负载是高度长尾分布的**，论文统计显示，:mdnice-bold-italic[排名前五的算子占据了约64%的GPU运行时间，而合成基准通常采用均匀的形状网格，完全没有体现这种分布特征]。 |
| 重要性权重偏差 | 绝大多数基准给每个任务相同的权重，一个冷门的逐元素算子和一个决定延迟的融合注意力算子得分占比一样。但在生产中，后者的优化价值是前者的几十上百倍。 |
| 性能标尺偏差 | 很多基准用未优化的PyTorch实现作为基线，超过基线就算“优秀”。**但生产环境的合格线是硬件理论上限，也就是屋顶线，达不到这个水平的内核都还有优化空间**。用软件基线做标尺，很容易出现“分数很高但实际没用”的情况。 |

### 1.2 被忽视的正确性幻觉

> 比标尺偏差更隐蔽的问题是“正确性幻觉”。

大多数基准的评判标准只有“对不对”，只要输出结果和参考实现一致就算通过。但 GPU 内核生成的目标是写出指定 DSL 的高性能内核，而不是得到正确的结果。**模型完全可以绕开目标 DSL，直接调用 PyTorch 自带的算子或者预编译的厂商库来得到正确结果，本质上是“用框架调包”而不是“写内核”。**

这种情况下，正确率越高，误导性越强。模型看起来通关率很高，但实际上根本没写出多少目标代码，完全达不到生产部署的要求。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/04.webp)

::: image-caption
图 2：各候选模型的正确性与目标 DSL 占比对比。橙色柱为完全正确的算子数量，蓝色柱为设备时间中 FlyDSL 占比超过 50% 的算子数量；两者的差距即为由非 DSL 回退带来的正确性虚高。该图直观揭示了 “正确性幻觉” 的存在：多数模型的正确算子数量远多于 FlyDSL 主导的算子数量，说明大量正确结果并非通过编写目标 DSL 内核实现，而是通过调用 PyTorch 接口、预置算子库等回退路径达成。其中 Kimi、Qwen、DeepSeek 等模型的差距尤为明显，接近一半的正确算子依赖非 DSL 路径；而 Claude Opus 4.7 是唯一 FlyDSL 算子数多于正确算子数的模型，体现了更强的原生内核编写能力。这种现象说明，仅用正确率评估内核生成能力会严重高估模型水平，必须结合目标 DSL 占比才能真实反映内核编写能力。
:::

::: block-1
总之，:mdnice-highlight[现有基准在问题来源、评分逻辑、合格标准三个层面都与真实生产场景脱节，还存在隐蔽的正确性幻觉]，最终测出的分数既不能反映模型的真实代码能力，也无法预测生产部署后的实际收益。
:::

## 二、Atrex-Bench：一套面向生产的基准契约

> 要解决现有基准的问题，不能只在原有题目库里加几个算子，而要从根上重构基准的设计逻辑。**Atrex-Bench 的核心思路，就是把“生产真实”贯穿从采样、构建到评分、验证的全流程，打造一套和生产环境对齐的“基准契约”**。:mdnice-bold-italic[这套契约有三个核心原则：负载来自真实线上轨迹，评分按生产重要性加权，标尺用硬件理论上限。]

### 2.1 从生产轨迹到基准单元

Atrex-Bench 的所有问题都是直接从生产集群的运行轨迹中采样而来。

> 数据来源覆盖了超过 10000 块加速卡的推理集群，:mdnice-bold-italic[横跨 vLLM、SGLang、AITER、RTP-LLM 四大推理框架，聚合了 1303 份生产性能画像和约 20 个部署模型的运行数据。最终筛选出 30 个核心算子、440 个高频形状，构成了基准的主体。]

这个采样过程有两个关键设计：

- 跨框架统一算子语义：把不同框架里功能等价的内核映射到同一个算子家族，比如不同框架的注意力算子都归为统一的基准问题，保证基准的通用性。
- 形状分桶保留真实分布：对动态 token 维度进行分桶，从单 token 解码到长上下文预填充都有覆盖，同时保留架构固定维度的精确值，既减少冗余又贴近真实。

### 2.2 五文件契约：筑起生成与评估的隔离墙

> 为了防止模型“作弊”，也就是通过记忆已知内核、利用评分公式取巧，Atrex-Bench 设计了严格的生成-评估边界，每个算子都由五个文件构成，分成可见和隐藏两类。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/05.webp)

::: image-caption
表 2：每个算子的问题规范文件；“Visible”标记生成期间候选智能体可访问的文件。五份文件中，reference.py、input.py、shapes.json 对生成模型可见，用于定义算子语义、输入规则和形状配置；metadata.json 与 roofline.json 隐藏，分别存储上游来源信息和评分基准数据。这种设计从根源上杜绝了模型通过检索上游内核名称、直接拟合评分公式等方式取巧，确保评测的是真实的代码生成能力，而非记忆或检索能力。评估阶段会在全新环境中导入生成代码，用完整隐藏数据打分，完全解耦生成过程与评估过程。
:::

### 2.3 屋顶线模型：用硬件上限做统一标尺

> Atrex-Bench 采用了 GPU 性能工程里经典的屋顶线（Roofline）模型，给每个问题设定一个硬件理论下限时间作为评分标尺。 屋顶线模型的核心公式是：

$$
T_{roofline, j}=max \left(\frac{F_{j}}{P_{\tau_{j}}}, \frac{M_{j}}{\beta}\right)
$$

其中 $F_j$ 是第 j 个算子的语义计算量（FLOPs），$P_{\tau_j}$ 是对应数据类型的硬件算力峰值；$M_j$ 是算子的内存访问量，$\beta$ 是硬件的内存带宽峰值。

**一个算子的理论最快速度由两个瓶颈决定：如果是计算密集型，速度上限就是算力峰值；如果是内存密集型，速度上限就是带宽峰值**。:mdnice-bold-italic[两者取更慢的那个，就是这个算子的“硬件天花板”。]

::: block-1
用屋顶线做标尺的好处是公平。不管是什么模型写的内核，都用同一个硬件标准来衡量，得分代表的是“发挥了硬件多少潜力”。
:::

### 2.4 重要性加权：让占时间的算子说了算

> 基准的总分是按生产重要性加权后的汇总分。每个算子的权重 $w_i$ 来自它在生产中的 GPU 时间占比，综合考虑了不同应用的卡时占比、prefill/decode 不同阶段的运行时间。最终所有权重归一化，总和为 1。

这样设计的结果是：:mdnice-bold-italic[占生产时间越长的算子，对总分的影响越大。把最重要的算子做好，总分才会高；反过来，就算把所有冷门算子都做对，只要核心算子不行，总分依然上不去。]

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/06.webp)

::: image-caption
表 3：按重要性权重 $w_i$ 排序的 Top-10 Atrex-Bench 算子。“Score”为归一化的应用卡时加权、分阶段感知 GPU 时间占比；“Shapes”为随附的（初始化/输入）配置数量；“Dtype”为算子的主精度。可以看出，权重分布呈现极端的长尾特征，仅前 5 个算子就占据了约 64%的总权重，仅 unified_attention 一项就占比超过三分之一。这意味着生产环境中绝大多数 GPU 时间都消耗在少数核心算子上，基准的加权机制精准反映了这一特征。同时形状数量与权重并不正相关，比如 rms_norm 有 56 个形状但权重仅 2.5%，进一步验证了“按算子重要性而非形状数量加权”的必要性。
:::

比如排名第一的 unified_attention 算子，权重高达 36.1%，相当于三分之一的总分都由它决定。这也和生产实际一致：注意力算子的性能直接决定了整个推理服务的延迟和吞吐。

## 三、六大前沿模型实测：最好的也只摸到 10.7%的天花板

> 用这套更严格的基准去测当前最顶尖的代码模型，结果会是怎样？:mdnice-bold-italic[研究团队测试了六款业界公认的前沿模型：Claude Opus 4.7、GPT-5.5、Qwen3.7-Max、Kimi-K2.6、GLM-5.1、DeepSeek-V4-Pro。最终的结果可以说给整个行业浇了一盆冷水：即便是表现最好的模型，也只达到了硬件理论上限的 10.7%，距离生产可用还有相当长的距离。]

### 3.1 整体表现排名

> 测试从四个维度展开：编译率、正确率、FlyDSL 采纳率、加权屋顶线得分 $S_{agg}$。其中 FlyDSL 是本次测试的目标 DSL，它的采纳率代表了代码中真正由目标 DSL 执行的时间占比。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/07.webp)

::: image-caption
图 4：输出 token 量与生产加权得分的散点图，其中，每个点对应一个模型，标签标注完全正确的算子数量。该图进一步验证了生成量与质量无关的结论，散点分布完全没有呈现正相关趋势。token 生成量最少的 GPT-5.5 反而位居得分榜首，生成量最大的 DeepSeek-V4-Pro 得分接近底部。这说明内核生成是一个 “知识密集型” 而非 “试错密集型” 任务，单纯增加生成篇幅无法提升性能，核心在于模型掌握的 GPU 优化知识的深度与准确性。同时，正确算子数量也与总分不完全对应，因为正确算子可能集中在低权重的简单算子上，进一步凸显了重要性加权评分的价值 —— 只有在高权重的核心算子上取得突破，才能真正提升生产级得分。
:::

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/08.webp)

::: image-caption
表 4：XPU-A 平台主测结果；所有指标均在 30 个算子上做算子均衡。$S_{agg}$ 为重要性加权屋顶线达成率；“vs”列为各算子中位数相对 torch.compile（t.c.）与生产内核的倍率。数据呈现出清晰的梯队分化。头部两款模型编译率接近满分，正确率也都在 90%以上，但生产加权的屋顶线得分拉开了近一倍差距，核心原因是 GPT-5.5 在高权重计算密集型算子上表现更优。中间梯队正确率看似与头部差距不大，但 FlyDSL 采纳率几乎腰斩，暴露了严重的正确性幻觉。尾部模型则在编译阶段就出现大量失败，基础代码能力尚有明显短板。最终没有任何一款原生模型能超过部署的生产内核，最好的 Claude 也仅达到生产基线的 0.99 倍。
:::

### 3.2 正确性幻觉：中间梯队的“作弊式”通关

> 正确率和 FlyDSL 采纳率的差值，就是“正确性幻觉”的量化体现。**对比每个模型“完全正确的算子数”和“FlyDSL 主导的算子数”，差异非常明显：**

- Claude Opus 4.7:24 个完全正确，26 个 FlyDSL 主导。后者比前者还多，说明 Claude 是真的在努力写目标 DSL 代码，甚至有些算子代码写对了但数值还没调准，是典型的“代码优先”风格。
- GPT-5.5:23 个完全正确，26 个 FlyDSL 主导，同样是代码多于正确，和 Claude 属于同一梯队。
- Qwen3.7-Max：23 个完全正确，11 个 FlyDSL 主导。差值高达 12 个，也就是超过一半的正确算子靠的是非 DSL 路径。
- Kimi-K2.6:23 个完全正确，10 个 FlyDSL 主导，差值 13 个，情况和 Qwen 类似。
- DeepSeek-V4-Pro：18 个完全正确，6 个 FlyDSL 主导，差值 12 个。

::: block-1
换句话说，:mdnice-bold-italic[中间梯队的模型普遍采用了“投机取巧”的策略：遇到不会写的 DSL 内核，就直接调用 PyTorch 或者预编译库来保证结果正确，看起来正确率很高，但实际上根本没完成“写内核”的任务。]
:::

这也解释了为什么光看正确率会高估模型能力：**正确率测的是“能不能得到正确结果”，而内核生成要的是“能不能写出正确的高性能内核”，两者根本不是一个目标。**

### 3.3 算子难度：最难的恰恰是最重要的

> 把每个算子的平均通过率算出来，就能看到清晰的难度梯度。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/09.webp)

::: image-caption
表 5：算子难度：六款模型的平均形状通过率（仅列出最难的算子；最简单的九个全部通过）。难度最高的算子集中在两类：一类是 FP8 低精度量化融合算子，另一类是计算密集的矩阵乘法与注意力算子。而恰恰是这些最难的算子，在生产中的重要性权重最高，比如 unified_attention、fused_moe、block_scaled_mm 都属于高权重高难度算子。反过来，最简单的 9 个算子所有模型都能通过，但大多是轻量的归一化、逐元素运算，权重占比很低。这种“重要的都难，简单的都不重要”的分布，也是为什么平均分看起来还行，但加权总分特别低的核心原因。
:::

### 3.4 内存绑定 vs 计算绑定：两类算子的表现鸿沟

> 按算术强度 $AI=\frac{FLOPs}{字节访问量}$把算子分成内存绑定和计算绑定两类，模型的表现差异会更加明显。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/10.webp)

::: image-caption
图 3：各模型在对比内存密集型与计算密集型算子的表现下的 Roofline 得分，得分采用单算子中位数得分公式计算。该图清晰展示了当前 LLM 内核生成能力的结构性短板：所有模型在内存密集型算子上的得分都远高于计算密集型算子。Claude Opus 4.7 在内存密集型算子上得分达 0.207，但计算密集型仅 0.009，相差超过 20 倍；GPT-5.5 是唯一在计算密集型算子上取得有意义得分的模型，但也仅 0.074。这种差异源于内存密集型算子优化逻辑简单，只需实现访存合并即可接近带宽上限；而计算密集型算子需要复杂的分块、流水线、指令调度优化，对硬件架构知识要求极高。这说明当前模型的硬件优化能力还停留在访存优化层面，深度计算调度能力严重不足。
:::

- 内存绑定算子：算术强度低，瓶颈在内存带宽。这类算子模型普遍表现更好，Claude 的中位数能达到 20.7%的屋顶线。
- 计算绑定算子：算术强度高，瓶颈在算力。这类算子所有模型表现都极差，Claude 的中位数只有 0.9%，GPT-5.5 也只有 7.4%。

换句话说，**现在的 LLM 写内存密集型算子还凑合，能发挥两成硬件潜力；但一遇到计算密集的核心算子，比如大矩阵乘法、长序列注意力，水平就直线下降，连十分之一都发挥不到**。:mdnice-bold-italic[而生产中权重最高的算子，恰恰都是计算绑定的。] 这就导致加权总分被核心算子严重拉低，出现了“简单题都对，大题全崩”的局面。

::: block-1
回顾一下整个评测结果，:mdnice-highlight[六大前沿模型的生产级内核生成能力还处于非常早期的阶段，最好水平仅为 10.7%的硬件上限，同时存在严重的正确性幻觉]。模型的能力短板集中在计算密集型算子的调度优化上，这也是未来提升的核心方向。
:::

## 四、AKA 优化智能体：把回退代码变成生产级内核

> 既然原生模型的能力还差得远，有没有办法通过工具链来补齐短板？**研究团队给出的答案是 Atrex-Kernel-Agent，简称 AKA，一个 profile 驱动的内核优化智能体。**

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/11.webp)

::: image-caption
图 5：AKA 架构与外层工作流，AKA 的七阶段工作流构建了系统化的内核优化框架。其核心设计逻辑是 “硬件接地、证据驱动、可追溯”：硬件 Roofline 阶段先明确性能上限与瓶颈类型，避免盲目优化；基线实现阶段先保证功能正确，再进行性能迭代；优化循环基于性能分析数据而非直觉，每次优化都有明确的证据支撑；部分重启机制通过屏蔽部分历史记忆，帮助优化器跳出局部最优；最终输出契约只交付可部署的内核代码，排除临时文件与调试信息。这种工程化的工作流设计，将 LLM 的代码生成能力与专业 GPU 优化知识结合，大幅提升了生产级内核的生成质量。
:::

它的目标是通过系统化的优化工作流，把原生模型写的“能用但慢”的代码，甚至是完全靠回退的代码，优化到生产级性能。

### 4.1 整体架构：知识库+迭代闭环+局部重启

> AKA 是一套完整的路由工作流，包含七个核心阶段，还有共享的知识库与工具链。整个架构有两个核心设计亮点：**第一个是分层 GPU 知识库** （GPU Wiki）。它是结构化的优化知识体系，包含两部分：

- :mdnice-bold-italic[298 个参考内核，按厂商架构分类，覆盖 NVIDIA、AMD 以及通用架构]，可以直接参考适配。
- :mdnice-bold-italic[244 份优化知识文档，分为优化模式、框架与 ISA 参考、DSL 转换方案、踩坑记录、硬件规格表五大类]，所有硬件参数都有来源可查，杜绝凭空编造。

**第二个是优化 dropout（部分重启）机制**。当优化进入瓶颈，:mdnice-bold-italic[找不到新的优化方向时，系统会保留当前已验证的最优代码和完整审计轨迹，但是抹掉一部分迭代记忆，让一个新的子智能体带着剩余状态重新探索。]

这就好比人做优化钻牛角尖的时候，换个人换个思路重新看，很容易发现之前忽略的点，有效跳出局部最优。

### 4.2 八步优化循环：每一步改动都有性能证据

> AKA 的核心是迭代优化循环，每一轮迭代都严格遵循八个步骤，确保每一次代码修改都有性能数据支撑，绝不凭感觉瞎改。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/12.webp)

::: image-caption
图 6：将性能分析数据转化为单次、限定范围的实现变更的八个编号阶段。该八阶段循环是 AKA 实现性能迭代优化的核心，其精髓是 “单步验证、证据闭环”。循环从性能剖面分析开始，通过硬件性能计数器定位具体瓶颈。这种小步快跑、每步验证的迭代模式，模拟了人类工程师的优化流程，结合知识库的领域知识，能够持续逼近硬件性能极限。
:::

| 步骤 | 说明 |
| --- | --- |
| 性能剖析 | 用官方硬件剖析工具跑当前内核，拿到详细的硬件计数器数据，而不是只看总耗时。 |
| 瓶颈提取 | 把原始计数器数据转化为屋顶线利用率、占用率、内存事务、指令混合比等结构化证据，给出明确的瓶颈假设。 |
| 知识查询 | 根据瓶颈假设，检索 GPU Wiki 里对应的优化方案、参考内核、避坑指南。 |
| 制定计划 | 输出明确的优化计划，包括测得的瓶颈、用到的知识来源、预期效果、正确性风险，以及本次要尝试的单一优化类别。 |
| 单类修改 | 每次只改一类优化点，比如分块、向量化、内存布局、预取、同步等等。这样改完之后，性能变好了还是变差了，能明确归因到哪一类改动。 |
| 验证门禁 | 先验正确性，不通过直接丢弃；通过了再测性能，和上一个版本对比。 |
| 记录更新 | 接受的优化更新到运行记忆，拒绝的也记录原因和证据，方便后续回溯。 |
| 停止判断 | 检查是否达到目标，或者是否还有可行的优化方向，决定继续循环还是退出。 |

这套流程的本质，**是把人类专家做 GPU 优化的方法论沉淀成了自动化的工作流：先测瓶颈，再找方案，小心验证，逐步迭代**。每一步都留痕，每一步都有理有据。

### 4.3 实测效果：弱模型补全，强模型提效

> 研究团队用 Qwen3.7-Max 和 Claude Opus 4.7 两个代表性模型，在三个计算密集型算子上做了对照实验，验证 AKA 的效果。

![文章插图](/articles/2026-09-28-llm-gpu-atrex-aka-517b4d69/images/13.webp)

::: image-caption
表 8：Qwen3.7-Max 与 Claude Opus 4.7 的优化增强评测（每个算子一个生产代表性形状，XPU-A 平台）。每个单元格为“原始版本 → 优化增强版本”，分别对应 FlyDSL 占比、屋顶线达成率 S、相对生产内核的加速比。结果清晰展现了 AKA 的双重作用。对于能力较弱的 Qwen3.7-Max，主要作用是“补全”：原生版本在两个算子上完全是 0%的 FlyDSL，纯靠 PyTorch 回退，性能只有生产内核的几十分之一；经过 AKA 优化后，全部变成接近 100%的 FlyDSL 内核，性能全面超过生产基线。对于能力较强的 Claude Opus 4.7，主要作用是“提效”：原生版本已经能写出接近 100%的 FlyDSL 代码，但性能还有差距；经过 AKA 优化后，屋顶线得分进一步提升，同样超过了手工调优的生产内核。最具代表性的 mla_decode 算子，生产基线是手写汇编级内核，AKA 优化后的版本依然实现了反超。
:::

::: block-1
总之，AKA 通过结构化的知识库和数据驱动的迭代优化流程，有效弥补了原生模型在领域知识和优化经验上的短板，:mdnice-highlight[第一次实现了 LLM 生成内核在真实生产算子上反超手工调优的[【生产基线】]。
:::

## 五、局限与未来方向

> 尽管这项工作迈出了重要的一步，但研究团队也在论文中坦诚地列出了当前版本的限制，以及后续的规划。

### 5.1 当前版本的边界

目前的 Atrex-Bench 和 AKA 还有三个主要局限：

- **硬件覆盖有限**：当前的主要实验都在 XPU-A 平台上完成，虽然设计上支持多硬件，但更多加速卡的验证还在进行中。
- **只覆盖推理场景：当前版本的算子全部来自推理服务**，训练场景的反向传播、优化器步进等内核还没有包含。
- 轨迹来自特定集群：采样的生产负载来自阿里自身的集群，代表的是计算受限、内存充足的 GPU 集群特征，不一定覆盖所有部署形态。

### 5.2 后续的演进路线

> 针对这些局限，团队也给出了明确的未来规划：

- 扩展硬件与负载：逐步支持更多厂商的加速卡，覆盖更多类型的工作负载，包括训练场景。
- 定期刷新基准：随着生产负载的演变，定期从新的轨迹中更新算子集合、形状分布和重要性权重，同时保留历史版本保证可复现。
- 增强智能体能力：**把内核拆分成更多区域做上下文隔离的子智能体调优，探索多模型协作的工作流**，更长周期的优化迭代，同时把验证过的经验持续沉淀回知识库。

## 结语

> 回到论文最初提出的问题：LLM 生成的 GPU 内核达到生产可用了吗？答案是：原生模型还远没有，但加上专业的工具链与知识库之后，已经开始摸到生产级的门槛。

**Atrex-Bench 把 LLM 内核生成的评测从“合成题大赛”拉回了真实生产场景，戳破了正确率和软基线带来的泡沫，给整个行业提供了一个更务实的能力标尺**。10.7%这个数字看起来不亮眼，但它才是真实的基线。

**而 AKA 的价值，则在于证明了领域知识与工具链的重要性**。LLM 的原始代码能力固然重要，但 GPU 优化是高度依赖经验和硬件细节的领域，:mdnice-bold-italic[把专家知识结构化、把优化流程自动化，带来的提升远比单纯堆模型参数来得快。]

::: block-1
对于整个 AI 基础设施领域来说，这项工作开启了一个新的方向：:mdnice-highlight[内核生成的终局是构建一套“模型+知识库+自动化工具”的完整体系，用工程化的方式把 LLM 的代码能力转化为真正的生产价值。]
:::
