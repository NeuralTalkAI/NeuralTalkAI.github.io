## 一、为什么非要在你自己的 Mac 上跑大模型

> 过去一年，主流厂商云 API 的 token 用量涨了大约一个数量级；行业预测全球推理算力将在 2027 年首次超过训练算力，到 2030 年占据数据中心算力的四成。

推理需求这条陡峭的增长曲线，正在给"一切上云"的架构假设施加越来越大的压力。**论文把推理向边缘设备迁移的理由归纳为四个相互独立的驱动力**，每一个都戳在云方案的软肋上。

| 迁移驱动力 | 说明 |
| --- | --- |
| 隐私与数据驻留 | 发往云端的提示词需穿越多租户环境、第三方基础设施和复杂司法辖区；Gartner 预测到 2027 年超四成 AI 相关数据泄露源于跨境提示词路由失控；本地推理使数据全程保留在受控环境中，天然满足物理隔离和零信任要求。 |
| 延迟 | 云端推理叠加请求处理、排队和 GPU 调度开销，高负载下首 token 延迟（TTFT）可达数百毫秒；本地推理剔除网络与排队环节，可实现 100 毫秒以内交互响应，支撑实时机器人与敏捷智能体工作流。 |
| 连接性 | 云 AI 系统高度依赖网络，网络故障、鉴权异常或共享云设施问题将导致整体瘫痪；Anthropic 状态页在 2025 年 10 月至 2026 年 4 月间记录 167 起事故。 |
| 成本 | 云推理按用量线性计费；本地推理转为一次性硬件投入，规模化后单次推理边际成本趋近于零。 |

> **硬件层面的先决条件其实早已成熟**。高通的骁龙 X Elite、英特尔的酷睿 Ultra 和 AMD 的锐龙 AI 都集成了专用 NPU，而 Apple Silicon 凭借高内存带宽、大容量统一内存和成熟的 GPU 计算栈脱颖而出。

**统一内存架构消除了 CPU 与 GPU 显存之间的传统隔离**，GPU 可以高带宽直接访问全部系统内存，这使得在本地跑大模型从"理论上可行"变成了"实用"。如今的 M 系列设备已经能以交互速度运行量化后的 7B 到 70B 模型。内存在很长一段时间里都是本地推理的头号瓶颈，因为每生成一个 token，模型权重都要从内存完整流式读入计算单元一次，容量和带宽这两道硬约束直接决定了哪些模型能在本地跑、跑多快。

Apple Silicon 的统一内存架构恰好同时松开了这两道约束：GPU 可以按需访问全部系统内存，大容量机型装得下更大的模型，高带宽则把权重搬运的时间压到最低。与此同时，**开源权重模型也在快速"瘦身"，前沿能力被压缩进适合本地部署的参数量级**。斯坦福团队关于"每瓦特智能"（Intelligence per Watt）的研究进一步表明，:mdnice-bold-italic[本地运行的模型能以明显更低的能耗，把相当大比例的常见查询处理得和云端模型一样准确。]

::: block-1
总的来说，:mdnice-highlight[边缘推理的需求侧和硬件侧都已就位，卡在中间的恰恰是软件：运行时能不能把硬件的真实能力兑现出来]。这正是 BaseRT 要解决的问题。
:::

## 二、框架的隐性税：现有运行时慢在哪

> 在 Apple Silicon 上做 LLM 推理，主流选择有两个：llama.cpp 和 MLX。它们各自背负着架构层面的包袱，决定了它们无法把这块芯片吃干榨净。

- llama.cpp 是部署最广的开源推理运行时，但它最初是一个跨平台、CPU 优先的代码库，Metal 后端是后来才嫁接上去的，整体架构带着这段历史的印记。
- MLX 虽然出自苹果官方、专为 Apple Silicon 设计，可它的定位是通用数组框架，惰性求值（lazy evaluation）和框架级调度会引入专用推理运行时中不存在的开销。

**所谓惰性求值，是指算子调用发生时并不立即执行，而是先攒成一张计算图，等到结果被真正消费时才统一调度、分配内存并求值**。这套机制对研究和原型开发极为友好，却意味着每生成一个 token，CPU 侧都要重复经历建图、调度、分配的完整流程。:mdnice-bold-italic[对矩阵运算动辄几十毫秒的训练场景，这点开销可以忽略；对单步只有几毫秒的端侧解码，它就是压在热路径上的真实税负]。

- 建立在 MLX 之上的 vllm-mlx 已经在这套约束内做到了比 llama.cpp 高 21% 到 87% 的吞吐，这本身就说明框架层之下还有可观的性能空间。
- 更近一些的原生 Metal 方案干脆绕开框架：RunAnywhere 的 MetalRT 直连 Metal、不设中间抽象层，开源运行时 uzu 则走混合路线，把工作负载在 GPU 内核和 MPSGraph 之间路由，借此同时调用 GPU 和苹果神经网络引擎（ANE）。

::: block-1
这两条路线都验证了同一件事：框架抽象是有价的，而且价格可以用吞吐数字量出来。BaseRT 沿这个方向走得更远，把抽象层削到了接近零。
:::

> 要理解为什么"削薄抽象层"能换来这么高的收益，需要先看清 LLM 推理的两个阶段各自被什么卡住。解码（decode）阶段每生成一个 token，都要把模型权重从内存完整流式读入计算单元一次，其单 token 延迟的下界可以用一个极简模型刻画：

$$
T_{\text{decode}} \approx \frac{W}{B}
$$

其中 $T_{\text{decode}}$ 是生成一个 token 所需的时间，$W$ 是每 token 需要读取的权重量（单位是字节，量化位宽越低 $W$ 越小），$B$ 是内存带宽。

拿 M4 Pro 举个具体的例子：它的 $B$ 是 273 GB/s，一个 Q4 量化的 3B 模型权重约 2 GB，代入公式得到单 token 的理论下界约 7.3 毫秒，对应每秒约 137 个 token；论文实测 BaseRT 在 Llama-3.2-3B Q4 上跑到 117.3 tok/s，已经相当贴近这个物理上限。

::: block-1
这个公式同时解释了论文里反复出现的一个规律：:mdnice-highlight[模型越小，实际吞吐离理论上限越远，因为每 token 的固定开销（内核启动、命令编码、CPU 与 GPU 同步）在小模型的延迟预算里占比越大，运行时工程能力的差距就暴露得越充分]；模型越大，大家越被同一根带宽管子勒住，差距自然收窄。
:::

总之，:mdnice-bold-italic[小模型的解码是一场"开销占比"之战，谁能把每 token 的固定成本压到最低，谁就能把实际吞吐推向带宽决定的理论上限。这就是 BaseRT 全部工程设计的靶心。]

## 三、BaseRT 的解题思路：把运行时削成一层薄纸

BaseRT 是一个直接瞄准 Metal GPU API 的 C++ 运行时，对外只暴露一个 C API 以便跨语言调用，模型权重使用其原生的 base 格式。整个设计围绕四个原则展开，每一项原则都对应着现有运行时里一个具体的开销来源。

### 3.1 原则1：数据驱动的架构描述符

在框架式运行时里支持一个新模型架构，通常意味着改动推理主循环、加条件分支、接线新的算子序列，引擎核心因此变得脆弱，也难以做统一优化。

> BaseRT 把架构间的全部差异点，包括激活函数与归一化的变体、MoE 的具体细节、注意力与位置编码的约定，统统收进一份紧凑的架构描述符里，用数据来表达，而不是写成控制流。**核心引擎只消费这份描述符，从不针对架构身份做任何分支判断，因此热路径在所有模型之间完全一致**。

目前 BaseRT 支持 LLaMA、Qwen3、Gemma、Whisper 和 BERT 家族，:mdnice-bold-italic[扩展一个新架构只是一次自包含的声明式改动，推理循环原封不动。这个设计带来的直接好处是：针对热路径做的每一处优化，会自动惠及所有模型。]

### 3.2 原则2：零分配解码循环

模型加载完成之后，BaseRT 的解码循环分配的字节数是零。

前向传播用到的全部中间缓冲区，包括残差、注意力和前馈网络的暂存空间，连同 logits 和 token 缓冲区，都在加载时一次性预分配并跨 token 复用。KV 缓存同样按最大上下文长度预分配，其布局经过专门选择，让注意力计算期间的 GPU 访存尽可能合并（coalesced）。连错误处理用的都是一个静态的线程本地缓冲区。

最终效果是，热路径上只剩下 GPU 命令分发和轻量的 CPU 侧参数修补，不存在分配器竞争和内存管理开销。

> 在此之上，BaseRT 还有两个直击解码热路径 CPU 开销的创新：一个是低开销的命令分发机制，把框架运行时里逐算子的调度、分配和图求值工作整体移除；另一个是解码调度方案，把 CPU 与 GPU 之间的同步成本摊薄到多个连续生成的 token 上，让 GPU 在 CPU 准备下一批命令时保持忙碌。

### 3.3 原则3：内核融合与特化

BaseRT 维护着一个庞大的手写 Metal shader 库，覆盖矩阵乘、注意力、归一化、RoPE、嵌入、激活和采样等类别。

矩阵乘内核是其中的大头：针对从 2 bit 到 16 bit 的每一种量化格式，都分别实现了 GEMV（解码用，$M=1$）和 GEMM（预填充用，$M>1$）两个变体，这里的 $M$ 指每次矩阵运算处理的行数，解码时一次只算一个 token 所以是 1，预填充时一批 token 一起算所以大于 1。**每个内核把反量化直接织进内层循环，权重在从内存流入计算单元的途中就地还原，全程不把反量化后的权重写回全局内存，内存流量因此按压缩比同比下降**。

在单内核优化之外，BaseRT 还**把其他运行时里通常分多次派发的算子序列融合起来，注意力路径上和前馈块内部都有这类融合**。每融合一次，就少一次内核启动、少一趟全局内存往返，这在解码阶段尤其值钱，因为此时单个内核的执行时间很短，启动开销的相对占比被放大。

**内核选择也是硬件自适应的**：依据 GPU 核心数与芯片家族（M1 到 M5）生成的逐芯片配置，决定线程组大小、内核选择阈值和融合决策，每种量化格式都被映射到它的专属内核与发射几何参数上。

### 3.4 原则4：Prefill：把 GPU 顶到算力上限

预填充阶段处理的是形状为 $[\text{seq} \times \text{dim}]$ 的激活张量，其中 $\text{seq}$ 是提示词长度、$\text{dim}$ 是隐藏维度。这个阶段的算力需求约 $2 \cdot \text{seq} \cdot \text{dim}^2$ 次浮点运算，而权重读取量与 $\text{seq}$ 无关，因此算术强度（每字节内存流量对应的浮点运算次数）随序列长度线性上升，预填充随之从访存受限转向算力受限。

> BaseRT 用 Metal 的 simdgroup 矩阵指令实现分块 GEMM 内核，块几何参数按序列长度区间调优，并通过有界最大块长的分块预填充（chunked prefill）给暂存内存封顶。注意力部分由 FlashAttention 内核按块计算，采用带运行统计量的在线 softmax，其核心递推可以写成：

$$
m_i = \max(m_{i-1},\ \mathrm{rowmax}(S_i)), \qquad l_i = l_{i-1} \cdot e^{m_{i-1} - m_i} + \mathrm{rowsum}(e^{S_i - m_i})
$$

其中 $S_i$ 是第 $i$ 个分块的注意力分数矩阵，$m_i$ 是到第 $i$ 块为止见过的最大值，$l_i$ 是归一化分母的滚动累积。

每当新的分块把最大值 $m_i$ 推高，旧累积量就乘上修正因子 $e^{m_{i-1}-m_i}$ 重新对齐。

这就像汇总一连串账户的余额，每来一个汇率更新的新账户，就把之前的汇总按新旧汇率差折算一遍，全程不需要把任何一份完整流水留档。得益于此，注意力的内存复杂度是 $O(n)$ 而非完整 $n \times n$ 注意力矩阵的 $O(n^2)$，长提示词下也不会爆内存。

::: block-1
总结下，:mdnice-highlight[BaseRT 的方法论可以概括成一句话：凡是热路径上的工作，要么提前到加载时做完，要么融合进别的内核里做完]，要么干脆不做。运行时的薄，换来的是 GPU 的忙。
:::

## 四、Decode 实测：小模型最高提速 56%，优势跨越芯片代际

> 评测在 M4 Pro（16 个 GPU 核心、24 GB 统一内存、273 GB/s 带宽）上进行，覆盖 Qwen3、Llama 3.2 和 Gemma 4 三个家族的六个模型，量化位宽为 Q4 和 Q8，解码指标是生成 128 个 token 的平均吞吐（tg128）。

评测方法学上有几个细节值得交代。对照组用的是 llama.cpp 的 Metal 后端（2026 年 6 月的 b9630 提交，默认设置）和 MLX v0.31.2 搭配 mlx-lm 的默认生成配置，**BaseRT 则把相同的模型检查点转换为自己的 base 权重格式，量化位宽与基线严格对齐**。论文省略了标准差以保持表格清爽，但说明了解码的波动普遍低于 3%，预填充低于 10%。此外还选了 Apple M3 基础款（8 个 GPU 核心、16 GB 统一内存、100 GB/s 带宽）做跨代际验证，避免结论只是某一款芯片的特例。

表 1：Apple M4 Pro 上的解码吞吐（tg128，tok/s），BaseRT 对比 llama.cpp 与 MLX。Gemma 4 E2B 不受 MLX 支持，20B 以上模型的 Q8 版本超出 M4 Pro 的 24 GB 统一内存。表中最抢眼的数字是 Qwen3-0.6B Q4 一行：BaseRT 跑到 464.5 tok/s，是 llama.cpp（297.4）的 1.56 倍、MLX（343.6）的 1.35 倍。还可以读出两条规律：一是 BaseRT 在 Q4 上的相对优势普遍大于 Q8，因为 Q4 权重更小、单步更快，固定的每 token 开销在预算中占比更大，恰好落在低开销分发机制的甜区；二是优势随模型变大而收窄，到 Qwen3-30B-A3B 和 Gemma-4-26B-A4B 这两个 MoE 模型上只剩 1.04 至 1.07 倍，解码此时已被内存带宽牢牢锁死。唯一的例外是 Gemma-4-26B-A4B 上 MLX 以 0.90 倍的比值反超，BaseRT 在这个配置上输了约一成。
:::

表 1 的数字分布完美印证了第二节的延迟模型。

- 小模型上，每 token 固定开销占比高，BaseRT 的零分配循环和低开销分发把这部分成本压到最低，于是甩开 llama.cpp 五成以上；
- MoE 大模型上，每 token 要搬运的激活权重字节数巨大，三家运行时都贴在同一条带宽曲线上，差距被压缩到个位数百分比。

值得注意的是，即便在这种带宽饱和区，BaseRT 依然保持了全胜或接近全胜，说明它的内核效率本身也不落下风。

![文章插图](/articles/2026-07-23-mac-56-basert-apple-silicon-1dd0d869/images/05.jpg)

::: image-caption
表 4：Apple M3 基础款上的解码吞吐（tg128，tok/s），BaseRT 对比 llama.cpp 与 MLX。Gemma 4 E2B 不受 MLX 支持。M3 基础款只有 8 个 GPU 核心、16 GB 统一内存和 100 GB/s 带宽，带宽不到 M4 Pro 的四成，但 BaseRT 在全部八个配置上对 llama.cpp 保持 1.13 至 1.34 倍的领先，对 MLX 保持 1.01 至 1.22 倍的领先，相对格局与 M4 Pro 高度一致。这一点很重要：BaseRT 的优势不是靠某款芯片的特定调参"碰巧"得来的，逐芯片配置机制让它能跨代际复现同样的领先幅度。对读者中保有量更大的入门款 MacBook Air 和 Mac mini 用户来说，这张表的意义其实比 M4 Pro 那张更实在。
:::

::: block-1
从 273 GB/s 的 M4 Pro 到 100 GB/s 的 M3 基础款，BaseRT 的解码领先没有一代落空。它的收益来源是结构性的低开销设计，而非针对单一硬件的投机性调优。
:::

## 五、Prefill 与 uzu 对决：MoE 才是真正的分水岭

> 预填充的战况比解码复杂得多，需要分模型类别来看。结论先行：稠密小模型上三家打成平手，MoE 大模型上 BaseRT 一骑绝尘。

![文章插图](/articles/2026-07-23-mac-56-basert-apple-silicon-1dd0d869/images/06.jpg)

::: image-caption
表 2：Apple M4 Pro 上的预填充吞吐（tok/s），BaseRT 对比 llama.cpp，提示词长度 128 至 2048。加粗表示该长度下更快的运行时。20B 以上模型的 Q8 版本超出 24 GB 统一内存。稠密模型上 BaseRT 落后 llama.cpp 几个百分点，Qwen3-0.6B 约 5% 到 10%，Llama-3.2-1B 约 1% 到 6%，Llama-3.2-3B 在正负 6% 以内，且不随提示词变长出现系统性漂移；Gemma-4-E2B 是例外，Q4 落后 3% 到 7%，Q8 反而领先 19% 到 23%。MoE 模型上局势彻底反转：BaseRT 在 pp128 时领先 Gemma-4-26B-A4B 达 1.59 倍、领先 Qwen3-30B-A3B 达 1.81 倍，随着上下文变长、GEMM 负载把 GPU 喂饱，差距逐渐收窄。
:::

::: image-caption
表 3：Apple M4 Pro 上的预填充吞吐（tok/s），BaseRT 对比 MLX，提示词长度 128 至 2048。加粗表示该长度下更快的运行时。Gemma 4 E2B 不受 MLX 支持。对 MLX 的图景类似：稠密模型在最短提示词 pp128 上 BaseRT 占优，从 pp512 起 MLX 反超；MoE 模型依旧一边倒，BaseRT 在 pp128 领先 Gemma-4-26B-A4B 达 1.42 倍、领先 Qwen3-30B-A3B 达 1.78 倍，到 pp2048 收敛至接近持平。两张表合起来揭示了一个清晰的分野：稠密模型的预填充是 GEMM 主导的算力受限负载，各家内核都能把 GPU 的矩阵单元喂饱，吞吐自然趋同；MoE 模型则因为专家路由引入了额外的调度与分发复杂度，框架运行时在这里付出的开销被成倍放大，而这正是 BaseRT 架构描述符加低开销分发机制的主场。对智能体这类长系统提示词、频繁重复前缀的应用场景，MoE 预填充接近两倍的提速会直接转化为首 token 延迟的大幅改善。
:::

最后一组对照实验把 BaseRT 推到了最严苛的擂台上：与同为原生 Metal 路线的 uzu 正面对决。uzu 会把工作负载在 GPU 内核和 MPSGraph 之间路由，MPSGraph 还能把计算派发给 ANE，等于比 BaseRT 的纯 GPU 路径多了一块算力。

把四张预填充表叠在一起看：稠密模型上大家殊途同归，因为算力上限对所有人一视同仁；MoE 模型上 BaseRT 最高领先 81%，因为路由复杂度惩罚一切带框架包袱的实现；对阵 uzu 的失利则说明，Apple Silicon 上 GPU 之外的 ANE 算力是下一片必争之地。
:::

## 六、BaseRT 的边界在哪

> 一篇诚实的系统论文，价值一半在数字里，另一半在它坦承做不到的事情里。

- BaseRT 目前**只支持单设备推理，没有实现连续批处理（continuous batching）、跨请求并行解码和多 GPU 张量并行**。这些是服务器级负载的必需品，:mdnice-bold-italic[对本文聚焦的单用户边缘场景则没那么关键，但这也意味着 BaseRT 现在还无法直接拿去搭多租户推理服务。]
- 其次，运行时**只面向 Metal，部署范围被限制在苹果硬件之内**；内部的设备抽象层虽然为多后端预留了设计，但 CUDA 和 Vulkan 后端目前都不存在。

路线图上的方向包括：把架构覆盖扩展到视觉语言模型和（混合）状态空间模型；通过 CUDA 后端与 GPU 级推理服务器正面对标，通过 Vulkan 后端覆盖 Android 和 Linux 平台，两者都只需要补后端内核，无需改动核心分发机制与推理循环；在服务端，连续批处理和投机解码（speculative decoding）是顺理成章的下一步。再叠加第五节提到的 ANE 利用问题，BaseRT 的性能故事显然还没讲到终章。

**还有一个论文没有展开、但对使用者很现实的问题：BaseRT 采用自有的 base 权重格式，模型需要先转换才能运行，这与 llama.cpp 生态里随处可见的 GGUF 形成了生态位差异**。:mdnice-bold-italic[GGUF 的价值从来不只是格式本身，还有围绕它的海量现成量化模型仓库]。BaseRT 要在易用性上追平 llama.cpp，转换工具的覆盖面和社区模型的供给速度，重要性不亚于内核本身。

## 结语：端侧推理的地基之争

> BaseRT 用一组跨模型、跨量化位宽、跨芯片代际的一致数字，把 Apple Silicon 的推理性能基线整体抬高一截，也把一个问题摆上了台面：**我们为"框架的便利"究竟付了多少性能税？**

这篇论文给出的答案相当具体：

- 在小模型解码上，税额最高达到 56%；
- 在 MoE 预填充上，最高达到 81%。

更重要的是它的方法论启示：当硬件走向统一内存、专用加速器林立的异构形态，通用抽象层的成本会越来越显眼，**贴着硬件执行的模型（数据驱动的架构描述、零分配热路径、芯片级内核特化）会比"一套框架跑天下"更有生命力。**

对正在发生的推理边缘化迁移而言，隐私、延迟、连接性和成本四大驱动力把需求推向本地，而 BaseRT 这类极致优化的本地运行时，正是让这场迁移从"能跑"变成"好用"的关键使能层。代码已在 GitHub[2] 开源，论文全文见 arXiv:2607.00501[3]，手边有 Mac 的读者不妨亲自跑一跑，感受一下这块芯片被释放出来的真实速度。

::: block-1
Apple Silicon 的推理天花板比此前报告的要高，框架抽象是真实且可量化的开销来源。这两条结论，会随着端侧 AI 的普及而变得越来越值钱。
:::
