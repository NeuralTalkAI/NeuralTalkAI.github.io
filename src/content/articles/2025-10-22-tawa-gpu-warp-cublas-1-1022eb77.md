## 一、引言

> 现代 GPU 架构已从同构处理器演变为复杂的异构系统，通过集成多个专用硬件单元来最大化性能。除了传统的 CUDA 核心处理通用算术运算外，**现代 GPU 还集成了专用引擎，例如用于密集矩阵计算的张量核心（Tensor Cores）和用于异步数据移动的张量内存加速器（TMA）**。这种架构设计支持细粒度、异步的数据流执行模型，在该模型中，**数据移动可被显式编排，并与计算过程重叠** （即数据移动和计算同时进行，以隐藏访问延迟）。

利用这一能力对于大型语言模型（LLMs）等延迟敏感型负载至关重要——这类负载的效率往往更多地受限于数据编排，而非原始浮点运算次数（FLOPs，衡量计算能力的指标）[1]-[5]。

然而，作为 CUDA（NVIDIA 的 GPU 编程框架）基础的主流 GPU 编程范式——单指令多线程（SIMT），与这种异构、任务并行的实际情况在本质上不匹配。SIMT 模型假设一个组（即 Warp）内的所有线程对不同数据执行相同指令，因此在控制流统一的问题上表现出色。**但该模型难以管理需由不同并发任务驱动的多样化硬件单元**。例如，:mdnice-bold-italic[一个任务可能涉及生成地址并通过 TMA 启动批量数据复制，而另一个任务则在张量核心上执行矩阵乘法]。这就造成了范式不匹配：硬件能够支持异步、任务并行执行，但软件模型却为同步、数据并行执行而设计。

**为解决这一矛盾，NVIDIA 的 Hopper 和 Blackwell 等现代 GPU 架构引入了硬件级别的 Warp 专业化** [6]、[7]。该机制通过允许不同线程组（Warp）承担不同角色，体现了硬件的任务并行特性。例如，生产者 Warp 可专门负责通过 TMA 管理数据传输，为在张量核心上执行计算的消费者 Warp 提供数据。**尽管这种新模型释放了硬件潜力，但针对它的编程仍然困难——因为周边的软件生态系统和抽象仍植根于 SIMT 范式**。这种可编程性鸿沟使得开发高性能核函数成为一项耗时费力的工作：即便是基本的 GEMM 核函数，也往往需要超过一千行手动优化的代码。

这种困难主要体现在三个挑战上：

### 挑战 1：协调并发的 Warp 角色

由于 SIMT 模型缺乏用于分配异构角色的一等抽象（即直接支持角色分配的核心抽象），开发者必须手动重构核函数，将角色特定的逻辑封装在复杂的条件分支中。随后，他们**还需编排这些专业化 Warp 的执行，以确保生产者和消费者任务保持正确同步且高效重叠。这一手动过程本质上很脆弱**。即便是 Triton[8]等现代、高层级的领域特定语言（DSL，针对特定领域设计的编程语言），也仍保留以 SIMT 为中心的抽象，这使得 **Warp 角色无法被显式分配，因此无法自然地表达 Warp 专业化程序。**

### 挑战 2：底层通信管理

**目前 CUDA 并未为 TMA 和事务屏障（mbarriers，用于线程间同步的硬件机制）操作提供 C++级别的接口**。因此，程序员必须依赖内联 PTX（GPU 的汇编语言）来配置 TMA 描述符、初始化和操作 mbarriers，并编排同步。这需要显式考虑到达计数（线程到达屏障的数量）、屏障阶段（屏障的不同状态）和共享内存别名（多个指针指向同一块共享内存）——**其中细微的错误都可能导致死锁** （线程互相等待无法继续执行的状态）。

**当涉及多个 mbarriers 和输入参数时，难度会进一步加剧**。这种底层编排会降低代码可读性，并大幅增加调试和维护的复杂性。CUTLASS[9]和 ThunderKittens[10]等高层级库提供了预编写的核函数，但仍要求用户**仔细组合** 这些核函数，以满足底层通信需求。

### 挑战 3：资源分配与流水线编排

要有效重叠专业化生产者 Warp 和消费者 Warp 的工作，需要手动实现深度软件流水线。开发者必须在共享内存中显式管理多缓冲方案（使用多个缓冲区交替存储数据以隐藏延迟），将核函数划分为序幕（Prologue，初始化阶段）、主体（Main Body，核心计算阶段）和尾声（Epilogue，结果处理阶段），并仔细平衡寄存器和共享内存等硬件资源的分配，以满足占用率限制（即流式多处理器 SM 上同时运行的线程块数量限制）。**这些设计选择紧密耦合，形成了庞大而复杂的优化空间。** 例如，增加流水线深度会影响共享内存容量，进而限制线程块大小，并影响 TMA 描述符布局。**探索这一优化空间需要反复、耗时的核函数重构，使得性能调优既困难又难以持续。**

> 为应对这些挑战，我们提出了 Tawa——一款自动化编译器，**能够系统性地分析从基于分块的 DSL 生成的计算图**，:mdnice-bold-italic[将程序划分为 Warp 专业化组件，并管理通信和流水线]。我们的贡献如下：

1. 我们提出了:mdnice-bold-italic[异步引用（aref）——一种用于 Warp 级别通信的抽象。aref 能够表达异步数据传输意图，同时不暴露底层硬件原语] （硬件的基本操作单元），在 IR 级别提供了简洁且可移植的表示。
2. 我们提出了 Tawa——一种用于 NVIDIA GPU 上 Warp 专业化的自动编译流程。**Tawa 接收 Triton 程序，跨 Warp 组执行任务感知分区** （根据任务特性划分 Warp 组），应用多粒度流水线，并生成用于 GPU 执行的高性能 PTX 代码。
3. 我们在 H100 GPU 上使用典型 LLM 核函数对 Tawa 进行了评估。我们的方法通过**简洁的核函数代码实现了高硬件利用率，性能达到或超过手动优化的基准**。对于 GEMM，Tawa 相较于 cuBLAS 的加速比最高可达 1.1 倍；对于注意力核函数，其相较于 Triton 的加速比达 1.2 倍，且性能与手动优化的 CUTLASS C++ FlashAttention-3[11]核函数相当。

> 在本节中，我们首先讨论现代 GPU 架构，然后简要概述现有的 GPU 编程模型。

### A. 现代 NVIDIA GPU 架构

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/07.webp)

::: image-caption
图 1：简化的 NVIDIA H100 SXM5 GPU 架构
:::

> 如图 1 所示，流式多处理器（SM）是现代 GPU 的基本计算单元，封装了计算和内存资源。

- 每个 SM 集成了一个大型寄存器文件、一个 Warp 调度器（每个时钟周期可向一个 Warp（32 个线程）下发指令），以及多个处理通用算术运算的 CUDA 核心。
- 此外，SM 还包含用于加速矩阵计算的专用张量核心，以及一个作为软件管理共享内存（SMEM）的内存块。
- 线程块（又称协作线程数组 CTA）在 SM 上调度，并共享 SM 的寄存器和 SMEM。

新一代 GPU（如 Hopper）对张量核心的依赖程度不断提高，使其成为计算吞吐量的主要来源——**在 Hopper 架构中，90%的总计算吞吐量由张量核心贡献** [6]。:mdnice-bold-italic[因此，要在现代 GPU 上实现高性能，关键在于为这些张量核心及时提供充足的数据，使其达到满负载运行状态。]

> 为此，Hopper 架构引入了两项**旨在提高【张量核心利用率】的【关键硬件创新】**：张量内存加速器（TMA）和 Warp 组矩阵乘加（WGMMA）。

- **TMA 支持硬件管理的、从全局内存（GMEM，GPU 的大容量内存，访问延迟较高）到共享内存的多维数据传输**，:mdnice-bold-italic[将地址生成和传输协调任务从软件卸载到专用硬件单元。]

为进一步支持这种（数据移动与计算的）重叠，**Hopper 架构通过异步事务屏障扩展了编程模型——这种屏障允许线程不仅基于“到达”（线程到达屏障点）进行同步，还能基于交换的数据量进行同步**。每个事务都携带一个字节计数，只有当所有生产者都到达屏障且达到预期的总事务计数时，屏障才会释放线程。该机制在协调异步内存复制和跨线程块的集合数据交换（多个线程块间的数据交互）时特别有效。

- 与此同时，**WGMMA 引入了 Warp 组级别的矩阵乘法操作**，:mdnice-bold-italic[允许多个 Warp（通常 4 个 Warp 组成一个 Warp 组）以异步、高效的方式协作执行大块分块（Large-Tile）GEMM 核函数。]

这些机制共同为 Warp 专业化奠定了基础——在该模式下，SM 内的不同 Warp 在数据通信和计算中承担不同角色，从而提高 LLM 负载的吞吐量[10]-[12]。

> :mdnice-bold-italic[这些趋势表明，GPU 架构正朝着【异步数据流执行】的方向发生更广泛的转变]，这一方向在 Blackwell[7]等后续架构中得到了延续。

### B. 当前 GPU 编程模型

CUDA 是 GPU 编程的主流接口[13]，但随着架构的演进，其编程复杂性大幅增加。

- NVIDIA 的 CUTLASS C++库[9]为 GEMM 及相关计算提供了模板化核函数，但要利用它编写神经网络算子，需要复杂的配置和手动调优。

为减少领域负载的工程工作量，专用库应运而生。

- ThunderKittens[10]基于 16×16 分块抽象引入了简洁的 C++接口，提供了性能具有竞争力的 GEMM 和注意力核函数。FlashInfer[12]专注于高效的注意力计算和 KV 缓存（LLM 推理中存储键值对的缓存）管理，并通过即时编译（JIT）特化支持大规模 LLM 推理。这些系统简化了高性能核函数的使用，但仍以库为中心：它们提供优化的算子模板，而非适用于不同应用的通用策略——这可能导致为不同大小的矩阵手动调优性能时出现大量维护问题。

为进一步提高抽象级别，研究者提出了领域特定编译器基础设施。

- TVM[14]率先提出了带有自动调度[15]、[16]的端到端编译框架，而 Relax[17]通过用于动态负载的图级别 IR 对其进行了扩展。
- Fireiron[18]也利用调度语言来指定分块和数据移动。
- Graphene[19]则通过提供一种 IR（用于将不同布局的张量映射到张量核心指令）进一步强化了这一思路。

> 尽管这些系统功能强大，但它们**均在 Hopper 架构之前开发，无法直接利用 TMA 和硬件 Warp 专业化**，因此未能释放大量潜在性能。类似地，**许多关于 GPU Warp 专业化的研究[20]-[23]也在 Hopper 架构之前提出，无法有效利用最新的 TMA 特性。**

出于对更精细控制的需求，一类新的基于分块的核函数语言应运而生。

- Triton[8]基于 MLIR[24]（一种模块化的编译器 IR 框架）构建，允许程序员用 Python 编写高效核函数，同时对分块和内存管理进行抽象。尽管 Triton 在推动核函数开发大众化方面取得了成功，但它仍**缺乏用于 Warp 专业化的固有抽象，因此在 Hopper 架构上存在性能差距。**
- TileLang[25]和 Mosaic[26]等近期研究通过引入用于数据流调度和流水线组合的显式 API，扩展了这一方向。
- Cypress[27]提出了一种基于任务的编程模型，通过逻辑计算描述和映射规范对复杂的数据移动和同步进行抽象。然而，程序员仍需手动管理线程、Warp 和 SM 的多级层次结构，以及相应的数据分解（将数据划分为适合并行处理的小块）。
- **Gluon[28]为 Triton 提出了一种添加了布局抽象的 IR，但仍要求程序员显式集成通信操作。**

这些方法为专业用户提供了富有表现力的控制能力，但它们**仍将同步和资源管理的重大责任强加给用户，从而限制了程序员的生产力**。

> 为此，我们认为**用户不应被迫处理底层硬件细节；相反，Warp 专业化程序应能自动生成**。Tawa 通过引入 aref 作为 Warp 通信的 IR 级别抽象，并自动生成支持 TMA 的 Warp 专业化流水线，填补了这些空白，从而在不增加底层编程负担的情况下实现了高性能。

### B. 异步引用

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/08.webp)

::: image-caption
图3：aref抽象及相关操作
:::

为更好地对线程束间的通信进行建模，我们引入了**异步引用（asynchronous reference，简称 aref）** ——一种 IR 抽象，用于建模 GPU 上生产者与消费者之间的单槽通道（one-slot channel），如图 3 所示。它将**数据缓冲区与两个由硬件同步屏障（mbarrier，用于线程间同步的硬件机制）实现的同步原语打包在一起，这两个同步原语通常被称为“空”（empty）和“满”（full）**。

在任何时刻，这两个屏障中恰好有一个能表示槽位的状态：

::: block-1
- 当“空”屏障（empty mbarrier）持有信用（credit）时，生产者可向槽位写入数据；
- 当“满”屏障（full mbarrier）持有信用时，槽位中包含可供消费者读取的已发布数据。
:::

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/09.webp)

::: image-caption
图4：aref操作的操作语义。σ是从aref标识符a到实际结构σ(a) = ⟨buf, F, E⟩的存储映射，其中F是满内存屏障标志，E是空内存屏障标志。初始时E = 1，F = 0
:::

> aref 接口提供三种操作：put（写入）、get（读取）和 consumed（消费完成），其形式化语义如图 4 所示。**这些语义为将操作下转为 GPU 专用指令提供了严格基础，具体将在 § III-E 中讨论。**

- **put（写入）：生产者的发布步骤**。它要求槽位处于“空”状态（即“空”屏障 E 持有信用），将有效载荷（payload）写入缓冲区，并通过以释放顺序（release ordering）到达“满”屏障 F，将状态切换为“满”。这一转换使数据对消费者可见，并防止后续写入操作过早复用该槽位。
- **get（读取）：消费者的获取步骤**。它要求槽位处于“满”状态（即检测到“满”屏障 F 被触发），将缓冲区中的数据读取到程序变量中，并将 aref 转换为“借用”状态——此时 E 和 F 均不持有信用，表明数据正在被使用，但槽位尚未可复用。
- **consumed（消费完成）：完成握手过程**。当消费者不再需要该数据时，它会到达“空”屏障 E，恢复“空”信用并允许下一次 put 操作；:mdnice-bold-italic[这一过程会形成“生产者写入 → 消费者读取 → 生产者后续复用”的先行发生（happens-before）链。]

因此，aref 可作为一等 IR 值（first-class IR value），表示具体的通信路径，确保线程束组间数据移动与计算的顺序正确性。

与 OpenCL 管道[32]或其他加速器编程模型中的类似机制[33-37]相比，**aref 抽象是专门为 GPU 线程束间通信设计的。其语义基于硬件支持的 mbarrier 同步，提供了清晰的排序模型**。

- 除同步语义外，**aref 还支持类型泛型** （type-generic），可支持 `<T>` 类型的缓冲区，使其能携带张量（tensor）或元组（tuple）等结构化有效载荷，同时复用相同的 mbarrier。
- 为便于深度流水线（deep pipelining），**多个 aref 实例可被分组为深度为 D 的循环缓冲区（cyclic buffer），形成环形结构**，支持跨流水线阶段存储和传输中间数据。

### D. 多粒度流水线

> 得到线程束专用程序后，我们**在计算线程束组上进一步优化，引入两种流水线机制以确保硬件组件并行工作**。具体而言，我们考虑两种流水线：

- **细粒度流水线**：重叠 MMA（矩阵乘法累加操作，Matrix Multiply-Accumulate）地址计算与计算过程；
- **粗粒度流水线**：重叠 CUDA 核心计算与张量核心计算。

#### 1. 细粒度流水线

现代 GPU 同时提供 CUDA 核心（处理标量和地址计算）和张量核心（加速 MMA 操作）；但 naive 的顺序执行会迫使这些单元按序工作——地址生成会阻塞张量执行，反之亦然，导致利用率低下。**为缓解这一低效问题，我们引入一种自动流水线算法**：:mdnice-bold-italic[通过深度为 P 的有界流水线（bounded pipeline），使 CUDA 核心上的地址计算与张量核心上的 MMA 执行重叠。]

在每次迭代中，编译器异步发布下一条 MMA 指令（`WGMMA.issue(k)`），仅当未完成操作（outstanding operation）的数量达到最大流水线深度 P 时才暂停（`WGMMA.wait() {pendings=P}`）。由于第 k 次 wait 操作无需在每次 MMA 发布后立即执行，因此在等待前可让更多 MMA 指令处于“飞行中”（in flight）。一旦流水线填满，就会释放第 $k-P$ 次迭代的结果引用（`aref.consumed(k-P)`）——这一操作通过强制数据流依赖确保正确性，并释放资源以供复用。在最后一次迭代后，编译器会在尾声中排空流水线（drain the pipeline），处理剩余的未完成操作。

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/11.webp)

::: image-caption
图6：细粒度流水线重叠MMA地址计算与计算。实际延迟未按比例显示
:::

这种设计有效解耦了地址计算与矩阵乘法，使两个功能单元能持续处理任务，**与顺序执行基线相比，能有效隐藏延迟并减少空闲时间，如图 6 所示。**

#### 2. 粗粒度流水线

**细粒度流水线在循环主要由矩阵乘法操作构成时效果最佳**。但当 CUDA 核心还需执行额外计算时，这些操作也可与 MMA 重叠。因此，我们进一步提出一种粗粒度三阶段“生产者-转换-（可选）消费者”流水线（如算法 1 所示）。

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/12.webp)

::: image-caption
算法 1：CUDA 核心与张量核心的粗粒度流水线
:::

每次循环迭代 j 包含三个阶段：

- 张量核心阶段 $T_j$：生成中间分块（如矩阵乘法片段）；
- CUDA 核心阶段 $C_j$：转换该中间分块（如归一化、激活函数、归约）；
- 可选的下游张量核心阶段 $U_j$：消费转换后的结果（如第二次矩阵乘法/尾声）。

**流水线执行过程**：

1. **序幕（Prologue）**：启动流水线——完成 $T_0$ 的执行，并立即计算 $C_0$；
2. **稳态（Steady state）**：使 $T_j$ 与 $C_{j-1}$（若存在则包括 $U_{j-1}$）重叠：
3. **尾声（Epilogue）**：排空最后一次 CUDA 核心转换；若使用 U 阶段，则发布并终止 $U_{N-1}$（N 为分块总数）。

正确性保障依赖两种同步机制：

::: block-1
- `DOTWAIT`($T_{j-1}$)及 `DOTWAIT`($U_{j-1}$)：确保张量核心边界处计算组的完成；
- `MAYBEAREFGET(·)`：仅当某个阶段实际消费跨线程束组的 aref 对象时，才执行 get 操作的包装器（wrapper）。若无需读取外部数据，包装器会编译为空操作（no-op），使模板最小化并避免不必要的暂停。
:::

**流水线构建方法**：

从 MLIR 计算图中构建调度的过程，包含一系列原则性分析和后续的机械合成步骤：

1. **阶段识别**：利用方言和类型级线索（dialect- and type-level cue），将每次迭代的子图划分为 $T_j$、$C_j$ 和（可选的）$U_j$：
2. **aref 使用检查**：标记任何读取其他线程束组生成数据的阶段；仅对这些标记阶段，才会生成 `MAYBEAREFGET(·)` 和 `MAYBEAREFCONSUMED(·)` 包装器。

### E. aref 下转

> aref 的下转（lowering）过程，是将高层级异步引用转换为可在 GPU 上直接执行的显式同步和内存传输指令。在 IR 层面：

- `create_aref`：声明缓冲区并分配所需的 mbarrier，作为通信子图的根节点；
- 编译器随后将 put、get、consumed 操作重写为具体指令：

这种模式匹配确保：当整个子图被重写后，抽象的 aref 节点可被安全删除，仅留下可执行的低层级同步和数据移动指令。

该转换的关键在于**流水线场景下的正确性** ——此时多个分块处于“加载-计算-消费”的飞行中状态。为避免循环等待导致的死锁，下转过程引入**奇偶校验机制** （parity mechanism）：每个操作在两组按迭代奇偶性（iteration parity）索引的屏障间交替切换。当奇偶性切换时，消费者若数据已生成则可跳过等待，生产者可复用缓冲区槽位而不覆盖仍在使用的值。**这一机制不仅保证了活性（liveness，即无死锁），还支持高效的多缓冲（multibuffering），使通信与计算能跨多个阶段重叠执行。**

通过这种方式，aref 下转为抽象的、声明式的异步数据流视图与高性能 GPU 所需的精确 TMA 和 mbarrier 指令之间，搭建了系统性的桥梁。

## 四、进一步优化

> 为在线程束专用场景下进一步提高张量核心利用率，TAWA 还集成了额外的优化，并将其融入编译流程，确保程序无需手动重构即可自动受益。

### A. 协作计算线程束组

线程束专用执行的一个关键限制是：每个线程束组可用的**寄存器预算** （register budget，即每个线程束组可使用的寄存器总量）有限，这会约束最大分块大小，并可能限制整体计算强度（compute intensity）。**“协作线程束组”优化通过允许多个线程束组协作计算同一个分块，缓解了这一瓶颈。**

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/13.webp)

::: image-caption
图7：（a）协作线程束组；（b）持久内核
:::

如图 7a 所示，两个消费者线程束组（WG1 和 WG2）共同消费由 TMA 线程束组（WG0）生成的数据。:mdnice-bold-italic[通过“汇集”寄存器（pooling registers），协作线程束可形成更大的分块——这能提高算术强度（arithmetic intensity）、改善数据复用，并减少内存流量]。从概念上看，该优化在“线程束专用”场景中，重新引入了标准的线程束并行性（即多个线程束对同一个分块的不同片段执行相同计算）。

TAWA 会透明地处理这一过程：通过告知后端代码生成器（backend code generator）协作映射关系，确保线程索引被一致分配。**重要的是，aref 抽象无需任何修改——因为通信语义保持不变。**

### B. 持久化内核

GPU 流水线中的另一大低效来源是**重复内核启动** （repeated kernel launch）——每次启动都会产生显著的线程块（CTA）启动开销（kernel launch overhead）。**“持久化内核”（persistent kernel）通过仅启动与流多处理器（SM）数量相等的 CTA，并使其在整个执行过程中保持驻留（resident），来减少这一开销。**

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/13.webp)

::: image-caption
图7：（a）协作线程束组；（b）持久内核
:::

:mdnice-bold-italic[如图 7b 所示，TAWA 将执行模型转换为“软件管理流水线”：驻留的 CTA 负责遍历分块，实现 TMA 驱动的加载、张量核心计算与 CUDA 核心尾声的跨迭代重叠] ——这消除了重启延迟（relaunch latency）并减少了空闲时间。TAWA 会在每次尾声前自动插入同步，以保证正确性。

该优化在**深流水线、大 K 维度（如矩阵乘法中的内维度）场景下效果尤为显著** ——此时累积的启动成本可能成为性能瓶颈。

## 五、实验评估

> 本节首先介绍实验设置，然后展示不同基准测试的结果。

### A. 实验设置

TAWA 基于 Triton[8]（提交号：0c7edf）构建，包含约 4000 行 C++ 代码，并引入了一个紧凑的 MLIR 方言，用于封装 aref 操作。我们将 TAWA 与一系列最先进的 GPU 编程框架和库进行对比，包括：

::: block-1
- cuBLAS[39]（v12.7）：NVIDIA 的闭源商业线性代数库；
- CUTLASS[9]（v4.0.0）：NVIDIA 的开源 CUDA 线性代数库；
- 基线 Triton：与 TAWA 基于同一提交版本的 Triton，默认启用官方软件流水线（流水线深度预先设定，以平衡通信与计算的重叠）；
- ThunderKittens[10]（提交号：6c27e2）：基于 CUDA 的 AI 内核库；
- TileLang[25]（提交号：bcfc83）：基于 TVM[14]的领域特定语言（DSL）。
:::

**为保证公平对比，所有基线均采用固定分块大小集合（{64, 128, 256} 的组合）进行手动调优**。对于 TAWA 生成的内核，aref 大小和 MMA 流水线深度通过手动选择以最大化性能——确保每种方法都有同等机会利用底层硬件。

硬件与软件环境：

::: block-1
- 硬件：NVIDIA H100 SXM5 GPU（配备 80GB HBM3e 内存）；
- 软件栈：CUDA 12.7；
- 实验流程：执行 25 次热身运行（warm-up run）和 1000 次测量运行，取平均执行时间作为结果。
:::

基准测试工作负载：

::: block-1
1. 矩阵乘法及其变体：评估 FP16（16 位半精度浮点数）和 FP8（8 位浮点数）精度；
2. 注意力内核：测试不同序列长度，以反映真实的大语言模型（LLM）工作负载。
:::

这些基准测试涵盖了多样化的计算模式，可全面评估“自动线程束专用”相对于“手动优化库”和“基于 DSL 的方法”的有效性。

### E. 超参数选择

为研究编译流程中超参数的影响，我们针对（非）持久化 GEMM 内核（$K=16384$），实验分析了两个关键超参数：

1. **aref 大小 D**：由异步屏障控制的独立共享内存暂存缓冲区（staging buffer）数量；
2. **MMA 深度 P**：同时处于飞行中的计算分块（WGMMA 发布组）数量。

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/15.webp)

::: image-caption
图11：不同aref和MMA流水线规模的影响
:::

> 如图 11 所示，在可行域（$D ≥P$）内，性能随 D 的增加而持续提升：**更大的 D 允许 TMA 生产者预取更多数据，平滑延迟波动，并更好地在计算过程中隐藏“全局内存到共享内存”的传输延迟**。但进一步增大 D 需要分配更多共享内存——这对于大分块大小而言是不可行的。

在固定 D 的情况下改变 P，会呈现典型的“过度流水线”权衡（over-pipelining trade-off）：

::: block-1
- 当 P 从 1 增加到 2 时，性能通常会提升（持久化内核在 $D=3$、$P=2$ 时达到峰值）——因为 **MMA 减少了对累加器可用性的依赖，分摊了指令级延迟**；
- 当 P 增加到 3 时，吞吐量会下降——更深的计算流水线会增加“存活片段”（live fragment）和累加器寄存器的数量，可能降低线程束组（WG）的占用率，导致“延迟隐藏的边际收益”被“寄存器和共享内存压力”抵消。
:::

对比图 11 中的两个子图（持久化 vs 非持久化 GEMM），:mdnice-bold-italic[持久化版本的性能始终更快（在大多数可行点上约快 5-10%）：持久化使 CTA 驻留在 SM 上，从全局工作队列中拉取多个分块] ——这消除了网格调度（grid-scheduling）和尾部效应（tail effect），改善了权重和尾声元数据的缓存局部性，并减少了干扰，使 TMA 和 MMA 保持稳定的节奏。

> 综上，该实验表明：应选择较大的 D 和适中的 P（1-2），以平衡重叠效果与资源压力；同时使用持久化内核以稳定流水线，并获取缓存/复用收益。

### F. 消融实验

![文章插图](/articles/2025-10-22-tawa-gpu-warp-cublas-1-1022eb77/images/16.webp)

为进一步研究 TAWA 中不同优化技术的效果，我们在 GEMM 和 MHA 内核上进行了消融实验——采用之前实验中最大的内核配置（GEMM：$K=16384$；MHA：$L=16384$），结果如图 12 所示。

#### GEMM 消融结果

- **基线 Triton（无线程束专用，No WS）**：吞吐量仅为 104 TFLOPs/s；
- **启用线程束专用（+Auto WS）**：在保持相同分块配置的情况下，使用单个线程束组实现线程束专用，性能提升 3.78×，达到 393 TFLOPs/s。这一显著提升反映了:mdnice-bold-italic[“在线程束级解耦生产者与消费者角色”的效率——改善了并行性并缓解了流水线暂停；]
- **增大分块大小（+Large Tile Size）**：将线程束组数量扩展到 2 个后，寄存器压力降低，可启用更大的分块大小（从 128×128×64 调整为更大尺寸），性能进一步提升 1.46×。更大的分块形状改善了数据复用，减少了冗余内存流量，:mdnice-bold-italic[表明“分块策略与线程束专用”具有协同效应；]
- **启用持久化内核（+Persistent Kernel）**：线程块在多个迭代中驻留在 SM 上，避免了高昂的内核启动开销，改善了数据局部性，性能再提升 10%；
- **优化 aref 大小（+Better Aref Size）**：结合持久化调整调度深度参数，:mdnice-bold-italic[最终达到 718 TFLOPs/s 的峰值吞吐量——相对于基线提升近 7 倍。]

#### MHA 消融结果

- **启用线程束专用与协作线程束组（+Auto WS + Cooperative WGs）**：两者结合使性能提升 2.84×；
- **添加粗粒度流水线与优化 aref 大小**：:mdnice-bold-italic[最终性能达到 654 TFLOPs/s。]

> TAWA 通过精心整合“线程束专用”“协作线程束组”和“流水线”等优化技术，解锁了现代 GPU 硬件的更高利用率。

## 六、未来工作

> Tawa 的一个自然扩展方向是扩大编译器支持的通信模式范围。

目前，**Tawa 主要面向基于双缓冲构建的生产者-消费者流水线，但更先进的模式（如乒乓内核、多播通信）有望进一步提升效率**。

- 乒乓内核允许 warp 组在不同迭代轮次间交替角色，从而在计算和数据移动需求动态变化的场景中平衡工作负载并缓解瓶颈。
- 类似地，多播通信支持单个生产者 warp 同时向多个消费者 warp 分发数据，减少冗余内存传输并更充分地利用共享缓冲区。

展望未来，我们**计划将 Tawa 的适用范围从 Hopper 架构扩展到下一代架构** 如 Blackwell 架构[7]。具体而言，:mdnice-bold-italic[Blackwell 架构引入了张量内存（tmem，一种硬件管理的新型内存层级），它通过在共享内存与全局内存之间提供更灵活的数据编排能力来补充 TMA 的功能]。要有效利用 tmem，需要扩展异步引用（aref）以建模多级数据移动，并重新审视跨异构内存资源的调度决策。

此外，未来工作负载对可扩展性的要求将更高，这促使我们需要**支持多 warp 组的多生产者-多消费者模式，同时开发更复杂的图划分算法——该算法需同时考虑负载均衡、寄存器压力和内存占用**。通过整合这些扩展，Tawa 有望发展成为一个通用编译器框架，为连续多代 GPU 硬件提供 warp 专用化、异步化的 GPU 编程支持。

## 七、结论

> 本文提出了 Tawa——一款自动化编译器，它通过引入异步引用（asynchronous reference，aref）为现代 GPU 生成高效的 warp 专用化内核。

我们的评估结果表明，**在一系列基准测试中，Tawa 的性能可与高度优化的手写库相媲美，同时大幅降低了编程工作量**。

我们认为，这项工作为异步 GPU 编程提供了原则性的编译器支持，为未来研究下一代架构的高性能内核自动生成技术提供了启发。
