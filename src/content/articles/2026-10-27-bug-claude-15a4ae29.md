## 一、形式化验证给程序增加了一道数学检查

### 1.1 测试检查若干次执行，证明讨论一类执行

> 开发者在写单元测试时，通常会准备几个输入，再检查输出是否符合预期：

```
assert(decompress(compress(input)) == input);
```

这行代码表达了一条很直观的性质：一段数据经过压缩，再解压，应该恢复原样。测试框架可以选十组、一万组输入来运行它。模糊测试还会继续随机生成和变异输入，尽量碰到开发者没有想到的情况。

无论运行多少次，这些检查都只覆盖实际执行过的输入。:mdnice-bold-italic[形式化验证则把同一性质写成一个数学命题：在满足约定条件的所有输入上，压缩后再解压都等于原输入。证明需要给出严格推理，证明检查器再逐步核对这些推理。]

::: block-1形式化方法里的“规约”对应英文 Specification，指对程序行为或应满足性质的精确描述。它与 GPU 编程中的 reduction 无关，后者通常译为“归约”，是把多个数据通过加法、求最大值等操作合并成一个结果。比如“任意合法输入都不会造成越界访问”就是一条规约，它规定验证目标，本身不执行数据计算。
:::

> 这里出现了三个基本概念：

- **规约（Specification）**：用精确语言写出程序应该满足的性质，例如“不越界访问内存”“压缩和解压可以往返”“相同输入产生相同输出”。
- **程序语义（Semantics）**：用数学规则描述程序怎样执行。一条指令怎样修改寄存器，一次内存读取返回什么，系统调用失败时进程怎样变化，都要有定义。
- **证明（Proof）**：从程序语义和前提出发，推出程序满足规约的完整论证。

有了这三部分，证明工具才能回答一个明确问题：给定这套执行模型和这条规约，证明是否成立。

### 1.2 Rocq 负责检查证明，不负责判断需求是否合理

> Rocq[2] 原名 Coq，是交互式定理证明系统。**使用者可以用它定义数学对象、陈述定理并编写证明。Rocq 的 kernel 会检查证明中的推理步骤。** 这里的 kernel 指定理证明器内部负责检查证明项的核心组件，与 GPU 上执行的计算 kernel、Linux 操作系统 kernel 都没有关系。Claude 在这套流程中承担证明生成工作，最终能否通过由 Rocq 判断。

这个分工很像编译器检查类型。

- AI 可以生成一大段代码，编译器仍能独立判断类型是否匹配；
- AI 也可以生成很长的证明，Rocq 仍能独立检查证明是否推出目标定理。

**两者的差别在于，类型检查通常关注程序结构，形式化证明可以讨论更深的执行性质**。例如，某个指针在一条分支中是否仍然有效，一棵红黑树经过旋转后深度是否仍有上界，一段输入是否可能让计数器下溢。

Rocq 无法替开发者回答“需求有没有写对”。如果规约只要求程序不崩溃，一个返回错误结果但正常退出的程序也可能满足它。如果 Linux 进程模型漏掉了某种系统调用行为，证明也只能继承这个缺口。**因此，机器检查解决的是推理一致性，规约与真实世界的对应关系仍需单独审查。**

### 1.3 形式化验证过去贵在证明工程

> 形式化验证已经用于高价值系统。seL4 是一个开源操作系统微内核，主要面向对安全性和可靠性要求较高的设备。微内核只把进程调度、地址空间等最基础的机制留在操作系统核心，将驱动程序等更多服务放到核心之外运行，以缩小需要重点验证的部分。

seL4 的实现约投入 2 人年，形式化验证约投入 20 人年。成本来自多个环节：写出足够精确的规约，建立程序语义，设计不变量，处理大量分支，再在代码变化后维护证明。

::: block-1
**普通项目很难承担这类投入**。一个业务团队即使愿意验证核心库，也未必有熟悉程序逻辑、证明语言和验证工具的成员。:mdnice-highlight[Claude 实验瞄准的正是证明构造环节：把大量重复、漫长、需要不断试错的推理交给 Agent，再由机器检查最终结果。]
:::

## 二、Claude 把已有模糊测试变成了证明任务

### 2.1 OSS-Fuzz 已经提供了规约的起点

> Google 的 OSS-Fuzz[3] 为开源项目提供持续模糊测试。项目维护者会编写测试入口，接收模糊测试器生成的数据，并调用库中的功能。测试入口可能只检查程序是否崩溃，也可能加入更具体的断言。

![文章插图](/articles/2026-10-27-bug-claude-15a4ae29/images/03.jpg)

::: image-caption图 1：模糊测试执行路径示意图。图中把程序可能经历的执行过程画成迷宫，每条深色折线代表一次真实测试所走的路径。左侧计数器分别记录已尝试的输入数量和发现的崩溃数量，绿色对勾标记崩溃修复后的路径。右侧大片浅色区域没有被这些执行轨迹覆盖，用来呈现已测试路径与全部可能路径之间的视觉差别。（图片来源：LLMs are making formal software verification feasible at a much larger scale[4]，由原始演示视频截取）
:::

例如，LZO 是一个注重压缩与解压速度的实时无损压缩库，常用于需要快速处理数据的系统。它的压缩测试入口会先压缩输入，再解压结果，并断言两个操作都成功、解压后的长度与原始长度一致。Anthropic 公布的核心代码[5]如下：

```
r = lzo1x_1_compress(data, size, compressed, &compressed_len, wrkmem);assert(r == LZO_E_OK);decompressed_len = size + 1;r = lzo1x_decompress(compressed, compressed_len,                     decompressed, &decompressed_len, NULL, NULL);assert(r == LZO_E_OK && decompressed_len == size);
```

在模糊测试中，断言失败会触发 `abort`，测试工具就找到了一个异常输入。转换成证明任务后，目标变成：对所有规定范围内的输入，这些断言都不会失败。

这样做省去了从零编写完整功能规约的工作。维护者已经在测试入口中写下了一部分自己关心的性质，Claude 可以沿用这些性质。证明“不崩溃”也因此可能包含功能正确性：LZO 的例子就涉及压缩与解压能否正确往返。

### 2.2 ASan 把一部分内存错误转成可证明目标

> AddressSanitizer，简称 ASan，是编译期插桩工具。它会在内存访问附近加入检查，在发现越界、释放后使用等问题时报告错误并终止程序。

**模糊测试配合 ASan，可以把许多原本悄悄破坏内存的错误变成明显崩溃。** 形式化验证也可以利用这一点：如果插入 ASan 的程序对所有规定输入都不会触发错误，那么 ASan 能检测的那类内存问题也被排除。

ASan 并不能检测所有内存安全问题。证明覆盖的是它能检测的范围，以及测试入口实际执行到的代码。仅凭这项结果，还不能说整个库已经内存安全。

### 2.3 直接验证二进制，少了一层源码翻译假设

> Anthropic 没有先把 C/C++ 源码翻译成另一种便于验证的语言，而是将程序编译为静态链接的 RISC-V Linux 二进制，再对编译结果建模。

这个选择减少了“翻译后的程序与原程序不一致”的风险。源码分析工具可能按照自己的理解处理 C/C++，编译器却可能进行优化、插入运行时逻辑或选择不同的底层指令。直接验证二进制，可以把实际指令流纳入证明。

代价也很明显。开发者眼中的一次函数调用，到了指令层面会变成寄存器保存、栈地址计算、跳转和返回。证明还要覆盖 C 运行时初始化、内存分配器、测试驱动和 ASan 自身。几百行库代码背后，可能有数万条指令以及大量公共运行时逻辑。

形式化验证公司 Theorem 提供的 RISC-V 指令语义和 Linux 进程语义，为这些执行行为提供数学定义。Claude 根据二进制、执行语义和目标性质生成 Rocq 证明，Rocq 的证明检查 kernel 再检查证明是否真正推出了目标定理。完整流程可以概括为：

## 三、证明普通程序安全，需要跨过 ASan 插桩这道差别

### 3.1 只证明 ASan 版本还不够

> 用户实际运行的程序通常没有启用 ASan。只证明插桩版本不崩溃，不能直接推出普通版本也有同样表现。插桩会改变内存布局、指令数量和运行路径，某些错误在两个版本中的外在表现也可能不同。

这套验证将目标拆成三类相互衔接的结论：

1. ASan 插桩二进制不会发生故障、主动中止或未建模行为。
2. 普通二进制与插桩二进制在规定的可观察行为上等价。
3. 普通二进制本身也不会发生上述错误。

第三个结论不能省略。这里的行为等价主要比较输入输出、退出方式和文件系统最终状态。如果一个版本崩溃、另一个版本无限循环，二者的可观察轨迹仍可能在某段范围内看起来一致。单独证明普通版本不崩溃，可以堵住这个推理缺口。

### 3.2 行为等价只比较明确定义的外部表现

> 行为等价具体比较标准输入读取的字节、标准输出和标准错误写出的字节、退出码或终止信号，以及文件系统最终状态。证明讨论的是这些外部可观察结果，不涉及性能、执行耗时和内部每一个临时状态。

这种处理让定理可以落地，也提醒读者先看清“等价”具体指什么。两个程序可能有完全不同的内部实现，只要约定的外部行为一致，就可以满足这条定理。对验证 ASan 插桩是否改变程序结果来说，这种定义有实际用途；它并不能替代所有可能的等价性要求。

### 3.3 这些证明的保证带有明确条件

::: block-1
Anthropic 公布的 239 个测试入口结论涉及小于 64 MB 的输入，以及模型所覆盖的 Linux 响应和内存布局。程序被设定为单线程、静态链接、具有固定内存预算，并运行在 RISC-V Linux 环境中。
:::

公开证明语句还采用更细的条件。例如，普通版本需要在规定内存预算内运行；ASan 相关语句使用 2 GiB 预算，单独 UBSan 语句使用 16 GiB 预算。UBSan 是 UndefinedBehaviorSanitizer 的简称，它在程序中检查有符号整数溢出、非法移位等 C/C++ 未定义行为，发现问题后报告或终止程序。部分系统调用可以被环境拒绝，具体允许哪些失败会写进对应定理。

这些条件并非附带说明，它们直接决定结论覆盖哪些执行情况。把结论放到 x86-64、ARM、动态链接 glibc、多线程或不同内核行为下，需要相应的语义模型和新的证明，不能直接沿用。

## 四、不崩溃证明也能推出一些更深的功能性质

### 4.1 断言把程序意图接进定理

> “不崩溃”听起来只关心程序能否活着退出，实际覆盖范围取决于崩溃怎样定义。Anthropic 将断言失败、ASan 等检查工具的报告、未捕获异常和无效内存访问等纳入错误。维护者写进测试入口的断言因此成为证明目标的一部分。

除了 LZO 的往返性质，p11-kit 的配置词法分析器也提供了例子。p11-kit 是一个管理 PKCS #11 加密模块、证书和信任配置的软件组件，可帮助应用程序访问智能卡等加密硬件。它解析 PEM 数据块时会执行长度断言。PEM 是一种用 Base64 文本封装证书、密钥等二进制数据的格式，常见特征是内容首尾带有 `BEGIN` 和 `END` 标记。这里的断言要求数据块长度不能越过输入缓冲区末尾。证明该断言在所有覆盖输入上不会失败，就同时证明了一项具体的缓冲区长度关系。

这条路线适合已有良好测试断言的项目。断言越能表达程序意图，证明得到的功能性质就越有内容。反过来，一个只调用函数、从不检查结果的测试入口，即使证明不崩溃，也主要提供安全性质，不能说明输出正确。

### 4.2 证明过程会迫使 Agent 处理底层数据结构的性质

> cpp-httplib 是一个仅由头文件组成的 C++ HTTP 客户端与服务器库，开发者可以直接把它加入项目，用来处理 HTTP 请求和响应。它的案例更能说明证明会怎样向底层扩展。

为了排除 `std::set` 析构时的栈溢出，Claude 需要限制递归深度。`std::set` 是 C++ 标准库中的有序集合容器，libc++ 则用红黑树实现它。递归深度取决于树高，于是证明一路落到红黑树再平衡算法：插入和删除后的调整必须让树高保持在对数范围内，避免树退化成一条长链。

这类性质并没有直接写在最初的“不崩溃”目标里，却是完成目标所必需的中间结论。形式化证明经常以这种方式迫使开发者补齐隐含假设。一个看似局部的安全问题，可能依赖容器不变量、整数范围、内存布局或调用约定。

## 五、Python 解释器实验展示了另一条验证路线

### 5.1 从二进制证明转向带契约的 Rust 源码

> Anthropic 还让 Claude 用 safe Rust 开发一个 Python 子集解释器，并用 Verus[7] 做验证。Verus 是一个面向 Rust 代码的形式化验证工具。开发者可以用 `requires` 写明函数调用前必须满足的条件，用 `ensures` 写明函数返回后应当成立的结果，再补充循环不变量。Verus 将这些契约和代码交给 Z3 SMT 求解器，自动检查是否存在违反契约的执行。

这里的基本工具从 Rocq 和机器指令语义，换成 Verus、Rust 源码契约和自动求解。开发者可以围绕函数前置条件、后置条件和循环不变量组织证明，抽象层次更接近日常源码。

Claude 按 17 个层级逐步实现解释器，并证明：只要解释器返回结果，该结果就符合所采用的形式语义。所有层级的 Verus 定理都通过检查。

### 5.2 形式语义与 CPython 之间仍靠实测连接

> 解释器实验采用了基于 λπ 核心语言的 Python 形式语义。实现与这套语义之间由证明连接；这套语义与真实 CPython 之间，则通过运行测试建立经验上的对应关系。

团队运行了超过 170 万个以随机生成为主的 Python 程序，观察到 99.95% 的测试与 CPython 行为一致，其余差异属于已知的角落情况。在同一实验中，团队向早期实现故意注入 7 个 Bug，其中 5 个逃过随机测试，7 个都破坏了证明。

这组结果同时展示了两类工具的作用。测试可以检查形式语义与 CPython 的大量实际行为是否一致；证明可以约束解释器实现与形式语义的关系。99.95% 是测试结果，不能改写成“解释器与 CPython 已有 99.95% 的形式化等价证明”。两者需要分开理解。

## 六、证明规模展示了自动化能力，也暴露了抽象不足

### 6.1 约 10 亿行尝试中，约 1.8 亿行进入最终证明

> Claude 在整个 OSS-Fuzz 证明项目中累计生成约 10 亿行 Rocq 代码，其中约 1.8 亿行成为通过检查的最终证明。这两个数字描述了不同阶段，不能混在一起。前者包含探索和失败尝试，后者才是最终有效成果。

在这批任务中，典型测试入口背后的库代码只有几百行，编译后约 2000 条 RISC-V 指令；完成后的证明却可能达到约 60 万行，分布在约 1400 个文件中。239 个入口所对应二进制的中位规模为 18000 条指令，典型证明约 60 万行。

证明膨胀的原因在于目标覆盖整个进程。库代码之外，C 启动过程、libc 分配器、`printf`、ASan 运行时和模糊测试驱动都可能进入执行路径。当前流程还难以把每个公共部分证明一次后到处复用，许多任务会重新处理相似内容。

**以 cJSON 为例，391 行解析入口对应约 63 万行证明，其中只有约十分之一的证明行直接涉及 cJSON。** fftw3 链接了约 51000 行代码，最终证明约 48 万行。证明长度与被测库自身规模没有简单的线性关系。

### 6.2 Claude 的证明能过检查，但写得很啰嗦

> 人类证明工程师通常会尽早建立抽象。例如，把函数调用约定总结成一条可复用规则，把互不重叠的内存区域封装成分离逻辑命题，把分配器行为隐藏在接口定理后面。之后遇到相同结构，就可以直接引用。

Claude 经常逐项展开寄存器内容、整数转换、地址互异关系、栈地址和程序分支。Agent 也构造过类似分离逻辑 framing rule 的抽象，并对内存分配器做过抽象，但并非所有 Agent 都会使用，缩短证明的效果也有限。

证明冗长不影响 Rocq 对定理的检查，却会影响生成成本、检查时间、复用和后续维护。从证明构成看，超过一半证明行由 Claude 自己编写的工具生成，例如指令编码和查找表；约四成是定义、机器模型、引理和证明步骤等文本。单个证明的检查可能需要 30 分钟到数小时 CPU 时间。

这说明当前瓶颈已经部分转移到证明工程方法：Agent 不只生产更多证明，还要学会建立更好的模块边界和抽象，否则复杂程序可能带来难以承受的组合膨胀。

### 6.3 模型效率和证明复用已经降低成本

> Anthropic 从真实 OSS-Fuzz 代码中缩小出 36 个任务，限制输入为 64 字节，并用精简 libc 和 mini-ASan 降低公共运行时规模。**每个任务在 500 万 Token 预算内进行三次独立单 Agent 尝试。**

Opus 5.5 完成其中一半任务时，所需 Token 比 Opus 5 少约 40%。

共享工作区实验则允许多个 Agent 复制和修改彼此的证明，平均 Token 消耗下降约 17%。34 个已完成任务中，有 30 个的共享成本低于独立工作的平均成本，另有两个任务只有共享条件下才完成。

**复用之所以有效，是因为不同程序共享大量运行时证明。** 一个团队完成 C 初始化或 ASan 相关证明后，另一个团队可以复制并适配，无须从零推导。长期看，证明库可能像普通依赖库一样积累：公共组件被反复使用，新任务只处理项目特有部分。

## 七、公开仓库让证明可以复查，也标出了尚未覆盖的部分

### 7.1 合作结果与公开仓库数字属于不同范围

> Anthropic 报告了整个合作项目在几周内的结果：123 个库、239 个测试入口、约 1.8 亿行最终 Rocq 证明。开源项目 theorem-labs/oss-verify-proofs[10]在 2026 年 10 月 25 日读取到的 README 显示，当前公开了 25 个库中 60 个测试入口的证明，使用 Rocq 9.2.0 检查。

同一仓库还列出 20164 条证明语句，其中 138 条状态为已证明。这里的“语句”包括 ASan、UBSan 等不同检查版本的定理，以及普通版本能否停止等其他定理，不能与“测试入口”直接比较。公开仓库是整个成果的子集；涉及尚未修复漏洞的证明也可能暂不发布。两组数字描述的对象和时间不同，不需要强行对齐。

公开仓库的证明检查文档[11]提供了复查路径。`oft check` 会校验二进制 SHA-256，生成内存镜像和定理语句，编译证明，再检查最终定理是否具有目标语句所要求的类型，并通过 `Print Assumptions` 排查不允许的公理。CI 会在提交和每周任务中重新检查。

### 7.2 信任没有消失，而是集中到了少数组件

> 采用机器检查证明后，使用者不必逐行阅读 1.8 亿行证明，但仍要信任若干基础组件：

- Rocq 的证明检查 kernel，以及证明允许使用的公理；
- RISC-V 指令和 Linux 进程的形式语义；
- 把 ELF 二进制转换为形式化内存镜像的工具；
- 定理语句本身是否表达了想要的性质；
- 检查脚本、运行检查所用的编译器和底层硬件、操作系统。

**这套方法把审查对象从每个项目的大量执行细节，收缩到可以跨项目复用的基础设施。** 基础设施一旦有错，可能影响许多证明，所以仍需独立验证和持续审计。Anthropic 也明确提醒，硬件、操作系统和 Rocq 所依赖的 OCaml 编译器等技术组件同样处在信任链上。

公开仓库 theorem-labs/oss-verify-proofs 的语义说明[12]尤其强调 LPS，即 Linux 进程语义模型，目前仍是尽力而为且不完整的模型。它只描述 Linux 的一部分，并包含一些未由模型自行检查的假设。证明成立以 LPS 准确为前提。

### 7.3 当前公开证明明确排除了几类过度解读

> 仓库文档逐项列出了证明没有表达的内容：

- 没有证明整个库功能正确，错误结果和内存泄漏可能仍存在；
- 只覆盖某个测试入口能够到达的代码，未触达代码和死代码不在其中；
- 针对特定静态 riscv64 二进制，不直接覆盖 x86-64 构建；
- 结论位于 LPS 模型内，模型与真实 Linux 的差异可能限制现实适用性；
- 当前“行为一致”类定理不排除程序永不结束，仓库此版本没有证明任何 halts 语句。

![文章插图](/articles/2026-10-27-bug-claude-15a4ae29/images/07.jpg)

::: image-caption图 3：形式化证明覆盖路径示意图。绿色线路从左侧入口向外展开，表示已经纳入证明并通过机器检查的执行区域；红色圆点标记证明过程中暴露的问题，带对勾的绿色圆点表示修复后重新检查的位置。右侧仍为浅灰色的区域标有“无法从该入口到达”，说明图中覆盖范围按入口可达性划分，而非按整个程序的面积计算。（图片来源：LLMs are making formal software verification feasible at a much larger scale，由原始演示视频截取）

**这些限制也解释了“形式化验证”和“软件没有 Bug”之间的距离。** 准确的说法应该落到具体对象、具体环境和具体性质上，例如：“在这个 RISC-V 二进制、这个测试入口、这组输入和内存条件下，不存在导致所定义错误的执行。”

## 八、发现 Bug 与完成证明是同一过程的两个结果

> 证明失败有时意味着证明能力不足，有时意味着程序真的存在反例。Agent 在推导过程中需要检查每个分支，因此可能走到模糊测试很难到达的状态组合。

Anthropic 公布的例子包括：一个解压缩程序中的计数器下溢会导致越界写入，触发条件要求约 20 MB 输入和罕见的数据布局；一个图像解码器需要 64 MB 输入和超过 2 GB 内存才会越界读取；另一个库需要跨两个文件句柄进行特定调用序列；libexpat 中的 CVE-2026-56132 则需要深度嵌套输入。

常见模糊测试器倾向于变异较小输入，通常上限约 1 MB，并依赖覆盖率引导。面对上述条件，盲目生成输入很难同时满足大小、布局和状态序列。证明则从符号约束出发，可以推导出“若要到达这里，输入必须满足什么”，再暴露不可能满足的安全假设。

Claude 还被允许在发现 Bug 后修改程序，再基于修改后的二进制重新生成规约并继续证明。这带来了 reward hacking 风险：Agent 可能删除功能、拒绝所有输入，或者把程序改成一个很容易证明却不完成原任务的版本。

> 为此，团队采取了对代码修改施加惩罚、鼓励说明输入行为变化、记录并审计补丁等措施。**对实际开发流程来说，这一环仍需要人工审查。** 证明可以验证修改后的程序满足某条规约，不能独自决定这次修改是否保留了产品需要的功能。

即使最终证明没有完成，寻找反例和补充中间引理的过程也可能发现真实问题。Anthropic 报告了一个潜伏超过十年的逻辑漏洞，还称在某个广泛使用的 PDF 阅读器上，一周发现的安全 Bug 数量相当于通常一年报告的数量。由于 Anthropic 尚未公开该阅读器名称和完整漏洞清单，这些结果的具体影响还需等待后续披露。

## 九、普通开发团队可以从关键性质开始尝试

### 9.1 解析器和编解码器适合作为起点

> 这类组件通常有清晰输入、相对集中的状态和可以自动检查的性质。例如：

- 任意输入都不能导致越界访问；
- 压缩后解压必须还原输入；
- 编码后解码必须恢复原对象；
- 对同一数据重复规范化，结果应该保持一致；
- 两种实现处理相同输入时，输出应该一致；
- 解析失败必须返回错误，不能进入未定义状态。

**团队可以先保留现有模糊测试入口，把断言写得更完整，再尝试将入口转换为形式化目标**。这样既能复用已有工程，也能避免一开始就为整个系统写完整规约。

### 9.2 验证范围应该围绕风险逐步扩大

::: block-1一个可执行的推进顺序是：先验证纯函数和小型库，再覆盖解析入口与关键数据结构，随后处理内存管理、系统调用和并发。每扩大一次范围，都要检查执行语义、环境假设和验证成本是否跟得上。
:::

如果项目使用 Rust，可以评估 Verus 等源码级工具；如果已有复杂 C/C++ 二进制和 OSS-Fuzz 入口，可以关注 Theorem 的二进制级路线；如果目标是算法或数学性质，Lean、Rocq 及其现有证明库可能更合适。工具选择取决于待验证程序、性质和团队已有技术栈。

AI 可以协助写规约草案、循环不变量、辅助引理和证明脚本，也可以根据检查器反馈迭代。**最终仍要把规约、环境假设和代码修改交给熟悉系统的人审查。证明检查器能过滤大量错误推理，却无法替团队决定安全需求。**

### 9.3 证明复用决定它能否成为日常基础设施

> 单次证明的成本仍然很高。只有公共运行时、通用数据结构、指令语义和常用引理能够持续复用，后续项目才可能摊薄投入。共享工作区减少 17% Token 的实验只是早期结果，**更长期的考验是代码升级后证明能否局部修复，以及证明库能否像普通软件依赖一样版本化。**

如果每次代码变化都要重新生成几十万行证明，实际团队很难长期使用。如果关键组件的证明可以稳定复用，验证就可能逐步接入持续集成：提交代码后自动检查受影响定理，失败时返回反例或证明缺口。

## 十、Claude 降低了写证明的门槛，正确性仍要从规约开始

> 这组实验把几件原本分散的事情连了起来：真实开源项目已经有模糊测试入口，ASan 能把内存错误转成明确失败，编译器能生成可执行二进制，形式语义能解释指令和进程，Claude 能生成大规模证明，Rocq 能独立检查证明。**连接之后，一部分过去需要专家长期完成的工作开始具备自动化条件**。

它也把一个老问题重新推到台前：软件究竟要证明什么。

- 规约太弱，证明再长也只能提供有限保证；
- 语义偏离真实环境，结论就可能无法覆盖实际部署；
- 测试入口没有触达某段代码，那段代码也不会因为其他入口通过证明而变得可靠。

::: block-1因此，阅读这类成果时，最值得关注的既有 239 个入口和 1.8 亿行证明，也有每个定理前面的条件。Claude 已经展示了生成证明的规模和发现深层 Bug 的能力。:mdnice-highlight[形式化验证要进入更多项目，接下来还需把规约写得更准确，把公共证明组织成可复用组件，并让验证结果能随着代码演进长期维护。]
:::
