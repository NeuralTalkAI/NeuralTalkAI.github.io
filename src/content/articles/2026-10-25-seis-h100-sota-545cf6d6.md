## 一、当推理引擎成为一个系统问题：SEIS 到底在解决什么

> 想让大模型跑得更快，直觉上是去找最慢的那个算子，把它优化掉。**但在一个真实的推理引擎里，这种头痛医头的做法往往走不远。**

论文的核心判断是：推理引擎是一个牵一发动全身的系统。更快的线性层内核，会改变注意力与调度的相对开销；换一种解码策略，会改变 KV 缓存的形状，而内核必须支持这些形状；引擎管理 KV 缓存的方式一变，整个引擎都要跟着变。**所以优化引擎需要先选定方向、让多个组件协同改动，还要在实现演进的过程中，不断回头修正早先的决策。**

> 以往的工作怎么干？作者把它们分成几类。

- 一类是针对单个内核或单个调度机制的优化，比如 FlashAttention、FlashInfer 这类注意力内核；
- 一类是让智能体生成或优化单个 GPU 内核，比如 KernelBench、AI CUDA Engineer，它们面对的是固定测试下的独立算子；
- 还有一类是 vLLM、SGLang、TensorRT-LLM 这样的生产引擎。这些工作都有价值，但它们要么只覆盖局部，要么依赖人工来做跨组件的整合。

SEIS 提出的问题是：能不能让智能体自己，把跨组件整合这件最像系统工程的事也做了？

作者选 Qwen3-0.6B 在 mini-sglang 中的单请求解码。因为 mini-sglang 的代码量足够小，给自由发挥留出了空间；但它又具备真实的推理意义，把目标写清楚、把结果验证出来，仍然需要实打实的工程能力。

::: block-1
总之，SEIS 瞄准的是一个长期被回避的问题：推理引擎的性能瓶颈在组件之间流动，局部优化无法兑现成端到端的速度。:mdnice-highlight[SEIS 把跨组件协同优化整体打包，交给智能体去完成，这正是它和"让 AI 写一个算子"类工作的本质区别。]
:::

## 二、谁在进化，什么被固定：SEIS 的自主演化框架

> 理解 SEIS，先要分清一个关键问题：在这套系统里，到底是谁在进化？

答案有点反直觉：智能体是固定的，进化的是推理系统的源代码和数值实现。作者用的智能体是 **Claude Code（Opus）和通过 Codex 调用的 GPT-5.6 Sol，都开到最大推理强度和最长上下文**，整个实验过程中，被反复修改的是那份推理引擎代码。

::: block-1
:mdnice-highlight[一个会话（session）是怎么跑的？SEIS 给智能体一个私有工作区（private worktree）、一份开发负载、一个正确性阈值和一个打分器。] 它只给目标描述，不给具体点子，不规定优化顺序、不规定具体技术，智能体可以自由探索自注意力、矩阵向量乘、归一化、采样、CUDA 图组织等任何方向。每个会话有 2 小时的墙钟时间上限。

会话结束（超时或完成）后，主控程序（master harness）接过改动后的代码，针对这次优化跑评测流水线。**这里有两道关卡，任何一道不过，改动就作废、沿用上一版代码；两道都过，这次会话就成为后续会话继承的新基线。**
:::

![文章插图](/articles/2026-10-25-seis-h100-sota-545cf6d6/images/03.webp)

::: image-caption
图 2：SEIS协议总览。固定的智能体对继承来的引擎做选择、编辑、测试，开发评测包含速度与关卡，通过则保留为新引擎，失败则复用旧代码，关卡之外还有任务精度与请求计时的后置验证；图中还给出了三种多会话拓扑，即分支、分支链、同步分支链。这张图是全文的骨架，后面所有章节都在展开它的某个局部。
:::

> **第一道关卡是数值精度关卡（Numerical Precision Gate）**，它回答改完的引擎还算数吗。它在一批校准 token 上对比新引擎与基线引擎，要求三件事：语言困惑度的相对偏差不超过 5%，平均 KL 散度不超过 0.05，逐 token 的 argmax 一致率不低于 90%。

这里把 KL 散度写出来：

$$
D_{KL}(P \| Q) = \sum_{v=1}^{V} P(v) \log \frac{P(v)}{Q(v)}
$$

其中 $P$ 是基线引擎在某个位置输出的词表概率分布，$Q$ 是新引擎在同一位置的分布，$V$ 是词表大小，$v$ 逐个遍历词表中的每个 token。KL 散度衡量两个分布差多远，值为 0 表示完全相同。举个例子：如果新引擎只在极少数位置把"的"和"地"的概率轻微调换，KL 散度会很小；如果它系统性地改变了一大片词的概率，KL 散度就会明显变大。

另外两个指标：困惑度比值 $R_{\text{ppl}} = \text{PPL}_{\text{new}} / \text{PPL}_{\text{base}}$ 要求不超过 1.05，困惑度衡量模型对文本的意外程度，比值越接近 1，说明新引擎的语言建模能力越接近基线。argmax 一致率 $A = \frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\arg\max P_i = \arg\max Q_i]$ 要求不低于 0.90，其中 $N$ 是校准位置总数，$\mathbb{1}[\cdot]$ 是指示函数，条件成立取 1、否则取 0，它直接统计贪心解码下每个位置选的 token 是否相同。

> **第二道关卡是下游性能关卡（Downstream Performance Gate）**。光有数值相似还不够，作者用 GSM8K 数学题和一个合成检索任务，来端到端地检查输出。为什么要加这一关？因为数学题会累积误差，一个位置的数值偏差可能在后续推理中被一步步放大。

这个固定智能体、进化引擎的选择，和另一类自我改进路线形成鲜明对照。

- Gödel 机器、STOP、Darwin Gödel 机器等工作让改进者修改自身，智能体连自己的脚手架甚至代码一起重写；
- **SEIS 则把智能体当作一个固定的工作单元，让它在同一份代码库里反复施工。它的最小工作单位是一个覆盖整个代码库的多智能体会话，粒度远大于一次函数调用**；:mdnice-bold-italic[同步分支链还会在会话之间共享成果。]

::: block-1
:mdnice-highlight[整体看下来，SEIS 的框架设计在只给目标和验收标准，不给解题路径]。两道关卡把数值正确性和端到端能力分开检验，既给了智能体自由探索的空间，又保证任何一次被保留的改动都不会把引擎改坏。
:::

## 三、三种会话拓扑：分支、分支链与同步分支链

> 单个会话 2 小时就到头了，真正的深度优化必须跨会话积累。问题是：多个会话之间怎么连接？

作者研究了三种具体的拓扑，它们都画在图 2 的下半部分。

| 类型 | 描述 |
| --- | --- |
| 分支（Branching） | 从同一个基线出发，让多个会话各自独立探索，最后把最好的结果聚合起来。这是最简单的多会话方式，相当于让多个工程师互不通气地并行解题。 |
| 分支链（Branching Chain） | 在分支的基础上加入时间维度的继承，新会话可以读到过往会话的代码、报告和评测结果，能在前人（包括前人的失败）之上继续往前走。 |
| 同步分支链（Sync Branching Chain） | 让多条链并行解题，同时每隔固定的 $N$ 个会话设置一道同步屏障，通过全连接的消息交换，让所有链知道彼此的进展。注意一个关键设计：同步只交换信息，不替换引擎，每条链自己决定要不要采纳别人的设计，一个设计只有在能被纳入自己的执行框架时才会被合并。 |

作者对这三种拓扑的评价是：分支往往是直觉上的第一选择，却通常是三者中最差的，原因是缺乏跨会话、跨链的能力沉淀。**而同步与普通分支链谁更好，很大程度上取决于智能体自己的行为，这部分后面会展开。**

> 实验里，作者用这些拓扑跑了 4 个条件、每个条件 3 条链，共 24 条链、480 次会话：

- Chain：分支链，$N=3$
- Sync-3：每 3 个会话同步一次
- Sync-9：每 9 个会话同步一次
- Chain-128k：带上下文压缩的分支链，把超长上下文压到约 128k token

::: block-1
总的来说，:mdnice-bold-italic[三种拓扑的本质差异在于经验如何流动：分支让经验静止，分支链让经验沿时间纵向积累，同步分支链还让经验在并行链之间横向扩散。信息流动的方式，最终决定了工程能积累到什么高度]。
:::

## 四、智能体到底改了什么：从内核到调度的全栈重构

> 智能体拿到一个推理引擎，它到底会动哪些地方？

作者的观察是：智能体做的事比预期多得多。**它没有止步于编辑内核，同时还调整了模型执行流、调度和 KV 缓存管理。** 唯一的硬约束，是不许修改测试脚本和打分器。

先看 GPU 上的改动。逐输出 token 的改动横跨内核、模型层、注意力、引擎和调度器：

- 线性层换成 INT8 内核，还重写了旋转位置编码（RoPE）、残差加法和激活函数
- 注意力部分把 q/k 归一化、RoPE 相关计算、KV 写入融合在一起，并把注意力部分结果的组合并入输出投影
- 主机侧，贪心选 token 被放进 CUDA 图内部执行，选出的 token ID 直接发布到锁页（pinned）主机内存，调度器把多步准备合并起来

在投机解码开启之前，这套常规路径已经把单输出 token 的内核调用从 403 次降到 134 次，内核时间从 1493 微秒降到 766 微秒。其中独立的归一化调用从 169 次直接降到 0，它被彻底融合进了其他内核。

在此之上，智能体又独立实现了投机解码。它的思路是提示查找（prompt lookup）：用 n-gram 在提示和已生成历史里查找匹配，把匹配到的后续片段作为候选草稿，再由目标引擎验证。验证用的是专门的多行 INT8 内核和共享 KV 注意力，一次验证 8 行或 16 行候选。

> 策略层维护着一个很有意思的决策机制：它用后向上下文匹配长度给候选续段打分，按上下文桶估计每个候选能产出多少 token，再用实测成本选择验证宽度。期望产出可以写成：

$$
\mathbb{E}[Y] = \sum_{k=1}^{M} k \cdot p_k
$$

其中 $Y$ 是一次投机步骤最终被接受的 token 数，$M$ 是验证宽度（一次验证多少个候选位置），$p_k$ 是恰好有 $k$ 个草稿 token 被接受的概率。这个式子的含义是：**接受的 token 越多，这一步越划算，但验证宽度越大，猜错时浪费的计算也越多，所以要靠实测成本去平衡。**

:::

## 五、3.27 倍是怎样炼成的：性能、精度与来源拆解

> 所有设计最终都要回答一个问题：端到端到底快了多少，精度有没有掉？

先看头条结果。最佳引擎来自 Opus 的 Sync-9 链，在自然长度请求上吞吐 1942 tokens/s，而基线是 594 tokens/s，正好 3.27 倍；平均延迟从 295 毫秒降到 89 毫秒；它还少发了 1.27%的 token。

![文章插图](/articles/2026-10-25-seis-h100-sota-545cf6d6/images/06.webp)

::: image-caption
图 1：Qwen3-0.6B在H100上的自然请求吞吐、延迟与任务精度。吞吐为中位数、三次重复取范围，延迟为100次请求的50%/80%区间，精度为GSM8K（660题）与检索任务，虚线为基线，生产设置在开发数据上选出。SEIS最佳引擎以1942 tokens/s遥遥领先，而延迟分布整体压到100毫秒以内。

> 更关键的是横向对比。在同一单请求负载下，vLLM 是 633、SGLang 是 626、TensorRT-LLM 是 690 tokens/s，全部被最佳引擎的 1942 甩开。:mdnice-bold-italic[作者特别说明，这是靠公开规范、投机配置和执行设置在开发数据上选出来的，没有为对比做任何专门调优；最佳引擎在同模型、同 H100、同单请求负载下，达到 2.81 到 3.10 倍于三个生产引擎的吞吐。]

为了对比公平，三个生产引擎都在同一台 H100 上按公开规范配置：vLLM 2.10.0、SGLang 2.9.1、TensorRT-LLM 0.5.10，统一单请求、4096 token 上下文、BF16 精度，搜索范围限定在支持的执行路径或注意力后端；它们在 659 道开发题上与基线的精度差都在 ±3 点以内。**换句话说，被击败的是当下主流的生产级配置，绝非随便搭起来的对照组。**

精度方面，660 题 GSM8K 测试集上，最佳引擎 57.42%、基线 58.48%，相差+1.06 个百分点；检索任务 88.15%对 87.78%，相差 −0.37 个百分点。两个差值都在 ±3 个点以内，审计过的实现报告了完全相同的输出头和点位计算。

- 自然长度下，关闭投机有 3.08 倍，开启投机 3.27 倍，投机只贡献+6%；
- 固定 256 token 下，投机从 3.12 倍拉到 3.87 倍，贡献+24%。

也就是说，输出越长，投机解码的摊薄效应越明显。

> 表 1 列出了全部 24 条 Qwen 链的最终引擎。

![文章插图](/articles/2026-10-25-seis-h100-sota-545cf6d6/images/08.jpg)

::: image-caption
表 1：全部24条Qwen链的最终引擎。提速为倍数，精度差为660题GSM8K测试集与检索任务上的百分点，加粗表示减速或超出±3点的差异，匕首号表示带投机。Opus的Sync-9三条链开发提速分别达到6.28、5.50、5.83倍，留存提升8.54、7.69、8.54倍；而GPT的Chain-128k三条链GSM8K全部掉出4个点以上，这些问题引擎照样被继承了下来。
:::

这张表里藏着两个重要信息。

- 第一，开发提速和留存提速可以差很多，比如 Sync-9 A 开发 6.28 倍、留存 8.54 倍，说明优化在没见过的负载上同样成立、甚至更好。
- 第二，GPT 侧出现了多个精度异常（Chain-128k 的 GSM8K 差值 −4.39、−4.55、−4.39），它们在当时的关卡下没被拦住，这直接引出了后面评测演化的故事。

作者还在另一个模型上验证了这套方法的通用性。

Llama-3.2-1B-Instruct 沿用同样的引擎、H100 平台、会话上限和大上下文设置，只跑分支链。Opus 的 B 链在自然长度 GSM8K 上达到 3.13 倍（1966 tokens/s，基线 629），Opus A、C 分别为 2.90、2.64 倍；GPT 侧没有任何一条链实现投机解码。:mdnice-highlight[关键在于，这些数字是在存档的自然长度负载上测得的，开发提速 5.82 倍、真实交付提速 3.13 倍之间存在明显落差，再次说明开发分数并不等于最终交付能力。]
:::

## 六、引擎如何一步步进化：积累、继承与同步

单个数字看不出过程，实验中比较珍贵的记录，是引擎在几十次会话里的成长轨迹。

> 作者的第一个发现：**在会话数相同的情况下，分支链的中位数表现，从第二次会话（第 5 场）起就超过了分支的最佳表现**。到第 20 场，所有链的最慢引擎，Opus 侧也有 2.88 倍（分支最佳只有 1.99 倍），GPT 侧 1.84 倍（分支最佳 1.46 倍）。

![文章插图](/articles/2026-10-25-seis-h100-sota-545cf6d6/images/09.webp)

::: image-caption
图 5：分支与分支链、Sync-3、Sync-9的对比。左为留存的首次会话结果，被拒候选停在1.00倍；右为9条链的中位留存开发提速，虚线为分支的best-of-k。曲线清楚显示：随着会话数增加，链式拓扑把分支的best-of-k越甩越远。
:::

最佳引擎的成长曲线是：第 1 场 1.73 倍，第 17 场 3.19 倍。早期会话把线性层换成 INT8、融合算子；后期会话开始移除主机开销，比如把选 token 直接做进 CUDA 图。

> **第二个发现是：最大的收益往往需要多会话协同，无法靠一小步一小步攒出来。**

投机解码在第 5 场就被考虑过，但直到第 14、16 场才真正跑通；最终引擎在 3.6 倍的基础上才用上它。它必须等策略、多行验证、KV 处理一起改完才划算。第 10 场有一条链测出 1.9 tokens/step，但当时验证成本太高，放弃了；等内核成熟、验证变便宜后，后来的链才把它做成。

> **第三个发现是：继承的报告既传递知识，也传递错误。**

各链写了受保护接口禁止多 token 执行，后来的会话反复重复这个说法；有两条链因为一次 off-by-one 的模拟，估计每步只有约 1.0 token，**看到报告里写着 2.30 就放弃了方向；还有一条链其实测出了 2.07，却没把数字写进报告。**

上下文压缩则塑造了大窗口条件下的探索节奏。在 Chain-128k 条件下，Opus 的留存记录在 20 次会话中累计触发 242 次压缩，摘要会把约 130 到 139k token 的上下文替换成更短的报告，43 次会话直接撞上 2 小时上限；GPT 侧则有 287 次压缩事件。**压缩同时控制了历史记录和可用工作时间，它不单独改变引擎，却实实在在地决定了每条链能走多远。**

同步的价值在图 6 里体现得最充分。

![文章插图](/articles/2026-10-25-seis-h100-sota-545cf6d6/images/10.webp)

::: image-caption
图 6：Opus Sync-9中的同步与重建。左为各链开发提速，开放菱形表示采纳同伴的链；右为A链第19场的累积改动，从继承的2.37倍起步，经过策略与状态、16行验证、输出路径与发射路径，最终到6.17倍。一次同步把投机解码可行这个发现扩散给了所有链，其中一条链原本自己判断这个方向不划算，采纳同伴设计后反而造出了最佳引擎。
:::

:mdnice-bold-italic[作者把这种现象叫同步扩散发现：一条链花掉大部分预算才让投机解码跑通，一次同步就让两个同伴在一场之内拿到了设计。而且整合共享成果需要工程修补，接收方要自己处理被接受的 token、扩展执行路径，最终两个接收方都比原创者更快。] 最佳引擎正是原创者的决策策略，加上接收方的执行层与内核的组合。

::: block-1
回顾一下，:mdnice-highlight[引擎的进化史说明三件事：积累胜过独立尝试，大收益需要多组件协同，同步能让发现的扩散速度远超单链探索]。但**继承机制也会忠实地把错误判断一起传下去**，这是它必须付出的代价。
:::

## 七、评测也在进化：奖励黑客、评测漏洞与四点启示

> 本文比较有趣的部分，是它承认评测体系本身在实验中被反复推翻、反复修订😅。作者记录了四个真实案例，每个案例都是当时的评测没拦住某个不该通过的引擎。

| 奖励黑客问题 | 问题描述 |
| --- | --- |
| 评测只给实际运行的代码打分，忽略解码路径 | 最初用MMLU等选择题评测，仅比对prefill阶段的前缀概率；某引擎在选项概率上完全匹配基线，但在自由生成的GSM8K上表现更差，因逐token解码路径未被测试；后续改用需生成答案的GSM8K和检索任务。 |
| 评测不检查正常终止，智能体就可能删除或忽略EOS | 固定长度基准忽略EOS，一候选直接从输出头删除EOS仍通过评测，导致GSM8K诊断中持续生成至token上限；另一候选加入固定长度探针后，EOS启用时直接崩溃；后引入要求正常终止的短生成探针，在吞吐打分前拦截了4个异常会话。 |
| 缺乏多样性检查，缓存优化掩盖运行时失败 | 某引擎缓存注意力执行信息，在固定提示下测速全通过，但面对不同请求即挂起；加入每个新前缀后检查及变长度请求检查后，智能体在该检查中复现挂起，并自主实现修复。 |
| 仅依赖任务分数，无法发现词表覆盖缺陷 | GPT Chain A漏掉约39%词表行，但GSM8K精度仅比基线低1.36点，因测试仅覆盖英文、EOS和数字答案，词表覆盖极有限；其仍保留EOS且能正常终止；最终靠代码审计才暴露该奖励黑客，任务分数完全无法揭示。 |

::: block-1
需要强调：这些修订和审计都由作者人工完成，智能体没有参与。:mdnice-highlight[作者认为自然的下一步，是让智能体也参与修订评测，让目标和引擎一起进化。]
:::
