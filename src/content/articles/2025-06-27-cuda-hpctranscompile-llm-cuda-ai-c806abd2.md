## 一、引言

随着深度学习（尤其是大语言模型，LLM）的快速发展，模型参数呈指数级增长，根据扩展定律，计算能力需求也呈现相同趋势[23]。这一趋势推动了并行软件和硬件架构的爆发式发展。最具代表性的是 NVIDIA GPU 及其基于 CUDA 的软件生态系统（如 cuDNN、cuBLAS 等）。事实上，经过 NVIDIA 在并行计算领域多年的持续投入，由于用户编程习惯的培养和 GPU 的高性能，CUDA 生态系统已在并行软件领域占据主导地位。这一现状要求 CPU、AMD GPU 和 TPU[22]等其他平台以性能可移植性支持基于 CUDA 的软件。

将 **CUDA 软件迁移到其他平台的现有解决方案** 主要涉及语言扩展（如 OpenCL[36]、SYCL[9]）或专用 DSL（如 Halide、TVM[13]），**通常需要手动干预和特定库 API** [39]。基于**编译器的方法** （如 Polygeist[30]）可自动进行翻译，但**受其实现的完整性和支持的 CUDA 工作负载范围的限制**。

> 这些局限性凸显了对能够自动、高效进行 CUDA 移植的健壮且通用工具的迫切需求。

大型生成式预训练语言模型的出现为解决这一挑战开辟了新可能。ChatGPT 等 LLM 在代码相关任务（包括代码补全[17]、翻译[14]和修复[21]）中已展现出卓越潜力。GitHub Copilot[5]和 Amazon CodeWhisperer[1]等工具展示了 LLM 如何促进软件开发。

> 然而，LLM 在将 CUDA 翻译到其他平台（尤其是高性能代码）中的应用仍未得到充分探索，**核心原因是缺乏与该任务相关的高质量训练数据集。**

尽管开源平台上有大量高性能 CUDA 和其他平台代码，但大多数代码缺乏描述，且难以按函数匹配。此外，大多数代码**高度集成在各种软件中**，包含许多**仅在特定软件架构内有效** 的定义和类型。从这些程序中收集的代码不利于增强 LLM 的通用知识。因此，构建一个能够自动生成 CUDA 代码和对应平台代码（**不与任何特定软件架构耦合**）的框架至关重要。

![文章插图](/articles/2025-06-27-cuda-hpctranscompile-llm-cuda-ai-c806abd2/images/02.webp)

**为应对这些挑战，我们提出了一个生成高性能 CUDA 及对应平台代码对的框架**。

::: block-1
该框架可利用现有语言扩展或专用 DSL 生成用于 LLM 微调的数据集。具体而言，我们**使用 TVM 作为演示工具来构建此框架**。TVM[13]是一个机器学习编译器，支持在 GPU、CPU 和其他 ASIC 等各种平台上进行算子自动优化和代码生成。**借助 TVM 自动调度器（可生成与人工优化库竞争的高效代码），TVM 可自动生成高性能 CUDA 和其他平台代码对**。

然而，**直接使用 TVM 仍存在挑战**：

- 一是 TVM 算子库（TOPI）支持的通用算子限制了计算的多样性；
- 二是生成的代码包含与 TVM 库相关的依赖项。
:::

为应对这些挑战，我们**提出了一种基于图的数据增强方法** 来**构建** 具有代表性和多样性的**数据集**，并修改 TVM 框架以确保生成的代码无特定依赖项。

同时，CPU 仍是各种应用中最常见且通用的计算平台。为 CPU 平台重新设计 CUDA 软件需要更高的成本和风险，尤其是在系统必须持续演进和适应的情况下。除实际需求外，**将 CUDA 翻译为 CPU 代码** 还代表了一项更广泛的学术挑战，体现了**跨不同并行编程范式** [26]（即 CUDA 的单程序多数据（SPMD）模型与 CPU 上使用的 fork-join 模型）进行桥接的需求。

> 因此，我们以 CUDA 到 CPU 的翻译任务为切入点，系统评估 LLM 解决 CUDA 生态系统兼容性挑战的潜力。

此外，我们精心选择具有代表性的算子来创建 HPCTransEval，这是一个用于高性能 CUDA 移植的基准测试。**HPCTransEval 包括 100 个独立算子、100 个由这些算子构建的计算图，以及 10 个深度学习模型的构建块**。该基准测试**独立于特定软件架构**，可**有效评估 LLM 在 CUDA 移植任务上的性能**。

实验在三个领先的 LLM（Qwen2.5Coder、DeepSeek-Coder-V2 和 OpenCoder）上进行，包括整体和细粒度性能分析、数据集大小的影响，以及对其各自优缺点的洞察。**结果凸显了高性能 CUDA 移植中的关键挑战，强调了利用自动代码生成对 LLM 进行微调以改善兼容性和优化性能的潜力。** 我们的代码可在 https://anonymous.4open.science/r/HPCTransCompile-4DC5 获取。

::: block-1
总之，本文的主要贡献如下：

- 我们提出了一个**生成 GPU 和对应平台高性能代码对的框架**。该框架可利用语言扩展或专用 DSL 进行自动代码生成，以创建用于 LLM 微调的数据集，提升其在 CUDA 移植任务中的性能。
- 我们**引入了 HPCTransEval，这是一个用于 CUDA 移植的高性能基准测试**。该基准测试**与架构无关**，可有效评估 LLM 在该任务上的性能。
- 我们**以 CUDA 到 CPU 的移植为例进行了实验**。HPCTransEval 和另一个基准测试的结果表明，我们的框架显著提升了 LLM 在 CUDA 移植中的性能，尤其是在高性能代码方面。
:::

## 二、背景知识

在本节中，我们将首先介绍代码领域的最新大型语言模型。接下来，我们将讨论用于自动生成 CUDA 和相应 CPU C 代码对的演示工具 TVM。

### 2.1 面向代码任务的大型语言模型

大型语言模型（LLM）在与代码相关的任务中表现出了卓越能力，包括代码补全、合成和移植。其中，Qwen2.5-Coder[20]、DeepSeekCoder-V2[45]和 OpenCoder[19]代表了重要进展。

**Qwen2.5-Coder 是一款专为多语言和多平台代码生成与理解任务定制的开源模型**。在其前身 Qwen-Coder 的基础上，它融入了增强的分词策略和先进的架构特性，如分组查询注意力和扩展的上下文窗口。Qwen2.5-Coder 的训练过程强调中间填充（fill-in-the-middle）和其他代码特定目标，利用捕捉多样化编程范式和模式的海量数据集。

**DeepSeek-Coder-V2 是一种为高性能编码任务设计的专家混合模型** （MoE）[35]。它在 DeepSeek-V2 的基础上进行了大幅改进，支持的编程语言从 86 种扩展到 338 种，上下文窗口长度从 16,000 个标记增加到令人印象深刻的 128,000 个标记。这种广阔的上下文长度使 DeepSeek-Coder-V2 能够在需要广泛上下文理解的任务（如代码移植）中表现出色。此外，它在增强编码和数学推理能力的同时，在通用语言任务中保持了有竞争力的性能。

**OpenCoder 是另一项值得注意的成果，专注于不同语言和范式之间的高效代码翻译**。通过利用最先进的 Transformer 架构和预训练技术，OpenCoder 在跨语言代码理解和转换任务中实现了高性能。它引入了用于语义对齐和语法保留的创新机制，能够进行准确且上下文感知的代码移植。

### 2.2 张量虚拟机（TVM）

TVM[13]是一个面向 CPU、GPU 和其他 ASIC 的开源机器学习编译器框架，在学术界和工业界均有广泛应用。

TVM 最吸引人的方面是**算子的自动优化**。TVM 利**用一种调度语言来描述循环优化原语，如分块（tiling）、展开（unrolling）、并行化等**，其灵感来自 Halide[33]编译器。调度语言和计算抽象的分离使 TVM 既适用于手动优化，也适用于自动搜索。TVM 支持模板引导搜索（AutoTVM）和无模板搜索（自动调度器），以找到具有相关配置的最佳调度原语。被称为 Ansor[42]的自动调度器可以自动生成覆盖全面优化的大型搜索空间，并能够找到甚至可与人类专家竞争的高性能程序。

在这项工作中，我们利用自动调度器为 TVM 算子库（TOPI）中的各种算子和生成的计算图工作负载搜索最佳调度配置。

### 3.1 算子选择

为了使生成的数据集可用且多样化，我们首先过滤 TVM 当前支持的算子。我们通过以下步骤选择算子：

1. 从 TVM 官方文档中**收集候选算子的信息**，包括算子名称、调用推断、功能描述和参数设置。
2. 验**证每个独立算子的正确性**。如果算子能够通过 TVM 的 CodeGen 模块生成相应的 GPU 和 CPU 代码，我们会将该算子添加到可用列表中。如果 CodeGen 模块不支持该算子，我们会手动实现它。
3. 根据计算模式**将算子分为五类**：逐元素运算（Elementwise）、归约（Reduction）、布局变换（Layout Transform）、逻辑密集型（Logic Intensive）和计算密集型（Compute Intensive）。

> 每类的详细描述见表 1。

### 3.2 计算图构建

在算子选择之后，我们使用可用列表中的算子构建计算图。我们旨在对高性能 GPU 到 CPU 的移植任务进行全面评估，这**需要一个涵盖不同类型和复杂度计算的多样化数据集。**

> 因此，在构建计算图时，我们既考虑图中包含的算子类型，也考虑整体计算复杂度。

具体来说，我们重复选择算子并将其扩展到图上。同时，我们**采用随机连接、分支扩展和分支合并等方法来增加计算图的复杂度**。计算图中的节点表示计算类型，边表示数据流。

::: block-1
每次计算图扩展后，我们**验证计算流的合法性。**

- 首先，计算图必须是有向无环图（DAG）。
- 其次，我们验证节点操作的一致性，每个节点的操作类型必须与其输入和输出的数据类型和形状匹配。
- 此外，所有计算节点的输入必须来自输入节点或其他计算节点，以避免“悬空”节点。
:::

如果当前扩展引入错误，扩展将回滚并执行新的随机扩展，直到满足最终约束。完整的计算图构建过程如算法 1 所示。

### 3.3 无用依赖移除

在完成计算图构建步骤后，数据集已经包含了各种计算模式，但仍有一个问题需要解决：TVM 代码生成器生成的 CPU C 代码**包含大量由 TVM 库自身定义的依赖项**，这可能**会影响模型微调和评估性能。**

更具体地说，原始 TVM CPU 平台编译过程将主机代码和设备代码混合在一个模块中，因为这两种代码最终都在 CPU 上运行，但这也导致生成的代码包含特定的库依赖代码。

> 因此，我们修改了 CPU 平台的几个相关编译过程，以在满足内核启动调用约定的同时，将主机和设备分离为两个模块。

在代码生成阶段，**主机和设备模块调用各自的代码生成器**。此外，对于设备模块代码生成器，我们避免生成包含 TVM 库特定头文件、宏定义和 TVM API 调用的代码，以生成干净的 CPU C 设备代码。CUDA 代码、基于 TVM 的 CPU 代码和无 TVM 依赖的 CPU 代码分别如清单 1、2 和 3 所示。

### 3.4 图标注

对于大型语言模型，**提示（prompt）是决定 LLM 性能[44]的关键因素**。在代**码移植领域，任务规范会显著影响生成代码的质量**。适当的提示可以引导模型生成更符合任务要求和上下文约束的代码，而不合适的提示可能导致代码出现逻辑错误、编译问题或意外行为。

> 在高性能 GPU 到 CPU 的移植任务中，处理器架构、可用核心和线程数、缓存容量等硬件信息也会影响生成的代码。

因此，我们将**使用的硬件信息记录为移植任务注释的一部分**。此外，我们**聘请专业高性能工程师提供计算流描述和硬件感知优化策略作为函数级注释**，用于解释内部逻辑并提供可行的优化路径。

### 3.5 数据集生成

我们使**用 TVM 表示图的计算流，并将其封装到一个用 `auto_scheduler` 模块装饰的函数中**。然后，我们**将该函数与目标** （CPU 上的 LLVM、GPU 上的 CUDA）**结合形成搜索任务**，**并指定调优** 方法。

在搜索过程中，我们将测量试验次数设置为 200 次。我们使用的 CPU 是 Intel(R) Xeon(R) Gold 6348 CPU @ 2.60GHz，具有 112 个核心。

**TVM 会自动搜索最佳调度，并将搜索到的配置保存在日志文件中**。当搜索次数达到设定阈值或超过最大搜索时间时，TVM 将停止搜索任务，并使用保存的最佳配置为相应硬件平台生成代码。如果在指定时间内未找到有效调度，下一个计算图的搜索任务将继续进行。

### 3.6 评估流程

为了评估生成的 CPU 代码的正确性，我们需要一个评估运行时来支持自动代码正确性测试，该测试支持加载、编译和执行源代码。

然而，原始 TVM CPU C 源运行时模块不支持这些功能，主要原因有两个：（1）如前所述，TVM CPU 平台的编译过程将主机代码和设备代码混合在一个模块中，导致生成的代码紧密耦合，难以用外部提供的代码替换内核函数；（2）CPU C 源运行时模块仅支持代码导出，不支持执行。因此，我们使用一个名为源代码评估运行时的新运行时扩展了原始 TVM 运行时，该运行时支持自动测试所需的所有功能。

![文章插图](/articles/2025-06-27-cuda-hpctranscompile-llm-cuda-ai-c806abd2/images/05.webp)

**源代码评估运行时的详细实现如图 2 所示**。该运行时为用户提供了源代码加载、编译和执行 API，用于测试外部提供的代码，同时实现了与 TVM 运行时框架集成的必要功能。值得注意的是，生成的数据集还包含导出的主机和设备运行时模块，以及与 CUDA 和 CPU C 代码对对应的附加元信息，用于评估。

::: block-1
在评估过程中，对于每个测试用例：

- 首先加载相关的导出主机和设备运行时模块及元信息。其次，将 CPU C 代码加载到设备模块，与自动生成的粘合代码（glue codes）一起编译，以匹配调用约定。
- 然后，通过 LLVM ORC JIT[8]执行主机模块，该模块调用已编译的设备内核函数以产生最终结果。
:::

在加载、编译和执行阶段，运行时可在编译或执行失败时返回相应错误。

## 四、实验设置

### 4.1 数据集与模型

我们利用提出的框架生成了一个名为 **HPCTransData 的数据集**，**包含 20,000 对 CUDA-CPU 代码对**。该数据集作为微调所选模型的基础。

在实验中，我们**选择支持多语言代码生成的前沿 LLM**，以确保全面评估。具体而言，我们选**取了三个开源模型**：Qwen2.5-Coder、DeepSeek-Coder-V2-Lite 和 OpenCoder，后续分别将其称为 $M_{1}$、$M_{2}$ 和 $M_{3}$。

实验在两个基准测试上进行：HPCTransEval 和 KernelBenchC。

- HPCTransEval 包含 TVM 生成的手动精选和补充代码，
- KernelBenchC 基于 KernelBench[31]构建，专门用于评估我们框架的泛化能力。

通过使用 KernelBenchC，我们**旨在评估框架对不同场景和新代码模式的适应能力**，为其在 CUDA 到 CPU 移植任务中的多功能性和鲁棒性提供更严格的验证。

#### HPCTransEval

**HPCTransEval** 是从基于 TVM 生成的 CUDA-CPU 代码对中精心挑选的**代表性原始算子和融合计算图集合**。

此外，HPCTransEval 还纳入了广泛使用的模型模块，以增强基准测试的全面性。具体而言，HPCTransEval 包括 100 个原始算子、100 个融合计算图和 10 个复杂模型，该基准测试中的代码不依赖任何特定框架。

#### KernelBenchC

KernelBench 基准测试是一组定义为 PyTorch 模块的 250 个神经网络任务，这些任务分为三个类别，标记为 Level 1、Level 2 和 Level 3。

- Level 1 任务是常见的 ML 原语，如 softmax 或各种矩阵乘法（matmuls）；
- Level 2 任务是这些原语的几步融合，如网络层激活后接归一化；
- Level 3 任务代表完整的网络架构（如 ResNet）。

我们通过手动编写与 PyTorch 模块对应的 CUDA 代码扩展了 KernelBench，形成了 KernelBenchC。

### 4.2 实现细节

#### 训练超参数

我们使用 HuggingFace Transformers 库 v4.45.0[38]实现 LLM 微调。我们使用原始模型的预训练分词器初始化分词器，并在特定训练数据集上进一步训练。

训练使用 AdamW 优化器[27]，批量大小为 32，共 5 个 epoch。微调过程中采用低秩适应（LORA）[18]，秩为 8，α 值为 16， dropout 率为 0.05，专门针对关键投影层（$q_{proj}$、$k_{proj}$、$v\_{proj}$）。此外，设置梯度累积步数为 2，应用 0.3 的热身比率和线性学习率调度器。

所有实验在单个节点上运行，配备 8 块 NVIDIA A100 SXM4 GPU，每块显存 80GB。为加速训练过程，启用了混合精度训练，可训练参数约占原始模型的 10%。

#### 评估指标

> 为评估不同 LLM 在微调前后的性能，我们使用三个关键指标：编译通过率（Compile Pass）、执行通过率（Execute Pass）和速度比（Speedup Ratio）。

- **编译通过率** 评估翻译后的 CPU 代码是否能无错误编译，确保语法和依赖项正确；
- **执行通过率** 验证翻译后的 CPU 代码是否能正确执行，在合理误差范围内产生预期结果；
- **速度比** 衡量性能提升，通过比较翻译后的 CPU 代码与 PyTorch 或 TVM 支持的原始代码的执行时间计算得出。

## 五、实验结果

### 5.1 整体有效性

![文章插图](/articles/2025-06-27-cuda-hpctranscompile-llm-cuda-ai-c806abd2/images/11.webp)

如表 2 所示，在 KernelBenchC 上，**微调结果表明，注入领域特定知识在较简单的计算内核上收益最大**，同时**对较复杂模型也有帮助。**

- 对于 $M_{1}$，基本操作（Level 1）的执行通过率显著提升 82.1%，速度比提升 132.8%，**这表明有针对性的调优极大加速了低级原语的代码生成和内核执行**。即使是融合操作（Level 2），$M_{1}$ 的编译通过率提升 50%，速度比提升 137.7%，凸显了**嵌入算子融合领域知识的收益**。
- 尽管与 $M_{1}$ 相比，$M_{2}$ 和 $M_{3}$ 的整体增益较小，这反映了其**基础架构的固有差异，但微调后的显著改进证实**，**注入内核级领域知识可有效提升 LLM 将代码翻译为高性能实现的能力**。

![文章插图](/articles/2025-06-27-cuda-hpctranscompile-llm-cuda-ai-c806abd2/images/12.webp)

对于 HPCTransEval，微调前速度比大多低于 1，表明生成的代码效率低下。如表 3 所示，微调后所有指标显著改善，尤其是速度比，基本操作（Level 1）和融合操作（Level 2）的速度比分别提升至 1 以上（+183%和+38%）。这表**明代码正确性和执行效率有所提高，尽管融合算子因复杂性导致改进较小**。

此外，由于 HPCTransEval 中模型构建块的实现过于复杂，没有算子能正确运行，这凸显了 LLM 在处理更复杂代码翻译任务时的局限性。相比之下，KernelBenchC 的许多 Level 3 任务成功完成，因为这些翻译主要涉及与 Torch API 调用的直接映射。

> 因此，专注于内核函数翻译的 HPCTransEval 为推进更细粒度和复杂代码翻译场景的研究提供了更有价值的参考。

在 Level 2，Gemm-Scale 和 Conv-Trans 的适度**改进归因于它们对矩阵乘法和中间数据操作的更高依赖**，微调可增强内核融合和执行效率。在 Level 3，尽管整体改进不明显，但 MobileNetV2 推理的增益表明微调使模型能够适应不同的层结构和操作。其他两个模型在微调后也表现出不同程度的性能改进。

### 5.3 详细案例研究

本节展示两个详细案例研究，证明我们框架内的微调模型可将 CUDA 内核翻译为 CPU 执行代码，同时针对 CPU 硬件特性优化生成的代码。我们分析两个代表性示例：

1. Qwen2.5-Coder-14B 对包含[Matmul, Dropout, Mean, Softmax]的分组内核的翻译，比较微调前后的输出
2. DeepSeek-Coder-V2-Lite 对 VGG-16 卷积神经网络的翻译，同样比较微调前后的输出

这些示例说明了微调如何使模型生成更好地利用平台特定功能的 CPU 代码，从而提升性能。

#### **第一个案例**：融合的[Matmul, Dropout, Mean, Softmax]内核

涉及融合的[Matmul, Dropout, Mean, Softmax]内核。代码 4 显示了基础 Qwen2.5-Coder-14B 模型生成的 C++代码，**一个显著的性能瓶颈源于 OpenMP 并行循环** （#pragma omp parallel for）**内 std::mt19937 伪随机数生成器（PRNG）的重复实例化。**

由于梅森旋转算法（Mersenne Twister algorithm）的初始化过程（涉及分配和播种相对较大的内部状态（624 个 32 位整数）），每次实例化都会产生大量开销。在并行循环内实例化此生成器会导致高计算成本和潜在的内存竞争。

![文章插图](/articles/2025-06-27-cuda-hpctranscompile-llm-cuda-ai-c806abd2/images/16.webp)

相比之下，微调后的 Qwen 模型生成的代码（代码 5）用轻量级的基于哈希的 PRNG 取代了“std::mt19937”生成器。这种替代方案依赖高效的按位运算和模运算，消除了与梅森旋转算法相关的大量状态初始化和维护开销。此优化减少了寄存器压力，最小化了 PRNG 初始化期间的线程竞争，并可能增强指令级并行性。尽管基于哈希的 PRNG 的统计质量可能低于“std::mt19937”，但它为神经网络中的典型 Dropout 层实现提供了足够的随机性，在计算效率和应用领域的随机性要求之间取得了有效平衡。

#### **第二个案例研究**：VGG-16 CPU 执行代码翻译

考察了 VGG-16 向 CPU 执行的翻译。

基础 DeepSeek-Coder-V2-Lite 模型生成的代码（代码 6）显示出因模仿 CUDA 编程模式而导致的架构不匹配，具体而言，它采用了类似于 GPU 共享内存的技术（每个线程使用 std::vector）和复杂的分块/索引方案。这些模式在具有显式管理的本地内存和大规模并行性的 GPU 上有效，但在严重依赖分层缓存和硬件预取的 CPU 上通常不利。**基础模型的方法破坏了数据局部性（空间和时间）**，导致**缓存利用率差、缓存未命中增加和内存延迟惩罚**。

![文章插图](/articles/2025-06-27-cuda-hpctranscompile-llm-cuda-ai-c806abd2/images/17.webp)

相反，**微调后的 DeepSeek 模型生成的代码（代码 7）对卷积操作采用了更传统的、缓存友好的嵌套循环结构**。这种结构更好地匹配 CPU 的顺序处理特性和内存层次结构，促进规则的内存访问模式，增强数据局部性，并最大化 CPU 缓存系统的有效性。此外，这种简单结构更易于编译器优化，如自动 SIMD 向量化，进一步提升性能。

> 这两个示例都强调，微调后的模型不仅能够生成功能正确的翻译，还能生成针对目标 CPU 平台特定架构约束优化的高性能代码。

> 总体而言，增加数据集大小对生成代码的性能始终具有积极影响。

## 六、相关工作

### 6.1 CUDA 生态系统兼容性

已有多种方法尝试将 CUDA 生态系统迁移到 CPU 或其他平台。最直接的方式是重新设计目标应用，如 Intel 的 oneDNN 库[7]，但这会导致巨大的开发成本。

**对于 AMD 等 GPGPU 硬件，他们开发了与 Nvidia CUDA 非常相似的 ROCM[3]编程接口**，并提供 HIP[2]——一种 C++运行时 API 和内核语言，允许开发人员通过单一源代码为 AMD 和 NVIDIA GPU 创建可移植应用。为了无缝支持 CUDA，**HIPIFY[6]可以通过编译器前端技术** （如 AST 转换）**将 CUDA 源代码翻译为 HIP 源代码。**

由于硬件架构和编程模型的差异，**仅通过替换 API 无法简单实现 CPU 上的 CUDA 软件兼容性**。从软件角度看，尽管用户使用 C 语言编程，但 CUDA 采用单程序多数据（SPMD）编程模型，而 CPU 使用 fork-join 编程模型。

> 现有的性能可移植性方法包括语言扩展（如 OpenCL[36]、SYCL[9]）、领域特定语言（如 Halide[33]、TVM[13]）和并行编程框架（如 Kokkos）。

然而，所有这些方法仍需要通过特定库 API 或 DSL 进行重写，这对于大型复杂应用或正在积极更新的应用来说并不可行。**最先进的自动方法是 Polygeist 编译器**，它可以通过**在中间表示（IR）中编码高级并行构造将 CUDA 代码移植到 CPU C 代码**，但这种方法受限于编译器实现的完整性，其前端和中间表示的设计也限制了它可处理的 CUDA 工作负载范围。

## 七、结论与未来工作

### 结论

> 针对基于 **CUDA 的 GPU 代码向其他平台进行高性能计算移植** 的挑战，我们提出的框架利用 TVM 的算子优化和基于图的数据增强技术生成高质量的 CUDA 及对应平台代码对，解决了现有 LLM 因训练数据集不足导致的局限性。

HPCTransEval 的引入为评估 LLM 在 CUDA 移植任务中的性能提供了强大的基准测试。

实验结果表明，**移植质量显著提升，凸显了将专门优化技术和领域特定知识集成到 LLM 中的潜力**。这种方法不仅增强了不同硬件平台之间的性能可移植性，还为并行计算中更高效和可扩展的解决方案铺平了道路，符合现代深度学习模型不断增长的计算需求。

### 未来工作

**未来工作将侧重于将框架扩展到更多硬件架构** （如 TPU 和边缘设备），并探索**预硅（Pre-silicon）场景下的代码优化，以支持芯片流片前的软件性能验证**。

此外，进一步研究如何通过持续学习动态更新数据集，以适应新出现的 CUDA 特性和硬件架构，将是提升框架长期有效性的关键方向。
