关键词：**统一内存**、:mdnice-bold-italic[LLM 服务基准]、**Apple Silicon**、推理引擎、内存纪律

> 桌面端统一内存的并发本地 LLM 服务必须保留内存余量与输出保真度，而仅关注速度的排名完全忽略了这两点。

过去几年，本地 LLM 的评测几乎都围绕单请求吞吐量展开，用户选引擎也只看谁跑的 token/s 更快。**但在统一内存架构的桌面设备上，这个逻辑存在根本性缺陷：**

::: block-1
- 推理引擎与操作系统、前台应用共享同一块内存，单纯追求吞吐量可能导致内存占满、系统卡顿；
- 真实使用中智能体等场景会产生大量并发请求，单请求速度完全代表不了并发下的表现；
- 不同引擎的实现差异还可能导致输出质量下降，跑分好看但实际用起来效果差。
:::

## 一、为什么单看吞吐量会误导桌面 LLM 评测？

> 统一内存架构正在让消费级桌面成为本地 LLM 服务的新阵地，从苹果硅到 NVIDIA DGX Spark，CPU 与 GPU 共享的 LPDDR 内存容量已经摸到 512GB，追上了过去数据中心加速器的水平。

苹果硅生态的爆发式增长就是最好的例证：Ollama、llama.cpp、LM Studio 每年数十万次 Mac 安装，mlx_lm 每月 PyPI 下载量达 145 万次，Hugging Face 的 mlx-community 社区已经有 4710 个转换模型。但繁荣的背后，评测标准却严重滞后，绝大多数评测还在用数据中心的思路衡量桌面设备。

### 1.1 统一内存的特殊约束

> 传统数据中心的 AI 加速器使用专用的 HBM 高带宽内存，全部留给计算任务，不需要和 CPU、操作系统共享。但统一内存桌面完全不同，CPU、GPU、NPU 等所有计算单元共享同一块 LPDDR 内存，操作系统内核、前台应用、后台服务都要占用内存资源。

在这种场景下，**LLM 推理引擎的内存开销由四部分组成：模型权重、KV 缓存、临时计算缓冲区、内存分配器保留的复用缓冲区**。如果引擎占用内存过多，系统会触发内存压缩、磁盘交换，不仅推理速度会暴跌，用户打开的浏览器、IDE、文档软件都会卡顿，甚至出现请求失败、程序崩溃。

::: block-1
更隐蔽的是，:mdnice-bold-italic[这种性能下降是静默的渐变过程：内存占用越高，系统压缩交换越频繁，推理速度越慢，用户只会觉得“电脑变卡了”，很难定位到是推理引擎的内存问题。]
:::

### 1.2 现有评测的三大盲区

> 当前主流的本地 LLM 评测普遍存在三个核心盲区，导致单看吞吐量排名极具误导性。

| 盲区 | 说明 |
| --- | --- |
| 只测单请求，不测并发 | 绝大多数评测都是跑单个 prompt，测每秒生成多少 token。但真实场景中，一个编码智能体就能同时发起 4 到 16 个工具调用请求，并发访问本地 LLM 服务。没有连续批处理能力的引擎，在并发负载下吞吐量会暴跌，单请求速度再快也没有意义。 |
| 只看速度，不看内存占用 | 很多评测只报吞吐量，完全不提跑的时候占了多少内存。有的引擎为了跑分好看，把 KV 缓存开的很大，或者不限制内存增长，确实能获得更高的吞吐量，但用户根本没法同时开别的软件，失去了本地部署的意义。 |
| 只测速度，不测输出保真度 | 不同引擎对模型算子的实现、采样逻辑的处理都可能有差异，有的引擎为了提速做了简化或近似，导致输出质量下降。如果只看 token 生成速度，就会忽略“跑的快但答不对”的问题。 |

### 1.3 三个核心评判标准

> 针对统一内存桌面的特殊场景，论文提出了三个衡量 LLM 服务质量的核心标准，作为整个评测体系的指导思想。

- **第一个标准是服务架构就绪度**。引擎需要能够快速适配新的模型架构，同时在并发负载下实现高效的请求调度，保证吞吐量和延迟都能满足使用需求。:mdnice-bold-italic[这考验的是引擎的架构先进性和生态适配速度]。
- **第二个标准是内存纪律**。引擎需要高效管理内存资源:mdnice-bold-italic[，在保证性能的同时，为操作系统和前台应用保留足够的内存余量]，不能一跑推理就把内存占满。这是桌面场景区别于数据中心的核心要求。
- **第三个标准是多节点缩放**。单台机器的内存总有上限，:mdnice-bold-italic[要支撑更大的模型，需要能够跨机器分布式推理，并且实现合理的性能收益。这决定了桌面平台能承载的模型上限。]

::: block-1
总之，:mdnice-highlight[统一内存桌面的 LLM 服务本质上是“资源共享场景下的并发服务”，而不是“专用硬件上的单任务推理”]。仅用吞吐量一个指标，既无法衡量并发负载下的实际体验，也无法反映内存占用带来的系统代价，更不能保证输出质量。
:::

## 二、SiliconBench：三维评测体系的设计逻辑

> 针对现有评测的缺陷，SiliconBench 构建了一套覆盖速度、内存、保真度的三维评测体系，同时覆盖聊天与智能体两类典型工作负载，不仅测单请求表现，更扫过 1、8、16 三级并发度，还原真实使用场景。

整个评测以苹果硅平台为核心，同时设置 DGX Spark 作为 CUDA 统一内存桌面的参考基准，还补充了更大规模的稠密模型、MoE 模型测试以及多节点分布式推理评测，形成了完整的验证矩阵。

### 2.1 评测对象：九款主流推理引擎

::: block-1
本次评测覆盖了 9 款活跃开发的苹果硅 LLM 服务引擎，基本涵盖了当前主流的技术路线。它们在批处理策略、KV 缓存布局、阶段调度、内存管理四个核心维度上的设计差异巨大，正是这些差异决定了最终的表现分化。
:::

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/05.webp)

::: image-caption
表 1：服务引擎在批处理与内存管理设计上存在差异。九款苹果硅推理引擎配置概览：提示批处理定义预填充阶段共享前向传播的方式，打包批次无填充；预填充/解码标识单轮前向传播是否可合并两个阶段；KV缓存布局对应活跃请求的缓存存储方式；内存策略为引擎声明的配置项，实际执行效果在第6.2节评测。
:::

> 从设计路线上，九款引擎可以分为几类：

- 打包批处理+同阶段路线代表是 llama.cpp、ollama、vllm-metal、hf_transformers，预填充和解码可以在同一次前向传播中完成，prompt 紧挨着打包没有填充浪费；
- 填充批处理+分阶段路线代表是 mlx_lm、vllm-mlx、mistral.rs，把不同长度的 prompt 都填充到相同长度再批处理，预填充和解码分两次执行；
- 单请求预填充路线代表是 omlx、sglang，一次只处理一个 prompt 的预填充，解码阶段再批处理。

内存管理上也分为三种：显式设置内存上限、跟随 Metal 的建议值、不限制按需增长。这些设计的实际表现，都会在后续的评测中得到验证。

### 2.2 工作负载与数据集

> **评测设置了聊天和智能体两类工作负载**，分别对应不同的使用场景，每类包含 100 条 prompt。

- 聊天工作负载的 prompt 来自 OpenOrca、CNN/DailyMail 数据集，token 长度从 21 到 3500 不等，输出固定为 64 或 256 个 token，模拟日常对话、文档总结等场景。
- 智能体工作负载的 prompt 来自 BFCL V3、Hermes、ClawsBench 数据集，token 长度从 300 到 8900 不等，输出最长 256 个 token，模拟智能体工具调用的长上下文、短回复场景。这类场景对首 Token 延迟更敏感，并发度更高。

> **模型选择上，Qwen3-0.6B 作为基准模型，所有九款引擎都能支持，保证横向对比的公平性**。Qwen3.5-0.8B 和 Gemma-4-E4B-it 用来测试引擎对新架构的支持能力，:mdnice-bold-italic[前者引入了混合线性注意力，后者是多模态模型且采用跨层 KV 缓存设计，对引擎的架构适配能力要求很高。]

除此之外，评测还补充了 Qwen3.8-27B 稠密模型和 Qwen3.6-35B-A3B MoE 模型的测试，验证更大模型下的表现；以及 35B 模型的多节点测试，验证分布式推理的缩放效果。

### 2.3 评测指标与维护机制

> **速度维度主要测三个指标**：输出吞吐量，即总生成 token 数除以总耗时，衡量整体处理能力；首 Token 延迟，即从请求发出到收到第一个 token 的时间，衡量响应速度；请求完成率，衡量运行稳定性。

内存维度主要测峰值系统内存占用，以及内存随并发度升高的变化趋势，判断引擎的内存控制能力和留给系统的余量。

保真度维度采用 GMRID 供应链事件分类任务，共 1146 个样本，8 个类别，分别测试 0 样本和 5 样本设置下的加权 F1 值，以 NVIDIA A100 上的 vLLM 为参考基准，确保相同权重和精度下的公平对比。

> 值得一提的是，SiliconBench 建立了一套可持续的维护机制：由 Claude Code 代理自动更新框架版本、运行基准测试、诊断问题并提出修复方案，维护人员审核通过后再发布正式结果。这套机制解决了 LLM 框架迭代太快、评测结果很快过时的问题。

论文中举了两个早期运行的例子，很能说明问题：

- 一次 MLX 版本从 0.31.1 升级到 0.31.2，直接导致三个框架出故障，代理自动定位并修复了两个；
- 还有一次 ollama 导入模型时漏掉了 ChatML 分隔符，导致分类任务 92%解析失败，代理自动诊断并切换了模型来源解决问题。

::: block-1
回顾一下，:mdnice-highlight[把桌面 LLM 评测从“单任务跑分”升级为“并发服务审计”，是 SiliconBench 的核心创新。它不仅测性能，更测可用性、可靠性和兼容性] **，三个维度的设计完全对准统一内存桌面的真实使用场景。
:::

## 三、九大引擎速度实测：并发负载下的真实性能分化

> 速度是用户最关心的指标，但真实场景下的速度是并发负载下的持续吞吐与低延迟。:mdnice-bold-italic[SiliconBench 在 64GB 的 Apple M5 Pro 上，用 Qwen3-0.6B BF16 模型，测试了 1、8、16 三级并发下的聊天与智能体工作负载，结果远超常规认知。]

同样支持打包批处理、分页 KV、混合阶段的引擎，并发扩展性天差地别；而聊天场景下表现接近的引擎，在智能体长上下文场景下迅速拉开差距。单请求排名靠前的引擎，并发下可能直接崩溃。

### 3.1 吞吐量：聊天与智能体的两副面孔

> 先看聊天工作负载，并发 1 的时候，各引擎的单请求吞吐量差距不大，排名和大家日常认知差不多。但随着并发度升高，差异迅速拉大。

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/06.webp)

::: image-caption
图 2：相近的聊天吞吐量背后，是智能体工作负载下迥异的性能表现。Apple M5 Pro上聊天（左）与智能体（右）工作负载在并发度1、8、16下的输出吞吐量；注意两侧y轴刻度不同。引擎按智能体并发8的性能排序。带斜线的彩色柱表示部分成功，灰色斜线柱表示崩溃。
:::

**从并发 1 到并发 16，vllm-metal 的聊天吞吐量提升了 3.65 倍，是所有引擎里扩展性最好的**。ollama 也表现不错，并发 16 的时候和 vllm-metal 吞吐量几乎持平。:mdnice-bold-italic[但其他引擎的增长就很有限了，有的甚至出现下降。😅]

再看智能体工作负载，情况发生了很大变化。**vllm-metal 以明显优势领跑，并发 16 时比第二名高出 32%。** ollama 的表现掉了下来，omlx 则稳住了阵脚。更严重的是，不少引擎直接出现了部分失败甚至完全崩溃😅。

::: block-1
:mdnice-highlight[为什么两个场景差异这么大？核心原因是智能体的 prompt 更长，平均约 4300token，最长接近 9000token]。长上下文下，填充批处理的浪费被指数级放大，而打包批处理能充分利用算力。同时，长上下文对 KV 缓存管理的要求也更高，分页 KV 的优势更明显。
:::

从数据上看，**vllm-metal 是唯一在两个场景下都实现了 2 倍以上吞吐量增长的引擎**。其他采用填充批处理或者单请求预填充的引擎，要么吞吐量增长不到 30%，要么随着并发升高性能倒退，甚至到 16 路并发直接崩溃。

### 3.2 首 Token 延迟：智能体体验的核心

> 在智能体场景下，首 Token 延迟其实比吞吐量更影响体验。因为智能体的每一轮工具调用都要等 LLM 返回结果，首 Token 越慢，轮次耗时越长，整个任务的完成时间就越久。

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/07.webp)

::: image-caption

从测试结果看，并发 16 下，vllm-metal 的智能体首 Token 延迟中位数只有 219 毫秒，是唯一进入 250 毫秒以内的引擎，和单请求相比变化不大。sglang 的首 Token 也比较快，655 毫秒，但它的解码吞吐量掉了 80%，属于“先答应你，再慢慢说”的类型，实际体验并不好。

其他引擎的首 Token 延迟就比较难看了，基本都在 1 秒以上，并发高了甚至到几秒、十几秒。试想你用智能体写代码，每调用一次工具要等好几秒才开始返回，整个流程会有多卡顿🤣。

### 3.3 请求完成率与模型覆盖

> 跑分再高，跑不完请求也是白搭。测试下来，**九款引擎里只有六款能在所有并发度下完成 90%以上的请求**。

- mistral.rs 在并发 8 就出现明显退化，并发 16 直接崩溃；
- mlx_lm 在智能体并发 16 只剩下 2/100 的成功率；
- hf_transformers 甚至在智能体场景直接超时，1 小时都跑不完。

这里需要说明一点，mlx_lm 在低并发下的部分失败，是因为工具调用解析成了空内容，不算完全崩溃，但并发 16 的崩溃是真实的内存溢出导致的。

除了基础模型的完成率，新架构模型的支持情况也是架构就绪度的重要部分。截至 2026 年 8 月的测试，九款引擎里只有五款能同时支持 Qwen3.5 和 Gemma 4，ollama、mistral.rs、sglang 的 MLX 后端都还不支持这两个新模型。这也体现了不同引擎的生态迭代速度差异。

## 四、内存纪律：统一内存系统最容易被忽略的硬约束

> 如果说速度决定了体验上限，内存纪律就决定了体验的底线。在统一内存桌面上，**推理引擎不能把所有内存都占满，必须留出余量给系统和前台应用**，否则用户一边跑 LLM 一边写代码、查网页，系统就会卡顿甚至崩溃。

更反直觉的是，:mdnice-bold-italic[引擎声明的显式内存预算，很多时候并不能真的保证内存占用在安全范围内；而有的引擎虽然能跑完所有请求，但内存已经摸到物理容量的天花板，随时可能出问题。] 🤣

### 4.1 三种内存策略的实测表现

> 九款引擎采用了三种不同的内存管理策略：

- 显式上限策略，由用户设置内存预算，引擎自己控制；
- 建议提示策略，跟随 Metal 框架给出的建议工作集大小，但 Metal 并不强制保证；
- 无限制策略，按需分配内存，没有上限。

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/10.webp)

::: image-caption
图 5：跑完所有请求不代表内存纪律合格。Qwen3-0.6B BF16在Apple M5 Pro上的吞吐量与峰值系统内存，每个split100个请求，并发度1、8、16（标记大小递增）。sglang和vllm-mlx虽然内存占用高但跑完了所有请求；vllm-metal在几乎恒定的内存下实现了吞吐量缩放。实心标记表示完成率≥90%，空心标记表示部分运行。
:::

> 实测结果和直觉不一样：

- **vllm-metal 和 llama.cpp 的内存占用几乎不随并发增长，非常平稳** 🙂。vllm-metal 在智能体场景的峰值内存只有 34.7-34.9GB，在 64GB 的机器上留出了将近一半的余量，用户完全可以同时开浏览器、IDE 和其他软件。
- ollama 的内存也很平稳，但直接占到了 Metal 建议值的 94%-97%，从并发 1 开始就没留什么余量，属于“卡着红线跑”，稍微开点别的软件就可能触发内存压力。
- omlx 的内存随需求增长，但整体控制在建议值以内，属于按需分配但不超限的类型。
- **最让人意外的是 mistral.rs、vllm-mlx、sglang 这三款，它们都声明了显式内存预算，但实际运行中内存快摸到 64GB 的物理 RAM 上限了** 😅，同时吞吐量还在下降。比如 mistral.rs 在智能体并发 8 就占到 59.3GB，只完成了 13/100 的请求，预算完全没起到作用。
- 无限制的 mlx_lm 就更夸张了，聊天场景内存几乎翻了三倍，只换来了 7%的吞吐量提升，性价比极低。

### 4.2 隐藏的内存浪费陷阱

> 很多时候内存占用高是引擎实现上的浪费导致的😄。有两个非常隐蔽的内存陷阱，很多用户甚至引擎开发者都没注意到。

**第一个陷阱是填充批处理的 padding 浪费**。比如 mlx_lm 用填充批处理，三个 prompt 分别是 30K、5K、10 个 token，并发执行的时候，:mdnice-bold-italic[查询张量的形状是[3, 30000]，KV 缓存也要对应开这么大。但实际有效 token 只有 35010 个，却占了 90000 个位置，61%的计算和内存都浪费在了填充的空 token 上。]

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/11.webp)

::: image-caption
图 1：64GB能放下的工作负载，在32GB上会引发内存颠簸。mlx_lm的填充批处理与批次连续KV（30K+5K+10输入token），在32GB M1 Pro（左）和64GB M1 Max（右）上的顺序与并发执行对比。并发填充触发页面压缩，在更小的机器上导致2.5倍减速。
:::

这个浪费在内存充足的时候可能没感觉，但在内存紧张的时候会触发大问题。比如同样的工作负载，在 64GB 的 M1 Max 上能轻松放下，并发执行和顺序执行速度差不多；但在 32GB 的 M1 Pro 上，并发执行的内存浪费触发了 macOS 的页面压缩机制，每次解码都要先解压 KV 缓存，算完再压缩回去，直接导致速度慢 2.5 倍。

说白了，这是静默的性能降级🤣，用户只会觉得电脑变卡了，根本不知道是推理引擎的 padding 浪费导致的。

**第二个陷阱是内存分配器滞留**。MLX 框架的内存分配器为了减少重复分配开销，会保留已经释放的缓冲区用来复用。这就导致就算推理任务完成了，张量释放了，内存也不会还给操作系统，引擎的内存占用一直维持在高位。需要定期调用 clear_cache 接口，或者设置单独的分配器缓存限制，才能缓解这个问题。

### 4.3 大模型下的内存天花板

> 在更大的 27B 模型测试中，内存纪律的重要性更加凸显。8 位量化的 Qwen3.8-27B 光模型权重就有 55.6GB，已经超过了 Metal 的建议工作集大小，属于贴着内存天花板运行。

测试的三款引擎都能跑完所有请求，但内存都已经摸到极限。llama.cpp 峰值内存 51.2GB，vllm-metal53.9GB，都在崩溃边缘徘徊。这种场景下，只要用户稍微开点别的软件，就可能触发内存压缩甚至 OOM。

::: block-1
总之，:mdnice-bold-italic[显式内存预算不等于内存纪律，请求成功不代表内存安全。统一内存桌面上的内存问题是从静默降级、系统卡顿到请求失败的连续谱。真正优秀的引擎，应该在保证性能的同时，把内存占用控制在合理范围]，给用户留出日常使用的余量。
:::

## 五、保真度验证：跑的快还要答的准

> 速度再快、内存再省，如果输出质量不行，那也是本末倒置。SiliconBench 用 GMRID 供应链事件分类任务，以 NVIDIA A100 上的 vLLM 为参考基准，验证各引擎的输出保真度，确保性能提升不是以牺牲质量为代价。

测试分 0 样本和 5 样本两种设置，覆盖三个模型，使用完全相同的权重和精度，排除量化差异的干扰，只看引擎实现带来的质量波动。

### 5.1 基准模型的保真度对比

> 在 Qwen3-0.6B 模型上，一共测试了八款引擎的保真度。

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/12.webp)

::: image-caption
表 3：Qwen3-0.6B上八款引擎中的六款符合参考水平；两款新模型上的五款引擎全部符合参考水平。保真度为GMRID任务的加权F1值，苹果M5 Pro上的生成结果，以NVIDIA A100上的vllm-nv为参考基准。阴影部分表示超出参考值周围约1.5个百分点的区间。-表示未测试；新模型仅覆盖五款苹果硅引擎。

结果显示，六款引擎的 0 样本和 5 样本 F1 值都在参考值上下 1.5 个百分点以内，属于正常的实现波动，保真度完全合格。**也就是说，绝大多数主流引擎的输出质量都能对齐 CUDA 参考实现。**

> 但也有两个明显的异常案例：

- 第一个是 ollama。它的 0 样本结果没问题，但 5 样本结果直接掉了约 30 个百分点，远低于正常水平。**研究人员分析，原因应该是它的聊天模板在处理多个示例时有 bug，导致模型无法正确理解少样本提示**。反正就是引擎实现的缺陷🤣。而且进一步验证发现，ollama 的工具调用输出经常是空内容，它的吞吐量里其实混了不少无效 token。
- 第二个是 vllm-mlx。它的 0 样本结果比参考值低了 5 个百分点，没有请求错误也没有解析错误，应该是特定版本的实现 bug😅。不过它在两个新模型上的保真度都符合参考水平，说明这个问题是版本特定的，不是架构性的。

### 5.2 新架构模型的保真度

> 在 Qwen3.5 和 Gemma 4 这两个新架构模型上，能支持的五款引擎的保真度全部达标，都在参考值 1.4 个百分点以内。这说明这些引擎对混合注意力、跨层 KV 缓存等新架构的实现是准确的，没有为了速度偷工减料。

这也侧面说明，:mdnice-bold-italic[只要引擎实现正确，苹果硅平台的推理精度和 CUDA 平台是一致的，不存在架构性的精度损失。用户担心的“苹果硅跑模型质量差”，更多是个别引擎的实现问题，不是平台本身的问题。]

::: block-1
回顾一下，:mdnice-highlight[绝大多数主流引擎的输出保真度都能对齐 CUDA 参考实现]，出现的问题基本都是工程实现的 bug。**但用户也要警惕，有的引擎看起来吞吐量高，其实混了空内容 token**，或者模板处理有问题导致实际任务效果大打折扣。
:::

## 六、多节点缩放：超越单卡内存上限的可行路径

> 单台苹果硅机器的内存总有上限，要跑更大的模型就得跨机器分布式推理。**但 Mac 之间的连接带宽远低于数据中心的 NVLink，用什么并行策略、走什么传输协议，直接决定了多节点的效率。**

SiliconBench 用两台 64GB 的 M4 Pro Mac mini，通过 Thunderbolt 5 连接，测试了张量并行和流水线并行两种策略，以及 RDMA 和 TCP 两种传输方式的表现。

### 6.1 两种并行策略的本质区别

> 很多人分不清张量并行和流水线并行，这里解释一下💡。

- **张量并行就是把模型的每一层权重都拆成两半，两台机器各存一半，每一层计算的时候，两边各自算自己的部分，中间同步结果**。好处是内存占用几乎线性降低，计算延迟低；坏处是通信量大，对带宽和延迟很敏感。
- 流**水线并行就是把模型按层分成两段，第一台机器算前半部分的层，把输出传给第二台机器，第二台算后半部分**。好处是通信量小；坏处是串行性强，延迟高，而且流水线填充有开销。

### 6.2 实测结果：RDMA 张量并行才是正解

> 测试使用的模型是 Qwen3.5-35B-A3B，8 位量化，单台机器就能放下，这样测出来的就是纯多节点开销，排除了容量因素的干扰。

![文章插图](/articles/2026-09-29-siliconbench-apple-silicon-llm-f1819f72/images/13.webp)

::: image-caption
表 4：基于RDMA的张量并行实现缩放，基于TCP的流水线并行反而退化。Qwen3.5-35B-A3B 8位模型的吞吐量，512个输出token。1-2台M4 Pro Mac mini，Thunderbolt 5+RDMA。llama.cpp使用基于TCP的流水线并行，macOS上不支持RDMA。
:::

结果非常清晰：

- **单节点性能上，EXO > mlx_lm > llama.cpp**。EXO 的单节点性能就比 mlx_lm 快 35%，优化程度很高。
- **双节点张量并行（走 RDMA）：mlx_lm 获得了 1.28-1.32 倍的吞吐量提升，EXO 获得了 1.30-1.37 倍的提升**。预填充阶段因为是计算密集型，提升更明显，短上下文下接近 2 倍，4K 上下文也有 1.7-1.8 倍。
- :mdnice-bold-italic[双节点流水线并行（走 TCP）：llama.cpp 反而慢了 16%-20%。因为 TCP 的延迟太高，流水线又是串行的，通信开销完全盖过了分布式计算带来的收益。]

### 6.3 意义与局限

> :mdnice-bold-italic[这个结果说明用消费级的 Thunderbolt 接口做 RDMA 张量并行，是可以获得正向性能收益的。未来随着模型越来越大，单台机器内存不够的时候，用户可以用雷雳线把几台 Mac 连起来，组成小型集群跑大模型。]

当然现在的测试也有局限：只测了两台机器，更多节点的缩放性还不确定；只有支持 RDMA 的引擎能享受到收益，用 TCP 的流水线并行得不偿失；而且现在测试的模型单台就能放下，真正跨节点跑超大模型的表现还有待验证。

::: block-1
整体看下来，:mdnice-highlight[苹果硅多节点推理的核心瓶颈在传输协议]。**基于 RDMA 的张量并行能获得正向收益，而基于 TCP 的流水线并行反而会拖慢性能**。随着雷雳带宽的提升和更多引擎支持 RDMA，桌面集群跑大模型会越来越可行。
:::

## 结论

> SiliconBench 用一套完整的三维评测体系，给统一内存桌面的 LLM 服务画了一张清晰的全景图。**九个引擎里，最终只有 llama.cpp、vllm-metal、omlx 三款通过了完成率、保真度、模型覆盖的全部门槛。**

这三款引擎各有侧重：

- llama.cpp 兼容性最好，支持的模型最多，内存占用平稳，适合追求稳定通用的用户；
- vllm-metal 并发性能最强，内存控制优秀，首 Token 延迟低，最适合智能体等高并发场景；
- omlx 功能全面，内存按需增长，适合复杂的工作负载。

### 桌面 LLM 服务演进方向

> 从这次评测中，我们可以得到四个关于桌面 LLM 服务演进方向的核心启示。

| 要点 | 说明 |
| --- | --- |
| 打包变长批处理+分页 KV+混合阶段将成为基线配置 | 随着智能体应用普及，并发请求会越来越普遍，:mdnice-bold-italic[只有支持打包的变长批处理、分页 KV 缓存、混合预填充解码阶段，才能同时兼顾高吞吐量和低首 Token 延迟。还在使用填充批处理的引擎，会越来越跟不上需求]。 |
| 内存管理需要向更精细的纪律方向演进 | **不能只满足于“不 OOM”，要考虑 padding 浪费、分配器滞留、系统内存压力等因素，真正做到可控的内存占用**，给用户留出日常使用的余量。未来内存纪律会成为桌面引擎的核心竞争力之一。 |
| 新架构支持速度是生态竞争的关键 | 现在新模型层出不穷，混合注意力、跨层 KV、MoE、多模态等新架构不断涌现，**引擎能不能快速适配，适配的质量好不好，直接决定了用户体验**。迭代慢的引擎会逐渐被淘汰。 |
| RDMA 多节点是桌面扩展的可行路径 | 单台机器的内存增长总有极限，而:mdnice-bold-italic[基于 Thunderbolt RDMA 的张量并行已经证明了可行性。未来随着接口带宽提升和生态完善，用多台 Mac 组成小型推理集群，会成为普通用户跑大模型的一个重要选项。] |

::: block-1
SiliconBench 的建立了**一套可持续维护的评测标准**，随着软件更新不断验证结果，给用户提供可靠的参考。:mdnice-highlight[对于桌面 LLM 这个快速发展的领域，这样兼顾速度、内存、保真度的三维评测体系，比单纯的吞吐量排名有价值得多]。它提醒整个行业，本地 LLM 的最终目标是服务用户的日常使用，而非刷跑分榜单。
:::
