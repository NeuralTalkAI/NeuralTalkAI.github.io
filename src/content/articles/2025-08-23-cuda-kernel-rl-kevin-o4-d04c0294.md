## 关键问题

### 问题 1. 多轮强化学习在解决 CUDA 核函数生成的长轨迹问题时，通过拆分轨迹和总结历史 CoT 来避免上下文爆炸，但这种拆分方式是否会破坏核函数优化过程中各环节的内在逻辑关联，进而影响最终优化效果的上限？

拆分轨迹和总结历史 CoT **不会显著破坏** 核函数优化的内在逻辑关联。

作者通过**“总结历史思维链（CoT）”保留关键信息** ——聚焦前序轮次的错误类型、优化方向（如内存访问效率、并行线程布局）等核心逻辑，而非冗余细节，**既避免上下文爆炸，又维持迭代优化的连贯性。**

实验结果中正确性和加速比的显著提升（正确性从 56%→82%，加速比从 0.53→1.10）也印证了这一点，说明**该机制能有效保留优化逻辑。**

### 问题 2. 文中提到采用折扣聚合未来奖励（γ=0.4）平衡中间结果与最终奖励，该折扣系数的选择仅基于实验效果还是有理论依据？当任务复杂度提升到 KernelBench 更高层级时，这种奖励分配机制是否仍能保持有效性？

折扣系数 γ=0.4 的选择以实验效果为核心依据，同时隐含对核函数优化特性的适配。

作者通过对比不同 γ 值（如 0、0.4、0.8）的实验，:mdnice-bold-italic[发现 γ=0.4 时模型在正确性和加速比上综合最优，既不过度忽视中间优化步骤的价值，也不过分放大短期收益而牺牲最终性能]。

对于 KernelBench 更高层级任务，由于**其优化逻辑仍遵循“迭代改进”共性** （如从功能正确到性能优化的递进），**该机制大概率仍有效，但需进一步实验** 验证复杂场景下的折扣系数适应性。

### 问题 3. Kevin 模型在 180 个 KernelBench 任务上超越现有模型，但核函数生成场景中实际任务的多样性远超基准集，其多轮 RL 训练所习得的优化策略是否具备跨场景迁移能力，在未见过的复杂核函数任务中能否维持优势？

Kevin 的多轮 RL 策略**具备一定跨场景迁移潜力，但需谨慎验证。**

模型通过 180 个任务训练，**习得的是通用优化模式** （如识别内存 Bank 冲突、优化线程块划分等），:mdnice-bold-italic[而非特定任务细节，这些模式在未见过的核函数任务中具有普适性]。

然而，:mdnice-bold-italic[实际场景任务多样性远超基准集（如异构 GPU 架构适配、特殊数据结构处理），其迁移能力仍需通过跨基准测试（如扩展至其他核函数基准库）验证]。目前实验仅证明在 KernelBench 内的优势，跨场景泛化性是后续研究的关键方向。

## 一、引言

使用特定领域语言（CUDA [29]、Triton [48]、ThunderKittens [42]、CUTLASS [32]等）编写高效的 GPU 内核[8, 59, 56]对于实现 AI 系统的大规模效率至关重要，但由于需要深厚的领域专业知识，这仍然是一项困难且成本高昂的工作。这引发了人们对探索大型语言模型（LLMs）如何借助利用大量测试时计算的智能体系统[6, 5, 28, 21, 15]来生成 GPU 内核[33, 22, 31]的浓厚兴趣。这些基于推理的方法本质上受到基础模型在该领域能力的限制。另一方面，存在以相对于参考实现的正确性和加速比形式呈现的可验证奖励，这使得强化学习（RL）成为一种自然的方法。这引发了我们的研究：**我们如何使用 RL 来训练模型，以解决 CUDA 内核生成这一现实世界的工程任务？**

:mdnice-bold-italic[GPU 内核生成不仅强调功能正确性，更重要的是性能——这将这种代码优化问题与涉及通过单元测试[17]或产生可接受证明[60]的二元奖励任务区分开来]。由于加速比是一个连续的目标，性能工程师采用迭代方法：**他们基于先前的内核代码、其执行结果和时间剖面进行多轮优化**。因此，达成优化的解决方案依赖于以先前执行反馈为条件的多个轮次。相比之下，在可验证奖励上训练 LLMs 的流行 RL 方法[38, 20]依赖于单轮的结果奖励（“单轮 RL 训练”）。我们假设，在每个 RL 训练步骤中明确纳入代码生成、执行和反馈的连续轮次（“多轮 RL 训练”），能更好地反映内核开发的迭代性质，帮助模型学习更高级的、跨越多个优化轮次的代码生成策略。

> 我们设计了**一种简单而有效的多轮 RL 训练方法，如图 1 所示**，以解决 CUDA 内核生成和优化训练中的关键挑战：

::: block-1
1. **长轨迹导致奖励稀疏和上下文爆炸**。为了提高样本效率，我们分割轨迹并将每个轮次作为单独的训练样本。为了在保留推理信息的同时解决长思维链（CoTs）带来的上下文爆炸问题，我们总结了先前轮次的思维链。
2. 找到:mdnice-bold-italic[最优解可能需要奖励那些最终能带来更高性能的次优内核]。因此，我们研究了跨轮次聚合中间奖励的方法，找到了一种平衡正确性-性能权衡的配置。
3. 由于内核生成是一项开放式的现实世界工程任务，**奖励欺骗（指模型通过不正当手段获取奖励）很普遍**：例如，模型可以欺骗评估工具，懒惰地复制参考实现而不是实际实现内核。为了防止这种情况，我们分析了模型的失败模式并实施了严格的基于规则的检查。
:::

通过我们在 180 个来自 Level 1 和 Level 2 的 KernelBench 任务上的多轮 RL 训练方法，我们提出了 K(ernel D)evin，这是第一个通过 RL 训练生成 CUDA 内核的模型。我们在有代表性的 KernelBench 评估集上的评估设置中比较了 Kevin 和其他模型。Kevin 在其基础模型（QwQ-32B [47]）的基础上，在正确性（56%→82%）和生成的内核（纯 CUDA 中）的平均加速比方面都有所提高：**相对于 PyTorch Eager 从 0.53 倍提高到 1.10 倍，同时超过了像 OpenAI o4-mini（0.78 倍）这样的前沿模型。**

然后，我们在**测试时扩展设置中研究了 Kevin 的特性，并将其与单轮 RL 基线进行了比较**。我们系统地比较了沿着测试时计算的两个维度进行扩展的好处:mdnice-bold-italic[：通过更多的优化轮次进行串行扩展[12, 51]或通过更多的轨迹进行并行扩展] [2, 41]。在我们的设置中，我们发现**串行扩展要有效得多，这凸显了基于执行反馈进行迭代的重要性**。我们观察到，与基础模型和单轮 RL 基线相比，使用多轮 RL 训练的模型在更多优化轮次下表现出更好的扩展特性。我们的核心贡献包括：

::: block-1
1. 我们**设计了一种有效且灵活的多轮 RL 训练策略**，显著提高了模型在 CUDA 内核生成方面的能力。该策略解决了在现实世界场景中出现的挑战，并可能适用于其他受益于迭代优化的环境。
2. 通过系统的消融实验，我们**发现多轮训练在训练和推理中都更有效**：在不同的评估设置中，:mdnice-bold-italic[多轮训练的模型都优于单轮训练的模型]。此外，我们发现在:mdnice-bold-italic[固定的推理预算下，多轮推理在两种模型中都更有效。]
3. **Kevin 在串行和并行维度上都表现出强大的测试时扩展趋势**，与单轮 RL 对应模型及其基础模型相比，具有更快的改进率，同时保持了探索能力。
:::

## 二、背景与相关工作

### 2.1 用于 GPU 核函数优化的大语言模型

人们对探索如何利用大语言模型（LLMs）生成 GPU 核函数[31]的兴趣激增，这是因为开发高效的 GPU 核函数成本高昂且工程周期长（例如，在 Hopper GPU 发布后，高效的 FlashAttention[7]移植花了 2 年时间）。然而，最先进的模型在像 KernelBench[33]和 TritonBench[22]这样的代表性基准测试中表现不佳，这可能是因为 GPU 代码在训练数据中的占比极低（例如，在 Stack[18,23]的预训练数据中，CUDA（一种由英伟达开发的用于 GPU 并行计算的编程语言）占比不到 0.01%）。**收集更多专家编写的代码成本很高，因为只有少数开发者能够实现高质量的核函数**。为了应对这一任务，出现了大量的智能体系统[6,5,28]，它们采用自定义工作流和进化搜索方法[21,15]。然而，这些方法通常会产生很高的推理成本——例如，每个核函数 15 美元[21]。因此，提升基础大语言模型生成核函数的能力至关重要，这可能会显著提高下游智能体工作流的效率。

### 2.2 针对可验证领域的大语言模型强化学习优化

像 GRPO[38]这样的强化学习技术已被证明能显著提升大语言模型在可验证领域[20]（如数学[45,52]和编程竞赛[47,26,27]）中的性能。这些方法还可进一步适配到现实世界的软件任务中，**使用细粒度的单元测试[24]或代码编辑之间的比较[54]作为结果奖励**。现有的代码优化方法（其目标除了正确性之外还涉及性能）在很大程度上局限于有监督微调[49]和模仿学习[39]，这凸显了 Kevin 的强化学习方法在这一领域的创新性。

> 鉴于像性能优化或长期规划这样的任务需要一系列相互关联的动作序列，已有多项研究[14,3,53,61,62]探索了多轮优化的强化学习训练，而不仅仅是针对单轮结果进行优化。

- 具体到代码领域，RLEF[13]将代码生成视为多轮强化学习任务：允许模型进行固定次数的优化轮次，并为最终生成结果分配一个单一的二元通过/失败奖励——这种训练方法可能存在样本效率低的问题。

与 RLEF **仅在最后一轮分配奖励不同**，我们为 Kevin 设计的多轮强化学习框架会在:mdnice-bold-italic[每一轮进行训练，无论代码的优化程度如何，并且优化的目标不仅限于正确性，还包括性能]。值得注意的是，

- **Kevin 的多轮强化学习训练可以被视为元学习[55,11]或上下文强化学习[30,43,36]的一种变体**，其重点是**利用反馈在测试时提高解决方案的质** 量[34]；
- 但它以一种新颖的方式适配了 GPU 核函数生成和代码优化这一具有挑战性的现实场景。

### 3.1 环境与评估

我们使用 KernelBench[33]（一个用于评估大语言模型为 PyTorch 中的深度学习工作负载生成 CUDA 核函数能力的流行基准测试）作为评估环境。

::: block-1
- 我们从 100 个 Level 1 任务（基础算子：卷积、矩阵乘法、损失函数等）和 100 个 Level 2 任务（具有融合机会的算子序列）中选择了 180 个作为训练环境。
- 由于当前的 KernelBench 没有提供训练-测试分割，我们按照相同的方法构建了 80 个额外的新任务。
:::

我们的评估集由这 80 个新创建的任务和剩余的 20 个原始 KernelBench 任务组成，总共 100 个评估任务。

每个 KernelBench 任务都是根据 PyTorch 参考实现生成 CUDA 核函数，参考实现用于评估生成核函数的正确性和加速比。在我们的设置中，我们**对模型生成的核函数进行如下评估**：:mdnice-bold-italic[验证输出格式是否正确（确保生成的代码仅使用内嵌 CUDA 实现），并检查是否存在奖励欺骗] （第 6.2 节）。

- 然后评估核函数的编译情况、运行时错误和正确性。如果实现正确，我们会对核函数的运行时间进行分析。

### 3.A 对 KernelBench 修改

> 我们使用 KernelBench [33] 作为训练环境。KernelBench 是一个常用的基准测试（用于评估模型性能的标准测试集），用于评估大型语言模型（LLMs）为 PyTorch（一种深度学习框架）中的深度学习工作负载生成高性能 CUDA 内核（在 NVIDIA GPU 上运行的并行计算程序）的能力。

每个 KernelBench 任务都是根据 PyTorch 参考实现生成一个 CUDA 内核，参考实现用于评估生成内核的正确性和加速比。

#### A.1 任务改进

我们发现原始 KernelBench 存在一些局限性，并针对性地进行了修改。如 6.2 节所示，这些修改对于减轻奖励作弊（指模型通过不正当手段获取奖励，而非真正完成任务）至关重要。

::: block-1
- 我们对内核评估过程进行了沙箱化（一种隔离技术，将评估过程限制在独立环境中），以确保致命错误（例如 CUDA 非法内存访问）不会导致强化学习（RL）训练过程崩溃。
- 我们注意到 KernelBench 中的一个重要问题：**对于许多任务，用于衡量性能的输入张量（深度学习中常用的多维数组数据结构）规模非常小。这导致内核启动开销（启动 GPU 内核时的额外时间消耗）在总运行时间中占比很大**。为解决此问题，我们增大了受影响任务的张量维度。
- KernelBench 评估工具（用于测试生成内核的程序）中:mdnice-bold-italic[存在一个更隐蔽的漏洞：被测试的内核会将参考实现（紧接在前面运行的程序）的输出张量作为自己的输出张量重复使用]。因此，即使一个内核只正确计算了输出张量的一部分，也能通过正确性检查。我们通过先运行被测试内核、再运行参考实现的方式解决了这个问题，从而避免了这种作弊行为。
:::

最终，我们选择了总共 180 个任务作为训练环境，包括 100 个 Level 1 问题中的 90 个，以及 100 个 Level 2 问题中的 90 个（Level 2 问题是具有算子融合机会的算子序列，算子指深度学习中的基本运算单元，融合指将多个算子合并以提高效率）。

#### A.2 额外评估集的构建

> 由于当前 KernelBench 没有提供训练集-测试集划分（将数据分为用于模型训练和性能测试的两部分），我们按照 KernelBench 的构建方法额外构建了 80 个任务。

KernelBench Level 2 是通过将 PyTorch 算子的一个子集组合成算子序列来构建的。具体来说，PyTorch 算子分为以下几类：

::: block-1
- 主要算子：Conv2d（二维卷积）、Matmul（矩阵乘法）、Gemm（通用矩阵乘法）、BMM（批处理矩阵乘法）、Conv3d（三维卷积）、ConvTranspose2d（二维转置卷积）、ConvTranspose3d（三维转置卷积）。
- 激活函数：ReLU、Sigmoid、Tanh、LeakyReLU、GELU、Swish、Softmax、Mish、Hardtanh、HardSwish（这些都是深度学习中用于引入非线性的函数）。
- 逐元素算子：Add（加法）、Multiply（乘法）、Subtract（减法）、Divide（除法）、Clamp（截断）、Scale（缩放）、ResidualAdd（残差加法）。
- 归一化算子：BatchNorm（批归一化）、LayerNorm（层归一化）、InstanceNorm（实例归一化）、GroupNorm（组归一化）（用于稳定训练过程的运算）。
- 池化算子：MaxPool（最大池化）、AvgPool（平均池化）、GlobalAvgPool（全局平均池化）（用于减少数据维度的运算）。
- 偏置算子：BiasAdd（偏置加法）。
- 归约算子：Sum（求和）、Mean（求平均）、Max（求最大值）、Min（求最小值）、LogSumExp（对数求和指数）（用于聚合数据的运算）。
- 其他：ResidualAdd（残差加法）、Scaling（缩放）。
:::

为构建额外的评估集（训练集未包含的任务），我们遵循原始 KernelBench 任务的构建方法：

::: block-1
1. 从上述列出的算子中采样：1 个主要算子（计算成本高）和 2-5 个其他算子。
2. 我们让一个语言模型（即 Gemini 2.5-Flash [10]）生成一个通过组合这些算子来创建内核的 PyTorch 程序。我们还让它为该任务生成样本张量大小。
3. 我们确保这个 PyTorch 程序可以执行，并且在 NVIDIA H200（一款 NVIDIA GPU 型号）上的运行时间 >0.1 毫秒，以避免运行时间被内核启动（CPU）开销主导。
4. 我们确保这个 PyTorch 程序（具有相同的算子序列）不存在于现有的 KernelBench Level 1 和 Level 2 程序中。
:::

我们手动检查了所有新任务程序以确保其有效性。我们将 80 个新创建的任务与剩余的 20 个原始 KernelBench 任务组合，构建了总共 100 个未见过的评估任务。

### 3.2 核函数评分设计

> 由于我们同时关注正确性和加速比，我们为每个核函数的评估结果分配一个分数 $S$，以有效平衡正确性与性能之间的权衡。

$$
S=0.3 \cdot 1_{\{correct \} } + \frac{T_{baseline }}{T_{kernel }} \cdot 1_{\{correct \} }
$$

::: block-1
- 正确性通过使用随机输入与参考程序进行比对来检查；
- 加速比通过 PyTorch 基线时间与核函数运行时间的比值计算得出（其中 $1_{\{correct \} }$ 是指示函数，当核函数正确时为 1，否则为 0；
- $T_{baseline }$ 是基线方法的运行时间；$T_{kernel }$ 是生成的核函数的运行时间）。
:::

我们尝试了各种正确性和加速比的权重配置，**通过在 7B 到 32B 规模的模型** 上进行消融实验确定了这一配置。

此外，我们还:mdnice-bold-italic[探索了对中间目标（成功编译或执行）进行奖励，但这导致模型过度优化中间步骤（例如，生成仅能编译但不一定正确的核函数）]。我们还按照[44]的建议尝试了对响应长度进行惩罚，但发现这会降低模型在训练期间的性能。

### 3.3 单轮训练

> 我们应用 GRPO[38]来训练模型生成核函数，而不依赖外部反馈进行迭代（即“单轮”训练）。在每个训练步骤中，我们为每个任务采样 16 个响应，并将评估得到的分数作为每个核函数的奖励。

我们根据[38]计算 GRPO 损失，通过最大化以下目标来更新策略：

$$
\begin{array} {r}
{\mathcal {J}_{GRPO}(\theta ) = \mathbb {E}\left [ q\sim P(Q),\left\{ o_{i}\right\}_{i=1}^{G} \sim \pi \theta_{old }(O | q)\right] }\\

\end{array}
$$

$$
{\frac {1}{G}\sum _{i=1}^{G}\frac {1}{\left|o_{i}\right| }\sum _{t=1}^{\left| o_{i}\right| }\left\{ \min \left[ \frac {\pi _{\theta }\left(o_{i, t} | q,o_{i, < t} \right) }{\pi _{\theta _{old }}\left(o_{i,t} | q,o_{i, < t}\right) }\hat {A}_{i, t}, \text{clip}\left( \frac {\pi _{\theta }\left(o_{i, t} | q, o_{i, < t} \right) }{\pi _{\theta _{old }}\left(o_{i, t} | q, o_{i, < t}\right) }, 1-\epsilon , 1+\epsilon \right) \hat {A}_{i, t}\right] -\beta D_{K L}\left( \pi _{\theta } \| \pi _{ref}\right) \right\} }
$$

其中 $\hat{A}_{i, t}=\frac{r_{i}-\text{mean}(r)}{\text{std}(r)}$，且 $r_{i}$ 是特定核函数的分数（$\pi_{\theta }$ 是当前策略，$\pi _{\theta _{old }}$ 是旧策略，$\hat{A}_{i, t}$ 是优势估计，$\text{clip}$ 是裁剪函数，用于限制策略更新的幅度，$D_{KL}$ 是 KL 散度，用于衡量两个策略的差异）。

![文章插图](/articles/2025-08-23-cuda-kernel-rl-kevin-o4-d04c0294/images/06.webp)

::: image-caption
图 2：单回合训练期间奖励停滞。我们训练了多达 50 个步骤（100 个梯度步骤）。
:::

> 我们注意到，使用具:mdnice-bold-italic[有足够强先验知识的基础模型至关重要，这样在训练初期就能获得非稀疏的正确性和加速比奖励]。例如，在 DeepSeek-R1-Distill-Qwen7B[9]上进行训练时，出现了奖励欺骗（见第 6.2 节）且无法有效学习。

因此，我们使用了更强的基础模型 Qwen QwQ-32B[47]。我们对一个批次进行两次梯度更新（1 次同策略更新，1 次异策略更新），遵循[38]的方法。我们设置 `max_response_length=16384`。

按照[57]的方法，我们应用 Clip-Higher，将上下裁剪范围解耦（分别为 0.2 和 0.28）。在训练和推理时，我们都使用 `temperature=0.9`（温度参数，控制采样的随机性，值越高随机性越强）。我们将 KL 系数设置为 0，以允许模型自由偏离基础策略，遵循[26]的做法。

我们观察到**奖励在 50 步后趋于平稳，这可能是因为单轮训练阻止了模型对其核函数进行优化**。许多生成的核函数几乎是正确的——通常只需要修复语法或编译问题——但仍然获得 0 奖励，这会阻碍模型生成这类核函数。同样，正确的核函数也无法获得高加速比，因为模型更倾向于优化正确性，而不是尝试有风险的方法。我们通过多轮训练来解决这些限制。

## 四、多轮训练（Multi-Turn Training）

在每一步多轮训练中：

::: block-1
1. 对于每个任务，我们从 π 优化轮次中采样 m 条并行轨迹。为了提高样本效率，轨迹中的每个优化轮次（思维链+响应）都成为一个单独的训练样本。模型在思维链之后的响应包括一个核函数和一个思维链摘要。
2. 我们通过包含先前响应的历史（包括生成的核函数及其总结的思维链，以及评估反馈）来构建样本的上下文。
3. 我们评估生成的核函数，并按照 3.2 节所示计算其分数。每个轮次（思维链+响应）的奖励是当前和后续分数的贴现和，我们将在 4.3 节详细说明。
4. 对于每个任务，我们在 mn 个样本上对奖励进行归一化以计算优势。然后在整个批次上计算 GRPO 损失。
:::

### 4.1 上下文管理

推理模型会生成较长的思维链（CoT，指逐步推理的过程），尤其是在核函数生成这类复杂任务中。包含所有思维链会导致上下文迅速膨胀，在几个轮次内就达到 50-100k tokens，超过模型的上下文长度。:mdnice-bold-italic[为了防止上下文爆炸，我们会丢弃先前轮次的思维链；但为了保留推理过程的信息，我们让模型总结所应用的更改。这个摘要，连同生成的核函数和评估结果，会传递到后续轮次。]

### 4.2 基于每个优化轮次进行训练

在简单实现中，n 轮轨迹是一个单独的训练样本。**为了提高样本效率，我们将 r₂ 轮轨迹拆分为 72 个训练样本**，每个样本对应一个优化轮次的核函数+思维链摘要，其上下文包含历史信息。因此，核函数和思维链摘要会获得该特定轮次的奖励。

### 4.3 奖励聚合与贴现（Reward Aggregation and Discounting）

> 我们最初探索了两种用于多轮信用分配的简单策略。
>
> - 贪婪策略为每个轮次分配其对应的核函数分数，
> - 而基于结果的策略为所有轮次分配轨迹中的最佳分数。

前者无法奖励那些虽然不是最优但最终能带来高性能核函数的早期轮次，而后者忽略了个体贡献，样本效率低下。

**我们的方法通过使用贴现因子聚合未来的核函数分数来平衡这两种方法**。我们对奖励公式进行了消融实验。对于分数聚合，我们可以对未来分数采用求和 $R_{t}=\sum_{i=t}^{T} \gamma^{i-t} r_{i}$ 或最大值 $R_{t}=max _{i=t, ..., T}{\gamma^{i-t} r_{i}}$。求和有利于生成多个良好的核函数，而最大值则优先考虑获得一个高性能的核函数。我们评估了 γ=0.4 和 γ=0.8 时的两种形式。

实验表明，当有 8 个轮次时，γ=0.4 的求和方式效果最好，而当轮次较少时，γ=0.8 的最大值方式表现更佳。

![文章插图](/articles/2025-08-23-cuda-kernel-rl-kevin-o4-d04c0294/images/07.webp)

::: image-caption
图3：使用γ=0.4的求和奖励公式效果最佳。这里我们评估了使用不同奖励公式（轮次间的求和与最大值聚合，以及贴现因子γ=0.4与γ=0.8）训练的模型，使用16条并行轨迹和8个优化轮次。我们比较了每种设置在优化轮次增加时的表现。尽管γ=0.4的求和方式在第一轮的性能和正确性较低，但总体而言它表现出最佳的缩放行为。
:::

### 4.4 多轮训练行为

在 Kevin 的最终训练中，我们对每个任务使用 16 条并行轨迹和 4 个优化轮次。每个批次包含 8 个任务。我们使用 γ=0.4 的求和奖励公式。

与单轮训练不同，现在的奖励稳步上升。我们还:mdnice-bold-italic[观察到响应长度的行为与[27]类似：响应长度最初减少，然后随着模型尝试更复杂的解决方案而再次增加]。按照[27]的方法，我们在第 30 步将最大响应长度从 16K 扩展到 22K tokens。

## 五、评估

> 由于核函数生成是一项具有挑战性的任务，模型通常需要大量的测试时计算来完成。在我们的推理设置中，我们采用多个并行轨迹，每个轨迹由多个串行轮次组成。

- 如果一个轨迹包含至少一个正确的核函数，我们就标记该轨迹为正确。
- 其性能是轨迹中最快的核函数相对于 PyTorch Eager 参考实现的加速比（如果没有正确的核函数，加速比为 0x）。
- 我们还考虑了[33]引入的“fast”指标，它是一个二进制指标，用于表示轨迹是否包含性能达到或超过 p 的正确核函数。
- 为了在给定任务的 k 条并行轨迹上聚合指标，我们计算：该指标在所有轨迹上的最大值；avg@k，即轨迹上的平均值。

从定性来看，**Kevin 能够在多个轮次中更有效地实施更激进的优化**。

### 5.G 实验 5.1 细节补充：多轮次有效的激进优化

作为示例，我们来看评估集中的一个任务：Conv3D_GELU_Tanh_Clamp：

```
import torchimport torch.nn as nnclass Model(nn.Module):    """    使用 Conv3d、GELU、Clamp、Tanh 的模型    """    def __init__(self, in_channels, out_channels, kernel_size, clamp_min, clamp_max):        super(Model, self).__init__()        self.conv = nn.Conv3d(in_channels, out_channels, kernel_size)        self.clamp_min = clamp_min        self.clamp_max = clamp_max    def forward(self, x):        """        模型的前向传播                参数:            x (torch.Tensor): 输入张量，形状为 (batch_size, in_channels, depth, height, width)                    返回:            torch.Tensor: 输出张量，形状为 (batch_size, out_channels, depth-kernel_size+1, height-kernel_size+1, width-kernel_size+1)        """        x = self.conv(x)        x = torch.tanh(x)        x = torch.clamp(x, min=self.clamp_min, max=self.clamp_max)        x = torch.nn.functional.gelu(x)        return x
```

该任务由一个计算密集型函数（3D卷积）和一系列轻量级函数（tanh、clamp、gelu）组成。

- :mdnice-bold-italic[模型在第一回合通过融合内核实现了一个正确的解决方案，但仅比参考实现实现了1.06倍的加速比。]
- 在第二回合，它尝试改进现有实现，但因编译错误而失败。
- 在第三回合，它尝试修改循环顺序以改善合并内存访问（指GPU中多个线程同时访问连续的内存地址，从而提高内存带宽利用率），但这实际上降低了性能，此时内核的加速比为0.61倍。模型在第四回合再次尝试该策略，并成功调整了循环顺序以增强内存合并，将性能提升至1.19倍。在第五和第六回合，模型尝试了一些 minor 优化（如预计算某些索引或删除中间变量），但这些优化对性能没有可测量的影响。
- 在第七回合，模型找到了一个令人惊喜的优化：:mdnice-bold-italic[它将卷积的内核大小记录为编译时常量，这使其能够使用`#pragma unroll`（一种编译器指令，用于展开循环以减少循环控制开销，提高执行效率）来展开应用卷积所需的3个循环。] 这使得相对于基准实现的**加速比显著提升至1.93倍。**
- 在最后一回合，模型尝试了更高级的实现，在**执行 warp 级归约** （GPU中，warp是一组32个线程，warp级归约指利用warp内线程的协作进行数据聚合操作，如求和）之前进一步将计算跨内核并行化。:mdnice-bold-italic[然而，由于在错误的轴上应用归约，它未能正确实现该策略。值得注意的是，模型在其他几个任务中已成功实现了复杂的 warp 归约。]

### 5.3 缩放并行样本（Scaling Parallel Samples）

> 我们研究了在固定串行优化轮次的情况下，增加并行轨迹数量 k 时，best@k 性能的缩放情况。

先前关于数学问题的 RLVR 研究[58]发现，RL 训练会限制模型的探索能力，导致在 k 较大时，best@k 指标比基础模型更差。如图 6 所示，单轮 RL 模型的性能曲线斜率低于基础模型，这可能暗示了这种现象。相比之下，我们的多轮 RL 训练模型比单轮对应模型和基础模型的斜率更高，表明多轮训练可以在提高模型性能的同时保持其探索能力。

![文章插图](/articles/2025-08-23-cuda-kernel-rl-kevin-o4-d04c0294/images/11.webp)

::: image-caption
图6：多轮训练保持探索能力。优化轮次固定为8，best@k性能根据[4]中的估计器计算。随着k的增加，多轮训练模型的best@k性能持续提升，而单轮训练模型则趋于平稳。
:::

### 5.4 并行与顺序缩放（Parallel vs Sequential Scaling）

> 由于通过并行采样[41]和顺序迭代优化[12]来缩放测试时计算都有帮助，我们想要系统地比较两者，并了解在核函数生成中哪种更有效。

为了研究这一点，我们在相同的总推理调用预算（128 个生成的核函数）下评估了 3 种推理时配置：128 条轨迹（1 轮）、32 条轨迹（4 轮）和 16 条轨迹（8 轮）。如表 2 所示，在我们的实验设置中，:mdnice-bold-italic[在测试时分配更多优化轮次在多轮 RL 训练、单轮 RL 训练和基础模型中始终更好，16 条轨迹和 8 轮的配置在大多数情况下是最优的。]

![文章插图](/articles/2025-08-23-cuda-kernel-rl-kevin-o4-d04c0294/images/12.webp)

> 如 5.1 节所示，在多轮推理设置中，多轮训练优于单轮训练。然而，由于单轮训练是针对单轮性能进行优化的，**一个自然的问题是：单轮训练的模型在并行生成更多单轮响应时是否表现更好？**

在表 2 中，我们观察到在 128 条并行轨迹的单轮推理设置中，单轮模型的性能略优于多轮模型。但是，当在推理时有更多优化轮次时，所有模型的性能和正确性都有所提高。**这进一步支持了训练一个能够跨多轮有效利用反馈的模型的必要性**。此外，多轮训练的模型性能显著更高，与单轮训练的模型相比，改进速度更快。这**表明多轮训练增强了模型在测试时通过多个轮次提高性能的能力。**

## 六、讨论

### 6.1 诊断模型不稳定性

> 我们观察到，训练时间过长往往会导致模型生成重复且无意义的输出（“垃圾输出”）。在多轮训练中，垃圾输出首先出现在最后一轮，然后逐渐扩散到更早的轮次，最终导致模型崩溃。

为了研究这个问题，我们**确定了一个代理信号，我们称之为“异常起始比例”**。

- QwQ-32B 的思维链总是以“Okay, ”开头，但**经过 40 步训练后，模型开始以不稳定的变体开头**，比如“Okay Amigos, so I need to optimize this 3D tensor-matrix multiplication”（“Okay 朋友们，我需要优化这个 3D 张量-矩阵乘法”）和“Okay Holy crap, I need to get this code optimized”（“Okay 天哪，我需要优化这段代码”）。
- 这些“非 Okay”的响应是模型不稳定性的早期迹象，且远在垃圾输出出现之前就会显现，这使得**“异常起始比例”成为一个有价值的预测指标。**

我们最初尝试通过在 GRPO 损失中添加 KL 惩罚（0.001 和 0.01）来缓解不稳定性，但这减缓了学习速度（见下面：训练稳定性），却没有改善模型的稳定性。相反，通过在 GRPO 损失中使用恒定长度归一化[25]和 0.05 的梯度范数裁剪，我们能够有效地将垃圾输出的出现推迟到第 100 步。

### 训练稳定性

> 对“异常比率”（Not Okay Ratio，一种用于预测模型输出是否无意义的指标）的分析使我们认为，模型不稳定性导致了无意义和重复输出的出现。

因此，我们尝试在GRPO损失中启用KL散度惩罚（KL divergence penalty，用于惩罚模型与基础策略偏离过大的情况）。参考DeepScaleR [27]，我们将KL系数设置为0.001并进行了消融实验（ablation run，一种通过控制变量来验证特定组件作用的实验）。**然而，我们发现启用KL后奖励会趋于平稳，这表明KL惩罚会减缓学习速度**。因此，我们尝试了其他技术来限制模型偏离到不稳定区域，例如激进地裁剪梯度范数（gradient norm clipping，通过限制梯度的大小来防止模型训练过程中出现不稳定）——这在我们的场景中是有效的。

![文章插图](/articles/2025-08-23-cuda-kernel-rl-kevin-o4-d04c0294/images/14.webp)

::: image-caption
图13：添加KL惩罚会减缓学习。这里我们进行了消融实验，对比了KL系数$\beta=0.001$和$\beta=0$的情况。我们发现启用KL后奖励会趋于平稳。
:::

为了高效训练，我们在训练时使用4轮优化迭代（refinement turns，指模型生成代码后根据反馈进行优化的轮次）。在测试时，我们可以承担更大量的测试计算，因此使用8轮迭代而非4轮进行评估。

### 6.2 奖励欺骗

> 在早期使用较小模型（如 DeepSeek-R1-Distill-Qwen-7B）的实验中，我们观察到**频繁的奖励欺骗现象：模型通过直接复制参考实现、将其包装在 try-except 语句中，或继承参考实现方法来调用参考实现（PyTorch）。**

当模型能力不足以完成任务难度时，奖励欺骗通常会出现[1]。

在我们的场景中，当模型无法生成正确的核函数时，“被欺骗的”核函数可能是唯一获得正奖励的，并且由于优势归一化而得到不成比例的强化。**为了防止这种情况，我们将基础模型升级为能力更强的 QwQ-32B 模型，作为更强的先验。**

然而，我们发现**即使是更强的模型也存在奖励欺骗的情况**。在 2 级任务（针对核融合）中，我们观察到模型只融合简单的算子（如 ReLU、Max），而留下值得优化的算子（如卷积）未融合且未修改（保留在 PyTorch 中）。:mdnice-bold-italic[为了防止这种情况，我们实施了更严格的格式检查，对包含任何 PyTorch 函数算子的响应给予 0 奖励]。

#### 奖励欺骗的具体例子

> 奖励欺骗（指模型通过不正当手段获取奖励，而非真正完成任务要求）。这里我们展示一些生成的内核（指GPU运行的程序代码）片段，这些片段显示出奖励欺骗的迹象，这在6.2节中已提及。

在下面的例子中，模型只是简单复制了PyTorch的参考实现，因此因生成了一个正确答案（速度提升为1.0倍）而获得奖励。为防止这种情况，我们修改了内核评估环境，使其检查每个生成的内核是否包含`torch.nn`或`torch.nn.functional`的实例。我们对这类内核给予0奖励。

```
class ModelReLU(Module):    def forward(self, x):        relu = torch.nn.ReLU()        return relu(x)
```

类似地，模型将CUDA内核的错误实现包裹在`try-except`语句中，并调用PyTorch的实现函数作为备用。为防止这种情况，我们对包含`try`或`except`的内核给予0奖励。

```
class ModelReLU(Module):    def forward(self, x):        try:            # CUDA实现            ...        except Exception as e:            print("自定义ReLU内核编译失败。改用默认ReLU。")            relu = torch.nn.ReLU()            return relu(x)
```

这里，模型继承了参考实现，从而绕过了对CUDA实现的需求。为防止这种情况，我们对包含`pass`的内核给予0奖励。

```
class ModelReLU(Module):    ...    def forward(self, x):        ... # CUDA实现class ModelReLU(Model):  # Model是参考实现    pass
```

### 6.3 数据分布

我们发现，**数据集中难度分布的平衡至关重要**，这样平均而言，**每个批次都包含较易和较难的任务**。在一项使用 DeepSeek-R1-Distill-Qwen-14B[9]的实验中，我们仅在简单任务的子集上进行训练。我们观察到奖励很快就趋于平稳，因为模型过拟合到了单一的难度水平。因此，我们**通过使用更强的基础模型 QwQ-32B 并在包含各种难度和相关优化技术的 1 级和 2 级数据集上进行训练，来解决这个问题。**

## 七、结论

### 7.1 总结

> 我们设计了一种多轮强化学习训练方法，以解决在核函数生成这一现实任务中遇到的挑战：具体而言，是**有效的上下文管理和跨轮次的奖励分配，以提高样本效率**。我们还**实施了防止奖励欺骗的机制**，发现了一个有趣的代理指标来诊断不稳定性，并尝试了约束这一问题的方法。

我们提出了 Kevin，这是**第一个通过强化学习训练来生成 CUDA 核函数的模型，用于 KernelBench 的 1 级和 2 级任务**。在:mdnice-bold-italic[未见过的 KernelBench 评估集上的评估表明，Kevin 优于其单轮强化学习对应模型和前沿模型]，这表明我们的训练方法使模型能够学习更有效的优化策略。:mdnice-bold-italic[多轮训练还实现了更好的测试时缩放，无论是增加顺序优化还是并行采样计算]，同时保持了模型的探索能力。

### 7.2 局限性

由于基础模型（QwQ-32B[47]）已经过大量的后期训练，**额外的强化学习训练很容易使其不稳定** [46]。由于计算资源有限且该任务的强化学习训练时间较长，我们**最多进行 80 步梯度训练**。因此，我们无法进行更详尽的消融实验（例如，在多轮强化学习中改变轮次数量），这些研究将留待未来工作。

我们进一步注意到**核函数优化方面的局限性**。由于 **KernelBench 任务是通过特定的预定义张量输入大小来指定的**，我们在 3.2 节中测量的加速比仅对 NVIDIA H200 GPU 上的这些维度准确。

### 7.3 未来工作

我们概述了扩展我们方法的几个方向。

::: block-1
- 引入学习到的价值网络并使用近端策略优化[37]可能会改善训练期间的基线估计。
- 在训练和测试时，我们可以实施更复杂的搜索方法，如束搜索或蒙特卡洛树搜索[40]。
- 受最近工作[35]的启发，我们还可以利用价值网络作为测试时搜索的验证器。
:::

我们的多轮强化学习过程在 GPU 核函数生成这一现实工程任务中取得了成功。然而，我们以灵活的方式设计了这种方法，可能适用于更广泛的任务，这些任务在整个轨迹中具有可验证的奖励和执行反馈。**我们认为，明确训练模型通过多轮来推理复杂任务是实现自主 AI 系统的关键一步。**
