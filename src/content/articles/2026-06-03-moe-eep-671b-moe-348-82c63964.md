## 一、背景与动机：为什么宽 EP MoE 需要故障容忍

### 1.1 专家并行：大规模 MoE 服务的基石

> 混合专家（MoE）模型通过将计算分散到多个稀疏激活的专家中，实现了参数规模的指数级增长，同时保持了与稠密模型相当的每 token 计算成本。在推理阶段，路由器为每个 token 选择少数几个专家，系统将 token 激活分发到托管这些专家的设备上，计算完成后再收集结果。

为了将这一过程扩展到数十块 GPU，现代系统普遍采用**专家并行（EP）** 技术：将所有专家均匀地分片到不同的 GPU 上，每个推理步骤包含两个关键的通信阶段——token 分发（dispatch）和 token 合并（combine），如图 2 所示。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/06.webp)

::: image-caption
图 2：专家并行将 token 路由至远端专家并汇总结果。传统实现将该模式绑定到固定通信器；EEP 则基于动态对等集合执行该流程。具体来说，传统方案依赖固定通信器，秩故障会直接断裂整个路由链路，导致服务终止；EEP 改用动态对等集合，可实时剔除故障秩、保留健康秩间的通信能力。这种动态适配设计贴合 MoE 多专家分布式部署特性，避免单一故障影响全局 token 分发与结果汇总。动态对等集合是 EEP 突破传统 EP 静态通信限制的关键，解决了集群动态故障与固定通信架构的核心矛盾。
:::

**专家并行的核心优势在于它能够聚合多块 GPU 的内存容量和带宽**。对于 671B 参数的 DeepSeek-V3 模型来说，单块 GPU 甚至无法容纳整个模型的权重，必须通过 EP 将 256 个专家分布到 32 块或更多 GPU 上。:mdnice-bold-italic[然而，这种分布式架构也带来了致命的脆弱性：每一个解码步骤都依赖于所有 EP 节点的正常工作，任何一个节点的故障都会导致整个通信流程中断。]

### 1.2 故障的普遍性与现有系统的无能

> 在大规模集群中，故障是常态而非例外。论文引用的生产数据显示，GPU 和节点故障占所有硬件故障的 78%，每月发生 382 次。:mdnice-bold-italic[更重要的是，随着作业规模的增加，故障率显著上升 —— 对于一个 32-GPU 的 EP 实例来说，局部故障已经从 "边缘情况" 变成了 "常态运营条件"。]

**然而，现有的 EP 系统对这种故障几乎没有抵抗力**。表 1 总结了主流通信库在进程故障时的行为和对成员关系重配置的支持情况。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/07.webp)

::: image-caption
表 1：现有通信库在故障和成员变更下的行为。从服务运行时的角度来看，它们仍将成员身份视为通信器或专家并行（EP）组状态，而非可修改的运行时状态。 现有主流通信库（Gloo、NCCL、DeepEP）均基于静态成员设计，无法适配 MoE 大规模集群的局部故障场景。Gloo 一旦检测到故障会直接终止整个进程组，无任何成员变更能力；NCCL 仅支持通信器收缩或重建，需上层适配 EP 状态，无法实现运行时动态调整；DeepEP 仅适配固定 EP 组，不支持专家位置修复与秩重连。静态成员设计是传统 EP 服务遇局部故障即全局宕机的核心诱因，凸显 EEP 动态成员设计的必要性。
:::

::: block-1
:mdnice-bold-italic[上表所有这些库都共享一个根本缺陷：它们将成员关系编码为初始化时建立的固定结构。当一个节点失效时，不仅通信目标变得无效，托管在该节点上的专家也变得不可达，而且 CUDA 图中捕获的路由状态也与当前实际情况不一致]。现有系统没有能力独立修复这些状态，因此一个局部故障必然导致整个实例的重建。
:::

### 1.3 三个无法调和的核心矛盾

这种静态成员关系的设计导致了三个结构性矛盾，使得在现有框架内实现部分故障容忍几乎不可能。

#### 矛盾 1：CUDA 图执行与在线重配置的根本对立

> CUDA 图是高性能 MoE 服务的基石。它通过一次性捕获整个 GPU 工作负载，然后以最小的 CPU 开销重放，消除了每步内核启动的开销。

然而，这种性能提升是以灵活性为代价的：**内核顺序、启动参数和指针身份在捕获时就被永久冻结**，只有通过这些固定指针可达的内存内容可以在重放时改变。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/08.webp)

::: image-caption
图 4：EEP 中 CUDA 图稳定的重配置机制。CUDA 图保留指向对等表和路由表的稳定指针，故障与重集成时可直接修改表内内容，无需变更指针。 该图解释了 EEP 如何破解 CUDA 图固化与动态重配置的矛盾：传统方案成员变更需重捕获 CUDA 图，耗时数分钟；EEP 让 CUDA 图指向固定内存地址的对等 / 路由表，仅修改表内成员状态、路由信息，不改动指针与图结构。健康秩无需重捕获图，仅在前后向传播间隙更新表内容，兼顾高性能与动态适配。CUDA 图稳定指针设计，是 EEP 实现低延迟故障恢复、不牺牲稳态性能的核心创新。
:::

成员关系变化要求通信目标和路由状态在故障或修复后发生改变。现有的解决方案要么收缩通信器然后重建上层 EP 状态，要么在健康节点上重新捕获 CUDA 图。:mdnice-bold-italic[前者仍然需要重建大量状态，后者的开销随模型大小和系统规模线性增长——对于 671B 模型来说，重新捕获 CUDA 图可能需要数十秒甚至数分钟。]

#### 矛盾 2：快速降级模式恢复与 MoE 语义完整性的根本对立

> 当一个节点失效时，系统应该尽快在剩余节点上恢复服务。:mdnice-bold-italic[但是，MoE 执行不能简单地省略随故障节点消失的专家：一旦某个逻辑专家变得不可达，后续请求就不再执行预期的模型，输出质量将严重下降。]

现有的两种选择都不可接受：

- 立即在缩减的对等集上继续服务会导致语义不完整；
- 等待故障节点重启或从存储中重新加载所有丢失的专家会导致可用性崩溃。

恢复必须在系统安全继续之前，在剩余节点上恢复专家覆盖，同时不能等待故障节点。

#### 矛盾 3：异步节点恢复与同步分布式运行时初始化的根本对立

> 即使在恢复了有效的缩减容量实例之后，吞吐量仍然低于基线，直到故障节点被修复并重新加入。然而，现有的分布式运行时假设初始化、进程组形成、元数据交换和 CUDA 图捕获都是整个组一起参与的。

如果恢复的节点遵循这条路径，健康节点将被拉入集体屏障、模型初始化和图重捕，导致数十秒的服务中断。**重集成必须允许恢复的节点独立完成其初始化，而不迫使健康节点离开服务关键路径。**

::: block-1
正是这三个矛盾的存在，使得现有 EP 系统无法在不重启整个实例的情况下处理部分节点故障。

EEP 的出现，正是为了从根本上解决这三个矛盾。
:::

## 二、EEP 系统设计：基于显式可变成员关系的弹性 EP

EEP 的设计围绕一个核心目标展开：**在部分故障期间保持宽专家并行实例的有效性**。:mdnice-bold-italic[它不试图让重启变得更快，而是让实例在成员关系变化时保持存活和有效。]

### 2.1 故障模型与范围

> EEP 针对的是**故障停止（fail-stop）故障**：由于 GPU 进程崩溃、主机故障或通信链路故障导致节点永久或暂时不可达。存活的节点保持健康并继续服务。故障节点可能在稍后被修复或重新启动，并应该能够重新加入实例以恢复吞吐量。

系统假设故障可以通过通信超时检测，并且大多数节点保持运行。故障发生时正在处理的请求被报告为失败，必须由客户端重试；**EEP 不缓冲或内部重试失败的请求，以保持恢复路径简单和故障语义明确**。专家覆盖修复和节点重集成发生在前向传播之间，那里服务循环中已经存在自然的同步点。

EEP 不处理拜占庭故障、静默数据损坏、将集群分裂为多个组件的网络分区，以及不触发基于超时的故障检测的瞬态性能下降。这些故障模式要么需要正交的检测机制，要么最好在服务栈的其他层解决。

### 2.2 活 EP 有效性：EEP 的核心理论基础

> EEP 最关键的洞见是：**部分故障容忍在宽 EP 中本质上是一个活 EP 有效性问题，而不是更快重启的问题**。一个 EP 实例是有效的，当且仅当以下三个条件同时成立：

1. **对等集有效性**：通信仅针对当前活跃和可达的节点。
2. **专家覆盖有效性**：每个逻辑专家至少由一个活跃节点托管。
3. **图可见路由有效性**：CUDA 图捕获的分发和合并内核使用的对等和路由状态与当前活跃成员关系和专家放置相匹配。

现有 EP 系统将这三个状态捆绑成一个静态配置。EEP 则将它们显式表示并分别修复。一旦实例再次满足有效性契约，即使它暂时以降低的容量运行，故障也被视为已处理。

### 2.3 设计概览

> 一个节点故障会同时使所有三个条件失效：活跃对等集立即改变，一些逻辑专家可能随故障节点消失，在旧成员关系下捕获的图可见路由状态不再描述正确的执行。EEP 将恢复视为一个三步修复过程，而不是实例重建。

图 5：EEP 整体架构概览。秩故障会使活跃对等集合、专家放置及图可见路由状态失效。EEP 就地修复上述状态，后续重集成恢复秩时无需重建 EP 实例。 该图完整呈现 EEP 故障处理全链路：故障发生后，依次修复对等集连通性、专家覆盖完整性、路由状态有效性；重集成时采用异步模式，不阻塞健康秩服务。区别于传统全实例重建，EEP 精准定位三类失效状态并针对性修复，专家覆盖修复采用本地复用、GPU 迁移、DRAM 重载三级策略，平衡恢复速度与资源开销。分状态修复 + 异步重集成架构，实现 “局部故障局部修复”，大幅降低故障影响范围与恢复时长。
:::

> EEP 的三个修复步骤直接对应于引言中提出的三个矛盾：

- 通过 GPU 驻留对等表恢复对等集有效性，该表的条目可以就地禁用，同时捕获的图继续执行（**解决矛盾 1**）。
- 通过本地重用、GPU 到 GPU 重定位或 DRAM 支持的重新加载满足的修复放置来恢复专家覆盖有效性（**解决矛盾 2**）。
- 通过与修复后的缩减容量配置匹配的可变对等和路由表恢复图可见路由有效性，并通过延迟加入协议重新集成修复的节点，而无需健康节点重新捕获 CUDA 图（**解决矛盾 3**）。

::: block-1
重集成是反向转换：延迟加入协议允许修复的节点独立预热，然后活跃对等集再次扩展，恢复首选放置，健康节点继续执行相同的捕获图。
:::

## 三、EEP 的核心机制详解

### 3.1 成员弹性 EP 通信：GPU 驻留对等表

> EP 通信直接位于 MoE 解码的关键路径上。在每个 MoE 层，每个节点必须将 token 激活分发到托管所选专家的节点，然后在专家计算后收集结果。现有实现将此模式实现为固定通信器或预配置 EP 组上的集合操作。这种设计在静态世界中是高效的，但一旦一个节点消失，存活的节点仍然执行旧世界的通信模式，因此进度和正确性都会中断。

EEP 通过在**可寻址的设备侧对等表** 而不是固定集合组上表达 EP 通信来恢复对等集有效性。每个 GPU 在 GPU 内存中维护一个对等上下文表。对等上下文存储到达该节点所需的传输元数据和一个指示该节点当前是否属于活跃实例的活动位。通信内核在运行时遍历此表以发出分发、合并和同步操作。因此，成员关系不编码在通信器身份或图结构中；它编码在可变的设备侧状态中。

图 3 展示了 EEP 中 GPU 驱动的 EP 通信路径。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/10.webp)

::: image-caption
图 3：EEP 中 GPU 驱动的 EP 通信路径。内核读取设备端对等表，直接从 GPU 发起传输，且无需重新捕获 CUDA 图即可跳过非活跃对等节点。 该图揭示 EEP 高性能故障弹性的底层支撑，区别于传统 CPU 中转通信模式，EEP 借助 GPUDirect RDMA 将网卡资源映射到 GPU 地址空间，由 CUDA 内核直接执行通信操作。设备端对等表实时标记节点活跃状态，故障节点可被内核直接跳过，无需修改 CUDA 图结构，消除 CPU 通信开销。GPU 直驱通信 + 设备端故障过滤，让 EEP 兼顾高吞吐与故障连续性，适配 MoE 低延迟服务需求。
:::

> 上图这种表示有两个关键后果：

1. **通信保持 GPU 驱动**：在初始化期间，EEP 执行一次访问每个对等所需的元数据交换。之后，CUDA 内核直接通过 GPU 映射的 RNIC 状态发布工作队列条目并敲响 NIC 门铃，因此分发和合并保持与 CUDA 图执行兼容。
2. **成员关系变化成为简单的表更新**：故障清除一个对等表条目；重集成用新元数据刷新该条目并再次将其标记为活动。

为了在不恢复到主机侧编排的情况下协调进度，EEP 使用基于 RDMA 原子操作的 GPU 侧同步。在发出通信轮次的传输后，每个节点向其对等节点发布原子更新，并等待直到其本地 GPU 驻留计数器反映来自活跃对等集的预期到达。如果预期的更新在超时窗口（当前为 1 秒）内未到达，则该对等被视为不可达。因此，故障检测来自于稳态中使用的相同 GPU 侧进度机制，而不需要在数据路径中单独的主机管理的看门狗。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/11.webp)

::: image-caption
图 7：EEP 的 GPU 驻留对等表条目及简化调度路径。成员变更时仅更新表内内容，不修改 CUDA 图结构，因此捕获的内核可在故障与重集成后继续使用。 该图给出对等表数据结构与调度内核的简化逻辑：对等表存储节点通信元数据与活跃标记，调度内核遍历表时自动跳过非活跃节点。成员变更仅修改 active 标记与通信参数，内核逻辑、CUDA 图指针均不变，无需重捕获。该设计将动态成员逻辑内置于 GPU 内核，消除 CPU 干预，兼顾高性能与故障弹性。结构化对等表 + 内核级故障过滤，是 EEP 实现无图重捕获动态路由的底层技术保障。

:::

这是 EEP 解决矛盾 1 的核心机制。

### 3.2 故障后专家覆盖修复：三层修复层次

> 仅修复对等集是不够的。在宽 EP 中，节点故障也是专家丢失事件：一些逻辑专家可能变得不可达，因为它们的权重托管在故障节点上。EEP 因此将对等集修复和专家覆盖修复视为单独的步骤。

- 前者恢复存活节点上的通信连续性；
- 后者重建一个放置，其中每个逻辑专家再次在至少一个活跃节点上可达。

在通信层识别出故障节点后，运行时在存活节点上计算一个修复后的放置。修复路径然后通过遵循带宽和延迟现实的层次结构来满足该放置：

1. **本地重用**：专家权重已经驻留在目标节点上。如果新放置仍然将专家分配给已经持有其权重的节点，则恢复纯粹是本地的。EEP 更新本地放置元数据，并在需要时重新组织 GPU 内存中的权重布局。:mdnice-bold-italic[这是最便宜的恢复路径。]
2. **GPU 到 GPU 重定位**：另一个健康节点上存在存活副本。如果目标节点不已经持有该专家，但另一个健康节点持有，则 EEP 执行直接的 GPU 到 GPU 重定位。由于故障通常同时使多个专家失效，重定位作为批处理传输调度而不是一系列独立副本发出。这使修复路径与底层结构的面向带宽的性质保持一致。
3. **DRAM 支持的重新加载**：所有 GPU 驻留副本都随故障节点丢失。这是困难的情况。从持久存储重新加载专家权重将主导恢复时间并破坏部分故障容忍的目的。EEP 因此在主机 DRAM 中维护一个分布式专家备份服务。每个节点运行一个管理器进程，该进程在固定的、RNIC 注册的内存中存储专家备份的子集。这些管理器共同持有恢复所需的专家的完整备份副本。:mdnice-bold-italic[当存活节点需要其实时副本已丢失的专家时，它通过 RDMA 直接将备份提取到 GPU 内存中，绕过文件系统并最小化 CPU 参与。]

::: block-1
这个层次结构是经过深思熟虑的。本地重用最便宜，当另一个副本存活时，GPU 到 GPU 重定位是常见的快速路径，而 DRAM 支持的重新加载仅在所有 GPU 驻留副本都已丢失时作为后备。:mdnice-bold-italic[通过将修复构造为具有显式源层次结构的放置问题，EEP 将常见情况保持在快速本地或 GPU 驻留路径上，并将 DRAM 恢复保留在冗余已耗尽的更困难情况下。]
:::

这解决了矛盾 2：降级模式恢复变得足够快以有用，而不会牺牲专家完整性。

### 3.3 修复后节点重集成：延迟加入协议

> 如果系统只能收缩，部分故障容忍是不完整的。在实践中，运营商希望修复或重新启动的节点重新加入现有实例，以便吞吐量可以恢复到故障前的水平。EEP 因此支持节点重集成：健康节点继续以降低的容量服务，而故障节点异步重新启动，一旦准备好就将其合并回活动实例。

重集成是故障处理的逆向过程，但它的核心难点不只是更新通信元数据。真正的挑战在于：让恢复中的进程能**异步走完完整的预热流程**，而系统其余部分**持续对外提供服务**。

::: block-1
具体来说，控制器不会在关键服务路径上阻塞操作，而是将故障进程在服务路径之外单独重启。重启后的节点会重新初始化自身运行时环境、CUDA 状态、通信端点，以及在当前恢复策略下分配给它的专家权重。
:::

与此同时，其他正常运行的节点不会停摆——它们会基于一个**缩小的对等节点集合** 继续执行推理任务。这些健康节点会定期检查重启节点的状态，一旦确认它已完成预热、通信就绪、权重加载完毕，就将其重新纳入服务集群。

整个过程强调“不中断服务”与“按需恢复”的协同：故障节点在后台安静重建，系统主干始终在线。

::: block-1
主要的技术挑战是重集成再次改变 EP 成员关系，但运行的实例不应该支付健康节点上 CUDA 图重捕的成本。EEP 通过**延迟加入后端路径** 提供这一点：:mdnice-bold-italic[恢复的节点形成一个仅本地的进程组，重建其 CUDA 和通信状态，加载权重，并独立地重新捕获其图]。只有在该预热完成后，健康节点才通过刷新对等元数据、扩展活跃成员掩码以及在前向传播之间更新路由可见状态来合并它。
:::

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/12.webp)

::: image-caption
图 6：EEP 的故障处理与秩重集成工作流。健康秩优先完成状态修复，快速启动降容服务；故障秩单独执行环境初始化、模型加载、CUDA 图捕获等耗时操作，不占用健康秩服务资源。待故障秩就绪后，通过延迟加入机制接入，健康秩仅轻量更新对等表，无全局同步。异步化工作流避免健康秩等待故障秩恢复，保障故障期间服务连续性，平衡恢复速度与吞吐量。

:::

整个收缩与扩展过程，都基于同一套清晰、可控的抽象机制：

- 显式定义的对等节点集合（而非隐式或动态推导）；
- 显式指定的专家节点部署图（每个节点的角色和职责一目了然）；
- 稳定不变的对等关系与路由表（不随节点增减而频繁重算或抖动）。

相比依赖底层通信层（如固定拓扑的网络设备或硬编码的连接逻辑），这种设计将控制逻辑上移到语义明确、易于理解与调试的抽象层，显著提升了系统的可维护性与弹性。

这解决了矛盾 3：重集成成为健康节点上的有界加入事件，而不是第二个重建事件。

## 四、实现细节：EEP 在 Mooncake 与 SGLang 中的集成

> 我们在与 SGLang 集成的 EP 服务栈中实现了 EEP，总共约 10K 行代码：

- 约 7.6K 行 C++、CUDA 和 Python 代码，涵盖成员弹性通信基板、专家覆盖修复路径和重集成控制路径。
- 约 2.3K 行 Python 代码在 SGLang 中，涵盖弹性 EP 运行时集成、专家位置管理和 Mooncake EP 分发器。

我们保留了与现有 MoE 服务工作流的 API 兼容性。

::: block-1
**EEP 的通信层在 Mooncake 中实现，特别是 Mooncake EP 和 Mooncake PG**。Mooncake 是一个开源的高性能通信库，专为 AI 工作负载设计，支持 GPU 发起的 RDMA 和 CUDA 图集成。SGLang 是一个高效的结构化语言模型程序执行框架，支持 MoE 模型的专家并行推理。
:::

关键的实现细节包括：

1. **自定义 torch.distributed 后端**：我们实现了一个支持弹性成员关系的自定义 torch.distributed 后端。这个后端允许恢复的节点构造一个仅将自己标记为活动的本地进程组，满足上层系统的分布式运行时要求，而不需要连接到健康节点。
2. **分布式 DRAM 备份服务**：每个节点运行一个独立的备份管理器进程，在启动时加载其分配的专家，将它们组装成连续的固定缓冲区，为 RDMA 注册缓冲区，并发布一个将专家标识符映射到地址和大小的描述符表。
3. **弹性专家并行负载均衡器（EPLB）**：我们实现了一个弹性感知的 EPLB 变体，它将当前活跃节点集作为输入，并返回一个在存活节点上覆盖所有逻辑专家的放置。

## 五、实验评估：量化验证 EEP 的性能与容错能力

> 我们评估 EEP 以回答三个直接对应于活 EP 有效性契约的问题：

1. 显式可变成员关系在静态服务下是否引入开销？
2. EEP 在部分故障后能多快恢复有效的缩减容量实例？
3. 修复的节点能否在不迫使健康节点通过实例重建的情况下重新集成？

### 5.1 实验设置

> 所有实验都在一个由 6 个计算节点组成的集群上进行，每个节点配备 8×NVIDIA GPU，通过节点内的 NVLink 和节点间的 8×400 Gbps Mellanox RoCE 链路互连。每个节点运行 Ubuntu 24.04.2 LTS、CUDA 12.9、驱动程序 535.161.08 和启用了 GPUDirect RDMA 的 Mellanox OFED 23.10。

我们使用 PyTorch 2.8.0 和 Python 3.12 实现 EEP。使用 DeepSeek-V3 模型进行评估，这是一个具有 256 个专家的 671B 参数 MoE 模型。静态性能研究使用解码密集型（1024 输入/1024 输出）和预填充密集型（4096 输入/256 输出）工作负载，并发度从 32 到 256。**故障恢复和重集成研究使用 256 输入 token 和 4096 输出 token 的解码密集型配置，在闭环中以最大并发度 512 运行。**

::: block-1
- 对于稳态性能，我们与 DeepEP（一个固定成员关系的 EP 后端）在相同的 PD 分离 SGLang 部署下进行比较。
- 对于故障场景，固定成员关系后端基线不支持部分故障恢复；我们测量相同硬件上的完整实例重启时间，这是唯一可用的恢复路径。
:::

我们通过 SIGKILL 终止 GPU 进程来模拟节点故障。恢复后吞吐量从恢复窗口关闭后系统返回到缩减容量稳态服务时的吞吐量时间序列中读取。

> 稳态问题是，与将成员关系编码为静态结构的后端相比，通过 GPU 驻留对等表路由每个 EP 分发和合并所引入的额外间接性是否会实质性地影响吞吐量或延迟。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/14.webp)

::: image-caption
图 9：在相同参数拆分（PD）部署下，EEP 与固定成员 DeepEP 基线的静态服务性能对比。误差线为三次重复实验的标准差。 该图量化了 EEP 在静态场景的性能损耗：吞吐量损失≤4.4%，预填充负载下仅 1.4%，TTFT 与 TPOT 指标也与基线高度吻合。性能差异仅源于对等表的轻微内存访问开销，EP 通信、专家计算的核心耗时未增加。这说明 EEP 的动态成员机制未牺牲稳态性能，兼顾弹性与高效。EEP 静态性能接近传统最优方案，为其在生产环境替代固定成员 EP 方案提供了性能可行性支撑。

**结果表明，EEP 的稳态性能与 DeepEP 几乎相同**。在整个并发度范围内，EEP 的总体吞吐量保持在 DeepEP 的 4.4%以内，在预填充密集型工作负载上保持在约 1.4%以内。差异的方向在不同点之间变化，与运行间噪声一致，而不是系统性的惩罚。

::: block-1
这是因为 EP 服务的主导成本是跨 GPU 的 token 分发和合并，每轮额外的表查找相对于该成本可以忽略不计。EEP 的稳态路径在结构上与通过固定成员关系后端的路径相同。
:::

### 5.3 故障恢复性能

> 故障恢复问题是 EEP 是否能足够快地恢复语义有效的实例以产生影响。比较对象是完整实例重启，这是固定成员关系设计中唯一可用的恢复路径，在此工作负载上需要 348 秒。

图 10 展示了不同故障规模下的故障恢复结果。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/15.webp)

::: image-caption
图 10：2 预填充 4 解码部署、256 输入 4096 输出请求、最大并发 512 下的故障恢复结果。左：三个恢复阶段的耗时最大值；中：存活秩的专家修复来源占比，8 秩故障前 GPU 迁移为主，副本稀缺时 DRAM 重载占比上升；右：恢复窗口结束后降容服务期的吞吐量，虚线为故障前正常吞吐量。 该图从耗时、修复来源、吞吐量三方面验证故障恢复性能：恢复耗时仅 6-11 秒，远低于全重启的 348 秒；小故障以 GPU 间快速迁移为主，大故障兜底 DRAM 备份重载；恢复后吞吐量可达故障前 95%。三级修复层级适配不同故障规模，平衡速度与可靠性。EEP 故障恢复高效且降容服务稳定，适配不同规模局部故障，满足生产环境高可用需求。
:::

恢复速度快且时间可控。在测试中，当发生 1 至 16 个节点故障时，系统均能在约 6–11 秒内完成恢复。具体耗时会随故障节点数量略有浮动，但始终远低于“完全重启整个实例”所需的 348 秒基准——提速达 10 倍至 100 倍。

修复过程严格遵循预设的源层次结构。

- 在小规模故障（如仅少数节点宕机）时，大部分专家模型权重可直接在仍正常运行的节点间 GPU 上迁移，因此恢复时间主要取决于 GPU 之间的数据传输速度。
- 而当故障规模扩大、存活节点变少时，越来越多的专家权重需从分布式 DRAM 备份服务中重新加载，这使得恢复过程逐渐从“GPU 间传输主导”转向“从内存读取主导”。

这一变化也清晰反映在恢复时间的构成比例中：**小故障时传输开销占优，大故障时加载开销上升，整体阶段分布随之自然调整。**

缩减容量服务保持生产力。恢复的实例在所有故障规模上维持健康吞吐量的有意义部分，并在故障节点异步修复时继续服务。:mdnice-bold-italic[即使在 16 个节点故障的情况下，EEP 仍能维持约 40% 的故障前吞吐量，保证基础服务能力。]

### 5.4 节点重集成性能

> 文章开头的图 1 已经展示了单节点故障情况的端到端效果：**两个有界暂停——一个用于恢复，一个用于重集成——与 348 秒的完整重启形成对比**。本节询问相同的结构是否在一系列故障规模上成立，以及它是否在不将健康节点拉出服务关键路径的情况下这样做。

图 11 展示了不同故障规模下的节点重集成吞吐量轨迹。

![文章插图](/articles/2026-06-03-moe-eep-671b-moe-348-82c63964/images/16.webp)

::: image-caption
图 11：秩重集成吞吐量曲线。每个子图对应一种故障规模（f1-f16）；虚线 t0 为稳态后首次吞吐量为 0 的时刻，曲线为 5 秒滑动平均。二次中断时长：f1 为 4 秒、f2 为 6 秒、f4 为 9 秒、f8 为 15 秒、f16 为 15 秒。 该图展示不同故障规模下重集成的吞吐量变化，均呈现 “稳态 - 恢复中断 - 降容服务 - 重集成中断 - 恢复稳态” 的规律。中断时长随故障规模小幅上升，但均≤15 秒，无长时间停机；重集成仅触发短时中断，健康秩全程无图重捕获，故障秩异步初始化。EEP 重集成机制对故障规模不敏感，始终保持短时中断特性，可快速恢复全量吞吐量，适配大规模 Mo 集群动态扩容需求。
:::

两个中断窗口在所有测试规模下都保持在可控范围内。每个故障恢复过程都呈现相同的阶段特征：

- 故障发生前的稳定运行阶段；
- 故障发生后、系统开始恢复期间的一段零吞吐量时期（该时段长度有明确上限）；
- 恢复过程中服务能力暂时下降，但维持在可运行的降级水平；
- 故障节点完成修复并重新加入集群时，出现第二个短暂的零吞吐量时段（同样具有明确上限）。

**实测表明，这两个中断窗口的持续时间在所有测试规模下均稳定在几秒至十几秒之间，未随集群规模扩大而显著增长**。值得注意的是，整个过程中，健康节点的状态无需重建——它们持续正常运行，仅在短暂窗口内暂停处理新请求，内部状态保持一致且完整。

::: block-1
重集成过程不会影响健康节点的运行状态。:mdnice-bold-italic[第二个零吞吐量窗口，本质上是对“矛盾3”所提出设计原则的一次直接验证。当故障节点完成修复、准备重新加入集群时，健康节点仅在本地更新 GPU 上驻留的对等节点信息和路由表，并同步扩展活跃成员掩码——整个过程无需重新捕获 CUDA 图、无需触发全局同步屏障，也无需重新加载模型状态]。与此同时，恢复中的节点在完全隔离的环境中独立完成全部初始化流程，不干扰健康节点的关键计算路径。

这一阶段出现的、时长可控的短暂暂停，恰恰说明：健康节点能在不重启或不重新执行实例初始化的前提下，顺利接纳并整合重新加入的节点。
:::

与完整实例重启的对比是鲜明的。完整重启基线对应于单个不间断的 348 秒中断。EEP 的轨迹反而显示了两个短暂的中断，由一个功能性服务平台隔开。总服务中断时间要短得多，并且暂停之间的间隔代表真正的生产吞吐量，而不是强制停机。

## 六、相关工作对比

先前的工作针对静态 EP 执行、计划弹性或通信器级恢复；EEP 则针对宽 EP 服务的实时部分故障修复，而无需重建服务。

### 6.1 LLM 服务系统

> 现代 LLM 服务系统如 vLLM 和 SGLang 通过批处理、KV 缓存管理、调度和高效执行来提高吞吐量和延迟。两者都支持 MoE 服务，vLLM 还公开了 EP 后端、专家负载平衡和实验性弹性 EP 示例。

这些系统表明，宽EP（专家并行）已在实际服务中落地应用，但它们对外暴露的接口仍把EP成员关系当作控制平面的静态配置来处理，而非运行时需主动应对的容错问题。:mdnice-bold-italic[换言之，它们并未将EP秩（rank）因故障而停止服务所导致的损失，视为一个端到端的闭环问题——即：如何安全收缩规模、快速恢复专家可达性，并在不中断当前推理实例的前提下，待故障恢复后再平滑扩容。]

**EEP（弹性专家并行）并非替代方案，而是对上述能力的补充**。我们在SGLang中实现了EEP，但其核心贡献在于提供了一套底层机制，支持以故障为触发条件、在原地完成EP修复——无需重启或迁移，真正实现容错驱动的动态弹性。

### 6.2 通信库与 EP 后端

> 通信库如 NCCL 和 Gloo 在通信器或进程组抽象上提供高性能集合操作，其成员关系通常在稳态执行时固定。

最近的 NCCL 工作添加了 RAS 支持、通信器收缩和替换工作流，以及 NCCL-EP 中的面向 EP 的 API。**这些是重要的进步，但核心抽象仍然是通信器管理：当成员关系变化时，应用程序收缩或重新创建通信器并重建绑定到通信器的 EP 状态**。:mdnice-bold-italic[我们的目标更具体于服务：通过使对等成员关系成为显式可变运行时状态，在成员关系变化期间保持活 EP 实例有效。]

DeepEP 和 UCCL-EP 更接近 EP 设置。DeepEP 专注于所选 EP 组的高效分发和合并内核，而 UCCL-EP 针对跨硬件和软件环境的便携式 EP 通信。**两者都提高了 EP 通信效率，但都没有解决我们针对的恢复契约**。在我们的设置中，仅通信修复是不够的：节点故障还可以删除逻辑专家并使图可见路由状态无效。EEP 因此结合了对等集修复、专家覆盖修复和图稳定重集成。

### 6.3 MoE 弹性系统

> 另一项工作通过路由、内核或负载平衡来提高 MoE 效率，包括 DeepSpeed-MoE、Tutel 和 MegaBlocks。:mdnice-bold-italic[这些系统使 MoE 更快、更可扩展，但没有研究延迟敏感的 EP 实例在意外节点故障后如何保持正确和可用。]

更密切相关的是，面向服务的系统如 Expert-as-a-Service（EaaS）和 ElasticMoE 研究 MoE 服务的可扩展部署、自动缩放和专家放置。关键区别在于恢复契约：计划缩放容忍控制平面编排，而部分故障修复必须在解码路径上反应，快速重新建立有效的缩减容量实例，并稍后恢复容量而不重建整个实例。

因此，本文不是关于通用弹性，而是关于**在部分故障下保持活 EP 有效性。**

## 七、结论与展望

> 宽专家并行中的部分故障容忍本质上是一个活 EP 有效性问题。EEP 不是在节点丢失后重建 EP 实例，而是修复使实例无效的对等集、专家覆盖和路由状态。:mdnice-bold-italic[我们的结果表明，宽 EP 推理不必将部分故障视为全局中断：服务可以收缩、保持有用，并稍后恢复容量，而无需完全重建。]

未来的工作方向包括：

1. **扩展故障模型**：支持更复杂的故障模式，如静默数据损坏、网络分区和拜占庭故障。
2. **优化大规模故障恢复**：进一步提高在多个节点同时故障时的恢复性能。
3. **与调度系统集成**：将 EEP 与集群调度系统集成，实现自动故障检测和节点替换。
4. **探索轻量级专家冗余策略**：结合故障特征优化专家分布，在成本与可用性间取得平衡。

::: block-1
EEP 为大规模 MoE 推理服务的高可用设计提供了关键思路，显著提升了故障场景下的服务稳定性。随着 MoE 模型成为 AI 基础设施的核心，像 EEP 这样的容错技术将变得越来越重要，确保我们的 AI 服务即使在面对不可避免的硬件故障时也能持续可靠地运行。
:::
