## 一、为什么 GPU 上的 Rust 安全编程是个硬骨头？

> 在系统编程领域，Rust 的安全承诺早已深入人心：不用垃圾回收，不用运行时检查，仅凭编译期的所有权与借用规则，就能从根源上消灭数据竞争与内存安全漏洞。**但这份安全红利，长期以来只停留在 CPU 侧。一旦涉及 GPU 加速，Rust 程序员就不得不踏入 unsafe 的世界，亲手管理线程同步、内存别名与边界检查，和写 CUDA C++没有本质区别**。

### 1.1 Rust 的安全基石：所有权与借用

Rust 安全体系的核心规则可以用一句话概括：别名 XOR 可变。:mdnice-bold-italic[也就是对于同一个值，同一时间内，要么只能存在一个可变引用，要么可以存在任意数量的不可变引用，二者不能同时成立。]

::: block-1
这个规则的通俗理解很简单：就像一本纸质笔记，**要么你一个人可以在上面涂改书写，要么所有人都只能翻开阅读**。不能有人正在写的时候，还有人凑过来读，否则可能读到写了一半的脏内容；更不能多个人同时往同一个位置写，否则内容会互相覆盖，谁也不知道最终结果是什么。
:::

Rust 的借用检查器会在编译期验证这条规则，不需要任何运行时开销，就能保证线程安全。对于 CPU 上的多线程编程，Rust 提供了不同层级的抽象：

- 能静态证明安全的就用安全抽象，比如迭代器并行；
- 不能静态证明的就加运行时检查，比如互斥锁；实在需要手动控制的，就提供 unsafe 入口，由程序员保证不变量。

这套分层设计让 Rust 既安全又灵活。

### 1.2 GPU 编程模型和 Rust 安全的天然错位

> GPU 的编程模式和 CPU 多线程有本质区别，这也是 Rust 安全规则难以直接落地的根源。

一套完整的 GPU 程序分为主机和设备两部分。主机运行在 CPU 上，负责分配设备内存、准备内核参数、向设备提交计算任务；设备运行在 GPU 上，以单程序多数据的模式启动成千上万条线程，所有线程从同一个入口函数开始执行，仅通过内置的线程坐标区分身份。内存访问的合法性、线程间的同步、数据竞争的规避，全部由程序员手动保证。

> 这种模型和 Rust 安全体系的冲突体现在三个层面。

| 问题类别 | 具体表现 | 根本原因 |
| --- | --- | --- |
| **边界类型坍缩** | Rust 的类型、所有权与生命周期信息在内核启动瞬间被压缩为原始指针和整数标量；设备端仅接收裸指针，主机端安全约束无法传递，借用检查器失效。 | 内核加载机制剥离高级类型元数据，GPU 运行时无 Rust 运行时支持。 |
| **跨线程别名无法验证** | GPU 上万级并发线程共享显存，Rust 借用检查器无法感知线程存在，亦无法静态验证别名访问合规性；运行时别名检查开销不可接受。 | 借用检查器设计面向 CPU 单/多线程模型，缺乏对 GPU 大规模并行执行上下文的建模能力。 |
| **内存排序语义断裂** | GPU 编译器激进重排内存操作以优化性能；CUDA C++ 依赖显式屏障、原子操作与栅栏保障顺序，而 Rust 引用隐含的内存顺序语义无法映射至 GPU 内存模型。 | Rust 的内存模型基于 CPU 顺序一致性假设，与 GPU 弱一致性、显式同步的硬件语义不兼容。 |

### 1.3 现有 Rust GPU 方案的局限

> 过去几年已经有不少项目探索 Rust 的 GPU 编程能力。:mdnice-bold-italic[rust-gpu、Rust-CUDA、cuda-oxide 等项目，分别通过不同的代码生成路径，证明了 Rust 代码可以编译成高效的 GPU 机器码。但这些项目都有一个共同的问题：它们解决了“能跑”的问题，却没有解决“安全”的问题，所有内核本质上都被当作 unsafe 代码处理。]

主机端的 AI 框架走了另一条路。Candle、Burn 等 Rust 原生框架提供了安全的主机端张量 API，把底层的 CUDA 调用封装起来。**但这种安全只停留在主机调用层，一旦需要编写自定义高性能内核，开发者还是要写 unsafe 代码，或者调用外部的 CUDA 库，内核本身的安全性无法验证。**

CubeCL 等项目支持跨后端的 Rust 内核编写，但采用的是 SIMT 风格的编程模型，没有基于所有权的分区安全机制，依然需要开发者手动保证数据不竞争。

**换句话说，现有方案要么让 Rust 只做主机端的“外壳”，要么让设备端代码裸奔在 unsafe 里，始终没有把 Rust 最核心的所有权安全体系，真正落地到 GPU 内核编程中**。这正是 cuTile Rust 要解决的核心问题。

::: block-1
GPU 的 SPMD 执行模型、主机设备边界的类型坍缩、内存排序的显式管理，三者共同构成了 Rust 安全语义向 GPU 延伸的核心障碍。现有方案仅实现了 Rust 代码在 GPU 上的可运行性，并未将所有权安全体系真正落地到内核编程中。
:::

## 二、cuTile Rust 的核心设计：把所有权契约搬上 GPU

> 直接把 Rust 的借用检查套到 GPU 的 SIMT 线程上，既不现实也没必要。GPU 内核的主流计算模式是张量操作，而张量操作天然可以按 Tile 进行分块。:mdnice-bold-italic[cuTile Rust 的核心洞察正在于此：不用去管每一个 GPU 线程的安全，而是把编程抽象提升到 Tile 级别，用“输出分区+单线程语义”的结构，让 Rust 的所有权规则自然适配 GPU 的并行模型。]

### 2.1 Tile 编程模型：安全的切入点

Tile 即瓦片或者分块，是张量运算中固定大小的小数据块。Tile 编程模型的思路是，把大的张量运算拆分成一个个小 Tile 的运算，程序员只需要编写单个 Tile 的顺序处理逻辑，编译器负责把这些 Tile 程序映射到 GPU 的线程块上，自动管理共享内存、并行分解、内存访问调度。

比如最常见的矩阵乘法，就是把大的 M×K 和 K×N 矩阵，拆成若干 BM×BK 和 BK×BN 的小 Tile，逐个计算小矩阵乘法再累加。程序员不用管底层有多少线程、数据怎么在共享内存和全局内存之间搬移，只需要关注 Tile 层面的计算逻辑。

> 这种模型恰好为安全检查提供了完美的切入点，原因有三点。

| 特性 | 说明 |
| --- | --- |
| **单线程语义** | Tile 程序采用顺序执行模型，程序员无需处理多线程同步；安全验证对象从数万并行线程简化为单个顺序程序，显著降低验证难度。 |
| **输出天然可分区** | 绝大多数张量运算的输出可划分为互不重叠的子块，每个 Tile 程序仅写入其对应子块，天然满足 Rust 的“可变引用互斥”规则。 |
| **安全检查零开销** | 常见分区访问合法性（如边界检查、分区独立性）可在编译期完成形式化验证；GPU 热路径中无需运行时判断，避免性能损耗，保障核心计算效率。 |

> 论文中的逐元素加法例子，直观展示了 cuTile Rust 的编程体验。

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/06.webp)

### 2.2 主机-设备边界的所有权映射

> 所有权规则要跨主机和设备生效，首先要解决的就是**启动边界的类型映射问题**。cuTile Rust :mdnice-bold-italic[通过过程宏自动生成内核启动代码，定义了一套完整的主机类型到设备类型的映射协议。]

这套协议的核心是两阶段生命周期：准备阶段和恢复阶段。

- 内核启动前，prepare 方法将主机端的张量类型转换成 GPU 可以接收的底层形式，同时交出主机端的访问权限；
- 内核执行完成后，recover 方法将底层形式还原成原始的主机类型，归还所有权和借用。整个过程的生命周期都由 Rust 借用检查器验证，不会出现悬垂引用或所有权泄露。

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/07.webp)

::: image-caption
表 1：内核启动边界处的主机到设备类型映射。每一行展示主机端Rust类型、对应的设备端内核参数类型，以及借用检查器强制执行的所有权语义。表中P、MP、MT<T,S,M>分别是Partition、MappedLaunchPartition<Partition>、MappedPartitionMut<T,S,M>的缩写。带有移动语义的条目会将主机张量转移到内核启动中；设备上的Tile程序随后通过排他的可变引用（分区时）或共享引用（未分区时）访问张量。这张表是cuTile Rust所有权跨边界的核心契约：可变输出必须以分区形式传入，确保设备端每个Tile程序拿到的都是排他的可变子张量；不可变输入可以共享广播，所有Tile程序都能只读访问。输入输出的所有权形式在启动前后完全一致，借入的张量归还借入，Arc张量归还Arc，完全契合Rust开发者的使用习惯。
:::

**这套映射还有一个关键不变量：同类型进，同类型出**。传入什么所有权形式的张量，执行完成后就返回什么形式。传入独占的张量就返回独占张量，传入借用就返回借用，传入 Arc 就返回 Arc。:mdnice-bold-italic[这样一来，整个启动-执行-返回的生命周期，都可以被 Rust 的借用检查器完整检查，不会破坏主机端的所有权规则。]

::: block-1
**需要注意的是，底层的 execute 方法本身是 unsafe 的**。因为内核启动是异步的，execute 返回的时候，GPU 的写入可能还在进行，如果直接把张量还给主机，就可能出现主机和 GPU 同时访问同一块内存的数据竞争。而对外暴露的 sync 方法会先等待流同步，确认 GPU 写入完成后再返回张量，因此是安全的。**这正是 Rust 典型的安全封装思路：底层用 unsafe 实现细节，对外暴露安全 API，不变量由库内部保证。**
:::

### 2.3 分区与令牌排序：从结构上消灭数据竞争

> cuTile Rust 的安全保障来自两个核心机制的配合：跨 Tile 程序的分区不相交，和单个 Tile 程序内的令牌（这里的令牌就是字面意思令牌👀）内存排序。前者解决多个程序之间的写冲突，后者解决单个程序内的操作顺序问题。

**分区不相交的原理非常直观。可变输出张量在启动前，会被切分成若干互不重叠的子张量，每个 Tile 程序对应唯一的一个子张量，拿到排他的可变引用**。就像一块完整的蛋糕，提前切成大小均匀的小块，每个人拿到属于自己的那一块，只能吃自己手里的，不可能抢到别人的，自然也就不会产生写冲突。

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/08.webp)

::: image-caption
图 2：主机到设备的分区示意。Partition<Tensor>为每个Tile程序分配一个排他的可变子张量（一对一映射）；&Tensor向所有Tile程序广播共享的只读张量视图。可变单元用玫瑰色标注，共享区域用青色标注。这张图直观展示了安全并行的核心原理：写操作被严格分区隔离，每个程序只拥有自己的写入范围；读操作可以全局共享，因为只读不会产生冲突。这正是Rust“别名XOR可变”规则在GPU上的直接映射。
:::

不可变的输入张量则不需要分区，直接广播给所有 Tile 程序作为只读引用。因为只读访问不会产生冲突，任意多个程序同时读同一块内存都是安全的，这也完全符合 Rust 的借用规则。

::: block-1
解决了跨程序的冲突，还要解决单个程序内的内存顺序问题。Tile IR 的内存模型默认允许编译器自由重排内存操作，如果没有顺序约束，同一个程序里对同一个可变张量的读和写可能被重排，导致逻辑错误。比如先读取旧值、累加计算、再写回新值的操作，如果被重排成先写后读，结果就会完全错误。
:::

cuTile Rust 用令牌链机制解决这个问题。:mdnice-bold-italic[所有对可变张量的读写操作，都会被编译器自动串上一条令牌链：前一个操作产生的令牌，是后一个操作的必要输入。这条令牌链建立了明确的先后发生关系，保证操作不会被编译器重排。而对不可变张量的读操作，不会附加令牌约束，编译器可以自由重排优化性能。]

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/09.webp)

::: image-caption
图 3：单个Tile程序内的令牌排序示意。Ti是Tile程序的可变子张量，对它的操作通过令牌串联，建立先后发生关系；共享的只读张量操作没有令牌约束，编译器可自由重排。可变引用对应有序操作，不可变引用对应无序优化，这完美对应了Rust引用类型的语义：&mut需要保证顺序一致性，而&可以尽情重排优化。程序员只需要按普通Rust的习惯写代码，编译器自动在底层处理内存排序。
:::

> **这两套机制结合，从结构上消灭了一整类数据竞争 bug**。论文中举了一个 cuTile Python 的真实 bug 案例（见 Listing 5）：程序员在写注意力头置换内核时，不小心把存储索引的两个维度写反了，导致多个 Tile 程序写入同一个目标位置，产生数据竞争，每次运行的结果都有 17%到 35%的元素不一致。:mdnice-bold-italic[而在 cuTile Rust 中，存储操作的目标就是分区视图本身，根本不存在可以随意修改的存储索引，这种索引写反的 bug 从语法层面就写不出来。]

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/10.webp)

::: image-caption
Listing 5：cuTile Python 存在索引越界写竞争的错误内核。网格配置下多 tile 线程写入同一目标位置，产生未定义数据竞争行为。 本代码作为反面案例，反衬 cuTile Rust 分块所有权模型的安全优势。Python 版本需程序员手动计算存储坐标，极易出现维度交换错误，实验中 17%–35%输出元素随机出错；cuTile Rust 移除手动索引写入接口，`dst.store()`仅能写入当前 tile 程序独占的分块，不存在跨 tile 写同一显存地址的语法可能性。从形式化证明角度，原论文附录 A 基于 Tile IR 内存模型证明：安全 cuTile Rust 代码不存在此类跨线程冲突，将索引类数据竞争 Bug 在编译期彻底消除，无需运行时检测或形式化验证工具，降低大模型内核开发调试成本。
:::

### 2.4 映射分区：从单输出到多输出的安全扩展

> 每个 Tile 程序只写一个输出子块的模式，虽然足够简单安全，但无法支持一些更高效的调度。比如 GEMM 运算，如果每个程序只负责一个输出 Tile，就需要频繁重新加载 K 维度的输入数据，性能不够理想。更高效的做法是让每个 Tile 程序负责多个输出 Tile，复用加载的 K 维度数据，提升计算密度。

**映射分区就是为了解决这个问题而设计的**。输出张量依然被切分成互不重叠的子块，但是每个 Tile 程序会被映射到一组子块，这组子块只属于当前程序，和其他程序的范围完全不相交。程序通过迭代器遍历自己的所有子块，迭代器产生的是带品牌的 PartitionIndex 值，和对应的分区深度绑定。

带品牌（Brand）索引的核心价值在于，编译器可以通过类型系统证明索引的合法性和不相交性，不需要在热循环里加动态边界检查。比如 GEMM 的 K 维度迭代器，编译器知道它的取值范围，加载操作就不需要额外的运行时边界判断。

> 论文中的 GEMM 内核示例清晰展示了这种写法。

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/11.webp)

::: image-caption
Listing 6：基于映射分块的 GEMM 内核。`z.iter_indices` 生成互不重叠的输出 tile 索引，K 轴迭代器提供静态有界维度，热循环无动态边界校验。 普通单 tile 单线程 GEMM 会重复加载 K 维度共享权重，访存效率低下；MappedPartitionMut 允许单个 tile 程序遍历多块输出，复用共享 K tile 提升张量核心利用率。编译器通过带标记 PartitionIndex 迭代器静态证明所有输出 tile 互不相交，删除循环内的动态边界判断，在 B200 f16 矩阵乘法测试中性能达到 cuBLAS 的 96.4%，与裸指针 unsafe 实现性能误差小于 0.3%。该抽象平衡安全与计算效率，是 cuTile Rust 支撑 Grout 推理引擎高效 Qwen3 GQA、线性层融合的底层核心，同时保留局部 unsafe 出口用于极致定制算子。
:::

这样的设计既保留了高效的调度方式，又维持了完整的安全保证，而且没有引入任何运行时开销。

**当然，安全 API 不可能覆盖所有场景。cuTile Rust 也提供了明确的“逃生舱”：可以用 unchecked_accesses 关掉边界检查，或者直接使用裸指针操作底层 Tile IR**。这些都需要放在 unsafe 块中，明确标记出不安全的范围。安全是默认选项，不安全是显式的局部选择，这完全符合 Rust 的设计哲学。

实际项目中也正是这么用的。Grout 推理引擎里，简单的逐元素运算、嵌入查找、argmax 都用安全 API 实现，而性能最关键的注意力内核、融合归一化内核，则通过逃生舱做极致优化。

::: block-1
cuTile Rust 通过 Tile 级抽象将 GPU 并行的安全问题简化为两个可解的子问题：跨程序的输出分区不相交，和单程序内的令牌内存排序。映射分区与带品牌索引的设计，进一步在不引入运行时开销的前提下，将安全表面扩展到了多输出子块的复杂调度场景。
:::

## 三、系统实现与执行模型

> 一套安全的编程模型，不仅要在类型层面自洽，还要有高效的实现和灵活的执行方式，适配不同的业务场景。**cuTile Rust 构建了从 Rust 源码到 GPU 机器码的完整编译链路**，:mdnice-bold-italic[同时提供了统一的惰性执行抽象，支持同步、异步、CUDA 图三种执行模式，一套内核代码可以无缝切换不同的运行方式。]

### 3.1 编译与 JIT 链路

cuTile Rust 的完整编译流程分为两个阶段：Rust 编译期和运行时 JIT。

- 在 Rust 编译阶段，`#[cutile::module]`过程宏会处理标注的内核模块，完成三件事。第一，生成脱糖（desugared）后的普通 Rust 代码，交给 rustc 进行类型和借用检查，保证内核代码本身符合 Rust 的安全规则。第二，生成类型安全的主机端启动接口，也就是开发者调用的内核函数。第三，将内核的抽象语法树提取出来，嵌入到编译好的主机二进制中。
- 到了运行阶段，第一次启动某个内核时，运行时系统会加载嵌入的抽象语法树，将其编译为 Tile IR，再进一步编译成 GPU 可执行的 cubin 文件，缓存起来。后续再启动同一个内核，就可以直接使用缓存的机器码，不需要重复编译。

**采用运行时 JIT 而非编译期直接生成机器码，主要是因为 Rust 的过程宏运行在类型检查和单态化之前，很多特化信息比如具体的张量形状、类型参数，要到实际启动时才能确定**。运行时 JIT 可以根据实际参数做针对性优化，生成更高性能的机器码。

为了降低用户的使用负担，cuTile Rust 用秩多态的 trait 把不同维度的生成结构封装起来。开发者写内核时不用关心张量的具体维度，直接调用通用的操作名即可，编译器会自动推断维度并分发到对应的实现。目前该系统的张量 API 仍在持续拓展完善中，功能边界与编程接口处于迭代演进状态。

### 3.2 三种执行模式：同步、异步、CUDA 图

> **cuTile Rust 所有的 GPU 计算，都统一在 DeviceOp 这个 trait 之下。DeviceOp 代表惰性的、带类型的 GPU 工作，它会持有操作数的所有权或借用，携带完整的生命周期信息**。多个 DeviceOp 可以组合拼接，形成更复杂的计算流水线，整个组合过程都不会真正执行，直到调用终端操作才会提交给 GPU。

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/12.webp)

::: image-caption
Listing 2：DeviceOp trait 及加法启动器自动生成的 execute 实现。execute 存在不安全风险，而安全的 sync 接口会同步 GPU 流并归还张量所有权。
:::

这种设计和 Rust 的迭代器非常相似：迭代器的各种组合子只是构建结构，不会产生计算，直到调用 collect 才真正执行。好处是类型系统可以在执行前就验证整个流水线的合法性，而且同一条流水线可以适配不同的执行模式。

> cuTile Rust 提供三种主流执行模式。

| 执行模式 | 说明 |
| --- | --- |
| **同步执行** | 通过 `.sync()` 方法调用。提交内核后阻塞当前线程，等待 GPU 执行完成再返回结果。适合逻辑简单、无需重叠主机工作的场景，是最常用默认模式。 |
| **异步执行** | 通过 Rust 的 `.await` 语法调用。启动内核后不阻塞，当前任务让出控制权，主机线程可并发处理 IO、逻辑判断、工具调用等；GPU 完成后恢复后续逻辑。适合主机与 GPU 需协同工作的场景，如流式语音识别、Agent 交互等。 |
| **CUDA 图模式** | 通过 `.graph()` 方法调用。将固定计算流水线捕获为 CUDA 图，支持高效重复重放，消除每次内核启动的主机端开销。适合重复执行的确定性计算流程，如 LLM 解码的单步前向传播（每步逻辑一致），可显著降低延迟。 |

## 四、性能实测：安全会不会拖后腿？

> 安全设计再精巧，如果性能掉一截，工业界也很难买账。**GPU 编程的核心诉求就是性能，任何安全抽象都不能以牺牲速度为代价。** cuTile Rust 的评测核心问题非常明确：**这些安全机制到底有没有运行时开销？这套系统能不能支撑真实的工业级工作负载？** 论文用微基准和端到端推理两组实验给出了答案。

### 4.1 微基准测试：安全零开销的验证

微基准测试在 NVIDIA DGX B200 上进行，选取了两个最具代表性的工作负载：内存受限的逐元素加法，和计算受限的通用矩阵乘法。测试对比四个版本：安全 Rust 实现、unsafe Rust 裸指针实现、cuTile Python 实现，以及 cuBLAS 厂商库基线。

**逐元素加法是典型的内存带宽受限场景，主要考验内存访问的效率**。测试使用 2 的 28 次方个 f16 元素，统计有效带宽。:mdnice-bold-italic[测试结果显示，安全 Rust 版本和 unsafe Rust 版本都达到了 7.02 TB/s 的带宽，cuTile Python 版本为 7.01 TB/s，三者几乎没有差别，非常接近 B200 的 7.68 TB/s 理论峰值带宽。]

**矩阵乘法是典型的计算受限场景，主要考验张量核心的利用率**。测试 M、N、K 从 1024 到 32768 的 f16 矩阵，统计计算吞吐量。在 M=N=K=8192 的尺寸下，:mdnice-bold-italic[安全 Rust 版本达到 2.07 PFlop/s，相当于 B200 稠密 f16 理论峰值的 92%，达到 cuBLAS 性能的 96.4%；unsafe Rust 版本和它的差距仅为 0.3%，完全在测量噪声范围内；cuTile Python 版本达到 2.04 PFlop/s，为 cuBLAS 的 94.9%。]

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/15.webp)

::: image-caption
图 5：安全开销微基准与JIT开销。左图为内存受限的逐元素加法带宽，中图为计算受限的GEMM算力，右图为首次使用的JIT编译开销。“Python”和“Rust”分别指cuTile Python与cuTile Rust，虚线为硬件峰值。误差条展示逐元素加法的25到75分位区间，以及GEMM的时间标准差转换后的算力波动。这组数据最核心的结论是“安全零开销”：安全Rust版和unsafe裸指针版的性能差异在测量噪声范围内，无论是内存 bound 还是计算 bound 场景都是如此。这意味着cuTile Rust的所有安全检查都在编译期完成，没有给运行时增加任何负担。同时Rust和Python两个前端共享同一个Tile IR后端，最终性能处于同一水平。
:::

这组微基准测试给出了**非常明确的结论：cuTile Rust 的所有安全机制，包括分区检查、带品牌索引、令牌排序，都没有引入可测量的运行时开销。安全和性能在这里实现了真正的统一。**

当然，运行时 JIT 会带来首次启动的编译开销，开销大小随 Tile 尺寸增长。但这是一次性成本，编译后的内核会被缓存，后续调用直接复用，不会重复产生开销。对于长期运行的服务端负载来说，这部分成本几乎可以忽略。

### 4.2 执行模式开销对比

> 执行模式的测试在 NVIDIA GeForce RTX 5090 上进行，测试不同长度的计算流水线下，三种执行模式的单操作延迟。流水线由 N 个逐元素乘法内核串联而成，计算量很小，启动开销占主导地位。**测试结果清晰地划分出三个成本区间。**

| 同步模式 | 开销说明 |
| --- | --- |
| 单独同步模式 | 开销最高，每个内核启动后都单独同步，稳定在约 7.3 微秒/操作；主要开销来自每次启动和同步的系统调用。 |
| 链式同步模式 | 开销次之，整条流水线仅在末尾同步一次，分摊后约 3.4 微秒/操作。 |
| 异步模式 | 开销与链式同步相近（约 3.4 微秒/操作），因存在固定回调成本，在短流水线时表现更差；随流水线增长，成本被摊销，性能与链式同步基本持平。 |
| CUDA 图重放 | 开销最低，约 0.8 微秒/操作；完全消除主机端每次启动开销，仅保留 GPU 端调度成本，接近硬件调度极限。 |

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/16.webp)

::: image-caption
图 6：RTX 5090上执行模式的扩展性。纵轴为N内核流水线的单操作延迟，线条为最小值，色带为最小值到75分位区间。这组数据展示了三种模式的成本梯度：同步最简单但开销最高，异步适合主机有并发工作的场景，CUDA图适合重复执行的短流水线。开发者可以根据自己的业务场景选择，不用修改内核代码。}
:::

::: block-1
论文附录还补充了异步重叠测试的结果：**当主机端有并发计算工作时，异步模式可以让主机计算和 GPU 执行完全重叠，最高能达到接近 2 倍的吞吐量提升**。:mdnice-bold-italic[对于流式交互、工具调用这类主机和 GPU 交替工作的场景，异步模式能显著提升整体资源利用率。]
:::

### 4.3 端到端推理：Grout 引擎的实战表现

> 微基准只能说明基础能力，真正的考验来自真实的工作负载。**为了验证 cuTile Rust 的实用性，研究团队基于它构建了一个专门的 Qwen3 推理引擎 Grout，主打单批量场景的高吞吐量，并和业界主流的 vLLM、SGLang 做对比。**

测试分为两组：RTX 5090 显卡运行 Qwen3-4B 模型，B200 显卡运行 Qwen3-32B 模型，均使用 f16 精度，单批量，关闭前缀缓存。测试指标包括预填充延迟随提示词长度的变化，以及解码吞吐量随生成长度的变化。

为了合理评估性能，论文计算了 HBM Roofline 作为理论参考上限，公式如下：

$$
R = \frac{\beta}{W + \bar{K}}
$$

其中 R 代表每秒生成的 token 数，β 是设备内存的理论峰值带宽，W 是模型权重的总字节数，$\bar{K}$ 是平均每个生成 token 需要读取的 KV 缓存字节数。这个公式的物理意义很直观：当解码阶段完全被内存带宽限制时，单位时间能处理的数据总量就是带宽，除以每个 token 需要读取的数据量，就是单位时间能生成的 token 数。就像一根水管的最大流量，等于水管的横截面积乘以流速，再除以每个水滴的体积。

::: block-1
测试结果显示，在 RTX 5090 + Qwen3-4B 的配置下，:mdnice-bold-italic[Grout 的预填充延迟在所有提示词长度下都是最低的，解码吞吐量也最高]。**生成长度为 8192 token 时，Grout 的解码速度达到 154.7 token 每秒，达到 Roofline 估计值的 74.7%。峰值解码速度可达 171 token 每秒，在消费级显卡上实现了接近云端的推理体验。**
:::

在 B200 + Qwen3-32B 的配置下，更大的模型让所有引擎都更接近内存带宽瓶颈，三者的差距有所缩小。

- Grout 依然保持最高的解码吞吐量，生成长度 8192 时达到 80.1 token 每秒，**为 Roofline 估计值的 66.7%，峰值可达 82 token 每秒；**
- **同期 vLLM 为 77.5 token 每秒，SGLang 为 76.5 token 每秒。** 在提示词长度达到 8192 时，三者的解码吞吐量基本收敛。

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/01.webp)

::: image-caption
图 7：Qwen3单请求性能（f16，批量1，中位数带四分位距阴影，禁用前缀缓存）。左组为RTX 5090/Qwen3-4B，右组为B200/Qwen3-32B。每个子图左侧展示预填充延迟随prompt长度的变化（生成36 token），右侧展示解码吞吐量随生成长度的变化（prompt长度18）。端到端结果证明cuTile Rust完全可以支撑工业级LLM推理工作负载。Grout作为一个模型专项优化的引擎，在batch=1解码场景下达到了和vLLM、SGLang相当甚至更优的性能，说明这套安全编程模型在真实 workload 下没有性能短板。
:::

**Grout 的性能优势，主要来自紧凑的单请求运行时、针对 Qwen3 的算子融合、CUDA 图重放、设备端贪心选 token，以及极低的调度和缓存管理开销**。其中非 GEMM 的简单内核使用安全 API 实现，:mdnice-bold-italic[性能关键的注意力和融合归一化内核使用“逃生舱”优化，大的矩阵乘则直接调用 cuBLAS，是一套非常务实的工程实现。]

![文章插图](/articles/2026-06-19-vllm-sglang-cutile-rust-gemm-4cf426a0/images/17.webp)

::: image-caption
图 8：异步调度补充实验结果。(a)固定 GPU 流水线下改变主机计算量的吞吐；(b)大小混合 GEMM 任务在串行/多线程/单线程异步调度下吞吐；(c)16 流道下主机计算量对吞吐的影响。 该补充实验论证异步执行模式在主机 CPU 资源受限场景的价值。当主机存在语音预处理、工具调用等并发任务时，异步协程可在 GPU 运行时释放 CPU，吞吐提升近 2 倍；多线程方案需为每个 CUDA 流分配独立 OS 线程，占用大量主机核心，嵌入式 GPU 设备资源不足时性能暴跌。单线程异步依托协作式调度复用 CPU 核心，8 流道后吞吐与多线程持平，主机 CPU 占用仅为其 1/S。面向对话式、流式推理等异构负载，cuTile Rust 异步 API 可降低服务器 CPU 资源开销，提升整机硬件利用率，是面向下一代智能体推理场景的关键优化特性。
:::

**从微基准到端到端推理，cuTile Rust 的安全机制均未引入可测量的运行时开销**。GEMM 达到 cuBLAS 的 96.4%，基于其构建的 Grout 推理引擎在单批量解码场景下性能对标 vLLM 与 SGLang，验证了这套系统的工业级实用价值。
:::

## 意义与局限：这一步到底有多远？

> cuTile Rust 不是第一个尝试 Rust GPU 编程的项目，但它是目前少数在 Rust 原生类型体系内，将所有权安全机制深度落地到 GPU 内核编程、同时达到工业级性能水平的代表性工作。**它的价值不止于写内核更安全，更在于为整个 Rust AI 基础设施栈提供了从主机到设备的完整安全语义，降低了高性能 GPU 代码的维护成本与 bug 风险。**

### 5.1 对 Rust GPU 生态的价值

cuTile Rust 的出现，填补了 Rust GPU 生态的一块核心空白。

在此之前，Rust 在 GPU 计算中始终扮演“主机端胶水”的角色。核心的自定义内核要么用 CUDA C++编写，要么用 Triton 等 Python DSL 编写，Rust 只负责调用和调度。这意味着整个系统的安全边界停留在主机层，内核里的内存越界、数据竞争、同步 bug，Rust 的安全体系完全管不到，依然需要靠人工测试和排查。

- **cuTile Rust 第一次让 Rust 的安全语义贯穿了主机和设备**。大部分张量内核都可以用安全代码编写，只有极端性能优化的场景才需要局部使用 unsafe。这大大缩小了不安全代码的表面积，降低了内核 bug 的概率，也降低了排查和维护的成本。:mdnice-bold-italic[对于 AI 推理引擎、AI 框架这类对稳定性要求很高的基础设施来说，这份价值非常重要。]
- **其次，统一的编程心智模型也降低了 GPU 开发的门槛**。Rust 开发者不用再学习一套完全不同的 GPU 编程范式，不用手动管理线程同步和内存别名，只用熟悉的所有权和借用思维，就能写出安全的 GPU 内核。编译器会负责处理底层的并行映射、内存调度、顺序保证。
- **第三，灵活的执行模型适配了非常广泛的场景**。从简单的同步调用，到协程异步，再到 CUDA 图重放，同一套内核代码不用修改就能适配不同的业务需求。:mdnice-bold-italic[尤其是异步执行模式，非常契合当下 Agent、流式交互、多模态推理等新场景，这些场景往往需要主机和 GPU 频繁交替工作，异步模式能在不增加线程的前提下提升资源利用率。]

### 5.2 现存局限与未来方向

> 当然，cuTile Rust 也不是万能的，它依然存在不少局限。

**最根本的局限来自 Tile 模型本身**。为了获得单线程语义和可验证的安全性，Tile 编程放弃了 SIMT 级别的精细控制，比如显式的 warp 原语、手动的共享内存管理。虽然 Tile IR 会自动做 warp 特化优化，但损失并没有完全消除。如何设计一个能和 Tile 编程无缝组合的安全 SIMT 模型，是未来需要解决的问题。

- 性能层面，部分矩阵尺寸下的 GEMM 和 cuBLAS 仍有差距，因此实际项目中还是会 fallback 到 cuBLAS。张量 API 的覆盖度也还不够完善，部分运算模式依然需要使用裸指针。目前张量 API 的覆盖度仍有不足，接口设计与功能边界还在持续演进完善。
- :mdnice-bold-italic[场景层面，目前的验证主要集中在张量运算和 LLM 推理，更通用的 GPU 计算场景覆盖还不足]。安全 API 的边界还需要持续拓展。

针对这些局限，论文也指出了几个未来方向。

- 第一是**继续扩大安全 API 的覆盖范围**，把注意力、融合归一化这些现在需要 unsafe 的内核，也纳入带品牌索引和有界迭代器的安全抽象中，零成本地缩小不安全代码的范围。
- 第二是**深化异步调度能力**，优化 GPU 工作、主机工作、IO、控制响应高度重叠的异构场景。
- 第三是**将分区思想扩展到多设备**，让每个 GPU 拥有一个分区，集合通信和 P2P 原语也融入借用系统中。

::: block-1
总体来看，**cuTile Rust 走出了 Rust 安全 GPU 编程的关键一步，第一次在工业级性能水平上验证了“安全与高性能可兼得”的可能性**。随着 AI 基础设施对可靠性、可维护性的要求越来越高，这套基于所有权的 Tile 编程模型，很可能成为未来 Rust GPU 生态的核心发展方向之一。
:::
