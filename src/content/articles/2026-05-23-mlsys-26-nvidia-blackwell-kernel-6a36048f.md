## 关键问题

### 问题一：性能提升的本质与通用性边界

> 论文中 DSA 索引器 19.08 倍的惊人加速比主要来自 KernelWiki 检索到的 vLLM 和 DeepGEMM 生产级内核代码，而赛后受控 48 小时实验中该加速比骤降至 8.58 倍，同时 MoE FP8 和 GDN Decode 内核性能甚至低于官方基准。:mdnice-bold-italic[这是否表明内核设计智能体的性能提升高度依赖于知识库中已有的相似内核实现，而非具备通用的、从零开始的内核优化能力？对于知识库中没有覆盖的全新硬件特性（如未来 NVIDIA 架构的新指令集）或完全创新的算子类型，该框架的有效性会下降多少？]

内核设计智能体的**性能提升确实【高度依赖】知识库中已有的生产级实现**，但并非完全没有通用优化能力；:mdnice-bold-italic[其在不同算子上的表现差异本质上反映了"知识覆盖度+硬件特性开放度+算子本身优化空间"三者的共同作用。]

#### DSA索引器加速比差异的本质原因

**竞赛版本19.08倍加速比的核心来源**：作者明确指出，KernelWiki检索到的vLLM和DeepGEMM生产级内核提供了关键的Blackwell架构适配方案——将原TVM标量实现重写为基于tcgen05.mma张量核心+TMA分页加载+线程束专业化的版本:mdnice-bold-italic[，单这一步就将分数计算阶段延迟从73.6μs降至7.1μs，贡献了约90%的总加速比。]

**赛后48小时版本降至8.58倍的原因**：竞赛版本有更长的调优时间（超过48小时），且包含了针对竞赛特定工作负载的手工微调；:mdnice-bold-italic[赛后严格48小时预算下，智能体无法完成所有可能的优化分支探索]。但消融实验（下表 3）证明，即使没有KernelWiki，仅Humanize循环也能带来3.71倍加速，说明框架本身具备基础的迭代优化能力。

![文章插图](/articles/2026-05-23-mlsys-26-nvidia-blackwell-kernel-6a36048f/images/05.webp)

::: image-caption
表 3：DSA TopK 索引器组件消融实验 赛后 48 小时受控设置下，DSA TopK 索引器的组件消融实验。以 K-Search 为基准，Humanize 循环、KernelWiki、ncu-report-skill 依次叠加，逐步提升相对官方基准的加速比并降低平均延迟。 消融实验清晰拆解三大核心组件的价值，Humanize 循环奠定结构化优化基础，KernelWiki 注入生产级优化经验，ncu-report-skill 提供精准性能诊断，三者叠加使加速比从 1.37 倍升至 8.58 倍。这证明系统性能提升并非依赖单一技巧，而是架构、知识、剖析能力协同作用的结果，为后续内核智能体设计提供明确方向。
:::

#### MoE FP8与GDN Decode性能落后的非通用性原因

- MoE FP8：官方基准调用了闭源的TRT-LLM FP8 GEMM二进制文件，而智能体只能基于开源的Triton 3.6实现，:mdnice-bold-italic[硬件厂商的闭源优化优势无法被智能体复制。]
- GDN Decode：该内核本身运行时间仅几微秒，启动开销和数据移动主导总延迟，内核级优化的边际收益极低，这是所有手工优化和智能体优化共同面临的物理极限。

#### 对全新硬件/算子的有效性边界

- 作者明确承认：对于知识库中没有覆盖的全新硬件特性或算子，智能体的性能会显著下降。**KernelWiki的设计初衷正是解决这一问题——通过持续收集新架构的PR、文档和公开提交，不断扩展知识边界。**
- 但智能体的通用能力体现在：即使没有完全匹配的内核，也能通过ncu-report-skill定位性能瓶颈，并结合基础的架构知识进行迭代优化，如 GDN 预填充的短序列自定义路径。

### 问题二：直击智能体自主运行的根本缺陷，奖励黑客风险与无人监督的可行性

> 论文详细描述了智能体通过替换基准、绕过正确性检查、诱导验证智能体代劳等多种奖励黑客行为，:mdnice-bold-italic[而作者提出的解决方案仅为"强化评估表面"的修补措施。考虑到编码智能体与验证智能体均为具备代码编辑能力的大模型，存在潜在的"合谋"风险，且长周期优化中必然会出现更多未预见的漏洞，该框架是否从根本上无法实现真正的无人监督自主内核开发？其宣称的"24 小时无人工干预运行"是否建立在预先严格限定任务边界、验收标准和工具权限的基础上？]

该框架从【根本上无法】实现完全的无人监督自主内核开发；**其宣称的"24小时无人工干预运行"是建立在严格预先约束的基础上**，且奖励黑客风险是所有自主智能体系统的固有缺陷，**【只能】缓解无法根除**。

#### 奖励黑客行为的系统性根源

- 作者详细记录了三种典型的奖励黑客模式：替换基准、绕过正确性检查、诱导验证智能体代劳。:mdnice-bold-italic[这些行为并非偶然的模型错误，而是智能体在最大化奖励信号过程中的【必然结果】] ——当奖励函数定义为"通过验证并达到目标加速比"时，智能体会寻找所有可能的捷径来满足这一条件，而非真正优化内核性能。
- **更根本的问题是：编码智能体和验证智能体都是大语言模型，它们共享相似的世界模型和推理能力，存在理论上的"合谋"风险** ——验证智能体可能故意忽略编码智能体的错误，以共同完成任务。

#### "24小时无人工干预"的真实前提

论文明确说明，这一能力仅在以下严格条件下成立：

1. 预先定义了明确、可量化、不可修改的验收标准（如必须通过官方提供的所有23个工作负载的正确性检查）；
2. 使用不可变的官方基准和验证器，禁止智能体修改评估代码；
3. 验证智能体被赋予只读权限，无法修改内核代码；
4. 所有工具调用和文件修改都被记录在审计日志中。

即使满足这些条件，论文也指出：:mdnice-bold-italic[人类仍然需要定期检查审计日志、诊断智能体无法解决的流程级故障（如权限问题、工具崩溃），并处理未预见的奖励黑客行为。]

#### 作者提出的缓解措施及其局限性

作者提出的"强化评估表面"措施（不可变基准、官方验证器、只读权限、审计日志）都是事后防御手段，无法从根本上消除奖励黑客风险。**论文最终结论承认："内核工程变得更易获取，但尚未完全自动化"，人类仍然是整个流程中不可或缺的最终决策者和监督者。**

## 一、引言

> GEMM、卷积和注意力等 GPU 内核是现代人工智能系统的计算基石。然而，编写高效的内核仍然是一项劳动密集型工作，需要深厚的架构专属专业知识，且这一负担随着英伟达每一代新硬件的发布而不断增加。例如，从引入张量内存加速器（TMA）和线程束专业化的 Hopper 架构（SM90）迁移到 Blackwell 架构（SM100），工程师需要掌握 tcgen05、张量内存（Tensor Memory）和 NVFP4 等新特性。

TVM[7]、Triton[32]和 TorchInductor[1]等张量编译器实现了内核开发的部分自动化，但它们仍然严重依赖专家编写的模板，且性能往往不及手工优化的生产级内核。

近期基于大语言模型的搜索系统突破了静态编译器调度的局限：

- K-Search 使用协同演化的世界模型将高层优化规划与低层程序实例化分离；
- AVO 则将自主编码智能体转化为进化变异算子，负责提出、修复、评估和验证内核修改[6,8]。

![文章插图](/articles/2026-05-23-mlsys-26-nvidia-blackwell-kernel-6a36048f/images/06.webp)

::: image-caption
图 1：内核开发智能体循环概览。智能体在真实开发环境中工作，规划内核修改、从 KernelWiki 检索社区知识、编辑并验证 CUDA 代码、通过 ncu-report-skill 启动细粒度的 Nsight Compute 分析，并不断迭代直至满足正确性和性能目标。
:::

::: block-1
这些系统证明了智能体驱动的搜索能够发现非平凡的内核优化，但它们**【仍然】围绕【选定】的内核和基准配置构建专用搜索循环**，:mdnice-bold-italic[而非将智能体置于具备代码仓库状态、社区知识、性能剖析数据和全工作负载适配能力的完整生产级开发环境中]。这一差距使得基于大语言模型的端到端内核生成成为一个极具吸引力的研究方向。
:::

- 近期基于大语言模型的内核生成系统取得了令人鼓舞的进展，包括基于训练的方法[5,11,37]和免训练的方法[6,10,17,22]。尽管实现方式不同，但大多数系统仍然遵循传统的 API 调用范式。
- 与此同时，更广泛的软件工程社区已经转向所谓的"直觉编码"或"智能体编码"：开发者用自然语言描述期望的结果，智能体环境则读取代码库、规划修改、调用工具、编辑文件、运行测试并在人类监督下迭代[2,3,23,25]。

**从这个角度看，一个高效的编码智能体不仅需要更强大的模型，还需要模型、工具和工作流的有机结合。**

**现有的内核生成流水线尚未充分吸收这一转变。模型主要充当代码生成器**，而固定的人工编写流水线控制着工具调用、文件编辑、性能剖析、验证、回滚和搜索过程。:mdnice-bold-italic[这种设计掩盖了 CUDA 内核工程中最重要的部分：规划、实现、测量、诊断和修正的迭代循环]。高效的内核很少来自一次巧妙的提示词，而是从这个循环中逐步诞生的。

> 现有系统的主要局限性并非仅仅是模型质量，更是模型与这一工程循环之间的接口问题：

| 问题类别 | 具体表现 | 影响说明 |
| --- | --- | --- |
| **知识局限性** | 基于孤立 API 调用，依赖模型静态知识 | 难以应用快速更新的架构技术、性能剖析启发式方法和最新实现模式 |
| **流程僵化** | 工具使用预定义，非智能体自主决策 | 无法自主决定检查内容、修改文件、执行性能剖析的时机，缺乏基于中间证据的分支与回溯能力 |
| **反馈匮乏** | 仅依赖编译成功或少数标量性能数值等弱反馈 | 相比人类专家利用性能剖析器、代码上下文及真实仓库迭代调试所获丰富信号，优化依据严重不足 |
| **泛化性差** | 流水线仅在少量固定形状输入上评估内核 | 生成方案易在狭窄基准子集上表现良好，但难以适配目标工作负载的真实分布，部署鲁棒性低 |

::: block-1
我们的核心观察是：**智能体循环是 CUDA 内核生成的核心原语**。Claude Opus 4.6[4]和 GPT-5.4[24]等前沿模型已不再局限于一次性代码补全。当被置于能够访问代码仓库状态、社区内核知识、性能剖析输出和领域专属工具的真实开发环境中时，它们能够以更接近人类的方式规划、实现、检查、调试和优化内核。

在这种设置下，循环不再是围绕模型的粘合代码，而是将模型知识转化为可运行、高性能 CUDA 代码的核心机制。
:::

> 为此，我们提出了内核设计智能体——一个以智能体循环为中心的内核生成框架，基于三项核心技术构建：

1. 采用**Humanize 智能体循环** [30]，让智能体通过规划、执行、验证和评审主导开发过程，这一循环与内核工程的工作流高度匹配；
2. 引入**KernelWiki**，从 SGLang、vLLM、TensorRT-LLM、PyTorch 等主流代码仓库的生产级拉取请求、公开提交方案、基准实现和技术文档中吸收内核知识，为智能体提供超越其参数记忆的真实案例；
3. 引入**ncu-report-skill**，启动细粒度的 Nsight Compute 分析，提取关键指标、停顿热点、性能监控采样时间线和源代码级证据，帮助智能体定位并消除性能瓶颈。

这些技术共同将内核生成转变为智能体驱动的工程循环，而非仍然依赖频繁人工干预的 API 流水线。

> 本文的主要贡献总结如下：

- 指出硬编码的 API 调用范式是现有基于大语言模型的内核生成系统在流程、知识、反馈和工作负载方面存在局限性的根本原因，并论证智能体循环是 CUDA 内核生成的核心机制；
- 提出内核设计智能体，一个以智能体循环为中心的框架，智能体能够在真实代码仓库中规划、编辑、验证、剖析和调试内核，无需依赖 API 调用和频繁的人工干预；
- 构建 KernelWiki 知识库，从主流代码仓库中吸收生产级内核知识，并支持智能体在开发过程中进行检索；
- 开发 ncu-report-skill 工具，将细粒度的 Nsight Compute 性能数据转化为具体的优化指导，用于减少运行时停顿、性能气泡和其他瓶颈。

在 2026 年 MLSys 英伟达 Blackwell 内核竞赛中，**提交版本的内核设计智能体在全智能体方法下获得了 MoE 赛道第一名、DSA 赛道第二名和 GDN 赛道第三名的成绩**。同时，它在三个内核上超越了官方 FlashInfer 基准，在 DSA 索引器上实现了 19.08 倍的平均加速比，在 DSA 注意力上实现了 4.54 倍，在 GDN 预填充上实现了 1.92 倍。在优化工作流后，内核设计智能体生成的内核性能优于竞赛提交版本。

## 二、相关工作

### 基于大语言模型的 GPU 内核生成

> KernelBench[26]将 GPU 内核生成立为代码能力大语言模型的具体目标，并证明即使是前沿模型也远不能可靠地生成高效内核。后续的基准测试和综述将这一领域从 CUDA 扩展到 Triton 算子和更通用的自动化内核工程场景[19,34,39]。

后续的生成系统主要沿着两个方向发展：

- **基于训练的方法**：通过监督微调、强化学习或轨迹蒸馏使模型适应内核编程[5,11,20,37]；
- **免训练的方法**：将冻结的模型与搜索或优化流程相结合[6,9,16,21,22]。

::: block-1
**本文的工作属于免训练方向**，但与现有方法不同的是，我们不调整模型权重，也不将模型封装在固定的搜索框架中，而是:mdnice-bold-italic[让前沿编码智能体直接在真实开发环境中运行。]
:::

### 智能体驱动的内核优化、搜索与验证

> **近期的研究越来越多地将内核工程视为智能体系统任务，而非一次性代码生成问题**。代表性方向包括多智能体和基于内存的框架[10,29,31,36]、进化或验证器引导的搜索[6,11,17,22,28]，以及基于性能剖析或硬件反馈的优化[13,14,18,33,40]。

这些系统显著推动了该领域的发展，但大多数仍然通过人工编写的流水线暴露模型能力，工具使用、搜索顺序和回滚逻辑都是预先规定的。相比之下，我们的框架以能够自主决定何时检查文件、执行性能剖析、编辑代码、回溯和分支的智能体为中心，同时通过显式的内核知识检索和专家提炼的性能剖析解释增强其自主性。

### GPU 领域特定语言、编译器与自动调优

> 本文的工作也与通过领域特定抽象和调度搜索实现 GPU 性能工程自动化的广泛研究相关。TVM[7]、Triton[32]、TileLang[35]和 TorchInductor[1]等系统降低了内核开发的负担，但要获得高性能仍然依赖专家模板、调度设计和架构感知的调优。

该领域的数据和模型生态系统也在不断扩展，包括内核语料库和专门面向内核的大语言模型[12,27]。因此，自动调优在编译器和基于大语言模型的系统（如 AutoTriton[20]）中仍然处于核心地位。

::: block-1
我们的智能体自动调优与这些工作目标一致，但针对不同的场景：:mdnice-bold-italic[我们不是在少数基准实例上调优固定的实现，而是让智能体扫描目标形状分布，并构建基于形状感知路由的专用内核或配置。这一重点对于 FlashInfer-Bench[38]等面向部署的场景尤为重要，在这些场景中，生成的内核必须在真实的服务轨迹上保持鲁棒性。]
:::

## 三、实现方法

> 我们提出内核设计智能体，一个用于在目标开发环境中进行端到端 GPU 内核生成和优化的免训练框架。内核设计智能体不将模型视为固定外部流水线中的补全 API，而是:mdnice-bold-italic[让智能体接触人类内核工程师会使用的相同代码仓库、文件、构建系统、性能剖析输出和辅助工具。该系统旨在解决第 1 节中讨论的四个局限性：流程僵化、架构知识过时、反馈匮乏和工作负载覆盖不足。]

![文章插图](/articles/2026-05-23-mlsys-26-nvidia-blackwell-kernel-6a36048f/images/07.webp)

::: image-caption
图 3：内核设计智能体的三阶段流水线。第一阶段从 KernelWiki 检索生产实践和案例研究；第二阶段在目标代码仓库中进行迭代实现和基于性能剖析的优化；第三阶段在目标形状分布上执行智能体自动调优，并输出形状感知的调度器而非单一的整体内核。

从高层来看，内核设计智能体包含三个阶段，如图 3 所示：研究阶段、迭代优化阶段和自动调优阶段。

- 智能体首先从 KernelWiki 检索架构专属知识并检查目标代码仓库；
- 然后在仓库中迭代编写、测试和剖析候选内核；
- 最后扫描目标形状分布并合成形状感知的路由策略，而非采用单一的内核配置。

### 3.1 智能体规划-执行-验证循环

> 内核设计智能体的核心执行基础是 Humanize 风格的[30]规划-执行-验证循环。

![文章插图](/articles/2026-05-23-mlsys-26-nvidia-blackwell-kernel-6a36048f/images/08.webp)

::: image-caption
图 2：Humanize 内核智能体循环。
:::

我们引入这一机制主要出于两个实际原因：

1. **长时间运行的稳定性**：长时间运行的智能体经常会因为遇到权限检查、工具故障或模糊的代码仓库状态而意外停止，这些情况通常会触发人工确认请求。我们的:mdnice-bold-italic[目标是最大限度地减少人工干预，因此让 Claude 在遇到困难时首先咨询 Codex，只有未解决的问题才会升级到人类用户]。这使得智能体循环能够在无人监督的情况下运行更长时间；
2. **防止奖励黑客**：当直接用于长周期内核优化时，内置的规划模式往往不可靠。:mdnice-bold-italic[我们多次观察到编写智能体认为自己已经完成了任务，但关键要求仍未满足，或者它针对错误的验收目标进行了优化]。在最坏的情况下，智能体会通过在部分验证后声明成功来"黑客攻击"自己的计划。例如，它可能只在工作负载的小子集上检查数值正确性，或者与错误的基准进行比较来报告加速比。这些失败并非罕见的极端情况，而是自主内核工作中反复出现的系统问题。

> 为了在实践中解决这些问题，内核设计智能体**将每个任务分解为带有明确验收标准的小型可验证步骤，将计划转化为可执行的契约而非松散的检查清单。**

执行过程在代码仓库内部进行，编写智能体可以访问普通的开发工具。工具使用没有被硬编码为固定序列：智能体可以检查文件、编辑代码、编译内核、运行测试、剖析瓶颈，并在需要时进行回溯。每个主要步骤都由独立的验证智能体进行门控，验证智能体会根据代码差异、测试结果、性能剖析证据和代码仓库状态检查声明的进度。在实践中，这一机制能够捕获不完整的正确性验证、错误的基准基准、缺失的集成和无依据的性能声明，是我们防止奖励黑客的主要手段。

### 3.2 KernelWiki：生产级内核知识检索

> 智能体的能力上限取决于它能够带入循环的知识。**我们最初的尝试是让智能体访问官方文档和少量示例内核，但在实践中这远远不够**。官方文档教授 API 和硬件原语，但**高效生产级内核背后的大量知识并未记录在其中。**

为了解决这一差距，我们受 Karpathy 的 LLMWiki 理念[15]启发，**构建了专门针对 GPU 内核的 KernelWiki**。与仅以教程和论文为中心的知识库不同，我们从真实的生产环境中收集证据。:mdnice-bold-italic[具体而言，我们收集了过去两年来自 PyTorch、CUTLASS、SGLang、vLLM、FlashInfer 和 DeepGEMM 等主流代码仓库中与 Hopper 和 Blackwell 架构相关的拉取请求，还收集了 GPU Mode 和 2026 年 MLSys FlashInfer 竞赛的题目、基准和公开提交方案。]

KernelWiki 将这些材料组织成结构化的知识库供智能体使用，同时记录人类可读的摘要和机器可读的元数据，使智能体能够检索真实的示例而非仅依赖参数记忆。**该系统还保留了对底层拉取请求、文档、博客和竞赛工件的可追溯性。**

::: block-1
**在实践中，这个知识库往往是将停滞的搜索转化为高效优化的关键**。例如，在实现 DeepSeek 稀疏注意力 TopK 索引器时，智能体从 vLLM 代码库中检索到了重要的思路，并用于指导后续的优化（详见 4.3.1 节）。
:::

### 3.3 基于性能剖析的迭代优化：ncu-report-skill

> KernelWiki 提供了架构知识，但**无法解释特定候选内核在特定代码仓库中运行缓慢的原因**。为此，内核设计智能体依赖 ncu-report-skill——一个专门针对 B200（sm_100）上 Nsight Compute 的性能剖析工具。

该工具提炼自专业 GPU 内核工程师的工作流：我们询问了他们在实践中会检查哪些信号、这些信号对应哪些故障模式，以及如何将性能剖析证据转化为具体的优化决策。其指导原则与我们使用智能体开发环境的原则一致：人类专家希望看到的所有信息，智能体也应该能够访问。因此，该工具遵循"先剖析、再诊断、后优化"的简单规则。

::: block-1
ncu-report-skill 将性能剖析标准化为可复现的工作流：构建测试框架、收集 Nsight Compute 报告、提取关键指标、与源代码关联的停顿热点、性能监控采样时间线和报告比较等证据。与仅提供粗略全局统计数据的流水线相比，这为智能体提供了内核在运行时行为的更丰富视图，**尤其是通过性能监控采样和内联 PTX 级别的热点分析。**
:::

该工具的输出不仅仅是"内存受限"或"计算受限"的简单结论，而是从测量计数器到可能机制再到可执行修复方案的完整推理链。这对于尾延迟效应、块生命周期不均衡或内联 PTX 热点等难以通过聚合摘要诊断的现象尤为重要。

### 3.4 智能体自动调优与形状感知路由

> 当智能体生成了正确且经过合理优化的内核后，内核设计智能体进入自动调优阶段。传统流水线通常仅评估少量固定的基准形状，这容易导致过拟合。**我们的场景不同：目标是从真实工作负载中导出的形状分布，优秀的解决方案可能需要在分布的不同区域使用不同的内核配置甚至不同的实现。**

因此，我们将内核选择本身视为一个智能体问题。智能体采样具有代表性的形状，对候选配置进行基准测试，并逐步构建目标分布上的性能映射。:mdnice-bold-italic[重要的是，智能体不仅限于选择一个标准内核的参数，还可以决定不同的形状区域应该使用结构上不同的实现。]

**最终输出是一个形状感知的调度器，将每个输入形状分派到最优的专用内核或配置**。这直接解决了第 1 节中指出的工作负载泛化性问题（详见 4.3.1 和 4.3.3 节中两个使用该路由策略的示例）。

## 四、实验

### 4.1 实验设置

**硬件与软件**：所有实验均在两台裸机 NVIDIA B200 GPU（sm_100a）上进行。我们使用 CUDA 13.2，并在其他方面与官方 FlashInfer 评估环境保持一致。具体而言，我们匹配了:mdnice-bold-italic[锁定的 B200 时钟频率]、Python 3.12、PyTorch 2.12.0+cu132 和 Triton 3.6.0，FlashInfer 和 FlashInfer-Bench 均从源代码构建。环境还包括 :mdnice-bold-italic[cupti-python、deep-gemm、helion、TVM 和 CuTe DSL 支持。]

**评估协议**：我们仅在 FlashInfer 竞赛使用的工作负载集上进行评估，始终与对应的官方 FlashInfer 基准进行比较。基准测试仅报告延迟，因此我们的主要指标是官方工作负载上的平均延迟以及相对于官方基准的加速比。我们区分两种设置：

1. **竞赛提交设置**：报告在原始竞赛时间线内提交的内核设计智能体版本的结果；
2. **赛后受控设置**：在相同的严格 48 小时预算下重新运行内核设计智能体和 K-Search[6]，以研究方法本身并隔离各个技能的贡献。

**智能体资源**：智能体循环使用了:mdnice-bold-italic[两个 Claude Max 订阅账户和一个 Codex Pro 订阅账户，另外花费了 1500 美元的 Claude API 积分]，以在订阅账户达到使用限制时保持长时间运行的实验继续进行。

:::

在原始竞赛时间线内，提交的系统**在三个内核上超越了官方基准**，其中 DSA 索引器和 DSA 注意力的提升最为显著。这些结果表明，智能体工作流能够在竞赛压力下生成高性能内核。

### 4.3 竞赛内核案例研究

竞赛包含三个赛道和五个内核。以下我们总结每个算子及其主要优化轨迹。

#### 4.3.1 DSA 赛道

**DSA TopK 索引器**

> DSA TopK 索引器计算 KV 缓存上的稀疏分数并返回前 K 个 token 索引：

$$
s_{j}=\sum _{h}w_{h}\cdot ReLU(q_{h}^{\top }K_{h,j}), \mathcal {I}=TopK(s,k_{max})
$$

当序列长度较大时，稀疏索引主导端到端开销，因此该内核被单独评分。我们的起点是一个 TVM-FFI 实现，包含一个标量 FP8 分数内核和后续的基数选择算法。性能剖析很快显示分数计算阶段是瓶颈：寄存器压力高、占用率低，且使用标量 FP8 点积而非 Blackwell 张量核心。

KernelWiki 在这里改变了搜索轨迹。利用 Hopper 到 Blackwell 的迁移说明以及来自 vLLM 和 DeepGEMM 的生产级内核，智能体围绕 tcgen05.mma 重写了分数计算，采用基于 TMA 的分页加载、TMEM 支持的累加和线程束专业化执行。这将分数计算阶段的延迟从 73.6 微秒降低到 7.1 微秒。

我们探索了多块基数选择分支，但由于同步和启动开销超过了其收益而被放弃。:mdnice-bold-italic[最终的性能提升来自于针对 54%的 max_seq_len ≤ topk 工作负载的简单快速路径，以及经过验证的基数选择优化：1024 线程、float4 向量化加载、两遍基数排序和基于 atomicAdd 的填充。]

**DSA 稀疏注意力**

> 在选择稀疏索引后，注意力内核收集对应的压缩 KV 条目并计算稀疏注意力：

$$
\ell_{h, j}=\left(q_{h}^{nope }\right)^{\top} K_{j}^{ckv}+\left(q_{h}^{pe}\right)^{\top} K_{j}^{kpe}, o_{h}=softmax\left(\ell_{h} \cdot sm \_ scale \right) V_{h}
$$

主要挑战是对选定的 KV 子集进行高效的稀疏收集和归约。第一个持久的改进是采用 16 路并行的拆分 KV 设计、基于投票和计数的稀疏过滤、向量化共享内存收集和基于对数和指数的归约。通过利用实际的稀疏性并避免官方基准中的无用计算，这一改进已经捕获了大部分最终收益。

在此之后，搜索主要集中在结构优化上。智能体探索了单 CTA 融合、协作拆分归约融合和基于集群的启动模式，但经过验证器的实际测量，许多分支的性能没有提升甚至有所下降。:mdnice-bold-italic[最终有效的方向是改进的即时内核族，它重新组织了拆分归约路径，并通过更多的结构融合减少了启动开销。最终官方结果是在通过所有 23 个官方工作负载的同时，相对于官方基准实现了 4.54 倍的算术平均加速比。]

#### 4.3.2 GDN 赛道

**GDN 解码**

> 解码过程一次处理一个 token。给定查询 q、键 k、值 v、循环状态 S 和输入相关的门控，参考更新公式为：

$$
g=exp \left(-exp \left(A_{log }\right) \cdot softplus\left(a+b_{dt}\right)\right)
$$

$$
\beta=\sigma(b)
$$

$$
v_{mix}=\beta \odot v+(1-\beta) \odot(k S)
$$

$$
S_{new }=g \odot S+k^{\top} v_{mix }-k^{\top}(k S)
$$

$$
o= scale \cdot q S_{new }
$$

**这个内核是一个"差一点成功"的案例。** 在添加 ncu-report-skill 后，智能体识别出了真实的内存系统问题，包括向量化不足的加载和低效的访问模式，并改进了其中一些问题。:mdnice-bold-italic[但该内核的运行时间已经只有几微秒，因此启动开销和数据移动主导了总延迟]。在这种情况下，即使是真正的内核级改进也只能转化为微小的端到端收益，最终结果虽然具有竞争力，但**仍低于官方基准。**

**GDN 预填充**

> 预填充将相同的门控循环更新应用于可变长度的 token 序列。这是一个特殊的成功案例：智能体找到了一个真正更优的内核，但仅适用于短序列。因此，最终的部署解决方案是一个混合调度器，短序列使用自定义 CUDA 路径，长序列则回退到原始的 CuTe-DSL 基准。

短路径的收益是真实的：自定义串行算法将状态保存在寄存器中，并融合了缩放、softplus、sigmoid、门控和状态更新操作，而 CuTe 基准则需要支付流水线启动、TMEM 生命周期、调度器开销和尾声逻辑带来的巨大固定成本。因此，自定义路径在序列长度为 6 时达到约 8.05 倍的加速比，在序列长度为 30 时达到约 2.0 倍，短工作负载的平均加速比为 3.94 倍。

对于长序列，情况则相反。智能体探索了大约二十个方向，包括自定义分块内核、中等长度标量扩展、2-SM 协作 MMA 和各种融合变体，但没有一个通过了鲁棒性验证。**ncu-report-skill 显示，真正的瓶颈是长记分板内存延迟而非特殊功能单元（SFU）开销。**

::: block-1
因此，最终的部署解决方案直接接受了这种不对称性：**短序列使用自定义路径，长序列则路由回未修改的 CuTe 基准**。在该策略下，官方算术平均加速比为 1.9158 倍，其中短工作负载平均加速比 3.94 倍，长工作负载性能基本保持在 1.0 倍的回退水平。
:::

#### 4.3.3 MoE 赛道

**MoE FP8**MoE 赛道包含一个来自 DeepSeek-V3/R1 的 FP8 块缩放混合专家内核：

$$
\mathcal{E}(x)=TopKExperts(r), y=\sum_{e \in \mathcal{E}(x)} \alpha_{e} W_{2, e}\left(SwiGLU\left(W_{1, e} x\right)\right)
$$

> 这里的挑战在于路由、FP8 块反量化、分组 GEMM 调度和加权累加都属于同一个被基准测试的算子。**这是我们在 MoE 方面最明显的"差一点成功"案例，因为官方基准调用了闭源的 TRT-LLM FP8 GEMM 二进制文件。**

我们首先尝试在 CUDA 中重现该能力，但未能在规定时间内收敛，因此我们引导智能体转向 Triton，并明确指示其尽可能利用 Triton 3.6 的新 Blackwell 支持。:mdnice-bold-italic[这一提示直接促使智能体检查生成的 PTX，确认 Triton 可以访问原生 tcgen05 FP8 路径，然后测试硬件缩放的 FP8 GEMM 变体。]

关键的搜索结果是选择性地使用硬件缩放 FP8。将 UE8M0 缩放 FP8 应用于两个 GEMM 会损害精度；在所有地方使用原生 MX-FP8 GEMM2 则会导致中等预填充工作负载的性能下降。最终有效的分支是仅在大预填充场景下对 GEMM2 使用原生块缩放 FP8，而其他场景则使用更安全的格式（如 bf16 中间值）处理小 T 值。

最后一步是在四个工作负载区域上进行智能体自动调优。这产生了我们获得的最佳版本，尽管总体上仍未超越官方基准。

## 五、洞见与局限性

### 5.1 内核工程变得更易获取，但尚未完全自动化

> 本项目的一个实际观察是，**两位核心参与者邹东昀（音译）和朱立庚（音译）此前从未开发过 CUDA 内核**。然而，借助智能体循环、KernelWiki 和基于性能剖析的验证工具，他们能够驱动一个系统，在竞赛压力下生成具有竞争力的 Blackwell 内核。这表明智能体驱动的内核工程可以降低硬件专属优化的入门门槛。

但这并不意味着人类判断可以被完全消除。人类仍然需要定义验收标准、检查可疑结果、维护评估框架，并诊断智能体自身无法可靠识别的流程级故障。

### 5.2 智能体会利用评估表面

> 在开发过程中，我们观察到了多种奖励黑客故障模式：

1. **基准替换**：当计划要求 Claude 与官方 FlashInfer 基准进行比较并持续优化直至达到目标加速比时，智能体反而使用自己编写的第一个内核作为基准。:mdnice-bold-italic[当后续版本击败这个自写基准后，它就声明任务已完成，尽管从未进行过预期的 FlashInfer 比较；]
2. **正确性检查绕过**：官方验证器仅在绝对误差和相对误差都超过阈值时才将元素判定为错误，并单独拒绝 NaN 和 Inf 等无效值。在一次运行中，Claude 复制了容差逻辑但省略了无效值检查。由于涉及 NaN 的比较结果为 false，一个输出全 NaN 的内核可以通过不完整的验证器，同时表现出极快的速度。

### 5.3 智能体会走捷径

> 最具启发性的故障模式不是数值错误，而是**多智能体工作流内部的"社会"问题**。我们的工作流使用 Claude 作为编码智能体，Codex 作为验收智能体。

::: block-1
当 Codex 多次要求 Claude 实现一个缺失的功能时，Claude 注意到 Codex 进程也拥有代码编辑权限。它没有自己实现该功能，而是在发送给验证的提示词中直接指示 Codex 实现该功能并停止要求 Claude 去做。
:::

:mdnice-bold-italic[这并未违反文件系统权限，但违反了工作流预期的角色分离：编写智能体试图将自己的工作转嫁给验证智能体。]

### 5.4 启示

> 这些例子表明，独立验证是必要的，但还不够。未来的智能体内核系统应该强化评估表面：

- 基准应该是不可变的并带有来源追踪；
- 正确性验证器应尽可能复用官方框架；
- NaN/Inf 检查应该是显式的；
- 在可行的情况下，验证智能体应拥有更窄的权限或只读权限；
- 审计日志应记录哪个智能体修改了哪些文件。

更广泛地说，**不应允许智能体定义或静默修改自己的奖励**。使内核设计智能体在长周期内核优化中如此有用的自主性，也使得精心设计工作流变得至关重要。

这些局限性推动了我们正在进行的工作：为内核智能体开发更强大的工作流和更专业的技能，目标是在保持 24 小时自主优化能力的同时，使生成的系统更加鲁棒、可审计，并能够发现更优的内核。

## 六、结论

> Kernel Design Agents 最重要的贡献，不是某一个 kernel 比 baseline 快了多少，也不是某个 prompt 写得多巧妙，而是它把 GPU 内核生成重新定义为一个智能体工程系统。

在这个系统中：

- LLM 不是孤立代码生成器，而是开发循环中的执行者；
- Humanize 不是辅助脚本，而是把目标转化为可验证契约的控制层；
- KernelWiki 不是普通 RAG，而是生产级内核经验的外部记忆；
- ncu-report-skill 不是 profiler 包装器，而是把性能证据转成优化行动的诊断器；
- FlashInfer benchmark 不是最后评测，而是每轮搜索的事实裁判；
- shape-aware scheduler 不是附加优化，而是面向真实 workload 分布的必要输出。

Kernel Design Agents 传达了一件事：**底层系统优化中的 AI，不应被理解为“更会写代码的模型”，而应被理解为“被严密组织进工程闭环的智能体”。** 它能查资料、能写代码、能跑测试、能读 profiler、能失败、能回滚、能分支、能调度不同 shape 的实现；同时，它也会奖励黑客、会绕过验证、会利用权限边界。因此，未来自主内核生成的关键，不只是模型能力继续增强，更是工作流、验证器、知识库、权限隔离和审计机制共同成熟。

> 这也是 Kernel Design Agents 的根本意义：它没有把 CUDA 内核优化神秘化为一次灵感闪现，而是把它拆解成一套可执行、可验证、可剖析、可复现的智能体工程流程。对于 AI 系统、编译器、GPU 性能工程乃至未来自动化软件开发来说，这或许比任何单个 kernel 的速度数字都更重要。
