关键词：**PTX**、Lean、:mdnice-bold-italic[GPU Kernel]、**形式化验证**、内存模型

> 大模型已经相当擅长优化 GPU Kernel。不过，在大规模训练任务中，我们仍然需要确认这些 Kernel 确实完成了正确的计算。测试只能覆盖有限数量的用例，还可能漏掉竞态条件等隐蔽问题。为了解决这一问题，SF Tensor 团队在过去几个月里构建了一套系统，用形式化方法证明 GPU Kernel 的正确性。

他们此前的工作《Proving Kernels Correct Instead of Testing Them》[1]**已经能够证明许多 Kernel 正确，但在可验证的 Kernel 类型上仍存在根本限制**。此后，团队探索了一条新路径：**先在 Lean 中形式化 Kernel 的语义，再写出由计算机检查的形式化证明。**

## 一、PTX 内存模型

> GPU 线程并不会共享一个简单的、全局一致的内存视图。线程 A 写入一个值后，线程 B 读取同一地址时能否看到这次写入，取决于两项操作之间的顺序关系。PTX 内存模型规定的正是这些规则。

**该模型建立在内存事件之间的关系之上。** 一个事件是某个线程在执行过程中的某个时刻完成的一次内存操作，例如一次加载、一次存储或一次屏障到达。下面介绍这些关系。

- 程序顺序（program order，po）刻画同一线程内的先后顺序。如果线程 0 先写入 x，随后到达一个屏障，这两个事件就具有程序顺序。
- 读取来源（reads-from，rf）记录一次读取的值来自哪里。如果读取 R 返回了写入 W 存储的值，那么 W 就是 R 的读取来源。
- 一致性顺序（coherence order，co）为同一地址上的所有写入建立偏序，表示在每个内存位置上，哪次写入“发生在”另一次写入之后。
- 同步关系（synchronizes-with，sw）刻画同步原语建立的跨线程顺序。当线程 0 到达 `bar.sync` 屏障——相当于 PTX 中的 `__syncthreads()`——而线程 1 从同一屏障返回时，线程 0 的到达事件就与线程 1 的返回事件形成同步关系。

::: block-1
这些关系共同构成因果关系（causality）：程序顺序与同步关系的传递闭包，再加上一些额外的边。:mdnice-highlight[分析内存可见性时，关键在于因果关系。如果事件 A 在因果上先于事件 B，A 产生的效果就对 B 可见。]
:::

> 内存模型的核心约束是因果公理：如果写入 W 在因果上先于读取同一字节的 R，R 就不能从任何在一致性顺序上早于 W 的写入中取值。换句话说，如果一次写入保证对一次读取可见，这次读取就必须看到该写入或更新的值。

来看一个具体例子。两个线程共享全局变量 x，其初始值为 0：

```
Thread 0                    Thread 1st.global.u32 [x], 1       bar.sync 0bar.sync 0                 ld.global.u32 r, [x]
```

线程 0 写入 x=1，然后到达屏障。线程 1 从屏障返回，然后读取 x。

![文章插图](/articles/2026-11-04-sf-tensor-lean-ptx-gpu-e5a0dd99/images/02.jpg)

::: image-caption
屏障同步在写入与读取之间建立因果链。图中，W 表示线程 0 的写入，R 表示线程 1 的读取，A0 和 A1 分别表示线程 0 到达屏障、线程 1 从屏障返回。程序顺序连接 W 与 A0，也连接 A1 与 R；同步关系连接 A0 与 A1。几段关系组合后，W 就在因果上先于 R，形成 W → A0 → A1 → R 的链条。
:::

换言之，W 已经“传播到 R”，所以 R 不能读取任何早于 W 的值。它不能读到初始值 0；由于 W 是此处唯一的另一次写入，R 必须读到 1。

屏障正是通过这一机制发挥作用：它在不同线程的内存操作之间建立因果链。如果没有屏障，写入与读取之间不存在因果顺序，线程 1 读到 0 也符合规则。

::: block-1
完整的 PTX 模型还包含其他关系与公理，例如一致性、单副本原子性、按位置的顺序一致性（SC-per-location）等。除了 no-thin-air 公理和 Fence-SC 公理，团队将其余内容全部形式化。省略这两条公理是因为建模难度较高，更多细节可见配套论文（见本文开头给的链接信息源）。这样做可能使某些 Kernel 无法得到正确性证明，但不会让实际有误的 Kernel 被证明为“正确”。
:::

## 二、我们如何对 PTX 建模

### 2.1 问题：内存模型不定义逐步执行

> PTX 内存模型是一份事后规约。给定所有线程的完整事件集合，它会判定哪些读取来源与一致性顺序配置是可能成立的，也就是哪些配置是“一致的”。它没有定义一步一步的执行过程。

**这给验证带来了循环依赖**。由于存在分支和数据依赖控制流，:mdnice-bold-italic[线程会产生哪些事件，取决于加载操作返回什么值；但加载操作能返回什么值，又取决于所有线程的完整事件集合]，因为内存模型正是基于这个集合进行推理的。

### 2.2 Oracle：打破读取结果与事件集合的循环依赖

> 团队用一个所谓的 Oracle（预言机）打破这种循环依赖。每个线程都配有一个 Oracle 函数。每当线程需要外部信息，例如加载结果、原子操作返回值或 warp shuffle 结果，它就查询 Oracle，由 Oracle 返回一个确定的值。具体返回什么值，后文会继续说明。

有了 Oracle，单个线程就能确定性地执行。每一步都会读取当前指令，可能查询 Oracle，随后更新寄存器、推进程序计数器，并发出零个或多个事件，例如读取、写入或屏障到达。分支会检查谓词寄存器，然后选择跳转或顺序执行。由于寄存器的值可能依赖 Oracle 的回答，线程的控制流路径，包括循环迭代次数，也可以取决于它从内存中读到的值。

Kernel 的一次执行会为每个启动的线程分配一个 Oracle。每个线程在自己的 Oracle 下确定性地运行，生成一份事件列表。团队把所有线程的事件合并成一个候选执行，然后询问：它是否符合 PTX 内存模型？

::: block-1
换句话说，能否选定读取来源、一致性顺序和同步匹配，使得：

1. 内存模型的所有公理都得到满足；
2. Oracle 的每个回答，都与读取来源关系所指定的写入值一致，也就是对应加载所读取的那次写入的值？

如果可以，这次执行就是被允许的。
:::

此时，正确性意味着：对于每一次一致且完整的执行——也就是所有线程都已退出——全局内存的最终状态都满足规约。

团队还会为每个 Kernel 单独构造一次有效执行，以证明非空性。这可以排除一种情况：由于建模错误导致一致性条件根本无法满足，系统中不存在一致执行，正确性命题因此空洞地成立。

### 2.3 用合成读取事件表示最终全局内存

> 该模型构建的是执行图，并未推进一个可变的“全局内存状态”，所以需要另行定义 Kernel 结束后全局内存的状态。

为此，团队为全局内存的每个字节添加一个合成读取事件，并让这些读取在因果上位于所有 Kernel 事件之后。内存模型公理会约束这些合成读取必须返回的值，从而具体表示 Kernel 的输出。

![文章插图](/articles/2026-11-04-sf-tensor-lean-ptx-gpu-e5a0dd99/images/03.jpg)

::: image-caption
因果公理排除过期读取。如果写入 W 将 x=1 存入内存，并且不存在其他对 x 的写入，那么合成读取在因果上位于 W 之后。因果公理会排除初始值这一读取来源，否则 R 就会返回早于 W 的值，与它在因果上位于 W 之后这一事实矛盾。图中展示了这条推导如何排除过期读取。
:::

### 2.4 扩展模型以覆盖现代 PTX 构造

> 基础模型可以处理加载、存储、算术运算和数据依赖控制流。现代 GPU Kernel 还会使用其他同步与通信原语，团队在基础模型之上扩展了其中许多机制的形式化定义。

例如，他们形式化了 WGMMA、proxy fence、warp shuffle，以及多个顺序启动的 Kernel 所组成的流水线。

对于流水线，API 同步会保证前一个 Kernel 完成后，下一个 Kernel 才开始。团队通过令后继 Kernel 的初始全局内存等于前驱 Kernel 的输出，为两个 Kernel 之间传递的全局内存建模，并将正确性结果沿多次启动串联起来。

![文章插图](/articles/2026-11-04-sf-tensor-lean-ptx-gpu-e5a0dd99/images/04.jpg)

::: image-caption
多 Kernel 流水线的正确性组合方式。每个 Kernel 经过验证的输出都会成为下一个 Kernel 的输入。借助这一接口，单个 Kernel 的证明可以组合成整条流水线的正确性结论。
:::

### 2.5 将浮点数建模为实数

> 团队把浮点数建模为采用精确算术的实数。这些证明建立的是语义正确性，即 Kernel 计算出了正确的数学函数；并未建立数值正确性，即 Kernel 的舍入行为可以接受。

团队没有尝试证明 Kernel 会产生逐位“正确”的浮点输出，因为同一运算的两种正确实现，经常由于归约顺序和累加精度不同而产生不同的浮点结果。

此外，使用实数表示的功能正确性是一个二值判断，也是开展数值分析的前提。还有一个重要的相关问题留待未来研究：如何判断 Kernel 的数值行为会导致推理精度下降，或使训练发散？

## 三、已经证明正确的 Kernel 示例

> 团队已经在 Lean 中形式化验证了以下 Kernel，没有使用 `sorry` 表示未证明的假设，也没有添加用户自定义公理。对于每一次合法启动，他们都证明了：所有一致、完整且没有未定义行为的执行，都会产生规约指定的输出。团队还分别构造了这样的执行，以证明非空性。

- 逐元素 Kernel。每个线程针对输入中的一个元素计算仿射映射。
- 标量矩阵乘法。每个线程通过沿归约维度循环，计算一个输出元素。证明在内部循环上使用了累加不变式。
- Ampere 分块矩阵乘法。这种分块矩阵乘法使用 `cp.async` 将数据从全局内存异步加载到共享内存，使用 CTA 屏障进行同步，并通过 `mma.sync` 完成张量核计算。
- Hopper 矩阵乘法。它使用 TMA 和 mbarrier 加载数据，使用异步 WGMMA 进行计算。该案例覆盖了模型中最复杂的部分：异步代理、proxy fence，以及 mbarrier 的阶段完成机制。
- 在线 FlashAttention。它在精确实数算术下计算 `softmax(alpha * Q * K^T) * V`，并采用在线 softmax。证明使用了在线 softmax 不变式和标量算术。
- 混合专家（MoE）。这条流水线由三个顺序执行的 Kernel 组成，分别负责专家路由、逐专家计算和专家结果合并。它使用了多 Kernel 组合接口：第一个 Kernel 经过验证的输出，会成为第二个 Kernel 的输入。
- 简单 megakernel。两个单线程 CTA 共享一个全局工作计数器。每个线程以原子方式递增计数器，并根据返回值选择要执行的任务。

## 四、未定义行为仍是外部假设

> 这些正确性结果假设 Kernel 不存在 ISA 层面的未定义行为，并假设 `ptxas` 与硬件行为正确。团队没有证明不存在未定义行为，这是一项外部假设。

证明不存在未定义行为，比看上去更困难。线程是否会执行到未定义操作，可能取决于它从内存中读取的值；这些值又取决于其他线程写入了什么，而这些写入还可能被编译器重排。

考虑两个线程，全局 u32 变量 x 和 y 的初始值都为 0，并使用 `.relaxed.gpu` 加载与存储：

```
T0                          T1r1 = load x                 r2 = load yif r1 == 1: UB              store x, r2store y, 1
```

这里的未定义行为可以是一次未对齐的内存访问。如果在未定义行为发生前停止 T0，就会移除它对 y 的存储。于是，T1 读到 y=0，并向 x 写入 0；T0 随后读到 x=0，永远不会到达未定义行为。按照这种部分执行分析，没有任何执行会触发未定义行为。

但编译器可以把 T0 中写入常量的 `store y, 1` 移到加载 x 之前。这样一来，T0 先写入 y=1；T1 读到 y=1，并向 x 写入 1；T0 随后读到 x=1，最终触发未定义行为。内存模型允许这种重排，因为这次存储的值并不依赖加载结果。

PTX 是一种虚拟 ISA，`ptxas` 会把它编译成机器码。**要从源码层面判定不存在未定义行为，不能只依赖内存模型公理，还需要考虑编译器变换**；而目前并不清楚究竟允许哪些变换。

::: block-1
改为对 SASS——GPU 实际执行的机器指令集——建模会有帮助。GPU 按顺序执行 SASS 指令，也不进行推测执行，这消除了编译器重排带来的不确定性。:mdnice-highlight[团队认为，SASS 模型甚至可能不需要 Oracle，可以采用全局、非确定性的小步语义，并把读取延迟到首次使用其值时。这种模型也会更接近硬件的实际执行方式，更直观地进行推理。]
:::

遗憾的是，NVIDIA 没有完整公开 SASS 文档，因此目前建立完整模型并不现实。

## 五、结论：扩展至多 GPU 与完整训练步骤

> 团队已经使用这套模型，分析现代高性能 GPU Kernel 所采用的大部分技术：异步张量核矩阵乘法、多 Kernel 流水线、通过原子操作进行动态工作分配，以及 acquire-release 同步。

他们正在扩大对 PTX 的覆盖范围，目标是能够证明完整训练步骤的正确性。团队还希望把模型扩展到多 GPU Kernel，以及 AMD 和 Trainium 等其他硬件。
