## 关键问题

### Q1. NCCL 的协议动态选择机制虽考虑多种因素，但在异构 GPU 集群（如混合架构 GPU、不同代际 NVLink/PCIe 配置）中，其自适应性能否保持最优？现有 heuristic 模型对硬件差异的容错性如何？

论文指出，**NCCL 的协议选择依赖系统拓扑、GPU 架构、消息大小等因素，通过内部调优模型动态决策** （如 LL/LL128 用于小消息，Simple 用于大消息）。但该**分析基于同构环境** （如统一架构的 GH200 节点），**未明确提及异构集群场景**。

> 对于**异构 GPU 集群** （混合架构、不同代际 NVLink/PCIe），现有 **heuristic 模型的适应性可能受限**：

- 一方面，**协议选择受硬件能力约束** （如 LL128 依赖原子 128 字节写，老旧 GPU 可能不支持），**会自动降级** 至兼容协议（如 LL 或 Simple），但这种降级可能破坏原有的性能平衡；
- 另一方面，**异构环境中带宽、延迟差异较大**，现有模型基于同构场景设计的参数（如 chunk 大小、通道数）可能无法最优匹配，导致容错性不足，性能波动增加。

### Q2. 论文指出 LL128 协议依赖原子 128 字节写操作，当硬件不支持时会被禁用，这种降级机制是否会导致跨平台部署时出现不可预测的性能断崖？其对大规模异构集群的通信一致性影响如何？

:mdnice-bold-italic[LL128 协议在硬件不支持时会被禁用，转而使用 LL 或 Simple 协议，这可能导致性能突变]：在支持 LL128 的环境中（如 NVLink 节点内），其可实现～ 95% 峰值带宽，而降级到 LL 后带宽仅为 25~50% 峰值，或降级到 Simple 后延迟显著增加（如小消息场景），形成 “性能断崖”。

:mdnice-bold-italic[对通信一致性而言，NCCL 通过严格的协议兼容性检查确保数据不损坏，但性能一致性会受影响]：在大规模异构集群中，不同节点可能因硬件差异启用不同协议（如部分节点用 LL128，部分用 LL），导致节点间通信出现 “协议不匹配”，增加协调开销（如同步等待），甚至引发整体通信效率下降。

### Q3. 环和树算法是 NCCL 的核心，但新兴的 Parallel Aggregated Trees（PAT）等算法在高规模场景下表现更优，现有对环/树算法的分析框架（如通信原语、流水线模型）能否直接迁移至新算法？新旧算法的性能边界在哪里？

论文指出，环 / 树算法基于低级别通信原语（`send`/`recv`/`recvReduceSend` 等）、迭代执行模型（分通道、分 slot 流水线）和拓扑映射（环 / 树结构）。

新兴的 PAT 算法虽未被详细分析，但其作为集体通信算法，可能共享部分底层原语（如数据分片、并行通道），因此**现有框架的核心逻辑** （如通信管道与 CUDA 层次映射、迭代处理）**可部分迁移，但需扩展以适配 PAT 的新特性** （如并行聚合树的拓扑与负载均衡）。

> 性能边界方面：

::: block-1
- 环算法在大消息、同构集群中优势显著（高带宽利用率）；
- 树算法适合小消息（低延迟）；
- PAT 作为新算法，可能在更大规模集群（如超 1000 节点）中表现更优，尤其在平衡多路径负载、减少跨节点同步开销上，但论文未提供具体数据，其与环 / 树算法的临界规模（如节点数、消息大小）仍需进一步验证。
:::

## 一、引言

> 高效的 GPU 间通信对于在分布式人工智能（AI）和高性能计算（HPC）工作负载中实现高性能至关重要。NVIDIA 集体通信库（NCCL）是一个被广泛采用的知名库，用于可扩展、优化的 GPU 通信[1], [2]。与 MPI[3]等通用消息传递框架不同，**NCCL 专门针对 GPU 间交互，利用 NVLink、PCIe 和 InfiniBand（IB）等互连技术来实现高带宽和低延迟。**

**尽管 NCCL 对大规模 GPU 系统至关重要且是开源的，但其内部机制的文档仍然不够充分**。这一点从 NCCL 的 GitHub 页面[1]上频繁出现的技术问题中可见一斑，:mdnice-bold-italic[用户在这些问题中寻求关于该库内部工作原理的细节]。虽然官方 API 文档很详尽，**但诸如拓扑构建、算法选择、流水线操作以及跨节点和设备的缓冲区管理等关键方面并未得到清晰描述**。这种透明度的缺乏使得系统研究人员、网络架构师和性能工程师难以在新硬件上以及大规模场景下优化或预测 NCCL 的性能[4], [5]。

> 在本文中，我们对 NCCL 的内部架构进行了全面且系统的探索。

我们的分析特别针对 NCCL 实现的四个主要方面：

::: block-1
1. 概述，包括 API 结构和通信通道管理；
2. 对通信协议（Simple、LL、LL128）的详细考察；
3. 对其数据传输模型的分析；
4. 对其集体通信算法的全面分析。
:::

从这项研究中获得的见解**为性能建模和架构优化提供了重要背景**。这些见解:mdnice-bold-italic[已被应用于诸如 ATLAHS[6]等仿真框架中]，ATLAHS 是一种应用跟踪驱动的网络仿真器，**旨在准确复现基于 NCCL 的机器学习工作负载的通信模式**。

> 通过阐明 NCCL 的内部设计原则，本分析支持系统研究人员、互连设计师和网络架构师在以 GPU 为中心的高性能计算环境中做出更明智的优化决策。

本文的分析基于 NCCL 2.19.1 版本。尽管特定的实现细节可能会在未来的版本中演变，但本文讨论的核心架构机制和通信策略预计将保持一致，确保所呈现的见解具有广泛的适用性。

## 二、NCCL 概述

### A. NCCL API

NCCL 专为 GPU 集群提供高度优化的集体通信操作，**重点关注低延迟和高带宽**。其:mdnice-bold-italic[核心是通过清晰高效的 API 管理 GPU 间通信]，该 API 抽象了复杂的技术细节。NCCL 主要为用户提供四类函数：

#### 1. 通信器管理

与 MPI 类似，NCCL 中的**所有通信操作都在通信器的上下文中执行**。每个参与通信的 GPU 都维护一个通信器对象，用于调用 NCCL 操作。:mdnice-bold-italic[用户【必须】首先初始化一个通信器，并定义参与的 GPU 集合。]

当所有设备在单个进程或线程内管理时，可以使用`ncclCommInitAll`集体创建通信器。对于多进程或多线程环境，每个进程调用`ncclCommInitRank`并传入一个共享的唯一标识符，以正确跨进程建立通信器。

通信任务完成后，应正确释放通信器以释放资源。NCCL 提供两个函数用于此目的：

- `ncclCommDestroy`：安全销毁通信器，确保在清理前完成所有未完成的通信操作。
- `ncclCommAbort`：立即终止通信器并取消正在进行的操作。这用于错误恢复或处理意外故障，以避免死锁。

#### 2. 集体通信

NCCL 提供 5 种集体操作：`ncclAllReduce`、`ncclBroadcast`、`ncclReduce`、`ncclAllGather`和`ncclReduceScatter`。历史上，NCCL 包含`ncclBroadcast`的原地变体`ncclBcast`，以模仿`MPI_Bcast`的行为（后者始终原地操作）。然而，为了支持更通用的用例并实现更规范的 API，NCCL 后来引入了具有独立发送和接收缓冲区的`ncclBroadcast`。`ncclBcast`现在已基本弃用，主要为了与 MPI 风格的接口兼容而保留。

#### 3. 点对点通信

NCCL 通过`ncclSend`和`ncclRecv`支持点对点操作。

#### 4. 组调用

**为了聚合操作并减少开销，NCCL 提供`ncclGroupStart`和`ncclGroupEnd`。** 这些函数括起一系列 NCCL 调用，并延迟其执行直到组结束。分组操作可包括多个发送/接收调用（以模拟 SendRecv、一对多、多对一或多对多模式）或一组集体操作。这种聚合通过确保所有分组操作作为单个 NCCL 启动的一部分一起执行，可以显著减少启动开销和延迟。

### B. 启动策略

NCCL **支持三种常见的执行模型** 来在:mdnice-bold-italic[多个 GPU 上启动操作]，每种方法都有不同的权衡。

::: block-1
- 每个 GPU 一个 CPU 进程：这种模型提供对进程放置的更大控制。通过将每个 GPU 绑定到单独的进程，相关的 CPU 代码可以调度在本地非统一内存访问（NUMA，一种内存架构，不同区域访问速度不同）域上，提高数据局部性并减少内存访问延迟。
- 每个 GPU 一个 CPU 线程：当单个 CPU 进程通过多个线程管理多个 GPU 时，它支持高效的进程内内存共享。这种设置允许直接访问跨 rank 的内存（包括 GPU 缓冲区），减少通信期间的内存复制开销。
- 多个 GPU 一个 CPU 线程：虽然单线程模型存在顺序内核启动和并发降低的问题，但它提供了简单性、最小的 CPU 开销和确定性执行，适用于小规模部署或原型环境（这些场景中实现的简便性比最高性能更重要）。
:::

### C. 通信通道

**NCCL 通过三个硬件组件协调通信：GPU、CPU 和网络接口**。GPU 执行归约（reduction，一种将多个数据合并为一个的操作）并在缓冲区之间移动数据，CPU 启动内核并管理主机端协调，网卡跨节点传输数据包。:mdnice-bold-italic[当仅由单个流多处理器（SM，GPU 上的计算单元）处理 GPU 工作时，大消息可能会使该 SM 过载，未充分利用其他 SM]，并且无法饱和 NVLink 或 InfiniBand 等链路[7], [8]。

为避免这种瓶颈，NCCL 将每个集体操作细分为通信通道。每个通道作为单独的 CUDA 块启动，在自己的 SM 上运行，并且库对输入缓冲区进行分区，使通道并行处理不相交的数据块。这种细粒度并行性提高了聚合吞吐量，特别是对于否则会在单个 SM 上序列化的大负载。将工作分散到多个通道还有助于在 NVLink 平台上平衡多个网卡的流量，因为每个通道可以通过不同的网卡独立退出节点。这提高了链路利用率，减少了空闲时间，并平衡了 NVLink、PCIe 和 InfiniBand 等互连的负载。

然而，**大量使用多个通道可能会对网络效率产生负面影响**。当每个通道的块大小小于网卡传输使用的 512 KiB FIFO 缓冲区大小时，代理线程会发送部分填充的缓冲区。这种未充分利用会降低 PCIe 和网络吞吐量，特别是当多个队列对（QP，用于网络通信的队列）活跃以启用等价多路径路由（ECMP，一种负载均衡技术）时。**NCCL 通过启发式减少小消息的通道数量** （参见`enqueue.cc`中的`calcP2pChunkSize`函数）**来解决此问题**。尽管如此，:mdnice-bold-italic[选择最佳通道数量仍然是 GPU 端并行性和网络利用效率之间的权衡。]

NCCL 中的通道管理在通信器级别进行协调，其中每个 GPU 会获得一个介于 0 到 n-1 之间的唯一 rank，n 为参与该通信器的 GPU 总数。在通信器初始化期间，NCCL 会建立一组初始的通道结构，其总数主要由系统拓扑和架构默认值决定。**当调用集体操作时，NCCL 为该特定任务动态选择算法和协议**。:mdnice-bold-italic[基于此运行时选择，NCCL 的内部调优模型然后确定为该操作使用多少个预先建立的通道，考虑所选策略、当前消息大小、可用带宽和每个通道的配置线程数]。尽管早期版本允许用户通过设置`NCCL_NTHREADS`等环境变量影响通道行为，但现在不鼓励这种手动调优。在最新版本中，这些设置通常被忽略，甚至可能导致错误行为。

**分配给每个通道的逻辑通信拓扑直接决定了每个操作期间 GPU 间的数据流向**。

- 在环形拓扑中，每个 GPU 识别其直接前驱和后继，形成单向通信环。
- 在树形拓扑中，每个 GPU 跟踪其父节点和子节点 rank，建立逻辑通信树。

:mdnice-bold-italic[为了提高带宽利用率，NCCL 采用双二叉树结构] [9], [10]：没有节点在两棵树中都是非叶节点，并且最多有一个节点在两棵树中都是叶节点。

::: block-1
- 当节点数为偶数时，第二棵树通过镜像第一棵树构建；
- 当节点数为奇数时，通过移位一个位置构建。
:::

这些拓扑在通信器初始化期间建立，并在所有集体操作中重用。

对于使用`ncclGroupStart`和`ncclGroupEnd`的分组点对点操作，NCCL 在可能的情况下将每个传输分配给单独的通道，使多个独立的发送和接收能够并行运行。这提供了跨传输的任务级并行性。

## 三、通信协议

> NCCL 采用多种通信协议来优化集体操作期间的数据传输效率。Simple、LL（低延迟）和 LL128 这三种协议旨在实现带宽和延迟之间的不同权衡。:mdnice-bold-italic[本节概述每种协议的机制。表 I 总结了这三种协议的关键特性。]

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/04.webp)

### A. Simple 协议

> **Simple 协议旨在最大化带宽利用率，用于大消息传输**。它通过:mdnice-bold-italic[将数据分成相对较大的块并在通信通道间分发来操作]。这种分块策略确保充分利用网络接口和 GPU 内存系统的高吞吐量。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/04.webp)

**为了保持内存一致性，该协议使用内存屏障** （确保内存操作按顺序执行的同步机制）**来强制数据的正确排序和可见性**。接收方必须等待完整块传输后才能访问它。虽然有效确保了正确性，但内存屏障的使用引入了显著开销。这种开销成为小消息的限制因素，其中同步成本主导总传输时间。

因此，虽然 :mdnice-bold-italic[Simple 协议为大消息实现了接近峰值的带宽，但在处理小负载时存在高延迟。]

### B. LL（低延迟）协议

> 为了解决 Simple 协议的延迟问题，NCCL 包含 LL 协议，**该协议针对带宽通常未被充分利用的小消息大小进行了优化**。LL 协议不依赖内存屏障，而是**使用轻量级的基于标志的同步** （通过小标志信号通知数据已准备好）。一个小标志与数据一起传输以指示其有效性，使接收方能够在数据可用后立即进行处理，而无需昂贵的内存屏障。

LL 协议中的每个传输包含 4 字节数据和 4 字节标志，通过 8 字节原子操作一起发送。这种方法显著减少了同步开销，并提高了对延迟敏感的工作负载的响应性。LL 强制中间缓冲区位于主机内存中，以便 CPU 可以轮询标志并检测数据何时准备好通过网卡发送。这是必要的，因为通过 PCIe 轮询 GPU 内存比 DRAM 访问慢得多，并且需要显式同步以确保主机上的数据可见性。虽然这种设计实现了低延迟，但它阻止了 GPU 直接远程直接内存访问（RDMA，不经过 CPU 直接访问远程内存）的使用，严重限制了带宽。因此，**LL 通常仅实现峰值带宽的 25-50%（取决于互连）**。因此，它:mdnice-bold-italic[仅适用于延迟至关重要而带宽利用率次要的小传输。]

### C. LL128 协议

> **LL128 协议在 LL 的基础上进行了改进，保留了其低延迟特性，同时显著提高了带宽效率，特别是在 NVLink 等高性能互连上**。与 LL 一样，它使用基于标志的同步来消除内存屏障，但它以 128 字节为单位传输数据，而不是 8 字节。在 128 字节中，120 字节用于数据，8 字节保留给标志，使该协议能够利用约 95%的峰值带宽。

在网络路径上，LL128 与 Simple 协议类似，发送 GPU 在通知 CPU 准备发送之前聚合相对较大的数据块。尽管这种基于块的聚合限制了跨节点的流水线（并行处理数据的不同阶段），但 LL128 由于其较小的传输粒度，在节点内仍受益于细粒度流水线。这种**低延迟和高吞吐量的组合使 LL128 适用于广泛的消息大小。**

:mdnice-bold-italic[然而，LL128 有更严格的硬件要求]。它**依赖于 128 字节的原子写入，内存系统或互连不得拆分或重新排序这些写入**。在由于 PCIe 限制或其他架构约束而无法保证此类操作的系统中，NCCL 会禁用 LL128 以避免数据损坏。因此，协议选择不仅受消息大小影响，还受系统级能力影响。

### D. 协议选择和比较

> NCCL 在运行时根据用户设置（即`NCCL_PROTO`）、集体算法和内部性能启发式动态在 Simple、LL 和 LL128 协议之间进行选择。

:mdnice-bold-italic[如果未明确指定，NCCL 使用调优模型，该模型考虑系统拓扑、GPU 架构、消息大小和预定义的性能指标来选择最佳的算法-协议对]。这种选择受到资源可用性的限制，例如协议特定缓冲区的内存。通常，LL/LL128 用于小消息以减少延迟，而 Simple 用于大消息以最大化吞吐量。

## 四、数据传输方法与传输层

> 高效的数据移动是 NCCL 通信性能的核心，尤其在多 GPU 和多节点环境中。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/05.webp)

如表 II 所示，NCCL 根据通信是发生在单个节点内（节点内）还是多个节点间（节点间），采用不同的数据传输策略和传输机制，**每种传输方式都针对特定的硬件和互连类型进行了优化**，以支持可扩展的集合通信。

### A. 节点内数据传输

NCCL 采用:mdnice-bold-italic[复杂的分层方法进行节点内通信]，**优先选择同一物理机器上 GPU 之间可用的最低延迟和最高带宽路径** （见图 1）。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/06.webp)

该策略**大量利用 NVIDIA 的 GPUDirect Peer-to-Peer** （P2P，GPU 直接点对点）技术，该技术使 GPU 能够直接访问彼此的内存，而无需通过 CPU 系统内存中转。

其**节点内策略的核心是 P2P 传输方式**，主要在 `src/transport/p2p.cc` 中管理。

::: block-1
- 当 GPU 通过 NVIDIA NVLink 互连时，NCCL 优先选择此路径，通过 NVLink 实现 GPUDirect P2P，以利用这些专用的、高速的、直接的 GPU 到 GPU 链路。
- 如果 NVLink 不可用，NCCL 可以通过 PCIe 总线利用 GPUDirect P2P 通信，这也由 P2P 传输层管理。
:::

这提供了一种 fallback（备用方案），其性能通常比使用 cudaMemcpy 进行主机内存中转要好得多。

**NCCL 的 P2P 传输中的一个关键优化是 `P2P_DIRECT` 模式，当通信的进程属于同一进程时启用**。虽然单进程和多进程通信都利用 GPU 到 GPU 的传输而无需 CPU 参与，但 `P2P_DIRECT` 模式通过两种方式显著提高效率。

::: block-1
- 首先，它通过在同一地址空间中使用直接的 GPU 内存指针，绕过了对 IPC（进程间通信）句柄的需求。
- :mdnice-bold-italic[更重要的是，它通过使用 `directSend` 和 `directRecv` 等原语消除了中间数据复制]，这些原语直接在源缓冲区和目标缓冲区之间传输数据，而不是通过中间的 FIFO（先进先出）缓冲区路由。
:::

尽管有这种优化的数据路径，NCCL 仍然通过共享结构（例如 `ncclSendMem` 和 `ncclRecvMem`）中的原子头和尾计数器来维持正确的同步，以确保适当的顺序并防止数据竞争。因此，`P2P_DIRECT` 在基础的 `GPUDirect P2P` 能力之上，通过简化的内存寻址和更直接的数据传输路径，提供了显著的性能优势。

**NCCL 不仅在直接的 GPU 到 GPU P2P 通信不可用时，而且在 P2P 不是最优选择时，可能会利用共享内存（SHM）传输方式**。:mdnice-bold-italic[特别是，跨插槽的 PCIe P2P 通常会生成 CPU 处理不善的 P2P 数据包，导致性能下降]。SHM 通过将流量路由到系统内存来避免这种情况，使用 PCIe 到内存和内存到 PCIe 的传输，而 CPU 通常对这些传输的处理进行了更好的优化。在 SHM 模式下，一个 GPU 的控制进程将数据写入共享内存段，然后由另一个 GPU 的进程读取。

请注意，在某些多插槽系统中，当每个 GPU 位于单独的 CPU 插槽上，且本地 NIC（网络接口卡）支持 GPUDirect RDMA 时，NCCL 可能会使用 NIC 进行 GPU 之间的节点内通信。NCCL 可能会通过 GPU–NIC–NIC–GPU 路径路由数据，而不是通过 CPU 互连，以利用 PCIe 带宽避免 CPU 瓶颈。这种行为由 NCCL 的拓扑感知逻辑决定，并且可以通过诸如 `NCCL_CROSS_NIC` 之类的环境变量进行控制。

### B. 节点间数据传输

> NCCL 中的节点间通信协调位于不同物理节点上的 GPU 之间的数据交换。此过程涉及执行 NCCL 内核的 GPU、在 CPU 上运行以管理网络操作的代理线程，以及底层网络结构。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/07.webp)

如图 2 所示，NCCL 根据可用硬件在两种主要网络传输方式之间进行选择，即标准的 TCP Socket（套接字）传输方式或高性能的 InfiniBand（IB，无限带宽）Verbs 传输方式。

#### 1. 基于套接字的通信

当网络接口不支持 RDMA（远程直接内存访问）时，NCCL 采用套接字传输方式，在 `transport/net_socket.cc` 中实现。在这种模式下，中间缓冲区被分配为主机内存中的 CUDA 固定内存（pinned memory，一种不会被分页到磁盘的内存）。

- 在发送端，数据从 GPU 复制到该缓冲区，然后使用标准的套接字调用通过网络发送。
- 在接收端，数据被接收到主机缓冲区中，然后复制到 GPU。

这种依赖主机内存作为中转区域的方式会产生 PCIe 总线上额外的内存复制开销。发送和接收都遵循一种 rendezvous（会合）协议，在实际数据传输发生之前，发送方和接收方会协调缓冲区的就绪状态。

#### 2. IB Verbs 传输方式

对于诸如 InfiniBand 或 RoCE（基于融合以太网的 RDMA）之类的高性能网络，NCCL 使用 IB 传输方式，在 `net_ib.cc` 中实现。IB 传输方式利用 RDMA 能力，以最小的 CPU 干预实现节点之间的直接数据移动。与套接字传输方式一样，所有传输都通过中间缓冲区中转，但该缓冲区的位置取决于硬件支持和配置。

默认情况下，如果 NIC 不能直接访问 GPU 内存，中间缓冲区会分配在主机内存中。GPU 内核将数据复制到该缓冲区，代理线程发布 RDMA 操作，通过 RDMA 写操作将数据从主机内存移动到远程节点[12]。在接收端，过程相反：NIC 将传入的数据写入主机缓冲区，代理线程协调从主机到设备内存的复制。代理线程的作用是管理这些 DMA（直接内存访问）和 RDMA 操作。与套接字传输方式一样，在数据传输之前，会使用会合协议来同步发送方和接收方。

> 在以下内容中，我们重点介绍 IB 传输方式中实现的一些关键特性和优化。

##### a) GPUDirect RDMA 优化

IB 传输中的一个关键优化是 GPUDirect RDMA（GDRDMA，GPU 直接远程直接内存访问），它使 NIC 能够直接访问 GPU 内存，消除了对主机内存中转的需求。

GDRDMA 仅在 NIC 和 GPU 都连接到同一个 PCIe 交换机时使用。在这种情况下，中间缓冲区分配在 GPU 内存中。CPU 代理线程使用诸如 nv_peer_mem[13]或 Linux DMA-BUF 子系统[14]之类的机制，向支持 RDMA 的 NIC 注册此 GPU 内存，允许 NIC 直接映射和访问 GPU 内存。然后，NIC 的 DMA 引擎直接对 GPU 执行 RDMA 读或写操作，完全绕过 CPU 和主机内存。

##### b) 每对等点多通道连接

作为提高带宽利用率和减少拥塞的优化措施，IB 传输方式默认情况下为每个远程 GPU 和每个 NIC 实例化 2 个逻辑通道（由 `NCHANNELS_PER_NET_PEER` 参数控制）。每个逻辑通道维护自己的 `ncclIbSendComm` 结构，嵌入独立的 InfiniBand QP（队列对）束。在执行过程中，主机端网络代理在发出 `ncclNet->isend()`调用时在两个 `sendComm` 句柄之间交替，从而在 QP 集之间分配流量。这种轮询策略增加了每个 QP 的有效块大小，为支持 ECMP（等价多路径路由）的网络结构引入了路径多样性，并提高了整体互连效率——所有这些都不会产生额外的协调开销。

##### c) QP 布局

对于每对进程（rank），RDMA 插件建立两个可靠连接（RC）QP，每个方向一个。前向 QP 负责 bulk data stream（大量数据流）：代理发布一个或多个 `RDMA_WRITE` 工作请求，将用户数据直接推送到对等端缓冲区，随后是一个 `RDMA_WRITE_WITH_IMM`（带立即数的 RDMA 写）用于完成通知。

这个最终请求的行为取决于通信模式：

::: block-1
- 对于小消息，它在单个操作中组合数据和大小信息，以最小化开销；
- 对于具有自适应路由的大消息，它发送一个零字节写操作，将传输大小作为立即数数据，以保证顺序，同时允许大量数据使用自适应路由；
- 对于聚合的多消息传输，它将精确的大小信息写入远程数组，同时使用立即数数据进行完成信号通知。
:::

反向 QP 仅携带微小的 clear-to-send（CTS，允许发送）消息，这是一个单独的 `RDMA_WRITE`，用于通告远程缓冲区地址、rkey（远程键）和标签信息。虽然理论上可以在单个 QP 上多路复用相同的功能，但将 CTS 分离到自己的通道可以将对延迟敏感的控制流量与占用大量带宽的数据流隔离开来，使网络能够以最小的头阻塞（head-of-line blocking，指队列中前面的数据包阻塞后面数据包传输的现象）来传输它。

##### d) 带环回 RDMA_READ 的本地刷新

当启用 `GPUDirect RDMA` 时，发送方**必须确保所有未完成的 PCIe 写操作** 在核（kernel）使用数据之前到达 GPU 内存。NCCL 通过在最后一次接收完成后发出一个 dummy（虚拟的）`RDMA_READ` 来实现这一点。一个专用的“flush（刷新）”QP 连接到自身，这意味着其 `ready-to-receive`（RTR，准备接收）阶段使用自己的本地 QP 编号作为目的地。

因此，该读取操作永远不会离开主机，但 verbs 层仍然会等待先前写操作的 PCIe 完成，从而提供一个低成本的顺序屏障。

## 五、NCCL 集合通信算法

> 集合通信算法是 NCCL 的核心，它支持 GPU 之间高效、同步的通信。这些算法管理数据移动和依赖关系，优化通信路径，并能随 GPU 数量增加而扩展。**NCCL 通过将每个集合通信操作分解为低级通信原语，并将其分布到多个并行通道来实现这些算法**。:mdnice-bold-italic[算法的选择] （通常是环形或树形）:mdnice-bold-italic[取决于具体的集合操作以及相关的执行参数]，如消息大小和拓扑结构[15]–[17]。本节将**概述 NCCL 集合通信算法的设计和主要特征**。

### A. 算法和协议支持概述

虽然 NCCL 提供了六种协议，但并非所有协议都适用于每种算法，且它们的可用性可能因硬件特性和运行时约束而有所不同。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/08.webp)

表 III 总结了 NCCL 2.19 版本中 5 种集合操作所支持的算法和通信协议。这些信息来自 `src/device` 目录下的相应头文件。除了常用的环形（Ring）和树形（Tree）算法外，该表还突出显示了对专门算法（即 CollNet 和 NVLS）的支持。

> **NVLS 和 CollNet 是主要为优化 AllReduce 性能而设计的专门算法**，其中 NVLS 还通过利用特定硬件能力支持 ReduceScatter 和 AllGather。

CollNet 算法适用于网络基础设施本身可以参与集合操作的场景，例如使用 NVIDIA SHARP（可扩展分层聚合和归约协议）技术，允许将归约或其他部分集合计算卸载到网络交换机，从而减少数据移动和延迟[18]。

CollNet 算法利用 NVIDIA SHARP（可扩展分层聚合和归约协议）技术进行网络辅助的集合操作。CollNet Direct 支持节点内的全对全通信。相比之下，CollNet Chain 将 GPU 线性排列，沿链向上执行归约，再向下广播[19]。

NVLS 算法旨在利用 NVIDIA 的 NVLink 交换机（NVSwitch）系统，该系统在多 GPU 服务器或 NVSwitch 架构内提供高带宽、直接的 GPU 到 GPU 通信路径，从而实现更高效的集合操作[2]。普通 NVLS 和 NVLS Tree 算法都使用 NVLink SHARP 进行节点内归约，但在节点间处理上有所不同：NVLS 通过 CollNet 和支持 SHARP 的交换机继续归约，而 NVLS Tree 使用基于树形的扇出方式[19]。

然而，本文不会分析 NVLS 和 CollNet，因为它们的实现严重依赖特定硬件（NVSwitch 和支持 SHARP 的网络），因此不具有广泛代表性。我们承认 NCCL 在不断发展，最近在 2.23 版本中引入了诸如并行聚合树（PAT）等额外算法[20]，[21]。尽管如此，**由于较新的算法尚未得到广泛采用，我们后续的讨论** 仍将:mdnice-bold-italic[集中在环形和树形算法上]。

### B. 通信原语

> NCCL 通过组合一组**低级通信原语** 来实现高级集合通信操作。这些原语构成了 NCCL 集合通信算法的基础，封装了诸如跨 GPU 发送、接收、归约和复制数据等基本操作。

常见的原语包括 `send`（发送）、`recv`（接收）、`recvReduceSend`（接收-归约-发送）、`recvCopySend`（接收-复制-发送）和 `recvReduceCopySend`（接收-归约-复制-发送），以及第四节 A 中讨论的它们的“直接”变体。

**每个原语代表一种不同的数据移动或计算模式，其命名规则清晰地表明了操作的顺序**。例如，`recvReduceSend` 表示 GPU 从对等节点接收数据、与本地缓冲区执行归约、然后将结果发送到下一个 GPU 的步骤。在执行过程中，NCCL 运行时会在循环步骤中迭代调度这些原语，从而支持不同算法、拓扑和传输层之间的灵活协调。

**每个 NCCL 原语的行为还受所选通信协议的影响**。同步、缓冲区管理和传输粒度会因使用 Simple、LL 还是 LL128 协议而有所不同。需要注意的是，:mdnice-bold-italic[这些低级原语针对具有固定、少量源和目的地的集合通信进行了高度优化]，例如环形和树形（通常涉及一个源和一个目的地，某些树形拓扑最多涉及三个）。虽然这种方法对许多标准集合通信算法能实现高效性，但对于需要处理 N 个源和 N 个目的地的模式（如全对全）则效果较差。

### C. NCCL 集合通信的迭代执行

> NCCL **处理集合通信操作** 时，首先将用户的输入数据分配到可用的通信通道中，从而在通道级别实现并行性。每个通道负责输入的一个连续段，其大小由元素总数（count）和通道数量决定。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/09.webp)

这种分区如图 3 所示，其中总数据被拆分，以便每个通道（如通道 0 和通道 1）独立处理其分配的区域。每个通道工作的起始索引由 workOffset 给出，大小由 channelCount 给出。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/10.webp)

**为了促进高效的数据传输和计算，NCCL 为每个通道分配一个固定大小的缓冲区，其容量取决于所选的通信协议** （Simple、LL 或 LL128，如表 IV 所示）。如果通道的数据区域大于其总缓冲区，NCCL 会将数据拆分为多个外循环迭代。每次迭代处理的数据段最大为缓冲区大小（每次迭代 loopCount 个元素），通道会循环执行足够多的迭代以覆盖其分配的所有元素。

**在每个外循环迭代中，NCCL 通过将通道缓冲区划分为固定数量的段** （称为槽位，通常为 8 个，由 `NCCL_STEPS` 参数设置）**来实现流水线**。每个槽位可以独立推进到通信和计算的不同阶段，允许流水线将数据传输与归约或复制重叠进行。在每个基本步骤中（遵循第五节 B 中描述的通信原语），一块数据（`chunkCount` 个元素，或循环中最后一块的 `lastChunkCount` 个元素）被处理并映射到缓冲区槽位。:mdnice-bold-italic[这种分块机制使 NCCL 能够保持通信通道繁忙，将新块与正在进行的操作重叠，以实现最大吞吐量。]

在 NCCL 中，**数据移动的基本单位称为元素，其含义取决于集合操作**。

- 对于 `ncclAllGather` 和 `ncclBroadcast`，每个元素是一个字节，因为这些操作专注于高效移动和连接数据。这种字节级粒度使 NCCL 能够灵活地打包和传输数据，而不受底层类型的限制。
- 对于 `ncclAllReduce`、`ncclReduceScatter` 和 `ncclReduce`，每个元素对应于用户定义的数据类型（如 float 或 int），因为这些操作需要仅在数据类型级别有意义的算术归约。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/09.webp)

**图 3 展示了这个过程的实际情况。图中的每个单元格代表 sendBuff 中的一个数据元素**。为了便于说明，本例假设 `channelCount` 等于 2，`chunkCount` 等于 2，`loopCount` 等于 4。

- 通道 0 从其 `workOffset` 开始，以 loopCount 为单位进行循环迭代处理元素，并将其进一步拆分为 `chunkCount` 大小的块。
- 通道 1 对自己的区域遵循相同的逻辑。

通过协调这种分区和流水线，NCCL 在所有参与的 GPU 上实现了高效、并行和可扩展的集合通信操作。

### D. 通信流水线到 CUDA 层次结构的映射

> 为了**充分理解 NCCL 的性能特征**，必须研究这些:mdnice-bold-italic[通信通道和数据流水线如何映射到 GPU 的并行执行模型]。NCCL 通过与 CUDA 线程组织对齐的精心结构化层次，在多个 SM（流式多处理器）上调度数十万个线程。

#### 1. 网格和块结构

NCCL 内核以`（nChannels, 1, 1）`的网格维度启动，其中 nChannels 表示操作的活动通信通道数量。这种一对一映射确保每个 CUDA 块（`blockIdx.x`）正好对应一个通信通道。在每个块内，NCCL 使用可变数量的线程，范围从 `NCCL_MIN_NTHREADS` 到 `NCCL_MAX_NTHREADS`。确切的线程数由 NCCL 的自动调优系统确定，并在核函数启动准备期间存储在 `plan->threadPerBlock` 中。

#### 2. 通道到块 ID 的映射

`blockIdx.x` 和通道 ID 之间的映射通过基于位掩码的方法管理。每个内核接收一个 channelMask，用于指定当前操作的活动通道。

设备代码使用位填充计数计算块索引和通道 ID 之间的对应关系：对于给定的 `blockIdx.x`，通道 ID 通过找到 channelMask 中第 `blockIdx.x` 个设置的位来确定。

#### 3. warp 级组织

在**每个块内，NCCL 在 warp** （线程束，CUDA 中 32 个线程组成的小组）**级别将线程组织为专门的角色**。

::: block-1
- 前两个 warp 处理初始化任务：warp 0 将通信器元数据（ncclDevComm）加载到共享内存中，而 warp 1 加载通道特定数据（ncclDevChannel）。
- 其余的 warp 执行实际的通信和计算工作。
:::

对于集合操作，工作 warp 的数量由工作描述符中的 nWarps 字段控制。不同的算法对这些 warp 的分配方式不同。例如，在 NVLS AllReduce 中，warp 被细分为不同阶段的组。对于点对点操作，warp 在发送和接收操作之间进行划分，其分布根据并发传输的数量动态计算。

#### 4. 基于槽位的流水线执行

**在每个通道的缓冲区中，`NCCL_STEPS` 槽位支持线程级的细粒度流水线**。:mdnice-bold-italic[warp 内的线程协作以循环方式将数据移动通过这些槽位]。每个槽位包含一个 `ncclConnFifo` 结构，该结构具有模式（mode）、偏移量（offset）、大小（size）和数据指针（data pointer）等字段，允许数据同时处于不同的流水线状态：正在计算中、排队等待传输、在网络上传输中或准备好供使用。

#### 5. 线程级数据移动

在最细粒度上，NCCL 在每个 warp 内的各个线程之间分配工作。对于批量数据移动，线程在每次迭代中以展开的方式处理多个数据元素。确切的数量取决于协议。

通过 warp 统一操作（warp 内所有线程执行相同操作）仔细管理线程分歧。例如，warp 中的所有线程执行相同的操作序列（发送、归约、复制），但针对不同的数据元素或内存地址。这**确保了 GPU 的 SIMT（单指令多线程）架构的最大利用率**。

#### 6. 并发流水线执行

- 关键的是，NCCL 从不执行高级描述中可能暗示的“一个通信任务”。
- 相反，它**同时维护数十个并发的数据移动流水线**。多个通道在不同的 SM 上并行执行，每个通道内的多个槽位流水线处理数据流动的不同阶段，每个通道内的多个 warp 处理通信的不同阶段。

这种多级并行性对于实现高带宽利用率至关重要。

### E. 定性算法分析

> 既然我们已经确定所有常见的 NCCL 集合通信算法都遵循迭代处理模型，那么一个重要的区别在于 **GPU 是否可以对连续的循环迭代进行流水线处理**。基于这一特征，:mdnice-bold-italic[算法可以分为两类：流水线式和非流水线式。]

在以下各节中，我们将据此组织集合通信算法，并**对每种算法进行定性分析**。对于每种算法，我们将**描述在每个循环迭代中执行的特定基本步骤序列**。

虽然我们最初考虑进行定量复杂度分析，以根据数据大小和 alpha-beta 模型等参数来界定算法运行时间，但我们发现这种方法不切实际，因为影响性能的因素很多。诸如 GPU 在节点间的分布方式等变量会产生重大影响。例如，单个节点上的 4 个 GPU 与分布在不同节点上的 4 个 GPU 会经历非常不同的带宽和延迟。包含所有这些变量会使模型过于复杂，违背了保持复杂度界限简单实用的目标。因此，我们的:mdnice-bold-italic[分析仍然是定性的，重点关注基本行为，而不是试图提供详细的理论运行时间估计。]

#### 1. 非流水线模式

> 在非流水线模式中，**每个 GPU 必须完成一次迭代中的所有任务才能开始下一次迭代**。环形 AllReduce、环形 AllGather 和环形 ReduceScatter 遵循这种模式。在下面的分析中，k 表示参与集合通信的 GPU 数量。

##### a) 环形 AllReduce

NCCL 中的环形 AllReduce 算法**结合了分布式归约阶段和数据分发阶段**，以**确保所有参与的 GPU 都能收到完整的、逐元素归约的结果**。该操作在每个循环中分为 2k-1 个步骤，详见表 V。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/11.webp)

环形 AllReduce 算法始于一个类似 ReduceScatter 的阶段，如图 4 上半部分所示。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/12.webp)

最初，在步骤 0 中，每个 GPU 将其本地数据的一个段发送到其邻居。在接下来的 k-2 个步骤中，每个 GPU 反复执行 `recvReduceSend` 操作：从其前序邻居接收一个数据段，与本地数据的对应段执行逐元素归约，然后将归约结果转发给环形中的后序 GPU。这种迭代归约持续到步骤 k-1。在这一步中，每个 GPU 接收一个数据段，执行最终归约，从而生成完全归约的段，并将结果复制到输出缓冲区中的指定位置，然后再将该段转发出去。

在这一步中，每个 GPU 接收一个数据段，执行最终归约，并将结果复制到输出缓冲区的指定位置，然后再将这个完全归约的段转发出去。在接下来的 k-2 个步骤中，每个 GPU 执行一系列 `recvCopySend` 操作。在每个步骤中，GPU 从前序邻居接收一个完全归约的段，将其直接复制到输出缓冲区的适当位置，并将该段原封不动地转发给下一个 GPU。环形 AllReduce 操作在步骤 2k-2 结束，每个 GPU 执行最后的 recv 以完成完全归约数据的收集。

##### b) 环形 AllGather

环形 AllGather 算法**使 k 个参与 GPU 中的每一个都能收集所有`_rank`（进程或设备的标识）贡献的完整数据块集**。该算法:mdnice-bold-italic[使用连接 GPU 的逻辑环形拓扑，通过 k-1 个通信步骤进行。]

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/13.webp)

在初始步骤（表 VI 中的步骤 0）中，每个 GPU i 准备其本地数据块。如果操作是原地（in-place）的，则该块已位于输出缓冲区的第 i 个段中。否则，GPU 使用 `copySend` 原语将数据从其输入缓冲区复制到该段中。完成此设置后，每个 GPU 将其本地块发送到其右侧邻居。

在接下来的 k-2 个步骤中，每个 GPU 执行一系列 `recvCopySend` 操作。在每个步骤中，GPU 从其左侧邻居接收一个块，将其存储在输出缓冲区的正确段中，然后转发给右侧邻居。最后一步是 `recv` 操作，用于传递最后一个缺失的块。此步骤后，所有 GPU 都持有集合数据的完整、有序副本。

##### c) 环形 ReduceScatter

环形 ReduceScatter 算法**对最初分布在 k 个 GPU 上的数据块执行逐元素归约，然后将完全归约结果的唯一段散射回每个 GPU**。:mdnice-bold-italic[开始时，每个 GPU 的 sendbuff 包含 k 个不同的数据块]，这些数据块:mdnice-bold-italic[在逻辑环形拓扑中移动时会逐步归约]。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/14.webp)

**表 VII 总结了环形 ReduceScatter 的单个循环迭代中每个步骤执行的原语**。

在初始步骤中，每个 GPU i 将其本地数据块之一发送到其直接邻居 GPU (i+1)%k，启动环形中的数据移动。在随后的 k-2 个步骤中，每个 GPU 执行一系列 `recvReduceSend` 操作：

- 从其左侧邻居（GPU (i-1)%k）接收一个部分归约的数据块，将该块与其 sendbuff 中存储的对应本地块进行逐元素组合。
- 然后将另一个部分归约的块转发给其右侧邻居。
- 在最后一步中，每个 GPU 从其左侧邻居接收最后一个数据块，应用最终归约操作，并将完全归约的结果直接复制到自己的 recvbuff 中。

#### 2. 流水线模式

> NCCL 中的树形 AllReduce、环形 Broadcast 和环形 Reduce 算法遵循流水线执行模式。

##### a) 树形 AllReduce

树形 AllReduce 算法**在每个循环迭代中分为两个不同的阶段：归约（Reduce）阶段和广播（Broadcast）阶段。**

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/15.webp)

数**据移动通过一个涉及 4 个 GPU 的示例在图 5 中说明**。尽管图示显示了四个`_rank` 上的完整树，但需要注意的是，:mdnice-bold-italic[分支结构仅在节点间构建。在每个节点内部，NCCL 将本地 GPU 以简单链的形式连接]。在 NCCL 的另一种实现中，这两个阶段通常通过将 SM（流式多处理器）划分为两个不均匀的组来并发执行。一组处理向根节点的归约，另一组同时执行从根节点的广播。**这种非对称分配将更多线程用于带宽密集型的归约阶段**，从而能够更好地利用可用资源。

::: block-1
- 在归约阶段，叶节点 GPU 通过 send 操作将其本地数据向上发送到其父节点，启动归约。中间节点 GPU 使用 `recvReduceSend` 原语从一个或多个子节点接收数据，与自己的数据执行逐元素归约，并将结果向上传递。最后，根节点 GPU 执行 `recvReduceCopySend`，通过将传入数据与其本地缓冲区组合并将完全归约的结果复制到用户提供的输出缓冲区来完成归约。
- 在广播阶段，完全归约的结果被向下传播到树中。根节点使用 `recvCopySend` 操作将结果发送到其子节点。中间节点 GPU 从其父节点接收数据，将其复制到自己的输出缓冲区，并使用相同的 `recvCopySend` 原语将其转发给其子节点。叶节点 GPU 使用简单的 recv 接收数据并将其复制到输出缓冲区。
:::

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/16.webp)

每种 GPU 角色使用的设备原语序列总结在表 VIII 中。

##### b) 环形广播

NCCL 环形广播算法**将数据从用户指定的根 GPU 分发到通信器中的所有其他 GPU**。尽管它使用环形拓扑，但:mdnice-bold-italic[通信模式实际上形成了一个有向链]，从根节点开始，依次经过每个 GPU，直到最后一个 GPU 收到数据。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/17.webp)

操作从根 GPU 开始，如表 IX 所示：

- 根节点如果其发送缓冲区也是接收缓冲区，则执行原地 send 操作；
- 否则执行 copySend，即将来自其不同发送缓冲区的数据先复制到接收缓冲区，然后再传输。

无论哪种情况，根节点都将其数据块发送到环形中的直接后继节点。链中间的每个后续 GPU 执行 `recvCopySend` 原语：从其前驱节点接收数据块，将其复制到自己的接收缓冲区，然后将数据块转发给其后继节点。 这个过程持续到数据到达链中的最后一个 GPU。最后一个 GPU 只需执行 recv 操作，将传入的数据复制到其接收缓冲区，不再发送，因为逻辑链中的所有 GPU 现在都已收到广播数据。

##### c) 环形归约

NCCL 环形归约算法**对分布在多个 GPU 上的数据执行逐元素归约，将最终结果聚合到用户定义的根 GPU 上**。与环形广播一样，:mdnice-bold-italic[该操作利用从环形拓扑派生的逻辑链，数据沿该链流动并向根节点聚合。]

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/18.webp)

- 如表 X 所示，链始于第一个 GPU 将其本地数据块发送到环形中的下一个 GPU。
- 中间 GPU 执行 `recvReduceSend` 原语：每个接收部分归约的块，使用自己的对应数据应用逐元素归约，并将更新后的结果转发给下一个 GPU。这个过程重复进行，直到数据到达目标根节点。
- 根 GPU 通过 `recvReduceCopy` 完成操作：接收最终的部分结果，与本地数据进行归约，并将完全归约的输出存储在其接收缓冲区中。

### F. 基准测试

在本节中，我们展示 NCCL 集合通信的基准测试结果。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/19.webp)

> 图 6 突出显示了**三种 NCCL 通信协议在节点内和节点间设置下 AllReduce 的运行时性能**，提供了它们行为的代表性视图。

实验在瑞士国家超级计算中心（CSCS）的 Alps 超级计算机系统上进行，使用 16 个配备 NVIDIA Grace Hopper 超级芯片（GH200）的节点。每个节点提供 150GB/s 的高带宽节点内互连，并通过 25GB/s 每方向的网络链路连接到 Cray Slingshot 互连[5]，[22]。

在**节点间** 设置中，对于树形和环形算法，:mdnice-bold-italic[LL 和 LL128 在小消息（小于 64 KiB）上表现最佳]。然而，当 AllReduce 消息大小在 16 个节点上增加到千兆字节范围时，与 Simple 协议相比，它们的性能急剧下降。这主要是**由于 LL 和 LL128 中细粒度的、基于标志的同步开销，这需要在网络上处理数百万个小的同步操作** （每 8 或 128 字节一个）。虽然 LL128 受益于更大的缓冲区大小，并且在 NVLink 上效率很高，**但对于大型节点间传输，这些优势被 RoCE 上的累积同步成本所抵消**。LL128 甚至可能落后于 LL，因为在大规模下，每个 128 字节操作的额外成本变得显著，或者在高竞争下，停顿对更大的数据单元影响更大。相比之下，Simple 协议使用更大的传输，同步事件更少，因此对网络延迟不太敏感，并且在大消息上更能维持高吞吐量。

![文章插图](/articles/2025-08-07-gpu-nccl-25-95-9e46767f/images/04.webp)

另一方面，在节点内设置中，**LL128 协议在所有消息大小上都表现出一致的性能，这要归功于它能够充分利用 NVLink 连接**。特别是对于小消息，LL128 的性能与 LL 相当或仅略差，而在大消息上几乎与 Simple 的性能相当（如预期的那样，比 Simple 慢 5%，见表 I）。其余两种协议 LL 和 Simple 在相反的极端表现最佳，**Simple 在大消息上提供最佳性能，LL 在小消息上提供最佳性能**。最后，我们观察到:mdnice-bold-italic[在节点内和节点间设置中，环形算法在大消息上表现出色，而树形算法在小消息上表现最佳。]

> 这个基准测试实验有三个结论。

::: block-1
- 首先，结果证实了预期：**LL 和 LL128 最适合小消息**，特别是**节点间** 通信，而 Simple 协议在大型分布式传输中始终优于其他协议。
- 其次，考虑通信是节点内还是节点间很重要，因为不同的传输算法（特别是 LL128）在这些配置中表现出明显不同的性能。
- 最后，虽然手动选择协议对于针对性调优可能有用，但在**大多数情况下，依赖 NCCL 的自动调优更为有利**。允许 NCCL :mdnice-bold-italic[根据工作负载特征选择协议通常能在大多数用例中提供稳健的性能和可扩展性。]
:::

## 六、集成到 ATLAHS 中

我们对 NCCL 内部通信模式、算法和流水线处理模式的深入分析，极大地指导了 ATLAHS 工具链[6]的设计和功能。

::: block-1
- **通过将 NCCL 操作的原语、数据依赖关系和时序行为** （细化到它们在 CUDA 流和通信通道上的迭代执行）**进行特征描述**，我们**能够准确地将集合通信分解为细粒度的计算、发送和接收事件**。这些知识:mdnice-bold-italic[对 ATLAHS 的 GOAL 调度生成过程[23]起到了关键作用]。
- 此外，**理解流水线式与非流水线式集合通信**，使我们**能够忠实地建模并发性和重叠性**，这对于模拟大规模大语言模型（LLM）训练至关重要。
:::

这种:mdnice-bold-italic[基于 NCCL 的建模方法使 ATLAHS 能够准确模拟真实 AI 训练工作负载中的 GPU 通信行为]。与以往主要依赖合成模式或抽象模型的模拟器不同，**ATLAHS 以高保真度捕捉集合操作的执行逻辑**。通过将这些见解嵌入到 GOAL 调度生成器中，ATLAHS 支持广泛的拓扑结构和配置，同时将仿真误差保持在 5%以下。

正如我们的验证和案例研究所示，这种设计使 ATLAHS 在大规模多 GPU 环境中的运行时预测方面，优于 AstraSim[24]等最先进的工具。

## 七、相关工作与展望

> 最近的研究对分布式深度学习和高性能计算（HPC）环境中的集合通信库（如 NCCL、MPI 和 Gloo）进行了详细分析和性能评估。

例如， - Lee 和 Lee[25]进行了一项实证研究，在各种训练架构和部署环境下对这些库进行了比较，强调了 NCCL 在节点内 GPU 到 GPU 通信（特别是大规模 All-Reduce 操作）中的明显优势，但也指出了其在虚拟化或容器化开销下的性能下降。
- 其他工作，如 Weingram 等人[26]的综合调查，对集合库生态系统提供了广泛视角，回顾了 NCCL、RCCL、oneCCL 和 Gloo 等行业解决方案，并指出虽然 NCCL 仍然是 GPU 中心集合通信的黄金标准，但替代库正在迅速发展以匹配其优化和硬件支持。

尽管这些研究提供了关于性能和架构选择的宝贵见解，但**大多数都侧重于实证基准测试、高层比较或特定算法创新**。:mdnice-bold-italic[我们的工作不同之处在于，对集合实现中的内部迭代执行算法、通信协议和数据依赖关系进行了深入、系统的分析。]

> 尽管 NCCL 被广泛采用，但它面临着来自**强调适应性、拓扑感知和容错性的最新进展的压力**。

新兴库（如 Blink）通过动态构建多棵树并利用先进的网络拓扑实现了显著的加速，在大规模和异构集群中优于 NCCL 的环形和树形算法[26,27]。

- 诸如 SCCL[28]之类的自动化框架通过为特定硬件合成和调优集合通信，进一步突破了极限，超越了手工优化的程序。
- 随着分布式 AI 工作负载变得更加资源密集和长期运行，容错性和弹性也成为关键要求[26]。

为了跟上步伐，我们认为**未来版本的 NCCL 需要支持自动化算法选择、强大的故障处理**，以及**与下一代网络** （具有网络内计算和智能网卡等功能）**的更紧密集成**。这些增强对于在日益苛刻的分布式训练环境中维持高性能、可扩展性和可靠性至关重要。

## 八、结论

> 本文对 NVIDIA 集合通信库（NCCL）进行了系统且深入的分析。

我们的研究考察了 NCCL 的**通信协议** （强调其:mdnice-bold-italic[设计权衡和动态选择逻辑]），以及在**节点内和节点间** 环境中采用的:mdnice-bold-italic[数据传输机制]。

::: block-1
我们还分析了 NCCL 广泛使用的**基于环形和树形的集合通信算法**，详细阐述了它们的迭代执行模型和所采用的 **GPU 通信原语序列**。这些见解不仅具有学术意义，还是 ATLAHS（一种能够准确建模大规模 AI 训练工作负载通信行为的应用跟踪驱动网络仿真工具链）开发的基础。
:::

通过揭示 NCCL 的内部机制和性能关键决策，这项工作为系统研究人员、网络架构师和性能工程师提供了诊断瓶颈、优化通信模式以及为未来高性能集合库设计提供信息所需的见解。
