## 关键问题

### 问题 1. 当前 LLM 在 AscendC、Pallas 等非 NVIDIA 主流硬件的 DL 核生成中表现极差（即使采用类别感知提示后，AscendC 最高 Pass@1 仍不足 40%，Pallas 不足 90%），其根本瓶颈是“训练数据中硬件特异性代码缺失”，还是“LLM 架构本身无法理解不同硬件的底层计算逻辑（如 AscendC 的异构计算单元协作、Pallas 的 TPU tile 调度）”？这一瓶颈是否会导致 LLM 在小众硬件核生成场景中始终无法达到工业实用水平？

从论文实验与分析来看，**“训练数据中硬件特异性代码缺失”是核心瓶颈，但“LLM 对硬件底层计算逻辑的理解能力不足”是重要辅助约束**，二者共同导致当前性能短板；且短期内 LLM 在:mdnice-bold-italic[小众硬件 核生成场景中难以完全达到工业实用水平]，但在下面三点上仍:mdnice-bold-italic[存在局部突破可能。]

::: block-1
1. **数据缺失是首要瓶颈**：论文明确指出，AscendC、Pallas 在 LLM 预训练语料中的覆盖率远低于 CUDA（如 4.2 节提到“AscendC 代码在预训练语料中曝光不足”，Pallas 因基于 Python 虽编译错误少，但 runtime 错误多源于“幻觉 API 关键字”）。而类别感知提示策略的效果（如 AscendC 的 Matrix Multiply 类别 Pass@1 从 0 提升至 35.3%，Pallas 的 Reduce 类别从 0 提升至 80%），直接证明“补充同类别硬件特异性代码示例”可显著改善性能——这反过来说明“数据缺失”是当前最核心的限制。
2. **LLM 架构对硬件逻辑的理解局限是次要但关键的约束**：即使补充类别示例，LLM 仍无法突破深层硬件逻辑的理解天花板。例如，论文 4.4 节提到 AscendC 的 Reduce 类别中，LLM 生成的核因“无法处理 3D 输入张量（示例仅为 2D）”而失败，暴露其“无法泛化硬件特异性数据结构逻辑”；AscendC 的异构计算单元（标量/向量/立方单元）协作、Pallas 的 TPU tile 调度等底层逻辑，LLM 仍只能通过示例模仿语法，而非真正理解原理（如 AscendC 的 Softmax 核仍会调用不存在的`AscendC::Softmax`函数）。
3. **工业实用水平的挑战**：当前即使采用最优策略，AscendC 最高 Pass@1 仅 40%（GPT-4o 的 Matrix Multiply 类别），Pallas 最高 Pass@1 仅 86.7%（DeepSeek-V3 的 Activation 类别），且 SpeedUp@1 普遍低于 30%（如 AscendC 的 Activation 类别最高仅 20%）。工业场景需“正确性 ≥99%+性能优于优化工具链”，而 LLM 当前既无法覆盖全类别（如 AscendC 的 Normalization 类别仍 0% Pass@1），也难以稳定超越工业级优化——短期内仅能在“简单类别（如 Activation）+ 数据补充充分”的局部场景落地，全场景实用仍需突破。
:::

### 问题 2. 论文采用“PyTorch eager 模式”作为性能基准计算 SpeedUp@k，但工业界实际会使用 TorchDynamo、TensorRT、Ascend CANN 等硬件优化工具链对核进行编译优化。若 LLM 生成的核仅比 eager 模式快，却慢于工具链优化后的原生核，其落地价值将大幅降低——那么当前 MultiKernelBench 的性能评估体系是否存在“基准宽松化”问题？该评估体系能否有效筛选出真正具备工业落地意义的 LLM 生成核？

**存在“基准与工业实际脱节”的宽松化问题，当前评估体系无法直接筛选出具备工业落地意义的 LLM 生成核，但具备优化潜力**。具体依据如下：

::: block-1
1. **基准宽松化的直接原因**：论文明确说明，选择“PyTorch eager 模式”作为基准是为了“避免 TorchDynamo、TensorRT 等工具链的平台依赖行为导致测量不一致”——这一选择保证了实验的可重复性，但与工业实际严重脱节：工业界不会使用未优化的 eager 模式作为部署基准，而是通过 TorchDynamo（CPU/GPU）、Ascend CANN（NPU）、TPU Compiler（TPU）等工具链实现 2-10 倍性能提升（论文未提及但符合行业常识）。
2. **评估体系的局限性**：论文的 SpeedUp@k 仅衡量“LLM 生成核相对 eager 模式的加速”，但未对比“LLM 生成核与工具链优化后原生核的性能”。例如，论文 4.3 节提到 LLM 生成的核通过“核融合”“稀疏性利用”实现加速，但这类优化在工业级工具链中已属标配（如 TensorRT 的自动核融合、CANN 的稀疏计算支持）——若 LLM 生成核仅比 eager 模式快，却慢于工具链优化核，则无实际落地价值。
3. **筛选能力的不足**：当前评估体系仅能筛选“语法正确、比基础模式快”的核，但工业落地需额外满足“兼容性（如支持动态 shape）、稳定性（无 runtime 波动）、可维护性（代码可读性）”等指标，而这些均未纳入 MultiKernelBench 的评估范围（论文 3.5 节仅关注编译、正确性、性能三指标）。
:::

### 问题 3. 论文提出的“类别感知单样本提示”虽能提升性能，但本质是通过同类别示例传递语法范式（如 Matrix Multiply 类的 AscendC API 调用方式），却未触及“硬件特异性逻辑适配”（如 AscendC 的 cube 单元矩阵计算流程、Pallas 的 block 维度约束）。这种提示策略是否仅解决了“表层语法正确性”，而无法突破“深层硬件逻辑理解”的天花板？未来是否需要更细粒度的“硬件-类别双维度提示”，且这种提示的标注成本是否会抵消 LLM 自动生成的效率优势？

类别感知提示:mdnice-bold-italic[本质上【仅】解决“表层语法正确性与类别特异性范式”，【未突破】“深层硬件逻辑理解”的天花板]；“硬件-类别双维度提示”的标注成本会显著上升，:mdnice-bold-italic[可能在部分场景【抵消】 LLM 的效率优势]。具体来说：

::: block-1
1. **类别感知提示的局限性**：论文 4.4 节的实验表明，该策略的核心价值是“传递同类别代码的语法范式与 API 调用习惯”（如 Matrix Multiply 类的 AscendC cube 单元调用格式），但无法解决“深层硬件逻辑适配”问题：
2. **“硬件-类别双维度提示”的标注成本挑战**：论文当前的类别示例需“手动从官方文档（如 AscendC samples）、开源库（如 PyTorch ATen）收集并验证”（3.3 节），已涉及 3 名资深核开发者的人工审核。若进一步细分“硬件-类别”维度（如 AscendC 的 Matrix Multiply 需区分 2D/3D 张量、FP16/FP8 精度，Pallas 的 Activation 需区分 per-element/per-tile 计算），则：
3. **效率优势的抵消风险**：LLM 自动生成的核心价值是“降低人工开发成本”，但若为构建细粒度提示需投入大量人工标注（如为 252 个细分场景各制作 1 个高质量示例，可能需数十人天），则在“中小规模核开发（如企业内部定制 10-20 个核）”场景中，标注成本可能超过 LLM 节省的开发成本——仅在“大规模核开发（如覆盖上百个核的通用库）”场景中，才能通过复用提示抵消标注成本。
:::

## 一、引言

深度学习模型的执行从根本上依赖于深度学习核函数的执行，这些核函数是使用底层并行编程语言实现的，例如用于英伟达图形处理器的 CUDA 和用于华为神经网络处理器的 AscendC（华为推出的面向昇腾神经网络处理器的底层核函数编程模型，能直接访问硬件的异构计算单元）。

编写正确且高性能的核函数是一个耗时的过程，需要深厚的硬件特定专业知识。:mdnice-bold-italic[近年来大型语言模型的发展为自动生成此类核函数提供了极具前景的方法。特别是，已有研究提出了多个核函数基准测试[23,29]，用于评估大型语言模型的能力，并为该领域的未来研究提供支持。]

### 1.1 研究空白

> 然而，我们对现有基准测试的分析表明，它们存在三个主要局限性：

#### 局限1：平台支持有限

**大多数现有基准测试【仅】关注英伟达图形处理器**，忽略了其他广泛使用的平台，如华为神经网络处理器和谷歌张量处理器。

这些平台同样需要核函数开发，但其带来的独特挑战在很大程度上仍未得到探索。此外，由于:mdnice-bold-italic[现有基准测试[23,29]采用紧耦合设计] ——将:mdnice-bold-italic[构建和评估流程与英伟达图形处理器生态系统紧密绑定] ——要扩展它们以支持多平台并非易事。

#### 局限2：缺乏详细分类

**现有基准测试要么完全不对核函数进行分类** [23]，要么采用过于**粗糙的分类** 方式（例如，将复杂度分为 3 或 4 个等级）[29]。这种分类粒度的缺失会带来问题，即使在同一等级内，大型语言模型生成的核函数性能也存在很大差异，这一现象就证明了这一点。

例如，在我们的实验中，DeepSeek-V3 在卷积类别的 CUDA 核函数上的正确率为 0%，而在激活类别的 CUDA 核函数上的正确率却超过 80%——但在现有基准测试[29]中，这两类核函数被归为同一难度等级。

#### 局限3：核函数分布不均衡

虽然大多数类别包含数量合理的核函数，但有些类别中的核函数数量极少，而且某些重要类别（如优化器核函数）完全缺失，导致**评估范围不均衡** 且不充分。

### 1.2 MultiKernelBench 介绍

> 为解决这些局限性，我们提出了 MultiKernelBench——一个全面的多平台基准测试套件，用于评估大型语言模型在深度学习核函数生成方面的能力。

与以往仅关注英伟达图形处理器的基准测试不同，MultiKernelBench **支持多种硬件平台**，包括英伟达图形处理器（基于 CUDA）、华为神经网络处理器（基于 AscendC）和谷歌张量处理器（基于 Pallas，一种构建在 JAX 生态系统之上的高级核函数编程接口），:mdnice-bold-italic[能够进行更贴近实际且应用范围更广的评估]。我们根据深度学习**核函数的功能特征对其进行分类**，并**在 KernelBench[29]的任务集基础上进行扩展，补充了缺失的类别并扩充了现有类别。**

总体而言，MultiKernelBench 包含 14 个定义明确的类别、285 项核函数生成任务，支持细粒度、与平台无关的评估。为确保可扩展性，我们实现了一个模块化后端抽象层，将平台特定逻辑与核心评估流程清晰分离。要支持新的硬件目标，只需为设备设置、编译、执行和资源管理实现一个统一的后端接口，而无需修改核心逻辑。

### 1.3 评估工作

我们还利用 MultiKernelBench 在不同设置下对一组大型语言模型进行了评估。我们选择了 7 个不同的大型语言模型，包括 DeepSeek、Qwen、GPT-4o 和 Claude，这些模型的:mdnice-bold-italic[参数规模从 320 亿到 6810 亿不等，既涵盖基础模型，也包括推理模型。]

为系统地评估核函数生成效果，我们报告了三个关键指标：

::: block-1
- Compilation@k：k 次生成中**至少一次编译成功** 的比例
- Pass@k：k 次生成中**至少一次通过正确** 性测试的比例
- $SpeedUp_{\alpha}@k$：k 次生成中**至少一次达到指定加速比**$\alpha$的比例
:::

这些指标涵盖了从基础编译成功到运行时加速的各个性能维度。我们设计了一个适用于多个平台的统一提示模板，并探索了不同的提示策略。

在默认设置下，我们将加法任务作为单样本示例，以展示基本的语法和格式。此外，我们还尝试从与目标任务相同的类别中选择单样本示例，帮助大型语言模型利用相关策略和领域特定知识。评估之后，我们进行了深入分析，包括失败原因诊断、类别级评估和加速案例研究。

我们的**实验揭示了几个关键发现**：:mdnice-bold-italic[【类别感知单样本提示】能显著提高模型在训练接触较少的平台 上的性能]，而且大型语言模型偶尔能发现有意义的优化方法，如**核函数融合** （将多个独立的核函数操作合并为一个，减少数据传输和 kernel 启动开销）和**利用数据稀疏性** （忽略数据中大量的零值或冗余信息，减少计算量）。

总之，本文的贡献如下：

::: block-1
1. 我们提出了 MultiKernelBench——首个用于核函数生成的多平台基准测试，涵盖图形处理器（GPUs）、神经网络处理器（NPUs）和张量处理器（TPUs）三大平台，包含 14 个类别、285 项任务。
2. 我们设计了一个可扩展的后端抽象层，将平台特定逻辑与核心评估流程解耦。通过实现统一的后端接口，即可添加新的硬件平台，从而便于在不同平台间进行集成和维护。
3. 我们提出了**一种简单但有效的类别感知单样本策略**，即:mdnice-bold-italic[从与目标任务相同的类别中选择一个示例核函数]。这种策略**通过提供领域特定模式，提高了大型语言模型的性能**，尤其在那些在大型语言模型训练数据中代表性不足的平台上效果显著。
4. 我们在 MultiKernelBench 上对 7 个大型语言模型在不同设置下进行了大量实验。我们的:mdnice-bold-italic[分析揭示了关于平台敏感性、类别级难度以及类别感知提示方法优势 的关键见解]。
:::

## 二、背景

### 2.1 深度学习计算硬件

更大的训练数据集和更多的模型参数让深度学习模型的性能更加强大，但同时也导致计算和存储需求大幅增加。传统的中央处理器架构已无法满足这些高强度需求。

为应对这一挑战，业界开发了多种定制化硬件解决方案，以加速深度学习的训练和推理过程。其中，英伟达（Nvidia）的图形处理器（GPU）、谷歌（Google）的张量处理器（TPU）和华为（Huawei）的神经网络处理器（NPU）是最具代表性的硬件，它们各自拥有独特的架构和设计理念。

| 深度学习计算硬件 | 英伟达 GPU | 谷歌 TPU | 华为 NPU |
| --- | --- | --- | --- |
| 核心设计目标 | 最初为图形渲染设计，后适配深度学习高效并行计算 | 专为深度神经网络的矩阵密集型计算设计 | 针对深度学习混合运算（标量+向量+矩阵），优化异构场景下的计算效率 |
| 关键硬件组件及说明 | 1. 数千个算术逻辑单元（ALU）：执行基本算术/逻辑运算2. 张量核心（Tensor Cores）：优化混合精度矩阵运算 | 数千个乘加单元：执行乘法-加法组合运算，单元直接连接形成大型物理矩阵 | 1. 标量单元：负责逻辑控制（如流程判断、跳转）2. 向量单元：处理按元素/向量运算3. 立方单元：专门执行矩阵计算 |
| 核心架构特点 | 依赖内存/寄存器存储矩阵运算中间变量，通过张量核心提升矩阵计算效率 | 乘加单元构成物理矩阵，矩阵乘法无需访问内存，减少数据交互延迟 | 异构架构设计，标量、向量、立方单元并行运作，功能特化且协同工作 |
| 优势 | 1. 支持高并行深度学习工作负载2. 张量核心加速混合精度矩阵运算3. 兼容主流框架与 CUDA 生态 | 大幅提升矩阵乘法等特定工作负载的性能，内存访问延迟极低 | 多类型运算并行处理，功能特化带来高计算效率，适配边缘低功耗场景 |
| 局限性 | 矩阵运算高度依赖内存/寄存器，分支任务适应性较弱 | 处理频繁分支或按元素运算的任务时，适应性较差 | 生态兼容性（如非国产框架适配）弱于 GPU/TPU |

### 2.2 深度学习核函数

> 要充分发挥深度学习加速器的性能，开发人员需要使用针对底层硬件定制的特定语言或库来编写程序。这些底层程序通常被称为“核函数”（Kernel），它们直接实现矩阵乘法、卷积、激活函数等计算原语（构成复杂计算任务的基本运算单元）。

#### CUDA

编写高效的核函数需要**密切关注内存层级结构** （不同速度、不同容量的存储设备组成的层级体系，如寄存器、缓存、内存，合理利用可减少数据访问延迟）、**并行性** （多个计算任务同时执行的能力）以及**硬件特定特性。**

CUDA 是英伟达的并行计算平台和编程模型，开发人员可借助它编写 GPU 加速代码。CUDA 通过允许对线程、内存和执行层级进行细粒度控制，充分释放 GPU 的海量并行能力。

AscendC 是华为为昇腾（Ascend）NPU 设计的底层核函数编程模型。它可直接访问硬件的异构计算单元（标量、向量、立方单元），并允许对内存传输和执行队列进行精确控制。

### 3.1 基准测试套件概述

> 图 2 展示了 MultiKernelBench 的整体框架。该基准测试套件使用参考 PyTorch 模块定义核函数任务，其中`forward`方法会调用官方算子，同时还会提供指定核函数需处理数据的输入张量。

- 每个核函数任务会与平台特定指令结合后输入到大型语言模型中。
- LLM 会生成两个组件：目标平台的定制化核函数实现，以及调用该定制化核函数的定制化 PyTorch 模块代码。
- 生成完成后，基准测试套件会启动构建流程，将所有 LLM 生成的输出编译为可执行的 PyTorch 模块，目标是在匹配原始模块功能的同时提升性能。
- 最后，使用相同的输入张量分别执行生成的模块和参考模块，以验证正确性并评估性能。

#### 输入

我们设计了一个适用于多平台核函数生成的统一提示词模板。如图 2 所示，每个提示词包含两部分：

::: block-1
1. :mdnice-bold-italic[平台特定指令，用于定义系统角色、描述任务]，并提供一个说明所需输出的单样本示例（单样本提示词，即通过一个示例引导模型生成符合要求的结果）；
2. :mdnice-bold-italic[目标核函数任务，包括待转换的 PyTorch 模块及其输入张量]。第二部分在所有平台上保持一致，而平台特定差异主要体现在单样本示例中。
:::

每个示例均以一个核函数任务（通常是加法任务）开头，随后是平台特定格式的描述和输出内容，帮助 LLM 掌握领域规范和所需的输出结构。

#### 输出

对于 CUDA 和 Pallas 平台，预期输出是自包含的 Python 代码。

::: block-1
- 在 CUDA 场景下，输出包括以 Python 字符串形式嵌入的 C++核函数代码，以及一个在`forward`函数中通过`cpp_extension`[8]（PyTorch 提供的用于集成 C++/CUDA 代码的工具）调用该核函数的 PyTorch 模块。
- 对于 Pallas 平台，输出包含一个用`pallas_call`包装的 Python 定义核函数，以及将该核函数编译并封装为 PyTorch 兼容模块的 JAX 与 PyTorch 集成代码。
- 对于 AscendC 平台，输出包括主机代码、分块配置、设备代码和 PyTorch 模块等结构化组件。如 3.4 节所述，这种输出格式是为支持后续编译而设计的。
:::

### 3.3 核函数任务

> 现有基准测试套件 KernelBench[29]提供了 250 个用于评估大型语言模型的核函数任务。这些任务按难度分为三个等级，涵盖卷积、不同输入形状的矩阵乘法等多种主题。

尽管 KernelBench 为核函数任务评估提供了坚实基础，但仍存在一些**局限性**：首先，其:mdnice-bold-italic[仅基于三个粗略难度等级的分类方案] 缺乏进行详细分析所需的粒度，无法区分同一难度等级下不同任务的差异；其次，该基准测试套件:mdnice-bold-italic[遗漏了几类重要的核函数运算]，导致其全面性不足。

为解决这些问题，我们:mdnice-bold-italic[基于核函数运算的功能语义，而非仅依赖难度等级，提出了一种新的分类体系]。我们通过系统化流程构建了更广泛、更具代表性的核函数任务分类：

::: block-1
1. **现有任务初步分类**：首先根据计算模式（如归约运算、矩阵乘法）和在典型深度学习流程中的功能角色（如激活函数、归一化层），对 KernelBench 中的 250 个核函数任务进行分类。
2. **通过核函数库审查识别缺口**：随后，我们审查了 PyTorch 原生 CUDA 核函数库[7]，判断每个核函数是否可归入现有类别。无法归入现有类别的核函数被列为新类别的候选对象。
3. **整合与细化**：对候选核函数进行系统化分类，并由三位拥有三年经验的核函数开发人员通过讨论细化类别定义，确保分类的完整性和一致性。
4. **删减稀疏和低影响类别**：根据三位开发人员的共识，移除代表性任务极少或与常见深度学习场景相关性较低的类别。例如，由于比较相关的核函数过于简单，对 LLM 性能评估的影响可忽略不计，因此将其排除在外。
:::

通过上述流程，我们最终确定了 14 个功能类别，涵盖了范围广泛且具有代表性的核函数运算，包括调整大小（Resize）、归约（Reduction）、归一化（Normalization）和索引（Indexing）等。

> 与 KernelBench 相比，我们新增了：
>
> 1. 广播（Broadcast）、调整大小（Resize）和优化器（Optimizer）三个类别，
> 2. 以覆盖之前未涉及的运算；
> 3. 同时扩展了原本仅包含两个任务的索引（Indexing）类别，使其更符合实际应用场景。
>
> 新任务从现有核函数库[7]中筛选得出，经过细化和人工验证，确保其具有实际相关性和全面的覆盖范围。

### 3.4 平台特定编译

> 生成核函数后，MultiKernelBench 会将 LLM 生成的文本转换为可执行的 PyTorch 模块，以便进行后续评估。

- **针对 Pallas 和 CUDA 平台生成的输出已是自包含的 Python 代码**。编译流程只需从文本中提取代码，并使用`exec`[6]（Python 的内置函数，用于执行动态生成的 Python 代码）动态执行即可。而像使用`nvcc`编译 CUDA 源代码这类实际构建过程，会由`cpp_extension`[8]等工具自动处理。此外，对于 CUDA 平台，应启用设备端断言（以进行故障分析。
- **对于 AscendC 平台，构建过程更为复杂**。与 CUDA 和 Pallas 不同，:mdnice-bold-italic[AscendC 没有提供可直接从 Python 中自动编译和绑定这些组件的工具]。因此，如 3.2 节所述，我们定义的 AscendC 输出格式包含多个组件。MultiKernelBench 使**用粘合脚本将这些组件组织成所需的文件结构**，执行 AscendC 编译流程，并生成可执行的 PyTorch 模块。

### 3.5 评估方法

> MultiKernelBench 使用三个关键指标自动评估生成核函数的质量：编译成功率、正确性和性能。

#### 评估指标1：编译成功率

MultiKernelBench 根据 3.4 节所述的平台特定构建过程中是否出现异常，来判断编译是否成功。由于 CUDA 和 AscendC 使用类 C/C++语言，与基于 Python 的 Pallas 相比，它们在编译阶段能捕获更多错误。该指标反映了模型理解平台语法和语言特定约束的最低要求。

#### 评估指标2：正确性

为评估正确性，MultiKernelBench 采用了与先前研究[29,36]类似的方法，通过随机测试验证核函数输出。它生成 N 个随机输入，并将这些输入分别输入到 LLM 生成的模块（产生输出`output_{llm}`）和参考模块（产生输出`output_{ref}`）中。若核函数满足以下条件，则认为其正确：

$$
|output_{llm} - output_{ref}| < atol + rtol \times |output_{ref}|
$$

其中，`atol`（绝对容差，用于允许固定的微小差异，如因浮点数精度问题导致的微小误差）用于处理固定的微小差异，`rtol`（相对容差，误差范围随参考输出的大小成比例变化，用于处理与输出量级相关的误差）则随参考输出的大小成比例变化，以处理比例误差。

我们遵循先前研究的设置来确定参数：$N=5$，$atol=1e-2$（即 0.01），$rtol=1e-2$（即 0.01）。先前的研究[29]发现，在 CUDA 平台上，五次随机测试的结果通常与一百次测试的结果一致。我们在 AscendC 和 Pallas 平台上也复现了这一现象，证实少量测试通常足以评估正确性。相对较大的容差值也能适应可能降低精度的优化（如使用 BF16 或 FP8 精度，这两种是比常用的 FP32 精度更低的浮点数格式，可减少内存占用和计算延迟，但会损失部分精度）。

#### 评估指标3：性能

MultiKernelBench 使用**平台特定方法测量性能**。

- 对于 CUDA 和 AscendC 平台，我们在:mdnice-bold-italic[核函数执行前后放置同步标记] [10,11]（用于记录时间点的标记，确保准确测量核函数执行的起始和结束时间，避免其他任务干扰），通过计算两个标记之间的时间差来得到执行时间。
- 然而，在 Pallas 当前的接口中，尚无此类同步标记可用。因此，我们使用调试工具来测量执行时间。

为确保一致性，我们**在不同时间在同一台机器上进行了实验**，证实所有三个平台的计时方法都是稳定的，且方差控制在较小范围内。

### 3.6 用于多平台评估的可扩展后端抽象

> 为实现跨不同硬件平台的核函数基准测试，我们引入了一种模块化后端架构，将平台特定逻辑与核心评估流程清晰地解耦。

**每个平台都由一个统一的“后端”（Backend）接口的专用子类提供支持**。该接口封装了以下核心职责：

::: block-1
1. 设备初始化和硬件识别（初始化硬件设备，识别设备型号、性能参数等信息）；
2. 核函数代码编译和执行；
3. 正确性验证和性能测量；
4. 资源清理和内存管理（释放不再使用的计算资源和内存空间，避免资源泄漏）。
:::

基准测试框架在运行时会根据指定的平台名称动态加载相应的后端。:mdnice-bold-italic[要支持新的硬件平台，只需使用`@register_backend(<platform>)`装饰器实现并注册一个新的后端类，无需修改任何核心评估逻辑]。这种基于插件的设计确保系统具有可扩展性和可维护性，只需最少的工程工作量就能轻松适配新兴的加速器架构。

## 四、实验

在本节中，我们在多种配置下对一组大型语言模型（LLM）进行了实验，并对结果进行了分析。具体而言，我们旨在解决以下三个研究问题：

::: block-1
- **研究问题 1（RQ1）**：当以“加法任务”作为单示例提示时，所评估的大型语言模型表现如何？
- **研究问题 2（RQ2）**：不同任务类别间的性能差异如何？
- **研究问题 3（RQ3）**：对于训练数据中曝光较少的平台，同类示例能否提高大型语言模型生成内核的正确性？
:::

::: image-caption

> 表 3 列出了实验中使用的七种大型语言模型。这些模型**在规模、设计和功能能力上存在差异**，涵盖了从通用语言生成到高级推理的广泛应用场景。

- DeepSeek-V3-0324 和 DeepSeek-R1-0528 是深度求索（DeepSeek）系列中最新、最强大的开源模型，分别代表了基础模型和推理模型类别中的最先进性能，两者均拥有 6850 亿参数。GPT-4o 是目前可用的最强大的专有基础模型之一；

- Qwen2.5-Coder 是一个相对精简的 320 亿参数模型，主要针对代码进行训练，代表了小型领域专用大型语言模型。
- Qwen3-235B[37]具有独特性，它在单个 2350 亿参数模型中集成了两种不同的运行模式——推理模式（“think”模式）和非推理模式，能够直接对比推理增强对各类任务性能的影响。

#### 报告的指标

- 与之前关于代码生成的研究[21,30,42]一致，我们采用广泛**使用的“Pass@k”指标来评估功能正确性**。在该指标下，每个问题生成 k 个代码样本，若至少有一个样本通过所有测试用例，则认为该问题已解决。
- **“Compilation@k”** 表示在 k 个生成样本中，至少有一个样本**编译成功的问题所占比例**；
- **“SpeedUpₐ@k”** 通过统计至少有一个样本**相较于预定义基准实现达到至少 α 倍（例如 2 倍）加速的问题比例**，来衡量运行时性能。

为确保性能测量的一致性和可重复性，我们将基准实现的评估限制在 PyTorch 的即时执行模式（eager mode）下，排除了 TorchDynamo 及其他编译模式——因为这些模式具有平台依赖性，可能导致测量结果不一致。我们针对 k=1 和 k=5 两种情况，报告了所有指标（Pass@k、Compilation@k 和 SpeedUpₐ@k）的结果。

::: block-1
- 对于 k=1，我们使用贪心解码（温度参数 temperature=0.0）来评估模型的最优预测解决方案；
- 对于 k=5，我们采用随机采样（温度参数 temperature=0.2，累积概率 top-p=0.95），以在生成输出的多样性和质量之间取得平衡，这一做法遵循了先前代码生成基准中的既定流程[16,17]。
:::

参考先前研究[29]，我们未对推理型模型应用随机采样，因为这类模型的推理时间和计算成本显著更高。

#### 模型性能对比

Claude-Sonnet-4 作为性能最强的编程模型之一，在整体任务通过数量上位居第一。两个推理型模型——DeepSeek-R1 和 Qwen3-235B（启用“think”模式），分别以第二和第三的任务通过数量紧随其后，这体现了强化学习在提升模型能力方面的有效性。

相比之下，Qwen2.5-Coder-32B 生成的正确内核数量最少，这表明较小的参数规模可能对性能产生负面影响。值得注意的是，尽管 DeepSeek-R1 在 CUDA 内核上表现出色，但在昇腾 C（AscendC）和帕拉斯（Pallas）内核上的性能落后于非推理型模型，在帕拉斯平台上的 Pass@k 得分在所有七个模型中最低。这可能是由于 DeepSeek-R1 相对较高的幻觉率[3]，以及其训练语料中昇腾 C 和帕拉斯代码的曝光量有限共同导致的。

> #### 结论
>
> 1. MultiKernelBench 是测试大型语言模型的挑战性基准；
> 2. 具有推理增强功能的模型总体表现更优，而像 Qwen-32B 这样的小型模型性能较差，这表明推理能力和模型规模均会对性能产生影响。

#### 平台对比

模型性能在不同平台间存在显著差异，这主要反映了训练语料覆盖范围的不同。

在 CUDA 平台上：

- GPT-4o 实现了最高的 Compilation@1 率（97.5%），表明其语法与 CUDA 规范的契合度很高；
- 而 DeepSeek-R1 在 Pass@1 和 SpeedUp₁@1 上表现最佳，说明其在 CUDA 代码优化能力方面更具优势。

相比之下，大多数模型在昇腾 C 和帕拉斯平台上的性能大幅下降：

- DeepSeek-V3 在昇腾 C 平台上的表现最佳，但 Pass@1 也仅为 2.5%，其他所有模型的 Pass@1 均低于 2.1%。

在帕拉斯平台上：Claude-Sonnet-4 以最高的 Pass@1（8.4%）和 Pass@5（10.5%）领先，而在 CUDA 平台上表现出色的 DeepSeek-R1 则排名最低，Pass@1 仅为 2.8%。:mdnice-bold-italic[这些平台特异性差异表明，模型的有效性与训练数据中相关示例的存在高度相关]；:mdnice-bold-italic[模型在昇腾 C 和帕拉斯平台上表现较弱，很可能是因为当前大型语言模型的预训练语料中，这两种平台的相关数据代表性不足。]

> #### 结论
>
> 模型性能具有高度的平台依赖性，这反映了 CUDA、昇腾 C 和帕拉斯在训练语料覆盖范围上的差异。

#### 失败原因分析

##### 分析1：CUDA 平台

在 CUDA 平台上，编译错误相对少见——尽管 CUDA 语法类似 C 语言且复杂度较高，但由于其文档丰富且在互联网上的覆盖范围广泛。然而，生成功能正确的内核对大型语言模型而言仍是一项重大挑战。即使是性能最佳的模型 Claude-Sonnet-4，其 Pass@1 也仅为 47.0%，Pass@5 为 55.8%，这意味着仍有许多任务以失败告终。我们对已编译内核的失败模式进行分析后发现：

- 输出不匹配是主要的运行时错误，占失败案例的 53.0%；输出形状不匹配占 16.1%；
- CUDA 运行时错误占 15.9%。

这些结果表明，:mdnice-bold-italic[即使在 CUDA 这样文档完善的领域，大型语言模型在推理精确的输出语义和数据结构对齐方面仍面临困难。]

##### 分析2：昇腾 C 平台

针对昇腾 C 平台的内核，**其编译错误率最高，这主要是因为大型语言模型对昇腾 C 的核心概念** （如单指令多数据（SIMD）计算、数据传输和内存管理）**理解有限** ——即使以加法内核作为单示例提示也是如此。

![文章插图](/articles/2025-08-31-multikernelbench-gpu-npu-tpu-kernel-aea94f84/images/10.webp)

::: image-caption
图 3：昇腾 C（AscendC）编译错误示例
:::

如图 3 所示，在 softmax 等任务中，大型语言模型生成的代码会直接调用不存在的函数（如 `AscendC::Softmax`），从而导致编译错误。这反映出预训练语料中昇腾 C 代码的曝光量不足，限制了模型生成该平台有效代码的能力。

##### 分析3：帕拉斯平台

对于帕拉斯平台，尽管其公开可用的**数据也很有限**，但由于它基于 Python 构建，许多**在 C/C++中常见的编译类错误被转移到了运行时错误中。** 尽管 Comp@1 相对较高，但对性能最佳的模型 Qwen3-235B 进行深入分析后发现，其 Pass@5 仅为 6.3%。失败日志显示：

- 最常见的运行时异常是“意外关键字参数（Unexpected Keyword Argument）”，占比 22.4%，这表明大型语言模型经常会虚构帕拉斯 API 中不存在的关键字。
- 另一种常见的失败模式是错误提示“帕拉斯 TPU 降级目前仅支持秩（rank）≥1 的块（blocks）”，占失败案例的 5%。这很可能是因为帕拉斯目前不支持标量值作为输入、输出或中间计算结果。

> #### 结论
>
> 1. 即使在 CUDA 这样文档完善的平台上，大型语言模型在保证功能正确性方面仍存在困难；
> 2. 昇腾 C 平台上较高的编译错误率表明，模型对该**平台特定语法的理解有限**；
> 3. 帕拉斯平台易出现运行时错误，主要由 API 使用不当导致。

在昇腾 C 和帕拉斯平台上，大型语言模型生成的内核仅在少数类别中取得成功。“激活函数”类别在所有三个平台上均是最容易的类别，这可能是因为其数学结构相对简单。相比之下，“归约”和“矩阵乘法（Matrix Multiply）”等在 CUDA 平台上表现良好的类别，在昇腾 C 和帕拉斯平台上的 Pass@1 均为 0，这表明**内核生成存在平台特异性挑战和偏好差异。**

> #### 结论
>
> 1. 大型语言模型在“激活函数”等简单类别上表现出色，但在“卷积”等复杂任务上存在困难，**任务难度差异显著；**
> 2. 在 CUDA 平台上表现优异的类别（如“归约”“矩阵乘法”）在昇腾 C 和帕拉斯平台上完全失败，说明内核生成的泛化能力存在平台特异性限制。

### 4.4 研究问题 3：同类单示例提示

研究问题 1 和研究问题 2 的实验均以加法内核作为单示例提示，结果显示模型在昇腾 C 和帕拉斯两个平台上的通过率极低。这很可能是因为这两种语言在大型语言模型的训练数据中占比有限。

> 我们认为，尽管加法内核能提供基本的语法和使用模式，但无法传递更复杂或特定任务所需的领域知识。每个类别通常需要独特的领域知识和编码规范，:mdnice-bold-italic[例如在华为神经网络处理器（NPU）上，矩阵乘法和通用数学运算使用不同的计算单元，且遵循不同的编程范式。]

表 8 和表 9 展示了使用这种“同类单示例提示”策略的结果。由于篇幅限制，我们仅报告了在该设置下通过率最高的三个模型的结果。除了每个类别的三个标准指标（Comp@1、Pass@1 和 SU₁@1）外，我们还报告了相较于默认设置（以加法任务为提示）的性能提升。对于每个模型，我们增加了一列以展示 Pass@1 的绝对提升量（即新值减去基准值）。此外，最后一行总结了每个指标的平均相对提升量，计算方式为相对于基准值的百分比增幅。

:mdnice-bold-italic[在昇腾 C 内核方面，使用同类单示例提示显著提高了编译成功率和执行成功率]。例如，GPT-4o 的编译成功率相对提升了 380%，正确性（Pass@1）相对提升了 160%。在类别层面，最显著的提升出现在“矩阵乘法”类别：默认设置下，所有模型均无法生成正确的内核；而通过同类单示例提示，模型开始生成有效的输出——尽管仍未实现运行时加速。这些**结果表明，同类示例能为大型语言模型提供有价值的领域知识，帮助其更好地理解硬件特异性编程模式和约束，最终同时提升编译成功率和正确性。**

尽管整体性能有所提升，但大型语言模型在生成部分昇腾 C 类别的正确内核时仍存在困难，例如“归一化”和“归约”类别。以“归约”类别为例，我们的分析显示，许多生成的内核无法正确处理三维输入张量，而单示例提示仅使用了二维张量。这凸显了:mdnice-bold-italic[模型在“形状特异性推理”方面的普遍局限性]。这些观察结果表明，**有必要进一步细化分类（可能基于输入张量形状），并开发“形状感知提示策略”**，以更好地引导大型语言模型准确处理此类情况。

:mdnice-bold-italic[在帕拉斯内核方面，模型的通过率大幅提升，相对增幅超过 100%，这表明精心选择的同类示例在引导大型语言模型生成正确内核方面发挥着关键作用]。与昇腾 C 不同，帕拉斯平台的所有类别均实现了性能提升。**这种差异可能源于帕拉斯语言的简洁性：大多数示例程序比昇腾 C 的对应程序短得多**，且将底层硬件特异性优化委托给了底层编译器。:mdnice-bold-italic[这些发现表明，设计能抽象底层实现细节的高级领域专用语言，有助于大型语言模型更轻松地生成正确且高效的代码]，从而提升此类语言在人工智能辅助编程中的可用性。

> #### 结论
>
> 1. 同类单示例提示显著提升了大型语言模型在训练曝光量有限平台上的性能；
> 2. 在帕拉斯平台上，所有类别均实现了显著的性能提升，这可能得益于其简洁的语法和编译器管理的优化。

## 五、有效性威胁

- 第一个有效性威胁在于我们**基准测试的构建，包括参考实现和示例内核**。为减轻这一威胁，我们:mdnice-bold-italic[手动审查] 了所有添加的内核，并通过:mdnice-bold-italic[编译和执行测试验证] 了其正确性。
- 第二个威胁涉及我们研究结果**对其他大型语言模型的可推广性**。为应对这一问题，我们选择了一组:mdnice-bold-italic[多样化的模型，涵盖从小规模（320 亿参数）到超大规模（6810 亿参数）的范围]，同时包括开源模型（DeepSeek、Qwen）和专有模型（GPT-4o）。
- 第三个威胁是**我们的结果能否推广到其他硬件平台和编程语言**。 随着深度学习加速器领域的不断扩展（如 AMD 的 HIP 平台和更通用的 Triton 框架），这一问题日益重要。为实现:mdnice-bold-italic[可扩展性，我们的基准测试包含了一个后端抽象层，只需最少的工作量即可集成新平台或语言]。例如，支持 Triton 框架仅需添加不到 20 行代码。我们计划在未来的工作中纳入此类平台。

## 六、相关工作

### 6.1 基于大语言模型（LLM）的代码生成

大语言模型（LLMs）在根据自然语言提示生成源代码方面展现出了令人瞩目的能力。DeepSeek 系列[26,27]、LLaMA 系列[20,32,33]、GPT 系列[13,15]等通用模型在代码生成任务中均表现出强劲性能。这些模型通过在包含代码和自然语言的大规模数据集上进行训练，学习编程模式、语法规则以及问题解决策略。

> 为进一步提升代码生成能力，许多研究方法会对性能优异的**基础模型** 进行:mdnice-bold-italic[持续预训练] 和:mdnice-bold-italic[代码专用指令微调。]

- 例如，Code Llama[30]和 DeepSeek-Coder-V2[18]分别以 LLaMA 2 和 DeepSeek-V2 为基础，利用来自 GitHub 公共仓库及相关文本的数万亿额外令牌（token，指文本处理中的基本单位，可理解为单词、字符或子词）进行进一步训练。
- 在持续预训练之后，通常会通过指令微调来提高模型与任务的对齐度。WizardCoder[28]、Magicoder[35]、DataScope[24]等模型采用为编码任务量身定制的合成指令数据，进一步提升了模型性能。

> 尽管取得了这些进展，挑战依然存在——尤其是在**生成需要深度上下文理解或领域专用 API 的正确代码方面**。:mdnice-bold-italic[检索增强生成] （RAG，一种结合检索外部知识来辅助生成的技术）已成为解决这些问题的潜在方向。

- 例如，RePoCoder[39]将基于相似度的检索器与预训练代码大语言模型集成到迭代式检索-生成流程中，以支持仓库级代码补全任务；
- 类似地，“仓库级提示生成器”（Repository-Level Prompt Generator）[31]通过筛选有用的代码片段，将领域知识注入提示中，从而生成特定于示例的提示；
- DocPrompting[40]则通过检索相关文档片段来增强代码生成效果。

### 6.2 代码生成基准测试

> 评估代码生成模型需要多样化且严谨的基准测试，这些基准测试需**在不同抽象层级上同时评估代码的功能正确性和质量**。

- 在**函数层级**，HumanEval[17]和 MBPP[14]等数据集通过单元测试验证生成代码的正确性，开创了代码生成评估的先河，至今仍广泛用于评估大语言模型在简短、独立编程问题上的性能。

为探索更复杂的生成场景，后续基准测试将评估粒度扩展到更高层级：

- ClassEval[19]评估**类层级** 的代码生成，DevEval[22]和 RepoEval[39]则评估模型在仓库级任务上的性能，包括长上下文推理和多文件一致性保障。

> **早期基准测试大多聚焦于通用编码任务** （如算法设计），而:mdnice-bold-italic[近年来的研究则逐渐转向领域专用或库密集型 代码生成。]

- 例如，ODEX[34]和 TorchDataEval[38]评估模型使用科学计算或数据加载专用库的能力；
- DOMAINEVAL[42]提出了一种自动化基准构建流程，针对密码学、系统编程等领域专用任务；
- 类似地，BigCodeBench[43]评估模型在数据分析、Web 开发等高级多步骤任务上的表现，这类任务需要整合多种 API 和函数调用，与真实世界的软件工程场景高度相似。

> 生成硬件高效内核是一个极具挑战性且影响重大的领域，在该领域中，模型不仅需生成功能正确的代码，还需确保代码具备较高的运行性能。

KernelBench[29]和 TritonBench[23]等基准测试便聚焦于这一任务：

::: block-1
- KernelBench 包含 250 个内核任务，并使用 fast@p 指标联合评估代码的正确性和加速比；
- TritonBench 则评估 184 个真实世界的 Triton 算子，重点关注其在 NVIDIA GPU 上的功能和性能分析。
:::

然而，这两个基准测试均局限于 NVIDIA 生态系统，忽略了其他重要硬件平台。为解决这一问题，:mdnice-bold-italic[MultiKernelBench 通过支持多种后端，构建了一个更全面、平台无关的评估框架。]

## 七、结论

> 随着不同硬件平台对高效深度学习内核开发的需求不断增长，利用大语言模型实现内核自动生成已变得愈发重要。

然而，当前的基准测试在广度、粒度和可扩展性方面存在不足，无法满足严谨评估的需求。

::: block-1
在本研究中，我们提出了 :mdnice-bold-italic[MultiKernelBench——首个用于深度学习内核生成 的全面、多平台基准测试套件]。该套件覆盖图形处理器（GPU）、神经网络处理器（NPU）和张量处理器（TPU）三类硬件平台，包含 14 个功能类别的 285 个任务。

通过对 7 个不同类型的大语言模型进行实验，我们发现模型**性能在不同平台和内核类别间存在显著差异**。值得注意的是，我们提出的一种简单的“**类别感知提示策略** ”（category-aware prompting strategy，即根据目标任务所属类别提供同类示例作为提示的方法），:mdnice-bold-italic[显著提升了模型在 AscendC 和 Pallas 平台上的生成性能。]
:::

总体而言，MultiKernelBench 为基准测试和改进大语言模型在深度学习系统编程中的应用提供了一个贴合实际且可扩展的基础，将助力未来在核生成与优化领域的研究。
