::: block-1

:::

## 一、 背景与挑战：为何我们需要摆脱自动调优？

### 1. GEMM：从算法到硬件的映射艺术

广义矩阵乘法定义为：

$$
C = \alpha A B + \beta C
$$

其中 $C \in \mathbb{R}^{M \times N}$， $A \in \mathbb{R}^{M \times K}$， $B \in \mathbb{R}^{K \times N}$。其最朴素的实现是一个三层嵌套循环。

::: block-1
在 GPU 上实现高性能 GEMM 的关键在于**层次化分块**。其核心思想是：将庞大的输出矩阵 $C$ 分解为多个小块（Tile），并利用 GPU 的多级存储和并行计算单元进行协同处理。

典型的“输出固定”数据流如 Algorithm 2 所示：将 $M$ 和 $N$ 维度在计算单元间进行空间上的并行划分，而将 $K$ 维度在时间上顺序累加。
:::

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/03.webp)

::: image-caption
Algorithm 2：分块矩阵乘法调度。算法引入 $M^T$（M 维度分块）、$N^T$（N 维度分块）、$K^T$（K 维度分块）参数，通过 SCHEDULETILE 函数在计算单元（CU）、wave 层面调度分块。在空间上并行处理 M/N 维度分块，时间上迭代 K 维度分块，是 tritonBLAS 层级分块架构的核心调度逻辑
:::

分块参数的选择是一场精密的权衡游戏：

- **并行性**：分块越小，产生的输出块越多，越能充分利用 GPU 上大量的计算单元。
- **局部性**：分块越大，每个数据块在被换出缓存前能被重用的次数越多，减少了昂贵的内存访问。

这里举一个例子：对于矩阵大小 $M=N=256, K=8192$，若选择分块尺寸 $(M_T, N_T, K_T) = (16, 16, 256)$，将产生 $16 \times 16 = 256$ 个输出块，正好可以映射到一个拥有 256 个计算单元（CU）的 GPU 上，实现完全并行。若选择 $(256, 256, 128)$ 的分块，则只产生 1 个输出块，整个计算将落在一个 CU 上，造成巨大的计算资源闲置。

### 2. 自动调优的“阿喀琉斯之踵”

以 Triton 为代表的现代 GPU 编程框架，通过高级语言抽象简化了内核开发，但其高性能严重依赖自动调优系统。**用户需要预先定义一个候选配置空间** 如不同的分块尺寸、warp 数量等。当内核首次被某个问题形状调用时，框架会：

1. 编译所有候选配置。
2. 在 GPU 上逐一运行并测量耗时。
3. 选择最快的配置并缓存。

> 这种方法的弊端显而易见：

- **高昂的开销**：编译和基准测试耗时与候选配置数量、问题规模成正比。对于动态形状或实时应用，此开销不可接受。
- **搜索空间限制**：性能严重依赖于用户定义的配置空间是否完备。穷举搜索在面对海量可能的矩阵形状时**不具备可扩展性**。
- **可移植性差**：在 A 显卡上调优出的最优配置，在 B 显卡上可能表现平平甚至糟糕。

## 二、 tritonBLAS 的核心创新：用分析模型取代“试错”

> tritonBLAS 的雄心在于：**不运行任何候选内核，仅通过一个分析模型，直接预测出给定问题在目标硬件上的近似最优配置**。其核心是一个**分层性能模型**，:mdnice-bold-italic[它将 GEMM 操作分解，并量化评估硬件架构与算法结构之间的相互作用。]

### 1. 设计目标：清晰而务实

- **接近最优性能**：对广泛矩阵形状达到近似最优。
- **零调优**：无需运行时搜索。
- **轻量快速**：选择配置的额外开销微乎其微。
- **确定性**：相同输入总是产生相同选择，确保可复现性。
- **架构可移植**：仅依赖可测量的硬件参数（带宽、指令延迟等），通过微基准测试校准即可适配新硬件。

tritonBLAS 性能模型的起点是**精确刻画 GPU 的层次化分块结构**。如下表 1 所示，对于 AMD MI300X GPU，分块层次自底向上包括：

## 三、 深入模型：如何量化并行性与局部性？

### 1. 量化并行性：从矩阵核心到芯片满载

> tritonBLAS 从三个层面量化并行性对性能的影响：

- **a) 矩阵核心级并行**：这是由 GPU 硬件决定的固定吞吐量。例如，一个 MFMA 指令可能在固定周期 $L_{MI}$ 内完成一个 $MI_M \times MI_N \times MI_K$ 的小矩阵乘。这是一个已知的硬件常数。
- **b) 计算单元内部并行**：一个工作组分块（位于共享内存中）需要被一个 CU 内的多个 SIMD 协作完成。其计算延迟可以通过将工作组分块尺寸分解为多个 MFMA 指令来估算（论文中 Algorithm 3）。

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/06.webp)

::: image-caption
Algorithm 3 | 计算共享内存分块的计算延迟。算法以矩阵指令维度（$MI_M、MI_N、MI_K$）和延迟 $LM_I$ 为输入，先计算处理共享内存分块所需的矩阵指令总数 $NM_I$，再乘以单条指令延迟得总计算延迟 $LM_T$。为 tritonBLAS 量化共享内存分块的计算开销提供了确定性公式
:::

- **c) 计算单元间并行（占用率）**：这是决定性能的关键。tritonBLAS 将 $M$ 和 $N$ 维度的输出块在 GPU 的各个 CU 之间进行分配。**占用率** 取决于输出块总数与 GPU CU 总数之比。

::: block-1
一个重要洞察是“**波次量化** ”问题：由于输出块总数不一定能被 CU 总数整除，:mdnice-bold-italic[最后一波（timestep）可能只有部分 CU 在工作，造成计算资源利用不足]。tritonBLAS 通过 Algorithm 4 （见后文）精确计算最后一波的活跃 CU 数，从而更准确地建模整体占用率。
:::

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/07.webp)

::: image-caption
图 2 | 计算单元（$CU_0、CU_1、CU_2$）在不同时间步 $\text{timpstep}(0), \text{timpstep}(1), \text{timpstep}(2)$ 的占用率示例。该图直观呈现了 GPU 计算单元（CU）的任务分配规律，核心体现作者强调的 “尾占用” 问题 —— 仅最后一个时间步存在计算单元未充分利用的情况。而 Algorithm 4 正是基于此规律，通过问题维度（M、N、K）与瓦片尺寸（MT、NT、KT）计算最后时间步的活跃 CU 数量，进而精准评估整体计算延迟。实际计算中，可假设除最后一步外其他时间步均为 100% 占用，这一简化既保证精度，又降低了模型复杂度
:::

上图是跨时间步（timestep）的占用率示意图，可以看出只有最后一个时间步是“未满载”的。

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/08.webp)

::: image-caption
Algorithm 4 | 计算最后一个时间步的活跃计算单元数。结合问题维度（$M、N、K$）、分块尺寸（$MT、NT、KT$）与总计算单元数（$NCU$），算法先算 $M/N$ 维度分块数，再推导输出分块总数（Tout），最终得到最后时间步的活跃 CU 数与波数（ω），解决 “尾占用” 问题，提升延迟估算精度
:::

### 2. 量化局部性：软件管理与硬件缓存的共舞

局部性分为两类：

- **软件管理局部性**：通过显式使用共享内存，程序员可以精确控制数据在 SIMD 内和 SIMD 间的复用。
- **硬件管理局部性**：由 GPU 的 L1/L2 缓存透明管理，其行为需要被预测。

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/09.webp)

::: image-caption
Algorithm 6 | 计算缓存范围内计算单元数的所有分块因子组合。对缓存域内的计算单元数 $\text{CU_Cache}$ 进行因式分解，生成所有满足 $f_m × f_n = N_{\text{CU_Cache}}$ 的因子对（$f_m, f_n$）。tritonBLAS 借助这些组合选择最优缓存分块形状，例如优先选接近正方形的组合以最大化数据复用
:::

**缓存行为预测** 是模型的精髓。tritonBLAS 首先通过 Algorithm 6，根据共享同一缓存的 CU 数量，枚举所有可能的长方形缓存分块形状（例如，16 个 CU 可以排成 1x16, 2x8, 4x4 等）。通常，最接近正方形的形状（如 4x4）能最大化缓存内数据的重用。

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/10.webp)

::: image-caption
Algorithm 5 | 基于分块维度估算缓存命中率。算法通过未缓存读取量（U，由缓存分块与共享内存分块维度计算）和总读取量（R），按公式 h=1-U/R 估算命中率。假设高层缓存按低层分块交互，为 tritonBLAS 建模内存延迟、优化数据局部性提供关键指标
:::

随后，利用 Algorithm 5 估算缓存命中率。其基本思想是：**高层缓存以底层分块为单位进行交互**。通过计算未缓存读取与总读取的比率，得到命中率 $h$。模型还会将每一步的**工作集大小** 与**缓存有效容量** 对比，若超出则按比例降低预测命中率，从而捕捉容量限制效应。

### 3. 权衡的艺术：并行性 vs. 局部性

> 最优分块并非单纯追求最高并行性或最强局部性，而是**寻找两者之间的最佳平衡点，使单次迭代（K 维度一步）的延迟最小**。由于软件流水线的存在，单次迭代的最终延迟是**计算延迟** 和**内存延迟** 的较大值。

tritonBLAS 将可能遇到的瓶颈归纳为几类：

| 瓶颈类别 | 核心描述 | 解决方案 |
| --- | --- | --- |
| 加载/存储指令发射率瓶颈 | 加载/存储单元的占用率不足，无法提供足够的带宽以支撑计算需求 | 提高加载/存储单元的占用率，确保数据传输能力与计算需求匹配 |
| 软件管理内存带宽瓶颈 | 已充分利用共享内存实现数据复用，但计算性能受限于从共享内存加载数据的带宽 | 增大寄存器分块尺寸，最大化从软件管理内存（如共享内存）加载数据的复用率 |
| 缓存带宽瓶颈 | 硬件管理的缓存（如L2、LLC）因带宽有限，成为限制计算性能的瓶颈 | 提高软件管理内存（如共享内存）中的数据复用率，减少对硬件缓存带宽的依赖 |
| 计算单元占用不足瓶颈 | 已占用的计算单元（CU）中矩阵指令利用率较高，但整体计算单元占用数量不足，无法达到最大吞吐量 | 展开K维度循环或调整分块尺寸，提高计算单元的整体占用率 |
| 最大并行计算瓶颈 | 所有计算单元均被占用，且因软件流水线无内存瓶颈，矩阵指令利用率处于较高水平，已达到硬件最大可实现性能 | 无需进一步优化，此状态下已实现最优性能 |

**这些目标常常相互冲突**：例如，为了提高并行性（占用率）而缩小分块，却可能损害缓存局部性。tritonBLAS 的分析模型正是通过第一性原理，估算不同分块选择下的计算与内存延迟，来导航这个复杂的权衡空间。

## 四、 从模型到实践：如何计算 GEMM 总延迟？

> tritonBLAS 将上述所有量化指标整合为一个最终的性能评估指标：**预测的 GEMM 总延迟**。这个过程分为三步（Algorithm 7/8/9 见本节末尾）：

1. **计算单次迭代延迟**：利用 Algorithm 7，结合各级缓存的命中率和带宽，计算完成一次 K 维度分块计算所需的内存延迟 $L_{mem}$，并与计算延迟 $L_{compute}$ 取最大值，得到流水线迭代延迟 $L_{looper}$。
2. **计算单个输出块延迟**：一个输出块的计算包含流水线“序章”（加载数据）、“主循环”（多次迭代）和“尾声”（写回结果）。其总延迟 $L_{tile}$ 由 Algorithm 8 计算。
3. **计算整个 GEMM 延迟**：根据输出块总数、CU 总数和每个输出块的延迟，通过 Algorithm 9 计算出整个 GEMM 运算的预测总延迟 $L_{total}$。

**这个预测的 $L_{total}$ 就是 tritonBLAS 为不同分块配置进行排名的“分数”**。模型会为给定问题评估所有合法的分块配置，选择预测延迟最小的那个。整个过程完全基于分析和计算，**无需运行任何内核代码**。

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/11.webp)

::: image-caption
Algorithm 7 | 计算一次循环迭代的内存延迟。通过整合各级缓存命中率（$H_1、H_2$）、带宽（$R_1、R_2$ 等）、活跃 CU 数，分别计算 CU 级、L1/L2 缓存及全局内存的延迟，取最大值作为内存瓶颈延迟。为 tritonBLAS 分析内存与计算瓶颈的权衡提供数据支撑
:::

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/12.webp)

::: image-caption
Algorithm 8 | 计算完成一个输出分块的延迟。算法纳入内存延迟$L_{mem}$、计算延迟$L_{compute}$、活跃 CU 数，叠加前导延迟（数据加载）和尾随延迟（结果写入），再加上循环迭代延迟（$L_{loopiter}×I$），得到单输出分块延迟，是总 GEMM 延迟计算的基础模块
:::

![文章插图](/articles/2026-01-17-amd-tritonblas-886f65ff/images/13.webp)

::: image-caption
Algorithm 9 | 计算总矩阵乘法（GEMM）延迟。先根据 $M/M_T、N/N_T$ 计算分块数（$n_m、n_n$），再推导波数（$N_\text{waves}$，即分块总数与总 CU 数的比值向上取整），最终用单输出分块延迟（$L_\text{tile}$）乘以波数得总延迟，是 tritonBLAS 筛选最优分块配置的核心量化依据
:::

## 六、 相关工作：站在巨人的肩膀上

> tritonBLAS 并非首个尝试用分析模型优化 GEMM 的工作，但其在 GPU 和 Triton 语境下的系统化实现独具特色：

- **CUTLASS/cuBLAS**：使用基于经验的启发式规则选择分块，但规则闭源且与 NVIDIA 执行模型深度耦合。
- **TVM/Ansor**：结合分析模型与基于学习的修正项来剪枝搜索空间，但仍依赖数据驱动拟合，不适合需要零样本确定性预测的场景。
- **DeLTA**：提出感知局部性的屋顶线模型，用于分析预定义内核的性能。而 tritonBLAS 更进一步，直接用于生成和选择配置。

::: block-1
tritonBLAS 的独特之处在于，它**将完整的、基于第一性原理的分析模型深度集成到 Triton JIT 编译流程中**，实现了:mdnice-bold-italic[从建模、选择到代码生成的全栈式、零调优解决方案。]
:::

## 七、 总结与展望

> tritonBLAS 向我们展示了一条通向高效 GPU 计算的新路径：**用严谨的分析和建模代替昂贵的“试错”**。它通过一个:mdnice-bold-italic[层次化、参数化的性能模型，精确量化了 GPU 上 GEMM 操作的并行性、局部性及其复杂权衡，从而能够在微秒级时间内为任意矩阵形状确定接近最优的内核配置。]

这项工作的意义深远：

1. **极大降低部署门槛**：消除了生产环境中令人望而却步的调优开销，使得高性能 GEMM 能够快速适配动态变化的工作负载。
2. **提升开发效率**：为库开发者和研究者提供了一个强大的分析工具，可以快速评估不同算法和硬件设计对性能的潜在影响。
3. **推动性能可移植性**：基于硬件参数的模型使其能够更平滑地跨不同代际、不同厂商的 GPU 进行迁移。

当然，tritonBLAS 目前聚焦于单 GPU 上的标准 GEMM。未来，其框架有望扩展到**多 GPU 分布式计算**、**更复杂的类 GEMM 算子** （如各种注意力机制）以及**更广泛的张量计算领域**。

::: block-1
在追求算力极致的时代，:mdnice-bold-italic[tritonBLAS 代表了一种思维的转变：从“盲目搜索”到“精准计算”]。它告诉我们，通过深刻理解硬件与算法的内在规律，我们完全可以**用“数学”算出最快的代码**。这不仅是技术的进步，更是工程美学的一种体现。
:::
